Deep Dive: Stage 1 — The Decorator's Elegant Solution

The Decorator Pattern offers a flexible alternative to subclassing for extending functionality. It involves creating a set of "decorator" classes that wrap the original object, adding new responsibilities transparently. Both the original component and the decorators share a common interface, allowing them to be used interchangeably. Each decorator adds its own behavior (e.g., modifies cost or description) before or after delegating the call to the wrapped component. This "wrapping" mechanism allows you to compose multiple features dynamically at runtime, avoiding the rigid structure of inheritance.

Deep Dive: Stage 2 — Crafting a Custom Coffee with Decorators

Here's how the Decorator Pattern works in practice, building a customizable coffee:

// ☕ The Component Interface
interface Coffee {
    String getDescription();
    double getCost();
}

// ☕ Concrete Component: The base item
class SimpleCoffee implements Coffee {
    public String getDescription() { return "Simple Coffee"; }
    public double getCost() { return 2.0; }
}

// 🎁 Abstract Decorator: Holds a reference to the wrapped object
abstract class CoffeeDecorator implements Coffee {
    protected Coffee decoratedCoffee;
    public CoffeeDecorator(Coffee coffee) {
        this.decoratedCoffee = coffee;
    }
    // Delegates to the decorated object by default
    public String getDescription() { return decoratedCoffee.getDescription(); }
    public double getCost() { return decoratedCoffee.getCost(); }
}

// 🥛 Concrete Decorator: Adds Milk
class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee coffee) { super(coffee); }
    public String getDescription() { return decoratedCoffee.getDescription() + ", Milk"; }
    public double getCost() { return decoratedCoffee.getCost() + 0.5; }
}

// 🍬 Concrete Decorator: Adds Sugar
class SugarDecorator extends CoffeeDecorator {
    public SugarDecorator(Coffee coffee) { super(coffee); }
    public String getDescription() { return decoratedCoffee.getDescription() + ", Sugar"; }
    public double getCost() { return decoratedCoffee.getCost() + 0.2; }
}

// 🚀 Usage Example
public class CoffeeShop {
    public static void main(String[] args) {
        Coffee myCoffee = new SimpleCoffee(); // Start with a simple coffee
        System.out.println(myCoffee.getDescription() + ": $" + myCoffee.getCost());
        // Output: Simple Coffee: $2.0

        myCoffee = new MilkDecorator(myCoffee); // Decorate with Milk
        System.out.println(myCoffee.getDescription() + ": $" + myCoffee.getCost());
        // Output: Simple Coffee, Milk: $2.5

        myCoffee = new SugarDecorator(myCoffee); // Decorate with Sugar
        System.out.println(myCoffee.getDescription() + ": $" + myCoffee.getCost());
        // Output: Simple Coffee, Milk, Sugar: $2.7
    }
}

⚠️ Failure Modes & Degraded Operation

When to Decorate (and When Not To)

Use the Decorator Pattern when you need to add responsibilities to individual objects dynamically and transparently, without affecting other objects. It's excellent for adhering to the Open/Closed Principle (open for extension, closed for modification). However, it can lead to many small objects if overused, potentially making debugging more complex due to the chain of delegated calls. Consider it for streaming APIs (like Java I/O streams), UI components that add borders/scrollbars, or dynamically adding logging/monitoring to existing objects.
