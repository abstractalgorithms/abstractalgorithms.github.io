Design a Distributed Lock
with Fencing Tokens.

When multiple microservices access a shared resource (such as executing payments, generating sequence numbers, or writing to shared storage), local process mutexes fail. Design a distributed lock service that guarantees mutual exclusion, handles client crashes, and prevents split-brain writes caused by JVM Stop-The-World (STW) pauses and clock drift.

R

Define the boundaries.

Requirements · 4 minutes
SAY THIS: “Before proposing a topology for Design a Distributed Lock with Fencing Tokens, I’ll clarify the core functional requirements, burst characteristics, data volume, and availability SLOs to define rigid system boundaries.”
Background financial invoice reconciliation worker holding a distributed Redis lock (Redlock) with a 30-second TTL. Failure cascade dynamic: 50k Mut. → Row X-Lock → Spinlock Thrash → Deadlock Graph → 💥 DB Freeze.

What the system does

  • Mutual exclusion: Exactly one worker can hold the lock for a given resource at any instant.
  • Deadlock-free: Locks must automatically expire via a lease Time-To-Live (TTL) if a worker crashes.
  • Fault tolerance: If a lock server node dies, locks must remain consistent without granting duplicates.
  • Fencing: Protect downstream storage from delayed writes issued by workers whose locks expired during GC pauses.

What to agree on

  • Latency: Lock acquisition and release should complete in under 5 ms.
  • High availability: The lock manager must survive single-node infrastructure outages.
  • Clock drift: System must remain safe even if physical system clocks jump or drift by seconds.

S

Keep state shared and partitioned.

Storage · 3 minutes
SAY THIS: “I’ll separate low-latency ephemeral cache state from authoritative durable storage, ensuring strict consistency where needed and partitioning for scale.”

Cache / Ephemeral state

state:{partitionKey}:activeWindow

  • In-memory key-value cache (Redis Cluster / Memcached).
  • TTL expiration matching window validity bounds.
  • Hash tags to co-locate keys for atomic Lua scripts or transactions.

Durable / Authoritative store

  • Distributed NoSQL / relational database (DynamoDB, PostgreSQL).
  • Durable write-ahead log with replica failover.
  • Cache-aside pattern: read misses warm cache from durable store.
  • Asynchronous CDC / event streaming to telemetry sinks.

Local-only node state is not a shared cluster quota: N nodes could admit roughly N × the configured limits. Ensure state co-location and transactional boundaries align with partition keys.

D

Make state mutations atomic.

Detailed design · 7 minutes
SAY THIS: “For the critical execution path, we enforce idempotency and concurrency controls using atomic primitives, avoiding lock contention and split-brain states.”
  1. Client sends POST /acquire-lock with resource ID, client ID, and lease TTL (e.g., 10 seconds).
  2. The lock manager atomically grants the lock and returns a monotonically increasing Fencing Token (e.g. Token 34).
  3. Client performs work and passes the Fencing Token in all write headers to downstream storage.
  4. The storage layer tracks the highest observed token (TmaxT_{max}Tmax​). If a write arrives with T<TmaxT < T_{max}T<Tmax​, the write is rejected immediately.
  5. If the client experiences a 10s GC pause and its lease expires, Client B acquires the lock with Token 35. When Client A wakes up and attempts to write with Token 34, Storage rejects it.

E

Stress-test the design.

Evaluation · 6 minutes
SAY THIS: “The biggest operational risks involve node failover, partition skew, network isolation, and cascading downstream backpressure. Here is how we mitigate each.”
Ingress Admission

Naive unconstrained buffering causes queue bloat and GC exhaustion. Mitigation: Bounded ingress gate with fast non-blocking shedding.

Resource Strategy

Static capacity allocations collapse under brownouts. Mitigation: Dynamic adaptive limits scaling to real-time physical bounds.

Outage Impact

Cascading lock convoys and memory saturation. Mitigation: Isolated failure domains keep P99 latency flat and protected.

Cascading Failure

Worker 1 acquires lock, starts processing, but hits an unexpected 35-second database freeze. The Redis lock TTL expires at t=30s. Worker 2 acquires the lock and begins writing. Worker 1 recovers at t=35s and completes its write, silently corrupting shared state.

Breakdown Chain

50k Mut. → Row X-Lock → Spinlock Thrash → Deadlock Graph → 💥 DB Freeze

Shedding Failure

Without fast rejection at the boundary, queued dead work triggers multi-second GC pauses, CPU thrashing, and cascading 504 Gateway Timeouts.
