03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Why Seconds_Behind_Source=0 and routing all reads to primary fail.

Why this matters: The problem: see what breaks without Why Seconds_Behind_Source=0 and routing all reads to primary fail under real concurrency or scale.

Two naive workarounds break under load:

  • Routing all reads to Primary: Destroys the >= 80% read offload across the 4 replicas, overloading the single writer.
  • Trusting Seconds_Behind_Source = 0: In MySQL, 0 only means the SQL thread caught up to the I/O thread's currently fetched relay log—if the I/O thread is stalled, the replica still serves stale data.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Redis Sticky-Primary Window + GTID Causal Tokens.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Preserve >= 80% replica offload while guaranteeing RYOW and < 50 ms read bounds:

  • Sticky-Primary Redis Window (ryow:user:{id}): On PATCH, set a short Redis key (TTL = 5 s) after the DB commits. While present, GET routes directly to the Primary (zero replica lag).
  • GTID Causal Verification: Return gtid_executed from the Primary commit (source_uuid:tx_id). Replicas run SELECT WAIT_FOR_EXECUTED_GTID_SET(gtid, 0.05) (50 ms max); if it times out (!= 0), fail over that single read to Primary.
  • Write-Through Cache Invalidation: Delete/update Redis after DB commit (never before) so concurrent reads never repopulate Redis from a stale replica.
RYOW Routing Architecture

Sticky-Primary Window & Bounded GTID Wait

1.5s Sticky Window: Recent mutators read from Primary for 5s, eliminating replica lag on immediate page reloads.

2.50ms GTID Gate: If a replica has not applied the caller's GTID within 50ms, fall back to Primary immediately.

3.Security-Critical Paths: RBAC permission checks bypass stale replicas or read from Primary/consistent cache.

Combining a 5s Redis sticky-primary flag with a 50ms GTID wait guarantees RYOW without sacrificing 80%+ replica offload.

STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Read-Your-Own-Writes patterns are used in production.

Why this matters: Scope boundary: identify where this pattern fits best and where simpler or async alternatives win.

Causal session consistency is essential in read-heavy, single-writer relational architectures:

  • Identity, MFA & RBAC Services: Guarantees revoked tokens/roles take effect immediately.
  • E-Commerce Cart & Profile Updates: Ensures users see their newly added address or payment method.
  • Multi-Region Read Replicas: Uses LSN/GTID watermarks in Postgres/MySQL to avoid global cross-region locks.
