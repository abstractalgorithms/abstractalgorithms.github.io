STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why Bounded Blocking Queues Matter.

In a telemetry pipeline with 16 producer threads bursting to 150,000 events/sec and 8 consumer threads, an unbounded LinkedBlockingQueue caused 4 GB JVM OOM crashes during downstream outages. Replacing it with a naive synchronized queue caused deadlocks and IndexOutOfBoundsException.

Constraints:

  • Zero Thread.sleep polling / busy-waiting.
  • Fixed array-backed ring buffer (O(1) enqueue/dequeue, zero per-node GC allocation).
  • Sustain 150,000 ops/sec across 24 concurrent threads with clean InterruptedException handling.
02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Real-World Impact of Unbounded or Broken Queues.

Queue misconfigurations break both memory safety and thread liveness:

  1. OOM Crashes: Unbounded queues absorb downstream stalls in heap until the JVM hits OutOfMemoryError.
  2. Missed Signals & Deadlocks: Calling notify() on a single monitor wakes an arbitrary thread—a producer can wake another producer when the queue is full, leaving consumers asleep forever.
  3. Spurious Wakeup Corruption: Using if (count == capacity) instead of while lets a woken thread overwrite an unconsumed slot or underflow count.
Bounded Ring Buffer Synchronization

Separate notFull & notEmpty Condition Queues

Separate Condition queues ensure producers only wake consumers and consumers only wake producers, eliminating missed signals.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive Solution (and Why It Breaks).

Using synchronized (this) with if (count == items.length) wait(); and notify() has three fatal bugs: (1) if fails on spurious wakeups or when another producer steals the freed slot before the woken thread re-acquires the lock; (2) notify() cannot target consumers vs. producers, causing lost wakeups; (3) notifyAll() causes thundering-herd context switches across all 24 threads.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise Solution: Circular Ring Buffer + Dual Condition Queues.

Implement an ArrayBlockingQueue-style ring buffer with ReentrantLock and two Condition queues:

  • Fixed Ring Buffer (Object[capacity]): Maintain putIndex, takeIndex, and count modulo capacity for O(1) operations and zero node allocation; null out items[takeIndex] on dequeue so GC can collect consumed objects.
  • while Guard + Separate Conditions: Producers await() on notFull in a while (count == items.length) loop and call notEmpty.signal(); consumers await() on notEmpty in while (count == 0) and call notFull.signal().
  • Timed offer/poll & Backpressure: Use awaitNanos(nanos) for bounded waiting and shed excess ingress with HTTP 429 rather than blocking Netty event loops.
Backpressure & Signal Flow

Producer Blocking, Signal Handoff & Timed Shedding

Targeted signal() wakes one waiting counterpart without thundering herds, while timed offer() enforces bounded backpressure.

import java.util.Objects;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class BoundedBlockingQueue<T> {
    private final Object[] items;
    private int putIndex, takeIndex, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();

    public BoundedBlockingQueue(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity must be > 0");
        this.items = new Object[capacity];
    }

    public void put(T item) throws InterruptedException {
        Objects.requireNonNull(item);
        lock.lockInterruptibly();
        try {
            while (count == items.length) {
                notFull.await();
            }
            enqueue(item);
        } finally {
            lock.unlock();
        }
    }

    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) {
                notEmpty.await();
            }
            return dequeue();
        } finally {
            lock.unlock();
        }
    }

    public boolean offer(T item, long timeout, TimeUnit unit) throws InterruptedException {
        Objects.requireNonNull(item);
        long nanos = unit.toNanos(timeout);
        lock.lockInterruptibly();
        try {
            while (count == items.length) {
                if (nanos <= 0L) return false;
                nanos = notFull.awaitNanos(nanos);
            }
            enqueue(item);
            return true;
        } finally {
            lock.unlock();
        }
    }

    private void enqueue(T item) {
        items[putIndex] = item;
        if (++putIndex == items.length) putIndex = 0;
        count++;
        notEmpty.signal();
    }

    @SuppressWarnings("unchecked")
    private T dequeue() {
        T item = (T) items[takeIndex];
        items[takeIndex] = null; // prevent GC retention
        if (++takeIndex == items.length) takeIndex = 0;
        count--;
        notFull.signal();
        return item;
    }
}

// Fail-fast backpressure with 429 shedding
if (!queue.offer(event, 50, TimeUnit.MILLISECONDS)) {
    metrics.counter("telemetry.dropped.backpressure").increment();
    return Response.status(429).build();
}

STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Bounded Blocking Queues Apply in System Design.

Bounded ring buffers are the backbone of high-throughput in-process pipelines:

  • Log & Telemetry Shippers: Absorbs micro-bursts while applying backpressure (429) when disk/network sinks stall.
  • Thread Pool Work Queues: Bounds ThreadPoolExecutor queues instead of using unbounded LinkedBlockingQueue.
  • LMAX Disruptor / Two-Lock Queues: At >1M ops/sec, splitting takeLock and putLock (like LinkedBlockingQueue) or using lock-free CAS ring buffers eliminates producer-consumer contention.
