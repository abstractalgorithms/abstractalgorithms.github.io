01 / UnderstandFailure & constraints

Clarify what is failing.

A reader misses Redis, reads v1 from DB, pauses while a writer commits v2 and deletes Redis, and then wakes up to write v1 into the empty Redis key.

Design objective

T1: Reader misses Redis.

Requirements

  • Prevent a slow cache-miss reader holding `v1` from overwriting or repopulating Redis after `v2` has been committed.
  • Also prevent two concurrent writers (`v2` vs `v3`) from leaving `v2` in Redis due to thread interleaving.
  • Maintain < 5ms p99 read latency on cache hits and zero distributed lock bottlenecks on reads.
  • Support both Cache-Aside (minimal infra) and CDC-based designs with clear trade-offs.

Constraints

  • PostgreSQL 16 supports `BIGINT` `version` columns and `RETURNING version` on `UPDATE`.
  • Redis 7 supports atomic server-side Lua scripts (`EVALSHA`).
  • Application code must be in Java or Python.
Known failure modes

35+ silent data reversions per day under 30k QPS.

  1. 01Reader Fetches v1: On cache miss, reader queries PostgreSQL and receives (data_v1, ver=1), then pauses.
  2. 02Writer Atomically Increments Version: PostgreSQL atomically increments row version to 2 and commits.
  3. 03Writer Stamps v2 in Redis: Writer atomically stores ver=2 (either new payload or 30s tombstone) in Redis.
  4. 04Late Reader Attempts Stale Write: Delayed reader wakes up and attempts to populate Redis with ver=1.
  5. 05Lua CAS Rejects v1: Redis sees stored ver=2 >= incoming ver=1 and rejects the stale write, preserving v2.
Stamping `ver=2` in Redis (via `cas_set` or a 30s tombstone) ensures any delayed `ver=1` reader is atomically rejected.

The invariants

  • Register LUA_CAS_SET on Redis startup.
  • On write, commit DB with version = version + 1 and call cas_set(key, new_ver, payload, 3600, 0) (or tombstone).
  • On read miss, fetch (payload, ver) from DB and call cas_set.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Delayed Double Delete relies on a heuristic sleep (`500ms`) that fails whenever a reader pauses longer than 500ms (e.g., GC pause or slow replica) and adds 500ms latency or async queue complexity.

Step 1

Compare heuristic timing (500ms window) vs deterministic version comparison (ver1 < ver2).

Step 2

Note that Delayed Double Delete also fails to order two concurrent writers (v2 vs v3) if their second DELs reorder.

Step 3

Choose Versioned Lua CAS when a version column can be added to the DB.

JAVA · Lifecycle trace
// Delayed Double Delete (heuristic fallback when DB schema cannot be altered)
public void updateWithDoubleDelete(long id, ProfileDto dto) {
    db.update(id, dto);
    redis.del("profile:" + id);
    scheduler.schedule(() -> redis.del("profile:" + id), 500, TimeUnit.MILLISECONDS);
}
Key trade-off

Delayed Double Delete requires no DB schema changes, but leaves a probabilistic gap under >500ms stalls.

04 / ImplementConfiguration & code

Build the safeguards.

If the replica is 400ms behind, the miss-reader fetches `v1` even *after* `v2` committed; if a tombstone is present, `cas_set` rejects `v1`, and the reader must fall back to the primary.

1. Reference implementation

PYTHON · Solution
LUA_CAS_SET = """
local cur = redis.call('HGET', KEYS[1], 'ver')
if cur and tonumber(cur) >= tonumber(ARGV[1]) then
    return 0  -- Reject stale or duplicate version
end
redis.call('HSET', KEYS[1], 'ver', ARGV[1], 'data', ARGV[2], 'tomb', ARGV[3])
redis.call('EXPIRE', KEYS[1], tonumber(ARGV[4]))
return 1
"""

def update_profile(db, redis, cas_sha, user_id, new_fields):
    row = db.execute(
        "UPDATE profiles SET bio = %s, version = version + 1 WHERE id = %s RETURNING version, bio",
        (new_fields['bio'], user_id)
    ).fetchone()
    # Stamp v2 directly (or tombstone='1' with ttl=30)
    redis.evalsha(cas_sha, 1, f"profile:{user_id}", row.version, row.bio, "0", 3600)

2. Harden for scale

If the replica is 400ms behind, the miss-reader fetches `v1` even *after* `v2` committed; if a tombstone is present, `cas_set` rejects `v1`, and the reader must fall back to the primary.

PYTHON · Scale hardening
def read_profile(db_primary, db_replica, redis, cas_sha, user_id):
    cached = redis.hgetall(f"profile:{user_id}")
    if cached and cached.get(b'tomb') == b'0':
        return cached[b'data'].decode()
    # Tombstone active -> bypass lagging replica and hit primary!
    db = db_primary if cached.get(b'tomb') == b'1' else db_replica
    row = db.fetch_profile(user_id)
    if redis.evalsha(cas_sha, 1, f"profile:{user_id}", row.version, row.bio, "0", 3600) == 0:
        return redis.hget(f"profile:{user_id}", "data").decode()
    return row.bio

3. Operational controls

Step 1

If Redis returned `tombstone=1` (meaning a recent write occurred), route the miss-read directly to the primary DB.

Step 2

Alternatively, pass `cas_set` result: if `cas_set` returns `0`, re-read Redis to get `v2`.

Step 3

Keep replica lag monitored and alert above `100ms`.

Implementation note

Zero distributed locks on reads while guaranteeing 100% monotonic cache state.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

When Debezium -> Kafka is the sole writer to Redis for a keyspace (or readers only read, never write back), there are no concurrent reader-writer races.

  • ↗
    Route all DB mutations through PostgreSQL WAL -> Debezium -> Kafka (partitioned by `user_id`).
  • ↗
    A single consumer per partition updates Redis sequentially in exact commit LSN order.
  • ↗
    Read-only API pods never `SET` Redis on a miss—they only query DB on miss.
YAML · Verification
# Single-writer CDC pipeline removes reader-SET race completely
kafka_topic: pg.public.profiles
partition_key: id   # Guarantees strict LSN order per user_id
redis_ttl: 3600     # Refreshed by CDC on every commit

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Reading `v1` from a lagging replica when Redis was cold (no tombstone) still requires a safety TTL.

Failure scenario 2

If an API pod also runs `redis.set()` on miss without Lua CAS, the race reappears.

Alternatives considered

  • Keep Cache-Aside + Lua CAS when read-your-own-writes (<5ms) is mandatory.
