R

Define the boundaries.

Requirements · 4 minutes
SAY THIS: “Before proposing a topology for Design a Distributed Key-Value Store, I’ll clarify the core functional requirements, burst characteristics, data volume, and availability SLOs to define rigid system boundaries.”
Distributed KV stores partition data across nodes using Consistent Hashing, replicate each key across N nodes, and use quorum voting (R + W > N) for strong consistency or eventual consistency.

What the system does

  • put(key, value): store or update key-value pair.
  • get(key): retrieve value associated with key.
  • High availability and fault tolerance: survive node failures without data loss.
  • Horizontal scalability: scale storage and throughput by adding nodes.
  • Tunable consistency: support configurable R (read quorum) and W (write quorum).

What to agree on

  • Key size: up to 256 bytes; value size: up to 1 MB.
  • Low latency: p99 read and write under 10 ms within same datacenter.
  • Handle network partitions (CAP theorem AP system with eventual consistency).

S

Keep state shared and partitioned.

Storage · 3 minutes
SAY THIS: “I’ll separate low-latency ephemeral cache state from authoritative durable storage, ensuring strict consistency where needed and partitioning for scale.”

Cache / Ephemeral state

state:{partitionKey}:activeWindow

  • In-memory key-value cache (Redis Cluster / Memcached).
  • TTL expiration matching window validity bounds.
  • Hash tags to co-locate keys for atomic Lua scripts or transactions.

Durable / Authoritative store

  • Distributed NoSQL / relational database (DynamoDB, PostgreSQL).
  • Durable write-ahead log with replica failover.
  • Cache-aside pattern: read misses warm cache from durable store.
  • Asynchronous CDC / event streaming to telemetry sinks.

Local-only node state is not a shared cluster quota: N nodes could admit roughly N × the configured limits. Ensure state co-location and transactional boundaries align with partition keys.

D

Make state mutations atomic.

Detailed design · 7 minutes
SAY THIS: “For the critical execution path, we enforce idempotency and concurrency controls using atomic primitives, avoiding lock contention and split-brain states.”
  1. Consistent Hash Ring: Map key to ring position using hash(key). The first N distinct physical nodes clockwise from the key position store replicas.
  2. Virtual Nodes (tokens): Each physical node owns V virtual positions on the ring to distribute data uniformly.
  3. Write Path: Coordinator sends write to all N replicas. Waits for W ACKs before returning success. On local node: write to Commit Log (WAL) -> MemTable in RAM -> flush to SSTables on disk (LSM-Tree).
  4. Read Path: Coordinator requests data from R replicas. Compares version timestamps/vector clocks. Returns most recent version and triggers read repair asynchronously.

TYPESCRIPT · REFERENCE IMPLEMENTATION
// Tunable Quorum Consistency Evaluation (R + W > N)
export interface QuorumConfig {
  N: number; // Total replicas across cluster
  W: number; // Write quorum size
  R: number; // Read quorum size
}

export function evaluateQuorum(config: QuorumConfig): { isStronglyConsistent: boolean; model: string } {
  const { N, W, R } = config;
  if (R + W > N) {
    return {
      isStronglyConsistent: true,
      model: `Strong Consistency: R(${R}) + W(${W}) > N(${N}) guarantees read/write quorum overlap.`
    };
  } else {
    return {
      isStronglyConsistent: false,
      model: `Eventual Consistency: R(${R}) + W(${W}) <= N(${N}) allows stale reads for high availability.`
    };
  }
}

Avoid client-side read-modify-write loops without concurrency control. Use atomic scripts, row-level locks, or conditional mutations at the storage tier to guarantee linearizability.

E

Stress-test the design.

Evaluation · 6 minutes
SAY THIS: “The biggest operational risks involve node failover, partition skew, network isolation, and cascading downstream backpressure. Here is how we mitigate each.”
R + W > N (Strong Consistency)

At least one node in read quorum overlaps with write quorum, guaranteeing the latest value is read.

W=1, R=1, N=3 (Eventual Consistency / Fast)

Low latency and high availability, but high risk of reading stale data.

Last-Write-Wins (LWW) vs Vector Clocks

LWW uses wall-clock timestamps (simple, but clock drift can overwrite valid concurrent writes). Vector Clocks preserve concurrent versions for client reconciliation, but add metadata size.

Hinted Handoff

During node outage, neighboring nodes store writes tagged with a hint. When the node recovers, neighbors deliver the hinted writes.

Anti-Entropy with Merkle Trees

Nodes compare hierarchical hash trees (Merkle Trees) of their key ranges. Only branches with differences are synchronized across the network, minimizing transfer bandwidth.

Gossip Protocol failure detection

Nodes exchange heartbeats randomly with neighbors. If a node fails to heartbeat within timeout, consensus marks it down without central health monitor.

D

Close with the trade-offs.

Discussion · 5 minutes
SAY THIS: “In closing, we optimized for sub-millisecond p99 latency and high availability under partition. We trade strict distributed linearizability for predictable throughput and operational simplicity.”

If the interviewer asks…

  • R + W > N (Strong Consistency): At least one node in read quorum overlaps with write quorum, guaranteeing the latest value is read.
  • W=1, R=1, N=3 (Eventual Consistency / Fast): Low latency and high availability, but high risk of reading stale data.

Keep the conclusion focused

  • What guarantees are strictly enforced at runtime?
  • What happens during network partitions or node failures?
  • Which CAP trade-off was intentionally chosen and why?
