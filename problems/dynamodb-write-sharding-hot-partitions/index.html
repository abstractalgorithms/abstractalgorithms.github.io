01 / UnderstandFailure & constraints

Clarify what is failing.

Table-level metrics average across all physical partitions (e.g., 10 partitions), masking that 1 partition is pegged at its 1,000 WCU/s physical limit.

Design objective

10,000 WCU across ~10 physical partitions = 1,000 WCU per partition.

Requirements

  • Sustain 5,000 writes/sec (1 KB items = 5,000 WCU) and 25,000 reads/sec for a single celebrity merchant without throttling.
  • Support querying the merchant's most recent 50 transactions sorted by timestamp in < 25ms p95.
  • Avoid over-sharding small merchants who only generate 1-5 writes/sec.
  • Diagnose and alert on hot keys before throttling impacts checkout.

Constraints

  • DynamoDB hard-caps every physical partition at 1,000 WCU/sec and 3,000 RCU/sec.
  • Each physical partition is also capped at 10 GB of storage.
  • Client SDK retries must not amplify throttling into a retry storm.
Known failure modes

Throwing more provisioned WCU at the table without fixing the partition key.

  1. 01Deterministic Sharded Write: Ledger hashes `tx_id % 8` for celebrity merchants, spreading 5,000 WCU across 8 partitions (~625 WCU each).
  2. 02Hot Read Cache Lookup: Read path checks Redis/DAX first, serving 25,000 reads/sec in < 2ms without touching DynamoDB.
  3. 03Scatter-Gather on Cache Miss: On cache miss, service queries `MERCHANT#42#0..7` in parallel (`Limit=50`, `ScanIndexForward=False`).
  4. 04Merge-Sort Top 50: Application runs `heapq.nlargest(50)` by `SK` and caches the merged list for 1-5 seconds.
  5. 05Hot-Key Detection: CloudWatch Contributor Insights alerts when any single `PK` exceeds 700 WCU/s to trigger shard promotion.
Sharding hot keys across 8 partitions eliminates write throttling while Redis/DAX absorbs 25K/s reads.

The invariants

  • Compute shard = blake2b(tx_id) % shard_count.
  • Write with ConditionExpression='attribute_not_exists(sk)'.
  • Query all shard_count partitions concurrently and merge-sort top 50 by sk.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Global 16x sharding multiplies read requests by 16x for normal merchants; use tiered sharding and store a `shard_read_set` during upgrades.

Step 1

Default shard_count = 1 for 99% of merchants.

Step 2

When a merchant approaches 700 WCU/s, bump write_shards = 8 while keeping read_shards = 8 (since 0..7 includes shard 0, old items in MERCHANT#id#0 remain visible!).

PYTHON · Lifecycle trace
# Notice: shard 0 is a subset of shards 0..7!

Key trade-off

Using 0-indexed shards means upgrading 1 -> 8 requires zero data migration to keep old items readable.

04 / ImplementConfiguration & code

Build the safeguards.

Place a short-TTL Redis cache or DynamoDB Accelerator (DAX) in front of `read_latest_tx` to absorb 95%+ of repeated queries.

1. Reference implementation

PYTHON · Solution
import hashlib, heapq
from concurrent.futures import ThreadPoolExecutor

def write_tx(table, merchant_id: str, tx_id: str, ts_iso: str, payload: dict, shard_count: int = 8):
    h = int.from_bytes(hashlib.blake2b(tx_id.encode(), digest_size=4).digest(), 'big')
    shard = h % shard_count
    table.put_item(
        Item={'pk': f'MERCHANT#{merchant_id}#{shard}', 'sk': f'TX#{ts_iso}#{tx_id}', **payload},
        ConditionExpression='attribute_not_exists(sk)',
    )

def read_latest_tx(table, merchant_id: str, shard_count: int = 8, limit: int = 50) -> list:
    def q(s):
        return table.query(
            KeyConditionExpression='pk = :pk',
            ExpressionAttributeValues={':pk': f'MERCHANT#{merchant_id}#{s}'},
            ScanIndexForward=False,
            Limit=limit,
        )['Items']
    with ThreadPoolExecutor(max_workers=shard_count) as pool:
        batches = list(pool.map(q, range(shard_count)))
    return heapq.nlargest(limit, (item for b in batches for item in b), key=lambda x: x['sk'])

2. Harden for scale

Place a short-TTL Redis cache or DynamoDB Accelerator (DAX) in front of `read_latest_tx` to absorb 95%+ of repeated queries.

def get_latest_cached(redis_client, table, merchant_id: str, shard_count: int):
    key = f'latest:{merchant_id}'
    cached = redis_client.get(key)
    if cached:
        return json.loads(cached)
    items = read_latest_tx(table, merchant_id, shard_count=shard_count)
    redis_client.setex(key, 2, json.dumps(items))
    return items

3. Operational controls

Step 1

Cache the merged top-50 list in Redis under `latest:MERCHANT#42` with a 2-second TTL and singleflight/request-coalescing on miss.

Step 2

Even at 25,000 req/sec, DynamoDB sees only 1 scatter-gather every 2 seconds (< 200 RCU).

Implementation note

Using `hash(tx_id)` instead of `random()` preserves write idempotency across client retries.

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Using `0`-indexed shards means upgrading `1 -> 8` requires zero data migration to keep old items readable.—
Option 2Amazon DAX (transparent read-through cache, though requires VPC peering and doesn't cache scatter-gather merges).—

Review questions

Failure scenario 1

Cache stampede when the 2s key expires under 25K req/s (mitigate with singleflight or probabilistic early refresh).

Failure scenario 2

Setting `max_attempts=10` with synchronous threads exhausts worker pools during a partition hot-spot.

Alternatives considered

  • Legacy `standard` mode (lacks client-side rate pacing).

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Adaptive Capacity and On-Demand mode cannot bypass DynamoDB's hard 1,000 WCU / 3,000 RCU per-partition ceiling; break hot keys with deterministic write sharding (PK#0..N-1) and offload hot reads to DAX/Redis.
  • 02Trade-off tip: Using 0-indexed shards means upgrading 1 -> 8 requires zero data migration to keep old items readable.
  • 03Watch out for: Cache stampede when the 2s key expires under 25K req/s (mitigate with singleflight or probabilistic early refresh).
