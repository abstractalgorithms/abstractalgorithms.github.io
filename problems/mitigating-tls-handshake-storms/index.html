01 / UnderstandFailure & constraints

Clarify what is failing.

RSA-2048 private-key signing and ECDHE key exchange are computationally expensive asymmetric operations (~1 ms/handshake) compared to hardware-accelerated AES-GCM symmetric encryption.

Design objective

Profile Envoy with `perf top` and observe `RSA_private_decrypt` / `BN_mod_exp` dominating CPU.

Requirements

  • Absorb a simultaneous 120,000-connection drop without Envoy CPU exceeding 75% or handshake p99 exceeding 150 ms.
  • Support stateless TLS 1.3 session resumption across all 40 Envoy pods with automatic key rotation.
  • Eliminate synchronized thundering-herd reconnect loops from the 1,500 client pods.
  • Preserve strict mTLS client-certificate verification and forward secrecy.

Constraints

  • Envoy fleet is fixed at 40 pods x 4 vCPU (160 vCPU total) during the incident.
  • Session Ticket Encryption Keys (STEKs) must rotate at least every 12 hours for forward secrecy.
  • No disabling mTLS or downgrading to plaintext.
Known failure modes

Assuming scaling NLB/ALB fixes CPU when the bottleneck is Envoy's pod-local TLS termination.

Shared STEK Ring (Current+Prev)

  1. 01Synchronized Ticket Keys: All 40 Envoy pods receive [Key_N, Key_N-1] via SDS so any pod can resume any ticket.
  2. 02Desynchronize Reconnect Wave: On disconnect, clients wait random(50ms, 3000ms) before opening a new TLS socket.
  3. 03Stateless PSK Resumption: Client presents cached session ticket; Envoy decrypts with shared STEK in ~0.05 ms.
  4. 04Fast Asymmetric Fallback: New clients without tickets perform ECDSA P-256 handshakes (~6x faster than RSA-2048).
  5. 05Ingress CPU Protection: Envoy listener limits concurrent TLS handshakes per worker to protect active bulk traffic.
Shared STEKs + ECDSA P-256 + jittered reconnects reduce storm CPU from >160 cores to ~1.5 cores.

The invariants

  • Issue ECDSA P-256 leaf certs from internal CA.
  • Rotate a 2-key STEK Secret every 12h via CronJob/Vault.
  • Add full jitter to client reconnects and max_connection_duration.

04 / ImplementConfiguration & code

Build the safeguards.

2. Harden for scale

With ECDSA P-256 (0.18 ms/handshake) and a 3-second client jitter window, even 0% resumption uses only ~7.2 cores (4.5% of fleet CPU).

YAML · Scale hardening
overload_manager:
  refresh_interval: 0.25s
  resource_monitors:
    - name: envoy.resource_monitors.fixed_heap
      typed_config: { max_heap_size_bytes: 2147483648 }

3. Operational controls

Step 1

Set Envoy `overload_manager` to shed new connections if CPU/heap crosses 85%.

Step 2

Ensure client handshake timeout is >= 3 s so jittered queues drain without aborting.

Step 3

Warm critical gRPC channels during pod `startupProbe`.

Implementation note

ECDSA P-256 + shared STEK cuts storm CPU by >95% with zero hardware changes.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Track `envoy_ssl_session_reused / (envoy_ssl_handshake + envoy_ssl_session_reused)` and test cross-pod resumption with `openssl s_client`.

  • ↗
    Save a session ticket from Pod A using `openssl s_client -sess_out ticket.pem`.
  • ↗
    Connect to Pod B using `-sess_in ticket.pem` and verify `Reused, TLSv1.3`.
  • ↗
    Alert if production resumption ratio drops below 70%.
BASH · Verification
openssl s_client -connect ingress-pod-a:443 -tls1_3 -sess_out /tmp/sess.pem </dev/null
openssl s_client -connect ingress-pod-b:443 -tls1_3 -sess_in /tmp/sess.pem </dev/null | grep Reused

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Failure scenario 1
