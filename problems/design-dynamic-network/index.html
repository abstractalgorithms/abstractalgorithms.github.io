Disjoint Set Union (Union-Find): Path Compression & Union by Rank
Disjoint Set Union (DSU) maintains a partition of N elements into non-overlapping sets, supporting find(x) and union(x, y) in O(alpha(N)) amortized time.
Consistent Hashing & Virtual Nodes
Consistent hashing assigns data keys to servers in a way that limits how many keys move when servers are added or removed. This helps avoid widespread cache misses and sudden load on databases.
Change Data Capture (CDC)
Change Data Capture (CDC) streams row-level inserts, updates, and deletes directly from a database's transaction log (WAL/binlog/oplog) into event buses like Kafka—eliminating dual-write race conditions and heavy polling queries.

Sizing 200M-Node DSU State & Latency Budgets.

Why this matters: Size a 200M-account fraud-ring DSU in 800 MB RAM plus a RocksDB ID-interning map with <1 ms connectivity queries.

Assume 200M active accounts mapped to dense int32 internal IDs via an ID-interning RocksDB/hash table.

  • DSU Array: 200M * 4 bytes (negative-size parent[]) = 800 MB RAM.
  • ID Interning Map: 200M * ~24 bytes = ~4.8 GB RAM.
  • Throughput: 100K union()/sec and 250K find()/sec easily run on 1–4 CPU cores in C++/Rust/Go at ~100 ns per operation.

Preventing False-Positive Collapses on Shared IPs & Hubs.

Why this matters: Prevent false-positive mega-component collapses on shared Wi-Fi/CGNAT IPs using attribute degree caps.

A naive union(account, ip) merges every user on an airport Wi-Fi or CGNAT IP into one mega-component. Before emitting a union edge for an attribute (IP, device, card), enforce a degree cap (e.g., max 20 accounts per IP per 24h) using a Redis/HyperLogLog or Count-Min Sketch gate.

Attributes exceeding the threshold are quarantined as super_node signals rather than hard DSU edges.

STAGE 02 · INGESTION & SUPER-NODE GUARD

Preventing False-Positive Collapses on Shared IPs & Hubs

1.Airport Wi-Fi Trap: One shared IP with 5,000 travelers would merge 5,000 innocent users into one giant fraud ring.

2.Attribute-Specific Caps: Cap shared IPs at 20 accounts, shared devices at 5, and shared cards at 3.

3.Quarantine Log: Send excluded super-node attributes to a separate anomaly stream instead of the DSU.

Attribute degree caps quarantine shared Wi-Fi/CGNAT IPs before union(), preventing giant-component false positives.

STAGE 03 · CORE DSU ENGINEintermediate

Thread-Safe Sharded Engine with Threshold Alerting.

Why this matters: Implement FraudRingDSU with iterative path halving, union-by-size, and >50-member ring threshold alerts.

On every union(a, b) that merges two distinct components whose combined size crosses ALERT_THRESHOLD = 50, emit an asynchronous alert event to the Risk Sink.

class FraudRingDSU:
    def __init__(self, capacity: int, alert_threshold: int = 50) -> None:
        self.parent = [-1] * capacity
        self.alert_threshold = alert_threshold

def find(self, x: int) -> int:
        if not (0 <= x < len(self.parent)):
            raise ValueError('Invalid account ID')
        root = x
        while self.parent[root] >= 0:
            root = self.parent[root]
        while x != root:
            nxt = self.parent[x]
            self.parent[x] = root
            x = nxt
        return root
STAGE 03 · CORE DSU ENGINE

Thread-Safe Sharded Engine with Threshold Alerting

1.Iterative Only: Path halving (parent[x] = parent[parent[x]]) runs in a simple while loop with zero recursion.

2.One-Time Crossing Alert: Alert when a merge pushes combined size from <50 to >=50 so downstream isn't spammed.

3.Thread Safety: Shard or synchronize writes on the single writer thread while serving lock-free/RCU reads.

Iterative path halving and union-by-size emit risk alerts the moment any merged component crosses 50 accounts.

STAGE 04 · CRASH RECOVERYintermediate

Idempotent WAL Replay & Non-Blocking Snapshots.

Why this matters: Recover crashed DSU instances via copy-on-write 60s parent[] snapshots and idempotent Kafka WAL replay.

Because union(a, b) is commutative and associative, replaying duplicate WAL records after a crash is naturally idempotent! Every 60 seconds, fork/copy-on-write snapshot the parent[] array + Kafka offset to object storage (S3/GCS).

On restart, mmap the latest 800 MB snapshot in < 1 second and replay only the tail WAL from the recorded offset.

STAGE 04 · CRASH RECOVERY

Idempotent WAL Replay & Non-Blocking Snapshots

1.Natural Idempotency: Because union(a, b) is commutative and associative, replaying duplicate Kafka messages changes nothing.

2.Copy-on-Write Fork: Using Linux fork() snapshots the 800 MB array to disk without pausing live queries.

3.Fast Boot: Loading an 800 MB binary snapshot plus 60s of Kafka tail takes <10 seconds.

60s copy-on-write snapshots and naturally idempotent Kafka union replay recover 200M-node state in <10 seconds.

STAGE 05 · HANDLING EDGE EXPIRYadvanced

Rolling Epoch DSU for 30-Day Sliding Windows.

Why this matters: Expire edges older than 30 days using rolling shadow-rebuilt epoch snapshots swapped atomically at midnight.

Instead of deleting edges online, maintain daily or weekly DSU epochs (or a background shadow-rebuild job over the trailing 30-day edge log). At midnight UTC, promote the freshly built 30-day DSU snapshot atomically via pointer swap.

Queries read the active immutable-horizon snapshot + live delta ring buffer.

STAGE 05 · HANDLING EDGE EXPIRY

Rolling Epoch DSU for 30-Day Sliding Windows

1.Why Not Online Delete?: Standard DSU with path compression cannot delete individual edges efficiently.

2.Shadow Rebuild Cost: Replaying 30 days of edges into a fresh int32[] array takes ~2 minutes on one background core.

3.Atomic Cutover: Swap the read-replica pointer cleanly once the shadow snapshot catches up to Kafka head.

Background 30-day shadow rebuilds and atomic pointer swaps expire old edges without sacrificing O(alpha(N)) finds.

Read Replicas & Cross-Shard Federation.

Why this matters: Scale read throughput linearly by replicating the Kafka edge stream to N local-RAM read replicas.

Replicate the Kafka edge stream to N stateless-recovery read replicas. Each replica maintains an identical in-memory DSU and serves sameRing(A, B) locally in < 1 ms.

If graph size outgrows single-node RAM, shard by region/tenant or run a two-tier architecture: local shard DSU + global cross-shard boundary-edge DSU.

STAGE 06 · READ SCALING

Read Replicas & Cross-Shard Federation

1.Zero Network Read Hop: Every API replica or sidecar holds the 800 MB DSU locally—queries never cross the network.

2.Deterministic Convergence: All replicas applying the same ordered Kafka log converge to identical connected components.

3.Regional Sharding: If accounts exceed 1B, shard by region and federate rare cross-region edges.

Streaming the Kafka edge log to local-RAM read replicas scales sameRing() reads horizontally at <1 ms.
