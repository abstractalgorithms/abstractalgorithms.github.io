R

Define the boundaries.

Requirements · 4 minutes
SAY THIS: “Before proposing a topology for Design a Distributed Unique ID Generator, I’ll clarify the core functional requirements, burst characteristics, data volume, and availability SLOs to define rigid system boundaries.”
UUID v4 is 128-bit and non-sequential, causing B-tree fragmentation, page splits, and cache misses in database indexes. Centralized DB auto-increment introduces a single write bottleneck and single point of failure.

What the system does

  • IDs must be globally unique across all nodes.
  • IDs must fit into a 64-bit integer (int64) for database index efficiency.
  • IDs must be roughly chronological / time-sortable.
  • High availability: service must generate at least 10,000 IDs per second per node with sub-millisecond latency.
  • No single point of failure and no runtime consensus round-trips (Paxos/Raft) in the ID generation path.

What to agree on

  • Generation Volume: 10,000 unique IDs per second per node (Peak: 100,000 IDs/sec across 10 nodes).
  • ID Length: 64-bit integer (fits in a standard signed 64-bit bigint / SQL BIGINT).
  • Ordering: Roughly time-sortable (higher timestamp prefix guarantees chronological collation).
  • Longevity: 69 years of epoch coverage (41 bits for millisecond timestamps: 2^41 ≈ 69.7 years).
  • Machine Allocation: 10 bits support 1,024 worker nodes (5 bits datacenter ID + 5 bits worker ID).

S

Keep state shared and partitioned.

Storage · 3 minutes
SAY THIS: “I’ll separate low-latency ephemeral cache state from authoritative durable storage, ensuring strict consistency where needed and partitioning for scale.”

Cache / Ephemeral state

state:{partitionKey}:activeWindow

  • In-memory key-value cache (Redis Cluster / Memcached).
  • TTL expiration matching window validity bounds.
  • Hash tags to co-locate keys for atomic Lua scripts or transactions.

Durable / Authoritative store

  • Distributed NoSQL / relational database (DynamoDB, PostgreSQL).
  • Durable write-ahead log with replica failover.
  • Cache-aside pattern: read misses warm cache from durable store.
  • Asynchronous CDC / event streaming to telemetry sinks.

Local-only node state is not a shared cluster quota: N nodes could admit roughly N × the configured limits. Ensure state co-location and transactional boundaries align with partition keys.

D

Make state mutations atomic.

Detailed design · 7 minutes
SAY THIS: “For the critical execution path, we enforce idempotency and concurrency controls using atomic primitives, avoiding lock contention and split-brain states.”
  1. 1 unused sign bit (always 0 to keep integer positive).
  2. 41 timestamp bits: milliseconds since custom epoch. 2^41 ms ≈ 69.7 years of IDs.
  3. 10 node ID bits: 5 bits datacenter ID (32 datacenters) + 5 bits worker ID (32 workers per DC) = 1,024 generator nodes.
  4. 12 sequence bits: supports up to 2^12 = 4,096 IDs per millisecond per node.
  5. Algorithm: read current timestamp. If same millisecond as last ID, increment sequence. If sequence overflows 4095, busy-wait until next millisecond. If new millisecond, reset sequence to 0.

TYPESCRIPT · REFERENCE IMPLEMENTATION
// Twitter Snowflake 64-bit ID Generator
// 1 bit unused | 41 bits timestamp (millis) | 10 bits machine/node ID | 12 bits sequence counter
export class SnowflakeIdGenerator {
  private static readonly EPOCH = 1609459200000n; // Custom Epoch: 2021-01-01
  private static readonly NODE_ID_BITS = 10n;
  private static readonly SEQUENCE_BITS = 12n;
  private static readonly MAX_SEQUENCE = (1n << 12n) - 1n;

  private sequence = 0n;
  private lastTimestamp = -1n;

  constructor(private readonly nodeId: bigint) {
    if (nodeId < 0n || nodeId > 1023n) throw new Error("Node ID must be between 0 and 1023");
  }

  public nextId(): bigint {
    let timestamp = BigInt(Date.now());
    if (timestamp < this.lastTimestamp) {
      throw new Error("Clock moved backwards! Rejecting generation.");
    }

    if (timestamp === this.lastTimestamp) {
      this.sequence = (this.sequence + 1n) & SnowflakeIdGenerator.MAX_SEQUENCE;
      if (this.sequence === 0n) {
        // Spin until next millisecond
        while (timestamp <= this.lastTimestamp) {
          timestamp = BigInt(Date.now());
        }
      }
    } else {
      this.sequence = 0n;
    }

    this.lastTimestamp = timestamp;
    return (
      ((timestamp - SnowflakeIdGenerator.EPOCH) << 22n) |
      (this.nodeId << 12n) |
      this.sequence
    );
  }
}

Avoid client-side read-modify-write loops without concurrency control. Use atomic scripts, row-level locks, or conditional mutations at the storage tier to guarantee linearizability.

E

Stress-test the design.

Evaluation · 6 minutes
SAY THIS: “The biggest operational risks involve node failover, partition skew, network isolation, and cascading downstream backpressure. Here is how we mitigate each.”
Custom epoch

Starting timestamp at application launch year (e.g., 2026) gives 69 years of runtime from now. Unix epoch would overflow 41 bits in 2039.

Static worker ID assignment vs ZooKeeper/etcd

Static config is simple but prone to human config error (duplicate worker IDs). Zookeeper/etcd ephemeral nodes assign unique worker IDs automatically on startup.

Clock skew / rollback

If system clock jumps backward, the generator will produce duplicate timestamps and therefore duplicate IDs!

Defense 1 (Wait)

If clock rollback is small (< 5 ms), spin-wait until the clock catches up to lastTimestamp.

Defense 2 (Reject)

If clock rollback is significant, reject requests and raise an alert; refuse to generate IDs until operator verifies or clock catches up.

Defense 3 (Clock-sequence bits)

Reserve 2 bits for clock sequence counter; increment clock sequence when rollback is detected to maintain uniqueness.

D

Close with the trade-offs.

Discussion · 5 minutes
SAY THIS: “In closing, we optimized for sub-millisecond p99 latency and high availability under partition. We trade strict distributed linearizability for predictable throughput and operational simplicity.”

If the interviewer asks…

  • Custom epoch: Starting timestamp at application launch year (e.g., 2026) gives 69 years of runtime from now. Unix epoch would overflow 41 bits in 2039.
  • Static worker ID assignment vs ZooKeeper/etcd: Static config is simple but prone to human config error (duplicate worker IDs). Zookeeper/etcd ephemeral nodes assign unique worker IDs automatically on startup.

Keep the conclusion focused

  • What guarantees are strictly enforced at runtime?
  • What happens during network partitions or node failures?
  • Which CAP trade-off was intentionally chosen and why?
