01 / UnderstandFailure & constraints

Clarify what is failing.

Context breaks at ingress (no traceparent), Java async executors (ThreadLocal drop), gRPC/Kafka boundaries (no header injection), and unstructured text logs.

Design objective

Check Envoy ingress for `traceparent` generation.

Requirements

  • Link 100% of logs across HTTP/REST, gRPC, async thread pools, and Kafka consumers via a single `trace_id` / `correlation_id`.
  • Support log lookup by `trace_id` in < 2 seconds across 120 GB/hour of aggregated logs.
  • Prevent context leakage or stale IDs across pooled worker threads and reused Kafka consumers.
  • Keep instrumentation overhead < 1.5% CPU and < 1 ms per hop.

Constraints

  • Polyglot stack: Envoy Gateway, Java 21 (Spring Boot + `CompletableFuture`), gRPC, Kafka, and Python 3.12 workers.
  • External clients cannot be trusted to supply valid or unique correlation IDs.
  • 100% trace span storage is too expensive; only 5% head + 100% error/tail traces are stored, while 100% of logs carry `trace_id`.
Known failure modes

name: Stale MDC on Reused Threads; description: Without `MDC.clear()`, threads log previous requests' trace IDs.; mitigation: Always clear MDC in `finally`.

  1. 01Edge Trace Initialization: Envoy generates a 128-bit trace_id, ignores spoofed client IDs, and returns X-Trace-Id in the response.
  2. 02Thread-Safe Async Propagation: CompletableFuture tasks inherit trace_id into Logback MDC and clear it in finally blocks.
  3. 03Kafka Header Injection: OTel ProducerInterceptor writes traceparent into Kafka RecordHeaders without altering the Avro/JSON payload.
  4. 04Python Worker Extraction: Python worker extracts traceparent from message headers and binds trace_id to structlog JSON output.
  5. 05< 2s Log Correlation: All 6 services emit structured JSON with trace_id, enabling instant single-query incident reconstruction.
W3C traceparent propagates seamlessly across Envoy, Java async pools, gRPC metadata, Kafka RecordHeaders, and Python workers.

The invariants

  • Generate traceparent at Envoy and return X-Trace-Id.
  • Wrap Java executors with Context.taskWrapping / MdcTaskDecorator.
  • Inject traceparent into Kafka RecordHeaders and extract in Python.
03 / Trace the lifecycleKey decisions

Follow the execution path.

External IDs can be spoofed, non-unique, or injection vectors; mint a fresh 128-bit `trace_id` at Envoy and index `trace_id` as a keyword while sampling spans.

Step 1

Store client-supplied X-Request-ID in a separate client_request_id attribute.

Step 2

Index trace_id as an exact keyword field in OpenSearch/Loki and drop verbose DEBUG logs in prod.

04 / ImplementConfiguration & code

Build the safeguards.

Create a new batch span with **Span Links** pointing to each message's `traceparent` rather than making 500 parents.

1. Reference implementation

PYTHON · Solution
from opentelemetry.propagate import inject, extract
headers = []
inject(carrier := {})
for k, v in carrier.items():
    headers.append((k, v.encode()))
producer.produce('payment.requested', value=payload, headers=headers)

2. Harden for scale

Create a new batch span with **Span Links** pointing to each message's `traceparent` rather than making 500 parents.

PYTHON · Scale hardening
links = [trace.Link(trace.get_current_span(extract(h)).get_span_context()) for h in batch_headers]
with tracer.start_as_current_span("consume_batch", links=links):
    for msg in batch:
        handle_message(msg)

3. Operational controls

Step 1

Extract `SpanContext` from each of the 500 Kafka messages.

Step 2

Start a batch span with `links=[Link(ctx) for ctx in contexts]` and process each item with its own child span.

Implementation note

factor: Kafka Headers vs. Payload Field; pro: Keeps business schemas clean and works with Schema Registry.; con: Requires consumers to read `msg.headers()`.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Use **SQLCommenter** (OTel DB instrumentation) to prepend `/*traceparent='00-...'*/` to every SQL query.

  • ↗
    Enable `otel.instrumentation.jdbc.statement-sanitizer.enabled=true` and `sqlcommenter`.
  • ↗
    PostgreSQL slow-query logs (`log_min_duration_statement = 200ms`) automatically capture the `trace_id`.
SQL · Verification
SELECT * FROM orders WHERE id = $1 /*traceparent='00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01'*/;

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
