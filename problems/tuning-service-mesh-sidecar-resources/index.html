The idea to keep with you

A Kubernetes payments cluster with 350 services runs Istio Envoy sidecars configured with `requests.cpu: 100m` and `limits.cpu: 200m`. Whenever a deploy triggers xDS route pushes or traffic spikes 2x, p99 latency on healthy pods jumps by 150–400 ms in sawtooth waves, and readiness probes fail. Application CPU is only 25%, yet `container_cpu_cfs_throttled_periods_total` on `istio-proxy` hits 65%.

01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why Kubernetes 200m CPU limits freeze Envoy sidecars for 90 ms.

In a 350-service Istio cluster (1,400 endpoints pushed to every pod), setting limits.cpu: 200m on istio-proxy gives Envoy only 20 ms of CPU time per 100 ms Linux CFS quota period (cpu.cfs_period_us = 100000). If 2 Envoy worker threads burn 10 ms each during an mTLS handshake or xDS push, CFS freezes the entire sidecar for the remaining 80–90 ms.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

150–400 ms sawtooth p99 latency waves and xDS memory bloat.

Throttled Envoy sidecars stall healthy applications even when app CPU is only 25%:

  1. Sawtooth Latency Waves: Every multi-hop call stacks 80–90 ms CFS quota pauses (150–400 ms p99 spikes) and fails readiness probes.
  2. Mesh-Wide xDS Bloat: Without Sidecar CRDs, all 350 services x 1,400 endpoints are parsed by every proxy, wasting hundreds of MBs of RAM on nodes already at 72% memory.
Linux CFS Quota Freeze

200m CPU Limit Stalls Envoy Event Loop for 80ms Every 100ms Period

Removing hard CPU limits eliminates CFS freezes while Sidecar CRDs cut xDS config size and parse CPU by 80-95%.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Why sizing CPU limits from 5-min averages and concurrency=0 fails.

A 5-minute Grafana CPU graph showing 80m average hides sub-100 ms micro-bursts during mTLS handshakes and xDS reloads. Leaving Envoy concurrency: 0 on 64-core nodes also spawns 64 worker threads, each consuming memory and contending for the 200m CFS quota.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Drop CPU Limits, Scope Sidecar CRDs, Tune Concurrency.

Eliminate 150–400 ms CFS stalls and shrink proxy memory across 350 services:

  • Remove limits.cpu, Keep requests.cpu: 200m: Without limits.cpu, Linux CFS does not hard-throttle bursts onto idle node CPU, while cpu.shares still protects co-located app containers under node contention.
  • Namespace Sidecar CRDs: Restrict each pod's egress.hosts to only its declared dependencies (./*, istio-system/*), cutting xDS config size, parse CPU, and Envoy RAM by 80–95%.
  • Set proxyMetadata / concurrency: 2: Bound Envoy worker threads to 2 instead of 0 (all host cores) to slash per-thread memory and lock contention.
Untrottled & Scoped Mesh

requests.cpu (No Limit) + Sidecar CRD + concurrency=2

1.Zero CFS Throttling: Dropping limits.cpu removes the 100ms hard quota wall while cpu.shares prevents noisy neighbors.

2.Sidecar CRD Scoping: Prunes 1,400 cluster-wide endpoints down to only the namespace's actual egress targets.

3.concurrency: 2: Prevents Envoy from spawning 64 threads on large nodes, saving RAM at 72% node utilization.

Removing CPU limits, scoping xDS via Sidecar CRDs, and setting concurrency=2 eliminates sawtooth latency and memory bloat.

apiVersion: networking.istio.io/v1beta1
kind: Sidecar
metadata:
  name: default-egress-scope
  namespace: payments
spec:
  egress:
    - hosts:
        - "./*"
        - "istio-system/*"
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where service mesh resource tuning is critical in Kubernetes.

CFS quota awareness and xDS scoping are essential for large multi-tenant meshes:

  • Istio / Linkerd Production Clusters: Standardizes no-CPU-limit Burstable QoS for latency-sensitive proxies.
  • Zero-Trust mTLS Payments Fleets: Keeps TLS handshakes sub-millisecond during pod autoscaling.
  • Large Multi-Namespace Meshes: Prevents O(N^2) xDS config push storms across 300+ services.
