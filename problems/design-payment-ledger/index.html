The idea to keep with you

When processing financial mutations across unreliable networks and external payment gateways, bind the idempotency key and balanced double-entry postings inside a single local ACID transaction before making any external PSP call so retries replay recorded state instead of double-charging.

TL;DR30-second simplified summary
▾

Holding a database row lock while waiting 200 ms for an external payment gateway exhausts connection pools under moderate load. Production ledgers split each payment into a fast local ACID hold (TX1), an unlocked external PSP capture using tx_id as the gateway idempotency token, and a fast local ACID finalization (TX2).

When a PSP call times out, the transaction remains in PSP_PENDING while an asynchronous reconciler polls the gateway. Downstream Kafka events are emitted via a transactional outbox written in the same commit as the postings.

STAGE 01 · REQUIREMENTS & SYSTEMS PHYSICSfoundation

Why Mutable Balances Break & 5,000 TPS Capacity Math.

Why this matters: Establish strict zero-sum ledger invariants, integer minor-unit arithmetic, and exact storage/IOPS budgets for 5,000 TPS.

Floating-point numbers (double/float) cannot represent 0.10 accurately in IEEE-754 binary, causing rounding drift across millions of transactions. Every monetary amount in a production ledger must be stored as a signed 64-bit integer in minor units (BIGINT cents, e.g., $19.99 = 1999) paired with an ISO-4217 currency code.

Similarly, running UPDATE accounts SET balance = balance - 5000 overwrites history. When an auditor asks why a balance dropped at 02:14 UTC, a mutable column has zero forensic lineage.

At 5,000 TPS average (and 15,000 TPS flash-sale burst), each payment creates 1 transactions row (~200 B) and at least 2 postings rows (1 debit + 1 credit, ~160 B each = ~520 B/tx) plus WAL overhead (~1.2 KB/tx):

  • Daily Write Volume: $5,000 \times 86,400 = 4.32 \times 10^8$ transactions/day ≈225 GB/day\approx 225\text{ GB/day}≈225 GB/day of structured rows (~82 TB/year before secondary indexes).
  • Write IOPS: 15,000 burst TPS with group-committed WAL batches (~2 ms fsync window) requires NVMe storage sustaining >25,000 write IOPS and partitioned database shards so no single primary exceeds ~3,000–4,000 write TPS.
  • Latency Budget: Internal ledger reservation must finish in < 25 ms p99, leaving 100–120 ms for external PSP network round-trips within a 150 ms p99 API SLO.

STAGE 02 · STORAGE & DATA LAYOUTfoundation

Double-Entry Schema, Sharding Keys & Balance Materialization.

Why this matters: Design the relational schema, partition key strategy, and atomic posting constraints so debits and credits never drift.

In double-entry bookkeeping, money never appears or disappears—it only moves between accounts. A $50.00 card capture debits buyer_card_receivable (-5000) and credits merchant_pending_escrow (+5000). When fees apply, a $1.50 fee debits merchant_pending_escrow (-150) and credits platform_fee_revenue (+150).

Shard the ledger database by merchant_id / ledger_partition_id (e.g., 16 PostgreSQL or Vitess shards) so single-merchant transactions stay co-located on one shard, avoiding distributed 2PC on the hot path.

CREATE TABLE ledger_transactions (
    tx_id           UUID PRIMARY KEY,
    idempotency_key VARCHAR(128) NOT NULL,
    merchant_id     BIGINT NOT NULL,
    status          VARCHAR(24) NOT NULL,
    currency        CHAR(3) NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (merchant_id, idempotency_key)
);

CREATE TABLE ledger_postings (
    posting_id      BIGINT GENERATED ALWAYS AS IDENTITY,
    tx_id           UUID NOT NULL REFERENCES ledger_transactions(tx_id),
    account_id      BIGINT NOT NULL,
    amount_minor    BIGINT NOT NULL CHECK (amount_minor <> 0),
    entry_side      CHAR(1) NOT NULL CHECK (entry_side IN ('D', 'C')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (account_id, created_at, posting_id)
);

STAGE 03 · IDEMPOTENCY & EXTERNAL PSP BOUNDARYcore

Two-Phase Idempotency Fencing Across Unreliable Payment Gateways.

Why this matters: Prevent double-charges when clients retry timed-out requests or when the external PSP hangs mid-capture.

Never hold a database row lock while making an HTTP call to an external PSP (Visa/Stripe/Adyen). External PSP calls take 80–400 ms (and up to 10 seconds during upstream brownouts). Holding a DB connection and row lock across that call exhausts your 100-connection pool at just 250 TPS.

Split payment execution into three atomic phases:

  1. Phase A (Local ACID Reserve — ~8 ms): Insert (merchant_id, idempotency_key) with status INITIATED, verify funds, and post a hold (Debit buyer_available, Credit buyer_held). Commit and release the DB connection.
  2. Phase B (External PSP Call — ~90 ms): Call the PSP passing tx_id as the PSP's idempotency token.
  3. Phase C (Local ACID Finalize — ~8 ms): On PSP 200 OK, transition tx_id to CAPTURED and move buyer_held to merchant_pending. On explicit decline (402), post a reversing entry (Debit buyer_held, Credit buyer_available) and mark FAILED.
THREE-PHASE PAYMENT EXECUTION

Decoupling DB Locks From Slow External PSP Calls

Database locks live for <10 ms per phase while external gateway latency occurs completely outside transaction boundaries.

STAGE 04 · IMPLEMENTATION & HOT-MERCHANT SKEWcore

Deterministic Lock Ordering & Sub-Sharding Hot Merchant Accounts.

Why this matters: Implement deadlock-free Java ledger commits and eliminate single-row lock contention during merchant flash sales.

When Account A transfers to Account B at the exact microsecond Account B transfers to Account A, naive row locking causes an AB-BA deadlock (40P01). Sorting lock acquisition by ascending account_id eliminates circular wait conditions completely.

public record Posting(long accountId, long amountMinor) {}

public final class LedgerService {
    private final DataSource dataSource;

    public LedgerService(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public void commitBalancedTransfer(UUID txId, List<Posting> postings) throws SQLException {
        if (postings == null || postings.size() < 2) {
            throw new IllegalArgumentException("Double-entry requires at least 2 postings");
        }
        long netSum = 0L;
        for (Posting p : postings) {
            if (p.amountMinor() == 0L) throw new IllegalArgumentException("Zero posting forbidden");
            netSum = Math.addExact(netSum, p.amountMinor());
        }
        if (netSum != 0L) {
            throw new IllegalStateException("Unbalanced transaction: netSum=" + netSum);
        }

        List<Posting> ordered = postings.stream()
                .sorted(Comparator.comparingLong(Posting::accountId))
                .toList();

        try (Connection conn = dataSource.getConnection()) {
            conn.setAutoCommit(false);
            try {
                for (Posting p : ordered) {
                    try (PreparedStatement lockStmt = conn.prepareStatement(
                            "SELECT available_minor FROM account_balances WHERE account_id = ? FOR UPDATE")) {
                        lockStmt.setLong(1, p.accountId());
                        try (ResultSet rs = lockStmt.executeQuery()) {
                            if (!rs.next()) throw new IllegalStateException("Missing account " + p.accountId());
                            long current = rs.getLong(1);
                            if (p.amountMinor() < 0 && Math.addExact(current, p.amountMinor()) < 0) {
                                throw new InsufficientFundsException(p.accountId());
                            }
                        }
                    }
                }
                for (Posting p : ordered) {
                    try (PreparedStatement insertPosting = conn.prepareStatement(
                            "INSERT INTO ledger_postings (tx_id, account_id, amount_minor) VALUES (?, ?, ?)")) {
                        insertPosting.setObject(1, txId);
                        insertPosting.setLong(2, p.accountId());
                        insertPosting.setLong(3, p.amountMinor());
                        insertPosting.executeUpdate();
                    }
                    try (PreparedStatement updateBal = conn.prepareStatement(
                            "UPDATE account_balances SET available_minor = available_minor + ?, version = version + 1 WHERE account_id = ?")) {
                        updateBal.setLong(1, p.amountMinor());
                        updateBal.setLong(2, p.accountId());
                        updateBal.executeUpdate();
                    }
                }
                conn.commit();
            } catch (Exception ex) {
                conn.rollback();
                throw ex;
            }
        }
    }
}
HOT-MERCHANT SUB-SHARDING

Eliminating Single-Row Lock Contention With 32 Clearing Sub-Accounts

Engineering Decision Framework
Problem
How to sustain 8,000+ TPS into a single mega-merchant account without violating zero-sum ledger invariants or stalling on row locks.
Naive Solution
Lock the single merchant account row (SELECT ... FOR UPDATE) on every customer payment capture.
Why It Fails
Row-level locking serializes all concurrent captures for that merchant behind a single WAL commit queue (~1,000 TPS max), causing connection pool exhaustion and p99 timeouts.
Alternatives
Compare single-row pessimistic locks, optimistic concurrency retries (CAS), and K-way sub-sharded clearing accounts.
Engineering Decision
When a single merchant or platform escrow account exceeds ~500 write TPS, split its clearing balance across K = 32 sub-accounts hashed by tx_id and consolidate them asynchronously prior to payout settlement.
Trade-Offs
Eliminates single-row lock contention linearly with K while preserving exact double-entry postings, at the cost of summing K rows when reading real-time merchant pending balance.

STAGE 05 · MULTI-REGION PHYSICS & GRACEFUL DEGRADATIONdeepDive

Clock Drift, Multi-Region Speed-of-Light & Criticality Failover.

Why this matters: Prevent timestamp-based race conditions across stateless API nodes and define strict fail-closed vs. fail-open boundaries.

Never use wall-clock timestamps (System.currentTimeMillis()) from stateless API servers to order ledger entries or expire idempotency keys. NTP clock skew of 50–200 ms across nodes can make a refund appear older than its parent capture or prematurely expire an in-flight key.

Assign ordering strictly from the database shard's monotonic sequence (BIGINT GENERATED ALWAYS AS IDENTITY) and Hybrid Logical Clocks (HLC) for cross-shard audit exports.

For Multi-Region Deployments, cross-continent speed-of-light RTT (e.g., US-East to EU-West at ~75 ms) makes synchronous cross-region quorum commits too slow for a 150 ms p99 checkout budget if an external PSP also needs 90 ms. Pin each merchant_id to a home region for writes, and replicate immutable postings asynchronously to secondary regions for read-only reporting and disaster recovery (RPO < 1s).

STAGE 06 · SETTLEMENT & CONTINUOUS RECONCILIATIONdeepDive

Transactional Outbox, Bank Settlement Files & Zero-Sum Auditing.

Why this matters: Guarantee downstream Kafka notifications and daily PSP settlement files match internal ledger postings down to the cent.

Publishing a PaymentCaptured event to Kafka directly from application code after conn.commit() creates a dual-write hole: if the process crashes between the DB commit and Kafka ack, downstream fraud, invoicing, and merchant webhook services never learn the payment succeeded.

Write the event into an outbox_events table inside the same local ACID transaction as the ledger postings. A CDC worker (Debezium or polling FOR UPDATE SKIP LOCKED) relays events to Kafka with at-least-once delivery, where consumers deduplicate on event_id.

Daily, an automated Three-Way Reconciliation Engine compares:

  1. Internal ledger_postings (CAPTURED + REFUNDED net totals)
  2. PSP Gateway Settlement Reports (T+1 clearing files)
  3. Bank Nostro/Settlement Account Statements

Any discrepancy > 0 cents triggers a P1 reconciliation alert and quarantines automated payouts for that merchant until resolved.

STAGE 07 · ASSUMPTIONS, LIMITATIONS & GLOSSARYdeepDive

System Boundaries, Operational Assumptions & Ledger Glossary.

Why this matters: Document explicit architectural assumptions, failure boundaries, and canonical payment ledger terminology.

Assumptions & Limitations:

  • Single-Currency Per Posting Pair: Multi-currency FX conversions require an explicit intermediate FX clearing account (USD_FX_BRIDGE and EUR_FX_BRIDGE) so each currency's postings independently sum to zero.
  • External PSP Idempotency Support: Assumes downstream card gateways honor a client-supplied idempotency token for at least 24 hours; legacy gateways lacking idempotency require pre-flight status lookup before any retry.
  • Bounded Sub-Shard Fan-In: Real-time balance queries for sub-sharded mega-merchants sum 32 rows (< 3 ms index-only scan) and tolerate 1–5 second sweep lag for payout eligibility.

Canonical Glossary:

  • Double-Entry Posting: An immutable debit or credit record tied to a tx_id where the sum of all postings in a transaction equals zero.
  • Idempotency Fence: A unique constraint (merchant_id, idempotency_key) committed in the same ACID transaction as the initial state mutation.
  • Transactional Outbox: A database table written in the same ACID transaction as domain state, ensuring reliable asynchronous event publication without dual-write races.
  • Sub-Sharding (Salted Clearing Accounts): Splitting a high-contention balance row into K independent partitions to parallelize row-level write locks.
