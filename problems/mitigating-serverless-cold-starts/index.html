01 / UnderstandFailure & constraints

Clarify what is failing.

Cold starts stack microVM boot, JVM/Spring DI scanning, and TLS DB handshakes, while per-sandbox connection pools multiply linearly with concurrency.

Design objective

Decompose the 3.4s: sandbox init + JVM startup + Spring classpath scanning + DB TLS handshake.

Requirements

  • Keep p99 latency under 600 ms even during a 20x burst (150 -> 3,000 RPS in 10 seconds).
  • Prevent serverless scale-out from exhausting RDS Postgres connection limits (max_connections = 500).
  • Control baseline idle cost (do not keep 100% peak provisioned 24/7).
  • Eliminate cold-start timeouts across both AWS Lambda and Cloud Run deployments.

Constraints

  • Must stay on Java 21 with existing Spring Boot 3.x business logic.
  • RDS Postgres instance cannot be scaled vertically beyond 500 max_connections during the event.
  • Monthly serverless compute budget increase must stay under 25%.
Known failure modes

Connection exhaustion cascades into 500 errors even on already-warm instances.

Multiplexes -> 60 PG Conns

  1. 01Absorb Initial Wave: Scheduled Provisioned Concurrency (or Cloud Run min-instances=3, concurrency=80) handles initial traffic at 45 ms.
  2. 02Fast Snapshot Restore: Overflow sandboxes restore pre-initialized JVM memory in ~380 ms via AWS Lambda SnapStart.
  3. 03Refresh Ephemeral State: CRaC hook re-seeds PRNG and opens a single lazy DB connection (Hikari maxPoolSize=1).
  4. 04Multiplex via RDS Proxy: Warm and spillover instances send queries to RDS Proxy over IAM-authenticated TLS.
  5. 05Protect Postgres: RDS Proxy pins transactions to 60 warm backend connections, keeping Postgres well below 500 max_connections.
Layered cold-start defense: provisioned baseline + sub-second SnapStart spillover + RDS Proxy connection multiplexing.

The invariants

  • Enable SnapStart on PublishedVersions in SAM/Terraform.
  • Implement CRaC Resource beforeCheckpoint/afterRestore to manage sockets safely.
  • Point Spring Boot datasource to RDS Proxy with maximum-pool-size: 1.

Key trade-off

Higher concurrency slashes cold starts and cost, but a single OOM crash affects up to 80 in-flight requests.

04 / ImplementConfiguration & code

Build the safeguards.

RDS Proxy and PgBouncer in transaction mode pin a client to a dedicated backend Postgres connection if session-scoped state is mutated.

1. Reference implementation

JAVA · Solution
@Component
public class DbSnapshotHook implements org.crac.Resource {
    private final HikariDataSource dataSource;
    public DbSnapshotHook(HikariDataSource ds) {
        this.dataSource = ds;
        Core.getGlobalContext().register(this);
    }
    @Override public void beforeCheckpoint(Context<? extends Resource> ctx) {
        dataSource.evictConnection(null); // Flush idle sockets before snapshot
    }
    @Override public void afterRestore(Context<? extends Resource> ctx) {
        // Connections lazily re-established to RDS Proxy on first query
    }
}

2. Harden for scale

RDS Proxy and PgBouncer in transaction mode pin a client to a dedicated backend Postgres connection if session-scoped state is mutated.

      maximum-pool-size: 1

3. Operational controls

Step 1

Identify common pinning triggers: prepared statements, SET commands, temporary tables, or advisory locks.

Step 2

Add prepareThreshold=0 to the PostgreSQL JDBC URL to disable server-side prepared statements.

Step 3

Move any session-level settings into transaction-local SET LOCAL.

Implementation note

SnapStart adds ~15s to CI/CD publish time to capture the microVM snapshot.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Pinning turns RDS Proxy into a 1:1 pass-through, re-exposing Postgres to connection exhaustion.

Failure scenario 2

Deploying to $LATEST instead of a published version silently bypasses SnapStart.

Alternatives considered

  • Canary alias traffic shifting (5% for 15 min) with InitDuration rollback alarms.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Combine SnapStart / container image optimization with predictive Provisioned Concurrency (min-instances), lazy initialization, and an external connection pooler (RDS Proxy / PgBouncer).
  • 02Trade-off tip: Higher concurrency slashes cold starts and cost, but a single OOM crash affects up to 80 in-flight requests.
  • 03Watch out for: Pinning turns RDS Proxy into a 1:1 pass-through, re-exposing Postgres to connection exhaustion.
