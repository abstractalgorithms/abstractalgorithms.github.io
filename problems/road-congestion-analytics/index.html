Dual-Sink Serving & Spatial Analytics Topology.

Think of Dual-Sink Serving & Spatial Analytics Topology as the intuition layer for Design a Real-Time Geospatial Road Congestion Analytics System (1M Pings/sec): Serve live heatmaps and ETA APIs from Redis while archiving trajectories in ClickHouse.

Flink outputs 60-second aggregated segment speeds to two sinks: Redis H3 Tile Cache (for sub-5ms traffic tile rendering and CCH ETA graph updates) and ClickHouse Spatial Analytics (storing raw/snapped trajectories for urban planning and ST-GNN training).

System Blueprint

Flink Map-Matching -> Redis Tiles + ClickHouse

1.H3 Tile Grouping: Grouping segment speeds into one Redis Hash per H3 Res-6 cell fetches an entire map tile in 1 RTT.

2.90-Day OLAP: ClickHouse answers city-wide bottleneck queries across months in seconds.

Redis H3 tile hashes power <5ms map overlays while ClickHouse retains 90-day spatial history.

Engineering Decision Framework
Problem
How to implement Design a Real-Time Geospatial Road Congestion Analytics System (1M Pings/sec) without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
If 10M active vehicles each send 1 ping every 10s, raw ingress is 1M pings/sec, batch GPS pings at the mobile SDK, ingest via gRPC into Kafka, run stateful Flink HMM map-matching + 60s tumbling windows, and serve Redis H3 tiles alongside ClickHouse spatial analytics.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Flink Map-Matching with Local OSM Tile Caching.

Why this matters: Execute 1M HMM snaps/sec in Flink without hitting an external spatial database.

Think of Flink Map-Matching with Local OSM Tile Caching as the intuition layer for Design a Real-Time Geospatial Road Congestion Analytics System (1M Pings/sec): Execute 1M HMM snaps/sec in Flink without hitting an external spatial database.

Querying PostGIS over the network 1M times/sec is impossible. Each Flink TaskManager memory-maps a compact binary OSM road-graph tile (~4 GB per continent) or lazy-loads H3 Res-6 OSM tiles into local RocksDB/RAM, snapping pings in <50 microseconds.

In-Process OSM

Flink TaskManager Local Mmap OSM Tile Cache

1.Zero DB Hops: Memory-mapped local R-trees eliminate network latency during map-matching.

2.Weekly Map Sync: New roads and turn restrictions roll out via versioned S3 tile broadcasts.

Memory-mapped H3-sharded OSM tiles inside Flink TaskManagers enable 1M snaps/sec with zero DB calls.

60-Second Tumbling Windows & Late-Ping Watermarks.

Why this matters: Handle cellular tunnel dropouts without skewing live congestion tiles.

Cars entering tunnels lose cellular signal and flush buffered pings 30–60 seconds later.

Flink uses a 60-second tumbling window with a 20-second event-time watermark.

Tunnel Dropouts

20s Watermark & Late-Ping Side-Output

1.Fresh Live Maps: Excluding >20s stale tunnel pings prevents ghost traffic jams from appearing later.

2.Complete History: ClickHouse still receives every delayed ping for accurate rush-hour baselines.

Event-time watermarks keep live traffic maps fresh while preserving delayed tunnel pings in ClickHouse.

Privacy-Preserving Telemetry & Trajectory Stripping.

Why this matters: Prevent tracking individual commuters' home/work addresses.

Think of Privacy-Preserving Telemetry & Trajectory Stripping as the intuition layer for Design a Real-Time Geospatial Road Congestion Analytics System (1M Pings/sec): Prevent tracking individual commuters' home/work addresses.

Raw GPS trajectories can reveal home addresses. The Ingestion API rotates ephemeral device_session_ids every 15 minutes (long enough for 5-ping HMM, too short for trip reconstruction) and strips the first/last 200 meters of trips before archiving to ClickHouse.

Location Privacy

15-Min Ephemeral IDs & 200m Endpoint Fuzzing

1.15-Min Rotation: Short-lived session tokens support HMM continuity without enabling cross-day tracking.

2.200m Fuzzing: Dropping trip start/end tails prevents reverse-engineering home driveways.

Ephemeral 15-minute session IDs and 200m endpoint stripping protect commuter privacy without hurting traffic accuracy.
