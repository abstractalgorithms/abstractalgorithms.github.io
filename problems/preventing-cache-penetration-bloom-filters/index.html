Preventing Cache Penetration
with Bloom Filters.

Queries for keys that exist in neither Redis nor the database (e.g., negative IDs, scraped random UUIDs, or deleted SKUs) bypass the cache on every single request and hammer the database directly.

01 / UnderstandFailure & constraints

Clarify what is failing.

Every unique random UUID still misses Redis and hits PostgreSQL once, while storing millions of `__NULL__` keys in Redis exhausts memory and evicts real hot items.

Design objective

Observe 50,000 unique random keys/sec * 60s TTL = 3,000,000 useless `__NULL__` keys in Redis.

Requirements

  • Reject malformed IDs at the edge/API gateway before touching Redis or PostgreSQL.
  • Block > 99% of valid-format non-existent key probes without querying PostgreSQL.
  • Handle newly created legitimate items immediately (zero false-negative rejections) and deleted items cleanly.
  • Protect against memory exhaustion in Redis if an attacker probes 100M+ distinct random IDs.

Constraints

  • Catalog/user dataset contains 20,000,000 valid items; growth is ~50,000 new items/day.
  • Edge/pod RAM budget for an in-memory filter is <= 128 MB per pod; Redis cluster has 32 GB RAM.
  • Application code must be in Java or Python.
Known failure modes

Redis LRU eviction storm knocking real hot items out of cache.

  1. 01Edge Format & Rate Guard: Gateway rejects malformed IDs (`-1`, `abc`) with HTTP 400 before touching caches or DB.
  2. 02Bloom Filter Fast Reject: If BF.EXISTS returns 0, item definitely does not exist; return 404 in <0.2ms with zero DB hit.
  3. 03Check Redis Data & Negative Cache: Lookup item in Redis; if `__NULL__` sentinel is cached, return 404 immediately.
  4. 04Bounded DB Lookup: Only legitimate cold items and 0.1% Bloom false positives (<50 QPS) reach PostgreSQL.
  5. 05Short-TTL Negative Cache: If PostgreSQL returns 0 rows, cache `__NULL__` for 60s to block repeated probes on that FP key.
Edge validation + a 72 MB Bloom Filter + 60s negative caching reduces a 50,000 QPS penetration flood to < 50 QPS at PostgreSQL.

The invariants

  • Initialize BF.RESERVE items:bf 0.001 40000000 (~72 MB).
  • Reject non-UUID inputs with HTTP 400.
  • On BF.EXISTS == 0, return 404 immediately.
  • On DB None, SET item:{id} '__NULL__' EX 60.
03 / Trace the lifecycleKey decisions

Follow the execution path.

RedisBloom gives instant global consistency for newly created items (`BF.ADD`), while per-pod in-memory Bloom Filters cut Redis network RTT to zero during massive DDoS floods.

Step 1

Evaluate RedisBloom: 1 shared 72 MB filter, instant BF.ADD visibility across all 40 pods.

Step 2

Evaluate In-Pod Filter: 40 * 72 MB = 2.88 GB total pod RAM, zero Redis network I/O during 50k+ QPS attack, but needs 5s delta sync.

Step 3

Choose RedisBloom for most workloads; add L1 in-pod Bloom only if network bandwidth to Redis saturates.

04 / ImplementConfiguration & code

Build the safeguards.

On item creation, synchronously execute `BF.ADD` and `DEL item:{id}` (to clear any prior `__NULL__` sentinel) right after DB `COMMIT`, backed by a CDC listener.

1. Reference implementation

PYTHON · Solution
import json, re

UUID_RE = re.compile(r"^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$")
NULL_SENTINEL = "__NULL__"

def get_item(redis, db, item_id: str):
    if not UUID_RE.match(item_id):
        raise BadRequestError("Invalid item_id format")

    if not redis.execute_command("BF.EXISTS", "items:bf", item_id):
        return None  # 99.9% of non-existent probes stop here

    cache_key = f"item:{item_id}"
    cached = redis.get(cache_key)
    if cached is not None:
        return None if cached == NULL_SENTINEL else json.loads(cached)

    row = db.fetch_item(item_id)
    if row is None:
        redis.set(cache_key, NULL_SENTINEL, ex=60)  # Absorb 0.1% FP repeats
        return None

    redis.set(cache_key, json.dumps(row), ex=3600)
    return row

2. Harden for scale

On item creation, synchronously execute `BF.ADD` and `DEL item:{id}` (to clear any prior `__NULL__` sentinel) right after DB `COMMIT`, backed by a CDC listener.

PYTHON · Scale hardening
def create_item(db, redis, item):
    db.insert_item(item)
    pipe = redis.pipeline()
    pipe.execute_command("BF.ADD", "items:bf", item["id"])
    pipe.delete(f"item:{item['id']}")  # Clear any lingering __NULL__
    pipe.execute()

3. Operational controls

Step 1

Commit new item to PostgreSQL.

Step 2

Execute `BF.ADD items:bf {item_id}` and `DEL item:{item_id}` in a Redis pipeline.

Step 3

Also stream inserts via Debezium CDC to heal any crash between DB commit and Redis update.

Implementation note

Adds 1 fast RedisBloom check (~0.2ms, or 0ms if using an in-pod Bloom filter) to eliminate 99.9% of penetration load.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Layer per-IP / per-ASN rate limiting on `404` responses at the API Gateway, and use `singleflight` on Redis misses so repeated probes for the same ID coalesce into 1 DB query.

  • ↗
    Apply Nginx/Envoy sliding-window rate limits per IP/subnet.
  • ↗
    Penalize IPs exceeding `20` 404-responses/min with a `429 Too Many Requests`.
  • ↗
    Combine with `singleflight` + `60s` `__NULL__` caching for any key that reaches DB.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

If `DEL` is omitted, a pre-probed `__NULL__` key blocks reads of the newly created item for 60s.

Failure scenario 2

Overly aggressive global 404 limits can block legitimate corporate NAT proxies.

Alternatives considered

  • WAF bot challenge / Captcha on high-404 ASNs.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Block non-existent key floods using a multi-layer shield: strict edge format validation, a fast in-memory/Redis Bloom Filter (or Cuckoo Filter) pre-check, and short-TTL Negative Caching (__NULL__ sentinels) for keys that pass the filter.
  • 02Trade-off tip: In-pod Bloom handles >500k QPS with zero Redis traffic, but requires CDC/PubSub delta streaming to avoid false negatives on new inserts.
  • 03Watch out for: If DEL is omitted, a pre-probed __NULL__ key blocks reads of the newly created item for 60s.
