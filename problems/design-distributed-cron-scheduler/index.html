The idea to keep with you

Design a distributed cron and delayed-job scheduler supporting 10M recurring schedules, 50,000 job triggers/sec at peak, <2s trigger drift, and strict protection against duplicate execution during worker crashes or GC pauses.

From patterns to decisions.

Scaling a distributed cron scheduler to 50,000 triggers/sec requires partitioning schedules into time-bucketed shards, issuing monotonic fencing tokens via etcd/Raft leases, and enforcing idempotency keys at target executors.

Full walkthrough · 5 stages
01
STAGE 01 · REQUIREMENTS & MATHL5 · APPLIED DESIGN

Clarify Scale, Drift SLO & Execution Semantics.

With 10M active schedules (~1 KB metadata each = ~10 GB), metadata fits easily in a sharded database, while 50,000 triggers/sec at top-of-minute spikes demands horizontal partitioning. Target <2s trigger drift, at-least-once dispatch with idempotency_key = hash(job_id, fire_ts), and zero split-brain double execution when workers pause or partition.

02
STAGE 02 · NAIVE BOTTLENECKSL5 · APPLIED DESIGN

Why Central Polling & Unfenced Locks Fail.

A single SELECT * FROM jobs WHERE next_run <= NOW() FOR UPDATE SKIP LOCKED creates severe B-Tree hot-page contention at top-of-minute boundaries. Worse, if Worker A acquires a 10s Redis lock, hits a 12s stop-the-world GC pause, and wakes up after Worker B took over, both workers fire the same billing webhook unless downstream storage checks a monotonic fencing token.

03
STAGE 03 · ENTERPRISE ARCHITECTUREL6 · SCALE & TRADE-OFFS

Time-Bucket Sharding + Etcd Fencing Tokens + Idempotent Executors.

Shard schedules by (minute_bucket, shard_id) so each scheduler node owns disjoint time-bucket partitions via an etcd lease. When Worker B takes over a partition, etcd increments the monotonic fencing token (epoch=42). Every state update and executor dispatch includes (epoch, idempotency_key), rejecting stale epoch=41 zombie writes.

Scheduler Data & Control Flow

Time-Bucket Sharded Cron & Fencing Pipeline

1.Bucket Sharding: Eliminates top-of-minute full-table index contention.

2.Fencing Token: Rejects delayed zombie worker writes with epoch < max_seen_epoch.

3.Idempotent Dispatch: Deterministic (job_id, scheduled_epoch) key deduplicates retries.

Caption: Combining time-bucket sharding with monotonic fencing tokens and idempotent executors prevents both hot-shard stalls and GC-pause double execution.

def execute_fenced_job(db_conn, job_id: str, scheduled_ts: int, epoch: int, webhook_fn) -> str:
    """Assumes db_conn enforces epoch >= last_epoch atomically before side effects."""
    cur = db_conn.execute(
        "UPDATE scheduled_runs SET status = 'RUNNING', last_epoch = %s "
        "WHERE job_id = %s AND scheduled_ts = %s AND status = 'PENDING' AND last_epoch < %s",
        (epoch, job_id, scheduled_ts, epoch),
    )
    if cur.rowcount != 1:
        db_conn.rollback()
        return "SKIPPED_STALE_OR_DUPLICATE"
    db_conn.commit()

    idem_key = f"{job_id}:{scheduled_ts}"
    return webhook_fn(job_id=job_id, idempotency_key=idem_key)
04
STAGE 04 · SCALE & BURST CONTROLL6 · SCALE & TRADE-OFFS

Absorbing Top-of-Minute Spikes & Slow Webhook Targets.

When 1M users schedule 0 * * * *, all jobs fire at :00 seconds. Apply deterministic jitter (hash(job_id) % 5s) for non-strict jobs, pre-fetch upcoming 60s buckets into an in-memory hashed time wheel, and dispatch through Kafka/SQS with per-tenant concurrency bulkheads and a Dead Letter Queue (DLQ) for failing webhooks.

05
STAGE 05 · INTERVIEW FOLLOW-UPSL7 · STAFF / PRINCIPAL

Multi-Region Failover & Catch-Up Policies.

Support explicit per-job misfire policies (SKIP_MISSED, FIRE_ONCE, BACKFILL_ALL) so a 10-minute outage does not accidentally fire 10x duplicate billing runs on recovery.
