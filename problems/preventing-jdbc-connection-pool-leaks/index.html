01 / UnderstandFailure & constraints

Clarify what is failing.

Unclosed `Connection` objects on exception paths stay open in the JVM (until GC, if ever) with `autoCommit=false`, leaving Postgres `idle in transaction`; sequential `close()` calls in `finally` abort if the first `close()` throws.

Design objective

Query `pg_stat_activity` for `state = 'idle in transaction'` and `now() - state_change`.

Requirements

  • Eliminate all JDBC `Connection`, `Statement`, and `ResultSet` leaks on both normal and exception code paths.
  • Detect any future connection leak within 5 seconds in logs with exact stack traces before the pool saturates.
  • Prevent `idle in transaction` connections from holding Postgres row locks or blocking `VACUUM` indefinitely.
  • Ensure pool sizing aligns with Postgres `max_connections` across 20 scaled pods.

Constraints

  • 20 application pods each with `maximumPoolSize: 30` = 600 potential connections against an RDS instance with `max_connections = 500`.
  • Legacy batch/DAO methods use raw `DataSource.getConnection()` for streaming large cursors and custom transaction rollbacks.
  • Cannot restart pods as a permanent fix; must eliminate the leak and bound blast radius.
Known failure modes

name: Pool Size Exceeds Postgres max_connections; description: 20 pods x 30 = 600 > 500 `max_connections`, crashing new pods on boot.; mitigation: Drop `maximumPoolSize` to 10 or deploy RDS Proxy / PgBouncer.

  1. 01Guaranteed AutoCloseable scope: DAO acquires Connection inside try(...); HikariCP starts a 5,000ms leak-detection timer.
  2. 02Multiplexed connection: 20 pods x 10 pool connections = 200 client slots multiplexed onto 32 Postgres server connections.
  3. 03Deterministic cleanup on error: On exception, catch rolls back and rethrows while try-with-resources closes ResultSet, Statement, and Connection.
  4. 04Immediate leak alerting: If any unclosed path holds a connection >5s, HikariCP logs a WARN stack trace pointing to the exact line.
  5. 05DB-side lock & vacuum protection: Postgres terminates any session stuck idle in transaction >30s, preventing row-lock pileups.
Try-with-resources fixes the root leak, HikariCP leakDetectionThreshold exposes regressions in 5s, and Postgres timeouts protect locks.

The invariants

  • Wrap Connection in outer try (...) and PreparedStatement/ResultSet in inner try (...).
  • Catch exceptions to call conn.rollback() before rethrowing; outer try always calls conn.close().
  • Set leak-detection-threshold: 5000, connection-timeout: 5000, maximum-pool-size: 10.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Add PgBouncer or RDS Proxy when horizontal pod scaling (`pods * pool_size`) or serverless Lambdas exceed Postgres `max_connections` (or ~200+ connections), as Postgres forks 1 OS process per connection.

Step 1

Calculate max_pods * maximum_pool_size (e.g., 50 pods x 10 = 500 -> hits limit).

Step 2

Deploy PgBouncer in transaction pooling mode (default_pool_size = 40).

Step 3

Keep prepareThreshold=0 (or PgBouncer 1.21+ protocol-level prepared statement support).

04 / ImplementConfiguration & code

Build the safeguards.

Set PostgreSQL JDBC `socketTimeout=15` and `connectTimeout=3` alongside `maxLifetime=1500000` so dead TCP sockets don't hang threads forever, and isolate slow batch queries onto a separate pool.

1. Reference implementation

JAVA · Solution
public void reconcileBatch(List<Payment> batch) throws SQLException {
    try (Connection conn = dataSource.getConnection()) {
        conn.setAutoCommit(false);
        try (PreparedStatement ps = conn.prepareStatement("UPDATE payments SET status = ? WHERE id = ?")) {
            for (Payment p : batch) {
                ps.setString(1, p.status());
                ps.setLong(2, p.id());
                ps.addBatch();
            }
            ps.executeBatch();
            conn.commit();
        } catch (Exception ex) {
            conn.rollback();
            throw ex;
        }
    } // Always closes conn and returns it to HikariCP
}

2. Harden for scale

Set PostgreSQL JDBC `socketTimeout=15` and `connectTimeout=3` alongside `maxLifetime=1500000` so dead TCP sockets don't hang threads forever, and isolate slow batch queries onto a separate pool.

YAML · Scale hardening
# JDBC URL with TCP timeouts so half-open sockets fail fast
jdbc:postgresql://prod-pg.internal:5432/payments?connectTimeout=3&socketTimeout=15&tcpKeepAlive=true

3. Operational controls

Step 1

Add `?connectTimeout=3&socketTimeout=15` to the JDBC URL.

Step 2

Separate OLTP (`leakDetectionThreshold=5000`) from Batch (`leakDetectionThreshold=60000`) DataSources.

Step 3

Alert on `hikaricp_connections_active == hikaricp_connections_max`.

Implementation note

factor: Raw try-with-resources vs. Spring `TransactionTemplate`; pro: `TransactionTemplate` eliminates boilerplate `setAutoCommit`/`rollback` code completely.; con: Requires Spring TX manager; raw `try-with-resources` works in any plain Java/JDBC code.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Enforce SonarQube/SpotBugs static analysis (`java:S2095`) on PRs, and run an integration test with `leakDetectionThreshold=1000` that asserts zero leak warnings under simulated `SQLException`s.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

name

Missing `socketTimeout` During AZ Partition; description: An AZ network blip leaves JDBC `read()` blocked for 15+ minutes waiting on OS TCP retries.; mitigation: Always set `socketTimeout` (e.g., 15s) in the JDBC connection string.

name

Factory Method Returning Unclosed Connection; description: A utility method opens a `Connection` and returns it to a caller that forgets `try-with-resources`.; mitigation: Ban methods returning raw `Connection` or `ResultSet`; pass lambdas/callbacks (`Consumer<Connection>`) instead.

Alternatives considered

  • Migrate remaining raw JDBC DAOs to Spring `JdbcClient` / `JdbcTemplate`.
