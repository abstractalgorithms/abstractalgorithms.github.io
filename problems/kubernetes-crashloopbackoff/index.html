In Kubernetes 1.29, CreateContainerConfigError (kubelet cannot mount a missing required Secret/ConfigMap) and CrashLoopBackOff (container starts and exits non-zero) are expected failure signals—not outages by themselves. They become outages when RollingUpdate is configured with maxUnavailable: 50%, allowing Kubernetes to terminate 6 healthy pods before verifying the new pods pass readiness.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: `maxUnavailable: 0` + SyncWaves + CI Gates.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Protect all 12 healthy replicas across every GitOps deploy:

  • Zero-Capacity-Loss Rollout: Set maxUnavailable: 0, maxSurge: 25% (temporary peak 15 pods), and progressDeadlineSeconds: 180 so old pods never terminate until new pods pass /readyz.
  • ArgoCD SyncWaves: Place ExternalSecret in sync-wave: "-1" and Deployment in sync-wave: "0" so secrets exist before pods are scheduled.
  • Strict Config Validation: Remove optional: true on required configs, use content-hashed ConfigMap/Secret names, and run kubeconform + helm-unittest in CI.
Safe GitOps Rollout

ArgoCD SyncWave (-1 Secret -> 0 Surge) Preserves 12 Healthy Pods

SyncWaves block Deployment rollout until ExternalSecrets are Ready, and maxUnavailable: 0 protects all 12 live pods.

spec:
  replicas: 12
  progressDeadlineSeconds: 180
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0     # Never drop below 12 healthy pods
      maxSurge: 25%         # Surge up to 15 pods during rollout
  template:
    spec:
      containers:
        - name: checkout
          envFrom:
            - secretRef:
                name: checkout-db-creds-v2
                optional: false
            - configMapRef:
                name: checkout-flags-v2
                optional: false
