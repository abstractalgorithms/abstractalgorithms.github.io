Quorum Consistency & Stale
Reads in Replicated Stores.

Even with R + W > N (N=3, W=2, R=2), partial replica degradation, sloppy quorums, or un-synchronized node restarts allow a read quorum to intersect only stale replicas and return outdated values.

01 / UnderstandFailure & constraints

Clarify what is failing.

Both sloppy quorum (`HintedR4`) and an amnesiac reboot of `R2` reduced the number of canonical replicas holding `v2` below `N - R + 1` (which must be >= 2 for `R=2` to guarantee intersection).

Design objective

Show that with `N=3, R=2`, at least 2 canonical replicas must durably hold `v2` for every 2-node read subset to intersect `v2`.

Requirements

  • Guarantee that once a write `v2` is acknowledged to a client, no subsequent read returns `v1` (linearizable / read-your-writes consistency for critical flags).
  • Prevent newly restarted or snapshot-restored replicas from serving reads until their state is synchronized.
  • Maintain availability for writes when 1 of 3 replicas is degraded, without silently violating `R + W > N` overlap.
  • Detect and heal divergent replica versions automatically in the background.

Constraints

  • Steady-state workload is 40,000 reads/sec and 5,000 writes/sec across 3 AZs (inter-AZ RTT ~ 1.2 ms).
  • Read p99 latency must stay under 12 ms during normal operation.
  • Replicas must survive single-node disk/EBS snapshot restores without corrupting quorum invariants.
Known failure modes

Treating hinted handoff nodes as equivalent to canonical replicas in `W` ack counting.

02 / Map the systemArchitecture & invariants

Separate concerns. Map the flow.

Fetch 1 full value + `R-1` digests from `ACTIVE` canonical replicas; if digests differ, fetch all full values, pick the highest HLC/version, and synchronously repair stale replicas before returning.

  1. 01Write to canonical replicas only: Coordinator refuses sloppy handoff to R4; requires 2 canonical acks from {R1, R2, R3}.
  2. 02R2 stays in CATCHUP on reboot: Gossip marks R2 as CATCHUP; R2 streams missed ranges from R1 via Merkle tree diff before joining R/W.
  3. 03Read hits healthy R1 + R3: Because R2 is gated, R=2 read contacts R1 (has v2) and R3 (has v1 digest) -> detects mismatch.
  4. 04Synchronously repair R3: Coordinator writes v2 to R3 and awaits ack before returning v2 to the client, ensuring monotonicity.
  5. 05Re-admit R2 after catchup: Once Merkle sync completes, R2 transitions to ACTIVE and safely participates in quorums.
Disabling sloppy quorum, gating restarted nodes behind Merkle catchup, and running blocking read repair restore the R+W>N invariant.

The invariants

  • Filter replica list to ACTIVE nodes only (excluding CATCHUP nodes).
  • Send 1 get_full and R-1 get_digest calls in parallel.
  • If all digests match, return immediately (~1.2 ms).
  • On mismatch, fetch full payloads, resolve winner by (hlc_ts, node_id), write winner to stale replicas, and await repair acks.
03 / Trace the lifecycleKey decisions

Follow the execution path.

For feature flags and session metadata (5,000 WPS, small key-value payloads), Raft/Paxos is almost always superior because it gives true linearizability without LWW clock-skew bugs or read-repair complexity.

Step 1

Compare write volume: 5,000 WPS across sharded Raft ranges (e.g., 64 ranges = ~78 WPS/range) is trivial for Raft.

Step 2

Note that Raft follower reads with leader lease or ReadIndex achieve < 12 ms p99.

Step 3

Reserve leaderless Dynamo quorums for massive multi-region write-heavy workloads where AP availability outweighs strict linearizability.

YAML · Lifecycle trace
# Example Cassandra/ScyllaDB LWT (Paxos) vs QUORUM

read_consistency: SERIAL    # Linearizable read
sloppy_quorum: false

Key trade-off

Paxos/LWT (SERIAL) requires 2–4 RTTs on writes, increasing write latency from ~2ms to ~6ms, while guaranteeing linearizability.

04 / ImplementConfiguration & code

Build the safeguards.

Store a unique `generation_id` / `node_epoch` in both local disk and the cluster's gossip/metadata ring; a mismatch or missing clean-shutdown marker forces `CATCHUP` mode.

1. Reference implementation

PYTHON · Solution
from concurrent.futures import ThreadPoolExecutor

def quorum_read(key: str, active_replicas: list, r_quorum: int = 2):
    if len(active_replicas) < r_quorum:
        raise RuntimeError("Insufficient ACTIVE replicas for strict R quorum")
    targets = active_replicas[:r_quorum]
    with ThreadPoolExecutor(max_workers=r_quorum) as pool:
        full_fut = pool.submit(targets[0].get_full, key)
        digest_futs = [pool.submit(rep.get_digest, key) for rep in targets[1:]]
        winner = full_fut.result(timeout=0.01)
        digests = [f.result(timeout=0.01) for f in digest_futs]

    if all(d == winner.digest for d in digests):
        return winner.value

    # Digest mismatch: fetch full values and perform blocking read repair
    responses = [winner] + [rep.get_full(key) for rep in targets[1:]]
    newest = max(responses, key=lambda rec: (rec.hlc_ts, rec.version))
    for rep, rec in zip(targets, responses):
        if rec.digest != newest.digest:
            rep.repair_write(key, newest)  # synchronous before returning
    return newest.value

2. Harden for scale

Store a unique `generation_id` / `node_epoch` in both local disk and the cluster's gossip/metadata ring; a mismatch or missing clean-shutdown marker forces `CATCHUP` mode.

PYTHON · Scale hardening
def should_enter_catchup(local_max_hlc: int, peer_max_hlc: int, clean_shutdown: bool) -> bool:
    if not clean_shutdown:
        return True
    # Even on clean shutdown, if node was offline > 5s, require Merkle sync
    return (peer_max_hlc - local_max_hlc) > 5_000_000  # 5s in microseconds

3. Operational controls

Step 1

On clean shutdown, flush memtables and write a `clean_shutdown_seq` to local disk.

Step 2

On boot, compare local `last_committed_hlc` against peers' `min_committed_hlc`.

Step 3

If behind by > threshold or `clean_shutdown` flag is absent, stay in `CATCHUP` and run Merkle tree sync before advertising `ACTIVE`.

Implementation note

Blocking read repair increases tail latency on divergent reads by 1 extra RTT, but prevents stale-read regressions on subsequent reads.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Yes, during an in-flight write before `W=2` finishes: Client A may read `v2` from `R1`, while Client B reads `v1` from `{R2, R3}` before `R2` receives `v2`—unless reads also trigger blocking read repair or use consensus.

  • ↗
    Trace: Write `v2` reaches `R1` first (not yet `R2`). Client A reads `{R1, R2}` -> sees `v2` and repairs `R2` (or doesn't if async).
  • ↗
    With *blocking* read repair, Client A's read repairs `R2` before returning `v2` to Client A, so any subsequent Client B read `{R2, R3}` sees `v2`.
  • ↗
    Without blocking read repair, Client B can read `v1` *after* Client A read `v2` (violating linearizability).

# ABD (Attiya-Bar-Noy-Dolev) algorithm summary:
# A quorum read must write back (phase 2) the winning value to W replicas
# BEFORE returning to the caller to guarantee linearizability in shared-memory quorums.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
