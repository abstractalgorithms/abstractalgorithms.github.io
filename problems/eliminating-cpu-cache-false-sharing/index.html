The idea to keep with you

A high-frequency Java telemetry ingestion service runs 8 worker threads on an 8-core x86_64 server, each incrementing its own dedicated counter in a shared long[8] array (or adjacent volatile fields in a metrics object) at 100M events/sec. Despite zero locks and zero logical data sharing, CPU utilization spikes to 100% sys/kernel-like stall cycles and total throughput collapses from ~800M ops/sec to ~25M ops/sec. Diagnose the hardware root cause and redesign the counter structure in Java to restore linear multi-core scaling.

STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why 64-byte cache-line false sharing kills lock-free scaling.

Modern x86_64 CPUs transfer memory between L1/L2 caches and RAM in 64-byte cache lines, not individual 8-byte longs. A long[8] array occupies 64 contiguous bytes—fitting all 8 thread counters on a single cache line. Even with zero locks and distinct array indices, every core writing its own long must broadcast a Read-For-Ownership (RFO) under the MESI coherence protocol, invalidating all other cores' L1 caches and collapsing throughput from 800M to 25M ops/sec.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens during MESI RFO cache-line ping-ponging.

When Core 0 writes counters[0] and Core 1 writes counters[1] concurrently:

  1. Cache-Line Ownership Theft: Core 0 transitions the shared 64-byte line to Modified, invalidating Core 1's copy.
  2. HITM Stall Cycles: Core 1 stalls waiting to fetch the Modified line (HITM in perf c2c) over the inter-core mesh.
  3. Serialized Execution: Instead of 8× parallel speed, all 8 cores serialize on one cache line.
MESI Coherence Ping-Pong

False Sharing on long[8] (1 Cache Line) vs. Padded Stripes

Padding each counter to >= 64 bytes (or using LongAdder) keeps each core's writes in its own L1 cache line.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive solution (and why AtomicLong[] or volatile fields still suffer).

Switching from long[] to AtomicLong[] or separate volatile long c0, c1... fields does not fix false sharing:

  • Adjacent Heap Layout: volatile long fields in the same object sit side-by-side in memory on the same 64-byte line.
  • AtomicLong Array Density: Contiguous AtomicLong references/objects can still share cache lines, and AtomicLong CAS retries under contention.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Striped LongAdder / 64-Byte Padded Cells.

High-frequency Java telemetry engines eliminate false sharing cleanly in JDK 17+:

  • java.util.concurrent.atomic.LongAdder: Uses internal @Contended-padded Cell stripes hashed by thread probe; each thread increments its own 64-byte-isolated Cell in < 5 ns amortized, and the 100 ms scraper calls .sum() to aggregate.
  • Explicit 64-Byte Stride / @Contended: When indexing by fixed worker ID (0..7), pad each slot to 64 bytes (stride of 8 longs = 64 bytes, or 16 longs = 128 bytes to defeat hardware spatial prefetchers) with zero JVM flags required.
  • Verification: Validate with JMH + perf c2c (L1-dcache-load-misses and HITM drop by > 95%).
Cache-Line Isolation

Thread-Local L1 Cache Lines via LongAdder / 64B Stride

1.LongAdder Stripes: Maintains @Contended-padded Cell[] so writers never share cache lines.

2.128B Stride Option: Using stride=16 longs also avoids adjacent-line hardware prefetcher bouncing.

3.Zero Lock Hot Path: Achieves < 5 ns amortized increment and linear 16-core scaling.

4.perf c2c Verified: Eliminates cross-core HITM stalls in hardware performance counters.

Isolating each thread's counter on its own 64-byte (or 128-byte) cache line restores 800M+ ops/sec linear scaling.

import java.util.concurrent.atomic.LongAdder;

// Option 1: JDK standard striped & @Contended-padded counter
public final class TelemetryCounters {
    private final LongAdder events = new LongAdder();
    public void record() { events.increment(); }         // <5 ns, zero RFO bouncing
    public long snapshot() { return events.sum(); }    // called every 100ms
}

// Option 2: Fixed worker-ID array with 128-byte stride (no -XX:-RestrictContended needed)
public final class PaddedWorkerCounters {
    private static final int STRIDE = 16; // 16 * 8B = 128B (defeats spatial prefetcher)
    private final long[] slots;
    public PaddedWorkerCounters(int workers) { this.slots = new long[workers * STRIDE]; }
    public void inc(int workerId) { slots[workerId * STRIDE]++; }
    public long total(int workers) {
        long s = 0;
        for (int i = 0; i < workers; i++) s += slots[i * STRIDE];
        return s;
    }
}

STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Cache-Line Padding applies in High-Throughput Systems.

Eliminating false sharing is a staple of low-latency infrastructure:

  • LMAX Disruptor Ring Buffer: Padding Sequence cursors (p1..p7) so producer and consumer heads never share a cache line.
  • Metrics & Observability Agents: LongAdder / Striped64 powering Micrometer, Prometheus, and Netty byte counters.
  • HFT & Telemetry Pipelines: Per-core statistics arrays padded to 64/128 bytes.
