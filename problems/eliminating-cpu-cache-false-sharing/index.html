01 / UnderstandFailure & constraints

Clarify what is failing.

Adjacent 8-byte longs share a 64-byte L1 cache line, causing MESI Read-For-Ownership invalidations across cores.

Design objective

Calculate memory layout: 8 longs * 8 bytes = 64 bytes (1 cache line).

Requirements

  • Explain how 64-byte L1/L2 cache lines and the MESI coherence protocol serialize writes across cores even when threads access distinct array indices.
  • Eliminate cross-core cache-line invalidations (RFO traffic) for 8–64 concurrent writer threads in Java.
  • Preserve exact read consistency when a background metrics scraper reads the aggregate sum every 100 ms.
  • Benchmark and verify the fix using JMH / perf c2c metrics (L1-dcache-load-misses and HITM reduction).

Constraints

  • Must scale linearly up to 16 hardware threads with < 5 ns amortized per-increment latency.
  • Must use Java (JDK 17+) without native JNI/C++ extensions.
  • Memory overhead per counter stripe must remain bounded (< 4 KB per active thread).
Known failure modes

Misdiagnosing false sharing as GC pause or OS scheduler contention because CPU % looks busy.

Stride = 128B (16 longs)

  1. 01RFO Broadcast: Core 0 broadcasts Read-For-Ownership to claim Modified state on shared 64B line.
  2. 02Cache Invalidation: Core 1's copy of counters[1] is invalidated even though it only reads/writes index 1.
  3. 03Line Bouncing: Core 1 stalls 40-80 ns fetching the modified line back from Core 0.
  4. 04Isolated Line A: With 128B stride, Core 0 holds Line A permanently in Modified state.
  5. 05Isolated Line B: Core 1 holds Line B permanently in Modified state with zero RFO traffic.
Striding thread slots by 128 bytes (16 longs) separates writers across distinct cache lines and defeats x86 adjacent-line prefetchers.

The invariants

  • Allocate new AtomicLongArray(numWorkers * 16) so each worker owns a 128-byte region.
  • Use lazySet / setRelease when only one thread writes each slot and exact atomic RMW is unnecessary.
  • Sum across i = 0..numWorkers-1 at index i * 16 for the 100 ms scraper.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Strided arrays and LongAdder work out of the box on JDK 17+, whereas @Contended requires -XX:-RestrictContended for application classes.

Step 1

Verify JVM flag requirements: @Contended is restricted to java.base unless -XX:-RestrictContended is passed.

Step 2

Use class-hierarchy padding (PrePad -> Value -> PostPad) when padding individual objects like Disruptor Sequence.

04 / ImplementConfiguration & code

Build the safeguards.

Never bind per-thread padded buffers to ThreadLocal for 100k virtual threads; use LongAdder or carrier-thread-bounded striping.

1. Reference implementation

JAVA · Solution
import java.util.concurrent.atomic.AtomicLongArray;

public final class PaddedWorkerCounters {
    private static final int STRIDE_LONGS = 16; // 16 * 8B = 128B (defeats 64B line + spatial prefetcher)
    private final int numWorkers;
    private final AtomicLongArray slots;

    public PaddedWorkerCounters(int numWorkers) {
        this.numWorkers = numWorkers;
        this.slots = new AtomicLongArray(numWorkers * STRIDE_LONGS);
    }

    // Single-writer per workerId: avoid expensive LOCK XADD by reading plain/opaque + setRelease
    public void incrementSingleWriter(int workerId) {
        int idx = workerId * STRIDE_LONGS;
        long next = slots.getPlain(idx) + 1;
        slots.setRelease(idx, next);
    }

    public long sum() {
        long total = 0;
        for (int i = 0; i < numWorkers; i++) {
            total += slots.getAcquire(i * STRIDE_LONGS);
        }
        return total;
    }
}

2. Harden for scale

Never bind per-thread padded buffers to ThreadLocal for 100k virtual threads; use LongAdder or carrier-thread-bounded striping.

JAVA · Scale hardening
import java.util.concurrent.atomic.LongAdder;

public final class VirtualThreadSafeCounter {
    private final LongAdder adder = new LongAdder();

    public void recordEvent() {
        adder.increment();
    }

    public long snapshot() {
        return adder.sum();
    }
}

3. Operational controls

Step 1

Recognize that 100,000 virtual threads * 128B ThreadLocal = 12.8 MB of fragmented heap.

Step 2

`LongAdder` (Striped64) caps its internal `Cell[]` table at the nearest power of 2 >= `Runtime.getRuntime().availableProcessors()`.

Implementation note

`getPlain` + `setRelease` avoids `LOCK XADD` (~10 ns) on x86_64, dropping increment cost to ~1-2 ns when each slot has a single writer.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Pad both the `head` and `tail` sequence cursors onto separate 128-byte cache lines and cache the remote cursor locally in each thread.

  • ↗
    Place `producerSeq` and `consumerSeq` on distinct 128-byte cache lines.
  • ↗
    Cache `cachedConsumerSeq` inside the producer's cache line so the producer only reads the volatile `consumerSeq` when the ring appears full.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Know what each control buys.

Option 2Increases object count if thousands of counters are allocated.—

Review questions

Failure scenario 1

Allocating per-virtual-thread `ThreadLocal` padded objects causes OOM or severe GC pressure.

Failure scenario 2

Forgetting to pad the ring buffer's underlying `Object[]` array ends or letting adjacent slots share a line when elements are small primitives.

Alternatives considered

  • Use `AtomicLongArray` with `head` at index 16 and `tail` at index 32.
