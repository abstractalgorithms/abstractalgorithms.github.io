Avoiding Partition Hotspots
on Monotonic Keys.

Using raw timestamps, auto-increment IDs, or UUIDv1 as a primary partition key routes 100% of current writes to a single shard or range server, saturating one node's CPU and NVMe IOPS while the rest of the cluster sits idle.

01 / UnderstandFailure & constraints

Clarify what is failing.

Consistent hashing maps identical partition keys to the exact same token and replica set. Because all 250k events/sec share the current hour string, 100% of writes hit one replica set.

Design objective

Inspect nodetool tablestats and nodetool tpstats to confirm one node has 16x higher write count and pending compaction tasks.

Requirements

  • Distribute the 250,000 writes/sec evenly across all 16 nodes (~15,625 writes/sec per node) with < 10% skew.
  • Support both single-device time-range queries (last 24 hours for device X) and global recent-events queries (last 15 minutes across all devices).
  • Keep individual partition sizes bounded below 100 MB (or 100,000 rows) to prevent compaction stalls and tombstones.
  • Maintain p99 write latency under 15 ms and p99 read latency under 50 ms.

Constraints

  • Cluster has 16 nodes (RF=3) or 16 logical shards with 128 KB/s–1 MB/s per-device burst rates.
  • Schema changes must avoid full-table cross-node joins; queries must specify the partition key.
  • Write amplification from secondary indexes is unacceptable at 250,000 writes/sec.
Known failure modes

The hot node runs out of commitlog/memtable bandwidth, causing cluster-wide coordinator timeouts.

32-way async merge

  1. 01Deterministic key salting: Combines shard_id with minute_bucket so writes spread across all 16 nodes evenly.
  2. 02Parallel partition writes: Token-aware driver routes each write directly to the owning replica set.
  3. 03Zero single-node hotspot: All 16 nodes operate at ~15,625 writes/sec and < 15 ms p99 latency.
  4. 04Targeted or bounded fan-out: Per-device reads hit 1 shard; global 15m reads issue 32 parallel async queries.
  5. 05Top-K stream merge: Coordinator merges 32 sorted streams in memory using a min-heap in < 50 ms p99.
Deterministic salting (hash(device_id) % 32) plus fine-grained time buckets distributes 250k writes/sec across all 16 nodes.

The invariants

  • Compute shard_id = zlib.crc32(device_id.encode()) % 32.
  • Write to both telemetry_by_device and telemetry_global_recent.
  • Query all 32 shards concurrently and merge with heapq.merge.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Size N to 2x–4x node count (32 for 16 nodes) so every node owns ~2 shards without excessive read fan-out; use deterministic hashing unless a single tenant dominates > 10% of writes.

Step 1

Calculate per-shard write throughput (250k / N) and partition byte size.

Step 2

Benchmark 32-way vs 256-way async read latency under p99 load.

PYTHON · Lifecycle trace
# Hybrid salt: deterministic for normal devices, 4-way sub-salted for VIP devices
def get_hybrid_shard(device_id: str, seq: int, is_high_volume: bool) -> int:
    base = zlib.crc32(device_id.encode()) % 32
    return (base + (seq % 4)) % 32 if is_high_volume else base
Key trade-off

Deterministic salting keeps single-device reads to 1 shard, whereas random salting forces N-way reads for everything.

04 / ImplementConfiguration & code

Build the safeguards.

With RF=3 and LOCAL_QUORUM, losing 1 node is transparent; if an entire shard's quorum is lost, per-shard timeouts and partial-result degradation prevent cascading thread exhaustion.

1. Reference implementation

PYTHON · Solution
import asyncio
import heapq
import zlib

NUM_SHARDS = 32

def get_shard_id(device_id: str) -> int:
    return zlib.crc32(device_id.encode("utf-8")) % NUM_SHARDS

async def query_global_minute(session, minute_bucket: str, limit: int = 100):
    tasks = [
        session.execute_async(
            "SELECT event_ts, device_id, payload FROM telemetry_global_recent "
            "WHERE shard_id = %s AND minute_bucket = %s LIMIT %s",
            (shard, minute_bucket, limit),
        )
        for shard in range(NUM_SHARDS)
    ]
    results = await asyncio.gather(*tasks)
    merged = heapq.merge(*results, key=lambda r: r.event_ts, reverse=True)
    return [row for _, row in zip(range(limit), merged)]

2. Harden for scale

With RF=3 and LOCAL_QUORUM, losing 1 node is transparent; if an entire shard's quorum is lost, per-shard timeouts and partial-result degradation prevent cascading thread exhaustion.

PYTHON · Scale hardening
results = await asyncio.gather(*tasks, return_exceptions=True)
valid_streams = [r for r in results if not isinstance(r, Exception)]
partial = len(valid_streams) < NUM_SHARDS

3. Operational controls

Step 1

Set per-shard read timeout to 30 ms with speculative execution.

Step 2

Catch TimeoutError per shard in asyncio.gather(return_exceptions=True) and return partial results with a flag.

Implementation note

Dual-writing to two query-optimized tables doubles write bandwidth, which is acceptable because writes are now spread across 16 nodes.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Range-partitioned databases split contiguous key ranges into tablets/ranges. Leading with a hash prefix, bit-reversed sequence, or UUIDv4 spreads inserts across all range leaders.

  • ↗
    Replace AUTO_INCREMENT / timestamp PK with (shard_id, timestamp, device_id) or bit-reversed sequence.
  • ↗
    Enable automatic load-based range splitting in CockroachDB/Spanner.
SQL · Verification
CREATE TABLE telemetry_spanner (
    shard_id INT64 NOT NULL,
    event_ts TIMESTAMP NOT NULL,
    device_id STRING(36) NOT NULL,
    payload BYTES(MAX)

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Unbounded retries on a failed shard multiply read traffic by 3x and stall all 32-way queries.

Failure scenario 2

Using COMMIT_TIMESTAMP as the leading key in Spanner pins all inserts to the rightmost split.

Alternatives considered

  • Use bit-reversed sequential IDs in Spanner for single-column primary keys.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Prefix or salt partition keys with a deterministic shard bucket (hash(entity_id) % N) combined with a coarse time bucket (yyyy-mm-dd-hh), and execute bounded scatter-gather reads across the N buckets.
  • 02Trade-off tip: Deterministic salting keeps single-device reads to 1 shard, whereas random salting forces N-way reads for everything.
  • 03Watch out for: Unbounded retries on a failed shard multiply read traffic by 3x and stall all 32-way queries.
