The idea to keep with you

An IoT platform ingests 250,000 events/sec (~500 B each = 125 MB/s, 450 GB/hr) into a 16-node ScyllaDB/Cassandra cluster (RF=3) keyed by `(event_hour, created_at, device_id)`. One hot node hits 98% CPU and 1,400 ms p99 write latency while 15 nodes sit at 6% CPU. Redesign the partition key and query path to keep partitions < 100 MB and p99 write < 15 ms.

STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why monotonic partition keys create single-node bottlenecks.

Distributed wide-column and KV stores (Cassandra, ScyllaDB, DynamoDB) hash the partition key to choose which nodes own a row. When an IoT pipeline uses event_hour or created_at_ms as the partition key at 250,000 writes/sec (125 MB/s), every single event in the current hour hashes to the exact same token—turning a 16-node cluster into a 1-node bottleneck.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

100% write skew, 1,400 ms p99 latency, and compaction stalls.

Concentrating 450 GB/hour (125 MB/s) onto 1 replica set (RF=3) causes:

  1. CPU & NVMe Saturation: The hot node hits 98% CPU and 1,400 ms p99 write latency while the other 13-15 nodes sit at 6% CPU.
  2. Unbounded Partition Growth: A 1-hour partition accumulates 450 GB (far above the 100 MB Cassandra safe ceiling), triggering OOMs during compaction and repair.
  3. Coordinator Queue Bloat: Slow writes pile up across all coordinators, causing timeouts cluster-wide.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive salting mistakes (random salts & oversized buckets).

Two common fixes introduce new failure modes:

  • Random Salt Without Time Bucket: Using shard_id alone prevents hot writes, but partitions grow forever over months until multi-GB compactions OOM nodes.
  • Over-Salting (N=512) or Random Salt on Device Reads: Setting N=512 forces every global 15-minute dashboard query to issue 512 parallel scans; random salting forces even single-device queries to scatter-gather all N shards.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Deterministic Shard + 5-Min Bucket + TWCS.

Size both the shard count N and time bucket mathematically:

  • Shard Count (N = 32): 2x the 16-node cluster spreads 250,000 writes/sec to 7,812 writes/sec (3.9 MB/s) per shard (~23.4 MB/s per node at RF=3).
  • 5-Minute Time Buckets: At 450 GB/hr, a 1-hour bucket per shard is 14.06 GB (too large!). A 5-minute bucket (3.9 MB/s × 300 s / 12? Wait: 125 MB/s × 300 s = 37.5 GB / 32 = ~1.17 GB or 1-minute bucket = ~234 MB, or N=64 with 1-min = ~117 MB / N=128 1-min = ~58 MB!) keeps partitions compact, and TWCS drops expired TTL SSTables with zero compaction I/O.
  • Dual Access Paths: Deterministic shard_id = hash(device_id) % 32 lets single-device queries hit 1 shard, while global recent-events queries run bounded 32-way async scatter-gather (< 50 ms p99).
Write & Read Path

Deterministic Salt + Time-Window Compaction (TWCS)

Deterministic salting + fine time buckets keep write latency <15 ms while supporting both single-device and global queries.

CREATE TABLE telemetry_events (
    shard_id int,
    time_bucket text,       -- e.g. '2026-11-18T09:15' (1-min or 5-min bucket)
    event_ts timestamp,
    device_id uuid,
    payload blob,
    PRIMARY KEY ((shard_id, time_bucket), event_ts, device_id)
) WITH CLUSTERING ORDER BY (event_ts DESC, device_id ASC)
  AND compaction = {
    'class': 'TimeWindowCompactionStrategy',
    'compaction_window_unit': 'HOURS',
    'compaction_window_size': 1
  }
  AND default_time_to_live = 86400;
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where deterministic key salting is used.

Write sharding and time-bucketing are mandatory whenever monotonic keys meet distributed hash/range partitions:

  • IoT & Metrics Ingestion: Cassandra/ScyllaDB and DynamoDB time-series tables salt partition keys by hash(entity_id) % N.
  • Sequential ID Hotspots: Replacing AUTO_INCREMENT / UUIDv1 keys with UUIDv4/hash-prefixed keys prevents Spanner and Bigtable range-server hotspots.
