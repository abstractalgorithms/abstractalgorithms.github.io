TL;DR30-second simplified summary
▾

At 50M concurrent WebSocket connections (~1,000 Gateway Pods holding 50K connections each), statefulness lives strictly at the edge gateway layer while all routing and persistence remain horizontally scalable.

Each incoming message receives a time-ordered Snowflake ID (or per-channel sequence ID) so clients sort messages deterministically across devices without relying on client clocks. Messages persist asynchronously to ScyllaDB / Cassandra partitioned by (channel_id, time_bucket) to bound partition sizes.

Real-Time Presence, Heartbeat Hysteresis & Hybrid Fan-Out
Real-time presence uses periodic WebSocket heartbeats into TTL-backed Redis keys (SETEX 45s) with online/offline hysteresis, paired with hybrid push/pull fan-out for small vs. massive channels.
Consistent Hashing & Virtual Nodes
Consistent hashing assigns data keys to servers in a way that limits how many keys move when servers are added or removed. This helps avoid widespread cache misses and sudden load on databases.

Think of Gateway Routing & Offline Push Fallback as the intuition layer for Design a Real-Time Chat, Typing & Presence System (Slack / Discord / WhatsApp Scale): Implement route_chat_message to batch-resolve recipient gateways and split delivery between Pub/Sub and push queues.

def route_chat_message(presence_store, pubsub, push_queue, recipient_ids: list[str], msg: dict) -> None:
    gateways = presence_store.mget_gateways(recipient_ids)
    for uid, gw_id in zip(recipient_ids, gateways):
        if gw_id:
            pubsub.publish(f'gw:{gw_id}', {'user_id': uid, 'msg': msg})
        else:
            push_queue.enqueue({'user_id': uid, 'channel_id': msg['channel_id'], 'preview': msg['snippet']})
STAGE 03 · SAFE IMPLEMENTATION

Gateway Routing & Offline Push Fallback

1.Zero N+1 Lookups: Batching recipient IDs into one MGET keeps gateway routing O(1) round-trips.

2.Multi-Device Support: Map user_id -> set of (device_id, gateway_id) so desktop and mobile both receive live pushes.

3.Offline Push Decoupling: Enqueue offline notifications asynchronously so slow APNs/FCM calls never block live chat.

Batch MGET resolution splits recipients cleanly between live gateway Pub/Sub and async offline push queues.

STAGE 04 · SCALING & TRADE-OFFS

Sharding & Hot-Spot Mitigation

1.Fan-Out Cap: In a 100K-member channel, pushing 1 message/sec would emit 100K writes/sec; pull caps amplification.

2.Active-View Pull: Only users currently viewing the massive channel poll or subscribe to its lightweight delta stream.

3.Lazy Presence: Clients subscribe to presence only for visible DM/sidebar contacts, avoiding global broadcasts.

Capping push fan-out at 500 members and using lazy presence subscriptions prevents 100K-member storms.

Failure Modes & Graceful Degradation

1.Full-Jitter Backoff: Spreading reconnects over 0..30s prevents TLS handshake storms after a gateway node restarts.

2.Slow-Consumer Isolation: Close sockets whose outbound send buffer fills; they recover missed messages via gap sync on reconnect.

3.Presence Hysteresis: 45s Redis TTL with 30s heartbeats absorbs transient 3G/4G packet loss without flapping offline.

Jittered reconnects, bounded socket send rings, and 45s heartbeat hysteresis contain mobile network churn.
