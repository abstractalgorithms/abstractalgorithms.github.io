01 / UnderstandFailure & constraints

Clarify what is failing.

The background heartbeat thread proves TCP liveness, while max.poll.interval.ms measures application-thread progress between poll() calls.

Design objective

Compare session.timeout.ms (45s) vs max.poll.interval.ms (300s) in broker GroupCoordinator logs.

Requirements

  • Keep consumer group membership stable during 120s downstream DB latency spikes without triggering rebalances.
  • Preserve at-least-once offset commit semantics only after durable persistence of every record in a partition.
  • Eliminate stop-the-world partition revocation across unaffected pods during scaling or rolling restarts.
  • Bound in-memory buffered records per pod under 50 MB to prevent OOMKills during backpressure.

Constraints

  • Downstream PostgreSQL p99 write latency can spike from 12 ms to 450 ms per batch during settlement windows.
  • Kafka broker cluster runs Apache Kafka 3.6 with 48 partitions per topic and 24 consumer pods.
  • Consumer pods have a 1 GiB JVM heap limit and 2 vCPU.
Known failure modes

Cascading LeaveGroup storms across all 24 pods.

Separate concerns. Map the flow.

Batch UPSERT

  1. 01Bounded Fetch: Poll thread fetches small batches and keeps max.poll.interval.ms timer reset every <5s.
  2. 02Partition Dispatch: Records routed to per-partition ordered worker queues to preserve key ordering.
  3. 03Backpressure Signal: Poll thread calls consumer.pause(tp) and poll(0) to maintain heartbeats without fetching.
  4. 04Idempotent Sink: Workers execute SQL batch UPSERT; on completion, record highest contiguous offset.
  5. 05Safe Commit & Resume: Poll thread commits completed offsets and calls consumer.resume(tp) when queue < 40%.
Decoupling poll() liveness from DB writes prevents GroupCoordinator eviction during 120s downstream stalls.

The invariants

  • Set max.poll.records=50 and enable-auto-commit=false.
  • Switch partition.assignment.strategy to CooperativeStickyAssignor with static group.instance.id.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Increasing max.poll.interval.ms delays dead-pod detection to 30 minutes, whereas pause() + CooperativeStickyAssignor preserves fast failure detection and incremental rebalances.

04 / ImplementConfiguration & code

Build the safeguards.

Implement ConsumerRebalanceListener.onPartitionsRevoked to await in-flight DB writes, commit completed offsets, and drop unstarted queued records.

1. Reference implementation

JAVA · Solution
if (queue.size() >= 160) consumer.pause(List.of(tp));
// worker completes batch -> completedOffsets.put(tp, nextOffset);
if (queue.size() <= 80 && consumer.paused().contains(tp)) consumer.resume(List.of(tp));

2. Harden for scale

Implement ConsumerRebalanceListener.onPartitionsRevoked to await in-flight DB writes, commit completed offsets, and drop unstarted queued records.

JAVA · Scale hardening
public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
    Map<TopicPartition, OffsetAndMetadata> toCommit = workers.drainAndCancel(partitions, Duration.ofSeconds(10));
    if (!toCommit.isEmpty()) consumer.commitSync(toCommit);
}

3. Operational controls

Step 1

Cancel queued unstarted tasks for revoked TopicPartitions.

Step 2

Await currently executing DB batch up to 10s and call commitSync() for those partitions.

Implementation note

Slightly higher code complexity for offset tracking vs zero rebalance storms.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Route non-retryable or 3x-failed records to a Dead Letter Queue (DLQ) with original partition/offset metadata so contiguous offset commits can advance.

  • ↗
    Classify exceptions into transient (SQLTransientException) vs permanent (DeserializationException, ConstraintViolation).
  • ↗
    Publish permanent failures to <topic>.dlq and mark offset complete.
JAVA · Verification
dlqProducer.send(new ProducerRecord<>(topic + ".dlq", record.key(), record.value())).get();
markOffsetCompleted(tp, record.offset() + 1);

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
