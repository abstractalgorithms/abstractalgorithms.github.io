01 / UnderstandFailure & constraints

Clarify what is failing.

The 24-hour `AWSALB` sticky cookie pinned 85% of returning authenticated users to Baseline, starving Canary of the exact cohort that exercises saved payment tokens.

Design objective

Trace how `AWSALB` cookies bypass weighted target-group selection on returning users.

Requirements

  • Ensure canary receives a representative 5% sample across both anonymous and authenticated/returning user cohorts
  • Eliminate sticky-session pinning across Baseline and Canary target groups
  • Enforce minimum sample size and cohort-stratified statistical significance gates before promotion
  • Catch authenticated-user regressions during canary before 100% rollout

Constraints

  • Cluster processes 4,000 RPS (85% returning authenticated users with long-lived sessions, 15% new visitors)
  • Evaluation window is 30 minutes per canary step
  • Zero user-visible session logouts allowed when shifting traffic between Baseline and Canary
Known failure modes

False-positive canary promotion leading to a 100% production outage

The invariants

  • Migrate session state to Redis/JWTs and set stickiness.enabled=false.
  • Route 5% per-request (or by hash(x-user-id)).
  • Add canary-auth-traffic-share and canary-auth-error-rate checks to AnalysisTemplate.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Use deterministic consistent hashing on `user_id` (or `session_id`) at the L7 proxy so 5% of *all* users map to Canary regardless of prior visits.

Step 1

Hash X-User-ID (e.g., MurmurHash(user_id) % 100 < 5).

Step 2

Unlike AWSALB cookies, this is stateless and newly applied on every release.

Step 3

Every cohort (new and returning) is split at an exact 5% ratio.

YAML · Lifecycle trace
http:
  - match:
      - headers:
          x-canary-cohort:
            exact: "true"
    route:
      - destination: { host: checkout, subset: canary }
Key trade-off

Requires an edge/API-gateway layer to compute the hash or inject x-canary-cohort before ALB/Istio

04 / ImplementConfiguration & code

Build the safeguards.

Add an explicit minimum-sample-size (`Inconclusive`) check in the `AnalysisTemplate` so promotion pauses until `N >= 5,000` requests.

1. Reference implementation

YAML · Solution
metrics:
  - name: canary-auth-traffic-share
    successCondition: result[0] >= 0.04 && result[0] <= 0.06
    query: |
      sum(rate(http_requests_total{version="canary",auth="true"}[5m])) /
      sum(rate(http_requests_total{auth="true"}[5m]))

2. Harden for scale

Add an explicit minimum-sample-size (`Inconclusive`) check in the `AnalysisTemplate` so promotion pauses until `N >= 5,000` requests.

YAML · Scale hardening
- name: min-canary-sample-size
  successCondition: result[0] >= 5000
  inconclusiveLimit: 10
  query: sum(increase(http_requests_total{version="canary",auth="true"}[30m]))

3. Operational controls

Step 1

Query `sum(increase(http_requests_total{version="canary",auth="true"}[30m]))`.

Step 2

Require `>= 5000` before `successCondition` can evaluate to true.

Step 3

If under 5,000, extend the canary window or require manual SRE sign-off.

Implementation note

Requires instrumenting `auth="true|false"` as a low-cardinality Prometheus label on HTTP metrics

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Use Envoy/Istio traffic shadowing (`mirror`) for read/idempotent endpoints, dropping mirrored responses while logging v2.8 exceptions and latency.

  • ↗
    Configure Envoy `request_mirror_policies` at 5–10% to `checkout-canary`.
  • ↗
    Tag mirrored requests with `X-Shadow-Request: true` so v2.8 skips payment-gateway charges and DB writes.
  • ↗
    Inspect v2.8 logs and metrics for `NullPointerException`s with zero user impact.
YAML · Verification
mirror:
  host: checkout-canary.prod.svc.cluster.local
mirrorPercentage:
  value: 10.0

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Dividing by zero or near-zero RPS in error-rate queries without `clamp_min(..., 1)`

Failure scenario 2

Forgetting to disable side effects (emails, Stripe charges) on shadowed requests causes duplicate charges

Alternatives considered

  • Replay sanitized production request logs in a staging environment against v2.8
