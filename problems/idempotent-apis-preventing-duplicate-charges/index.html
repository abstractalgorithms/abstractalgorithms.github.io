The idea to keep with you

Your `billing-service` (Java 21 + PostgreSQL 16 + Redis) processes 2,500 `POST /v1/charges` requests/sec. On flaky 4G mobile networks, a payment succeeds at the card processor (taking 2.1s), but the HTTP response drops before reaching the client. The mobile SDK and Envoy ingress automatically retry `POST /v1/charges` up to 3 times. Because `billing-service` has no idempotency-key enforcement, **0.4% of transactions (10/sec)** are double- or triple-charged, causing $180,000/day in chargebacks and support tickets. Design a strictly consistent, crash-safe idempotency layer that guarantees at-most-once charging even under concurrent identical retries, server crashes mid-flight, and payload-mismatch bugs.

STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why Idempotent Payment APIs Matter.

A billing-service (Java 21 + PostgreSQL 16 + Redis) processing 2,500 POST /v1/charges req/s sees mobile SDKs and Envoy auto-retry when a 2.1s card processor response drops on flaky 4G networks. Without idempotency enforcement, 0.4% of transactions (10/sec) are double- or triple-charged—costing $180,000/day in chargebacks.

Constraints:

  • PostgreSQL 16 handles OLTP ledger writes; Redis is not durable across failover.
  • External PSP (Stripe/Adyen) accepts our idempotency_key.
  • Zero TOCTOU race conditions (SELECT then INSERT without unique constraints is forbidden); retain ~216M keys/day for 24h at < 3 ms p99.
02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Real-World Impact of Non-Idempotent Retries.

Without atomic idempotency keys, retries cause three severe production failures:

  1. Duplicate Charges: Concurrent retries arriving 5 ms apart both pass a naive SELECT check and charge the card twice.
  2. Connection Pool Starvation: Holding a PostgreSQL transaction open during a 2.1s external PSP HTTP call exhausts HikariCP connections under load.
  3. Payload Reuse Bugs: Reusing the same Idempotency-Key with a different amount or currency silently returns a stale receipt instead of 422 Unprocessable Entity.
Atomic Idempotency Protocol

Two-Phase Claim & Finalize vs. Concurrent Retry

Claiming the unique key in a fast Tx1 before calling the PSP prevents concurrent duplicate charges without holding DB locks for 2.1s.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive Solution (and Why It Breaks).

Checking SELECT * FROM charges WHERE idempotency_key = $1 before calling Stripe suffers from a classic TOCTOU race: two retries arriving 5 ms apart both see 0 rows and both charge the card. Relying solely on Redis SETNX loses keys during failover, while holding a Postgres transaction open across the 2.1s PSP call exhausts the DB connection pool.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise Solution: Two-Phase DB Claim + SHA-256 Guard + Redis Fast Path.

Implement crash-safe atomic idempotency using PostgreSQL unique constraints and short transactions:

  • Tx 1 (Atomic Claim): INSERT INTO idempotency_keys (merchant_id, key, req_hash, status) VALUES (...) ON CONFLICT DO NOTHING. If inserted, proceed; if conflict, compare req_hash (422 on mismatch), return 409 Conflict (Retry-After: 1) if IN_PROGRESS, or replay the cached http_status + response_body if COMPLETED.
  • External PSP Call (No DB Lock Held): Forward idempotency_key to Stripe/Adyen so even a mid-flight pod crash cannot double-charge on recovery.
  • Tx 2 (Finalize) & Partitioned Retention: Update status to COMPLETED (or release key on guaranteed non-execution) and populate Redis as a read-through cache. Partition idempotency_keys by hour/day for instant DROP TABLE TTL cleanup of 216M keys/day.
Two-Phase Idempotency Storage

PostgreSQL Authoritative Claim + Partitioned Cache

1.Unique Constraint: Eliminates TOCTOU races without table-level locks.

2.Payload Hash: SHA-256 check returns 422 if key is reused with different body.

3.Crash Recovery: Stale IN_PROGRESS keys (>30s) re-query PSP using same key.

4.Partitioned TTL: Drop daily partitions instead of running expensive DELETEs.

PostgreSQL provides durable atomic locking via unique constraints while Redis accelerates <3 ms replay lookups.

STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Idempotent APIs Apply in System Design.

Idempotency keys are a core building block for reliable distributed mutations:

  • Payment Gateways & Fintech Ledgers: Prevents duplicate card captures and ledger postings across mobile retries.
  • Order & Inventory Reservation APIs: Ensures checkout retries return the same order_id instead of double-decrementing stock.
  • Webhook & Saga Orchestrators: Makes at-least-once message delivery behave as exactly-once state transitions.
