Designing Idempotent APIs to
Prevent Duplicate Billing.

Mobile SDKs and Envoy auto-retry timed-out POST /v1/charges requests, creating duplicate Stripe/card charges because the payment API lacks atomic idempotency enforcement.

01 / UnderstandFailure & constraints

Clarify what is failing.

Concurrent retries arriving milliseconds apart pass `SELECT` simultaneously (TOCTOU race), and holding a DB transaction open during the 2.1s PSP call exhausts the pool.

Design objective

Trace two retries arriving 5ms apart both seeing 0 rows on `SELECT`.

Requirements

  • Guarantee at-most-once external card processor charge per logical payment attempt, even with concurrent retries arriving 5 ms apart.
  • Return the exact original HTTP status and JSON body on retry, or `409 Conflict` / `422` if the same key is reused with a different request payload.
  • Handle mid-flight crashes cleanly (if `billing-service` crashes after calling the card processor or before committing).
  • Retain idempotency records for 24 hours (~216M keys/day) with < 3 ms p99 lookup overhead.

Constraints

  • PostgreSQL 16 primary handles OLTP ledger writes; Redis is available but not durable across failover.
  • External card processor (e.g., Stripe/Adyen) supports passing our `idempotency_key` on outbound calls.
  • Zero race conditions allowed (cannot rely on `SELECT` then `INSERT` without unique constraints).
Known failure modes

name: Connection Pool Exhaustion; description: HikariCP max=50 saturates in 20ms during PSP slowdowns.; mitigation: Release DB connection between Tx 1 (claim) and Tx 2 (finalize).

02 / Map the systemArchitecture & invariants

Separate concerns. Map the flow.

Claim `IN_PROGRESS` atomically in Tx 1, call PSP with the forwarded key, and persist `COMPLETED` + response JSON in Tx 2.

  1. 01Validate Key & Hash Body: API validates UUIDv4 header and computes SHA-256 of canonical request JSON.
  2. 02Atomic Claim (Tx 1, < 2ms): Acquires IN_PROGRESS row and releases DB connection immediately before external I/O.
  3. 03External PSP Call: No DB lock held during 2.1s PSP call; forwarding key protects against post-charge pod crashes.
  4. 04Commit Response (Tx 2, < 2ms): Persists exact HTTP status + JSON body in idempotency_keys and ledger tables.
  5. 05Deterministic Retry Replay: Subsequent retries match request_hash and return the exact cached 200/402 response; IN_PROGRESS returns 409.
Splitting DB claim (Tx 1) and DB completion (Tx 2) around the 2.1s PSP call prevents connection-pool exhaustion while guaranteeing at-most-once billing.

The invariants

  • Partition idempotency_keys hourly for O(1) 24h expiry.
  • Claim via INSERT ... ON CONFLICT DO NOTHING.
  • Compare SHA-256 request hash; return 422 on mismatch, 409 on IN_PROGRESS, cached JSON on COMPLETED.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Cache terminal business outcomes (`200`, `402`), but clear/mark `RETRYABLE` on transient `503`/network timeouts (after verifying the PSP didn't charge) so retries can succeed.

Step 1

Cache 200 OK and 402 Card Declined permanently for 24h.

Step 2

On 5xx or timeout, keep IN_PROGRESS until reaper verifies PSP state, or delete key if PSP returned a clean pre-auth 503.

JAVA · Lifecycle trace
if (pspResponse.isTerminal()) {
    repo.complete(key, pspResponse.status(), pspResponse.body());
} else if (pspResponse.isGuaranteedNotProcessed()) {
    repo.releaseKey(key);
}
Key trade-off

factor: Releasing Key on Transient 503; pro: Allows client's automatic retry to succeed.; con: Must only release if PSP explicitly guarantees non-processing (otherwise risk double charge).

04 / ImplementConfiguration & code

Build the safeguards.

Put a Redis read-through cache in front of PostgreSQL for `COMPLETED` keys so 50,000 duplicate replays never touch PostgreSQL.

1. Reference implementation

JAVA · Solution
ClaimResult claim = repo.claimKey(merchantId, key, sha256(body));
if (claim.isDuplicate()) {
    if (!Arrays.equals(claim.hash(), sha256(body))) throw new UnprocessableEntityException();
    if (claim.status() == IN_PROGRESS) throw new ConflictException("Retry-After: 1");
    return ResponseEntity.status(claim.httpStatus()).body(claim.responseBody());
}
// Execute PSP call with key, then Tx 2 finalize()

2. Harden for scale

Put a Redis read-through cache in front of PostgreSQL for `COMPLETED` keys so 50,000 duplicate replays never touch PostgreSQL.

PYTHON · Scale hardening
cached = redis.get(f"idem:{merchant}:{key}")

3. Operational controls

Step 1

Check Redis `GET idem:{merchant}:{key}` first; if `COMPLETED`, verify hash and return in < 0.5 ms.

Step 2

On Redis miss, fall through to authoritative PostgreSQL `INSERT ... ON CONFLICT`.

Implementation note

factor: Hourly Partitioning; pro: Drops 108 GB/day with < 10 KB WAL.; con: Requires checking current + previous hour partition if key spans an hour boundary.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Reject with `400 Bad Request`; generating a key server-side defeats idempotency because each retry would generate a brand-new key.

  • ↗
    Enforce `Idempotency-Key` presence at the API Gateway / controller filter.
  • ↗
    Return `400 Bad Request` with clear documentation link.
JAVA · Verification
if (idempotencyKey == null || !UUID_REGEX.matcher(idempotencyKey).matches()) {
    return ResponseEntity.badRequest().body("Missing or invalid Idempotency-Key");
}

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
