Load Balancing gRPC &
HTTP/2 Across Kubernetes Pods.

HTTP/2 multiplexes thousands of gRPC calls over a single persistent TCP connection, causing L4 load balancers to pin all traffic from a client to one backend pod even after horizontal autoscaling.

01 / UnderstandFailure & constraints

Clarify what is failing.

L4 load balancers only route on TCP connection establishment (SYN). Because HTTP/2 multiplexes all gRPC calls onto one long-lived TCP subchannel per VIP, existing clients never open new connections to hit the 20 new pods.

Design objective

Inspect active TCP connections (`ss -tnp | grep :9090`) on old vs. new pods.

Requirements

  • Distribute gRPC RPCs evenly (<10% skew) across all 24 backend pods within 30 seconds of HPA scale-out.
  • Prevent connection storms or TLS handshake spikes when cycling long-lived HTTP/2 connections.
  • Support both Java (grpc-netty) and Python (grpcio) clients without dropping in-flight RPCs.
  • Maintain sub-15 ms p99 latency during pod scale-up and rolling deployments.

Constraints

  • Peak aggregate throughput is 45,000 RPS across 120 client pods.
  • TLS 1.3 mTLS is mandatory on all service-to-service gRPC channels.
  • In-flight unary RPCs take up to 2 seconds and must complete gracefully before socket closure.
Known failure modes

Leaving default `pick_first` policy on headless DNS still pins all traffic to the first returned IP.

The invariants

  • Set defaultLoadBalancingPolicy("round_robin") on ManagedChannelBuilder.
  • Set maxConnectionAge to 180s with maxConnectionAgeGrace of 5s on NettyServerBuilder.
  • In Python, pass options=[('grpc.lb_policy_name', 'round_robin')] to grpc.aio.insecure_channel / secure_channel.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Lowering `MAX_CONNECTION_AGE` to 10s behind an L4 NLB still leaves each client with only 1 subchannel—meaning any single client's burst still hits 1 pod, and TLS 1.3 handshakes spike 18x.

Step 1

Compare per-client fan-out: 1 subchannel behind VIP vs. 24 subchannels with headless DNS.

Step 2

Calculate TLS 1.3 handshake rate: 2,880 / 10s = 288 handshakes/sec vs. 16 handshakes/sec.

Step 3

Verify that round_robin balances every single RPC across all 24 pods immediately.

04 / ImplementConfiguration & code

Build the safeguards.

At 200,000 sockets, full-mesh client-side LB wastes memory (~50 KB/socket = 10 GB) and causes epoll/TLS churn. Migrate to gRPC-xDS subsetting or an L7 Envoy gateway tier.

1. Reference implementation

JAVA · Solution
ManagedChannel channel = ManagedChannelBuilder
    .forTarget("dns:///payment-ledger-headless.prod.svc.cluster.local:9090")
    .defaultLoadBalancingPolicy("round_robin")
    .build();

Server server = NettyServerBuilder.forPort(9090)
    .maxConnectionAge(180, TimeUnit.SECONDS)
    .maxConnectionAgeGrace(5, TimeUnit.SECONDS)
    .addService(new LedgerServiceImpl())
    .build();

2. Harden for scale

At 200,000 sockets, full-mesh client-side LB wastes memory (~50 KB/socket = 10 GB) and causes epoll/TLS churn. Migrate to gRPC-xDS subsetting or an L7 Envoy gateway tier.

YAML · Scale hardening
# Envoy L7 upstream cluster with bounded connections
connect_timeout: 0.25s
type: STRICT_DNS
lb_policy: LEAST_REQUEST
typed_extension_protocol_options:
  envoy.extensions.upstreams.http.v3.HttpProtocolOptions:
    "@type": type.googleapis.com/envoy.extensions.upstreams.http.v3.HttpProtocolOptions
    explicit_http_config:
      http2_protocol_options:
        max_concurrent_streams: 250

3. Operational controls

Step 1

Cap per-client subchannels using xDS subset load balancing (e.g., 16–24 endpoints per client).

Step 2

Alternatively, route through a stateless Envoy L7 proxy tier of 20 pods (1,000×20 + 20×200 = 24,000 sockets).

Implementation note

180s maxConnectionAge adds ~16 TLS handshakes/sec cluster-wide (negligible CPU).

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Kubernetes removes the pod from Endpoints asynchronously while sending SIGTERM. Without a `preStop` hook and `GOAWAY` grace period, the pod closes sockets before kube-proxy/CoreDNS updates propagate.

  • ↗
    Add `lifecycle.preStop.exec` (`sleep 5`) so the pod stays alive while CoreDNS/EndpointSlices propagate.
  • ↗
    Call `server.shutdown()` and `awaitTermination(20, SECONDS)` on SIGTERM to emit HTTP/2 GOAWAY.
YAML · Verification
lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 5"]
terminationGracePeriodSeconds: 30

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Client-side `round_robin` eliminates single-client hot-spotting without proxy infrastructure.—
Option 2Requires internal DNS visibility to pod IPs (not possible across public internet).—
Option 3Topology-aware routing (same-AZ preference) to shrink cross-AZ connection meshes.—

Review questions

Failure scenario 1

Without subsetting, 1,000 clients × 200 servers exhausts conntrack tables and ephemeral ports.

Failure scenario 2

Killing the process before `sleep 5` drops streams still in flight from clients with cached DNS.

Alternatives considered

  • Enable client-side gRPC `retryPolicy` for idempotent unary reads on `UNAVAILABLE`.
