STAGE 02 · IMPACTL5 · APPLIED DESIGN

Real-World Impact of Cyclic AB-BA Locking.

Why this matters: The problem: see what breaks without Real-World Impact of Cyclic AB-BA Locking under real concurrency or scale.

When two threads acquire locks in opposite orders:

  1. Permanent Thread Freeze: synchronized monitors have no timeout or deadlock detector—blocked threads stay hung until JVM restart.
  2. Worker Pool Exhaustion: As other threads touch either A or B, they pile up behind the deadlocked pair, halting all 25,000 TPS.
  3. Hash-Collision Trap: Ordering by System.identityHashCode() alone can still deadlock on rare 32-bit hash collisions.
Cyclic AB-BA Deadlock vs. Total Lock Ordering

Cyclic Monitor Freeze vs. Canonical ID Lock Ordering

Enforcing a strict total order (min accountId -> max accountId) makes lock-wait graphs acyclic by construction.

STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise Solution: Canonical `accountId` Ordering + Tie-Breaker / `tryLock`.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Guarantee deadlock freedom while scaling across 10M accounts:

  • Strict Total Order by Immutable accountId: Guard if (from.id == to.id) return; then always lock first = from.id < to.id ? from : to before second. Because A < B globally, no cycle can ever form.
  • Hash-Code Tie-Breaker (if no unique ID): If ordering by System.identityHashCode, acquire a global TIE_LOCK only on the 1-in-2322^{32}232 hash collision.
  • Timed tryLock + Jitter / DB Alignment: For ReentrantLocks or multi-row SQL (SELECT ... FROM accounts WHERE id IN ($1, $2) ORDER BY id FOR UPDATE), consistent ascending ID order prevents both JVM and PostgreSQL deadlocks.
Acyclic Lock Acquisition

Canonical Ordering Eliminates Cycles

Every thread traverses account locks in strictly increasing ID order, guaranteeing a DAG with zero deadlocks.

import java.util.*;
import java.util.concurrent.locks.ReentrantLock;

public class LedgerService {
    public static final class Account {
        private final long id;
        private long balance;
        private final ReentrantLock lock = new ReentrantLock();
        public Account(long id, long balance) { this.id = id; this.balance = balance; }
        public long id() { return id; }
    }

    public void transfer(Account from, Account to, long amount) {
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        if (from.id() == to.id()) return;

        Account first = from.id() < to.id() ? from : to;
        Account second = from.id() < to.id() ? to : from;

        first.lock.lock();
        try {
            second.lock.lock();
            try {
                if (from.balance < amount) throw new IllegalStateException("Insufficient funds");
                from.balance -= amount;
                to.balance += amount;
            } finally {
                second.lock.unlock();
            }
        } finally {
            first.lock.unlock();
        }
    }

    public void batchTransfer(Map<Account, Long> deltas) {
        List<Account> ordered = deltas.keySet().stream()
                .sorted(Comparator.comparingLong(Account::id))
                .distinct()
                .toList();
        List<Account> acquired = new ArrayList<>(ordered.size());
        try {
            for (Account acc : ordered) {
                acc.lock.lock();
                acquired.add(acc);
            }
            for (var entry : deltas.entrySet()) {
                if (entry.getKey().balance + entry.getValue() < 0) {
                    throw new IllegalStateException("Insufficient funds: " + entry.getKey().id());
                }
            }
            deltas.forEach((acc, delta) -> acc.balance += delta);
        } finally {
            for (int i = acquired.size() - 1; i >= 0; i--) {
                acquired.get(i).lock.unlock();
            }
        }
    }
}

Where Lock Ordering Applies in System Design.

Why this matters: Scope boundary: identify where this pattern fits best and where simpler or async alternatives win.

Canonical lock ordering is a universal primitive for multi-resource atomicity:

  • Payment & Double-Entry Ledgers: Atomic debit(from) + credit(to) in both JVM memory and SQL ORDER BY id FOR UPDATE.
  • Distributed Lock Managers: Sorting Redis/etcd lock keys lexicographically before multi-key acquisition.
  • Graph & Inventory Engines: Locking multiple SKUs in sorted sku_id order during cart checkout.
