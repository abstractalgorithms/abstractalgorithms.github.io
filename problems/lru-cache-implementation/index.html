Implement an LRU Cache

Design a data structure that follows the constraints of a Least Recently Used (LRU) cache. Implement get(key) and put(key, value) operations in O(1) average time complexity. When the cache reaches its capacity, it should invalidate and evict the least recently used key before inserting a new item.

Scope, Requirements & Constraints

Hash map provides O(1) key lookup, but doesn't track ordering. Array tracks order, but eviction/shifting is O(N). Doubly linked list allows O(1) node deletion and insertion when a pointer is held. Combining a Hash Map with a Doubly Linked List achieves O(1) for both get and put.

Core Functional Requirements

  • ✓Initialize LRUCache with positive capacity.
  • ✓int get(int key) returns the value of the key if it exists, otherwise -1.
  • ✓void put(int key, int value) updates the value of the key if it exists. Otherwise, add the key-value pair to the cache. If keys exceed capacity, evict least recently used key.
  • ✓Both get and put operations must run in O(1) average time complexity.

Scale & Latency Constraints

  • —1 <= capacity <= 3000
  • —0 <= key <= 10^4
  • —0 <= value <= 10^5
  • —At most 2 * 10^5 calls will be made to get and put.

Reference Architecture & System Blueprint

Use a Hash Map mapping key -> Node, and a doubly linked list with dummy head and tail nodes. Most recently used nodes are placed near head, least recently used are evicted from near tail.

System Architecture & Theory

Architectural Overview & Separation of Concerns

An LRU (Least Recently Used) Cache requires both $O(1)$ key lookup and $O(1)$ item reordering/eviction upon capacity overflow. A Hash Map alone provides $O(1)$ search but cannot track temporal usage without an $O(N)$ scan. An array tracks order but requires $O(N)$ shifts on mid-array deletions. Combining a Hash Map with a Doubly Linked List achieves strict $O(1)$ for both `get` and `put` operations.

Data Model & Storage Internals
1. Doubly Linked List Nodes: Each node contains `{ key, value, prev, next }`. Storing the `key` within the node is critical because when an eviction occurs at the tail, the cache must delete the corresponding entry from the Hash Map in $O(1)$ without searching. 2. Sentinel Boundary Nodes: A pseudo dummy `head` (MRU) and dummy `tail` (LRU) node permanently anchor list boundaries. Sentinels eliminate all null-pointer edge cases during insertion and deletion.
Scale Bottlenecks, Operational Hazards & Failure Modes
1. Thread Safety in Multithreaded Environments: In Java or Go, concurrent reads and writes require lock striping or Read-Write locks (`sync.RWMutex`). Notice that even a `get()` operation modifies pointers by promoting the accessed node to the MRU position, converting reads into write operations on the linked list unless using a lock-free or read-buffered LRU variant. 2. Memory Overhead: Each node stores two 64-bit pointers (`prev`, `next`) plus key/value object overhead, approximately doubling the raw payload memory consumption.
⚡ Architectural Invariant

Sentinel dummy head and tail nodes eliminate tedious boundary conditions, enabling clean, error-free O(1) memory updates.

Hardened Implementation Steps

  1. 1Node contains key, value, prev, next pointers.
  2. 2Dummy head and tail nodes avoid special cases for empty list and single-item updates.
  3. 3get(key): if key in map, find node, removeNode(node), addNodeToHead(node), return node.val; else return -1.
  4. 4put(key, val): if key exists, update val, move to head. If new, create node, add to head, insert into map. If size > capacity, remove tail.prev node, delete from map.

Key Decisions & Trade-Off Analysis

Trade-offs in LRU Cache design.

Architectural Decisions & Trade-Offs

  • ⚖Storing key in Node: enables O(1) removal from the hash map when evicting tail.prev node (map.delete(tailNode.key)). Without key in Node, deleting from hash map would require an O(N) search through the map.
  • ⚖Dummy Head & Tail: eliminates edge checks for head === null or tail === null in add and remove methods, drastically reducing bug surface.

Scale Bottlenecks & Operational Hazards

Operational Hazards & Mitigations

  • ⚠Concurrent access race conditions: Multiple threads mutating doubly-linked list pointers cause cyclic references and pointer corruption.
  • ⚠Coarse-grained lock (ReentrantLock / Mutex): thread-safe, but serializes all reads and writes, creating CPU bottleneck under high concurrent read traffic.
  • ⚠Read-write lock: allows concurrent reads, but in LRU every read (get) mutates the list to promote the accessed node, turning every read into a write lock! Solution: Read-Write lock with buffered access queues (like Caffeine Cache) or Clock/Second-Chance approximation.

Changed Constraints & System Extension

Follow-up: How would you implement Time-To-Live (TTL) expiration alongside LRU eviction? Does expired item cleanup run on get, or in a background cleaner?

Extension Implementation Steps

  1. 1Add expiresAt timestamp to each Node.
  2. 2Passive expiration: on get(key), check if now > node.expiresAt. If expired, evict immediately and return -1.
  3. 3Active expiration: periodic background task samples keys or inspects a min-heap ordered by expiresAt to reclaim memory proactively.

Follow-Up Trade-Offs

  • ⚖Passive only: low overhead, but dead keys that are never read again waste memory until LRU capacity eviction forces them out.
  • ⚖Active with Min-Heap: proactive memory reclamation, but adding/updating keys requires O(log N) heap adjustments instead of strict O(1).
