01 / UnderstandFailure & constraints

Clarify what is failing.

The Linux kernel cgroup OOM killer enforces memory.max against the entire process RSS (Heap + Metaspace + DirectByteBuffers + Thread Stacks + Native arenas + Page Cache), not just -Xmx.

Design objective

Check kubectl describe pod for Reason: OOMKilled and Exit Code: 137.

Requirements

  • Account for every non-heap memory consumer (Metaspace, DirectByteBuffers, Netty PooledByteBufAllocator, thread stacks, CodeCache, and glibc malloc arenas) inside a deterministic container memory budget.
  • Eliminate silent kernel SIGKILL (137) events by bounding off-heap allocations so the JVM fails fast or applies backpressure before hitting cgroup memory.max.
  • Expose off-heap and cgroup RSS telemetry to Prometheus so alerts fire at 85% cgroup saturation.
  • Ensure Guaranteed QoS (requests.memory == limits.memory) so kubelet never evicts the service due to node-level memory contention.

Constraints

  • Service runs Java 21 on Linux cgroup v2 containers with Netty 4.1+ / gRPC.
  • Total container memory limit cannot exceed 8 GiB per pod due to node bin-packing constraints (32 GiB worker nodes).
  • Pods must handle 400 concurrent Netty/worker threads and 64 KB request/response payloads at 12,000 RPS.
Known failure modes

Waiting for a JVM OutOfMemoryError log fails because kernel SIGKILL terminates the process immediately.

  1. 01Off-heap buffer allocation: Netty allocates pooled direct memory capped at -XX:MaxDirectMemorySize=1024m.
  2. 02Bounded JVM regions: Heap, Metaspace, CodeCache, and 512k thread stacks remain within 4.55 GiB combined.
  3. 03Arena-capped native RSS: MALLOC_ARENA_MAX=2 prevents glibc from hoarding 64 MiB per-thread arenas.
  4. 04Headroom verification: Total working set stays around 6.1 GiB, leaving >2 GiB safety margin below memory.max.
  5. 05Graceful backpressure: If direct memory spikes, Netty hits OutOfDirectMemoryError cleanly instead of silent kernel SIGKILL.
Explicitly bounding every JVM and native memory region keeps total cgroup working set safely under memory.max.

The invariants

  • Set requests.memory == limits.memory == 8192Mi.
  • Explicitly bound -Xmx, -XX:MaxDirectMemorySize, -XX:MaxMetaspaceSize, and -Xss.
  • Set MALLOC_ARENA_MAX=2 and Netty maxOrder=9.
03 / Trace the lifecycleKey decisions

Follow the execution path.

MaxRAMPercentage only scales the JVM heap and leaves MaxDirectMemorySize equal to heap, which routinely blows past container limits in Netty/gRPC services.

Step 1

Calculate worst-case native + off-heap footprint independently of heap.

Step 2

Subtract off-heap + 20% headroom from limits.memory to derive -Xmx.

JAVA · Lifecycle trace
// Verify effective runtime limits at startup
long maxHeapMiB = Runtime.getRuntime().maxMemory() / (1024 * 1024);
System.out.println("Configured Max Heap MiB: " + maxHeapMiB);
Key trade-off

Explicit flags must be updated if container limits change, whereas MaxRAMPercentage auto-scales but is unsafe for off-heap-heavy apps.

04 / ImplementConfiguration & code

Build the safeguards.

Apply gRPC/Netty concurrency limits and AUTO_READ=false backpressure so excess requests receive 429/RESOURCE_EXHAUSTED rather than allocating unbounded direct buffers.

1. Reference implementation

YAML · Solution
resources:
  requests:
    memory: "8192Mi"
    cpu: "2000m"
  limits:
    memory: "8192Mi"
env:
  - name: MALLOC_ARENA_MAX
    value: "2"
  - name: JAVA_TOOL_OPTIONS
    value: >- 
      -Xms3584m -Xmx3584m -XX:MaxMetaspaceSize=512m
      -XX:MaxDirectMemorySize=1024m -Xss512k
      -XX:ReservedCodeCacheSize=256m -XX:NativeMemoryTracking=summary
      -Dio.netty.allocator.maxOrder=9 -XX:+ExitOnOutOfMemoryError

2. Harden for scale

Apply gRPC/Netty concurrency limits and AUTO_READ=false backpressure so excess requests receive 429/RESOURCE_EXHAUSTED rather than allocating unbounded direct buffers.

JAVA · Scale hardening
ServerBootstrap b = new ServerBootstrap();
b.childOption(ChannelOption.WRITE_BUFFER_WATER_MARK,
    new WriteBufferWaterMark(32 * 1024, 64 * 1024));

3. Operational controls

Step 1

Configure Netty ChannelOption.WRITE_BUFFER_WATER_MARK (low=32KB, high=64KB).

Step 2

Reject incoming requests with gRPC RESOURCE_EXHAUSTED when in-flight memory crosses 80% of MaxDirectMemorySize.

Implementation note

Using 3584m heap inside an 8 GiB pod leaves 4.5 GiB for off-heap and native safety, trading slightly higher GC frequency for zero OOM kills.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Explicit flags must be updated if container limits change, whereas MaxRAMPercentage auto-scales but is unsafe for off-heap-heavy apps.—
Option 2Configure Netty unpooled heap buffers (-Dio.netty.noPreferDirect=true) at the cost of extra memory copies and GC pressure.—

Review questions

Failure scenario 1

Slow-reading clients cause outbound write queues to accumulate direct buffers unless WriteBufferWaterMark is enforced.

Failure scenario 2

Alerting only on raw working_set > 85% misses slow leaks until minutes before an outage.

Alternatives considered

  • Run periodic jcmd VM.native_memory summary.diff via an automated diagnostic sidecar.
