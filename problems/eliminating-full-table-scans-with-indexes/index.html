01 / UnderstandFailure & constraints

Clarify what is failing.

With no index leading on `merchant_id`, PostgreSQL falls back to either a 240 GB Sequential Scan or a Backward Index Scan on `(created_at)` that discards 99.8% of rows via random heap fetches.

Design objective

Run `EXPLAIN (ANALYZE, BUFFERS)` on the exact parameterized query to observe `shared hit` vs `shared read` blocks.

Requirements

  • Eliminate full sequential and backward index scans on `orders_ledger` for the settlement query, keeping p99 query latency under 10 ms at 2,400 QPS.
  • Deploy the index remediation in production with zero `ACCESS EXCLUSIVE` table-write blocking.
  • Prevent runaway un-indexed queries from exhausting the 500-connection HikariCP pool and starving unrelated health-check or checkout transactions.
  • Establish automated query-plan regression detection in CI/CD and production observability before queries hit peak traffic.

Constraints

  • PostgreSQL 16 primary (16 vCPU, 64 GB RAM, 32 GB `shared_buffers`, 16,000 provisioned NVMe IOPS) with 180M rows (240 GB heap) and ~1,200 writes/sec.
  • Only ~3.2% of rows (`~5.7M` rows) have `status = 'PENDING_SETTLEMENT'` at any time; 96.8% are historical `SETTLED` or `CANCELLED` rows.
  • Zero-downtime deployment: `CREATE INDEX` without `CONCURRENTLY` is prohibited because it blocks concurrent `INSERT`/`UPDATE` statements.
Known failure modes

Running `EXPLAIN ANALYZE` on a hot-cached staging DB with 100k rows masks the 240 GB disk thrashing seen in production.

02 / Map the systemArchitecture & invariants

Separate concerns. Map the flow.

A partial covering index `(merchant_id, created_at DESC) INCLUDE (amount_cents, currency) WHERE status = 'PENDING_SETTLEMENT'` shrinks the index to 228 MB, enabling sub-millisecond Index-Only Scans in RAM.

Replacing a 240 GB sequential/backward scan with a 228 MB partial covering index keeps 99%+ of reads in shared_buffers.

The invariants

  • Set lock_timeout = '200ms' and maintenance_work_mem = '2GB' in the migration session.
  • Execute CREATE INDEX CONCURRENTLY so INSERT/UPDATE traffic continues uninterrupted.
  • Tune autovacuum_vacuum_scale_factor = 0.02 so Visibility Map bits stay clean for Index-Only Scans.
  • Enforce statement_timeout = 1500ms in HikariCP/PostgreSQL role settings and route through PgBouncer.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Equality columns (`merchant_id`) must precede sort/range columns (`created_at DESC`) so PostgreSQL can seek directly to the merchant's newest 50 rows without an explicit `Sort` node.

Step 1

Place equality predicates first (merchant_id), followed by ORDER BY columns (created_at DESC).

Step 2

Move status = 'PENDING_SETTLEMENT' into the WHERE partial-index predicate to eliminate 96.8% of rows.

Step 3

Place non-filtered projection columns (amount_cents, currency) in INCLUDE so they do not bloat internal B-Tree branch pages.

SQL · Lifecycle trace
-- Optimal: 228 MB, Index-Only Scan, 0 Sort nodes
CREATE INDEX CONCURRENTLY idx_orders_pending_merchant_created
ON orders_ledger (merchant_id, created_at DESC)
INCLUDE (amount_cents, currency)
WHERE status = 'PENDING_SETTLEMENT';
Key trade-off

Adding INCLUDE columns increases leaf page size slightly (~16 bytes/row) but eliminates random 8 KB heap page fetches.

04 / ImplementConfiguration & code

Build the safeguards.

Heavy `UPDATE` churn clears Visibility Map bits, degrading Index-Only Scans into Index Scans with random heap fetches, while failed concurrent index builds leave write-amplifying `INVALID` indexes.

1. Reference implementation

JAVA · Solution
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:postgresql://pgbouncer.prod.internal:6432/payments");
config.setMaximumPoolSize(40);
config.setConnectionTimeout(1000);
config.addDataSourceProperty("options", "-c statement_timeout=1500 -c lock_timeout=200");
config.addDataSourceProperty("prepareThreshold", "3");

2. Harden for scale

Heavy `UPDATE` churn clears Visibility Map bits, degrading Index-Only Scans into Index Scans with random heap fetches, while failed concurrent index builds leave write-amplifying `INVALID` indexes.

YAML · Scale hardening
groups:
  - name: postgres-query-regression
    rules:
      - alert: PostgresHighDiskReadsPerQuery
        expr: rate(pg_stat_statements_shared_blks_read_total[1m]) / rate(pg_stat_statements_calls_total[1m]) > 500
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Query reading >500 blocks/call from disk; check missing index or VM bloat."

3. Operational controls

Step 1

Monitor `pg_stat_user_tables.n_dead_tup` and `Heap Fetches` in `EXPLAIN ANALYZE`.

Step 2

Increase `autovacuum_vacuum_cost_limit` on `orders_ledger` so vacuum keeps up with status transitions.

Step 3

Alert on `pg_index.indisvalid = false` and `pg_stat_statements` `shared_blks_read` spikes.

Implementation note

Partial index only accelerates `PENDING_SETTLEMENT` queries; queries for `SETTLED` orders must be routed to a read replica or given a separate index.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Combine CI-level query plan assertions against production-like `pg_statistic` snapshots with runtime `pg_stat_statements` regression alerts and `hypopg` index verification.

  • ↗
    Export anonymized `pg_statistic` / table row counts to CI or use `hypopg` to validate query plans.
  • ↗
    Fail CI if any new SQL query triggers a `Seq Scan` or exceeds a `total_cost` threshold on tables >1M rows.
  • ↗
    Configure `auto_explain.log_min_duration = '200ms'` with `auto_explain.log_buffers = on` in staging and canary.
PYTHON · Verification
import psycopg

def assert_no_seq_scan(conn, sql, params):
    plan = conn.execute(f"EXPLAIN (FORMAT JSON) {sql}", params).fetchone()[0][0]["Plan"]
    def walk(node):
        if node.get("Node Type") == "Seq Scan" and node.get("Relation Name") == "orders_ledger":
            raise AssertionError("Forbidden Seq Scan on orders_ledger")
        for child in node.get("Plans", []):
            walk(child)
    walk(plan)

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Adding `INCLUDE` columns increases leaf page size slightly (~16 bytes/row) but eliminates random 8 KB heap page fetches.—
Option 2Offload historical `SETTLED` order queries to a dedicated PostgreSQL read replica with a separate `statement_timeout`.—

Review questions

Failure scenario 1

Leaving `maximumPoolSize` at 500 during a disk regression starves CPU and locks up the DB even faster.

Failure scenario 2

Testing against an empty or 1,000-row CI database causes PostgreSQL to legitimately choose `Seq Scan`, creating false positives.

Alternatives considered

  • Use `pg_stat_statements` diffing in canary deployments to block rollout if `shared_blks_read` per call increases >2x.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Align B-Tree composite key order (equality columns first, range/sort columns second) with partial/covering clauses, enforce statement_timeout, and gate query plans in CI.
  • 02Trade-off tip: Adding INCLUDE columns increases leaf page size slightly (~16 bytes/row) but eliminates random 8 KB heap page fetches.
  • 03Watch out for: Leaving maximumPoolSize at 500 during a disk regression starves CPU and locks up the DB even faster.
