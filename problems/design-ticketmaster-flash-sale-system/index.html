The idea to keep with you

Design a high-concurrency event ticketing platform like Ticketmaster or BookMyShow. The system must handle sudden 1,000,000-user traffic surges attempting to purchase 50,000 seats at the exact same second. It must guarantee strict transactional consistency (zero double-booking), handle user cart abandonment, and prevent database deadlocks.

From patterns to decisions.

STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why flash-sale ticketing breaks standard e-commerce architectures.

When 1,000,000 fans hit refresh at the exact same second for 50,000 concert seats, read-to-write ratios and hot-row contention spike by 1,000×. Seat map browsing must stay < 100 ms and reservation holds < 500 ms, while guaranteeing strict ACID zero double-booking and automatic release of abandoned 5-minute carts.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens without edge admission control and read caching.

Sending 1M concurrent users directly to the booking database causes an immediate thundering-herd outage:

  1. Connection Pool & Lock Exhaustion: Thousands of concurrent SELECT ... FOR UPDATE queries on the same show_id exhaust DB connections and stall all transactions.
  2. Seat Map Read Storm: Repeatedly querying Postgres for available seats saturates read IOPS before anyone even checks out.
  3. Ghost Inventory: Abandoned carts lock seats indefinitely if TTL expiry is not automated.
Admission & Reservation Flow

Virtual Waiting Room -> Cached Seat Map -> Atomic 5-Min Hold

Edge queuing caps concurrency reaching the database while atomic conditional UPDATEs guarantee zero double-booking.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive solution (and why DB-only locking without a waiting room fails).

A naive design puts all 1M users directly onto the booking API backed by Postgres SELECT FOR UPDATE:

  • Thundering Herd Collapse: Even though only 50k seats exist, 950k doomed requests saturate CPU and HikariCP pools.
  • Lock Wait Cascades: Unbounded FOR UPDATE without NOWAIT / SKIP LOCKED piles up blocked worker threads.
  • No Read/Write Split: Seat-map polling competes with payment commits on the primary DB.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Virtual Waiting Room + Conditional ACID Hold + TTL Sweeper.

Production flash-sale platforms layer four defenses:

  • Virtual Waiting Room (Edge): Queue 1M users in a FIFO/shuffled Redis or Cloudflare Durable Object queue, issuing signed admission JWTs at a rate the DB can sustain (e.g., 5,000 users/sec).
  • Read/Write Separation: Serve static venue SVG + live seat availability from CDN + Redis (updated via CDC/outbox) in < 100 ms.
  • Atomic Conditional Hold: Reserve seats in sharded Postgres (shard_key = event_id) using UPDATE seats SET status='HELD', hold_until=now()+interval '5 min' WHERE seat_id = ANY($1) AND status='AVAILABLE' (sorted IDs, NOWAIT).
  • Automated Expiry: A background sweeper + Redis keyspace/delay queue releases unpaid holds after 5 minutes.
Read/Write Isolation

Edge Queue + Redis Seat Map + Sharded ACID Inventory

1.Waiting Room: Absorbs 1M spike at edge and drips signed admission tokens.

2.Seat Map Cache: Offloads 99% of browsing reads from the primary RDBMS.

3.Conditional UPDATE: Atomic WHERE status='AVAILABLE' prevents double-booking.

4.5-Min TTL Sweeper: Reclaims abandoned holds back to AVAILABLE automatically.

Metering admission at the edge and serving seat maps from Redis lets the sharded RDBMS focus solely on atomic 5-minute holds.

-- Atomic, deadlock-free 5-minute seat hold (seat_ids passed sorted)
UPDATE show_seats
SET status = 'HELD',
    held_by_user_id = $1,
    hold_token = $2,
    hold_expires_at = NOW() + INTERVAL '5 minutes'
WHERE show_id = $3
  AND seat_id = ANY($4::bigint[])
  AND (status = 'AVAILABLE' OR (status = 'HELD' AND hold_expires_at < NOW()))
RETURNING seat_id;
-- Application verifies returned row count == cardinality($4); otherwise ROLLBACK.
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Flash-Sale Reservation Patterns apply in System Design.

The edge-queue + conditional-lease architecture generalizes to any scarce-inventory spike:

  • Sneaker Drops & E-Commerce Flash Sales: Metering checkout queues while decrementing bounded SKU inventory.
  • Airline & Train Seat Maps: Serving high-read seat maps from cache while locking PNR inventory atomically.
  • Concert & Sports Ticketing: Isolating hot event_id shards from unrelated venue traffic.
