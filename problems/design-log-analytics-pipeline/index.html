01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why 50 TB/day log pipelines break on storage amplification and bursts.

Across 4,000 Kubernetes nodes generating 600,000 JSON events/sec (576 MB/s = 49.8 TB/day), traditional inverted-index stacks inflate 50 TB/day into 90+ TB/day—exceeding an 80 TB 7-day hot SSD budget by 7x. Worse, an outage triggers a 4x (2.5M/sec) log storm right when engineers need trace_id lookups in < 5 seconds.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Mapping explosions, log storms, and ClickHouse `Too many parts`.

Three failure modes hit production log platforms:

  1. Dynamic JSON Key Explosion: Logging UUIDs as top-level JSON keys creates 500K+ columns/mappings, crashing metadata coordinators.
  2. Incident Feedback Loops: 2,000 pods logging stack traces saturate brokers and drop root-cause ERROR logs.
  3. Small-Insert Part Overload: Unbatched inserts into ClickHouse trigger Too many parts (300) rejections.
Burst-Decoupled Log Pipeline

Fluent Bit -> Kafka (zstd) -> Flink Schema Guard -> ClickHouse + S3

5:1 Kafka zstd compression and 8:1 ClickHouse columnar compression fit 7 hot days into ~65 TB inside the 80 TB cap.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive direct-to-Elasticsearch shipping and schemaless indexing.

Shipping directly from Fluent Bit to Elasticsearch couples 2.5M/sec incident bursts to storage, drops logs when indexers stall, and allows dynamic JSON mapping to explode cluster state.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Priority Fluent Bit + Kafka + ClickHouse MergeTree + S3.

Meet < 5 s freshness, <= 80 TB hot SSD, and 365-day retention:

  • Node Agent (Fluent Bit in C): Stays under 150 MB RAM / 2% CPU with a 2 GB filesystem ring buffer, priority shedding (drop DEBUG/INFO first during storms, preserve ERROR/FATAL), and zstd batching.
  • Kafka Buffer: 24 h retention at 5:1 zstd (~20 TB at RF=2 across 18 brokers), with per-tenant quotas.
  • ClickHouse Hot Tier (7 days): Promote 15-20 typed columns (LowCardinality(String) for service/env/level) and pack arbitrary keys into a bounded Map(String, String) (preventing schema explosion). ORDER BY (tenant_id, service, timestamp) with tokenbf_v1 bloom filters on message/trace_id and ZSTD(3) (~8:1 compression) fits 7 days at RF=2 in ~65 TB.
  • Cold Tier: ClickHouse TTL offloads >7d partitions to S3 Parquet for 365-day compliance.
ClickHouse MergeTree Layout

Primary Sparse Index (tenant, service, ts) + tokenbf_v1 Bloom Filter

Sparse primary indexes and tokenbf_v1 bloom filters deliver <1.5 s p95 trace_id lookups without full inverted-index bloat.

CREATE TABLE logs_hot (
    tenant_id LowCardinality(String),
    service   LowCardinality(String),
    level     LowCardinality(String),
    ts        DateTime64(3),
    trace_id  String,
    message   String,
    attrs     Map(String, String), -- Capped dynamic keys
    INDEX idx_trace trace_id TYPE tokenbf_v1(32768, 3, 0) GRANULARITY 4,
    INDEX idx_msg   message  TYPE tokenbf_v1(65536, 3, 0) GRANULARITY 4
) ENGINE = MergeTree()
PARTITION BY toYYYYMMDD(ts)
ORDER BY (tenant_id, service, ts)
TTL toDateTime(ts) + INTERVAL 7 DAY TO VOLUME 's3_cold';
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where ClickHouse + Kafka log pipelines are used.

Columnar analytical stores have largely replaced full-text clusters for high-volume observability:

  • Cloudflare, Uber & Datadog-Scale Telemetry: Pair Kafka buffering with ClickHouse MergeTree + S3 cold tiering to cut SSD costs 5x-8x.
  • Security & Audit SIEMs: Retain 365 days of Parquet in S3 queried via Trino/ClickHouse external tables.
