STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why spot-indexing and gate concurrency matter in Parking Lot LLD.

A multi-floor smart parking garage with multiple entry/exit gates must assign the nearest available compatible spot (Compact, Large/SUV, EV) in O(log N) or O(1) time without two entry gates ever issuing tickets for the same spot simultaneously.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens with linear scans and coarse global locks.

Scanning all spots linearly or locking the entire ParkingLot creates two bottlenecks:

  1. Double-Assigned Spots: Gate A and Gate B both read spot F2-14 as free and issue two tickets for it.
  2. Gate Contention: A single global lock on ParkingLot blocks Gate B on Floor 5 while Gate A is processing a ticket on Floor 1.
Concurrent Gate Allocation

Multi-Gate Entry Race Prevention with Per-Floor Min-Heap & Lock

Per-floor locks serialize spot pops within a floor in O(log N) while allowing different floors to allocate in parallel.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive solution (and why if-else pricing + ArrayList scans fail).

A basic implementation iterates over a List<ParkingSpot> and hardcodes if (vehicle == EV) fee math inside ExitGate:

  • O(N) Allocation: Scanning thousands of spots per entry degrades under rush-hour bursts.
  • Open/Closed Violation: Adding weekend surge or EV kWh billing requires editing ExitGate and ParkingLot.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Per-Floor Min-Heaps + FeeStrategy + Ticket State.

Production LLD structures the domain cleanly:

  • O(log N) Nearest-Spot Heap: Each ParkingFloor maintains a min-heap (heapq / PriorityQueue) per SpotType ordered by distance to the elevator/gate, guarded by a per-floor Lock.
  • Strategy Pattern for Pricing: ExitGate delegates fee calculation to a FeeStrategy (HourlyStrategy, EvChargingStrategy) injected at runtime.
  • Atomic Release on Exit: Paying the ticket marks it PAID and pushes the spot back into its floor's min-heap.
O(log N) Spot Indexing

Per-Floor Min-Heap by SpotType & Distance

1.Min-Heap Pop: Returns the closest available spot in O(log N) time.

2.Per-Floor Lock: Prevents two gates from popping the same spot concurrently.

3.FeeStrategy: Swaps hourly, flat-rate, or EV pricing without touching Gate classes.

4.Ticket Lifecycle: Tracks ACTIVE -> PAID to prevent duplicate exit releases.

Partitioning min-heaps by floor and spot type keeps allocation O(log N) and isolates lock contention.

class ParkingFloor:
    def __init__(self, floor_id: int):
        self._lock = threading.Lock()
        self._free_spots = {SpotType.COMPACT: [], SpotType.LARGE: []}
    def park(self, vehicle_type: SpotType) -> Optional[Spot]:
        with self._lock:
            return heapq.heappop(self._free_spots[vehicle_type]) if self._free_spots[vehicle_type] else None

public Optional<ParkingSpot> allocateSpot(SpotType type) {
    floorLock.lock();
    try {
        PriorityQueue<ParkingSpot> q = freeByType.get(type);
        return Optional.ofNullable(q.poll());

STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Heap Allocation & Strategy Patterns apply in System Design.

The same indexed resource-pool + Strategy architecture appears across real systems:

  • Cloud VM / Container Schedulers: Maintaining priority queues of available compute slots per availability zone.
  • EV Charging & Locker Networks: Thread-safe bay reservation with pluggable tariff strategies.
  • Warehouse Slot Assignment: Assigning nearest-to-dock bins in O(log N) under concurrent picker traffic.
