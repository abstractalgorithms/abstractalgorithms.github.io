01 / UnderstandFailure & constraints

Clarify what is failing.

`oom_badness()` scores `(% of cgroup memory used * 10) + oom_score_adj`; lowering `oom_score_adj` below its initial value requires `CAP_SYS_RESOURCE`, which Kubernetes drops.

Design objective

Show the formula: `score = (RSS + swap + pagetables) / mem_limit * 1000 + oom_score_adj`.

Requirements

  • Ensure a leaking worker process is always terminated before the Gunicorn master, PID 1, or critical sidecars.
  • Prevent a single worker's memory leak from exceeding 2 GB without affecting the other 7 healthy workers.
  • Provide graceful backpressure or early worker recycling before hard `SIGKILL` occurs.
  • Eliminate silent pod-wide crashes caused by cgroup v2 `memory.oom.group` misconfiguration.

Constraints

  • Pod memory limit is 16 GB (`memory.max = 16 GiB`) on Linux kernel 5.15 with cgroup v2.
  • Gunicorn master loads a 1.5 GB shared read-only model (`preload_app = True`) via Copy-on-Write `fork()`.
  • Redis sidecar uses 2.2 GB RSS for feature caching.
Known failure modes

Writing `-500` to `/proc/self/oom_score_adj` inside a standard container fails with `PermissionError` (`EACCES`).

Isolated cgroup + Guaranteed QoS

  1. 01Clean CoW Fork: Master freezes GC before forking so the 1.5 GB model stays shared in read-only physical pages.
  2. 02Bias OOM Victim Selection: Workers inherit +200 oom_score_adj (master keeps 0 or -500), ensuring workers are always sacrificed first.
  3. 03Proactive Worker Recycling: A lightweight watchdog or middleware detects worker RSS > 1.8 GB and sends SIGTERM after current request.
  4. 04Contained Blast Radius: With oom.group=0, cgroup kills only the 1 leaking worker; Gunicorn master respawns it in <100 ms.
  5. 05Protect Stateful Cache: Moving Redis to its own Guaranteed-QoS pod guarantees app OOMs never evict the cache.
Combining oom_score_adj biasing, gc.freeze(), per-worker RSS watchdogs, and sidecar separation ensures only a leaking worker is recycled.

The invariants

  • Freeze GC objects in master before fork.
  • Set oom_score_adj = 300 in worker.
  • Check /proc/self/statm RSS in post_request and SIGTERM self if > 1.8 GB.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Move Redis to its own pod. Even with `Guaranteed` QoS, sharing a node/pod lifecycle means ML pod restarts or node evictions unnecessarily flush the cache.

04 / ImplementConfiguration & code

Build the safeguards.

`memory.oom.group = 1` treats the entire cgroup as an indivisible unit, killing the Gunicorn master and all 8 workers simultaneously on any OOM.

1. Reference implementation

PYTHON · Solution
import gc, os, signal

preload_app = True
workers = 8
MAX_WORKER_RSS_BYTES = 1800 * 1024 * 1024

def when_ready(server):
    gc.freeze()

def post_fork(server, worker):
    with open("/proc/self/oom_score_adj", "w") as f:
        f.write("300")

def post_request(worker, req, environ, resp):
    with open("/proc/self/statm") as f:
        rss_pages = int(f.read().split()[1])
    if rss_pages * os.sysconf("SC_PAGE_SIZE") > MAX_WORKER_RSS_BYTES:
        os.kill(os.getpid(), signal.SIGTERM)

2. Harden for scale

`memory.oom.group = 1` treats the entire cgroup as an indivisible unit, killing the Gunicorn master and all 8 workers simultaneously on any OOM.

PYTHON · Scale hardening
with open("/sys/fs/cgroup/memory.oom.group") as f:
    assert f.read().strip() == "0", "memory.oom.group=1 will kill the parent master!"

3. Operational controls

Step 1

Verify `/sys/fs/cgroup/memory.oom.group` is `0` for multi-process worker containers.

Step 2

Keep `1` only for tightly coupled single-unit workloads like JVM + child helpers.

Implementation note

Reading `/proc/self/statm` takes ~5 microseconds per request—negligible for ML inference.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

A container OOM kill produces `reason: OOMKilled` (exit code 137) and increments `container_oom_events_total` in cAdvisor/kernel `dmesg`, whereas a child-only OOM leaves the pod running (`status: Running`) while logging `SIGKILL` in Gunicorn master logs.

  • ↗
    Check `kube_pod_container_status_last_terminated_reason{reason="OOMKilled"}`.
  • ↗
    Alert on Gunicorn worker `SIGKILL` exit codes (`-9`) in application logs.

# Alert rules:

# 2. Worker-level OOM: rate(gunicorn_worker_sigkill_total[5m]) > 0

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Protect critical parent/supervisor processes with oom_score_adj = -500..-1000, isolate workers in dedicated cgroup v2 slices (memory.high + memory.oom.group), and enforce per-worker RSS limits.
  • 02Trade-off tip: Moving Redis out adds ~0.2 ms network RTT compared to localhost, which is negligible for ML inference.
  • 03Watch out for: Pod-wide exit 137 when only 1 of 8 workers leaked.
