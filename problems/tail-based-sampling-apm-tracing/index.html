01 / UnderstandFailure & constraints

Clarify what is failing.

Head-based sampling decides at the ingress hop before execution begins, discarding 99% of slow requests blindly and keeping only ~0.9 slow traces/sec without bias toward anomalies.

Design objective

Explain that trace_id sampling happens at hop 1 before DB locks or downstream timeouts occur.

Requirements

  • Capture 100% of traces with total duration > 1,500 ms or any span containing an HTTP 5xx / gRPC error.
  • Retain a 0.5% baseline sample of healthy fast traces for latency distribution baselines.
  • Keep APM storage/ingestion costs flat (under 1,200 spans/sec exported to backend).
  • Handle 18,000 RPS across 120 microservices without dropping spans due to trace-id routing mismatches.

Constraints

  • Average trace has 12 spans (~1.8 KB per span) across Go, Java, and Python services.
  • Cannot exceed 32 GB RAM per collector pod; max end-to-end trace visibility lag is 45 seconds.
  • All services already emit OpenTelemetry OTLP/gRPC spans.
Known failure modes

Missing root cause for p99.9 outages because no slow trace survived the 1% coin flip.

  1. 01Emit All Spans to Tier 1: Services disable head sampling and stream all 216k spans/sec to stateless Tier 1 gateways.
  2. 02Compute Exact SpanMetrics: Tier 1 computes unbiased p50/p99 histograms over 100% of spans before any trace is dropped.
  3. 03Route by Trace ID: Load-balancing exporter hashes traceID so all 12 spans of a trace land on the same Tier 2 pod.
  4. 04Tail Policy Evaluation: After decision_wait=30s, Tier 2 keeps traces with latency > 1500ms, error=true, or 0.2% baseline.
  5. 05Cost-Bounded APM Export: 100% of rare 6-second freezes are exported while staying under the $14k/mo span budget.
Separating metric generation (Tier 1) from consistent-hashed tail sampling (Tier 2) eliminates sampling bias without distorting metrics or blowing up APM costs.

The invariants

  • Configure Tier 1 loadbalancing exporter with routing_key: traceID.
  • Configure Tier 2 memory_limiter (12 GiB) to prevent OOMKills.
  • Define tail_sampling policies for status_code ERROR, latency >= 1500ms, and 0.2% baseline.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Tail sampling intentionally over-represents slow and errored traces (100% of >1.5s vs 0.2% of fast), which severely skews any latency percentiles computed post-sampling.

Step 1

Show the math: keeping 100% of 0.5% slow traces and 0.2% of 99.5% fast traces makes slow traces ~71% of the exported dataset.

Step 2

Place spanmetrics connector in Tier 1 before loadbalancing/tail_sampling.

Step 3

Export exact Prometheus histograms independently of trace sampling.

YAML · Lifecycle trace
# Tier 1 SpanMetrics + TraceID LoadBalancer
connectors:
  spanmetrics:
    histogram:
      explicit:
        buckets: [10ms, 50ms, 100ms, 250ms, 500ms, 1500ms, 5000ms]
exporters:
  loadbalancing:
    routing_key: traceID
    protocol:
      otlp:
        tls: { insecure: true }
    resolver:
      dns:
        hostname: otel-tail-collector-headless.monitoring.svc.cluster.local
Key trade-off

Computing spanmetrics on 216k spans/sec adds ~15% CPU to Tier 1 gateways.

04 / ImplementConfiguration & code

Build the safeguards.

A 3x spike pushes buffered payload to ~35 GB raw (~75 GB with Go overhead), exceeding 64 GB fleet RAM unless memory_limiter and attribute stripping are configured.

1. Reference implementation

YAML · Solution
# Tier 2 Tail-Sampling Collector (otel-tail-collector.yaml)
processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 12288
    spike_limit_mib: 2048
  tail_sampling:
    decision_wait: 30s
    num_traces: 250000
    expected_new_traces_per_sec: 5000
    policies:
      - name: errors-policy
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow-traces-policy
        type: latency
        latency: { threshold_ms: 1500 }
      - name: baseline-sample
        type: probabilistic
        probabilistic: { sampling_percentage: 0.2 }

2. Harden for scale

A 3x spike pushes buffered payload to ~35 GB raw (~75 GB with Go overhead), exceeding 64 GB fleet RAM unless memory_limiter and attribute stripping are configured.

YAML · Scale hardening
processors:
  attributes/truncate:
    actions:
      - key: db.statement
        action: delete # Strip bulky SQL payloads before 30s Tier 2 buffering

3. Operational controls

Step 1

Size Tier 2 pods with 2.4x headroom (4 x 16 GB or 6 x 16 GB).

Step 2

Configure memory_limiter to refuse/drop new spans cleanly instead of OOMKilling the pod and losing all 30s of buffered traces.

Step 3

Strip large debug attributes (e.g., full SQL bodies > 512 bytes) at Tier 1 before buffering.

Implementation note

Buffering 216k spans/sec for 30s requires ~26 GB fleet RAM across 4 stateful pods.

Prove the fix works.

Monitor collector decision latency, orphan span rate, and exporter drop counters in Prometheus.

  • ↗
    Alert on otelcol_processor_refused_spans (memory_limiter triggers).
  • ↗
    Run a synthetic canary trace every 60s with a forced 2,000ms sleep and assert all 12 spans arrive in APM.
SQL · Verification
-- PromQL alerts for Tail-Sampling health
rate(otelcol_processor_tail_sampling_sampling_trace_dropped_too_early[5m]) > 0
rate(otelcol_processor_refused_spans[1m]) > 0

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Failure scenario 1

OOMKill wipes out the entire 30s in-memory buffer of all 135,000 active traces simultaneously.

Failure scenario 2

Clock skew or >30s async spans causing partial orphan traces.

Alternatives considered

  • Periodic manual trace inspection.
