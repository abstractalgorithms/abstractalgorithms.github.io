01 / UnderstandFailure & constraints

Clarify what is failing.

Symptomless threshold alerts (CPU >85%, 1-minute 5xx spikes) created chronic false positives, while lack of dependency inhibition turned a single DB pool outage into 47 simultaneous pages.

Design objective

Audit PagerDuty incident logs over the last 30 days to compute the auto-resolve percentage per alert rule.

Requirements

  • Reduce weekly PagerDuty pages from ~420 to <15 actionable pages without missing any P1 SLO breach (>0.1% error budget burn in 5 minutes).
  • Suppress cascading downstream alerts (e.g., API gateway 504s) when an upstream root-cause service (e.g., Postgres primary) is already firing a critical alert.
  • Ensure duplicate alerts across Prometheus HA pairs and multi-AZ collectors collapse into a single PagerDuty incident via deterministic deduplication.
  • Route non-urgent, self-healing anomalies (single-pod OOM, transient CPU >85%) to async Slack/ticket queues instead of waking on-call.

Constraints

  • P1 detection latency (MTTD) must remain <= 2 minutes for hard availability drops (>5% 5xx rate).
  • Must work with existing Prometheus, Alertmanager, OpenTelemetry metrics, and PagerDuty Events API v2.
  • Cannot drop raw telemetry or hide warnings from engineering dashboards used during post-incident forensics.
Known failure modes

Confusing short-duration pages caused by human quick-fixes with genuine self-healing false positives.

Warnings & low-burn tickets

  1. 01Burn-Rate Evaluation: Both prom-0 and prom-1 evaluate 14.4x (5m & 1h) and 6x (30m & 6h) burn-rate rules with minimum RPS guards.
  2. 02Grouping & Root-Cause Inhibition: Alertmanager waits 30s to batch related alerts and suppresses downstream 504s if postgres-primary critical is active.
  3. 03Deduplicated Critical Page: Only page-severity alerts hit PagerDuty using deterministic dedup_key = env:cluster:service:alertname.
  4. 04Async Ticket & Slack Routing: Slow-burn (1x-3x) and single-pod resource warnings route to #ops-triage and auto-create Jira follow-ups.
  5. 05Clean On-Call Triage: On-call receives 1 consolidated incident with runbook link and root-cause context instead of 47 noisy pings.
Alertmanager's gossip mesh deduplicates HA Prometheus evaluations and applies inhibition rules before dispatching to PagerDuty or Slack.

The invariants

  • Create Prometheus recording rules for 5m, 30m, 1h, and 6h error ratios.
  • Gate paging alerts on both long and short windows exceeding the burn-rate threshold AND traffic > 10 RPS.
  • Configure Alertmanager group_wait (30s), inhibit_rules for DB/upstream outages, and dedup_key without replica labels.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Dual-window gating requires sustained error budget consumption while resetting immediately when the 5m window recovers, eliminating both micro-bursts and long reset tails.

Step 1

Compare 2-minute static threshold (fires on any 2-minute deploy blip) vs. 14.4x 1h+5m dual window.

Step 2

Add minimum RPS floor (>10 RPS) for ratio alerts or route low-QPS services to synthetic blackbox probes.

PYTHON · Lifecycle trace
def should_page_burn_rate(errors_5m: int, total_5m: int, errors_1h: int, total_1h: int, slo_target: float = 0.9995) -> bool:
    if total_5m < 3000:  # < 10 RPS over 5m (300s)
        return False
    budget = 1.0 - slo_target
    burn_5m = (errors_5m / total_5m) / budget
    burn_1h = (errors_1h / max(total_1h, 1)) / budget
    return burn_5m >= 14.4 and burn_1h >= 14.4
Key trade-off

Gating on >10 RPS prevents false pages on admin endpoints, at the cost of requiring separate blackbox uptime checks for low-QPS APIs.

04 / ImplementConfiguration & code

Build the safeguards.

A single-instance Alertmanager is a single point of failure for paging; a 3-node gossip mesh plus an external Watchdog heartbeat guarantees delivery.

1. Reference implementation

YAML · Solution
inhibit_rules:
  - source_matchers: ['alertname="PostgresPrimaryDown"', 'severity="page"']
    target_matchers: ['severity=~"page|warning"', 'upstream_dep="postgres-primary"']
    equal: ['cluster']

receivers:
  - name: 'pagerduty-critical'
    pagerduty_configs:
      - dedup_key: '{{ .GroupLabels.cluster }}:{{ .GroupLabels.service }}:{{ .GroupLabels.alertname }}'
        severity: 'critical'

3. Operational controls

Step 1

Deploy 3 Alertmanager replicas across 3 AZs joined via --cluster.peer.

Step 2

Configure Prometheus to send alerts to ALL Alertmanager endpoints (not behind a single load balancer).

Step 3

Route an always-firing Watchdog alert to an external heartbeat monitor that pages if silenced for >5 minutes.

Implementation note

Multi-window rules require 5-60 minutes of metric history; new services need 1 hour of warmup before burn-rate alerts stabilize.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Continuous alert governance prevents threshold drift by flagging rules with high auto-resolve rates or zero-action acknowledgments every Monday.

PYTHON · Verification
import requests

def audit_noisy_alerts(pd_token: str, since_iso: str) -> list[dict]:
    resp = requests.get(
        "https://api.pagerduty.com/incidents",
        headers={"Authorization": f"Token token={pd_token}"},
        params={"since": since_iso, "limit": 100, "statuses[]": "resolved"},
        timeout=10,
    )
    resp.raise_for_status()
    return [i for i in resp.json()["incidents"] if i.get("resolve_reason") is None]

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Putting Alertmanager behind a single Kubernetes ClusterIP Service instead of headless DNS causes Prometheus to only reach 1 pod.

Failure scenario 2

Ignoring warning-tier Slack noise until engineers mute the #ops-triage channel too.

Alternatives considered

  • Enforcing CI/CD policy checks (Conftest/OPA) blocking any new PrometheusRule without a runbook_url and for-duration.
