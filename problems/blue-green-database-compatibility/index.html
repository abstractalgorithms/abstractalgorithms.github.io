01 / UnderstandFailure & constraints

Clarify what is failing.

Green's Flyway migration mutated the shared PostgreSQL schema destructively, breaking Blue's SQL assumptions and making rollback impossible without a database restore.

Design objective

Identify that `RENAME COLUMN billing_zip TO postal_code` broke all Blue `SELECT` and `INSERT` queries.

Requirements

  • Guarantee instant (<30s) rollback from Green (N) to Blue (N-1) with 0% schema errors
  • Support concurrent Blue and Green reads/writes during canary/drain windows on a single shared database
  • Prevent destructive migrations (`DROP`, `RENAME`, `NOT NULL` without default) from running in the same release as code cutover
  • Automate CI/CD schema compatibility enforcement before deployment

Constraints

  • Blue and Green share one primary PostgreSQL 15 database (no separate DB per color)
  • ALB connection draining takes up to 60 seconds, meaning Blue and Green overlap in production
  • Zero downtime allowed for 2,000 RPS payment processing
Known failure modes

Running Flyway `undo` drops `tax_jurisdiction` and destroys data written by Green

Separate concerns. Map the flow.

Use a pre-deploy Expand migration with additive columns and a `BEFORE INSERT OR UPDATE` sync trigger, followed by a post-stabilization Backfill/Validate and a v43 Contract.

  1. 01CI Compatibility Gate: Reject RENAME, DROP, or bare NOT NULL in PRs; allow only additive nullable/default columns.
  2. 02Pre-Deploy Expand: Add postal_code and nullable tax_jurisdiction (DEFAULT 'UNKNOWN'); attach sync trigger.
  3. 03Safe Dual-Version Traffic: Blue writes billing_zip; Green writes postal_code + tax_jurisdiction. Rollback is 100% safe.
  4. 04Post-Cutover Backfill: Once Green is stable, backfill NULLs and run VALIDATE CONSTRAINT for NOT NULL.
  5. 05Final Cleanup: In v43, drop the sync trigger and legacy billing_zip column after Blue is decommissioned.
Decoupling Expand (pre-deploy) from Contract (v43) keeps N and N-1 versions 100% compatible on a single DB.

The invariants

  • Expand: Add postal_code (nullable) and tax_jurisdiction (DEFAULT 'PENDING').
  • Sync: Attach a BEFORE INSERT OR UPDATE trigger to keep billing_zip and postal_code identical.
  • Contract (v43): After Blue is retired, drop the trigger and billing_zip.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Always run Expand migrations as an independent pre-deployment pipeline job before Green containers start, never inside the application startup hook.

Step 1

Avoid race conditions when 20 Green pods boot simultaneously and contend on Flyway's schema lock.

Step 2

Ensure migration failures abort the pipeline before any Green pod enters the ALB target group.

Step 3

Keep container startup fast (<5s) and deterministic.

YAML · Lifecycle trace
jobs:
  migrate-expand:
    runs-on: ubuntu-latest
    steps:
      - run: squawk db/migration/V42__*.sql
      - run: flyway -url=$DB_URL -lockRetryCount=3 migrate
  deploy-green:
    needs: migrate-expand
    steps:
      - run: ecs deploy --service payments-green --image v42
Key trade-off

Requires CI runner network access to the private VPC database (e.g., via self-hosted runner or SSM)

04 / ImplementConfiguration & code

Build the safeguards.

Backfill `'PENDING'` rows in throttled 1,000-row batches, then use `ADD CONSTRAINT ... NOT VALID` + `VALIDATE CONSTRAINT` before setting `NOT NULL`.

1. Reference implementation

SQL · Solution
ALTER TABLE invoices
  ADD COLUMN IF NOT EXISTS postal_code VARCHAR(16),
  ADD COLUMN IF NOT EXISTS tax_jurisdiction VARCHAR(16) DEFAULT 'PENDING';

CREATE OR REPLACE FUNCTION sync_invoices_postal_code() RETURNS TRIGGER AS $$
BEGIN
  IF NEW.postal_code IS NULL THEN NEW.postal_code := NEW.billing_zip; END IF;
  IF NEW.billing_zip IS NULL THEN NEW.billing_zip := NEW.postal_code; END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

2. Harden for scale

Backfill `'PENDING'` rows in throttled 1,000-row batches, then use `ADD CONSTRAINT ... NOT VALID` + `VALIDATE CONSTRAINT` before setting `NOT NULL`.

SQL · Scale hardening
SET lock_timeout = '2000ms';
ALTER TABLE invoices ADD CONSTRAINT chk_tax_jurisdiction_nn
  CHECK (tax_jurisdiction IS NOT NULL) NOT VALID;
ALTER TABLE invoices VALIDATE CONSTRAINT chk_tax_jurisdiction_nn;

3. Operational controls

Step 1

Verify 0% of Blue traffic remains and backfill any `tax_jurisdiction = 'PENDING'` or `NULL` rows.

Step 2

Add `CHECK (tax_jurisdiction IS NOT NULL) NOT VALID` (instant metadata lock).

Step 3

Run `VALIDATE CONSTRAINT` under `SHARE UPDATE EXCLUSIVE` so live reads/writes continue uninterrupted.

Implementation note

Trigger-based sync keeps N and N-1 consistent at the cost of a small per-write PL/pgSQL invocation

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Enforce automated SQL AST linting with Squawk in CI and require explicit multi-PR separation between Expand and Contract.

  • ↗
    Add Squawk to GitHub Actions on every PR touching `db/migration/`.
  • ↗
    Ban `rename-column`, `drop-column`, `ban-drop-table`, and `adding-not-nullable-field` by default.
  • ↗
    Require `pg_stat_statements` verification showing zero queries referencing the old column before approving a Contract PR.
YAML · Verification
- name: Lint SQL Migrations
  uses: sbdchd/squawk-action@v1
  with:
    files: db/migration/*.sql
    fail-on-violations: true

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Running `ALTER COLUMN tax_jurisdiction SET NOT NULL` directly acquires `ACCESS EXCLUSIVE` for the entire 50M-row scan

Failure scenario 2

Relying on manual code review alone inevitably misses subtle lock or N-1 incompatibilities

Alternatives considered

  • Test every PR in CI by running v(N-1) integration tests against the v(N)-migrated database
