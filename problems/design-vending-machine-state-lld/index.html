01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why the State Pattern matters in Vending Machine LLD.

A vending machine processes asynchronous events (insertCoin, selectItem, dispense, cancelRefund) across four distinct modes (Idle, HasMoney, Dispensing, SoldOut). Mixing state checks with business logic inside one VendingMachine class quickly turns into fragile nested if-else branches where coins can be lost or items dispensed without sufficient change.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens without explicit state encapsulation and change rollback.

Procedural switch(state) code introduces three common bugs:

  1. Illegal State Mutations: Pressing dispense twice or inserting coins during Dispensing corrupts balance.
  2. Trapped Change: Dispensing a $1.50 item when the user inserted $2.00 fails mid-way if the machine lacks $0.50 in coins, stranding inventory or money.
  3. Rigid Extensions: Adding NFC/card payments forces edits across every if-else block.
Vending State Machine

Idle -> HasMoney -> Dispensing -> Idle / SoldOut

Each State implementation handles only valid actions for its mode and rejects or refunds invalid transitions.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive solution (and why monolithic if-else switching breaks).

A naive VendingMachine stores String state and branches inside every method:

  • Zero Isolation: Adding a Maintenance or CardTap state requires auditing every method in VendingMachine.
  • Non-Atomic Dispense: Decrementing slot.qty before checking if the coin tray can make change leaves the machine inconsistent.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: GoF State Pattern + Atomic Change Validator.

Clean LLD delegates behavior to concrete VendingState classes:

  • Zero if-else in Context: VendingMachine forwards insertMoney, selectItem, dispense, and cancel directly to self.state.
  • Atomic Change Check: In HasMoneyState.select_item(), verify qty > 0, balance >= price, AND coin_inventory.can_make_change(balance - price) before transitioning to DispensingState; otherwise refund and revert to IdleState.
  • Payment Strategy: Abstract PaymentMethod (CoinAcceptor, CardReader) so new payment rails plug in cleanly.
Atomic Purchase & Rollback

Item Selection, Change Verification & Safe Dispense

Verifying change availability before decrementing inventory guarantees atomic purchase or full refund.

class HasMoneyState(VendingState):
    def select_item(self, machine, code: str):
        item = machine.inventory.get(code)
        if machine.balance >= item.price:
            machine.set_state(machine.dispensing_state)

public class HasMoneyState implements VendingState {
    public void selectItem(VendingMachine m, String code) {
        Item item = m.getInventory().get(code);
        if (m.getBalance() >= item.price()) m.setState(m.getDispensingState());
    }
}
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where the State Pattern applies in System Design.

Explicit State objects power complex lifecycle-driven systems beyond vending machines:

  • Order & Payment Lifecycles: CREATED -> AUTHORIZED -> CAPTURED -> REFUNDED with strict transition guards.
  • Workflow & Saga Orchestrators: Ensuring compensating transactions only run from valid intermediate states.
  • Connection & Protocol Drivers: Modeling TCP/WebSocket/gRPC channel states cleanly.
