Design a Distributed Unique ID Generator

Design a globally distributed unique ID generation service (similar to Twitter Snowflake). Generated IDs must be 64-bit integers, globally unique, roughly time-sortable, and generated at high scale without cross-node network coordination.

Scope, Requirements & Constraints

UUID v4 is 128-bit and non-sequential, causing B-tree fragmentation, page splits, and cache misses in database indexes. Centralized DB auto-increment introduces a single write bottleneck and single point of failure.

Core Functional Requirements

  • ✓IDs must be globally unique across all nodes.
  • ✓IDs must fit into a 64-bit integer (int64) for database index efficiency.
  • ✓IDs must be roughly chronological / time-sortable.
  • ✓High availability: service must generate at least 10,000 IDs per second per node with sub-millisecond latency.
  • ✓No single point of failure and no runtime consensus round-trips (Paxos/Raft) in the ID generation path.

Scale & Latency Constraints

  • —64 bits maximum.
  • —System lifetime: at least 50 years before epoch overflow.
  • —Clock synchronization: tolerate minor NTP clock drift without generating duplicate IDs.

Reference Architecture & System Blueprint

Twitter Snowflake 64-bit structure: 1 sign bit + 41 timestamp bits + 10 machine/datacenter bits + 12 sequence bits.

Architecture Flow Narrative[1 bit: Sign][41 bits: Millisecond Timestamp][10 bits: Machine ID][12 bits: Sequence Number]

Hardened Implementation Steps

  1. 11 unused sign bit (always 0 to keep integer positive).
  2. 241 timestamp bits: milliseconds since custom epoch. 2^41 ms ≈ 69.7 years of IDs.
  3. 310 node ID bits: 5 bits datacenter ID (32 datacenters) + 5 bits worker ID (32 workers per DC) = 1,024 generator nodes.
  4. 412 sequence bits: supports up to 2^12 = 4,096 IDs per millisecond per node.
  5. 5Algorithm: read current timestamp. If same millisecond as last ID, increment sequence. If sequence overflows 4095, busy-wait until next millisecond. If new millisecond, reset sequence to 0.

Key Decisions & Trade-Off Analysis

Architectural Decisions & Trade-Offs

  • ⚖Custom epoch: Starting timestamp at application launch year (e.g., 2026) gives 69 years of runtime from now. Unix epoch would overflow 41 bits in 2039.
  • ⚖Static worker ID assignment vs ZooKeeper/etcd: Static config is simple but prone to human config error (duplicate worker IDs). Zookeeper/etcd ephemeral nodes assign unique worker IDs automatically on startup.

Scale Bottlenecks & Operational Hazards

Operational Hazards & Mitigations

  • ⚠Clock skew / rollback: If system clock jumps backward, the generator will produce duplicate timestamps and therefore duplicate IDs!
  • ⚠Defense 1 (Wait): If clock rollback is small (< 5 ms), spin-wait until the clock catches up to lastTimestamp.
  • ⚠Defense 2 (Reject): If clock rollback is significant, reject requests and raise an alert; refuse to generate IDs until operator verifies or clock catches up.
  • ⚠Defense 3 (Clock-sequence bits): Reserve 2 bits for clock sequence counter; increment clock sequence when rollback is detected to maintain uniqueness.

Changed Constraints & System Extension

Follow-up: What if client requests peak above 4,096 IDs in a single millisecond on one node? How does the generator absorb this burst?

Extension Implementation Steps

  1. 1When sequence reaches 4,095, block and yield CPU until timestamp advances to the next millisecond.
  2. 2Horizontal scale: add more generator worker nodes to distribute the load across more 10-bit machine namespaces.

Follow-Up Trade-Offs

  • ⚖Blocking on sequence overflow: introduces microsecond latency jitter on burst, but guarantees strict uniqueness without allocating extra bits.
