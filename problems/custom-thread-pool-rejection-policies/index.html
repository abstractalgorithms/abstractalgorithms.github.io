01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why default ThreadPoolExecutor policies fail mixed-criticality workloads.

A payment ledger runs 32 worker threads (~1,600 RPS normal capacity at 20 ms/req) fed by non-blocking Netty event-loop threads. During a 30-second flash-sale burst (4,800 RPS), low-value AuditLog and EmailReceipt tasks occupy 60% of the queue—causing AbortPolicy to reject CommitSettlement and FraudWebhook RPCs indiscriminately.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Event-loop hijacking, silent Future hangs, and lost settlements.

Each built-in JDK RejectedExecutionHandler breaks under mixed-criticality load:

  1. CallerRunsPolicy: Forces Netty's 8 I/O threads to execute 200 ms blocking JDBC calls, stalling TCP keep-alives and causing cluster-wide disconnect storms.
  2. DiscardPolicy / DiscardOldestPolicy: Silently drops tasks without completing CompletableFutures, hanging callers until socket timeout.
  3. Uncaught RejectedExecutionException: Bypasses .exceptionally() handlers if thrown before returning the future.
Rejection Policy Comparison

CallerRunsPolicy I/O Hijack vs. Criticality-Aware Shedding

Shedding BEST_EFFORT tasks at 70% depth frees 100% of worker capacity for the 1,920 RPS critical stream.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive `ConcurrentLinkedQueue` and unbounded priority queues.

Swapping to PriorityBlockingQueue without a semaphore bound grows unboundedly until OOM, while ConcurrentLinkedQueue.size() is O(N) on the hot path. Using CallerRunsPolicy is strictly unsafe whenever callers are non-blocking event-loop threads.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Reserved Criticality Lane + Fast-Fail 503.

Bound total queued tasks at 512 (< 2,000 cap) using an ArrayBlockingQueue(512) with O(1) depth checks:

  • 70% High-Watermark for BEST_EFFORT: Reject AuditLog and EmailReceipt once queue.size() >= 358, reserving 154 slots (30%) exclusively for CRITICAL RPCs (CommitSettlement, FraudWebhook).
  • Explicit Future Completion: Wrap submission in try/catch and use a custom RejectedExecutionHandler that emits per-criticality Micrometer counters and completes the CompletableFuture exceptionally -> HTTP 503 with Retry-After.
  • Optional Spillover: Route shed EmailReceipt tasks to a bounded disk/Kafka fallback rather than dropping permanently.
Queue Admission Control

Criticality-Aware Queue Watermark Admission

Reserving the top 30% of the bounded queue guarantees critical settlements survive 3x bursts without stalling Netty.

public CompletableFuture<Void> submit(PrioritizedTask task) {
    if (task.priority == Priority.BEST_EFFORT && pool.getQueue().size() >= 358) {
        metrics.counter("pool.shed", "priority", "best_effort").increment();
        return CompletableFuture.failedFuture(new ShedException("503 Retry-After: 2"));
    }
    CompletableFuture<Void> future = new CompletableFuture<>();
    try {
        pool.execute(() -> { task.run(); future.complete(null); });
    } catch (RejectedExecutionException ex) {
        metrics.counter("pool.rejected", "priority", task.priority.name()).increment();
        future.completeExceptionally(ex); // Never block Netty I/O thread!
    }
    return future;
}
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where criticality-aware rejection is applied.

Priority-aware admission control protects every mixed-workload backend:

  • Payment & Ledger Gateways: Sheds receipt emails and analytics hooks so settlements and fraud checks never drop.
  • API Gateways (Envoy / NGINX): Enforces priority load shedding before worker queues saturate.
