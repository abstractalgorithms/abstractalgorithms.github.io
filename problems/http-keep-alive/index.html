Aligning HTTP Keep-Alive
Timeouts Across Proxies.

When a backend's HTTP keepAliveTimeout (e.g., 60s) is shorter than or equal to the upstream reverse proxy's idle timeout (e.g., AWS ALB 60s or Nginx 65s), the backend closes the socket with FIN at the exact millisecond the proxy reuses it—causing intermittent 502 Bad Gateway / ECONNRESET errors.

STAGE 02 · IMPACTL5 · APPLIED DESIGN

Real-World Impact of the TCP FIN / RST Race.

Why this matters: The problem: see what breaks without Real-World Impact of the TCP FIN / RST Race under real concurrency or scale.

When a downstream server closes an idle keep-alive socket at the exact millisecond an upstream proxy writes a new request onto it:

  1. 502 Bad Gateway: Node.js (5s) or Tomcat (60s) sends TCP FIN while Nginx/ALB simultaneously writes POST /orders.
  2. TCP RST Aborts: The backend kernel replies TCP RST to the closed socket; Nginx logs upstream prematurely closed connection and returns 502.
  3. Unsafe Retries: Because the proxy cannot know whether the backend parsed the POST before sending FIN, retrying risks double-charging.

Backend FIN Race (502) vs. Proxy-Initiated Close

Strictly increasing keep-alive timeouts downstream ensures the upstream proxy always initiates idle socket teardown.

STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise Solution: Strict Downstream Timeout Hierarchy.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Enforce a strictly increasing idle-timeout and max-request ladder from edge to origin so the caller always closes first:

  • AWS ALB: idle_timeout = 60s (must be < Nginx downstream keepalive_timeout = 75s).
  • Nginx -> Backend Upstream: Set keepalive_timeout 55s and keepalive_requests 5000 on the Nginx upstream pool.
  • Backend (Tomcat / Node.js): Set server.tomcat.keep-alive-timeout: 90s (server.keepAliveTimeout = 90000, headersTimeout = 95000 in Node.js) and max-keep-alive-requests: 10000 so the backend never closes an active pooled connection first.
  • Verification: Confirm with tcpdump that FIN packets originate from the proxy, not port 8080.
Timeout Ladder Alignment

Increasing Keep-Alive & Request Limits Downstream

1.Edge -> Nginx: ALB idle_timeout (60s) < Nginx client keepalive_timeout (75s).

2.Nginx -> App: Nginx upstream keepalive_timeout (55s) < Tomcat/Node (90s).

3.Max Requests: Backend max-keep-alive-requests (10,000) > Nginx (5,000).

4.Node.js Pitfall: Node defaults to 5s keepAliveTimeout; must override to 90,000 ms.

Every upstream hop closes idle sockets before the downstream server's timer expires, eliminating 502 ECONNRESET races.

# Spring Boot application.yaml
server:
  tomcat:
    keep-alive-timeout: 90s
    max-keep-alive-requests: 10000

# Node.js equivalent:
# server.keepAliveTimeout = 90000;
# server.headersTimeout = 95000;

# Nginx upstream block (safe)
upstream backend_pool {
  server app-service:8080;
  keepalive 128;
  keepalive_timeout 55s;
  keepalive_requests 5000;
}

# Verify FIN direction on backend pod
# tcpdump -ni eth0 'tcp[tcpflags] & (tcp-fin|tcp-rst) != 0 and port 8080'

STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Keep-Alive Alignment Applies in System Design.

Why this matters: Scope boundary: identify where this pattern fits best and where simpler or async alternatives win.

Timeout hierarchy alignment is critical across multi-hop cloud topologies:

  • API Gateways & Ingress Controllers: Envoy, Nginx, HAProxy, and AWS ALB/NLB pooling to Go, Node.js, or JVM backends.
  • Service Mesh Sidecars: Istio/Envoy sidecars must have shorter idle timeouts than application servers.
  • gRPC / HTTP/2 Connection Pools: Aligning MAX_CONNECTION_IDLE and KEEPALIVE_TIME prevents GOAWAY races.
