The idea to keep with you

Your marketplace catalog service updates product prices and inventory in PostgreSQL and immediately calls Elasticsearch's REST `_doc` API in the same request handler. Over 6 months, 3.2% of 15M SKUs have drifted: sold-out items still appear in search results, and flash-sale price drops show stale prices for hours. Root causes include: (1) PostgreSQL transaction rollbacks after ES already succeeded, (2) ES 429/timeout failures after PG committed, and (3) concurrent updates arriving at ES out of order. Redesign the sync pipeline for eventual consistency with zero permanent drift.

From patterns to decisions.

Full walkthrough · 5 stages
01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why dual-write drift between PostgreSQL and Elasticsearch is inevitable.

Calling es.index(doc) inside the same request handler that writes to PostgreSQL (15M SKUs, 2,500 writes/sec peak) guarantees permanent index drift (3.2% stale prices and phantom in-stock items). Without a distributed 2PC transaction, Postgres can roll back after ES succeeded, ES can 429/timeout after Postgres committed, or concurrent updates can arrive at ES out of order.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens under partial failures and out-of-order updates.

Application-level dual writes fail in three ways:

  1. Phantom Stock: Postgres transaction rolls back, but ES already indexed stock = 5.
  2. Silent Missing Updates: ES returns 429 or times out after Postgres committed, leaving old prices live for hours.
  3. Out-of-Order Overwrites: Thread A's older $100 update arrives at ES after Thread B's newer $80 flash-sale update, overwriting $80 with $100.
Dual-Write Race vs. Versioned CDC

Out-of-Order Dual-Write Overwrite vs. Debezium + ES External Version

Passing the monotonic LSN/version with version_type=external ensures Elasticsearch drops any stale out-of-order write.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive solution (and why async fire-and-forget or updated_at polling breaks).

Two common patches still lose or reorder data:

  • Async Fire-and-Forget: Spawning a background HTTP call to ES still drops updates on pod crashes and reorders concurrent edits.
  • SELECT * WHERE updated_at > last_poll: Polls miss hard deletes, struggle at 2,500 writes/sec, and hammer the primary DB.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Postgres WAL CDC (Debezium) + Kafka + ES External Versioning.

Zero-drift search sync decouples the write path completely:

  • Single Source of Truth: The API writes only to PostgreSQL (optionally writing a compact outbox row in the same ACID transaction).
  • WAL-Based CDC (Debezium -> Kafka): Debezium tails Postgres logical replication (pgoutput) with zero polling load on primary tables and publishes ordered events keyed by sku_id.
  • Idempotent Bulk Sink (<= 2 s p99): A Kafka Connect / consumer worker batches updates into ES _bulk using version=<lsn_or_epoch>&version_type=external so ES rejects stale versions (409 Conflict).
  • Backfill: Run an initial Debezium snapshot or sku_id-range backfill job to heal the existing 3.2% drift.
Zero-Drift CDC Pipeline

Postgres ACID Commit -> WAL Logical Replication -> Kafka -> ES Bulk

1.Atomic Capture: Every committed PG mutation is guaranteed to appear in the WAL.

2.Zero DB Polling: Logical replication streams changes without SELECT * load on primary.

3.Ordered Partition: Keying Kafka by sku_id preserves per-SKU mutation order.

4.External Version: ES drops out-of-order/replayed updates with version <= current.

WAL CDC + ES external versioning eliminates partial failures and out-of-order overwrites within <= 2s p99.

// Elasticsearch _bulk upsert with monotonic external version (LSN / row_version)
{ "index": { "_index": "catalog_skus", "_id": "sku_98124", "version": 48291044, "version_type": "external" } }
{ "sku_id": "sku_98124", "price_cents": 7999, "in_stock": true, "updated_at": "2026-11-18T09:00:01Z" }
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where CDC + External Versioning applies in System Design.

The Outbox/CDC + idempotent sink pattern is the universal antidote to dual-write drift:

  • DB-to-Search Sync: Keeping Postgres/MySQL synchronized with Elasticsearch or OpenSearch.
  • DB-to-Cache Invalidation: Invalidating or updating Redis keys from Debezium WAL streams.
  • CQRS Read Projections: Building denormalized read models and analytical lakes from OLTP primaries.
