01 / UnderstandFailure & constraints

Clarify what is failing.

App-level dual writes fail due to DB rollbacks after ES writes, ES failures after DB commits, and concurrent requests arriving at ES out of order.

Design objective

Trace `@Transactional` methods calling `esClient` directly.

Requirements

  • Guarantee atomic capture of every PostgreSQL mutation with zero lost updates even if the app crashes mid-request.
  • Prevent out-of-order concurrent writes from overwriting newer product states in Elasticsearch.
  • Propagate PostgreSQL updates to Elasticsearch within <= 2 seconds p99.
  • Provide a deterministic reconciliation/backfill mechanism for the existing 3.2% drifted SKUs.

Constraints

  • Catalog size is 15M SKUs with 2,500 write/sec peak (flash sales & price updates).
  • Elasticsearch cluster supports up to 10,000 bulk-indexed docs/sec.
  • PostgreSQL primary cannot sustain heavy polling queries (`SELECT * WHERE updated_at > ...`) during peak.
Known failure modes

Holding DB connections open while waiting for ES HTTP responses exhausts HikariCP.

  1. 01Atomic Domain + Outbox Write: Price/stock update, version increment, and outbox row commit in one ACID transaction.
  2. 02Zero-Polling Capture: Debezium reads committed outbox rows from PostgreSQL WAL and publishes keyed by sku_id.
  3. 03Batched Consumer: Search-indexer consumes partition-ordered events and builds an ES _bulk request.
  4. 04Optimistic Version Guard: ES accepts only if incoming version > stored version; stale replays return 409 and are safely acked.
  5. 05Drift Reconciliation: Read-replica backfill streams all 15M SKUs with version_type=external to heal the 3.2% drift.
ACID outbox commits + WAL CDC + external version checks eliminate partial-failure drift and out-of-order overwrites.

The invariants

  • Increment skus.version and insert into catalog_outbox in one ACID transaction.
  • Stream catalog_outbox via Debezium pgoutput into Kafka partitioned by sku_id.
  • Bulk-index into ES with version_type=external and treat 409 as idempotent.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Kafka guarantees order within a single partition, but does not prevent a parallel backfill job or DLQ replay from overwriting newer live CDC updates.

Step 1

Pass row.version in both live CDC events and backfill batches.

Step 2

Handle 409 Conflict in _bulk responses as a safe skip.

PYTHON · Lifecycle trace
for item in bulk_resp["items"]:
    res = item.get("index") or item.get("delete")
    if res["status"] == 409:
        continue  # Newer version already in ES
    if res["status"] >= 400:
        send_to_dlq(res)
Key trade-off

Requires storing/incrementing a monotonic version column on skus.

04 / ImplementConfiguration & code

Build the safeguards.

Stream keyset-paginated batches (`WHERE sku_id > last_id ORDER BY sku_id LIMIT 5000`) from a PostgreSQL read replica, throttled to 8,000 docs/sec with `version_type=external`.

1. Reference implementation

2. Harden for scale

Stream keyset-paginated batches (`WHERE sku_id > last_id ORDER BY sku_id LIMIT 5000`) from a PostgreSQL read replica, throttled to 8,000 docs/sec with `version_type=external`.

SQL · Scale hardening
SELECT sku_id, price_cents, stock, version
FROM skus
WHERE sku_id > :last_sku_id
ORDER BY sku_id ASC
LIMIT 5000;

3. Operational controls

Step 1

Query a read replica using keyset pagination (never `OFFSET`).

Step 2

Throttle `_bulk` writes to 8,000 docs/sec so live CDC keeps 2,000/s headroom.

Step 3

Rely on `version_type=external` so any SKU updated live during the 31-minute backfill isn't clobbered.

Implementation note

Adds ~300-800ms eventual consistency lag vs. synchronous writes, which is well within the 2s SLA.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Emit an outbox `DELETE` event with `version + 1` in the same transaction as `DELETE FROM skus`, and use ES `_bulk` `delete` with `version_type=external`.

  • ↗
    Capture `op_type = 'DELETE'` and `version = old.version + 1` in `catalog_outbox`.
  • ↗
    Execute ES `delete` action; ES retains a tombstone version briefly to reject late-arriving `UPSERT`s.
SQL · Verification
WITH del AS (DELETE FROM skus WHERE sku_id = 10421 RETURNING sku_id, version)
INSERT INTO catalog_outbox (sku_id, version, op_type, payload)
SELECT sku_id, version + 1, 'DELETE', '{}'::jsonb FROM del;

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Requires storing/incrementing a monotonic `version` column on `skus`.—
Option 2Debezium incremental snapshot (`signal` table) to stream backfill through the exact same Kafka topic.—

Review questions

Failure scenario 1

Replica lag causing the backfill to read a 2-second-old version—safely ignored by ES `version_type=external`.

Failure scenario 2

ES `index.gc_deletes` (default 60s) purges delete tombstones after 60s, so backfills shouldn't resurrect hard-deleted rows.

Alternatives considered

  • Soft-delete in PostgreSQL + ES document `status: deleted` filter.
