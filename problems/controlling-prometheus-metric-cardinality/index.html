01 / UnderstandFailure & constraints

Clarify what is failing.

A 15-bucket histogram creates 18 series per label combination (18.4M total), consuming ~92 GB of head-block RAM.

Design objective

Multiply label tuples by 18 histogram series.

Requirements

  • Immediately stabilize Prometheus so it stays up and resumes firing critical alerts.
  • Drop the offending high-cardinality series (`user_id`, `trace_id`, raw `path`) at scrape/ingestion time.
  • Fix application instrumentation so route templates (`/orders/{id}/items`) are used instead of raw URIs.
  • Enforce `sample_limit` per scrape target to prevent a single bad deploy from OOM-killing Prometheus again.

Constraints

  • Prometheus pod memory is capped at 64 GB RAM (`~6-8 KB` per active series in head block).
  • Histograms with 15 buckets multiply every unique label combination by 18x (`le` buckets + `_sum` + `_count` + `_bucket`).
  • Must preserve normalized HTTP latency SLIs (`route`, `status_class`, `method`).
Known failure modes

OOM loop during WAL replay prevents Prometheus from even reading new configs.

The invariants

  • Add sample_limit: 50000 and action: drop for bad labels.
  • Replace raw URI with route template + UNMATCHED fallback.
  • Use Exemplars for trace_id.
03 / Trace the lifecycleKey decisions

Follow the execution path.

`labeldrop` collapses distinct `user_id` series from the same pod into identical metric names with different values at the same scrape timestamp, causing ingestion collisions.

Step 1

Trace two users scraped from the same pod at timestamp T after stripping user_id.

YAML · Lifecycle trace
# Safe: drop the entire poisoned series until app rolls out fix
- source_labels: [user_id]
  regex: '.+'
  action: drop
Key trade-off

Temporarily loses that metric for offending pods until fixed, but guarantees clean TSDB ingestion.

04 / ImplementConfiguration & code

Build the safeguards.

Map all unmatched/404 routes to a constant `route="UNMATCHED"` label before recording metrics.

1. Reference implementation

YAML · Solution
scrape_configs:
  - job_name: 'api'
    sample_limit: 50000
    metric_relabel_configs:
      - source_labels: [user_id]
        regex: '.+'
        action: drop

2. Harden for scale

Map all unmatched/404 routes to a constant `route="UNMATCHED"` label before recording metrics.

PYTHON · Scale hardening
route_label = request.scope["route"].path if request.scope.get("route") else "UNMATCHED"

3. Operational controls

Step 1

Check if router matched a registered endpoint; if None/404, set route='UNMATCHED'.

Implementation note

sample_limit rejects the bad target's scrape rather than crashing Prometheus for the entire cluster.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Enable OpenMetrics Exemplars (`--enable-feature=exemplar-storage`), which attach one `trace_id` per histogram bucket update without creating new time series.

  • ↗
    Enable exemplar storage in Prometheus and scrape via OpenMetrics.
  • ↗
    Attach `trace_id` in the OTel/Micrometer histogram observation.
YAML · Verification
args:
  - --enable-feature=exemplar-storage
  - --storage.exemplars.max-exemplars=100000

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Keep Prometheus labels strictly bounded (low cardinality); drop or normalize dynamic labels via metric_relabel_configs at scrape time and move per-user/per-request dimensions to logs or distributed traces.
  • 02Trade-off tip: Temporarily loses that metric for offending pods until fixed, but guarantees clean TSDB ingestion.
  • 03Watch out for: 404 scanner traffic creating millions of series.
