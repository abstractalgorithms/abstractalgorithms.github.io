01 / UnderstandFailure & constraints

Clarify what is failing.

When Service B slows down, Service A's worker threads block waiting for responses. Soon Service A runs out of threads and fails to serve its own clients, cascading the failure through the entire system. Circuit Breakers fail fast immediately, preventing thread pool exhaustion.

Requirements

  • Track failure rates and slow call rates over a sliding evaluation window.
  • Transition from Closed to Open when failure threshold is exceeded, failing fast immediately without calling downstream.
  • Transition from Open to Half-Open after a configured sleep window, allowing a trial percentage of probe calls.
  • Transition from Half-Open to Closed if probes succeed, or back to Open if probes fail.
  • Provide fallback responses when circuit is Open.

Constraints

  • Minimal overhead on the critical request path (< 0.1 ms latency added).
  • Thread-safe state transitions without blocking concurrent in-flight requests.

The invariants

  • 1. Closed: Calls pass to downstream. Record call outcomes (success, failure, timeout). If failureRate > threshold (e.g. 50% over last 100 calls), trip to Open.
  • 2. Open: Reject incoming calls immediately with CircuitBreakerOpenException or execute fallback. Start waitDuration timer (e.g. 30 seconds).
  • 3. Half-Open: When timer expires, enter Half-Open. Allow a limited number of test calls (e.g. 10 probe calls).
  • 4. If probe failureRate < threshold: reset to Closed. If probe fails: return to Open for another waitDuration.

1. Reference implementation

TYPESCRIPT · Solution
// 3-State Circuit Breaker (CLOSED, OPEN, HALF_OPEN)
export enum CircuitState { CLOSED, OPEN, HALF_OPEN }

export class CircuitBreaker {
  private state = CircuitState.CLOSED;
  private failureCount = 0;
  private nextAttempt = Date.now();

  constructor(
    private readonly failureThreshold: number = 5,
    private readonly timeoutMs: number = 10000
  ) {}

  public async execute<T>(fn: () => Promise<T>, fallback: () => T): Promise<T> {
    if (this.state === CircuitState.OPEN) {
      if (Date.now() > this.nextAttempt) {
        this.state = CircuitState.HALF_OPEN; // Test downstream health with probe request
      } else {
        return fallback(); // Fast-fail immediately without network call
      }
    }

    try {
      const result = await fn();
      if (this.state === CircuitState.HALF_OPEN) {
        this.state = CircuitState.CLOSED; // Downstream healed!
        this.failureCount = 0;
      }
      return result;
    } catch (err) {
      this.failureCount++;
      if (this.failureCount >= this.failureThreshold || this.state === CircuitState.HALF_OPEN) {
        this.state = CircuitState.OPEN; // Trip circuit
        this.nextAttempt = Date.now() + this.timeoutMs;
      }
      return fallback();
    }
  }
}
05 / Verify & observeEvidence & acceptance

Prove the fix works.

Contextual fallback strategies.

  • ↗
    1. Recommendations / Feeds: Return cached recommendations or default popular items. Degradation is invisible to user.
  • ↗
    2. Search: Fall back to basic keyword search instead of vector neural search.
  • ↗
    3. Payments / Checkout: NEVER fake a payment. Return clean error advising user to retry shortly, or queue transaction for asynchronous background processing.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Distributed state (Redis)

High precision global state, but adds network latency to every call and creates a dependency on Redis. If Redis is down, circuit breakers fail!

Local in-memory state

Zero latency overhead, highly resilient. Downstream receives at most 500 * probe_count test calls, which is typically safe for downstream capacity.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Isolate ingress routing, decouple transactional state from background operations, and enforce explicit timeout and retry budgets across all service boundaries.
  • 02Trade-off tip: Count-based (last N calls): Good for predictable call volumes, but in low-traffic periods 5 failures over 2 days could trip the circuit.
  • 03Trade-off tip: Time-based (last T seconds): Reflects current operational health accurately, but requires minimum call threshold before evaluation to avoid tripping on a single failure.
  • 04Watch out for: Distributed state (Redis): High precision global state, but adds network latency to every call and creates a dependency on Redis. If Redis is down, circuit breakers fail!
  • 05Watch out for: Local in-memory state: Zero latency overhead, highly resilient. Downstream receives at most 500 * probe_count test calls, which is typically safe for downstream capacity.
