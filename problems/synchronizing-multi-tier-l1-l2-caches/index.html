01 / UnderstandFailure & constraints

Clarify what is failing.

Pod 12 misses L1/L2 and reads V1 from DB before Pod 3 commits V2 and calls `DEL`. Pod 12 then writes V1 into L2 and L1, overwriting the invalidation until TTL expires.

Design objective

Order the operations chronologically: `Pod12_DB_Read(V1) -> Pod3_DB_Commit(V2) -> Pod3_DEL -> Pod12_Cache_Set(V1)`.

Requirements

  • Propagate price/catalog invalidations across all 40 pods' L1 Caffeine caches in <= 200 ms p99.
  • Prevent stale-fill races where an in-flight DB/L2 read populates L1 or L2 with an older version after a newer write committed.
  • Limit worst-case staleness to <= 30 seconds even if a pod temporarily misses a Pub/Sub invalidation packet.
  • Keep L2 Redis hit/miss overhead low so Redis CPU stays < 40% at 80,000 aggregate RPS.

Constraints

  • 40 stateless Java (or Python) pods; Redis Cluster 7.x; PostgreSQL 16.
  • Checkout validation can tolerate <= 500 ms propagation lag, never 5 minutes.
  • Application code must be in Java or Python.
Known failure modes

Stale `V1` remains pinned in L2 Redis for the full 30-minute TTL.

  3. 03Broadcast Invalidation: Writer publishes key:5 to cache:inv channel (< 5 ms fan-out).
  4. 04L1 Versioned Eviction: All 39 pods receive key:5 and invalidate L1 if cached version < 5.
  5. 05Reconnect Self-Heal: On Pub/Sub reconnect, pod calls l1.invalidateAll() so missed messages never linger.
Redis Pub/Sub invalidates all 40 pods in < 5 ms, while monotonic version fencing blocks stale-fill races in both L1 and L2.

The invariants

  • Build Caffeine cache with expireAfterWrite(30, SECONDS).
  • Subscribe to cache:inv via Lettuce RedisPubSubAdapter; flush L1 in subscribed().
  • Compare version atomically in both L1 compute() and L2 Lua.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Redis Pub/Sub already exists in the L2 stack, delivers < 5 ms fan-out without per-pod consumer group management, and the 30s L1 TTL + reconnect flush eliminates the need for durable Kafka offsets.

Step 1

Compare operational overhead: 40 unique Kafka consumer groups vs 1 Redis SUBSCRIBE.

Step 2

Verify 30s TTL bounds any missed-message window.

if not cur or tonumber(ARGV[1]) > tonumber(cur) then
    redis.call('HSET', KEYS[1], 'version', ARGV[1], 'payload', ARGV[2])

    return 1
end
return 0

Key trade-off

Redis Pub/Sub does not buffer messages during pod restarts (acceptable because restarted pods start with empty L1).

04 / ImplementConfiguration & code

Build the safeguards.

Coalesce bulk invalidations in a 100 ms buffer or emit a single `FLUSH_PREFIX:merchant_42` message when batch size > 500 keys.

1. Reference implementation

JAVA · Solution
Cache<String, VersionedPrice> l1 = Caffeine.newBuilder()
    .maximumSize(100_000)
    .expireAfterWrite(Duration.ofSeconds(30))
    .build();

// Version-fenced L1 write
void putL1IfNewer(String key, VersionedPrice incoming) {
    l1.asMap().compute(key, (k, existing) ->
        (existing == null || incoming.version() > existing.version()) ? incoming : existing);
}

// Pub/Sub listener
public void message(String channel, String msg) {
    String[] parts = msg.split(":");
    String key = parts[0];
    long newVer = Long.parseLong(parts[1]);
    l1.asMap().computeIfPresent(key, (k, v) -> v.version() < newVer ? null : v);
}

public void subscribed(String channel, long count) {
    l1.invalidateAll(); // Self-heal on connect/reconnect
}

2. Harden for scale

Coalesce bulk invalidations in a 100 ms buffer or emit a single `FLUSH_PREFIX:merchant_42` message when batch size > 500 keys.

JAVA · Scale hardening
if (updatedKeys.size() > 500) {
    redisPubSub.publish("cache:inv", "__FLUSH_ALL__:0");
} else {
    updatedKeys.forEach(k -> redisPubSub.publish("cache:inv", k + ":" + ver));
}

3. Operational controls

Step 1

Detect bulk imports (> 500 keys in 100 ms).

Step 2

Publish a single `FLUSH_ALL` or `FLUSH_MERCHANT:<id>` control event instead of 200k individual messages.

Implementation note

Flushing all of L1 on reconnect causes a brief 1–2s spike in L2 Redis reads for that pod.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Redis Pub/Sub does not buffer messages during pod restarts (acceptable because restarted pods start with empty L1).—
Option 2Maintain a merchant-level version epoch in L1 so bumping 1 epoch invalidates all keys for that merchant in O(1).—

Review questions

Failure scenario 1

Unthrottled 200k `PUBLISH` calls can hit Redis `client-output-buffer-limit pubsub` and disconnect slow pods.

Failure scenario 2

In Redis Cluster, `CLIENT TRACKING` must be enabled on every master shard independently.

Alternatives considered

  • Stick to explicit `PUBLISH` when running Redis Cluster with custom sharding or RESP2 clients.

Practical heuristics & interview traps
