Kafka Exactly-Once Processing
& Zombie Fencing.

01 / UnderstandFailure & constraints

Clarify what is failing.

`initTransactions()` increments `producer_epoch` for a given `transactional.id`, fencing older epochs, while `read_committed` hides aborted records downstream.

Design objective

Explain that `transactional.id` maps to a persistent `(PID, epoch)` in `__transaction_state`.

Requirements

  • Fence any stalled ('zombie') producer instance immediately when a replacement takes over its partition.
  • Atomically tie output records in `payments.scored` to input consumer offsets in `__consumer_offsets`.
  • Ensure downstream microservices never observe uncommitted or aborted transactional records.
  • Prevent `InvalidPidMappingException` or `TransactionCoordinatorFencedException` from halting the pipeline.

Constraints

  • Pipeline uses Kafka 3.6 with `acks=all`, `enable.idempotence=true`, and 32 input partitions.
  • Kubernetes pods may experience 20-30s network/GC stalls before liveness probes kill them.
  • Downstream consumers read `payments.scored` at 15,000 events/sec.
Known failure modes

Leaving `isolation.level` at default `read_uncommitted` exposes downstream services to aborted zombie writes.

02 / Map the systemArchitecture & invariants

Separate concerns. Map the flow.

A Java EOS loop that ties output records and consumer offsets into a single Kafka transaction, aborting/seeking on transient errors and closing on `ProducerFencedException`.

  1. 01Epoch Bump & Fence: Coordinator bumps producer_epoch from 1 to 2 and aborts any open tx from Epoch 1.
  2. 02Zombie Write Rejected: Waking zombie attempts to flush with Epoch 1; broker rejects with ProducerFencedException.
  3. 03Atomic Output & Offset Commit: Replacement pod writes scored events and input offset atomically under Epoch 2.
  4. 04Advance Last Stable Offset: Transaction Coordinator writes ABORT marker for Epoch 1 and COMMIT marker for Epoch 2.
  5. 05read_committed Filtering: Downstream consumer discards aborted Epoch 1 bytes and delivers only committed Epoch 2 events.
Deterministic transactional.id + initTransactions() fences zombies at the broker, while read_committed hides aborted transactions.

The invariants

  • Configure deterministic transactional.id and enable.idempotence=true.
  • Call producer.initTransactions() once before polling.
  • Inside the poll loop: beginTransaction(), send(), sendOffsetsToTransaction(offsets, consumer.groupMetadata()), commitTransaction().
  • On ProducerFencedException, close immediately; on KafkaException, abort and reset consumer offsets.
03 / Trace the lifecycleKey decisions

Follow the execution path.

EOS v2 (`KIP-447`) uses one transactional producer per worker thread instead of per partition, reducing broker connection and memory overhead by 10-50x.

Step 1

EOS v1 required N_partitions producers per instance, creating thousands of open sockets and __transaction_state entries.

Step 2

EOS v2 passes consumer.groupMetadata() so the coordinator validates consumer generation IDs during sendOffsetsToTransaction.

JAVA · Lifecycle trace
// EOS v2: one deterministic transactional.id per static consumer instance
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "fraud-scorer-" + staticInstanceId);
props.put(ConsumerConfig.GROUP_INSTANCE_ID_CONFIG, staticInstanceId);
Key trade-off

EOS v2 drastically cuts broker memory and socket count; EOS v1 isolates a slow partition from delaying other partitions' commits.

04 / ImplementConfiguration & code

Build the safeguards.

Lower `transaction.timeout.ms` to `15000 ms` and enable static membership (`group.instance.id`) + `session.timeout.ms=10000` so stalled transactions abort quickly.

1. Reference implementation

JAVA · Solution
producer.initTransactions();
while (running) {
    ConsumerRecords<String, byte[]> records = consumer.poll(Duration.ofMillis(200));
    if (records.isEmpty()) continue;
    try {
        producer.beginTransaction();
        Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
        for (ConsumerRecord<String, byte[]> rec : records) {
            byte[] scored = scoreFraud(rec.value());
            producer.send(new ProducerRecord<>("payments.scored", rec.key(), scored));
            offsets.put(new TopicPartition(rec.topic(), rec.partition()), new OffsetAndMetadata(rec.offset() + 1));
        }
        producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());
        producer.commitTransaction();
    } catch (ProducerFencedException | OutOfOrderSequenceException | AuthorizationException fatal) {
        producer.close(Duration.ZERO);
        consumer.close();
        throw fatal;
    } catch (KafkaException transientEx) {
        producer.abortTransaction();
        resetToCommittedOffsets(consumer);
    }
}

2. Harden for scale

Lower `transaction.timeout.ms` to `15000 ms` and enable static membership (`group.instance.id`) + `session.timeout.ms=10000` so stalled transactions abort quickly.

JAVA · Scale hardening
props.put(ProducerConfig.TRANSACTION_TIMEOUT_MS_CONFIG, 15000);
props.put(ProducerConfig.DELIVERY_TIMEOUT_MS_CONFIG, 12000);
props.put(ConsumerConfig.MAX_POLL_INTERVAL_MS_CONFIG, 30000);

3. Operational controls

Step 1

Set `transaction.timeout.ms=15000` (must be `<= transaction.max.timeout.ms` on broker).

Step 2

Monitor `kafka_consumer_fetch_manager_records_lag_max` and `LSO - LEO` gap per partition.

Implementation note

Using `consumer.groupMetadata()` (KIP-447) simplifies single-producer EOS, while per-partition producers isolate LSO stalls.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Setting `transaction.timeout.ms` lower than `max.poll.interval.ms` if a batch takes 20s causes the broker to abort active healthy transactions.

Failure scenario 2

Assuming Kafka EOS protects external databases or HTTP webhooks leads to duplicates on consumer restarts.

Alternatives considered

  • Storing the Kafka offset directly inside the same PostgreSQL transaction as the fraud alert.
