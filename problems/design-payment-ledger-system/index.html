Full walkthrough · 2 stages
01
SYSTEM-DESIGN · STAGE 01L4 · FUNDAMENTALS

Clarify invariants, idempotency & scale.

Every payment state transition must be backed by immutable double-entry ledger rows (debit + credit summing to 0) inside ACID transactions. Clients send a UUID Idempotency-Key so mobile network retries never charge a card twice.

ChoiceWhat it buysWhat it costs
SQL ACID Ledger vs. NoSQLMulti-row atomic debit+credit in one transactionRequires shard-by-account-group past ~10K TPS

Insight 1

Never mutate a single balance column without an append-only ledger_entries audit trail.

Insight 2

Store idempotency_key with a unique constraint in PostgreSQL so duplicate retries return the original response.

02
SYSTEM-DESIGN · STAGE 02L5 · APPLIED DESIGN

Payment execution, PSP calls & Outbox.

Never hold a database transaction open while calling an external Payment Service Provider (Visa/Stripe). Instead, record PENDING locally, release the DB connection, call the PSP, and commit SETTLED + an outbox event for Kafka via the Transactional Outbox.

Insight 1

Lock accounts in sorted account_id order (SELECT ... FOR UPDATE) to eliminate deadlocks.

Insight 2

Run nightly three-way reconciliation comparing internal ledger, PSP settlement files, and bank statements.

PSP Timeout Ambiguity

PSP charges the card, but the HTTP response times out before reaching your server.
