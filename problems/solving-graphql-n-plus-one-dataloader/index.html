Solving GraphQL N+1
Queries with DataLoader.

01 / UnderstandFailure & constraints

Clarify what is failing.

Unbatched nested resolvers multiply calls at every list level: `1 + 50 + 200 + 200 = 451` calls/req * 60 RPS = 27,060 QPS.

Design objective

Enable GraphQL tracing / OpenTelemetry spans to count resolver invocations per request.

Requirements

  • Reduce backend calls for the 50-order nested query from **451** down to **<= 4** batched calls (1 per entity tier).
  • Prevent malicious or accidental deep-nested queries (e.g., `order -> items -> product -> seller -> orders -> ...`) from exhausting server CPU/DB.
  • Ensure `DataLoader` caches are strictly request-scoped so user A never sees user B's data or stale mutations.
  • Keep GraphQL Order History p99 latency under **120 ms** at 500 RPS.

Constraints

  • GraphQL Gateway runs on Java (`graphql-java` / Netflix DGS) or Node/Python.
  • Orders and Items live in PostgreSQL; Seller ratings live in `Seller-Service` (gRPC).
  • Cannot rewrite the mobile app immediately; old mobile clients must be supported cleanly.
Known failure modes

name: Connection Pool Exhaustion; description: 27,060 QPS exhausts PostgreSQL connections in seconds.; mitigation: Batch via DataLoader.

The invariants

  • Implement MappedBatchLoader<String, SellerDto>.
  • Set DataLoaderOptions.newOptions().setMaxBatchSize(100).
  • Add MaxQueryDepthInstrumentation(6) and MaxQueryComplexityInstrumentation(500).
03 / Trace the lifecycleKey decisions

Follow the execution path.

`BatchLoader` requires the returned `List<V>` to match the exact size and order of `List<K>`, whereas `MappedBatchLoader` keys by ID and safely returns `null` for missing sellers.

Step 1

Return Map<String, SellerDto> from batchGetSellers.

Step 2

Missing/deleted sellers resolve to null instead of shifting array indices.

PYTHON · Lifecycle trace
# Safe mapped lookup
sellers_by_id = {s.id: s for s in grpc_batch_get_sellers(list(set(keys)))}
return [sellers_by_id.get(k) for k in keys]
Key trade-off

factor: Map Alignment; pro: Zero index-shift corruption if a seller was deleted.; con: Negligible hash-map allocation.

04 / ImplementConfiguration & code

Build the safeguards.

Enforce hard `maxPageSize = 50` in input validation and multiply complexity by `first` (`5000 * 10 = 50,000 > 500`).

1. Reference implementation

JAVA · Solution
@Bean
public Instrumentation maxDepth() { return new MaxQueryDepthInstrumentation(6); }

@Bean
public Instrumentation maxComplexity() { return new MaxQueryComplexityInstrumentation(500); }

2. Harden for scale

Enforce hard `maxPageSize = 50` in input validation and multiply complexity by `first` (`5000 * 10 = 50,000 > 500`).

JAVA · Scale hardening
if (first > 50) {
    throw new IllegalArgumentException("Page size 'first' cannot exceed 50");
}

3. Operational controls

Step 1

Clamp or reject `first > 50` at schema/argument validation.

Step 2

Use a field-cost calculator that multiplies child cost by `first`.

Implementation note

factor: MappedBatchLoader vs. BatchLoader; pro: `MappedBatchLoader` handles missing IDs cleanly without positional alignment bugs.; con: Requires returning `Map<ID, Value>`.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Deploy Automatic Persisted Queries (APQ) first, collect all legacy query hashes for 30 days, seed them into the allowlist, then enforce strict allowlist.

  • ↗
    Enable APQ (hash -> query cached in Redis).
  • ↗
    Log all unpersisted queries from older app versions and add their hashes to the allowlist before flipping `allowArbitraryQueries = false`.
YAML · Verification
graphql:
  persistedQueries:
    mode: ALLOWLIST_ONLY
    redisCacheTtlSeconds: 86400
    legacyGracePeriodDays: 30

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
