The idea to keep with you

A multi-tenant e-commerce catalog cluster on Elasticsearch 8.11 (12 data nodes, 64 GB RAM / 31 GB JVM heap each, 20 primary shards with 1 replica) experiences 18-second G1GC stop-the-world pauses and HTTP 503 circuit-breaker rejections whenever scrapers or export jobs paginate past page 500 (`from=50000, size=100`). Redesign the pagination architecture, query limits, and client export path to eliminate coordinator OOMs and GC pauses while preserving deterministic ordering under concurrent writes.

01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why deep from+size pagination crashes Elasticsearch clusters.

In a 20-shard Elasticsearch 8.11 index (31 GB heap per data node, 400 updates/sec), from=50000, size=100 forces every shard to sort and return 50,100 tuples (20 * 50,100 = 1,002,000 entries) to the coordinator node just to discard 50,000 and return 100. That O(N * (from + size)) heap spike triggers 18-second G1GC pauses and HTTP 503 parent circuit-breaker trips.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens with deep from+size and unpinned refreshes.

Using from + size for deep pagination or scraping causes two severe production failures:

  1. Coordinator Heap Explosion: Deep pages allocate millions of sort-key objects, breaching indices.breaker.total.limit (95% heap) and stalling interactive 1,500 QPS search.
  2. Duplicate/Skipped Items: With a 1 s index refresh and 400 writes/sec, shifting ranks between page requests causes items to appear twice or vanish.
O(from+size) vs. O(size) Pagination

from=50000 Heap Storm vs. PIT + search_after Cursor

search_after with PIT bounds per-shard and coordinator memory to O(size) and freezes Lucene segment state.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive solution (and why Scroll API or raising max_result_window fails).

Two common workarounds backfire in production:

  • Raising index.max_result_window above 10,000: Removes the safety guardrail and lets scrapers OOM the cluster.
  • Legacy Scroll API: Holds heavy search contexts open on shards for interactive users and is deprecated in favor of PIT + search_after.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: PIT + search_after + Tie-Breaker + Guardrails.

Production Elasticsearch pagination enforces three rules:

  • Interactive Cap: Keep index.max_result_window: 10000 and reject deep page numbers with 400 Bad Request.
  • PIT + search_after: Open a lightweight Point-in-Time snapshot (_pit?keep_alive=2m) and pass the last hit's sort array (including a unique tie-breaker like _shard_doc or product_id) into search_after—bounding shard work to O(size) (20 * 100 = 2,000 tuples) and supporting backward navigation by reversing sort order.
  • Async Bulk Export: Route > 10,000-row catalog exports to an offline worker using PIT + search_after writing to S3.
Constant-Memory Cursor Seeking

Shard BKD/DocValues Seek via search_after Sort Tuple

1.PIT Handle: Pins segment state across pages so concurrent writes don't shift ranks.

2.O(size) Memory: Each shard returns only `size` hits after the cursor, never `from + size`.

3.Unique Tie-Breaker: Appending `_shard_doc` guarantees deterministic ordering on equal scores.

4.Breaker Guardrail: Keeping max_result_window=10000 protects interactive 180ms P99 SLA.

Seeking past the last sort tuple inside a frozen PIT snapshot eliminates coordinator OOMs and duplicate/skipped hits.

// 1. Open lightweight Point-in-Time snapshot
// POST /catalog/_pit?keep_alive=2m -> { "id": "46ToAwMDa..." }

// 2. Paginate forward with O(size) memory & deterministic tie-breaker
{
  "size": 100,
  "pit": { "id": "46ToAwMDa...", "keep_alive": "2m" },
  "query": { "match": { "category": "electronics" } },
  "sort": [
    { "popularity": "desc" },
    { "_shard_doc": "asc" }
  ],
  "search_after": [94.5, 184320]
}
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Cursor / search_after Pagination applies in System Design.

Keyset / cursor pagination replaces offset pagination across all distributed data systems:

  • E-Commerce Search & Faceting: Infinite scroll and deep catalog feeds without coordinator GC pauses.
  • SQL Keyset Pagination: Replacing OFFSET 50000 in Postgres/MySQL with WHERE (created_at, id) < ($1, $2).
  • Bulk Data Exports: Streaming millions of records to S3/CSV via PIT cursors.
