Design a URL Shortener

Design a URL shortening service similar to bit.ly or TinyURL. Users submit a long URL and receive a short alias (e.g., https://short.ly/aB3xY). When a user visits the short URL, the service redirects them to the original. The service must handle high read traffic, provide low-latency redirects, and allow optional analytics per short URL.

Scope, Requirements & Constraints

Core requirements: generate short alias → store mapping → resolve + redirect. Key constraints: 100M writes/day ≈ 1,160 writes/sec; 100:1 read ratio ≈ 116,000 reads/sec; 62^7 alias space; p99 redirect < 10 ms. Out of scope for base design: per-user authentication, abuse prevention, real-time analytics dashboards.

Core Functional Requirements

  • ✓Given a long URL, generate a unique short alias and return it to the user.
  • ✓Given a short alias, resolve and redirect to the original URL with low latency.
  • ✓Short aliases must be unique and collision-resistant.
  • ✓Optionally support custom aliases chosen by the user.
  • ✓Optionally record click count and basic analytics per short URL.
  • ✓Short URLs should not expire by default; expiry is an optional configuration.

Scale & Latency Constraints

  • —Write volume: ~100 million new URLs per day (assume 100:1 read-to-write ratio).
  • —Redirect p99 latency target: under 10 ms.
  • —Alias length: 7 characters (default) using [a-z, A-Z, 0-9] — 62^7 ≈ 3.5 trillion combinations.
  • —Data retention: indefinite unless expiry is explicitly set.
  • —Assume globally distributed read traffic, writes concentrated in a few regions.

Reference Architecture & System Blueprint

Two-tier architecture: an ID generation service produces 7-character Base-62 aliases; a write path stores the mapping (shortId → longUrl, metadata) in a distributed KV store (e.g., DynamoDB or Cassandra); a read path resolves aliases via an in-memory cache (Redis) in front of the KV store and returns an HTTP 301/302 redirect.

URL Shortener Dual-Path Architecture

Separation of concerns between the high-throughput write path (ID generation) and the ultra-low latency read path (cache-aside).

System Architecture & Theory

Architectural Overview & Separation of Concerns

A modern URL shortening architecture decouples the high-throughput write path (~1,160 writes/sec peak) from the ultra-low latency read path (~116,000 reads/sec at a 100:1 read-to-write ratio). Rather than overwhelming a single relational database with point-lookup scans, write operations are isolated into atomic ID allocation and durable key-value writes, while read traffic is terminated at the edge and absorbed by an in-memory cache-aside cluster.

Write Path Mechanics (Ingestion to Persistence)
1. Ingress & Gatekeeping: The client issues `POST /shorten` with the original URL. The API Gateway terminates TLS, validates URI structure, and enforces rate limits via Redis Token Bucket to prevent scraping abuse. 2. Monotonic ID Allocation: The gateway routes to stateless ID Generator nodes. Range-based counter partitioning (e.g., node 1 allocates ranges 1–1,000,000 via ZooKeeper/etcd leasing) eliminates coordination bottlenecks and database collision retry loops. 3. Base-62 String Encoding: The counter is translated into a 7-character Base-62 string ([a-zA-Z0-9]). With $62^7 \approx 3.52 \times 10^{12}$ combinations, the namespace supports ~95 years of continuous writes at 100M/day. 4. Primary Persistence: The record `{ shortId: PK, longUrl, createdAt, userId }` is written to a distributed KV store (Cassandra/DynamoDB) sharded by `hash(shortId)`.
Read Path & High-Velocity Redirect Tier
1. Geographically Distributed Ingress: A user clicks `https://short.ly/{shortAlias}`. Anycast DNS routes the query to the nearest Edge CDN POP. 2. In-Memory Cache Tier: The gateway checks Redis. As short link traffic follows the Pareto 80/20 power law, keeping the hot 20% of links in Redis absorbs over 95% of aggregate read traffic with p99 latency < 2ms. 3. Cache Miss Resolution: Cold misses query Cassandra/DynamoDB by partition key, return the original URL, and populate Redis asynchronously with a sliding TTL (7–30 days). 4. Redirect Dispatch: The client receives `HTTP 301 (Moved Permanently)` if client-side browser caching is prioritized, or `HTTP 302 (Found)` if per-click telemetry and real-time geo-attribution are required.
Data Model & Storage Internals
Wide-column / NoSQL key-value storage is preferred over relational systems because point lookups require $O(1)$ partition-key access without cross-table joins. Primary Key: `shortId` (Hash Partition Key), ensuring even distribution across storage clusters without hot shards.
Scale Bottlenecks, Operational Hazards & Failure Modes
1. Thundering Herd Mitigation: When viral links expire from Redis, thousands of parallel readers simultaneously fall through to the database. We employ probabilistic early expiration (XFetch algorithm) or single-flight distributed mutex locks in Redis to ensure only one worker repopulates the cache while others read cached stale values. 2. ID Namespace Expansion: If the 7-character capacity threshold (70% utilization) is reached, alias length automatically expands to 8 characters ($62^8 \approx 218 \text{ trillion permutations}$). 3. Multi-Region Replication: Asynchronous cross-region replication with Last-Write-Wins (LWW) conflict resolution provides high availability during regional data center outages.
⚡ Architectural Invariant

Cache-aside with Redis in front of a sharded KV store keeps read latency under 10ms for 116k QPS while Base-62 counters prevent hash collision loops.

Hardened Implementation Steps

  1. 1Client submits POST /shorten with the long URL.
  2. 2API layer validates and rate-limits the request.
  3. 3ID Generator creates a unique 7-char Base-62 alias (using a counter with Base-62 encoding or a hash-then-truncate strategy).
  4. 4Write the mapping {shortId → longUrl, createdAt, userId?} to the KV store. Check uniqueness before committing.
  5. 5Return the full short URL (https://short.ly/{alias}) to the client.
  6. 6For redirect: client GET /alias → API checks Redis cache → on miss, reads KV store → returns 301 (permanent) or 302 (trackable) redirect.
  7. 7Cache the mapping in Redis on first read (TTL-based). Hot URLs stay in cache indefinitely under TTL.

Key Decisions & Trade-Off Analysis

Architectural Decisions & Trade-Offs

  • ⚖301 (Permanent): Browser caches the redirect, reducing repeat load on the service. Cost: no click analytics on cached requests. Use when analytics are not needed.
  • ⚖302 (Temporary/Found): Every visit hits the service, enabling click counting. Cost: higher server load for popular links. Use when analytics are required.
  • ⚖Base-62 vs hash: Base-62 counter gives monotonically increasing, collision-free IDs at the cost of a coordination step. Hash-truncate is simpler but requires a collision retry mechanism.
  • ⚖Redis as redirect cache: Cold start adds one KV read per alias. Warm state handles virtually all read traffic without touching the persistent store — critical for the p99 < 10 ms target.
  • ⚖Custom aliases: Require a separate namespace to avoid collisions with generated IDs. Store in the same KV with a reserved prefix or a separate index.

Alternatives Evaluated

  • →Skip caching (Redis) and read from KV directly: feasible for DynamoDB with sub-ms reads in the same region, but adds cross-region latency. Cache is recommended for global traffic.
  • →Relational DB (Postgres) instead of KV: simpler query model and transactional custom-alias uniqueness checks. Bottleneck at 116,000 reads/sec requires read replicas + aggressive caching.

Scale Bottlenecks & Operational Hazards

Operational Hazards & Mitigations

  • ⚠Hot/viral link: Single alias generates millions of cache reads. Redis handles this as a single key — but if that key evicts or Redis restarts, the KV store absorbs a thundering herd. Mitigation: never evict hot keys (LFU eviction policy + keep TTL long for popular links); use probabilistic early refresh.
  • ⚠ID space exhaustion: 62^7 ≈ 3.5 trillion — at 100M/day it takes ~95 years. Non-issue for MVP. Future: extend alias length to 8 chars (62^8 ≈ 218 trillion).
  • ⚠ID generator failure: If using a centralized counter, a single-node failure stops ID generation. Mitigation: replicate the counter with leader election (Zookeeper/etcd) or switch to a distributed range-based scheme.
  • ⚠Cache failure (Redis down): All redirects fall back to KV reads. At 116K reads/sec this can overwhelm KV. Mitigation: circuit breaker on the cache client; read replicas on the KV store; multi-layer edge cache (CDN) for the most popular links.
  • ⚠Regional outage: Cross-region replication of the KV store with eventual consistency. Reads from the nearest region. Writes: accept last-write-wins for duplicate short alias creation across regions (acceptable given the collision probability is extremely low).

Changed Constraints & System Extension

Changed constraint: the product team now requires real-time click analytics — total clicks, unique visitors (by IP hash), and referrer breakdown — accessible within 5 seconds of a click. How does this change your design? What new components do you introduce and what trade-offs arise?

Extension Implementation Steps

  1. 1On each redirect request, publish a lightweight click event (shortId, timestamp, ipHash, referrer) to a Kafka topic asynchronously — do NOT block the redirect path.
  2. 2A Flink or Kafka Streams job aggregates events over 5-second tumbling windows and writes counts to a time-series store (ClickHouse, DynamoDB with TTL, or Redis sorted sets).
  3. 3An Analytics API reads from the aggregated store and serves dashboards.
  4. 4To track unique visitors without storing PII, use HyperLogLog (Redis) for approximate cardinality — accurate to within 1% error.

Follow-Up Trade-Offs

  • ⚖Async event emission on the redirect path: keeps redirect latency unaffected but risks losing click events if Kafka is unavailable. Accept at-least-once delivery with deduplication downstream.
  • ⚖Real-time window vs batch: 5-second windows require streaming infrastructure. Hourly batch (simpler) would not meet the requirement.
  • ⚖HyperLogLog for unique visitors: ~1% error is acceptable for analytics; exact counts require storing user identifiers, raising privacy concerns.
