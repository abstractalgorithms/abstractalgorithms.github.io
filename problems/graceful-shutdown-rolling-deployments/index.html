01 / UnderstandFailure & constraints

Clarify what is failing.

Kubernetes triggers EndpointSlice removal and container SIGTERM concurrently. Because the JVM closes port 8080 in ~15 ms while Envoy/kube-proxy take 2-8s to update routing tables, thousands of requests hit a closed socket.

Design objective

Trace t=0: Pod enters Terminating state.

Requirements

  • Achieve zero dropped in-flight HTTP/gRPC requests during rolling updates at 20,000 RPS.
  • Ensure load balancers (ALB, Envoy, kube-proxy) stop sending new requests before the pod stops accepting connections.
  • Drain long-running in-flight requests (up to 25 seconds) cleanly without prematurely closing keep-alive connections.
  • Guarantee deployment rollout velocity remains bounded without stalling CI/CD pipelines.

Constraints

  • Maximum allowed request duration is 25 seconds; pod terminationGracePeriodSeconds cannot exceed 45 seconds.
  • Application runs on Spring Boot 3 / Java 21 behind Kubernetes Ingress (Envoy) and AWS ALB.
  • Must handle both HTTP/1.1 keep-alive connection reuse and HTTP/2/gRPC multiplexed streams.
Known failure modes

17,500+ dropped requests per deployment wave at 20,000 RPS. · TCP RSTs on reused HTTP/1.1 keep-alive connections.

Active Tx Completion

  1. 01Remove Pod IP: Control plane marks pod Terminating; Envoy/ALB stop routing new requests within 2-8s.
  2. 02Synchronous 10s Wait: Kubelet runs preStop (sleep 10) BEFORE sending SIGTERM; pod continues serving straggler requests.
  3. 03Absorb Propagation Lag: Requests routed during the 2-8s propagation window succeed normally on the still-listening pod.
  4. 04Start Graceful Drain: Spring Boot stops accepting new connections, sends HTTP/2 GOAWAY, and waits up to 30s for active work.
  5. 05Clean Exit (t<=40s): Active requests complete DB commits and return 200 OK before JVM exits cleanly ahead of 45s SIGKILL.
Decoupling EndpointSlice propagation (preStop 10s) from socket closure (SIGTERM 30s drain) eliminates the 502 race window.

The invariants

  • Set strategy.rollingUpdate.maxUnavailable=0 and maxSurge=25%.
  • Add preStop sleep 10 and terminationGracePeriodSeconds: 45.
  • Enable server.shutdown=graceful and set timeout-per-shutdown-phase=30s.
03 / Trace the lifecycleKey decisions

Follow the execution path.

If the server closes an idle HTTP/1.1 connection before the ALB/Envoy does, the proxy may dispatch a request into a closing socket causing a 502. Setting server idle timeout to 65s (>60s ALB) ensures the proxy closes first.

Step 1

Check upstream ALB/Envoy idle_timeout (typically 60s).

Step 2

Configure Spring Boot Tomcat/Netty keepAliveTimeout to 65s.

Step 3

Verify HTTP/2 server sends GOAWAY on SIGTERM so Envoy opens new streams on healthy pods.

YAML · Lifecycle trace
# application.yaml (Spring Boot 3)
server:
  shutdown: graceful
  tomcat:
    keep-alive-timeout: 65s
    max-keep-alive-requests: 10000
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
management:
  endpoint:
    health:
      probes:
        enabled: true
Key trade-off

Longer server keep-alive (65s) holds slightly more file descriptors per pod.

04 / ImplementConfiguration & code

Build the safeguards.

Long-lived WebSocket/SSE streams will be force-closed at 45s unless the application handles SIGTERM by sending a reconnect/close frame with jittered backoff.

1. Reference implementation

YAML · Solution
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-gateway
spec:
  replicas: 40
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 25%
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: payment-gateway
          image: registry.internal/payment-gateway:2.4.1
          ports:
            - containerPort: 8080
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 10"]
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            periodSeconds: 5
            failureThreshold: 2

2. Harden for scale

Long-lived WebSocket/SSE streams will be force-closed at 45s unless the application handles SIGTERM by sending a reconnect/close frame with jittered backoff.

JAVA · Scale hardening
@Component
public class GracefulWebSocketDrainer implements ApplicationListener<ContextClosedEvent> {
    private final SessionRegistry sessionRegistry;

    public GracefulWebSocketDrainer(SessionRegistry sessionRegistry) {
        this.sessionRegistry = sessionRegistry;
    }

    @Override
    public void onApplicationEvent(ContextClosedEvent event) {
        // Instruct clients to reconnect to healthy surge pods with jitter
        sessionRegistry.activeSessions().forEach(session -> 
            session.closeQuietly(CloseStatus.SERVICE_RESTARTED));
    }
}

3. Operational controls

Step 1

Listen for ContextClosedEvent in Java to notify active WebSocket/SSE clients.

Step 2

Send WebSocket CloseStatus.SERVICE_RESTARTED (1012) so clients reconnect with 1-5s jitter.

Step 3

Cap non-streaming HTTP requests with a 25s server timeout.

Implementation note

maxSurge: 25% requires 10 extra pods worth of cluster capacity during rollouts.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Longer server keep-alive (65s) holds slightly more file descriptors per pod.—
Option 2HTTP/2 multiplexing avoids keep-alive races via GOAWAY but requires TLS/ALPN or h2c between Envoy and pod.—
Option 3Separate stateless REST pods from stateful WebSocket gateway pods.—
Option 4Use NATS/Redis Streams to replay missed messages after client reconnect.—

Review questions

Failure scenario 1

Reconnection storm if all 50,000 WebSocket clients reconnect simultaneously without jitter.

Failure scenario 2

Kubelet SIGKILL leaving half-open TCP sockets on clients without TCP keepalive.

Failure scenario 3

PDB deadlock if replicas=1 and minAvailable=1.

Failure scenario 4

Spot instance 2-minute interruption notice bypassing normal PDB if node-termination-handler is missing.

Alternatives considered

  • Use maxUnavailable: 1 for ultra-critical small deployments (<10 replicas).
  • Schedule node drains during off-peak hours via Karpenter Disruption Budgets.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Kubernetes sends SIGTERM to the container in parallel with removing the pod from EndpointSlices; without a preStop delay, the app closes its listening socket before load balancers stop routing traffic to it.
  • 02Trade-off tip: Longer server keep-alive (65s) holds slightly more file descriptors per pod.
  • 03Trade-off tip: HTTP/2 multiplexing avoids keep-alive races via GOAWAY but requires TLS/ALPN or h2c between Envoy and pod.
  • 04Watch out for: Reconnection storm if all 50,000 WebSocket clients reconnect simultaneously without jitter.
  • 05Watch out for: Kubelet SIGKILL leaving half-open TCP sockets on clients without TCP keepalive.
