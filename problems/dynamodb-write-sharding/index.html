DynamoDB provisions capacity across physical partitions, but each individual physical partition is hard-capped at 1,000 WCU/sec, 3,000 RCU/sec, and 10 GB. When PK = MERCHANT#<merchant_id> receives 3,500 writes/sec (3,500 WCU) and 12,000 reads/sec (12,000 RCU) for one celebrity merchant, that single partition throttles with ProvisionedThroughputExceededException even though the table's 10,000 WCU total is only 12% utilized.

What happens without write sharding and read caching.

Why this matters: The problem: see what breaks without What happens without write sharding and read caching under real concurrency or scale.

Leaving a skewed PK = MERCHANT#<id> unsharded triggers three cascading failures:

  1. Hard Partition Throttling: 3,500 WCU > 1,000 WCU ceiling drops ~71% of writes.
  2. SDK Retry Amplification: Default exponential retries pile up on the same hot partition, turning a spike into a sustained outage.
  3. Adaptive Capacity Limits: Even DynamoDB adaptive capacity cannot exceed the 1,000 WCU single-partition physical ceiling.

STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Adaptive Write Sharding + Scatter-Gather Top-50 + Cache.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Production DynamoDB architectures combine three patterns:

  • Adaptive Write Sharding: Lookup shard_count in a cached config (N=1 for normal merchants, N=8 or 16 for celebrity merchants). Writers pick suffix = random(0, N-1) -> PK = MERCHANT#<id>#<suffix>, keeping each partition around ~625 WCU at 5,000 WCU total.
  • Parallel Scatter-Gather Top-50: To fetch the latest 50 transactions (SK = TX#<ts>#<tx_id>), issue N async Query(..., ScanIndexForward=False, Limit=50) calls and k-way merge the top 50 in < 25 ms p95.
  • Read Cache + Bounded Retries: Serve 25,000 reads/sec from DAX/Redis (5–10 s TTL) and cap SDK retries with jitter + circuit breaker.
Sharded Write & Cached Read Path

Adaptive Suffix Writer + Redis/DAX Cache + N-Shard Scatter-Gather

1.Adaptive Suffix: Normal merchants use N=1; celebrity merchants scale to N=8..16.

2.Scatter-Gather: Queries N shards in parallel with Limit=50 and heap-merges top 50.

3.DAX / Redis: Absorbs 25,000 reads/sec well below the 3,000 RCU/partition ceiling.

4.Contributor Insights: Detects emerging hot keys early to bump N before throttling.

Adaptive sharding + DAX/Redis caching sustains 5k WCU and 25k RCU for a single merchant without over-sharding small tenants.

import random, asyncio
from heapq import merge

SHARD_MAP = {"celebrity_m1": 8}  # loaded from dynamic config / Redis

def write_tx(ddb, merchant_id: str, ts_iso: str, tx_id: str, payload: dict):
    n_shards = SHARD_MAP.get(merchant_id, 1)
    suffix = random.randrange(n_shards)
    pk = f"MERCHANT#{merchant_id}#{suffix}"
    ddb.put_item(Item={"PK": pk, "SK": f"TX#{ts_iso}#{tx_id}", **payload})

async def get_recent_50(async_ddb, merchant_id: str):
    n_shards = SHARD_MAP.get(merchant_id, 1)
    tasks = [
        async_ddb.query(
            KeyConditionExpression="PK = :pk",
            ExpressionAttributeValues={":pk": f"MERCHANT#{merchant_id}#{i}"},
            ScanIndexForward=False,
            Limit=50,
        )
        for i in range(n_shards)
    ]
    pages = await asyncio.gather(*tasks)
    merged = merge(*(p["Items"] for p in pages), key=lambda x: x["SK"], reverse=True)
    return list(merged)[:50]

Where Write Sharding & Scatter-Gather apply in System Design.

Why this matters: Scope boundary: identify where this pattern fits best and where simpler or async alternatives win.

Write sharding with bounded scatter-gather is the standard remedy for single-key hotspots:

  • Payment Ledgers & Flash-Sale Counters: Distributing celebrity merchant or viral SKU writes across N partitions.
  • IoT & Telemetry Ingestion: Sharding high-volume device/fleet IDs by device_id#bucket.
  • Social Celebrity Timelines: Splitting mega-influencer fanout or engagement counters across K shards.
