01 / UnderstandFailure & constraints

Clarify what is failing.

Redis Cluster partitions keys across 16,384 slots using CRC16(key) & 16383; keys without matching hash tags land on different slots and different primaries.

Design objective

Compute how CRC16 hashes `user:1042:balance` vs `user:1042:nonce` to different slots.

Requirements

  • Guarantee single-round-trip Lua atomicity for per-user multi-key mutations (`balance`, `ledger`, `nonce`).
  • Support 50-key cross-user `MGET`/`MSET` batch reads without `CROSSSLOT` errors.
  • Keep batch read p99 latency under 2ms (versus 25ms for 50 sequential RTTs).
  • Prevent hot-shard skew so no single primary receives > 40% of cluster traffic.

Constraints

  • Cluster has 3 primaries owning slots 0-5460, 5461-10922, and 10923-16383 using CRC16(key) & 16383.
  • Redis Cluster strictly forbids multi-key commands (MGET, DEL, MULTI/EXEC, EVAL) whose keys map to different hash slots.
  • Inter-node/client RTT is 0.5ms.
Known failure modes

Silent runtime CROSSSLOT exceptions in production if not tested against a multi-shard cluster.

  1. 01Hash tag colocates per-user keys: All three keys share {user:1042}, hashing to slot 4120 on Primary 1 so Lua executes atomically.
  2. 02Scatter-gather splits 50-key MGET: Client computes CRC16 for all 50 keys and groups Primary 1's 17 keys into a single pipeline.
  3. 03Parallel pipeline to Primary 2: Client concurrently dispatches Primary 2's 16 keys without triggering CROSSSLOT.
  4. 04Parallel pipeline to Primary 3: Client concurrently dispatches Primary 3's 17 keys in the same 0.5ms network window.
  5. 05Reassemble in original key order: Client merges the 3 shard responses back into the caller's 50-element list in <1ms.
Entity-level {hash_tags} enable single-slot Lua atomicity, while client-side slot grouping executes 50-key MGETs in 1 parallel RTT.

The invariants

  • Format per-user keys as {user:<id>}:balance, {user:<id>}:ledger, {user:<id>}:nonce.
  • Compute slot for each key in batch MGET and map to its primary node.
  • Execute one pipeline per primary concurrently and reassemble results in input order.
03 / Trace the lifecycleKey decisions

Follow the execution path.

A single primary owns 5,461 slots; `MGET` on two keys in different slots on the *same* primary still fails with CROSSSLOT.

Step 1

Verify that CROSSSLOT is enforced at the slot level, not the physical node level.

Step 2

Confirm that pipelining GET k1, GET k2, ..., GET k17 in one TCP write gives 1-RTT batching with zero CROSSSLOT risk.

04 / ImplementConfiguration & code

Build the safeguards.

Primary 1 returns `-MOVED 4120 <Primary2_IP>` for that key in the pipeline; the client refreshes its slot map and retries only the redirected keys.

1. Reference implementation

PYTHON · Solution
import binascii
from collections import defaultdict
from concurrent.futures import ThreadPoolExecutor
from typing import Dict, List, Optional

def user_keys(user_id: int) -> tuple[str, str, str]:
    tag = f"{{user:{user_id}}}"
    return f"{tag}:balance", f"{tag}:ledger", f"{tag}:nonce"

def compute_slot(key: str) -> int:
    s = key.find("{")
    if s != -1:
        e = key.find("}", s + 1)
        if e != -1 and e > s + 1:
            key = key[s + 1:e]
    return binascii.crc_hqx(key.encode("utf-8"), 0) & 16383

def scatter_gather_mget(cluster_nodes: Dict[str, object], slot_to_node: Dict[int, str], keys: List[str]) -> List[Optional[str]]:
    grouped: Dict[str, List[tuple[int, str]]] = defaultdict(list)
    for idx, k in enumerate(keys):
        node_id = slot_to_node[compute_slot(k)]
        grouped[node_id].append((idx, k))

    results: List[Optional[str]] = [None] * len(keys)

    def fetch_node(node_id: str, items: List[tuple[int, str]]):
        pipe = cluster_nodes[node_id].pipeline(transaction=False)
        for _, k in items:
            pipe.get(k)
        vals = pipe.execute()
        return [(idx, val) for (idx, _), val in zip(items, vals)]

    with ThreadPoolExecutor(max_workers=len(grouped)) as pool:
        futures = [pool.submit(fetch_node, nid, items) for nid, items in grouped.items()]
        for fut in futures:
            for idx, val in fut.result():
                results[idx] = val
    return results

2. Harden for scale

Primary 1 returns `-MOVED 4120 <Primary2_IP>` for that key in the pipeline; the client refreshes its slot map and retries only the redirected keys.

# Retry only keys whose pipeline slot returned MOVED/ASK rather than re-fetching all 50 keys

3. Operational controls

Step 1

Inspect per-command errors inside the pipeline response array.

Step 2

Trigger a single-flight CLUSTER SHARDS refresh on -MOVED.

Step 3

Retry only the keys that received -MOVED or -ASK.

Implementation note

3 parallel pipelines complete in ~0.9ms vs 25ms sequential.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Execute the authoritative atomic debit/credit in a transactional database (Postgres/Spanner) and project balances to Redis via CDC/outbox, or use a two-phase idempotent Saga.

  • ↗
    Perform `UPDATE accounts ...` atomically in the primary RDBMS.
  • ↗
    Emit an outbox/CDC event to update `{user:1042}:balance` and `{user:2099}:balance` in Redis.
  • ↗
    Use versioned `SET` (Lua `if new_ver > cur_ver`) so out-of-order CDC updates never regress balances.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Unbounded retry loops if a cluster is in `CLUSTERDOWN` state.

Failure scenario 2

Out-of-order CDC delivery overwriting a newer balance if version checks are omitted.

Alternatives considered

  • Two-phase reservation keys in Redis with TTL rollback (complex edge cases on crash).

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Colocate strictly atomic entity keys on one slot using {hash_tags} (e.g., {user:1042}:balance), and replace cross-entity MGET/MSET with slot-grouped parallel scatter-gather pipelines.
  • 02Trade-off tip: Pipelined GETs use slightly more framing bytes than a single MGET but are 100% slot-safe.
  • 03Watch out for: Unbounded retry loops if a cluster is in CLUSTERDOWN state.
