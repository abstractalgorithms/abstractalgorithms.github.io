01 / UnderstandFailure & constraints

Clarify what is failing.

Under PACELC's `Else` branch, linearizable reads must contact the Raft leaseholder (often in `us-east-1`) to guarantee no newer write committed, incurring full cross-continent RTT.

Design objective

Contrast CAP (partition-only) with PACELC (normal-operation Latency vs. Consistency).

Requirements

  • Bring `ap-south-1` and `eu-west-1` read p99 latency under 25ms during normal operation.
  • Preserve strict serializability / linearizability for wallet debits and inventory deductions.
  • Reduce cross-region write RTT for regional user sessions and orders without losing durability.
  • Eliminate leader-lease round trips for read-heavy catalog and user-profile queries.

Constraints

  • Inter-region RTTs are physically bounded by speed of light: US-EU 75ms, EU-IN 130ms, US-IN 195ms.
  • All 3 regions must remain active-active for user traffic.
  • Catalog reads are 95% of total QPS (60,000 RPS); ledger/inventory writes are 5% (3,000 RPS).
Known failure modes

Holding thousands of worker threads open waiting on cross-region RTT.

  1. 01Bounded-Staleness Follower Read: 95% read traffic hits the local Mumbai replica at a closed timestamp 5s in the past (<4ms).
  2. 02Regional Leaseholder Write: Indian user orders are homed to an ap-south-1 Raft leaseholder.
  3. 03Nearest-Neighbor Quorum: Mumbai replicates to Frankfurt (130ms) or local AZs for 2-of-3 quorum without waiting on Virginia (195ms).
  4. 04Strict PC/EC Path: Only global shared-inventory mutations pay cross-region quorum RTT.
  5. 05Read-Your-Writes Bypass: Write returns an HLC timestamp; subsequent user reads bypass follower-read for 5s.
Separating PA/EL follower reads from homed PC/EC writes cuts 95% of traffic from 195ms to <5ms without sacrificing ledger correctness.

03 / Trace the lifecycleKey decisions

Follow the execution path.

`ZONE FAILURE` puts all voting replicas in one region for <10ms writes but cannot survive a full region outage; `REGION FAILURE` spreads voters across regions, paying cross-region RTT on writes.

Step 1

Compare write RTT (<10ms vs. 130ms) and RPO/RTO during a full AWS region failure.

Step 2

Choose REGION FAILURE for financial ledgers and ZONE FAILURE (or async DR) for replaceable session state.

Key trade-off

Surviving a region failure requires at least 2 of 3 voting replicas in separate regions, imposing one inter-region RTT on every commit.

04 / ImplementConfiguration & code

Build the safeguards.

Under `P`, `PA/EL` catalog follower reads in `ap-south-1` continue serving 100% of reads locally, while `PC/EC` global inventory writes fail fast (unavailable) because `ap-south-1` cannot form a 2-of-3 quorum.

1. Reference implementation

PYTHON · Solution
import time

FOLLOWER_STALENESS_SEC = 5.0

def fetch_user_profile(db, user_id: str, last_write_ts: float | None):
    # Preserve read-your-own-writes for 5s after a mutation
    if last_write_ts and (time.time() - last_write_ts) < FOLLOWER_STALENESS_SEC:
        return db.query_one(
            "SELECT user_id, address FROM users WHERE user_id = %s", (user_id,)
        )
    # Otherwise use PA/EL local follower read (<5ms)
    return db.query_one(
        "SELECT user_id, address FROM users AS OF SYSTEM TIME follower_read_timestamp() WHERE user_id = %s",
        (user_id,),
    )

PYTHON · Scale hardening
# Graceful degradation during partition: allow browsing, queue or reject checkout cleanly
def checkout_with_partition_guard(db, sku_id: str, timeout_ms: int = 800):
    try:
        return db.execute_with_timeout("UPDATE inventory SET qty = qty - 1 WHERE sku_id = %s", (sku_id,), timeout_ms)
    except TimeoutError:
        raise ServiceUnavailable("Checkout temporarily paused in your region during network partition")

3. Operational controls

Step 1

Trace catalog reads: local replica serves closed-timestamp snapshots without needing quorum.

Step 2

Trace global inventory writes: Raft blocks/times out to prevent split-brain overselling.

Implementation note

Users see <5ms reads 99% of the time while paying a single leaseholder RTT only within 5s of their own edits.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Know what each control buys.

Review questions

Failure scenario 1

No client timeout on partitioned writes causes API thread pool exhaustion.

Failure scenario 2

Fragmented stock leaves 50 units stranded in `eu-west-1` while `ap-south-1` shows sold out if the rebalancer lags.

Alternatives considered

  • Accept 130ms checkout RTT for the 5% write path since users tolerate 200ms on 'Place Order' clicks.
