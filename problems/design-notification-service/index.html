Design a Scalable
Notification Service.

Design a notification service for a social media platform. The service must deliver notifications to users via push (mobile), email, and in-app channels. Notifications are triggered by user events (likes, comments, follows, mentions). The system must be reliable, handle notification preferences, and avoid spamming users.

R

Define the boundaries.

Requirements · 4 minutes
SAY THIS: “Before proposing a topology for Design a Scalable Notification Service, I’ll clarify the core functional requirements, burst characteristics, data volume, and availability SLOs to define rigid system boundaries.”
Main challenges: (1) Fanout — a single event (e.g., a post from a celebrity with 10M followers) generates millions of push notifications. (2) Preference filtering — each recipient has different opt-in/opt-out settings. (3) Reliability — ensure delivery even if a channel (push) is temporarily down. (4) Batching/rate limiting — avoid overwhelming users with dozens of individual notifications.

What the system does

  • Deliver notifications via push (APNs/FCM), email (SMTP/SES), and in-app channels.
  • Respect per-user notification preferences (enabled/disabled per type and channel).
  • Deduplicate: do not send duplicate notifications for the same event within a time window.
  • Batch low-priority notifications (e.g., group 5 likes into one notification).
  • Prioritize: deliver time-sensitive notifications (e.g., DM, security alert) with low latency.

What to agree on

  • 10 million daily active users; peak: 500,000 notification events/second.
  • Push delivery p99 < 5 seconds after event; email < 1 minute.
  • In-app notifications must be queryable (paginated history per user).
  • At-least-once delivery guarantee; tolerate duplicate delivery if deduplicated at receiver.
  • Support notification expiry (e.g., a 'like' notification older than 24 hours is stale).

S

Keep state shared and partitioned.

Storage · 3 minutes
SAY THIS: “I’ll separate low-latency ephemeral cache state from authoritative durable storage, ensuring strict consistency where needed and partitioning for scale.”

Cache / Ephemeral state

state:{partitionKey}:activeWindow

  • In-memory key-value cache (Redis Cluster / Memcached).
  • TTL expiration matching window validity bounds.
  • Hash tags to co-locate keys for atomic Lua scripts or transactions.

Durable / Authoritative store

  • Distributed NoSQL / relational database (DynamoDB, PostgreSQL).
  • Durable write-ahead log with replica failover.
  • Cache-aside pattern: read misses warm cache from durable store.
  • Asynchronous CDC / event streaming to telemetry sinks.

Local-only node state is not a shared cluster quota: N nodes could admit roughly N × the configured limits. Ensure state co-location and transactional boundaries align with partition keys.

D

Make state mutations atomic.

Detailed design · 7 minutes
SAY THIS: “For the critical execution path, we enforce idempotency and concurrency controls using atomic primitives, avoiding lock contention and split-brain states.”
  1. Platform emits a domain event (e.g., UserLikedPost{postId, actorId, recipientId}) to Kafka.
  2. Notification Service consumes the event: fetch recipient preferences from a low-latency cache (Redis); if the channel is disabled or event type is muted, drop the event.
  3. Deduplication: check a Redis set {recipientId}:{eventType}:{entityId}:{windowHash} with TTL = dedup window (e.g., 1 hour). If key exists, drop; else SET NX and continue.
  4. Batching worker: for low-priority types (likes, follows), accumulate events in a Redis sorted set by recipient, flush every 30 seconds, send a single batched notification.
  5. Fanout: for high-priority (DM, security), route directly to the channel worker queue.
  6. Channel workers: push worker calls APNs/FCM; email worker calls SES; in-app worker writes to a notifications table (sharded by userId) and updates a Redis badge counter.
  7. Delivery failure: retry with exponential backoff; after max retries, write to a dead-letter queue for audit.

TYPESCRIPT · REFERENCE IMPLEMENTATION
// Multi-Channel Notification Dispatcher with Deduplication
export async function sendNotification(event: NotificationEvent): Promise<DispatchResult> {
  // 1. Idempotency Check using Redis SETNX with 24h TTL
  const dedupKey = `dedup:notification:${event.idempotencyKey}`;
  const isNew = await redis.set(dedupKey, "LOCKED", "EX", 86400, "NX");
  if (!isNew) {
    return { status: "DUPLICATE_IGNORED", messageId: event.idempotencyKey };
  }

  // 2. Query User Notification Preferences
  const prefs = await userPreferenceService.get(event.userId);
  if (!prefs.channels[event.channel]) {
    return { status: "SUPPRESSED_BY_USER", messageId: event.idempotencyKey };
  }

  // 3. Publish to Channel-Specific Kafka / SQS Queue for Async Delivery
  const queueName = `notifications.${event.channel.toLowerCase()}`;
  await messageBroker.publish(queueName, {
    recipient: event.recipient,
    payload: event.payload,
    retryCount: 0,
    timestamp: Date.now()
  });

  return { status: "ENQUEUED", messageId: event.idempotencyKey };
}

Avoid client-side read-modify-write loops without concurrency control. Use atomic scripts, row-level locks, or conditional mutations at the storage tier to guarantee linearizability.

E

Stress-test the design.

Evaluation · 6 minutes
SAY THIS: “The biggest operational risks involve node failover, partition skew, network isolation, and cascading downstream backpressure. Here is how we mitigate each.”
Separate queues per channel

failures in email delivery do not block push delivery; scaling is independent.

Redis for preferences

avoids DB read on every notification event; stale preference cache (up to TTL) is acceptable — a user muting a notification type will stop receiving after the TTL expires.

Write fanout vs read fanout

Write fanout writes to each follower's queue immediately — O(followers) writes per post. Read fanout computes on read — O(followers) reads per inbox load. Write fanout is faster for notification delivery; read fanout is cheaper for celebrities (99% of followers never check their inbox).

Hybrid

use write fanout for regular users (<10K followers) and read fanout (or dedicated celebrity workers with throttled write) for high-follower accounts.

Celebrity fanout

5M push notifications in 5 seconds = 1M/sec. A single Kafka consumer + push worker cannot keep up. Solution: horizontal scaling of push workers; partition the notifications Kafka topic by userId hash so consumers can parallelize. Precompute follower lists for high-fan-out accounts.

APNs slow

push workers timeout waiting for APNs. Solution: set a short timeout (2 s); if APNs is slow, put undelivered notifications back in the queue with lower priority. Users will receive the push when APNs recovers.

APNs down

retry with exponential backoff up to the notification expiry TTL. After expiry, drop — stale notifications degrade UX more than missing ones.

In-app notification write surge

shard the notifications table by userId; use a write-behind cache (Redis) to absorb burst writes and flush to the DB asynchronously.

D

Close with the trade-offs.

Discussion · 5 minutes
SAY THIS: “In closing, we optimized for sub-millisecond p99 latency and high availability under partition. We trade strict distributed linearizability for predictable throughput and operational simplicity.”

If the interviewer asks…

  • Separate queues per channel: failures in email delivery do not block push delivery; scaling is independent.
  • Redis for preferences: avoids DB read on every notification event; stale preference cache (up to TTL) is acceptable — a user muting a notification type will stop receiving after the TTL expires.

Keep the conclusion focused

  • What guarantees are strictly enforced at runtime?
  • What happens during network partitions or node failures?
  • Which CAP trade-off was intentionally chosen and why?
