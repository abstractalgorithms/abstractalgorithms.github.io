Design a Notification Service

Design a notification service for a social media platform. The service must deliver notifications to users via push (mobile), email, and in-app channels. Notifications are triggered by user events (likes, comments, follows, mentions). The system must be reliable, handle notification preferences, and avoid spamming users.

Scope, Requirements & Constraints

Main challenges: (1) Fanout — a single event (e.g., a post from a celebrity with 10M followers) generates millions of push notifications. (2) Preference filtering — each recipient has different opt-in/opt-out settings. (3) Reliability — ensure delivery even if a channel (push) is temporarily down. (4) Batching/rate limiting — avoid overwhelming users with dozens of individual notifications.

Core Functional Requirements

  • ✓Deliver notifications via push (APNs/FCM), email (SMTP/SES), and in-app channels.
  • ✓Respect per-user notification preferences (enabled/disabled per type and channel).
  • ✓Deduplicate: do not send duplicate notifications for the same event within a time window.
  • ✓Batch low-priority notifications (e.g., group 5 likes into one notification).
  • ✓Prioritize: deliver time-sensitive notifications (e.g., DM, security alert) with low latency.

Scale & Latency Constraints

  • —10 million daily active users; peak: 500,000 notification events/second.
  • —Push delivery p99 < 5 seconds after event; email < 1 minute.
  • —In-app notifications must be queryable (paginated history per user).
  • —At-least-once delivery guarantee; tolerate duplicate delivery if deduplicated at receiver.
  • —Support notification expiry (e.g., a 'like' notification older than 24 hours is stale).

Reference Architecture & System Blueprint

Event → Kafka topic → Notification Service (preference filter + dedup) → Channel Workers (push/email/in-app).

System Architecture & Theory

Architectural Overview & Separation of Concerns

A modern notification engine decouples high-volume domain event publishers (orders, social likes, security alerts) from slow, unreliable third-party delivery networks (Apple APNs, Google FCM, SendGrid SMTP, Twilio SMS). The system enforces at-least-once delivery, recipient channel opt-in filtering, and duplicate event suppression while shielding client request threads from network latency.

Write Path Mechanics (Ingestion to Persistence)
1. Event Ingestion: Microservices emit domain notification events asynchronously to Kafka topics partitioned by `userId`. Partitioning guarantees strict per-user in-order event sequencing. 2. Deduplication & Preference Filtering: The stateless Notification Core engine consumes events, queries user channel preferences from Redis cache, and applies atomic deduplication keys via `SETNX {userId}:{eventType}:{entityId} EX 300`. Duplicate triggers within the time window are dropped. 3. Channel Isolation Queues: Evaluated notifications are fanned out to dedicated channel queues (Push Queue, Email Queue, In-App Queue). Dedicated queues guarantee that vendor outages (such as slow SMTP handshakes) do not backpressure rapid mobile push notifications.
Read Path & High-Velocity Redirect Tier
1. Worker Dispatch: Stateless worker pools scale horizontally to pull messages from channel queues. 2. External Gateway Dispatch: Push workers maintain persistent HTTP/2 multiplexed sockets to APNs and FCM. Email workers send batch requests to transactional email providers. 3. In-App Inbox Persistence: In-app workers commit notifications to the user inbox in a sharded database (Cassandra or PostgreSQL sharded by `userId`) and increment the unread badge count in Redis.
Scale Bottlenecks, Operational Hazards & Failure Modes
1. Provider Circuit Breakers: When external gateways (e.g., APNs or SES) experience degradation or 5xx responses, worker circuit breakers trip, diverting failed events to Dead Letter Queues (DLQ) with exponential backoff and jitter. 2. Celebrity Event Thundering Herd: When an account with 10M+ followers publishes a post, a hybrid fanout approach writes to an activity feed table rather than fanning out 10M individual queue messages simultaneously.
⚡ Architectural Invariant

Decoupling ingestion (Kafka) from channel dispatch via isolated per-channel queues prevents downstream provider outages from stalling the platform.

Hardened Implementation Steps

  1. 1Platform emits a domain event (e.g., UserLikedPost{postId, actorId, recipientId}) to Kafka.
  2. 2Notification Service consumes the event: fetch recipient preferences from a low-latency cache (Redis); if the channel is disabled or event type is muted, drop the event.
  3. 3Deduplication: check a Redis set {recipientId}:{eventType}:{entityId}:{windowHash} with TTL = dedup window (e.g., 1 hour). If key exists, drop; else SET NX and continue.
  4. 4Batching worker: for low-priority types (likes, follows), accumulate events in a Redis sorted set by recipient, flush every 30 seconds, send a single batched notification.
  5. 5Fanout: for high-priority (DM, security), route directly to the channel worker queue.
  6. 6Channel workers: push worker calls APNs/FCM; email worker calls SES; in-app worker writes to a notifications table (sharded by userId) and updates a Redis badge counter.
  7. 7Delivery failure: retry with exponential backoff; after max retries, write to a dead-letter queue for audit.

Key Decisions & Trade-Off Analysis

Architectural Decisions & Trade-Offs

  • ⚖Separate queues per channel: failures in email delivery do not block push delivery; scaling is independent.
  • ⚖Redis for preferences: avoids DB read on every notification event; stale preference cache (up to TTL) is acceptable — a user muting a notification type will stop receiving after the TTL expires.
  • ⚖Write fanout vs read fanout: Write fanout writes to each follower's queue immediately — O(followers) writes per post. Read fanout computes on read — O(followers) reads per inbox load. Write fanout is faster for notification delivery; read fanout is cheaper for celebrities (99% of followers never check their inbox).
  • ⚖Hybrid: use write fanout for regular users (<10K followers) and read fanout (or dedicated celebrity workers with throttled write) for high-follower accounts.

Scale Bottlenecks & Operational Hazards

Operational Hazards & Mitigations

  • ⚠Celebrity fanout: 5M push notifications in 5 seconds = 1M/sec. A single Kafka consumer + push worker cannot keep up. Solution: horizontal scaling of push workers; partition the notifications Kafka topic by userId hash so consumers can parallelize. Precompute follower lists for high-fan-out accounts.
  • ⚠APNs slow: push workers timeout waiting for APNs. Solution: set a short timeout (2 s); if APNs is slow, put undelivered notifications back in the queue with lower priority. Users will receive the push when APNs recovers.
  • ⚠APNs down: retry with exponential backoff up to the notification expiry TTL. After expiry, drop — stale notifications degrade UX more than missing ones.
  • ⚠In-app notification write surge: shard the notifications table by userId; use a write-behind cache (Redis) to absorb burst writes and flush to the DB asynchronously.

Changed Constraints & System Extension

New requirement: users can now set a 'Do Not Disturb' schedule (e.g., no notifications from 10 PM to 8 AM local time). High-priority notifications (security alerts, DMs) must still be delivered immediately. How do you implement this without blocking the notification pipeline?

Extension Implementation Steps

  1. 1Store DND schedules in the user preferences table (start_hour, end_hour, timezone).
  2. 2When a notification is about to be dispatched, check if recipient is in DND window (convert user's local time using stored timezone).
  3. 3If DND active AND notification priority is not 'critical': delay the notification by adding it to a scheduled delivery queue (Redis sorted set keyed by userId, scored by scheduled_delivery_time).
  4. 4A scheduler process polls the sorted set every minute and re-enqueues notifications whose delivery time has passed.
  5. 5If priority is 'critical' (DM, security): bypass DND check and deliver immediately.

Follow-Up Trade-Offs

  • ⚖Redis sorted set for delayed delivery: simple, low latency, but Redis is in-memory — persisted scheduled notifications need DB backup for durability.
  • ⚖Per-notification vs batch: check DND per notification at dispatch time. More accurate than batch processing, but adds a Redis lookup per notification.
  • ⚖Timezone accuracy: always store user timezone explicitly — do not infer from IP. Use IANA timezone identifiers.
