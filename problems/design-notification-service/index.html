Event-Driven Architecture (EDA)
Event-driven architecture (EDA) decouples producers and consumers by broadcasting immutable state-change facts through an asynchronous message broker or durable event log.
Distributed & Application Caching
Caching keeps a reusable copy of data so an application can avoid repeating a database query, calculation, or network call. It can make responses faster and reduce database load. The trade-off: the copy may be out of date.
Database Sharding & Range Partitioning
Horizontally partitioning a dataset across independent database nodes by a shard key—using either contiguous key ranges or consistent hashing—to scale write throughput and storage beyond a single primary's CPU, IOPS, and memory ceiling.
Rate Limiting Algorithms, Token Buckets & Redis Lua
Rate limiting enforces caps on request or resource consumption per caller, tenant, or endpoint over time to protect downstream capacity, ensure fair multi-tenant sharing, and blunt abuse.

STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens without priority isolation and deduplication.

Why this matters: The problem: see what breaks without What happens without priority isolation and deduplication under real concurrency or scale.

Routing all notifications through a single FIFO queue without preferences or dedup causes immediate user-facing incidents:

  1. Head-of-Line Blocking: A viral post generating 200,000 like notifications delays a 2FA security alert by minutes.
  2. Notification Spam: Retried upstream events send duplicate push alerts to the same device.
  3. Provider Throttling: Unbounded bursts trigger 429 / connection drops from APNs/FCM and SES.
Priority & Dedup Pipeline

Ingestion -> Preference/Dedup Check -> Priority Queues -> Workers

Priority topics isolate latency-critical alerts from viral like storms while Redis SETNX suppresses duplicate deliveries.

Engineering Decision Framework
Problem
How to implement Design a Scalable Notification Service without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
When traffic spikes expose hidden coupling, separate high-priority security/DM queues from batchable social likes, deduplicate with Redis SETNX idempotency keys, and route permanent failures to a Dead-Letter Queue.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Naive solution (and why synchronous fanout & single queues break).

Why this matters: The problem: see what breaks without Naive solution under real concurrency or scale.

A naive design calls FCM/SES synchronously from the monolith or uses one shared queue:

  • API Latency Spike: Upstream POST /like stalls whenever SES slows down.
  • No Batching: Sending 50 individual push notifications for 50 likes causes users to disable notifications.
  • Silent Drops: Transient 5xx errors from APNs drop notifications without retries or a DLQ.

STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Priority Topics, Redis Dedup, Batching & DLQ.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Production notification platforms combine four building blocks:

  • Priority-Tiered Kafka Topics: Separate notif.p0.critical (security/DM, < 5 s SLA) from notif.p2.social (likes/follows).
  • Preference & Expiry Filter: Check cached user channel preferences and drop stale events (e.g., like older than 24 h).
  • Idempotency & Aggregation: Use Redis SETNX with TTL for dedup, and a short tumbling window (e.g., 60 s Redis list/counter) to collapse 5 likes into one push.
  • Channel Workers + DLQ: Dedicated APNs/FCM/SES worker pools with token-bucket rate limiters, exponential backoff, and a Dead-Letter Queue.
Channel & State Architecture

Redis Dedup/Batch Cache + Priority Queues + In-App Store

1.Redis Dedup: SETNX idempotency_key prevents duplicate alerts on upstream retries.

2.Social Batching: Aggregates low-priority likes over a 60s window into a single summary.

3.In-App History: Writes paginated inbox records keyed by (user_id, created_at).

4.DLQ & Backoff: Moves exhausted retries to DLQ for inspection without blocking P0.

Redis absorbs dedup and preference lookups at sub-millisecond latency while channel workers rate-limit outbound provider calls.

import time

class NotificationRouter:
    def __init__(self, redis_client, kafka_producer, pref_store):
        self.redis = redis_client
        self.kafka = kafka_producer
        self.prefs = pref_store

    def handle_event(self, event: dict) -> str:
        if time.time() - event["created_at"] > 86400 and event["type"] == "like":
            return "DROPPED_STALE"
        dedup_key = f"notif:dedup:{event['event_id']}:{event['user_id']}"
        if not self.redis.set(dedup_key, "1", nx=True, ex=3600):
            return "DROPPED_DUPLICATE"
        channels = self.prefs.enabled_channels(event["user_id"], event["type"])
        if not channels:
            return "OPTED_OUT"
        topic = "notif.p0.critical" if event["priority"] == "P0" else "notif.p2.social"
        self.kafka.send(topic, key=event["user_id"], value={**event, "channels": channels})
        return f"QUEUED:{topic}"

Where Scalable Notification Architectures are used.

Why this matters: Scope boundary: identify where this pattern fits best and where simpler or async alternatives win.

This priority-isolated, idempotent fanout pattern is standard across consumer and enterprise platforms:

  • Social Networks & Creator Platforms: Collapsing high-volume likes/follows while delivering DMs in < 5 s.
  • Fintech & Security Alerts: Isolating OTP/fraud alerts on dedicated P0 partitions with multi-provider SES/Twilio failover.
  • E-Commerce Order Updates: Guaranteeing at-least-once delivery for shipping and refund confirmations.
