The idea to keep with you

Your high-throughput aggregator microservice (Python `requests` / Java `RestTemplate` on Kubernetes Linux nodes) calls an internal pricing service at 1,500 RPS per pod. During peak traffic, pods begin throwing `Cannot assign requested address (EADDRNOTAVAIL)` and `BindException` while CPU is only 35%. `ss -tan state time-wait | wc -l` reveals 28,200+ sockets stuck in `TIME_WAIT` against the same `10.96.45.12:8080` destination IP:port. Identify why ports exhausted at 1,500 RPS, fix the HTTP client architecture, and apply safe Linux/Kubernetes mitigations.

Full walkthrough · 5 stages
01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why ephemeral ports exhaust in 18 seconds at 1,500 RPS.

Linux allocates outbound client ports from ip_local_port_range = 32768..60999 (28,232 ports). When an aggregator pod calls a single ClusterIP (10.96.45.12:8080) using a new HTTP client per request, the client actively closes each TCP socket, placing it in TIME_WAIT for 2 * MSL = 60 seconds. At 1,500 RPS, 1,500 * 60 = 90,000 ports are needed—exhausting all 28,232 ports in 18.8 seconds and throwing EADDRNOTAVAIL.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens when every request creates a fresh TCP socket.

Opening and closing a TCP socket per outbound call causes three failures:

  1. 4-Tuple Exhaustion: Because (dst_ip, dst_port) is fixed to 10.96.45.12:8080, all 28,232 (src_ip, src_port) pairs lock in TIME_WAIT.
  2. TCP/TLS Handshake Tax: Every call pays 1–2 extra RTTs for TCP + TLS handshakes.
  3. Unsafe Kernel Hacks: Enabling deprecated tcp_tw_recycle breaks clients behind NAT / kube-proxy.
Socket Lifecycle Comparison

Per-Request Socket (28.2k TIME_WAIT) vs. Keep-Alive Pool (<200 Sockets)

A singleton keep-alive pool of ~100–200 persistent sockets serves 1,500–5,000 RPS with near-zero TIME_WAIT churn.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive solution (and why widening ip_local_port_range alone fails).

Expanding net.ipv4.ip_local_port_range to 1024 65535 (~64,500 ports) only delays exhaustion from 18.8 s to 43 s at 1,500 RPS—and still fails completely at 5,000 RPS (5,000 * 60 = 300,000 ports needed).

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Singleton HTTP Keep-Alive Pool + HTTP/2 + Safe Sysctls.

Production microservices eliminate port exhaustion at the client layer:

  • Singleton Keep-Alive Connection Pool: Initialize one process-wide requests.Session / httpx.AsyncClient (Python) or PoolingHttpClientConnectionManager (Java) with max_connections=200, keepalive_expiry=30s (aligned below server idle timeout), and max_conn_lifetime=55s for DNS rotation.
  • HTTP/2 Multiplexing: Where supported, multiplex concurrent requests over a handful of long-lived TCP connections.
  • Safe Kernel Tuning: Keep ip_local_port_range = 10240 65535 and tcp_tw_reuse = 1 (safe for outbound client connections only; never tcp_tw_recycle).
Persistent Socket Pooling

Singleton HTTP Pool + Idle/Max-TTL Recycling -> Pricing Pods

1.Singleton Pool: Reuses < 200 established TCP/TLS sockets across 5,000+ RPS.

2.Sub-10ms Latency: Eliminates per-request SYN/ACK and TLS 1.3 handshake RTTs.

3.Timeout Alignment: Client idle timeout < server keep-alive avoids half-closed 502 races.

4.No Unsafe Sysctls: Avoids tcp_tw_recycle which breaks kube-proxy SNAT traffic.

Reusing 100–200 pooled keep-alive connections cuts TIME_WAIT sockets from 28,200+ to < 200 and scales cleanly past 5,000 RPS.

import httpx

# Process-wide singleton HTTP/1.1 + HTTP/2 keep-alive pool (reused across all requests)
limits = httpx.Limits(
    max_connections=200,
    max_keepalive_connections=150,
    keepalive_expiry=30.0,  # strictly < upstream server idle timeout (e.g. 60s)
)
pricing_client = httpx.AsyncClient(
    base_url="http://pricing-service.internal:8080",
    limits=limits,
    http2=True,
    timeout=httpx.Timeout(2.0, connect=0.2),
)
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Connection Pooling & Socket Hygiene apply in System Design.

Connection pooling and TIME_WAIT awareness are essential for any high-QPS service-to-service mesh:

  • API Gateways & BFF Aggregators: Calling internal pricing, auth, and inventory services at 5,000+ RPS.
  • Load Generators & Benchmarks: Avoiding client-side EADDRNOTAVAIL when simulating thousands of virtual users.
  • Database & Redis Clients: Bounding HikariCP / redis-py pools to prevent TIME_WAIT and file-descriptor exhaustion.
