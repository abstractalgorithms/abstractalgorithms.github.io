01 / UnderstandFailure & constraints

Clarify what is failing.

Liveness checked the DB and shared Tomcat's blocked worker pool with a 1s timeout; all 24 pods failed 3 checks in 15s and entered 45s cold-start loops.

Design objective

Trace the 2-way failure: DB check fails + Tomcat thread queue blocks `/actuator/health`.

Requirements

  • Ensure downstream DB slowness or thread-pool saturation marks pods **NotReady** (`/readyz`) without ever triggering a `livenessProbe` restart.
  • Guarantee `/livez` responds in <50 ms even when all 200 business threads and all 20 DB connections are blocked.
  • Support 45-second JVM + Spring context initialization cleanly without `livenessProbe` killing booting pods.
  • Prevent kubelet CPU-throttling false positives on liveness checks.

Constraints

  • JVM cold start + JIT warm-up takes 45 seconds.
  • Pods run with `resources.limits.cpu: 2` (CFS quota 200 ms/100 ms) and `memory: 4Gi`.
  • Postgres connection pool per pod is strictly capped at 20 connections.
Known failure modes

All pods restarting simultaneously saturates CPU and DB connection handshakes.

02 / Map the systemArchitecture & invariants

Separate concerns. Map the flow.

Separate management onto port `8081`, bind `liveness` strictly to `livenessState`, `readiness` to `readinessState,db`, and configure `startupProbe`.

  1. 01Startup Gate (0-90s): Kubelet runs startupProbe until JVM + Spring boot completes, suppressing liveness kills during cold start.
  2. 02Downstream Contention: Postgres lock stalls all 20 DB connections; Tomcat threads queue up with bounded 2s connectionTimeout.
  3. 03Readiness Fails -> Shed Traffic: Readiness detects DB/pool saturation and removes pod from Service Endpoints without restarting the JVM.
  4. 04Out-of-Band Liveness Survives: Dedicated :8081 management threads respond 200 OK immediately, preventing cascading SIGKILL restarts.
  5. 05Zero-Restart Recovery: After 4s, DB recovers, warm JVM pools resume serving, and readinessProbe re-adds pods cleanly.
Separating liveness onto an isolated management port with zero downstream checks prevents transient DB/CPU overload from triggering pod restarts.

The invariants

  • Set management.server.port: 8081.
  • Configure group.liveness.include: livenessState and group.readiness.include: readinessState,db.
  • Add startupProbe, readinessProbe, and livenessProbe in K8s spec.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Yes, for single-pod DB network splits, readiness should fail; however, if Postgres itself is down, all 24 pods failing readiness causes `kube-proxy` to drop all endpoints (503/connection refused) unless `publishNotReadyAddresses` or fast-fail 503s are preferred.

Step 1

Distinguish local pod DB-pool exhaustion from global DB outage.

Step 2

Explain that returning HTTP 503 with Retry-After from warm pods is often cleaner than removing all 24 endpoints.

JAVA · Lifecycle trace
// Fail fast with 503 via Hikari timeout instead of blocking threads
@RestControllerAdvice
public class PoolOverloadHandler {
    @ExceptionHandler(SQLTransientConnectionException.class)
    public ResponseEntity<String> handlePoolExhausted() {
        return ResponseEntity.status(503).header("Retry-After", "2").body("DB pool saturated");
    }
}
Key trade-off

Fast 503s keep pods in the Service pool so recovery is instantaneous when the DB lock clears.

04 / ImplementConfiguration & code

Build the safeguards.

Linux CFS CPU quota throttling (`limits.cpu: 2`) freezes the entire JVM process—including port 8081 threads—for up to 90+ ms per 100 ms period.

1. Reference implementation

YAML · Solution
# application.yaml
management:
  server:
    port: 8081
  endpoint:
    health:
      probes:
        enabled: true
      group:
        liveness:
          include: livenessState
        readiness:
          include: readinessState,db
spring:
  datasource:
    hikari:
      connection-timeout: 1500
---
# Kubernetes Pod Spec
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8081 }
  periodSeconds: 5
  failureThreshold: 18
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8081 }
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2
  successThreshold: 2
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8081 }
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 6

2. Harden for scale

Linux CFS CPU quota throttling (`limits.cpu: 2`) freezes the entire JVM process—including port 8081 threads—for up to 90+ ms per 100 ms period.

YAML · Scale hardening
resources:
  requests:
    cpu: "2"
    memory: "4Gi"
  limits:
    memory: "4Gi"
    # Omit limits.cpu or set higher burst headroom to avoid CFS throttling

3. Operational controls

Step 1

Check `container_cpu_cfs_throttled_periods_total`.

Step 2

Remove `limits.cpu` (keep `requests.cpu`) or raise `timeoutSeconds: 5` and `limits.cpu` headroom.

Implementation note

Port 8081 ensures `/livez` responds even when port 8080's 200-thread pool is 100% blocked.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Only unrecoverable internal failures: `OutOfMemoryError` (`-XX:+ExitOnOutOfMemoryError` exits directly without needing liveness), or an internal deadlock detected by `ThreadMXBean.findDeadlockedThreads()`.

  • ↗
    Use `-XX:+ExitOnOutOfMemoryError` for immediate OOM exit.
  • ↗
    Optionally check `ThreadMXBean.findDeadlockedThreads()` in a custom liveness indicator.
JAVA · Verification
import java.lang.management.ManagementFactory;
import java.lang.management.ThreadMXBean;

public boolean isJvmDeadlocked() {
    ThreadMXBean bean = ManagementFactory.getThreadMXBean();
    long[] deadlocked = bean.findDeadlockedThreads();
    return deadlocked != null && deadlocked.length > 0;
}

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Use `timeoutSeconds5` + `failureThreshold: 6` so transient 200 ms CFS pauses never accumulate 6 consecutive failures.—

Review questions

Failure scenario 1

Strict `limits.cpu` with multi-threaded JVM GC causes severe tail-latency and probe timeouts.

Failure scenario 2

Putting complex lock checks inside liveness without caching can itself add CPU overhead.

Alternatives considered

  • Keep liveness strictly as a lightweight `200 OK` ping and rely on `-XX:+ExitOnOutOfMemoryError`.
