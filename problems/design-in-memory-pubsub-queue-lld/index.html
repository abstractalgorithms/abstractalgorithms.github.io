01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why fan-out Pub-Sub needs independent offsets and per-topic locks.

Unlike a point-to-point BlockingQueue (where 1 consumer pops and removes each message), Pub-Sub requires every subscriber on a topic to receive all messages independently and support resetOffset() for replay—all while isolating slow subscribers and unrelated topics.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Head-of-line blocking, busy-wait CPU burn, and global-lock contention.

Naive in-memory brokers break in three ways:

  1. Synchronous Fan-Out: Calling subscriber.onMessage(msg) directly inside publish() lets one slow subscriber stall the publisher and all fast subscribers.
  2. Busy-Wait Polling: while (offset >= log.size()) {} burns 100% CPU when caught up.
  3. Global Broker Lock: Synchronizing all topics on one lock causes Topic A traffic to block Topic B.
Non-Blocking Fan-Out

Per-Topic Append Log + Condition Wakeup for Independent Consumers

Publishers append and signalAll() in O(1) while each SubscriberWorker advances its own offset independently.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive `BlockingQueue` per subscriber or `Thread.sleep(10)` loops.

Duplicating messages into N separate BlockingQueues wastes N× memory and cannot support resetOffset(0) replay. Meanwhile, Thread.sleep(10) polling wastes CPU and adds 10 ms artificial tail latency.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Per-Topic Log + `Condition` + `AtomicInteger` Offsets.

Build clean isolation across topics and subscribers:

  • ConcurrentHashMap<String, Topic>: createTopic uses putIfAbsent with zero global lock during publish().
  • Per-Topic ReentrantLock + Condition: publish() appends to List<Message> and calls newMessageCond.signalAll(). SubscriberWorker sleeps via newMessageCond.await() inside a while (offset.get() >= topic.size()) loop (handling spurious wakeups).
  • Independent AtomicInteger Offset: Each SubscriberWorker tracks its own offset; resetOffset(newOffset) sets the offset and signals the condition variable to replay immediately.
Broker Memory Layout

Topic-Isolated Append Log & Per-Subscriber Cursors

Sharing one immutable append log per topic avoids N-way message copying and enables instant offset replay.

public class Topic {
    private final List<Message> log = new ArrayList<>();
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition hasNew = lock.newCondition();

    public void publish(Message msg) {
        lock.lock();
        try {
            log.add(msg);
            hasNew.signalAll();
        } finally { lock.unlock(); }
    }

    public Message readAt(AtomicInteger offset) throws InterruptedException {
        lock.lock();
        try {
            while (offset.get() >= log.size()) {
                hasNew.await(); // Sleeps with zero CPU spin until publish or resetOffset
            }
            return log.get(offset.getAndIncrement());
        } finally { lock.unlock(); }
    }
}
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where append-log Pub-Sub architectures are used.

This exact in-memory model scales out into distributed streaming logs:

  • Apache Kafka & Redpanda: Store immutable per-partition append logs on disk and track per-consumer-group offsets independently for replay.
  • In-Process Event Buses: High-frequency trading and game servers use ring-buffer/append-log buses to fan out market ticks to isolated strategy threads.
