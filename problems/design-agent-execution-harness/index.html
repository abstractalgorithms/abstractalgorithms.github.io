TL;DR30-second simplified summary
▾

All outbound VM traffic passes through an Envoy Egress Proxy that blocks SSRF/metadata IPs and injects short-lived capability-scoped OAuth headers.

Idempotent Run Ingestion & Per-Tenant Concurrency Queues.

Why this matters: Prevent duplicate agent launches and noisy-neighbor worker starvation.

Think of Idempotent Run Ingestion & Per-Tenant Concurrency Queues as the intuition layer for Design a Distributed Autonomous Agent Execution Harness: Prevent duplicate agent launches and noisy-neighbor worker starvation.

Clients submit runs with an idempotency_key stored in PostgreSQL (UNIQUE(tenant_id, idempotency_key)). Accepted runs enqueue onto Kafka/Redis Streams partitioned by tenant_id, while a Fair-Queue Scheduler caps active concurrent runs per tenant (e.g., max 50) so one customer's 10,000-task batch never starves interactive users.

Stage 1 - Run Scheduling

Idempotent Fair-Queue Ingestion

1.Fair-Share Queuing: Weighted fair queuing prevents bulk batch tenants from starving interactive runs.

2.Early Rejection: Validate tool permissions and budget limits at ingestion before allocating workers.

Idempotent ingestion and tenant fair-queuing protect cluster capacity under spiky agent workloads.

Durable Worker Pods & Fencing-Token Checkpointing.

Why this matters: Guarantee exactly-once state advancement even when workers stall or split-brain.

If Worker A pauses during a GC storm and its lease expires, Worker B picks up the run.

Without fencing, a waking Worker A could corrupt state. Every checkpoint write uses Optimistic Concurrency Control (`UPDATE runs SET step=step+1, lease_epoch=...

Stage 2 - Lease Fencing

Fenced Durable State Store

1.Heartbeat Leases: Workers renew leases every 5s; missed 15s heartbeat triggers safe re-claim.

2.Deterministic Steps: Checkpoint both LLM outputs and tool results before advancing step_seq.

Monotonic lease-epoch fencing prevents split-brain corruption during worker failovers.

Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
When inference latency or GPU memory limits bind throughput, separate control-plane durable orchestration from a warm MicroVM execution pool, using idempotent outbox scheduling, lease-based worker fencing, and event-sourced traces.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

03
intermediate

Warm Firecracker MicroVM Pool & Snapshot Pre-Warming.

Why this matters: Deliver <100ms sandbox startup for 100K+ tool executions without kernel-sharing risks.

Cold-booting a VM takes seconds; cold-installing Python packages takes longer.

A Pool Manager maintains pre-booted Firecracker MicroVM snapshots (memory + rootfs COW overlay) across bare-metal hosts.

Stage 3 - Warm Sandbox Pool

Pre-Warmed Firecracker MicroVM Pool

1.Zero State Leakage: Always destroy or reset COW overlays after a run; never reuse dirty VMs across tenants.

2.Autoscaling Buffer: Target 15% warm buffer above p95 active concurrency.

Copy-on-write snapshot pools combine hardware-level isolation with <100ms startup.

04
intermediate

Zero-Trust Egress Proxy & Scoped Capability Tokens.

Why this matters: Let sandboxed tools call authorized enterprise APIs without ever holding raw credentials.

Think of Zero-Trust Egress Proxy & Scoped Capability Tokens as the intuition layer for Design a Distributed Autonomous Agent Execution Harness: Let sandboxed tools call authorized enterprise APIs without ever holding raw credentials.

When an agent needs to call GitHub or Jira from inside a MicroVM, the Worker mints a short-lived, action-scoped capability token (run_id, allowed_hosts, allowed_methods, exp=60s). The VM routes all outbound traffic through an Envoy Egress Proxy, which validates the token, drops unauthorized domains/IPs (including metadata 169.254.169.254), and injects the real OAuth header.

Stage 4 - Capability Egress

Secretless VM Egress Proxy

1.SSRF Protection: Block all RFC1918 private IPs and cloud metadata endpoints at the egress proxy.

2.Method Scoping: Restrict tokens to GET-only when a step only needs read access.

Egress proxies eliminate SSRF and credential theft even if sandboxed code turns malicious.

05
intermediate

HITL Approval Gate, Webhook Callbacks & Timeout Escalation.

Why this matters: Support multi-hour human approvals cleanly across 100K+ parked workflows.

High-risk transitions emit an ApprovalRequested event and park the run in WAIT_HITL with a durable timer (e.g., 24h SLA).

The worker releases all memory and MicroVMs immediately.

Stage 5 - Async HITL

Parked Workflow & Signed Callback

1.RBAC Verification: Confirm the approver has permission for that specific tenant and tool scope.

2.Auto-Expiry: Expire unanswered approvals cleanly after 24h and run Saga cleanup if needed.

Event-driven HITL parking scales to hundreds of thousands of waiting approvals at near-zero cost.

06
advanced

Event-Sourced Execution Ledger & Time-Travel Replay.

Why this matters: Power live trace streaming, compliance auditing, and deterministic offline debugging.

Workers append every step transition, token usage, and redacted tool I/O to Kafka (agent-events).

ClickHouse indexes trace spans for sub-second UI waterfall queries, while full compressed payloads land in S3.

Stage 6 - Trace Ledger

Kafka -> ClickHouse + S3 Replay Ledger

1.PII Redaction: Scrub bearer tokens and secrets before writing payloads to the trace ledger.

2.Partition Ordering: Partition Kafka by run_id so step events stay strictly ordered.

Partitioned Kafka ledgers power both real-time trace UIs and deterministic offline replay.

07
advanced

Multi-Region Active-Passive DR & Saga Compensation.

Why this matters: Protect against regional outages and clean up partial external side effects.

Checkpoints and event logs replicate asynchronously cross-region.

If a primary region fails, standby workers promote the replicated state and resume parked/active runs using idempotency keys.

Stage 7 - DR & Saga Cleanup

Cross-Region Recovery & Saga Undo

1.Idempotent Recovery: External tool idempotency keys prevent double-execution during regional failover.

2.Bounded Saga Retries: Retry failed compensations with exponential backoff before alerting ops.

Cross-region checkpoint replication and Saga compensations ensure clean recovery from outages.
