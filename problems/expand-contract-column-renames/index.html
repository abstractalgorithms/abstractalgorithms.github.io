01 / UnderstandFailure & constraints

Clarify what is failing.

Metadata speed does not solve application-level schema skew: v2.0 pods still issue SQL referencing `user_phone`, which immediately ceases to exist.

Design objective

Explain that `maxSurge: 25%, maxUnavailable: 0` guarantees v2.0 and v2.1 overlap.

Requirements

  • Support v2.0 and v2.1 pods running concurrently on the same MySQL 8.0 table for the full rollout duration
  • Complete the rename without blocking 3,000 QPS of live reads and writes on the 25M-row `customers` table
  • Eliminate initContainer race conditions across parallel pod startups
  • Ensure clean rollback to v2.0 if v2.1 fails readiness or canary checks

Constraints

  • MySQL 8.0 InnoDB with 25M rows (~18 GB table size)
  • Kubernetes rolling update with `maxSurge: 25%`, `maxUnavailable: 0`
  • Zero downtime; metadata locks must stay under 1 second
Known failure modes

initContainer migrations running concurrently across multiple surging pods

Separate concerns. Map the flow.

Add `phone_e164` with `ALGORITHM=INSTANT`, synchronize both columns via `BEFORE INSERT/UPDATE` triggers using `<=>`, backfill in batches, and drop `user_phone` in v2.2.

  1. 01Expand Schema: Add nullable phone_e164 with ALGORITHM=INSTANT and attach INSERT/UPDATE sync triggers.
  2. 02Throttled Backfill: Copy user_phone to phone_e164 in 2k-row PK batches, then add online index (LOCK=NONE).
  3. 03N-1 Traffic Continuity: Draining v2.0 pods continue writing user_phone; trigger mirrors values to phone_e164.
  4. 04N Traffic Cutover: New v2.1 pods read/write phone_e164; trigger mirrors values back to user_phone for safe rollback.
  5. 05Drop Legacy Column: In v2.2 after v2.0 is gone, drop triggers and DROP COLUMN user_phone, ALGORITHM=INSTANT.
Bidirectional triggers and ALGORITHM=INSTANT keep v2.0 and v2.1 pods 100% compatible throughout the rolling update.

The invariants

  • Run Expand in a single K8s pre-upgrade Job with lock_wait_timeout = 2.
  • Use <=> in BEFORE UPDATE to detect whether v2.0 or v2.1 changed the value.
  • Backfill 25M rows in 2,000-row batches and add indexes with LOCK=NONE.
03 / Trace the lifecycleKey decisions

Follow the execution path.

A `VIRTUAL` generated column avoids triggers and backfill entirely if v2.1 only *reads* `phone_e164`, but cannot be written to directly by `INSERT/UPDATE`.

Step 1

Virtual generated columns compute phone_e164 on read with zero storage overhead.

Step 2

However, MySQL rejects INSERT INTO customers (phone_e164) VALUES (...) on generated columns.

Step 3

Therefore, triggers are required when v2.1 must write to phone_e164 while v2.0 still writes to user_phone.

SQL · Lifecycle trace
-- Valid ONLY if v2.1 reads phone_e164 but still writes user_phone:
ALTER TABLE customers
  ADD COLUMN phone_e164 VARCHAR(20) GENERATED ALWAYS AS (user_phone) VIRTUAL;
Key trade-off

Virtual columns are instant and trigger-free, but force v2.1 to still write to the old column name

04 / ImplementConfiguration & code

Build the safeguards.

MySQL's Metadata Lock (MDL) queue gives `ALTER TABLE` priority over new `SELECT/UPDATE`s; without `lock_wait_timeout`, all 3,000 QPS queue behind the analytics query.

1. Reference implementation

SQL · Solution
SET SESSION lock_wait_timeout = 2;
ALTER TABLE customers ADD COLUMN phone_e164 VARCHAR(20) NULL, ALGORITHM=INSTANT;
-- Backfill in 2k batches, then:
ALTER TABLE customers ADD INDEX idx_phone_e164 (phone_e164), ALGORITHM=INPLACE, LOCK=NONE;

2. Harden for scale

MySQL's Metadata Lock (MDL) queue gives `ALTER TABLE` priority over new `SELECT/UPDATE`s; without `lock_wait_timeout`, all 3,000 QPS queue behind the analytics query.

SQL · Scale hardening
SET SESSION lock_wait_timeout = 2;
ALTER TABLE customers ADD COLUMN phone_e164 VARCHAR(20) NULL, ALGORITHM=INSTANT;

3. Operational controls

Step 1

Trace the MDL pileup: Analytics `SELECT` -> `ALTER TABLE` waits -> all 3,000 QPS OLTP queries block.

Step 2

Set `SET SESSION lock_wait_timeout = 2;` so the DDL fails fast instead of blocking traffic.

Step 3

Retry the DDL with exponential backoff until the analytics query finishes.

Implementation note

Requires two releases (v2.1 + v2.2) to complete the rename cleanly

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Execute migrations in a dedicated single-pod Kubernetes `Job` (Helm `pre-upgrade` hook or ArgoCD `PreSync` hook) before updating the `Deployment`.

  • ↗
    Remove Alembic/Flyway from application `initContainers`.
  • ↗
    Create a Kubernetes `Job` with `completions: 1`, `parallelism: 1`, and `backoffLimit: 2`.
  • ↗
    Gate the `Deployment` rollout on `Job` completion.
YAML · Verification
apiVersion: batch/v1
kind: Job
metadata:
  name: customers-db-migrate-v21
  annotations:
    argocd.argoproj.io/hook: PreSync
spec:
  backoffLimit: 2
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: alembic
          image: payments-api:v2.1
          command: ["alembic", "upgrade", "head"]

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Virtual columns are instant and trigger-free, but force v2.1 to still write to the old column name—
Option 2Use `gh-ost` or `pt-online-schema-change` for non-instant schema changes on large tables—

Review questions

Failure scenario 1

Default MySQL `lock_wait_timeout` is 31,536,000 seconds (1 year), guaranteeing an outage if an `ALTER` blocks

Failure scenario 2

If `ttlSecondsAfterFinished` is omitted, old migration Jobs accumulate in the namespace

Alternatives considered

  • Use a distributed advisory lock (`GET_LOCK` in MySQL) if migrations must remain in-app

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Never rename a live column in place during a rolling deploy; use additive columns, generated/triggered sync, or updatable views across two releases.
