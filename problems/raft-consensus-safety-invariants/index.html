01 / UnderstandFailure & constraints

Clarify what is failing.

An entry from an earlier term replicated to a majority can still be overwritten by a new leader whose log has a higher-term entry at an earlier index.

Design objective

Trace S1 writing entry at index 2 in term 2, crashing, and S5 getting elected in term 3.

Requirements

  • Guarantee Election Safety (at most 1 leader per term) and Leader Completeness across arbitrary crash/restart and asymmetric partitions.
  • Prevent the Raft Figure 8 bug where a newly elected leader overwrites an indirectly replicated entry.
  • Serve linearizable reads without writing dummy no-op entries to disk on every read.
  • Compact WAL logs via snapshots without stalling followers or breaking `prevLogIndex`/`prevLogTerm` checks.

Constraints

  • Cluster size N=5 (quorum = 3, tolerates 2 node failures).
  • Cross-AZ RTT = 15 ms; `electionTimeout` must be 150–300 ms randomized, `heartbeatInterval` = 50 ms.
  • Disk `fsync` latency = 2–5 ms per batch; WAL cap = 10 GB before snapshot compaction.
Known failure modes

Violating this rule causes silent data loss of acknowledged writes after double leader crashes.

  1. 01Client Request: Leader appends write to local WAL and fsyncs, or records current commitIndex for ReadIndex.
  2. 02Log Matching RPC: Followers verify prevLogIndex/prevLogTerm, truncate conflicts, append, and fsync.
  3. 03Quorum Confirmation: Leader receives majority ACKs confirming term T leadership or replication.
  4. 04Safe Commit & Apply: Leader advances commitIndex only for term T entries and applies to FSM.
  5. 05Linearizable Response: Once lastApplied >= target index, leader returns result to client.
Enforcing currentTerm-only commits and ReadIndex quorum heartbeats preserves linearizability across partitions.

The invariants

  • In advanceCommitIndex, iterate N from lastLogIndex down to commitIndex + 1.
  • Check log[N].term == currentTerm and count(matchIndex >= N) > N_NODES / 2.
  • In handleAppendEntries, reject if term < currentTerm or prevLog mismatches.
03 / Trace the lifecycleKey decisions

Follow the execution path.

`ReadIndex` is strictly safe under arbitrary clock skew (15 ms RTT); `LeaseRead` hits 0.1 ms latency but requires bounded monotonic clock drift.

Step 1

Batch concurrent ReadIndex requests into a single quorum heartbeat round.

Step 2

Compare against LeaseRead using CLOCK_MONOTONIC bounded by electionTimeout / 2.

JAVA · Lifecycle trace
public String linearizableRead(String key) {
    long readIdx = this.commitIndex;
    if (!confirmQuorumHeartbeat()) {
        stepDown();
        throw new NotLeaderException();
    }
    waitUntilApplied(readIdx);
    return stateMachine.get(key);
}
Key trade-off

Batching ReadIndex coalesces 1,000 reads into 1 heartbeat RTT, achieving high throughput without clock assumptions.

04 / ImplementConfiguration & code

Build the safeguards.

`PreVote` blocks term inflation while partitioned; `CheckQuorum` forces a partitioned leader to step down within 1 election timeout.

1. Reference implementation

JAVA · Solution
public synchronized void advanceCommitIndex() {
    for (int n = log.size() - 1; n > commitIndex; n--) {
        if (log.get(n).term() != currentTerm) continue;
        int replicated = 1; // leader itself
        for (int match : matchIndex.values()) {
            if (match >= n) replicated++;
        }
        if (replicated > clusterSize / 2) {
            commitIndex = n;
            applyCommittedEntries();
            break;
        }
    }
}

2. Harden for scale

`PreVote` blocks term inflation while partitioned; `CheckQuorum` forces a partitioned leader to step down within 1 election timeout.

PYTHON · Scale hardening
def handle_pre_vote(cand_term: int, cand_last_term: int, cand_last_idx: int,
                    my_term: int, leader_recently_active: bool, my_log_tail: tuple[int, int]) -> bool:
    if leader_recently_active:
        return False
    if cand_term < my_term:
        return False
    return is_log_up_to_date(cand_last_term, cand_last_idx, my_log_tail[0], my_log_tail[1])

3. Operational controls

Step 1

Partitioned node sends `PreVote` without incrementing `currentTerm`.

Step 2

Healthy majority rejects `PreVote` because they recently heard from the active leader.

Step 3

Cluster avoids unnecessary leader step-down and election pause.

Implementation note

Scanning backwards from `lastLogIndex` breaks immediately on the highest valid index, O(N) worst case.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Retain a 10k-entry trailing WAL buffer after taking a snapshot, and stream `InstallSnapshot` in 1 MB chunks with flow control.

  • ↗
    Take non-blocking copy-on-write snapshot of FSM at `lastApplied`.
  • ↗
    Keep `max(0, snapshotIdx - 10000)` in WAL so minor lags use normal `AppendEntries`.
  • ↗
    Stream `InstallSnapshot` chunks asynchronously with offset tracking.
PYTHON · Verification
def compact_wal(wal: list, snapshot_idx: int, keep_tail: int = 10000) -> int:
    truncate_to = max(0, snapshot_idx - keep_tail)
    del wal[:truncate_to]
    return truncate_to

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Know what each control buys.

Option 2Use `LeaderTransfer` RPC for planned maintenance step-downs (zero timeout wait).—

Review questions

Failure scenario 1

Without `PreVote`, a node with a one-way network fault increments term to 10,000 and forces healthy leader step-downs on reconnect.

Failure scenario 2

Deleting WAL up to `snapshot_idx` synchronously blocks the Raft loop if snapshot serialization isn't copy-on-write.

Alternatives considered

  • Rate-limit `InstallSnapshot` bandwidth (e.g., 50 MB/s) to protect foreground `AppendEntries` latency.

Theory & Tips and Tricks

Practical heuristics & interview traps
