01 / UnderstandFailure & constraints

Clarify what is failing.

Losing `connect-offsets` (RF=1) plus dropping the Postgres slot caused `when_needed` to create a fresh slot at the current WAL head, bypassing the 4-hour gap.

Design objective

Trace how RF=1 on connect-offsets caused offset loss on a single broker disk failure.

Requirements

  • Guarantee Debezium offsets and PostgreSQL `confirmed_flush_lsn` survive single-broker or Connect worker failures with zero silent data loss.
  • Prevent PostgreSQL WAL disk exhaustion caused by idle or filtered-out tables holding back the replication slot LSN.
  • Detect synchronization gaps between PostgreSQL and downstream sinks (Elasticsearch/Snowflake) within 5 minutes.
  • Backfill or repair missed rows using non-blocking incremental snapshots (`signal.data.collection`) while live streaming continues.

Constraints

  • The `orders` table is 1.8 TB (420M rows); a full blocking `INITIAL` snapshot takes 14 hours and cannot be used during peak business hours.
  • PostgreSQL `max_slot_wal_keep_size` is capped at 100 GB to protect the primary database's NVMe volume.
  • Downstream Kafka consumers must tolerate at-least-once delivery and out-of-order snapshot vs. streaming events.
Known failure modes

Silent data drift in Elasticsearch and Snowflake.

02 / Map the systemArchitecture & invariants

Separate concerns. Map the flow.

Use RF=3 compacted `connect-offsets`, 10s heartbeats, and `public.debezium_signal` with `additional-conditions` to backfill the 4-hour window in ~30 seconds.

  1. 01Continuous WAL & Heartbeat: Debezium reads pgoutput WAL frames and triggers a 10s heartbeat write so confirmed_flush_lsn advances continuously.
  2. 02Compacted RF=3 Offset Commit: Debezium flushes CDC events and commits the LSN to connect-offsets (RF=3, min.insync.replicas=2, compact).
  3. 03Surgical Incremental Backfill: Operator inserts a targeted execute-snapshot row into debezium_signal with an updated_at window for the 4h gap.
  4. 04Watermarked Chunk Streaming: Debezium interleaves 4,096-row SELECT chunks with live WAL events using open/close watermark windows.
  5. 05Out-of-Order Safe Indexing: Elasticsearch rejects stale backfilled docs if a newer WAL event already indexed a higher row_version.
Compacted RF=3 offsets + 10s heartbeats + DBLog incremental snapshots prevent and heal CDC gaps without table locks.

The invariants

  • Configure connect-offsets with cleanup.policy=compact, RF=3, min.insync.replicas=2.
  • Enable heartbeat.interval.ms=10000 and heartbeat.action.query.
  • Insert an execute-snapshot row scoped to the 4-hour updated_at range.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Debezium uses watermarked window deduplication in-flight, and Elasticsearch enforces `version_type=external` keyed by monotonic `row_version` as an end-to-end invariant.

Step 1

Include a monotonically increasing version column on orders.

Step 2

Configure the Elasticsearch sink connector to pass version with version_type=external.

Step 3

Elasticsearch automatically rejects any update with incoming_version <= stored_version.

JSON · Lifecycle trace
{
  "version.type": "external",
  "document.id.strategy": "record.key",
  "behavior.on.version.conflict": "ignore"
}
Key trade-off

Requires a monotonic version column or LSN-derived integer on every indexed document.

04 / ImplementConfiguration & code

Build the safeguards.

The primary DB stays online safely; on recovery, recreate the slot and trigger a targeted incremental snapshot from the last `debezium_heartbeat` timestamp.

1. Reference implementation

SQL · Solution
INSERT INTO public.debezium_signal (id, type, data) VALUES (
  'repair-4h-gap', 'execute-snapshot',
  '{"data-collections":["public.orders"],"type":"incremental","additional-conditions":[{"data-collection":"public.orders","filter":"updated_at >= ''2026-11-12 10:00:00+00''"}]}'
);

2. Harden for scale

YAML · Scale hardening
# PostgreSQL postgresql.conf WAL protection
max_slot_wal_keep_size: 102400MB # 100 GB hard cap
wal_keep_size: 4096MB

3. Operational controls

Step 1

Read the last committed timestamp from `connect-offsets` or sink watermark.

Step 2

Recreate the Debezium connector with a fresh slot.

Step 3

Emit an `execute-snapshot` signal covering `[last_committed_ts - 5m, now]`.

Implementation note

Incremental snapshots take 30s for 1.2M rows with zero table locks, vs. 14 hours for a full snapshot.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Run a lightweight Python cron every 5 minutes comparing row counts and `updated_at` bucket checksums between a Postgres read replica and Elasticsearch.

  • ↗
    Query `[now - 10m, now - 5m]` (allowing 5m replication lag) on both stores.
  • ↗
    Compare `COUNT(*)` and `BIT_XOR(id_hash)`.
  • ↗
    On mismatch, auto-insert a Debezium `execute-snapshot` signal for that 5-minute window.
PYTHON · Verification
if pg_count != es_count or pg_checksum != es_checksum:
    emit_debezium_signal(window_start, window_end)
    metrics.increment("cdc_drift_auto_repaired")

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Know what each control buys.

Review questions

Failure scenario 1

No alert on `pg_replication_slots.wal_status = 'lost'`, delaying recovery.

Failure scenario 2

Comparing `[now - 1m, now]` and false-alarming on normal 200ms replication lag.

Alternatives considered

  • Debezium Server + Prometheus lag metrics alone (detects lag, not silent sink drops).
