Preventing PostgreSQL XID
Wraparound Shutdowns.

01 / UnderstandFailure & constraints

Clarify what is failing.

32-bit XIDs wrap after ~2.14B transactions; an abandoned slot or long query pins global xmin, preventing vacuum from freezing or pruning tuples.

Design objective

Explain modular 32-bit XID arithmetic (past vs future 2B split).

Requirements

  • Safely recover the database from wraparound shutdown without losing committed data.
  • Identify and remove the `xmin` blockers preventing `VACUUM FREEZE` from advancing `relfrozenxid`.
  • Tune autovacuum I/O budgets on large append/update tables so freeze vacuums finish well ahead of the 2B limit.
  • Add alerting at 500M and 1B XID age so wraparound never reaches the 2B emergency stop.

Constraints

  • Emergency `VACUUM FREEZE` on an 800 GB table in single-user mode can take hours if indexes are scanned; minimize downtime.
  • Must not drop active production replication slots or corrupt WAL.
  • OLTP write throughput is ~3,500 TPS (~300M XIDs/day).
Known failure modes

Ignoring wraparound warnings until the hard 2B stop forces single-user recovery.

The invariants

  • Enter postgres --single.
  • Drop dead slot, raise vacuum_cost_limit, run VACUUM (FREEZE, INDEX_CLEANUP OFF).
  • Restart primary and run online VACUUM.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Default cost_limit=200 throttles vacuum to ~10-20 MB/s (designed for spinning HDDs); NVMe SSDs easily sustain cost_limit=4000 with cost_delay=2ms.

Step 1

Compute vacuum I/O budget: cost_limit / cost_delay * 8KB page costs.

SQL · Lifecycle trace
ALTER TABLE ledger_entries SET (autovacuum_vacuum_cost_limit = 4000, autovacuum_vacuum_cost_delay = 2);
Key trade-off

Higher cost_limit increases background I/O slightly while preventing multi-day vacuum backlogs.

04 / ImplementConfiguration & code

Build the safeguards.

Turn `hot_standby_feedback = off` on analytics replicas, set `max_standby_streaming_delay = '60s'` or `statement_timeout = '5min'`, and use logical replication/warehouse export for 14-hour BI jobs.

1. Reference implementation

SQL · Solution
SET vacuum_cost_limit = 10000;
VACUUM (FREEZE, INDEX_CLEANUP OFF) ledger_entries;

3. Operational controls

Step 1

Disable hot_standby_feedback on BI replicas.

Step 2

Enforce statement_timeout = '5min' for BI roles.

Implementation note

Skipping index cleanup cuts downtime from 22h to ~45m, at the cost of running an online VACUUM afterward.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Alert on `max(age(datfrozenxid)) > 500_000_000` (warning) and `> 1_000_000_000` (page), plus inactive replication slots and long transactions > 15 minutes.

  • ↗
    Export `pg_database_xid_age` and `pg_replication_slots_active` via postgres_exporter.
YAML · Verification
- alert: PostgresXidAgeHigh
  expr: pg_database_xid_age > 500000000
  for: 15m

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Enabling hot_standby_feedback on a BI replica effectively turns primary autovacuum off for hours.

Failure scenario 2

Alerting only at 1.9B leaves < 12 hours to vacuum an 800 GB table.

Alternatives considered

  • Daily cron check on `age(relfrozenxid)` top-10 tables.
