The idea to keep with you

Design an in-process thread-safe cache for a 64-core API server holding 10M entries (~8 GB, ~800 B/entry) at 1,200,000 `get()`/sec (95% reads, 5% writes) and < 50 us p99 latency. A single-lock `HashMap + DoublyLinkedList` collapses to 140K ops/sec because `get()` mutates the list. Add scan resistance and bounded TTL.

01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why classic LRU fails on 64-core servers.

Every textbook teaches HashMap + DoublyLinkedList for O(1) LRU. On a 64-core server handling 1,200,000 get()/sec (95% reads), get() is not read-only: it must unlink the node and move it to the MRU head—forcing a global write lock that caps throughput at ~140,000 ops/sec (>85% CPU spent spinning).

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Mutex convoying, one-hit scan pollution, and expired-key leaks.

Three bottlenecks destroy in-process cache performance:

  1. Global Write-Lock Contention: 64 threads serialize on one mutex (140k vs 1.2M ops/sec).
  2. One-Hit Scan Pollution: A batch job scanning 10M cold keys flushes the entire hot working set out of a pure LRU.
  3. Lazy-TTL Memory Leak: Keys that expire without being read again occupy the 8 GB budget unless swept.
W-TinyLFU + Striped Cache

1% Admission Window -> 4-bit Count-Min Sketch -> Segmented Main

Striped read ring buffers remove read-path locks while W-TinyLFU protects hot entries from sequential scans.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive `RWLock` and un-aged frequency counters.

A ReentrantReadWriteLock still requires an exclusive write lock on get() to mutate the LRU list. Meanwhile, a naive LFU without periodic counter halving lets historically hot keys permanently block newly hot keys.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Lock Striping / SIEVE + W-TinyLFU + Timing Wheel.

Scale to 1.2M+ ops/sec within 8 GB (~880 MB metadata + 7.12 GB payload):

  • Zero-Contention Read Path: Partition into 128 shards (78,125 entries and 9,375 ops/s per shard) + a Caffeine-style striped read ring buffer (drains promotions asynchronously under tryLock) or SIEVE (if (!node.visited) node.visited = true; avoids even dirtying the cache line on hot reads!).
  • Scan Resistance (W-TinyLFU): Admit new keys into a 1% Window LRU; on eviction, a 4-bit Count-Min Sketch (periodically halved) admits the candidate to Main SLRU only if its frequency beats the Main victim.
  • Active TTL: Hierarchical timing wheel sweeps expired entries in O(1).
Deferred Promotion & Eviction

Lock-Free Read Buffer Drain & W-TinyLFU Admission Filter

Readers never wait on list locks; a single tryLock drain updates LRU order and filters one-hit scans via CMS.

// SIEVE / Deferred-Read Pattern: avoid write-locking on hot reads
public V get(K key) {
    Node<K, V> node = map.get(key); // ConcurrentHashMap lock-free read
    if (node == null || node.isExpired(clock.millis())) return null;
    if (!node.visited) {
        node.visited = true; // Avoids cache-line bouncing on hot keys
    }
    readBuffer.offer(node);  // Lossy ring buffer drained asynchronously
    return node.value;
}
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where high-concurrency W-TinyLFU caches are used.

Caffeine (Java) and Ristretto/Otter (Go) implement this exact architecture:

  • L1 In-Process Caches: Sits in front of Redis/DB in high-QPS API servers to serve 95% hot reads in < 50 us.
  • Database & Storage Block Caches: RocksDB/CockroachDB Pebble use segmented/clock-pro caches to resist large range-scan pollution.
