Design a Distributed Rate Limiter

Design a rate limiter for a public API that enforces per-user and per-IP request limits at scale. The service must handle high throughput, be deployable across multiple data center regions, and gracefully degrade when the rate-limiting backend is unavailable.

Scope, Requirements & Constraints

Core tension: single-server counters don't work across nodes; distributed counters add network round-trips. The 2 ms latency budget is tight — a Redis call is typically 0.5–1 ms in the same data center. Algorithm choice (token bucket, fixed window, sliding window log, sliding window counter) affects accuracy, memory, and implementation complexity.

Core Functional Requirements

  • ✓Enforce per-user and per-IP rate limits (e.g., 1,000 requests/minute per user).
  • ✓Return a clear 429 response with retry-after headers when limits are exceeded.
  • ✓Support multiple limit windows (per-second, per-minute, per-hour).
  • ✓The limiter must work across multiple API server instances.
  • ✓Degrade gracefully: if the rate-limit store is unreachable, choose fail-open or fail-closed based on product policy.

Scale & Latency Constraints

  • —API receives ~500,000 requests/second at peak.
  • —Rate limit decisions must add ≤ 2 ms to request latency (p99).
  • —The limiter must be consistent across 10+ API nodes in a region.
  • —Configurable limits: different limits per API key tier (free, pro, enterprise).
  • —No shared memory between API processes — distributed counter required.

Reference Architecture & System Blueprint

Sliding window counter backed by Redis. Each incoming request: compute window boundaries → INCRBY the current window counter for the key (userId:windowStart) → read previous window counter → compute weighted count = prevCount × (remaining fraction of prev window) + currCount → if weighted count > limit, return 429.

System Architecture & Theory

Architectural Overview & Separation of Concerns

A distributed rate limiter enforces client request limits across multi-region edge gateways without introducing significant latency to request processing. Because API clusters receive hundreds of thousands of requests per second across dozens of container instances, local in-memory counters fail to maintain accurate global quotas. The system relies on atomic Redis execution via Lua scripts to eliminate race conditions within a sub-2ms latency budget.

Write Path Mechanics (Ingestion to Persistence)
1. Request Interception: Envoy sidecars intercept incoming HTTPS traffic at the API gateway layer. 2. gRPC Rate Limit Check: Envoy issues an asynchronous gRPC check to the Rate Limiter service cluster with `{ client_ip, user_id, api_key, endpoint }`. 3. Atomic Redis Evaluation: The limiter executes an atomic Lua script (`EVALSHA`) in Redis. The script calculates the sliding window counter: `current_count + previous_count * (1 - time_into_current_window / window_size)`. If the calculated count is below quota, the counter increments and returns allowed; otherwise, it returns the TTL until quota reset.
Scale Bottlenecks, Operational Hazards & Failure Modes
1. Fail-Open vs. Fail-Closed Resilience: If the Redis rate limiter cluster becomes unreachable or exceeds a 5ms timeout threshold, the gateway defaults to a configurable Fail-Open policy for non-critical endpoints, logging an alert while permitting traffic to preserve core business availability. 2. Hot Key Mitigation: For viral tenants or DDoS targets hitting the same rate key, local token buckets on gateway instances pre-filter excess bursts before querying Redis.
⚡ Architectural Invariant

Executing rate-limiting logic inside Redis Lua scripts eliminates distributed race conditions without requiring slow application-level locks.

Hardened Implementation Steps

  1. 1Request arrives at API node with userId and timestamp.
  2. 2Compute current 60-second window start: windowStart = floor(now / 60) * 60.
  3. 3Redis MULTI: INCR user:{userId}:{windowStart}, GET user:{userId}:{windowStart-60}, EXPIRE user:{userId}:{windowStart} 120.
  4. 4weightedCount = prevWindowCount × ((windowStart + 60 - now) / 60) + currWindowCount.
  5. 5If weightedCount > limit: set X-RateLimit-Remaining: 0, return 429 with Retry-After header.
  6. 6Else: decrement or allow — return 200 with X-RateLimit-Remaining header.

Key Decisions & Trade-Off Analysis

Architectural Decisions & Trade-Offs

  • ⚖Sliding window vs fixed window: Fixed window allows up to 2× burst at the boundary (last second of window N + first second of window N+1). Sliding window eliminates this at O(1) memory cost.
  • ⚖Redis vs local counter: Local is O(0ms) but each node allows limit requests independently — 10 nodes allow 10× limit. Redis adds ~1 ms but provides a shared accurate counter.
  • ⚖Fail-open (allow on Redis failure): Protects availability; risk: abuse during outage. Use for non-critical APIs or when abuse impact is low.
  • ⚖Fail-closed (block on Redis failure): Protects against abuse; risk: legitimate users blocked during outage. Use for billing/sensitive APIs.
  • ⚖Lua scripts for atomicity: Redis MULTI/EXEC provides optimistic locking; Lua scripts provide true atomicity. For rate limiting, a Lua script is preferred to avoid race between INCR and GET.

Scale Bottlenecks & Operational Hazards

Operational Hazards & Mitigations

  • ⚠Redis node failure: With Redis Sentinel or Cluster, replica promotion takes 10–30 s. During that window: fail-open (allow) or local fallback counter (allow up to local_limit = limit/node_count). Redis Cluster with consistent hashing for key distribution — each userId is pinned to one shard.
  • ⚠Hot user: A single userId key in Redis becomes a hot key, concentrating load on one Redis shard. Mitigation: replicate hot keys to N replicas and read-balance across them; or shard the counter across K sub-keys (userId:0..K-1) and sum them — introduces K reads per request.
  • ⚠Cross-region rate limiting: Each region maintains its own Redis counter. Eventual synchronization via async replication — allows up to sum(regional_limits) globally. True global rate limiting requires a global counter service (high latency) or token-bucket with quota allocation per region.

Changed Constraints & System Extension

New requirement: the API has 3 tiers — free (100 req/min), pro (1,000 req/min), enterprise (unlimited). Enterprise customers also get burst headroom of 50% for up to 10 seconds. How do you model this? Where does tier information come from?

Extension Implementation Steps

  1. 1Resolve tier from API key on each request — cache the key→tier mapping in local memory (5-minute TTL) to avoid DB round-trips.
  2. 2Look up limit for the resolved tier from a config store (environment variable, feature flag service, or DB with in-process cache).
  3. 3For enterprise burst: maintain a separate burst counter with a 10-second TTL. Allow up to limit * 1.5 for the burst window, then enforce normal limit.
  4. 4Pass the effective limit into the sliding window counter logic — same algorithm, different threshold.

Follow-Up Trade-Offs

  • ⚖Local API-key→tier cache: reduces DB load but has up to 5-minute lag on tier changes (acceptable for most plan upgrades).
  • ⚖Enterprise unlimited: skip the rate limiter entirely for unlimited-tier keys — reduces Redis calls. Risk: runaway client bugs consume infrastructure. Recommended: enforce a very high soft limit (e.g., 1M/min) and alert rather than truly unlimited.
