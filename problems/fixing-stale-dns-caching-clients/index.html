The idea to keep with you

Your payment orchestration service (Java 17 + Apache HttpClient 5 / Netty WebClient) communicates with an external partner's AWS Application Load Balancer (`api.partner-pay.com`, DNS TTL = 60s). When AWS scales or replaces the ALB nodes, the DNS A-records rotate to new IPs and the old ALB IPs are decommissioned 5 minutes later. However, your long-lived pods continue sending 100% of traffic to the dead IP for hours—triggering `ConnectTimeoutException` and `504 Gateway Timeout` until pods are manually restarted. Fix both the DNS cache layer and the persistent HTTP connection pool.

From patterns to decisions.

Java's default infinite/long DNS cache and unrecycled TLS keep-alive pools pin pods to decommissioned AWS ALB IPs; setting networkaddress.cache.ttl=30, connection max-lifetime=55s with jitter, and NodeLocal DNSCache ensures <=60s IP rotation without TLS storms.

01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why stale DNS breaks long-lived HTTP/2 and TLS clients.

When an external partner's AWS ALB (api.partner-pay.com, DNS TTL = 60 s) scales or rotates IPs, old IPs are drained and decommissioned 5 minutes later. Long-lived Java pods (200 pods × 100 persistent TLS connections) keep sending 100% of traffic to dead IPs—causing ConnectTimeoutException and 504 Gateway Timeout until pods are manually restarted.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens when DNS TTL and connection pools are unbounded.

Two independent caching layers pin traffic to dead ALB nodes:

  1. JVM InetAddress Cache: With a SecurityManager or older defaults, Java caches DNS forever; even with 30 s default, it only applies to new socket connections.
  2. Unbounded Keep-Alive Socket Lifetime: Existing TLS 1.3 sockets stay open indefinitely, never performing a new DNS lookup even after the JVM DNS cache expires.
Two-Layer IP Pinning

ALB IP Rotation: Pinned TLS Socket (504) vs. Bounded connTTL + DNS TTL

Bounding both JVM DNS TTL (30s) and pooled connection max-lifetime (55s + jitter) rotates traffic within 60s without TLS storms.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive solution (and why Connection: close or TTL=0 fails).

Setting Connection: close or networkaddress.cache.ttl=0 trades outages for latency and CoreDNS saturation:

  • TLS 1.3 Handshake Tax: Disabling keep-alive adds ~18 ms RTT to every single partner call.
  • CoreDNS Flood: 200 pods resolving uncached DNS on every request blows past the < 2,000 QPS CoreDNS budget.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: JVM DNS TTL=30s + Jittered connTTL + NodeLocal DNS.

Production Java clients combine three coordinated settings:

  • 1. Bounded JVM DNS Cache: Set Security.setProperty('networkaddress.cache.ttl', '30') and networkaddress.cache.negative.ttl=5 (respecting the 60s ALB TTL).
  • 2. Jittered Connection Max-Lifetime (connTTL): Configure Apache HttpClient 5 (TimeValue.ofSeconds(55 + jitter)) or Netty ConnectionProvider.maxLifeTime(55s) so persistent TLS sockets recycle gracefully across 55–75 s—avoiding synchronized TLS handshake spikes.
  • 3. NodeLocal DNSCache + Multi-IP Failover: Absorb 200-pod DNS refreshes on-node (< 1 ms) and enable Happy Eyeballs / retry-on-connect-timeout across multiple returned A-records.
Coordinated DNS & Pool Recycling

NodeLocal DNS -> JVM Cache (30s) -> Jittered connTTL (55-75s)

1.JVM DNS TTL=30s: Refreshes A-records within half the 60s ALB DNS TTL.

2.Jittered connTTL: Staggers TLS 1.3 reconnects across 55–75s to prevent handshake storms.

3.NodeLocal Cache: Keeps CoreDNS well under the 2,000 QPS external lookup budget.

4.Connect Retry: Safe idempotent retry on ConnectTimeoutException tries next ALB IP.

Coordinating DNS TTL, jittered connection max-lifetime, and NodeLocal DNS achieves <= 60s failover with minimal TLS overhead.

// 1. Bound JVM DNS cache (startup)
java.security.Security.setProperty("networkaddress.cache.ttl", "30");
java.security.Security.setProperty("networkaddress.cache.negative.ttl", "5");

// 2. Apache HttpClient 5 / Netty: bound connection max-lifetime so sockets re-resolve DNS
var connManager = PoolingHttpClientConnectionManagerBuilder.create()
    .setDefaultConnectionConfig(ConnectionConfig.custom()
        .setConnectTimeout(Timeout.ofMilliseconds(500))
        .setTimeToLive(TimeValue.ofSeconds(55 + ThreadLocalRandom.current().nextInt(20))) // jittered
        .build())
    .setMaxConnPerRoute(100)
    .build();
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where DNS & Connection Lifecycle Alignment applies.

Coordinated DNS + connection-pool TTLs are critical whenever talking to elastic cloud endpoints:

  • AWS ALB / NLB & CloudFront Integrations: Following elastic load balancer node scaling without 504s.
  • Multi-Region DNS Failover: Ensuring Route53 health-checked failover propagates to long-lived microservices in < 60 s.
  • gRPC & HTTP/2 Clients: Combining MAX_CONNECTION_AGE on servers with client-side DNS re-resolution.
