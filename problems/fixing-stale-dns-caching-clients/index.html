Fixing Stale DNS Caching
in Long-Lived Clients.

01 / UnderstandFailure & constraints

Clarify what is failing.

Keep-alive TCP/TLS connections only perform DNS resolution at socket creation; an already-open socket continues sending bytes to the old IP until closed.

Design objective

Check `java.security` / JVM flags for `networkaddress.cache.ttl`.

Requirements

  • Ensure pods discover rotated upstream ALB IPs within <= 60 seconds without restarts.
  • Recycle long-lived TLS/HTTP2 keep-alive connections so pinned TCP sockets do not outlive DNS TTL.
  • Prevent CoreDNS/upstream resolver flooding when 200 pods refresh DNS simultaneously.
  • Fail over cleanly if one of multiple returned A-records becomes unreachable.

Constraints

  • 200 application pods each maintain up to 100 persistent TLS connections to the partner ALB.
  • TLS 1.3 handshake adds ~18ms RTT, so disabling keep-alive (`Connection: close`) is unacceptable.
  • CoreDNS cluster budget limits external DNS queries to < 2,000 QPS.
Known failure modes

Setting `Security.setProperty` after Spring Boot initializes `InetAddress` has no effect.

Separate concerns. Map the flow.

Combine `networkaddress.cache.ttl=30` with `setTimeToLive(60s)` and `connectTimeout(2s)` so sockets recycle gracefully and re-resolve DNS.

Active Healthy Target

  1. 01Steady-State Reuse: Pod reuses persistent TLS 1.3 connection to 10.0.1.5 for up to 60s (+/- 15s jitter).
  2. 02Graceful Socket Eviction: After 60s, pool closes idle/completed socket instead of returning it, triggering fresh connect.
  3. 03Fresh DNS Lookup: JVM DNS cache (TTL=30s) has expired; pod queries NodeLocal DNSCache and receives 10.0.2.9.
  4. 04Connect to New IP: Pool opens new persistent connection to 10.0.2.9 before 10.0.1.5 is terminated.
  5. 05Fast-Fail Retry: If 10.0.1.5 dies mid-window, 2s connectTimeout + idempotent retry hits 10.0.2.9 immediately.
Both DNS cache TTL and HTTP connection pool lifetime must be bounded so long-lived pods converge onto rotated ALB IPs.

The invariants

  • Set JVM networkaddress.cache.ttl=30 and negative.ttl=1 via JAVA_TOOL_OPTIONS.
  • Set timeToLive=60s and maxIdleTime=20s on PoolingHttpClientConnectionManager.
  • Set connectTimeout=2s so dead IPs fail fast instead of hanging for 30s.
03 / Trace the lifecycleKey decisions

Follow the execution path.

HTTP/2 multiplexes all concurrent requests onto a single TCP connection, so one stale socket pins 100% of a pod's traffic to a single backend IP.

Step 1

Verify protocol negotiation (ALPN h2 vs http/1.1).

Step 2

Enforce GOAWAY / connection rotation via maxLifeTime or sidecar Envoy.

YAML · Lifecycle trace
# Envoy cluster config for HTTP/2 upstream
common_http_protocol_options:
  max_connection_duration: 60s
dns_refresh_rate: 30s
lb_policy: ROUND_ROBIN
Key trade-off

Envoy strict_dns + max_connection_duration handles rotation uniformly across Java, Python, and Go services.

04 / ImplementConfiguration & code

Build the safeguards.

Deploy Kubernetes `NodeLocal DNSCache` and jitter connection lifetimes so DNS lookups are served locally from node memory over TCP/UDP.

1. Reference implementation

JAVA · Solution
ConnectionConfig.custom()
    .setConnectTimeout(Timeout.ofSeconds(2))
    .setTimeToLive(TimeValue.ofSeconds(60))
    .setValidateAfterInactivity(TimeValue.ofSeconds(5))
    .build();

2. Harden for scale

Deploy Kubernetes `NodeLocal DNSCache` and jitter connection lifetimes so DNS lookups are served locally from node memory over TCP/UDP.

YAML · Scale hardening
.:53 {
    cache 30 {
        serve_stale 5m
    }
    forward . /etc/resolv.conf
}

3. Operational controls

Step 1

Enable `NodeLocal DNSCache` DaemonSet (`169.254.20.10`) to bypass `kube-proxy` conntrack.

Step 2

Enable CoreDNS `cache 30` with `serve_stale`.

Implementation note

60s `timeToLive` costs ~1.6 TLS handshakes/sec per pod while guaranteeing < 60s ALB IP convergence.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Run a chaos test that updates a mock DNS A-record to IP2, waits 60s, then drops packets to IP1 via `iptables` while asserting 0% 5xx rate.

PYTHON · Verification
# Synthetic chaos assertion
assert error_rate_during_ip_drain < 0.001, f'Stale IP pinning detected: {error_rate_during_ip_drain}'

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Align DNS resolution TTL (networkaddress.cache.ttl=30), cap HTTP connection maxConnectionLifeTime (60s), and enable proactive DNS refresh in Netty/HttpClient.
  • 02Trade-off tip: Envoy strict_dns + max_connection_duration handles rotation uniformly across Java, Python, and Go services.
  • 03Watch out for: Linux conntrack table exhaustion on high-QPS UDP DNS queries without NodeLocal DNSCache.
