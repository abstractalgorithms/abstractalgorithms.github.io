Preventing Cache Avalanche
with TTL Jitter.

When tens of thousands of hot cache keys are warmed together with an identical fixed TTL (e.g., 3600s), they expire simultaneously, unleashing a massive thundering herd onto the database that exhausts connection pools and triggers cascading 504s.

01 / UnderstandFailure & constraints

Clarify what is failing.

Uniform `EX 3600` synchronized all 120,000 expirations into 1 second, flipping 70,000 QPS of cache hits into simultaneous DB misses that saturated PgBouncer's 400 connections.

Design objective

Calculate the miss surge: 80,000 QPS * 88% miss rate = 70,400 QPS hitting PostgreSQL.

Requirements

  • Eliminate synchronized mass key expiration spikes across both batch-warmed and lazy-loaded keys.
  • Ensure at most 1 database query per expired hot key per app instance (or cluster) during cache rebuilds.
  • Serve graceful stale responses if PostgreSQL latency exceeds 150ms during a cache-miss surge.
  • Keep p99 catalog API latency under 25ms across the 01:00:00 UTC expiration boundary.

Constraints

  • Redis 7 cluster has 64 GB RAM; PostgreSQL primary + 2 read replicas cap at 4,000 QPS combined.
  • Catalog staleness of up to 60 seconds is acceptable for product descriptions and ratings (not live inventory).
  • Application tier runs 40 stateless Python (FastAPI) or Java (Spring Boot) pods.
Known failure modes

Complete DB connection exhaustion every hour on the hour.

Trips on DB p99 > 150ms

  1. 01Read With Logical Soft-TTL: Pod fetches `{data, soft_exp}` from Redis. Hard TTL is `base_ttl * 2 + jitter(0, 720s)`.
  2. 02Serve Stale Immediately: If `now > soft_exp`, pod returns cached `data` in <2ms and triggers async background refresh.
  3. 03Coalesce Concurrent Refreshes: In-process singleflight ensures at most 1 background DB query per pod per expired key.
  4. 04Bounded Origin Refresh: Leader coroutine queries PostgreSQL and writes back to Redis with fresh `soft_exp` and jittered `hard_ttl`.
  5. 05Degrade Gracefully on DB Stress: If DB latency > 150ms, circuit breaker opens and serves stale L1/Redis entries instead of 504s.
Decoupling logical `soft_exp` from jittered Redis `hard_ttl` + in-process `singleflight` turns a 70,000 QPS cliff into a flat ~167 QPS background trickle.

The invariants

  • Store {"data": val, "soft_exp": now + base_ttl + jitter} with Redis ex = base_ttl * 2 + jitter.
  • If now > soft_exp on hit, return data immediately and trigger singleflight background refresh.
  • On hard miss, await the shared inflight[key] Future.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Caffeine `refreshAfterWrite` protects each pod's L1 cache with zero network hops, while Redis Soft-TTL shares refreshed data across all 40 pods and caps total DB rebuilds.

Step 1

Use L1 Caffeine/LRU (short 60s TTL, ~256MB) for ultra-hot keys and Redis outage survival.

Step 2

Use Redis Soft-TTL as the shared L2 source of truth across all 40 pods.

Step 3

Optionally add a Redis SETNX lock:key 1 EX 2 inside _singleflight_refresh so even across 40 pods only 1 pod queries DB.

04 / ImplementConfiguration & code

Build the safeguards.

L1 in-memory LRU absorbs immediate traffic, PgBouncer + DB semaphore caps concurrent origin queries, and a circuit breaker serves stale L1 or degraded responses when DB latency exceeds 150ms.

1. Reference implementation

PYTHON · Solution
import asyncio, json, random, time

inflight: dict[str, asyncio.Future] = {}

async def get_product(redis, db, key: str, base_ttl: int = 3600):
    raw = await redis.get(key)
    now = time.time()
    if raw:
        payload = json.loads(raw)
        if now > payload["soft_exp"] and key not in inflight:
            asyncio.create_task(_singleflight_refresh(redis, db, key, base_ttl))
        return payload["data"]
    return await _singleflight_refresh(redis, db, key, base_ttl)

async def _singleflight_refresh(redis, db, key: str, base_ttl: int):
    if key in inflight:
        return await inflight[key]
    fut = asyncio.get_running_loop().create_future()
    inflight[key] = fut
    try:
        data = await asyncio.wait_for(db.fetch_product(key), timeout=0.5)
        jitter = random.randint(0, int(base_ttl * 0.2))
        payload = {"data": data, "soft_exp": time.time() + base_ttl + jitter}
        await redis.set(key, json.dumps(payload), ex=base_ttl * 2 + jitter)
        fut.set_result(data)
        return data
    except Exception as exc:
        fut.set_exception(exc)
        raise
    finally:
        inflight.pop(key, None)

2. Harden for scale

PYTHON · Scale hardening
db_sem = asyncio.Semaphore(10)

async def protected_db_fetch(db, l1_cache, key):
    if db_sem.locked() and key in l1_cache:
        return l1_cache[key]  # Shed load to L1 stale
    async with db_sem:
        return await asyncio.wait_for(db.fetch_product(key), timeout=0.5)

3. Operational controls

Step 1

Enable Redis AOF (`appendfsync everysec`) + replica failover so shard restarts rarely lose data.

Step 2

Cap per-pod DB concurrency with an `asyncio.Semaphore(10)` (40 pods * 10 = 400 max DB conns).

Step 3

When DB p99 > 150ms, circuit breaker opens and serves L1 stale entries.

Implementation note

Doubles Redis TTL window (more memory) in exchange for zero latency spikes on expiration.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

XFetch triggers a probabilistic refresh before TTL expiry weighted by the key's recompute duration `delta`, ensuring the hottest keys refresh early without waiting for an exact `soft_exp` boundary.

  • ↗
    Store `delta` (last DB fetch duration in seconds) alongside `expiry` in Redis.
  • ↗
    On read, evaluate `time.time() - delta * beta * math.log(random.random()) >= expiry`.
  • ↗
    Because `-ln(rand())` is positive, higher `delta` or closer `expiry` increases refresh probability smoothly.
PYTHON · Verification
import math, random, time

def should_xfetch_refresh(expiry: float, delta_sec: float, beta: float = 1.0) -> bool:
    # Random value in (0, 1]; -ln(u) is exponential distribution
    u = max(random.random(), 1e-9)
    return (time.time() - delta_sec * beta * math.log(u)) >= expiry

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Without a semaphore, 40 pods can still open thousands of waiting coroutines against PgBouncer.

Failure scenario 2

If `delta_sec` is 0 or unrecorded, XFetch degrades to standard hard-TTL expiration.

Alternatives considered

  • Fixed `soft_exp` + `singleflight` (simpler to debug).
