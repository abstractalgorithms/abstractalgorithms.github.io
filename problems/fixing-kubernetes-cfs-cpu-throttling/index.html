Fixing Kubernetes CFS
CPU Throttling Freezes.

01 / UnderstandFailure & constraints

Clarify what is failing.

Linux CFS gives a `2` CPU pod 200ms of CPU time per 100ms wall-clock period. 16 parallel threads consume 200ms in 12.5ms, freezing the entire pod for the remaining 87.5ms.

Design objective

Compute `cpu.cfs_quota_us` (200,000) / `cpu.cfs_period_us` (100,000).

Requirements

  • Bring payment gateway p99 latency below 15ms under peak load.
  • Eliminate 75ms+ CFS throttling pauses without over-provisioning nodes by 10x.
  • Ensure JVM thread pools (Netty, ForkJoinPool, G1GC) do not over-allocate threads for 64 host cores.
  • Maintain noisy-neighbor isolation on shared Kubernetes worker nodes.

Constraints

  • Kubernetes 1.28+ on Linux kernel 5.15+ (cgroup v2).
  • 64-vCPU worker nodes running mixed microservices.
  • Service requires 2 vCPUs of sustained compute at peak.
Known failure modes

GC pauses and Netty event-loop stalls cascade into upstream timeouts.

The invariants

  • Set requests.cpu: "2" and remove limits.cpu for zero CFS throttling.
  • Add JAVA_TOOL_OPTIONS with -XX:ActiveProcessorCount=2 and bounded GC threads.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Use either (1) `Guaranteed` QoS with integer CPUs + kubelet `--cpu-manager-policy=static` (bypasses CFS quota via `cpuset`), or (2) `CustomCPUCFSQuotaPeriod` reducing `cpuCFSQuotaPeriod` from 100ms to 5ms.

Step 1

Configure cpuManagerPolicy: static in KubeletConfiguration for exclusive core pinning.

Step 2

Alternatively set cpuCFSQuotaPeriod: 5ms so any freeze is <= 3.75ms.

YAML · Lifecycle trace
# KubeletConfiguration for strict limits without 90ms freezes
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
cpuManagerPolicy: static
cpuCFSQuota: true
cpuCFSQuotaPeriod: 5ms
Key trade-off

static CPU Manager requires integer CPU requests (2, not 1500m) and Guaranteed QoS (requests == limits for both CPU and memory).

04 / ImplementConfiguration & code

Build the safeguards.

In Go, use `uber-go/automaxprocs` (reads cgroup CPU quota and sets `GOMAXPROCS=2` instead of 64). In Python/Gunicorn, size `--workers` and `OMP_NUM_THREADS` to the CPU request.

1. Reference implementation

YAML · Solution
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-gateway
spec:
  template:
    spec:
      containers:
        - name: gateway
          image: payment-gateway:2.4.1
          env:
            - name: JAVA_TOOL_OPTIONS
              value: "-XX:ActiveProcessorCount=2 -XX:ParallelGCThreads=2 -XX:ConcGCThreads=1"
          resources:
            requests:
              cpu: "2"
              memory: "4Gi"
            limits:
              memory: "4Gi"
              # cpu limit intentionally omitted to prevent CFS throttling freezes

2. Harden for scale

In Go, use `uber-go/automaxprocs` (reads cgroup CPU quota and sets `GOMAXPROCS=2` instead of 64). In Python/Gunicorn, size `--workers` and `OMP_NUM_THREADS` to the CPU request.

PYTHON · Scale hardening
import math
from pathlib import Path

def cgroup_cpu_limit(default: int = 2) -> int:
    cpu_max = Path("/sys/fs/cgroup/cpu.max")
    if cpu_max.exists():
        quota, period = cpu_max.read_text().strip().split()
        if quota != "max":
            return max(1, math.ceil(int(quota) / int(period)))
    return default

3. Operational controls

Step 1

Avoid reading `os.cpu_count()` (returns 64 host cores) when sizing Gunicorn/Uvicorn/ThreadPoolExecutor.

Step 2

Read `/sys/fs/cgroup/cpu.max` in Python to cap worker/thread pools dynamically.

Implementation note

Zero CFS throttling; pod is guaranteed 2 cores via `cpu.weight` under contention and can burst when host is idle.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Alert on the ratio of throttled periods (`container_cpu_cfs_throttled_periods_total / container_cpu_cfs_periods_total > 0.05`) and total throttled time (`container_cpu_cfs_throttled_seconds_total`).

  • ↗
    Monitor both `throttled_periods` ratio (>5%) and `throttled_seconds` rate.
  • ↗
    Correlate spikes directly against service `http_request_duration_seconds` p99.
YAML · Verification
# PrometheusRule for CFS CPU throttling
- alert: HighContainerCPUThrottling
  expr: |
    (
      rate(container_cpu_cfs_throttled_periods_total{container!=""}[2m])
      /
      rate(container_cpu_cfs_periods_total{container!=""}[2m])

  for: 5m
  labels:
    severity: warning

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Know what each control buys.

Review questions

Failure scenario 1

`os.cpu_count()` in Python ignores cgroup v2 `cpu.max` and returns 64.

Failure scenario 2

Division by zero on idle containers with `container_cpu_cfs_periods_total == 0` unless filtered.

Alternatives considered

  • Read `/sys/fs/cgroup/cpu.stat` `throttled_usec` directly via OpenTelemetry hostmetrics.
