Design a Distributed Key-Value Store

Design a distributed, highly available key-value store similar to DynamoDB or Cassandra. The system must support put(key, value) and get(key) across multiple storage nodes with configurable consistency, automatic data partitioning, and failure recovery.

Scope, Requirements & Constraints

Distributed KV stores partition data across nodes using Consistent Hashing, replicate each key across N nodes, and use quorum voting (R + W > N) for strong consistency or eventual consistency.

Core Functional Requirements

  • ✓put(key, value): store or update key-value pair.
  • ✓get(key): retrieve value associated with key.
  • ✓High availability and fault tolerance: survive node failures without data loss.
  • ✓Horizontal scalability: scale storage and throughput by adding nodes.
  • ✓Tunable consistency: support configurable R (read quorum) and W (write quorum).

Scale & Latency Constraints

  • —Key size: up to 256 bytes; value size: up to 1 MB.
  • —Low latency: p99 read and write under 10 ms within same datacenter.
  • —Handle network partitions (CAP theorem AP system with eventual consistency).

Reference Architecture & System Blueprint

Dynamo-style decentralized architecture with Consistent Hashing ring and virtual nodes.

Hardened Implementation Steps

  1. 1Consistent Hash Ring: Map key to ring position using hash(key). The first N distinct physical nodes clockwise from the key position store replicas.
  2. 2Virtual Nodes (tokens): Each physical node owns V virtual positions on the ring to distribute data uniformly.
  3. 3Write Path: Coordinator sends write to all N replicas. Waits for W ACKs before returning success. On local node: write to Commit Log (WAL) -> MemTable in RAM -> flush to SSTables on disk (LSM-Tree).
  4. 4Read Path: Coordinator requests data from R replicas. Compares version timestamps/vector clocks. Returns most recent version and triggers read repair asynchronously.

Key Decisions & Trade-Off Analysis

Quorum configurations and conflict resolution.

Architectural Decisions & Trade-Offs

  • ⚖R + W > N (Strong Consistency): At least one node in read quorum overlaps with write quorum, guaranteeing the latest value is read.
  • ⚖W=1, R=1, N=3 (Eventual Consistency / Fast): Low latency and high availability, but high risk of reading stale data.
  • ⚖Last-Write-Wins (LWW) vs Vector Clocks: LWW uses wall-clock timestamps (simple, but clock drift can overwrite valid concurrent writes). Vector Clocks preserve concurrent versions for client reconciliation, but add metadata size.

Scale Bottlenecks & Operational Hazards

Operational Hazards & Mitigations

  • ⚠Hinted Handoff: During node outage, neighboring nodes store writes tagged with a hint. When the node recovers, neighbors deliver the hinted writes.
  • ⚠Anti-Entropy with Merkle Trees: Nodes compare hierarchical hash trees (Merkle Trees) of their key ranges. Only branches with differences are synchronized across the network, minimizing transfer bandwidth.
  • ⚠Gossip Protocol failure detection: Nodes exchange heartbeats randomly with neighbors. If a node fails to heartbeat within timeout, consensus marks it down without central health monitor.

Changed Constraints & System Extension

Follow-up: How do you handle Hot Partitions where a single celebrity key receives 100,000 writes/sec?

Extension Implementation Steps

  1. 1Salting: append random suffix (key_0 to key_K) to scatter writes across multiple ring partitions.
  2. 2Read aggregation: read all K salted keys and merge values.
  3. 3In-memory write buffering: absorb writes in an edge cache (Redis) and flush to KV store in batch.

Follow-Up Trade-Offs

  • ⚖Salting increases write throughput for hot keys, but scatters reads across K queries.
