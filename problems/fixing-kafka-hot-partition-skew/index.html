Hot-Partition Skew.

01 / UnderstandFailure & constraints

Clarify what is failing.

Kafka's default Murmur2 partitioner maps a single key ('acme-corp') to a single partition regardless of total partition count, and a partition can only be consumed by one consumer thread in a group.

Design objective

Verify Murmur2('acme-corp') % N always produces a single target partition.

Requirements

  • Eliminate the single-partition bottleneck so no partition exceeds 2x the cluster average throughput (~1,560 msg/s).
  • Preserve per-tenant 1-minute tumbling window aggregations accurately even when a tenant's events span multiple partitions.
  • Keep strictly ordered sub-entities (e.g., user_id within tenant_id) ordered where needed.
  • Support dynamic onboarding of new whale tenants without requiring topic recreation.

Constraints

  • Total cluster throughput is 25,000 events/sec (~25 MB/s) across 32 partitions and 32 consumer threads.
  • A single consumer thread maxes out at ~2,200 events/sec due to JSON parsing and enrichment.
  • Zero data loss during key-strategy migration.
Known failure modes

Adding partitions without changing keys wastes broker file descriptors while partition 14 remains 100% saturated.

The invariants

  • Check if key (tenant_id) is in hotTenants map (with spread factor K=16).
  • Extract user_id from headers or composite key 'tenant_id:user_id'.
  • Compute (basePartition + Murmur2(user_id) % K) % numPartitions.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Key salting reuses existing consumer pods and infrastructure uniformly, whereas dedicated topics provide stronger blast-radius isolation at the cost of per-tenant topic/deployment sprawl.

Step 1

Evaluate ops overhead: 1 topic + dynamic map vs N custom topics + N consumer deployments.

Step 2

Evaluate noisy-neighbor isolation: dedicated topic protects SLA-bound small tenants from whale bursts.

Step 3

Choose salting for 5-50 whale tenants; choose dedicated tier topics for massive enterprise isolation.

# Stage 2 Reducer (Python) merging salted 1-minute partials by tenant_id
def merge_partials(partials):
    totals = {}
    for p in partials:
        key = (p["tenant_id"], p["window_start"])
        totals[key] = totals.get(key, 0) + p["count"]
    return totals
Key trade-off

Dedicated topics prevent a whale burst from filling shared partition queues, but complicate consumer autoscaling.

04 / ImplementConfiguration & code

Build the safeguards.

Push hot-tenant spread updates dynamically via a lightweight config topic or feature-flag SDK so producers expand K from 16 to 32 in seconds without restarts.

1. Reference implementation

JAVA · Solution
public class HotTenantAwarePartitioner implements Partitioner {
    private final ConcurrentHashMap<String, Integer> hotTenantSpread = new ConcurrentHashMap<>(Map.of("acme-corp", 16));

    @Override
    public int partition(String topic, Object key, byte[] keyBytes, Object value, byte[] valueBytes, Cluster cluster) {
        int numPartitions = cluster.partitionCountForTopic(topic);
        String rawKey = new String(keyBytes, StandardCharsets.UTF_8);
        String[] parts = rawKey.split(":", 2); // format: tenant_id:user_id
        String tenantId = parts[0];
        int base = Utils.toPositive(Utils.murmur2(tenantId.getBytes(StandardCharsets.UTF_8))) % numPartitions;
        int spread = hotTenantSpread.getOrDefault(tenantId, 1);
        if (spread <= 1) return base;
        int subHash = parts.length > 1
            ? Utils.toPositive(Utils.murmur2(parts[1].getBytes(StandardCharsets.UTF_8)))
            : ThreadLocalRandom.current().nextInt(spread);
        return (base + (subHash % spread)) % numPartitions;
    }
    @Override public void close() {}
    @Override public void configure(Map<String, ?> configs) {}
}

2. Harden for scale

Push hot-tenant spread updates dynamically via a lightweight config topic or feature-flag SDK so producers expand K from 16 to 32 in seconds without restarts.

JAVA · Scale hardening
// Dynamic update hook in CustomPartitioner
public void updateSpread(String tenantId, int newSpread) {
    hotTenantSpread.put(tenantId, Math.max(1, newSpread));
}

3. Operational controls

Step 1

Publish updated {tenant_id: spread_factor} to a compacted config topic or Consul/etcd.

Step 2

CustomPartitioner updates hotTenantSpread ConcurrentHashMap live.

Step 3

Scale consumer pods/partitions if total cluster rate exceeds 32 * 2,200 = 70,400 msg/s.

Implementation note

Using tenant_id:user_id preserves per-user FIFO while balancing 17,000 msg/s across 16 partitions.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Compare max partition lag against median partition lag and track broker-level BytesInPerSec per partition.

  • ↗
    Export per-partition lag via Burrow or kafka_exporter.
  • ↗
    Alert when max(lag) > 50,000 AND max(lag) > 5 * avg(lag).
  • ↗
    Alert on per-partition BytesInPerSec > 3x cluster partition mean.

  for: 2m

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
