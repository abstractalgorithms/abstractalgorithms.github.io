01 / UnderstandFailure & constraints

Clarify what is failing.

All three dependencies shared a single 200-thread Tomcat pool and a single 200-connection HttpClient pool, allowing 10-second hangs in one service to consume 100% of shared capacity.

Design objective

Compute saturation time: 60 req/s per pod * 10s hang = 600 threads needed, exhausting the 200-slot pool in ~3.3s.

Requirements

  • Guarantee that a complete stall in `RecommendationService` causes 0% availability loss and < 10 ms p99 latency impact on `InventoryService` and `PricingService`.
  • Partition both execution concurrency (threads/semaphores) and underlying TCP/HTTP connection pools per downstream dependency.
  • Return a degraded `/checkout/summary` response (e.g., cached or empty recommendations) when the recommendation bulkhead or circuit breaker trips.
  • Size each partition mathematically using Little's Law (`concurrency = RPS * latency`) with headroom for p99 bursts.

Constraints

  • Total BFF pod CPU/memory limits allow max 250 total worker/async threads per instance across 20 pods (60 req/s per pod).
  • Downstream `InventoryService` and `PricingService` SLAs require strict 150 ms and 200 ms timeouts respectively.
  • The BFF is implemented in Java (Spring Boot / Resilience4j).
Known failure modes

Forgetting to isolate the HTTP connection pool when adding thread-pool bulkheads.

  1. 01Dispatch critical Inventory call: Runs on dedicated Inventory ThreadPoolBulkhead & HttpClient; unaffected by Recommendation stalls.
  2. 02Dispatch critical Pricing call: Runs on dedicated Pricing ThreadPoolBulkhead & HttpClient with 200ms socket timeout.
  3. 03Contain Recommendation blast radius: At most 16 threads + 4 queued tasks can block on RecommendationService; 17th fails fast.
  4. 04Trip Circuit Breaker & degrade: After 50% timeouts over 20 calls, CircuitBreaker opens for 15s and returns cached/empty recommendations in 0ms.
  5. 05Serve 200 OK Checkout Summary: Customer completes checkout seamlessly with Inventory + Pricing intact.
Each downstream dependency has its own ThreadPoolBulkhead, dedicated HttpClient pool, strict timeout, and circuit breaker.

The invariants

  • Define resilience4j.thread-pool-bulkhead for inventory (16), pricing (20), and reco (16, queue=4).
  • Configure resilience4j.timelimiter (250ms for reco) and circuitbreaker (50% failure/slow-call rate).
  • Annotate or wrap the recommendation call with a fallback returning cached/empty list.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Use `SemaphoreBulkhead` for non-blocking reactive/async calls (or Java 21 virtual threads) where thread context-switching is pure overhead; use `ThreadPoolBulkhead` when calling blocking synchronous I/O.

Step 1

Explain that SemaphoreBulkhead executes on the caller thread and only decrements an atomic permit counter.

Step 2

Note that with blocking I/O, a caller thread waiting on a slow socket still blocks inside the semaphore until the socket timeout fires.

Step 3

With non-blocking Netty/WebClient, SemaphoreBulkhead caps in-flight requests cleanly without extra threads.

YAML · Lifecycle trace
resilience4j.bulkhead:
  instances:
    recoAsync:
      maxConcurrentCalls: 16
      maxWaitDuration: 10ms # fail fast without blocking caller thread
Key trade-off

SemaphoreBulkhead has zero thread-pool overhead and preserves ThreadLocal automatically, but cannot interrupt a hung non-reactive socket.

04 / ImplementConfiguration & code

Build the safeguards.

Partition bulkheads by shard/tenant or pair the bulkhead with a per-endpoint outlier detector so 1 bad shard doesn't consume all 16 inventory threads.

1. Reference implementation

JAVA · Solution
import io.github.resilience4j.bulkhead.ThreadPoolBulkhead;
import io.github.resilience4j.bulkhead.ThreadPoolBulkheadConfig;
import io.github.resilience4j.circuitbreaker.CircuitBreaker;
import java.time.Duration;
import java.util.Collections;
import java.util.List;
import java.util.concurrent.CompletableFuture;

public class CheckoutAggregator {
    private final ThreadPoolBulkhead recoBulkhead = ThreadPoolBulkhead.of("reco", ThreadPoolBulkheadConfig.custom()
        .coreThreadPoolSize(8).maxThreadPoolSize(16).queueCapacity(4)
        .keepAliveDuration(Duration.ofSeconds(30)).build());
    private final CircuitBreaker recoBreaker = CircuitBreaker.ofDefaults("reco");

    public CompletableFuture<List<String>> fetchRecommendations(String userId) {
        return recoBulkhead.executeSupplier(
            CircuitBreaker.decorateSupplier(recoBreaker, () -> recoHttpClient.getRecos(userId))
        ).toCompletableFuture().exceptionally(ex -> Collections.emptyList());
    }
}

2. Harden for scale

Partition bulkheads by shard/tenant or pair the bulkhead with a per-endpoint outlier detector so 1 bad shard doesn't consume all 16 inventory threads.

YAML · Scale hardening
# Envoy / service-mesh outlier detection complements app bulkheads
outlier_detection:
  consecutive_5xx: 5
  interval: 5s
  base_ejection_time: 30s
  max_ejection_percent: 30

3. Operational controls

Step 1

If calling shards directly, use per-shard connection pools + Envoy/client outlier detection.

Step 2

Add hedged requests or fast 150 ms timeouts so a single bad shard doesn't hold all 16 threads.

Implementation note

Dedicated threads per pool add ~1 MB stack memory per thread (52 MB total), which is negligible for 2–4 GB JVM pods.

Prove the fix works.

  • ↗

# Prometheus alert for bulkhead saturation

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Ejecting >50% of shards during a global spike causes cascading overload on remaining healthy shards.

Failure scenario 2

Alerting only on HTTP 5xx hides that 100% of users are seeing degraded empty recommendations.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Partition thread pools, semaphores, and HTTP connection pools per downstream dependency—and pair them with strict timeouts, circuit breakers, and fallback responses—so a failing non-critical service cannot starve critical paths.
  • 02Trade-off tip: SemaphoreBulkhead has zero thread-pool overhead and preserves ThreadLocal automatically, but cannot interrupt a hung non-reactive socket.
  • 03Watch out for: Ejecting >50% of shards during a global spike causes cascading overload on remaining healthy shards.
