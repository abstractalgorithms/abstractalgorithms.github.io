01 / UnderstandFailure & constraints

Clarify what is failing.

Inverted timeouts (90s downstream > 60s gateway) created zombie work, while 3x retries at multiple hops multiplied load by 9x and starved shared pools.

Design objective

Explain zombie work: Gateway returned 504 at 60s while Order/Pricing kept holding threads for 90s.

Requirements

  • Eliminate wasted downstream work on requests whose API Gateway deadline has already expired
  • Cap retry amplification below 1.1x (10% retry budget) during downstream slowdowns
  • Isolate the slow `/orders` path so unrelated `/catalog` and `/profile` endpoints stay at 99.99% availability
  • Ensure consistent, monotonically decreasing timeout budgets across all 4 hops

Constraints

  • Synchronous REST/gRPC call chain; cannot rewrite `/orders` to async event-driven in this incident response
  • API Gateway SLA for `POST /orders` is 5 seconds max
  • 2,500 RPS baseline across 30 pods per service
Known failure modes

Client SDK retries on `504` add another 3x layer on top of service retries

02 / Map the systemArchitecture & invariants

Separate concerns. Map the flow.

Use Envoy `retry_budget: 10%` with per-route circuit breakers, propagate relative remaining TTL, and clamp DB `statement_timeout` dynamically.

  1. 01Edge Deadline & Isolation: Envoy isolates /orders into its own circuit breaker/pool and stamps an absolute epoch deadline.
  2. 02Budget Enforcement: Order checks remaining budget; if <50ms, fails fast (504) without calling Pricing.
  3. 03Dynamic DB Timeout: Pricing caps SQL execution to min(1500ms, remaining_deadline_ms) so DB never runs zombie queries.
  4. 04Token-Bucket Retry Cap: Retries are disabled in Pricing and capped at 10% active-retry ratio in Order/Envoy.
  5. 05Blast-Radius Containment: Dedicated upstream pools and LIFO load shedding keep unrelated routes at 99.99% availability.
Monotonic deadlines, dynamic SQL timeouts, and 10% retry budgets eliminate 3^N retry storms and zombie DB work.

The invariants

  • Set monotonic timeouts: Gateway 5s -> Order 4.2s -> Pricing 2.5s -> DB <=1.5s.
  • Cap retries to 10% via Envoy retry_budget and disable retries in Pricing.
  • Set SET LOCAL statement_timeout from remaining deadline budget.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Relative remaining TTLs are immune to NTP clock skew between VMs/pods, whereas absolute timestamps can immediately expire if a downstream node's clock is 2 seconds ahead.

Step 1

Explain NTP clock drift (100ms–2s on overloaded VMs).

Step 2

Each hop reads X-Timeout-Remaining-Ms, subtracts its own processing + estimated network RTT, and forwards the remainder.

Step 3

This matches gRPC's standard grpc-timeout wire design.

PYTHON · Lifecycle trace
def forward_headers(remaining_ms: int, start_time: float) -> dict:
    elapsed_ms = int((time.monotonic() - start_time) * 1000)
    next_budget = remaining_ms - elapsed_ms - 10  # 10ms wire margin
    return {"X-Timeout-Remaining-Ms": str(max(0, next_budget))}
Key trade-off

Relative TTLs don't account for variable network transit time unless a small wire margin (10–20ms) is subtracted

04 / ImplementConfiguration & code

Build the safeguards.

Combine adaptive concurrency limiting (CoDel / LIFO queue with 200ms max queue wait) and HTTP `503` shedding so the healthy subset of requests finishes within the 5s SLA.

1. Reference implementation

YAML · Solution
circuit_breakers:
  thresholds:
    - max_requests: 1000
      max_pending_requests: 200
      retry_budget:
        budget_percent: { value: 10.0 }
        min_retry_concurrency: 5

2. Harden for scale

Combine adaptive concurrency limiting (CoDel / LIFO queue with 200ms max queue wait) and HTTP `503` shedding so the healthy subset of requests finishes within the 5s SLA.

PYTHON · Scale hardening
if queue_wait_ms > 200 or not db_semaphore.acquire(blocking=False):
    return Response(status=503, headers={"Retry-After": "5"})

3. Operational controls

Step 1

Cap active in-flight calls to the DB at its sustainable concurrency (e.g., 150 connections).

Step 2

Use a LIFO queue with a 200ms sojourn timeout (CoDel) so stale queued requests shed immediately.

Step 3

Return `503 Service Unavailable` with `Retry-After: 5` instead of letting all 2,500 RPS time out at 5s.

Implementation note

Dynamic `SET LOCAL statement_timeout` adds 1 extra lightweight SQL command per transaction (or use `BEGIN; SET LOCAL ...`)

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Use Equal/Full Jitter on client `Retry-After` backoff and a Circuit Breaker `HALF_OPEN` ramp (or Envoy slow-start) to smooth recovery.

  • ↗
    Ensure clients apply Full Jitter: `sleep = random(0, min(cap, base * 2^attempt))`.
  • ↗
    Configure Circuit Breaker `permittedNumberOfCallsInHalfOpenState: 10` before closing.
  • ↗
    Gradually ramp pod weights or concurrency limits via AIMD.
PYTHON · Verification
def backoff_with_full_jitter(attempt: int, base: float = 0.5, cap: float = 30.0) -> float:
    exp = min(cap, base * (2 ** attempt))
    return random.uniform(0, exp)

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Relative TTLs don't account for variable network transit time unless a small wire margin (10–20ms) is subtracted—
Option 2Prioritized load shedding (shed non-VIP or retry traffic first, preserve checkout)—

Review questions

Failure scenario 1

FIFO queuing under overload causes 0% goodput because every request waits 5s and times out

Failure scenario 2

Fixed backoff (`sleep(5)`) synchronizes all 2,500 clients to slam the DB together every 5 seconds

Alternatives considered

  • Decorrelated jitter (`sleep = min(cap, random(base, prev_sleep * 3))`)
