The idea to keep with you

If latency budgets leave no room for synchronous retries, enforce `try-with-resources` (or Spring `JdbcTemplate`/JPA) on every `Connection`, `PreparedStatement`, and `ResultSet`, enable `leak-detection-threshold=5000`, and cap `maxLifetime` below DB/NAT idle timeouts.

Real-World Impact of Leaked & Over-Provisioned Pools.

Why this matters: The problem: see what breaks without Real-World Impact of Leaked & Over-Provisioned Pools under real concurrency or scale.

Connection leaks and oversized pools fail together:

  1. Slow Pool Starvation: A single unclosed Connection in a catch block reduces pool capacity until all 30 slots are permanently leased.
  2. 30-Second Thread Freeze: Callers block for connectionTimeout=30000ms before throwing SQLTransientConnectionException.
  3. RDS max_connections Breach: 20 pods × 30 connections = 600 > 500 RDS limit, rejecting new pods during scale-out.

STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise Solution: `try-with-resources`, `leak-detection-threshold` & Pool Sizing.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Eliminate leaks and align fleet-wide connection math:

  • Enforce try-with-resources / JdbcTemplate: Wrap every Connection, PreparedStatement, and ResultSet in try (...) (or migrate raw DAOs to Spring JdbcTemplate / @Transactional) so connections always return to HikariCP even on exceptions.
  • Enable leak-detection-threshold: 5000: Logs the exact allocation stack trace whenever a connection is held > 5s (keep streaming cursors paginated or bounded), plus connection-timeout: 3000 (fail fast) and max-lifetime: 1800000.
  • Fleet Math & PgBouncer: Cap maximum-pool-size: 15 (20 × 15 = 300 < 500) or place PgBouncer in transaction-pooling mode in front of RDS.
Fleet-Wide Connection Budget

Bounding 20 Pods Safely Below RDS max_connections = 500

1.try-with-resources: Deterministic close() in reverse order (ResultSet -> Stmt -> Conn).

2.leakDetectionThreshold: 5,000 ms threshold logs exact line number of leaked borrows.

3.Fail-Fast Timeout: 3,000 ms connectionTimeout prevents 30s thread-pool freezes.

4.Pool Headroom: Leaves 200 RDS connections free for rolling deploys & migrations.

Deterministic resource closing, 5s leak detection, and bounded fleet pool math eliminate 6-hour pool exhaustion.

public void reconcileBatch(List<Payment> batch) throws SQLException {
    try (Connection conn = dataSource.getConnection()) {
        conn.setAutoCommit(false);
        try (PreparedStatement ps = conn.prepareStatement("UPDATE payments SET status = ? WHERE id = ?")) {
            for (Payment p : batch) {
                ps.setString(1, p.status());
                ps.setLong(2, p.id());
                ps.addBatch();
            }
            ps.executeBatch();
            conn.commit();
        } catch (Exception ex) {
            conn.rollback();
            throw ex;
        }
    } // Always closes conn and returns it to HikariCP
}

# application.yml HikariCP settings
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      minimum-idle: 2
      connection-timeout: 5000
      max-lifetime: 1500000
      leak-detection-threshold: 5000

STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Connection Pool Hygiene Applies in System Design.

Why this matters: Scope boundary: identify where this pattern fits best and where simpler or async alternatives win.

Connection-pool sizing and leak prevention are critical in any relational backend:

  • High-Replica Kubernetes Fleets: pods × maximumPoolSize must always leave headroom under max_connections during rolling deployments.
  • Multi-Tenant & Serverless Backends: PgBouncer / RDS Proxy transaction pooling decouples app concurrency from Postgres backend processes.
  • Observability: Alerting on hikaricp_connections_pending > 0 catches leaks hours before 503 outages.
