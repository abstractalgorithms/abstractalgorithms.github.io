R

Define the boundaries.

Requirements · 4 minutes
SAY THIS: “Before proposing a topology for Design a Token Bucket Rate Limiter, I’ll clarify the core functional requirements, burst characteristics, data volume, and availability SLOs to define rigid system boundaries.”
Fixed Window allows 2x burst spikes across window boundaries (e.g., 100 reqs at 00:59 + 100 at 01:00). Separate GET and SET calls create a TOCTOU race condition under concurrency.

What the system does

  • Enforce per-API-key sustained rate and burst capacity accurately across all 40 stateless gateway nodes.
  • Keep p99 rate-check latency overhead <= 2 ms on the hot request path.
  • Return standard HTTP 429 Too Many Requests with X-RateLimit-Remaining and Retry-After headers.
  • Remain available and protect downstream origin services even if a Redis shard fails or partitions.

What to agree on

  • 10,000,000 active API keys; ~2,000,000 hot keys active within any 60-second window.
  • 400,000 req/s peak global traffic; Redis Cluster must not become a single-threaded CPU bottleneck.
  • Zero race conditions under concurrent requests for the same API key (no overshooting burst limits).

S

Keep state shared and partitioned.

Storage · 3 minutes
SAY THIS: “I’ll separate low-latency ephemeral cache state from authoritative durable storage, ensuring strict consistency where needed and partitioning for scale.”

Cache / Ephemeral state

state:{partitionKey}:activeWindow

  • In-memory key-value cache (Redis Cluster / Memcached).
  • TTL expiration matching window validity bounds.
  • Hash tags to co-locate keys for atomic Lua scripts or transactions.

Durable / Authoritative store

  • Distributed NoSQL / relational database (DynamoDB, PostgreSQL).
  • Durable write-ahead log with replica failover.
  • Cache-aside pattern: read misses warm cache from durable store.
  • Asynchronous CDC / event streaming to telemetry sinks.

Local-only node state is not a shared cluster quota: N nodes could admit roughly N × the configured limits. Ensure state co-location and transactional boundaries align with partition keys.

D

Make state mutations atomic.

Detailed design · 7 minutes
SAY THIS: “For the critical execution path, we enforce idempotency and concurrency controls using atomic primitives, avoiding lock contention and split-brain states.”
  1. Read server time via redis.call('TIME') inside Lua.
  2. Compute refilled = math.min(capacity, tokens + (elapsed_ms * rate) / 1000.0).
  3. Deduct cost if refilled >= cost, persist via HSET + PEXPIRE, and return [allowed, remaining, retry_after_ms].

PYTHON · REFERENCE IMPLEMENTATION
TOKEN_BUCKET_LUA = """
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate_per_sec = tonumber(ARGV[2])
local cost = tonumber(ARGV[3])

local t = redis.call('TIME')
local now_ms = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)

local data = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1])
local last_ts = tonumber(data[2])

if tokens == nil then
    tokens = capacity
    last_ts = now_ms
else
    local elapsed_ms = math.max(0, now_ms - last_ts)
    tokens = math.min(capacity, tokens + (elapsed_ms * rate_per_sec) / 1000.0)
    last_ts = now_ms
end

local allowed = 0
local retry_after_ms = 0
if tokens >= cost then
    tokens = tokens - cost
    allowed = 1
else
    retry_after_ms = math.ceil(((cost - tokens) / rate_per_sec) * 1000)
end

local ttl_ms = math.ceil((capacity / rate_per_sec) * 2000)
redis.call('HSET', key, 'tokens', tostring(tokens), 'ts', tostring(last_ts))
redis.call('PEXPIRE', key, ttl_ms)
return {allowed, math.floor(tokens), retry_after_ms}
"""

Avoid client-side read-modify-write loops without concurrency control. Use atomic scripts, row-level locks, or conditional mutations at the storage tier to guarantee linearizability.

E

Stress-test the design.

Evaluation · 6 minutes
SAY THIS: “The biggest operational risks involve node failover, partition skew, network isolation, and cascading downstream backpressure. Here is how we mitigate each.”
Architectural Trade-Off

Centralized checking adds ~0.8 ms network RTT per request vs ~0.01 ms for local batching.

Operational Hazard

Unbounded l1_deny dict without LRU eviction leaks memory under random-key DDoS.

D

Close with the trade-offs.

Discussion · 5 minutes
SAY THIS: “In closing, we optimized for sub-millisecond p99 latency and high availability under partition. We trade strict distributed linearizability for predictable throughput and operational simplicity.”

If the interviewer asks…

  • “Need stronger consistency?” Introduce synchronous consensus or linearizable leases; accept higher tail latency.
  • “Need lower cross-region latency?” Route reads to local replicas with asynchronous replication; accept bounded staleness.

Keep the conclusion focused

  • What guarantees are strictly enforced at runtime?
  • What happens during network partitions or node failures?
  • Which CAP trade-off was intentionally chosen and why?
