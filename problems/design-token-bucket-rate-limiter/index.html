The idea to keep with you

Design a distributed rate-limiting service for an API Gateway cluster (40 stateless Envoy/Go/Java nodes) handling 400,000 global requests/sec across 10,000,000 active API keys. Each tenant has a configurable sustained rate (e.g., 100 req/s) and burst capacity (e.g., 250 tokens).

STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why distributed Token Bucket rate limiting matters at 400k req/s.

Across 40 stateless API gateway nodes serving 400,000 req/s and 10M active API keys (2M hot keys), per-node in-memory counters allow a client to exceed its limit by 40× via round-robin routing. A distributed Token Bucket must enforce burst capacity B and sustained rate R accurately across all nodes within a <= 2 ms p99 latency budget.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens with TOCTOU races and background refill timers.

Two classic bugs break distributed rate limiters at scale:

  1. TOCTOU Overshoot: Two gateways concurrently GET tokens=1, both allow the request, and both SET tokens=0—letting bursts bypass limits.
  2. Timer Storm: Running background cron jobs to refill 10,000,000 keys every second saturates Redis CPU with millions of wasted writes for idle keys.
Atomic Lazy Refill

40 Gateways -> Redis Cluster EVALSHA (Single Round-Trip)

Redis executes the Lua script atomically in one RTT, eliminating TOCTOU races and background refill timers.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive solution (and why GET/SET or single-node Redis breaks).

A naive implementation uses GET + SET against a single Redis instance:

  • Race Condition: Non-atomic read-modify-write overshoots burst limits under concurrent requests.
  • Single-Core Saturation: 400k req/s (800k GET+SET commands/s) overwhelms a single Redis thread.
  • Cascading Failure: If Redis times out and the gateway fails closed, all 400k req/s of legitimate API traffic get 500/429.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Sharded Redis Cluster + EVALSHA + Local Fallback.

Production rate limiters (Stripe, Envoy, Kong) combine three techniques:

  • Atomic Lazy Refill (EVALSHA): Compute tokens = min(cap, tokens + (now - last) * rate / 1000) inside a single Redis Lua script and set PEXPIRE so idle keys auto-evict.
  • Redis Cluster Sharding: Hash {api_key} across 16+ Redis Cluster primaries so each shard handles ~25k req/s in < 1 ms.
  • Fail-Open Local Fallback: If a Redis shard is unreachable (circuit breaker open), fall back to an in-memory local token bucket (cap / N_nodes) so origin services remain protected without a total outage.
Sharded Rate-Limit Architecture

Stateless Gateways -> Local Fallback / Sharded Redis Cluster

1.EVALSHA Script: Pre-cached Lua executes lazy refill + decrement atomically in 1 RTT.

2.TTL Auto-Eviction: Sets key TTL to full-refill window so 10M idle keys don't leak RAM.

3.Cluster Sharding: Distributes 400k req/s across 16+ shards to avoid single-thread CPU cap.

4.429 Headers: Returns X-RateLimit-Remaining and Retry-After for well-behaved clients.

Sharded EVALSHA keeps hot-path overhead <= 2 ms p99 while local fallback buckets prevent Redis outages from taking down the API.

-- Redis EVALSHA atomic lazy-refill Token Bucket
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate_per_ms = tonumber(ARGV[2])
local now_ms = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local data = redis.call('HMGET', key, 'tokens', 'last_ms')
local tokens = tonumber(data[1])
local last_ms = tonumber(data[2])

if tokens == nil then
  tokens = capacity
  last_ms = now_ms
else
  local elapsed = math.max(0, now_ms - last_ms)
  tokens = math.min(capacity, tokens + elapsed * refill_rate_per_ms)
  last_ms = now_ms
end

local allowed = 0
local retry_after_ms = 0
if tokens >= requested then
  tokens = tokens - requested
  allowed = 1
else
  retry_after_ms = math.ceil((requested - tokens) / refill_rate_per_ms)
end

local ttl_ms = math.ceil(capacity / refill_rate_per_ms) * 2
redis.call('HMSET', key, 'tokens', tokens, 'last_ms', last_ms)
redis.call('PEXPIRE', key, ttl_ms)
return {allowed, math.floor(tokens), retry_after_ms}
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Distributed Token Buckets are used in System Design.

Distributed token buckets are the standard throttling primitive across API infrastructure:

  • Multi-Tenant API Gateways: Enforcing per-key burst and sustained quotas with 429 + Retry-After.
  • LLM Token & RPM Limiters: Throttling both requests/min and tokens/min by passing requested = estimated_tokens.
  • Downstream Partner Protection: Capping outbound webhook or PSP calls to stay within third-party SLAs.
