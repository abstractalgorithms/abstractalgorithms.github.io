SQL Isolation Levels:
Preventing Phantom Reads.

Under READ COMMITTED, each SQL statement acquires a fresh snapshot, allowing concurrent INSERTs to appear mid-transaction as phantom rows; meanwhile, PostgreSQL REPEATABLE READ prevents phantoms via transaction-level snapshots but still permits write skew without SERIALIZABLE or explicit parent locking.

01 / UnderstandFailure & constraints

Clarify what is failing.

READ COMMITTED allows phantom reads and over-allocation; PostgreSQL REPEATABLE READ prevents phantom reads on re-SELECT but still allows write skew (over-allocation); SERIALIZABLE detects the rw-antidependency and aborts one transaction with 40001.

Design objective

Trace Tx A and Tx B snapshots under READ COMMITTED.

Requirements

  • Prevent phantom reads and concurrent multi-row invariant violations (over-allocating GPUs or on-call slots) under 500 concurrent requests/sec.
  • Explicitly distinguish how PostgreSQL MVCC (READ COMMITTED vs REPEATABLE READ vs SERIALIZABLE) behaves compared to MySQL InnoDB Next-Key Locking.
  • Handle serialization failures (SQLSTATE 40001) or lock contention cleanly in application code with bounded exponential backoff.
  • Avoid coarse table-level locks that serialize unrelated projects or teams.

Constraints

  • Primary database is PostgreSQL 16 (with comparison notes for MySQL 8.0 InnoDB).
  • A single project averages 5–20 concurrent allocation requests/sec, while 10,000 other projects are active concurrently.
  • P99 transaction latency must stay below 40 ms.
Known failure modes

Without an index on project_id, SSI escalates to relation-level SIREAD locks and aborts unrelated projects.

The invariants

  • Set SET LOCAL lock_timeout = '2000ms'.
  • Execute SELECT quota_limit FROM projects WHERE id = %s FOR UPDATE.
  • Sum current allocations and insert only if within quota.
03 / Trace the lifecycleKey decisions

Follow the execution path.

MySQL InnoDB REPEATABLE READ uses MVCC for plain SELECTs (still allowing write skew) but uses Next-Key Locks (record + gap lock) for SELECT ... FOR UPDATE, blocking concurrent phantom INSERTs into the gap.

Step 1

Compare plain SELECT (snapshot read) vs SELECT ... FOR UPDATE (locking read with gap lock) in InnoDB.

Step 2

Note that PostgreSQL has no gap locks—it uses SSI (SERIALIZABLE) or parent/advisory locks instead.

SQL · Lifecycle trace
-- MySQL 8.0 InnoDB: Next-Key Lock blocks phantom INSERTs into project_id = 42
START TRANSACTION;
SELECT SUM(gpus) FROM allocations WHERE project_id = 42 FOR UPDATE;
INSERT INTO allocations (project_id, gpus) VALUES (42, 4);
COMMIT;
Key trade-off

InnoDB gap locks prevent phantoms in REPEATABLE READ, but frequently cause gap-lock deadlocks (Error 1213) under high concurrency.

04 / ImplementConfiguration & code

Build the safeguards.

High contention on optimistic SSI causes retry storms (livelock). Switching that hot path to pessimistic parent-row FOR UPDATE (or maintaining a materialized used_gpus column on projects) converts retries into short FIFO waits.

1. Reference implementation

PYTHON · Solution
import psycopg
from psycopg import errors

def allocate_gpus_locked(conn: psycopg.Connection, project_id: int, requested: int) -> bool:
    with conn.transaction():
        conn.execute("SET LOCAL lock_timeout = '2000ms'")
        row = conn.execute(
            "SELECT quota_limit FROM projects WHERE id = %s FOR UPDATE",
            (project_id,),
        ).fetchone()
        if not row:
            raise ValueError("Project not found")
        quota_limit = row[0]
        used = conn.execute(
            "SELECT COALESCE(SUM(gpus), 0) FROM allocations WHERE project_id = %s",
            (project_id,),
        ).fetchone()[0]
        if used + requested > quota_limit:
            return False
        conn.execute(
            "INSERT INTO allocations (project_id, gpus) VALUES (%s, %s)",
            (project_id, requested),
        )
        return True

2. Harden for scale

High contention on optimistic SSI causes retry storms (livelock). Switching that hot path to pessimistic parent-row FOR UPDATE (or maintaining a materialized used_gpus column on projects) converts retries into short FIFO waits.

SQL · Scale hardening
-- Single-statement atomic update eliminates multi-row read/write skew entirely
UPDATE projects
SET used_gpus = used_gpus + 4
WHERE id = 42 AND used_gpus + 4 <= quota_limit
RETURNING used_gpus;

3. Operational controls

Step 1

Maintain a materialized `used_gpus` integer on `projects` updated atomically.

Step 2

Execute single-statement conditional UPDATE: UPDATE projects SET used_gpus = used_gpus + $1 WHERE id = $2 AND used_gpus + $1 <= quota_limit.

Implementation note

Parent-row locking eliminates 40001 aborts completely for project-scoped writes, at the cost of holding one row lock per active transaction.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
