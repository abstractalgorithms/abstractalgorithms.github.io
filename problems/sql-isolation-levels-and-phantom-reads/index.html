The idea to keep with you

A cloud resource-quota and shift-scheduling service running on PostgreSQL 16 (default READ COMMITTED) enforces a rule: 'A team may have at most 3 active on-call engineers per shift, and total allocated GPU quota per project cannot exceed 16 GPUs.' Under concurrent API requests, two transactions both query `SELECT SUM(gpus) FROM allocations WHERE project_id = $1`, both read 12 GPUs, and both `INSERT` a new 4-GPU allocation—resulting in 20 GPUs allocated. Worse, re-running the `SELECT` inside the same transaction suddenly shows the newly committed row (a phantom read). Design the exact isolation, locking, and retry strategy to prevent both phantom reads and multi-row invariant violations.

From patterns to decisions.

Under READ COMMITTED, each SQL statement acquires a fresh snapshot, allowing concurrent INSERTs to appear mid-transaction as phantom rows; meanwhile, PostgreSQL REPEATABLE READ prevents phantoms via transaction-level snapshots but still permits write skew without SERIALIZABLE or explicit parent locking.

01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why SELECT SUM(...) + INSERT breaks quota invariants under MVCC.

A PostgreSQL 16 quota service enforces SUM(gpus) <= 16 per project (5–20 concurrent requests/sec per project, 10,000 active projects). Under default READ COMMITTED, each statement takes a fresh MVCC snapshot—allowing two concurrent transactions to both read SUM(gpus) = 12, both insert 4 GPUs (Wait—or 8 GPUs!), and silently violate the 16-GPU cap.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Phantom rows under READ COMMITTED and write skew under REPEATABLE READ.

Multi-row invariants fail silently across two isolation levels in PostgreSQL:

  1. Phantom Reads (READ COMMITTED): Concurrent INSERTs committed by Tx B appear mid-transaction in Tx A.
  2. Write Skew (REPEATABLE READ): PostgreSQL's Snapshot Isolation eliminates phantoms for queries, but two concurrent INSERTs see the same pre-insert SUM and both commit, violating the 16-GPU or 3-on-call-engineer cap.
Snapshot Isolation Write Skew

PostgreSQL REPEATABLE READ Allows Both Quota Inserts to Commit

PostgreSQL REPEATABLE READ prevents phantoms, but only SERIALIZABLE (SSI) or parent-row FOR UPDATE prevents write skew.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Why SELECT ... FOR UPDATE on child rows fails in PostgreSQL.

Unlike MySQL InnoDB—which uses Next-Key (Gap) Locks to block phantom INSERTs into a range under REPEATABLE READ—PostgreSQL has no gap locks. Running SELECT ... FROM allocations WHERE project_id = $1 FOR UPDATE only locks existing rows and does not block a concurrent INSERT of a new row!

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: PostgreSQL SERIALIZABLE (SSI) or Parent-Row FOR UPDATE.

Enforce multi-row invariants cleanly at < 40 ms p99 across 10,000 projects:

  • Parent-Row SELECT ... FOR UPDATE: Lock the single projects row (WHERE id = $1 FOR UPDATE) before querying SUM(gpus) and inserting. Contention is scoped per-project (5–20 RPS), leaving the other 9,999 projects lock-free.
  • PostgreSQL SERIALIZABLE (SSI): Uses non-blocking SIREAD predicate locks to detect rw-antidependency cycles and abort one conflicting writer with SQLSTATE 40001, which the app retries with bounded exponential backoff + jitter.
PostgreSQL SSI vs. Parent Lock

MVCC Snapshot + SIREAD Predicate Locks / Parent Row Lock

1.No Gap Locks in PG: FOR UPDATE on child rows does not block new INSERTs in Postgres (unlike InnoDB Next-Key locks).

2.Parent-Row Lock: Locking projects.id serializes only that project without blocking 10,000 others.

3.SSI (SQLSTATE 40001): Detects write-skew rw-cycles without blocking readers; app retries 40001 with jitter.

Locking the parent row or using SERIALIZABLE with 40001 retries enforces multi-row invariants under MVCC.

-- Option A: Parent-row lock serializes quota checks per project (works in READ COMMITTED)
BEGIN;
SELECT gpu_quota FROM projects WHERE id = $1 FOR UPDATE;
SELECT COALESCE(SUM(gpus), 0) FROM allocations WHERE project_id = $1;
-- Verify sum + new_gpus <= 16, then INSERT INTO allocations ...
COMMIT;

-- Option B: PostgreSQL SERIALIZABLE (SSI) with retry loop on SQLSTATE 40001
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT COALESCE(SUM(gpus), 0) FROM allocations WHERE project_id = $1;
INSERT INTO allocations (project_id, gpus) VALUES ($1, $2);
COMMIT; -- Aborts one concurrent writer with 40001 if write skew detected
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where isolation-level guarantees protect business invariants.

Understanding MVCC vs. locking isolation prevents subtle financial and quota bugs:

  • Cloud Quota & Seat-Limit Enforcement: Prevents over-allocating GPUs, licenses, or shift slots.
  • Double-Entry Ledgers & Balances: Uses parent-account FOR UPDATE or SERIALIZABLE to prevent negative balances.
  • Booking & Inventory Systems: Avoids double-booking overlapping time slots via EXCLUDE USING gist or SSI.
