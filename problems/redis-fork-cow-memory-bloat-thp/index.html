Fixing Redis Fork
Copy-on-Write Memory Bloat.

When Linux Transparent Huge Pages (2 MB) is enabled, a 64-byte write during Redis BGSAVE fork() copies an entire 2 MB page (512x write amplification), doubling RSS from 24 GB to 48 GB in 90 seconds and triggering the OOM killer.

01 / UnderstandFailure & constraints

Clarify what is failing.

Linux fork() Copy-on-Write operates at page granularity; with 2 MB THP, a 64-byte mutation forces the kernel to copy an entire 2 MB page (512x more than 4 KB pages).

Design objective

Trace fork() marking all page-table entries read-only.

Requirements

  • Eliminate the 512x Copy-on-Write memory amplification caused by 2 MB Transparent Huge Pages during `fork()`.
  • Ensure worst-case `used_memory + CoW_overhead` during a 90-second `BGSAVE` never exceeds 85% of physical host RAM.
  • Preserve durable RDB/AOF backups without blocking or OOM-killing the primary.
  • Provide an automated Python watchdog that monitors `rdb_last_cow_size` and write-rate headroom before allowing manual/scheduled `BGSAVE`.

Constraints

  • Host has 32 GB physical RAM; current dataset is 24 GB (75% of RAM) with 15,000 random writes/sec.
  • Linux default page size is 4 KB; THP hugepage size is 2 MB (512x larger).
  • BGSAVE takes 90 seconds to serialize 24 GB to NVMe.
Known failure modes

OOM-killer terminates Redis primary during peak write traffic.

Checks rdb_last_cow_size & RAM

  1. 01Disable THP permanently: Boot parameter transparent_hugepage=never eliminates 512x CoW amplification.
  2. 02Cap primary RAM <= 50% and disable local RDB: Each primary holds 12 GB on 32 GB RAM and streams replication without hourly primary BGSAVE.
  3. 03Pre-flight memory headroom check: Watchdog inspects INFO memory & INFO persistence before triggering replica BGSAVE.
  4. 04Bounded CoW snapshot on replica: Replica peaks at 14.7 GB / 32 GB (46% RAM) during the 90s RDB write, zero OOM risk.
  5. 05Continuous CoW telemetry: Watchdog exports rdb_last_cow_size and THP status to Prometheus to catch drift.
Disabling THP cuts CoW bloat by 5-8x, while sharding below 50% RAM and offloading BGSAVE to replicas eliminates primary OOM kills.

The invariants

  • Read /sys/kernel/mm/transparent_hugepage/enabled and fail if [never] is not selected.
  • Query INFO memory (used_memory_rss, total_system_memory) and INFO persistence (rdb_last_cow_size, rdb_bgsave_in_progress).
  • Estimate required headroom as rss + max(last_cow, 0.25 * rss) and abort BGSAVE if >= 80% of host RAM.
03 / Trace the lifecycleKey decisions

Follow the execution path.

At 15,000 writes/sec over 90s with 4 KB pages, CoW still adds up to 5.4 GB (24 + 5.4 = 29.4 GB), leaving <2.6 GB for the Linux kernel, page cache, and network buffers.

Step 1

Add 24 GB RSS + 5.4 GB worst-case 4 KB CoW = 29.4 GB.

Step 2

Account for OS/kernel/socket buffers (~2-3 GB) and jemalloc fragmentation (~1.1x).

Step 3

Conclude that 32 GB is insufficient; either upgrade to 64 GB or shard to 2x 12 GB.

04 / ImplementConfiguration & code

Build the safeguards.

With default `vm.overcommit_memory = 0`, Linux estimates that `fork()` might need 24 GB + 24 GB = 48 GB of virtual memory and rejects `fork()` with ENOMEM on a 32 GB host.

1. Reference implementation

PYTHON · Solution
from pathlib import Path

def is_thp_disabled(thp_path: str = "/sys/kernel/mm/transparent_hugepage/enabled") -> bool:
    text = Path(thp_path).read_text().strip()
    return "[never]" in text

def safe_trigger_bgsave(r) -> str:
    if not is_thp_disabled():
        return "ABORT_THP_ENABLED"

    mem = r.info("memory")
    pers = r.info("persistence")
    if pers.get("rdb_bgsave_in_progress", 0) == 1:
        return "SKIP_BGSAVE_IN_PROGRESS"

    rss = mem["used_memory_rss"]
    total_ram = mem["total_system_memory"]
    last_cow = pers.get("rdb_last_cow_size", 0)
    estimated_cow = max(last_cow, int(rss * 0.25))

    if (rss + estimated_cow) > (total_ram * 0.80):
        return f"ABORT_LOW_RAM_HEADROOM:rss={rss},cow={estimated_cow},ram={total_ram}"

    r.bgsave()
    return "BGSAVE_STARTED"

2. Harden for scale

With default `vm.overcommit_memory = 0`, Linux estimates that `fork()` might need 24 GB + 24 GB = 48 GB of virtual memory and rejects `fork()` with ENOMEM on a 32 GB host.

# /etc/sysctl.d/99-redis.conf

3. Operational controls

Step 1

Observe Linux's heuristic overcommit check during `fork()`.

Step 2

Set `vm.overcommit_memory = 1` so `fork()` succeeds and allocates physical pages lazily on CoW faults.

Implementation note

Aborting BGSAVE when RAM > 80% prevents an immediate primary outage, alerting operators to scale/shard before backups fall behind.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Enable `repl-diskless-sync yes` on the primary so the forked child streams the RDB directly over the socket to the replica without hitting disk, and size `repl-backlog-size` generously (e.g., 1 GB) to avoid unnecessary full resyncs.

  • ↗
    Set `repl-backlog-size 1gb` so brief network blips use partial resync (`PSYNC`) with zero `fork()`.
  • ↗
    Set `repl-diskless-sync yes` and `repl-diskless-sync-delay 5` to batch multiple joining replicas into one `fork()`.
PYTHON · Verification
# redis.conf replication tuning:
# repl-diskless-sync yes
# repl-diskless-sync-delay 5
# repl-backlog-size 1gb

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
