Why Preventing Cache Avalanche Matters.

Why this matters: The mechanism: understand how Why Preventing Cache Avalanche Matters works from first principles.

An e-commerce catalog serves 80,000 QPS from a 4-shard Redis 7 cluster (64 GB RAM, 99.4% hit rate) backed by PostgreSQL (4,000 QPS max).

Every night at 00:00 UTC, a batch job pre-warms 120,000 product keys with an identical EX 3600 TTL.

STAGE 02 · IMPACTL5 · APPLIED DESIGN

Real-World Impact of Synchronized TTL Expiry.

Why this matters: The problem: see what breaks without Real-World Impact of Synchronized TTL Expiry under real concurrency or scale.

Synchronized expiration turns a 99.4% cache hit ratio into an instant DB outage:

  1. 17.5× DB Overload: 70,000 QPS hits a 4,000 QPS Postgres cluster, exhausting connections and CPU.
  2. Retry Amplification: Timed-out pods retry, compounding DB saturation.
  3. Slow Recovery: Even after Redis starts repopulating, Postgres cannot respond fast enough to refill 120,000 keys.
Cache Avalanche Defense

TTL Jitter + Singleflight + Stale-While-Revalidate

1.TTL Jitter: base_ttl + random(0, 20%) spreads 120k expirations across 12 minutes.

2.Singleflight: Coalesces concurrent pod misses for the same key into 1 DB query.

3.Soft/Hard TTL: Serve stale data up to 60s while refreshing asynchronously.

4.Circuit Breaker: Shed/serve stale if DB latency spikes.

TTL jitter spreads expirations over 12 minutes while soft-TTL stale-while-revalidate shields Postgres.

STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise Solution: Randomized TTL Jitter, Singleflight & Soft-TTL Refresh.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Break expiration synchronization and cap DB refresh concurrency:

  • Randomized TTL Jitter: Never write uniform TTLs in batch warmers; set ttl = 3600 + random.randint(0, 720) so 120,000 keys expire smoothly at ~166 keys/sec instead of 120,000/sec.
  • Logical Soft-TTL (stale-while-revalidate): Store {payload, soft_exp} with a longer Redis physical TTL (hard_exp = soft_exp + 300s). When now > soft_exp, serve the cached value immediately (within the 60s staleness SLA) and trigger a background refresh.
  • In-Process Singleflight + Mutex: Coalesce concurrent misses per pod via singleflight and guard Postgres with a Redis SET NX lease.
Soft-TTL Background Refresh

01:00:00 UTC Synchronized Cliff vs. Smooth Jittered Refresh

Soft-TTL stale serving + randomized jitter keeps Postgres load flat across batch-warmed key expirations.

import asyncio, json, random, time

inflight: dict[str, asyncio.Future] = {}

async def get_product(redis, db, key: str, base_ttl: int = 3600):
    raw = await redis.get(key)
    now = time.time()
    if raw:
        payload = json.loads(raw)
        if now > payload["soft_exp"] and key not in inflight:
            asyncio.create_task(_singleflight_refresh(redis, db, key, base_ttl))
        return payload["data"]
    return await _singleflight_refresh(redis, db, key, base_ttl)

async def _singleflight_refresh(redis, db, key: str, base_ttl: int):
    if key in inflight:
        return await inflight[key]
    fut = asyncio.get_running_loop().create_future()
    inflight[key] = fut
    try:
        data = await asyncio.wait_for(db.fetch_product(key), timeout=0.5)
        jitter = random.randint(0, int(base_ttl * 0.2))
        payload = {"data": data, "soft_exp": time.time() + base_ttl + jitter}
        await redis.set(key, json.dumps(payload), ex=base_ttl * 2 + jitter)
        fut.set_result(data)
        return data
    except Exception as exc:
        fut.set_exception(exc)
        raise
    finally:
        inflight.pop(key, None)

Where Cache Avalanche Defense Applies in System Design.

Why this matters: Scope boundary: identify where this pattern fits best and where simpler or async alternatives win.

TTL jitter and soft-expiration are standard across high-QPS read-heavy systems:

  • E-Commerce Product Catalogs & Pricing: Prevents nightly batch pre-warming from causing midnight DB cliffs.
  • CDN & Edge Caching: Cache-Control: max-age=3600, stale-while-revalidate=60.
  • Session & Feature-Flag Stores: Spreads bulk-loaded key expirations evenly.
