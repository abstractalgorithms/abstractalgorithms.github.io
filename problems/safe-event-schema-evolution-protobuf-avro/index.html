01 / UnderstandFailure & constraints

Clarify what is failing.

Protobuf encodes `(tag << 3) | wire_type` on the wire; changing `int64` (wire type 0) to `string` (wire type 2) breaks binary framing, while Avro needs defaults to project missing fields.

Design objective

Explain Protobuf wire types: `0` (varint) vs `2` (length-delimited).

Requirements

  • Block breaking Avro and Protobuf schema changes in CI/CD and at the Kafka broker/registry before any bad bytes reach production topics.
  • Support independent upgrades where consumers upgrade before or after producers (`FULL_TRANSITIVE` compatibility).
  • Prevent a single malformed or incompatible event from stalling an entire Kafka partition (`poison pill` resilience).
  • Provide a replayable Dead-Letter Queue (DLQ) with schema version metadata for recovery.

Constraints

  • 50,000 events/sec across 64 Kafka partitions; consumers cannot be stopped for coordinated big-bang deployments.
  • Both Avro (Confluent Wire Format) and Protobuf (`proto3`) are used across different domain topics.
  • Existing bad messages may already be sitting in the partition ahead of valid traffic.
Known failure modes

Using `BACKWARD` alone allows a producer to add a required field that crashes older consumers.

Safe Deserializer + DLQ

  1. 01CI Compatibility Check: PR fails immediately if Avro lacks defaults or Protobuf reuses/changes tag types (buf breaking).
  2. 02Consume Binary Record: Consumer reads raw bytes first (ByteArrayDeserializer) before attempting schema decode.
  3. 03Resolve Writer Schema: On cache miss, consumer fetches exact writer schema by 4-byte ID to project onto reader schema.
  4. 04Isolate Poison Pill: If decode fails, wrap raw payload + exception metadata into DLQ and commit offset.
  5. 05Uninterrupted Stream: Partition offset advances past poison pills so downstream Flink/services stay healthy.
CI compatibility checks prevent bad schemas, while ByteArray consumption + DLQ routing prevents poison pills from stalling partitions.

The invariants

  • Parse the 5-byte header (magic == 0x00 + 4-byte schema_id) or delegate to AvroDeserializer/ProtobufDeserializer.
  • On SerializationError or DecodeError, produce the raw msg.value() to <topic>.dlq with error headers.
  • Commit the source offset only after dlq_producer.flush() succeeds.

04 / ImplementConfiguration & code

Build the safeguards.

Switch to `KafkaRecordDeserializationSchema` with a `Collector<Either<BadRecord, ValidEvent>>` (or Flink Side Output) that routes bad bytes to a DLQ sink.

1. Reference implementation

PYTHON · Solution
import struct
from confluent_kafka.serialization import SerializationContext, MessageField, SerializationError

def process_message(msg, deserializer, dlq_producer, handler):
    raw = msg.value()
    try:
        if not raw or len(raw) < 5 or raw[0] != 0:
            raise SerializationError("Missing Confluent 5-byte wire header")
        schema_id = struct.unpack(">I", raw[1:5])[0]
        ctx = SerializationContext(msg.topic(), MessageField.VALUE)
        event = deserializer(raw, ctx)
        handler(event)
    except Exception as exc:
        dlq_producer.produce(
            topic=f"{msg.topic()}.dlq",
            key=msg.key(),
            value=raw,
            headers={
                "error": str(exc),
                "source_partition": str(msg.partition()),
                "source_offset": str(msg.offset()),
            },
        )
        dlq_producer.flush()

2. Harden for scale

Switch to `KafkaRecordDeserializationSchema` with a `Collector<Either<BadRecord, ValidEvent>>` (or Flink Side Output) that routes bad bytes to a DLQ sink.

JAVA · Scale hardening
// Flink-style safe deserialization pattern in Java
public void deserialize(ConsumerRecord<byte[], byte[]> record, Collector<DecodedOrError> out) {
    try {
        Event evt = avroDecoder.decode(record.value());
        out.collect(DecodedOrError.ok(evt));
    } catch (Exception ex) {
        out.collect(DecodedOrError.dlq(record.topic(), record.partition(), record.offset(), record.value(), ex.getMessage()));
    }
}

3. Operational controls

Step 1

Catch `Throwable` inside `KafkaRecordDeserializationSchema.deserialize(ConsumerRecord, Collector)`.

Step 2

Wrap bad bytes in a `DeserializationResult` tagged for a Flink `OutputTag<RawRecord>("dlq")`.

Step 3

Send the side output to `<topic>.dlq` so checkpoints and watermarks continue advancing.

Implementation note

Handling deserialization explicitly prevents partition stalls, at the cost of out-of-order DLQ replay.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

If `auto.register.schemas=true`, a misconfigured producer can silently register an unreviewed schema or fail in production at runtime instead of CI.

  • ↗
    Register schemas explicitly during CI/CD deployment.
  • ↗
    Set `auto.register.schemas=false` and `use.latest.version=true` (or pinned schema ID) in production.
PYTHON · Verification
producer_conf = {
    "bootstrap.servers": "kafka:9092",
    "schema.registry.url": "https://sr.internal",
    "auto.register.schemas": False,
}

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Know what each control buys.

Review questions

Failure scenario 1

Returning `null` silently from `deserialize()` drops data without any audit trail or alert.

Failure scenario 2

Accidental `auto.register.schemas=true` combined with `NONE` compatibility lets any typo create a broken schema version.

Alternatives considered

  • Using RBAC on Schema Registry so production app service accounts have `READ` access only.
