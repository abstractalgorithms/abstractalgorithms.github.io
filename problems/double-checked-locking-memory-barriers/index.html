01 / UnderstandFailure & constraints

Clarify what is failing.

x86-64 TSO preserves store-store order in hardware, whereas ARM64 allows the pointer store to become visible before constructor field stores.

Design objective

Break `new RoutingTable()` into: (1) allocate, (2) init fields, (3) assign `instance`.

Requirements

  • Explain why non-volatile DCL fails intermittently on ARM64 while appearing to work on x86-64.
  • Provide a memory-model-safe DCL implementation in Java that minimizes volatile read overhead on the hot path.
  • Contrast `volatile` memory barriers against `VarHandle` acquire/release fences and the Initialization-on-Demand Holder idiom.
  • Handle constructor exceptions safely without poisoning the singleton.

Constraints

  • Read path is called > 500,000 times/sec per pod; cannot acquire a `synchronized` lock on every read.
  • Target architecture is ARM64 (weak memory model) running Java 21.
  • Initialization involves loading a 20 MB routing snapshot, so eager startup initialization is discouraged if unused.
Known failure modes

Assuming `final` fields alone save DCL if the `instance` reference itself is read without a barrier (in practice `final` has freeze semantics, but non-final fields or JIT optimizations still break).

02 / Map the systemArchitecture & invariants

Separate concerns. Map the flow.

Use `volatile` for happens-before safety and a local variable `result` to perform only one volatile read on the hot path.

Caches volatile in local variable

  1. 01Initialize Object Fields: Thread A acquires monitor lock and populates all RoutingTable fields in its store buffer.
  2. 02Volatile Release Store: Writing `volatile instance` emits `stlr` on ARM64, flushing all constructor writes before publishing the pointer.
  3. 03Single Volatile Read: Thread B reads `RoutingTable r = instance;` once using `ldar`, establishing a happens-before edge.
  4. 04Lock-Free Return: Seeing `r != null`, Thread B returns `r` directly without entering `synchronized` or re-reading `instance`.
  5. 05Safe Exception Recovery: If snapshot loading throws inside `synchronized`, `instance` stays `null` so the next caller can retry.
Volatile release/acquire barriers pair with a local variable cache for safe, lock-free reads on ARM64.

The invariants

  • Declare private static volatile RoutingTable instance;.
  • Read RoutingTable result = instance; once before the outer if.
  • Synchronize on RoutingTable.class only when result == null.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Use the Holder idiom for parameterless singletons with zero-barrier reads; avoid it when initialization needs runtime arguments or must be retryable on failure.

Step 1

JVM class initialization lock guarantees thread-safe lazy loading of Holder.INSTANCE.

Step 2

If new RoutingTable() throws in <clinit>, the class is permanently poisoned with NoClassDefFoundError.

JAVA · Lifecycle trace
public final class HolderSingleton {
    private HolderSingleton() {}
    private static class Holder {
        static final HolderSingleton INSTANCE = new HolderSingleton();
    }
    public static HolderSingleton getInstance() {
        return Holder.INSTANCE; // zero volatile read overhead
    }
}
Key trade-off

Holder has ~0.5ns read cost vs. ~1.5ns for volatile DCL, but lacks retryability and runtime parameters.

04 / ImplementConfiguration & code

Build the safeguards.

Swap an immutable `RoutingTable` instance atomically via `AtomicReference` or a `volatile` field updated by a background scheduler.

1. Reference implementation

JAVA · Solution
public final class RoutingTable {
    private static volatile RoutingTable instance;
    private final Map<String, String> routes;

    private RoutingTable(Map<String, String> routes) {
        this.routes = Map.copyOf(routes);
    }

    public static RoutingTable getInstance(Supplier<Map<String, String>> loader) {
        RoutingTable result = instance; // single volatile read
        if (result == null) {
            synchronized (RoutingTable.class) {
                result = instance;
                if (result == null) {
                    result = new RoutingTable(loader.get());
                    instance = result; // volatile store-release
                }
            }
        }
        return result;
    }
}

2. Harden for scale

Swap an immutable `RoutingTable` instance atomically via `AtomicReference` or a `volatile` field updated by a background scheduler.

JAVA · Scale hardening
private static volatile RoutingTable current = new RoutingTable(Map.of());

public static void refresh(Map<String, String> nextRoutes) {
    current = new RoutingTable(nextRoutes); // atomic immutable swap
}

public static String lookup(String key) {
    return current.routes.get(key);
}

3. Operational controls

Step 1

Build the new immutable `Map.copyOf(...)` off the request thread.

Step 2

Atomically publish the new reference via `volatile` write (`instance = nextTable`).

Step 3

Readers continue using `RoutingTable r = instance;` with zero locks.

Implementation note

Local variable caching avoids a second `ldar` instruction on every fast-path call.
