STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why Double-Checked Locking breaks on ARM64 without volatile.

On x86-64 (Total Store Order), hardware preserves store-store ordering, masking broken non-volatile Double-Checked Locking (DCL) for years. On AWS Graviton ARM64 (a weak memory model), both the JIT compiler and CPU can reorder the allocation pointer assignment (instance = addr) ahead of RoutingTable's constructor field writes (this.routes = ...). Another thread reading instance != null at 500,000+ reads/sec observes a partially constructed object with null or 0 fields.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

What happens during out-of-order publication on weak memory models.

Without a volatile StoreStore/LoadLoad barrier, two threads race as follows:

  1. Thread A allocates memory for RoutingTable and writes the non-null reference to instance before finishing routes initialization.
  2. Thread B checks if (instance == null) (false!), skips synchronized, and dereferences instance.routes -> NullPointerException.
  3. Constructor Exception Poisoning: If initialization throws, non-atomic state leaves the singleton broken.
ARM64 Reordering Bug

Partially Constructed Object Publication Without volatile

Without volatile (dmb ish / stlr on ARM64), Thread B can observe a non-null reference before constructor stores drain.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive solution (and why synchronized getInstance() or non-volatile DCL fails).

Two common fixes are either broken or too slow:

  • Synchronized getInstance(): Acquiring a monitor on every 500,000+ reads/sec hot-path call serializes reader threads.
  • Non-volatile DCL: Checking instance == null outside synchronized without volatile has no happens-before edge in the Java Memory Model (JMM).
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Local-Cached volatile DCL or Class-Holder Idiom.

Java 21 provides two zero-contention, JMM-safe lazy initialization patterns:

  • Local-Variable volatile DCL (when runtime args or retries are needed): Declare private static volatile RoutingTable instance; and read it once into a local variable RoutingTable r = instance; on the fast path—avoiding a second volatile load and keeping ARM64 ldar overhead minimal.
  • Initialization-on-Demand Holder (zero-barrier fast path): Place static final RoutingTable INSTANCE = new RoutingTable(); inside a private static Holder class; JVM class-initialization locking (LC) guarantees thread-safe publication with zero volatile reads on subsequent calls.
JMM Happens-Before Fix

volatile StoreStore/LoadLoad Barrier vs. JVM Class-Init Lock

1.volatile Write: Emits StoreStore + LoadStore barrier so constructor fields finish before publication.

2.Local Cache Ref: Reading volatile into local `r` avoids two volatile loads on the 500k/s hot path.

3.Exception Safety: If constructor throws, instance stays null so next caller can retry cleanly.

4.Holder Idiom: JVM class-loading lock eliminates volatile reads completely when no args are needed.

volatile establishes a formal JMM happens-before edge; caching it in a local variable minimizes hot-path read cost.

public final class RoutingTable {
    private static volatile RoutingTable instance;
    private final byte[] snapshot;

    private RoutingTable() {
        this.snapshot = load20MbSnapshot(); // throws cleanly if load fails
    }

    public static RoutingTable getInstance() {
        RoutingTable local = instance; // single volatile read on hot path
        if (local == null) {
            synchronized (RoutingTable.class) {
                local = instance;
                if (local == null) {
                    local = new RoutingTable();
                    instance = local; // volatile write publishes fully initialized object
                }
            }
        }
        return local;
    }
}
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Memory Barriers & Safe Publication apply in System Design.

Understanding weak memory models (ARM64) and safe publication is critical for high-throughput runtimes:

  • Lazy Config & Routing Snapshots: Publishing immutable 20 MB routing tables across 500k RPS worker threads.
  • Lock-Free Ring Buffers (Disruptor): Using VarHandle.releaseFence() / acquireFence() for inter-thread visibility.
  • Graviton / Apple Silicon Migrations: Auditing legacy x86-64 concurrency code for missing volatile or atomic fences.
