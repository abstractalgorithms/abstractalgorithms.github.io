01 / UnderstandFailure & constraints

Clarify what is failing.

By Little's Law (`L = λ × W`), 25 RPS × 12s requires 300 concurrent connections—exceeding all 200 connections across 10 pods and leaving zero connections for 4 ms lookups.

Design objective

Compute `25 RPS × 12s = 300` required connections > 200 available.

Requirements

  • Prevent slow search queries from starving fast `/items/{id}` lookups (`p99 < 25 ms`).
  • Fail fast (<1.5s) when the pool is saturated instead of blocking Tomcat threads for 30 seconds.
  • Kill runaway SQL queries on PostgreSQL before they hold connections for 12 seconds.
  • Keep total PostgreSQL active connections within optimal hardware concurrency (~16–32 active backends).

Constraints

  • PostgreSQL primary has 8 vCPUs and NVMe SSDs; `max_connections = 300`.
  • 10 application pods share the primary database.
  • Tomcat has 200 worker threads per pod.
Known failure modes

Tomcat threads hang for 30s, triggering upstream 504 Gateway Timeouts.

The invariants

  • Set maximumPoolSize: 15, connectionTimeout: 1500, leakDetectionThreshold: 5000.
  • Enforce SET statement_timeout = 2000 on every borrowed connection via connectionInitSql.
  • Cap /items/search concurrency at 4 via Resilience4j Bulkhead.
03 / Trace the lifecycleKey decisions

Follow the execution path.

1,000 concurrent queries on an 8-core PostgreSQL server cause severe CPU thrashing, lock contention, and memory bloat (~10 MB/backend = 10 GB), making *every* query—including `/items/{id}`—take seconds.

Step 1

Apply PostgreSQL sizing formula: (8 cores × 2) + 4 = ~20 optimal active connections.

Step 2

Show that 1,000 active backends increases context-switching and L3 cache misses.

JAVA · Lifecycle trace
// Optimal pool sizing rule of thumb (PostgreSQL wiki / HikariCP)
int optimalFleetConnections = (dbCores * 2) + effectiveSpindleCount;
int perPodPoolSize = Math.max(5, optimalFleetConnections / appPodCount);
Key trade-off

Keeping pools small preserves peak DB throughput, requiring slow queries to be bulkheaded or indexed.

04 / ImplementConfiguration & code

Build the safeguards.

Insert **PgBouncer** in `transaction` pooling mode between the 50 pods and PostgreSQL, multiplexing 750 client connections onto 32 server connections.

1. Reference implementation

YAML · Solution
spring:
  datasource:
    hikari:
      maximum-pool-size: 15
      minimum-idle: 15
      connection-timeout: 1500
      leak-detection-threshold: 5000
      connection-init-sql: "SET statement_timeout = 2000"
      data-source-properties:
        socketTimeout: 3
resilience4j:
  bulkhead:
    instances:
      itemSearch:
        maxConcurrentCalls: 4
        maxWaitDuration: 0ms

2. Harden for scale

Insert **PgBouncer** in `transaction` pooling mode between the 50 pods and PostgreSQL, multiplexing 750 client connections onto 32 server connections.

YAML · Scale hardening
# pgbouncer.ini
pool_mode = transaction
max_client_conn = 2000
default_pool_size = 32
reserve_pool_size = 8
reserve_pool_timeout = 2

3. Operational controls

Step 1

Deploy PgBouncer with `pool_mode = transaction`, `max_client_conn = 2000`, `default_pool_size = 32`.

Step 2

Disable server-side prepared statements in JDBC (`prepareThreshold=0`) if using older PgBouncer.

Implementation note

Queries exceeding 2s abort with `QueryTimeoutException` instead of starving the entire pod.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Create a `pg_trgm` GIN index using `CREATE INDEX CONCURRENTLY` (or offload `LIKE '%widget%'` to OpenSearch/read replica).

  • ↗
    Run `EXPLAIN (ANALYZE, BUFFERS)` to confirm the `Seq Scan`.
  • ↗
    Enable `pg_trgm` and build `CREATE INDEX CONCURRENTLY` with `lock_timeout = '2s'`.
SQL · Verification
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX CONCURRENTLY idx_items_name_trgm ON items USING gin (name gin_trgm_ops);

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Keeping pools small preserves peak DB throughput, requiring slow queries to be bulkheaded or indexed.—
Option 2Use AWS RDS Proxy or PostgreSQL 15+ connection pooling.—

Review questions

Failure scenario 1

Using session-scoped `connectionInitSql` with PgBouncer transaction mode leaks `statement_timeout` across tenants unless set at the DB role level.

Failure scenario 2

Building a GIN index without `CONCURRENTLY` blocks all writes on `items`.

Alternatives considered

  • Sync `items` to Elasticsearch/OpenSearch via Debezium CDC.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Enforce strict DB statement_timeout and JDBC socketTimeout, size pools using Little's Law ((cores * 2) + spindles) rather than inflating them, and isolate slow endpoints with bulkheads.
  • 02Trade-off tip: Keeping pools small preserves peak DB throughput, requiring slow queries to be bulkheaded or indexed.
  • 03Watch out for: Using session-scoped connectionInitSql with PgBouncer transaction mode leaks statement_timeout across tenants unless set at the DB role level.
