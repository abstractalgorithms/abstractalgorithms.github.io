01 / UnderstandFailure & constraints

Clarify what is failing.

PostgreSQL's MVCC creates dead tuples on every UPDATE/DELETE; when autovacuum lags or is blocked by long-running snapshots, index scans must traverse millions of dead index entries.

Design objective

Compute dead tuple generation: 15,000 updates/sec = 54M dead tuples/hour.

Requirements

  • Sustain 20,000 outbox inserts/sec inside the same ACID transaction as the payment ledger write.
  • Eliminate MVCC dead-tuple bloat and `FOR UPDATE SKIP LOCKED` lock/index contention on `outbox_events`.
  • Deliver events to Kafka with at-least-once guarantees, ordering per `aggregate_id`, and < 50ms p99 relay lag.
  • Bound PostgreSQL WAL disk retention and handle Kafka or relay-consumer outages gracefully.

Constraints

  • Primary database is PostgreSQL 16 (RDS/Aurora or self-managed) with 64 vCPUs and 40,000 provisioned IOPS.
  • Long-running read replicas or analytics transactions may hold old `xmin` snapshots for up to 15 minutes.
  • Application code must remain in Java or Python; schema/infra configs may use SQL/YAML.
Known failure modes

Transaction ID (XID) wraparound emergency vacuum freezing writes.

  1. 01Atomic Append-Only Write: Payment Service inserts into ledger and append-only partitioned outbox_events in one ACID transaction; zero UPDATE/DELETE.
  2. 02Sequential WAL Streaming: PostgreSQL streams committed outbox inserts from WAL via `outbox_pub` publication without touching heap/index pages.
  3. 03Idempotent Event Publish: Debezium Outbox Event Router SMT transforms the WAL record and publishes to Kafka partitioned by aggregate_id.
  4. 04Advance Replication Slot: After Kafka acks=all, Debezium advances the slot LSN so PostgreSQL can recycle old WAL segments.
  5. 05O(1) Partition Rotation: A scheduled job drops hourly partitions older than 2 hours, reclaiming 100% of disk without VACUUM.
Replacing SQL polling with `pgoutput` WAL streaming and append-only range partitions eliminates MVCC dead tuples and polling IOPS.

The invariants

  • Define outbox_events partitioned by RANGE (created_at) with no status column needed for polling.
  • Create PUBLICATION outbox_pub FOR TABLE outbox_events WITH (publish = 'insert').
  • Insert ledger row and outbox row in the same Spring/JDBC @Transactional boundary.

Follow the execution path.

Configure Debezium's `EventRouter` SMT with `route.by.field` and `table.field.event.key = aggregate_id`, and cap PostgreSQL slot retention with `max_slot_wal_keep_size`.

Set plugin.name = pgoutput and publication.name = outbox_pub.

Step 2

Use EventRouter SMT so Kafka key = aggregate_id (guaranteeing partition ordering).

Step 3

Set max_slot_wal_keep_size = '50GB' in postgresql.conf.

04 / ImplementConfiguration & code

Build the safeguards.

Pause partition drops, run a bounded batch replay from the un-dropped hourly partitions starting at the last committed Kafka offset timestamp, then recreate the slot.

1. Reference implementation

SQL · Solution
CREATE TABLE outbox_events (
    event_id      UUID NOT NULL,
    aggregate_id  VARCHAR(64) NOT NULL,
    event_type    VARCHAR(64) NOT NULL,
    payload       JSONB NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (event_id, created_at)
) PARTITION BY RANGE (created_at);

-- Filtered publication: decode ONLY inserts on outbox_events
CREATE PUBLICATION outbox_pub
FOR TABLE outbox_events
WITH (publish = 'insert');

2. Harden for scale

Pause partition drops, run a bounded batch replay from the un-dropped hourly partitions starting at the last committed Kafka offset timestamp, then recreate the slot.

PYTHON · Scale hardening
def backfill_missed_outbox(conn, kafka_producer, since_ts, batch_size=5000):
    last_ts, last_id = since_ts, '00000000-0000-0000-0000-000000000000'
    while True:
        rows = conn.execute("""
            SELECT event_id, aggregate_id, event_type, payload, created_at
            FROM outbox_events
            WHERE (created_at, event_id) > (%s, %s)
            ORDER BY created_at ASC, event_id ASC
            LIMIT %s
        """, (last_ts, last_id, batch_size)).fetchall()
        if not rows:
            break
        for eid, agg_id, etype, payload, ts in rows:
            kafka_producer.send(etype, key=agg_id.encode(), value=payload, headers=[('event_id', str(eid).encode())])
        kafka_producer.flush()
        last_ts, last_id = rows[-1][4], str(rows[-1][0])

3. Operational controls

Step 1

Halt the hourly `DROP TABLE` job so no un-published partitions are deleted.

Step 2

Query the latest `created_at` successfully published to Kafka.

Step 3

Run a Python/Java backfill worker scanning `outbox_events WHERE created_at >= :last_ts` in 5,000-row keyset batches.

Step 4

Recreate the `outbox_slot` and resume Debezium; idempotent consumers deduplicate any overlap.

Implementation note

Primary key must include the partition key (`created_at`), requiring UUIDv7 or `(event_id, created_at)` composite PK.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Use a two-table or ring-buffer partition swap (`outbox_active` / `outbox_draining`) where workers drain the frozen partition and reclaim 100% of space with `TRUNCATE` instead of `DELETE`.

  • ↗
    Rotate `outbox_active` every 60 seconds using a view or `ALTER TABLE ... RENAME`.
  • ↗
    Workers read sequentially from the frozen `outbox_draining_N` table without `FOR UPDATE SKIP LOCKED`.
  • ↗
    Once drained, execute `TRUNCATE TABLE outbox_draining_N` in O(1) time.
SQL · Verification
-- Atomic table rotation avoids row-level DELETE and VACUUM
BEGIN;
ALTER TABLE outbox_active RENAME TO outbox_drain_1042;
CREATE TABLE outbox_active (LIKE outbox_drain_1042 INCLUDING ALL);
COMMIT;
-- After relay drains outbox_drain_1042:
TRUNCATE TABLE outbox_drain_1042;

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Capping WAL at 50GB protects primary DB availability during multi-hour CDC outages, requiring a fallback replay job.—
Option 2Increase `max_slot_wal_keep_size` if disk headroom allows > 4 hours of WAL.—

Review questions

Failure scenario 1

Dropping a partition before backfill finishes causes permanent event loss.

Failure scenario 2

`ALTER TABLE` acquires `ACCESS EXCLUSIVE` lock; without `lock_timeout`, a slow insert queues behind it and stalls writes.

Alternatives considered

  • PostgreSQL `LISTEN/NOTIFY` for low-volume (< 1,000 TPS) triggers.

Practical heuristics & interview traps
