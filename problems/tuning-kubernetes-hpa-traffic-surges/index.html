01 / UnderstandFailure & constraints

Clarify what is failing.

The 220s lag is the sum of metrics-server/CPU averaging (~60s) + HPA sync (15s) + EC2 node provisioning (110s) + JVM warmup/readiness (35s).

Design objective

Measure each link in the chain: metrics pipeline, HPA controller, Cluster Autoscaler, and container startup.

Requirements

  • Detect and trigger scale-out within 15 seconds of a 10x traffic surge using leading metrics (RPS / in-flight requests / queue depth).
  • Reduce pod-to-ready time from 145 seconds down to < 20 seconds for urgent surge capacity.
  • Eliminate HTTP 503 connection drops on existing 10 pods during the scale-up window.
  • Prevent thrashing/premature scale-in between secondary wave surges.

Constraints

  • Each pod handles 200 RPS at 70% CPU (1,000m CPU, 2 GiB RAM); 20,000 RPS requires 100 pods.
  • JVM cold-start + Spring Boot warmup takes 35 seconds; EC2 node provisioning takes 90–110 seconds.
  • Budget allows maintaining up to 15% warm headroom or low-priority pause-pod buffer.
Known failure modes

Setting CPU limits=requests throttles JVM JIT compilation, inflating 35s startup to >90s.

  1. 01Leading Metric Signal: KEDA polls Envoy RPS every 5s and sees 10x surge before CPU averages rise.
  2. 02Aggressive ScaleUp Policy: HPA behavior allows +100% or +30 pods per 15s (selectPolicy: Max).
  3. 03Instant Node Scheduling: Scheduler evicts low-priority pause pods in <1s; new pods land on pre-warmed nodes with cached images.
  4. 04Surge Protection: While pods warm up, Envoy/app sheds excess with HTTP 429 Retry-After to prevent OOM/503.
  5. 05Anti-Thrashing Stabilization: HPA holds capacity for 5 minutes after traffic dips to absorb secondary ticket waves.
Replacing lagging CPU metrics with KEDA RPS triggers, warm pause-pod nodes, and aggressive scaleUp policies cuts scale lag from 220s to ~20s.

The invariants

  • Define ScaledObject targeting ticketing-api with minReplicas=10, maxReplicas=120.
  • Set pollingInterval: 5 and scaleUp policies: 100% or +30 pods per 15s.
  • Deploy PriorityClass (-10) pause pods to hold 20 vCPU of warm EC2 nodes.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Even fast Karpenter node provisioning takes 45–90 seconds for EC2 instance launch and kubelet join; pause pods trade ~15–20% idle compute cost for <1s scheduling.

Step 1

Calculate cost of 20 vCPU warm buffer (~$0.80/hr) vs revenue lost during 90s of 503s.

Step 2

Combine pause pods for unexpected spikes with cron pre-scaling for scheduled ticket drops.

Step 3

Use Spot instances for pause-pod overflow nodes if interruption tolerance allows.

YAML · Lifecycle trace
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority-pause
value: -10
globalDefault: false
Key trade-off

Pause pods guarantee instant scheduling for the first burst wave while Karpenter provisions additional nodes in parallel.

04 / ImplementConfiguration & code

Build the safeguards.

Enforce per-pod concurrency limits and edge rate-limiting (HTTP 429 Retry-After) at Envoy/Ingress so the 10 existing pods stay at 100% healthy throughput instead of OOMing under 10x overload.

1. Reference implementation

YAML · Solution
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: ticketing-api-scaler
spec:
  scaleTargetRef:
    name: ticketing-api
  pollingInterval: 5
  minReplicaCount: 10
  maxReplicaCount: 120
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:
          stabilizationWindowSeconds: 0
          selectPolicy: Max
          policies:
            - type: Percent
              value: 100
              periodSeconds: 15
            - type: Pods
              value: 30
              periodSeconds: 15
        scaleDown:
          stabilizationWindowSeconds: 300
          policies:
            - type: Percent
              value: 10
              periodSeconds: 60
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring:9090
        query: sum(rate(envoy_http_downstream_rq_total{app="ticketing-api"}[30s]))
        threshold: "180"

2. Harden for scale

Enforce per-pod concurrency limits and edge rate-limiting (HTTP 429 Retry-After) at Envoy/Ingress so the 10 existing pods stay at 100% healthy throughput instead of OOMing under 10x overload.

YAML · Scale hardening
startupProbe:
  httpGet:
    path: /healthz
    port: 8080
  periodSeconds: 2
  failureThreshold: 15
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 2

3. Operational controls

Step 1

Configure Envoy circuit_breakers max_requests / local rate limit.

Step 2

Return HTTP 429 with Retry-After: 5 so well-behaved clients retry onto newly ready pods.

Step 3

Keep readinessProbe separate from startupProbe so warming pods don't receive traffic prematurely.

Implementation note

5-second Prometheus polling increases query load slightly but cuts detection time by 5x.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Configure KEDA's fallback.replicas and keep a secondary CPU/Memory trigger in the ScaledObject so HPA seamlessly falls back to metrics-server.

  • ↗

  • ↗
    Include a secondary type: cpu trigger at 65% utilization.
  • ↗
    Alert immediately on KEDA scaler errors.
YAML · Verification
fallback:
  failureThreshold: 3
  replicas: 40

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Clients retrying 429s immediately without backoff amplify ingress load.

Failure scenario 2

Without fallback, KEDA freezes at the current replica count when Prometheus is unreachable.

Alternatives considered

  • Use metrics-server + custom-metrics-apiserver HA pair.
