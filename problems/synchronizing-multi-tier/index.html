The idea to keep with you

When a single bottleneck threatens end-to-end availability, synchronize L1 and L2 caches by broadcasting invalidations over Redis Pub/Sub (with short 30–60s L1 TTLs as a safety net) and fencing L1/L2 writes with monotonic version tokens to prevent stale fill races.

Core Mechanics: Running 40 pods with in-process L1 Caffeine caches (TTL = 5 min, 82% hit rate) in front of L2 Redis Cluster (TTL = 30 min, 16% hit rate) and PostgreSQL 16 (2% miss) delivers sub-millisecond reads.

Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
When a single bottleneck threatens end-to-end availability, synchronize L1 and L2 caches by broadcasting invalidations over Redis Pub/Sub (with short 30–60s L1 TTLs as a safety net) and fencing L1/L2 writes with monotonic version tokens to prevent stale fill races.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Redis Pub/Sub is fire-and-forget—if Pod 12 briefly disconnects or reconnects, it misses invalidation messages. Relying solely on Pub/Sub with a 5-minute L1 TTL still leaves Pod 12 stale for 5 minutes; and forgetting l1Cache.invalidateAll() on Pub/Sub reconnect preserves missed updates.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Redis Pub/Sub Broadcast + Version Fencing + 30s L1 TTL.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Achieve <= 200 ms invalidation p99 and bounded <= 30 s worst-case staleness:

  • Redis Pub/Sub Invalidation (PUBLISH cache:inv <key>:<ver>): Broadcasts price updates to all 40 pods in < 5 ms; each subscriber evicts/updates Caffeine if cached.ver < ver.
  • 30s + Jitter L1 TTL + Reconnect Flush: Cap L1 TTL at 30 s (with jitter to avoid stampedes) and call l1Cache.invalidateAll() whenever the Pub/Sub client reconnects.
  • Monotonic price_version Fencing: Store price_version in Postgres; both L2 Redis (via Lua CAS) and L1 Caffeine reject any fill whose version is <= the known latest version.
Synchronized L1 + L2 Architecture

Version-Fenced Caffeine L1 + Redis L2 + Pub/Sub Bus

1.<=200ms Fanout: Redis Pub/Sub notifies all 40 pods simultaneously without polling overhead.

2.Reconnect Invalidation: Flush L1 on Pub/Sub reconnect and bound L1 TTL to 30s as a self-healing safety net.

3.Version Fencing: Both L1 and L2 reject stale DB reads with version < latest committed version.

Pub/Sub fanout, 30s L1 TTLs, reconnect flushes, and monotonic version fencing eliminate multi-tier cache drift.

05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where synchronized L1/L2 caching is used at scale.

Why this matters: Scope boundary: identify where this pattern fits best and where simpler or async alternatives win.

Two-tier L1+L2 caching powers ultra-low-latency read paths:

  • E-Commerce Pricing & Promotions: Keeps 80%+ hits in-process at < 0.1 ms while propagating price edits in < 200 ms.
  • Feature Flags & Routing Tables: Uses Pub/Sub or SSE/gRPC streams to push rule changes fleet-wide.
  • Auth Token Revocation Lists: Broadcasts revoked jti IDs to all API gateway pods immediately.
