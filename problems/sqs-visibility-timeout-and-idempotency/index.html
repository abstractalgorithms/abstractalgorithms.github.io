01 / UnderstandFailure & constraints

Clarify what is failing.

A static 900s visibility timeout delays crash recovery to 15 minutes whenever a Spot worker is terminated mid-job, and still does not protect against SQS Standard duplicate deliveries.

Design objective

Note that 85% of jobs finish in 10s, so a 900s timeout penalizes normal Spot interruption recovery by 90x.

Requirements

  • Prevent healthy long-running jobs (up to 15 minutes) from becoming visible to other workers prematurely.
  • Detect crashed or OOM-killed workers within 45 seconds so their jobs are retried quickly rather than waiting 15 minutes.
  • Guarantee zero duplicate payment gateway charges even when SQS delivers the same message twice (e.g., due to network partition or Standard queue at-least-once semantics).
  • Handle SQS's 12-hour maximum visibility timeout limit and receipt-handle expiration cleanly.

Constraints

  • Peak throughput is 400 jobs/sec; average job duration is 10s, p99 is 110s, hard max SLA is 900s (15 min).
  • Payment gateway charges are irreversible without a manual refund.
  • Workers run on Spot EC2/ECS instances where SIGTERM/SIGKILL interruptions occur.
Known failure modes

If `HEARTBEAT_INTERVAL_SEC` is too close to `INITIAL_VISIBILITY_SEC` (e.g., 40s vs 45s), a single 6s network blip causes duplicate delivery.

  1. 01Acquire message with 45s visibility: Worker receives message and starts a daemon heartbeat timer set for 20s.
  2. 02Check/claim idempotency record: If status is already COMPLETED, worker skips OCR/payment and deletes the SQS message immediately.
  3. 03Extend lease every 20s while healthy: For 110s p99 jobs, the heartbeat refreshes the 45s window at t=20s, 40s, 60s, 80s, 100s.
  4. 04Execute OCR and gateway charge: Gateway deduplicates by `invoice_id` even if a GC pause caused a rare concurrent retry.
  5. 05Commit state and delete message: Update DynamoDB to COMPLETED, stop heartbeat in `finally`, and call `DeleteMessage`.
Short initial visibility (45s) + 20s heartbeats + DynamoDB conditional writes eliminate both duplicate processing and slow crash recovery.

The invariants

  • Acquire an idempotency lease in DynamoDB before starting expensive OCR.
  • Start a daemon threading.Thread that waits on stop_event.wait(20) and calls change_message_visibility.
  • On completion, mark DynamoDB COMPLETED, set stop_event.set(), and call delete_message.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Treat `ConditionalCheckFailedException` as a signal that another worker owns an active lease or already completed the invoice; never force-overwrite it.

Step 1

Read the existing DynamoDB item to check status.

Step 2

If status == COMPLETED, delete the SQS message immediately and return.

Step 3

If status == IN_PROGRESS and lease_expires_at > now, abort processing and let SQS visibility expire naturally (or extend slightly) without charging.

PYTHON · Lifecycle trace
from botocore.exceptions import ClientError

def claim_invoice_lease(ddb_table, invoice_id: str, now_epoch: int, lease_sec: int = 60) -> str:
    try:
        ddb_table.put_item(
            Item={"invoice_id": invoice_id, "status": "IN_PROGRESS", "lease_expires_at": now_epoch + lease_sec},
            ConditionExpression="attribute_not_exists(invoice_id) OR (#s = :prog AND lease_expires_at < :now)",
            ExpressionAttributeNames={"#s": "status"},
            ExpressionAttributeValues={":prog": "IN_PROGRESS", ":now": now_epoch},
        )
        return "CLAIMED"
    except ClientError as e:
        if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
            item = ddb_table.get_item(Key={"invoice_id": invoice_id}).get("Item", {})
            return "ALREADY_COMPLETED" if item.get("status") == "COMPLETED" else "LOCKED_BY_OTHER"
        raise
Key trade-off

Using lease_expires_at requires bounded clock skew between workers (use NTP/Amazon Time Sync Service).

04 / ImplementConfiguration & code

Build the safeguards.

Defense-in-depth: conditional transition to `COMPLETED` in DynamoDB + `Idempotency-Key` at the payment gateway prevents double charges even if two workers run OCR concurrently.

1. Reference implementation

PYTHON · Solution
import threading
import time
import boto3

sqs = boto3.client("sqs")

class VisibilityHeartbeat:
    def __init__(self, queue_url: str, receipt_handle: str, extend_sec=45, interval_sec=20, max_sec=900):
        self.queue_url = queue_url
        self.receipt_handle = receipt_handle
        self.extend_sec = extend_sec
        self.interval_sec = interval_sec
        self.max_sec = max_sec
        self._stop = threading.Event()
        self._thread = threading.Thread(target=self._run, daemon=True)

    def _run(self):
        start = time.monotonic()
        while not self._stop.wait(self.interval_sec):
            if time.monotonic() - start >= self.max_sec:
                break
            try:
                sqs.change_message_visibility(
                    QueueUrl=self.queue_url,
                    ReceiptHandle=self.receipt_handle,
                    VisibilityTimeout=self.extend_sec,
                )
            except sqs.exceptions.ReceiptHandleIsInvalid:
                break

    def __enter__(self):
        self._thread.start()
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        self._stop.set()
        self._thread.join(timeout=2)

3. Operational controls

Step 1

Both workers pass `Idempotency-Key: invoice_{invoice_id}` to Stripe/Adyen, so the gateway executes at most one charge.

Step 2

Before returning success, Worker A attempts a conditional `UpdateItem` requiring `status = IN_PROGRESS` and its own `worker_token`.

Step 3

If Worker B already claimed and completed it, Worker A's conditional write fails and Worker A skips `DeleteMessage`.

Implementation note

Using a daemon thread per job is simple for I/O-bound workers; for 50+ concurrent jobs per process, a single shared `ScheduledExecutorService` / timer wheel is more memory-efficient.

Review questions

Failure scenario 1

Generating a random UUID per attempt for `Idempotency-Key` instead of deterministic `invoiceId` breaks deduplication.

Failure scenario 2

Deleting the SQS message before durably persisting the job record risks silent job loss on crash.

Alternatives considered

  • Split 500-page PDFs into 10-page chunks so each SQS job stays under 30 seconds.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Because SQS guarantees at-least-once delivery, pair a calibrated visibility heartbeat (ChangeMessageVisibility every T/2) with a strict idempotent consumer store so neither long jobs nor worker crashes cause duplicate side effects.
  • 02Trade-off tip: Using lease_expires_at requires bounded clock skew between workers (use NTP/Amazon Time Sync Service).
  • 03Watch out for: Generating a random UUID per attempt for Idempotency-Key instead of deterministic invoiceId breaks deduplication.
