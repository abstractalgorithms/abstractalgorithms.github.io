01 / UnderstandFailure & constraints

Clarify what is failing.

`Seconds_Behind_Source` is wall-clock-based and only measures the lag between the relay log's last fetched event and applied event; it misses un-fetched binlog events and clock skew.

Design objective

Inspect `SHOW REPLICA STATUS` for `Retrieved_Gtid_Set` vs `Executed_Gtid_Set`.

Requirements

  • Ensure any user who mutates their profile, MFA, or RBAC settings sees the updated state immediately on subsequent reads.
  • Avoid blocking request threads for > 50 ms waiting on replica catch-up.
  • Maintain >= 80% read offload on MySQL replicas during normal operation.
  • Support multi-region or multi-replica pools where different replicas may have different lag.

Constraints

  • MySQL 8.0 asynchronous GTID replication cannot be converted to synchronous Group Replication due to existing single-writer topology.
  • Authorization checks (`GET /v1/users/{id}/permissions`) must never return stale revoked permissions.
  • Solution must integrate cleanly with Python FastAPI + SQLAlchemy async engines.
Known failure modes

Passing a huge `gtid_executed` string with thousands of ranges; use `OWN_GTID` single-transaction GTIDs instead.

GTID_SUBSET check

  1. 01Primary Mutation: FastAPI commits MFA/RBAC update on MySQL primary.
  2. 02GTID Capture: Service captures the committed GTID set for the user.
  3. 03Sticky Window & Cache Update: Stores GTID token with 5s TTL and updates write-through profile cache.
  4. 04Replica GTID Check: If cache misses, checks whether replica has applied target GTID.
  5. 05Zero-Stale Fallback: Routes directly to primary when GTID_SUBSET returns 0.
Combining write-through Redis caching with GTID_SUBSET verification eliminates stale self-reads even under 3-second MySQL replication lag.

The invariants

  • After primary COMMIT, store gtid in ryow:user:{user_id} with EX 5.
  • On GET, fetch ryow:user:{user_id} from Redis with a 5 ms timeout.
  • If gtid exists, run SELECT WAIT_FOR_EXECUTED_GTID_SET(:gtid, 0.03) on the replica; if result != 0, use the primary session.
03 / Trace the lifecycleKey decisions

Follow the execution path.

RBAC revocations affect a target user even when initiated by a *different* admin user, so per-writer RYOW alone is insufficient—use versioned write-through Redis invalidation.

Step 1

Increment users.auth_version on any role/MFA change.

Step 2

Immediately update/delete rbac:user:{target_id} in Redis post-commit and embed auth_version in JWTs or session lookup.

PYTHON · Lifecycle trace
async def revoke_role(admin_id: str, target_user_id: str, db, redis):
    await db.execute(text(
        "UPDATE users SET role='VIEWER', auth_version=auth_version+1 WHERE id=:id"
    ), {"id": target_user_id})
    await db.commit()
    await redis.delete(f"rbac:user:{target_user_id}")
Key trade-off

Global cache invalidation guarantees cross-user consistency for security-critical permissions.

04 / ImplementConfiguration & code

Build the safeguards.

Every pinned request pays an extra 30 ms penalty before falling back to primary; a circuit breaker on replica lag should bypass the wait immediately.

1. Reference implementation

PYTHON · Solution
async def get_read_session(user_id: str, redis: Redis, primary_pool, replica_pool):
    gtid = await redis.get(f"ryow:user:{user_id}")
    if not gtid:
        return replica_pool()
    async with replica_pool() as rep_sess:
        res = await rep_sess.execute(
            text("SELECT WAIT_FOR_EXECUTED_GTID_SET(:g, 0.03)"), {"g": gtid}
        )
        if res.scalar() == 0:
            return rep_sess
    return primary_pool()

2. Harden for scale

Every pinned request pays an extra 30 ms penalty before falling back to primary; a circuit breaker on replica lag should bypass the wait immediately.

YAML · Scale hardening
replica_circuit_breaker:
  timeout_threshold_pct: 20
  window_seconds: 10
  open_duration_seconds: 30
  fallback: primary_or_write_through_cache

3. Operational controls

Step 1

Track replica timeout rate in a 10-second sliding window.

Step 2

When timeout rate > 20%, open the circuit for that replica and route pinned reads directly to primary (0 ms wait).

Implementation note

30 ms max wait avoids unnecessary primary fallback for normal 10 ms lag while bounding tail latency.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

`OWN_GTID` returns only the single GTID of the transaction just committed inside the MySQL protocol OK packet, eliminating an extra SQL round-trip and shrinking the token size.

  • ↗
    Set `session_track_gtids = OWN_GTID` in MySQL `my.cnf` or session initialization.
  • ↗
    Read the tracked GTID from the driver's session-state metadata after `COMMIT`.
SQL · Verification
SET SESSION session_track_gtids = 'OWN_GTID';
-- Driver receives single GTID e.g. 3e11fa47-...:94821 in OK packet

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Keeping a stalled replica in the load balancer pool continues to degrade p99 latency.

Failure scenario 2

Parsing `gtid_executed` when it contains hundreds of gapped ranges inflates Redis memory and `GTID_SUBSET` CPU.

Alternatives considered

  • Use `SELECT @@SESSION.gtid_next` or `@@GLOBAL.gtid_executed` if the Python driver lacks session-tracker support.
