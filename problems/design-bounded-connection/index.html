Full Thread-Safe Java Implementation.

Why this matters: Assemble the complete, deadlock-free Java pool with dial-failure rollback and validation.

Notice how every failure path (!isAlive(), isExpired(), dial exception, or !idle.offer(conn)) decrements totalCreated and closes the underlying socket cleanly.

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class BoundedConnectionPool implements AutoCloseable {
    private final BlockingQueue<PooledConn> idle;
    private final AtomicInteger totalCreated = new AtomicInteger(0);
    private final int maxSize;
    private final long maxLifetimeMs;

public BoundedConnectionPool(int maxSize, long maxLifetimeMs) {
        this.maxSize = maxSize;
        this.maxLifetimeMs = maxLifetimeMs;
        this.idle = new ArrayBlockingQueue<>(maxSize);
    }

Leak-Free Slot Accounting Across All Branches

1.Accounting Invariant: Every +1 in totalCreated has a matching -1 on destroyQuietly() or dial failure.

2.No Nested Locks: Dialing happens outside any pool lock so slow DB handshakes never block other threads.

Caption: Dialing outside locks and balancing every CAS +1 with a -1 on destruction prevents both contention and slot leaks.

Handling Uncommitted Transactions & Double-Close Bugs.

Why this matters: Prevent dirty transaction state or duplicate queue entries when callers misbehave.

Think of Handling Uncommitted Transactions & Double-Close Bugs as the intuition layer for Low-Level Design: Thread-Safe Bounded Connection Pool for 500+ Workers: Prevent dirty transaction state or duplicate queue entries when callers misbehave.

If a caller starts a SQL transaction, hits an application exception, and exits try-with-resources, returning that dirty socket to idle would poison the next thread! release(conn) must reset autoCommit = true / rollback pending work, and PooledConn.close() must guard with AtomicBoolean so double-close is a safe no-op.

State Hygiene

Sanitizing Handles Before Re-Queueing

1.Session Isolation: Never return a connection with an open transaction or altered session variable.

2.Destroy on Reset Fail: If rollback() throws an IOException, destroy the socket instead of re-queueing.

Caption: Idempotent close guards and session rollbacks prevent dirty state from leaking between worker threads.

Think of Background Health Sweeper & Jittered maxLifetime as the intuition layer for Low-Level Design: Thread-Safe Bounded Connection Pool for 500+ Workers: Proactively evict idle stale sockets and stagger connection recycling to avoid synchronized re-dial spikes.

A scheduled daemon thread (ScheduledExecutorService) wakes every 30s, drains or inspects idle connections, and destroys any socket exceeding maxLifetimeMs (e.g., 30 min +/- 10% random jitter) or failing a lightweight liveness probe.

Health Sweeper

Periodic Idle Eviction with Jittered TTL

1.Staggered Recycling: Randomizing per-connection maxLifetime avoids all 32 sockets re-handshaking at the exact same second.

2.Daemon Thread: Mark the sweeper thread as daemon and cancel its future in pool.close().

Caption: Jittered maxLifetime and periodic sweeping keep idle connections fresh without synchronized re-dial spikes.

Starvation & Fairness: FIFO vs LIFO Under Heavy Contention.

Why this matters: Choose between fair wait queues (ArrayBlockingQueue(C, true)) and LIFO socket reuse.

Think of Starvation & Fairness: FIFO vs LIFO Under Heavy Contention as the intuition layer for Low-Level Design: Thread-Safe Bounded Connection Pool for 500+ Workers: Choose between fair wait queues (ArrayBlockingQueue(C, true)) and LIFO socket reuse.

ArrayBlockingQueue(C, true) enforces FIFO waiter wakeup (preventing thread starvation under 500-thread contention at a minor throughput cost), whereas unfair mode (false) maximizes throughput via thread-local cache warmth.

Contention Tuning

Fair FIFO Waiters vs High-Throughput Unfair Mode

1.Tail Latency vs QPS: Fair mode bounds worst-case wait variance; unfair mode avoids extra park/unpark context switches.

2.Pool Size Formula: Keep C close to (2 * DB_cores + effective_spindle_count) rather than matching 500 app threads.

Caption: Selecting queue fairness trades peak throughput against worst-case waiter tail latency.
