01 / UnderstandFailure & constraints

Clarify what is failing.

4 tiers of 3x retries create $3^4 = 81\times$ amplification; the resulting backlog and synchronized 100 ms retries keep CPU/queues saturated in a self-sustaining metastable loop.

Design objective

Measure `upstream_rq_retry` vs `upstream_rq_total` in Envoy across all 4 tiers.

Requirements

  • Bound total retry amplification across the 4-tier call graph to <= 1.25x normal traffic during a 50% downstream brownout.
  • Ensure automatic recovery within 60 seconds once the downstream database stabilizes (no metastable lock-in).
  • Prevent non-idempotent mutations (`POST /orders`) from being retried without idempotency keys.
  • Maintain >= 99.5% success rate during transient <5% single-pod hiccups.

Constraints

  • Synchronous gRPC/REST call chain cannot be rewritten to async Kafka overnight.
  • Client request timeout at API Gateway is 2,000 ms total.
  • Services run Java 21 (Resilience4j) behind Envoy 1.30 sidecars.
Known failure modes

Restarting Pricing pods one by one fails because the 162k RPS retry wave immediately kills each new pod.

02 / Map the systemArchitecture & invariants

Separate concerns. Map the flow.

Centralize retries at the edge with a 20% `retry_budget`, full-jitter backoff, and explicit deadline checks.

Adaptive Concurrency Limit

  1. 01Propagate Absolute Deadline: Gateway attaches an absolute epoch deadline and strips internal retry triggers.
  2. 02Zero Hop-by-Hop Amplification: Order and Inventory do not retry; failures bubble cleanly to the gateway or circuit breaker.
  3. 03Adaptive Concurrency Shedding: Pricing sheds excess load with 503 when DB latency spikes, keeping active connections healthy.
  4. 04Token-Bucket Retry Gate: Gateway allows 1 jittered retry only if retry_ratio < 20% and remaining deadline > 400 ms.
  5. 05Bounded Recovery: Total system traffic stays <= 2,400 RPS, allowing Postgres to recover immediately.
Collapsing retries to the edge + 20% retry budget + deadline propagation eliminates metastable storms.

The invariants

  • Set budget_percent: 20.0 and min_retry_concurrency: 5 in Envoy circuit_breakers.
  • Disable retries in internal hops (num_retries: 0).
  • Add deadline check in Java before attempting any retry.
03 / Trace the lifecycleKey decisions

Follow the execution path.

A circuit breaker trips binary (all-or-nothing) at a threshold, whereas a 20% retry budget smoothly throttles retries proportionally to healthy traffic.

Step 1

At 5% failure, 20% budget allows all 5% to retry.

Step 2

At 50% failure, 20% budget caps retries at 20% and fast-fails the rest.

Step 3

Pair with a circuit breaker as the final backstop at >60% failure.

PYTHON · Lifecycle trace
def allow_retry(active_reqs: int, active_retries: int, budget_pct: float = 0.20) -> bool:
    return active_retries < max(5, int(active_reqs * budget_pct))
Key trade-off

Smooth degradation prevents sudden cliff-edge oscillations from circuit breakers flapping open/closed.

04 / ImplementConfiguration & code

Build the safeguards.

Require a client-generated `Idempotency-Key` stored in Postgres/Redis with an atomic `INSERT ... ON CONFLICT` or state-machine lock.

1. Reference implementation

YAML · Solution
retry_budget:
  budget_percent:
    value: 20.0
  min_retry_concurrency: 5

2. Harden for scale

Require a client-generated `Idempotency-Key` stored in Postgres/Redis with an atomic `INSERT ... ON CONFLICT` or state-machine lock.

SQL · Scale hardening
INSERT INTO idempotency_keys (key, request_hash, status)
VALUES ($1, $2, 'IN_PROGRESS')
ON CONFLICT (key) DO NOTHING
RETURNING key;

3. Operational controls

Step 1

Reject `POST /orders` without `Idempotency-Key` header (400 Bad Request).

Step 2

Store `(idempotency_key, request_hash, response_json, status)` in Postgres.

Step 3

Return cached response on replay; return `409 Conflict` if `request_hash` differs.

Implementation note

Edge-only retry + 20% budget trades a tiny amount of wasted upstream hops for guaranteed immunity to $R^N$ storms.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Inject a 30-second 50% fault/latency spike in staging using Chaos Mesh or Envoy fault injection and verify recovery within 15 seconds of fault removal.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Retrying a `POST` when the first attempt actually committed on the DB but timed out on the response socket.

Failure scenario 2

Testing at 10% load instead of 100% peak load misses queue-buildup metastable loops.

Alternatives considered

  • Use Toxiproxy between Pricing and Postgres in a staging load test.
