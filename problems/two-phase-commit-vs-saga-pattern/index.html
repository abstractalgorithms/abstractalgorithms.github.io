01 / UnderstandFailure & constraints

Clarify what is failing.

In 2PC, participants that vote YES in Phase 1 enter an IN_DOUBT state holding exclusive row locks until the coordinator sends COMMIT or ABORT. External REST APIs lack XA prepare/commit hooks.

Design objective

Trace Phase 1 (Prepare) and Phase 2 (Commit/Abort) message sequence.

Requirements

  • Guarantee no orphaned charges or leaked inventory reservations across Order, Inventory, and Payment services.
  • Sustain 2,500 checkouts/sec (p99 <= 400 ms) without blocking database locks across external Stripe HTTP calls (150-300 ms).
  • Handle partial failures, network timeouts, and duplicate retries idempotently.
  • Prevent dirty reads or double-spending of inventory while a checkout is in flight.

Constraints

  • Each microservice owns an independent database; external PaymentService (Stripe) does not support XA/2PC.
  • Kafka/message brokers provide at-least-once delivery (duplicates and out-of-order events occur).
  • Orchestrator process can crash at any step and must resume cleanly from durable state.
Known failure modes

Participant lock starvation during coordinator outage or slow downstream network.

  1. 01Start Saga & Semantic Lock: Create Order in PENDING_PAYMENT state in a 3 ms local transaction with outbox event.
  2. 02Compensatable Reservation: Atomically decrement available and increment reserved; record saga_id in idempotency table.
  3. 03Execute Pivot Transaction: Call Stripe with Idempotency-Key=checkout_id. No DB locks are held during the 200 ms HTTP call.
  4. 04Backward Compensation: If T3 fails/times out definitively, execute C2 (release_stock) and C1 (cancel_order) in reverse order.
  5. 05Forward Recovery Post-Pivot: Once T3 succeeds, T4 (confirm_order) and commit_inventory must retry with backoff until succeeded.
Steps before the Pivot (T3) are compensated on failure; steps after the Pivot are retried until completion.

The invariants

  • Persist SagaState (STARTED, INVENTORY_RESERVED, PAYMENT_CHARGED, CONFIRMED, COMPENSATING, FAILED) in local DB.
  • On failure at ChargePayment (Pivot), transition to COMPENSATING and run releaseInventory -> cancelOrder.
  • On success at Pivot, transition to PAYMENT_CHARGED and retry confirmOrder until completion.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Orchestration keeps business flow, timeout sweeps, and reverse compensation order in one explicit state machine, whereas Choreography scatters workflow logic across 3+ services and risks cyclic dependencies.

Step 1

Compare coupling: Choreography couples services to each other's domain events; Orchestrator depends on participants via commands.

Step 2

Compare observability: Orchestrator has a single saga_state table to query stuck checkouts.

Step 3

Note that Choreography works well for 2-step fan-out, while Orchestration scales cleanly to 3+ steps with compensation.

JAVA · Lifecycle trace
// Idempotent participant handler using unique (saga_id, step) constraint
public void onReserveInventory(String sagaId, String sku, int qty) {
    if (idempotencyRepo.tryInsert(sagaId, "RESERVE_INVENTORY")) {
        int updated = inventoryRepo.reserve(sku, qty);
        outbox.publishReply(sagaId, "RESERVE_INVENTORY", updated > 0);
    }
    // Duplicate delivery is safely ignored
}
Key trade-off

Orchestrator can become a 'god service' if business logic (e.g., pricing rules) leaks into it instead of staying purely a workflow coordinator.

04 / ImplementConfiguration & code

Build the safeguards.

Out-of-order compensation is solved by inserting a `COMPENSATED` tombstone in the idempotency log so late forward commands abort; Stripe 504s must be resolved via idempotent status polling before compensating.

1. Reference implementation

JAVA · Solution
public enum SagaStatus { STARTED, INVENTORY_RESERVED, PAYMENT_CHARGED, CONFIRMED, COMPENSATING, FAILED }

public void handleStepResult(String sagaId, String step, boolean success) {
    SagaRecord saga = sagaRepo.findForUpdate(sagaId);
    switch (saga.status()) {
        case STARTED -> {
            if (step.equals("RESERVE_INVENTORY") && success) {
                saga.transitionTo(SagaStatus.INVENTORY_RESERVED);
                outbox.enqueue(sagaId, "CHARGE_PAYMENT", saga.paymentCmd());
            } else {
                saga.transitionTo(SagaStatus.FAILED);
                outbox.enqueue(sagaId, "CANCEL_ORDER", saga.orderCmd());
            }
        }
        case INVENTORY_RESERVED -> {
            if (step.equals("CHARGE_PAYMENT") && success) { // Pivot succeeded
                saga.transitionTo(SagaStatus.PAYMENT_CHARGED);
                outbox.enqueue(sagaId, "CONFIRM_ORDER", saga.orderCmd());
            } else { // Pivot failed -> backward compensation
                saga.transitionTo(SagaStatus.COMPENSATING);
                outbox.enqueue(sagaId, "RELEASE_INVENTORY", saga.invCmd());
            }
        }
        case COMPENSATING -> {
            if (step.equals("RELEASE_INVENTORY") && success) {
                saga.transitionTo(SagaStatus.FAILED);
                outbox.enqueue(sagaId, "CANCEL_ORDER", saga.orderCmd());
            }
        }
        case PAYMENT_CHARGED -> {
            if (step.equals("CONFIRM_ORDER") && success) {
                saga.transitionTo(SagaStatus.CONFIRMED);
            } else {
                retryScheduler.scheduleWithBackoff(sagaId, "CONFIRM_ORDER");
            }
        }
    }
}

2. Harden for scale

Out-of-order compensation is solved by inserting a `COMPENSATED` tombstone in the idempotency log so late forward commands abort; Stripe 504s must be resolved via idempotent status polling before compensating.

JAVA · Scale hardening
// Out-of-order compensation guard
public void onReleaseInventory(String sagaId, String sku, int qty) {
    if (!idempotencyRepo.tryInsert(sagaId, "RELEASE_INVENTORY")) return;
    if (idempotencyRepo.markAbortedIfAbsent(sagaId, "RESERVE_INVENTORY")) {
        // Reserve never arrived yet; tombstone prevents late Reserve from executing
        return;
    }
    inventoryRepo.release(sku, qty);
}

3. Operational controls

Step 1

On `ReleaseInventory`, if `RESERVE` is not in `idempotency_log`, insert `(sagaId, 'RESERVE', 'ABORTED')` so a late `Reserve` is a no-op.

Step 2

On Stripe 504 timeout, call `GET /v1/payment_intents/{id}` with the same `Idempotency-Key`.

Step 3

Never compensate a payment until Stripe confirms the intent is `canceled` or `requires_payment_method`.

Implementation note

Row-level `findForUpdate` on `sagaId` serializes concurrent callbacks for the same checkout without blocking other checkouts.

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Compensating on a 504 timeout when Stripe actually charged the card results in a free order or double-charge.

Failure scenario 2

Warehouse fulfillment jobs querying orders without `status = 'CONFIRMED'` ship unpaid items.

  • Read-your-own-writes session stickiness via CQRS read-model projection.
