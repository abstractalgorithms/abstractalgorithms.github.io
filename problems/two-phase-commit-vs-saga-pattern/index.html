01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why 2PC cannot span microservices and external Stripe APIs at 2,500/sec.

An e-commerce checkout at 2,500 checkouts/sec (p99 <= 400 ms) spans OrderService (PostgreSQL), InventoryService (PostgreSQL), and PaymentService (Stripe 150–300 ms HTTP). External APIs do not support XA prepare/commit, and holding database row locks across 300 ms network RTTs under 2PC destroys throughput and wedges if the coordinator crashes.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Coordinator wedging in 2PC vs. dirty reads in naive Sagas.

Both extremes fail if designed carelessly:

  1. 2PC (XA) Lock Wedging: Holding Inventory locks during Phase 1/2 across 300 ms Stripe calls caps concurrency and leaves participants blocked indefinitely if the coordinator dies.
  2. Naive Saga Anomalies: Because Sagas lack ACID Isolation (I), concurrent checkouts can read uncommitted state or double-deduct inventory on Kafka redelivery.
Orchestrated Saga & Compensation

Reserve -> Charge Stripe -> Compensate on Failure (Non-Blocking)

Orchestrated Sagas use local ACID transactions, semantic RESERVED locks, and idempotent compensations without cross-service locks.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Why choreography-only Sagas and non-idempotent steps break at scale.

Pure event choreography across 3+ services obscures checkout state and creates cyclic dependencies. Worse, executing Saga steps or compensations without an idempotency_log primary key causes at-least-once Kafka retries to double-deduct or double-refund inventory.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Crash-Safe Orchestrated Saga + Semantic Locks.

Sustain 2,500 checkouts/sec (p99 <= 400 ms) with zero leaked stock or orphaned charges:

  • Durable Orchestrator + Transactional Outbox: Persist each Saga state transition (PENDING -> RESERVED -> PAID -> CONFIRMED) alongside an outbox row in one local ACID commit so a crashed orchestrator resumes cleanly.
  • Isolation Countermeasures: Use Semantic Locks (reserved = reserved + qty before CONFIRMED), Commutative Updates (+qty / -qty), and Pivot Transaction ordering (Stripe charge).
  • Idempotent Steps & Compensations: Guard every local handler with INSERT INTO idempotency_log (saga_id, step) PK and pass saga_id as Stripe's Idempotency-Key.
Crash-Safe Saga State Machine

Forward Progress & Reverse Compensation Transitions

Durable state + outbox + idempotency_log PKs allow the orchestrator to crash and resume at any step safely.

BEGIN;
INSERT INTO idempotency_log (saga_id, step) VALUES ($1, $2); -- PK prevents duplicates
UPDATE inventory
   SET available = available - $3, reserved = reserved + $3
 WHERE sku = $4 AND available >= $3;
INSERT INTO outbox (event_id, topic, payload) VALUES ($5, 'saga.events', $6);
COMMIT;
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Sagas replace 2PC in distributed architectures.

Orchestrated Sagas are the standard pattern for cross-domain workflows:

  • E-Commerce Checkout & Fulfillment: Coordinates Order, Inventory, Payment, and Shipping.
  • Travel & Flash-Sale Bookings: Combines flight/hotel/seat reservations with semantic TTL locks.
  • Cloud Provisioning Pipelines: Rolls back partial VPC/IAM/VM resources on step failure.
