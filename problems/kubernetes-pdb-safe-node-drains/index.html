The idea to keep with you

During a mandatory Kubernetes 1.28 -> 1.29 EKS node-group security upgrade, the upgrade stalls for 6 hours and fails. Node drain logs show `Cannot evict pod as it would violate the pod's disruption budget` (HTTP 429 TooManyRequests from the Eviction API). Investigation reveals three broken PDBs across the cluster: (1) `redis-cache` has `replicas: 1` and `minAvailable: 1`, (2) `auth-service` has `replicas: 3`, `minAvailable: 3`, and (3) `billing-worker` has `minAvailable: 4` while its HPA scaled it down to 3 replicas during off-peak hours. Redesign the PDB standards, admission guardrails, and drain runbooks so cluster upgrades complete within SLA without risking availability.

Why Kubernetes PDBs & Safe Node Drains Matter.

During a Kubernetes 1.28 -> 1.29 EKS upgrade across 180 nodes and 3 AZs, node drains stall for 6 hours with HTTP 429 Cannot evict pod as it would violate the pod's disruption budget. Three broken PDBs block eviction: redis-cache (replicas: 1, minAvailable: 1), a StatefulSet with minAvailable: 100%, and a Deployment with maxUnavailable: 0.

Constraints:

  • Multi-AZ stateless services must keep at least N-1 replicas during voluntary drains.
  • Zero unapproved --force --grace-period=0 deletes on stateful production pods.
02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Real-World Impact of Misconfigured PDBs.

A PDB with allowedDisruptions == 0 turns routine maintenance into an operational deadlock:

  1. Blocked Security Upgrades: EKS/Karpenter cannot cordon and drain nodes, leaving CVEs unpatched for hours.
  2. Autoscaler Deadlock: Cluster Autoscaler / Karpenter cannot consolidate underutilized nodes.
  3. Panic Force-Deletes: Frustrated operators run --force --grace-period=0, bypassing preStop hooks and corrupting stateful storage.
Kubernetes Eviction API & PDB Check

Blocked Drain (0 Allowed Disruptions) vs. Safe Rolling Eviction

Ensuring disruptionsAllowed >= 1 lets the Eviction API gracefully drain nodes while preserving N-1 availability.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive Solution (and Why It Breaks).

Deleting all PDBs unblocks node drains but allows the upgrade controller to evict every replica of a service simultaneously, causing an outage. Conversely, setting minAvailable: 100% or maxUnavailable: 0 permanently blocks voluntary evictions whenever all pods are healthy—and even minAvailable: 2 on a 3-replica service blocks drains if 1 pod is temporarily CrashLoopBackOff.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise Solution: `maxUnavailable` Budgets, `replicas >= 2` & Alerting.

Design PDBs so voluntary drains always succeed safely while protecting quorum:

  • Never Set minAvailable == replicas: Run critical services with replicas >= 2 across AZs (topologySpreadConstraints) and use maxUnavailable: 1 (or 25%) so HPA scaling never breaks the budget.
  • StatefulSets & Quorum: For 3-node Raft/etcd/Kafka clusters, set maxUnavailable: 1 so quorum (2/3) always holds.
  • Admissions & Prometheus Alerting: Reject minAvailable == 100% or maxUnavailable == 0 via Kyverno/OPA policies, and alert when kube_poddisruptionbudget_status_pod_disruptions_allowed == 0 for > 15m (using unhealthyPodEvictionPolicy: IfHealthyBudget in K8s 1.27+).
Multi-AZ PDB Quorum Safety

Maintaining Quorum & N-1 Capacity During Node Drains

1.Use maxUnavailable: Scales cleanly with HPA unlike fixed minAvailable counts.

2.Minimum 2 Replicas: Single-replica pods cannot tolerate any disruption with a PDB.

3.K8s 1.27+ Policy: unhealthyPodEvictionPolicy: IfHealthyBudget unblocks stuck CrashLoop pods.

4.OPA / Kyverno Gate: Block maxUnavailable: 0 in CI/CD before it reaches EKS.

Topology spread + maxUnavailable: 1 + OPA admission checks guarantee zero-downtime EKS upgrades across 180 nodes.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: billing-worker-pdb
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app: billing-worker
---
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: block-deadlocking-pdb
spec:
  validationFailureAction: Enforce
  rules:
    - name: disallow-zero-disruptions
      match:
        any:
          - resources:
              kinds: ["PodDisruptionBudget"]
      validate:
        message: "PDB must not set maxUnavailable=0 or minAvailable=100%."
        deny:
          conditions:
            any:
              - key: "{{ request.object.spec.maxUnavailable || '' }}"
                operator: Equals
                value: 0
              - key: "{{ request.object.spec.minAvailable || '' }}"
                operator: Equals
                value: "100%"

# 3-node quorum StatefulSet (e.g., Zookeeper/etcd): allows 1 node down at a time
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: zookeeper

STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where PDBs & Safe Drains Apply in System Design.

Disruption budgeting is vital across any orchestrated infrastructure:

  • Zero-Downtime Cluster Upgrades: Enables automated EKS/GKE/Karpenter node rotation without manual intervention.
  • Stateful Databases & Brokers: Protects Raft/Kafka quorum during kernel patching.
  • Cost Optimization: Lets Karpenter consolidate underutilized spot/on-demand nodes without violating SLAs.
