01 / UnderstandFailure & constraints

Clarify what is failing.

Redis's aeMain event loop is single-threaded; DEL synchronously walks and frees all 2.5M hash entries before processing the next queued command.

Design objective

Recognize that Redis executes commands sequentially on one main thread.

Requirements

  • Eliminate synchronous >2ms event-loop blocks during both explicit invalidation and automatic TTL expiration.
  • Support full catalog refreshes without serving an empty cache window (zero cache-stampede gap).
  • Keep maximum individual Redis key memory footprint under 10 MB so any single-key operation stays sub-millisecond.
  • Provide safe operational cleanup for existing 2.5M-field keys in production without downtime.

Constraints

  • Redis primary handles 85,000 OPS with a strict 200ms client socket timeout.
  • Redis runs on a 4-vCPU instance with 16 GB RAM; only the main aeMain thread executes commands, while bio_lazy_free handles async deallocation.
  • Application clients are written in Python (redis-py).
Known failure modes

200ms client timeouts trigger application retries, multiplying load when Redis unfreezes.

Async Free of v42 Buckets (480 MB)

  1. 01Populate new versioned buckets: Refresher writes 2.5M entries into 64 sharded hashes under v43 in pipelined batches of 500 while clients still read v42.
  2. 02Atomic O(1) version pointer flip: Single atomic SET switches all readers from v42 to v43 with zero cache-miss window.
  3. 03Non-blocking O(1) unlink: aeMain removes the 64 v42 keys from the main dictionary in <0.2ms without freeing their 480 MB payload inline.
  4. 04Offload memory reclamation to background: bio_lazy_free frees all 2.5M dictEntry allocations asynchronously without touching aeMain latency.
  5. 05Zero client timeouts: Concurrent GET/HGET traffic experiences 0ms freeze throughout the entire refresh and cleanup.
Sharding into 64 buckets (<8 MB each) and swapping a version pointer with async UNLINK eliminates both event-loop freezes and cache-miss stampedes.

The invariants

  • Compute bucket = zlib.crc32(item_id.encode()) % 64.
  • Write new version buckets in 500-entry pipelines, flip active_ver, and UNLINK old buckets.
  • Use HSCAN COUNT 500 + HDEL with 1ms sleep for safe in-place legacy big-key removal.
03 / Trace the lifecycleKey decisions

Follow the execution path.

64 sharded Hashes use ~40% less RAM via listpack/dict overhead sharing and allow fast versioned UNLINK, whereas individual keys are required only when items need independent TTLs.

Step 1

Compare memory overhead: 2.5M top-level keys add 2.5M redisObject + dictEntry headers (~240 MB extra overhead).

Step 2

Check TTL granularity: catalog refreshes expire together, so bucket-level TTL + version pointer is ideal.

Key trade-off

04 / ImplementConfiguration & code

Build the safeguards.

Enable `replica-lazy-flush yes` in redis.conf so the replica flushes its old dataset asynchronously in bio_lazy_free before loading the incoming RDB.

1. Reference implementation

PYTHON · Solution
import time
import zlib
from typing import Dict, Iterable

NUM_BUCKETS = 64

def bucket_key(version: str, item_id: str) -> str:
    bucket = zlib.crc32(item_id.encode("utf-8")) % NUM_BUCKETS
    return f"catalog:{version}:{bucket:02d}"

def refresh_catalog_blue_green(r, new_ver: str, old_ver: str, items: Iterable[tuple[str, str]]) -> None:
    pipe = r.pipeline(transaction=False)
    count = 0
    for item_id, payload in items:
        pipe.hset(bucket_key(new_ver, item_id), item_id, payload)
        count += 1
        if count % 500 == 0:
            pipe.execute()
    if count % 500 != 0:
        pipe.execute()

    r.set("catalog:active_ver", new_ver)
    old_keys = [f"catalog:{old_ver}:{b:02d}" for b in range(NUM_BUCKETS)]
    r.unlink(*old_keys)

def chunked_delete_big_hash(r, key: str, batch_size: int = 500) -> None:
    cursor = 0
    while True:
        cursor, data = r.hscan(key, cursor=cursor, count=batch_size)
        if data:
            r.hdel(key, *data.keys())
        if cursor == 0:
            break
        time.sleep(0.001)
    r.unlink(key)

Enable `replica-lazy-flush yes` in redis.conf so the replica flushes its old dataset asynchronously in bio_lazy_free before loading the incoming RDB.

3. Operational controls

Step 1

Identify that during full resync, a replica must flush its entire existing keyspace before loading the primary's RDB.

Step 2

With replica-lazy-flush no, that flush blocks the replica's main thread for seconds, failing health checks.

Implementation note

64 buckets keep each key ~7.5 MB, eliminating big-key stalls on both reads and TTL expirations.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Run `redis-cli --bigkeys -i 0.1` against a read replica (never the primary) or sample `MEMORY USAGE key SAMPLES 5` during off-peak hours.

  • ↗

# Safe replica-only sampling check
def sample_key_bytes(replica_conn, key: str) -> int:

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Read replicas serving traffic during resync fail readiness probes if flush blocks synchronously.

Failure scenario 2

Running `MEMORY USAGE` without `SAMPLES 5` on a 2.5M-element key performs an O(N) full traversal.

Alternatives considered

  • Offline RDB analysis (`rdbtools`) on a nightly backup snapshot.
