01 / UnderstandFailure & constraints

Clarify what is failing.

Under REPEATABLE READ, InnoDB locks the gaps around scanned index entries (and the supremum gap if no rows match) to prevent phantom reads.

Design objective

Inspect `SHOW ENGINE INNODB STATUS` -> `LATEST DETECTED DEADLOCK` for `lock_mode X locks gap before rec insert intention`.

Requirements

  • Eliminate gap locks and insert-intention lock contention blocking concurrent `INSERT`s.
  • Allow multiple background workers to dequeue `PENDING` rows concurrently without blocking each other.
  • Make the 90-day `DELETE` cleanup non-blocking via primary-key chunking.
  • Implement idempotent deadlock retry with jitter in the Java/Spring data layer.

Constraints

  • MySQL 8.0 with `binlog_format = ROW` enabled.
  • Peak insert rate is 3,500 `INSERT`s/sec into `ledger_entries`.
  • Zero duplicate processing of `PENDING` rows by concurrent workers.
Known failure modes

name: Supremum Lock Contention; description: Empty range scans lock the tail of the index.; mitigation: Switch to READ COMMITTED.

READ COMMITTED + ROW binlog

  1. 01Unblocked Inserts: Under READ COMMITTED, no gap locks exist on idx_created_at or status, so INSERTs never wait.
  2. 02Lock-Free Queue Claim: Each worker acquires record locks only on unclaimed PENDING rows, skipping locked ones.
  3. 03PK-Bounded Purge: Deletes operate on bounded historical PK ranges far below the active insert tail.
  4. 04Zero Contention: Workers process disjoint batches without deadlocking each other.
  5. 05Steady Throughput: 3,500 INSERT/s completes cleanly with zero ER_LOCK_DEADLOCK spikes.
READ COMMITTED removes gap locks while SKIP LOCKED and PK-chunked deletes isolate workers and purges.

The invariants

  • Set @Transactional(isolation = Isolation.READ_COMMITTED).
  • Use FOR UPDATE SKIP LOCKED in the worker query.
  • Add @Retryable for CannotAcquireLockException.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Bounding by primary key (`id BETWEEN low AND high`) restricts locks strictly to old historical IDs far away from the auto-increment insert tail.

Step 1

Query SELECT MIN(id), MAX(id) for rows older than 90 days.

Step 2

Loop in 1,000-ID increments.

SQL · Lifecycle trace
-- Safe PK-chunked purge (run in loop incrementing @cur_id by 1000)
DELETE FROM ledger_entries
WHERE id BETWEEN @cur_id AND @cur_id + 999
  AND created_at < NOW() - INTERVAL 90 DAY;
Key trade-off

factor: PK-Chunked Delete; pro: Zero overlap with live INSERTs at the table tail.; con: Requires a small driver script or stored procedure.

04 / ImplementConfiguration & code

Build the safeguards.

Switch to time-based range partitioning (`PARTITION BY RANGE (TO_DAYS(created_at))`) so purging 90-day data becomes an instant `ALTER TABLE ... DROP PARTITION` metadata operation.

1. Reference implementation

JAVA · Solution
@Retryable(retryFor = CannotAcquireLockException.class, maxAttempts = 4,
           backoff = @Backoff(delay = 25, maxDelay = 200, multiplier = 2, random = true))
@Transactional(isolation = Isolation.READ_COMMITTED)
public List<Long> claimPendingBatch(long accountId, int limit) {
  return jdbc.queryForList(
    "SELECT id FROM ledger_entries WHERE status = 'PENDING' AND account_id = ? ORDER BY id LIMIT ? FOR UPDATE SKIP LOCKED",
    Long.class, accountId, limit);
}

2. Harden for scale

Switch to time-based range partitioning (`PARTITION BY RANGE (TO_DAYS(created_at))`) so purging 90-day data becomes an instant `ALTER TABLE ... DROP PARTITION` metadata operation.

SQL · Scale hardening
-- Instant metadata-only purge via partitioning
ALTER TABLE ledger_entries DROP PARTITION p_2026_07;

3. Operational controls

Step 1

Include `created_at` in the primary key `(id, created_at)` as required by MySQL partitioning.

Step 2

Automate monthly/weekly partition creation and `DROP PARTITION`.

Implementation note

factor: READ_COMMITTED per transaction vs global; pro: Minimizes blast radius for legacy code that might rely on repeatable snapshots.; con: Must be applied consistently on all writing/locking services.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Audit transactions that issue multiple `SELECT`s expecting a frozen snapshot; those specific read-only reports can explicitly run `START TRANSACTION WITH CONSISTENT SNAPSHOT` or use `REPEATABLE READ` on a replica.

SQL · Verification
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION WITH CONSISTENT SNAPSHOT;

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
