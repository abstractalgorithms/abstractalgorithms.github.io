The idea to keep with you

Your payment service runs on MySQL 8.0 (`REPEATABLE READ` isolation). A background worker polls `SELECT id FROM ledger_entries WHERE status = 'PENDING' AND account_id = 42 FOR UPDATE`, and a cleanup job runs `DELETE FROM ledger_entries WHERE created_at < NOW() - INTERVAL 90 DAY` using a non-unique `idx_created_at` index. Concurrent `INSERT INTO ledger_entries` transactions for completely different accounts block for 50s (`Lock wait timeout exceeded`) and fail with `ER_LOCK_DEADLOCK` (1213). Fix the locking behavior without losing data integrity.

From patterns to decisions.

Switch transaction isolation to `READ COMMITTED` (with `binlog_format=ROW`) to disable InnoDB gap locks on non-unique range scans, replace `FOR UPDATE` worker polling with `FOR UPDATE SKIP LOCKED`, and batch range deletes by primary key.

STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why MySQL InnoDB Gap-Lock Deadlocks Matter.

On MySQL 8.0 (REPEATABLE READ, binlog_format = ROW) handling 3,500 INSERTs/sec into ledger_entries, a worker polling SELECT id FROM ledger_entries WHERE status = 'PENDING' AND account_id = 42 FOR UPDATE and a cleanup job running DELETE FROM ledger_entries WHERE created_at < NOW() - INTERVAL 90 DAY on non-unique idx_created_at trigger frequent ERROR 1213 (40001): Deadlock found.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Real-World Impact of Next-Key & Gap-Lock Contention.

Under MySQL's default REPEATABLE READ, range scans acquire Next-Key Locks (record + preceding gap) and Supremum Gap Locks:

  1. Phantom Insert Blocking: A FOR UPDATE or DELETE on a non-unique index locks gaps—including the open-ended +infinity supremum—blocking unrelated INSERTs.
  2. Insert-Intention Deadlocks: Two transactions hold shared/exclusive gap locks and then request LOCK_INSERT_INTENTION on each other's gaps, triggering Deadlock 1213.
  3. Throughput Collapse: 3,500 TPS inserts stall behind 90-day batch deletes.
InnoDB Gap & Insert-Intention Locks

REPEATABLE READ Next-Key Locking vs. READ COMMITTED + SKIP LOCKED

1.Why Gap Locks Exist: InnoDB prevents phantom rows under REPEATABLE READ.

2.READ COMMITTED: Disables gap locks (safe with binlog_format=ROW); only locks matched rows.

3.SKIP LOCKED: SELECT ... FOR UPDATE SKIP LOCKED lets workers claim rows without waiting.

4.PK-Chunked Deletes: Delete by primary key batches (LIMIT 1000) instead of range scans.

Switching to READ COMMITTED (with ROW binlog), FOR UPDATE SKIP LOCKED, and PK-batched deletes eliminates gap-lock deadlocks.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive Solution (and Why It Breaks).

Retrying Deadlock 1213 in application code masks the symptom while still burning lock waits and CPU under 3,500 TPS inserts. Adding LOCK IN SHARE MODE or widening indexes without changing REPEATABLE READ or query patterns still acquires gap locks on non-unique ranges.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise Solution: `READ COMMITTED`, `SKIP LOCKED` & PK-Chunked Deletes.

Eliminate InnoDB gap locks safely while guaranteeing zero duplicate worker processing:

  • Set transaction_isolation = READ-COMMITTED: Since binlog_format = ROW is enabled, READ COMMITTED is replication-safe and disables gap/next-key locks for regular queries (except foreign-key/duplicate-key checks).
  • Worker Queueing with FOR UPDATE SKIP LOCKED: Poll SELECT id FROM ledger_entries WHERE status='PENDING' AND account_id=? ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED (backed by composite index (status, account_id, id)).
  • PK-Batched Cleanup & Partitioning: Fetch ids via SELECT id ... LIMIT 1000 and DELETE FROM ledger_entries WHERE id IN (...)—or better yet, range-partition by created_at and DROP PARTITION in O(1).
Zero-Contention Worker & Cleanup Flow

SKIP LOCKED + PK-Chunked Delete Under 3,500 TPS Inserts

Workers never block each other, and 3,500 TPS inserts proceed without gap-lock interference.

-- Inspect active InnoDB lock waits
SELECT r.trx_id waiting_trx, r.trx_mysql_thread_id waiting_thread,
       b.trx_id blocking_trx, l.lock_mode, l.lock_type, l.lock_data
FROM performance_schema.data_lock_waits w
JOIN information_schema.innodb_trx r ON r.trx_id = w.REQUESTING_ENGINE_TRANSACTION_ID
JOIN information_schema.innodb_trx b ON b.trx_id = w.BLOCKING_ENGINE_TRANSACTION_ID
JOIN performance_schema.data_locks l ON l.ENGINE_LOCK_ID = w.BLOCKING_ENGINE_LOCK_ID;

-- Safe PK-chunked purge (run in loop incrementing @cur_id by 1000)
DELETE FROM ledger_entries
WHERE id BETWEEN @cur_id AND @cur_id + 999
  AND created_at < NOW() - INTERVAL 90 DAY;

@Retryable(retryFor = CannotAcquireLockException.class, maxAttempts = 4,
           backoff = @Backoff(delay = 25, maxDelay = 200, multiplier = 2, random = true))
@Transactional(isolation = Isolation.READ_COMMITTED)
public List<Long> claimPendingBatch(long accountId, int limit) {
  return jdbc.queryForList(
    "SELECT id FROM ledger_entries WHERE status = 'PENDING' AND account_id = ? ORDER BY id LIMIT ? FOR UPDATE SKIP LOCKED",
    Long.class, accountId, limit);
}
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where Gap-Lock Avoidance Applies in System Design.

InnoDB lock contention is a classic bottleneck in high-write MySQL systems:

  • Transactional Outbox & Job Queues: FOR UPDATE SKIP LOCKED turns MySQL/Postgres into a high-throughput concurrent work queue.
  • Ledger & Payment Tables: Time-based partitioning replaces expensive range DELETEs with instant DROP PARTITION.
  • Multi-Worker Batch Processors: Composite indexes + READ COMMITTED keep insert latency flat.
