01 / UnderstandFailure & constraints

Clarify what is failing.

An open transaction, idle-in-transaction session, or replica with hot_standby_feedback=on is pinning OldestXmin.

Design objective

Inspect pg_stat_activity.backend_xmin and pg_stat_replication.backend_xmin.

Requirements

  • Unblock autovacuum immediately so dead tuples are reclaimed without restarting PostgreSQL.
  • Reclaim the 480 GB of existing table and index bloat without an ACCESS EXCLUSIVE write outage.
  • Prevent BI queries, ORM `idle in transaction` connections, and read replicas from pinning the primary's `xmin` horizon.
  • Keep read-replica analytical queries running up to 2 hours without impacting primary OLTP.

Constraints

  • Primary has 800 GB NVMe total; 660 GB is currently used (82.5% full).
  • Table receives 3,500 UPDATEs/s and 12,000 SELECTs/s 24/7.
  • `VACUUM FULL` is strictly forbidden because it holds an ACCESS EXCLUSIVE lock for hours.
Known failure modes

Disk full or Transaction ID wraparound shutdown.

Online Shadow Copy

  1. 01Unpin Horizon: Kill idle-in-tx sessions and set hot_standby_feedback=off on BI replica.
  2. 02Vacuum Free Space: Autovacuum marks dead tuples reusable in FSM (prevents further growth).
  3. 03Free Index Bloat: Rebuilds 260 GB bloated indexes down to 70 GB, freeing 190 GB disk.
  4. 04Online Heap Pack: Copies 110 GB live heap to shadow table while capturing live UPDATEs.
  5. 05Atomic Cutover: Swaps relfilenode with minimal lock; disk drops from 660 GB to 180 GB.
Unpinning OldestXmin stops bloat growth; concurrent index rebuild + pg_repack shrinks 660 GB back to 180 GB online.

The invariants

  • Terminate idle-in-tx sessions and disable hot_standby_feedback on BI replica.
  • Compact indexes first, then compact heap via pg_repack.
03 / Trace the lifecycleKey decisions

Follow the execution path.

One BI query must never be allowed to bloat the primary OLTP database and cause a production outage.

Step 1

Set hot_standby_feedback = off and max_standby_streaming_delay = 1800s.

Step 2

Route >30m exports to a dedicated snapshot/logical replica.

YAML · Lifecycle trace
hot_standby_feedback: off
max_standby_streaming_delay: 1800s
Key trade-off

Long replica queries may see recovery conflict cancellations.

04 / ImplementConfiguration & code

Build the safeguards.

PostgreSQL refuses all new write transactions (`database is not accepting commands to avoid wraparound data loss`) until freeze vacuum completes.

1. Reference implementation

SQL · Solution
ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';
-- pg_repack --only-indexes --table ledger_entries -d prod_db

2. Harden for scale

PostgreSQL refuses all new write transactions (`database is not accepting commands to avoid wraparound data loss`) until freeze vacuum completes.

SQL · Scale hardening
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY age(datfrozenxid) DESC;

3. Operational controls

Step 1

Monitor max(age(datfrozenxid)) in Prometheus/Grafana.

Step 2

Alert at 150M and auto-kill pinned transactions before 500M.

Implementation note

pg_repack generates extra WAL during shadow copy.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Default autovacuum_vacuum_scale_factor=0.20 waits for 20% dead tuples (~36 GB) on large tables. Lower it to 0.01 and raise cost_limit.

  • ↗
    Set per-table autovacuum_vacuum_scale_factor = 0.01.
  • ↗
    Increase autovacuum_vacuum_cost_limit = 2000 and set fillfactor = 85 for HOT updates.
SQL · Verification
ALTER TABLE ledger_entries SET (fillfactor = 85, autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_cost_limit = 2000);

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
