STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why PostgreSQL VACUUM Starvation & Bloat Matter.

A 180 GB PostgreSQL 15 ledger_entries table receiving 3,500 UPDATEs/s and 12,000 SELECTs/s bloated to 660 GB (82.5% of an 800 GB NVMe disk) in 10 days, pushing PK lookup p99 from 4 ms to 52 ms. Even though autovacuum is running continuously, n_dead_tup exceeds 420M rows with zero dead tuples reclaimed—and VACUUM FULL is strictly forbidden because it takes an ACCESS EXCLUSIVE lock for hours.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

Real-World Impact of MVCC Dead-Tuple Accumulation.

In PostgreSQL MVCC, every UPDATE writes a new tuple version and marks the old one dead, relying on VACUUM to reclaim space:

  1. Horizon Pinning (xmin): A single long-running idle in transaction session, BI query on a hot_standby_feedback=on replica, or orphaned replication slot pins the global xmin horizon—forbidding autovacuum from removing any dead tuple newer than that snapshot.
  2. Index & Heap Bloat: 420M dead tuples force index/heap scans to read 3.6× more pages, evicting hot pages from shared_buffers and spiking p99 from 4 ms to 52 ms.
  3. Disk Exhaustion: At 82.5% NVMe usage, the primary risks read-only/crash shutdown before standard VACUUM can shrink files.
MVCC Horizon Pinning & Bloat

Pinned xmin Blocks autovacuum Until Unblocked + pg_repack

1.Find Horizon Blocker: Check pg_stat_activity (backend_xmin) and pg_replication_slots.

2.Timeout Guardrails: Set idle_in_transaction_session_timeout = '60s' and statement_timeout.

3.Replica Isolation: Disable hot_standby_feedback on BI replicas so reports don't pin primary.

4.pg_repack: Rebuilds bloated 660 GB table online without ACCESS EXCLUSIVE lock.

Unpinning the xmin horizon lets autovacuum reclaim dead tuples, while pg_repack shrinks the 660 GB file online.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive Solution (and Why It Breaks).

Running VACUUM FULL locks the 180 GB table with ACCESS EXCLUSIVE for hours, causing a total write/read outage. Cranking autovacuum_vacuum_cost_limit alone does nothing while an idle in transaction session or hot_standby_feedback=on replica pins xmin.

04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise Solution: Unpin `xmin`, Tune `autovacuum` & Run `pg_repack`.

Restore MVCC reclamation and reclaim the 480 GB of bloat online:

  • Unblock xmin Horizon: Query pg_stat_activity (backend_xmin) and pg_replication_slots (xmin, catalog_xmin); terminate stale idle in transaction sessions and drop orphaned slots. Enforce idle_in_transaction_session_timeout = '60s'.
  • Isolate BI Replicas: Set hot_standby_feedback = off on analytics replicas (use max_standby_streaming_delay instead).
  • Online Compaction (pg_repack) + HOT Tuning: Run pg_repack -t ledger_entries to rebuild heap/indexes in a shadow table using triggers and swap metadata in milliseconds. Lower table fillfactor = 80 for HOT updates and increase autovacuum_vacuum_scale_factor = 0.01.
pg_repack Online Compaction

Zero-Downtime Heap & Index Rebuild Without Long Locks

pg_repack shrinks 660 GB down to 180 GB while 3,500 UPDATEs/s and 12,000 SELECTs/s continue running.

SELECT pid, state, now() - xact_start AS age, backend_xmin FROM pg_stat_activity WHERE backend_xmin IS NOT NULL ORDER BY age(backend_xmin) DESC;

ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';
-- pg_repack --only-indexes --table ledger_entries -d prod_db

05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where PostgreSQL VACUUM & Bloat Control Apply in System Design.

MVCC bloat hygiene is essential for any write-heavy PostgreSQL deployment:

  • High-Churn Ledger & Job Queue Tables: fillfactor=80 + aggressive per-table autovacuum keeps HOT updates in-page.
  • OLTP + BI Read-Replica Splits: hot_standby_feedback=off prevents analytics queries from bloating the primary.
  • Disk & Tail-Latency Management: pg_repack reclaims space safely without VACUUM FULL downtime.
