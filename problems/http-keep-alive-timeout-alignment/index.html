Aligning HTTP Keep-Alive
Timeouts Across Proxies.

When a backend's HTTP keepAliveTimeout (e.g., 60s) is shorter than or equal to the upstream reverse proxy's idle timeout (e.g., AWS ALB 60s or Nginx 65s), the backend closes the socket with FIN at the exact millisecond the proxy reuses it—causing intermittent 502 Bad Gateway / ECONNRESET errors.

01 / UnderstandFailure & constraints

Clarify what is failing.

The backend closes an idle TCP socket (`FIN`) right as the proxy writes a new request to it. The backend kernel replies with `TCP RST` before the HTTP layer ever sees the request.

Design objective

Check default timeouts: Node.js (`5s`), Tomcat (`60s`), ALB (`60s`), Nginx (`65s`).

Requirements

  • Eliminate 100% of `502 Bad Gateway` / `ECONNRESET` errors caused by idle connection closure races.
  • Preserve HTTP keep-alive connection reuse to avoid ephemeral port exhaustion and TLS churn.
  • Ensure non-idempotent `POST /orders` requests never suffer silent socket drops.
  • Align timeouts across all three hops: AWS ALB -> Nginx -> Tomcat / Node.js.

Constraints

  • AWS ALB `idle_timeout` is 60 seconds (cannot be lowered below 1s, standard is 60s).
  • Peak traffic is 6,000 RPS across 30 backend pods.
  • `POST /orders` is non-idempotent if already received by the backend.
Known failure modes

Backend logs remain completely clean, misleading engineers into blaming the network.

02 / Map the systemArchitecture & invariants

Separate concerns. Map the flow.

Set Nginx server `keepalive_timeout` to 75s (> ALB 60s), Nginx upstream `keepalive_timeout` to 55s, and both Tomcat and Node.js `keepAliveTimeout` to 90s.

  1. 01ALB Initiates Close: Because Nginx server keepalive_timeout (75s) > ALB (60s), ALB always closes first.
  2. 02Safe Upstream Reuse: Nginx upstream keepalive_timeout is 55s; backend keeps socket open for 90s.
  3. 03Race-Free Response: Backend never surprises Nginx with an unexpected FIN mid-request.
  4. 04Proxy-Owned Eviction: Nginx drains idle upstream sockets at 55s, 35s before backend's 90s timer.
  5. 05Graceful Teardown: Backend acknowledges Nginx's FIN cleanly with zero 502 Bad Gateway errors.
Every upstream proxy must expire its idle connections before the downstream server closes them.

The invariants

  • Configure Nginx server block (75s) and upstream block (55s).
  • Configure Spring Boot server.tomcat.keep-alive-timeout: 90s.
  • Configure Node.js server.keepAliveTimeout = 90000 and server.headersTimeout = 95000.
03 / Trace the lifecycleKey decisions

Follow the execution path.

Retrying `error` on non-idempotent `POST /orders` is dangerous (and disabled by default in Nginx) because a socket error after partial write can duplicate orders.

Step 1

Explain that proxy_next_upstream skips POST unless non_idempotent is explicitly enabled.

Step 2

Even for GET, retrying masks the root cause and adds tail latency.

YAML · Lifecycle trace
# Nginx upstream block (safe)
upstream backend_pool {
  server app-service:8080;
  keepalive 128;
  keepalive_timeout 55s;
  keepalive_requests 5000;
}
Key trade-off

Fixing timeout ordering prevents the error at the source for all HTTP methods including POST.

04 / ImplementConfiguration & code

Build the safeguards.

Tomcat's default `maxKeepAliveRequests` is `100`. At 6,000 RPS across 30 pods (200 RPS/pod), each socket hits 100 requests every 0.5 seconds and closes!

1. Reference implementation

YAML · Solution
# Spring Boot application.yaml
server:
  tomcat:
    keep-alive-timeout: 90s
    max-keep-alive-requests: 10000

# Node.js equivalent:
# server.keepAliveTimeout = 90000;
# server.headersTimeout = 95000;

2. Harden for scale

Tomcat's default `maxKeepAliveRequests` is `100`. At 6,000 RPS across 30 pods (200 RPS/pod), each socket hits 100 requests every 0.5 seconds and closes!

YAML · Scale hardening
server:
  tomcat:
    keep-alive-timeout: 90s
    max-keep-alive-requests: 10000 # Must exceed Nginx keepalive_requests (5000)

3. Operational controls

Step 1

Raise `server.tomcat.max-keep-alive-requests` from `100` to `10000` (or `-1`).

Step 2

Align Nginx `keepalive_requests 5000` so Nginx closes the socket before Tomcat's `10000`.

Implementation note

90s backend timeout holds idle sockets slightly longer, using negligible RAM while eliminating 502s.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Capture TCP `FIN` flags with `tcpdump` on the backend port (`8080`) and verify the source IP of `FIN` packets is Nginx, not the pod.

  • ↗
    Run `tcpdump -ni any 'tcp[tcpflags] & tcp-fin != 0 and port 8080'`.
  • ↗
    Confirm `upstream prematurely closed connection` drops to 0 in Nginx metrics.
YAML · Verification
# Verify FIN direction on backend pod
# tcpdump -ni eth0 'tcp[tcpflags] & (tcp-fin|tcp-rst) != 0 and port 8080'

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

06 / Discuss trade-offsBoundaries & alternatives

Know what each control buys.

Control / PatternBenefitTrade-off
Option 1Fixing timeout ordering prevents the error at the source for all HTTP methods including `POST`.—
Option 2Use `maxKeepAliveRequests = -1` (unlimited) and let Nginx's `keepalive_requests 5000` manage rotation.—

Review questions

Failure scenario 1

Leaving `maxKeepAliveRequests = 100` recreates the exact same `FIN`/write race via request count instead of time.

Failure scenario 2

Seeing `RST` from backend port 8080 indicates another timeout (e.g., `requestTimeout` or `maxKeepAliveRequests`) is still firing.

Alternatives considered

  • Monitor `nginx_ingress_controller_requests{status="502"}` in Prometheus.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Interview anchor: Always set the backend's keepAliveTimeout strictly greater than the upstream proxy's idle timeout (e.g., ALB 60s -> Backend 75s), and let the proxy initiate idle closes.
  • 02Trade-off tip: Fixing timeout ordering prevents the error at the source for all HTTP methods including POST.
  • 03Watch out for: Leaving maxKeepAliveRequests = 100 recreates the exact same FIN/write race via request count instead of time.
