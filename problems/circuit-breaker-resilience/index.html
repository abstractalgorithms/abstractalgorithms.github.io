Design a Circuit Breaker for Microservices

Design a resilient Circuit Breaker pattern to protect distributed microservices from cascading failures when downstream dependencies degrade or fail. The breaker must support Closed, Open, and Half-Open states with automatic recovery testing.

Scope, Requirements & Constraints

When Service B slows down, Service A's worker threads block waiting for responses. Soon Service A runs out of threads and fails to serve its own clients, cascading the failure through the entire system. Circuit Breakers fail fast immediately, preventing thread pool exhaustion.

Core Functional Requirements

  • ✓Track failure rates and slow call rates over a sliding evaluation window.
  • ✓Transition from Closed to Open when failure threshold is exceeded, failing fast immediately without calling downstream.
  • ✓Transition from Open to Half-Open after a configured sleep window, allowing a trial percentage of probe calls.
  • ✓Transition from Half-Open to Closed if probes succeed, or back to Open if probes fail.
  • ✓Provide fallback responses when circuit is Open.

Scale & Latency Constraints

  • —Minimal overhead on the critical request path (< 0.1 ms latency added).
  • —Thread-safe state transitions without blocking concurrent in-flight requests.

Reference Architecture & System Blueprint

State machine with Count-based or Time-based sliding window metrics.

Architecture Flow Narrative[Closed] --(failure > 50%)--> [Open] --(timer expired)--> [Half-Open] --(probes pass)--> [Closed] OR --(probes fail)--> [Open]

Hardened Implementation Steps

  1. 1Closed: Calls pass to downstream. Record call outcomes (success, failure, timeout). If failureRate > threshold (e.g. 50% over last 100 calls), trip to Open.
  2. 2Open: Reject incoming calls immediately with CircuitBreakerOpenException or execute fallback. Start waitDuration timer (e.g. 30 seconds).
  3. 3Half-Open: When timer expires, enter Half-Open. Allow a limited number of test calls (e.g. 10 probe calls).
  4. 4If probe failureRate < threshold: reset to Closed. If probe fails: return to Open for another waitDuration.

Key Decisions & Trade-Off Analysis

Architectural Decisions & Trade-Offs

  • ⚖Count-based (last N calls): Good for predictable call volumes, but in low-traffic periods 5 failures over 2 days could trip the circuit.
  • ⚖Time-based (last T seconds): Reflects current operational health accurately, but requires minimum call threshold before evaluation to avoid tripping on a single failure.

Scale Bottlenecks & Operational Hazards

Operational Hazards & Mitigations

  • ⚠Distributed state (Redis): High precision global state, but adds network latency to every call and creates a dependency on Redis. If Redis is down, circuit breakers fail!
  • ⚠Local in-memory state: Zero latency overhead, highly resilient. Downstream receives at most 500 * probe_count test calls, which is typically safe for downstream capacity.

Changed Constraints & System Extension

Follow-up: How do you design meaningful Fallback mechanisms for payments vs recommendation feeds?

Extension Implementation Steps

  1. 1Recommendations / Feeds: Return cached recommendations or default popular items. Degradation is invisible to user.
  2. 2Search: Fall back to basic keyword search instead of vector neural search.
  3. 3Payments / Checkout: NEVER fake a payment. Return clean error advising user to retry shortly, or queue transaction for asynchronous background processing.
