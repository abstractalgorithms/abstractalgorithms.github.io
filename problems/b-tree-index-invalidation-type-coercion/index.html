From patterns to decisions.

Passing an integer bind parameter against a `VARCHAR` indexed column forces the database to cast the column on every row, invalidating the B-Tree index and triggering a 50M-row full table scan.

Full walkthrough · 5 stages
01
STAGE 01 · WHY IT MATTERSL4 · FUNDAMENTALS

Why one mismatched bind type triggers a 50M-row scan.

A B-Tree index on phone_number VARCHAR(20) orders keys lexicographically ('00123' < '09876' < '123'). When an API refactor changes a DTO field from String to Long, JDBC/ORM binds 9876543210 as an integer. Because '09876543210' and '9876543210' are different strings yet equal integers, the database cannot seek the VARCHAR B-Tree.

02
STAGE 02 · IMPACTL5 · APPLIED DESIGN

4 page reads vs. 2.88 million page reads per query.

In MySQL 8, the optimizer rewrites WHERE phone_number = 9876543210 to CAST(phone_number AS DOUBLE) = 9876543210 (and risks precision loss above 2^53):

  1. IOPS Explosion: An index seek on 50M rows reads 4 B-Tree pages (32 KB, < 2 ms). A Seq Scan reads 22 GB / 8 KB = 2.88M pages (18 s), saturating 40,000 NVMe IOPS at 3,500 QPS.
  2. CPU Starvation: Casting 50M strings per query pegs all DB CPU cores at 100%.
B-Tree Seek vs. Seq Scan

4-Page Index Seek vs. 2.88M-Page Implicit Cast Scan

Wrapping the indexed column in an implicit CAST() bypasses the B-Tree and forces a 22 GB full table scan.

03
STAGE 03 · NAIVE SOLUTIONL5 · APPLIED DESIGN

Naive fixes (and why locking or blind casting fails).

Two common reactions cause outages or subtle bugs:

  • ALTER TABLE users ALTER COLUMN phone_number TYPE BIGINT: Acquires an ACCESS EXCLUSIVE lock rewriting 22 GB (minutes of total downtime) and silently strips leading zeros ('09876543210' -> 9876543210) or fails on '+91-...'.
  • Non-Concurrent CREATE INDEX: Locks writes on the 3,500 QPS users table during index build.
04
STAGE 04 · ENTERPRISE SOLUTIONL6 · SCALE & TRADE-OFFS

Enterprise solution: Concurrent Bridge Index + SARGable Bind Parity.

Restore < 5 ms latency with zero table downtime in two steps:

  • Immediate DB Bridge: If data is clean numeric, build a non-blocking CREATE INDEX CONCURRENTLY idx_users_phone_bigint ON users ((phone_number::bigint)) (or MySQL functional index) to stop the IOPS hemorrhage before code rolls out.
  • Permanent SARGable Fix: Restore String binding (PreparedStatement.setString) so phone_number = ? is bare on the column side, verify EXPLAIN (ANALYZE, BUFFERS) shows Index Scan (4 buffers), and enforce CI query-plan regression tests + hibernate.hbm2ddl.auto=validate.
Zero-Downtime Remediation

Concurrent Expression Index Bridge -> SARGable Bind Fix

A concurrent expression index restores <2 ms lookups immediately while the String bind fix rolls out safely.

-- 1. Emergency zero-lock bridge (if all values match digits)
CREATE INDEX CONCURRENTLY idx_users_phone_num
  ON users ((phone_number::bigint))
  WHERE phone_number ~ '^[0-9]+$';

-- 2. Verify SARGable plan after restoring PreparedStatement.setString()
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, password_hash FROM users WHERE phone_number = '9876543210';
-- Expected: Index Scan using idx_users_phone (Buffers: shared hit=4, time=0.05 ms)
05
STAGE 05 · SYSTEM DESIGN APPLICATIONSL7 · STAFF / PRINCIPAL

Where SARGable query hygiene is critical.

Implicit type coercion and non-SARGable predicates are among the top causes of sudden OLTP database meltdowns:

  • Auth & Lookup Tables: VARCHAR phone numbers, national IDs, and latin1/utf8mb4 join mismatches silently disable indexes.
  • CI Query-Plan Gates: High-scale teams run EXPLAIN assertions in integration tests to block Seq Scan regressions before merge.
