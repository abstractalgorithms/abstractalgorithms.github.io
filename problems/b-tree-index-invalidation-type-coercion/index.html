Why Implicit Type Coercion
Breaks B-Tree Indexes.

Passing an integer bind parameter to query a VARCHAR indexed column (WHERE phone_number = 9876543210) forces the database to cast the column on every row, invalidating the B-Tree index and triggering a full table scan.

01 / UnderstandFailure & constraints

Clarify what is failing.

A `VARCHAR` B-Tree is sorted lexicographically, whereas numeric comparison treats `'09876543210'` and `'9876543210'` as equal. The database must cast every row's column value, invalidating the index.

Design objective

Run `EXPLAIN (ANALYZE, BUFFERS)` (PostgreSQL) or `EXPLAIN FORMAT=JSON` (MySQL).

Requirements

  • Restore `WHERE phone_number = ?` lookup latency from 18 seconds back to < 5 ms.
  • Eliminate the 50-million-row `Seq Scan` / full table scan without locking `users`.
  • Provide an immediate DB-level mitigation before application code deploys, followed by a permanent code fix.
  • Prevent future type-mismatch regressions in CI/CD or ORM mappings.

Constraints

  • `users` has 50 million rows (~22 GB) at 3,500 QPS.
  • In MySQL 8, `WHERE phone_number = 9876543210` coerces `VARCHAR` -> `DOUBLE`/`BIGINT`; in PostgreSQL, untyped or mismatched JDBC `setLong()` / `BIGINT` binds fail or force casts if coerced.
  • Zero table downtime is allowed.
Known failure modes

Testing on small staging tables hides the `Seq Scan` until production hits 50M rows.

03 / Trace the lifecycleKey decisions

Follow the execution path.

No—wrapping the *column* in `CAST(phone_number AS BIGINT)` still prevents `idx_users_phone` from being used. You must cast the *parameter* (`CAST(? AS VARCHAR)`), or better, bind a `String`.

Step 1

Keep the indexed column bare on the left-hand side: WHERE phone_number = CAST(? AS VARCHAR).

Step 2

Verify idx_users_phone is selected in EXPLAIN.

SQL · Lifecycle trace
-- Non-SARGable (ignores idx_users_phone):
SELECT id FROM users WHERE CAST(phone_number AS BIGINT) = 9876543210;

-- SARGable (uses idx_users_phone):
SELECT id FROM users WHERE phone_number = CAST(9876543210 AS VARCHAR);
Key trade-off

Casting the parameter is SARGable, though it still fails if leading zeros ('09876543210') were stripped by the integer.

04 / ImplementConfiguration & code

Build the safeguards.

Mismatched **character sets or collations** (e.g., `utf8mb4_unicode_ci` vs `utf8mb4_0900_ai_ci` or `latin1`) force MySQL/PostgreSQL to convert one column per row, invalidating the B-Tree index.

1. Reference implementation

JAVA · Solution
String sql = "SELECT id, password_hash FROM users WHERE phone_number = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, phoneNumber); // Matches VARCHAR(20) -> SARGable
    try (ResultSet rs = ps.executeQuery()) {
        // < 2 ms B-Tree Index Scan
    }
}

3. Operational controls

Step 1

Inspect `SHOW CREATE TABLE users` and `SHOW CREATE TABLE profiles` for `COLLATE` differences.

Step 2

Align both columns to the identical charset and collation.

Implementation note

Fixing the bind type costs 0 extra storage and avoids write amplification on `users`.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Run integration tests against a seeded PostgreSQL/MySQL container with `enable_seqscan = off` or assert `EXPLAIN (FORMAT JSON)` shows `Index Scan` on all critical repository queries.

  • ↗
    Parse `EXPLAIN (FORMAT JSON)` in a JUnit/pytest test and fail if `Node Type == 'Seq Scan'` on large tables.
  • ↗
    Enable `log_min_duration_statement = 200` in staging load tests.
PYTHON · Verification
cur.execute("EXPLAIN (FORMAT JSON) SELECT id FROM users WHERE phone_number = %s", ("9876543210",))
plan = cur.fetchone()[0][0]["Plan"]
assert plan["Node Type"] != "Seq Scan", f"Non-SARGable query plan: {plan}"

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.

Review questions

Failure scenario 1

Legacy tables created before an upgrade often retain `latin1` or `utf8mb3` collations.

Failure scenario 2

Testing against an empty table never catches index invalidation.

Alternatives considered

  • Use PostgreSQL `auto_explain` in staging with `auto_explain.log_min_duration = '50ms'`.
