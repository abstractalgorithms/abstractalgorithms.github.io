01 / UnderstandFailure & constraints

Clarify what is failing.

KafkaConsumer invokes the configured key/value Deserializer inside consumer.poll() before returning records to application code, so an unhandled exception kills the thread before your try/catch is reached.

Design objective

Inspect stack trace showing Deserializer.deserialize() called inside Fetcher.parseCompletedFetch().

Requirements

  • Isolate malformed records in < 10 ms without crashing the consumer process or stalling healthy messages in the same partition.
  • Distinguish permanent poison pills (SerializationException, SchemaViolation) from transient errors (DB timeout) using non-blocking retry topics.
  • Preserve raw payload bytes, original topic, partition, offset, timestamp, and stack trace in DLQ headers for deterministic replay.
  • Prevent malformed events from entering the topic via Schema Registry and producer-side validation.

Constraints

  • Partition 7 must resume draining its 2.8M backlog at >= 5,000 msg/s without manual offset skipping.
  • Consumer pods must never silently drop messages; 100% of failed records must land in DLQ or be processed.
  • DLQ writes must not block if the DLQ broker is temporarily degraded (circuit breaker or local spill).
Known failure modes

Calling commitSync() after catching the error without producing to DLQ silently drops the event.

  1. 01Safe Raw Fetch: Consumer polls raw bytes without throwing inside poll(), preventing pod crashes.
  2. 02In-App Validation: Application decodes JSON/Avro and validates required invoice_id inside try/catch.
  3. 03Immediate Poison-Pill Quarantine: Malformed bytes + x-orig-offset/exception headers are produced to DLQ and offset is committed.
  4. 04Non-Blocking Deferral: DB timeout records move to retry-30s with x-retry-count=1 so main partition never stalls.
  5. 05Controlled Replay: Operator or replay CLI patches schema/encoding and republishes to main topic with audit trail.
Decoupling raw byte fetching from deserialization eliminates CrashLoopBackOff while preserving 100% of failed payloads.

The invariants

  • Poll raw bytes from billing.events.
  • Decode UTF-8 and JSON, validating invoice_id.
  • On permanent error, produce raw bytes + headers to billing.events.dlq and flush() before commit().
03 / Trace the lifecycleKey decisions

Follow the execution path.

In-memory retries are only safe for sub-second blips (<2s total); longer transient outages require retry topics to avoid max.poll.interval.ms eviction, while strict ledger ordering may require halting or per-key parking.

Step 1

Use 2 fast in-memory retries (100ms, 300ms) for brief network blips.

Step 2

Move longer transient failures (DB failover) to retry-30s topic.

Step 3

Use DLQ for permanent schema/data bugs, or per-key parking if key order is mandatory.

# Error classification decision

Key trade-off

Retry topics preserve main partition throughput at the cost of out-of-order execution for retried keys.

04 / ImplementConfiguration & code

Build the safeguards.

A 100% poison-pill flood turns the DLQ into a mirror of the broken stream and indicates a systemic deployment bug rather than isolated bad records; a DLQ-ratio circuit breaker should pause consumption.

1. Reference implementation

PYTHON · Solution
import json
from confluent_kafka import Consumer, Producer

def route_to_dlq(dlq_producer: Producer, msg, exc: Exception):
    headers = [
        ("x-orig-topic", msg.topic().encode()),
        ("x-orig-partition", str(msg.partition()).encode()),
        ("x-orig-offset", str(msg.offset()).encode()),
        ("x-exception-class", type(exc).__name__.encode()),
        ("x-exception-msg", str(exc)[:256].encode()),
    ]
    dlq_producer.produce("billing.events.dlq", key=msg.key(), value=msg.value(), headers=headers)
    dlq_producer.flush(timeout=5.0)

def process_message(msg, dlq_producer, db):
    try:
        payload = json.loads(msg.value().decode("utf-8"))
        if "invoice_id" not in payload:
            raise ValueError("Missing required field: invoice_id")
    except (UnicodeDecodeError, json.JSONDecodeError, ValueError) as exc:
        route_to_dlq(dlq_producer, msg, exc)
        return
    db.upsert_invoice(payload)

2. Harden for scale

A 100% poison-pill flood turns the DLQ into a mirror of the broken stream and indicates a systemic deployment bug rather than isolated bad records; a DLQ-ratio circuit breaker should pause consumption.

PYTHON · Scale hardening
if window_total >= 100 and (window_dlq / window_total) > 0.50:
    consumer.pause(consumer.assignment())
    alert_oncall("DLQ ratio > 50% - halting consumption to prevent systemic corruption")

3. Operational controls

Step 1

Track sliding-window DLQ ratio over 1,000 messages or 30 seconds.

Step 2

If DLQ ratio > 50% (and count > 100), call consumer.pause() and page on-call.

Step 3

Roll back the broken upstream producer and resume.

Implementation note

Flushing per DLQ message adds ~2-5ms only on poison pills while keeping normal throughput at 5,000+ msg/s.

05 / Verify & observeEvidence & acceptance

Prove the fix works.

Replay tools must filter by original timestamp/exception, patch the payload, increment x-retry-count, and rely on idempotent consumer keys (invoice_id) so already-processed records are not double-billed.

  • ↗

Acceptance criteria

Target: no scenario-correlated errors in the tested workload, no duplicate committed writes, and no routine forced termination. Document traffic patterns, duration, and fault injections. A clean run is evidence—not an unconditional guarantee.
