## Stage 1 — Estimation Decision Flow

- Use this decision tree to structure any capacity estimation from scratch.
- Start with DAU and follow the branches to determine what infrastructure tier your system actually needs — single server, horizontally scaled, or fully distributed.
- The key decision point is the scale tier .
- A system handling 100 RPS and one handling 100,000 RPS require fundamentally different architectures — not just bigger servers, but different data stores, caching strategies, and deployment models.

*Applies **caching** to the decision above.*

  • Twitter/X-Scale Feed - DAU: 400M users.
  • Each user reads ~10 timeline requests/day; each user writes ~0.1 tweets/day.

Stage 3 — Deep Dive: Worked Example — Design a Pastebin

    • Write QPS = (1M × 1 paste/day) / 86400 ≈ 12 writes/sec - Read QPS = 12 × 10 = 120 reads/sec - Storage: 12 writes/sec × 10 KB × 86400 = ~10 GB/day → 10 TB over 3 years.
    • Read bandwidth: 120 reads/sec × 10 KB = 1.2 MB/sec → no CDN needed at this scale.
  • What this tells you: - A single PostgreSQL can comfortably handle sub-1000 writes/sec.
    • Storage backend should be durable object storage to handle 10 TB over 3 years.

Applies jvm-internals-and-garbage-collection to the decision above.

Observable outcome: - Storage backend should be durable object storage to handle 10 TB over 3 years.

Stage 4 — Practical: Interview Estimation Template

  • In a system design interview, the interviewer is watching whether you have a structured process — not whether you arrive at the exact right number.
  • Here is a reusable five-step template you can follow verbatim: Quick Reference Decision Rules Two threshold rules that short-circuit most infrastructure architecture debates: - If storage 1 TB/day → use object storage (…
  • A relational database is not designed for multi-terabyte raw ingest at sustained write rates.
    • If read bandwidth 1 GB/s → put a CDN in front.

Applies consistency-replication to the decision above.

Step 1 — State assumptions:
  - DAU: X million
  - Read:Write ratio: X:1
  - Average object size: X KB/MB

Step 2 — Calculate QPS:
  - Write QPS = DAU × writes_per_user / 86400
  - Read QPS = Write QPS × read_write_ratio
  - Peak QPS = Average QPS × 3

Step 3 — Calculate Storage:
  - Storage/day = write QPS × record_size × 86400
  - 5-year storage = storage/day × 365 × 5
  - Account for replication: × 3

Step 4 — Calculate Bandwidth:
  - Read bandwidth = read QPS × response_size
  - CDN threshold: > 1 GB/s read bandwidth

Step 5 — Determine scale tier:
  - < 1k RPS: single server
  - 1k-100k RPS: horizontal scaling + cache
  - > 100k RPS: distributed + CDN

Observable outcome: - If read bandwidth 1 GB/s → put a CDN in front.

Stage 5 — Spring Boot + JMeter: From Capacity Estimates to Measured Throughput

  • Spring Boot is the standard Java framework for building the HTTP services whose QPS, storage, and latency you estimate.
  • Apache JMeter is the open-source load testing tool that validates those estimates against a running service — generating synthetic traffic at the calculated peak load and measuring actual throughput and p95 latency.
  • The workflow: estimate peak QPS on paper → implement the endpoint → run a JMeter test plan at estimated load → compare results against your SLA targets.
  • Instrument the endpoint to compare live p95/p99 against your paper estimate: JMeter test plan — simulating estimated peak load: Capacity estimate vs.

Applies caching to the decision above.

// Close the estimation feedback loop: @Timed captures actual latency from live traffic
// so you can compare measured p95 against the "p95 < 50ms at 11,600 RPS" estimate.

@GetMapping("/api/users/{id}")
@Timed(value = "user.lookup.latency",
       percentiles = {0.50, 0.95, 0.99},    // exported to Prometheus/Grafana/Actuator
       description = "Cache-aside: Redis ~0.5ms hit, DB ~5ms miss")
public ResponseEntity<UserDto> getUser(@PathVariable String id) {
    // L1 — Redis: serves ~90%+ of requests at sub-millisecond cost
    UserDto cached = cache.opsForValue().get("user:" + id);
    if (cached != null) return ResponseEntity.ok(cached);

    // L2 — PostgreSQL: cache miss, fills cache for next request (5-minute TTL)
    return userRepository.findById(id)
        .map(u -> { cache.opsForValue().set("user:" + id, u, 5, MINUTES); return ResponseEntity.ok(u); })
        .orElse(ResponseEntity.notFound().build());
}
// If Actuator shows p99 > 100ms → add a read replica or extend Redis TTL

Stage 6 — Key Lessons from Back-of-Envelope Estimation

  • Five lessons that separate engineers who nail capacity estimation from those who overcomplicate it: 1.
  • The goal is the scale tier, not the exact number.
  • Whether your estimate lands at 80,000 RPS or 120,000 RPS doesn't change the architecture decision: both require distributed infrastructure with a load balancer and horizontal scaling.
  • A 10× error is usually tolerable; a 100× error is a design problem.
