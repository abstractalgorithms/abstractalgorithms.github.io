This walkthrough focuses on The Architectural Problem: Handling Unexpected Traffic Spikes.

Before making a design choice, clarify:

  • Imagine it is 09:00 AM on a Friday, and a highly anticipated ticket sale goes live.
  • Within seconds, millions of users hit the web application simultaneously.
  • If all these requests are routed to a single application server, the server's CPU will spike, physical memory (RAM) will be exhausted, request queues will fill up, and the server will ultimately crash under the load.

Stage 1 — Load Balancing Algorithms

  • Load balancers use specific algorithms to determine which backend server should handle an incoming request.
  • The choice of algorithm depends on the nature of the workload and the server pool capacity.
  • Round Robin and Weighted Round Robin - Round Robin: The load balancer loops through the list of servers sequentially, sending each new request to the next server in line.
  • It assumes all servers have equal capacity and all requests require equal processing time.

Stage 2 — High Availability & Health Checks

  • A load balancer is a single point of failure (SPOF) if not configured correctly.
  • To ensure high availability and prevent downtime, production systems use redundant clustering and passive health monitoring.
  • Active-Passive and Active-Active Clusters - Active-Passive Setup: Two load balancers share a virtual IP (VIP) using protocols like Keepalived or VRRP (Virtual Router Redundancy Protocol).
  • The active node handles all traffic.

    upstream backend_pool {
        server 10.0.0.4:8080 weight=3 max_fails=3 fail_timeout=10s;
        server 10.0.0.5:8080 weight=1 max_fails=3 fail_timeout=10s;
        server 10.0.0.6:8080 backup; # Handles traffic only when others are down
    }

    server {
        listen 80;
        server_name api.abstractalgorithms.dev;

        location / {
            # Route all incoming requests to the upstream pool
            proxy_pass http://backend_pool;

            # Forward client metadata to backend instances
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        }
    }

Stage 6 — Overload Protection and Backpressure

    • Rate limits protect fairness per user, token, tenant, or IP.
    • Concurrency limits cap expensive in-flight work even when request rate looks modest.
    • Bounded queues absorb short bursts; unbounded queues convert overload into memory exhaustion and extreme latency.
    • Load shedding returns a fast 429 or 503 for optional work rather than timing out every request.

End-to-end outcome

After working through the stages, you should be able to explain:

    • Load balancing distributes capacity; overload protection preserves it.
    • Autoscaling is delayed, so headroom and load shedding handle sudden spikes.

Alternatives considered

Load balancers operate at different layers of the OSI model, primarily Layer 4 (Transport Layer) and Layer 7 (Application Layer). The choice between L4 and L7 significantly impacts performance, scalability, and routing capabilities.

Load balancers operate at different layers of the OSI model, primarily Layer 4 (Transport Layer) and Layer 7 (Application Layer).

Layer 4 (Transport Layer) Load Balancing

Layer 4 load balancers make routing decisions based solely on transport-level protocols (TCP/UDP).

Layer 7 (Application Layer) Load Balancing

Layer 7 load balancers operate at the application level, parsing the full HTTP/HTTPS payload.
