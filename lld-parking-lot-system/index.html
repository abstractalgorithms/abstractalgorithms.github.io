Deep Dive

Detailed Architectural Analysis

Scenario context

You pull up to a mall garage. Three things happen:

  1. Entry gate: You press a button → get a ticket → gate opens.
  2. Parking: Find a spot (the system might display "Floor 2, Spot 14").
  3. Exit: Scan your ticket → system calculates fee based on time parked → gate opens.

The software behind this manages hundreds of concurrent vehicles across multiple floors, spot types, and pricing tiers.

This walkthrough focuses on The Mall Garage Problem.

Before making a design choice, clarify:

  • Entry gate: You press a button → get a ticket → gate opens.
  • Parking: Find a spot (the system might display "Floor 2, Spot 14").
  • Exit: Scan your ticket → system calculates fee based on time parked → gate opens.

Stage 1 — Parking Lot Design Basics

  • Before writing any code, it helps to map out the real-world entities the system must represent.
  • Spot Types — Not every bay fits every vehicle.
  • A typical garage divides its spaces into three tiers: Vehicle Types — Each vehicle carries a licensePlate and a VehicleType enum ( BIKE , CAR , TRUCK ).
  • The type determines which spot tier it can occupy — a TRUCK cannot squeeze into a CompactSpot .

Applies tree-data-structures to the decision above.

Observable outcome: The type determines which spot tier it can occupy — a TRUCK cannot squeeze into a CompactSpot .

Stage 3 — OOP Pillars in the Parking Lot Domain

  • The four OOP pillars are not abstract ideals here — each one maps to a concrete class or interface in this design.
  • Encapsulation — ParkingFloor hides its Min-Heap ParkingFloor owns a Map<VehicleType, PriorityQueue<ParkingSpot internally.
  • No external class ever touches that map directly.
  • The public surface is exactly two methods: findNearest(VehicleType) (wraps poll() ) and releaseSpot(ParkingSpot) (wraps offer() ).

Stage 4 — Finding the Nearest Spot: Min-Heap

  • A naive O(N) linear scan through all spots is too slow for a large garage.
  • Optimized: Use a Min-Heap (priority queue ordered by spot ID, lowest = nearest entrance) per vehicle type per floor.
  • Operations: - findNearest(CAR) → heaps.get(CAR).poll() → O(log N) - releaseSpot(spot) → heaps.get(spot.type).offer(spot) → O(log N) For N = 1000 spots per floor: log₂(1000) ≈ 10 operations vs.

Stage 5 — Deep Dive: Factory and Strategy Patterns

  • Callers use VehicleFactory.create(VehicleType.CAR, "ABC-123") — never new Car(...) directly.
  • This decouples object creation from business logic and makes it easy to add ElectricVehicle later.

Applies tree-data-structures to the decision above.

public class VehicleFactory {
    public static Vehicle create(VehicleType type, String plate) {
        return switch (type) {
            case BIKE   -> new Bike(plate);
            case CAR    -> new Car(plate);
            case TRUCK  -> new Truck(plate);
        };
    }
}

Observable outcome: This decouples object creation from business logic and makes it easy to add ElectricVehicle later.

Stage 6 — Strategy Pattern for Pricing

  • Pricing rules vary (hourly, daily, weekend, EV charging surcharge): The ParkingLot holds a reference to any PricingStrategy .
  • Swapping from HourlyPricing to DynamicPricing requires zero changes to the rest of the code.
  • 📊 Factory and Strategy: Class Diagram This class diagram extends the core domain model to show the full Factory and Strategy pattern integration, including the VehicleFactory creation point, the pluggable PricingStrate…
  • The key relationship is that ParkingLot depends on interfaces ( PricingStrategy , SpotAllocator ) rather than concrete classes, which is what allows EVSpot and ChargingPricing to be added without modifying any existing…

Applies vector-databases-rag to the decision above.

public interface PricingStrategy {
    double calculateFee(VehicleType type, long parkingMinutes);
}

public class HourlyPricing implements PricingStrategy {
    public double calculateFee(VehicleType type, long minutes) {
        double ratePerHour = type == VehicleType.TRUCK ? 3.50 :
                             type == VehicleType.CAR   ? 2.00 : 1.00;
        return ratePerHour * Math.ceil(minutes / 60.0);
    }
}
