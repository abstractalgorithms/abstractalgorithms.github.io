Cache-Aside & Read-Through Pattern

Mitigating high database latency under read-heavy workloads while maintaining consistency.

Structural Solution Shape

Caching keeps a reusable copy of data so an application can avoid repeating a database query, calculation, or network call. It can make responses faster and reduce database load. The trade-off: the copy may be out of date.

Problem Fit & Applicability Criteria
  • ✓Frequently read product descriptions or reference data.
  • ✓Expensive reports that can tolerate a short delay in freshness.
Core Trade-Off: Local vs shared cache
PRO: A local cache avoids network calls.CON: Each application instance has its own copy. A shared cache reduces duplication but adds a network dependency.
Primary Failure Mode: Many keys expire together

Add random TTL jitter and stagger refilling. Limit database concurrency as a safety net.

Token Bucket Rate Limiting Pattern

Traffic Shaping & Resiliencycanonical

Token Bucket Rate Limiting Pattern

Preventing service degradation and cascading resource exhaustion under sudden bursts of incoming client traffic.

Structural Solution Shape

Rate limiting enforces caps on request or resource consumption per caller, tenant, or endpoint over time to protect downstream capacity, ensure fair multi-tenant sharing, and blunt abuse.

Problem Fit & Applicability Criteria
  • ✓Protecting public APIs, login/OTP endpoints, and expensive compute routes (LLM inference, PDF export) from abuse, scraping, and brute-force attacks.
  • ✓Enforcing tiered SaaS commercial quotas (e.g., Free: 60 req/min, Pro: 1,000 req/min) and preventing noisy-neighbor starvation in multi-tenant platforms.
Core Trade-Off: Global Accuracy vs. Tail Latency
PRO: Synchronous Redis Lua checks enforce exact cross-region or cross-pod quotas.CON: Adds 0.5-2 ms network RTT per request and makes Redis availability a critical-path dependency.
Primary Failure Mode: Hot-Key Contention in Redis

Batch token leases locally at the gateway (e.g., fetch 50 tokens at a time) or shard the key across N slots (`key:{0..15}`) with N-way split quotas.

Probabilistic Membership Testing (Bloom Filter)

Membership & Filteringcanonical

Probabilistic Membership Testing (Bloom Filter)

Eliminating expensive authoritative database round-trips for non-existent keys with zero false negatives.

Structural Solution Shape

A Bloom filter is a space-efficient probabilistic data structure used to test set membership. It answers queries with "definitely not in set" (zero false negatives) or "probably in set" (with a tunable false positive rate). By eliminating expensive disk reads and database scans for non-existent keys, Bloom filters protect high-throughput databases like Cassandra, RocksDB, and HBase.

Problem Fit & Applicability Criteria
  • ✓LSM-Tree Storage Engines (RocksDB, Cassandra, HBase) to determine if an SSTable on disk contains a row key before performing expensive disk reads.
  • ✓Content Delivery Networks (Akamai) to identify "one-hit wonders" and cache items only upon their second request.
Core Trade-Off: Memory vs False Positive Rate
PRO: 10 bits per item yields a false positive rate under 1% regardless of whether the set has 1 million or 1 billion items.CON: Requires contiguous in-memory bit allocation; reducing false positive rate to 0.1% requires doubling memory to 15 bits/item.
Primary Failure Mode: Saturation Bit Fill Collapse

Monitor filter saturation ratio; deploy Scalable Bloom Filters that dynamically chain new bit arrays as capacity grows.

Circuit Breaker Fault Isolation Pattern

Traffic Shaping & Resiliencycanonical

Circuit Breaker Fault Isolation Pattern

Failing fast and isolating cascading downstream service latency before exhaustion of connection pools.

Structural Solution Shape

A stateful proxy that monitors downstream failures and slow calls over a sliding window, tripping open to fail fast in microseconds instead of letting 2,000ms+ timeouts exhaust caller thread pools.

Problem Fit & Applicability Criteria
  • ✓Synchronous HTTP/REST or gRPC calls to external third-party APIs (e.g., Stripe, Twilio, shipping carriers) where latency spikes are outside your control.
  • ✓Internal service-to-service calls on non-critical paths (recommendations, loyalty points, analytics enrichment) where a cached or degraded fallback preserves core checkout.
Core Trade-Off: Window Sensitivity
PRO: Small windows (e.g., 10 calls) or low failure thresholds (25%) trip rapidly during sudden outages, saving threads immediately.CON: Too sensitive a threshold causes false-positive trips during normal GC pauses or isolated transient network blips.
Primary Failure Mode: Misclassified 4xx Tripping

Explicitly configure recordExceptions / ignoreExceptions so only 5xx, 429, network resets, and timeouts increment the failure counter.

Horizontal Database Sharding Pattern

Distributed Storage & Partitioningcanonical

Horizontal Database Sharding Pattern

Scaling relational storage throughput and capacity beyond the physical constraints of a single database node.

Structural Solution Shape

Horizontally partitioning a dataset across independent database nodes by a shard key—using either contiguous key ranges or consistent hashing—to scale write throughput and storage beyond a single primary's CPU, IOPS, and memory ceiling.

Problem Fit & Applicability Criteria
  • ✓Write throughput or index working-set size exceeds what the largest single-node primary can sustain without p99 latency spikes or vacuum/compaction stalls.
  • ✓Data exhibits a natural isolation boundary—such as tenant_id, account_id, or region—so 95%+ of queries can route to a single shard.
Core Trade-Off: Partitioning strategy (Range vs. Hash)
PRO: Range partitioning executes ordered scans (`BETWEEN`, `ORDER BY`, prefix lookups) on 1–2 shards without scatter-gather.CON: Monotonic keys (auto-increment IDs, `now()`) concentrate 100% of inserts onto the tail shard unless prefixed with a high-cardinality tenant or hash byte.
Primary Failure Mode: Tail-shard write hotspot

Prefix the shard key with a high-cardinality attribute (`tenant_id`, `org_id`) or a 2-byte hash prefix, or switch to hash partitioning for write-heavy append logs.

Distributed Locking with Fencing Tokens

Concurrency & Coordinationcanonical

Distributed Locking with Fencing Tokens

Enforcing mutual exclusion across distributed stateless workers accessing shared non-atomic resources.

Structural Solution Shape

Distributed locking coordinates mutually exclusive access to a shared resource across independent processes that share no memory, using a network-accessible lease store such as Redis, etcd, or ZooKeeper.

Problem Fit & Applicability Criteria
  • ✓Preventing duplicate execution of expensive or non-idempotent side effects such as charging a payment gateway or provisioning cloud infrastructure.
  • ✓Coordinating single-leader election for background workers, partition consumers, or cron dispatchers where only one active controller should run.
Core Trade-Off: Consensus (etcd / ZooKeeper) vs. In-Memory Leases (Redis / Redlock)
PRO: Consensus stores guarantee linearizability and emit monotonic fencing tokens across leader failovers without relying on synchronized wall-clock bounds.CON: Consensus writes incur Raft/Zab disk fsync and quorum RTTs (typically 5–20 ms), offering lower raw throughput than single-node Redis (<1 ms).
Primary Failure Mode: Lease Expiration During Process Pause (Split-Brain)

Attach a monotonic fencing token from etcd/ZooKeeper to every downstream write and enforce `token >= last_seen_token` at the storage layer.

Log-Structured Merge-Tree (LSM) Write Buffering

Storage Engines & Internalscanonical

Log-Structured Merge-Tree (LSM) Write Buffering

Optimizing high-throughput sequential write ingestion without stalling on random disk seeks.

Structural Solution Shape

B-Trees update fixed-size disk pages (4–16 KiB) in place for fast, predictable point and range reads, whereas LSM-Trees buffer writes sequentially in memory (MemTable + WAL) and merge immutable sorted runs (SSTables) in the background for orders-of-magnitude higher write throughput.

Problem Fit & Applicability Criteria
  • ✓Choose a B-Tree when workloads are read-heavy (>70% reads), require tight p99 point-lookup and range-scan latency, and update existing keys frequently in place.
  • ✓Choose an LSM-Tree when workloads are write-heavy (IoT telemetry, time-series, event logs, append-heavy KV) where sequential disk/NVMe writes and high Zstd/LZ4 block compression matter.
Core Trade-Off: Write Amplification vs. Read Amplification
PRO: LSM-Trees convert random mutations into sequential flushes, sustaining 5x–10x higher write throughput on SSDs/NVMe.CON: Reads may probe MemTable, L0 overlapping SSTables, and multiple lower levels if Bloom filters miss or range scans span levels.
Primary Failure Mode: LSM Write Stall from Compaction Debt

Increase `max_background_jobs`, enable rate-limited compaction I/O, and alert on `rocksdb.num-files-at-level0` before hitting the stop threshold.

Saga with Compensating Transactions

Integration & Data Consistencycanonical

Saga with Compensating Transactions

Coordinating multi-service business workflows without distributed two-phase commit locks.

Structural Solution Shape

A Saga coordinates a multi-service business transaction as a sequence of local ACID transactions paired with compensating actions that semantically undo prior steps on failure, avoiding distributed 2-Phase Commit locks at the cost of eventual consistency.

Problem Fit & Applicability Criteria
  • ✓Multi-service workflows (e.g., e-commerce checkout, flight+hotel booking, loan origination) spanning independent databases.
  • ✓Long-running business processes (seconds to days) involving external payment gateways or human approvals where DB locks cannot be held.
Core Trade-Off: Orchestration vs Choreography
PRO: Orchestration makes state, timeouts, and compensation order explicit in one workflow definition with clear observability.CON: Adds an orchestrator dependency (Temporal/Step Functions) that must be operated and scaled alongside microservices.
Primary Failure Mode: Dual-Write Split-Brain

Use the Transactional Outbox pattern: write the domain change and outbox event in the same local ACID transaction, then tail it via Debezium CDC or a poller.

Transactional Outbox

Integration & Data Consistencycanonical

Transactional Outbox

Publishing integration events reliably after local database commits without dual-write races.

Structural Solution Shape

The Transactional Outbox pattern eliminates dual-write split-brain by inserting domain events into an `outbox` table inside the exact same ACID database transaction as the business state change, then relaying them asynchronously to Kafka/RabbitMQ.

Problem Fit & Applicability Criteria
  • ✓Publishing domain events (`OrderCreated`, `PaymentSettled`) to Kafka, RabbitMQ, or SNS/SQS whenever a microservice mutates its own relational or document database.
  • ✓Replacing fragile Two-Phase Commit (XA) across a database and a message broker with reliable at-least-once event delivery.
Core Trade-Off: Log-Tailing CDC (Debezium) vs. Polling Publisher (`SKIP LOCKED`)
PRO: CDC reads the WAL sequentially with near-zero impact on OLTP query plans and ~20–50 ms latency.CON: CDC requires running Kafka Connect, managing PostgreSQL logical replication slots, and handling WAL disk retention if Debezium goes down; polling is pure SQL and trivial to deploy.
Primary Failure Mode: PostgreSQL WAL Disk Exhaustion from Stalled Replication Slot

Set `max_slot_wal_keep_size` (e.g., `20GB`) on PostgreSQL 13+, alert when `pg_wal_lsn_diff` lag exceeds 1 GB, and test slot recreation + snapshot recovery.

CQRS Read/Write Separation

Integration & Data Consistencycanonical

CQRS Read/Write Separation

Scaling asymmetric read and write workloads with independent models and projections.

Structural Solution Shape

CQRS separates write-side command validation from read-side query projections, while Event Sourcing persists every state transition as an immutable append-only log of domain events rather than overwriting current rows.

Problem Fit & Applicability Criteria
  • ✓Financial ledgers, healthcare records, or compliance-heavy domains requiring a cryptographically or structurally immutable audit trail of every state change.
  • ✓Systems with extreme read/write asymmetry (e.g., 100:1 reads to writes) where read queries need specialized denormalized views in Elasticsearch or Redis.
Core Trade-Off: Read-After-Write Consistency
PRO: Decoupled async projections let write and read databases scale and fail independently.CON: Introduces replication lag (typically 10–200 ms), meaning a user who submits a command may refresh and see stale data unless the UI tracks a `streamVersion` watermark.
Primary Failure Mode: Projection Lag & Stale Read-Your-Writes

Return the committed `streamPosition` in the command response and have read queries wait (briefly) or fall back to reading the aggregate until the projection reaches that checkpoint.

Bulkhead Resource Isolation

Traffic Shaping & Resiliencycanonical

Bulkhead Resource Isolation

Preventing one slow dependency from exhausting shared thread pools and connection limits.

Structural Solution Shape

The bulkhead pattern partitions shared compute, thread pools, connection pools, and memory into isolated compartments so a slow or failing downstream dependency exhausts only its own quota rather than sinking the entire service.

Problem Fit & Applicability Criteria
  • ✓Services calling multiple downstream dependencies with different SLAs (e.g., critical payment gateway vs. non-critical recommendations or analytics).
  • ✓Multi-tenant SaaS platforms where a noisy neighbor's bursty queries or large exports could starve CPU, DB connections, or queue workers for other tenants.
Core Trade-Off: Resource Utilization vs. Isolation
PRO: Hard per-dependency caps guarantee that a stalled integration cannot consume 100% of threads, sockets, or memory.CON: Static partitions reduce statistical multiplexing—idle threads in the Payments bulkhead cannot help a sudden spike in Search traffic.
Primary Failure Mode: Unbounded Bulkhead Queue Causes OOM

Always set a tight, bounded `queueCapacity` (e.g., 10–50) or `0` (`SynchronousQueue`) and reject excess with HTTP 503.

Idempotent API Handlers

Integration & Data Consistencycanonical

Idempotent API Handlers

Making retries safe under at-least-once delivery from gateways, queues, and mobile clients.

Structural Solution Shape

Idempotency keys and deduplication logs ensure that network retries, at-least-once message deliveries, and double-clicks execute state mutations at most once while returning the original cached outcome.

Problem Fit & Applicability Criteria
  • ✓Payment, billing, and ledger APIs (e.g., Stripe-style `POST /v1/charges` with `Idempotency-Key` UUIDv4) where duplicate execution causes financial loss.
  • ✓Event-driven consumers reading from at-least-once brokers (Kafka, SQS Standard, SNS, RabbitMQ) that redeliver messages on consumer rebalance or visibility timeout expiry.
Core Trade-Off: Same-DB Transaction vs. Redis Dedup Cache
PRO: Inserting the dedup key in the same ACID transaction as the business mutation guarantees zero split-brain between state and dedup record.CON: Adds write IOPS and storage growth to the primary OLTP database, requiring TTL partitioning/pruning (e.g., 24h–7d retention).
Primary Failure Mode: Check-Then-Act Race Condition

Use an atomic `INSERT ... ON CONFLICT DO NOTHING` / `UNIQUE` constraint or Redis `SET key value NX EX 3600`—never a separate `SELECT` followed by `INSERT`.
