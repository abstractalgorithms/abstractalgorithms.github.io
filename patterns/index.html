Cache-Aside & Read-Through Pattern

Mitigating high database latency under read-heavy workloads while maintaining consistency.

Structural Solution Shape

Caching stores high-frequency read data in fast RAM instead of slow disk/network databases. Redis achieves sub-millisecond QPS by operating a single-threaded event loop paired with OS epoll I/O multiplexing, completely eliminating thread locking contention.

Problem Fit & Applicability Criteria
  • ✓Read-heavy workloads (>80% reads, <20% writes).
  • ✓Session storage, rate-limiting counters, and leaderboards.
Core Trade-Off: Concurrency Model
PRO: Single thread avoids deadlocks, lock contention, and OS context switching overhead.CON: Long-running O(N) operations (e.g. KEYS *) block all concurrent clients.
Primary Failure Mode: Cache Stampede (Thundering Herd)

Use probabilistic early expiration (XFetch algorithm) or distributed lock mutex (SETNX).

Token Bucket Rate Limiting Pattern

Traffic Shaping & Resiliencycanonical

Token Bucket Rate Limiting Pattern

Preventing service degradation and cascading resource exhaustion under sudden bursts of incoming client traffic.

Structural Solution Shape

Rate limiting controls the incoming request rate per client or IP address to prevent server overload, DDoS attacks, and resource starvation.

Problem Fit & Applicability Criteria
  • ✓Public API endpoints exposed to third-party developers.
  • ✓Authentication / login routes.
Core Trade-Off: Algorithm Selection
PRO: Token bucket permits bursts while keeping average throughput predictable.CON: Sliding window log requires more memory.
Primary Failure Mode: Race Condition in Counter

Execute Redis Lua scripts for atomic counter updates.

Probabilistic Membership Testing (Bloom Filter)

Eliminating expensive authoritative database round-trips for non-existent keys with zero false negatives.

Structural Solution Shape

Hash Tables & Probabilistic Bloom Filters provides core foundational patterns in Algorithms & Data Structures. Achieve O(1) constant time lookups and test set membership with zero false negatives using space-efficient Bloom filters.

Problem Fit & Applicability Criteria
  • ✓High-scale enterprise production systems in Algorithms & Data Structures.
  • ✓Performance-critical services requiring predictable latency bounds.
Core Trade-Off: Complexity vs Resilience
PRO: Higher fault tolerance and clear separation of concerns.CON: Adds initial architectural setup overhead.
Primary Failure Mode: Misconfiguration Overhead

Circuit Breaker Fault Isolation Pattern

Traffic Shaping & Resiliencycanonical

Circuit Breaker Fault Isolation Pattern

Failing fast and isolating cascading downstream service latency before exhaustion of connection pools.

Structural Solution Shape

Circuit Breakers monitor remote service call failure rates. If downstream failures exceed a threshold (e.g. 50%), the breaker trips to OPEN, instantly returning fallback responses instead of stalling threads.

Problem Fit & Applicability Criteria
  • ✓Microservice HTTP calls to third-party APIs.
  • ✓Database connection attempts.
Core Trade-Off: Resilience vs Freshness
PRO: Prevents thread pool exhaustion and cascading crashes.CON: Returns degraded fallback data while OPEN.
Primary Failure Mode: Flapping Circuit

Add evaluation sliding window size and recovery cooldown timeouts.

Horizontal Database Sharding Pattern

Distributed Storage & Partitioningcanonical

Horizontal Database Sharding Pattern

Scaling relational storage throughput and capacity beyond the physical constraints of a single database node.

Structural Solution Shape

Sharding splits a monolithic database into independent database nodes (shards). Each row is routed to a shard based on a shard key.

Problem Fit & Applicability Criteria
  • ✓Tables exceeding 1TB or 50,000 write QPS.
  • ✓Global multi-region data residency compliance.
Core Trade-Off: Cross-Shard Joins
PRO: Infinite storage & write throughput scaling.CON: Cross-shard SQL joins and distributed transactions are extremely slow.
Primary Failure Mode: Hotspot Shard

Salt shard keys or use composite keys (user_id + date).

Saga with Compensating Transactions

Coordinating multi-service business workflows without distributed two-phase commit locks.

Transactional Outbox

Integration & Data Consistencycanonical

Transactional Outbox

Publishing integration events reliably after local database commits without dual-write races.

Structural Solution Shape

The outbox table stores events in the same DB transaction as business rows; a relay process publishes to Kafka/RabbitMQ with at-least-once delivery.

Problem Fit & Applicability Criteria
  • ✓Microservices emitting integration events
  • ✓Need DB + broker alignment
Core Trade-Off: Relay lag
PRO: Strong local consistencyCON: Events appear after small delay
Primary Failure Mode: Stuck relay

Lag alerts and dead-letter for poison payloads.

CQRS Read/Write Separation

Scaling asymmetric read and write workloads with independent models and projections.

Structural Solution Shape

CQRS splits command (write) and query (read) paths; event sourcing stores state transitions as immutable events that can rebuild projections.

Problem Fit & Applicability Criteria
  • ✓High read/write asymmetry
  • ✓Rich audit requirements
Core Trade-Off: Complexity
PRO: Flexible read modelsCON: Event versioning and replay pipelines required
Primary Failure Mode: Stale projections

Lag metrics, replay jobs, and idempotent projectors.

Bulkhead Resource Isolation

Traffic Shaping & Resiliencycanonical

Bulkhead Resource Isolation

Preventing one slow dependency from exhausting shared thread pools and connection limits.

Structural Solution Shape

The bulkhead pattern limits resources per dependency or tenant—like ship compartments—so failures stay localized.

Problem Fit & Applicability Criteria
  • ✓Multi-tenant SaaS
  • ✓Services with heterogeneous dependency SLAs
Core Trade-Off: Pool sizing
PRO: Blast radius controlCON: Under-utilization if pools are too conservative
Primary Failure Mode: Pool exhaustion in one bulkhead

Dynamic borrowing with caps and metrics.

Idempotent API Handlers

Integration & Data Consistencycanonical

Idempotent API Handlers

Making retries safe under at-least-once delivery from gateways, queues, and mobile clients.

Structural Solution Shape

At-least-once delivery is the practical default; idempotent handlers and deduplication tables turn duplicate deliveries into harmless no-ops.

Problem Fit & Applicability Criteria
  • ✓HTTP APIs with retries
  • ✓Kafka consumers
Core Trade-Off: Dedupe store
PRO: Simple correctness storyCON: Storage and TTL governance required
Primary Failure Mode: Key collision

Scope keys per operation type and principal.
