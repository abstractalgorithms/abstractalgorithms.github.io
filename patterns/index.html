Cache-Aside & Read-Through Pattern

Mitigating high database latency under read-heavy workloads while maintaining consistency.

Structural Solution Shape

Caching is the architectural technique of retaining copies of frequently accessed, computationally expensive data in high-speed, volatile memory (e.g. Redis, Memcached, CPU caches) to bypass slow disk I/O, database table scans, and network hops. Proper caching slashes latency from tens of milliseconds to sub-milliseconds and shields databases from query saturation.

Cache-Aside & Read-Through Pattern

Mitigating high database latency under read-heavy workloads while maintaining consistency.

Structural Solution Shape

Caching is the architectural technique of retaining copies of frequently accessed, computationally expensive data in high-speed, volatile memory (e.g. Redis, Memcached, CPU caches) to bypass slow disk I/O, database table scans, and network hops. Proper caching slashes latency from tens of milliseconds to sub-milliseconds and shields databases from query saturation.

Problem Fit & Applicability Criteria
  • ✓Read-heavy workloads with high read-to-write ratios ($10:1$ or higher).
  • ✓Serving computationally expensive aggregated responses (e.g. user newsfeeds, analytics dashboards).
Core Trade-Off: In-Memory Local Cache vs Distributed Remote Cache (Redis)
PRO: Local in-process caches (Caffeine / Guava) execute in sub-microseconds without network serialization.CON: Local caches duplicate data across all application nodes and easily drift out of sync, serving inconsistent state.
Primary Failure Mode: The Cache Avalanche

Add random jitter to TTLs: TTL = base_ttl + rand(-300, 300) seconds, spreading expirations smoothly across time.

Token Bucket Rate Limiting Pattern

Traffic Shaping & Resiliencycanonical

Token Bucket Rate Limiting Pattern

Preventing service degradation and cascading resource exhaustion under sudden bursts of incoming client traffic.

Structural Solution Shape

Rate limiting controls the consumption rate of system resources by restricting the number of API calls or operations a client can make within a specified window. Proper rate limiting prevents denial-of-service (DoS) attacks, isolates noisy tenants in multi-tenant architectures, smooths burst traffic, and enforces commercial usage quotas.

Problem Fit & Applicability Criteria
  • ✓Public REST/GraphQL API Gateways (Kong, Envoy, AWS API Gateway) to protect backend microservices.
  • ✓Preventing brute-force credential stuffing attacks on authentication endpoints.
Core Trade-Off: Precision vs Memory Footprint
PRO: Token Bucket requires only 10 bytes per user (2 bytes tokens + 8 bytes timestamp).CON: Sliding Window Log tracks every request timestamp, consuming 20–50 bytes per request and requiring periodic compaction.
Primary Failure Mode: Distributed Redis Counter Race Condition

Execute counter decrements inside an atomic Redis Lua script.

Probabilistic Membership Testing (Bloom Filter)

Membership & Filteringcanonical

Probabilistic Membership Testing (Bloom Filter)

Eliminating expensive authoritative database round-trips for non-existent keys with zero false negatives.

Structural Solution Shape

A Bloom filter is a space-efficient, bit-level probabilistic data structure used to test set membership. It answers queries with "definitely not in set" (zero false negatives) or "possibly in set" (tunable false positive probability). By eliminating expensive disk reads and network lookups for non-existent keys, Bloom filters protect databases like Cassandra, RocksDB, and HBase from disk I/O starvation.

Problem Fit & Applicability Criteria
  • ✓LSM-Tree Storage Engines (RocksDB, Cassandra, HBase) to determine if an SSTable on disk contains a row key before performing expensive disk reads.
  • ✓Content Delivery Networks (Akamai) to identify "one-hit wonders" and cache items only upon their second request.
Core Trade-Off: Memory vs False Positive Rate
PRO: 10 bits per item yields a false positive rate under 1% regardless of whether the set has 1 million or 1 billion items.CON: Requires contiguous in-memory bit allocation; reducing false positive rate to 0.1% requires doubling memory to 15 bits/item.
Primary Failure Mode: Saturation Bit Fill Collapse

Monitor filter saturation ratio; deploy Scalable Bloom Filters that dynamically chain new bit arrays as capacity grows.

Circuit Breaker Fault Isolation Pattern

Traffic Shaping & Resiliencycanonical

Circuit Breaker Fault Isolation Pattern

Failing fast and isolating cascading downstream service latency before exhaustion of connection pools.

Structural Solution Shape

A circuit breaker wraps remote network calls in a stateful monitoring harness that automatically trips OPEN to fail-fast when downstream error or timeout thresholds breach, preventing caller thread exhaustion and cascading distributed outages. By failing fast, circuit breakers insulate upstream services and grant recovering dependencies breathing room to heal.

Problem Fit & Applicability Criteria
  • ✓Wrapping remote HTTP, gRPC, and database calls in distributed microservice call chains.
  • ✓Protecting caller thread pools from thread starvation and memory exhaustion during third-party API outages.
Core Trade-Off: In-Process (Resilience4j) vs Service Mesh (Envoy) Circuit Breakers
PRO: In-process breakers execute rich application fallback logic (e.g. returning stale domain objects from Redis).CON: In-process breakers must be configured in every programming language across polyglot microservices.
Primary Failure Mode: Tripping on 4xx Client Validation Errors

Configure the circuit breaker to count ONLY HTTP 5xx server errors, network timeouts, and connection reset exceptions.

Horizontal Database Sharding Pattern

Distributed Storage & Partitioningcanonical

Horizontal Database Sharding Pattern

Scaling relational storage throughput and capacity beyond the physical constraints of a single database node.

Structural Solution Shape

Database sharding is the horizontal data partitioning architecture that splits a monolithic database into multiple independent physical database instances (shards), distributing storage capacity, write IOPS, and RAM buffer pools across independent compute nodes.

Problem Fit & Applicability Criteria
  • ✓Total dataset size exceeds 1-2 Terabytes and active working sets no longer fit within single-server RAM.
  • ✓Write transaction throughput exceeds single-instance database disk IOPS and connection limits (> 10,000 writes/sec).
Core Trade-Off: Hash-Based vs Range-Based Sharding
PRO: Hash-based sharding provides mathematically uniform write distribution, eliminating write hotspots.CON: Hash-based sharding destroys range query efficiency; a query for a date range requires querying every shard in the cluster.
Primary Failure Mode: The Celebrity Key Hotspot (Data Skew)

Implement Salted Composite Keys for high-volume entities: shard_key = hash(user_id + "_" + (post_id % 10)), distributing comments across 10 shards.

Transactional Outbox

Integration & Data Consistencycanonical

Transactional Outbox

Publishing integration events reliably after local database commits without dual-write races.

Structural Solution Shape

The outbox table stores events in the same DB transaction as business rows; a relay process publishes to Kafka/RabbitMQ with at-least-once delivery.

Problem Fit & Applicability Criteria
  • ✓Microservices emitting integration events
  • ✓Need DB + broker alignment
Core Trade-Off: Relay lag
PRO: Strong local consistencyCON: Events appear after small delay
Primary Failure Mode: Stuck relay

Lag alerts and dead-letter for poison payloads.

CQRS Read/Write Separation

Scaling asymmetric read and write workloads with independent models and projections.

Structural Solution Shape

CQRS splits command (write) and query (read) paths; event sourcing stores state transitions as immutable events that can rebuild projections.

Problem Fit & Applicability Criteria
  • ✓High read/write asymmetry
  • ✓Rich audit requirements
Core Trade-Off: Complexity
PRO: Flexible read modelsCON: Event versioning and replay pipelines required
Primary Failure Mode: Stale projections

Lag metrics, replay jobs, and idempotent projectors.

Bulkhead Resource Isolation

Preventing one slow dependency from exhausting shared thread pools and connection limits.

Structural Solution Shape

The bulkhead pattern limits resources per dependency or tenant—like ship compartments—so failures stay localized.

Problem Fit & Applicability Criteria
  • ✓Multi-tenant SaaS
  • ✓Services with heterogeneous dependency SLAs
Core Trade-Off: Pool sizing
PRO: Blast radius controlCON: Under-utilization if pools are too conservative
Primary Failure Mode: Pool exhaustion in one bulkhead

Dynamic borrowing with caps and metrics.
