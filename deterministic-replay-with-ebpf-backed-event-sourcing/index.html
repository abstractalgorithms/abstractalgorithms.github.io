Detailed Architectural Analysis

Deep Dive: Stage 1 — The Solution: eBPF + Event Sourcing

  1. eBPF Tracepoints hook into sys_enter/sys_exit for every process that belongs to the target service.
  2. Each event is serialized into a fixed‑size struct containing:
    • timestamp (ns), pid, tid, syscall_id, args[], return_code.
  3. The eBPF program writes the struct into a perf event ring buffer.
  4. A user‑space consumer reads the ring buffer, writes each event to an append‑only event log (e.g., Kafka or a local file).
  5. A replay engine consumes the log, re‑injects syscalls via ptrace or seccomp‑based sandbox, preserving the original timestamp order.

Because the events are stored in a canonical, immutable log, the replay is deterministic even if the original system had clock drift or out‑of‑order packet arrivals.

Deep Dive: Stage 3 — Trade‑offs

  • Overhead: The eBPF program adds ~1 µs per syscall; fine‑grained tracing on high‑throughput services may need sampling.
  • Storage: Persisting every syscall can grow fast; consider compression or selective filtering.
  • Re‑execution cost: Replaying syscalls in a sandbox can be slower than the original run, but it’s isolated and safe for debugging.

By combining eBPF’s zero‑overhead tracing with an immutable event store, you get a deterministic, reproducible debugging surface that works in production and lets you trace back to the exact sequence that caused a bug.
