🎯 System Scenario & Requirements

System Goal

An API Gateway centralizes "cross-cutting concerns" like authentication, rate limiting, and routing at the edge of your infrastructure.

Actors & Components

  • Application or API tier
  • Core service under design
  • Operator or SRE observer

Functional Requirements

  • TLDR: An API Gateway centralizes "cross-cutting concerns" like authentication, rate limiting, and routing at the edge of your infrastructure.
  • The architectural crux is the separation of the Control Plane (managing configurations) from the Data Plane (high-performance request proxying).
  • By using an in-memory Radix Tree for routing and Redis for distributed rate limiting, the gateway ensures that backend services remain decoupled, secure, and focused solely on domain logic.

  • Constraints are derived from the rebuilt scenario stages.

This walkthrough focuses on The "Messy Front Door" Problem.

Before making a design choice, clarify:

  • Imagine you’ve successfully migrated your monolith to 200 microservices.
  • Each service has its own URL, its own way of checking user permissions, and its own rate limits.
  • Now, your mobile app needs to render a single "Home Screen" that requires data from five different services: User Profile, Notifications, Order History, Recommendations, and Promotional Banners.

Concepts in play: caching, system-design-hld-architectures, rate-limiting, tree-data-structures

Stage 2 — The Gateway Mechanics: The Plugin Pipeline

  • A request doesn't just "jump" to the backend.
  • It passes through a Linear Filter Chain .
    • Pre-Auth Filters: IP Whitelisting, DDoS protection.
    • Auth Filters: JWT signature verification, API key lookup.

Applies system-design-hld-architectures to the decision above.

Observable outcome: - Auth Filters: JWT signature verification, API key lookup.

Stage 3 — Estimations & Design Goals

  • Capacity Math (The Enterprise Scale) - Requests per Second (RPS): 100,000 (Steady state).
    • Active Consumers: 50,000 API Keys.
    • Log Volume: $100K \text{ requests/sec} \times 1KB \text{ per log} = \mathbf{100 \text{ MB/sec}}$ of log data.
  • Scaling Targets - Max Latency Overhead: 5ms.

Applies rate-limiting to the decision above.

Observable outcome: Scaling Targets - Max Latency Overhead: 5ms.

Stage 4 — High-Level Design: The Distributed Gateway Architecture

  • mermaid Internals: Radix Tree Path Lookup and Token Authentication Caching A naive routing implementation stores routes in a list and searches linearly — O(N) per request.
  • With 2,000 routes and 100,000 RPS, this burns significant CPU.
  • A Radix Tree (Patricia Trie) compresses route paths into a branching prefix structure.
  • Looking up /api/v1/users/42 traverses the tree character-group by character-group until a leaf node bound to an upstream URL is reached.
