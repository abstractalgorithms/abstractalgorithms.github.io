Stage 2 — Eviction Policies and TTL

  • Memory (RAM) is expensive and limited.
  • A cache cannot grow indefinitely.
  • To manage memory constraints, caches use two mechanisms: Time-To-Live (TTL) and Eviction Policies .
  • Time-To-Live (TTL) Every cached key should be assigned an expiration timer (TTL).

Applies consistency-replication to the decision above.

Observable outcome: Time-To-Live (TTL) Every cached key should be assigned an expiration timer (TTL).

Stage 3 — Caching Gotchas and Mitigation

  • Cache Avalanche - The Problem: A large number of cached keys expire at the exact same time, or the cache server crashes.
  • This causes all client traffic to hit the database simultaneously, causing a database crash.
    • Mitigation: Add a random jitter (e.g., adding a random offset of 1 to 5 minutes) to the TTL of every key, spreading expiration events evenly over time.
  • Cache Penetration - The Problem: Clients request keys that do not exist in either the cache or the database (e.g., searching for a non-existent user ID).

Applies database-indexing to the decision above.

Observable outcome: Cache Penetration - The Problem: Clients request keys that do not exist in either the cache or the database (e.g., searching for a non-existent user ID).

Stage 4 — Write-Around: Keep One-Time Writes Out of the Cache

  • Write-around sends writes directly to the database and invalidates any old cached value.
  • The cache is populated only if a later read needs the record.
  • It is useful for imports, audit events, large objects, and other data that is written once but may never become hot.
  • Its cost is predictable: the first read after every write is a cache miss.

Stage 6 — Capacity Planning and Observability

  • Suppose an API serves 20,000 reads per second, the database safely handles 2,500, and the target cache hit ratio is 90%.
  • The expected database read rate is 2,000 per second: within budget, but with little room for a stampede.
  • At 80% hits the database receives 4,000 reads per second and is already overloaded.
  • Capacity planning must test degraded hit ratios, not only the happy path.

End-to-end outcome

After working through the stages, you should be able to explain:

    • A cache reduces load only while its miss path remains controlled.
    • Pattern choice is primarily a consistency and failure-semantics decision.

Alternatives considered

Decision Guide: Selecting the Caching Pattern

Use this guide to choose the caching strategy for your system: - Use Cache-Aside if: - Your application is read-heavy and you want to cache data dynamically.

Redis vs Memcached: Choose Capabilities, Not Brand Recognition

Choose Memcached when values are disposable blobs, operations are simple, and rebuilding the entire cache is acceptable.
