The idea to keep with you

To keep the architecture evolvable without sacrificing reliability, Redis delivers sub-millisecond latency via RAM-resident data structures and a single-threaded event loop—no mutex contention, provided you avoid O(N) blocking commands.

TL;DR30-second simplified summary
▾

Redis multiplexes thousands of TCP connections via epoll/kqueue and executes commands sequentially on one main thread—making every single command atomic.

Production Redis mastery means choosing the right structure (Hash, ZSet, Stream), configuring eviction (allkeys-lru/lfu), and designing for sentinel/cluster failover.

Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.

Request & State Flow

Hot keys, cache stampede & big-key deletion

Why does deleting a 500MB Hash with DEL freeze Redis, and what should you use instead?

DEL frees memory synchronously on the main thread. Use UNLINK so memory reclamation happens asynchronously on a background BIO thread.

How do you mitigate a hot key receiving 200K reads/sec on one Redis shard?

Add a short-TTL L1 in-process cache (e.g., Caffeine) in app servers or replicate the hot key across N salted keys (key#0..key#N).

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Always set TTLs on cache keys and jitter expiration times (+/- 10%) to avoid synchronized cache stampedes.
  • 02Use allkeys-lfu for skewed workloads (Zipfian hot keys) and noeviction when Redis stores rate-limit/queue state.
  • 03In Redis Cluster, wrap related keys in {user:42}:profile and {user:42}:cart hash tags so multi-key Lua scripts land on the same hash slot.
