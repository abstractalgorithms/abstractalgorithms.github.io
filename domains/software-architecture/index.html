The idea to keep with you

Good architecture makes changing your mind less expensive. Start with clear boundaries, explicit ownership, and controlled communication.

From patterns to decisions.

Learn to design software systems that remain understandable, changeable, scalable, and resilient as teams, traffic, and business requirements grow.

01
Foundation / Responsibility before topology

Understand architectural boundaries.

Architecture shapes where responsibilities live, how components interact, and which decisions are expensive to reverse. Its quality is not the number of services; it is how well the structure supports the system's requirements.

Cohesion

Keep behavior and data that enforce the same business rules close together. Changes to one business capability should not require touching unrelated parts of the application.

Coupling

A dependency becomes costly when its consumer must understand internal details or coordinate every change. Prefer explicit, narrow contracts over shared implementation knowledge.

Order platform / Ordering is not payment processing

Ordering is not payment processing.

Ordering owns order status and line items. Payments owns charges, refunds, and provider interactions.

They may start as modules in one application, but each should have a clear responsibility and interface.

Lesson: A boundary separates ownership and change, not merely database tables.
Pause & reason: where would you draw the boundary?▼
  • Which responsibilities change together?
  • Who owns the data needed to enforce each rule?
  • Which operations need a single transaction?
  • Which failures should remain independent?

02
Evolution / Earn the complexity

Design for change.

A modular monolith can provide strong boundaries, one deployment, and straightforward transactions. Extract a service when independent ownership, scaling, release cadence, or fault isolation creates a concrete benefit.

ChoiceWhat it buysWhat it costs
Modular monolithIn-process calls. Simpler deployment. Straightforward transactions.Shared runtime. Shared deployment and scaling envelope.
Separate serviceIndependent deployment. Separate resources and ownership.Network failures. Distributed consistency. Additional operational overhead.

Make decisions visible

An architecture decision record captures context, alternatives, the chosen approach, its consequences, and evidence that might cause the decision to be revisited.

Keep options open

Use migration seams, compatible contracts, and staged rollouts when uncertainty is meaningful. Reversibility has value, but abstractions also have a cost.

Order platform / Reporting outgrows the main application

Reporting outgrows the main application.

Heavy reports compete with checkout for resources.

First isolate reporting behind an interface and measure the bottleneck. Then build a separate read model, compare outputs, gradually route requests, and retain a rollback path.

Lesson: Extract to solve a measured problem, not to satisfy a service-count target.
Pause & reason: where would you draw the boundary?▼
  • What specific constraint would extraction remove?
  • Can module isolation solve the problem first?
  • What new failure and consistency problems would appear?
  • How would migration and rollback work?

03
Domain modeling / One word, different meanings

Align software with the business.

A bounded context defines where a model and its language apply. Discover it by exploring real workflows with domain experts, rather than dividing entities into individual services.

Model the invariants

Entities have identity across changes. Value objects are defined by their values. Aggregates group state and behavior that must satisfy transactional rules.

Choose consistency boundaries

Keep an aggregate no larger than its invariants require. Changes across aggregates may need workflows or eventual consistency. One aggregate per transaction is a design guideline, not a universal database law.

Order platform / A customer is not one universal object

A customer is not one universal object.

Billing needs payment responsibility, shipping needs a recipient and address, and support needs interaction history.

Each context can own its model and exchange only the facts it needs. An anti-corruption layer can translate foreign concepts instead of leaking them into the local model.

Lesson: The same identifier or word does not imply shared model ownership.
Pause & reason: where would you draw the boundary?▼
  • What does this business term mean in this context?
  • Who owns the rule and its authoritative state?
  • Which rules need immediate consistency?
  • Which external concepts need translation?

04
Application structure / Policy before framework

Separate rules from infrastructure.

Clean, hexagonal, and onion architectures share a useful goal: core business policy should not depend directly on replaceable infrastructure. Define ports around application needs and implement adapters for HTTP, databases, queues, and vendors.

HTTP adapterTranslates incoming requests.
→
Use case and domainContains application workflows and business policy.
→
Payment portApplication-owned contract for payment operations.
→
Vendor adapterTranslates the application contract to a provider SDK.
Order platform / Replace a payment provider

Replace a payment provider.

Checkout currently uses one external payment provider but may need to support another.

The charge-customer use case calls an application-level payment port. A provider adapter translates that request to the vendor SDK and maps its response into application terms.

Lesson: Business decisions should not depend directly on one vendor's SDK.
  • Runtime calls may go outward even though source-code dependencies point toward application-defined contracts.
  • Do not add an interface around every class.
  • A fake adapter helps test business behavior but does not prove that the real provider integration works.
Pause & reason: where would you draw the boundary?▼
  • Which code expresses business policy?
  • Which code only translates protocols or storage formats?
  • Can the use case run without the real database or vendor SDK?
  • Which dependency should be isolated behind an application-owned contract?

05
Communication / Ownership survives the network

Choose how work crosses boundaries.

Synchronous calls suit interactions that need an immediate answer. Asynchronous messages allow work to proceed independently but introduce delay, duplicate delivery, ordering, and operational state. Neither approach removes coupling.

PatternUse whenDesign for
Synchronous APIThe caller needs an immediate result.Timeouts., Latency budgets., Unavailable dependencies.
Command messageA named capability should perform work later.Validation., Retries., Idempotency., Dead-letter handling.
Domain eventConsumers need to react to an already-committed fact.Schema evolution., Delivery guarantees., Duplicate delivery., Ordering.

Keep data ownership explicit

Services should not bypass one another's contracts by writing shared tables. Private ownership can exist within a shared database server; separate hardware is not always necessary.

Separate read needs when useful

A history projection can consume events into a query-friendly model. That is CQRS. Event sourcing, in which the event history is authoritative, is a separate optional decision.

Order platform / Order placement starts a workflow

Order placement starts a workflow.

An order must be created while inventory reservation, payment, and notification may involve separate systems.

Commit the order and an outbox record in one local transaction. A relay publishes the event. Consumers handle duplicates safely. A saga reserves inventory and charges payment, with business compensation if a later step fails.

Lesson: A saga is not a global atomic transaction. Compensation is business work and can fail too.
  • A transactional outbox closes the local database and event-record gap.
  • Event publication may happen more than once, so reliable relaying, monitoring, and idempotent consumers are still needed.
  • A distributed workflow must account for failed compensation and uncertain outcomes.
Pause & reason: where would you draw the boundary?▼
  • What identifies the logical operation?
  • Where is deduplication persisted?
  • How does the user interface describe a pending order?
  • What happens if compensation repeatedly fails?

06
Scale and resilience / Bound the blast radius

Design for load and partial failure.

Scaling is not simply adding instances. Find the constrained resource, control admitted work, and define which capabilities survive when a dependency is slow or unavailable.

Reduce avoidable work

Bound resource consumption

Order platform / No recommendations is better than no checkout

No recommendations is better than no checkout.

A recommendations dependency becomes slow or unavailable.

Give recommendations a short deadline and independent concurrency budget. Open a circuit breaker when failure thresholds are reached. Omit recommendations or use an explicitly permitted cached result while checkout continues.

Lesson: Fault isolation requires resource limits and a fallback policy, not just separate services.
  • A queue buffers bursts but cannot handle unlimited demand. Bound backlog and monitor message age.
  • Serverless functions need downstream concurrency limits.
  • Durable state should not depend on ephemeral function memory.
Pause & reason: where would you draw the boundary?▼
  • What is the critical user capability?
  • Which workloads share its connection or worker pools?
  • Which data may be stale, and for how long?
  • What is the retry budget for a request?

07
Operations / Close the feedback loop

Operate, measure, and evolve.

Architecture earns its value in production. Translate quality goals into measurable targets, test contracts and boundaries, deploy compatibly, and use incidents as evidence for the next decision.

Observe user outcomes

Define service-level objectives for success rate and latency. Track traffic, errors, saturation, and tail latency. Correlate structured logs and traces across synchronous and asynchronous boundaries.

Protect evolution

Use contract tests, schema compatibility checks, and automated dependency rules in CI. Roll out changes gradually and define rollback.

Order platform / A new dependency slows checkout

A new dependency slows checkout.

A checkout request becomes slower after a downstream dependency is introduced.

Tracing locates the added wait. Metrics show elevated p99 latency and resource saturation. Compare the result with the checkout SLO, reduce the dependency's resource budget or remove it from the critical path, then validate the change.

Lesson: Diagrams suggest a design; telemetry shows how it behaves.
  • Audit authentication, authorization, tenant isolation, sensitive-data handling, and retention across boundaries.
  • These quality attributes are architectural requirements, not a final checklist after scaling.
  • Error-budget policies should guide priorities rather than become an automatic universal feature ban.
Pause & reason: where would you draw the boundary?▼
  • Which user-visible outcome has a measurable target?
  • What boundary rule can CI enforce?
  • How would you safely test a dependency outage?
  • What incident evidence would cause you to revisit an architecture decision?

Synthesis / One connected design

Put the order platform together

The system must accept orders, reserve inventory, charge customers, send notifications, and serve order history.

A candidate architecture, not a universal answer

ClientSends an idempotent order request.
→
OrderingOwns the order and records an outbox event in the same transaction.
→

  1. Ordering owns order transitions; inventory owns reservations; payment owns charges.
  2. These logical boundaries do not all need to be separate deployments.
  3. Record the accepted order and outbox event in one local transaction.
  4. Coordinate downstream work with persisted workflow state, retries, and compensations.
  5. Build order history asynchronously and keep notifications off the checkout path.
  6. Monitor workflow age, duplicate handling, failed compensation, and user-visible completion.

The decision framework

01

What capability and invariant are we protecting?

Start from business behavior rather than a technology preference.

02

Who owns the data and contract?

Explicit ownership avoids hidden writers, cross-team schema dependencies, and ambiguous authority.

03

What consistency and communication are actually required?

Require immediate answers only when the business needs them.

04

What happens under failure and overload?

Specify deadlines, bounded resources, retries, degradation, and recovery.

05

How can the decision be verified and reversed?

Use measurable targets, migration seams, compatibility checks, and production feedback.

Practice / Explain the consequences

Make the trade-off yourself.

Exercise 01 / boundaries

Model a commerce application.

Identify responsibilities, data owners, invariants, and transactions before proposing any services.

Check your reasoning
  • Can each boundary be justified by change, ownership, or consistency?
  • Did you separate a logical module boundary from a deployment boundary?
  • Which shared models might create coordination costs?
Exercise 02 / migration

Extract reporting safely.

Explain the extraction trigger, read-model strategy, output validation, gradual rollout, rollback, and new operational risks.

Check your reasoning
  • What data lag is acceptable?
  • Which system remains authoritative during the transition?
  • How will you compare old and new outputs?
  • Could rollback silently discard new state?
Exercise 03 / recovery

Recover a partially completed order.

Inventory is reserved, payment status is uncertain, and notifications are unavailable. Describe workflow state, retries, reconciliation, compensation, and user messaging.

Check your reasoning
  • How do you avoid creating a duplicate charge?
  • How do you represent uncertainty to the user?
  • What happens if compensation fails?
  • Can notifications recover independently from order processing?
What to take away

Good architecture is a set of justified decisions.
