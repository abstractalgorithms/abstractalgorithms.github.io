01
Distributed Systems / Stage 01

Foundations & Network Physics.

Distributed nodes lack shared memory and global clocks. Every remote call traverses NIC buffers, switches, and kernel TCP stacks where packets drop, reorder, or queue behind congestion. Under Little's Law (L = λW), even a brief downstream slowdown multiplies in-flight connections and memory pressure, while partial failures leave a sender unable to tell whether a peer crashed, a packet dropped, or a reply is merely delayed.

Partial failure creates permanent ambiguity

When an RPC times out, the caller cannot know if the server never received the request, crashed mid-execution, or committed the mutation and lost the ACK. Every mutating RPC must be idempotent.

Hardware latency spans six orders of magnitude

L1 cache (~1 ns) and RAM (~100 ns) are dwarfed by NVMe (~10 us), intra-AZ RTT (~500 us), and cross-region RTT (~80 ms). Minimizing network round-trips dominates local micro-optimizations.

TCP guarantees byte-stream order, not message atomicity

TCP sliding windows and congestion control recover lost packets via retransmission, which introduces head-of-line blocking—a single dropped packet stalls all subsequent bytes on that connection.

Order platform / Preventing a Little's Law connection-pool collapse during packet loss

Preventing a Little's Law connection-pool collapse during packet loss.

A 1% packet loss on an intra-region switch pushed TCP retransmissions and RPC latency from 12ms to 1,800ms, causing inbound API threads to pile up 150x and exhaust OS file descriptors.

Applied finite per-hop deadlines (150ms), bounded concurrency limits (semaphores/AIMD adaptive concurrency), and exponential backoff with full jitter on idempotent retries, shedding excess load at the edge before thread pools saturated.

Lesson: Finite timeouts, bounded concurrency, and jittered retries prevent network jitter from cascading into node exhaustion.
Pause & reason: where would you draw the boundary?▼
  • When a TCP write succeeds locally, how much of the remote operation is actually guaranteed to have completed?
  • According to Little's Law (L = λW), what happens to your service's memory and connection pools if downstream p99 jumps 20x?
  • How do you distinguish a slow GC-paused peer from a crashed peer—or does your protocol avoid needing to?
  • Where are deadlines propagated across hops so expired client requests stop consuming downstream CPU?

RPC & Service Communication Protocols.

Service-to-service communication trades human readability for compact binary framing, strict contracts, and connection efficiency. Protobuf encodes fields using compact Tag-Length-Value (TLV) varints with explicit field numbers, allowing additive forward/backward compatibility without breaking rolling deploys. gRPC layers Protobuf over HTTP/2, multiplexing concurrent request/response streams over one TLS connection—though a single TCP packet loss still stalls all multiplexed streams.

PatternUse whenDesign for
gRPC (Protobuf over HTTP/2)Low-latency internal East-West microservice calls, strongly typed contracts, or bidirectional streaming.L7 load balancing (HTTP/2 pins L4 connections)., Deadline propagation (`grpc-timeout`)., Additive-only Protobuf field evolution.
REST / JSON over HTTP/1.1 or HTTP/2Public North-South APIs, browser clients, and cacheable resource-oriented endpoints.Payload compression and pagination., Idempotency-Key headers on POST., Explicit versioning or tolerant readers.

Never reuse or renumber Protobuf field tags

Protobuf identifies fields on the wire by integer tag, not field name. Deleting and reusing a tag causes old binaries to silently misparse new payloads; mark retired tags reserved.

HTTP/2 multiplexing needs stream flow-control tuning

Sharing one TCP connection eliminates TLS handshake overhead, but small HTTP/2 window sizes or TCP head-of-line blocking under loss can throttle high-throughput streams.

Order platform / Zero-downtime schema evolution across rolling gRPC deployments

Zero-downtime schema evolution across rolling gRPC deployments.

A checkout service renamed and changed the wire type of field `3` (`amount` from `int32` to `string`) in a shared `.proto` contract, crashing older inventory pods during a rolling deploy.

Reverted the in-place mutation, marked field `3` as `reserved`, added `amount_minor_units` as field `7` (`int64`), and deployed consumers before producers using expand-and-contract compatibility checks in CI (`buf breaking`).

Lesson: Wire compatibility during rolling upgrades requires additive-only field evolution and automated breaking-change checks.
Pause & reason: where would you draw the boundary?▼
  • Can older v1 clients and newer v2 servers coexist safely during a 30-minute rolling deployment?
  • Are gRPC connections routed through an L7 proxy or client-side load balancer rather than a single L4 connection?
  • How do you prevent a slow streaming consumer from exhausting server-side HTTP/2 send buffers?
  • Which endpoints carry explicit Idempotency-Key tokens so client retries never duplicate side effects?

Clocks, Time & Event Ordering.

Quartz oscillators drift by tens of parts per million, and NTP synchronization can jump backward (step) or slew unpredictably across asymmetric network paths. Using wall-clock Last-Write-Wins (LWW) timestamps silently drops concurrent writes when one node's clock lags by even 50ms. Lamport timestamps establish a partial causal order (a -> b => L(a) < L(b)), Vector Clocks detect true concurrency (a || b), and Google's TrueTime bounds physical clock uncertainty [earliest, latest] via GPS and atomic clocks.

ChoiceWhat it buysWhat it costs
Wall Clock (NTP / LWW)Zero extra state; human-readable timestamps. Sufficient for approximate log correlation and TTL expiration.NTP backward jumps and clock skew silently discard newer writes in LWW. Cannot distinguish causality from concurrency.
Lamport & Vector ClocksCaptures exact happens-before causality without synchronized hardware. Vector clocks explicitly flag conflicting concurrent updates for merge/CRDT resolution.Lamport timestamps cannot tell if two events were concurrent. Vector clocks grow O(N) with the number of writing actors/replicas.
Hybrid Logical Clocks (HLC) / TrueTimeCombines physical time proximity with monotonic logical counters (HLC). Enables external consistency (commit-wait) when uncertainty ε is bounded.TrueTime requires specialized GPS/atomic clock hardware. Commit-wait adds 2ε latency to write transactions.
Order platform / Silent data loss from NTP skew in a Last-Write-Wins profile store

Silent data loss from NTP skew in a Last-Write-Wins profile store.

A user updated their shipping address on Node A (clock ahead by 120ms) and immediately corrected a typo on Node B (clock behind by 80ms). The correction vanished.

Because the store used physical wall-clock LWW (`updated_at`), Node B's newer write carried a smaller timestamp and was silently overwritten by Node A's stale replica. Replacing wall-clock LWW with Hybrid Logical Clocks (HLC) and per-key version vectors preserved causal ordering and surfaced concurrent edits.

Lesson: Never use unsynchronized wall-clock timestamps for conflict resolution or distributed ordering; use logical clocks or causal version vectors.
Pause & reason: where would you draw the boundary?▼
  • If an NTP daemon steps a server's clock backward by 200ms, what invariants in your codebase break?
  • Are you measuring elapsed durations with a monotonic clock (`CLOCK_MONOTONIC`) rather than wall time (`CLOCK_REALTIME`)?
  • When two replicas accept concurrent offline writes, does your system silently drop one (LWW) or preserve both via vector clocks/CRDTs?
  • How does your database assign snapshot read timestamps without stale reads across regions?

Distributed Systems / Stage 04

Replication & Consensus Models.

Replication improves durability and read scale, but introduces divergence risk. Single-leader replication orders writes at one primary and ships WAL/binlog entries to followers (sync or async). Multi-leader accepts writes in multiple regions but requires conflict resolution. Leaderless Dynamo-style clusters write to W and read from R of N replicas, achieving overlap when R + W > N. For linearizable state (metadata, locks, ledgers), Raft consensus uses randomized election timeouts, term numbers, and strict majority quorums (floor(N/2) + 1) so at most one leader is elected per term and committed entries are never lost.

Quorum R + W > N alone does not guarantee linearizability

Under concurrent writes or sloppy quorums/hinted handoff, Dynamo-style quorums can return stale values unless paired with read-repair, anti-entropy Merkle trees, and causal versioning.

Raft safety hinges on the Leader Completeness property

A candidate can only win an election if its log is at least as up-to-date as a majority of voters, guaranteeing the new leader already holds every previously committed entry.

Async replication risks committed data loss on failover

Promoting a lagging async follower after a primary crash drops acknowledged writes; semi-synchronous replication (waiting for at least one follower ACK) bounds loss at the cost of write latency.

Order platform / Preventing split-brain during an asymmetric datacenter partition in Raft

Preventing split-brain during an asymmetric datacenter partition in Raft.

A 5-node etcd cluster split into a 2-node minority (including the old leader) and a 3-node majority after a top-of-rack switch failure.

The 3-node majority incremented the Raft term, elected a new leader, and continued committing writes. Meanwhile, the old leader in the 2-node minority could not gather 3 ACKs for heartbeats or AppendEntries, stepped down via CheckQuorum, and rejected stale reads/writes—preventing split-brain divergence.

Lesson: Odd-numbered majority quorums (`floor(N/2) + 1`) ensure at most one partition can ever elect a leader or commit state.
  • Read-only queries served by a Raft leader still risk stale reads if the leader was partitioned and has not confirmed its lease/ReadIndex with a quorum.
  • Multi-leader replication shifts complexity from failover availability to deterministic conflict resolution.
Pause & reason: where would you draw the boundary?▼
  • Under CAP/PACELC, does this workload choose Consistency or Availability during a partition, and Latency or Consistency in normal operation?
  • If the primary database crashes right after acknowledging a write, can an async replica lose that transaction on promotion?
  • How does a Raft leader serve linearizable reads without writing a no-op entry to the log on every read?
  • Why is a 4-node consensus cluster no more fault-tolerant than a 3-node cluster?

Distributed Data Partitioning & Sharding.

Naive hash(key) % N sharding fails catastrophically when N changes, relocating nearly 100% of keys and triggering database stampedes. Consistent hashing maps both nodes and keys onto a 0..2^32-1 ring so adding or removing a node moves only K/N keys between immediate neighbors. Virtual nodes (vnodes) assign many ring tokens per physical machine to smooth key variance and weight heterogeneous hardware, while range partitioning supports efficient range scans at the risk of sequential hot-spots.

ChoiceWhat it buysWhat it costs
Consistent Hash Ring + VnodesUniform key distribution across heterogeneous nodes. Adding or removing a node moves only ~1/N of keys.Cannot execute ordered range queries without scatter-gather across all shards. Celebrity/hot keys still overload a single shard.
Range PartitioningSupports fast contiguous range scans (`WHERE timestamp BETWEEN ...`). Easy to split hot ranges dynamically (like Spanner/CockroachDB).Monotonic keys (timestamps, auto-increment IDs) concentrate all writes on the newest tail shard.

Mitigate hot keys with salting or bounded-load hashing

Consistent hashing balances average key count, not request QPS. For viral celebrity keys, append a small bounded suffix (key#0..k) for reads/writes or use consistent hashing with bounded loads.

Decouple logical shards from physical nodes

Pre-allocating fixed logical partitions (e.g., 4,096 hash slots in Redis Cluster) lets you rebalance whole slots between physical hosts without rehashing individual keys.

Order platform / Eliminating shard skew and migration stampedes in a 64-node cache cluster

Eliminating shard skew and migration stampedes in a 64-node cache cluster.

A 64-node Memcached fleet using `hash(key) % 64` suffered a 98% cache miss storm and PostgreSQL overload whenever a single node rebooted, and uneven hardware sizes left some nodes at 90% RAM while others sat at 40%.

Migrated to a consistent hash ring with 256 virtual nodes per 64GB host (and 512 vnodes for 128GB hosts). Node loss now relocated only ~1.5% of keys to adjacent vnodes, and key-salting (`hot_key#0..7`) spread viral product lookups across 8 shards.

Lesson: Consistent hashing bounds key movement to K/N, while virtual nodes and key-salting cure physical skew and hot-key traffic spikes.
Pause & reason: where would you draw the boundary?▼
  • What percentage of keys must move if you scale your cluster from 10 nodes to 11 nodes?
  • How many virtual nodes per physical host are needed to keep standard deviation of key load under 5%?
  • If one tenant or celebrity key receives 30% of all QPS, how do you prevent that single shard from saturating?
  • Do your access patterns require range scans (favoring range partitioning) or point lookups (favoring hash partitioning)?

Caching & In-Memory Architectures.

In-memory caches cut read latency from milliseconds to sub-millisecond, but introduce coherence and stampede hazards. Cache-aside lets the application manage misses and keeps the cache off the critical write path, whereas read-through/write-through delegate origin I/O to the cache provider. Write-back buffers writes in RAM for extreme throughput at the risk of data loss on node crash. Under high concurrency, expiring a hot key triggers a cache stampede unless guarded by singleflight request coalescing or probabilistic early expiration.

Stop cache stampedes with Singleflight + probabilistic refresh

Singleflight coalesces 5,000 concurrent cache misses for the same key into 1 origin database query, while jittered TTLs and XFetch probabilistic early refresh renew hot keys before they expire.

Guard against cache penetration on non-existent keys

Repeated queries for missing IDs bypass the cache and hammer the database. Cache explicit null tombstones with short TTLs or place an in-memory Bloom filter in front of the origin.

Avoid write-invalidation races

Concurrent read-miss + write updates can leave stale data in cache if a slow miss overwrites a newer invalidation. Use versioned/fenced SET or CDC-driven invalidation.

Order platform / Defeating a midnight TTL thundering herd on a flash-sale catalog

Defeating a midnight TTL thundering herd on a flash-sale catalog.

Every night at 00:00 UTC, 20,000 cached product pages expired simultaneously, sending 80,000 concurrent SQL queries to PostgreSQL and crashing the primary.

Added ±15% random TTL jitter to spread expirations, wrapped cache-miss origin fetches in Go `singleflight.Group` so only 1 goroutine queried Postgres per key, and enabled stale-while-revalidate serving for 30 seconds during background refresh.

Lesson: TTL jitter, singleflight coalescing, and stale-while-revalidate turn catastrophic cache expirations into flat origin load.
  • Write-back (write-behind) caching risks permanent data loss if a cache node crashes before flushing dirty pages to durable storage.
  • L1 in-process caches eliminate network hops but require pub/sub invalidation or ultra-short TTLs to bound cross-pod staleness.
Pause & reason: where would you draw the boundary?▼
  • If 10,000 concurrent requests miss on the exact same expired key, how many queries hit your database?
  • How do you prevent queries for non-existent IDs (penetration) from bypassing the cache?
  • Can a slow read-miss populate the cache with stale data after a concurrent write already invalidated it?
  • What happens to database CPU if the entire Redis cluster restarts cold?

Distributed Locking & Coordination.

Single-node mutexes fail across machines, and naive Redis SET NX EX locks fail when a lock holder experiences a Stop-The-World GC pause or VM stall: its TTL expires, Node B acquires the lock, and Node A resumes and corrupts shared state. Safe distributed locking requires two layers: (1) a consensus-backed lease service (etcd/ZooKeeper) with active keep-alive heartbeats, and (2) a monotonically increasing fencing token (e.g., etcd mod_revision) passed to the storage engine, which rejects any write carrying a token lower than the highest seen.

Consensus Lock Service (etcd / ZooKeeper)Grants a time-bounded lease via Raft/Zab and returns a monotonically increasing fencing token (e.g., token = 33).
→
Lock Holder (Worker A)Renews the lease via heartbeat while executing work; attaches token = 33 to every downstream storage mutation.
→
Lease Expiry & New Holder (Worker B)If Worker A freezes in a GC pause, the lease expires and Worker B acquires the lock with higher token = 34.
→
Fenced Storage EngineProcesses Worker B's write (token = 34) and rejects Worker A's late zombie write (token = 33 < 34).

Fencing tokens are mandatory for correctness, not optional

Without storage-side fencing token validation, no distributed lock—not even Redlock or etcd—can prevent a GC-paused zombie client from overwriting a newer lock holder's state.

Distinguish efficiency locks from correctness locks

If a duplicate execution merely wastes a few cents of compute (efficiency), a simple Redis lease suffices. If duplicate execution corrupts money or inventory (correctness), you need Raft leases + fencing tokens.

Order platform / Stopping zombie-worker overwrites during JVM GC pauses

Stopping zombie-worker overwrites during JVM GC pauses.

A distributed cron scheduler used a 10-second Redis `SET NX PX` lock to ensure only one worker compacted a billing file. During a 14-second JVM GC pause on Worker A, Worker B acquired the lock; Worker A then woke up and overwrote Worker B's output.

Migrated lock coordination to etcd leases that returned a monotonic `revision` as a fencing token, and added an optimistic compare-and-swap check (`WHERE fencing_token < :new_token`) on the metadata store. When Worker A woke up with token 41 after Worker B wrote with token 42, the database rejected Worker A's stale write.

Lesson: A distributed lock without a storage-enforced fencing token cannot guarantee mutual exclusion across process pauses.
  • Redlock relies on bounded clock drift across independent Redis primaries and provides no fencing token, making it unsafe for strict correctness locks.
  • Keep lease TTLs and renewal intervals tuned so transient 1-second network blips do not cause unnecessary lock churn.
Pause & reason: where would you draw the boundary?▼
  • If the current lock holder freezes for 2x the lease TTL due to a GC pause or VM live-migration, what stops it from writing when it resumes?
  • Does your downstream database or object store actually validate and reject stale fencing tokens?
  • Is this lock protecting strict correctness (requiring consensus + fencing) or merely avoiding duplicate work (efficiency)?
  • What happens if the lock service itself becomes partitioned from half the workers?

A fintech wallet platform serves 50M users across US and EU regions, requiring <50ms local balance reads, zero double-spend under network partitions, and resilience against cache stampedes and zombie workers.

An availability zone loses network connectivity while a settlement worker inside it is mid-GC pause. Naive single-node locks or async replication would allow split-brain commits or stale zombie overwrites.

The minority AZ's Raft followers cannot form a majority quorum and reject writes; the healthy majority elects a new leader, issues a higher fencing token to a healthy worker, and the storage engine rejects the old worker's stale token when it unpauses.

The decision framework

01

Under CAP/PACELC, what does this operation trade off during a partition and during normal operation?

Choose CP (linearizable quorum) for financial/inventory invariants and AP (eventual convergence) for feeds, analytics, or counters.

02

Are all mutating RPCs idempotent and bounded by propagated deadlines?

Network timeouts leave completion ambiguous; idempotency keys make retries safe, and deadlines stop Little's Law queue explosions.

03

Does ordering depend on physical wall clocks or causal logical clocks?

NTP skew and backward steps corrupt wall-clock LWW; use Lamport, Vector, or Hybrid Logical Clocks for causal correctness.

04

How does data partitioning handle node churn and hot keys?

Use consistent hashing with virtual nodes to bound reshuffling to K/N, and salt or bound-load celebrity keys.

05

If a lock holder or leader stalls in a GC pause, what enforces mutual exclusion?

Pair consensus leases with monotonically increasing fencing tokens validated at the storage layer.

What to take away

Good architecture is a set of justified decisions.

Distributed systems replace the illusion of a single reliable machine with explicit protocols for partial failure: bounded deadlines, idempotent RPCs, logical clocks, majority quorums, consistent hash rings, and fenced leases.
