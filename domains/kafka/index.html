STAGE 01 · SHIFT IN MINDSET & STORAGE PHYSICSfoundation

Why Sequential Disk + OS Page Cache Beats In-Memory Queues.

Why this matters: Understand sequential segment writes, sparse offset indexes, and zero-copy sendfile() mechanics.

Traditional brokers (ActiveMQ/RabbitMQ) track per-message delivery state in B-trees and delete messages on ack—causing random disk I/O and memory fragmentation when slow consumers build up multi-gigabyte backlogs. Kafka flips the model: partitions are append-only segment files (.log + .index + .timeindex) on disk.

Sequential NVMe/disk throughput reaches hundreds of MB/s—matching network NIC speeds—while Linux kernel Page Cache keeps recent log segments in RAM without JVM heap GC overhead. When consumers read near the tail, Kafka calls sendfile() to transfer bytes directly from kernel page cache to the NIC socket buffer, bypassing user-space JVM copies completely.

STAGE 02 · CORE PRIMITIVES & DURABILITYcore

ISR Replication, High Watermark & Idempotent Producer Sequence Numbers.

Why this matters: Prevent silent data loss on leader failover and eliminate duplicate records during network retries.

With acks=1, a leader writes to its local page cache and immediately acknowledges the producer. If the leader crashes before followers replicate that offset, the acknowledged message is permanently lost.

Production durability requires three settings together:

  1. acks=all + min.insync.replicas=2 (with replication.factor=3): A write commits only after the leader and at least one ISR follower persist it, advancing the High Watermark (HW)—consumers can never read uncommitted offsets above HW.
  2. enable.idempotence=true: Assigns each producer a (PID, epoch) and monotonic per-partition sequence number so broker-side deduplication drops retried batches cleanly while preserving strict ordering (max.in.flight.requests.per.connection <= 5).

STAGE 03 · CONSUMER SCALING & REBALANCE STABILITYcore

Cooperative Incremental Rebalancing & Static Group Membership.

Why this matters: Eliminate stop-the-world consumer group pauses during rolling deployments and transient GC stalls.

Classic Eager rebalancing revokes all partitions across every consumer in a group whenever one pod restarts—halting cluster-wide consumption for seconds to minutes.

Configure partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor (revoking only the specific partitions moving to a new owner) and group.instance.id (Static Membership) so rolling pod restarts within session.timeout.ms (e.g., 45s) reclaim their exact partitions without triggering any rebalance.

STAGE 04 · PRODUCTION IMPLEMENTATION & POISON PILLScore

Manual Offset Commits, Dead-Letter Topics & Hot-Partition Mitigation.

Why this matters: Implement at-least-once idempotent consumption with non-blocking Dead-Letter Queue (DLQ) routing in Java.

Enabling enable.auto.commit=true commits offsets on a background timer before your consumer finishes writing to the database—silently losing messages if the pod crashes mid-batch.

import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.clients.producer.*;
import java.time.Duration;
import java.util.*;

public final class SafeKafkaEventProcessor {
    private final KafkaConsumer<String, String> consumer;
    private final KafkaProducer<String, String> dlqProducer;
    private final String dlqTopic;

    public SafeKafkaEventProcessor(
            KafkaConsumer<String, String> consumer,
            KafkaProducer<String, String> dlqProducer,
            String dlqTopic) {
        this.consumer = consumer;
        this.dlqProducer = dlqProducer;
        this.dlqTopic = dlqTopic;
    }

    public void pollAndProcessBatch(RecordHandler handler) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(250));
        if (records.isEmpty()) return;

        Map<TopicPartition, OffsetAndMetadata> offsetsToCommit = new HashMap<>();
        for (TopicPartition tp : records.partitions()) {
            List<ConsumerRecord<String, String>> partitionRecords = records.records(tp);
            for (ConsumerRecord<String, String> rec : partitionRecords) {
                try {
                    handler.applyIdempotently(rec.key(), rec.value(), rec.offset());
                } catch (NonRetryablePayloadException badPayload) {
                    // Route poison pill to DLQ synchronously so partition is not blocked forever
                    dlqProducer.send(new ProducerRecord<>(dlqTopic, rec.key(), rec.value()));
                }
                offsetsToCommit.put(tp, new OffsetAndMetadata(rec.offset() + 1));
            }
        }
        dlqProducer.flush();
        consumer.commitSync(offsetsToCommit);
    }

    @FunctionalInterface
    public interface RecordHandler {
        void applyIdempotently(String key, String value, long offset);
    }
}
NON-BLOCKING ERROR RECOVERY

Tiered Retry Topics & Dead-Letter Queue (DLQ) Topology

Engineering Decision Framework
Problem
How to handle malformed or permanently failing events in an ordered Kafka partition without stalling all subsequent events for healthy users.
Naive Solution
Retry the failing record infinitely in a while(true) loop before calling commitSync().
Why It Fails
One corrupted JSON payload blocks the entire partition indefinitely (Head-of-Line blocking), causing consumer lag to grow unboundedly.
Alternatives
Compare infinite blocking retries, silent drop on exception, and bounded retry topics + Dead-Letter Topic (DLQ).
Engineering Decision
Apply 2–3 fast in-memory retries for transient blips, then publish poison-pill records to a dedicated Dead-Letter Topic ({topic}.dlq) with original headers/offset metadata before advancing the committed offset.
Trade-Offs
Preserves partition availability and zero message loss in exchange for out-of-band DLQ replay tooling.

Exactly-Once Semantics (EOS) Realities & When Not to Use Kafka.

Why this matters: Clarify what Kafka EOS actually covers and identify workloads where simpler queues or databases win.

The Exactly-Once Myth: Kafka's transactional EOS (isolation.level=read_committed + transactional producer) guarantees atomic read-process-write strictly inside Kafka-to-Kafka pipelines (e.g., Kafka Streams). The moment a consumer writes to PostgreSQL, Redis, or an external REST API, Kafka cannot span a distributed 2PC transaction across that external system.

For Kafka-to-Database pipelines, achieve Effective Exactly-Once via At-Least-Once delivery + Idempotent Consumer writes (deduplicating on (topic, partition, offset) or business event_id inside the target database transaction).

When NOT to Use Kafka: Do not deploy Kafka for simple task queues needing per-message priority, delayed/scheduled retries on millions of arbitrary timestamps, or low-volume (< 500 msg/s) background jobs where Amazon SQS, RabbitMQ, or PostgreSQL FOR UPDATE SKIP LOCKED eliminates broker/KRaft cluster operations completely.
