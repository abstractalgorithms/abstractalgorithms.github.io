Kubernetes

Treating Kubernetes like a magic self-healing platform—while misconfiguring liveness probes, omitting preStop connection draining, setting minAvailable: 100% on PodDisruptionBudgets, or ignoring Linux CFS CPU throttling—causes rolling deployments to drop live traffic and freeze cluster upgrades. Production Kubernetes mastery means understanding the reconciliation loop (API Server -> etcd -> Scheduler -> Kubelet), decoupling readiness from liveness, right-sizing CPU/memory cgroups, and coordinating graceful pod termination.

STAGE 01 · SHIFT IN MINDSET & CONTROL PLANEfoundation

API Server, etcd Raft Quorum, Scheduler & Kubelet Watch Loops.

Why this matters: Trace how a Deployment rollout moves asynchronously through watch streams without synchronous orchestration.

Kubernetes never executes imperative commands like 'start pod X on node Y'. Every component talks exclusively to kube-apiserver, which validates RBAC/admission webhooks and writes objects into etcd (Raft consensus).

  1. Deployment Controller sees replicas: 6 vs. 0 existing and creates a ReplicaSet.
  2. ReplicaSet Controller creates 6 Pod objects with spec.nodeName = "".
  3. kube-scheduler filters nodes (taints, resource requests, topology spread constraints) and scores candidates, binding spec.nodeName.
  4. kubelet on that node receives the watch event, invokes CRI (containerd) to pull images, CNI to attach pod IP, and starts probes.

STAGE 02 · LIFECYCLE & ZERO-DOWNTIME DRAINScore

Startup, Readiness & Liveness Probes + Zero-502 Termination Sequence.

Why this matters: Prevent cascading probe restart storms and eliminate connection resets during pod termination.

  • startupProbe: Protects slow-starting JVMs/ML models during boot before liveness checks activate.
  • readinessProbe: Controls whether the pod's IP is included in EndpointSlices (receiving live traffic). Fails safely when warm-up or critical downstream circuit breakers open.
  • livenessProbe: Restarts the container (SIGKILL after grace period) when the process is deadlocked. Never check external databases or Redis inside livenessProbe—a transient DB stall will cause kubelet to kill your entire healthy app fleet simultaneously.

The Race Condition During Pod Termination: When a pod is deleted, kubelet sends SIGTERM to the container at the exact same moment the EndpointSlice controller notifies kube-proxy/Envoy to remove the pod's IP. For 1–3 seconds, ingress proxies still send new requests to a pod that already closed its HTTP server.

Fix: Add a lifecycle.preStop sleep 5 hook and set terminationGracePeriodSeconds: 45 so the pod keeps accepting in-flight requests until iptables/xDS rules propagate, then drains cleanly.

03
STAGE 03 · KERNEL PHYSICS, CFS QUOTAS & DNS NDOTScore

Linux CFS CPU Throttling, Memory OOMKill & The ndots:5 DNS Storm.

Why this matters: Eliminate artificial p99 tail latency caused by CFS CPU limits and Kubernetes DNS search path amplification.

In Kubernetes, resources.requests reserves guaranteed capacity for scheduling, whereas resources.limits enforces hard Linux cgroup ceilings:

  • Memory Limit (memory.max): Exceeding it triggers an immediate kernel OOMKill (Exit Code 137). Always set memory.requests == memory.limits for predictable QoS.
  • CPU Limit (cpu.cfs_quota_us): Linux enforces CPU limits over 100 ms periods. An 8-thread Java/Python service with limits.cpu: 1 (100 ms quota per 100 ms wall time) consumes its entire 100 ms quota in 12.5 ms across 8 cores, then gets frozen by the kernel for the remaining 87.5 ms—injecting 87 ms tail stalls even when the host node is 70% idle.

Production Best Practice: Set accurate requests.cpu (for scheduling and HPA) and omit limits.cpu (or set generous burst headroom) on latency-critical services while relying on Guaranteed memory bounds.

The ndots:5 DNS Multiplier: Kubernetes /etc/resolv.conf defaults to options ndots:5. Any external hostname with fewer than 5 dots (e.g., api.stripe.com, 2 dots) triggers 4 failed search-domain lookups (api.stripe.com.default.svc.cluster.local, etc.) before resolving externally—multiplying CoreDNS UDP traffic 5x and exhausting nf_conntrack tables. Set dnsConfig.options: [{name: ndots, value: "2"}] or use trailing dots (api.stripe.com.).

STAGE 04 · HIGH AVAILABILITY & MANIFEST AUDIT GUARDcore

PodDisruptionBudgets, Topology Spread & Automated Manifest Linter.

Why this matters: Prevent cluster upgrade deadlocks and single-AZ outages with automated manifest policy checks in Python.

A PodDisruptionBudget (PDB) with minAvailable: 100% (or maxUnavailable: 0 on a 1-replica Deployment) blocks kubectl drain and cluster autoscaler node consolidation indefinitely, halting security patching.

def validate_production_pod_spec(spec: dict) -> list[str]:
    violations: list[str] = []
    replicas = spec.get("replicas", 1)
    if replicas < 2:
        violations.append("Production services require replicas >= 2 across Availability Zones")

    pdb = spec.get("pdb", {})
    if pdb.get("maxUnavailable") == 0 or pdb.get("minAvailable") == "100%":
        violations.append("PDB blocks voluntary node drains; set maxUnavailable >= 1 or <= 25%")

    for container in spec.get("containers", []):
        name = container.get("name", "unknown")
        res = container.get("resources", {})
        req_mem = res.get("requests", {}).get("memory")
        lim_mem = res.get("limits", {}).get("memory")
        if not req_mem or req_mem != lim_mem:
            violations.append(f"Container '{name}': set requests.memory == limits.memory to prevent OOM evictions")
        if "cpu" in res.get("limits", {}):
            violations.append(f"Container '{name}': remove hard limits.cpu to prevent Linux CFS 100ms throttling")

    if not spec.get("hasPreStopDrain", False):
        violations.append("Missing preStop drain hook; rolling deploys will drop in-flight traffic")
    return violations

Engineering Decision Framework
Problem
How to prevent rolling deployments and cluster node upgrades from dropping user requests or deadlocking node drains.
Naive Solution
Use default Kubernetes probe/termination settings and set PodDisruptionBudget minAvailable: 100% to 'guarantee uptime'.
Why It Fails
Default termination closes sockets before EndpointSlices propagate, while minAvailable: 100% prevents Kubernetes from ever draining a node.
Alternatives
Compare default deployment settings, minAvailable: 100% PDBs, and rolling updates (maxUnavailable: 0, maxSurge: 25%) + preStop sleep + maxUnavailable: 1 PDB.
Engineering Decision
Configure maxUnavailable: 0, maxSurge: 25% on Deployments, add a 5s preStop sleep hook, spread pods across AZs (maxSkew: 1), and set PDB maxUnavailable: 1 (or 25%).
Trade-Offs
Adds ~5 seconds per pod during rollouts in exchange for zero dropped connections and safe automated node upgrades.

STAGE 05 · PRODUCTION BOUNDARIES & WHEN NOT TO USE KUBERNETESdeepDive

StatefulSets, Storage Operators & When Managed Serverless Wins.

Why this matters: Evaluate stateful workloads on Kubernetes and identify teams/workloads where Kubernetes adds unnecessary toil.

StatefulSets provide stable network identities (db-0, db-1), ordered rollout/scaling, and sticky PersistentVolumeClaims (PVCs). However, running high-IOPS primary databases on Kubernetes requires mature Operators (CloudNativePG, Strimzi) and local NVMe CSI drivers—because network-attached EBS volumes add 1–3 ms per WAL fsync.

When NOT to Use Kubernetes: Do not adopt self-managed Kubernetes for a 5-person engineering team running 4 CRUD services and a PostgreSQL database. Managed container platforms (AWS ECS Fargate, Google Cloud Run) or PaaS platforms eliminate CNI upgrades, kube-apiserver certificate rotations, etcd backups, and ingress controller toil so engineers ship product features instead of YAML.

Should you check external database connectivity inside a Kubernetes `livenessProbe`?

Never—a transient database blip will fail liveness across every pod simultaneously, triggering a self-inflicted fleet restart storm.

Should you set hard `limits.cpu` on latency-sensitive multi-threaded pods?

Omit hard `limits.cpu` (while setting accurate `requests.cpu`) so Linux CFS quota enforcement does not freeze multi-threaded runtimes mid-request.
