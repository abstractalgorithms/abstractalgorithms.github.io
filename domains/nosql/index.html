STAGE 01 · SHIFT IN MINDSET & PARTITION KEYSfoundation

Query-Driven Modeling, Composite Keys & Time-Bucketed Partitions.

Why this matters: Design bounded partition and clustering keys that prevent single-node hot spots and scatter-gather scans.

In SQL, you design normalized entity tables first and write arbitrary WHERE and JOIN clauses later. In NoSQL, you start with your exact read queries and shape (partition_key, clustering_key) so each query reads a contiguous slice from a single partition.

The Unbounded Partition Trap: Partitioning an IoT or audit log table solely by tenant_id means an enterprise tenant generating 5M events/day accumulates 1.8 billion rows in one physical partition—exceeding the ~100 MB partition sweet spot and crashing compaction/repair. Adding a time bucket (PRIMARY KEY ((tenant_id, bucket_date), event_ts, event_id)) caps every physical partition cleanly and aligns with Time-Window Compaction (TWCS).

UNBOUNDED KEY VS. TIME-BUCKETED PARTITION

Preventing Multi-Gigabyte Partition Bloat With Composite Keys

After · Time-Bucketed Composite Key ((tenant_id, date), ts)

STAGE 02 · CORE PRIMITIVES & LSM-TREE INTERNALScore

MemTables, SSTables, Bloom Filters & Compaction Strategies.

Why this matters: Control read amplification and disk I/O spikes by matching compaction strategies to workload patterns.

Because SSTables are immutable, updating or deleting a key writes a newer version (or tombstone marker) to a new SSTable. A point read must check the MemTable and potentially multiple SSTables unless accelerated by in-memory Bloom filters (which rule out non-existent keys in O(k) hashes with ~1% false-positive rate) and block-offset sparse indexes.

Choose compaction strategy by workload:

  • Size-Tiered Compaction (STCS): Merges similarly sized SSTables; best for pure write-heavy ingest, but requires 50% free disk headroom for major compactions.
  • Leveled Compaction (LCS): Organizes SSTables into exponentially growing levels (L0, L1, L2...) with non-overlapping key ranges per level; bounds read amplification to 1 SSTable per level (ideal for update-heavy, read-sensitive KV workloads) at higher write amplification.
  • Time-Window Compaction (TWCS): Groups SSTables strictly by time window (1 day); ideal for TTL time-series because expired windows drop whole files instantly without tombstone compaction.

STAGE 03 · QUORUM CONSISTENCY & TOMBSTONE TRAPScore

Tunable Quorums (R + W > N), Read Repair & Tombstone Storms.

Why this matters: Configure quorum overlap for strong consistency and eliminate query timeouts caused by delete tombstones.

With replication factor N=3N = 3N=3, configuring W=2W = 2W=2 (LOCAL_QUORUM) and R=2R = 2R=2 ensures R+W=4>3R + W = 4 > 3R+W=4>3, guaranteeing at least one replica in every read quorum holds the latest acknowledged write.

The Tombstone Trap: In LSM-tree stores, DELETE or overwriting columns with null does not erase bytes immediately—it writes a tombstone marker so offline replicas learn of the deletion during anti-entropy repair instead of resurrecting deleted data (zombie reads). If a queue-like table deletes 500,000 rows in a partition, subsequent SELECT scans must read through 500,000 tombstones in memory before finding live rows—triggering TombstoneOverwhelmingException.

STAGE 04 · INVARIANT & PRODUCTION GUARDRAILScore

Quorum Overlap Verifier & Tombstone-Safe Write Builder in Python.

Why this matters: Enforce quorum invariants and strip null-column tombstones on partial updates in Python.

A subtle production bug in Cassandra/DynamoDB drivers is binding null for unset optional fields during an INSERT or UPDATE—every null writes an explicit tombstone to disk even when the column was never populated.

def validate_quorum_config(replication_factor: int, read_quorum: int, write_quorum: int) -> bool:
    if replication_factor < 1 or read_quorum < 1 or write_quorum < 1:
        raise ValueError("Quorum parameters must be positive integers")
    if read_quorum > replication_factor or write_quorum > replication_factor:
        raise ValueError("R and W cannot exceed replication factor N")
    return (read_quorum + write_quorum) > replication_factor

def build_tombstone_free_upsert(partition_key: str, clustering_key: str, attributes: dict) -> dict:
    if not partition_key or not clustering_key:
        raise ValueError("Partition and clustering keys are mandatory")
    # Strip None values so unset optional fields do not generate LSM tombstones
    clean_attrs = {k: v for k, v in attributes.items() if v is not None}
    return {
        "partition_key": partition_key,
        "clustering_key": clustering_key,
        "columns": clean_attrs,
    }

Why Tombstones Must Survive Until Merkle-Tree Repair Completes

Engineering Decision Framework
Problem
How to store 90 days of clickstream events (80,000 writes/sec) with automatic expiration and zero tombstone read degradation.
Naive Solution
Use a single user_id partition key with Leveled Compaction (LCS) and run nightly DELETE FROM events WHERE ts < cutoff jobs.
Why It Fails
Explicit DELETE jobs flood partitions with millions of tombstones, causing read timeouts and heavy compaction I/O.
Alternatives
Compare explicit DELETE jobs with LCS, single-key TTLs with STCS, and time-bucketed partitions (user_id, YYYY-MM-DD) with TWCS + row TTL.
Engineering Decision
Partition by (user_id, YYYY-MM-DD) with Time-Window Compaction Strategy (TWCS) and a 90-day TTL so entire expired daily SSTable files drop cleanly from disk without scanning tombstones.
Trade-Offs
Eliminates tombstone compaction overhead completely while requiring multi-day queries to issue parallel per-day partition reads.

STAGE 05 · PRODUCTION BOUNDARIES & WHEN NOT TO USE NOSQLdeepDive

Secondary Index Traps, Cross-Partition Transactions & When SQL Wins.

Why this matters: Identify anti-patterns where NoSQL engines underperform relational or distributed SQL databases.

Global Secondary Index Scatter-Gather Trap: Querying a low-cardinality secondary index (e.g., WHERE country = 'IN') in a 30-node Cassandra cluster forces the coordinator to scatter-gather across all 30 nodes—destroying p99 latency.

When NOT to Use NoSQL:

  • Complex Ad-Hoc Filtering & Multi-Entity Joins: Financial ledgers, ERP systems, and CRM apps with dynamic filters belong in PostgreSQL/MySQL.
  • Cross-Partition ACID Invariants: Double-entry accounting or multi-item inventory checkout across independent partition keys requires relational or Distributed SQL (CockroachDB/Spanner) transactions.
  • Modest Scale (< 3,000 write TPS, < 1 TB): A single replicated PostgreSQL primary is far simpler to operate and query.

The decision framework

01

How do you guarantee strict quorum overlap on reads and writes with replication factor N?

Configure `R + W > N` (e.g., `N=3, W=2, R=2`) so read and write replica quorums always intersect on at least one up-to-date node.

02

How do you prevent unbounded partition growth and tombstone storms on time-ordered event tables?

Compound the partition key with a time bucket (`(entity_id, YYYY-MM-DD)`) and use Time-Window Compaction (TWCS) with TTLs instead of manual `DELETE` jobs.

The idea to keep with you

NoSQL Databases & Distributed Storage Engines

High-scale NoSQL systems deliver predictable single-digit millisecond latency when schemas follow exact query access patterns: keep physical partitions bounded with time buckets, match LSM compaction (LCS vs. TWCS) to mutation/TTL patterns, eliminate accidental tombstones, and configure R + W > N quorums according to consistency needs.
