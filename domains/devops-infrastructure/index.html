Layer 4/7 Load Balancing & Edge Proxies.

Edge load balancers sit at the boundary between external clients and backend fleets. Layer 4 balancers forward TCP/UDP packets using 5-tuple hashing or Direct Server Return (DSR) at line rate without inspecting payloads, whereas Layer 7 reverse proxies terminate TLS and TCP, inspect HTTP/gRPC headers, enforce rate limits, and multiplex requests over persistent backend connections.

ChoiceWhat it buysWhat it costs
Layer 4 (TCP/UDP) Load BalancerUltra-low latency and high PPS throughput using kernel/XDP packet forwarding. Protocol-agnostic for non-HTTP workloads (databases, Kafka, MQTT).Cannot route by URL path, host header, or gRPC method. Long-lived HTTP/2 or gRPC TCP connections pin traffic to one backend pod.
Layer 7 (HTTP/gRPC) Edge ProxyPer-request load balancing across multiplexed HTTP/2 streams. Centralizes TLS termination, JWT validation, canary header routing, and retries.Higher CPU/memory cost for TLS termination and payload parsing. Misconfigured timeouts or retries can amplify downstream load.

Maglev consistent hashing survives backend churn

Maglev builds a compact lookup table using permutation hashing so adding or removing a backend node disrupts only ~1/N flows without requiring shared connection state across L4 load balancer replicas.

Graceful draining requires preStop delays

Removing a pod from a load balancer's endpoint list happens asynchronously. A pod must fail readiness, wait for endpoint propagation (preStop sleep), and finish in-flight HTTP/2 streams before closing its listening socket.

Order platform / Fixing uneven gRPC load distribution behind an L4 NLB

Fixing uneven gRPC load distribution behind an L4 NLB.

A gRPC payment service scaled from 4 to 16 pods during a traffic spike, yet CPU stayed pinned at 95% on the original 4 pods while the 12 new pods sat idle.

Because gRPC multiplexes thousands of RPCs over a single persistent HTTP/2 TCP connection, the L4 Network Load Balancer kept all streams pinned to the initial 4 pods. Switching internal East-West routing to an L7 Envoy proxy balanced individual gRPC frames across all 16 pods and added connection-draining GOAWAY frames on scale-down.

Lesson: L4 balances TCP connections, not L7 requests; HTTP/2 and gRPC require L7-aware balancing or client-side load balancing.
Pause & reason: where would you draw the boundary?▼
  • Are clients holding long-lived HTTP/2 or WebSocket connections that bypass L4 connection-level balancing?
  • If one L4 load balancer instance reboots, do Maglev or ECMP tables preserve active TCP flows?
  • How many seconds elapse between SIGTERM on a backend pod and the edge proxy stopping new request dispatch?
  • Which HTTP status codes or timeouts are safe for the edge proxy to retry automatically?

Linux Containers, Namespaces & Cgroups.

A Linux container is not a lightweight VM; it is a normal host process constrained by kernel primitives. Namespaces restrict what a process can see (PIDs, network stack, mount points, IPC, hostname, UID/GID mapping), while cgroups v2 restrict what physical resources it can consume (CPU CFS bandwidth quotas, hard memory.max limits, and blkio). OverlayFS stacks read-only image layers beneath a writable container layer via copy-on-write.

CPU limits throttle; memory limits OOM-kill

Exceeding a cgroup CPU quota causes the Completely Fair Scheduler (CFS) to pause the container until the next 100ms period (tail-latency spikes). Exceeding memory.max triggers the kernel OOM killer (SIGKILL, exit code 137).

cgroups v2 unifies hierarchy and adds PSI

cgroups v2 replaces fragmented v1 hierarchies with a single unified tree, adds Pressure Stall Information (PSI) metrics to detect memory/IO contention early, and enables safe rootless delegation.

PID 1 signal handling and zombie reaping

Inside its PID namespace, a container's entrypoint runs as PID 1, which ignores default SIGTERM handlers unless explicitly registered—causing 30-second forced SIGKILL delays during rollouts.

Order platform / Diagnosing periodic 90ms p99 latency spikes in a Go microservice

Diagnosing periodic 90ms p99 latency spikes in a Go microservice.

A Go service running in a 4-CPU Kubernetes pod averaged 15% CPU utilization yet suffered sharp 90ms latency stalls every second.

The container had a strict `cpu: 500m` limit (50ms quota per 100ms CFS period). Bursty Go GC background threads burned the entire 50ms quota in the first 12ms of the period, forcing all goroutines to be CFS-throttled for the remaining 88ms. Removing artificial CPU limits while keeping CPU requests eliminated the throttling spikes.

Lesson: Container CPU limits enforce hard CFS time-slice ceilings that cause burst throttling even when host CPUs are idle.
  • Language runtimes (JVM, Go, Python) that read `/proc/meminfo` or `nproc` instead of cgroup files will mis-size heap and thread pools.
  • Writing large temporary logs to the container's OverlayFS upperdir can exhaust host `/var/lib/containerd` disk space.
Pause & reason: where would you draw the boundary?▼
  • Does the application runtime inspect cgroup v2 `/sys/fs/cgroup` limits or host `/proc` totals when sizing heaps and thread pools?
  • Is container exit code 137 caused by a Pod memory limit OOM or a node-wide kernel OOM killer?
  • Are containers running as non-root UIDs with user namespace mapping and read-only root filesystems?
  • How does PID 1 in the container forward SIGTERM and reap orphaned child processes?

Kubernetes Core Architecture & Pod Scheduling.

Kubernetes is a level-triggered declarative state machine. Clients write manifests to kube-apiserver, which validates, mutates/admits, and persists objects into etcd (backed by Raft consensus). Controllers watch etcd via informer caches and emit edge-triggered workqueues to converge actual state toward desired state. The kube-scheduler binds unscheduled pods in two phases: filtering (predicates like CPU/RAM, taints/tolerations, node affinity) and scoring (soft preferences like topology spread).

kube-apiserver & AdmissionAuthenticates requests, runs mutating/validating webhooks, and persists versioned state to etcd.
→
etcd (Raft Consensus)Provides linearizable key-value storage and watch streams across an odd-numbered quorum (3 or 5 nodes).
→
kube-schedulerFilters feasible nodes, scores candidates for bin-packing or HA spread, and writes the Pod's nodeName.
→
kubelet & CRI/CNIWatches assigned Pods on its node, pulls images via CRI, configures networking via CNI, and runs probes.

Separate liveness from readiness probes

A liveness probe should only check whether the process itself is deadlocked; if it checks downstream database reachability, a brief DB hiccup causes Kubernetes to restart healthy pods in a cascading death spiral.

PodDisruptionBudgets (PDB) protect voluntary drains

PDBs ensure node upgrades or cluster autoscaler scale-downs never evict more than maxUnavailable replicas simultaneously.

Order platform / Preventing a cascading pod restart storm during a Redis blip

Preventing a cascading pod restart storm during a Redis blip.

When a Redis cluster failed over for 8 seconds, 120 API pods failed their `/healthz` liveness probes—which pinged Redis—and kubelet restarted all 120 pods simultaneously, turning an 8-second blip into a 12-minute cold-start outage.

Split `/livez` (returns 200 OK if the HTTP event loop is responsive) from `/readyz` (returns 503 if Redis is unreachable, removing the pod from Service endpoints without restarting the container), and added a `PodDisruptionBudget` with `minAvailable: 80%`.

Lesson: Liveness probes restart broken processes; readiness probes remove pods from traffic without killing them.
Pause & reason: where would you draw the boundary?▼
  • If etcd loses 2 out of 3 nodes, what happens to running pods vs new deployments and HPA scaling?
  • Does your liveness probe depend on any external database, cache, or downstream API?
  • Are Pod topologySpreadConstraints configured across availability zones so a single AZ outage cannot take down all replicas?
  • What happens to in-flight requests if `terminationGracePeriodSeconds` expires before the app finishes draining?

Kubernetes Networking, Services & Ingress.

The Kubernetes network model requires every Pod to have a unique routable IP without NAT between Pods. CNI plugins achieve this either via encapsulated overlays (VXLAN/Geneve) or native BGP/eBPF host routing. Because Pods are ephemeral, a Kubernetes Service assigns a stable virtual ClusterIP and DNS name; kube-proxy (or Cilium eBPF) programs kernel iptables, IPVS, or bpf maps to DNAT traffic to healthy EndpointSlice targets.

ChoiceWhat it buysWhat it costs
Overlay Networking (VXLAN / Geneve)Works across any L2/L3 cloud VPC without requiring BGP peering. Decouples Pod CIDR space from underlying host subnet limits.Encapsulation header overhead reduces effective MTU (e.g., 1450 bytes). Extra CPU cost for packet encapsulation/decapsulation.
Direct Routing / eBPF (BGP / Cilium)Native wire-speed forwarding with no encapsulation overhead. eBPF replaces O(N) iptables chains with O(1) hash map lookups.Requires VPC/ToR router BGP integration or flat routable Pod CIDRs. Depends on modern Linux kernel versions (5.10+) for full eBPF features.

iptables scales O(N) with Services; IPVS/eBPF scales O(1)

In clusters with thousands of Services, sequential iptables rule traversal adds measurable packet latency and slow kube-proxy syncs. IPVS or Cilium eBPF uses hash tables for constant-time lookups.

Avoid double-hop SNAT on NodePort/LoadBalancer

Setting externalTrafficPolicy: Local routes external traffic only to pods on the receiving node, preserving client source IP and eliminating cross-node hops.

Order platform / Eliminating CoreDNS conntrack drops and iptables latency at 5,000 services

Eliminating CoreDNS conntrack drops and iptables latency at 5,000 services.

A multi-tenant cluster hosting 5,000 Kubernetes Services experienced intermittent 5-second DNS timeouts and rising p99 East-West latency.

Sequential iptables chains had grown to 40,000+ rules per node, and UDP DNS queries were racing in the Linux `nf_conntrack` table during simultaneous A/AAAA lookups. Migrating `kube-proxy` to Cilium eBPF socket-level load balancing and deploying `NodeLocal DNSCache` over TCP eliminated both conntrack races and O(N) rule traversal.

Lesson: At high Service counts, replacing sequential iptables with IPVS/eBPF and caching DNS locally removes hidden kernel bottlenecks.
Pause & reason: where would you draw the boundary?▼
  • How many iptables rules does kube-proxy maintain per node at your peak Service count?
  • Is CoreDNS UDP conntrack racing causing intermittent 5-second `ndots:5` lookup delays?
  • Are NetworkPolicies defaulting to deny-all ingress/egress between namespaces?
  • Does your Ingress or Gateway API controller preserve client source IP and enforce per-route timeouts?

Service Mesh Architecture & mTLS.

A service mesh splits East-West networking into a control plane (e.g., Istio istiod) and a data plane (e.g., Envoy sidecars). The control plane issues short-lived SPIFFE X.509 workload identities (spiffe://cluster.local/ns/...) and pushes routing/circuit-breaking config via Envoy's xDS gRPC API. Traffic enters and leaves the pod through transparent interception (iptables REDIRECT or eBPF sockops), enforcing zero-trust mTLS, retries, and distributed tracing without language-specific SDKs.

Envoy threading model avoids cross-core locks

Envoy uses a single listener thread and N worker threads (typically one per vCPU), each running its own non-blocking libevent loop and thread-local connection pool.

Prevent retry amplification across mesh hops

If Service A -> B -> C each configure 3 automatic retries at the sidecar layer, a failure in C triggers 3 x 3 = 9x traffic amplification. Enforce per-request x-envoy-max-retries and retry budgets.

Order platform / Enforcing zero-trust mTLS and 5% canary traffic splitting across polyglot services

Enforcing zero-trust mTLS and 5% canary traffic splitting across polyglot services.

A fintech platform running Go, Java, and Python services needed strict PCI-DSS encrypted East-West traffic and header-based canary routing without maintaining three separate TLS rotation libraries.

Deployed Istio with Envoy sidecars in `STRICT` mTLS mode, rotating 24-hour SPIFFE certificates automatically via SDS, and used `VirtualService` weights to shift 5% of internal checkout traffic to v2 while capping sidecar retries with a 20% retry budget.

Lesson: A service mesh standardizes cryptographic identity and L7 traffic policy across polyglot services, provided sidecar latency and retry budgets are explicitly bounded.
  • Sidecar proxies add ~1-3ms per hop and consume significant RAM/CPU at high pod counts; ambient/eBPF modes reduce per-pod overhead.
  • Mesh proxies only see L7 status codes (HTTP 503/gRPC UNAVAILABLE), not business-level partial failures inside a 200 OK payload.
Pause & reason: where would you draw the boundary?▼
  • What is the measured p99 latency and memory overhead per pod of running an Envoy sidecar?
  • Are SPIFFE workload identities short-lived and automatically rotated without restarting pods?
  • Could stacked sidecar retries across a 4-hop call chain cause a retry storm during a partial outage?
  • How does the application wait for the sidecar proxy to start before accepting traffic, and exit cleanly on shutdown?

Infrastructure as Code (IaC) & Immutable Systems.

Imperative setup scripts fail halfway and drift whenever someone SSHs in to hot-fix a config. Declarative IaC (Terraform/OpenTofu) compiles resource declarations into a Directed Acyclic Graph (DAG), compares desired config against a remote state file protected by distributed locks (e.g., S3 + DynamoDB or GCS object locks), and computes an explicit plan diff before applying changes. Immutable infrastructure pairs IaC with Packer/OCI images so servers are replaced rather than patched in place.

Remote state locking prevents concurrent corruption

Two engineers running terraform apply simultaneously without a state lock will create orphaned cloud resources and corrupt state. Always use remote backends with atomic locking and state encryption.

Blast-radius isolation via small state files

Putting VPCs, EKS clusters, and RDS databases in one giant state file makes every plan slow and every apply high-risk. Split state by lifecycle and ownership boundary.

Lifecycle rules protect stateful resources

Use prevent_destroy = true and create_before_destroy = true on production databases, KMS keys, and load balancers so an accidental rename cannot wipe data.

Order platform / Recovering from drift and preventing an accidental production RDS replacement

Recovering from drift and preventing an accidental production RDS replacement.

An engineer manually modified a security group in the AWS console, and a subsequent Terraform PR refactored a database subnet group—which silently planned a destroy-and-recreate of the production PostgreSQL RDS instance.

Automated `terraform plan` in CI flagged the destructive `-/+` diff on the RDS resource and blocked merge. The team imported the out-of-band security group rule, added `lifecycle { prevent_destroy = true }` to stateful modules, and split networking from database state files.

Lesson: Never run `apply` without reviewing a CI-generated `plan`, and isolate stateful resources behind smaller state boundaries and `prevent_destroy` guards.
Pause & reason: where would you draw the boundary?▼
  • Where is your Terraform state stored, who has read access to secrets inside it, and how is concurrent locking enforced?
  • If an engineer makes an emergency console change, how quickly does drift detection surface it?
  • What is the blast radius of a single `terraform apply`—one service or an entire production region?
  • Are VM/container artifacts baked immutably with Packer/Docker or mutated in place via SSH?

CI/CD Verification Pipelines & Supply Chain Security.

A CI/CD pipeline is a Directed Acyclic Graph of quality gates: static analysis, unit/integration tests, container builds, vulnerability scanning, and progressive delivery. To prevent 'works on my runner' bugs and SolarWinds-style compromises, builds must be hermetic (pinned base digests, lockfiles, no ambient secrets), produce a Software Bill of Materials (SBOM), and sign artifacts with Cosign/Sigstore so admission controllers verify SLSA provenance before any pod starts.

Pin images by SHA-256 digest, not mutable tags

Tags like :latest or :1.20 can be overwritten upstream. Pinning base images and deployment manifests by immutable sha256: digest guarantees bit-for-bit reproducibility.

Cosign + Admission Policy closes the deploy loop

Signing images in CI is useless unless Kubernetes admission controllers (Kyverno/OPA Gatekeeper) reject unsigned or high-CVE images at deploy time.

Content-addressable build caching accelerates CI safely

Use BuildKit layer caches and Bazel/Turborepo remote caches keyed by input hashes to keep PR feedback under 10 minutes without leaking state across branches.

Order platform / Stopping a compromised dependency and cutting build times from 28m to 6m

Stopping a compromised dependency and cutting build times from 28m to 6m.

A monorepo CI pipeline took 28 minutes per PR, pulled unpinned npm packages without lockfile enforcement, and deployed containers tagged `:main` directly to EKS.

Enabled `npm ci` with strict lockfile checks, BuildKit registry layer caching, and parallel test sharding (cutting CI to 6 minutes). Added Syft SBOM generation, Trivy CVE gates, Cosign keyless OIDC signing, and a Kyverno policy requiring valid signatures and SHA-256 digests in production.

Lesson: Fast, hermetic CI with cryptographic provenance turns security and reproducibility into automated gates rather than manual release checklists.
  • Never pass long-lived cloud IAM keys into CI runners; use short-lived OIDC workload identity federation.
  • Cache poisoning can occur if PR branches from forks can write to the shared main-branch build cache.
Pause & reason: where would you draw the boundary?▼
  • Can you reproduce the exact binary running in production from a git commit SHA and pinned dependency lockfile?
  • Does your cluster admission controller block unsigned images or `:latest` tags from scheduling?
  • Are CI runners authenticating to cloud registries via short-lived OIDC tokens rather than static secrets?
  • How quickly can you identify every running container affected by a newly disclosed CVE using stored SBOMs?

The decision framework

01

What level of orchestration and networking complexity does team size justify?

Adopt Kubernetes, eBPF, and service meshes only when polyglot scale, multi-tenancy, or compliance outweighs managed PaaS simplicity.

02

How are compute, memory, and network boundaries enforced at the kernel level?

Set explicit cgroups v2 memory limits, avoid unnecessary CPU throttling, and enforce deny-by-default NetworkPolicies.

03

How is state drift prevented between git and running cloud infrastructure?

Use remote-locked IaC state, immutable artifacts, and GitOps controllers rather than manual SSH or console edits.

04

What is the maximum blast radius of a bad deployment or dependency outage?

Bound rollouts with canary stages, PodDisruptionBudgets, separate liveness/readiness probes, and capped mesh retry budgets.

05

How are artifacts verified from commit to running pod?

Require hermetic builds, SBOM generation, SHA-256 digest pinning, and admission-time signature verification.

What to take away

Good architecture is a set of justified decisions.

Reliable cloud infrastructure is engineered from the kernel up: bound resources with cgroups v2, route efficiently at L7/eBPF, reconcile immutable state via GitOps, verify every artifact cryptographically, and gate releases with automated SLO rollbacks.
