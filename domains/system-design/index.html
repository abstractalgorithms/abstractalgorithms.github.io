System Design / Stage 01L4 · FUNDAMENTALS

Foundations.

Every sound system design begins by bounding the problem before drawing boxes. Clarify functional scope (the exact 3–4 core user journeys), non-functional SLOs (availability targets like 99.95%, p99 latency budgets, durability vs. eventual consistency), and traffic shape (read/write ratio, payload size, bursty peak-to-average multiplier).

Back-of-the-envelope capacity math converts product numbers into hardware constraints in 60 seconds: DAU * actions / 86,400 gives average QPS, multiplied by 3–10x for diurnal/flash peaks. Multiply write QPS by payload size and retention to size storage and IOPS; multiply QPS by response size to check NIC/egress bandwidth. Knowing hardware latency numbers (L1 ~1ns, RAM ~100ns, NVMe ~10us, intra-AZ ~0.5ms, cross-region ~80ms) tells you immediately whether a single node suffices or horizontal sharding is mandatory.

Under Little's Law (L = lambda * W), in-flight concurrency equals arrival rate times service time; capacity planning must budget for p99 slowdowns, not just average latency.

Always derive storage, bandwidth, and concurrency ceilings from concrete numbers before choosing databases or queues.

Quantify Peak QPS, Storage & Bandwidth Before Picking Tech

10,000 QPS of 1KB writes is ~10MB/s (~860GB/day), easily handled by one well-indexed NVMe primary; 500,000 QPS of 10KB payloads saturates a single 10Gbps NIC.

Latency Budgets Dictate Network Hops

If your API SLO is 100ms p99, you cannot make 5 sequential cross-region RPCs or synchronous fan-outs without caching or async decoupling.

Little's Law Links Latency Spikes to Thread Exhaustion

If arrival rate is 1,000 req/s and latency jumps from 10ms to 1,000ms, active in-flight requests jump from 10 to 1,000—exhausting pools unless bounded.

Order platform / Right-Sizing a URL Shortener Without Over-Engineering

Right-Sizing a URL Shortener Without Over-Engineering.

Requirements call for 100M new URLs/month (~40 writes/sec avg, 200 peak) and a 100:1 read/write ratio (4,000 reads/sec avg, 20k peak).

Capacity math shows 5 years of URLs at 500 bytes/row is only ~3TB—fitting on a single sharded/replicated PostgreSQL cluster + Redis cache rather than requiring a complex multi-datacenter NoSQL ring.

Lesson: Back-of-the-envelope math prevents premature distributed complexity when a simpler architecture easily clears 10x peak.

System Design / Stage 02L4 · FUNDAMENTALS

APIs, Services and Protocols.

Service interfaces are long-lived contracts. Public-facing APIs favor HTTP/REST + JSON (ubiquitous tooling, CDN/HTTP caching, human debuggability) or GraphQL (when diverse mobile/web clients need flexible field selection, paired with DataLoader batching to prevent N+1 queries and persisted queries to block abusive deep nesting). Internal east-west microservice calls favor gRPC over HTTP/2: binary Protobuf framing cuts payload size 3–5x, multiplexes concurrent streams over a single TCP connection, and enforces strict schema evolution rules (never reuse field numbers).

Because HTTP/2 multiplexes many RPCs onto one persistent TCP connection, naive L4 load balancers pin all traffic to a single backend pod; gRPC requires L7 load balancing (Envoy/Linkerd or client-side xDS) to distribute per-RPC.

Every API boundary must also defend against overload and duplicates: enforce cursor-based pagination (keyset WHERE id > last_id instead of OFFSET), idempotency keys on mutations, token-bucket rate limiting, and deadline propagation so downstream drops expired work.

Propagate Remaining Deadline Budgets

Decrement elapsed time at every hop (grpc-timeout) so a request that already timed out at the gateway never executes expensive DB queries downstream.

System Design / Stage 03L5 · APPLIED DESIGN

Data Modeling and SQL.

Relational databases (PostgreSQL, MySQL/InnoDB) remain the default workhorse for transactional systems because they enforce schemas, foreign keys, and ACID transactions via Write-Ahead Logging (WAL) and Multi-Version Concurrency Control (MVCC). Under MVCC, readers never block writers and writers never block readers: each transaction sees a consistent snapshot by checking row version timestamps (xmin/xmax in Postgres or undo logs in InnoDB), while durability is guaranteed by sequential fsync to the WAL before acknowledging COMMIT.

Understanding Isolation Levels prevents subtle financial bugs: Read Committed allows non-repeatable reads; Repeatable Read prevents non-repeatable reads (and in Postgres Snapshot Isolation prevents phantoms, though write-skew remains possible); Serializable (SSI) prevents all anomalies including write-skew. Under high contention, choose between pessimistic SELECT ... FOR UPDATE row locks and optimistic version-column CAS (WHERE version = v).

Query performance relies on B-Tree composite indexes following the equality-before-range leftmost-prefix rule, avoiding implicit type coercion or functions on indexed columns, and managing MVCC dead-tuple bloat (VACUUM in Postgres).

Relational Engine Internals

MVCC Snapshot Visibility & Write-Ahead Log Durability

1.Non-Blocking Reads: Readers inspect snapshot versions without blocking concurrent writers.

2.Sequential WAL: Appends redo records sequentially on COMMIT before dirty pages flush.

3.Composite Indexes: B-Tree (equality, range) keeps point and range lookups O(log N).

4.Vacuum / Undo: Reclaims obsolete MVCC row versions to prevent table bloat.

Caption: MVCC Snapshot Visibility & Write-Ahead Log Durability (Client Transaction -> MVCC Snapshot Engine -> WAL (Sequential fsync) -> B-Tree & Heap Pages).

MVCC Separates Readers from Writers

Snapshot reads inspect row visibility metadata without acquiring shared read locks, eliminating read-write contention on analytical queries.

Composite Index Column Order: Equality First, Range Last

An index on (tenant_id, status, created_at) serves WHERE tenant_id = ? AND status = ? AND created_at > ? in a single B-Tree range scan; flipping the order ruins selectivity.

Write-Skew Anomaly Under Snapshot Isolation

Two concurrent transactions reading overlapping rows and updating disjoint rows pass Repeatable Read yet violate cross-row invariants; use SELECT ... FOR UPDATE or SERIALIZABLE.

Online DDL & Connection Pooling (PgBouncer)

Never run ALTER TABLE locks or open 5,000 direct app connections to Postgres; use expand-contract DDL and transaction-mode pooling.

Order platform / Preventing Double-Booking Write Skew in an On-Call / Room Scheduler

Preventing Double-Booking Write Skew in an On-Call / Room Scheduler.

Under Postgres REPEATABLE READ, two doctors simultaneously clicked 'leave on-call shift' when 2 doctors were on duty, leaving 0 doctors on call.

Each transaction read count >= 2 from its MVCC snapshot and updated its own distinct doctor row—causing Snapshot Isolation write-skew. Switching to SERIALIZABLE (with retry on 40001) or locking the parent shift row with SELECT ... FOR UPDATE enforced the invariant.

Lesson: Snapshot Isolation prevents dirty and non-repeatable reads, NOT disjoint-row write-skew.
  • Adding a standard B-Tree index without CONCURRENTLY locks table writes in production.
  • Every additional secondary index accelerates reads at the cost of extra B-Tree page writes and VACUUM/undo overhead.

System Design / Stage 04L5 · APPLIED DESIGN

NoSQL, Partitioning and IDs.

When write throughput, dataset size, or global multi-region latency outgrows a single primary, data must be horizontally partitioned (sharded) across independent nodes. Choose the NoSQL model to match access patterns: Key-Value (Redis/DynamoDB) for O(1) point lookups, Wide-Column (Cassandra/Bigtable) for high-volume time-series/partition-plus-sort-key scans, and Document (MongoDB) for self-contained hierarchical aggregates.

Partitioning strategy determines whether a cluster scales linearly or melts down on a single hot shard: Range partitioning supports fast range scans but creates hot-shard bottlenecks on monotonic keys (timestamp, auto_increment). Hash partitioning (with Consistent Hashing + Virtual Nodes) spreads writes evenly across nodes and bounds resharding data movement to 1/N when nodes join or leave—but requires scatter-gather for secondary queries unless inverted indexes or write-sharded suffixes (key#0..9) are used.

In sharded systems without a central auto-increment sequence, 64-bit Snowflake IDs (41-bit timestamp | 10-bit worker ID | 12-bit sequence) or UUIDv7 generate k-sortable, globally unique IDs locally with zero cross-node coordination.

Assigning 150-256 vnodes per physical shard prevents skew and ensures adding a node only migrates 1/N keys from existing shards.

Avoid Monotonic Partition Keys in Hash/Range Shards

Sharding by created_at or celebrity_id sends 100% of writes to one shard; salt hot keys (key#0..15) or compound (tenant_id, bucket).

Snowflake / UUIDv7 Preserve B-Tree Locality

Random UUIDv4 keys cause constant B-Tree page splits and cache misses; time-ordered 64-bit Snowflake or UUIDv7 IDs append sequentially.

Design Partition Keys Around Top Queries

In DynamoDB or Cassandra, cross-partition scatter-gather destroys tail latency; co-locate related items under one partition key.

Lesson: A single high-traffic partition key cannot exceed one physical shard's IOPS ceiling—split hot keys with bounded random suffixes.

System Design / Stage 05L6 · SCALE & TRADE-OFFS

Caching and Fast Reads.

Caching exploits Zipfian access skew—where 20% of keys serve 80%+ of reads—to cut latency from tens of milliseconds to sub-millisecond RAM or edge CDN hits. Production systems layer Edge/CDN caches (HTTP Cache-Control, ETag, stale-while-revalidate), L1 in-process caches (zero network hop, tiny bounded LRU/W-TinyLFU), and L2 distributed caches (Redis/Memcached).

Most read-heavy services use Cache-Aside (Lazy Loading): check cache -> on miss, query DB -> populate cache with TTL. Write-through keeps cache warm on writes, while Write-Back (Write-Behind) batches async DB flushes for extreme write throughput at the risk of data loss on node crash.

At scale, three cache failure modes can still take down the backing database: Cache Stampede / Thundering Herd (thousands of concurrent misses on an expired hot key—solved with singleflight request coalescing and probabilistic early refresh); Cache Penetration (queries for non-existent keys bypassing cache—solved with Bloom filters or short-TTL negative caching); and Cache Avalanche (synchronized TTL expirations—solved by adding random TTL jitter).

Multi-Tier Read Path

L1 In-Process + L2 Redis + Singleflight Protection

1.L1 Micro-Cache: Absorbs hot-key bursts locally with short 1-5s TTLs.

2.L2 Shared Cache: Jittered TTLs prevent synchronized avalanche expirations.

3.Singleflight: Ensures only one miss per pod queries the DB on key expiry.

4.Bloom / Negative: Blocks nonexistent-key penetration before hitting disk.

Caption: L1 In-Process + L2 Redis + Singleflight Protection (L1 In-Process -> L2 Redis Cluster -> Singleflight -> Primary DB + Bloom).

Singleflight Coalescing Stops Hot-Key Stampedes

Deduplicate concurrent cache misses for the same key within each app instance (or via distributed lease) so only 1 DB query runs instead of 5,000.

Bloom Filters & Negative Caching Block Penetration

Cache NOT_FOUND tombstones for 30-60s or front-load a compact Bloom filter so bot scans for nonexistent IDs never touch Postgres.

Add Random Jitter to Every TTL

Warming 100k keys with an identical TTL=3600s creates synchronized expiration avalanches; use base_ttl + rand(0, 300).

Avoid Dual-Write Cache Races

Concurrent read-miss + write updates can leave stale values in Redis until TTL expires; use short TTLs, versioned keys, or CDC-driven invalidation.

Order platform / Surviving a Viral Hot-Key Expiration Without Melting Postgres

Surviving a Viral Hot-Key Expiration Without Melting Postgres.

When a trending product's 5-minute Redis TTL expired during a flash sale, 12,000 concurrent requests hit the database simultaneously, spiking DB CPU to 100%.

Adding in-process singleflight coalescing, L1 micro-caching (2s TTL), and logical soft-TTL early background refresh reduced DB queries on expiration from 12,000 to 1 per app pod.

Lesson: Never let thousands of concurrent requests independently recompute an expired hot cache key.
  • In-process L1 caches are faster than Redis but create per-pod staleness; keep L1 TTLs very short (seconds) or invalidate via pub/sub.
  • Always size your database for at least partial cache-miss bursts so a cold Redis restart does not trigger a permanent outage.

System Design / Stage 06L6 · SCALE & TRADE-OFFS

Distributed Coordination.

Under the CAP & PACELC theorems, network partitions are inevitable—so during a partition (P), a system must choose between strict linearizable Consistency (C) and Availability (A); even during normal operation (E), it trades Latency (L) against Consistency (C). Multi-region systems minimize cross-region round-trips by classifying which invariants truly need CP linearizability (inventory deduction, leader election) vs. AP/CRDT eventual convergence (likes, shopping carts).

Consensus protocols (Raft, Paxos) guarantee a single leader per term via majority quorums (floor(N/2) + 1): a 3-node cluster tolerates 1 failure; a 5-node cluster tolerates 2. Similarly, Dynamo-style quorum systems satisfy R + W > N so reads overlap with the latest write quorum (though without consensus ordering, concurrent writes still require LWW or version vectors).

The deadliest coordination bug is trusting distributed lock TTLs alone: if Lock Holder A experiences a 15-second GC pause after its lease expires, Lock Holder B acquires the lock, and A wakes up and overwrites B's data. Correctness requires monotonic fencing tokens verified by the storage layer (WHERE fencing_token > last_seen_token).

Consensus & Fencing Safety

Raft Majority Quorum & Storage-Enforced Fencing Tokens

1.Majority Quorum: Writes commit only after floor(N/2)+1 replicas persist to WAL.

2.Monotonic Token: Every lock acquisition increments the fencing token strictly.

3.Storage Guard: DB rejects late writes from GC-paused old leaders.

Caption: Raft Majority Quorum & Storage-Enforced Fencing Tokens (Raft Lock / Leader -> Follower Quorum -> Fenced Storage).

Majority Quorums & Odd Cluster Sizes

Use 3 or 5 Raft nodes (never 2 or 4—4 nodes tolerate the same 1 failure as 3 nodes while increasing quorum size to 3).

Leases Alone Are Unsafe Without Fencing Tokens

Process pauses (GC, VM live migration) outlive lock TTLs; attach a monotonically increasing fencing token checked by the target database or storage.

PACELC Captures Normal-Case Latency vs. Consistency

Even when the network is healthy, synchronous cross-region replication adds ~80-150ms RTT to every write; async replication drops latency at the cost of RPO > 0.

Logical Clocks (Lamport / HLC) Over Wall Clocks

NTP clocks skew and jump backward; use Lamport/Hybrid Logical Clocks or TrueTime uncertainty bounds for causal ordering.

Order platform / Stopping Split-Brain File Overwrites with Monotonic Fencing Tokens

Stopping Split-Brain File Overwrites with Monotonic Fencing Tokens.

Two worker nodes occasionally overwrote each other's S3/DB ledger updates despite acquiring an etcd/Redis distributed lock.

GC pauses caused worker 1's lock to expire while it was mid-flight. Passing etcd's monotonic mod_revision as a fencing token and having the DB reject writes with token <= current_token made stale writes impossible.

Lesson: A distributed lock without storage-enforced fencing tokens is only an advisory optimization, not a safety guarantee.
  • Quorum intersection (R + W > N) alone does not guarantee linearizability without read-repair or leader coordination.
  • Never use NTP wall-clock timestamps for last-write-wins (LWW) conflict resolution on critical financial or inventory state.

System Design / Stage 07L7 · STAFF / PRINCIPAL

Storage Engines.

Storage engine choice boils down to the RUM Conjecture: balancing Read Amplification, Write (Update) Amplification, and Space (Memory) Amplification on physical SSDs and cloud object stores. B-Trees (PostgreSQL, InnoDB) organize data into fixed 4–16KB sorted pages updated in-place. Because every point lookup traverses 3–4 tree levels (with upper levels pinned in RAM), B-Trees deliver predictable, low read amplification and fast range scans—but random updates rewrite entire 16KB pages (high write amplification) and require page-split latches.

LSM-Trees (RocksDB, Cassandra, Pebble) optimize for sequential write throughput: incoming writes append to a sequential WAL and an in-memory MemTable, then flush immutably as sorted SSTables (L0 -> L1 -> ...). Because writes never overwrite existing disk pages, write amplification on ingestion is minimal—but reads may have to check multiple SSTable levels unless accelerated by Bloom filters and fence pointers, and background compaction (leveled vs. size-tiered) consumes disk I/O and CPU to purge tombstones.

Modern cloud-native warehouses and lakehouses (Snowflake, Iceberg, ClickHouse) push this further by storing immutable columnar Parquet/ORC files in S3/GCS with zone-map min/max metadata, skipping 99% of bytes on analytical scans.

LSM-Tree vs. B-Tree Hierarchy

MemTable, Bloom-Filtered SSTables & Compaction Tiers

1.WAL + MemTable: Absorbs random writes sequentially in RAM with crash durability.

2.Bloom Filters: Skips SSTables that definitely do not contain the target key.

3.Compaction: Merges sorted runs, purges tombstones, and bounds read amplification.

4.B-Tree Contrast: Updates 16KB pages in-place; faster point reads, higher write amp.

Caption: MemTable, Bloom-Filtered SSTables & Compaction Tiers (WAL + MemTable (RAM) -> L0 SSTables + Bloom -> L1-Ln Leveled Runs -> SSTable).

B-Tree Storage Engine (OLTP / SQL)Predictable, fast point lookups and ordered range scans (single tree traversal). No background compaction stalls.In-place random page writes and WAL full-page writes increase write amplification. Page fragmentation wastes disk space over time.

B-Trees Win Read Predictability; LSM-Trees Win Write Ingestion

B-Trees update fixed pages in-place (1-path lookup, higher random write amp); LSM-Trees batch sequential flushes (fast writes, relies on Bloom filters and compaction).

Bloom Filters Eliminate Useless SSTable Disk Seeks

A few bits per key in RAM tell an LSM reader with 99% certainty whether an SSTable contains a key before issuing an NVMe read.

Tombstones & Compaction Stall Latency

Deletes in LSM-Trees write tombstone markers; heavy delete workloads without timely compaction cause range scans to wade through millions of tombstones.

Columnar Formats & Zone Maps for Analytics

Storing columns contiguously enables SIMD vectorized scans and dictionary/RLE compression 5-10x smaller than row-oriented pages.

Order platform / Diagnosing Cassandra Read Latency Spikes from Tombstone Accumulation

Diagnosing Cassandra Read Latency Spikes from Tombstone Accumulation.

A queue-like table in Cassandra slowed from 4ms to 1,400ms on SELECT scans despite holding only 500 active rows.

Deleting processed items generated millions of LSM tombstones that had not yet been compacted away, forcing every range scan to read and discard 100,000+ tombstones. Switching to a dedicated queue/stream (Kafka) or time-bucketed partitions eliminated tombstone scans.

Lesson: Never use an LSM-Tree database as a FIFO queue with high delete churn; tombstones turn small scans into full-partition reads.

System Design / Stage 08L6 · SCALE & TRADE-OFFS

Message Queues, Event Streaming & Backpressure.

Asynchronous messaging absorbs traffic spikes and isolates downstream failures, but naive queues turn silent backlogs into memory exhaustion or lost events. In Kafka-style partitioned logs, a topic is split into ordered, append-only partitions; each partition is consumed by at most one member of a consumer group, bounding parallelism to the partition count and preserving per-key ordering when producers hash by entity ID (e.g., order_id).

Because databases and brokers cannot share a two-phase commit without hurting availability, services avoid dual-write drift using the Transactional Outbox pattern: business state and an outbox row commit in one local ACID transaction, and a Change Data Capture (CDC) relay (such as Debezium) tails the WAL to publish events at-least-once. Consumers must therefore be idempotent (deduplicating on event_id or monotonic version).

When a malformed payload or transient dependency failure repeatedly crashes a consumer, infinite retries block the entire partition head-of-line. Route poisoned records to a Dead-Letter Queue (DLQ) after bounded exponential retries, and enforce backpressure (bounded producer buffers, pull-based consumer polling, and max.poll.interval.ms tuning) so slow sinks never OOM brokers or workers.

Reliable Async Decoupling

Transactional Outbox, Partitioned Log & DLQ Isolation

1.Atomic Outbox: State and event commit together; zero dual-write loss.

2.Key Partitioning: Hashes entity ID to preserve per-entity order.

3.DLQ Isolation: Quarantines poison pills after N failed attempts.

Caption: Transactional Outbox, Partitioned Log & DLQ Isolation (DB + Outbox Tx -> CDC Log Relay -> Kafka Partitions -> Consumer + DLQ).

Partition Keys Determine Ordering and Hot-Spot Risk

Kafka guarantees strict order only within a single partition. Choosing a skewed key (like a celebrity tenant_id) pins all traffic to one partition; append a bounded salt only when strict global key order is unnecessary.

Transactional Outbox Eliminates Dual-Write Drift

Writing to Postgres and then calling Kafka risks partial failure if the pod crashes between calls. Committing both state and outbox row locally lets CDC publish reliably with zero 2PC overhead.

Separate Retry Topics from Dead-Letter Queues

Blocking a partition on a bad record stalls healthy traffic behind it. Offload transient failures to delayed retry topics and park unparseable poison pills in a DLQ with alerting.

Pull-Based Backpressure Prevents Consumer OOM

Consumers pull batches sized to their processing capacity (max.poll.records). When downstream latency rises, lag grows on durable disk rather than crashing worker heaps.

Search Engines, Inverted Indexes & Geospatial Indexing.

Relational LIKE '%term%' queries trigger full table scans that collapse under scale. Full-text engines (Elasticsearch, OpenSearch, Lucene) invert the data model: an inverted index maps normalized tokens (lowercased, stemmed, stop-word filtered) to sorted posting lists of document IDs, term frequencies, and positions. Queries intersect posting lists via skip pointers or Roaring Bitmaps and rank matches using BM25, which saturates term frequency (diminishing returns for repeated words) and normalizes by document length.

Each index is split into shards, and each shard is a self-contained Lucene instance composed of immutable segments merged in the background. Because deep FROM/SIZE pagination forces every shard to sort and return from + size results to a coordinator (O(shards * offset)), production search uses cursor-based search_after with a tie-breaker sort key.

For proximity and map workloads (find drivers within 2 km), 2D coordinates (lat, lon) cannot be indexed efficiently with two independent B-Trees. Geohash interleaves latitude/longitude bits into a base-32 Z-order string so nearby points share prefixes (querying 8 neighbor cells to avoid boundary edge misses). Quadtrees adaptively subdivide dense urban cells while keeping rural cells coarse, and Uber H3 uses uniform hexagonal grids so all 6 neighbors sit at equal center-to-center distance.

Search & Spatial Query Path

Scatter-Gather Inverted Index & H3 Spatial Filtering

1.Inverted Index: Posting lists + Roaring Bitmaps intersect in sub-ms.

2.Spatial Grid: H3 k-ring or Geohash+8 neighbors avoids edge misses.

3.Cursor Paging: search_after avoids O(shards * offset) heap blowups.

Caption: Scatter-Gather Inverted Index & H3 Spatial Filtering (Query Coordinator -> Inverted Shards -> H3 / Geo Filter -> RRF Rank Merge).

BM25 Beats Raw TF-IDF on Term Saturation & Length

BM25 caps the boost from repeating a keyword (k1) and penalizes overly long documents (b), preventing keyword-stuffed pages from dominating relevance.

Avoid Deep Pagination with search_after Cursors

Requesting page 1,000 at 20 hits/page forces every shard to materialize 20,000 scored docs. Use search_after with (score, doc_id) to keep pagination O(page_size).

Geohash Prefix Queries Always Check 8 Neighbors

Two cafes 50 meters apart across a prime meridian or grid boundary can have completely different Geohash prefixes; always expand queries to the center cell plus its 8 surrounding cells.

Hybrid Search Fuses BM25 Lexical + HNSW Vector Scores

Combine exact keyword matching (BM25) with semantic dense embeddings (HNSW) via Reciprocal Rank Fusion (RRF) so product SKUs and natural-language queries both rank accurately.

CDN, Edge Routing, Object Storage & Media Delivery.

Origin servers should never proxy large binary blobs or serve static assets to global users. Anycast BGP routes each client's IP packet to the topologically closest CDN Edge PoP, terminating TLS close to the user (saving 100–200ms of TCP/TLS handshake RTT) and serving cached objects from edge NVMe/RAM.

Cache freshness relies on immutable content-hashed filenames (app.8f3a1c.js with Cache-Control: public, max-age=31536000, immutable) for zero-invalidation deploys, paired with surrogate keys / cache tags and Origin Shielding (a mid-tier cache layer that collapses edge-PoP cache misses before they stampede the origin).

For user uploads and downloads, application servers mint short-lived presigned S3/object-storage URLs so clients stream gigabytes directly to/from blob storage without tying up API worker threads. Video platforms transcode raw uploads into chunked HLS / MPEG-DASH segments (2–6s .ts/.m4s files across 360p–4K bitrates) indexed by a manifest (.m3u8/.mpd), letting players switch quality mid-stream as bandwidth fluctuates.

Edge & Blob Delivery

Anycast Edge PoP, Origin Shield & Direct-to-Object Media Flow

1.Anycast Routing: Terminates TLS at nearest PoP for low TTFF.

2.Origin Shield: Deduplicates regional cache misses before origin.

3.Presigned Bypass: Clients upload/download blobs directly to S3.

Caption: Anycast Edge PoP, Origin Shield & Direct-to-Object Media Flow (Anycast Edge PoP -> Origin Shield -> Object Storage -> Transcode Worker).

Bypass Application Servers with Presigned Object URLs

Routing 500MB video uploads through API pods exhausts memory and NIC bandwidth. Issue a 5-minute presigned S3 PUT URL and verify completion via S3 event notifications.

Content-Hashed URLs Beat Global Cache Purges

Global CDN invalidations take seconds to propagate and risk stale mixes. Bake a content hash into asset URLs so every release gets a fresh, infinitely cacheable key.

Origin Shielding Collapses Multi-PoP Misses

Without an origin shield, 200 global PoPs missing a newly published video thumbnail hit your origin 200 times simultaneously. A regional shield coalesces those into 1 origin fetch.

HLS/DASH Enables Adaptive Bitrate & CDN Chunk Caching

Splitting video into 4-second segments turns streaming into standard HTTP GETs that CDNs cache effortlessly while players adapt bitrate per segment.

Rate Limiting, API Gateways & Load Shedding.

Without admission control at the edge, a single misbehaving client or downstream slowdown saturates worker pools and triggers cascading retries across every tier. API Gateways enforce rate limiting per tenant, IP, or API key: Token Bucket allows controlled bursts up to bucket capacity while refilling at a steady rate, whereas Sliding Window Counter smooths fixed-window boundary spikes (where 2x traffic could slip through at 00:59 and 01:01) using weighted counts from the previous and current buckets.

In a multi-gateway fleet, a naive GET + SET in Redis introduces race conditions under concurrency. Execute rate checks in a single atomic Redis Lua script (or fail-open to local in-memory token buckets if Redis is unreachable so the limiter never becomes a single point of failure).

Static rate limits alone cannot protect a service when downstream DB latency spikes 10x—even normal QPS will exhaust threads under Little's Law. Pair per-tenant rate limits with adaptive concurrency limits (AIMD / Netflix Concurrency Limits, or Envoy overload manager) and priority-aware load shedding: drop low-priority background/analytics traffic with HTTP 503 + Retry-After while preserving capacity for critical checkout or auth paths.

Combine per-tenant quotas with latency-driven adaptive concurrency so overloaded tiers shed cheap work fast.

Token Bucket Allows Bursts; Sliding Window Prevents Edge Spikes

Use Token Bucket for burst-friendly public APIs; use Sliding Window Counter when strict per-minute quotas must prevent 2x boundary bursts.

Atomic Redis Lua Scripts Prevent Distributed Over-Admission

Reading a counter and incrementing in two round-trips lets concurrent requests bypass the limit. Encapsulate refill + decrement in one single-threaded Redis Lua script.

Adaptive Concurrency Beats Static QPS Limits During Slowdowns

When DB latency rises from 10ms to 500ms, a static 5,000 QPS limit still queues 2,500 in-flight requests. AIMD concurrency limits shrink the active window automatically as RTT climbs.

Priority-Aware Load Shedding Protects Revenue Paths

Tag requests at the gateway (critical, standard, best-effort) so overload sheds recommendation widgets before dropping checkout mutations.

System Design / Stage 12L7 · STAFF / PRINCIPAL

Multi-Region Active-Active, Observability & Disaster Recovery.

Single-region systems fail completely when an entire cloud region loses control-plane or backbone connectivity. Disaster Recovery starts by quantifying RPO (Recovery Point Objective)—maximum tolerable data loss (e.g., 0s for ledgers via synchronous quorum, <5s for feeds via async replication)—and RTO (Recovery Time Objective)—maximum tolerable downtime for DNS/Anycast failover.

Active-Passive keeps a warm standby region fed by async replication, simplifying consistency at the cost of failover lag and potential RPO loss. Active-Active serves writes in multiple regions simultaneously for local latency (<30ms) and zero-RTO failover, but requires either home-region user pinning (EU users write in eu-west-1, US users in us-east-1), global consensus (Spanner/CockroachDB paying cross-region RTT), or CRDTs (Conflict-free Replicated Data Types) to merge concurrent updates deterministically without coordination.

Operating multi-region fleets requires end-to-end observability: propagate W3C traceparent headers across HTTP, gRPC, and Kafka; bound Prometheus metric cardinality (never put user_id or request_id in labels); use tail-based sampling to retain 100% of error and p99 traces; and continuously validate failover runbooks with Chaos Engineering GameDays.

Global Resilience & Telemetry

Multi-Region Routing, Home-Region Replication & OTel Tail Sampling

1.RPO / RTO Bounds: Health-checked failover shifts traffic in <60s.

2.Blast Isolation: Zero synchronous cross-region hops on hot paths.

3.W3C Tracing: Correlates spans across gateways, RPCs, and queues.

Caption: Multi-Region Routing, Home-Region Replication & OTel Tail Sampling (Geo-DNS / Anycast -> Region US-East -> Region EU-West -> OTel Tail Sampler).

Let RPO and RTO Drive Active-Active vs Active-Passive

Active-Active eliminates regional failover RTO for stateless tiers, but multi-region writes force either cross-region consensus latency or CRDT/home-region conflict rules.

Pin Users to Home Regions Before Reaching for Multi-Leader Writes

Sharding user state by home_region gives 99% of requests local-region writes and strong consistency while keeping another region warm for DR promotion.

Tail-Based Sampling Captures 100% of Errors Without Storage Bloat

Head-based 1% sampling drops 99% of rare p99 bugs. Buffer spans briefly at the OTel collector and keep every trace with an error status or high latency.

Untested Failover Plans Are Broken Failover Plans

Run scheduled GameDays (blackholing a region's DNS or draining an AZ) to catch hidden single-region dependencies like shared auth databases or stale DNS TTLs.

Viral Link Cache Expiration + Analytics Queue Backlog

A celebrity shares a short link driving 80,000 redirects/sec right as its Redis key expires, while a downstream analytics warehouse slows down and threatens to back up redirect workers.

Decouple hot user paths from slow fanout, indexing, and analytics pipelines.
