Problem
How to implement Time-Series Databases without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
When concurrent writes contend on shared state, time-series workloads are append-mostly, immutable, and queried over recent time windows—allowing specialized columnar compression and retention drops.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

# Delta-of-delta timestamp encoding concept (Python)
def delta_of_delta(timestamps: list[int]) -> list[int]:
    deltas = [timestamps[i] - timestamps[i - 1] for i in range(1, len(timestamps))]
    return [deltas[0]] + [deltas[i] - deltas[i - 1] for i in range(1, len(deltas))]

Inverted Index Memory Exhaustion

#1 PRODUCTION OUTAGE

Putting unbounded IDs (user_id, request_id, trace_id) into indexed tags creates millions of unique series, blowing up RAM.

The rule / invariant

Keep indexed tags low-cardinality (<100K active series/shard); put high-cardinality IDs in logs/traces or unindexed fields.

When to use it / trade-off

Design Trade-Off

Late-arriving samples & averaging percentiles

Before · Unbounded Coupling
  • No backpressure on spikes
  • Implicit shared state
  • Cascading tail latency
After · Bounded & Observable
  • Explicit capacity budgets
  • Isolated failure domains
  • Predictable p99 latency
Why can you never average p99 latencies across servers or time buckets?

Percentiles are non-additive. Store mergeable histograms (HDRHistogram / DDSketch / Prometheus native histograms) so p99 can be accurately aggregated across shards and windows.

How do TSDBs handle out-of-order / late-arriving IoT samples?

Modern TSDBs buffer recent out-of-order samples in a mutable head/WAL window and merge them during chunk compaction, rejecting samples older than a bounded grace window.

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Never put unbounded IDs (user_id, request_id, URL path with IDs) in indexed TSDB tags.
  • 02Store mergeable histograms (or sum + count) instead of pre-computed p99s or averages so rollups remain mathematically valid.
  • 03Use time-based chunk partitioning so retention cleanup is an instant file drop rather than expensive row-by-row DELETEs.
