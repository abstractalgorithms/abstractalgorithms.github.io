01
Software Engineering / Stage 01

Engineering Craftsmanship & Clean Code.

Code is written once but read, debugged, and modified dozens of times. Clean code is not about clever one-liners or premature patterns; it is about reducing cognitive load. Intention-revealing names encode domain units and invariants, Command-Query Separation (CQS) ensures functions either mutate state or return data without hidden side effects, and pure core functions keep I/O at the edges. Apply DRY to business knowledge rather than incidental code duplication—two functions that look similar today but evolve for different business reasons should remain separate.

Command-Query Separation & Pure Cores

Separate deterministic domain calculations from side-effecting I/O (DB writes, HTTP calls, clock reads). Pure functions require zero mocks to test and cannot corrupt shared state.

Knowledge DRY vs Incidental Duplication

Avoid coupling unrelated domains through a shared helper just because two snippets look alike today; wrong abstractions are far more expensive than three lines of duplicated code.

Order platform / Untangling a 400-Line Billing Method with Pure Domain Extraction

Untangling a 400-Line Billing Method with Pure Domain Extraction.

A monthly invoicing function mixed tax calculation, discount eligibility, SQL updates, and email sending in a single nested loop, causing frequent off-by-one rounding bugs that required a live database to reproduce.

The team extracted pure functions for prorated line-item calculation and tax rules (returning immutable value objects) while keeping database persistence and email dispatch in a thin orchestrator. Unit tests for edge cases like leap years and negative credits dropped from 4 seconds to 2 milliseconds.

Lesson: Separating pure business rules from I/O side effects makes correctness obvious to readers and trivial to verify.
  • Never apply the Boy Scout Rule so aggressively inside a bugfix PR that unrelated formatting diffs obscure the actual behavioral change.
  • YAGNI applies to speculative extensibility, not to basic input validation, logging, or error handling.
Pause & reason: where would you draw the boundary?▼
  • Which functions in your hot path both mutate state and return calculated results?
  • Can you test your core business logic without booting a database, HTTP server, or clock mock?
  • Where has premature DRY coupled two features that actually change for different reasons?
  • Does a new engineer reading this module understand its invariants without tracing five other files?

02
Software Engineering / Stage 02

The Automated Testing Pyramid.

Defect remediation cost grows exponentially the later a bug is caught—from seconds in an IDE to costly production rollbacks. The Automated Testing Pyramid optimizes feedback speed and signal-to-noise: a broad base (~70%) of sub-millisecond, isolated unit tests; a focused middle (~20%) of integration tests (using ephemeral Testcontainers for real SQL/Redis behavior) and consumer-driven contract tests (Pact/OpenAPI); and a thin peak (~10%) of critical end-to-end user journeys. Inverting this into an 'Ice-Cream Cone' of hundreds of brittle browser tests creates multi-hour CI queues and chronic flakiness.

ChoiceWhat it buysWhat it costs
Isolated Unit Tests (Base)Execute in milliseconds with zero network or disk I/O. Pinpoint exact logic regressions and edge cases immediately.Do not verify SQL queries, serialization formats, or third-party wire protocols.
Integration & Contract Tests (Middle)Testcontainers verify real database migrations, indexes, and queries. Contract tests catch breaking API schema changes without booting full environments.Slower container startup (seconds) and higher CI memory footprint.
End-to-End Tests (Peak)Verify full-stack wiring across UI, auth, APIs, and persistence.Slowest execution and highest susceptibility to timing and environment flakiness.

Determinism Invariant

Eliminate Thread.sleep()/setTimeout() polling guesses, shared mutable fixtures, and real wall-clock dependencies; inject deterministic clocks and use explicit condition-polling assertions.

Consumer-Driven Contract Testing

Verify producer-consumer API compatibility in CI via Pact or schema registries rather than maintaining fragile staging environments where all microservices must be deployed simultaneously.

Order platform / Reversing a 90-Minute Flaky E2E Suite into a 7-Minute Pyramid

Reversing a 90-Minute Flaky E2E Suite into a 7-Minute Pyramid.

A 60-engineer SaaS org relied on 1,200 Selenium end-to-end tests that took 90 minutes in CI and failed 30% of the time on network timeouts, prompting engineers to blindly click 'Rerun'.

The team moved validation, pricing, and permission assertions down into unit tests, replaced cross-service E2E checks with Pact contract tests and PostgreSQL Testcontainers, and kept only 25 critical-path E2E smoke tests. CI runtime dropped to 7 minutes with <1% flakiness.

Lesson: Push every assertion as far down the test pyramid as possible while still verifying the real boundary behavior.
Pause & reason: where would you draw the boundary?▼
  • What percentage of your CI failures are caused by flaky tests rather than real regressions?
  • Which E2E tests are actually verifying pure business logic that belongs in unit tests?
  • Are database queries and migrations tested against a real engine (Testcontainers) or an in-memory mock that diverges in SQL dialect?
  • How do you catch breaking API contract changes before deploying two services to staging?

03
Software Engineering / Stage 03

Test-Driven Development (TDD) Mastery.

Test-Driven Development is primarily a design discipline rather than a coverage metric. In the Red phase, writing a failing test forces you to specify the caller's ergonomics, inputs, and edge-case contracts before committing to internal data structures. In the Green phase, you write the simplest code to pass—guided by the Transformation Priority Premise (TPP), moving from constants to variables to conditionals to recursion—avoiding premature generality. In the Refactor phase, with a green safety net, you eliminate duplication and sharpen abstractions. Over-mocking internal collaborators (London/mockist style) couples tests to implementation details; testing through public module boundaries (Detroit/classicist style) keeps refactoring painless.

1. Red (Specify Behavior)Write a small, failing test describing one concrete requirement or edge case at the module boundary.
→
2. Green (Minimal Implementation)Write the simplest code needed to pass the test without speculative abstractions.
→
3. Refactor (Clean Structure)Improve naming, extract pure helpers, and remove duplication while keeping all tests green.
→
4. Repeat in Small IncrementsAdvance step-by-step using TPP rather than designing a rigid monolith upfront.

Test Behavior, Not Implementation

Assert observable outputs and state transitions at the public boundary; avoid mocking private helpers or verifying internal call counts that break on every refactor.

Transformation Priority Premise (TPP)

Prefer simpler code transformations (null -> constant -> scalar -> conditional -> iteration) as you make each new test pass so algorithms emerge cleanly without getting stuck.

Order platform / Designing a Rate-Limiter Token Bucket via Red-Green-Refactor

Designing a Rate-Limiter Token Bucket via Red-Green-Refactor.

An engineer needed to build an in-memory token bucket rate limiter with burst capacity, continuous refill, and clock-skew safety.

Starting with a test for an empty bucket, then a single refill tick, then fractional elapsed seconds, and finally burst capping forced a clean Clock interface injection from test #1. The resulting 50-line class had zero hidden time.now() calls and 100% deterministic edge-case coverage.

Lesson: Writing the test first immediately exposes hidden dependencies like system clocks, randomness, and global state.
Pause & reason: where would you draw the boundary?▼
  • When a function is hard to write a unit test for, is the problem the test framework or the function's hidden dependencies?
  • Do your tests break when you rename private methods or change internal data structures without changing behavior?
  • Are you writing tests after the fact that merely mirror implementation bugs, or specifying invariants first?
  • Which external boundaries (clocks, random generators, gateways) should be injected to keep TDD loops fast?

04
Software Engineering / Stage 04

Continuous Integration & Delivery (CI/CD).

Continuous Integration means merging small, verified changes into the main trunk at least daily, eliminating the integration hell of long-lived GitFlow branches. Incomplete features are decoupled from deployment via runtime feature flags and expand-and-contract database migrations (add nullable column -> dual-write -> backfill -> switch reads -> drop old column). Builds must be hermetic and reproducible—pinning dependencies via cryptographic lockfiles and generating a Software Bill of Materials (SBOM)—and the exact immutable container digest built in CI is promoted unchanged from staging to canary to production.

ChoiceWhat it buysWhat it costs
Trunk-Based DevelopmentSmall, frequent merges eliminate multi-week merge conflicts. Forces modular decoupling via feature flags and backward-compatible migrations.Requires fast, reliable CI gates and strict discipline to clean up stale feature flags.
Long-Lived Feature Branches (GitFlow)Isolates unfinished work from main without runtime feature flags.Causes painful merge conflicts, delayed integration bugs, and large risky release batches.

Build Once, Promote Everywhere

Never rebuild source code per environment; compile and sign a single immutable container image digest (sha256) and inject environment-specific config at runtime.

Zero-Downtime Expand-and-Contract Migrations

Separate schema expansion from old-column removal across deployments so rolling upgrades and instant rollbacks never fail on missing columns.

Order platform / Eliminating Release Freezes with Trunk-Based Delivery & Canary Rollouts

Eliminating Release Freezes with Trunk-Based Delivery & Canary Rollouts.

A fintech team used 3-week release branches in GitFlow; every bi-weekly release required a 2-day code freeze and manual QA sign-off, yet still caused 4-hour rollback incidents.

The team adopted trunk-based development with <24-hour PRs, automated ephemeral preview environments, expand-and-contract DB migrations, and Argo Rollouts canary analysis (auto-aborting if error rate >0.5% or p99 >250ms). Deployment frequency rose from bi-weekly to 15 times daily.

Lesson: Small batch sizes plus automated canary rollback reduce both deployment risk and mean time to recovery.
Pause & reason: where would you draw the boundary?▼
  • How many days does an average branch live before merging to main, and how often do merge conflicts occur?
  • Are staging and production running the exact same immutable artifact digest built in CI?
  • Can you roll back a code deployment in under 2 minutes without breaking database schema compatibility?
  • Are third-party build dependencies pinned by cryptographic hash and scanned for supply-chain CVEs?

Software Engineering / Stage 05

Refactoring & Legacy Code Rescue.

Michael Feathers defines legacy code simply as code without tests. Editing it directly creates the Legacy Code Dilemma: you need tests to refactor safely, but you often must refactor to introduce tests. Break this deadlock by first writing characterization (golden master) tests that record the system's actual current behavior—quirks included—before changing logic. Next, identify seams (link, object, or parameter seams) to break hardcoded static calls or database dependencies without altering behavior. For large structural replacements, use Branch by Abstraction: introduce an interface over the legacy module, route a new implementation behind a feature flag, shadow-compare outputs, and delete the legacy path only after parity is proven.

Characterization (Golden Master) Tests

Capture representative production inputs and assert the exact outputs of the legacy module today so accidental behavioral shifts are caught immediately during cleanup.

Branch by Abstraction

Wrap a tangled legacy subsystem behind a clean abstraction, build the replacement incrementally behind a toggle, validate parity in production, and retire the old code without a risky big-bang rewrite.

Order platform / Replacing a Legacy Pricing Engine Without Downtime

Replacing a Legacy Pricing Engine Without Downtime.

An e-commerce platform's 10-year-old discount engine had zero unit tests and subtle rounding quirks that downstream accounting reports depended on.

Engineers recorded 5,000 real cart snapshots as characterization tests, wrapped the engine behind a PricingPort seam, and used Branch by Abstraction to shadow-run the new engine against live traffic. Discrepancies were fixed before cutting over 100% of traffic.

Lesson: Never rewrite legacy code in the dark; pin its current behavior with characterization tests and migrate behind an abstraction seam.
  • Resist 'big-bang rewrites'—they freeze feature delivery while inevitably re-introducing forgotten edge-case fixes.
  • Keep structural refactoring commits separate from behavioral feature commits so git bisect and code review remain clear.
Pause & reason: where would you draw the boundary?▼
  • Which high-churn legacy module currently has zero automated tests protecting its behavior?
  • What minimal seam (parameter injection, wrapper interface, or extract-and-override) lets you test this module in isolation?
  • How will you verify that a refactored replacement preserves undocumented edge-case behavior?
  • Can you migrate traffic incrementally via Branch by Abstraction instead of a single cutover PR?

Software Engineering / Stage 06

Code Review Rigor & Team Collaboration.

Code review exists to catch logic flaws, security gaps, and architectural drift while spreading system knowledge across the team. Review effectiveness collapses when pull requests exceed ~300-400 lines: reviewers skim and default to 'LGTM'. High-performing teams automate formatting, imports, and lint rules in pre-commit/CI so human reviewers never waste cycles on whitespace. Reviewers follow a structured checklist—verifying correctness, edge cases, failure handling, security boundaries, and test quality—and distinguish blocking defects from optional nitpicks.

Small-Batch PR Ergonomics (<300 LOC)

Decompose large features into stacked or sequential small PRs (schema migration, core logic, API wiring) so each review takes 10 minutes and receives deep scrutiny.

Automate Formatting, Humanize Design Review

Offload style and syntax rules to Prettier/Black/Spotless in CI; focus human review on concurrency safety, data invariants, error paths, and operational observability.

Order platform / Cutting PR Turnaround Time by 65% via Stacked Small PRs

Cutting PR Turnaround Time by 65% via Stacked Small PRs.

A backend team averaged 4 days per PR review because engineers routinely opened 1,500-line feature PRs mixing migrations, refactoring, and business logic.

The team instituted a 350-line soft cap, automated formatting/linting in pre-commit, added a PR template requiring test evidence and rollback notes, and labeled minor comments as 'nit:'. Median time-to-first-review dropped from 26 hours to 3 hours.

Lesson: Small, focused pull requests with automated style checks turn code review from a bottleneck into a fast quality multiplier.
Pause & reason: where would you draw the boundary?▼
  • What is the median line count and wait time of pull requests on your team?
  • How many review comments in the last month were about formatting or naming rules that a linter could enforce?
  • Do reviewers explicitly check concurrency, idempotency, and failure-path test coverage?
  • Are blocking architectural concerns clearly separated from non-blocking suggestions?

Software Engineering / Stage 07

Static Analysis, Linters & Mutation Testing.

Line coverage only proves that a test executed a line—not that it asserted anything meaningful about the result. Static Application Security Testing (SAST) tools like Semgrep, CodeQL, and SonarQube parse Abstract Syntax Trees (ASTs) and data-flow graphs to detect SQL injection, tainted inputs, null dereferences, and excessive cyclomatic or cognitive complexity before code review. Mutation testing (PIT for Java, Stryker for JS/TS, mutmut for Python) goes a step further: it systematically injects small faults (flipping > to >=, removing return values, negating conditionals) and measures the mutation score—the percentage of mutants killed by failing tests.

Cognitive Complexity Budgets

Track cognitive complexity (nested conditionals, early-return violations) rather than raw line count so deeply tangled methods are flagged automatically in CI.

Mutation Score Over Raw Line Coverage

Run mutation testing on critical domain and financial modules to expose tests that execute code without asserting boundary conditions.

Order platform / Exposing Hollow Tests in a Billing Engine with PIT Mutation Testing

Exposing Hollow Tests in a Billing Engine with PIT Mutation Testing.

A Java billing service boasted 92% JaCoCo line coverage, yet a subtle off-by-one bug in tiered pricing overcharged enterprise customers in production.

Running PIT mutation testing on the pricing package revealed a 48% mutation score—existing tests executed the tier-boundary branches without asserting exact boundary values. Adding targeted boundary assertions raised the mutation score to 91% and caught two latent rounding bugs.

Lesson: Line coverage measures execution; mutation testing measures whether your assertions actually detect bugs.
  • Run mutation testing incrementally on changed files or critical packages in CI rather than across an entire monorepo on every commit.
  • Treat SAST rules as curated team invariants; disable noisy false-positive rules so engineers do not ignore real security alerts.
Pause & reason: where would you draw the boundary?▼
  • Which critical modules have high line coverage but have never been checked for assertion strength?
  • What SAST and secret-scanning checks run locally or in CI before a human ever opens a PR?
  • Where is cyclomatic or cognitive complexity highest in your codebase, and does it correlate with bug frequency?
  • How do you prevent new architectural boundary violations or tainted-input vulnerabilities from entering main?

Theory & Tips and Tricks

  • 02End-to-end lesson: Speed and reliability reinforce each other: fast, deterministic CI enables small batches, which reduce defect rates.
  • 03Failure check — Non-Backward-Compatible Migration Blocks Emergency Rollback: A PR renames a database column and updates application code in the same release. A PR renames a database column and updates application code in the same release. When a latency regression forces an immediate rollback to the previous container image, the old code crashes because the original column was already dropped.

The decision framework

01

Is business logic separated from I/O and framework side effects?

Pure domain functions can be tested in milliseconds without brittle mocks or live databases.

02

Does this check belong at the unit, integration, contract, or E2E layer?

Push verification as far down the test pyramid as possible to keep CI under 10 minutes and eliminate flakiness.

03

Can this change be merged to trunk behind a flag or compatible schema?

Small daily merges and expand-and-contract migrations prevent merge debt and enable instant rollbacks.

04

Are existing behaviors pinned before refactoring legacy code?

Characterization tests and seams protect undocumented production invariants during structural cleanup.

05

Can an automated gate enforce this rule instead of a human reviewer?

Use linters, SAST, lockfiles, and mutation testing for mechanical rules so reviewers focus on design and correctness.
