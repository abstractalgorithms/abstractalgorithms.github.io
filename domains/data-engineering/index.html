Data Engineering / Stage 01Foundation

Big Data Foundations & Architecture Patterns.

Why this matters: Understand the 5 Vs, Warehouse vs Lake vs Lakehouse trade-offs, Lambda vs Kappa, and Medallion architecture.

Modern data platforms reconcile the 5 Vs of big data—Volume, Velocity, Variety, Veracity, and Value—by decoupling compute from durable object storage (S3/GCS/ADLS).

Traditional Data Warehouses enforce strict schema-on-write over proprietary storage, delivering fast SQL BI at high storage/ingestion cost, while raw Data Lakes offer cheap schema-on-read object storage but degrade into unindexed 'data swamps' lacking ACID transactions. The Lakehouse unifies both by layering an open transactional metadata log (Apache Iceberg, Delta Lake, or Hudi) directly over Parquet/ORC files on object storage.

Medallion Lakehouse Flow

Decoupled Ingestion, Bronze/Silver/Gold ACID Tiers & Multi-Engine Serving

1.Bronze (Raw Replay): Captures exact source payloads with ingestion timestamps so downstream logic bugs can always be replayed.

2.Silver (Conformed): Applies ACID MERGE INTO for deduplication, null checks, and schema enforcement across entities.

3.Gold (Serving): Pre-aggregated star-schema tables and ML feature views tuned for sub-second BI queries.

Medallion architecture isolates raw ingestion from conformed business logic on a single open ACID storage layer.

ChoiceWhat it buysWhat it costs
Lakehouse (Iceberg / Delta on Object Storage)Open Parquet storage eliminates vendor lock-in while supporting ACID transactions and time travel. Single copy of data serves both BI SQL engines (Trino/Snowflake) and ML/Spark workloads.Requires periodic table maintenance (compaction, Z-ordering, snapshot expiration). Object storage listing/metadata overhead requires careful partitioning to avoid small-file bottlenecks.
Kappa Architecture (Single Stream)Eliminates dual-codebase drift between batch and streaming business logic. Reprocessing historical backfills simply replays offsets from a retained Kafka or Bronze log.Long-retention Kafka topics or large stateful joins increase state-store operational complexity. Not all ad-hoc multi-year ML feature backfills fit comfortably in streaming semantics.

Decouple Compute from Open Storage

Store immutable columnar files (Parquet) in cheap object storage and spin up ephemeral Spark or Trino clusters only during query or ETL windows, scaling storage and compute independently.

Medallion Contracts (Bronze -> Silver -> Gold)

Keep Bronze raw and replayable so parser bugs never lose source events; enforce schema validation, deduplication, and PII masking in Silver; publish domain-specific dimensional aggregates in Gold.

Prevent the Small-Files Problem Early

Writing thousands of 100 KB files per minute destroys S3 GET/LIST throughput and Spark driver memory. Target 128 MB - 512 MB Parquet files via buffering or async compaction.

Apache Spark Internals, Shuffles & AQE.

Why this matters: Master Driver/Executor scheduling, Catalyst optimizer, Broadcast vs Sort-Merge Joins, partitioning, and AQE.

Apache Spark executes transformations lazily by building a logical DAG, which the Catalyst Optimizer transforms via rule-based (predicate pushdown, column pruning, constant folding) and cost-based optimizations into a physical execution plan.

Stages are separated by wide transformations (groupBy, join, repartition) that require a network Shuffle—writing sorted spill files to local NVMe disks and fetching partitions across executors—whereas narrow transformations (map, filter) pipeline in memory within a single stage. Most production Spark OOMs and 10x tail latencies stem from shuffle data skew (one hot key sending gigabytes to a single executor task), suboptimal join strategies (falling back to Sort-Merge Join when a small dimension table could be Broadcasted), or executor misconfiguration (oversized heaps causing 30-second GC pauses).

AQE Runtime Re-Planning

Structured Streaming, Kafka & Watermarking.

Why this matters: Build exactly-once Kafka-to-Lakehouse pipelines with event-time watermarks and stateful aggregations.

Distributed streaming pipelines must process unbounded event streams where network delays and mobile offline buffering cause events to arrive out of order.

Processing-time windows break historical correctness whenever a consumer lags or replays, so production pipelines window on Event Time (when the event occurred) and use Watermarks (W = max_event_time - allowed_lateness) to bound how long the engine keeps window state open before emitting final results and garbage-collecting state. Without a watermark, stateful aggregations (like sessionization or deduplication) accumulate unbounded state in memory until executors OOM.

Event-Time Watermarking

How Watermarks Advance, Emit Windows, and Evict Expired State

Advancing the watermark (max_event_time - allowed_lateness) triggers final window emission and bounds RocksDB state growth.

ChoiceWhat it buysWhat it costs
HDFSBackedStateStore (JVM Heap)Lowest per-lookup latency for small state (< 100k keys per partition). Zero external native dependency.Millions of state keys trigger severe JVM Stop-the-World GC pauses. Hard-capped by executor heap memory.
RocksDB State Store (Off-Heap + SSD)Scales to tens of millions of active keys per executor using local NVMe SSD. Incremental changelog checkpoints avoid rewriting gigabytes of state every micro-batch.Higher serialization/deserialization overhead per key lookup. Requires tuning block cache and write-buffer memory off-heap.

Always Pair Stateful Ops with a Watermark

Specify withWatermark('event_time', '15 minutes') before dropDuplicates or groupBy(window(...)) so Spark can safely evict expired state keys.

Separate Event Time from Ingestion Time

Use event_time for business windows and watermarks, and ingestion_time for Iceberg/Delta partition pruning and SLA lag monitoring.

Handle Poison Pills Without Halting the Stream

Parse JSON/Avro defensively inside from_json/UDF wrappers that route malformed records to a Dead Letter Queue (DLQ) topic instead of crashing the micro-batch.

Order platform / Taming Unbounded Deduplication State in a Mobile Telemetry Stream

Taming Unbounded Deduplication State in a Mobile Telemetry Stream.

A Kafka-to-Delta streaming job running dropDuplicates(['event_id']) grew executor memory by 4 GB/day until crashing every 72 hours.

Without a watermark, Spark retained every seen event_id forever in JVM heap. Switching to dropDuplicates(['event_id', 'event_time']) with a 2-hour watermark and enabling the RocksDB state store stabilized memory flat at 1.2 GB indefinitely.

Lesson: Unbounded deduplication in a stream is a guaranteed delayed OOM—bound state with an event-time watermark and RocksDB.

Data Engineering / Stage 04Advanced

Lakehouse Formats, Orchestration & Governance.

Why this matters: Operate Iceberg/Delta/Hudi tables, idempotent DAG backfills, SCD Type 2 modeling, and data lineage.

Open Lakehouse table formats—Apache Iceberg, Delta Lake, and Apache Hudi—bring database-grade ACID transactions, Optimistic Concurrency Control (OCC), snapshot isolation, and schema evolution to object storage.

Each commit atomically appends a new metadata manifest/JSON log entry referencing immutable Parquet files, enabling time-travel queries and zero-copy rollbacks. For mutable workloads (CDC upserts, GDPR deletes, SCD Type 2 history), engineers choose between Copy-on-Write (CoW, rewriting entire Parquet files on update for fast reads) and Merge-on-Read (MoR, writing lightweight delete/delta files merged at read time for fast streaming writes).

Iceberg / Delta Snapshot MVCC

Optimistic Atomic Metadata Commits Over Immutable Parquet Files

1.Snapshot Isolation: Concurrent BI readers pinned to Snapshot v41 never see partial writes while v42 is being staged.

2.Optimistic Concurrency: Atomic pointer swap in the catalog/log detects conflicting file-level mutations and retries cleanly.

3.Time Travel & Rollback: Immutable data files let operators query AS OF TIMESTAMP or instantaneously roll back bad deploys.

Atomic metadata pointer swaps over immutable Parquet files give object storage database-grade MVCC isolation and instant rollbacks.

ChoiceWhat it buysWhat it costs
Copy-on-Write (CoW)Fastest read performance because queries scan clean Parquet files with zero merge overhead. Simple storage layout ideal for hourly/daily batch MERGEs.High write amplification: updating 1 row rewrites an entire 256 MB Parquet file. Unsuitable for sub-minute streaming CDC upserts.
Merge-on-Read (MoR)Low write latency: appends small delta or positional/equality delete files immediately. Supports 1-minute CDC freshness without rewriting large base files.Readers pay merge-on-read CPU overhead until background compaction runs. Requires disciplined async compaction SLAs to prevent read degradation.

Hidden Partitioning & Partition Evolution

Use Iceberg transforms (days(ts), bucket(16, user_id)) so users query raw columns without knowing partition layouts—and evolve granularity without rewriting historical data.

Idempotent Partition-Scoped Backfills

Design Airflow DAGs to parameterize execution_date and execute REPLACE WHERE / dynamic partition overwrite so re-running a failed task never duplicates rows.

Schedule Compaction & Snapshot Expiration

Run periodic rewrite_data_files (bin-packing small files to 256 MB) and expire_snapshots (keeping 7 days for time travel) to bound metadata growth and S3 costs.

Eliminating Read Degradation in a High-Churn CDC Lakehouse Table.

Dimensional Modeling, Star Schemas & SCD Type 2.

Why this matters: Design analytical schemas balancing Kimball Star Schemas vs One Big Table (OBT), surrogate keys, and Slowly Changing Dimensions.

Analytical warehouses and Lakehouse Gold layers optimize for read-heavy aggregations rather than OLTP write normalization. Ralph Kimball's Dimensional Modeling organizes data into Fact tables (high-volume, immutable business events like orders or clicks with additive numeric measures) joined to Dimension tables (descriptive context like customers, products, and dates). A Star Schema keeps dimensions denormalized in a single hop around the fact table, minimizing join depth compared to a normalized Snowflake Schema. In modern columnar engines (BigQuery, Snowflake, ClickHouse, Trino), teams frequently weigh Star Schemas against One Big Table (OBT)—pre-joining dimensions into wide denormalized fact tables to eliminate runtime joins at the cost of higher storage and dimension-update amplification.

Because real-world attributes change over time (a customer's loyalty tier or shipping address), Slowly Changing Dimensions (SCD) govern how history is preserved: SCD Type 1 overwrites in place (losing history), whereas SCD Type 2 appends a new versioned row with a unique Surrogate Key, effective_from, effective_to, and is_current flags. Fact tables join to the dimension's Surrogate Key at the time of the event so historical revenue reports never retroactively shift when a customer changes tier.

Kimball Star & SCD Type 2

Surrogate Key Joins Preserving Point-in-Time Dimension History

1.Fact Grain: Immutable event rows storing additive measures and foreign surrogate keys.

2.SCD Type 2: Appends new row version on attribute change with non-overlapping validity windows.

3.Conformed Dims: Shared dimensions ensure Finance and Growth compute identical metrics.

Star schemas pair immutable fact grains with SCD Type 2 surrogate keys so historical analytics remain reproducible.

Simpler SQL for analysts without multi-table join pitfalls or fan-out bugs.Updating a historical dimension attribute requires expensive backfills across massive wide tables. Declare the Fact Grain Before Modeling

Every fact table must state its exact grain (e.g., one row per order line item). Mixing grains in a single table causes silent double-counting in SUM aggregations.

Surrogate Keys Isolate Warehouse from Source IDs

Use deterministic hashed or monotonically generated surrogate keys (customer_sk) rather than natural OLTP primary keys so SCD Type 2 versions and multi-source merges never collide.

SCD Type 2 Point-in-Time Accuracy

Track valid_from, valid_to (using 9999-12-31 for active rows), and is_current so historical fact joins (event_ts BETWEEN valid_from AND valid_to) reproduce exact past state.

CDC (Debezium), Outbox & Exactly-Once Ingestion.

Why this matters: Capture OLTP mutations reliably via WAL tailing, the Transactional Outbox pattern, Schema Registry, and idempotent upserts.

Dual-writing from application code to both an OLTP database and Kafka fails whenever one write succeeds and the other crashes, causing permanent drift between operational state and analytical lakes. Change Data Capture (CDC) via Debezium eliminates dual-writes by tailing the database Write-Ahead Log (PostgreSQL logical replication slots, MySQL binlog) asynchronously with near-zero impact on OLTP queries. For domain events that shouldn't expose raw internal table schemas, services use the Transactional Outbox pattern: writing business state and an outbox row in the same ACID database transaction, which Debezium then streams to Kafka.

Because CDC pipelines guarantee at-least-once delivery across connector restarts, downstream consumers must achieve effectively-once semantics using idempotent MERGE INTO upserts keyed on (primary_key, lsn_or_ts_ms)—never blindly appending. Finally, pairing CDC topics with a Schema Registry (Avro or Protobuf with BACKWARD/FULL compatibility) prevents upstream ALTER TABLE changes from silently breaking downstream Spark or Flink consumers.

Atomic OLTP Commit to Idempotent Lakehouse Upsert

The Transactional Outbox + WAL CDC + LSN-ordered MERGE guarantees zero dual-write drift and idempotent retries.

Guard PostgreSQL Replication Slots Against WAL Bloat

Deduplicate replayed CDC events by keeping only the highest (source.lsn, op_ts) per primary key before executing Lakehouse MERGE INTO.

Columnar Storage (Parquet/Arrow) & Distributed Query Engines.

Why this matters: Understand Parquet internals, Apache Arrow zero-copy memory, Trino/Presto MPP execution, predicate pushdown, and Z-ordering.

Analytical queries typically scan billions of rows across only 4–5 columns out of 100+. Row-oriented formats (CSV, JSON, Avro) force engines to read and deserialize every column of every row. Apache Parquet solves this with hybrid columnar storage: data is split into horizontal Row Groups (typically 128 MB–512 MB), and within each Row Group, values for each column are stored contiguously in Column Chunks and Pages. Contiguous homogeneous types unlock Dictionary Encoding, Run-Length Encoding (RLE), and ZSTD compression—often shrinking storage 5–10x—while Footer min/max statistics allow engines like Trino, DuckDB, and Spark to skip entire Row Groups via Predicate Pushdown.

In memory, Apache Arrow standardizes columnar buffers so vectorized engines process batches via CPU SIMD instructions without row-by-row deserialization overhead, and exchange data across Python/JVM/Rust boundaries via Arrow Flight with zero serialization copy. Distributed MPP engines like Trino/Presto execute SQL in pipelined in-memory stages without writing intermediate shuffles to disk (unlike batch Spark), delivering interactive sub-second to second BI latency. To maximize data skipping on multi-dimensional filters (tenant_id AND event_date), tables use Z-ordering (space-filling curve clustering) or Iceberg sort orders to co-locate related rows within the same Parquet files.

Parquet & MPP Query Pruning

3-Level Skipping: Partition -> Row Group -> Column Page

1.Footer Metadata: Stored at end of file so readers fetch schema and min/max stats in one S3 range GET.

2.RLE + Dictionary: Compresses low-cardinality strings into integer codes before ZSTD.

3.Z-Order Clustering: Co-locates multi-column predicates into tight Row Group min/max bounds.

Columnar pruning, Row-Group min/max skipping, and Arrow vectorization minimize S3 I/O and CPU cycles.

Columnar Pruning + Row-Group Min/Max Skipping

Parquet footers store min/max bounds and bloom filters per Row Group. Selecting 3 columns and filtering on a sorted/clustered key skips >95% of S3 byte reads.

Z-Ordering & Clustering for Multi-Column Filters

Sorting solely by date leaves customer_id scattered across every file. Z-ordering interleaves bits of multiple filter columns so Parquet min/max ranges stay tight.

Use Arrow-backed Pandas/Polars UDFs in PySpark and Arrow Flight for BI connectors to eliminate row-wise JVM-to-Python pickle/JSON serialization.

Data Engineering / Stage 08Advanced

Real-Time OLAP (ClickHouse/Pinot/Druid) & Materialized Views.

Why this matters: Deliver sub-100ms user-facing analytical queries using LSM merge-tree OLAP engines, inverted/bitmap indexes, and incremental materialized views.

Lakehouse engines like Trino and Spark excel at internal BI and multi-terabyte ad-hoc joins, but object-storage S3 GET latency (30–100ms per file) makes them unsuitable for high-concurrency, user-facing dashboards requiring <100ms p99 latency at 1,000+ QPS. Real-Time OLAP engines—ClickHouse, Apache Pinot, and Apache Druid—bridge this gap by ingesting directly from Kafka onto local NVMe SSDs using Log-Structured Merge-tree (LSM) storage (such as ClickHouse MergeTree parts). Incoming micro-batches write immutable sorted parts in milliseconds and merge asynchronously in the background, supporting millions of inserts per second alongside sparse primary indexes (granule marks every 8,192 rows), roaring bitmap/inverted indexes, and bloom-filter skip indexes.

To avoid scanning raw billions of rows on every dashboard load, Real-Time OLAP systems rely on Incremental Materialized Views (e.g., ClickHouse AggregatingMergeTree or SummingMergeTree, or Flink-maintained rollups). Instead of recomputing full tables on a cron schedule, triggers transform incoming Kafka blocks into pre-aggregated partial states (e.g., HyperLogLog sketches for distinct counts, sum/count states) at insert time, turning 5-second scans into 5ms lookups.

Real-Time OLAP Serving

Kafka -> LSM MergeTree Parts -> Incremental Materialized Views

1.Sparse Index: 1 mark per 8,192 rows binary-searches granules directly in RAM.

2.Bitmap / Skip Index: Roaring bitmaps and bloom filters prune non-matching granules fast.

3.Partial Agg States: HyperLogLog and sum states merge incrementally on insert.

LSM MergeTree parts and incremental materialized views turn high-velocity Kafka streams into sub-100ms OLAP queries.

Sparse Primary Indexes Fit Entirely in RAM

ClickHouse stores one index mark per 8,192 rows rather than per row, keeping the entire primary index in memory for binary-search granule pruning on multi-billion-row tables.

Incremental Materialized Views with Partial States

Data Engineering / Stage 09Advanced

Data Quality Contracts, Lineage & Idempotent DAGs.

Why this matters: Prevent silent data corruption using Data Contracts, Write-Audit-Publish (WAP), column-level lineage, and idempotent Airflow/Dagster backfills.

In data systems, silent corruption is far worse than a crashed job: a null spike, broken join, or duplicate backfill can poison executive dashboards and ML training sets for weeks before anyone notices. Data Quality Contracts establish explicit producer-consumer SLAs on schema, freshness, completeness, and value invariants (e.g., order_total >= 0, null_rate(user_id) < 0.01%). To enforce contracts before bad data ever reaches production consumers, Lakehouse pipelines use the Write-Audit-Publish (WAP) pattern: Spark or dbt writes new partition data to an isolated Iceberg branch or staging snapshot, automated quality gates (Great Expectations, Soda, dbt tests) validate row counts and invariants, and only on pass does the catalog fast-forward main atomically.

Orchestrators (Airflow, Dagster) must treat every task as strictly idempotent and partition-scoped: using logical_date parameters with INSERT OVERWRITE / REPLACE WHERE rather than non-idempotent APPEND or CURRENT_TIMESTAMP(). Finally, OpenLineage metadata emitted by Spark, dbt, and Airflow builds a column-level DAG graph so engineers can trace any broken metric upstream to its root table or assess downstream blast radius before a schema change.

Data Governance, PII Masking, Retention & FinOps.

Why this matters: Implement fine-grained row/column RBAC, GDPR/CCPA crypto-shredding & Lakehouse deletes, storage tiering, and compute FinOps.

At enterprise scale, data platforms must balance self-serve analytics with strict regulatory compliance (GDPR, CCPA, HIPAA) and cloud cost discipline. Fine-grained governance enforces Row-Level Security (e.g., region = current_user_region()) and Column-Level Masking/Tokenization (hashing or redacting email, ssn, ip_address) centrally at the catalog or query engine (Unity Catalog, Lake Formation, Trino/OPA), rather than duplicating dozens of redacted table copies. For GDPR 'Right to be Forgotten' requests across immutable Parquet files, teams either run periodic Iceberg/Delta DELETE + rewrite_data_files + expire_snapshots (so deleted bytes are physically purged) or use Crypto-Shredding: encrypting each user's PII with a per-user KMS/Vault key and deleting the key to render historical backups unreadable.

Data FinOps treats petabyte cost as an engineering metric: avoiding S3 Intelligent-Tiering/Glacier retrieval traps on frequently compacted Bronze tables, right-sizing Spark Spot/Graviton fleets with dynamic allocation, enforcing query byte-scan quotas, and expiring unreferenced Iceberg snapshots and orphan files automatically.

Broadcast Join vs Sort-Merge Join?

Broadcast when the smaller table fits safely in executor memory (< 50-100 MB); otherwise Sort-Merge with AQE skewJoin.

02

Lambda vs Kappa Architecture?

Choose Kappa with a durable log or Lakehouse replay to avoid maintaining two separate codebases.

Copy-on-Write vs Merge-on-Read?

Choose CoW for read-heavy batch tables and MoR for frequent streaming/CDC upserts.
