The idea to keep with you

Patterns are not abstraction trophies; they are targeted seams for isolating what changes from what stays invariant, from in-memory object graphs to asynchronous message pipelines.

From patterns to decisions.

Learn to recognize recurring coupling, lifecycle, concurrency, and integration problems and apply SOLID principles, GoF patterns, and Enterprise Integration Patterns only where concrete variation or failure isolation justifies the indirection.

  • ↗Enforce SOLID boundaries so business rules depend on stable abstractions rather than concrete drivers or SDKs.
  • ↗Select creational patterns (Factory, Abstract Factory, Builder) to guarantee valid object invariants at construction time.
  • ↗Compose runtime behavior and adapt incompatible interfaces using Decorator, Adapter, and Proxy without subclass explosion.
  • ↗Replace brittle conditional branching and tight object-to-object coupling with Strategy, Command, Observer, and Mediator.
  • ↗Coordinate concurrent execution safely using bounded Producer-Consumer queues, Thread Pools, and Futures.
  • ↗Design asynchronous integration flows with Pipes and Filters, Content-Based Routers, Aggregators, and Transactional Outbox.
01
Design Patterns / Stage 01

SOLID & Object-Oriented Principles.

SOLID principles diagnose why codebases become rigid or fragile. Single Responsibility aligns a module with one actor or reason to change; Open/Closed lets new variants plug in without editing tested callers; Liskov Substitution guarantees subtypes honor caller-visible contracts and invariants; Interface Segregation prevents fat interfaces from forcing dummy implementations; and Dependency Inversion keeps high-level policy independent of low-level I/O.

Liskov Substitution (LSP) is behavioral, not syntactic

A subtype must not strengthen preconditions, weaken postconditions, throw unexpected exceptions, or mutate invariants that callers of the base type rely on. Classic Rectangle/Square inheritance breaks LSP because mutating width silently mutates height.

Dependency Inversion (DIP) flips compile-time coupling

High-level billing or pricing policy defines the repository or gateway interface it needs, and the concrete SQL or HTTP adapter implements it. Policy never imports driver packages.

Interface Segregation (ISP) trims unnecessary recompilation

Splitting a monolithic Worker or Storage interface into narrow role interfaces (Readable, Writable, HealthCheckable) prevents read-only clients from coupling to write-path changes.

Order platform / Isolating tax and discount policy from database and ERP drivers

Isolating tax and discount policy from database and ERP drivers.

An invoicing module directly instantiated a MySQL connection and a legacy SOAP tax client inside calculateTotal(), making unit testing impossible without a live database and forcing edits to core billing whenever a new tax jurisdiction was added.

Extracted a TaxCalculator port and InvoiceRepository interface owned by the billing domain (DIP/SRP). Each regional tax rule became an independent implementation registered behind the abstraction (OCP), while read-only reporting consumers depended only on a slim InvoiceSummaryReader interface (ISP).

Lesson: SOLID turns a single-file tangle of business rules and I/O into testable policy modules with explicit extension seams.
  • SRP means one reason to change (one stakeholder/actor), not one method per class.
  • Prematurely splitting every class behind an interface adds indirection without reducing coupling when only one implementation exists.
Pause & reason: where would you draw the boundary?▼
  • Which distinct business actors could force this class to change for unrelated reasons?
  • Does any subclass violate a precondition, postcondition, or invariant assumed by callers of its parent type?
  • Are high-level domain policies importing concrete database, HTTP, or filesystem libraries directly?
  • Which methods on this interface are irrelevant or throwing UnsupportedOperationException for some implementers?

Design Patterns / Stage 02

Creational Patterns & Object Lifecycle.

Calling new directly scatters concrete class names and multi-step setup logic across callers. Factory Method delegates single-product instantiation to subclasses or creator hooks; Abstract Factory produces coherent families of related objects that must match (e.g., UI widgets or cloud storage + KMS clients); and Builder separates step-by-step configuration from validation so immutable objects are never observed partially initialized.

ChoiceWhat it buysWhat it costs
Factory MethodDecouples caller from concrete product class. Simple extension hook for creating one product type.Can lead to parallel creator class hierarchies if overused.
Abstract FactoryGuarantees compatible families of objects are created together. Swaps entire provider suites at startup or configuration time.Adding a new product type requires updating the factory interface and every concrete family.
BuilderEliminates telescoping constructors with many optional parameters. Validates cross-field invariants once in build() and returns an immutable instance.Extra builder boilerplate for simple value objects with 2-3 fields.

Enforce invariants at build() time

Validate mutually dependent fields (such as minConnections <= maxConnections or non-empty TLS cert when mTLS is enabled) inside build() so invalid configurations fail fast before entering runtime.

Beware hidden global state in Singletons

Classical static Singletons create hidden dependencies and cross-test contamination. Prefer dependency-injected single-instance lifecycles managed by the application composition root.

Order platform / Multi-cloud storage client family and HTTP client configuration

Multi-cloud storage client family and HTTP client configuration.

A data pipeline needed to switch seamlessly between AWS (S3BlobStore + SqsQueue) and GCP (GcsBlobStore + PubSubQueue), while each HTTP client required 12 optional timeout, retry, and TLS settings.

An Abstract Factory (CloudProviderFactory) ensured S3 was never paired with PubSub by accident, while a fluent HttpClientConfig.Builder validated that connectTimeout < requestTimeout and produced an immutable config object.

Lesson: Use Abstract Factory to enforce family compatibility and Builder to guarantee valid, immutable configuration.
Pause & reason: where would you draw the boundary?▼
  • Can a caller construct this object in a half-configured or inconsistent state before calling all setters?
  • Do multiple objects need to match a specific environment or provider family without mixing implementations?
  • Is a static Singleton hiding dependencies that should be passed explicitly through constructors?
  • Would a simple static factory method (e.g., Money.of(amount, currency)) suffice instead of a full Factory hierarchy?

03
Design Patterns / Stage 03

Structural Patterns: Adapters & Decorators.

Structural patterns assemble objects into larger, flexible structures. Adapter translates an external or legacy interface into the contract your domain expects without polluting domain types. Decorator wraps an object implementing the same interface to layer orthogonal capabilities—compression, buffering, caching, metrics, or retries—at runtime instead of creating a combinatorial explosion of subclasses (CachedBufferedEncryptedStream).

Object Adapter over Class Adapter

Wrapping the adaptee via composition (Object Adapter) works with interfaces, final classes, and runtime-injected instances, whereas multiple-inheritance Class Adapters lock you to a single concrete parent.

Decorator preserves transparency; Proxy controls access

Both wrap the same interface, but Decorator stacks composable enhancements chosen by the caller, whereas Proxy governs lifecycle, lazy loading, access control, or remote dispatch transparently.

Facade simplifies subsystems without hiding escape hatches

A Facade offers a clean high-level entry point over noisy multi-step subsystems while still allowing advanced callers to access underlying components when needed.

Order platform / Composable HTTP client middleware and legacy payment SDK adaptation

Composable HTTP client middleware and legacy payment SDK adaptation.

An e-commerce backend needed to wrap outgoing REST calls with optional retry, rate-limit metrics, and response caching, while integrating a legacy vendor SDK whose method signatures used XML strings and error codes.

Wrapped the vendor SDK in an Object Adapter implementing the domain's PaymentGateway interface so XML parsing stayed isolated. Implemented RetryClient, MetricsClient, and CachingClient as Decorators around HttpClient, letting each integration compose only the layers it needed.

Lesson: Compose orthogonal behaviors with Decorators and isolate foreign APIs behind Adapters to avoid subclass explosion and model leakage.
  • Decorator ordering matters: placing a CachingDecorator outside a RetryDecorator caches final results, whereas placing Retry outside Caching retries cache misses.
  • Deeply nested decorator stacks can make stack traces and debugging harder if decorators are not named clearly.
Pause & reason: where would you draw the boundary?▼
  • If we have 3 orthogonal features (logging, caching, encryption), how many subclasses would inheritance require vs Decorators?
  • Where is the boundary that prevents a third-party SDK's types and exceptions from leaking into domain logic?
  • What breaks if two Decorators in this pipeline are applied in the reverse order?
  • Are we using a Proxy for access/lifecycle control or a Decorator for caller-chosen feature composition?

Design Patterns / Stage 04

Behavioral Patterns: Strategy, Command & Template.

When business rules branch on type codes (if/elif/switch repeated across files), adding a new variant forces edits everywhere. Strategy extracts each algorithm behind a shared interface so it can be swapped at runtime or injected per tenant. Command reifies an action and its parameters as an object—enabling queueing, scheduling, auditing, and undo/redo. Template Method fixes an invariant multi-step skeleton in a base class while delegating specific steps to hooks.

ChoiceWhat it buysWhat it costs
Strategy (Composition)Swappable at runtime per request or tenant. Each algorithm is independently testable with zero base-class coupling.Callers or a registry must select the right strategy.
Template Method (Inheritance)Enforces an invariant step ordering in one place. Eliminates duplicated boilerplate around setup/teardown.Binds variants at compile time via subclassing; harder to mix and match steps.
Command (Reified Invocation)Supports persistent queues, retries, undo logs, and macro batching. Decouples the invoker from knowing how the receiver executes the work.Requires serializable payloads and inverse state snapshots if undo is needed.
Order platform / Dynamic freight pricing and undoable document editor operations

Dynamic freight pricing and undoable document editor operations.

A logistics engine had a 400-line if/else block calculating shipping rates across Ground, Air, ColdChain, and Hazmat carriers, while an internal route planner needed multi-step undo/redo for dispatchers.

Replaced the conditional tree with a ShippingRateStrategy map keyed by carrier mode, allowing new carrier rules to be added as isolated classes. Modeled dispatcher edits (AssignDriver, ReorderStop) as Command objects pushed onto an undo/redo stack with inverse execute/undo methods.

Lesson: Use Strategy to eliminate branching over interchangeable algorithms, and Command when invocations themselves must be queued, logged, or reversed.
Pause & reason: where would you draw the boundary?▼
  • Are the same switch/if-else branches over a mode or type enum duplicated across multiple methods?
  • Does the algorithm need to change dynamically at runtime, or is the outer workflow skeleton truly fixed?
  • Do we need to serialize, queue, rate-limit, audit, or undo individual operations?
  • In languages with first-class functions, would passing a lambda/function type replace a single-method Strategy class cleanly?

Design Patterns / Stage 05

Behavioral Patterns: Observer, Mediator & Visitor.

Direct references between collaborating components create N-squared coupling webs. Observer decouples a state-changing subject from an open set of listeners, though strong references without explicit unsubscription cause the Lapsed Listener memory leak. Mediator centralizes complex multi-widget or multi-actor coordination into one hub so peers never reference each other directly. Visitor uses double dispatch to add new operations (e.g., type-checking, codegen, serialization) across a stable AST or element hierarchy.

Prevent the Lapsed Listener memory leak

When a long-lived subject holds strong references to short-lived observers, garbage collection cannot reclaim dead UI views or sessions. Always pair subscribe() with explicit unsubscribe(), RAII/disposable tokens, or weak references.

Keep Mediators from becoming God Objects

A Mediator should coordinate interaction rules between colleagues without absorbing each colleague's internal domain logic.

Visitor trades type extensibility for operation extensibility

Adding a new operation (new Visitor) is trivial, but adding a new concrete Element class requires updating every Visitor interface.

Order platform / Fixing a memory leak in an order-book UI and coordinating checkout form fields

Fixing a memory leak in an order-book UI and coordinating checkout form fields.

A trading dashboard leaked 1.2 GB of heap per hour because closed chart panels remained registered on the long-lived MarketFeed subject, while a checkout form had 6 widgets directly mutating each other's enabled/disabled state.

Returned an AutoCloseable Subscription handle from MarketFeed.subscribe() and used WeakReference cleanup for dropped listeners, eliminating the Lapsed Listener leak. Replaced peer-to-peer widget callbacks with a CheckoutFormMediator that evaluated coupon, shipping, and tax rules in one place.

Lesson: Observer decouples publishers from subscribers only when subscription lifetimes are bounded; Mediator tames N-to-N peer spaghetti.
Pause & reason: where would you draw the boundary?▼
  • If an observer outlives its UI screen or request scope, what mechanism guarantees its subscription is released?
  • Are N components calling each other directly in a mesh that a single Mediator could simplify?
  • Is the set of element types stable while operations grow frequently (favoring Visitor), or do new element types arrive constantly?
  • Could synchronous Observer callbacks trigger re-entrant loops or block the subject's critical path?

Design Patterns / Stage 06

Concurrency & Threading Patterns.

Ad-hoc thread spawning (new Thread() per request) exhausts OS stack memory and context-switches CPUs into thrashing. Thread Pools bound concurrency and amortize thread creation; Producer-Consumer pipelines use bounded blocking queues to absorb bursts and apply backpressure when consumers fall behind; and Future/Promise compositions chain non-blocking async stages while propagating cancellation and timeouts.

Never use an unbounded queue in Producer-Consumer

An unbounded queue hides consumer slowdowns until heap memory is exhausted (OOM). Use a bounded BlockingQueue with an explicit rejection or backpressure policy (CallerRuns, drop-oldest, or HTTP 429).

Separate CPU-bound and I/O-bound Thread Pools

Running blocking socket I/O on a small CPU-sized fork-join pool starves compute tasks. Isolate blocking I/O onto dedicated pools or virtual threads/async event loops.

Avoid lock-ordering deadlocks and nested Future blocking

Calling Future.get() inside a worker pool whose tasks submit subtasks to the same pool causes thread-pool starvation deadlock. Chain callbacks (thenCompose) or use separate executors.

Order platform / Eliminating thread-pool starvation in an async image-processing service

Eliminating thread-pool starvation in an async image-processing service.

An upload service used a single shared 32-thread pool where parent tasks called Future.get() on child thumbnail tasks submitted to the same pool. Under burst load, all 32 threads blocked waiting for queued child tasks that could never run.

Split ingestion and thumbnail rendering into two dedicated pools connected by a bounded ArrayBlockingQueue (capacity 500) with CallerRuns backpressure, and replaced blocking Future.get() chains with non-blocking CompletableFuture composition and per-stage timeouts.

Lesson: Bounded queues, pool isolation, and non-blocking Future composition prevent thread starvation and memory exhaustion under load.
  • Read-Write locks improve concurrency only when reads vastly outnumber writes and critical sections are non-trivial; otherwise lock overhead or writer starvation hurts throughput.
  • Every async Future/Promise chain needs a timeout and cancellation hook so abandoned requests do not leak work.
Pause & reason: where would you draw the boundary?▼
  • What happens to heap memory if producers emit 10x faster than consumers for 5 minutes?
  • Could a task on this thread pool block waiting for another task queued on the exact same pool?
  • Are blocking I/O calls sharing an executor with latency-sensitive CPU or event-loop threads?
  • How does cancellation propagate if the upstream caller disconnects before the Future completes?

Design Patterns / Stage 07

Enterprise Integration Patterns (EIP).

Enterprise Integration Patterns standardize how asynchronous systems transform, route, and correlate messages across process boundaries. Pipes and Filters chain independent, stateless transformation stages over message channels; Content-Based Routers inspect headers or payloads to dispatch messages to specialized handlers; Splitters break composite batches into individual items; and Aggregators reassemble correlated replies using a correlation ID and completion timeout.

Ingress Pipe & Schema FilterValidates envelope schema, assigns a correlation ID, and rejects malformed payloads to a Dead-Letter Channel.
→
Content-Based RouterInspects message attributes (region, priority, eventType) to route to the appropriate downstream channel.
→
Splitter & Parallel FiltersDecomposes batch orders into per-item messages for independent enrichment and validation.
→
Stateful AggregatorCorrelates enriched items by correlation ID, emits the assembled result, and expires incomplete batches on timeout.

Aggregators require durable state and expiry timeouts

If item 3 of 5 never arrives, an in-memory aggregator without a completion timeout leaks memory forever. Persist partial groups and emit partial/failed notifications on TTL expiry.

Wire Tap and Dead-Letter Channel make pipelines debuggable

A Wire Tap copies messages to an audit/observability channel without altering the main flow, while a Dead-Letter Channel quarantines poison messages so they do not block healthy consumers.

Order platform / Decoupling a multi-partner customs & fulfillment pipeline

Decoupling a multi-partner customs & fulfillment pipeline.

A cross-border commerce platform needed to validate, enrich, split by warehouse, and reassemble multi-vendor shipments, but a single monolithic processor stalled whenever one carrier API slowed down.

Refactored the flow into Pipes and Filters over Kafka topics: an enrichment filter normalized addresses, a Content-Based Router dispatched hazardous vs standard items to separate carrier queues, a Splitter fanned out per-warehouse picklists, and a Redis-backed Aggregator with a 30s timeout consolidated tracking numbers.

Lesson: EIP primitives let each stage scale, retry, and quarantine poison messages independently while preserving end-to-end correlation.
  • Every Splitter/Aggregator pair must preserve a unique correlation ID and sequence count across retries.
  • Idempotent receivers are mandatory because at-least-once messaging channels can redeliver the same message.
Pause & reason: where would you draw the boundary?▼
  • Can each Filter stage be deployed, scaled, and unit-tested using only its input and output message schemas?
  • What happens to an Aggregator's memory if 1% of split child messages are permanently lost?
  • Where do unparseable poison messages go so they do not trigger infinite retry loops?
  • How does an operator trace a single business request across 5 asynchronous EIP channels?

Theory & Tips and Tricks

Practical heuristics & interview traps

  • 01Domain principle: Patterns are not abstraction trophies; they are targeted seams for isolating what changes from what stays invariant, from in-memory object graphs to asynchronous message pipelines.
  • 02End-to-end lesson: Each pattern solves a specific structural or operational problem—lifecycle validation, vendor isolation, behavioral swapping, or concurrency bounding.
  • 03Failure check — Slow Webhook Endpoint Starves Checkout Workers: A tenant's webhook server stalls for 30 seconds per request. Without bounded queues and pool isolation, notification retries exhaust the shared application thread pool and freeze synchronous invoice charges. Recovery: Isolate webhook delivery behind an EIP Content-Based Router feeding a dedicated bounded Producer-Consumer worker pool with per-request timeouts and a Dead-Letter Channel for repeated failures.

The decision framework

01

What exact axis of change or coupling are we trying to isolate?

Introduce a pattern only when concrete variation, lifecycle complexity, or dependency direction demands an abstraction seam.

02

Can composition (Strategy, Decorator, Adapter) replace inheritance here?

Object composition avoids fragile base-class hierarchies and allows behaviors to be combined or swapped at runtime.

03

Are object invariants enforced at construction time?

Use Builders or factory methods so invalid, half-initialized objects cannot exist in the domain.

04

Are concurrency and messaging boundaries explicitly bounded?

Every Producer-Consumer queue, Thread Pool, and EIP Aggregator needs finite capacity, timeouts, and backpressure or dead-letter handling.

05

Is the added indirection paying for itself in testability and clarity?

Delete speculative factories or single-implementation interfaces that obscure simple code paths.

What to take away

Good architecture is a set of justified decisions.

Effective design patterns are pragmatic seams, not ceremony. Ground your code in SOLID dependency direction, favor composition over inheritance, enforce invariants at construction, and bound every concurrency and integration channel.
