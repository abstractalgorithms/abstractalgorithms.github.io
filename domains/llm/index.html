Large Language Models (LLM)
Systems & Inference.

Serving Large Language Models in production fails when treated like stateless CPU microservices: autoregressive decoding is strictly GPU HBM memory-bandwidth bound, unpaged KV caches waste 60–80% of VRAM via fragmentation, and static request batching stalls fast users behind 2,000-token generations. Engineering high-throughput LLM gateways requires separating compute-bound Prefill from memory-bound Decode, paging KV-cache blocks (PagedAttention), caching shared system prefixes via radix trees, and enforcing deterministic schema + prompt-injection guardrails.

The idea to keep with you

When architecting production LLM inference systems, separate compute-bound prefill from HBM-bandwidth-bound decode with continuous iteration-level batching and paged KV-cache blocks so GPU utilization scales without blowing Time-To-First-Token (TTFT) or tail inter-token latency.

Prefill vs. Decode, Arithmetic Intensity & KV-Cache VRAM Math.

Why this matters: Calculate exact GPU HBM memory and bandwidth limits for autoregressive Transformer inference.

During Prefill of a 4,000-token prompt, the GPU multiplies [4000, d_model] matrices in parallel—achieving high arithmetic intensity (FLOPs per byte read from HBM). During Decode, batch size B=1B = 1B=1 multiplies [1, d_model] vectors: the GPU reads all model weights (e.g., 140 GB for a 70B FP16 model) from HBM just to produce one token.

On an NVIDIA H100 (3.35 TB/s HBM3 bandwidth), reading 140 GB of weights takes $140 / 3350 \approx 42\text{ ms}$ minimum per token—leaving Tensor Cores 95% idle unless you batch B=64–128B = 64\text{–}128B=64–128 sequences together.

KV-Cache Sizing Formula: For a Llama-style 70B model (80 layers, 8 GQA KV heads, 128 head_dim, FP16 = 2 bytes): KV per token=2×80×8×128×2 B=327,680 B≈320 KB/token\text{KV per token} = 2 \times 80 \times 8 \times 128 \times 2\text{ B} = 327,680\text{ B} \approx 320\text{ KB/token}KV per token=2×80×8×128×2 B=327,680 B≈320 KB/token A single 32,768-token session consumes $10.5\text{ GB}$ of VRAM just for its KV cache.

STAGE 02 · CORE PRIMITIVES & MEMORY MANAGEMENTcore

PagedAttention Block Tables & Radix-Tree Prefix Caching.

Why this matters: Share immutable system-prompt KV blocks across requests via copy-on-write radix trees.

Inspired by OS virtual memory paging, PagedAttention splits each sequence's KV cache into fixed-size blocks (e.g., 16 tokens per block) mapped through a block table—eliminating external fragmentation and internal over-reservation.

In agentic and RAG workloads, 85% of prompt tokens are identical across requests (system instructions, JSON tool schemas, few-shot examples). RadixAttention (Prefix Caching) hashes token block prefixes into a radix tree in GPU HBM: when a new request shares a 3,000-token system prompt, it links directly to existing read-only KV blocks with reference counting—cutting TTFT by 5x–10x and saving prefill FLOPs.

STAGE 03 · LATENCY ACCELERATION & QUANTIZATIONcore

FP8/INT4 Weight Quantization & Speculative Decoding.

Why this matters: Break the single-request HBM bandwidth wall using low-bit weights and draft-verify token speculation.

Because Decode is memory-bandwidth bound, shrinking model weights from 16-bit (FP16) to 8-bit (FP8 on H100) or 4-bit (AWQ/GPTQ INT4) halves or quarters HBM bytes transferred per token—nearly doubling single-stream token generation speed.

Speculative Decoding (EAGLE / Medusa / Draft Model): A tiny draft model (or multi-head MTP predictor) guesses the next γ=5\gamma = 5γ=5 tokens autoregressively in ~4 ms, and the target 70B model verifies all 5 tokens in one parallel forward pass (identical arithmetic cost to 1 decode step). Using lossless rejection sampling, the output distribution is mathematically identical to greedy/nucleus sampling from the 70B model alone, yielding 2.0x–2.8x faster TPOT.

STAGE 04 · DETERMINISTIC GUARDRAILS & KV-CACHE SIZERcore

Constrained FSM JSON Decoding & KV-Cache Capacity Calculator in Python.

Why this matters: Guarantee 100% schema-valid JSON outputs and prevent GPU VRAM OOM via exact KV-cache admission control.

Prompting an LLM with 'Please output valid JSON' still fails 2–5% of the time on escaped quotes or trailing commas. Constrained Decoding compiles a JSON Schema / Regex into a Finite State Machine (FSM) and masks out invalid vocabulary logits (-inf) before softmax at every token step—guaranteeing 100% syntactic schema compliance.

from dataclasses import dataclass

@dataclass(frozen=True)
class KvCacheBudget:
    bytes_per_token: int
    max_concurrent_sequences: int
    total_kv_gb: float

def calculate_kv_cache_capacity(
    total_gpu_vram_gb: float,
    model_weights_gb: float,
    num_layers: int,
    num_kv_heads: int,
    head_dim: int,
    kv_bytes_per_elem: int = 2,  # 2 for FP16/BF16, 1 for FP8
    avg_seq_len_tokens: int = 8192,
    vram_utilization_cap: float = 0.90,
) -> KvCacheBudget:
    usable_vram_bytes = int(total_gpu_vram_gb * vram_utilization_cap * (1024**3))
    weights_bytes = int(model_weights_gb * (1024**3))
    available_kv_bytes = usable_vram_bytes - weights_bytes
    if available_kv_bytes <= 0:
        raise ValueError("Model weights exceed usable GPU VRAM budget")

    bytes_per_token = 2 * num_layers * num_kv_heads * head_dim * kv_bytes_per_elem
    bytes_per_seq = bytes_per_token * avg_seq_len_tokens
    max_seqs = available_kv_bytes // bytes_per_seq

    return KvCacheBudget(
        bytes_per_token=bytes_per_token,
        max_concurrent_sequences=max_seqs,
        total_kv_gb=round(available_kv_bytes / (1024**3), 2),
    )
DISAGGREGATED LLM SERVING

Separating Compute-Bound Prefill GPUs From Bandwidth-Bound Decode GPUs

Engineering Decision Framework
Problem
How to keep interactive chat Time-Per-Output-Token (TPOT) under 30 ms while serving mixed 500-token and 16,000-token requests.
Naive Solution
Mix long 16K-token prefills into the same GPU batch loop as active decode requests with no chunking.
Why It Fails
A single 16K prefill monopolizes the GPU for 300–500 ms, freezing token streaming for every active user on that GPU.
Alternatives
Compare unchunked mixed batching, Chunked Prefill (512-token slices), and Disaggregated Prefill/Decode pools.
Engineering Decision
Enable Chunked Prefill (slicing long prompts into 512-token chunks piggybacked onto decode steps) on single-node deployments, and separate Prefill vs. Decode GPU pools at multi-node scale.
Trade-Offs
Caps decode jitter under 30 ms TPOT in exchange for slightly higher scheduler complexity or KV transfer bandwidth.

Prompt-Injection Sandboxing, Cascaded Model Routing & When Not to Use an LLM.

Why this matters: Defend production LLM endpoints against injection/exfiltration and avoid paying GPU costs for deterministic tasks.

Defense-in-Depth Guardrails:

  1. Input Shield: Fast lightweight classifier + heuristic scanner blocking jailbreaks and PII leaks.
  2. Data-Plane Isolation: Wrap retrieved RAG/tool outputs in escaped XML tags (<untrusted_context>) with explicit system instructions.
  3. Output Verifier: Constrained JSON schema decoding + regex/PII egress filter + deterministic citation verification.

Multi-Model Cascaded Routing: Do not send classification, entity extraction, or simple FAQ queries to a 70B/405B frontier model. Route 70% of structured/simple traffic to a fine-tuned 8B model (10x cheaper, 4x faster) and escalate only multi-step reasoning or low-confidence responses to the flagship model.

When NOT to Use an LLM: Never use a generative LLM for deterministic arithmetic, exact SQL aggregations, regex validation, or low-latency (< 5 ms) hot-path routing—deterministic code and classical ML classifiers are 1,000x faster, cheaper, and 100% reproducible.
