💡 Executive Summary

Follow one system-design interview from a vague multi-leader proposal through the exact anomalies, isolation levels, replication models, shard-key choices, and consensus rules that make the design defensible.

🎯 System Scenario & Requirements

System Goal

Give a learner a precise vocabulary so an interview answer and a production design name the same anomaly, the same isolation guarantee, and the same replication or consensus trade-off.

Functional Requirements

  • Map each term to one mechanism: snapshot, quorum, shard key, or leader election.
  • State what an operator can observe when the guarantee holds or fails.

Constraints & Assumptions

  • The feed is globally distributed and accepts writes in more than one region.
  • Default isolation on the primary is Read Committed unless the design raises it.
  • Cross-shard transactions are not free and must be called out explicitly.

Detailed Architectural Analysis

Deep Dive: Stage 1 — How Vocabulary Breaks System Design Interviews (and Production Systems)

You are 35 minutes into a system design interview. You have just proposed multi-leader replication for a globally distributed social feed. The interviewer pauses and says: "Your design doesn't account for write skew. Walk me through how you'd prevent it."

A nod is not an answer. Write skew is a specific interleaving: two transactions each read an overlapping predicate, each decides the constraint still holds, and each writes a different row. No single-row lock fires. Both commits succeed. The predicate the product promised — at least one doctor on call, one seat left, one canonical post id — is now false.

That is different from a dirty read (you saw an uncommitted write that later vanished), a lost update (two read-modify-writes hit the same row and one overwrote the other), and "eventual consistency" (replicas have not caught up yet). If the answer uses those phrases interchangeably, the interviewer cannot tell which mechanism you would actually ship.

The decision in this stage is to freeze the design and name the anomaly before picking a database feature. The component that must change is the candidate's next sentence, not the diagram. The observable output is a sentence of the form: "Two writers can each pass the on-call check and update different rows; I will close that with Serializable isolation or a shared lock row, not with multi-leader replication."

The same failure shows up in production incident reviews. A ticket titled "inconsistent data" hides three different bugs and three different fixes. Vocabulary is the routing key for the rest of this scenario.

Deep Dive: Stage 2 — Consistency Anomalies: The Ways Transactions Can Lie to You

Once the anomaly has a name, classify it against the catalog. Each row below is a different lie the database can tell a transaction, and each lie has a different business symptom.

AnomalyWhat the transaction observesWhat the product ships
Dirty readA value that another transaction has not committed and may roll backA decision based on state that never existed
Non-repeatable readTwo selects of the same row in one transaction return different committed valuesA branch taken on a number that is already stale
Phantom readA range query grows or shrinks inside one transactionA constraint check that passed on an incomplete set
Read skewTwo related rows are read from different points in timeA transfer that looks balanced in neither account
Write skewTwo transactions each pass a shared check and write non-overlapping rowsDouble booking, empty on-call roster
Lost updateTwo read-modify-writes of the same row; one write disappearsA balance incremented once instead of twice
Dirty writeA second transaction overwrites an uncommitted first writeA row whose history cannot be reconstructed

The on-call example is write skew, not a lost update. Alice reads count(on_call) = 2 and sets her own row to off. Bob does the same for his row. Neither update touches the other's row, so Read Committed and snapshot isolation both allow both commits. A later count(on_call) returns 0.

The decision is to pick one row from that table and refuse the others. The component behavior is the interleaving above. The observable output is a query after both commits that shows the invariant false — proof you named the right anomaly.

Deep Dive: Stage 3 — Isolation Levels: PostgreSQL's Six-Way Dial Between Safety and Speed

Isolation is the dial that decides which rows from the previous table are still possible. PostgreSQL does not implement Read Uncommitted; that setting is promoted to Read Committed. The levels you actually choose among are Read Committed, Repeatable Read, and Serializable.

Read Committed takes a new snapshot per statement. Two selects of balance inside one transaction can return 100 and then 50 if another transaction committed in between. That is a non-repeatable read. It is the default, and it is the right default for single-statement work. It does not protect check-then-act logic.

Repeatable Read takes one snapshot for the transaction. The same row keeps the same value, and PostgreSQL's MVCC visibility rules also hide phantoms that were inserted after the snapshot. It still allows write skew, because each transaction's snapshot cannot see the other transaction's concurrent write to a different row.

Serializable in PostgreSQL is serializable snapshot isolation. Transactions still run on snapshots, but the engine records read-write dependencies. When Alice's read depends on a row Bob writes and Bob's read depends on a row Alice writes, one commit is aborted with SQLSTATE 40001. The survivor stays. The aborted session must retry; on retry it sees the updated count and refuses to go off call.

BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM on_call
  WHERE shift = current_date AND status = 'active';
-- application: proceed only when count > 1
UPDATE on_call
   SET status = 'off'
 WHERE doctor_id = $1 AND shift = current_date;
COMMIT;

The decision is not "turn Serializable on for the whole pool." Ordinary single-row updates stay at Read Committed, often with SELECT … FOR UPDATE on the row they will change. Only the multi-row predicate — on-call count, remaining seats across a cabin, inventory across warehouses — moves to Serializable, and the service retries 40001 with backoff.

Oracle's label "Serializable" is snapshot isolation. It does not give you this abort. If the design says "we set serializable," the observable output must name the engine: a PostgreSQL 40001 in the logs, or an explicit lock row if the engine cannot detect the cycle.

Deep Dive: Stage 4 — Replication Models and the Consistency Spectrum Across Databases

Isolation answers what one node lets concurrent transactions see. Replication answers what another node is allowed to serve after the client was told the write succeeded.

Single-leader replication gives one node the right to order writes and ships that log to followers. Synchronous replication waits until a configured set of followers has the record before the leader acks the client. A failover then has the write. Asynchronous replication acks from the leader alone. It is faster, and a crash can drop the tail that followers never received. Readers on a lagging follower can also miss the write; that is replica lag, not write skew.

Multi-leader replication lets more than one node accept writes, usually one leader per region. Conflicts are inevitable when the same key is written in two places. Last-write-wins is a policy for discarding one of them, not a proof that both happened. Use it only when the product can say which value may disappear.

Leaderless replication (the Dynamo family) lets any replica accept a write and reconciles with quorums and read repair. A write quorum W and a read quorum R with W + R > N overlap, so a read sees the latest write if no node is missing from both sets. If W + R ≤ N, a read can miss a write that succeeded. That is a different knob from isolation level, and interview answers that mix them are answering two questions with one word.

The decision for the social feed's authoritative post record is single-leader synchronous replication (or a quorum that overlaps reads and writes). Multi-leader is allowed only for data whose conflict rule is written down. The observable output is: after the client sees success, a promoted follower or a quorum read returns the new post, and replication lag is a separate metric from serialization failures.

Deep Dive: Stage 5 — Partitioning and Sharding: Distributing Data Across Nodes

Replication copies the same data so you can survive a node loss and spread reads. Sharding splits the data so no single node holds every row or absorbs every write. The shard key is the column the router uses to choose a node. It is expensive to change later because every row may have to move.

A useful key has high cardinality, spreads writes, matches the query you run most often, and does not change for the life of the row. user_id on a timeline does that: one user's posts live together, and writes from many users spread out. created_at looks high-cardinality and still sends every insert to the newest shard. country_code is easy to explain and creates a permanent hot shard for the largest country.

Range sharding keeps order, so a between-query can stay on one shard, and it creates a hot tail when keys increase monotonically. Hash sharding spreads sequential keys and turns every range scan into a scatter-gather. Consistent hashing keeps most keys in place when you add a node: about 1/N of the data moves, especially with virtual nodes. A directory (shard map) lets you place a celebrity key on its own node, and the map itself becomes a dependency that must stay available.

The decision is to shard the feed by user_id (or a compound tenant plus user key) with hashing or consistent hashing, and to serve "latest across everyone" from a separate index rather than from a scatter on the primary table. The observable output is a timeline read that touches one shard, plus a dashboard query whose plan shows N shard round-trips if someone forgot the key.

Deep Dive: Stage 6 — Consensus and Leader Election: Deciding Who Gets the Final Say

Sharding and replication both assume someone knows which node is the leader and which shard owns a key. If two nodes both believe they are leader, you get two histories. Clocks do not settle that argument: "latest timestamp" is another last-write-wins policy, and clocks drift.

Consensus protocols (Raft is the one most teams can walk through) elect one leader per term and replicate a log. A candidate needs votes from a majority. A log entry is committed only after a majority has stored it. A partition that holds only a minority cannot elect a leader and cannot commit. Clients in that partition see errors and retry. That unavailability is the mechanism that prevents split brain.

The same rule applies to the shard map. If the map is updated by a single node without a quorum, a stale router can send writes to a shard that no longer owns the key. Leader election for the database and quorum agreement for the map are the same idea: a majority must agree before the configuration is real.

Do not implement "whoever heartbeats last wins" in application code. The decision is to put leader election and the shard map on a consensus system (the database's own Raft group, or a dedicated one) and to surface the term and commit index. The observable output is one leader per term, a commit index that does not move backwards, and a minority partition that rejects writes instead of accepting a second log.

📊 System Outcome & Trade-offs

End-to-End Result: The same vocabulary now drives both the interview answer and the production controls: name the anomaly, pick the isolation or replication rule that closes it, place data with a shard key that matches the query, and elect one leader with a quorum.

Observed User & Operator Behavior

User: Readers and writers see either a committed post that survives failover or an explicit retry, never a silent double-booking or a second history.

Operator: Dashboards show isolation aborts, replication lag, hot shards, and leader terms as separate signals instead of one 'consistency' alert.

Key Architectural Trade-offs

  • Serializable closes write skew but requires retry handling for SQLSTATE 40001.
  • Synchronous replication removes the lost-tail window and adds ack latency.
  • A query-aligned shard key makes the primary path local and pushes secondary access patterns onto indexes.
  • Quorum consensus prevents split brain and refuses writes when a majority is unreachable.

🔄 Evaluated Alternatives

Stay on Read Committed and lock the predicate

For a single hot row, SELECT FOR UPDATE is enough and avoids serialization retries. It does not close write skew across two different rows unless you also lock a shared sentinel row.

Multi-leader with last-write-wins

Cuts cross-region write latency but turns conflicts into silent overwrites. Use it only when the product can name the conflict rule and the data that may be discarded.

⚠️ Failure Modes & Degraded Operation

Write skew under snapshot isolation

Both sessions commit. The shared invariant is false only after both commits. Detection is a constraint query after the fact, or a 40001 abort if the transaction ran at Serializable.

Hot shard from a monotonic key

The newest range absorbs every insert. Cluster throughput collapses to that one node's capacity. Mitigation is a hashed or compound key, or pre-split ranges with monitoring on the tail.

Minority partition during leader election

The minority cannot gather a quorum, so it rejects writes. Clients retry against the majority leader. Accepting those writes would fork the log.

✅

Key learnings

  • Name the anomaly before you name the feature. Write skew, lost update, replica lag, and split brain are four different bugs.
  • Read Committed and Repeatable Read do not close write skew. PostgreSQL Serializable does, and the application must retry 40001.
  • Replication chooses who may ack a write. Sharding chooses which node stores it. Consensus chooses who is allowed to decide either of those facts.
  • A shard key is a query-locality decision. A monotonic key with range sharding creates a hot shard no amount of replication will fix.
  • A minority partition that still accepts writes has already forked history. Quorum refusal is the correct degraded mode.
