Stage 1 — Key Concepts: Embeddings and Vector Similarity

  • When you search for "refund policy" in a document, a keyword search returns results containing those exact words.
  • But what if your policy document says "money-back guarantee"?
  • An embedding is a list of numbers — a high-dimensional vector (e.g., 1,536 numbers for OpenAI's text-embedding-3-small ) that encodes the semantic meaning of a piece of text.
  • Similar meanings produce vectors that point in similar directions in that space.

Stage 2 — Step 1: Chunking and Embedding Your Documents

  • Before storing, split your documents into chunks and convert each to an embedding.
  • Overlap (typically 10–20% of chunk size) preserves context across chunk boundaries.

Applies vector-embeddings-and-similarity to the decision above.

from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,    # ~500 tokens: self-contained enough for focused retrieval without losing sentence coherence
    chunk_overlap=50,  # 10% overlap ensures sentences split at boundaries appear in both adjacent chunks
)
chunks = splitter.split_documents(docs)

Observable outcome: Overlap (typically 10–20% of chunk size) preserves context across chunk boundaries.

Stage 3 — Step 2: Storing and Searching with ChromaDB

  • ChromaDB stores embeddings locally (persisted to disk).
  • FAISS is an alternative — in-memory only, faster for pure search, no built-in persistence.

Applies llm-agents-and-langgraph to the decision above.

from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    persist_directory="./chroma_db",
)

# Retrieve top-4 most relevant chunks for a query
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})

Observable outcome: FAISS is an alternative — in-memory only, faster for pure search, no built-in persistence.

Stage 4 — Deep Dive: The RetrievalQA Chain in LangChain

  • The chain type="stuff" injects all retrieved chunks into one prompt.
  • For larger context windows, use "map reduce" (summarize each chunk separately, then combine) or "refine" .
  • 🔬 Internals RAG pipelines split documents into overlapping chunks (typically 512–1024 tokens with 10–20% overlap), embed each chunk with a sentence encoder, and store embeddings in a vector index.
  • At query time, the query is embedded and the top-k chunks are retrieved by approximate nearest-neighbor search (HNSW or IVF).

Applies sorting-and-searching-algorithms to the decision above.

from langchain.chains import RetrievalQA
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    chain_type="stuff",   # "stuff" = inject all context at once
    retriever=retriever,
    return_source_documents=True,
)

result = qa_chain.invoke({"query": "What is our refund policy?"})
print(result["result"])
print(result["source_documents"])

Stage 6 — Real-World Applications of RAG

  • RAG powers document Q&A systems across every industry.
  • The core pattern is identical — the differences are in which documents get indexed and what guardrails are required.
  • Hybrid search in production: Pure semantic search sometimes misses exact terms — product codes, error numbers, names.
  • Production systems often combine keyword search (BM25) with vector search, then rerank with a cross-encoder model.
