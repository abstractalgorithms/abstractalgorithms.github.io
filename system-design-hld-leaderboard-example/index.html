💡 Executive Summary

Real-time leaderboards for 10M+ active users require an in-memory ranking engine.

🎯 System Scenario & Requirements

System Goal

Real-time leaderboards for 10M+ active users require an in-memory ranking engine.

Actors & Components

  • Architecture diagram in the source
  • Edge Traffic Ingress
  • Stateless Microservices
  • Datastore Infrastructure
  • API Gateway
  • Domain Service
  • Redis Cache
  • Transactional DB

Functional Requirements

  • TLDR: Real-time leaderboards for 10M+ active users require an in-memory ranking engine.
  • Redis Sorted Sets (ZSET) are the industry standard, providing $O(\log N)$ updates and rank lookups via an internal Skip List data structure.
  • Relational databases fail at this scale because calculating rank is an $O(N)$ operation (counting rows with higher scores) that becomes a bottleneck during peak traffic spikes.

Constraints & Assumptions

  • Critical Failure Mode — The Redis Restart Without Persistence: If the Redis instance restarts and AOF (Append Only File) persistence was not enabled, the entire ZSET is lost.
  • Re-hydrating 100M entries from Postgres requires streaming all score records, computing each player's cumulative score, and executing 100M ZADD commands.

In-Memory Caching & Event Loop Architecture

↗

Caching stores high-frequency read data in fast RAM instead of slow disk/network databases. Redis achieves sub-millisecond QPS by operating a single-threaded event loop paired with OS epoll I/O multiplexing, completely eliminating thread locking contention.

  • Just sort the table by score and pick the top rows.
  • However, at scale, there is a massive difference between sorting and ranking .
  • Sorting: Ordering a set of elements.

Deep Dive: Stage 4 — Mechanics: The Logic of Score Updates

  • The core mechanic of a modern leaderboard is the Accumulation and Fan-out of score events.
    • Incremental Updates: Instead of overwriting the score, we often send "score deltas" (e.g., +50 points).
  • This allows for easier concurrent updates.
    • Tie-Breaking: To ensure deterministic ranking, we use a composite score.

Deep Dive: Stage 6 — High-Level Design: The Ranking Pipeline

  • The architecture separates the fast-path ranking engine from the durable-path storage.
  • The Ranking Pipeline above separates two concerns that must never share a bottleneck: the write path (score ingestion via Kafka → Score Processor → Redis ZSET) and the read path (Leaderboard API → Redis ZREVRANK).
  • The Game Server never writes directly to Redis — it goes through the Ingestion Service and Kafka, ensuring durability before the score is considered committed.
  • If Redis is unavailable, the API falls back to Postgres for correctness at the cost of higher latency.
