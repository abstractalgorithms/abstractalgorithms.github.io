Backend for Frontend (BFF): Tailoring APIs for UI

The One-Size-Fits-All API Problem

🎯 System Scenario & Requirements

System Goal

A "one-size-fits-all" API causes bloated mobile payloads and underpowered desktop dashboards.

Actors & Components

  • Client Layer
  • BFF Layer
  • Core Services
  • Data & Persistence
  • Mobile Client
  • Web Client
  • Mobile BFF
  • Web BFF

Functional Requirements

  • TLDR: A "one-size-fits-all" API causes bloated mobile payloads and underpowered desktop dashboards.
  • The Backend for Frontend (BFF) pattern solves this by creating a dedicated API server for each client type — the mobile BFF reshapes data for small screens, the web BFF aggregates for dashboards.
  • You have a mobile app and a web dashboard.

Constraints & Assumptions

  • BFF is not always the right answer: Code duplication risk: If mobile and web BFFs share 80% of logic, refactor the common parts into shared service clients — not into both BFFs.

Deep Dive: Stage 1 — BFF Basics: One Backend Per Frontend

  • A generic REST API returns the same response shape to every caller.
  • That works for simple apps but breaks down when clients have radically different needs: - Mobile apps run on limited bandwidth and battery.
  • They need compact, pre-computed responses.
    • Web dashboards need rich, aggregated data combining multiple domain objects.

Deep Dive: Stage 2 — One API Layer per Client Type

  • The BFF pattern introduces a thin, client-specific server between each frontend and the shared microservices: Key properties: - Tight coupling by design: The Mobile BFF is owned by the mobile team.
  • When the app screen changes, the BFF changes with it.
    • Data shaping: The BFF projects the microservice response to exactly what the client needs.
    • Protocol bridging: Microservices may speak gRPC internally.

Deep Dive: Stage 3 — Request Flow Through a BFF

  • The request lifecycle from client to microservices flows through the BFF: Each step adds value: 1.
  • Auth validation — the BFF verifies the token before hitting any upstream service.
  • Parallel upstream calls — fan out to N services simultaneously to minimize latency.
  • Response aggregation — merge the N responses into one JSON object.

Deep Dive: Stage 4 — Deep Dive: What Lives Inside a BFF

  • A BFF is not a full microservice.
  • It is a lightweight orchestration layer.
  • Typical responsibilities: A BFF should contain no business logic .
  • If you find yourself writing pricing rules or fraud detection inside a BFF, that code belongs in a separate service.

Deep Dive: Stage 5 — Deep Dive: Parallel Aggregation: The Common BFF Pattern

  • The most useful thing a BFF does is fan out requests and merge them: Three upstream calls run in parallel (~80 ms total instead of sequential ~240 ms).
  • The client gets a single clean response in one round trip.
