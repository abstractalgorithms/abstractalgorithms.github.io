System Design Data Modeling and Schema Evolution: Query-Driven Storage That Survives Change

Scenario context

In system design interviews, data modeling is where architecture meets reality. A good model starts from query patterns, chooses clear entity boundaries, defines indexes deliberately, and includes a schema evolution path so the system can change without breaking reads and writes.

TLDR: If your schema does not match your dominant queries, no amount of caching will save the design.

Observable outcome: Add new nullable columns or new tables (expand).

Database Indexing: B-Trees vs LSM-Trees

↗

Database indexes turn linear O(N) table scans into logarithmic O(log N) lookups. B-Trees optimize point & range reads; LSM-Trees turn random writes into sequential disk writes.

In-Memory Caching & Event Loop Architecture

↗

Caching stores high-frequency read data in fast RAM instead of slow disk/network databases. Redis achieves sub-millisecond QPS by operating a single-threaded event loop paired with OS epoll I/O multiplexing, completely eliminating thread locking contention.
