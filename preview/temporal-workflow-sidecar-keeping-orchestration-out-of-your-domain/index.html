Temporal Workflow Sidecar: Keeping Orchestration Out of Your Domain

TLDR: Keep orchestration logic separate from your domain code by running Temporal workflows in a dedicated sidecar service. This preserves Clean Architecture layers, simplifies unit tests, and gives you a single point for retry & monitoring. 🚀

⚠️ The Gotcha

When you sprinkle Temporal SDK calls (workflow.execute, workflow.schedule) directly inside your domain services, you violate the Dependency Rule of Clean Architecture: the inner layers now depend on an outer framework. This tight coupling makes unit testing hard (you must mock Temporal), hampers refactoring, and blurs the boundary between business logic and orchestration concerns.

🛠️ The Sidecar Solution

Create a Temporal Orchestrator Service—a thin, stateless sidecar that:

  1. Exposes a clean port (e.g., a gRPC or HTTP API) for your domain services to request workflow starts.
  2. Uses the Temporal SDK to orchestrate workflows, delegating domain work to activities that call back into your domain via ports/adapters.
  3. Keeps all Temporal dependencies outside the core domain layer, so the domain remains pure and testable.

📦 Architecture Kit Diagram

⚖️ Trade‑offs

  • Pros: Clear separation, easier unit tests, single point for retry/backoff logic, independent scaling.
  • Cons: Extra deployment unit, more operational overhead, latency added by inter‑service calls.

🚀 Production Tips

  • Keep the sidecar stateless; let Temporal handle state.
  • Use dependency injection in the sidecar to swap activity implementations for testing.
  • Expose metrics (e.g., workflow counts, error rates) from the sidecar to a monitoring stack.
  • Run the sidecar in the same pod as the Temporal worker if you want minimal latency, but still expose a clean port for the domain.

By isolating Temporal orchestration in a sidecar, you maintain the integrity of Clean Architecture while still leveraging Temporal’s powerful workflow capabilities.
