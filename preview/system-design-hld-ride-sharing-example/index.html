System Design HLD Example: Ride-Sharing (Uber/Lyft)

TLDR: A ride-sharing platform is a high-velocity geospatial matching engine. Drivers stream GPS coordinates every 5 seconds into a Redis Geospatial Index. When a rider requests a trip, the Matching Service executes a GEORADIUS query to find the closest available drivers. A distributed Trip State Machine ensures transactional consistency (no double-matching), while WebSockets provide the real-time "car on map" experience.

1. Use Cases & Requirements

Imagine it’s New Year's Eve in New York City. At 12:05 AM, one million people open their ride-sharing apps simultaneously. In the background, 50,000 drivers are moving through the city, sending GPS updates every few seconds.

Every ride request triggers a database range query. With 100,000 concurrent requests, the database's CPU hits 100%, lock contention skyrockets, and the "Nearest Driver" query that usually takes 10ms now takes 30 seconds. By the time a driver is matched, they’ve already moved three blocks away.

The challenge is maintaining a high-velocity, in-memory index of moving objects that can be queried hundreds of times per second without falling behind.

Actors & Journeys

  • Rider: Requests a ride, views ETAs, tracks the driver in real-time, and pays for the trip.
  • Driver: Updates availability (Online/Offline), broadcasts location, and accepts/rejects trip requests.
  • System Admin: Monitors surge pricing, platform health, and fraud detection.

Scope Boundaries

  • In-Scope: Real-time driver tracking, geospatial matching, trip lifecycle management, and live position streaming.
  • Out-of-Scope: Driver background checks, vehicle maintenance scheduling, and airport queuing queues.

Functional Requirements

  • Real-time Location Stream: Drivers must broadcast GPS coordinates every 5 seconds.
  • Geospatial Matching: Efficiently find available drivers within a 2km radius of a rider.
  • Trip Management: Manage the full lifecycle of a ride (Request $\rightarrow$ Match $\rightarrow$ Pickup $\rightarrow$ Dropoff).
  • Live Tracking: Stream the driver's current position to the rider's map with low latency.

Non-Functional Requirements (NFRs)

  • Ultra-Low Matching Latency: A rider should see a matching confirmation in under 2 seconds.
  • High Write Availability: Handle 100k+ GPS updates per second without dropping pings.
  • Strict Consistency for Matching: One driver must never be matched to two riders simultaneously.
  • Scalability: Handle city-wide surges without cascading failures.

Components & Responsibilities

  1. Location Ingestion Service: Processes 5s driver GPS location broadcasts and pushes them to Redis and Kafka.
  2. Redis Geospatial Cache: Maintains the real-time localized index of available drivers.
  3. Matching Service: Queries the Geo Index and coordinates matching rules.
  4. Trip Management Service: Orchestrates trip lifecycle states and commits them durably.
  5. WebSocket Gateway: Manages persistent stateful connections to push location updates to riders.

Key Takeaway: Run location streaming in memory and persist state machine transitions to database storage.

4. Detailed Design: Location Ingestion & Geohashing

A traditional relational database with a B-tree index cannot execute two-dimensional range queries efficiently under heavy load. To solve this, the Location Service leverages Geohashing.

The Mechanics of Geohashing

Geohashing partitions the Earth's surface into a hierarchical grid of cells. Each grid cell is represented by a unique base-32 string.

  • The Prefix Property: Points situated close to each other in physical space share a common geohash prefix. For instance, 9q8yy and 9q8yz are both within San Francisco.
  • Redis Geo Indexing: Redis encodes longitude and latitude into a 52-bit integer score inside a Sorted Set using a space-filling Hilbert curve.
  • Range Scan: Searching for nearest drivers involves locating the rider's geohash cell, identifying its 8 adjacent grid neighbors, and scanning the sorted set range. This turns a complex geometry intersection into a fast, log-time index lookup.

Key Takeaway: Geohashing transforms a costly O(N) spatial geometry problem into a highly performant O(log N) string matching lookup.

5. Detailed Design: Matching Engine & Distributed Locking

A core correctness invariant is that a driver must never be matched to two riders at the same time. Double-booking is a catastrophic user experience failure.

Distributed Locking Flow

  1. Candidate Discovery: The Matching Service queries GEORADIUS to find available drivers within a 2km radius.
  2. Lock Acquisition: For each candidate, the service attempts to acquire an atomic distributed lock in Redis:
    const acquired = await redis.set(`driver_lock:${driverId}`, 'locked', 'NX', 'PX', 15000);
  3. Conflict Resolution: If the lock attempt fails (returns null), another Matcher instance is matching this driver. The engine skips to the next candidate.
  4. Transaction Commit: Once the lock is acquired, the trip record is written to Postgres, changing the driver status to ON_TRIP.
  5. Lock Release: The distributed lock is released immediately after the SQL write commits.

Key Takeaway: Use Redis distributed locks for short-lived concurrency guards, committing the final trip state durably in Postgres.

6. Detailed Design: WebSocket Gateway Fleet & Real-Time Updates

Pings from active drivers must be streamed live to the matched rider's map display to provide the expected real-time tracking experience.

Gateway Scalability

At a scale of 1 million concurrent riders, maintaining WebSocket connection states on a single instance is impossible. We scale this horizontally:

  • Stateless Gateways: A fleet of WebSocket gateway nodes holds open TCP connections with client apps.
  • Redis Pub/Sub Backplane: When the Location Service receives a driver update, it publishes the coordinate packet to Redis Pub/Sub on channel trip:ws:${riderId}.
  • Unicast Delivery: Whichever gateway instance holds the connection for riderId receives the subscription message and pushes it down the WebSocket to the client.

Key Takeaway: Decouple connection state from processing logic to allow horizontal scaling of WebSocket gateways.

7. Database Schema & Data Models

Relational databases handle durable state transactions, while Redis sharding handles rapid geospatial index reads.

Relational Tables (PostgreSQL)

Driver Profile Table

  • driver_id (UUID, PK)
  • status (ENUM: OFFLINE, AVAILABLE, ON_TRIP)
  • vehicle_type (VARCHAR: UberX, UberXL, Black)
  • rating (DECIMAL)
  • city_id (VARCHAR)

Trip Ledger Table

  • trip_id (UUID, PK)
  • driver_id (UUID, FK to Driver)
  • rider_id (UUID, FK to Rider)
  • status (ENUM: REQUESTED, MATCHED, EN_ROUTE, ARRIVED, IN_PROGRESS, COMPLETED, CANCELLED)
  • pickup_lat / pickup_lng (DECIMAL)
  • requested_at / completed_at (TIMESTAMP)

8. Design for NFR: Redundancy & High Availability

To achieve 99.99% system availability, our design must avoid single points of failure (SPOFs) at every tier.

Redundancy Strategy

  1. Multi-Region Deployment: Active-active deployment across multiple cloud regions, with users routed to the nearest region via geo-routing DNS.
  2. Redis Sharding by City ID: Drivers in San Francisco never match riders in New York. Sharding the geospatial index by city_id ensures that a cache failure in one city has no impact on other regions.
  3. Durable PostgreSQL Master-Replica Groups: Postgres operates with a primary node for write transactions and read-replicas for historical lookups. We use synchronous replication for hot-failover standby nodes.

Key Takeaway: Shard geospatial indexes by city and replicate transactional databases to isolate regional faults.

9. Design for NFR: Scaling under Load & Surge

Holiday surges (like New Year's Eve) require special scaling patterns to prevent database CPU starvation.

Surge Mechanisms

  • Event Streams (Kafka): Ingest pings into a Kafka topic first. If the Redis write rate spikes, Kafka buffers the pings, allowing consumer instances to apply updates to Redis at a stable rate.
  • Surge Pricing (Uber H3 Index): We divide the city into hexagonal sectors using Uber's open-source H3 index. If matching requests in a hexagon outpace available drivers, the Pricing Service increases the surge multiplier.
  • Write Coalescing: If driver pings arrive faster than the cache can handle, consumer processes can drop stale pings, writing only the latest coordinate update for each driver ID.

Key Takeaway: Use event streaming logs as buffers to shield in-memory database grids from transactional write spikes.

10. Technology Choices & Trade-offs

Choosing the right components requires balancing performance against consistency constraints.

Transport Protocols: WebSockets vs SSE vs HTTP Polling

  • WebSockets: Full-duplex transport, low overhead. Perfect for high-frequency location broadcasts.
  • Server-Sent Events (SSE): Simple unidirectional server-to-client updates. Great for riders tracking a match.
  • HTTP Polling: Stateless but high overhead. Avoid at scale.

Spatial Storage: Redis vs PostGIS vs Cassandra

  • Redis ZSET: In-memory, sub-millisecond lookups. Reaches single-threaded write limits quickly.
  • PostGIS: Rich query syntax, disk-backed. Too slow for 100k writes/sec.
  • Cassandra: Extremely fast writes, but lacks native range-based geospatial scanning support.

Key Takeaway: Trade database rich queries for in-memory speed (Redis) on high-frequency paths.

11. Advanced Follow-ups: Scheduled Rides & Carpooling

After establishing the core real-time matching system, interviewers often ask how to extend the system to handle scheduled rides and pooling.

Scheduled Rides

Scheduled rides require deferred matching. We store requests in Postgres with a status of PRE_SCHEDULED. A scheduler job polls the database every minute, selecting rides starting in the next 10 minutes and pushing them to the active Matching Service queue.

Carpooling

Matching groups of riders with overlapping routes requires vector calculations. The system:

  1. Computes route directions (vectors) for active rider requests.
  2. Groups riders with similar angles and destinations.
  3. Runs the Traveling Salesperson Problem (TSP) algorithm to find the optimal pickup/dropoff sequence.

Key Takeaway: Extend the core architecture by layering specialized modules (like route segment caches) on top of the matching engine.

12. Architecture Limits & Mitigations

No architecture scales infinitely without trade-offs. Let's analyze the limits of our design.

Structural Bottlenecks & Mitigations

  • Replication Lag: Read replicas of our PostgreSQL database can fall behind the primary node by a few hundred milliseconds. If the Matching Service queries a replica for driver status, it might read stale data.
    • Mitigation: Read driver availability and active locks exclusively from the Primary PostgreSQL node (or Redis). Use read replicas only for historical analytics and billing lookups.
  • GPS Teleportation (Stale Map Car): GPS updates arrive only once every 5 seconds. If client maps rendered raw pings directly, the car icon would jump or teleport across the screen.
    • Mitigation: Implement client-side dead reckoning. The client app interpolates vehicle movement using the last known heading and velocity to render a smooth path.

Key Takeaway: Use client-side interpolation to hide network latency and update intervals from the user.

13. Real-World Implementations: Uber, Lyft, and DiDi

Understanding how real-world companies implement these patterns validates our design choices.

Production Implementations

  • Uber DISCO: Uber's location indexer (DISCO - Driver Indexing Service for City Operations) shards the world using a custom hexagon grid (H3 index). This operates similarly to our sharded Redis Geo Index, dividing cities into distinct shards.
  • Lyft's Streaming Buffer: Lyft streams location updates through Kafka, using a streaming engine to aggregate telemetry. This aligns with our design's Kafka-to-Redis ingestion path.
  • DiDi's Micro-Grids: DiDi handles massive scale by nesting macro-cells inside micro-cells. This two-tier hierarchy reduces search spaces and improves geospatial lookup efficiency.

Key Takeaway: Global scales require multi-tiered sharding to prevent index write bottlenecks.

15. Final Summary Cheat Sheet

Architecture Cheat Sheet

  • Location Ingestion: Mobile App $\rightarrow$ API Gateway $\rightarrow$ Kafka $\rightarrow$ consumer writes to Redis Geo Index.
  • Matching Flow: Rider requests match $\rightarrow$ execute GEORADIUS $\rightarrow$ acquire Redis NX lock $\rightarrow$ write trip record to Postgres $\rightarrow$ notify driver.
  • Live Tracking Stream: Location Service updates $\rightarrow$ publish to Redis Pub/Sub channels $\rightarrow$ WebSocket gateways relay updates to clients.

Failure Checklist

  • [x] Stale MATCHED status? Background job times out matches after 90 seconds.
  • [x] Redis instance fails? Replicate using master-replica standby groups.
  • [x] Postgres database bottlenecks? Shard database keys by rider ID.

Common Pitfalls

  • Writing driver coordinates directly to disk on every ping. This will quickly bottleneck database disk IO.
  • Greedily matching the closest driver without locking. This causes race conditions and double-booking errors.
