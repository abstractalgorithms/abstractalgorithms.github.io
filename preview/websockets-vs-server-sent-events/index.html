How do apps send real-time notifications? | WebSockets vs. Server-Sent Events (SSE)

TLDR: Real-time application updates can be delivered via WebSockets or Server-Sent Events (SSE). WebSockets provide a low-latency, full-duplex TCP connection suitable for bi-directional communication, while SSE utilizes standard HTTP to stream mono-directional server-to-client updates efficiently.

The Real-Time Problem: Bypassing HTTP Polling

Standard HTTP is built on a strict Request-Response lifecycle. The client initiates a TCP connection, sends an HTTP request, the server processes it, returns a response, and the connection is closed (or kept alive for subsequent requests). The server cannot initiate communication or push data to the client without a prior request.

Historically, applications achieved real-time updates using two techniques:

  • Short Polling: The client repeatedly sends HTTP requests to the server at fixed intervals (e.g., every 2 seconds) to check for new data. This is extremely inefficient, consuming server CPU cycles and network bandwidth on empty responses.
  • Long Polling (Comet): The client sends a request, and the server holds the request open until new data is available. Once data is returned, the client immediately opens a new long-poll request. While more efficient than short polling, it still incurs connection renegotiation overhead.

To support true real-time experiences—such as chat applications, financial tickers, and collaborative dashboards—developers use dedicated real-time protocols: WebSockets and Server-Sent Events (SSE).

WebSockets: Full-Duplex Bi-Directional Messaging

WebSockets is a distinct protocol (running over TCP) designed for low-latency, bi-directional, full-duplex communication.

How it works: The Upgrade Handshake

A WebSocket connection begins as a standard HTTP request. The client sends a handshake request containing specific upgrade headers:

GET /chat HTTP/1.1
Host: api.abstractalgorithms.dev
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

If the server supports WebSockets, it responds with an HTTP 101 Switching Protocols status:

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Once the handshake is complete, the HTTP protocol is discarded. The underlying TCP socket remains open, and both the client and server can transmit data frames concurrently.

Key Characteristics of WebSockets

  • Full-Duplex: Both client and server can send data simultaneously over the same connection.
  • Message-Based API: Unlike raw TCP streams, WebSockets transmits messages as distinct frames (text or binary).
  • Custom Protocol: Runs over port 80 (ws://) and 443 (wss://), requiring firewalls and proxies to support the WebSocket protocol upgrade.

Server-Sent Events (SSE): Mono-Directional Streaming

Server-Sent Events (SSE) is a standard web technology that allows a server to stream text-based data to clients over a persistent HTTP connection.

How it works: The Event Stream

Unlike WebSockets, SSE does not upgrade the connection to a new protocol. It uses standard HTTP. The client opens a request, and the server responds with a specific MIME type: text/event-stream.

GET /stream HTTP/1.1
Host: api.abstractalgorithms.dev
Accept: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

The server keeps this connection open indefinitely. When new data is available, it writes an event block to the connection buffer:

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

event: notification
data: {"message": "You have a new follower!"}

event: ticker
data: {"symbol": "AAPL", "price": 175.50}

The browser's native EventSource API parses this stream automatically and triggers event callbacks.

Key Characteristics of SSE

  • Mono-Directional: Data flows only from the server to the client. The client cannot send data over the stream; it must use separate standard HTTP requests (e.g., POST) for client-to-server writes.
  • Text-Based: Only text data (typically JSON) can be sent; binary streaming is not natively supported.
  • Standard HTTP: Runs over standard HTTP/HTTPS ports without requiring custom protocol proxies.

🧠 Deep Dive: Connection Management and Heartbeats

In a high-scale real-time system, managing connection state is the primary challenge. Because TCP connections can drop silently (e.g., when a mobile device switches towers), both WebSockets and SSE need mechanisms to detect dead connections and free server resources.

WebSockets Ping/Pong

The WebSocket protocol includes built-in control frames for connection checks:

  • The server periodically sends a Ping frame.
  • The client must immediately respond with a Pong frame.

If the server sends a Ping and does not receive a Pong within a timeout window, it closes the TCP socket and frees the connection memory.

SSE Heartbeats

Because SSE uses standard HTTP, it does not have custom Ping/Pong control frames. Instead, the server must write dummy data periodically (e.g., an empty comment line : keep-alive) to the event stream. If the network interface drops, the client's socket will eventually timeout, and the EventSource API will automatically initiate a reconnection attempt.

⚖️ Trade-offs and Failure Modes

WebSockets Trade-offs

  1. Stateful Load Balancing: WebSocket servers are stateful. Once a connection is established, the client remains pinned to that specific server instance. Scaling requires using sticky sessions or a message broker (like Redis Pub/Sub) to coordinate messages across multiple WebSocket nodes.
  2. Proxy and Firewall Blocks: Some corporate firewalls and reverse proxies block or terminate non-standard HTTP connections, causing WebSocket upgrades to fail.

SSE Connection Limits

A major limitation of SSE is the browser connection limit. Under HTTP/1.1, browsers limit the number of concurrent connections to a single domain to 6. If a user opens 6 tabs of your website, and each tab opens an SSE connection, the 7th tab will stall.

Mitigation: This limit is bypassed when using HTTP/2, which multiplexes multiple streams over a single TCP connection, allowing hundreds of concurrent SSE streams.

🧭 Decision Guide: Selecting the Real-Time Protocol

Use this guide to choose the appropriate protocol for your real-time updates:

  • Choose WebSockets if:
    • You are building a bi-directional, high-frequency interactive application (e.g., chat apps, multiplayer games, collaborative editors).
    • You need to stream binary payloads efficiently.
    • You can manage the scaling complexity of stateful socket clusters.
  • Choose Server-Sent Events (SSE) if:
    • You only need mono-directional server-push capability (e.g., push notifications, live dashboards, news feeds).
    • You want automatic reconnection handling out of the box.
    • You want to work over standard HTTP/2 without proxy upgrade issues.

Authentication, Resume, and Delivery Semantics

Authenticate before committing server resources to a long-lived connection. Browsers cannot freely attach arbitrary headers to the native WebSocket constructor, so applications commonly use a secure same-site cookie, a short-lived single-use ticket obtained over HTTPS, or a token in the negotiated subprotocol. Avoid long-lived bearer tokens in query strings because URLs leak into logs and monitoring systems.

Token expiry must have an explicit policy: close and reconnect with a refreshed credential, or support a narrowly defined re-authentication message. Authorization must still be checked for every subscribed channel because a connection authenticated as one user must not subscribe to another tenant’s events.

SSE includes the last received event ID during reconnection. Persist a bounded event log so the server can replay after that ID:

app.get('/events', authenticate, async (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache, no-transform');
  res.setHeader('X-Accel-Buffering', 'no');

  const cursor = req.get('Last-Event-ID');
  for (const event of await eventStore.after(req.user.id, cursor, 500)) {
    res.write('id: ' + event.id + '\\nevent: ' + event.type + '\\ndata: ' + JSON.stringify(event.data) + '\\n\\n');
  }
  const unsubscribe = bus.subscribe(req.user.id, event => {
    res.write('id: ' + event.id + '\\ndata: ' + JSON.stringify(event.data) + '\\n\\n');
  });
  req.on('close', unsubscribe);
});

WebSockets provide transport, not exactly-once delivery. If messages matter, add sequence IDs, acknowledgements, idempotency keys, and a replay window. Reconnect with exponential backoff plus jitter so a regional recovery does not trigger millions of simultaneous handshakes.

Backpressure and Slow Consumers

A server that produces faster than a client consumes will accumulate buffered messages. Set a maximum outbound buffer per connection. For replaceable updates such as cursor positions, coalesce to the newest value. For durable events, disconnect a slow consumer and let it resume from the event log. Never permit an unbounded per-socket queue.

SSE uses normal HTTP flow control, but application buffers and proxies can still grow. WebSocket libraries expose buffered-byte counts or drain signals; monitor and enforce them. Compression reduces bandwidth for repetitive text but consumes CPU and can increase memory per connection, so enable it only after load testing.

Scaling Beyond One Server

Connections are stateful, but event ownership should not live only in process memory. Store presence and subscription metadata in a bounded shared system and distribute events through Redis Pub/Sub, Redis Streams, Kafka, NATS, or another broker chosen for the required durability.

Pub/Sub is appropriate when disconnected clients may miss replaceable events. Streams or Kafka are better when consumers must resume and replay. Sticky sessions reduce reconnect movement but do not eliminate the need for external event distribution or recovery.

Proxy and Deployment Configuration

Configure idle timeouts above the heartbeat interval and disable response buffering for SSE. Some intermediaries close quiet connections, so send lightweight heartbeat comments. Historical browser limits of roughly six connections per origin primarily affect HTTP/1.1; HTTP/2 multiplexing changes that constraint, though server and intermediary stream limits still apply.

For deployment, stop accepting new connections, advertise a reconnect delay, allow a bounded drain period, then close remaining sockets with a retryable reason. Without jitter, every client reconnects to the new fleet at once.

End-to-End Notification Example

For a notification feed, the write transaction stores the notification and an outbox event atomically. A relay publishes the event to a durable stream. Realtime gateways deliver it to connected users; disconnected users retrieve it through the normal notifications API. The client deduplicates by notification ID and persists the last acknowledged cursor. This design keeps the database as the source of truth while realtime delivery remains an acceleration path.

Observability

Monitor concurrent connections, connection attempts and failures, authentication rejection, reconnect rate, connection duration, heartbeat timeouts, broker lag, fan-out latency, messages per connection, dropped or replayed events, outbound buffered bytes, and memory per 10,000 connections. Alert on reconnect rate and buffer growth before total connection count becomes critical.

Operator Field Note: Reconnect Storm After a Regional Recovery

When a region returns, clients often reconnect at the same instant. Handshakes, authentication, subscription restoration, and replay queries overload the recovering fleet. Apply randomized client backoff, admission limits, bounded replay batches, and gradual regional traffic restoration. Preserve the durable cursor so rejected clients can retry without losing events.

15-Minute Reliability Drill

  1. Restart every realtime gateway and verify clients reconnect with distributed jitter.
  2. Slow one client until it exceeds the buffer limit and confirm other clients remain healthy.
  3. Disconnect a user for five minutes and verify ordered, deduplicated replay.
  4. Expire a token mid-connection and confirm the documented re-authentication behavior.

Implementation Checklist

  • Choose SSE for server-to-client streams and WebSockets for true bidirectional interaction.
  • Define authentication, authorization refresh, heartbeat, reconnect, and resume behavior.
  • Bound connection count, outbound buffers, replay batches, and broker subscriptions.
  • Use sequence IDs and idempotent handlers for important events.
  • Configure proxy buffering, idle timeouts, draining, and HTTP version deliberately.
  • Test network changes, slow consumers, broker delay, and full-fleet restart.

📚 Lessons Learned

  • A persistent connection is not a durable message guarantee.
  • SSE simplifies one-way delivery and resume; WebSockets enable richer interaction at higher operational cost.
  • Backpressure and reconnect storms are capacity problems, not edge cases.
  • Keep durable state outside individual gateway processes.
  • Protocol choice should follow directionality, delivery, replay, and scale requirements.

📌 TLDR: Summary & Key Takeaways

  • Use SSE for notifications and live feeds when clients mainly receive events.
  • Use WebSockets for chat, games, and collaboration requiring frequent two-way messages.
  • Add authentication refresh, cursors, replay, deduplication, and bounded buffers explicitly.
  • Design and drill reconnect behavior before a fleet restart tests every client simultaneously.
