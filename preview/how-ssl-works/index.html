How SSL/TLS Works: The Handshake Explained

Scenario context

SSL (now TLS) secures data between your browser and a server. It uses Asymmetric Encryption (Public/Private keys) once — to safely exchange a fast Symmetric Session Key. Everything after the handshake is encrypted with the session key.

Stage 5 — Deep Dive: Session Keys, Forward Secrecy, and Performance

  • ECDH and Perfect Forward Secrecy (PFS) In TLS 1.3, the session key is derived via ECDHE (Elliptic Curve Diffie-Hellman Ephemeral).
  • "Ephemeral" means a fresh key pair is generated for every session and discarded after.
  • Perfect Forward Secrecy: Even if an attacker records encrypted traffic today and steals the server's private key tomorrow, they cannot decrypt past sessions — because the ephemeral ECDH keys are long gone.
  • TLS 1.2 without PFS (RSA key exchange): steal the private key → decrypt all stored traffic.

server {
    listen 443 ssl;
    server_name yourdomain.com;

    ssl_certificate     /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;

    # Enforce TLS 1.2 minimum; prefer TLS 1.3
    ssl_protocols TLSv1.2 TLSv1.3;

    # ECDHE ciphers only — ensures Perfect Forward Secrecy
    ssl_ciphers ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;

    # HSTS — tells browsers to always use HTTPS for the next year
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
}
