Cassandra Write Path & Tombstone Gotchas

TLDR: Cassandra turns deletes into special markers called tombstones. Excessive deletes lead to heavy tombstone scanning and GC stalls during reads.

📊 Visualizing the Gotcha

In Apache Cassandra, write operations avoid expensive random disk I/O by executing sequential appends. When a mutation is executed, Cassandra appends the mutation to a sequential CommitLog on disk for immediate durability and writes the updated row into an in-memory sorted structure known as a Memtable.

When the Memtable reaches capacity or age limits, Cassandra flushes its sorted contents directly to immutable disk files called SSTables (Sorted String Tables).

Because SSTables are strictly immutable once written, executing a CQL DELETE query cannot immediately modify or erase data stored inside existing SSTable files on disk. Instead, Cassandra handles deletions by inserting a specialized tombstone record containing a deletion timestamp marker into the Memtable.

⚖️ The Solution & Trade-offs

When a read query executes, the Cassandra coordinator must scan across multiple SSTables on disk and merge the latest values while filtering out tombstoned entries:

  • The Tombstone Pitfall: If your workload generates frequent updates, row deletions, or rapid TTL expirations on high-volume tables, read queries must scan through thousands of tombstone markers. This causes sudden CPU spikes, triggers TombstoneOverloadedException, and causes severe JVM stop-the-world garbage collection pauses.
  • Best Practice Solution: Avoid database anti-patterns that rely on frequent single-row updates or deletes. For time-series telemetry or logging workloads with automatic expiration, configure TimeWindowCompactionStrategy (TWCS) so entire SSTable files drop cleanly when their window expires without triggering tombstone scans.
