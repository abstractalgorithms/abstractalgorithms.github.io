System Design HLD Example: Distributed Rate Limiter

Scenario context

A distributed rate limiter protects APIs from abuse and "noisy neighbors" by enforcing request quotas across a cluster of servers. The core technical challenge is Atomic State Management—solved by using Redis Lua scripts to perform a "check-and-increment" operation in a single atomic step, preventing race conditions that would allow users to bypass their limits.

Stage 6 — Deep Dive: How Each Algorithm Works and When the Atomic Redis Pattern Is Required

  • Internals: How Redis Lua Scripts Provide Atomic Enforcement Across a Distributed Cluster Redis executes Lua scripts on its single-threaded event loop — the same loop that handles all GET, SET, INCR, and EXPIRE commands.
  • When a Rate Limiter Service instance sends a EVALSHA command with a Lua script, Redis processes it from start to finish without executing any other command in between.
  • This is not a transaction (which requires MULTI/EXEC and does not prevent interleaving of other clients' commands) — it is true atomicity at the command level.

In-Memory Caching & Event Loop Architecture

↗

Caching stores high-frequency read data in fast RAM instead of slow disk/network databases. Redis achieves sub-millisecond QPS by operating a single-threaded event loop paired with OS epoll I/O multiplexing, completely eliminating thread locking contention.

End-to-end outcome

After working through the stages, you should be able to explain:

  • The Policy Service Is as Critical as the Enforcement Engine.
  • Teams that hardcode rate limits in application configuration files spend hours debugging why limit changes require a full deployment.
    • A distributed rate limiter must use shared state (Redis) — not local per-server counters — to enforce limits correctly across a cluster of application servers.
    • Redis Lua scripts provide the atomic check-and-increment operation required to prevent race conditions where two concurrent requests both slip past a limit boundary.
