How do websites survive unexpected traffic spikes? | Load Balancing Explained

TLDR: Load balancing is the practice of distributing incoming network traffic across a cluster of backend servers to optimize capacity utilization, minimize latency, and ensure high availability. By acting as a reverse proxy, a load balancer prevents server saturation, handles SSL termination, and dynamically manages server pools via health checks.

The Architectural Problem: Handling Unexpected Traffic Spikes

Imagine it is 09:00 AM on a Friday, and a highly anticipated ticket sale goes live. Within seconds, millions of users hit the web application simultaneously. If all these requests are routed to a single application server, the server's CPU will spike, physical memory (RAM) will be exhausted, request queues will fill up, and the server will ultimately crash under the load.

To survive such traffic spikes, modern web architectures rely on Horizontal Scaling—adding more application servers to a pool. However, horizontal scaling is useless without a mechanism to distribute incoming requests across these servers. This is the primary function of a Load Balancer.

A load balancer acts as a reverse proxy and traffic cop at the entry point of your infrastructure. It intercepts incoming client requests, evaluates the current state of the backend server pool, and routes each request to the most appropriate server, optimizing resource utilization and preventing any single node from becoming a bottleneck.

Layer 4 vs. Layer 7 Load Balancing

Load balancers operate at different layers of the OSI model, primarily Layer 4 (Transport Layer) and Layer 7 (Application Layer). The choice between L4 and L7 significantly impacts performance, scalability, and routing capabilities.

Layer 4 (Transport Layer) Load Balancing

Layer 4 load balancers make routing decisions based solely on transport-level protocols (TCP/UDP). They do not inspect the application payload (e.g., HTTP headers or cookies).

  • How it works: The load balancer intercepts a TCP packet, evaluates the source and destination IP addresses and ports, and forwards the packet to a selected backend server using Network Address Translation (NAT).
  • Pros:
    • High Performance: Since the load balancer does not need to decrypt SSL/TLS or parse application payloads, it is extremely fast and consumes minimal CPU.
    • Simple Setup: Less configuration overhead, making it highly suitable for raw TCP traffic (e.g., database clusters or SMTP servers).
  • Cons:
    • No Content-Aware Routing: Cannot route traffic based on URL paths, HTTP headers, user-agents, or cookies.
    • No SSL Termination: The SSL/TLS handshake must be performed by each backend server, increasing CPU usage on the application nodes.

Layer 7 (Application Layer) Load Balancing

Layer 7 load balancers operate at the application level, parsing the full HTTP/HTTPS payload.

  • How it works: The load balancer terminates the client's HTTP/HTTPS connection, decrypts the TLS layer, inspects the headers, cookies, path, and body, and opens a new connection to the selected backend server.
  • Pros:
    • Content-Aware Routing: Can route requests dynamically (e.g., sending /static/* requests to a CDN or file server, and /api/* requests to an API microservice).
    • SSL Termination: Offloads the expensive cryptographic handshake from backend servers to the edge load balancer.
    • Security & Features: Supports header injection (e.g., X-Forwarded-For), rate limiting, WAF (Web Application Firewall) filtering, and sticky sessions via cookies.
  • Cons:
    • CPU & Memory Intensive: Inspecting payloads and handling cryptography requires substantial computing power.
    • Higher Latency: Parsing the full application layer adds a small latency overhead (usually 1-5ms).

Load Balancing Algorithms

Load balancers use specific algorithms to determine which backend server should handle an incoming request. The choice of algorithm depends on the nature of the workload and the server pool capacity.

1. Round Robin and Weighted Round Robin

  • Round Robin: The load balancer loops through the list of servers sequentially, sending each new request to the next server in line. It assumes all servers have equal capacity and all requests require equal processing time.
  • Weighted Round Robin: Assigns a capacity weight (e.g., 1 to 5) to each server. A server with a weight of 3 receives three times as many requests as a server with a weight of 1, allowing heterogeneous hardware configurations to coexist safely.

2. Least Connections and Weighted Least Connections

  • Least Connections: The load balancer tracks active TCP connections on each backend server. It routes the next incoming request to the server with the fewest active connections.
  • Weighted Least Connections: Combines the active connection count with the configured capacity weight of the servers, balancing load based on real-time execution stress.
  • Best Use Case: Workloads with long-lived transactions or heavy database queries where connection count is a reliable indicator of server load.

3. IP Hashing

  • IP Hashing: The client's IP address is hashed, and the hash value is mapped to a specific server in the pool.
  • Best Use Case: Stateful applications requiring session persistence (sticky sessions), where a client must repeatedly interact with the same backend server to maintain local memory state.
  • Cons: If a backend server goes offline, the hash ring changes, and all sessions are disrupted. Additionally, high-volume gateways (like corporate NATs) can cause uneven load distribution by grouping many clients under a single IP hash.

High Availability & Health Checks

A load balancer is a single point of failure (SPOF) if not configured correctly. To ensure high availability and prevent downtime, production systems use redundant clustering and passive health monitoring.

Active-Passive and Active-Active Clusters

  • Active-Passive Setup: Two load balancers share a virtual IP (VIP) using protocols like Keepalived or VRRP (Virtual Router Redundancy Protocol). The active node handles all traffic. It sends periodic heartbeats to the passive node. If the active node crashes, the passive node instantly assumes the VIP and continues routing traffic.
  • Active-Active Setup: Multiple load balancers are configured concurrently. DNS round-robin or Anycast routing distributes incoming traffic across the load balancers, sharing the workload and providing instant failover.

Health Checks

The load balancer must monitor the health of the backend server pool to avoid routing traffic to crashed instances. It runs periodic checks:

  • TCP Checks: Attempts to open a TCP socket connection on the server's port. If the connection fails, the server is marked offline.
  • HTTP Checks: Sends an HTTP GET request to a specific health endpoint (e.g., /health). If the server returns a non-200 status code or fails to respond within a timeout window, it is removed from the active pool.

NGINX Load Balancing Configuration

The following NGINX configuration demonstrates a Layer 7 Weighted Round Robin load balancer with health check failover.

http {
    # Define a logical upstream pool of servers
    upstream backend_pool {
        server 10.0.0.4:8080 weight=3 max_fails=3 fail_timeout=10s;
        server 10.0.0.5:8080 weight=1 max_fails=3 fail_timeout=10s;
        server 10.0.0.6:8080 backup; # Handles traffic only when others are down
    }

    server {
        listen 80;
        server_name api.abstractalgorithms.dev;

        location / {
            # Route all incoming requests to the upstream pool
            proxy_pass http://backend_pool;

            # Forward client metadata to backend instances
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        }
    }
}

🧠 Deep Dive: Connection Queuing and TCP Backlog Tuning

When a massive traffic spike hits the load balancer, the backend application servers may not be able to keep up, even with load balancing. In this scenario, how the load balancer and the OS manage the connection queue is critical.

When a client initiates a connection, the TCP handshake passes through two queues in the operating system:

  1. SYN Queue (Incomplete Connections): Stores connections that have received a SYN packet but have not yet completed the 3-way handshake (waiting for the client's ACK).
  2. Accept Queue (Completed Connections): Stores connections that have completed the handshake and are waiting for the application (e.g., NGINX, Spring Boot) to call accept().
Client ---- SYN ----> [ SYN Queue ]
Client <--- SYN-ACK -
Client ---- ACK ----> [ Accept Queue ] ---- accept() ----> Application

If the application is overloaded, the Accept Queue fills up. Once the queue is full (governed by the sysctl parameter net.core.somaxconn and the application's backlog setting), the OS will reject or silently drop incoming SYN packets. This results in clients experiencing connection timeouts.

A high-performance load balancer mitigates this by maintaining its own Connection Queue. It accepts TCP connections instantly at the edge and holds them in memory, feeding them to the backend servers only when they have capacity. This shields the backend application servers from TCP backlog saturation.

⚖️ Trade-offs and Architectural Challenges

Implementing load balancing introduces several design trade-offs:

  1. Increased Complexity: Instead of deploying a single application instance, you must manage multiple servers, configure the load balancer, setup VIP clustering, and synchronize deployment versions.
  2. Session State Management: In a multi-server setup, local in-memory sessions (like Java HTTP Sessions) will fail if a user's requests are routed to different servers. You must implement stateless architecture (e.g., JWT tokens) or distribute sessions to a shared cache (e.g., Redis).
  3. Data Consistency: Multiple servers writing to a single database can saturate the database layer, shifting the bottleneck from the application layer to the storage layer.

🧭 Decision Guide: Selecting the Right Load Balancer

Use this guide to choose the appropriate load balancing strategy for your system:

  • Choose a Layer 4 Load Balancer if:
    • You need maximum throughput and minimum latency (e.g., millions of packets per second).
    • You are load balancing database traffic (e.g., Postgres, MySQL clusters) or non-HTTP protocols.
    • You want to perform SSL termination directly on the backend nodes.
  • Choose a Layer 7 Load Balancer if:
    • You need path-based routing (e.g., /api to microservice A, /images to microservice B).
    • You want to centralize SSL termination and certificate management at the edge.
    • You need sticky sessions or HTTP cookie inspection.
    • You require rate limiting, header manipulation, or WAF protection at the ingress point.

A Load Balancer Is Not an Autoscaler

A load balancer distributes work across capacity that already exists. It cannot rescue a fleet whose instances are all saturated. Surviving a spike requires layers: CDN caching absorbs cacheable traffic; admission control rejects excess work; the load balancer routes accepted requests; bounded queues smooth short bursts; and autoscaling adds capacity after its detection and startup delay.

flowchart LR
  U[Users] --> E[CDN and edge cache]
  E --> G[Rate limit and admission control]
  G --> LB[Load balancer]
  LB --> A[Healthy app instances]
  A --> Q[Bounded async queue]
  A --> D[(Database and cache)]
  M[Metrics] --> AS[Autoscaler]
  AS --> A

If traffic jumps from 1,000 to 50,000 requests per second and 80% is edge-cacheable, the origin still receives 10,000 requests per second. If the existing fleet handles 4,000, the system must immediately shed or queue 6,000 while new instances warm. Scaling policies that react after five minutes are irrelevant to the first five minutes of the incident.

Overload Protection and Backpressure

  • Rate limits protect fairness per user, token, tenant, or IP.
  • Concurrency limits cap expensive in-flight work even when request rate looks modest.
  • Bounded queues absorb short bursts; unbounded queues convert overload into memory exhaustion and extreme latency.
  • Load shedding returns a fast 429 or 503 for optional work rather than timing out every request.
  • Circuit breakers stop calls to a failing dependency, but must not create synchronized retry storms.
  • Retry budgets allow only a small fraction of traffic to be retries and require exponential backoff with jitter.

Prefer explicit rejection to accepting work that cannot finish inside the client’s latency budget. A response produced after the client has timed out consumes capacity without delivering value.

Production Routing Details

Health checks should test readiness, not merely whether a process accepts TCP connections. Use consecutive-success and consecutive-failure thresholds so one slow probe does not flap a host in and out. When adding capacity, use slow start to ramp traffic while caches and connection pools warm.

During deployments, first mark an instance unready, stop new connections, and allow a bounded drain window. WebSockets and long requests require a specific drain policy. Sticky sessions can simplify local session state but produce uneven load and make failover harder; prefer external session storage when practical.

Layer 4 can pass TLS through to backends, while capable proxies may also terminate or proxy TLS depending on architecture. Layer 7 commonly centralizes termination and supports path, host, header, cookie, WAF, and rate-limit rules. The choice is about required visibility and control, not a universal TLS rule.

NGINX Example with Failure Bounds

upstream api_pool {
    least_conn;
    zone api_pool 64k;
    server api-1:8080 max_fails=3 fail_timeout=10s slow_start=30s;
    server api-2:8080 max_fails=3 fail_timeout=10s slow_start=30s;
    keepalive 64;
}

limit_req_zone $binary_remote_addr zone=per_ip:10m rate=20r/s;

server {
    location /api/ {
        limit_req zone=per_ip burst=40 nodelay;
        proxy_connect_timeout 2s;
        proxy_read_timeout 10s;
        proxy_next_upstream error timeout http_502 http_503;
        proxy_next_upstream_tries 2;
        proxy_pass http://api_pool;
    }
}

Retries are capped because retrying across many upstreams can multiply an outage. Non-idempotent requests should not be retried unless they carry an idempotency key and the backend implements it correctly.

Observability and Capacity Model

Track accepted and rejected request rate, active and queued connections, per-upstream latency, p95/p99 response time, 429/5xx rate, unhealthy-host count, retry volume, connection-pool saturation, instance CPU/memory, autoscaling lag, and dependency saturation. Break metrics down by route: one expensive endpoint can overload a fleet while aggregate CPU appears normal.

Capacity tests should identify the sustainable request rate at the latency SLO, not the point where the process crashes. Maintain headroom for one zone failing and for normal deployment drains.

Operator Field Note: Retry Storm During a Partial Failure

When one zone slows down, health checks may remain green while latency rises. Clients retry, the proxy retries again, and the remaining healthy instances receive several times the original traffic. First cap retries, shed optional endpoints, and remove demonstrably slow targets. Scale only after preventing request multiplication; otherwise new capacity can be consumed immediately by retries.

15-Minute Spike Drill

  1. Increase staging traffic tenfold in under one minute.
  2. Verify rate and concurrency limits reject excess work before queues grow without bound.
  3. Remove one zone and confirm the remaining capacity preserves the critical-route SLO.
  4. Add instances and measure readiness-to-first-traffic plus slow-start behavior.
  5. Confirm dashboards distinguish original requests from retries.

Implementation Checklist

  • Define per-route latency, error-rate, and concurrency budgets.
  • Configure active readiness checks with anti-flapping thresholds.
  • Bound connect/read timeouts, retries, queues, and drain duration.
  • Test CDN bypass, cache loss, one-zone failure, and autoscaling delay.
  • Use idempotency keys before retrying writes.
  • Ensure the database and cache scale limits match the application fleet.

📚 Lessons Learned

  • Load balancing distributes capacity; overload protection preserves it.
  • Autoscaling is delayed, so headroom and load shedding handle sudden spikes.
  • Health, slow start, and draining determine whether deployments remain available.
  • Retry multiplication can be more damaging than the original failure.
  • Measure sustainable throughput at the latency SLO, not maximum raw requests.

📌 TLDR: Summary & Key Takeaways

  • Combine CDN caching, admission control, load balancing, bounded queues, and autoscaling.
  • Use fast failure and backpressure when accepted work cannot finish on time.
  • Bound every timeout and retry, and drain instances deliberately.
  • Practice a sudden spike and a zone failure before launch-day traffic arrives.
