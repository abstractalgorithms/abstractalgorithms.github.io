Outbox Table Partitioning: Scaling Event Delivery Without Locking

TLDR: Partition your outbox table to avoid write contention and speed up event reads—just remember to keep partitions balanced and keep your cleanup job in sync! 🚀

📌 The Bottleneck Problem

You’re building a microservice that writes domain events into a single outbox table as part of a transaction. Under load, every write hits the same table, causing lock contention, slow commits, and a backlog of events for the publisher. The question is: how do you keep the outbox write fast while still guaranteeing reliable event delivery?

⚙️ Partitioning Strategy

Use table partitioning (PostgreSQL, MySQL, or a sharded NoSQL table) to spread writes across multiple physical segments. Common strategies:

StrategyHow it worksWhen to use
Hash‑by‑entityPartition key = hash(entity_id)Many small entities, even distribution
Time‑windowPartition key = date_trunc('hour', event_time)Temporal bursts, easy retention
Tenant‑IDPartition key = tenant_idMulti‑tenant SaaS with per‑tenant isolation

Example: PostgreSQL hash partition 

CREATE TABLE outbox (
  id          BIGSERIAL PRIMARY KEY,
  tenant_id   BIGINT NOT NULL,
  event_type  TEXT NOT NULL,
  payload     JSONB NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
) PARTITION BY HASH (tenant_id);

CREATE TABLE outbox_p0 PARTITION OF outbox FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE outbox_p1 PARTITION OF outbox FOR VALUES WITH (MODULUS 4, REMAINDER 1);
-- … up to p3

⚖️ Trade‑offs & Gotchas

FactorBenefitRisk
Write speedFewer locks per partitionSkewed partitions → hot spot
Read parallelismPublisher can poll multiple partitions concurrentlyComplexity of managing multiple partitions
CleanupDrop old partitions instead of deleting rowsMust coordinate cleanup with publisher to avoid missing events
Schema evolutionAdd columns to all partitionsMigration scripts must target each partition

✅ Quick Checklist

  1. Choose a stable partition key that distributes writes evenly.
  2. Monitor partition sizes; add or drop partitions as needed.
  3. Implement idempotent reads in the publisher to handle duplicate reads from partitions.
  4. Schedule cleanup (e.g., DROP TABLE outbox_p0 for old data) after confirming delivery.

By partitioning the outbox, you keep your transaction fast, your event stream smooth, and your system ready to scale.
