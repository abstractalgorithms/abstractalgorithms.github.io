Stage 1 — Streams as Unbounded Tables: The Core Abstraction of Structured Streaming

  • Structured Streaming reframes how engineers think about data in motion.
  • In the traditional batch model, a dataset is a finite, bounded table: you read it all, compute results, and write output.
  • In Structured Streaming, a data stream is modelled as an unbounded table — a table that never stops growing because new rows are constantly being appended by the source (a Kafka topic, a file directory, a socket).
  • Reading and Writing a Stream To consume a stream, you use readStream on a SparkSession .

Stage 3 — How Structured Streaming Guarantees Correctness at Scale

  • The Internals of MicroBatchExecution MicroBatchExecution extends StreamExecution , which is the base class for all Spark streaming execution engines.
  • The object hierarchy is worth knowing when reading stack traces or Spark source code: Epoch-based offset tracking is how Structured Streaming achieves determinism.
  • Each micro-batch is assigned a monotonically increasing epoch number (the batch ID).
  • The offset log and commit log are both indexed by this epoch number.

Stage 5 — Real-World Patterns: Kafka, Incremental File ETL, and Delta Lake Sinks

  • Kafka Source with Structured Streaming Kafka is the most common source for Structured Streaming production deployments.
  • The KafkaSource maps each Kafka partition to a Spark task and tracks {topic, partition, offset} triples as the offset state.
  • The source guarantees that each offset range is processed exactly once across restarts.
  • A critical operational detail: Spark does not commit offsets back to Kafka's consumer offsets topic by default.

  • Lesson 1: The checkpoint is not optional — treat it like a database.
  • Teams routinely point the checkpoint location at a local filesystem or ephemeral NFS mount for development convenience and then forget to change it before deploying to production.
  • TLDR: Spark Structured Streaming models a data stream as an unbounded table and executes queries over it using the micro-batch engine ( MicroBatchExecution ).
  • Each trigger fires a Spark batch job over a bounded offset range.

Alternatives considered

These three execution models represent genuinely different tradeoffs — not just a dial turned from slow to fast.

These three execution models represent genuinely different tradeoffs — not just a dial turned from slow to fast.

Micro-Batch (Structured Streaming default)

The micro-batch engine achieves latency in the range of 100ms to several seconds depending on trigger configuration and cluster size.

Continuous Processing (Spark experimental)

Continuous processing ( Trigger.Continuous("1 second") ) eliminates the micro-batch boundary.

Apache Flink

Flink's streaming runtime is a true event-at-a-time engine.

Failure and degraded modes

The source does not isolate a separate failure mode. Limits that matter for the scenario are called out in the stage decisions above.
