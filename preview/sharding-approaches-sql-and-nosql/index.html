Sharding Approaches in SQL and NoSQL: Range, Hash, and Directory-Based Strategies Compared

Scenario context

Sharding splits your database across multiple physical nodes so no single machine carries all the data or absorbs all the writes. The strategy you choose — range, hash, consistent hashing, or directory — determines whether range queries stay cheap, writes stay balanced, and adding a new node moves 100% or just 1/N of your data. The shard key is the single most consequential architectural decision you will make, and…

This walkthrough focuses on When One PostgreSQL Instance Is No Longer Enough.

Before making a design choice, clarify:

  • A single PostgreSQL instance handles 50k writes per second.
  • You've already maxed out CPU, RAM, and the fastest NVMe disks money can buy — you cannot scale up further.
  • But three teams before yours tried to shard this same table and failed.

Concepts in play: database-sharding, caching, consistency-replication, database-indexing

Stage 2 — The Four Sharding Strategies and What Each One Optimizes

  • Range Sharding: Natural Ordering at the Cost of Write Balance Range sharding assigns contiguous key intervals to each shard.
  • If your shard key is user id and you have four shards, you might configure: - Shard 1 → user id 0 – 999,999 - Shard 2 → user id 1,000,000 – 1,999,999 - Shard 3 → user id 2,000,000 – 2,999,999 - Shard 4 → user id 3,000,0…
  • The router holds a simple lookup table of ranges.
  • Any query with a known user id lands on exactly one shard.

Stage 3 — Deep Dive: How SQL and NoSQL Databases Wire Sharding Into Their Engines

  • Internals: Query Routing, Shard Maps, and Database-Specific Partitioning Models SQL databases were designed around the assumption that all data lives in one engine on one server.
  • Sharding is an external capability in most SQL systems, not a native one.
  • PostgreSQL's native PARTITION BY feature creates partitions on the same server — useful for query pruning but not horizontal scaling.
  • True sharding requires the Citus extension (now part of Azure Cosmos DB for PostgreSQL).

Quorum Consistency & Raft Consensus

↗

Distributed databases replicate data across N nodes for fault tolerance. Quorum math (Read Nodes + Write Nodes > Total Nodes) guarantees that any read operation overlaps with at least one node containing the latest write.

Database Indexing: B-Trees vs LSM-Trees

↗

Database indexes turn linear O(N) table scans into logarithmic O(log N) lookups. B-Trees optimize point & range reads; LSM-Trees turn random writes into sequential disk writes.
