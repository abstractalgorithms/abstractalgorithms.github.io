Choosing the Right Database: CAP Theorem and Practical Use Cases

Scenario context

Database selection is a trade-off between consistency, availability, and scalability. By using the CAP Theorem as a compass and matching your data access patterns to the right storage engine (Relational, Document, KV, or Wide-Column), you can build systems that scale without collapsing under architectural debt.

Observable outcome: It works beautifully for the first week.

Stage 2 — Core Mechanics: Sharding and Partitioning

  • How do databases actually scale?
  • They all eventually run out of room on a single disk.
  • The mechanic for solving this is Partitioning (often called Sharding).
  • Vertical Partitioning: Putting different tables on different servers (e.g., Users table on DB1, Orders table on DB2).

Quorum Consistency & Raft Consensus

↗

Distributed databases replicate data across N nodes for fault tolerance. Quorum math (Read Nodes + Write Nodes > Total Nodes) guarantees that any read operation overlaps with at least one node containing the latest write.

Database Indexing: B-Trees vs LSM-Trees

↗

Database indexes turn linear O(N) table scans into logarithmic O(log N) lookups. B-Trees optimize point & range reads; LSM-Trees turn random writes into sequential disk writes.

Stage 5 — Advanced Concepts: NewSQL and Distributed SQL


    

  • A new category called NewSQL (like TiDB or Google Spanner ) attempts to provide the best of both worlds: the SQL interface and ACID transactions of a relational DB with the horizontal scale of NoSQL.
    • 

  • They achieve this using consensus algorithms like Paxos or Raft to manage state across many nodes.
