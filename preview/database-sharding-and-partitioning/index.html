What happens when a database gets too big for one server? | Database Sharding & Partitioning

TLDR: When a database outgrows a single server's capacity, horizontal scaling becomes necessary. Partitioning splits tables locally within a single database instance, while Sharding distributes data across completely separate physical database servers. Sharding keys determine how records are routed, utilizing hash-based, range-based, or lookup-based strategies.

The Scaling Problem: Up vs. Out

Every database scaling journey begins with a single server running a database engine like PostgreSQL or MySQL. In the early stages, this setup is simple and robust. However, as the application gains traction, read and write traffic increases, and the database file size grows. Eventually, the server will saturate its hardware limits (CPU, Memory, Disk I/O).

At this stage, architects face a choice between two scaling vectors:

1. Vertical Scaling (Scale Up)

Vertical scaling involves adding more power to the existing server: upgrading to faster CPUs, installing more RAM, or moving to higher-throughput NVMe SSD storage arrays.

  • Pros:
    • No Code Changes: The database engine remains unchanged; the application code does not need to understand distributed routing.
    • ACID Integrity: Transactions are processed locally, maintaining full ACID guarantees without distributed lock overhead.
  • Cons:
    • Hardware Ceilings: There is a physical limit to the number of CPU cores and RAM slots a single motherboard can support.
    • Exponential Costs: High-end enterprise servers become exponentially expensive as you approach maximum capacities.
    • No Redundancy: A single database server remains a single point of failure (SPOF).

2. Horizontal Scaling (Scale Out)

Horizontal scaling involves distributing the database workload across multiple independent database servers (nodes).

  • Pros:
    • Theoretically Infinite Scale: You can continue adding cheap commodity servers to the cluster as your data grows.
    • Isolated Failures: If one server crashes, only a portion of the dataset is affected; the remaining nodes continue serving traffic.
  • Cons:
    • High Complexity: The application or proxy layer must route queries to the correct database server.
    • Loss of Joins & Transactions: Joins across separate database servers are impossible or slow, and distributed transactions require complex coordination.

Partitioning vs. Sharding

It is critical to distinguish between database partitioning and database sharding. While they both divide a large dataset into smaller subsets, they operate at different architectural boundaries.

Database Partitioning

Database partitioning divides a single large table into smaller, more manageable physical subsets (partitions) within the same database server.

For example, a table storing historical orders can be partitioned by year:

  • orders_2025 stores all orders placed in 2025.
  • orders_2026 stores all orders placed in 2026.

When a query requests orders from 2026, the database engine skips scanning the orders_2025 partition entirely. This optimization is known as Partition Pruning. The data remains on the same file system, managed by the same database process.

Database Sharding

Database sharding goes a step further: it distributes those table partitions across completely separate physical database instances running on different servers. Each server is called a Shard.

Each shard is an independent database containing a subset of the total data. The application or a middleware router directs queries to the specific shard holding the requested records.

Sharding Strategies

To implement sharding, you must choose a Sharding Key—the column(s) in your table used to determine which shard a record belongs to. Choosing the correct sharding key is the most critical decision in distributed database design.

1. Algorithmic (Hash-Based) Sharding

In hash-based sharding, the load is distributed by applying a hash function to the sharding key, followed by a modulo operation:

$$\text{Shard ID} = \text{Hash}(\text{Sharding Key}) \pmod{\text{Number of Shards}}$$

  • Pros:
    • Even Distribution: Writes and reads are evenly distributed across all shards, preventing hot spots.
  • Cons:
    • Re-sharding Complexity: If you add a new shard, the modulo denominator changes. Nearly every record in the database will hash to a different Shard ID, requiring a massive and expensive data migration.

2. Range-Based Sharding

In range-based sharding, data is divided into continuous ranges of the sharding key.

  • Pros:
    • Simple Routing: Easy to configure and understand (e.g., sharding by alphabetical ranges of names: A-M on Shard 1, N-Z on Shard 2).
    • Efficient Range Queries: Querying a range of keys within a shard is fast because the records are stored contiguously.
  • Cons:
    • Hot Spots: If you shard by date ranges (e.g., months), all new inserts will target the current month's shard, saturating its resources while historical shards remain idle.

3. Directory-Based (Lookup) Sharding

A central directory service or lookup table stores the mapping between every sharding key and its corresponding Shard ID.

  • Pros:
    • Maximum Flexibility: You can move individual records from one shard to another without changing hash functions or range boundaries.
  • Cons:
    • Performance Bottleneck: Every database read and write query requires an initial lookup query to the directory service, adding network latency.
    • SPOF: If the directory service crashes, the entire sharded database cluster becomes unreachable.

🧠 Deep Dive: Consistent Hashing and the Hash Ring

To solve the re-sharding limitation of algorithmic sharding (where adding a node requires migrating almost all data), architects use Consistent Hashing.

Consistent hashing maps both the database shards and the sharding keys onto a logical circular space called a Hash Ring (typically from $0$ to $2^{32} - 1$).

            Shard A (Hash: 1000)
             /                \
   Key 1 (Hash: 200)           Key 2 (Hash: 1500)
           /                    \
  Shard C (Hash: 3000) ------- Shard B (Hash: 2000)
  1. Mapping Nodes: Each database shard is hashed based on its IP or hostname, and placed at a coordinate on the ring.
  2. Mapping Keys: When a record is inserted, its sharding key is hashed and mapped to a coordinate on the ring.
  3. Routing Rule: The record is stored on the first database shard encountered when traveling clockwise from the key's coordinate.

What happens when a Shard is added?

If we add a new shard, Shard D, to the ring between Shard A and Shard B, only the keys that map to that specific segment of the ring need to be migrated to Shard D. The rest of the keys remain on their current shards.

On average, consistent hashing requires migrating only $\frac{1}{N}$ of the total database records when scaling the cluster (where $N$ is the new number of shards), compared to 90%+ in simple modulo-based sharding.

Challenges and Pitfalls of Sharding

Sharding is an architectural last resort. While it solves scaling limits, it introduces severe design challenges:

1. Cross-Shard Joins

You cannot execute a standard SQL JOIN query across tables located on different physical shards. If your query requires data from two separate shards, the application must run multiple queries to each shard and merge the datasets in memory, which degrades latency.

2. Distributed Transactions (Two-Phase Commit)

Maintaining ACID properties across multiple database nodes requires a Distributed Transaction Coordinator and protocols like Two-Phase Commit (2PC). 2PC introduces heavy network coordination overhead:

  • Phase 1 (Prepare): The coordinator asks all shards if they are ready to commit.
  • Phase 2 (Commit): If all shards agree, the coordinator instructs them to finalize the transaction.

If any shard fails to respond, the entire transaction is rolled back. The network round-trips significantly reduce write throughput.

3. Distributed ID Generation

In a single-node database, you can rely on auto-incrementing integer primary keys. In a sharded cluster, individual shards do not communicate their current ID state. If Shard 1 and Shard 2 both insert a new row, they will generate overlapping IDs (e.g., ID: 101), leading to primary key conflicts.

To solve this, you must implement distributed ID generators (e.g., Twitter's Snowflake algorithm, which generates time-sorted 64-bit IDs) or use UUIDs (which increases index size).

⚖️ Trade-offs: When to Shard

Sharding should only be implemented when all other optimization strategies have been exhausted:

  • Before Sharding, verify if you can:
    • Optimize Indexing: Ensure your read paths are covered by optimal indexes.
    • Implement Caching: Offload read traffic to a distributed cache (e.g., Redis).
    • Read Replicas: Route read traffic to read-only replica databases.
    • Database Partitioning: Use local horizontal partitioning to keep table scans small.

🧭 Decision Guide: Selecting the Sharding Strategy

Use this matrix to select the sharding strategy for your workload:

  • Use Algorithmic (Hash-Based) Sharding if:
    • Your read/write workload is distributed randomly and you need to prevent hot spots.
    • Your queries request specific keys rather than ranges of data.
    • Your cluster size is stable and does not scale up or down frequently.
  • Use Range-Based Sharding if:
    • Your application frequently executes range queries (e.g., pulling all orders for a specific date range).
    • Your sharding key distributes data evenly over time (avoid sharding by incremental timestamp).
  • Use Directory-Based Sharding if:
    • You require dynamic placement of records across shards.
    • You can tolerate the latency overhead of a lookup directory service.

Partitioning Inside One Database

Partitioning divides one logical table into physical pieces managed by the same database. Horizontal partitioning splits rows; vertical partitioning separates groups of columns, often moving large or rarely accessed fields away from the hot row. PostgreSQL supports range, list, and hash partitions while preserving one SQL-facing table.

CREATE TABLE orders (
  id bigint NOT NULL,
  tenant_id bigint NOT NULL,
  created_at timestamptz NOT NULL,
  total_cents bigint NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_07 PARTITION OF orders
FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');

CREATE INDEX ON orders_2026_07 (tenant_id, created_at DESC);

Partition pruning can reduce scanned data and make retention cheap: detach or drop an old monthly partition instead of deleting billions of rows. It does not add write capacity beyond the database server, and a query that ignores the partition key can still scan every partition.

Choosing a Shard Key

A useful shard key has high cardinality, stable ownership, even traffic distribution, and alignment with common queries. Evaluate data volume and request rate separately: ten equally sized tenants are not balanced if one produces 80% of traffic.

User ID hashEven point reads and writesRange queries scatter across shards
Time rangeEfficient retention and time queriesCurrent range becomes a write hotspot
Geographic regionData residency and localityCross-region users and uneven regions
Directory lookupFlexible placement and migrationLookup service becomes critical infrastructure

Before committing, replay a representative query log against the proposed key. Measure the percentage of single-shard queries, maximum-to-average shard load, largest tenant, and expected growth for at least the next capacity horizon.

Online Resharding Without a Long Outage

Resharding is a migration, not a configuration toggle:

  1. Create the destination shard and a versioned shard map.
  2. Snapshot-copy the selected key range while normal writes continue.
  3. Capture concurrent changes through CDC or an outbox.
  4. Replay changes idempotently until lag approaches zero.
  5. Shadow-read and compare source and destination results.
  6. Route reads to the destination, then writes, using a reversible feature flag.
  7. Retain the source for a rollback window before deletion.

Avoid unconstrained application dual-writes: a timeout can leave the caller unable to tell which shard committed. A log-based replication stream with offsets and idempotent consumers gives operators something measurable and replayable.

Cross-Shard Operations

Global uniqueness can use a globally unique ID generator, a dedicated registry, or IDs scoped by shard. Cross-shard pagination needs a cursor per shard plus a merge step; an offset applied independently to every shard is neither efficient nor stable. Aggregations should usually flow into a separate analytical store rather than fan out across every transactional shard on each request.

For financial workflows, prefer keeping one invariant inside one shard. When that is impossible, use a saga with explicit compensation or a carefully justified distributed transaction. Two-phase commit provides atomicity but increases coordination latency and can reduce availability during coordinator or participant failures.

Operational Topology

Each shard still needs replicas, backups, schema migrations, monitoring, and recovery testing. One hundred shards do not remove database operations; they multiply them. Automate migrations with bounded batches, pause on elevated replication lag, and record completion per shard so retries do not restart the fleet.

Monitor storage and traffic skew, hottest shard CPU, connection count, replica lag, cross-shard query percentage, shard-map lookup latency, migration lag, failed routing attempts, and capacity headroom. Alert on imbalance before the busiest shard reaches saturation—the average shard is not the constraint.

Operator Field Note: The Shard Map Is Part of the Data

If routing metadata is stale, a healthy shard can appear to lose records. Version shard-map updates, cache them briefly, and include the resolved shard ID and map version in traces. During a migration, first stop new movement, pin routing to the last known-good map, and reconcile writes by idempotency key. Never improvise a second migration while the first is unresolved.

15-Minute Reliability Drill

  1. Mark one shard unavailable and verify requests fail narrowly instead of exhausting every connection pool.
  2. Serve a stale shard-map version and confirm clients refresh rather than write to both locations.
  3. Run a bounded reshard of one test tenant and demonstrate rollback.
  4. Restore one shard from backup and verify application-level invariants, not only row counts.

Implementation Checklist

  • Exhaust indexing, query tuning, replicas, caching, archival, and native partitioning first.
  • Quantify shard-key skew using real request and data distributions.
  • Make routing metadata versioned, highly available, and observable.
  • Bound fan-out, connection pools, retries, and migration concurrency.
  • Design IDs, uniqueness, pagination, analytics, backup, and schema migration before cutover.
  • Practice resharding and single-shard recovery before an emergency.

📚 Lessons Learned

  • Partitioning improves manageability inside one database; sharding distributes ownership across databases.
  • A shard key is an operational commitment encoded in every important query.
  • Resharding and fleet-wide schema changes are the real long-term cost.
  • Design business invariants to remain within one shard whenever possible.
  • Measure the hottest shard rather than fleet averages.

📌 TLDR: Summary & Key Takeaways

  • Start with vertical scaling, indexing, replicas, caching, archival, and native partitioning.
  • Shard only when a measured storage or throughput boundary requires distribution.
  • Choose keys using data size, traffic, locality, and query fan-out—not uniform hashing alone.
  • Treat shard maps, resharding, backups, and migrations as first-class production systems.
