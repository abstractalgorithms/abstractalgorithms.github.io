📦 Snap & Roll: Raft Log Compaction in Serverless Functions

TLDR: In serverless Raft, the log can balloon fast because functions are stateless. Persisting compacted snapshots to object storage lets you restart a node in seconds and keep state machine size manageable.

⚠️ The Gotcha

Serverless functions (e.g., AWS Lambda, Azure Functions) terminate after a short run. A Raft node that stores its log in memory loses it on shutdown. If you restart the function, you must replay the entire log from the last snapshot. With a growing log, this replay can take minutes or even hours, breaking the low‑latency guarantees of a serverless state machine.

🛠️ The Solution & Trade‑offs

  1. Persist Snapshots – After every N log entries or at a regular interval, serialize the state machine’s current state and the last committed index. Store this blob in durable object storage (S3, Blob, etc.).
  2. Store Metadata – Keep a small metadata file that records the snapshot’s index, term, and a checksum. This allows a new function instance to validate the snapshot before loading.
  3. Incremental Snapshots – Rather than full snapshots each time, store diffs (e.g., using a Merkle tree or diff‑patch). This reduces bandwidth and storage costs.
  4. Lazy Loading – On function start, load the latest snapshot into memory, then replay only the entries that follow the snapshot’s index. Because the snapshot contains the state machine’s entire state, the replay window is tiny.
  5. Cold‑start Optimisation – Cache the snapshot in a shared in‑memory store (e.g., Redis, DynamoDB DAX) for the next few invocations to avoid hitting object storage each time.

Trade‑offs:

  • Latency vs. Cost – Full snapshots give the fastest restarts but cost more storage; incremental snapshots save space but add computation during snapshot creation.
  • Consistency – You must ensure the snapshot is written atomically; otherwise, a corrupt snapshot can bring the node down.

📈 When to Use

  • High‑frequency writes where the log can outgrow memory in a few minutes.
  • Cost‑sensitive environments where you want to keep the function runtime short.
  • Regulatory compliance requiring state to be recoverable after a crash or function termination.

By treating snapshots as first‑class citizens in your serverless Raft design, you keep state machine size under control and ensure that cold starts remain a brief, predictable event rather than a cascading delay.
