How to serve data at lightning speed | Caching Strategies (Redis/Memcached)

TLDR: Caching accelerates application performance by storing frequently accessed data in fast, in-memory key-value stores like Redis or Memcached. Selecting the correct caching strategy—such as Cache-Aside, Write-Through, or Write-Behind—determines how data consistency is maintained between the cache and the primary database.

The Performance Problem: Database Bottlenecks

In modern web development, database access is often the primary bottleneck. Relational databases (like PostgreSQL or MySQL) store data on disk. When a client requests a resource, the application server must execute a SQL query, parse the request, scan table indexes, read disk blocks into memory, perform joins, and return the result.

Even with fast SSDs and optimized indexes, disk I/O and query compilation take time (typically 5ms to 50ms). Under high traffic, concurrent database connections saturate, disk queues fill up, and application latency increases.

To serve data at lightning speed, architects introduce a Cache Layer. A cache is a high-speed storage layer that stores a subset of data in volatile, random-access memory (RAM). In-memory key-value stores (such as Redis or Memcached) can read and write data in sub-millisecond response times, handling hundreds of thousands of operations per second on modest hardware.

Caching Patterns

The flow of data between the application, the cache, and the database is governed by specific caching patterns.

1. Cache-Aside (Lazy Loading)

This is the most common caching pattern. The application is responsible for managing both the cache and the database.

  • Read Flow: The application checks the cache. If the data is found (Cache Hit), it returns it. If not (Cache Miss), the application queries the database, writes the retrieved data to the cache, and returns it to the client.
  • Write Flow: When data is updated, the application writes the change directly to the database and then deletes the cached key. Deleting the key (invalidation) forces the next read to fetch the fresh data from the database.
  • Pros:
    • Resilient to cache failures. If the cache crashes, the application can still read directly from the database.
    • Data is only loaded into the cache when requested, saving memory.
  • Cons:
    • Cache misses incur a double penalty: reading from the database and then writing to the cache.
    • Potential for stale data if the cache invalidation step fails.

2. Write-Through

The cache acts as the primary interface for writes. The application writes data directly to the cache, and the cache synchronously writes it to the database.

  • Flow: When the application updates a record, it sends the write to the cache. The cache updates its memory and immediately writes the change to the database. The write transaction completes only when both stores are updated.
  • Pros:
    • Guaranteed data consistency; the cache is never stale.
    • Subsequent reads are extremely fast because data is already in the cache.
  • Cons:
    • High write latency. Every write requires two network hops (to the cache and then to the database).
    • Memory is consumed by data that might never be read again (mitigated by TTL eviction).

3. Write-Behind (Write-Back)

The application writes data to the cache, which acknowledges the write instantly. The cache then asynchronously flushes the writes to the database in batches.

  • Flow: The application writes to the cache. The cache stores the dirty write in memory and acknowledges success. A background thread periodically collects these dirty writes and batches them into the database.
  • Pros:
    • Extremely high write performance and throughput.
    • Reduces write load on the database by batching and coalescing updates (e.g., merging 10 increments of a counter into a single database update).
  • Cons:
    • Risk of data loss. If the cache node crashes before flushing its memory to the database, committed writes are lost.
    • Complex implementation; requires managing queue backlogs and handling write failures to the database.

4. Read-Through

The application delegates the read logic to the cache library or middleware.

  • Flow: The application requests data from the cache. If a cache miss occurs, the cache itself queries the database, updates its own memory, and returns the data to the application.
  • Pros:
    • Simplifies application code; the application does not manage database fallback logic.
  • Cons:
    • Requires database drivers and connector configurations inside the caching middleware.

Eviction Policies and TTL

Memory (RAM) is expensive and limited. A cache cannot grow indefinitely. To manage memory constraints, caches use two mechanisms: Time-To-Live (TTL) and Eviction Policies.

Time-To-Live (TTL)

Every cached key should be assigned an expiration timer (TTL). Once the TTL expires, the cache deletes the key. This ensures that data is periodically refreshed from the database, capping the duration that stale data can remain in the cache.

Eviction Policies

When the cache memory is full, it must evict existing keys to make room for new data. Common eviction policies include:

  • LRU (Least Recently Used): Discards the keys that have not been accessed for the longest period.
  • LFU (Least Frequently Used): Discards the keys with the lowest access count, keeping hot keys in memory regardless of how recently they were accessed.
  • FIFO (First In, First Out): Evicts keys in the order they were inserted, regardless of access patterns.
  • Random: Evicts keys randomly. Useful when access patterns are completely uniform.

🧠 Deep Dive: Cache Invalidation and the Dual-Write Problem

The hardest problem in caching is Cache Invalidation—ensuring the cache accurately reflects updates made to the database.

When an application performs writes in a Cache-Aside setup, it must perform two updates: write to the database and invalidate/delete the cache key. This is a Dual-Write operation. Because these updates are not bound by a single transaction, the order of operations matters:

Pattern A: Update Database, then Delete Cache

This is the recommended approach. Let us analyze a potential race condition:

  1. Initial State: Cache has no key. Database has value $A$.
  2. Client 1 (Reader): Experiences a cache miss. Reads value $A$ from the database.
  3. Client 2 (Writer): Updates database value to $B$. Sends a delete request to the cache (cache is already empty, so this is a no-op).
  4. Client 1 (Reader): Writes the old value $A$ back to the cache.
  5. Result: Cache holds stale value $A$, while database has value $B$.

While possible, this race condition requires the reader's database read and subsequent cache write to straddle the writer's entire update transaction, which is rare because cache writes are extremely fast compared to database updates.

Pattern B: Delete Cache, then Update Database

This pattern is highly vulnerable to race conditions:

  1. Client 1 (Writer): Deletes the cache key.
  2. Client 2 (Reader): Experiences a cache miss. Reads the old value from the database.
  3. Client 2 (Reader): Writes the old value to the cache.
  4. Client 1 (Writer): Updates the database to the new value.
  5. Result: The cache is now permanently out of sync with the database until the TTL expires.

To resolve this, developers use Cache Invalidation pipelines (like Change Data Capture - CDC) to listen to database write logs and invalidate cache keys asynchronously, ensuring consistent states.

Caching Gotchas and Mitigation

1. Cache Avalanche

  • The Problem: A large number of cached keys expire at the exact same time, or the cache server crashes. This causes all client traffic to hit the database simultaneously, causing a database crash.
  • Mitigation: Add a random jitter (e.g., adding a random offset of 1 to 5 minutes) to the TTL of every key, spreading expiration events evenly over time.

2. Cache Penetration

  • The Problem: Clients request keys that do not exist in either the cache or the database (e.g., searching for a non-existent user ID). Because the data is not in the database, the query always results in a cache miss, hitting the database repeatedly.
  • Mitigation:
    • Cache Null Values: Store an empty placeholder value in the cache with a short TTL when a database query returns nothing.
    • Bloom Filters: Use an in-memory Bloom Filter to quickly determine if an ID exists before querying the cache or database.

3. Cache Stampede (Thundering Herd)

  • The Problem: A highly popular hot key expires. Because thousands of concurrent requests hit the application at that exact millisecond, they all experience a cache miss simultaneously and attempt to query the database and rebuild the cache key at the same time.
  • Mitigation: Use Mutex Locking. The first thread that experiences a cache miss acquires a lock and queries the database to rebuild the cache key, while other threads wait or return a slightly stale value.

🧭 Decision Guide: Selecting the Caching Pattern

Use this guide to choose the caching strategy for your system:

  • Use Cache-Aside if:
    • Your application is read-heavy and you want to cache data dynamically.
    • You require resilience; if the cache fails, the application can continue running using the database.
  • Use Write-Through if:
    • Data consistency is critical and you cannot tolerate stale reads.
    • Your write volume is relatively low compared to reads.
  • Use Write-Behind if:
    • You have extremely high write volumes (e.g., tracking user clicks, IoT telemetry, game states).
    • You can tolerate the risk of losing a few seconds of writes in the event of a cache crash.

Write-Around: Keep One-Time Writes Out of the Cache

Write-around sends writes directly to the database and invalidates any old cached value. The cache is populated only if a later read needs the record. It is useful for imports, audit events, large objects, and other data that is written once but may never become hot. Its cost is predictable: the first read after every write is a cache miss. It is therefore a poor fit for profiles, permissions, or product inventory that users read immediately after updating.

Write-through improves read-after-write behavior, but it does not magically provide absolute consistency. Cache replication lag, database commit failures, failover, and timeouts can still leave ambiguous outcomes. The application needs idempotency keys, retry rules, and reconciliation for important writes.

Redis vs Memcached: Choose Capabilities, Not Brand Recognition

CapabilityRedisMemcached
Data modelStrings plus hashes, sets, sorted sets, streams and moreOpaque byte/string values
PersistenceOptional snapshots and append-only logNone
Replication and failoverReplicas, Sentinel, managed clustersUsually client-side sharding; no native persistence

Good default useShared cache, rate limits, locks, queues, rankingsDisposable high-throughput object cache

Choose Memcached when values are disposable blobs, operations are simple, and rebuilding the entire cache is acceptable. Choose Redis when the design needs richer atomic behavior, replication, persistence options, or data structures. Neither should silently become the source of truth unless the durability and recovery design explicitly supports that role.

Practical Cache-Aside with Stampede Protection

async function getProduct(id: string) {
  const key = 'product:v3:' + id;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  // SET NX lets one request rebuild the key. Others briefly retry or serve stale data.
  const lockKey = key + ':lock';
  const ownsLock = await redis.set(lockKey, requestId, { NX: true, PX: 3_000 });
  if (!ownsLock) return retryWithJitter(() => getProduct(id), 40, 120);

  try {
    const product = await db.products.findUnique({ where: { id } });
    const ttlSeconds = 300 + Math.floor(Math.random() * 60); // expiry jitter
    await redis.set(key, JSON.stringify(product ?? null), { EX: product ? ttlSeconds : 30 });
    return product;
  } finally {
    // Production code should compare the lock token before deletion.
    await releaseLockIfOwner(lockKey, requestId);
  }
}

async function updateProduct(id: string, patch: ProductPatch) {
  const updated = await db.products.update({ where: { id }, data: patch });
  await redis.del('product:v3:' + id); // DB first, invalidate second
  return updated;
}

Version cache keys when the serialized schema changes. Cache null results briefly to stop repeated misses, but never give negative entries the same TTL as real data. For critical invalidation, publish database changes through an outbox or CDC stream and make invalidation consumers idempotent.

Capacity Planning and Observability

Suppose an API serves 20,000 reads per second, the database safely handles 2,500, and the target cache hit ratio is 90%. The expected database read rate is 2,000 per second: within budget, but with little room for a stampede. At 80% hits the database receives 4,000 reads per second and is already overloaded. Capacity planning must test degraded hit ratios, not only the happy path.

Monitor cache hit ratio by endpoint, miss latency, evictions, expired keys, memory usage, hot-key traffic, Redis command latency, connection saturation, replication lag, database fallback rate, and rebuild-lock contention. Alert when backend load approaches its safe limit even if cache latency still looks healthy.

Operator Field Note: When the Cache Becomes the Outage Multiplier

A common incident begins with a Redis failover. Clients reconnect simultaneously, every instance sees empty local state, and thousands of requests rebuild the same popular keys. The database—not Redis—then fails. Contain it by shedding optional traffic, limiting concurrent cache rebuilds, serving bounded stale values, and warming only the highest-value keys. Do not bulk-warm the entire dataset during an incident.

15-Minute Reliability Drill

  1. Disable the cache in staging and confirm the database remains within its fallback budget.
  2. Expire one hot key under load and verify only one rebuild reaches the database.
  3. Simulate an invalidation failure and measure the maximum stale-data window.
  4. Record the command for disabling cache reads and the owner authorized to use it.

Implementation Checklist

  • Set a memory limit and explicit eviction policy.
  • Put a TTL on every disposable key and add expiry jitter.
  • Bound cache client connections, request timeouts, retries, and rebuild concurrency.
  • Define whether stale data is safe for each domain.
  • Version key schemas and validate maximum value size.
  • Protect hot keys with request coalescing or stale-while-revalidate.
  • Test cache loss, partial invalidation, failover, and cold-start recovery.

📚 Lessons Learned

  • A cache reduces load only while its miss path remains controlled.
  • Pattern choice is primarily a consistency and failure-semantics decision.
  • Redis provides capabilities; Memcached provides a deliberately smaller surface.
  • Hit ratio without backend fallback capacity is a misleading success metric.
  • Invalidation must be observable, replayable, and safe to retry.

📌 TLDR: Summary & Key Takeaways

  • Use cache-aside as the general default, write-around for cold writes, and write-behind only where acknowledged data loss is acceptable.
  • Choose Redis for richer distributed coordination and Memcached for a simple disposable object cache.
  • Prevent avalanches with TTL jitter, hot-key rebuild locks, negative caching, and bounded stale reads.
  • Design and test the cache-loss path before production traffic tests it for you.
