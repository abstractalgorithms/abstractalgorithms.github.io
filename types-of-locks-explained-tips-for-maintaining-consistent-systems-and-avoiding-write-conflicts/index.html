Functional Requirements

  • TLDR: Pessimistic locking locks the record before editing — safe but slower under low contention.
  • Optimistic locking checks for changes before saving using a version number — fast but can fail and require retry under high contention.
  • Choosing correctly depends on your write-conflict probability.

Constraints & Assumptions

  • The probability of lock contention under random access can be modeled as: $$P( ext{conflict}) pprox 1 - e^{-\lambda t}$$ where $\lambda$ is the arrival rate of writers and $t$ is the average transaction duration.
  • When $\lambda t$ is small (< 0.1), optimistic is clearly cheaper.

Deep Dive: Stage 1 — Locking Fundamentals: Concurrency and Write Conflicts

  • Before picking a locking strategy, it helps to understand exactly what can go wrong without one.
  • When two transactions read and write the same row at overlapping times, the database can produce incorrect results — silently.
  • These are called concurrency anomalies .
  • Locking prevents these anomalies by serialising access to shared data.

Deep Dive: Stage 2 — Pessimistic Locking: SELECT ... FOR UPDATE

  • Pessimistic locking acquires an exclusive database lock on a row before any modification.
  • While Transaction A holds the lock, Transaction B's SELECT ...
  • FOR UPDATE on the same row blocks until A commits or rolls back.

In-Memory Caching & Event Loop Architecture

↗

Caching stores high-frequency read data in fast RAM instead of slow disk/network databases. Redis achieves sub-millisecond QPS by operating a single-threaded event loop paired with OS epoll I/O multiplexing, completely eliminating thread locking contention.

Deep Dive: Stage 3 — Optimistic Locking: Version Column Pattern

  • Optimistic locking adds a version column.
  • No lock is held during the read — only at write time does the system check whether anyone else modified the row first.
  • In Java with JPA: JPA throws OptimisticLockException when the version check fails — the calling service must catch it and retry.

Deep Dive: Stage 4 — Deep Dive: How Database Locks Are Implemented

  • Databases implement pessimistic locks via a lock manager : an in-memory hash table keyed by (table, row) that tracks which transaction holds each lock and which are waiting.
  • The lock manager periodically scans wait queues for cycles to detect deadlocks, then rolls back one transaction as the victim.
  • Optimistic locking needs no lock manager — the version check happens inside the UPDATE statement itself, handled entirely by the storage engine at commit time.

Quorum Consistency & Raft Consensus

↗

Distributed databases replicate data across N nodes for fault tolerance. Quorum math (Read Nodes + Write Nodes > Total Nodes) guarantees that any read operation overlaps with at least one node containing the latest write.

Deep Dive: Stage 5 — Choosing Your Lock Strategy

  • The decision between pessimistic and optimistic locking is primarily a question of conflict frequency .
  • Use the flowchart below as a quick decision guide, then validate against your observed write-conflict rate in production.
  • 📊 Lock Type Selection Decision Tree If your write-conflict rate sits between 5 % and 10 %, measure under realistic load before deciding.
