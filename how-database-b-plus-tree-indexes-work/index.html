How It Works: The Internals of Database B+ Tree Indexes

Design Challenge: The Cost of Full Table Scans

Abstract Algorithms•Jun 18, 2026•Evidence & Source
tree-data-structuresdatabase-indexingcachingsorting-and-searching-algorithms
💡 Executive Summary

Database indexes utilize B+ Trees to minimize slow disk I/O operations.

🎯 System Scenario & Requirements

System Goal

Database indexes utilize B+ Trees to minimize slow disk I/O operations.

Actors & Components

  • Application Workers
  • Volatile Memory Tier
  • Persistent Disk Tier
  • Worker Process
  • In-Memory Cache
  • Primary Database

Functional Requirements

  • TLDR: Database indexes utilize B+ Trees to minimize slow disk I/O operations.
  • By organizing data into balanced, wide node pages and linking leaf nodes sequentially, databases resolve queries in logarithmic time and support fast range scans.
  • Imagine you are running a financial reporting application storing 100 million transaction records in a database table.

Constraints & Assumptions

  • While B+ Trees provide fast reads, they introduce trade-offs for write operations: Write Amplification (Page Splits): When inserting rows in random order, pages fill up quickly and split.
  • Writing a single 100-byte row can force the database to allocate, split, and write multiple 16 KB pages back to disk, causing high disk write amplification.

Stage 2 — Core Mechanics: Lookups, Splits, and Leaf Pointers

  • The B+ Tree maintains balance and search efficiency through three core operations: 1.
  • The Lookup Operation To locate a key, the database starts at the root page.
  • It runs a binary search on the keys stored in the root page to find the child pointer range that covers the target.
  • It follows the pointer to the next internal node page and repeats this process until it reaches a leaf node page, where the actual data resides.

Stage 4 — Deep Dive: Disk I/O Blocks and Node Fan-out

  • Understanding why B+ Trees outperform other trees (like Red-Black trees or AVL trees) on disk requires analyzing how hardware reads data.
  • The Internals of Page Allocations and Row Offsets Operating systems and storage controllers read and write data in fixed-size blocks (typically 4 KB).
  • Databases group these blocks into pages (e.g., 16 KB pages in MySQL InnoDB).
  • When the database reads a single byte from a row, the storage controller must transfer the entire 16 KB page block from disk to the RAM buffer pool.

Stage 5 — Real-World Implementation: MySQL InnoDB and PostgreSQL

  • Most modern relational databases implement B+ Trees as their primary indexing structure.
  • In MySQL's InnoDB storage engine, tables are organized as a clustered index .
  • The leaf nodes of the primary key index do not just hold pointers to rows—they store the actual row data itself.
  • If you query by primary key, the lookup returns the row immediately.

Stage 6 — Practical Implementation: MySQL InnoDB Page Sizing

  • In MySQL InnoDB, the default page size is 16 KB, which is optimal for most OLTP workloads.

End-to-end outcome

After working through the stages, you should be able to explain:

  • Avoid these indexing mistakes when scaling database architectures: 1.
  • UUIDs as Primary Keys: Using random UUIDs as primary keys in a clustered index causes inserts to target random leaf pages.
  • Wide Fan-out: B+ Tree nodes match disk blocks, keeping the tree flat (height 3-4) to minimize disk reads.
  • Leaf Linked List: Doubly linked leaf nodes allow fast range scans without traversing parent nodes.
