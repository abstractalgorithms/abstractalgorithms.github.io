Apache Spark: AQE, Catalyst
Optimizer & Distributed DataFrames.

Apache Spark processes petabyte-scale batch and streaming data across distributed clusters using lazy DAG execution, the Catalyst query optimizer, Tungsten off-heap memory, and Adaptive Query Execution (AQE) over columnar formats like Parquet, Delta Lake, and Apache Iceberg.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Almost every slow Spark job comes down to shuffle volume, data skew, or small files—fix those three via broadcast joins, AQE skew handling, and 128 MB–512 MB Parquet/Iceberg compaction before throwing more executors at the cluster.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Unoptimized Spark pipelines routinely burn 5x–10x more cloud compute than necessary due to wide shuffles, 99% straggler tasks from skewed join keys, or metadata timeouts scanning millions of 50 KB JSON files. Mastering Catalyst, AQE, and columnar table formats turns 2-hour failing nightly ETLs into 10-minute predictable jobs.

  • Spark builds a lazy Logical Plan -> Catalyst optimizes (predicate pushdown, projection pruning) -> Physical Plan split at wide shuffles into Stages and Tasks.
  • Narrow transformations (filter, map, withColumn) stay within one partition; Wide transformations (groupBy, join, repartition) trigger expensive network+disk Shuffles.
  • Adaptive Query Execution (AQE) in Spark 3+ dynamically coalesces small shuffle partitions, switches Sort-Merge Joins to Broadcast Hash Joins at runtime, and splits skewed partitions.
  • Always use columnar formats (Parquet/ORC) inside Delta Lake or Iceberg so Spark skips irrelevant row groups via min/max statistics and reads only needed columns.
  • Python UDFs serialize rows between the JVM and Python workers via Pickle/Arrow; prefer built-in pyspark.sql.functions (compiled via Tungsten whole-stage codegen) or Arrow-backed Pandas UDFs.

Good candidates

  • Transforming, joining, or aggregating 100 GB to 100+ TB datasets across object storage (S3, GCS, ADLS) using SQL, PySpark, or Scala.
  • Building medallion (Bronze/Silver/Gold) lakehouse pipelines on Delta Lake or Apache Iceberg with ACID upserts and time travel.
  • Running near-real-time micro-batch streaming (10s–5m latency) from Kafka into lakehouse tables via Structured Streaming.

Think twice

  • Small datasets under ~10–20 GB that fit on a single machine where DuckDB, Polars, or PostgreSQL runs 10x faster with zero JVM startup overhead.
  • Sub-second OLTP point lookups or high-concurrency user-facing dashboards (use PostgreSQL, DynamoDB, ClickHouse, or Pinot instead).
  • Sub-100ms true event-at-a-time stream processing with complex per-key timers (prefer Apache Flink).
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA daily Spark job joins 800 GB of clickstream events with 20 GB of user profiles on user_id. 199 tasks finish in 3 minutes, while 1 task stalls for 4 hours and OOMs because user_id = NULL accounts for 35% of traffic.

The idea

Apache Spark is a distributed compute engine built around immutable distributed datasets (DataFrames/Datasets) and lazy DAG execution. Rather than executing transformations line by line, Spark records a Logical Plan and waits for an Action (write, count, collect).

When an action triggers, the Catalyst Optimizer applies rule-based and cost-based optimizations—pushing WHERE filters down into Parquet footers (Predicate Pushdown) and dropping unused columns (Column Pruning). Next, the Tungsten engine compiles physical operators into tight Java bytecode (Whole-Stage Codegen) operating on off-heap binary UnsafeRow buffers to avoid JVM object/GC overhead.

Execution splits into Stages wherever data must cross the network (Shuffle). Narrow stages pipeline filter -> map -> project in memory at ~200–500 MB/s per core; wide stages write sorted shuffle blocks to local NVMe and fetch them across executors.

Concrete walkthrough

Trace a 500 GB Parquet Orders + 8 MB Stores aggregation in Spark 3.5 with AQE enabled:

  1. Logical & Catalyst Optimization: orders.filter(col('dt') == '2026-11-12').join(stores, 'store_id').groupBy('region').agg(sum('amount')). Catalyst pushes dt = '2026-11-12' to partition pruning (reading only 15 GB of Parquet instead of 500 GB) and prunes 42 unused columns down to 3 (store_id, amount, dt).
  2. Stage 1 (Map-Side Broadcast + Partial Agg): Because stores is 8 MB (< 10 MB autoBroadcastJoinThreshold), the Driver broadcasts stores as a read-only hash map to all executors. Each task scans a 128 MB Parquet split, probes the local stores hash map (zero shuffle on orders), and performs a map-side partial sum(amount) per region.
  3. Shuffle Write & AQE Coalesce: Executors write tiny partial sums (< 50 MB total across the cluster) into 200 shuffle partitions. AQE inspects shuffle statistics at the stage boundary and coalesces 200 partitions down to 2 (64 MB target size).
  4. Stage 2 (Final Agg & Write): Just 2 tasks merge the partial sums and write 2 clean, compacted Delta Parquet output files.

Catalyst optimizes before execution, Tungsten runs code-generated stages off-heap, and AQE adapts the plan between shuffles.

AQE and key configuration levers

Spark 3's Adaptive Query Execution (spark.sql.adaptive.enabled=true) eliminates most manual partition tuning by re-planning between stages using real runtime byte counts:

  • Dynamic Partition Coalescing (coalescePartitions.enabled=true): Combines small post-shuffle partitions toward advisoryPartitionSizeInBytes (64 MB default), preventing thousands of near-empty tasks.
  • Skew Join Optimization (skewJoin.enabled=true): Automatically detects shuffle partitions exceeding skewedPartitionFactor (5x median) and skewedPartitionThresholdInBytes (256 MB), splitting them into sub-partitions and duplicating the matching right-side partition.
  • Dynamic Join Strategy Switching: If a filtered table shrinks below autoBroadcastJoinThreshold (10 MB) at runtime, AQE downgrades a Sort-Merge Join to a Broadcast Hash Join on the fly.

Failure modes

  • Shuffle FetchFailedException: When Spot/Preemptible executors are reclaimed mid-job, local shuffle files vanish and Spark must recompute upstream stages. Use External Shuffle Service, Push-Based Shuffle, or on-demand nodes for shuffle-heavy stages.
  • Spill-Induced Disk Full: A skewed groupBy or join spills hundreds of GBs to /tmp on executor nodes, crashing multiple tasks on the same host.
  • Broadcast Timeout (300s): Broadcasting a table that triggers a slow upstream scan times out (spark.sql.broadcastTimeout). Materialize or increase timeout only after verifying size.
  • Cross-Join Explosion: Omitting or mis-typing a join condition triggers a Cartesian product (N * M rows) unless spark.sql.crossJoin.enabled is kept false.

Lakehouse formats: Delta Lake and Iceberg

Raw Parquet directories lack atomicity: a failed Spark job leaves half-written files that corrupt downstream readers. Delta Lake and Apache Iceberg solve this by adding a transactional metadata layer (_delta_log JSON/checkpoint files or Iceberg manifest snapshots):

  • ACID Isolation: Readers always see a consistent snapshot while writers execute MERGE INTO upserts or DELETEs.
  • Data Skipping & Z-Ordering: File-level min/max column statistics let Spark skip 95%+ of Parquet files on selective WHERE filters.
  • Schema Evolution & Time Travel: Safely add columns or roll back a bad pipeline write (VERSION AS OF 42) without restoring backups.

Practical checklist

  • Confirm dataset size justifies Spark (>20 GB) rather than single-node DuckDB/Polars.
  • Enable AQE (spark.sql.adaptive.enabled=true) and skew join handling in Spark 3+.
  • Replace Python @udfs with built-in pyspark.sql.functions or Arrow @pandas_udf.
  • Size executors to 4–5 cores and <= 24–30 GB heap (staying below the 32 GB CompressedOops boundary).
  • Store tables in Delta Lake or Apache Iceberg (Parquet + Snappy/Zstd) and compact files to 128 MB–512 MB.
  • Inspect the Spark UI SQL/Stages tab for Shuffle Read, Spill (Disk), and Max Task Time vs. Median Task Time.
03 / Engineering trade-offs

Weighing architectural decisions

Broadcast Hash Join vs. Sort-Merge Join

Advantage: Broadcast Join (`<= 10 MB` default, tunable up to ~100–256 MB) eliminates the huge fact-table shuffle completely.

Drawback: Broadcasting a table that exceeds driver/executor memory causes `OutOfMemoryError` or broadcast timeouts.

`repartition(N)` vs. `coalesce(N)`

Advantage: `coalesce(N)` avoids a full shuffle by merging existing partitions locally when shrinking partition count.

Drawback: `coalesce(N)` cannot increase partitions and can create uneven partition sizes or reduce upstream parallelism; `repartition(N)` guarantees even distribution via a full shuffle.

Executor Sizing (Fat vs. Thin Executors)

Advantage: 4–5 cores and 16–32 GB RAM per executor balances multi-core broadcast sharing with low JVM GC pause times (staying under the 32 GB CompressedOops limit).

Drawback: Oversized executors (>8 cores, >64 GB heap) suffer long GC stop-the-world pauses and HDFS/S3 I/O contention; tiny 1-core executors duplicate broadcast tables excessively.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Driver OutOfMemoryError (`collect()` / Large Broadcast)

Calling `.collect()`, `.toPandas()`, or broadcasting a multi-GB dimension table pulls all partitions into the single Driver JVM.

What helps: Write results directly to S3/Delta (`df.write`), use `.take(100)` for debugging, and keep `autoBroadcastJoinThreshold` well below 10% of driver/executor heap.

Data Skew Stragglers (99/100 Tasks Done)

A single hot key (`NULL`, `guest`, or a mega-tenant) routes millions of rows to one shuffle partition, causing disk spill and executor OOM.

What helps: Enable AQE skew join (`spark.sql.adaptive.skewJoin.enabled=true`), filter nulls before joining, or salt hot keys (`concat(key, '_', rand() % N)`).

Small Files Explosion

Writing 200+ partitions every 30-second micro-batch creates millions of <1 MB files, saturating S3 `LIST` APIs and Driver metadata memory.

What helps: Use AQE partition coalescing, `.repartition(N)` / `maxRecordsPerFile` on write, and scheduled `OPTIMIZE` compaction in Delta Lake or Iceberg.

Python UDF Serialization Bottleneck

Standard `@udf` functions force row-by-row JVM-to-Python serialization, bypassing Catalyst and Tungsten whole-stage codegen.

What helps: Rewrite logic with native `pyspark.sql.functions` / Spark SQL expressions, or use vectorized Arrow `@pandas_udf` when Python libraries are mandatory.

05 / Practical checklist

Avoid these mistakes

  • Calling `.cache()` or `.persist()` on massive DataFrames used only once, wasting executor memory and triggering spill.
  • Leaving `spark.sql.shuffle.partitions` at the static default `200` on 50 TB jobs (causing 250 GB/partition) or 500 MB jobs (creating 200 tiny files) without AQE coalescing.
  • Joining two large tables without checking for `NULL` or default sentinel keys first.
  • Using `count()` or `show()` inside production ETL loops, forcing repeated full DAG re-evaluations.
  • Setting executor heap above `32 GB`, losing JVM Compressed Oops and triggering multi-second GC pauses.
