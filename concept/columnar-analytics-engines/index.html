Columnar Analytics
Engines.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Use columnar engines (ClickHouse, DuckDB, Parquet) for wide-table aggregations and time-series scans, but keep single-row OLTP updates in row stores.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Row-oriented databases (PostgreSQL, MySQL) store every column of a tuple contiguously on 8KB/16KB pages. Running SELECT SUM(revenue) FROM events WHERE day = '2026-11-01' on a 120-column table forces a row store to read all 120 columns off disk, wasting 97%+ of I/O bandwidth and CPU cache lines. Columnar engines store each column in contiguous blocks, reading only the 2–3 referenced columns and executing tight SIMD loops over compressed arrays.

  • Projection pushdown skips unreferenced columns entirely; predicate pushdown uses per-block min/max zone maps and Bloom filters to skip entire 64MB row groups or 8,192-row granules.
  • Homogeneous column data enables extreme compression: Dictionary encoding maps repeated strings to integers, Run-Length Encoding (RLE) collapses sorted runs, and Delta/Frame-of-Reference (FOR) packs timestamps before ZSTD/LZ4.
  • Vectorized execution (DuckDB, ClickHouse, Velox) processes batches of 1,024–4,096 values per column in L1/L2 CPU cache, avoiding tuple-at-a-time virtual function call overhead.
  • LSM-tree / immutable part architectures (ClickHouse MergeTree, Parquet files) batch writes into large sequential flushes and merge small parts asynchronously in the background.
  • Sort key (ORDER BY) design determines both query speed via sparse primary indexes and compression ratio via RLE on leading low-cardinality columns.

Good candidates

  • OLAP aggregations, funnel analytics, and observability logs scanning millions to billions of rows across a subset of columns.
  • Data lakehouse storage (Apache Parquet / Iceberg on S3/GCS) queried by DuckDB, Trino, or Spark where storage cost and scan bandwidth dominate.
  • Real-time user-facing dashboards requiring sub-100ms p95 GROUP BY and percentile queries over append-heavy event streams.

Think twice

  • High-concurrency OLTP workloads doing thousands of single-row INSERT/UPDATE/DELETE operations by primary key (e.g., banking ledgers, user profiles).
  • Point lookups that return all 80+ columns of a single record (SELECT * FROM users WHERE id = ?), where row stores require only 1 B-Tree page read.
  • Low-latency transactional workflows requiring multi-row ACID locks across arbitrary tables.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn ad-tech platform ingests 50,000 events/sec (120 columns per event) and needs sub-second cohort breakdowns by tenant_id, campaign_id, and event_date.

The idea

Columnar analytics engines invert physical storage layout from row-major (storing all fields of row 1, then row 2) to column-major (storing all values of column A together, then all values of column B). Because analytical queries typically aggregate 2 to 5 columns across millions of rows, columnar storage eliminates up to 95%+ of unnecessary disk and network I/O. Storing identical data types contiguously also unlocks lightweight encodings—Dictionary, Run-Length Encoding (RLE), and Delta—followed by ZSTD/LZ4 compression and SIMD vectorized execution directly in CPU cache.

Concrete walkthrough

Suppose a 100-column orders table holds 500 million rows (600 GB uncompressed). We run: SELECT country, SUM(amount_cents) FROM orders WHERE created_date >= '2026-11-01' AND status = 'PAID' GROUP BY country;

  1. Metadata Pruning: The engine reads the Parquet file footers or ClickHouse primary.idx sparse index (1 entry per 8,192 rows). Min/max zone maps on created_date immediately skip 92% of row groups/granules from earlier months.
  2. Column Projection: Only 4 columns (created_date, status, country, amount_cents) are fetched via S3 byte-range requests or mmap—ignoring the other 96 columns (JSON payloads, shipping addresses, user agents).
  3. Late Materialization & Vectorized Filter: The engine decompresses status (dictionary-encoded as 1-byte integers), evaluates status == 'PAID' using a tight SIMD loop into a 2,048-bit selection vector, and only decompresses amount_cents for matching rows.
  4. In-Cache Aggregation: country and amount_cents are aggregated in an L2-cache-resident hash table, returning the result in ~80ms instead of 40+ seconds.

Query execution pipeline in a vectorized columnar engine, combining metadata pruning, column projection, and late materialization.

Encoding pipelines and sparse primary indexes

Columnar compression happens in two stages: type-specific logical encoding followed by general-purpose block compression (LZ4 or ZSTD):

  • Dictionary Encoding: Replaces repeated strings (e.g., country, status, device_os) with compact integer IDs, shrinking 16-byte strings to 1-byte or 2-byte codes.
  • Run-Length Encoding (RLE): When sorted by ORDER BY (tenant_id, event_date), thousands of identical tenant_id values collapse into a single (value, count) pair.
  • Delta + Bit-Packing: Monotonic timestamps (1730419200, 1730419201, ...) are stored as small deltas (+1, +1) packed into 2–4 bits each.

Unlike OLTP B-Trees that index every single row (consuming tens of GBs of RAM), engines like ClickHouse use a sparse primary index recording only 1 key per 8,192-row granule. A 1-billion-row table requires only ~122,000 index entries, fitting effortlessly in L3 cache or a few megabytes of RAM.

Failure modes

  • Unbatched insert fragmentation: Inserting 1 row per HTTP request creates thousands of tiny parts/files, triggering Too many parts errors in ClickHouse or metadata bloat in Iceberg.
  • Poor ORDER BY key selection: Putting a high-cardinality UUID first in the sort key prevents RLE compression and forces full-table scans for tenant-scoped queries.
  • Materialized view write amplification: Attaching 10+ synchronous MATERIALIZED VIEW targets to an ingest table multiplies CPU and I/O on every batch insert.
  • Clock-skewed partitioning: Partitioning by client-generated timestamps without bounds creates thousands of stray historical/future partitions (e.g., year 1970 or 2099).

Query execution and materialization

To keep p95 latency predictable under concurrent dashboard load:

  • Pre-aggregate with Incremental Materialized Views: Roll up raw 50k RPS clickstreams into 1-minute SummingMergeTree or AggregatingMergeTree tables using AggregateFunction(quantiles(0.95), latency_ms) states.
  • Data Skipping Indexes: Add minmax or bloom_filter(0.01) secondary skipping indexes on high-cardinality filter columns like trace_id or order_id that are not in the primary ORDER BY prefix.
  • Zero-Copy Arrow Interchange: Use Apache Arrow Flight or DuckDB-to-Pandas/Polars zero-copy buffers when feeding analytical slices into ML feature pipelines, avoiding JSON/CSV serialization overhead.

Practical checklist

  • Order ORDER BY / sort keys from lowest-cardinality common filter to highest-cardinality (e.g., (tenant_id, event_type, toDate(ts), user_id)).
  • Batch all writes to at least 10,000–100,000 rows per flush (or 128MB–256MB Parquet row groups).
  • Partition by coarse time intervals (toYYYYMM or toYYYYMMDD)—never by user_id or hour.
  • Replace SELECT * in application queries and BI tools with explicit column projections.
  • Pre-aggregate recurring 95th-percentile and count-distinct queries via incremental materialized views or HyperLogLog sketches.
  • Enforce per-query memory limits and disk-spill thresholds so a single runaway GROUP BY cannot OOM-kill the node.
03 / Engineering trade-offs

Weighing architectural decisions

Read Scan vs. Point Mutation

Advantage: Sequential columnar reads and SIMD vectorization deliver 10x–100x faster analytical aggregations.

Drawback: Updating or deleting a single row requires rewriting immutable column files or maintaining expensive delete bitmaps/tombstones.

Sort Order & Compression

Advantage: Sorting by low-cardinality columns first (e.g., `country`, `event_type`) maximizes RLE compression and range pruning.

Drawback: Queries filtering only on trailing high-cardinality columns (e.g., `user_uuid`) cannot use the sparse prefix index and degrade to full scans.

Ingest Batching vs. Freshness

Advantage: Batching 10k–100k rows per insert creates large parts with minimal background merge overhead.

Drawback: Micro-batching adds 1–5 seconds of ingestion latency compared to immediate single-row OLTP commits.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Too Many Parts (Small-Insert Storm)

Sending 1,000 single-row INSERTs per second into ClickHouse or Iceberg creates thousands of tiny immutable files, exhausting file descriptors and stalling background merges.

What helps: Buffer writes in Kafka, Vector, or `async_insert=1` and flush in batches of 10,000–100,000 rows every 1–5 seconds.

High-Cardinality GROUP BY OOM

Grouping by an unindexed high-cardinality key like `session_id` or `url` across 500M rows blows past per-query memory limits during hash aggregation.

What helps: Enable external disk spill (`max_bytes_before_external_group_by`), pre-aggregate via materialized views, or use approximate sketches (`uniqHLL12`).

SELECT * Defeating Column Pruning

Application ORMs or BI tools issuing `SELECT *` on a 150-column Parquet/ClickHouse table force decompression of every column, erasing the columnar advantage.

What helps: Enforce explicit column projections in query builders and create narrow projection views for BI dashboards.

Unmerged Duplicate Rows in ReplacingMergeTree

Expecting immediate deduplication on `ReplacingMergeTree` or Iceberg equality deletes before background compaction finishes causes double-counted metrics.

What helps: Query with `FINAL` (or `argMax` aggregations) on small windows, or run scheduled compaction before downstream SLA reporting.

05 / Practical checklist

Avoid these mistakes

  • Choosing `UUID` or `timestamp_ms` as the leading column in `ORDER BY`, which destroys RLE compression and forces full-partition scans for tenant queries.
  • Leaving Parquet row groups at 1MB–5MB instead of 128MB–256MB, causing excessive S3 GET requests and poor dictionary/ZSTD ratios.
  • Partitioning tables by high-cardinality keys like `user_id` or `hour` instead of `day` or `month`, creating millions of tiny metadata files.
  • Running OLTP-style `UPDATE ... WHERE id = ?` mutations in a loop against a columnar store instead of append-only event logs or CDC.
  • Ignoring memory limits on vectorized hash joins when joining two large fact tables without broadcast hints or sort-merge.
