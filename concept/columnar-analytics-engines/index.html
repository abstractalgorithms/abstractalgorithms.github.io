STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are Columnar Analytics Engines.

Why this matters: The mechanism: understand how Columnar Analytics Engines works from first principles.

Columnar analytics engines invert physical storage from row-major (all fields of row 1, then row 2) to column-major (all values of column A together, then column B).

Because analytical queries aggregate 2–5 columns out of a 100-column table, projection pushdown skips 95%+ of disk I/O. Homogeneous column values then unlock 10x–20x compression (Dictionary encoding, Run-Length Encoding, Delta/FOR before LZ4/ZSTD), while vectorized execution (DuckDB, ClickHouse, Velox) processes batches of 1,024–4,096 values in CPU L1 cache with SIMD instructions.

Metadata & Zone-Map Pruning

Parquet / ClickHouse Sparse Primary Index -> Granule Pruning -> SIMD Scan

1.Projection Pushdown: SELECT country, SUM(amount) reads only 3 column streams out of 100 columns.

2.Predicate Zone Maps: Per-block min/max metadata skips entire 64 MB Parquet row groups or 8,192-row granules.

3.Vectorized CPU: Tight loops over contiguous primitive arrays avoid row-by-row virtual dispatch overhead.

Projection pushdown + zone-map pruning + SIMD vectorization turn 600 GB scans into sub-100 ms queries.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Row Stores choke on OLAP (and columnar failure modes).

Why this matters: The problem: see what breaks without Why Row Stores choke on OLAP under real concurrency or scale.

Scanning 500M rows in PostgreSQL loads all 100 columns per 8 KiB heap page and evaluates tuple visibility row-by-row.

Yet columnar engines fail fast if misused:

  1. Unbatched Single-Row Inserts: Inserting 1 row per HTTP request creates thousands of tiny immutable parts/files, triggering Too many parts errors in ClickHouse or Iceberg metadata bloat.
  2. Bad ORDER BY Sort Key: Putting a high-cardinality UUID first in the sort key destroys RLE compression and forces full-table scans for tenant/date queries.
  3. Row-Level OLTP Updates: Updating 1 row in Parquet/ClickHouse requires rewriting immutable segments or merge-on-read tombstones.
Batch & MergeTree Ingestion

Kafka / Buffer Batch -> Immutable Column Parts -> Background Merge

1.Batch Ingestion: Flush 10k-100k rows per batch (or async_insert) so background merges keep part counts low.

2.Sort-Key Prefix: Order by (tenant_id, toDate(ts), event_type) from low-to-high cardinality for max RLE + pruning.

3.Incremental MVs: Roll up raw 50k RPS streams into 1-minute AggregatingMergeTree tables for <20ms dashboards.

Columnar engines thrive on batched, sort-key-aligned appends and incremental materialized rollups.

Engineering Decision Framework
Problem
How to implement Columnar Analytics Engines without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
When durability and read throughput pull in opposite directions, use columnar engines (ClickHouse, DuckDB, Parquet) for wide-table aggregations and time-series scans, but keep single-row OLTP updates in row stores.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Before · Unbounded Coupling
  • No backpressure on spikes
  • Implicit shared state
  • Cascading tail latency
After · Bounded & Observable
  • Explicit capacity budgets
  • Isolated failure domains
  • Predictable p99 latency
-- ClickHouse MergeTree with optimal sort key, Bloom skipping index, and 1-min rollup MV
CREATE TABLE events_raw (
    tenant_id LowCardinality(String),
    ts DateTime64(3),
    trace_id String,
    latency_ms UInt32,
    INDEX idx_trace trace_id TYPE bloom_filter(0.01) GRANULARITY 4
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(ts)
ORDER BY (tenant_id, toStartOfHour(ts), ts);

CREATE MATERIALIZED VIEW events_1m_mv
ENGINE = AggregatingMergeTree()
ORDER BY (tenant_id, bucket_1m)
AS SELECT
    tenant_id,
    toStartOfMinute(ts) AS bucket_1m,
    quantilesState(0.95, 0.99)(latency_ms) AS lat_q
FROM events_raw GROUP BY tenant_id, bucket_1m;

Observability and analytics platforms stream events from Kafka in large batches into ClickHouse on NVMe (serving 30-day hot dashboards in <100 ms via AggregatingMergeTree), while expiring older partitions to S3 Parquet/Iceberg for ad-hoc Trino/DuckDB queries.

Hot/Cold OLAP Tiering

Kafka Batch -> ClickHouse NVMe (Hot 30d) -> S3 Iceberg (Cold)

1.Zero Part Explosion: Kafka engine / batcher flushes large blocks so MergeTree merges stay healthy.

2.90% Cost Reduction: TTL policies offload >30d partitions from expensive NVMe to S3 object storage.

3.Sub-100ms Dashboards: Queries hit pre-computed 1-minute AggregatingMergeTree states instead of scanning raw events.

Tiering NVMe ClickHouse with S3 Iceberg gives sub-100ms live dashboards and petabyte-scale cold economics.
