What is a Data Lakehouse & Medallion Architecture.

Why this matters: The mechanism: understand how a Data Lakehouse & Medallion Architecture works from first principles.

A Data Lakehouse places an open transactional metadata layer (Apache Iceberg, Delta Lake, or Apache Hudi) directly over immutable Parquet/ORC files in S3/GCS. Object stores lack in-place updates, so Iceberg maintains an atomic metadata.json catalog CAS pointer -> manifest list -> manifest files (with per-file min/max column stats) -> Parquet data files.

Data flows through three Medallion tiers: Bronze (raw append-only history), Silver (cleansed, deduplicated, conformed entities via MERGE INTO), and Gold (Z-ordered business aggregates & ML feature tables).

Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
If latency budgets leave no room for synchronous retries, data Lake & Medallion Architecture, store data once in open table formats (Apache Iceberg or Delta Lake) on cloud object storage, using Bronze/Silver/Gold tiers to progressively refine raw events into governed, query-ready business tables.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to manage Compaction, Z-Ordering & Hidden Partitioning.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Keep a Lakehouse fast with four automated maintenance jobs:

  1. Bin-Packing Compaction: Merge streaming 50 KB files into 128–512 MB Parquet files (rewrite_data_files) to prevent planner OOMs.
  2. Z-Ordering / Clustering: Sort rows inside Parquet by common filter keys (customer_id, tenant_id) so row-group min/max stats skip 95%+ of blocks.
  3. Snapshot Expiration & Vacuum: Expire snapshots >7 days and remove orphan files >24h.
  4. Hidden Partitioning: Use PARTITIONED BY (days(event_ts)) in Iceberg so queries filtering WHERE event_ts >= '2026-11-01' prune partitions automatically.
Component Topology

How to manage Compaction, Z-Ordering & Hidden Partitioning

-- Apache Iceberg table with hidden daily partitioning & maintenance procedures (Spark SQL)
CREATE TABLE silver.orders (
    order_id BIGINT,
    customer_id BIGINT,
    status STRING,
    total_cents BIGINT,
    event_ts TIMESTAMP
) USING iceberg
PARTITIONED BY (days(event_ts));

-- Periodic bin-packing compaction + Z-order clustering + snapshot expiration:
CALL system.rewrite_data_files(table => 'silver.orders', strategy => 'sort', sort_order => 'zorder(customer_id)');
CALL system.expire_snapshots(table => 'silver.orders', older_than => TIMESTAMP '2026-11-10 00:00:00');

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Architecture: Medallion Governance & File Health.

Why this matters: Production architecture: see how the components compose end to end under real load.

Think of Production Architecture: Medallion Governance & File Health as the intuition layer for Data Warehousing, Data Lake & Medallion Architecture: Production architecture: see how the components compose end to end under real load.

Enforce strict layer boundaries via catalog RBAC: restrict BI service accounts to Gold schemas, isolate backfills on Iceberg branches, and enable Deletion Vectors (Delta) or Puffin NDV sketches (Iceberg) to accelerate MERGE mutations.

Avoid Over-Partitioning

Never partition by user_id or hour + country + device_type, which creates sparse 200 KB files that destroy Parquet compression and planning speed.

Prevent Catalog Divergence

Never write directly to S3 Parquet paths bypassing the Iceberg REST / Unity Catalog—direct writes create invisible rows and stale metadata.
