THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Store data once in open table formats (Apache Iceberg or Delta Lake) on cloud object storage, using Bronze/Silver/Gold tiers to progressively refine raw events into governed, query-ready business tables.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Traditional two-tier architectures force teams to pay twice: raw files sit in an ungoverned S3 Data Lake for ML, while curated subsets are copied into an expensive proprietary Data Warehouse for BI—creating data silos, sync lag, and vendor lock-in.

  • Open table formats (Apache Iceberg, Delta Lake, Apache Hudi) add a metadata transaction log (manifests/JSON commits) on top of Parquet files in S3/GCS/ADLS.
  • ACID & Time Travel: optimistic concurrency control enables atomic writes, snapshot isolation for readers, and instant rollbacks (AS OF VERSION / TIMESTAMP).
  • Medallion Architecture: Bronze (raw, append-only history), Silver (cleansed, deduplicated, conformed entities), Gold (aggregated, business-level star schemas & feature tables).
  • Compute-storage separation: stateless engines (Trino, Spark, Snowflake, DuckDB) scale independently while reading shared Parquet files via catalog APIs (Iceberg REST, Unity Catalog).
  • File maintenance is mandatory: background compaction (OPTIMIZE), Z-ordering/clustering, and snapshot expiration (VACUUM) prevent the small-files problem.

Good candidates

  • Organizations running both BI SQL analytics and Python/Spark ML workloads over the same multi-terabyte datasets.
  • When avoiding proprietary storage lock-in (e.g., querying the same S3 data from Snowflake, Trino, Spark, and DuckDB) is a priority.
  • When teams need ACID mutations (GDPR deletes, CDC upserts, time travel) on cheap object storage.

Think twice

  • Small datasets (< 1 TB) with purely SQL/BI needs where a managed serverless warehouse (BigQuery, Snowflake, DuckDB) requires zero compaction or file-management overhead.
  • Sub-10ms point-lookup OLTP workloads, which belong in PostgreSQL, DynamoDB, or Redis—not a lakehouse.
  • Real-time operational alerting requiring < 100ms end-to-end latency, better served by ClickHouse, Apache Pinot, or Flink.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA video platform stored 400 TB of clickstream logs in S3 Parquet and copied 60 TB into Redshift nightly. Nightly COPY jobs took 4.5 hours, and GDPR deletion requests required rewriting entire monthly partitions.

The idea

Data platforms evolved across three generations: Data Warehouses (schema-on-write, fast SQL, expensive proprietary storage), Data Lakes (schema-on-read, cheap object storage, no ACID transactions or schema enforcement—often degrading into data swamps), and Data Lakehouses.

A Lakehouse places an open transactional metadata layer (Apache Iceberg, Delta Lake, or Apache Hudi) directly over immutable Parquet/ORC files in cloud object storage. This gives object storage full ACID transactions, snapshot isolation, schema evolution, and partition pruning without copying data into a proprietary warehouse. To keep transformations maintainable, Lakehouses commonly structure data through the Medallion Architecture (Bronze -> Silver -> Gold).

Concrete walkthrough

Trace a single Order Event through a Medallion Lakehouse:

  1. Bronze (Raw Ingestion): Debezium streams Postgres orders CDC events into Kafka, and Flink appends them as-is into bronze.orders_raw (Iceberg) with _ingested_at and _source_offset metadata. Zero transformations—if a downstream bug is discovered 6 months later, Silver can be replayed from Bronze.
  2. Silver (Conformed & Deduplicated): An hourly dbt/Spark job reads incremental Bronze snapshots, deduplicates by order_id keeping the latest op_ts, casts currencies to DECIMAL(18,2), masks customer_email, and MERGEs into silver.orders.
  3. Gold (Business Aggregates): A downstream model joins silver.orders with silver.customers and silver.fx_rates to materialize gold.daily_revenue_by_region—a Z-ordered, BI-optimized table powering Looker/Tableau and ML churn features.

Medallion Lakehouse architecture: raw data lands immutably in Bronze, is cleansed and conformed in Silver, and is served as business-ready Gold aggregates.

How open table formats achieve ACID on object storage

Object stores (S3, GCS) only support immutable object writes, not in-place file updates. Open table formats solve this via snapshot-based metadata trees:

  • Apache Iceberg: Maintains a metadata.json pointer (swapped atomically via catalog CAS) -> manifest list (per-snapshot partition bounds) -> manifest files (per-file min/max column stats) -> Parquet data files. Readers prune 99% of files using manifest stats without calling S3 ListObjects.
  • Delta Lake: Uses an ordered _delta_log/*.json transaction log plus periodic Parquet checkpoints. Writers use conditional PutIfAbsent (or a lock service) to claim the next sequential log version.
  • Hidden Partitioning (Iceberg): Decouples physical partitioning (days(event_ts)) from logical query filters (WHERE event_ts >= '2026-11-01'), preventing user errors that cause full-table scans.

Failure modes

  • Metadata Bottleneck: Uncompacted Iceberg/Delta tables with 100,000+ small files cause coordinator OOMs during query planning.
  • Over-Partitioning: Partitioning by hour + country + device_type creates sparse 200 KB files that destroy Parquet compression and I/O throughput.
  • Dangling Delete Files (MoR): Heavy CDC MERGE workloads using Merge-on-Read accumulate thousands of positional/equality delete files, degrading read latency by 10x until compacted.
  • Catalog Divergence: Writing directly to S3 Parquet paths bypassing the Iceberg/Unity Catalog causes stale metadata and invisible rows.

Maintenance and performance tuning

Keep a Lakehouse fast with four automated jobs:

  1. Bin-Packing Compaction: Merge small files into 256–512 MB Parquet files every few hours for streaming tables.
  2. Data Clustering / Z-Ordering: Sort rows inside Parquet files by common filter/join keys (customer_id, tenant_id) so min/max row-group statistics skip 95%+ of blocks.
  3. Snapshot Expiration & Vacuum: Expire snapshots older than 7 days and delete orphan files > 24 hours old to cap S3 storage growth.
  4. Deletion Vectors / Puffin Stats: Enable deletion vectors (Delta) or Puffin NDV sketches (Iceberg) to accelerate MERGE mutations and join reordering.

Practical checklist

  • Standardize on an open table format (Apache Iceberg or Delta Lake) backed by a unified catalog (Iceberg REST, Unity Catalog, AWS Glue).
  • Enforce strict separation: Bronze (raw, restricted PII), Silver (deduplicated, conformed), Gold (BI/ML-ready).
  • Target 128–512 MB file sizes and coarse partitioning (e.g., day or month, never user_id).
  • Automate background compaction, Z-ordering, and snapshot expiration jobs.
  • Enable time-travel retention (e.g., 7 days) for instant rollback after bad pipeline deployments.
03 / Engineering trade-offs

Weighing architectural decisions

Open Lakehouse vs. Proprietary Cloud Warehouse

Advantage: Zero storage lock-in, multi-engine interoperability (Spark, Trino, DuckDB), and 5–10x cheaper raw storage ($23/TB/mo on S3).

Drawback: Requires managing table maintenance (compaction, vacuuming, manifest rewriting) unless using a managed catalog service.

Copy-on-Write (CoW) vs. Merge-on-Read (MoR)

Advantage: CoW delivers fastest read performance because no delete files need to be merged at query time.

Drawback: CoW rewrites entire 256 MB Parquet files for a single-row update; MoR speeds up CDC writes at the cost of slightly slower reads until compaction.

Strict 3-Hop Medallion vs. Virtualized Views

Advantage: Materializing Bronze, Silver, and Gold creates clear replayability, auditability, and decoupled SLAs.

Drawback: Materializing every intermediate hop triples storage writes and adds end-to-end latency if Silver is needlessly duplicated.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

The Small-Files Problem

Streaming jobs commit thousands of 50 KB Parquet files per hour, causing query planners to spend minutes listing metadata and exhausting memory.

What helps: Schedule asynchronous bin-packing compaction (`rewrite_data_files`) to target 128–512 MB Parquet files and buffer streaming writes into 1–5 minute micro-batches.

Unbounded Snapshot & Orphan File Bloat

Frequent streaming commits accumulate tens of thousands of historical snapshots and unreferenced Parquet files, inflating S3 bills and planning time.

What helps: Run automated snapshot expiration (e.g., retain 7 days) and orphan-file cleanup (`VACUUM`) while preserving tagged compliance snapshots.

Medallion Layer Leakage

BI dashboards query Bronze raw JSON directly or Silver tables contain unmodeled business-specific KPIs, breaking clean separation of concerns.

What helps: Restrict BI tool service accounts to Gold schemas via catalog RBAC, and enforce Silver-to-Gold modeling in dbt/SQLMesh.

Concurrent Write Contention

Multiple Spark jobs or compaction workers update the same partition simultaneously, triggering optimistic concurrency `CommitFailedException` loops.

What helps: Partition writes cleanly by ingestion date/region, use isolated Iceberg branches for backfills, and schedule compaction off-peak or with lock-free MoR.

05 / Practical checklist

Avoid these mistakes

  • Treating Bronze, Silver, and Gold as rigid physical folders that must always be 3 separate materialized tables even when a simple view suffices.
  • Partitioning tables on high-cardinality columns (e.g., `user_id` or `timestamp_ms`), creating millions of tiny partitions and killing query pruning.
  • Ignoring Parquet row-group sorting (Z-ordering / Hilbert curves) on high-selectivity filter columns like `tenant_id` or `order_id`.
  • Running `VACUUM` with a 0-hour retention window while long-running queries are still reading older snapshots, causing `FileNotFoundException`.
  • Leaving raw PII unencrypted or unmasked in Bronze without strict IAM isolation, turning Bronze into a compliance liability.
