HTTP Semantics
& Caching.

HTTP caching (RFC 9111) uses explicit freshness lifetimes, validation headers (ETag/Last-Modified), and Vary keys so browsers, CDNs, and reverse proxies serve safe, fast responses without stale leaks.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Separate immutable static assets (Cache-Control: public, max-age=31536000, immutable) from dynamic APIs (Cache-Control: no-cache + ETag revalidation), and use Vary carefully so you never fragment cache hit ratios or leak user-specific responses.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Every uncached request that hits an origin server pays full TLS/origin compute, database I/O, and cross-region RTT (50–250 ms). Properly configured HTTP caching offloads 70–95% of traffic to edge CDNs (Cloudflare, Fastly, CloudFront) and browser caches, cutting p95 latency under 15 ms. Conversely, a single misconfigured Cache-Control or missing Vary header can cache authenticated PII on a shared CDN and serve User A's account page to User B.

  • Cache-Control directives govern storage and freshness: no-store forbids all caching; no-cache allows storage but mandates origin revalidation before every reuse; private restricts storage to the browser, blocking shared CDNs.
  • Freshness lifetime is computed from s-maxage (shared caches only) -> max-age -> Expires, compared against the response Age header; stale-while-revalidate lets caches serve slightly expired content while refreshing asynchronously.
  • Conditional validation uses strong/weak ETag (If-None-Match) or Last-Modified (If-Modified-Since) to return 304 Not Modified without resending the response body.
  • The Vary header defines secondary cache keys (e.g., Vary: Accept-Encoding, Accept-Language); Vary: User-Agent or Vary: Cookie destroys CDN cache hit ratios by creating thousands of distinct keys.
  • Unsafe methods (POST, PUT, DELETE, PATCH) must invalidate matching cached URI entries on compliant caches, while GET and HEAD are safe and cacheable by default when freshness headers are present.

Good candidates

  • Content-hashed static assets (JS, CSS, fonts, images) where filenames change on every build, enabling 1-year immutable caching.
  • Public or semi-static read APIs (catalogs, feature flags, product pages) where 10–60 second edge TTLs plus stale-while-revalidate absorb traffic spikes.
  • Large payloads (JSON schemas, media manifests) where ETag / If-None-Match conditional requests turn 500 KB downloads into 300-byte 304 Not Modified responses.

Think twice

  • Personalized, authenticated, or financial endpoints unless explicitly marked Cache-Control: private, no-store (or private, max-age=0, must-revalidate).
  • Real-time transactional state (live inventory counts, payment status) where even a 2-second stale read breaks business invariants.
  • Non-idempotent or state-mutating methods (POST, PUT, DELETE), which RFC 9111 forbids standard caches from serving without explicit invalidation.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA storefront serves app.8f3c2a.js (420 KB) and /api/v1/catalog/featured (65 KB JSON, updated every 5 minutes) behind Fastly.

The idea

HTTP is not merely a transport framing protocol—RFC 9110 (Semantics) and RFC 9111 (Caching) encode a distributed caching contract directly into request and response headers. Every intermediary—browser cache, corporate proxy, Varnish/Nginx reverse proxy, and global CDN—reads the same headers to answer two questions: Can I store this response? and Can I reuse it without asking the origin?

Storage rules come from Cache-Control: no-store forbids persistence; private allows only single-user browser caches; public permits shared caches. Freshness rules compare a response's calculated lifetime (s-maxage for shared caches, else max-age, else Expires - Date) against its Age. While Age < lifetime, the response is fresh and served directly from cache in 1–15 ms.

Once Age >= lifetime (or if no-cache was specified), the entry becomes stale. Rather than discarding it, the cache sends a conditional request (If-None-Match: "v42" or If-Modified-Since) to the origin. If the resource has not changed, the origin replies 304 Not Modified with an empty body and refreshed headers, resetting freshness without transferring megabytes of payload.

Concrete walkthrough

Trace a product catalog request GET /v1/products/42 with Accept-Encoding: br traversing a Browser -> Cloudflare Edge POP -> Origin API (Node/Go + Postgres):

  1. Cold Cache Miss (t = 0s): The browser has no entry. Cloudflare hashes the primary key (GET, https://api.example.com/v1/products/42) and misses. It forwards the request to Origin. Origin queries Postgres (18 ms) and responds 200 OK with Cache-Control: public, max-age=15, s-maxage=60, stale-while-revalidate=120, ETag: "9d4f2a", and Vary: Accept-Encoding.
  2. Shared & Private Storage: Cloudflare stores the Brotli-compressed body keyed by (URL, Accept-Encoding=br) with a 60-second shared TTL. The browser stores it for 15 seconds (max-age=15).
  3. Fresh Edge Hit (t = 25s): A second user in the same city requests /v1/products/42. Cloudflare sees Age: 25 < s-maxage: 60 and returns 200 OK in 9 ms—Origin sees zero traffic.
  4. Stale-While-Revalidate (t = 75s): Another user arrives at t = 75s. The 60s s-maxage has expired, but 75s < 60s + 120s (stale-while-revalidate). Cloudflare immediately serves the stale cached response in 9 ms while asynchronously sending GET /v1/products/42 with If-None-Match: "9d4f2a" to Origin.
  5. 304 Revalidation: Origin checks the row version, sees it is still "9d4f2a", and returns 304 Not Modified (no body, 220 bytes of headers). Cloudflare resets Age: 0 for another 60 seconds.

HTTP caching lifecycle: browser private cache, shared CDN freshness with s-maxage, stale-while-revalidate non-blocking refresh, and 304 ETag validation.

Cache keys, Vary, and surrogate keys

By default, an HTTP cache keys entries by (HTTP Method, Scheme, Host, Path + Query). Two subtle mechanisms control key cardinality and invalidation:

  • Vary (Secondary Cache Keys): When an origin returns Vary: Accept-Encoding, Accept-Language, the cache stores separate variants per header value tuple. Avoid Vary: User-Agent or Vary: Cookie—a single popular endpoint can fracture into 50,000+ cold keys. If you must vary on auth or device type, normalize at the edge into a coarse header (e.g., X-Device-Class: mobile|desktop).
  • Surrogate-Key / Cache-Tag: URL-based purging fails when a single product update affects /products/42, /category/shoes, and /search?q=running. CDNs like Fastly and Cloudflare support Surrogate-Key: product-42 cat-shoes (stripped before reaching the browser), enabling O(1) tag-based invalidation across thousands of cached URLs simultaneously while keeping s-maxage high (e.g., 24 hours).

Failure modes

  • Web cache poisoning via unkeyed headers: If an origin reads X-Forwarded-Host or X-Original-URL to build script URLs in HTML without listing that header in Vary, an attacker can send a crafted header on a cache miss and poison the CDN entry for all subsequent users.
  • Cache stampede on TTL expiration: Without stale-while-revalidate or request coalescing (collapsed forwarding), a hot key expiring at s-maxage=60 unleashes hundreds of simultaneous origin queries.
  • Set-Cookie stripping or accidental caching: Sending Set-Cookie on a 200 OK with Cache-Control: public can either cache a session cookie for all users or cause CDNs to silently bypass caching.
  • Query string cache busting abuse: Attackers appending ?cb=random123 to bypass CDN caches and hit the origin directly unless query parameters are allowlisted in the CDN cache key.

Designing cacheable APIs & HTML shells

A reliable web architecture pairs two distinct caching tiers:

  1. HTML Entrypoints (index.html): Serve with Cache-Control: no-cache (or s-maxage=10, stale-while-revalidate=60) and a strong ETag. Clients always get the latest deployment manifest via a fast 304 check.
  2. Fingerprinted Assets & Read APIs: Serve JS/CSS/images with content hashes and max-age=31536000, immutable. For read APIs, strip cookies on public endpoints, prefer Surrogate-Key invalidation over tiny TTLs, and set stale-if-error=86400 so the CDN continues serving the last good response if the origin returns 500/502/504.

Practical checklist

  • Default all authenticated or user-scoped endpoints to Cache-Control: private, no-store.
  • Use Cache-Control: public, max-age=31536000, immutable for all content-hashed static bundles.
  • Add stale-while-revalidate and stale-if-error on public read APIs to eliminate stampedes and mask origin blips.
  • Audit Vary headers; never emit Vary: User-Agent or Vary: * on CDN-fronted routes.
  • Enable request coalescing (collapsed forwarding) at the reverse proxy/CDN for cache misses.
  • Ensure Surrogate-Key / Cache-Tag headers are stripped at the edge before forwarding responses to browsers.
03 / Engineering trade-offs

Weighing architectural decisions

Long TTLs vs. Instant Content Updates

Advantage: Maximizes edge offload (95%+) and shields origins from thundering herds.

Drawback: Requires content-hashed filenames or active purge APIs (e.g., Cloudflare/Fastly surrogate-key purges) to retract bad deploys.

no-cache + ETag vs. max-age=0 / no-store

Advantage: `no-cache` with `ETag` saves bandwidth via `304 Not Modified` while guaranteeing freshness on every request.

Drawback: Still incurs a full network round-trip to the origin (or shielding POP) to validate the ETag on every load.

Granular Vary Headers vs. Cache Hit Ratio

Advantage: Prevents serving compressed gzip bytes to non-gzip clients or wrong-language pages.

Drawback: Every unique value combination of `Vary` headers multiplies cache keys; `Vary: *` or `Vary: User-Agent` collapses hit rates toward 0%.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Authenticated PII Cache Leak

An endpoint returns user-specific data with `Cache-Control: public` or no `Cache-Control` header behind a permissive CDN rule, causing the shared cache to serve one user's data to subsequent visitors.

What helps: Default all authenticated API middleware to `Cache-Control: private, no-store` and add automated CI/gateway assertions that block `public` or `s-maxage` when `Set-Cookie` or `Authorization` is present.

Cache Key Explosion via Unbounded Vary

Returning `Vary: User-Agent` or `Vary: Accept-Encoding, Accept` splits a single popular URL into tens of thousands of cache variants across Chrome/Safari/Firefox minor versions.

What helps: Normalize `Accept-Encoding` at the CDN edge to `{gzip, br, identity}` and strip `Vary: User-Agent` in favor of responsive CSS or normalized device-class headers.

Thundering Herd on Synchronized TTL Expiry

A hot endpoint with `s-maxage=60` expires simultaneously across 50 edge POPs, sending 50x–500x concurrent origin requests that overwhelm database connections.

What helps: Combine `s-maxage=60` with `stale-while-revalidate=120` and `stale-if-error=600`, plus request coalescing (collapsed forwarding) at the reverse proxy/CDN.

Misunderstanding no-cache vs. no-store

Developers set `Cache-Control: no-cache` expecting sensitive medical or financial payloads never to be written to disk, unaware that browsers still store the response locally and merely revalidate it.

What helps: Use `Cache-Control: no-store` for sensitive data that must never touch disk or shared memory, and reserve `no-cache` for payloads that should be cached but revalidated.

05 / Practical checklist

Avoid these mistakes

  • Confusing `no-cache` (store, but revalidate before reuse) with `no-store` (do not store anywhere).
  • Omitting `immutable` on fingerprinted static assets, causing browsers on manual reload (F5) to fire unnecessary `If-None-Match` revalidation bursts.
  • Setting both `Expires` and `Cache-Control` with conflicting values, forgetting that `Cache-Control: max-age` / `s-maxage` always overrides `Expires` per RFC 9111.
  • Returning weak ETags (`W/"abc"`) for byte-range requests (`Range: bytes=0-1023`), which RFC 9110 forbids for `206 Partial Content` coalescing.
  • Using `Vary: Cookie` on public marketing pages because an analytics cookie is present, reducing CDN cache hit rate to near zero.
