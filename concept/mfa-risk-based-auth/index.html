MFA &
Risk-Based Authentication.

Risk-based Multi-Factor Authentication (RBA) evaluates contextual telemetry—device posture, ASN/GeoIP, impossible travel, and TLS fingerprints—in real time to dynamically step up high-risk logins to phishing-resistant WebAuthn/FIDO2 while keeping trusted sessions frictionless.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Static SMS/push MFA fails against AiTM reverse-proxy phishing and MFA fatigue; pair FIDO2/WebAuthn (origin-bound keys) with a contextual risk engine that challenges only anomalous logins and revokes sessions on mid-session risk spikes.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Credential stuffing and Adversary-in-the-Middle (AiTM) phishing proxies (like Evilginx) routinely bypass passwords and even TOTP/SMS codes by relaying them in real time, while attackers overwhelm users with push notifications (MFA fatigue) until someone taps Approve. Risk-based authentication combined with origin-bound FIDO2/WebAuthn stops both classes of attack without forcing legitimate users to solve MFA on every page load.

  • Phishing-resistant MFA (FIDO2 / WebAuthn / Passkeys) cryptographically binds the signature to the exact TLS rpId domain, making AiTM reverse-proxy phishing mathematically impossible.
  • Risk engines score signals in <50 ms: known device cookie/fingerprint, IP reputation (Tor/VPN/residential proxy ASN), impossible travel (>800 km/h between logins), and JA4 TLS fingerprint.
  • Push MFA must enforce Number Matching (user types a 2-digit code shown on the login screen) and display app/location context to defeat MFA fatigue bombing.
  • Authentication Context Class Reference (acr) and Authentication Methods References (amr) claims in OIDC ID/access tokens let downstream APIs enforce step-up before sensitive actions (e.g., wire transfers).
  • Continuous Access Evaluation (CAEP / Shared Signals) extends risk checks beyond login time, revoking refresh tokens mid-session if a device loses MDM compliance or changes ASN mid-session.

Good candidates

  • Consumer and enterprise SSO gateways (OIDC / SAML) protecting high-value accounts, admin consoles, or financial transfers.
  • Reducing login friction for trusted corporate devices (mTLS/MDM-enrolled laptops on corporate VPN) while requiring strong step-up for unknown IPs or new browsers.
  • Meeting NIST SP 800-63B AAL2/AAL3 or PCI-DSS / SOC2 compliance requirements for phishing-resistant authentication and adaptive session protection.

Think twice

  • Machine-to-machine (M2M) service accounts—use short-lived OIDC workload identity tokens, SPIFFE/mTLS certificates, or asymmetric JWTs rather than interactive MFA.
  • Emergency break-glass recovery paths without an offline backup key—locking out all admins because a risk engine flagged a datacenter outage IP can prolong a P0 incident.
  • Public, unauthenticated read-only endpoints where session state and user identity do not exist.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAttackers bought stolen employee credentials, automated 40 push-MFA prompts at 2:00 AM until a fatigued engineer tapped Approve, and harvested session cookies via an Evilginx proxy.

The idea

Traditional MFA applies a blunt, static rule: ask every user for a second factor on every login, regardless of context. That creates two problems: friction fatigue (users blindly tap Approve on push prompts) and channel vulnerability (SMS and TOTP codes can be phished by Adversary-in-the-Middle proxies).

Risk-based authentication (RBA) separates session assurance from static checklists. On every authentication or sensitive action, an Auth Gateway streams contextual telemetry to a Risk Scoring Engine in <50 ms. Low-risk logins from a recognized, healthy device pass silently; medium-risk logins trigger a phishing-resistant FIDO2/WebAuthn step-up (cryptographically bound to the exact domain origin); and high-risk logins (impossible travel, known credential-stuffing ASN) are blocked and trigger token revocation.

Concrete walkthrough

Trace an OIDC login attempt to auth.example.com protected by RBA + WebAuthn:

  1. Primary credential & telemetry capture: User submits username/password (or passkey identifier). The Auth Gateway collects client IP, ASN, MaxMind GeoIP2 coordinates, JA4 TLS fingerprint, and a signed HTTP-only device token.
  2. Sub-50 ms risk scoring: The Risk Engine checks Redis for recent login locations. Last login was 20 minutes ago in Bengaluru (12.97°N, 77.59°E); this attempt originates from a residential proxy ASN in Frankfurt (50.11°N, 8.68°E)—an impossible travel velocity of ~21,000 km/h. Risk score jumps to 68 (Medium-High).
  3. Phishing-resistant step-up: Rather than trusting a password or sending an SMS, the gateway generates a 32-byte cryptographic challenge (WebAuthn AssertionOptions) with rpId: "auth.example.com".
  4. Origin-bound verification: The browser's WebAuthn API verifies the TLS origin matches auth.example.com (blocking any AiTM proxy on auth-example.evil.com), prompts the user's biometric/YubiKey, and returns the ECDSA signature.
  5. Claim issuance: The gateway verifies the signature against the user's stored public key and issues an OIDC ID Token stamped with acr: "aal3" and amr: ["pwd", "hwk"]. Downstream payment APIs inspect acr before allowing wire transfers.

Risk-based auth keeps trusted logins fast while forcing high-risk sessions through domain-bound WebAuthn verification.

Factor strength and NIST AAL levels

Not all second factors defend against the same threat model:

  • SMS / Voice OTP (NIST AAL2 deprecated/restricted): Vulnerable to SIM swapping, carrier social engineering, and SS7 interception. Avoid for admin or financial accounts.
  • TOTP (RFC 6238, 30 s window) & Number-Matched Push: Defeats credential stuffing and MFA fatigue, but remains vulnerable to AiTM reverse-proxy phishing because the user manually types or approves a code that a proxy can relay.
  • FIDO2 / WebAuthn & Passkeys (NIST AAL3 when hardware-backed): Phishing-resistant. The browser includes the exact TLS origin in clientDataJSON, so an attacker's proxy domain cannot obtain a valid signature for your real domain.

Failure modes

1. Account lockout / DoS via bad risk tuning: Blocking entire mobile carrier ASNs or VPN providers locks out legitimate travelers. Treat high risk as step-up to WebAuthn whenever possible, reserving hard blocks for verified credential-stuffing signatures or breached passwords.

2. Recovery path downgrade: Requiring a YubiKey to log in is pointless if the "Forgot my security key" flow lets an attacker reset MFA using only an email link or SMS code. Recovery must match or exceed the primary AAL.

3. Stale session cookies after password reset: Changing a password or flagging a session as compromised without revoking active refresh tokens and short-lived JWTs (via a Redis revocation list or CAEP event) leaves the attacker logged in.

Step-up auth and continuous evaluation

Authentication is not a one-time gate at /login. Implement step-up authorization using OIDC acr_values when a user attempts high-impact mutations (changing payout bank details, creating API keys, exporting bulk data) even if they logged in 20 minutes ago.

For long-lived sessions, adopt Continuous Access Evaluation (CAEP) patterns: if the user's IP shifts to a new country/ASN mid-session or their corporate MDM device posture flips to non-compliant, invalidate the refresh token immediately and force a fresh WebAuthn assertion.

Practical checklist

  • Prioritize FIDO2 / WebAuthn (Passkeys or hardware keys) as the default second factor for all privileged and high-value accounts.
  • Enable Number Matching and geographic/app context on any legacy Push MFA, and deprecate SMS OTP.
  • Enforce strict rate limiting on TOTP/OTP verification (e.g., max 5 attempts per 15 minutes) and encrypt TOTP seeds at rest.
  • Configure the risk engine to fail-safe to step-up MFA (never allow) on timeouts, keeping evaluation latency under 50 ms.
  • Disable legacy basic-auth protocols (IMAP/POP3/SMTP auth) and revoke all active refresh tokens on password reset or high-risk anomaly.
03 / Engineering trade-offs

Weighing architectural decisions

FIDO2 / WebAuthn vs. TOTP / SMS OTP

Advantage: WebAuthn is origin-bound (immune to AiTM phishing), requires zero shared secrets on the server, and completes in one biometric tap.

Drawback: Requires cross-device passkey sync (iCloud/Google) or hardware keys (YubiKey) and clear recovery flows if a user loses their primary device.

Strict Risk Thresholds vs. User Friction

Advantage: Aggressive risk scoring blocks VPNs, Tor exit nodes, and new ASNs immediately, minimizing account takeover blast radius.

Drawback: Legitimate travelers, privacy-conscious VPN users, and mobile CGNAT carriers (where IPs hop cities) suffer false-positive lockouts.

Fail-Closed vs. Fail-Open Risk Engine

Advantage: Failing closed (forcing step-up MFA when the risk service times out) guarantees attackers cannot bypass MFA by DDoSing the risk scorer.

Drawback: If the risk engine has a 500 ms latency spike or outage, every user gets challenged—or blocked if their MFA channel is also degraded.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

AiTM Reverse-Proxy Session Hijacking

An attacker hosts `login-corp.evil.com`, proxies traffic to the real IdP, and tricks the user into entering password + TOTP/SMS; the proxy steals the resulting `Set-Cookie` session token.

What helps: Mandate FIDO2/WebAuthn (which verifies `rpId` matches the real origin) and bind session cookies to device keys (DBSC / Token Binding).

MFA Fatigue (Push Bombing)

Attacker scripts repeated login attempts with a leaked password, flooding the victim's phone with push prompts until they tap Approve by mistake or annoyance.

What helps: Require Number Matching on all push prompts, rate-limit push requests (e.g., max 3 per 15 min), and lock the account on repeated denials.

SIM-Swapping & SS7 Interception

Attackers bribe or socially engineer a mobile carrier to port the victim's phone number to an attacker SIM, intercepting SMS OTPs in minutes.

What helps: Deprecate SMS OTP for high-value accounts in favor of WebAuthn/Passkeys or app-based TOTP (RFC 6238).

Risk Engine Latency / Fail-Open Bypass

A slow GeoIP/ML risk model times out at 2 seconds and the auth gateway defaults to `risk=0` (allow), letting credential-stuffing bots slip through unchallenged.

What helps: Keep risk evaluation under 50 ms using local MaxMind MMDB/Redis caches and fail-safe to `step-up MFA` (never `allow`) on timeout.

05 / Practical checklist

Avoid these mistakes

  • Treating SMS OTP or un-numbered Push notifications as equivalent to FIDO2/WebAuthn against targeted phishing.
  • Checking risk only at `/login` and never re-evaluating `acr`/`amr` or IP/device changes during a 30-day refresh-token lifetime.
  • Leaving legacy authentication protocols (IMAP, POP3, SMTP basic auth, XML-RPC) enabled, which completely bypass modern OIDC MFA policies.
  • Allowing unlimited TOTP guesses (`6 digits = 1,000,000` combinations) without strict per-user rate limiting (e.g., 5 attempts per 15 min).
  • Storing TOTP shared secrets in plaintext in the database instead of encrypting them with an envelope KMS key.
