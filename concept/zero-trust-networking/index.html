Zero Trust
Networking.

Zero-trust networking replaces implicit IP- and VLAN-based perimeter trust with cryptographic workload identity (SPIFFE/mTLS), continuous device/user attestation, and per-request L7 authorization (Envoy/OPA) on every hop.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Never trust a packet because it arrived on a private RFC 1918 subnet; authenticate every caller's short-lived X.509 SVID over mTLS and authorize the exact HTTP/gRPC action on every service boundary.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Traditional castle-and-moat networks assume anything inside 10.0.0.0/8 is benign. Once an attacker compromises a single CI runner, SSRF-vulnerable pod, or developer laptop over VPN, flat internal networks allow unconstrained lateral movement to databases and KMS endpoints. In ephemeral Kubernetes and multi-cloud clusters where pod IPs recycle every few minutes, IP allowlists are both operationally brittle and security-blind—only cryptographic identity scales.

  • Every workload receives a cryptographic identity—typically a SPIFFE ID (spiffe://prod.internal/ns/payments/sa/ledger-api) encoded in a short-lived X.509 SVID (1-hour to 24-hour TTL) rotated automatically without restarts.
  • Transport encryption and mutual authentication (mTLS via TLS 1.3) ensure both client and server verify each other's certificates before exchanging a single application byte.
  • Authorization is evaluated per request at L7 (Envoy RBAC, OPA/Rego, or Cilium eBPF) using (caller_spiffe_id, user_jwt_claims, method, path)—not source IP or CIDR blocks.
  • User-to-service access uses Identity-Aware Proxies (OIDC/OAuth2 + device posture/TPM attestation) so compromised credentials on an unmanaged device are still rejected.
  • Default-deny network posture: services reject all unauthenticated or unauthorized RPCs, and egress proxies restrict outbound calls to explicitly allowlisted domains/APIs.

Good candidates

  • Multi-tenant or regulated microservices (PCI-DSS, HIPAA, SOC 2) in Kubernetes/ECS where lateral movement after a single pod compromise must be blocked by default-deny L7 policies.
  • Hybrid or multi-cloud architectures (e.g., AWS EKS calling on-prem Postgres or GCP Cloud Run) where traffic traverses untrusted WANs without relying on brittle site-to-site IPsec tunnels.
  • Remote engineering access to internal admin panels, CI/CD, and production APIs via Identity-Aware Proxies (Cloudflare Access, Google BeyondCorp IAP, Tailscale) instead of broad corporate VPNs.

Think twice

  • Ultra-low-latency (<100 microsecond) IPC or kernel-bypass HPC/HFT fabrics (RDMA/DPDK) inside a physically isolated single-tenant rack where per-packet TLS/sidecar proxy hops blow the latency budget.
  • Legacy embedded OT/SCADA hardware incapable of TLS 1.3 or short-lived certificate rotation, which must instead be isolated behind terminating zero-trust gateways.
  • Single-process monoliths or isolated dev sandboxes where adding a full SPIRE + Envoy control plane introduces operational complexity without meaningful trust boundaries.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn attacker exploits a deserialization CVE in a public-facing frontend-web pod (10.24.8.19) and attempts to query ledger-db-proxy:5432 and kms-signer:8443 directly from a shell inside the pod.

The idea

Per NIST SP 800-207, zero-trust networking starts from a single premise: network location does not imply trust. Whether a packet originates from a coffee-shop Wi-Fi, a corporate office LAN, or 10.42.0.15 inside your own Kubernetes VPC, it is treated as untrusted until proven otherwise.

Instead of defending a static IP perimeter, zero trust binds security to cryptographic identity and per-request context:

  1. Workload Identity (SPIFFE/SPIRE): Every service instance proves who it is via node/platform attestation (AWS IID, K8s projected ServiceAccount token, or hardware TPM 2.0) and receives a short-lived X.509 certificate (SVID) encoding its canonical URI (spiffe://trust-domain/ns/payments/sa/checkout).
  2. Mutual TLS (mTLS): Both caller and callee present and verify SVIDs over TLS 1.3, guaranteeing confidentiality, integrity, and mutual authentication on every hop.
  3. Policy Decision & Enforcement (PDP/PEP): An in-line Policy Enforcement Point (Envoy proxy or Identity-Aware Proxy) evaluates each request against least-privilege rules combining who the caller is (SPIFFE ID), who the end-user is (verified OIDC JWT), and what action is requested (POST /v1/refunds).

Concrete walkthrough

Trace an engineer triggering a refund via an internal support tool (https://support.corp.internal) backed by support-bff -> payments-api in Kubernetes:

  1. User & Device Attestation: The engineer's browser hits the Identity-Aware Proxy (IAP). IAP redirects to the OIDC IdP, verifies a hardware FIDO2 passkey plus MDM device-posture claim (disk_encrypted=true, os_patched=true), and attaches a 15-minute signed JWT (sub=alice@corp.com, role=support_l2) before forwarding to support-bff.
  2. Workload Identity Issuance: On the Kubernetes worker node, the local SPIRE Agent attests support-bff's pod UID and projected ServiceAccount token against the Kubelet, then delivers a 1-hour X.509 SVID (spiffe://prod.corp/ns/support/sa/support-bff) over a Unix domain socket via Envoy SDS.
  3. mTLS Handshake: support-bff calls https://payments-api.prod.svc:8443/v1/refunds. Its local Envoy sidecar initiates TLS 1.3 mTLS with payments-api's Envoy sidecar. Both sides validate the SPIFFE trust-bundle root CA and SAN URI (~1.4 ms new handshake, <0.1 ms on pooled HTTP/2 connection).
  4. L7 Policy Evaluation: payments-api's Envoy PEP inspects the verified peer SPIFFE ID (support-bff), the forwarded OIDC JWT (role=support_l2), and the HTTP route (POST /v1/refunds). Its compiled RBAC/OPA rule (allow if peer == support-bff AND jwt.role in ['support_l2', 'finance']) passes in 0.3 ms and forwards the request to the payments-api container over localhost.

Zero-trust request path: SPIRE provisions short-lived workload SVIDs, IAP attests user/device context, and Envoy enforces mTLS plus L7 RBAC on every service hop.

Workload identity, mTLS, and policy enforcement

A production zero-trust fabric separates identity issuance from policy enforcement:

  • SPIFFE / SPIRE: Solves the "secret zero" problem—how a freshly booted container gets its first credential without baking static API keys into images. SPIRE verifies platform-native signals (AWS EC2 instance identity documents signed by AWS, GCP instance metadata JWTs, or Kubernetes projected ServiceAccount tokens) before minting an X.509 SVID with a 1-hour lifetime.
  • mTLS & Connection Pooling: TLS 1.3 reduces full handshakes to 1 RTT (~1–2 ms intra-region). By keeping HTTP/2 or gRPC connections pooled between Envoy sidecars, subsequent RPCs amortize handshake cost to near zero while retaining per-stream L7 authorization.
  • Defense in Depth (L4 + L7): Pair kernel eBPF/CNI NetworkPolicy (blocking unexpected ports like SSH/22 or direct DB access) with L7 Envoy/OPA policies (restricting GET /users/* vs. DELETE /users/*), since L4 firewalls alone cannot inspect HTTP verbs or JWT claims.

Failure modes

  • CA outage exceeding SVID TTL: If SPIRE Server / Istiod is down longer than the 1-hour SVID lifetime, rotating certificates fail and all east-west mTLS traffic collapses simultaneously.
  • Permissive mode drift: Teams enable mTLS: PERMISSIVE during migration and forget to flip to STRICT, allowing unauthenticated plaintext lateral movement.
  • Header spoofing (Confused Deputy): Backends trust X-Forwarded-User headers from any mTLS peer without validating who is allowed to assert end-user identity.
  • Centralized PDP latency/outage: Making synchronous remote calls to an external OPA server on every RPC turns policy evaluation into a single point of failure.

Operational sizing & rotation math

Two quantitative rules keep a zero-trust mesh reliable at scale:

  1. Certificate Rotation Budget: With 10,000 pods and a 1-hour SVID TTL rotated at 50% lifetime (30 min), the CA signs 10,000 / 1,800s ≈ 5.6 CSRs/sec steady-state—but during a simultaneous node-pool scale-up of 2,000 pods, burst signing hits 300+ CSRs/sec. Size SPIRE/Istiod CPU for 10x burst CSR signing and set cert_rotation_jitter to prevent thundering herds.
  2. mTLS CPU & Memory Overhead: At 50,000 RPS across Envoy sidecars using AES-128-GCM (hardware AES-NI) and pooled HTTP/2 connections, TLS framing adds ~3–6% CPU, while Envoy connection buffers and xDS config consume ~60–120 MB RSS per pod (rising to 300+ MB if cluster-wide Sidecar egress scoping is omitted).

Practical checklist

  • Enforce STRICT TLS 1.3 mTLS across all production namespaces; verify zero plaintext listeners remain.
  • Issue short-lived workload SVIDs (1–24h TTL) via SPIRE or mesh CA with automatic rotation at 50% lifetime and 500 ms max NTP/Chrony clock skew.
  • Scope Envoy Sidecar / AuthorizationPolicy manifests to explicit (caller_spiffe_id, method, path) tuples—never principals: ["*"].
  • Validate OIDC/JWT signatures and strip untrusted X-User-* headers at the edge and service boundaries.
  • Run OPA/RBAC evaluation in-process (Envoy native RBAC or Wasm) rather than synchronous remote PDP calls.
  • Lock down pod egress with default-deny egress proxies and maintain a documented break-glass runbook for IdP/CA outages.
03 / Engineering trade-offs

Weighing architectural decisions

Sidecar Proxy (Envoy/Istio) vs. Ambient / Kernel eBPF (Cilium)

Advantage: Sidecars enforce rich L7 HTTP/gRPC RBAC, JWT validation, and per-RPC telemetry uniformly across any language.

Drawback: Adds ~1–2 ms p99 latency per hop and ~50–100 MB RAM + 0.05–0.15 vCPU per pod; ambient/eBPF modes cut memory by moving L4 mTLS to node-level ztunnel/kernel.

Short-Lived SVIDs (1h TTL) vs. Long-Lived Certs + CRL/OCSP

Advantage: Eliminates brittle CRL/OCSP revocation lookups on the hot path—stolen certs expire automatically within 60 minutes.

Drawback: Requires a highly available, low-latency local SDS/SPIRE Agent on every node; if the CA control plane stalls for >1h, workloads lose valid certs simultaneously.

Strict Default-Deny Policy vs. Developer Velocity

Advantage: Prevents shadow APIs and accidental over-privileged service-to-service paths from reaching production.

Drawback: New microservice integrations fail with `403` until explicit `AuthorizationPolicy` manifests are reviewed and deployed in CI/CD.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Mesh-Wide Certificate Expiry Outage

The root/intermediate CA (SPIRE Server or Istiod) fails to rotate intermediate signing keys or nodes lose connectivity to the CA for longer than the SVID TTL (e.g., 1–24 hours), causing all mTLS handshakes across the cluster to fail simultaneously.

What helps: Monitor `cert_expiry_seconds_remaining` with alerts at 50% TTL, configure overlapping rotation at 50% lifetime, run HA multi-AZ CA replicas, and keep intermediate TTLs (7–30 days) well above workload SVID TTLs (1–24h).

Confused Deputy via Unvalidated JWT / Header Forwarding

Service A authenticates over mTLS to Service B and forwards a user's `X-User-Id` header or unverified JWT; Service B trusts the header without verifying the JWT signature or restricting which callers may assert user context.

What helps: Strip untrusted `X-User-*` headers at the edge proxy, validate signed OIDC/JWT tokens at every L7 hop (or mint short-lived actor/delegation tokens), and bind L7 RBAC to both caller SPIFFE ID and JWT `aud`/`sub` claims.

Policy Engine Bottleneck on the Hot Path

Every Envoy proxy makes a synchronous network call to a centralized OPA cluster for authorization, adding 15–40 ms tail latency and turning an OPA outage into a full site outage.

What helps: Compile Rego policies into local Wasm or Envoy-native `RBAC` filters evaluated in-process (<0.5 ms), or co-locate OPA as a node/pod sidecar with fail-closed/cached bundle sync.

Clock Skew Breaking Short-Lived SVID & JWT Validation

A VM or bare-metal node drifts >5 minutes behind UTC, causing it to reject newly minted SVIDs (`notBefore` in the future) and expired JWTs.

What helps: Enforce Chrony/PTP time sync across all nodes, alert on >500 ms drift, and backdate SVID `notBefore` by 30–60 seconds during issuance.

05 / Practical checklist

Avoid these mistakes

  • Terminating TLS at the ingress/API gateway and running plaintext HTTP inside the cluster (`PERMISSIVE` mTLS mode left on indefinitely), leaving internal traffic exposed to sniffing and spoofing.
  • Using IP-based `NetworkPolicy` alone without L7 workload identity—IPs are reused rapidly in Kubernetes and cannot distinguish two tenants or two endpoints on the same host.
  • Granting wildcard authorization (`principals: ["*"]` or `methods: ["*"]`) to unblock a deploy and never scoping it down to least-privilege `(spiffe_id, method, path)`.
  • Forgetting egress controls—allowing compromised pods to open arbitrary outbound TCP/DNS tunnels to attacker C2 servers.
  • Neglecting emergency break-glass runbooks when the OIDC provider or SPIRE server is unreachable during an incident.
