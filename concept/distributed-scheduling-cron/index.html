01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Distributed Cron & Scheduling.

A single-host crontab fails silently on VM reboots and cannot scale past one machine. A distributed scheduler separates scheduling from execution: a durable Schedule Store tracks next_run_at in UTC, a Dispatcher claims due triggers via atomic leases or partitioned ownership, and stateless Workers execute tasks.

Because network partitions make true exactly-once dispatch impossible, production schedulers deliver at-least-once dispatch + idempotent execution keyed by (job_id, scheduled_epoch).

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Naive Schedulers Double-Fire & Pile Up at Midnight.

80% of user cron jobs default to 0 0 * * * (midnight UTC), causing 100x thundering herds at :00. Meanwhile, split-brain leader failovers or crashed workers (SIGKILL) either fire duplicate runs or leave jobs stuck in RUNNING forever without deterministic run_id constraints and lease reapers.

Atomic Claim & Lease

SKIP LOCKED Dispatch -> Idempotent Worker -> Lease Reaper Recovery

A unique (job_id, scheduled_epoch) key prevents duplicate runs during failover, while a lease reaper recovers crashed workers.

Sharded Postgres Scheduler with Deterministic Jitter

Adding jitter_sec = hashtext(job_id) % 300 and polling with FOR UPDATE SKIP LOCKED smoothed midnight CPU spikes by 5x across 40,000 customer report jobs.

Kubernetes CronJob with `Forbid` Concurrency

Setting concurrencyPolicy: Forbid and startingDeadlineSeconds: 120 prevented an 8-minute slow ETL run from overlapping with the next 5-minute tick.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Distributed Schedulers Fit (and When Kafka / Temporal Win).

Use distributed cron for recurring business jobs and millions of delayed user timers ('send reminder in 24h'); use Kafka for reactive sub-second events and Temporal/Airflow for multi-step data DAGs.

ChoiceWhat it buysWhat it costs
Use: Recurring Billing, Compaction & Millions of Delayed TimersSurvives node crashes, enforces `Forbid`/`Replace` concurrency, audits every run.Requires UTC storage + IANA timezone evaluation for DST safety.
Avoid: Sub-Second Reactive Event ProcessingKafka/SQS triggers workers immediately upon event arrival without polling lag.N/A
Avoid: Multi-Step Data/Workflow DAGsUse Temporal or Apache Airflow for dynamic parent-child task dependencies.Plain cron lacks durable workflow state between steps.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to Handle DST, Misfires, Jitter & Idempotency.

  1. UTC + IANA Timezones: Store next_run_at in UTC, evaluate cron in explicit IANA zones (e.g., Asia/Kolkata), and deduplicate fall-back DST repeats via scheduled_epoch.
  2. Deterministic Jitter: Offset non-precision-critical :00 jobs by hash(job_id) % 60s.
  3. Capped Misfire Policies: Default non-critical jobs to Skip or cap Backfill windows so a 4-hour outage doesn't fire 240 simultaneous runs.
  4. Track schedule_lag_seconds p99: Rising lag signals dispatcher/worker saturation.
-- Atomic PostgreSQL SKIP LOCKED claim + idempotent run_id insertion
WITH due AS (
    SELECT id, next_run_at
    FROM schedules
    WHERE state = 'IDLE' AND next_run_at <= NOW()
    ORDER BY next_run_at ASC
    LIMIT 50
    FOR UPDATE SKIP LOCKED
)
INSERT INTO job_runs (job_id, scheduled_epoch, status, lease_expires_at)
SELECT id, EXTRACT(EPOCH FROM next_run_at)::BIGINT, 'QUEUED', NOW() + INTERVAL '60 seconds'
FROM due
ON CONFLICT (job_id, scheduled_epoch) DO NOTHING
RETURNING job_id, scheduled_epoch;

Alternatives: SQL `SKIP LOCKED` vs. Redis ZSET vs. Partitioned Timing Wheel.

Scale your scheduler storage engine to match your triggers-per-second target.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Architecture: Time-Bucketed Sharding & Lease Lifecycle.

At >10k timers/sec, partition schedules by (shard_id, time_bucket) across a consistent hash ring so each shard loads only the next 1–5 minutes into an in-memory Hierarchical Timing Wheel backed by durable storage cursors.
