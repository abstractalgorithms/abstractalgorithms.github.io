The idea to keep with you

B-Trees organize sorted keys into fixed-size mutable pages optimized for fast, predictable point and range reads, whereas LSM-Trees buffer writes in memory and flush immutable sorted runs to disk for high write throughput.

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are B-Trees and LSM-Trees.

Storage engines balance three competing costs (The RUM Conjecture): Read Amplification, Write (Update) Amplification, and Space (Memory) Amplification.

  • B-Trees (Update-in-Place): Store sorted keys in fixed-size mutable pages (8 KB in PostgreSQL, 16 KB in InnoDB) with 3–4 levels for 100M+ rows (O(log N) reads). Updates modify leaf pages in place via WAL and split full pages.
  • LSM-Trees (Out-of-Place): Append writes sequentially to a WAL + in-memory MemTable (skiplist), flushing immutable sorted SSTables to disk and merging them asynchronously via compaction.
Update-in-Place Index

B-Tree 3-Level Traversal & Covering Leaf Page

B-Trees traverse a fixed 3–4 level path to contiguous leaf pages, yielding tight, predictable p99 read and range-scan latency.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Picking the Wrong Index Structure Causes IOPS Cliffs.

Picking a B-Tree for random high-velocity writes turns 100-byte inserts into random 8–16 KB page reads, splits, and full-page WAL writes; picking an LSM-Tree for uncached point lookups without Bloom filters fans out across dozens of SSTables.

LSM-Tree Read/Write Path

RocksDB Write-Optimized MemTable, L0/L1 SSTables & Bloom Filters

LSM-Trees turn random writes into sequential WAL + SSTable flushes while per-file Bloom filters (~10 bits/key) skip 99% of disk reads.

IoT Telemetry: InnoDB vs. RocksDB (120k Writes/Sec)

Random UUIDv4 primary keys saturated NVMe IOPS in InnoDB due to 16 KB page splits. Moving to RocksDB converted writes into sequential WAL + SSTable flushes, cutting write IOPS by 6x and disk footprint by 55%.

Covering B-Tree Index Dropping p99 from 45ms to 1.8ms

On a 400M-row Postgres orders table, adding (customer_id, created_at DESC) INCLUDE (status, total_cents) enabled Index-Only Scans without heap fetches.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where B-Trees vs. LSM-Trees Belong.

Match the storage engine to your read/write ratio, key ordering, and compression requirements.

ChoiceWhat it buysWhat it costs
B-Trees (PostgreSQL, MySQL InnoDB)Best for read-heavy OLTP, frequent in-place updates, fast `BETWEEN` range scans, and strict p99 read SLAs.Random UUIDv4 keys cause severe page splits and ~67% fill fragmentation.
LSM-Trees (RocksDB, Cassandra, ScyllaDB, Pebble)Best for write-heavy telemetry, event logs, time-series, and 2–4x Zstd SSTable compression.Background compaction can spike tail latency; deletes leave tombstones that slow range scans.
Avoid: Excessive Secondary Indexes on Write-Heavy TablesKeep only indexes justified by query plans.Every secondary index multiplies write amplification on every insert/update.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to Tune Keys, Covering Indexes & LSM Compaction.

  1. Time-Ordered Keys on B-Trees: Use UUIDv7, ULID, or monotonic sequences so inserts append to the rightmost leaf page.
  2. Equality-First Composite Columns: Order columns by equality predicates first, then range predicates: (tenant_id, created_at) + INCLUDE (status).
  3. Pin LSM Bloom Filters in RAM: Size block cache so 100% of Bloom filters (~1.2 MB per 1M keys at 10 bits/key) and index blocks stay in memory, and leave 30–50% free disk headroom.
-- PostgreSQL covering B-Tree index enabling Index-Only Scans (no heap fetch)
CREATE INDEX CONCURRENTLY idx_orders_cust_recent
ON orders (customer_id, created_at DESC)
INCLUDE (status, total_cents);

-- Verify Index-Only Scan and zero heap fetches:
EXPLAIN (ANALYZE, BUFFERS)
SELECT status, total_cents FROM orders
WHERE customer_id = 48291 ORDER BY created_at DESC LIMIT 20;

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Leveled (LCS) vs. Size-Tiered (STCS) vs. Time-Window (TWCS).

Within LSM-Trees, compaction strategy governs write vs. read vs. space amplification.

ChoiceWhat it buysWhat it costs
Leveled Compaction (LCS — RocksDB Default)Low ~1.1x space amplification; non-overlapping L1..Ln bounds point-read checks.Higher 10–30x write amplification from frequent cross-level merges.
Size-Tiered Compaction (STCS — Cassandra Default)Low write amplification for pure append workloads.Requires 50% free disk headroom (up to 2x temporary space amplification) and hurts read latency.
Time-Window Compaction (TWCS)Drops expired 1-day time-series SSTable buckets instantly without compaction overhead.Only works when writes and TTLs align strictly with time windows.
06
STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Architecture: Avoiding Write Stalls & Tombstone Scans.

Monitor l0_num_files (approaching level0_stop_writes_trigger freezes writes!), pending compaction bytes, and tombstone-to-live-row ratios on LSM nodes; on PostgreSQL B-Trees, tune autovacuum and run REINDEX CONCURRENTLY when bloat exceeds 30%.

Prefix Bloom Filters for Short Range Scans

Storing a Bloom filter on key prefixes (e.g., tenant_id) lets LSM range scans (WHERE tenant_id = 'acme' AND ts > ...) skip irrelevant SSTables.

Never Use LSM Tables as FIFO Queues

Rapidly inserting and deleting keys in an LSM store leaves millions of tombstones in L0–L2, slowing SELECT range scans from 2 ms to 2 seconds.
