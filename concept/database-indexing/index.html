Database Indexing: B-Trees
vs LSM-Trees.

B-Trees organize sorted keys into fixed-size mutable pages optimized for fast, predictable point and range reads, whereas LSM-Trees buffer writes in memory and flush immutable sorted runs to disk for high write throughput.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Choose B-Trees for read-heavy OLTP workloads needing predictable p99 read latency and in-place updates; choose LSM-Trees for write-heavy ingestion, time-series, and high-compression workloads.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Every database query and write path is governed by its storage engine's index structure: picking the wrong engine turns high-throughput writes into random-I/O stalls (B-Tree page splits) or turns point reads into multi-SSTable fan-out spikes (LSM read amplification).

  • B-Tree structure: balanced tree of fixed-size pages (8 KB in Postgres, 16 KB in InnoDB) with high fan-out (typically 3–4 levels for 100M+ rows), yielding O(log N) reads.
  • LSM-Tree write path: writes append to an on-disk Write-Ahead Log (WAL) and insert into an in-memory MemTable (skiplist/red-black tree), flushing sequentially as immutable SSTables.
  • The RUM Conjecture: no index can simultaneously minimize Read, Update (Write), and Memory (Space) amplification—B-Trees optimize reads; LSM-Trees optimize writes and space.
  • Bloom filters & fence pointers: LSM-Trees use per-SSTable Bloom filters (~10 bits/key for 1% false-positive rate) to skip non-matching files on point lookups.
  • Compaction trade-off: Size-Tiered Compaction (STCS) minimizes write amplification for append-heavy loads, while Leveled Compaction (LCS) bounds space and read amplification.

Good candidates

  • Use B-Trees (PostgreSQL, MySQL InnoDB) for read-heavy OLTP workloads, frequent in-place updates, and strict p99 read latency guarantees.
  • Use LSM-Trees (RocksDB, Cassandra, ScyllaDB, Pebble) for write-intensive telemetry, event logging, and key-value stores where sequential append throughput dominates.
  • Use LSM-Trees when storage compression matters: immutable SSTables compress 2–4x better than fragmented B-Tree pages.

Think twice

  • Avoid B-Trees on spinning HDDs or high-churn append streams where random 8–16 KB page writes saturate IOPS.
  • Avoid LSM-Trees for workloads dominated by uncached, random-key range scans across heavily updated keys without sufficient Bloom filter/block-cache RAM.
  • Avoid creating secondary indexes indiscriminately on write-heavy tables—every secondary index multiplies write amplification.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA fleet platform ingested 120,000 sensor writes/sec into a MySQL InnoDB table indexed by random UUIDv4 primary keys. Buffer pool thrashing and random 16 KB page splits pinned NVMe IOPS at 100%.

The idea

Storage engines balance three competing costs—Read Amplification (bytes read per query), Write Amplification (bytes written to disk per logical write), and Space Amplification (disk bytes stored per logical byte). Two dominant architectures resolve this trade-off differently:

  • B-Trees (Update-in-Place): Store sorted keys in fixed-size mutable pages (8–16 KB). Lookups traverse 3–4 levels from root to leaf in O(log N). Updates modify leaf pages in place (buffered in RAM and persisted via WAL), splitting pages when full.
  • LSM-Trees (Log-Structured Merge-Trees, Out-of-Place): Append all writes sequentially to an in-memory MemTable (backed by a WAL). When full, the MemTable flushes as an immutable, sorted SSTable on disk. Background compaction merges overlapping SSTables to reclaim space and bound read fan-out.

Concrete walkthrough

Compare PUT(k='user:42', v='active') followed by GET('user:42') across both engines:

B-Tree Path (PostgreSQL / InnoDB):

  1. Write logs the change to the WAL, then locates leaf page #8812 via root -> internal -> leaf traversal (3 page lookups, usually cached in Buffer Pool).
  2. Leaf page #8812 is dirtied in RAM; if full, it splits into two 50%-filled pages and updates the parent.
  3. GET('user:42') traverses the exact same 3-level path to leaf #8812—1 leaf read, deterministic latency.

LSM-Tree Path (RocksDB):

  1. PUT appends to the sequential WAL and inserts into the active MemTable (~microseconds, zero random disk seeks).
  2. Once the MemTable hits 64 MB, it freezes and flushes sequentially to L0 SSTable.
  3. GET('user:42') checks the active MemTable, immutable MemTables, and then probes L0 SSTables (which may have overlapping key ranges) and L1..Ln SSTables. Per-file Bloom filters skip 99% of SSTables that don't contain 'user:42', reading only the matching block.

Storage engine mechanics: LSM-Trees buffer writes in MemTables and compact immutable SSTables sequentially, while B-Trees traverse and update fixed-size mutable pages in place.

Compaction strategies and Bloom filters

LSM-Tree performance hinges on two mechanisms:

  • Bloom Filters: A compact bit array (~10 bits per key = ~1.2 MB per 1M keys) stored in each SSTable's metadata. Before reading a data block from disk, the engine hashes the key into the Bloom filter: a negative result guarantees the key is absent (zero disk I/O), while a positive result has a ~1% false-positive rate.
  • Leveled Compaction (LCS, e.g., RocksDB default): Each level Li is 10x larger than Li-1 (L1 = 256 MB, L2 = 2.56 GB, etc.) with non-overlapping key ranges from L1 downward. Space amplification is low (~1.1x), and point reads check at most 1 file per level, at the cost of higher write amplification (~10–30x).
  • Size-Tiered Compaction (STCS, e.g., Cassandra default): Merges SSTables of similar size when N accumulate. Write amplification is low, but space amplification can temporarily reach 2x (requiring 50% free disk headroom).

Write PathRandom in-place page updates + WALSequential WAL + MemTable + sequential flush
Write AmplificationHigh on random keys (rewrites full 8–16 KB page for 100B row)Tunable (low in STCS, moderate in LCS)
Read AmplificationLow & predictable (1 leaf lookup; O(log N))Higher on cache miss (MemTable + L0 + L1..Ln, mitigated by Bloom)

Failure modes

  • LSM Write Stalls: If L0 SSTables pile up faster than compaction can merge them into L1, RocksDB throttles or halts all writes to prevent read amplification from exploding.
  • B-Tree Page-Split Storms: Bulk-loading out-of-order keys triggers cascading page splits, doubling WAL volume (full-page writes after checkpoints in Postgres) and saturating disk bandwidth.
  • Out-of-Memory Block Cache: If Bloom filters and index blocks exceed RAM, every LSM GET requires extra disk seeks just to read the Bloom filter.
  • Tombstone Read Amplification: In LSM-Trees, deleting 90% of a key range leaves tombstones that must be scanned until compacted into the bottommost level.

Modern optimizations: Bw-Trees, Prefix Bloom, and Tiered Storage

  • Prefix Bloom Filters: Store a Bloom filter on key prefixes (e.g., tenant_id) so short range scans (WHERE tenant_id = 'acme' AND ts > ...) can also skip irrelevant SSTables.
  • Composite & Covering Indexes (INCLUDE): In B-Trees, appending non-key payload columns to leaf pages (CREATE INDEX ... INCLUDE (status)) avoids random heap table lookups.
  • Time-Window Compaction (TWCS): Groups time-series SSTables into fixed time buckets (e.g., 1-day windows) and drops expired windows instantly without compaction overhead.

Practical checklist

  • Use time-ordered primary keys (UUIDv7, ULID, Snowflake IDs) on B-Tree tables to keep inserts sequential at the right edge.
  • Keep B-Tree composite index columns ordered by equality predicates first, then range predicates ((tenant_id, created_at)).
  • Size LSM-Tree RAM so 100% of Bloom filters and index blocks remain pinned in memory.
  • Monitor l0_num_files, compaction pending bytes, and tombstone-to-live-row ratios on LSM engines.
  • Leave at least 30–50% free disk headroom on LSM nodes for compaction temporary space.
03 / Engineering trade-offs

Weighing architectural decisions

Read Latency vs. Write Throughput

Advantage: B-Trees check a single root-to-leaf path (1 disk/cache lookup at the leaf), giving tight p99 read latency.

Drawback: LSM-Trees may probe the MemTable plus multiple SSTable levels on cache misses, though Bloom filters mitigate point-lookup overhead.

Write Amplification & Page Fragmentation

Advantage: LSM-Trees batch writes sequentially and pack SSTables densely (~100% fill factor vs. ~67% average B-Tree page fill).

Drawback: LSM background compaction rewrites data multiple times (10–30x in Leveled Compaction) and can cause latency spikes if it saturates NVMe bandwidth.

Range Scans & Tombstones

Advantage: B-Trees keep keys physically contiguous inside leaf pages, making `BETWEEN` range scans fast.

Drawback: LSM-Tree deletes write tombstone markers; heavy delete workloads without compaction force range scans to skip millions of tombstones.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

LSM Compaction Stalls (Write Stop)

Sustained writes outpace background compaction, causing L0 SSTable count to hit `level0_stop_writes_trigger` and freezing client writes.

What helps: Monitor L0 file count and compaction pending bytes; allocate dedicated compaction threads, rate-limit bursts, or use NVMe SSDs with higher sustained write IOPS.

B-Tree Random UUIDv4 Page Thrashing

Inserting random UUIDv4 keys into a clustered B-Tree forces constant random leaf-page reads, page splits, and dirty-page eviction.

What helps: Use time-ordered identifiers (UUIDv7, ULID, or monotonic sequences) so inserts append to the rightmost leaf page.

LSM Tombstone Accumulation

Queue-like workloads that insert and delete keys rapidly leave millions of tombstones in L0–L2, slowing `SELECT` range scans from 2 ms to 2 seconds.

What helps: Avoid queue patterns in LSM stores, or enable `PeriodicCompaction` / TTL-aware compaction (e.g., Cassandra TWCS) to purge expired keys.

B-Tree Index Bloat & Dead Tuples

Heavy `UPDATE`/`DELETE` churn in MVCC B-Trees (like PostgreSQL) leaves dead index entries that bloat tree depth and cache usage.

What helps: Tune `autovacuum` aggressiveness and run `REINDEX CONCURRENTLY` or `pg_repack` when index bloat exceeds 30%.

05 / Practical checklist

Avoid these mistakes

  • Using random UUIDv4 as a clustered primary key in MySQL InnoDB, destroying buffer pool locality and causing 50% page fragmentation.
  • Assuming LSM-Trees have zero read penalty without sizing RAM for Bloom filters and the block cache.
  • Over-indexing OLTP tables with 8+ secondary indexes, multiplying write amplification on every `INSERT` or `UPDATE`.
  • Using a leading wildcard (`LIKE '%foo'`) or wrapping an indexed column in a function (`LOWER(email)`), bypassing the B-Tree entirely.
  • Neglecting `compaction_throughput` limits in RocksDB/Cassandra, allowing compaction to starve foreground query I/O.
