Database Indexing: B-Trees vs LSM-Trees

Optimize query read latencies using balanced search trees or log-structured merge-tree write buffers.

Orientation & Intuition

Database indexes turn linear O(N) table scans into logarithmic O(log N) lookups. B-Trees optimize point & range reads; LSM-Trees turn random writes into sequential disk writes.

Key takeaway Choose B-Trees for read-heavy workloads (PostgreSQL/MySQL) and LSM-Trees for write-heavy append workloads (Cassandra/RocksDB).

Core Architecture & Trade-offs

Without indexes, searching 10,000,000 rows requires scanning every byte on disk. Indexes keep sorted pointers in memory/disk structures.

Key Architecture Invariants

  • B+ Trees store key-pointer pairs in self-balancing nodes; leaf nodes form a doubly-linked list for fast range scans.
  • LSM-Trees buffer writes in a MemTable (RAM) and write sequential SSTables to disk, compacting periodically.

When to Use

  • High-cardinality foreign keys and primary keys.
  • Range queries on timestamp or numerical columns.

When NOT to Use

  • Low-cardinality boolean columns (e.g. is_active).
  • Tables with massive write-only volume where index update overhead slows ingestion.
