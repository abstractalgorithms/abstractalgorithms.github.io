STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is a Message Queue.

A message queue buffers asynchronous events between producers and consumers so slow or crashed downstream services do not block upstream APIs.

Two dominant architectures exist: point-to-point work queues (SQS, RabbitMQ) where workers compete-consume and delete messages on ACK, and partitioned append-only logs (Kafka, Pulsar) that retain ordered history for multiple independent consumer groups.

Delivery Lifecycle

At-Least-Once Message Delivery & DLQ State Machine

Because a worker can crash after processing but before ACK, consumers must be idempotent and poison pills must route to a DLQ.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why synchronous RPC chains collapse—and why queues need DLQs & Outbox.

Synchronous HTTP/gRPC chains couple every service's availability to its slowest dependency: a 3-second billing DB stall backs up checkout threads and crashes the API gateway.

Moving to queues introduces two classic failure modes: Poison-Pill Infinite Retry Loops (a malformed message crashes every worker before ACK, burning 100% CPU) and Dual-Write Split-Brain (DB commits, then producer.send() crashes, losing the event).

Dual-Write Fix

Transactional Outbox + Debezium CDC Pipeline

1.1. Atomic Outbox: Write business state and outbox event in the same SQL transaction—zero dual-write drift.

2.2. Prefetch Backpressure: Cap basic.qos / max.poll.records so fast brokers never OOM slow workers.

3.3. Bounded DLQ: Route messages exceeding maxReceiveCount (3-5) to a monitored DLQ for replay.

Transactional Outbox guarantees every committed DB change reaches the broker; prefetch + DLQ protect consumers.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Idempotent Consumer + Bounded Prefetch & DLQ Routing.

Deduplicate redeliveries using a unique event_id in Redis/SQL, cap max.poll.records to bound memory, and route permanent failures to a DLQ.

def handle_message(msg, db, dlq_producer):
    event_id = msg.headers["event_id"]
    try:
        with db.transaction():
            # Idempotency guard: INSERT ... ON CONFLICT DO NOTHING
            if not db.mark_event_processed(event_id):
                return msg.ack()  # Safe duplicate redelivery
            apply_business_mutation(db, msg.payload)
        msg.ack()
    except PermanentValidationError as err:
        dlq_producer.send(msg.payload, reason=str(err))
        msg.ack()  # Remove poison pill from main queue

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Partitioned Log (Kafka) vs. Smart Queue (RabbitMQ/SQS).

Choose between multi-consumer replayable logs and flexible per-message work queues.

ChoiceWhat it buysWhat it costs
Partitioned Log (Kafka / Pulsar)1M+ msgs/sec via sequential disk I/O + zero-copy `sendfile`; multi-day replay for multiple consumer groups.Parallelism capped by partition count; one slow message in a hot partition blocks that partition.
Smart Broker Queue (RabbitMQ / SQS)Flexible per-message ACK, native DLQ redrive, and easy worker scaling without partition limits.Messages are deleted upon ACK; no built-in historical replay.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Backpressure, Partition Ordering & Retry Topics.

In Kafka, never sleep inside the consumer poll loop for long retries (which triggers max.poll.interval.ms rebalance storms). Instead, publish failed messages to tiered retry topics (retry-10s, retry-5m) before routing exhausted events to the DLQ.

Partition Key Head-of-Line Blocking

Keying by order_id preserves Created -> Paid -> Shipped order, but avoid coarse keys like tenant_id for whale tenants.

Alert on DLQ Depth & Consumer Lag

Page on DLQ growth > 0 and sustained consumer lag growth rather than transient queue depth spikes.
