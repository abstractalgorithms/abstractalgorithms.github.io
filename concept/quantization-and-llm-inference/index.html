LLM Quantization, GPTQ/AWQ
& Inference Performance.

LLM quantization compresses 16-bit model weights and KV caches into 8-bit or 4-bit representations (FP8, AWQ, GPTQ, GGUF) to slash VRAM usage by 2-4x and accelerate memory-bandwidth-bound token generation.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Because autoregressive LLM decode is memory-bandwidth bound at low batch sizes, moving from FP16 to INT4/FP8 cuts HBM reads per token by 2-4x while keeping accuracy loss under ~1% when activation outliers are protected.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

A 70B-parameter LLM in FP16 consumes ~140 GB just for weights—requiring two 80 GB H100s before serving a single token—and autoregressive decoding reads all 140 GB from HBM for every single generated token. Quantization fits that 70B model onto a single 48 GB or 80 GB GPU and multiplies decode throughput by shrinking memory traffic.

  • LLM inference has two distinct phases: compute-bound prefill (processing the prompt in parallel) and memory-bandwidth-bound decode (1 token at a time).
  • On an H100 (3.35 TB/s HBM3), reading 140 GB (FP16) caps batch-1 decode near ~24 tok/s, whereas 35 GB (INT4) raises the bandwidth ceiling near ~95 tok/s.
  • Activation outliers (~1% of channels with >6.0 magnitude) break naive Round-To-Nearest (RTN) INT4; AWQ, GPTQ, and SmoothQuant preserve those salient channels.
  • FP8 (E4M3) on Hopper/Ada Tensor Cores delivers near-lossless (<0.2% MMLU drop) W8A8 compute speedup for both prefill and decode.
  • KV-cache quantization (FP8/INT8) is often just as important as weight quantization at 32k+ context lengths where KV cache dominates VRAM.

Good candidates

  • Serving 7B-70B+ models on fewer GPUs (e.g., fitting Llama-3.1-70B INT4 onto a single 80 GB A100/H100 instead of 2x GPUs).
  • Accelerating memory-bandwidth-bound decode latency (tok/s per user) in interactive chat and coding copilots.
  • Compressing long-context KV caches with FP8 (E4M3) to double or quadruple concurrent batch size at 32k-128k context.

Think twice

  • Tiny models (<3B parameters) running at high batch sizes on H100s where inference is already compute-bound and INT4 dequantization overhead can hurt.
  • Sub-4-bit (INT2 / 1.58-bit) post-training quantization on complex reasoning or multi-step code generation without quantization-aware training (QAT).
  • Hardware lacking native INT8/FP8 Tensor Cores or fused dequantize-GEMM kernels (e.g., older GPUs running unoptimized INT4).
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA production team needs to serve Llama-3.1-70B-Instruct with 8k context on 80 GB A100 GPUs using vLLM.

The idea

Autoregressive LLM generation is split into two physically opposite regimes. Prefill processes all prompt tokens in parallel as large matrix-matrix multiplications (GEMM), making it compute-bound (limited by Tensor Core TFLOPS). Decode generates one token per step per sequence, multiplying a thin activation vector against every weight matrix in the network—making it memory-bandwidth bound.

Quantization maps 16-bit floating-point numbers (BF16/FP16) onto smaller discrete grids (FP8, INT8, INT4) using affine scaling (x_q = round(x / scale) + zero_point). By shrinking weights 2x–4x, decode steps move 2x–4x fewer bytes across GPU HBM3 buses, directly multiplying tokens/sec while freeing VRAM for larger batches and longer KV caches.

Concrete walkthrough

Suppose we deploy Llama-3.1-70B (80 layers, GQA 8 KV heads) on an 80 GB H100 (3.35 TB/s HBM3):

  1. FP16 baseline: Weights alone require 70B * 2 bytes = 140 GB, so it cannot fit on 1x H100. Across 2x H100s with tensor parallelism, batch-1 decode reads 140 GB/token.
  2. AWQ INT4 quantization (group_size=128): Using 256 calibration prompts, AWQ identifies the top ~1% salient weight channels (driven by large activation magnitudes) and scales them up before rounding to 4 bits. Packed weights drop to ~38 GB.
  3. Fused Marlin kernel execution: During decode in vLLM, the Marlin kernel loads packed INT4 weights from HBM (38 GB per pass), dequantizes them to FP16 inside GPU shared memory/registers on the fly, and multiplies against FP16 activations—cutting HBM traffic by ~3.7x.
  4. FP8 KV cache: Enabling --kv-cache-dtype fp8 halves KV-cache memory per token, leaving ~36 GB for PagedAttention blocks.

Fused dequantize-GEMM kernels keep dequantization inside fast on-chip registers so HBM3 bandwidth is never wasted on unpacked FP16 weights.

Why naive rounding fails: activation outliers

Transformer activations in models >6B parameters exhibit systematic outlier features: roughly 0.1%–1% of hidden dimensions consistently reach magnitudes 10x–100x larger than the median. Naive min-max quantization stretches the quantization grid to cover the outlier, squeezing 99% of normal values into a handful of buckets and destroying accuracy.

Modern schemes solve this in three ways:

  • LLM.int8(): Keeps the ~0.1% outlier columns in FP16 and quantizes the remaining 99.9% to INT8.
  • SmoothQuant (W8A8): Migrates quantization difficulty from activations (X) into weights (W) via a diagonal scale s: Y = (X diag(s)^-1)(diag(s) W).
  • AWQ (W4A16): Protects the top ~1% salient weight channels identified by activation magnitude without storing mixed-precision exceptions.

Failure modes

Production deployments of quantized LLMs commonly fail in four ways:

  • High-batch W4A16 slowdown: At batch sizes >32, W4A16's register dequantization adds ALU overhead that makes it slower than FP8 W8A8 on Hopper GPUs.
  • Silent tool-calling / JSON breakage: Perplexity barely moves (+0.15), yet strict JSON bracket balancing or tool-argument extraction degrades noticeably on 3-bit or uncalibrated 4-bit models.
  • Missing fused kernels: Loading a GPTQ checkpoint without marlin or exllamav2 falls back to slow PyTorch dequantize-then-matmul, running slower than FP16.
  • Unquantized KV cache: A 70B INT4 model serving 128k context still hits OOM if KV cache remains in FP16.

How to benchmark before shipping

Never ship a quantized checkpoint on perplexity alone. Run a 3-layer gate:

  1. Task-specific evals: Measure exact-match accuracy on your production prompts (tool calls, SQL, RAG citations) against the BF16 baseline.
  2. Throughput vs. concurrency curve: Sweep concurrency (1, 8, 32, 64, 128 requests) measuring Time-To-First-Token (TTFT p95) and Inter-Token Latency (ITL p95).
  3. VRAM headroom check: Verify peak KV-cache utilization under max context length with PagedAttention enabled.

Practical checklist

  • Choose FP8 (W8A8) on H100/L40S when serving medium-to-high batch concurrency; choose AWQ + Marlin (W4A16) for single-GPU 70B or low-latency decode.
  • Enable FP8 KV-cache (--kv-cache-dtype fp8) for workloads with >8k average context length.
  • Calibrate AWQ/GPTQ on 128–512 domain-matched samples (including code/JSON if used in production).
  • Confirm fused kernels (Marlin, FlashInfer, CUTLASS FP8) are active in engine startup logs.
  • Run end-to-end JSON schema, tool-calling, and RAG faithfulness regressions against the FP16/BF16 baseline.
03 / Engineering trade-offs

Weighing architectural decisions

Precision vs. VRAM footprint

Advantage: INT4 (AWQ/GPTQ/Q4_K_M) reduces weight memory by ~3.5-4x compared to FP16.

Drawback: Requires fused dequantize-GEMM kernels (Marlin/ExLlamaV2) and risks minor reasoning degradation on edge prompts.

Weight-only INT4 (W4A16) vs. W8A8 (FP8/INT8)

Advantage: W4A16 maximizes single-user decode speed by minimizing HBM reads.

Drawback: W8A8 (FP8) uses native Tensor Cores to accelerate compute-bound prefill and high-batch throughput, which W4A16 cannot.

Calibration time vs. deployment simplicity

Advantage: AWQ/GPTQ calibration on 128-512 domain samples preserves accuracy much better than zero-shot RTN.

Drawback: Adds a 10-45 minute offline quantization step and requires domain-representative calibration text.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Outlier Channel Clipping

Naive min-max quantization scales an entire weight tensor to fit one extreme outlier, crushing normal weights into 1-2 bits.

What helps: Use group-wise quantization (group_size=128) paired with AWQ activation scaling or SmoothQuant.

Dequantization Kernel Bottleneck at High Batch

W4A16 models dequantize weights to FP16 in registers; at batch=64+, compute saturates and W4A16 becomes slower than FP8 W8A8.

What helps: Benchmark at target concurrency (e.g., batch=32 vs batch=1) and switch to FP8 W8A8 on H100/L40S for high-batch serving.

Calibration Dataset Mismatch

Calibrating GPTQ exclusively on English prose degrades accuracy on SQL, Python, or multilingual prompts.

What helps: Include a representative mix of code, JSON, and target-language samples in the 256-sample calibration set.

KV-Cache OOM Under Long Context

Compressing weights from 140 GB to 35 GB still OOMs if 100 concurrent 32k-token requests allocate 60+ GB of FP16 KV cache.

What helps: Enable PagedAttention with FP8 KV-cache quantization (--kv-cache-dtype fp8 in vLLM).

05 / Practical checklist

Avoid these mistakes

  • Evaluating quantized models only on WikiText perplexity instead of task-specific evals like HumanEval, GSM8K, or strict JSON schema adherence.
  • Using W4A16 on H100s for high-concurrency batch workloads where FP8 W8A8 delivers higher total tokens/sec.
  • Forgetting to quantize the KV cache when serving 32k-128k context windows.
  • Deploying uncalibrated RTN INT4 instead of AWQ, GPTQ, or GGUF K-quants (Q4_K_M).
  • Ignoring kernel support—running GPTQ without Marlin or ExLlamaV2 kernels leaves 2-3x decode speed on the table.
