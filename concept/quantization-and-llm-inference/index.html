The idea to keep with you

LLM quantization compresses 16-bit model weights and KV caches into 8-bit or 4-bit representations (FP8, AWQ, GPTQ, GGUF) to slash VRAM usage by 2-4x and accelerate memory-bandwidth-bound token generation.

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is LLM Quantization (Prefill vs. Decode).

Autoregressive LLM inference has two opposite regimes: Prefill (processes prompt tokens in parallel via large GEMMs -> compute-bound) and Decode (generates 1 token per step -> memory-bandwidth bound).

A 70B model in FP16 consumes 140 GB of weights—requiring 2x 80 GB H100s—and batch-1 decode on an H100 (3.35 TB/s HBM3) is capped near ~24 tok/s. Quantizing weights to INT4 (W4A16) shrinks weights to ~35 GB (fitting on 1x GPU) and lifts the bandwidth ceiling near ~95 tok/s; FP8 (W8A8) uses Hopper Tensor Cores to accelerate both prefill and high-batch decode.

GPU Memory Hierarchy

HBM3 Bandwidth Bottleneck & Quantized Weight/KV-Cache Footprint

1.1. Weight Compression: INT4 (AWQ/GPTQ) cuts 70B weights from 140 GB to ~35 GB, fitting on a single 80 GB GPU.

2.2. Outlier Protection: AWQ scales salient ~1% activation outlier channels before group-wise (128) quantization.

3.3. KV-Cache FP8: At 32k-128k contexts, quantizing KV cache to FP8 prevents VRAM OOM under concurrency.

Shrinking bytes read from HBM per token directly multiplies low-batch decode speed.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Naive Rounding Fails (Activation Outliers).

Transformer activations in models >6B parameters exhibit systematic outlier features: ~0.1%–1% of hidden channels reach magnitudes 10x–100x larger than the median. Naive Round-To-Nearest (RTN) stretches the quantization grid to fit one outlier, crushing normal weights into 1–2 bits and destroying reasoning and JSON tool calling.

AWQ, GPTQ & SmoothQuant

AWQ protects salient weight channels identified by activation magnitude; GPTQ uses second-order Hessian error compensation; SmoothQuant migrates outlier difficulty from activations into weights.

High-Batch W4A16 Inversion

At batch > 32, W4A16 register dequantization ALU overhead saturates compute—making FP8 W8A8 faster on H100/L40S.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Quantization fits (and where BF16/QAT wins).

Choose W4A16 (AWQ+Marlin) for single-GPU 70B / low-latency decode, FP8 (W8A8) for high-batch Hopper serving, and skip sub-4-bit PTQ on complex coding/reasoning.

ChoiceWhat it buysWhat it costs
Good Candidate: 7B–70B+ Interactive Serving (FP8 / AWQ)2–4x VRAM reduction and 2–3x higher decode tok/s with <1% accuracy drop.Requires fused kernels (Marlin, ExLlamaV2, FP8 Tensor Cores) and domain-matched calibration data.
Avoid: Sub-4-Bit PTQ (INT2) on Code/Math ReasoningKeep BF16/FP8 or use Quantization-Aware Training (QAT) for strict JSON/SQL/reasoning fidelity.Post-training 2-bit quantization degrades multi-step reasoning severely.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Quantized Serving & Task-Specific Evals are managed.

Never ship a quantized checkpoint on WikiText perplexity alone. Calibrate on 256 domain-representative samples (code, JSON, target languages), enable --kv-cache-dtype fp8 for long contexts, and run task-specific evals (HumanEval, JSON schema adherence) + concurrency sweeps against BF16.

# Production vLLM launch with FP8 weights + FP8 KV-cache & Marlin/PagedAttention
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-3.1-70B-Instruct-FP8 \
  --quantization fp8 \
  --kv-cache-dtype fp8 \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.92
