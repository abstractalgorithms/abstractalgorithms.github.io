The idea to keep with you

Argo CD is a declarative, pull-based GitOps continuous delivery controller for Kubernetes that continuously reconciles live cluster state against Git repositories.

TL;DR30-second simplified summary
▾

Core Mechanics: Argo CD pulls desired Kubernetes manifests from Git and reconciles them against the live API via argocd-server, argocd-repo-server, and argocd-application-controller.

Visual & Structural Flow: Depicts Argo CD Sync & Health State Machine (SYNCED + HEALTHY -> OUT OF SYNC -> SYNCED / DEGRADED); CI Image Bump -> GitOps Repo -> Argo CD Pull Reconciliation (CI Runner -> GitOps Repo -> Repo Server -> App Controller); GitOps Repo -> Management Argo CD -> Workload Clusters + ESO (GitOps Repo + CI -> Mgmt Argo CD -> Prod K8s Cluster -> Vault / ESO).

Trade-Offs & Production: Choose the Argo CD grouping pattern that matches your fleet size, or compare against Flux CD. Scale-out platforms isolate Argo CD onto a dedicated management cluster while workload pods pull runtime credentials via External Secrets Operator (ESO).

Failure Modes & Application: Connect GitOps reconciliation to graceful shutdowns, canary rollbacks, and Kubernetes PodDisruptionBudgets.

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Argo CD GitOps.

Argo CD pulls desired Kubernetes manifests from Git and reconciles them against the live API via argocd-server, argocd-repo-server, and argocd-application-controller. Sync (manifests match Git) and Health (Pods pass readiness probes) are tracked independently.

Reconciliation Loop

Argo CD Sync & Health State Machine

An Application can be Synced to the latest Git commit while still Degraded if Pods fail readiness checks.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Pull-Based GitOps (and why push CI fails).

Push-based kubectl apply leaks prod kubeconfigs to CI runners and misses manual drift. In Argo CD, guard against HPA vs. Git replica fights (ignoreDifferences), CRD 262 KB annotation overflow (ServerSideApply=true), and infinite CI commit loops.

Webhook Reconciliation

CI Image Bump -> GitOps Repo -> Argo CD Pull Reconciliation

Separating the CI code repo from the GitOps manifest repo gives cryptographic audit trails and instant git revert rollbacks.

Sync Phases & Waves

Order PreSync (DB migrations), Sync (workloads), and PostSync (smoke tests) using integer argocd.argoproj.io/sync-wave annotations.

Protect Stateful Resources

Always set Prune=false on PVCs, Namespaces, and databases so a refactor never deletes production storage.

03
STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Argo CD excels (and where imperative scripts fit).

Argo CD is built for declarative Kubernetes fleets, multi-environment promotion, and platform-team RBAC.

ChoiceWhat it buysWhat it costs
Multi-Cluster Kubernetes Fleets (`ApplicationSet`)Matrix/Git generators stamp out consistent apps across dev/stage/prod clusters.A bad generator template edit can blast all child Applications simultaneously.
Progressive Delivery (Argo Rollouts + GitOps)Automates Canary/Blue-Green traffic shifting and Prometheus metric-driven rollbacks.Requires Ingress/Service Mesh traffic-splitting integration.
Avoid: Storing Raw Secrets in GitPair with External Secrets Operator (ESO) or SealedSecrets so Git holds only pointers.Raw Kubernetes Secrets in Git leak credentials in commit history permanently.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Sync Options, IgnoreDifferences, and AppProjects are managed.

Pin @sha256: digests, enable ServerSideApply=true, ignore /spec/replicas for HPA, and isolate teams with AppProject.

# Production-hardened Argo CD Application manifest
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: billing-prod
  namespace: argocd
spec:
  project: payments-team
  source:
    repoURL: https://github.com/acme/platform-gitops.git
    targetRevision: main
    path: envs/prod/billing
  destination:
    server: https://prod-eks.internal
    namespace: billing
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers: ["/spec/replicas"]
  syncPolicy:
    automated: { prune: true, selfHeal: true }
    syncOptions: [ServerSideApply=true, CreateNamespace=true]

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Application vs. App-of-Apps vs. ApplicationSet vs. Flux.

Choose the Argo CD grouping pattern that matches your fleet size, or compare against Flux CD.

ChoiceWhat it buysWhat it costs
Single `Application` / `ApplicationSet`ApplicationSet dynamically generates per-cluster/per-PR apps from Git dirs or cluster labels.Requires careful RBAC and progressive-sync rollouts to avoid simultaneous fleet blast radius.
App-of-Apps PatternPure Application CRDs pointing to a directory of child Applications.Cascading delete risks if finalizers are misconfigured; harder templating than ApplicationSet.
Flux CDLightweight modular K8s controllers with native OCI artifact and HelmController support.Lacks Argo CD's rich multi-tenant Web UI and SSO/RBAC management out of the box.
06
STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Dedicated Management Cluster + ESO Secrets.

Scale-out platforms isolate Argo CD onto a dedicated management cluster while workload pods pull runtime credentials via External Secrets Operator (ESO).

Hub-and-Spoke GitOps

GitOps Repo -> Management Argo CD -> Workload Clusters + ESO

1.Hub-and-Spoke Isolation: Compromising a workload cluster never compromises the central Argo CD management plane.

2.Webhook + Redis Cache: Git webhooks trigger immediate reconciliation while Redis caches rendered Helm/Kustomize outputs.

3.Zero-Secret Git: Git stores only ExternalSecret references; ESO syncs actual values at runtime.

Hub-and-spoke Argo CD + ESO delivers auditable, self-healing multi-cluster deployments without secret sprawl.
