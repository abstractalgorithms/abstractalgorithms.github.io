Argo CD
GitOps.

Argo CD is a declarative, pull-based GitOps continuous delivery controller for Kubernetes that continuously reconciles live cluster state against Git repositories.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Git is the single source of truth: Argo CD's in-cluster controller pulls desired manifests and self-heals configuration drift without exposing cluster credentials to external CI runners.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Push-based CI/CD pipelines (kubectl apply from GitHub Actions) require giving external CI runners cluster-admin credentials and leave clusters blind to manual kubectl edit drift. Argo CD runs inside Kubernetes, detects OutOfSync drift within seconds (or via webhooks), and reconciles Helm, Kustomize, or plain YAML deterministically with instant Git-revert rollbacks.

  • Pull-based reconciliation loop: Argo CD's application-controller compares the live Kubernetes API state against the rendered Git target state every 3 minutes (default timeout.reconciliation) or immediately on Git webhook.
  • Three-component architecture: argocd-server (API/UI/RBAC), argocd-repo-server (clones Git and renders Helm/Kustomize/Jsonnet), and argocd-application-controller (diffs and applies).
  • Sync vs. Health are independent: Synced means live manifests match Git; Healthy means Pods/Deployments pass readiness checks—an app can be Synced yet Degraded.
  • Sync waves and hooks (PreSync, Sync, PostSync) order dependencies—such as running a DB migration Job in wave -1 before rolling out Deployments in wave 0.
  • App-of-Apps and ApplicationSet: ApplicationSet replaces brittle nested App-of-Apps patterns using Git directory, list, or cluster generators to template 100s of apps cleanly.

Good candidates

  • Managing multi-environment (dev/staging/prod) or multi-cluster Kubernetes deployments where auditability and drift detection are mandatory.
  • Eliminating external CI/CD access to production Kubernetes API servers in regulated or zero-trust environments.
  • Orchestrating progressive delivery (canary/blue-green) alongside Argo Rollouts or fleet-wide add-ons via ApplicationSet generators.

Think twice

  • Non-Kubernetes infrastructure provisioning (VPCs, IAM roles, RDS instances), where Terraform/OpenTofu or Crossplane is the right control plane.
  • Ephemeral PR preview environments that need imperatively scripted teardown hooks faster than Git commit/PR lifecycle workflows.
  • Single-node hobby clusters where a 10-line CI deploy script is simpler than operating Argo CD's repo-server, Redis, and controller.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA platform team manages Prometheus, ExternalDNS, and Kyverno across 35 EKS clusters.

The idea

Argo CD turns Kubernetes deployments inside out: instead of an external CI pipeline pushing kubectl apply with long-lived admin tokens, an in-cluster controller continuously pulls desired state from Git and reconciles it against the live Kubernetes API. Every change—image bumps, RBAC rules, Helm values—is a Git commit, giving you cryptographic audit trails, git revert rollbacks, and automatic drift detection.

Concrete walkthrough

Suppose CI builds ghcr.io/acme/billing:v1.4.2 and updates envs/prod/billing/kustomization.yaml in the platform-gitops repo.

  1. Webhook & Fetch: GitHub sends a webhook to argocd-server, which notifies argocd-application-controller to bypass the 3-minute polling interval.
  2. Render: argocd-repo-server clones platform-gitops at the new commit SHA, runs kustomize build envs/prod/billing, and caches the rendered YAML in Redis.
  3. Diff: The controller compares the rendered target manifests against the live billing namespace state in Kubernetes, flagging the Deployment as OutOfSync.
  4. Wave-Ordered Sync: The controller executes a PreSync schema-migration Job (wave -1), waits for Complete, then applies the Deployment (wave 0) using Server-Side Apply and monitors readiness until Health returns Healthy.

Argo CD's pull-based control loop keeps Kubernetes clusters converged to Git without granting external CI runners cluster access.

Sync phases, waves, and Server-Side Apply

Real deployments require ordering. Argo CD executes syncs in three phases: PreSync (e.g., DB schema migrations), Sync (main workloads), and PostSync (smoke tests, Slack notifications). Within each phase, argocd.argoproj.io/sync-wave integers (default 0, ascending order) ensure CRDs and Namespaces land before Custom Resources.

Enabling ServerSideApply=true in syncOptions delegates field ownership and strategic merges to the Kubernetes API server, eliminating the 262 KB kubectl.kubernetes.io/last-applied-configuration annotation limit on large CRDs (like Prometheus Operator or Istio).

Failure modes

  1. HPA vs. Git Replica Fight: Leaving replicas: 3 in Git when HPA scales pods to 8 causes Argo CD selfHeal to scale pods back down to 3. Fix: omit replicas from Git or add /spec/replicas to ignoreDifferences.
  2. Orphaned Finalizer Deadlock: Deleting an Application with resources-finalizer.argocd.argoproj.io hangs forever if the target cluster is unreachable. Fix: patch out the finalizer only after verifying the target cluster is decommissioned.
  3. CRD Annotation Overflow: Applying large CRDs with client-side apply fails with metadata.annotations: Too long. Fix: use ServerSideApply=true and Replace=true for CRDs.
  4. Shared repo-server Bottleneck: One overloaded repo-server pod running slow Helm plugins delays syncs for the entire org. Fix: scale repo-server horizontally and enable Redis caching.

Scaling Argo CD across teams

Separate your Argo CD control plane from application workloads on a dedicated management cluster, and isolate teams with AppProject boundaries (sourceRepos, destinations, clusterResourceWhitelist) mapped to OIDC groups. Pair Argo CD with External Secrets Operator (ESO) so Git holds only ExternalSecret pointers to AWS Secrets Manager or HashiCorp Vault, never raw credentials.

Practical checklist

  • Pin immutable tags or digests: never reference :latest in GitOps manifests; use semantic tags + SHA256 digests.
  • Protect stateful resources: set argocd.argoproj.io/sync-options: Prune=false on PVCs, Namespaces, and DBs.
  • Enable Server-Side Apply: add ServerSideApply=true to avoid CRD annotation size limits and field-manager conflicts.
  • Configure ignoreDifferences: whitelist HPA-managed /spec/replicas and webhook-injected fields.
  • Use separate config repos: decouple CI build repos from GitOps manifest repos and wire Git webhooks for sub-second sync triggers.
03 / Engineering trade-offs

Weighing architectural decisions

`autoSync` + `selfHeal` vs. Manual Sync

Advantage: Zero-touch continuous delivery; manual `kubectl` hotfixes are automatically reverted to preserve compliance.

Drawback: Urgent incident mitigations must go through Git (or temporarily disable auto-sync), adding 1–2 minutes if CI checks block merges.

Monorepo vs. App-Code + Config-Repo Split

Advantage: Separating `app-repo` (CI builds image) from `gitops-config-repo` (Argo CD watches) prevents infinite CI-trigger loops.

Drawback: Requires CI or Argo CD Image Updater to open automated PRs/commits to bump image tags across repos.

Plain Secrets vs. External Secrets Operator (ESO)

Advantage: Committing encrypted SealedSecrets/SOPS keeps everything self-contained in Git.

Drawback: ESO/Vault integration avoids storing any secret material—even encrypted—in Git history and simplifies key rotation.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Helm/Kustomize Rendering Timeout in `repo-server`

Large monorepos or slow `helm dependency build` calls exhaust `argocd-repo-server` CPU/memory, stalling all app syncs with `ComparisonError`.

What helps: Pin Helm chart versions in an internal OCI registry, scale `repo-server` replicas, and set `ARGOCD_EXEC_TIMEOUT` appropriately.

Endless Sync Loop on Mutated Fields

A mutating webhook (e.g., Istio sidecar injector or HPA changing `spec.replicas`) alters live resources, causing Argo CD to report perpetual `OutOfSync` and re-apply.

What helps: Configure `ignoreDifferences` (e.g., `/spec/replicas` when HPA is active) or use Server-Side Apply (`ServerSideApply=true`).

Accidental `Prune=true` Mass Deletion

A bad refactor renames a Kustomize path or deletes an `Application` with `cascade=true` and `prune: true`, wiping production Deployments and PVCs.

What helps: Add `argocd.argoproj.io/sync-options: Prune=false` on stateful PVCs/Namespaces and require PR review on `ApplicationSet` changes.

Kubernetes API Rate Limiting (429)

Managing 500+ Applications from one controller without sharding overwhelms the kube-apiserver with list/watch and patch calls.

What helps: Enable controller sharding (`--sharding-method=round-robin`), increase `--kube-api-qps`, and use Git webhooks instead of polling every 30s.

05 / Practical checklist

Avoid these mistakes

  • Pointing Argo CD at the same repository where CI runs without `[skip ci]` or a separate config repo, causing infinite commit loops.
  • Leaving `spec.replicas` hardcoded in Git Deployments alongside a HorizontalPodAutoscaler (HPA), triggering constant scale fights.
  • Committing unencrypted Kubernetes `Secret` manifests to Git instead of using External Secrets Operator, SealedSecrets, or SOPS.
  • Using `latest` image tags in Git manifests—Argo CD cannot detect a new digest behind `latest`, breaking rollbacks and reproducibility.
  • Enabling `selfHeal: true` and `prune: true` globally on production databases without `Prune=false` annotations on PersistentVolumeClaims.
