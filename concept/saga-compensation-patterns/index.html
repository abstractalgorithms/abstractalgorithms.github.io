Compensation Patterns.

A Saga coordinates a multi-service business transaction as a sequence of local ACID transactions paired with compensating actions that semantically undo prior steps on failure, avoiding distributed 2-Phase Commit locks at the cost of eventual consistency.

Transaction Isolation & Distributed ACID
Isolation levels control which concurrent read/write anomalies a database permits, trading throughput and lock/abort rates for correctness—while distributed ACID extends those guarantees across shards via 2PC, TrueTime, or HLCs.
Idempotency & Deduplication
Idempotency keys and deduplication logs ensure that network retries, at-least-once message deliveries, and double-clicks execute state mutations at most once while returning the original cached outcome.

What is a Saga.

Why this matters: The mechanism: understand how a Saga works from first principles.

Think of What is a Saga as the intuition layer for Saga & Compensation Patterns: The mechanism: understand how a Saga works from first principles.

When each microservice owns its own database, a checkout spanning Order, Inventory, and Payment cannot use a single local ACID transaction—and 2-Phase Commit (2PC) holds cross-network locks that stall throughput. A Saga splits the workflow into local ACID transactions, classifying steps into: Compensable (ReserveInventory -> undoable via ReleaseInventory), Pivot (ChargeCard -> point of no return), and Retriable (ConfirmOrder, SendEmail -> guaranteed to succeed after Pivot).

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Sagas Lack Isolation (ACD vs. ACID Countermeasures).

Why this matters: The problem: see what breaks without Why Sagas Lack Isolation under real concurrency or scale.

Think of Why Sagas Lack Isolation (ACD vs. ACID Countermeasures) as the intuition layer for Saga & Compensation Patterns: The problem: see what breaks without Why Sagas Lack Isolation under real concurrency or scale.

Because each local transaction commits immediately, Sagas provide ACD (Atomicity, Consistency, Durability) without Isolation: concurrent sagas can observe intermediate PENDING states (dirty reads) or cause lost updates. To prevent anomalies without 2PC locks, use Semantic Locks (status = PENDING_RESERVATION with TTL sweepers), Commutative Updates (delta +/- instead of absolute SET), and Transactional Outboxes to eliminate dual-write split-brain.

Write domain mutations and outbox events in the same local ACID transaction (tailed by Debezium CDC or FOR UPDATE SKIP LOCKED relay), and enforce an inbox(event_id PRIMARY KEY) table on every participant.

Design Trade-Off

How Transactional Outbox & Idempotent Consumers are implemented

Before · Unbounded Coupling
  • No backpressure on spikes
  • Implicit shared state
  • Cascading tail latency
After · Bounded & Observable
  • Explicit capacity budgets
  • Isolated failure domains
  • Predictable p99 latency
# Idempotent Transactional Outbox relay loop (Python + Postgres)
def publish_pending_outbox_events(db_conn, kafka_producer, batch_size: int = 100) -> int:
    rows = db_conn.execute(
        "SELECT id, aggregate_id, payload FROM outbox WHERE published_at IS NULL "
        "ORDER BY id ASC LIMIT %s FOR UPDATE SKIP LOCKED",
        (batch_size,),
    ).fetchall()
    for event_id, agg_id, payload in rows:
        kafka_producer.send("saga.events", key=agg_id, value=payload)
        db_conn.execute("UPDATE outbox SET published_at = NOW() WHERE id = %s", (event_id,))
    db_conn.commit()
    return len(rows)

# Note: Wrap batch in try/except Exception: db_conn.rollback(); raise so failed Kafka sends do not leave partial DB state.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Temporal Orchestrator + Outbox + Semantic Locks.

Why this matters: Production architecture: see how the components compose end to end under real load.

Think of Production example: Temporal Orchestrator + Outbox + Semantic Locks as the intuition layer for Saga & Compensation Patterns: Production architecture: see how the components compose end to end under real load.

A Temporal workflow orchestrates Order (PENDING semantic lock + TTL sweeper), Inventory (commutative delta + inbox dedup), and Payment (Pivot). Every service commits domain state + outbox rows atomically, eliminating dual-write split-brain.

Zero Dual-Write

Local ACID Commit + Transactional Outbox + Idempotent Inbox

1.1. Atomic Outbox: Domain row and outbox event commit together—eliminating crash-induced split-brain.

2.2. Inbox Dedup: INSERT INTO inbox(event_id) ON CONFLICT DO NOTHING makes at-least-once retries safe.

3.3. TTL Sweeper: Stuck PENDING semantic locks expire cleanly if a saga hits workflow timeout.

Outbox + Inbox + Semantic Locks give Sagas reliable execution without distributed 2PC locks.
