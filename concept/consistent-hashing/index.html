Consistent Hashing

Distributing data dynamically across heterogeneous clusters without central coordination.

Orientation & Intuition

In distributed caching and storage, traditional modulo routing hash(key) % N remaps nearly 100% of keys whenever a server crashes or joins, triggering catastrophic cache stampedes. Consistent Hashing maps both data keys and server nodes onto the same virtual 32-bit ring ($0$ to $2^{32}-1$). Adding or removing a node only migrates $1/N$ of the keys, bounding rebalancing overhead and shielding database origins.

Key takeaway Traditional modulo hashing destroys cache hit ratios during cluster resizing. Consistent hashing bounds key reassignment to $K/N$, while Virtual Nodes (vNodes) ensure mathematically balanced load distribution across physical hardware.

Core Architecture & Trade-offs

Dynamic scaling in distributed storage (e.g. DynamoDB, Cassandra, Memcached clusters) requires elastic addition and removal of nodes without downtime. Without consistent hashing, single-node churn cascades into cluster-wide cache invalidation and database collapse.

Key Architecture Invariants

  • Maps data keys and server addresses onto a shared 32-bit integer space (the Hash Ring: 0 to 2^32 - 1).
  • Keys are assigned to the first server encountered when traversing the ring clockwise.
  • When a node joins or fails, only the keys between that node and its predecessor are reassigned (falling forward to the next clockwise node). Disruption is bounded to 1/N.
  • Virtual Nodes (vNodes) solve hash clustering: each physical node hashes multiple times (e.g. ServerA#1, ServerA#2), interleaving servers across the ring for uniform distribution.

When to Use

  • Distributed in-memory caching clusters (Memcached, Redis clusters) where cache miss storms must be avoided during scale-out/scale-in.
  • Distributed NoSQL storage systems (Apache Cassandra, Amazon DynamoDB, Riak) requiring partitioned, decentralized data ownership.
  • Load balancers routing persistent user sessions or WebSockets to backend worker fleets.

When NOT to Use

  • Single-server architectures or small fixed clusters with zero node churn.
  • Relational databases relying on global ACID transactions across multiple foreign keys.

Deep Dive & Production Considerations

📖 Operational Architecture of Consistent Hashing

Consistent hashing eliminates the structural flaw of traditional distributed routing by decoupling key placement from the absolute count of active nodes.

1. The Modulo Problem

In distributed caching, the naive approach to routing a key to a specific server is using the modulo operator:

text 
server_index = hash(key) % N  (where N is the number of servers)

If you have 4 servers ($N=4$), a key hashes to server 0, 1, 2, or 3.

The fatal flaw: If a server crashes ($N$ becomes 3), the result of hash(key) % 3 changes for almost every single key. This causes a massive cache miss storm, potentially taking down your origin databases.

2. The Hash Ring & Clockwise Traversal

Consistent hashing solves this by mapping both the data keys and the server nodes onto the same virtual ring (typically a 32-bit integer space from $0$ to $2^{32} - 1$).

text 
         [ Node A ] (Hash: 10)
             /   \
           /       \
 (Hash: 90)         (Hash: 25)
 [ Node D ]         [ Node B ]
           \       /
             \   /
         [ Node C ] (Hash: 60)

When a request for a key comes in, we hash the key to find its position on the ring. We then walk the ring clockwise until we find the first Server Node. That server owns the key.

The mathematical guarantee: If Node B crashes, only the keys that lived between Node A and Node B are reassigned (they fall forward to Node C). The rest of the ring remains completely untouched. You only move $1/N$ of your data!

$$\text{Fraction of Keys Reassigned} = \frac{1}{N}$$

3. Virtual Nodes (vNodes)

If you only have 4 physical servers, their hashes might cluster close together on the ring, causing severe load imbalance. We solve this using Virtual Nodes (vNodes):

  • Instead of hashing Server A once, we hash it 100–256 times: hash("ServerA#1"), hash("ServerA#2"), etc.
  • This interleaves the physical servers across the ring, perfectly balancing the load.
  • If Server A has 2x the RAM/CPU of Server B, we give Server A 200 vNodes and Server B 100 vNodes, achieving proportional capacity balancing.
typescript 
export class ConsistentHashRing {
  private ring: Map<number, string> = new Map();
  private sortedKeys: number[] = [];
  private vNodes: number;

  constructor(vNodes = 128) {
    this.vNodes = vNodes;
  }

  public addNode(nodeId: string): void {
    for (let i = 0; i < this.vNodes; i++) {
      const hash = this.murmurHash3(`${nodeId}#${i}`);
      this.ring.set(hash, nodeId);
      this.sortedKeys.push(hash);
    }
    this.sortedKeys.sort((a, b) => a - b);
  }

  public getNode(key: string): string | null {
    if (this.sortedKeys.length === 0) return null;
    const hash = this.murmurHash3(key);

    // Binary search for the first node with hash >= key's hash
    let low = 0;
    let high = this.sortedKeys.length - 1;
    while (low <= high) {
      const mid = (low + high) >> 1;
      if (this.sortedKeys[mid] >= hash) {
        high = mid - 1;
      } else {
        low = mid + 1;
      }
    }
    // Wrap around to index 0 if hash is greater than all nodes
    const targetIdx = low < this.sortedKeys.length ? low : 0;
    return this.ring.get(this.sortedKeys[targetIdx]) || null;
  }

  private murmurHash3(key: string): number {
    let hash = 0;
    for (let i = 0; i < key.length; i++) {
      hash = (Math.imul(31, hash) + key.charCodeAt(i)) | 0;
    }
    return Math.abs(hash);
  }
}
