A foundational engineering concept

Consistent
Hashing.

Consistent hashing assigns data keys to servers in a way that limits how many keys move when servers are added or removed. This helps avoid widespread cache misses and sudden load on databases.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Place keys and servers on the same hash ring. Assign each key to the next server clockwise, and use virtual nodes to spread work more evenly.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

With modulo routing such as hash(key) % numberOfServers, changing the number of servers can redirect many keys. In a cache, this can cause a surge of misses and overload the database. Consistent hashing changes assignments only in the affected parts of the ring.

  • Hash ring: a circular range of hash values where both keys and servers are placed.
  • Key assignment: a key belongs to the first server found by moving clockwise from the key's position.
  • Node change: when a server joins or leaves, only keys in the affected ring segment need reassignment.
  • Virtual nodes: multiple ring positions assigned to each physical server to improve distribution.
  • Replication: store copies on distinct physical servers when resilience is required.

Good candidates

  • Distributed caches where servers may be added or removed.
  • Distributed storage systems that partition data across nodes.
  • Systems that need to spread keys across a changing pool of workers.

Think twice

  • A single-server system or a small cluster that rarely changes.
  • Systems where another routing or partitioning strategy already meets the needs.
  • Workloads that require global transactions across data on many servers without additional coordination.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA cache cluster grows from 9 servers to 10. With modulo routing, many keys may map to different servers because the divisor changed. With consistent hashing, the new server takes over only a portion of the ring.

Move only the keys affected by a server change

Consistent hashing places both data keys and servers on a circular hash space called a ring. A key belongs to the first server found by moving clockwise from the key's position.

When a server joins or leaves, only keys in the affected ring segment need a new owner. This avoids remapping the entire keyspace as can happen with modulo routing.

  • Hash ring: the shared circular space of hash values.
  • Key assignment: move clockwise from the key to find its server.
  • Virtual nodes: give each physical server multiple positions on the ring to improve distribution.
  • Replication: keep copies on distinct physical servers when availability requires it.

Good candidates

  • Distributed caches that scale up or down.
  • Distributed storage systems that partition data across nodes.
  • Workloads where limiting key movement during membership changes is useful.

Think twice

  • A single server or small, stable cluster.
  • Systems that need a different partitioning strategy or global coordination.
  • Workloads where a node's successor cannot absorb additional traffic.

Adding a server, step by step

Imagine a cache cluster with nine servers. With modulo routing, adding a tenth server changes the divisor, so many keys may map to different servers. With consistent hashing, the new server is placed on the ring and takes over only the keys in its segment from the next server clockwise.

Most keys keep their existing owners. The keys that move may need to be fetched again or transferred, so the cluster still needs a plan for rebalancing and extra load.

Consistent hashing with 150–256 virtual nodes per server bounds load skew and limits key movement to ~K/N during node additions or failures, preserving cache hit rates.

Use virtual nodes to smooth out the ring

A physical server can appear at multiple positions on the ring. These positions are called virtual nodes. They help reduce the chance that one server receives too many keys simply because its single position landed in an unlucky spot.

Servers with more capacity can be assigned more virtual nodes, but the system should still monitor actual traffic and resource use. Virtual nodes improve distribution; they do not guarantee perfectly balanced load.

Fewer moved keys, with coordination overhead

Consistent hashing can limit how much data changes owners during scaling. In return, the system must maintain a consistent ring configuration and handle uneven load, failover, and replication.

A failed server may send extra work to its clockwise successor. Make sure remaining servers have enough headroom, and place replicas on distinct physical machines.

Before using consistent hashing

  • Use the same hash function and ring configuration wherever keys are routed.
  • Use virtual nodes if a single position per server creates uneven distribution.
  • Monitor key counts, request volume, and resource use per physical server.
  • Leave capacity for node failures and controlled rebalancing.
  • Place replicas on distinct physical servers, not just distinct virtual nodes.
  • Test what happens when a server joins, leaves, or becomes unreachable.
03 / Engineering trade-offs

Weighing architectural decisions

Limited key movement vs operational complexity

Advantage: Adding or removing a server usually affects only part of the keyspace.

Drawback: The ring and node changes need to be managed consistently by every client or routing service.

Virtual nodes vs resource overhead

Advantage: Multiple positions per server help reduce uneven load and support capacity-based weighting.

Drawback: More virtual nodes increase routing metadata and can add lookup and management overhead.

Replication vs storage and network cost

Advantage: Replicating data across physical servers can improve availability.

Drawback: Copies consume extra storage and require coordination during writes and node changes.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Uneven key distribution

A few servers may receive a much larger share of keys or traffic than others.

What helps: Use virtual nodes, monitor per-node load, and adjust node weights or placement when needed.

A failed server overloads its successor

The next server clockwise inherits keys and traffic, potentially becoming overloaded.

What helps: Keep capacity headroom, spread replicas across distinct physical servers, and use controlled failover or rebalancing.

Different clients calculate different owners

Clients with inconsistent ring membership, hash functions, or configuration may route the same key to different servers.

What helps: Use a consistent hashing implementation and hash configuration, and distribute membership changes reliably.

Too few virtual nodes

With too few positions, physical servers may be distributed unevenly around the ring.

What helps: Choose and validate a suitable virtual-node count based on the number of servers and workload.

Replication targets virtual nodes instead of machines

Several replicas may land on different virtual positions belonging to the same physical server, so one machine failure can lose multiple copies.

What helps: Choose replicas on distinct physical servers, not merely distinct virtual nodes.

05 / Practical checklist

Avoid these mistakes

  • Assuming consistent hashing guarantees perfectly balanced traffic without monitoring or virtual nodes.
  • Treating the 1/N movement estimate as an exact guarantee for every ring and workload.
  • Using inconsistent hash functions or ring configurations across clients.
  • Replicating data across virtual nodes without checking that replicas are on distinct machines.
  • Ignoring the extra capacity required when a node fails and its keys move elsewhere.
