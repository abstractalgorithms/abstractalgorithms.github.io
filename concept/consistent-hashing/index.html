STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Consistent Hashing.

Consistent hashing places both data keys and servers onto a circular hash space (a hash ring, e.g., [0 .. 2^32 - 1]). To route a key, compute hash(key) and walk clockwise to the first server on the ring.

With plain modulo routing (hash(key) % N), changing NNN from 9 to 10 remaps almost 90% of keys. On a consistent hash ring, adding or removing 1 server only reassigns keys in the single arc between the new server and its predecessor—roughly K/NK/NK/N keys—while assigning virtual nodes (vnodes) (150–256 tokens per host) smooths out uneven arc sizes.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Virtual Nodes & Physical Replica Awareness.

Naive consistent hashing (1 token per server) fails in two ways:

  1. Hot-Spot Skew: With only 4 servers on a ring, random hashing frequently gives one node 45% of the arc and another 8%.
  2. Cascading Failover Overload: If S1 crashes without vnodes, 100% of S1's traffic dumps onto its single clockwise neighbor S2, overloading S2 next. With 200 vnodes per host, S1's load spreads evenly across all surviving servers.
  3. Co-Located Replicas: Walking clockwise for RF=3 replicas can hit two vnodes belonging to the same physical server unless you skip duplicate physical hosts.
Minimal Key Movement

Adding or removing a node only invalidates keys in the immediately affected ring segment.

Weighted Vnodes

Assign more virtual nodes to beefier hardware (e.g., 256 vnodes for 64 GB RAM vs. 128 for 32 GB RAM).

Consistent Hash Function

Use a fast, uniform non-cryptographic hash (MurmurHash3 or xxHash) identical across all routing clients.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Consistent Hashing is used.

Consistent hashing powers distributed caches, Dynamo-style storage partitions, and sticky L7 load balancers.

ChoiceWhat it buysWhat it costs
Distributed Caches (Memcached / Twemproxy / Envoy)Prevents cluster-wide cache stampedes when cache nodes autoscale or restart.All clients/proxies must share an identical view of ring membership to avoid split routing.
Partitioned KV Stores (Cassandra / DynamoDB / Riak)Tokens map key ranges cleanly; vnodes parallelize streaming during node bootstrap/repair.Must place replicas on distinct physical racks/AZs when walking the ring.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How a Consistent Hash Ring with Vnodes is implemented.

Maintain a sorted NavigableMap / bisect array of (token, physical_host) pairs and walk clockwise (wrapping around 0) while skipping already-selected physical hosts for replication.

// Consistent Hash Ring using TreeMap and virtual nodes (Java)
public final class ConsistentHashRing {
    private final NavigableMap<Long, String> ring = new TreeMap<>();
    private final int vnodesPerHost;

    public ConsistentHashRing(int vnodesPerHost) {
        this.vnodesPerHost = vnodesPerHost;
    }

    public void addHost(String host) {
        for (int i = 0; i < vnodesPerHost; i++) {
            ring.put(hash64(host + "#" + i), host);
        }
    }

    public List<String> getReplicas(String key, int rf) {
        if (ring.isEmpty()) return List.of();
        List<String> result = new ArrayList<>(rf);
        Set<String> seenHosts = new HashSet<>();
        long h = hash64(key);
        var tail = ring.tailMap(h, true).values().iterator();
        var head = ring.values().iterator();
        while (result.size() < rf && seenHosts.size() < ring.size()) {
            String host = tail.hasNext() ? tail.next() : (head.hasNext() ? head.next() : null);
            if (host == null) break;
            if (seenHosts.add(host)) result.add(host); // skip duplicate physical hosts
        }
        return result;
    }
}

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Modulo vs. Consistent Hashing vs. Rendezvous vs. Jump Hash.

Compare key-movement overhead, memory, and dynamic node support.

ChoiceWhat it buysWhat it costs
Consistent Hashing + Vnodes~K/N key movement; supports arbitrary node joins/removals and weighted hosts.O(N * V) ring state in memory; requires consistent membership view across callers.
Rendezvous (HRW) HashingZero ring state; computes argmax_i hash(key, node_i) with minimal K/N movement.O(N) lookup time per key (fine for N <= 50, slower for huge clusters).
Jump Consistent Hash / Redis 16,384 SlotsJump Hash uses O(1) memory and O(ln N) time; Redis slots give explicit manual rebalancing.Jump Hash only supports removing the *last* numbered bucket (not arbitrary middle nodes).

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Rack-Aware Cassandra / Envoy Ring + Bounded Load.

Large cache/KV fleets pair consistent hashing with Bounded-Load Consistent Hashing (Google Maglev / Envoy): if a hot-key node's load exceeds (1 + epsilon) * avg_load, requests spill clockwise to the next healthy node, preventing single-node meltdowns.

Bounded-Load Routing

Envoy Router -> Hash Ring Lookup -> Load Cap Check -> Distinct-AZ Replica

1.Hot-Key Spillover: Bounded-load hashing caps any single cache node at 1.25x average load during viral spikes.

2.Rack/AZ Diversity: Replica selection skips vnodes in the same AZ so a zone outage never loses multiple replicas.

3.Headroom Sizing: Keep cluster utilization <= 70% so surviving nodes absorb a dead node's vnodes cleanly.

Bounded-load spillover + rack-aware vnode placement solves both viral hot keys and zone failures.
