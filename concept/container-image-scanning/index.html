THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Pair build-time SBOM generation (Syft/Trivy) with VEX-filtered admission gates (Kyverno/Cosign) so you block reachable critical CVEs without drowning engineers in unexploitable base-image noise.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

A single container image bundles an entire Linux userland, language runtime, and dozens of transitive libraries. Vulnerabilities like CVE-2024-21626 (runc) or CVE-2021-44228 (Log4Shell) sit dormant in base layers until an attacker pivots from an exposed HTTP endpoint to host escape.

  • OCI images are stacked tarballs; a vulnerability deleted in a later RUN rm layer still exists in earlier layer blobs and remains extractable.
  • Distro-specific feeds (Alpine secdb, Debian Security Tracker, Red Hat OVAL) are far more accurate than raw NVD CPE matching because maintainers backport fixes without bumping upstream version numbers.
  • Generating a CycloneDX 1.5 or SPDX 2.3 SBOM once at build time lets you re-evaluate zero-day exposure in milliseconds without re-pulling multi-gigabyte images.
  • Cryptographic attestation via Sigstore Cosign binds the scan result and SBOM to the immutable sha256 image digest, preventing tag-mutation bypasses.
  • VEX (Vulnerability Exploitability eXchange) documents and reachability analysis cut alert fatigue by 70–90% by suppressing CVEs in unused binaries or uncalled functions.

Good candidates

  • Every CI/CD build producing OCI images destined for staging or production Kubernetes clusters.
  • Admission control in Kubernetes (Kyverno or OPA Gatekeeper) to reject unsigned or unpatched images before pod scheduling.
  • Continuous registry re-scanning of already-deployed image digests when new CVEs publish to NVD, OSV, or distro security feeds.

Think twice

  • As a substitute for runtime intrusion detection (eBPF sensors like Falco or Tetragon) against zero-day exploits.
  • To block PR merges on unfixed LOW or MEDIUM OS-package CVEs that have no upstream patch and no reachable code path.
  • On ephemeral local dev containers where blocking on network-fetched vulnerability DBs stalls developer iteration.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA Go 1.22 payments microservice built on ubuntu:22.04 (185 MB) triggered 47 HIGH/CRITICAL Trivy alerts per build—mostly in openssl, curl, and apt—causing developers to bypass the CI gate.

The idea

Container image scanning treats an OCI image not as an opaque binary, but as a verifiable manifest of filesystem layers, package databases, and language dependency graphs. An OCI image consists of a JSON manifest pointing to a config blob and an ordered stack of compressed tar layers. Scanners like Trivy and Grype unpack these layers virtually (without executing the container), extract package manifests (/var/lib/dpkg/status, /lib/apk/db/installed, go.mod, package-lock.json, pom.xml), and cross-reference exact package-version pairs against curated vulnerability advisories (NVD, OSV, GitHub Advisory Database, and vendor OVAL/secdb feeds).

Because modern supply-chain security separates inventory from evaluation, best-in-class pipelines first generate a standardized SBOM (CycloneDX 1.5 or SPDX 2.3) via Syft or Trivy, attach VEX exploitability statements, and cryptographically sign the bundle to the immutable sha256 digest with Sigstore Cosign. Admission controllers then verify both the signature and policy compliance in milliseconds at cluster scheduling time.

Concrete walkthrough

Consider a Python 3.12 FastAPI service built via GitHub Actions and deployed to Amazon EKS:

  1. Multi-stage build & secret hygiene: Stage 1 installs uv dependencies; Stage 2 copies only the virtualenv into cgr.io/chainguard/python:latest (~48 MB) using BuildKit --mount=type=secret for private PyPI credentials.
  2. Inventory & Scan: trivy image --format cyclonedx --output sbom.cdx.json ghcr.io/acme/billing@sha256:9f8a... catalogs 38 Wolfi APK packages and 64 Python wheels in ~4.2 seconds using a cached 45 MB BoltDB.
  3. Policy Evaluation: A follow-up trivy sbom --severity CRITICAL,HIGH --ignore-unfixed --exit-code 1 sbom.cdx.json checks the SBOM against the latest advisory feed and applies a signed .vex.json suppressing CVE-2023-45853 (present in an unused zlib CLI tool).
  4. Attestation: cosign attest --predicate sbom.cdx.json --type cyclonedx ghcr.io/acme/billing@sha256:9f8a... stores the signed SBOM in the OCI registry via Rekor transparency logs.
  5. Admission & Runtime: Kyverno checks the Cosign signature and scan attestation age (<24h) before allowing the Pod to schedule, while registry webhooks re-evaluate stored SBOMs every 6 hours.

End-to-end container scanning separates SBOM extraction from advisory evaluation, binds signed attestations to immutable digests, and enforces policy at Kubernetes admission.

Layer mechanics, backports, and reachability

Naive vulnerability scanners match software names to NVD Common Platform Enumeration (CPE) strings, producing massive false-positive rates on Linux distributions. Debian, Ubuntu, RHEL, and Alpine routinely backport security patches into older upstream package versions (for example, openssl 3.0.11-1~deb12u2 remains 3.0.11 upstream while containing the fix for a 3.0.13 CVE). Distro-aware scanners parse /etc/os-release and query vendor-specific security trackers first.

Beyond OS packages, application-level reachability separates theoretical exposure from real risk. Tools like govulncheck or Endor Labs construct call graphs from main() to third-party symbols: if your service imports golang.org/x/net solely for html.EscapeString, a CVE inside http2.Server is unreachable at runtime and can be documented via a VEX code_not_in_execute_path statement.

Failure modes

The most dangerous failure mode is digestless deployment: scanning :latest or :v1.2 in CI and deploying by tag allows a stale or compromised image to slip past admission. A close second is secret persistence across layers—copying .env or SSH keys in layer 3 and deleting them in layer 4 leaves the secret readable via docker save or skopeo copy. Finally, unbounded policy gates that block builds on unfixed MEDIUM CVEs force engineers to add blanket .trivyignore waivers, eroding trust in the entire security pipeline.

Runtime correlation and continuous triage

Static scanning cannot tell you whether a vulnerable shared library is actually loaded into process memory. Pairing build-time SBOMs with runtime eBPF telemetry (such as Tetragon or Falco) closes the loop: if a newly disclosed CRITICAL CVE hits an image running across 40 pods, runtime process/file-open telemetry identifies which pods actually execute the affected binary, letting SREs prioritize rolling restarts in minutes instead of orchestrating blind cluster-wide drains.

Practical checklist

  • Switch production stages to Distroless, Chainguard Wolfi, or scratch using multi-stage Dockerfiles.
  • Use BuildKit --mount=type=secret for private package registries; run trivy fs --scanners secret on every PR.
  • Generate a CycloneDX 1.5 or SPDX 2.3 SBOM during CI and push it as a Cosign-signed OCI attestation.
  • Gate CI merges strictly on CRITICAL and HIGH CVEs with --ignore-unfixed, routing MEDIUM/unfixed items to an async backlog.
  • Enforce sha256 digest pinning and Cosign signature verification in Kyverno or OPA Gatekeeper.
  • Schedule registry-side SBOM re-evaluation every 6 hours to detect zero-day drift on already-running workloads.
03 / Engineering trade-offs

Weighing architectural decisions

Strictness vs. Delivery Velocity

Advantage: Failing CI on any `HIGH` or `CRITICAL` CVE prevents known-exploitable code from reaching production.

Drawback: Unfixed upstream OS CVEs can freeze all hotfixes unless paired with `--ignore-unfixed` or time-bound VEX exceptions.

Minimal Base Images (Distroless/Wolfi) vs. Debuggability

Advantage: Eliminating shells, package managers, and libc bloat removes 80%+ of the CVE surface area.

Drawback: Engineers cannot `kubectl exec` into a shell and must rely on `kubectl debug` ephemeral containers and structured telemetry.

Central Registry Scanning vs. CI-Only Scanning

Advantage: Registry scanners catch newly disclosed CVEs against long-lived running images that haven't been rebuilt in weeks.

Drawback: Requires persistent storage, DB sync bandwidth, and automated Jira/Slack routing so stale findings actually get patched.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Tag Mutation Bypass (TOCTOU)

CI scans `myapp:v1.4.2`, passes, and pushes; an attacker or misconfigured pipeline overwrites the mutable tag before Kubernetes pulls it.

What helps: Sign immutable `sha256` digests with Cosign and enforce digest-only references in Kyverno admission policies.

Stale Vulnerability Database

Air-gapped or cached CI runners scan against a Trivy/Grype DB that is 14 days old, silently missing newly published critical CVEs.

What helps: Enforce a max DB age check (`--db-repository` mirror synced every 6 hours) and fail builds if DB metadata is older than 24 hours.

False Negatives on Static/Vendored Binaries

Scanners inspecting only `/var/lib/dpkg` or `apk` miss statically linked Go, Rust, or C++ binaries compiled without embedded build-info or SBOM metadata.

What helps: Enable language-specific analyzers (`go.mod`, `Cargo.lock`, `package-lock.json`) and compile with Go `-buildinfo` / Syft source cataloging.

Alert Fatigue & Blanket Exceptions

Teams faced with 300 unfixable `MEDIUM` CVEs add global `.trivyignore` wildcards, accidentally suppressing future critical alerts.

What helps: Gate only on `CRITICAL`/`HIGH` with `fixed` status, require expiration dates on VEX exceptions, and auto-reopen expired waivers.

05 / Practical checklist

Avoid these mistakes

  • Scanning only the Dockerfile base image instead of the final multi-stage output image containing application dependencies.
  • Leaving `AWS_SECRET_ACCESS_KEY` or `.npmrc` tokens in intermediate `ARG`/`ENV` layers without using BuildKit `--mount=type=secret`.
  • Ignoring distro backport metadata and panicking over upstream version strings reported by naive CPE scanners.
  • Treating a clean scan at deploy time as permanent—an image scanned 30 days ago may have 5 new `CRITICAL` CVEs today.
  • Deleting sensitive files in a subsequent `RUN rm` instruction instead of using multi-stage builds, leaving secrets intact in earlier OCI layer blobs.
