THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Match the balancing layer and algorithm to your traffic: use L4 (Maglev/DSR) for raw packet scale, L7 (Envoy/ALB) for gRPC/HTTP routing, and Power-of-Two-Choices (P2C) + EWMA to crush p99 tail latency.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

A single server has hard CPU, NIC, and failure boundaries; without load balancing, one overloaded instance or crashed AZ takes down the whole service. Worse, naive round-robin load balancing sends heavy requests to already-busy nodes, spiking p99 tail latency even when cluster average CPU sits at 40%.

  • L4 (Transport) balancers route on (src_ip, src_port, dst_ip, dst_port, proto) using IPVS/eBPF/Maglev at millions of PPS; L7 (Application) balancers terminate TLS/HTTP to route on headers, paths, and gRPC frames.
  • gRPC / HTTP/2 Trap: Because HTTP/2 multiplexes thousands of RPCs over one TCP connection, an L4 balancer sends all traffic to a single backend; you must use L7 load balancing or client-side balancing.
  • Power of Two Choices (P2C) + Peak EWMA (used by Envoy and Linkerd) samples 2 random backends and picks the one with lower active requests or exponentially weighted moving average latency—cutting tail latency dramatically over Round Robin.
  • Combine active health checks (/healthz every 5s) with passive outlier detection (ejecting a pod for 30s after 3 consecutive 5xx/timeouts) to catch gray failures.
  • Consistent Hashing (Ketama / Maglev) maps keys (user_id, session_id, cache_key) to the same backend with minimal remapping (1/N keys) on node churn—vital for stateful caches and LLM KV-cache affinity.

Good candidates

  • Horizontally scaling stateless APIs, microservices, or LLM inference replicas across multiple pods, VMs, or Availability Zones.
  • Zero-downtime deployments (blue/green, canary traffic splitting) and automatic outlier ejection when a backend node degrades.
  • Multiplexed protocols like HTTP/2 and gRPC, where L4 TCP-level balancing pins an entire long-lived connection to one backend pod.

Think twice

  • Single-node local development or tiny internal tools where a single reverse proxy (Caddy/NGINX) without multi-AZ health meshes suffices.
  • Stateful leader-only databases (e.g., primary PostgreSQL writes) where arbitrary request spraying breaks consistency—route via service discovery or read-replica pools instead.
  • Blindly stacking multiple redundant L7 proxies in series when each hop adds TLS termination, serialization, and debugging overhead.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA microservices team scaled a Go gRPC service from 4 to 20 pods behind a Layer-4 Network Load Balancer, yet 2 pods hit 100% CPU while 18 pods sat idle.

The idea

At its core, load balancing solves a distributed scheduling problem: given M concurrent clients and N heterogeneous, failure-prone backends, map each connection or request to a healthy backend so no single node saturates while total throughput and tail latency stay optimal.

Production architectures almost always use a two-tier pipeline:

  1. Edge L4 Tier (Anycast BGP + ECMP -> Maglev/IPVS): Statelessly hashes 5-tuples across L7 proxy nodes at line rate without terminating TLS.
  2. L7 Proxy Tier (Envoy / NGINX / ALB): Terminates TLS, inspects HTTP/gRPC metadata, applies rate limits and circuit breakers, and dispatches individual requests using Power of Two Choices (P2C) or Consistent Hashing.

Concrete walkthrough

Trace a single gRPC API request hitting a high-traffic Kubernetes cluster:

  1. DNS & Anycast BGP: Client resolves api.example.com to an Anycast VIP announced by 3 regional PoPs; ECMP routes the TCP SYN packet to an L4 Maglev/IPVS node.
  2. L4 -> L7 Dispatch: Maglev hashes the 5-tuple consistently to envoy-ingress-04 (so even if another L4 node reboots, the TCP flow stays pinned to envoy-ingress-04).
  3. L7 Termination & Auth: envoy-ingress-04 terminates TLS 1.3, parses the HTTP/2 :path (/inference.v1/Generate), and checks token-bucket rate limits.
  4. P2C-EWMA Backend Selection: Envoy picks 2 healthy pods from the 24-pod inference endpoint list (pod-07 with Peak EWMA 18 ms vs pod-19 with Peak EWMA 94 ms) and forwards the RPC over a pre-warmed HTTP/2 connection pool to pod-07.
  5. Outlier Protection: If pod-07 returns 3 consecutive 503/DEADLINE_EXCEEDED responses within 10s, Envoy's passive outlier detector ejects pod-07 for 30s without waiting for the next active /readyz poll.

Combining stateless L4 scaling at the edge with L7 P2C-EWMA and passive outlier detection prevents both HTTP/2 pinning and tail-latency spikes.

Algorithms: P2C, Peak EWMA, and Consistent Hashing

  • Power of Two Choices (P2C): Checking all N backends per request takes O(N) and causes 'herd' behavior when distributed proxies all see the same single least-loaded node and stampede it simultaneously. P2C picks 2 backends uniformly at random (O(1)) and routes to the better one—mathematically reducing maximum queue depth from O(log N / log log N) to O(log log N).
  • Peak EWMA: Active-connection count alone misses a degraded pod that fails fast or stalls on GC pauses. Peak EWMA tracks each backend's exponentially weighted moving average latency multiplied by (active_requests + 1), automatically steering traffic away from slow or throttling nodes.
  • Maglev & Ring Hash: When routing stateful caches or LLM prefix caches, Ring Hash (Ketama) or Google Maglev builds a lookup table where adding/removing 1 of N nodes remaps only ~1/N of keys instead of invalidating the entire cache.

Failure modes

  1. Retry Storms Amplifying Outages: If 3 microservice hops each retry 3 times on timeout, a single slow downstream DB receives 3 * 3 * 3 = 27x normal traffic. Fix: Enforce retry budgets (max 10–20% of active requests) and per-request deadline propagation (grpc-timeout).
  2. Connection Pool Exhaustion / Ephemeral Port Starvation: Opening a new TCP connection per upstream request exhausts the 65,535 ephemeral ports (TIME_WAIT) at high RPS. Fix: Enable HTTP/1.1 keep-alive / HTTP/2 multiplexing and tune tcp_tw_reuse.
  3. Thundering Herd on Pod Restart: All new pods register simultaneously and get hit before warming up. Fix: Use slow-start weight ramping and jittered health-check intervals.
  4. L4 Asymmetric Routing Drops: Under Direct Server Return (DSR), misconfigured VIP loopback interfaces or strict rp_filter kernel settings silently drop return packets. Fix: Set net.ipv4.conf.all.rp_filter=2 (loose mode) and automate VIP loopback provisioning.

Zero-downtime draining and zone awareness

Most 502/504 errors during deployments happen because the orchestrator kills a pod before the load balancer stops sending it traffic:

  • Decoupled Readiness: On SIGTERM, the app immediately flips /readyz to 503 (while keeping /livez 200), sends Connection: close or HTTP/2 GOAWAY frames, and waits 15–30s (terminationGracePeriodSeconds > preStop + drain) so in-flight requests finish cleanly.
  • Zone-Aware Routing: Configure Envoy/K8s Topology Aware Hints so proxies route within the same Availability Zone whenever local capacity >=80% of demand, eliminating cross-AZ latency and data-transfer bills.

Practical checklist

  • Use L7 load balancing (Envoy/ALB/NGINX) for HTTP/2 and gRPC; reserve L4 (NLB/IPVS/Maglev) for edge TCP/UDP scale.
  • Configure P2C + Least-Request or Peak EWMA for heterogeneous API workloads, and Consistent Hashing with bounded loads for cache/LLM-prefix affinity.
  • Pair shallow /readyz probes (no external DB calls) with passive outlier detection (max_ejection_percent <= 50%).
  • Enforce GOAWAY + preStop sleep (15–30s) on SIGTERM so rolling deploys drop zero in-flight requests.
  • Enable retry budgets (10–20% cap) and end-to-end deadline propagation to prevent retry storms.
  • Turn on zone-aware routing to avoid unnecessary cross-AZ latency and egress charges.
03 / Engineering trade-offs

Weighing architectural decisions

L4 (IPVS/Maglev/DSR) vs. L7 (Envoy/ALB/NGINX)

Advantage: L4 handles massive packet rates (>10M PPS) with near-zero CPU overhead and preserves client IPs via Direct Server Return (DSR).

Drawback: Cannot inspect HTTP paths, JWTs, or gRPC requests, and cannot rebalance multiplexed HTTP/2 connections.

Round Robin vs. Least-Connections / P2C-EWMA

Advantage: Round Robin is stateless, O(1), and zero-coordination across distributed balancer replicas.

Drawback: Ignores heterogeneous request costs (e.g., a 5s PDF export vs a 5ms health check), causing severe head-of-line queuing on slow nodes.

Consistent Hashing vs. Stateless Least-Loaded

Advantage: Maximizes local in-memory cache and KV-cache hit rates by pinning keys to specific backends.

Drawback: A viral 'hot key' can overload its assigned shard unless mitigated with bounded loads or key salting.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Herd / Cascading Failure via Health Check Storm

A backend slows down under load, fails `/healthz` timeouts, gets ejected, and dumps its traffic onto the remaining 4 nodes—causing them to fail `/healthz` too in a domino collapse.

What helps: Cap max ejection percentage (e.g., Envoy `max_ejection_percent: 50%`) and panic-threshold routing (fall back to all hosts if healthy % drops below 50%).

Slow-Start Cold Cache Spike

A newly booted pod passes `/healthz` immediately and receives full traffic before JIT compilation or local caches warm up, timing out user requests.

What helps: Enable slow-start mode (linearly ramping weight over 30–60s) and separate `/livez` from `/readyz`.

Cross-AZ Bandwidth & Latency Tax

A cluster-wide balancer sprays requests across 3 Availability Zones evenly, adding 1–2 ms per hop and $0.01–$0.02/GB inter-AZ data transfer fees.

What helps: Enable zone-aware / topology-aware routing so traffic prefers same-AZ backends unless local capacity is exhausted.

Sticky Session / Consistent Hash Imbalance

One enterprise tenant generates 40% of traffic on a single `tenant_id` hash bucket, saturating one pod.

What helps: Use Consistent Hashing with Bounded Loads (cap node load at 1.25x mean) or salt hot keys across `k` virtual buckets.

05 / Practical checklist

Avoid these mistakes

  • Putting gRPC or HTTP/2 clients behind an L4 TCP load balancer without client-side balancing or an L7 proxy.
  • Implementing `/healthz` that queries the primary database—turning a transient DB hiccup into total fleet-wide pod eviction.
  • Disabling connection keep-alives between L7 proxy and backends, forcing a fresh TCP + TLS handshake on every internal hop.
  • Forgetting graceful draining (`SIGTERM` -> fail `/readyz` -> wait `preStop` 15–30s) during rolling deploys, causing 502 Bad Gateway spikes.
  • Relying on DNS round-robin alone for failover—clients and JVMs cache DNS TTLs aggressively and ignore dead IPs.
