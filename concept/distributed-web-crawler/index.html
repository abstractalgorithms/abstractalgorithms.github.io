The idea to keep with you

To bound blast radius during partial cluster failures, route each hostname deterministically to one Back Queue with a per-host politeness timer (`10x` last RTT) and cached `robots.txt` rules.

TL;DR30-second simplified summary
▾

A naive FIFO queue of discovered URLs fails catastrophically at web scale: links from wikipedia.org cluster together and flood one host with thousands of concurrent requests (violating politeness and getting IP-banned), while high-value news pages wait behind millions of low-value forum links.

The Mercator URL Frontier splits scheduling into two stages: K Front Queues ordered by PageRank/freshness priority, and M Back Queues where a consistent-hash router maps every URL's hostname to exactly one Back Queue.

Core Intuition & Failure Mode

1.Naive FIFO Trap: A single priority queue sends 500 workers simultaneously to wikipedia.org, triggering IP bans.

2.Mercator Two-Stage Split: Front Queues rank URL importance; Back Queues enforce 1 active request + crawl-delay per host.

3.Work Conservation: Workers stay 100% busy across millions of other hosts while any single host cools down.

The Mercator Frontier separates priority Front Queues from per-host Back Queues to maximize throughput without DDoSing origins.

STAGE 02 · CORE MECHANICS

Architectural Mechanics

1.Biased Front Drain: Higher-priority Front Queues are sampled more frequently without starving lower-priority tiers.

2.Sticky Host Mapping: Hashing hostname -> Back Queue ensures only one queue tracks a domain's crawl-delay.

3.Dynamic Backoff: Add crawl_delay + 2 * last_rtt after each fetch so slow origins automatically slow down.

Biased Front-Queue draining, consistent host hashing, and a ready-time min-heap enforce adaptive per-host politeness.

Engineering Decision Framework
Problem
How to implement Distributed Web Crawler & Mercator URL Frontier without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
To bound blast radius during partial cluster failures, route each hostname deterministically to one Back Queue with a per-host politeness timer (10x last RTT) and cached robots.txt rules.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

STAGE 03 · SAFE IMPLEMENTATIONintermediate

Mercator Politeness Heap Scheduler.

Why this matters: Implement PolitenessFrontier with per-host deques and a min-heap that never dispatches before ready_at.

import heapq
from collections import deque

class PolitenessFrontier:
    def __init__(self) -> None:
        self.back_queues: dict[str, deque[str]] = {}
        self.ready_heap: list[tuple[float, str]] = []

def push(self, host: str, url: str, now: float) -> None:
        if host not in self.back_queues:
            self.back_queues[host] = deque()
            heapq.heappush(self.ready_heap, (now, host))
        self.back_queues[host].append(url)
STAGE 03 · SAFE IMPLEMENTATION

Mercator Politeness Heap Scheduler

1.One Entry Per Host: Keep at most one heap entry per active host to prevent heap bloat when a domain has 1M URLs.

2.Empty Deque Cleanup: Only re-insert (next_ready, host) into ready_heap if back_queues[host] remains non-empty.

3.O(log M) Scheduling: Heap size M equals active hosts—not total URLs—keeping pops fast even at 1B URLs.

Maintaining one heap entry per active host keeps scheduling O(log M) while strictly enforcing per-host cooldowns.

STAGE 04 · SCALING & TRADE-OFFS

Throughput & Latency Trade-Offs

1.URL Seen Set: A hash set of 10B URLs needs ~640 GB RAM; a partitioned Bloom/Cuckoo filter fits in ~12-18 GB.

2.DNS Bottleneck: Synchronous gethostbyname() blocks worker threads; use async c-ares/Unbound with local caching.

3.Disk Spillover: Back-queue tails spill to RocksDB/disk so billions of queued URLs never OOM frontier RAM.

URL canonicalization, partitioned Bloom filters, and async DNS caching sustain 10K+ pages/sec within bounded RAM.

Blast-Radius & Failure Isolation

1.Crawler Traps: Infinite calendar links (/2026/11/24/...) or session-ID URLs exhaust frontier queues unless depth-capped.

2.Strict Timeouts: Cap TCP connect, TLS handshake, and body size (e.g., 10 MB) so tarpits cannot pin workers.

3.5xx / 429 Backoff: Exponentially back off hosts returning 429/503 and cap consecutive failures per domain.

robots.txt caching, URL depth caps, and strict read timeouts isolate crawler traps and slow tarpits.
