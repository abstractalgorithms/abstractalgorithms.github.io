Circuit Breakers & Resilience Patterns

Prevent cascading microservice outages by tripping circuit breakers when downstream failure thresholds are breached.

Orientation & Intuition

A circuit breaker wraps remote network calls in a stateful monitoring harness that automatically trips OPEN to fail-fast when downstream error or timeout thresholds breach, preventing caller thread exhaustion and cascading distributed outages. By failing fast, circuit breakers insulate upstream services and grant recovering dependencies breathing room to heal.

Key takeaway The three states are non-negotiable: CLOSED monitors error rates during normal traffic; OPEN immediately fails fast without making remote network calls; and HALF-OPEN executes rate-limited probe trials to verify recovery before restoring full production load.

Core Architecture & Trade-offs

In microservice architectures, synchronous network calls block worker threads. When a downstream service slows or fails, upstream threads back up in unbounded queues, exhausting database connections and CPU, eventually causing global platform brownouts.

Key Architecture Invariants

  • Finite State Machine: Transitions deterministically between CLOSED, OPEN, and HALF-OPEN states based on continuous error telemetry.
  • Sliding Evaluation Window: Monitors failure percentages over a rolling time window (e.g. 10 seconds) or fixed call count (e.g. 100 calls) with minimum request thresholds.
  • Half-Open Recovery Canary: Sends a limited trial batch (e.g. 5 requests) to downstream services; if all succeed, circuit closes; if any fail, circuit trips back to open.
  • Thread Pool Isolation (Bulkheading): Pairs with dedicated thread pools so that one slow dependency cannot consume threads allocated to others.
  • Graceful Degradation Fallbacks: Returns cached data, empty recommendations, or static placeholders when the circuit is OPEN.

When to Use

  • Wrapping remote HTTP, gRPC, and database calls in distributed microservice call chains.
  • Protecting caller thread pools from thread starvation and memory exhaustion during third-party API outages.
  • Enabling graceful degradation (serving stale cache, default values, or simplified UI) when dependencies fail.
  • Preventing the thundering herd from crushing an upstream service while it is rebooting after a crash.

When NOT to Use

  • In-memory CPU-bound calculations or local disk reads where network latency does not exist.
  • Write-critical idempotent transactions where operations cannot fail fast or serve stale fallbacks (use transactional outbox instead).
  • Endpoints where callers have asynchronous fire-and-forget message broker queues.

Deep Dive & Production Considerations

📖 Operational Architecture of Circuit Breakers

In distributed systems, failures are inevitable. A circuit breaker acts as an automatic electrical fuse for software dependencies: when downstream failure rates cross safety thresholds, the breaker trips to protect the caller from thread pool exhaustion.
