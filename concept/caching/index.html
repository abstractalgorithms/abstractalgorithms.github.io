The idea to keep with you

Caching keeps a reusable copy of data so an application can avoid repeating a database query, calculation, or network call. It can make responses faster and reduce database load. The trade-off: the copy may be out of date.

01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Caching.

Caching stores the result of an expensive database query, computation, or RPC in fast memory (in-process L1 or distributed Redis/Memcached) so subsequent reads reuse it in sub-millisecond time.

Every cache design revolves around five core primitives: Cache Hit (served from cache), Cache Miss (computed/fetched from source of truth), TTL (expiry window bounding staleness), Invalidation (deleting/updating on write), and Eviction (LRU/LFU removal when RAM is full).

Cache-Aside Read/Write Path

App -> L1/Redis Cache -> Singleflight Guard -> PostgreSQL

1.Cache-Aside Read: On hit, return in <1 ms; on miss, coalesce via singleflight, query Postgres, and SETEX with jitter.

2.Delete-on-Write: After committing a DB update, DEL product:42 rather than trying to race-update the cached JSON.

3.Eviction Budget: Configure maxmemory-policy allkeys-lru/lfu so Redis never OOMs under burst.

Keeping PostgreSQL as the clear source of truth with TTL jitter and singleflight prevents both staleness and meltdowns.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Stampede, Avalanche & Penetration Defenses.

A naive cache works fine in calm traffic and collapses on bad days due to three failure modes:

  1. Cache Avalanche: Thousands of keys loaded at deploy time share the exact same TTL (300s) and expire simultaneously, sending a flood of misses to PostgreSQL. Fix: Add random TTL jitter (300s +/- 30s).
  2. Hot-Key Stampede (Breakdown): One viral key (product:42) expires while 5,000 RPS hit it—all 5,000 threads miss and hammer the DB at once. Fix: Request coalescing (singleflight) or probabilistic early refresh.
  3. Cache Penetration: Attackers query nonexistent IDs (product:-999), bypassing the cache every time. Fix: Bloom filters or short-TTL negative caching (NULL sentinel).
Invalidation & Stampede

Cache-Aside Miss Coalescing & Post-Commit Invalidation

Singleflight collapses thousands of concurrent misses for the same expired hot key into a single database query.

Invalidate, Don't Blindly Overwrite

Updating DB + deleting cache is safer than dual-writing DB + cache, though a concurrent reader can still race unless versioned.

Bound Fallback Concurrency

Even with caching, put a semaphore/bulkhead in front of the DB fallback so a cold Redis restart cannot take down Postgres.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Caching Patterns fit.

Start with one shared Redis layer; add in-process L1 (Caffeine/Ristretto) or CDN layers only when latency or cost justifies extra invalidation complexity.

ChoiceWhat it buysWhat it costs
Cache-Aside (Lazy Loading)Only caches actually requested keys; resilient if Redis is flushed or restarts.First read is slow (miss penalty); invalidation and refill can race under concurrent writes.
Write-ThroughCache stays warm on writes; consistent read-after-write through the cache tier.Adds write latency and caches cold data that may never be read.
Write-Behind (Write-Back)Absorbs extreme write spikes by batching dirty cache writes asynchronously to DB.Data loss risk if cache node crashes before async flush; complex recovery.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How TTL Jitter, Singleflight, and Eviction are managed.

Measure hit rate, eviction rate, p99 latency, cache error rate, and DB fallback QPS together—a 99% hit rate still crashes your DB if the remaining 1% is unthrottled during a hot-key stampede.

# Cache-aside with random TTL jitter, negative caching, and per-key coalescing (Python)
import random, threading

_inflight_locks: dict[str, threading.Lock] = {}
_registry_lock = threading.Lock()

def get_product_cached(redis, db, product_id: int, base_ttl: int = 300):
    key = f"product:{product_id}"
    cached = redis.get(key)
    if cached is not None:
        return None if cached == b"__NULL__" else cached

    with _registry_lock:
        key_lock = _inflight_locks.setdefault(key, threading.Lock())

    with key_lock: # single-process stampede guard
        cached = redis.get(key)
        if cached is not None:
            return None if cached == b"__NULL__" else cached
        row = db.fetch_product(product_id)
        jittered_ttl = base_ttl + random.randint(-30, 30) # avalanche guard
        if row is None:
            redis.setex(key, 60, b"__NULL__") # negative cache stops penetration
            return None
        redis.setex(key, jittered_ttl, row)
        return row

Alternatives: In-Process L1 vs. Distributed Redis vs. CDN Edge.

Compare latency, consistency, and operational overhead across cache tiers.

ChoiceWhat it buysWhat it costs
In-Process L1 (Caffeine / Guava)Sub-microsecond RAM reads; zero network serialization; immune to Redis outages.Per-pod memory limit; pods can drift out of sync until L1 TTL expires or pub/sub invalidates.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Two-Tier L1+L2 Cache with CDC Invalidation.

High-QPS read platforms pair a tiny L1 in-process cache (10–30s TTL) for ultra-hot keys with Redis Cluster (L2) and CDC/Debezium invalidation—so DB commits asynchronously purge stale Redis keys and broadcast L1 evictions via Redis Pub/Sub.

CDC-Driven Freshness

Postgres Commit -> Debezium CDC -> Redis DEL + L1 Pub/Sub Purge

1.No App Dual-Write: Application code only writes to Postgres; CDC handles cache invalidation reliably.

2.Versioned Refill: Attach monotonic DB version/xmin so stale async refills never overwrite newer data.

3.Graceful Cold Start: Singleflight + DB concurrency bulkhead keep Postgres safe if L2 is empty.

CDC-driven invalidation eliminates dual-write races between the database and multi-tier caches.
