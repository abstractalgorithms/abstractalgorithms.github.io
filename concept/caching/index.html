In-Memory Caching
Architecture.

Caching keeps a reusable copy of data so an application can avoid repeating a database query, calculation, or network call. It can make responses faster and reduce database load. The trade-off: the copy may be out of date.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Keep a clear source of truth. Decide how stale a cached value may be, how to refresh it, and what happens when the cache is empty or unavailable.

Explanation anchor
01 / The idea

Do the work once. Reuse the result.

Many requests ask for the same information. Reusing a cached result leaves the database more capacity for other work. A 10x traffic surge without a robust caching layer causes database saturation. The benefit depends on how often requests reuse data and how much work a hit avoids.

  • Cache hit: the requested value is found and can be reused.
  • Cache miss: the application fetches or computes the value.
  • TTL (time to live): how long an entry may remain before it expires. It can still become stale before expiry.
  • Invalidation: removing a cached copy when its source changes.
  • Eviction: removing entries to stay within a memory limit, sometimes before their TTL expires.

Good candidates

  • Frequently read product descriptions or reference data.
  • Expensive reports that can tolerate a short delay in freshness.
  • Public content and static assets served through a CDN.

Think twice

  • Values that change so often that cached copies are rarely reused.
  • Correctness-critical decisions based only on potentially stale balances, prices, or stock counts.
  • Already-cheap queries where caching adds little measurable benefit.

02 / Concrete walkthrough

A request, step by step

This cache-aside example uses Redis for a reusable copy and PostgreSQL as the source of truth. The application queries the database and fills the cache; Redis does not query PostgreSQL itself.

GET /products/42 checks Redis for product:42. On a miss, the application reads PostgreSQL and caches the description for about five minutes.

GET /products/42 · GET /products/42 checks Redis for product:42. On a miss, the application reads PostgreSQL and caches the description for about five minutes.

A hit avoids the source lookup. A miss still costs a source lookup plus cache work. Actual savings depend on your workload.

03 / Speed versus freshness

Keeping data fresh

After a product edit, commit the database update, then delete product:42 from Redis. The next miss loads a fresh copy.

This is not atomic across both systems. Invalidation can fail. A reader can also fetch an old value before the update and refill it after invalidation. Short TTLs limit exposure but do not eliminate that race. Stronger freshness needs a coordinated, version-aware protocol.

For a correctness-critical transaction, validate the decision in the authoritative system rather than relying only on a stale cached value.

04 / Data movement, not a consistency guarantee

Data movement is not a consistency guarantee

PatternHow it worksMain limitation
Cache-asideApplication loads missing data and fills the cache.Misses are slower; invalidation and refill can race.
Write-throughA caching layer synchronously persists writes to the database.Adds write latency; partial failures and concurrency still need coordination.
Write-behindWrites are persisted to the database later.Unpersisted acknowledged updates can be lost without durable recovery.
Refresh-aheadRefresh hot entries before expiry.Adds background work and does not guarantee fresh data.

Local vs shared cache

Advantage: A local cache avoids network calls.

Drawback: Each application instance has its own copy. A shared cache reduces duplication but adds a network dependency.

TTL vs invalidation

Advantage: TTL is simple; invalidation can remove outdated data sooner.

Drawback: Expiry permits stale reads, and invalidation can fail or race with a concurrent refill. Neither alone guarantees instant freshness.

Memory capacity vs cost

Advantage: More capacity can retain a larger reusable working set.

Drawback: Extra memory costs money and may not help when requests rarely reuse data. Cold starts still need controlled refilling.

05 / Failure modes

Protect the database on a bad day.

Many keys expire together

A burst of misses sends extra traffic to the database. This is called a cache avalanche.

What helps: Add random TTL jitter and stagger refilling. Limit database concurrency as a safety net.

One popular key expires

Many requests try to rebuild the same value at once. This is a cache stampede, also called hot-key breakdown.

What helps: Coalesce refreshes so one worker loads the value. Other requests wait for a bounded time or use an explicitly allowed stale copy.

Requests target missing records

Repeated requests for nonexistent IDs keep reaching the database. This is cache penetration.

What helps: Validate inputs, briefly cache not-found results, and rate-limit abuse. A Bloom filter is safe to reject records only when it accurately represents the current dataset.

The cache is unavailable

Unrestricted fallback can overwhelm the database.

What helps: Use short cache timeouts, bounded fallback, circuit breakers, and load shedding. Sometimes an error is safer than another database query.

An old value refills the cache

A reader fetches an old database value, a writer updates the database and invalidates the key, then the reader caches the old value.

What helps: Use a coordinated, version-aware protocol when stronger freshness is needed. Short TTLs reduce exposure but do not eliminate this race.

Expiry without a traffic spike

Use TTL = base TTL + random offset. With a base of 300 seconds and an offset between -30 and +30 seconds, entries expire after 270–330 seconds. An offset of +14 gives 314 seconds.

Jitter spreads expiry across different keys. It does not protect a single hot key; use refresh coalescing for that.

If refresh coordination uses a distributed lock, use an expiring lease, a unique owner token, and atomic owner-checked release. Bound waiting and retries, and handle work that outlasts the lease.

06 / Practical checklist

Start small and measure

Begin with one cache layer. Set a memory budget and eviction policy. Bound client connections, timeouts, and database fallback.

Measure hit rate alongside end-to-end latency, cache errors, evictions, refresh duration, and database load. Add local caches or CDN layers only when the workload justifies their extra invalidation rules and failure modes.

Avoid these mistakes

  • Treating an expendable cache as durable storage.
  • Leaving memory limits, connections, timeouts, or retries unbounded.
  • Omitting tenant, user, locale, or other response-changing inputs from cache keys.
  • Assuming write-through automatically provides strong consistency.
  • Measuring only hit rate instead of response latency, cache errors, evictions, and database load.
