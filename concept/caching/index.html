In-Memory Caching & Event Loop Architecture

Eliminate DB latency bottlenecks using single-threaded event loops, Epoll I/O multiplexing, and LRU/LFU memory eviction.

Orientation & Intuition

Caching is the architectural technique of retaining copies of frequently accessed, computationally expensive data in high-speed, volatile memory (e.g. Redis, Memcached, CPU caches) to bypass slow disk I/O, database table scans, and network hops. Proper caching slashes latency from tens of milliseconds to sub-milliseconds and shields databases from query saturation.

Key takeaway Treat caches as transient performance accelerators, never as authoritative databases: design for cache misses, choose explicit invalidation patterns (Cache-Aside vs Write-Through), tune eviction policies (LRU vs TinyLFU), and implement mutexes to prevent thundering herds.

Core Architecture & Trade-offs

Disks and relational database queries are inherently bounded by I/O bottlenecks and connection pool limits. A 10x traffic surge without a robust caching layer causes database CPU saturation, connection starvation, and complete application collapse.

Key Architecture Invariants

  • Cache-Aside (Lazy Loading): Application reads from cache; on miss, reads from DB and writes to cache. Simple and resilient to cache failure, but vulnerable to stale data until TTL expires.
  • Write-Through: Application writes to cache, which synchronously updates the database. Ensures data is always fresh, but incurs higher write latency.
  • Write-Behind (Write-Back): Application writes to cache; cache asynchronously writes to DB in batches. Extreme write throughput, but risks data loss on cache node crash.
  • Eviction Algorithms: LRU (Least Recently Used), LFU (Least Frequently Used), and W-TinyLFU (Frequency-weighted admission filter).
  • Cache Stampede & Thundering Herd: When an expired key is simultaneously requested by thousands of clients, all rush to query the database concurrently.

When to Use

  • Read-heavy workloads with high read-to-write ratios ($10:1$ or higher).
  • Serving computationally expensive aggregated responses (e.g. user newsfeeds, analytics dashboards).
  • Storing user session tokens, permissions, and transient shopping cart state.
  • Edge content distribution of static media assets via CDNs.

When NOT to Use

  • Write-heavy workloads where data changes continuously on every request (cache churn yields 0% hit rates).
  • Financial balance ledgers or inventory stock checks requiring strict ACID linearizability where serving 100ms-stale data causes financial loss.
  • Small datasets that already fit completely within database buffer pool RAM.

Deep Dive & Production Considerations

📖 Operational Architecture of High-Performance Caching

Caching exploits the Principle of Locality: applications tend to access data that was recently accessed (Temporal Locality) or data that is physically adjacent (Spatial Locality). In distributed backend architectures, caching layers sit between application services and durable persistence datastores.

2. Cache Stampede Mitigation: Mutex Locking (SETNX)

text 
function getWithMutex(key, ttl):
    value = redis.get(key)
    if value == null:
        if redis.setnx("lock:" + key, "1", 5_seconds) == 1:
            value = db.query(key)
            redis.set(key, value, ttl)
            redis.del("lock:" + key)
        else:
            sleep(50_ms)
            return getWithMutex(key, ttl)
    return value

3. Cache Penetration Mitigation: Bloom Filters

Deploy an in-memory Bloom filter in front of the cache. If the filter returns false, the key is mathematically guaranteed not to exist: reject immediately without querying cache or database.
