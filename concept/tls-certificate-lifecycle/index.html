THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Automate issuance and rotation at 2/3 lifetime (e.g., day 60 of a 90-day cert) using ACME or SPIFFE/cert-manager, and reload proxies without restart—manual calendar reminders inevitably cause outages.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

An expired or mischained TLS certificate instantly breaks every HTTPS client, mobile app, and microservice mTLS call with zero graceful degradation. As public CAs move from 398-day maximum lifetimes toward 90-day and 47-day industry mandates (Apple/Google CA/B Forum proposals) and service meshes rotate mTLS SVIDs every 1–24 hours, manual CSR generation and NGINX restarts are operationally impossible.

  • A leaf X.509v3 certificate binds a public key (ECDSA P-256 or RSA-2048) to Subject Alternative Names (SANs) and notBefore/notAfter timestamps, signed by an Intermediate CA.
  • ACME (RFC 8555) automates issuance via HTTP-01 (port 80 /.well-known/acme-challenge/), DNS-01 (TXT record _acme-challenge—required for wildcard *.example.com certs), or TLS-ALPN-01.
  • Always renew at ~2/3 of certificate lifetime (e.g., 30 days remaining on a 90-day cert) so a failed ACME challenge leaves a 30-day buffer for alerting and retries.
  • Certificate Revocation Lists (CRLs) and OCSP often fail-open in browsers due to latency/privacy; short-lived certs (hours to 47 days) and OCSP stapling (RFC 6066) are far more reliable.
  • Zero-downtime rotation requires hot-reloading certificates in memory (Envoy SDS, NGINX nginx -s reload, Go GetCertificate callback) without severing active HTTP/2 or WebSocket streams.

Good candidates

  • Securing public ingress endpoints (API gateways, CDNs, load balancers) with automated Domain Validated (DV) certificates via ACME (RFC 8555) and Let's Encrypt or ZeroSSL.
  • Enforcing zero-trust mutual TLS (mTLS) between Kubernetes microservices using short-lived X.509 SPIFFE Verifiable Identity Documents (SVIDs) rotated hourly by SPIRE or Istio.
  • Responding to a private key compromise or CA incident by revoking compromised certs and forcing immediate emergency rotation across edge proxies.

Think twice

  • Hardcoding long-lived (5–10 year) static certificates inside mobile binaries or IoT firmware for certificate pinning—if a CA rotates or a key leaks, devices brick until an app/firmware update.
  • Terminating TLS inside a single pod when an L7 ingress (Envoy/ALB) already handles public TLS and an internal mesh (Cilium/Istio) manages pod-to-pod mTLS, unless end-to-end app-level encryption is legally required.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA SaaS platform hosts 400 customer subdomains under *.app.acme.io behind an AWS NLB + Envoy/NGINX Ingress and needs automated TLS without opening port 80.

The idea

A TLS certificate (X.509v3) is a time-bounded cryptographic attestation signed by a trusted Certificate Authority (CA) binding a domain or workload identity (SAN) to a public key. Because private keys can leak and algorithms age, every certificate has an expiry.

Managing TLS at scale means treating certificates as ephemeral, automated state machines rather than static config files: generate a fresh key pair locally (the private key never leaves the host/cluster), prove control over the identity (ACME or SPIFFE), install the signed chain, hot-reload the listener, and trigger the next renewal at 2/3 of the certificate's lifetime.

Concrete walkthrough

Trace an automated 90-day public TLS renewal using cert-manager and Let's Encrypt (ACME RFC 8555) with DNS-01:

  1. Trigger (Day 60): cert-manager inspects tls.crt (notAfter - notBefore = 90d) and sees <= 30d remaining (renewBefore: 720h). It generates a fresh ECDSA P-256 private key in memory.
  2. Order & Challenge: cert-manager submits an ACME Order for *.api.example.com to acme-v02.api.letsencrypt.org and receives a DNS-01 token.
  3. Proof of Control: It computes base64url(sha256(token + "." + accountKeyThumbprint)) and writes a TXT record _acme-challenge.api.example.com via Route53 API, polling authoritative DNS until propagated.
  4. Issuance & CT Logging: Let's Encrypt validates the TXT record from multiple vantage points, appends the cert to public Certificate Transparency (CT) logs (RFC 6962), and returns fullchain.pem (Leaf + Intermediate R10/E5).
  5. Zero-Downtime Swap: cert-manager atomically updates the Kubernetes Secret; Envoy (via SDS) swaps the TLS context in memory within ~1 second while existing TCP/HTTP2 streams finish cleanly.

Automated renewal replaces manual CSRs and restarts with an ACME state machine and in-memory proxy hot-reload.

Revocation, OCSP Stapling & Short-Lived Certs

When a private key leaks, CAs publish a CRL (Certificate Revocation List) or serve OCSP (Online Certificate Status Protocol) responses. In practice, live OCSP lookups from clients add 50–200 ms to handshakes, leak browsing metadata to the CA, and fail-open when the CA's OCSP responder hiccups.

Two patterns solve this:

  • OCSP Stapling (RFC 6066): The server (NGINX/Envoy) periodically fetches the CA-signed OCSP response and staples it directly into the TLS Certificate handshake message—zero extra client round-trips.
  • Short-Lived Certificates: Let's Encrypt ended OCSP support in favor of CRLs + short lifetimes (moving toward 6-day optional / 47-day max certs), and internal meshes like SPIFFE/Vault PKI issue 1–24 hour certs so compromised credentials expire before a CRL even propagates.

Failure modes

  1. Split-Brain Renewal in Multi-Instance Fleets: Five stateless instances behind a load balancer all run HTTP-01 locally; the CA's validation request hits Instance B while Instance A holds the challenge token, causing random 403 failures. Centralize issuance in a single controller (cert-manager) or use DNS-01.
  2. CAA Record Blocking: A domain's DNS CAA record permits only digicert.com, causing Let's Encrypt renewals to fail silently until expiry.
  3. Root Store Expiry: Older IoT devices or unpatched Docker base images (alpine:3.12) lack newer Root CAs (e.g., ISRG Root X2), rejecting valid modern chains.

Observability & Emergency Rotation

Monitor the served certificate on the wire, not just the file on disk:

  • Blackbox Exporter (probe_ssl_earliest_cert_expiry): Probe every public and internal VIP every 60s. Page at < 14 days (catches 60-day renewal failures with 2 weeks to spare) and critical-page at < 5 days.
  • Chain & Protocol Audits: Verify fullchain.pem completeness, TLS 1.2/1.3 cipher suites, and CAA records on every deploy.
  • Emergency Rotation Drill: Practice revoking and force-renewing a staging cert twice a year so you know how long DNS TTLs and CDN edge propagation actually take.

Practical checklist

  • Automate issuance and renewal at 2/3 lifetime via ACME (cert-manager, caddy, certbot) or SPIRE.
  • Serve leaf + intermediate (fullchain.pem), never leaf-only and never include the Root CA.
  • Verify listeners hot-reload certs without dropping active TCP/HTTP2 connections.
  • Configure Blackbox TLS probing on live endpoints (alert at < 21d warning, < 7d page).
  • Add CAA DNS records explicitly authorizing your chosen CA(s).
  • Never hardcode leaf cert pins in mobile/IoT clients; use short-lived certs and automated CT monitoring.
03 / Engineering trade-offs

Weighing architectural decisions

HTTP-01 vs. DNS-01 ACME Challenge

Advantage: `HTTP-01` requires zero DNS API credentials and works immediately for single-domain public endpoints.

Drawback: `HTTP-01` cannot issue wildcard (`*.domain.com`) certs and fails for internal/firewalled services; `DNS-01` handles both but requires scoped DNS write permissions.

ECDSA P-256 vs. RSA-2048 Keys

Advantage: ECDSA P-256 keys are ~10x smaller (256-bit vs 2048-bit), cut TLS 1.3 handshake CPU by ~3–5x, and reduce certificate chain bytes on mobile.

Drawback: Legacy clients (pre-2014 Java 7/Android 4, old embedded scanners) may lack ECDSA cipher support, requiring dual-cert RSA fallback.

Short-Lived Certs (1h–7d) vs. Long-Lived + CRL/OCSP

Advantage: Short-lived certs eliminate revocation infrastructure complexity because compromised keys age out automatically.

Drawback: Tightens dependency on the local CA/ACME control plane—if the CA is down longer than the TTL, the entire fleet expires simultaneously.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Missing Intermediate CA in `fullchain.pem`

Server serves only the leaf certificate instead of `leaf + intermediate`. Desktop browsers (which cache intermediates) pass, while `curl`, Go, and Java clients fail with `unable to verify the first certificate`.

What helps: Always bundle leaf + intermediate(s) in `fullchain.pem` (never include the Root CA) and validate chains in CI with `openssl s_client -verify_return_error`.

Let's Encrypt Rate Limit Exhaustion

A broken Kubernetes loop repeatedly deletes and recreates `Secret` objects, hitting Let's Encrypt's 50 certs/week per registered domain or 5 duplicate certs/week limit and blocking valid renewals.

What helps: Test all automation against Let's Encrypt's Staging CA first, persist ACME account keys and issued secrets, and alert on `certmanager_certificate_ready_status == 0`.

Clock Skew Triggering Premature Expiry / NotYetValid

A VM or container with NTP drift 10 minutes behind CA time rejects a freshly minted mTLS cert because `now < notBefore`.

What helps: Enforce `chrony`/NTP sync across all nodes and configure internal CAs to backdate `notBefore` by 2–5 minutes.

Silent Hot-Reload Failure

cert-manager renews the `tls.crt` file on disk, but the Java or Go microservice loaded the `KeyStore` once at startup and serves the expired cert 30 days later.

What helps: Terminate TLS at Envoy/NGINX with SDS or `fsnotify` reloaders, or use Go's `tls.Config.GetCertificate` / Spring Boot SSL bundles with `reload-on-update: true`.

05 / Practical checklist

Avoid these mistakes

  • Monitoring certificate expiry with a calendar invite instead of Prometheus `probe_ssl_earliest_cert_expiry` alerts at 21 days and 7 days.
  • Renewing at 95% lifetime (e.g., day 85 of 90) instead of 66% (day 60), leaving too little time to recover from a DNS or CA outage.
  • Including the Root CA inside the server's TLS certificate chain, wasting ~1.5 KB per TLS 1.3 handshake.
  • Pinning leaf public keys in mobile apps instead of pinning the Root/Backup CA or relying on Certificate Transparency.
  • Storing private keys in Git or unencrypted S3 buckets instead of KMS, Vault PKI, or Kubernetes Secrets encrypted at rest.
