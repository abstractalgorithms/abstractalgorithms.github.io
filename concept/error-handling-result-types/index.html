Error Handling with
Result Types.

Result types represent the outcome of a fallible operation as an explicit discriminated union (Ok(T) | Err(E)) in the function's return signature rather than throwing out-of-band exceptions.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

By forcing callers to unwrap or propagate errors at compile time, Result types turn hidden control-flow jumps into type-checked data pipelines with zero stack-unwinding overhead.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Unchecked exceptions create invisible exit paths in functions: a caller cannot tell from a signature like chargeCard(orderId): Receipt whether the function can fail on network timeouts, insufficient funds, or invalid currency. In high-throughput services (e.g., 50k+ RPS payment gateways or parsers), throwing and capturing stack traces costs 1–10 microseconds per exception and breaks linear composition. Result types make failure modes part of the API contract, enabling exhaustive pattern matching, railway-oriented chaining (map, andThen), and predictable latency.

  • Explicit signatures: Result documents both the happy path and the finite set of domain errors in the type system.
  • Exhaustive handling: sealed interfaces (Java 21+), Rust enum, or TypeScript discriminated unions force callers to handle every error variant or explicitly propagate it.
  • Monadic composition: map transforms Ok values without touching Err, while flatMap (andThen) short-circuits a chain of fallible steps on the first Err.
  • Zero-cost error paths: returning an Err struct allocates a small value on the stack or heap without walking and symbolizing 40+ stack frames.
  • Boundary translation: convert low-level exceptions (JDBC SQLException, IOException) into typed domain Result variants at repository or client boundaries.

Good candidates

  • Expected domain and I/O failures such as validation errors, HTTP 4xx/5xx responses, rate limits, or record-not-found lookups where the caller must decide how to recover.
  • Performance-critical hot paths (parsers, codecs, network proxies, trading engines) where JVM/CLR stack-trace allocation on error paths causes tail-latency spikes.
  • Functional and concurrent pipelines (Java CompletableFuture/sealed interfaces, Rust Result<T, E>, TypeScript neverthrow) where errors must travel cleanly across async boundaries or thread pools.

Think twice

  • Truly unrecoverable programmer bugs or invariant violations (null-pointer dereference, out-of-bounds array index, OOM, corrupted heap) that should panic or crash fast.
  • Deeply nested UI or scripting glue where every intermediate call only logs and aborts, and the host language lacks ? or flatMap ergonomics—causing verbose boilerplate.
  • Legacy frameworks (Spring MVC @ControllerAdvice, JAX-RS mappers) whose entire middleware stack already relies on typed exception interception unless you wrap at the boundary.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA checkout service validates a cart, reserves inventory in Redis, and captures funds via an external PSP. Previously, PaymentException was caught three layers up, masking whether a failure was retryable (HTTP 503) or terminal (card declined).

The idea

Exceptions implement non-local goto: when a function throws, the runtime suspends normal execution, unwinds stack frames until it finds a matching catch block, and allocates a stack trace along the way. Because throws clauses are often unchecked (Python, TypeScript, Go panic, Java RuntimeException), callers have no compile-time guarantee that they handled failure modes.

Result types invert this model by treating failure as ordinary data. A function that can fail returns a tagged union Result with exactly two mutually exclusive states: Ok(T) holding the success payload, or Err(E) holding a typed error value. Because Result is not T, the compiler refuses to let you read the T without first inspecting the tag—either via pattern matching, map/flatMap combinators, or early-return propagation.

Concrete walkthrough

Consider an order-fulfillment step reserveAndCharge(OrderRequest req) that must: (1) validate SKU quantities, (2) reserve stock in Redis via a Lua script, and (3) charge the customer's card via Stripe. Using railway-oriented programming, each step returns Result:

  1. validate(req) returns Ok(ValidatedOrder) or short-circuits with Err(InvalidQuantity(sku)).
  2. reserveStock(order) runs only if step 1 returned Ok. If Redis reports insufficient inventory, it returns Err(OutOfStock(sku, available=0))—skipping the Stripe call entirely.
  3. chargeCard(reservation) runs only if step 2 returned Ok. If Stripe returns HTTP 402, it returns Err(CardDeclined(reason)), and a compensating onErr hook releases the Redis reservation.
  4. At the HTTP controller boundary, a single exhaustive switch maps Ok(receipt) -> HTTP 200, InvalidQuantity -> HTTP 400, OutOfStock -> HTTP 409, and CardDeclined -> HTTP 402.

Railway-oriented execution: Ok values advance down the happy track while any Err immediately bypasses downstream steps and routes to compensation or boundary mapping.

Language mechanics and ergonomics

How cleanly Result types work depends heavily on language support for algebraic data types (ADTs) and propagation syntax:

  • Rust (std::result::Result): Built into the standard library with #[must_use]. The ? operator unwraps Ok(v) or returns Err(From::from(e)) in a single character, giving exception-like brevity with compile-time checking.
  • Java 21+ (Sealed Interfaces + Pattern Matching): While java.util lacks a built-in Result, a 15-line sealed interface Result permits Ok, Err combined with switch (res) { case Ok(var v) -> ...; case Err(var e) -> ...; } gives full exhaustiveness checking without third-party dependencies (or use Vavr Either/Try).
  • Python 3.10+ (returns library or @dataclass unions): Typing Result = Ok[T] | Err[E] with match res: (PEP 634) enables static checking via mypy --strict or pyright, though runtime overhead remains higher than native Rust enums.

Failure modes

  • Silent Discarding: If the language does not warn on unused return values, calling sendEmail() and ignoring its Result silently drops failures. Enforce @CheckReturnValue (Java ErrorProne) or #[must_use] (Rust).
  • Error-Type Explosion: Defining a single giant AppError enum with 80 variants forces unrelated modules to depend on every error in the system. Instead, scope error unions per module (AuthError, BillingError) and compose at boundaries.
  • Async Wrapper Friction: Nesting CompletableFuture> or Promise> creates awkward double-wrapping (thenCompose + flatMap). Use a dedicated AsyncResult helper or structured concurrency.

Boundary design: Exceptions vs. Results

Production systems rarely use Result types for 100% of code; they draw a crisp boundary between panics/exceptions (bugs) and Results (expected operational failures):

  1. Inner Core (Domain & Adapters): Wrap third-party SDKs (JDBC, AWS SDK, HTTP clients) in thin adapters that catch IOException, TimeoutException, or SQLException and translate them into Result.
  2. Panic/Defect Boundary: Let NullPointerException, IllegalStateException (broken internal invariant), or OutOfMemoryError bubble up to a top-level supervisor or HTTP 500 handler that logs the full stack trace and alerts on-call.
  3. Observability: Emit a structured counter metric operation_result_total{op="capture", status="err", code="card_declined"} inside your Result constructor or boundary mapper so every error variant is automatically graphed.

Practical checklist

  • Define a closed sealed interface or enum for every module's error type E—never use String or raw Exception.
  • Enable compiler/linter enforcement (#[must_use], @CheckReturnValue, mypy --strict) so Result values cannot be silently ignored.
  • Ban .unwrap() / .get() in production paths outside unit tests and startup config parsing.
  • Convert external SDK exceptions into typed Result variants at the outermost adapter layer.
  • Attach correlation IDs and contextual operation names when wrapping lower-level Err values upward.
  • Keep unrecoverable programmer bugs (invariant violations, OOM) on the panic/exception path with full stack traces.
03 / Engineering trade-offs

Weighing architectural decisions

Ergonomics vs. Explicitness

Advantage: Every possible failure is visible at the call site, preventing silent swallowed errors or surprise runtime crashes.

Drawback: In languages without `?` propagation syntax (like Java or Go without generics sugar), chaining 5+ fallible calls requires verbose `flatMap` lambdas or repetitive `if (res.isErr())` checks.

Latency & Allocation Profile

Advantage: Avoids `Throwable.fillInStackTrace()`, making error paths 10x–100x faster under high error rates (e.g., bot traffic or malformed input bursts).

Drawback: Every happy-path return wraps the value in a `Result` container (unless stack-allocated or value-typed), adding a minor wrapper allocation in GC languages.

Debugging Context

Advantage: Structured error enums carry domain fields (`retryAfterMs`, `fieldName`, `upstreamCode`) that serialize cleanly to JSON logs and metrics.

Drawback: Lacks an automatic call-stack trace by default; engineers must attach explicit context frames (`wrapErr("loading user 42")`) or correlation IDs when propagating across layers.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Result-Wrapping Without Context (Context Loss)

Propagating a bare `Err(NotFound)` up six service layers makes logs useless because you cannot tell whether the missing record was a User, Merchant, or PromoCode.

What helps: Attach contextual error wrappers at layer boundaries (`mapErr(e -> new OrderLoadError(orderId, e))`) and include a structured `traceId`.

Panic via Unchecked `.unwrap()` in Production

Developers bypass the type safety of `Result` by calling `.unwrap()` or `.get()` on happy-path assumptions, turning recoverable errors into process crashes.

What helps: Ban `.unwrap()` in production code via linter rules (Clippy `unwrap_used`, ArchUnit/ErrorProne) and allow only `.unwrapOr()`, `.match()`, or explicit propagation.

Stringly-Typed `Result<T, String>`

Using `String` as the error type `E` forces callers to parse English error messages with regexes to decide between retrying and failing fast.

What helps: Restrict `E` to a closed `enum` or `sealed interface` where each variant encodes machine-actionable metadata.

Leaky Infrastructure Errors in Domain Signatures

Returning `Result<Order, SQLException>` from a business service couples callers to PostgreSQL internals and breaks abstraction boundaries.

What helps: Map `SQLException` SQLState codes (e.g., `23505` unique violation) into domain errors (`DuplicateOrder`, `StorageUnavailable`) inside the repository adapter.

05 / Practical checklist

Avoid these mistakes

  • Mixing exceptions and Result types in the same method so callers must catch `Throwable` AND unwrap a `Result`.
  • Using `Result<Void, Error>` for operations that cannot fail instead of returning `void` or `Unit`.
  • Dropping the original cause when mapping `Err(lowLevel)` to `Err(highLevel)`, breaking root-cause diagnostics.
  • Ignoring returned `Result` values on side-effecting calls like `auditLog.write()`—always enforce `@CheckReturnValue` or `#[must_use]`.
  • Putting stack traces inside every `Err` object by default, which reintroduces the exact allocation overhead Result types were meant to avoid.
