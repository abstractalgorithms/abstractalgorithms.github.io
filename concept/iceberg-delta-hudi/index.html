Lakehouse Table Formats
(Iceberg, Delta, Hudi).

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are Open Lakehouse Table Formats.

Why this matters: The mechanism: understand how Open Lakehouse Table Formats works from first principles.

Cloud object stores (S3, GCS, ADLS) lack atomic multi-file commits, and Hive-style directory listings (s3://bucket/dt=2026-11-18/) stall on millions of partitions. Open table formats (Apache Iceberg, Delta Lake, Apache Hudi) place a versioned ACID metadata/transaction log over immutable Parquet files.

Instead of listing S3 directories, readers consult the latest atomic snapshot pointer (metadata.json -> manifest list -> manifest files in Iceberg, or _delta_log/*.json in Delta) to get snapshot isolation, time travel, GDPR MERGE INTO / DELETE, and schema evolution.

Iceberg Metadata Tree

Catalog Pointer -> Snapshot -> Manifest List -> Parquet Data Files

1.Zero Directory LIST: Query engines prune partitions and data files using manifest min/max stats before reading S3.

2.Snapshot Isolation: Readers see a consistent point-in-time snapshot even while concurrent writers commit.

3.Partition Evolution: Iceberg evolves daily -> hourly partitioning in metadata without rewriting historical Parquet.

A hierarchical metadata tree turns eventually-consistent object storage into an ACID multi-engine database.

Problem
How to implement Lakehouse Table Formats (Iceberg, Delta, Hudi) without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
To keep storage layouts predictable as data grows, delta, Hudi), never write raw Hive-style Parquet directories for mutable production tables—use Iceberg, Delta, or Hudi for atomic commits, snapshot isolation, and partition evolution.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

In production, Flink or Spark Structured Streaming commits Bronze/Silver micro-batches every 1–5 minutes, while an asynchronous maintenance job compacts small files into 256 MB Parquet blocks and expires snapshots older than 7 days.

ACID Commit & Compaction

Concurrent Writers -> Optimistic Catalog CAS -> Async Compaction

1.Optimistic Concurrency: Two writers touching disjoint partitions both commit via catalog CAS retry.

2.Copy-on-Write vs MoR: CoW optimizes pure read speed; MoR + Deletion Vectors absorb frequent CDC updates.

3.Safe Vacuum: Retain >=24–72h of snapshots so long-running Trino/Spark jobs never hit FileNotFoundException.

Optimistic catalog commits decouple streaming writers from readers while background compaction keeps scan performance fast.
