What are State, Strategy, and Observer.

Why this matters: The mechanism: understand how State, Strategy, and Observer works from first principles.

Although State and Strategy share nearly identical UML class diagrams, their intent is distinct:

  • State: Context delegates to a State object representing its current lifecycle phase; transitions happen inside states as actions occur.
  • Strategy: Context delegates an algorithm (e.g., pricing, routing) to an injected Strategy interface that can be swapped without changing lifecycle.

Vending Machine State Transitions

Each concrete State class handles valid actions for that phase and rejects invalid ones (e.g., dispense() while IDLE).

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why hardcoded switch/if-else chains fail the Open/Closed Principle.

Why this matters: The problem: see what breaks without Why hardcoded switch/if-else chains fail the Open/Closed Principle under real concurrency or scale.

In both LLD interviews and production codebases, requirements evolve: 'add weekend flat-rate pricing', 'add a Maintenance state', or 'notify an audit webhook on dispense'.

When all transitions and algorithms live in one giant switch(status) block, every new feature modifies tested core logic and risks breaking unrelated branches. Behavioral patterns isolate each new state, algorithm, or listener into its own cohesive class.

Clean Java interfaces for State, Strategy & Observer.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Think of Clean Java interfaces for State, Strategy & Observer as the intuition layer for Core LLD Behavioral Patterns: State, Strategy & Observer in Practice: Operational control: configure bounds, failure handling, and safe production defaults.

Keep State implementations stateless (no per-machine mutable fields if shared as singletons) and store listeners in CopyOnWriteArrayList for safe concurrent iteration.

public interface PricingStrategy {
    long calculateCents(Ticket ticket);
}

public interface SpotState {
    void occupy(ParkingSpot spot, Vehicle v);
    void vacate(ParkingSpot spot);
}

public final class ParkingLotSubject {
    private final java.util.List<AvailabilityObserver> observers =
        new java.util.concurrent.CopyOnWriteArrayList<>();

    public void subscribe(AvailabilityObserver obs) { observers.add(obs); }
    public void unsubscribe(AvailabilityObserver obs) { observers.remove(obs); }
    public void notifyChange(FloorEvent evt) {
        for (var obs : observers) obs.onAvailabilityChanged(evt);
    }
}

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Avoiding Singleton State Corruption & Observer Leaks.

Why this matters: Production architecture: see how the components compose end to end under real load.

Think of Avoiding Singleton State Corruption & Observer Leaks as the intuition layer for Core LLD Behavioral Patterns: State, Strategy & Observer in Practice: Production architecture: see how the components compose end to end under real load.

Two production pitfalls trip up teams using behavioral patterns: storing instance-specific fields inside shared singleton State objects (causing cross-request race conditions), and registering short-lived UI/request observers without unsubscribe() (leaking memory).

Design Trade-Off

Avoiding Singleton State Corruption & Observer Leaks

Before · Unbounded Coupling
  • No backpressure on spikes
  • Implicit shared state
  • Cascading tail latency
After · Bounded & Observable
  • Explicit capacity budgets
  • Isolated failure domains
  • Predictable p99 latency

Stateless Transitions

Pass the Context (ParkingSpot, VendingMachine) into every State method and mutate fields only on the Context.

Weak/Explicit Unsubscribe

Always pair subscribe() with deterministic unsubscribe() or AutoCloseable handles.
