Stream Watermarks &
Late Data.

Watermarks track event-time progress in unbounded streams, telling stateful operators when a time window is complete enough to emit results—while allowed lateness and side outputs handle straggling events.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

In Apache Flink or Spark Structured Streaming, set watermarks to max_observed_event_time - bounded_out_of_orderness, pair them with allowedLateness for corrections, and route beyond-lateness events to a side output rather than silently dropping them.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Mobile apps, IoT sensors, and multi-region Kafka topics deliver events out of order; without event-time watermarks, tumbling windows either emit wrong counts prematurely or hold state in memory forever until OOM.

  • Event time (when the action happened) differs from processing time (when the Flink/Spark worker sees the record); watermarks bridge the two.
  • A watermark W(t) is a monotonic assertion that no more events with timestamp <= t are expected; when W(t) passes window_end, the window fires.
  • Bounded-out-of-orderness watermarks (maxEventTime - delta) trade latency for completeness: larger delta catches more late events but delays window emission and increases state size.
  • An idle Kafka partition stops advancing its local watermark and stalls the global min-watermark across all parallel subtasks unless withIdleness() is configured.
  • Events arriving after W(t) passes window_end + allowedLateness are dropped from state—route them to a Dead Letter / side output for batch reconciliation.

Good candidates

  • Event-time aggregations (tumbling, sliding, or session windows) in Apache Flink, Apache Beam, or Spark Structured Streaming.
  • Out-of-order streams from mobile clients offline-buffering events, multi-AZ producers, or cross-region replication.
  • Billing, fraud detection, or SLA alerting where results depend on when an event occurred rather than when the server ingested it.

Think twice

  • Simple stateless per-event transformations (filtering, JSON enrichment, regex masking) that require no windowing.
  • Strict processing-time monitoring where wall-clock ingestion rate is the actual metric (e.g., raw Kafka consumer lag).
  • Batch-only workloads over bounded, already-complete daily Parquet files.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA ride-hailing app buffers GPS pings during tunnel drops; 99% arrive within 15 seconds, while 0.8% arrive up to 2 minutes late.

The idea

In distributed streaming, network jitter and offline buffering scramble event arrival order. A watermark W(t) is a special timestamped marker injected into the data stream asserting that no further events with event_time <= t are expected. It decouples correctness (event time) from infrastructure speed (processing time), giving stateful operators a deterministic signal to fire windows and garbage-collect old state.

Concrete walkthrough

Suppose we aggregate 1-minute tumbling windows ([12:00, 12:01)) with a 10-second out-of-orderness bound (delta = 10s) and allowedLateness = 30s:

  1. Events with timestamps 12:00:15, 12:00:48, and 12:01:05 arrive. maxEventTime becomes 12:01:05, so W = 12:00:55 (window [12:00, 12:01) stays open).
  2. Event 12:01:12 arrives -> W = 12:01:02. Because W >= 12:01:00, the [12:00, 12:01) window fires its initial aggregate.
  3. Window state is retained until W reaches 12:01:30 (window_end + allowedLateness).
  4. A late event 12:00:52 arrives while W = 12:01:15: it enters the retained window and triggers an updated emission.
  5. Once W >= 12:01:30, the window state is purged; any subsequent 12:00:xx event is routed to the side output.

Watermarks advance window triggers monotonically while allowed lateness and side outputs prevent silent data loss on straggling records.

Multi-partition and join alignment

Every parallel operator subtask tracks one watermark per input channel and sets its own watermark to the minimum across all active channels. This guarantees that a fast partition cannot prematurely close a window before a slower partition catches up. However, if a single partition goes silent, withIdleness() must mark it temporarily inactive so the minimum can advance. Similarly, in stream-stream interval joins, both sides buffer records in RocksDB until the combined minimum watermark passes the join upper bound.

Failure modes

Two silent killers dominate production streaming: clock-skew poisoning (a single future-dated event jumps W(t) ahead by days, dropping all subsequent traffic as late) and checkpoint backpressure (when RocksDB state swells from long allowedLateness, checkpoint barriers stall behind full buffers, causing consumer lag to spiral).

Monitoring watermark health

In Flink or Spark, monitor currentInputWatermark vs. wall-clock time (watermarkLag = now - watermark). A flatlining watermark while Kafka offsets climb indicates an idle partition or skewed key. Always expose a counter for numLateRecordsDropped and sideOutputLateCount so silent data loss triggers an alert immediately.

Practical checklist

  • Set boundedOutOfOrderness from the p99 arrival delay distribution, not a guess.
  • Enable withIdleness() on all multi-partition Kafka sources.
  • Clamp future client timestamps (event_time > now + 5m) before watermark assignment.
  • Always attach a sideOutputLateData sink instead of silently dropping ultra-late records.
  • Pair allowedLateness with an idempotent upsert sink (keyed by window_start, key).
03 / Engineering trade-offs

Weighing architectural decisions

Watermark delay (delta) vs. window latency

Advantage: A generous out-of-orderness bound (e.g., 60s) reduces late-data retractions and downstream upserts.

Drawback: Every window waits 60s longer to emit and retains open RocksDB/heap state for 60s more.

Allowed lateness vs. state storage cost

Advantage: Keeping window state open for allowedLateness lets the stream engine emit accurate updated totals for late arrivals.

Drawback: RocksDB state size grows linearly with lateness duration, increasing checkpoint size and recovery time.

Retractions/upserts vs. append-only sinks

Advantage: Emitting early speculative triggers plus late updates keeps dashboards fresh and eventually accurate.

Drawback: Downstream sinks must support idempotent upserts (e.g., PostgreSQL ON CONFLICT or ClickHouse ReplacingMergeTree) rather than append-only logs.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Idle partition watermark stall

One empty or skewed Kafka partition emits no events, pinning the operator's min-watermark in the past and halting all window outputs while state grows unboundedly.

What helps: Always configure idle-source detection (withIdleness in Flink) and alert on watermark-to-wall-clock lag.

Clock skew poisoning maxEventTime

A single buggy client sends a timestamp 10 years in the future, jumping the watermark to 2036 and causing all real-time events to be treated as late and dropped.

What helps: Clamp or quarantine future timestamps (event_time > processing_time + max_skew) at the ingestion/deserialization boundary.

Silent data loss on late records

Default window operators silently discard records arriving after window_end + allowedLateness, causing revenue/billing undercounts.

What helps: Attach a side output (lateOutputTag) to route ultra-late records to a cold-path Parquet/S3 reconciliation job.

Unbounded state on high-cardinality session windows

Long allowedLateness combined with millions of per-user session keys exhausts RocksDB disk/memory and times out checkpoints.

What helps: Bound session gaps, set explicit State TTL, and size RocksDB block cache + incremental checkpoints.

05 / Practical checklist

Avoid these mistakes

  • Assuming watermarks are global wall-clock timers rather than data-driven metadata flowing inside the stream.
  • Forgetting that an operator with multiple upstream inputs advances its watermark to min(input_watermarks), not max.
  • Leaving idle-partition timeouts unset on topics with uneven key distribution.
  • Using append-only sinks (like plain CSV or unkeyed Kafka) when allowedLateness emits multiple updates per window.
  • Trusting untrusted client device clocks without clamping future timestamps.
