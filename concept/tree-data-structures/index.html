THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Pick B+ trees for read-heavy, range-scannable disk indexes (PostgreSQL/InnoDB), LSM-trees for write-heavy append workloads (RocksDB), and radix/ART trees for fast in-memory prefix lookups.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Every database index, filesystem directory, kernel process scheduler, and Git commit graph is backed by a specialized tree tuned to its storage medium—optimizing for either 64-byte CPU cache lines or 4–16 KB disk pages.

  • B+ trees store all row pointers/values in linked leaf pages and only routing keys in internal nodes; with 16 KB pages (InnoDB), a fanout of ~500 indexes 5003=125M500^3 = 125\text{M}5003=125M rows in just 3 levels.
  • LSM-trees (Log-Structured Merge-trees) buffer writes in an in-memory skip list/RB-tree (memtable) and flush immutable sorted SSTables sequentially, trading read amplification and background compaction for high write throughput.
  • Adaptive Radix Trees (ART, used in DuckDB and HyPer) dynamically resize node fanouts (4, 16, 48, 256 children) to match CPU cache lines without wasting memory on sparse alphabets.
  • Red-Black trees (std::map, Linux CFS vruntime scheduler) guarantee O(log⁡N)O(\log N)O(logN) worst-case height with at most 2 rotations per insert/delete, making them ideal for bounded latency in-memory sets.
  • Merkle trees hash child digests bottom-up so two replicas (Git, Cassandra anti-entropy repair, DynamoDB) can detect divergent key ranges in O(log⁡N)O(\log N)O(logN) network round-trips.

Good candidates

  • Sorted point lookups and range queries (WHERE created_at BETWEEN t1 AND t2) where hash tables cannot scan in order.
  • Disk or NVMe-backed indexes where minimizing random I/O hops (tree height 3–4 for 100M+ keys via high fanout B+ trees) dominates CPU comparisons.
  • Longest-prefix matching, autocomplete, or IP routing tables (CIDR /24 lookups) using compressed Radix/Patricia tries.

Think twice

  • Pure equality lookups (session_id = ?) with no ordering or range requirements; an in-memory hash table gives O(1)O(1)O(1) vs O(log⁡N)O(\log N)O(logN).
  • High-dimensional vector similarity search (>128 dims) where standard trees suffer the curse of dimensionality; use HNSW graphs or IVF-PQ.
  • Small static collections (<64 elements) where a flat sorted array with binary search or linear SIMD scan beats pointer-chasing trees in CPU cache.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn e-commerce database runs SELECT * FROM orders WHERE customer_id = 48219 ORDER BY created_at DESC LIMIT 20 on a 50M-row table.

The idea

A tree is an acyclic connected graph rooted at a single node, where every child has exactly one parent. While textbook binary search trees (BSTs) branch by 2 at each node, real-world systems choose branching factor BBB to match the cost of crossing a memory boundary.

If crossing a boundary means fetching a 16 KB SSD page (50–100 μ\muμs), you pack ~500 keys into one node (a B+ tree) so 100 million keys fit in height 3–4. If crossing a boundary means an L3 cache miss (40 ns), you use an Adaptive Radix Tree or in-memory B-tree with 64-byte cache-line-aligned nodes. And if random page writes are too slow on flash, an LSM-tree turns random tree mutations into sequential log appends plus background merge-sorts.

Concrete walkthrough

Trace a range query SELECT id, total FROM orders WHERE id BETWEEN 4200 AND 4250 in an InnoDB B+ tree (16 KB pages, 4 levels, 100M rows):

  1. Root Page (Level 0, pinned in Buffer Pool): Binary search across ~500 separator keys locates the child page pointer covering [4000, 250000).
  2. Internal Pages (Levels 1 & 2): Two more binary searches in RAM narrow the range to [4180, 4390) and yield the physical page ID of the leaf page.
  3. Leaf Page (Level 3): A binary search inside the leaf page finds id = 4200. Because B+ tree leaves store full row payloads (clustered index) and maintain doubly-linked next_page pointers, InnoDB scans sequentially through 4201..4250 along the leaf chain without ever climbing back up the tree.

High fanout keeps tree height at 3–4 even for 100M+ rows, while linked leaf pages turn range queries into sequential scans.

The RUM conjecture: Read, Update, Memory

Every tree-based storage engine trades off along the RUM Conjecture (Read, Update, and Memory amplification)—you can optimize any two at the expense of the third:

  • B+ Trees optimize Read (single path of 3–4 pages) and Memory (no extra bloom filters or duplicate SSTable versions), at the cost of Update amplification (rewriting a whole 16 KB page for a 100-byte row change, plus WAL full-page writes).
  • LSM-Trees optimize Update (sequential append to WAL + memtable) and Memory/Space (high compression on immutable SSTables), at the cost of Read amplification (checking memtable + L0..Ln SSTables, mitigated by Bloom filters and block caches).

Failure modes

Tree structures fail operationally when workload patterns violate their structural invariants:

  • Sequential vs. random key mismatch: Random UUIDv4 keys shred B+ tree locality, turning 99% buffer-pool hit rates into constant NVMe page faults.
  • Tombstone accumulation in LSM-trees: Deleting millions of rows writes tombstone markers rather than freeing space immediately; range scans over deleted ranges must skip millions of tombstones until compaction purges them.
  • Covering index omission: Even a fast B+ tree lookup incurs a second random I/O per row (heap fetch in PostgreSQL) if the query selects columns not included in the index (INCLUDE (...)).

Modern cache- and NVMe-aware designs

Modern engines blur classical boundaries:

  • B-link Trees (PostgreSQL): Lehman-Yao B-link trees add right-sibling pointers at every level so concurrent readers never block on page splits—eliminating lock coupling.
  • Bw-Tree / Latch-Free B-trees: Replace physical page pointers with logical PIDs in a mapping table, using atomic Compare-And-Swap (CAS) delta chains instead of reader-writer latches.
  • WiscKey (Key-Value Separation): Stores only small keys and value pointers in the LSM-tree while keeping large values (>1 KB) in an append-only vLog, slashing compaction I/O by 10x.

Practical checklist

  • Use UUIDv7 or monotonic 64-bit IDs (Snowflake) for clustered B+ tree primary keys to keep inserts append-mostly.
  • Order composite index columns with equality predicates first, sort/range columns second, and non-filtered projection columns in INCLUDE.
  • On RocksDB/LSM engines, monitor compaction_pending bytes, L0 file count, and Bloom filter false-positive rates (target ~1%, ~10 bits/key).
  • Prefer BTreeMap / absl::btree_map over std::map for in-memory sorted maps >1,000 entries to cut pointer-chasing cache misses.
  • Periodically inspect PostgreSQL pgstatindex (avg_leaf_density) or InnoDB fragmentation on high-churn tables.
03 / Engineering trade-offs

Weighing architectural decisions

B+ Tree vs. LSM-Tree

Advantage: B+ trees deliver predictable, fast point/range reads without checking multiple SSTable levels or Bloom filters.

Drawback: Random B+ tree updates trigger in-place page rewrites and splits, causing 10–30x write amplification on SSDs.

AVL Tree vs. Red-Black Tree

Advantage: AVL trees maintain stricter height balance ($\le 1.44 \log_2 N$), yielding slightly faster lookups.

Drawback: AVL deletes can trigger $O(\log N)$ rotations up to the root, whereas Red-Black trees cap rotations at $O(1)$ per mutation.

Pointer-Based Binary Tree vs. Cache-Conscious Array/ART

Advantage: Standard BSTs are simple to implement and support $O(1)$ node splicing.

Drawback: Heap-allocated nodes cause CPU L2/L3 cache misses on every pointer dereference; ART or B-trees pack keys contiguously into 64-byte cache lines.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

B+ Tree Index Bloat and Page Splits

Inserting random UUIDv4 primary keys into a clustered B+ tree (e.g., MySQL InnoDB) forces frequent 50% page splits, dropping fill factor to ~50% and doubling memory/disk footprint.

What helps: Use monotonically increasing or time-ordered keys like UUIDv7 or ULID for clustered indexes, and schedule periodic `REINDEX` / `OPTIMIZE TABLE` if fragmentation exceeds 30%.

LSM-Tree Write Stall Under Compaction Backlog

Heavy write bursts accumulate too many L0 SSTables before background compaction catches up, causing RocksDB to throttle or stall foreground writes.

What helps: Size `max_background_compactions` to match NVMe IOPS, tune `level0_slowdown_writes_trigger`, and isolate WAL on a separate queue/device if needed.

Unbalanced BST Degeneration

Inserting pre-sorted timestamps into an unbalanced binary search tree degenerates height from $\log_2 N$ to $N$, turning $O(\log N)$ lookups into $O(N)$ stack-overflowing linked-list scans.

What helps: Always use self-balancing variants (Red-Black, AVL, B-tree) or randomized structures like treaps/skip lists.

Latch Contention on Hot Rightmost Leaf

Monotonic timestamp inserts contend on the single rightmost B+ tree leaf page latch under 64+ concurrent writer threads.

What helps: Shard or hash-prefix the leading key (e.g., `(shard_id, timestamp)`), or batch inserts through a single-writer queue.

05 / Practical checklist

Avoid these mistakes

  • Using UUIDv4 as a clustered primary key in InnoDB/SQL Server, destroying insert locality and buffer pool hit rates.
  • Creating wide multi-column B+ tree indexes in the wrong column order (e.g., `(status, user_id)` when queries filter only on `user_id`), violating the leftmost-prefix rule.
  • Forgetting Bloom filters on LSM-tree SSTables, forcing point lookups for missing keys to scan every level on disk.
  • Using a pointer-heavy binary tree in C++/Java for small in-memory sorted sets instead of a cache-friendly B-tree (e.g., `absl::btree_map` or Rust's `BTreeMap`).
  • Neglecting to tune `fillfactor` (e.g., 70–80% in PostgreSQL) on frequently updated tables, preventing HOT (Heap-Only Tuple) updates.
