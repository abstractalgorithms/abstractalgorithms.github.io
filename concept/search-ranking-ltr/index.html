Multi-Stage Search & Learning-to-Rank
(BM25 + LTR).

Multi-stage search pairs fast inverted-index retrieval (BM25 + Roaring Bitmaps) over 100M+ documents with expensive Learning-to-Rank (GBDT/Neural) reranking on only the top ~200 candidates.

The idea to keep with you

If latency budgets leave no room for synchronous retries, scoring 100M documents with a neural/GBDT model blows past a 100ms latency budget; a funnel architecture (100M -> Top-1000/shard -> Top-200 -> Top-20) achieves both web-scale speed and ML relevance.

TL;DR30-second simplified summary
▾

Index shards prune postings with Block-Max WAND to emit Top-1000 candidates. A hedged Coordinator merges to Top-200, hydrates real-time features via Redis MGET, and scores with LambdaMART GBDT to optimize NDCG@10.

01
foundation

Why Lexical BM25 Alone Fails Modern Search Relevance.

Why this matters: Recognize the gap between term-frequency matching and user intent, freshness, and authority.

Think of Why Lexical BM25 Alone Fails Modern Search Relevance as the intuition layer for Multi-Stage Search & Learning-to-Rank (BM25 + LTR): Recognize the gap between term-frequency matching and user intent, freshness, and authority.

BM25 scores documents purely on term frequency, inverse document frequency, and length normalization. It has no awareness of document quality, click-through rate, recency, personalization, or synonym semantics—meaning a stale 2014 page with repeated keywords can outrank today's canonical guide.

FOUNDATION

Lexical BM25 vs. Behavioral Signals

1.Term Saturation: BM25 k1=1.5 dampens keyword stuffing but cannot judge authority.

2.Zero Context: BM25 treats a 10-year-old doc identically to yesterday's release.

BM25 excels at fast lexical recall but lacks behavioral, freshness, and personalization signals.

02
foundation

L0 Retrieval: Sharded Inverted Index & Block-Max WAND.

Why this matters: Retrieve the Top-1,000 candidates per shard in <15ms without scanning entire posting lists.

Think of L0 Retrieval: Sharded Inverted Index & Block-Max WAND as the intuition layer for Multi-Stage Search & Learning-to-Rank (BM25 + LTR): Retrieve the Top-1,000 candidates per shard in <15ms without scanning entire posting lists.

For common terms like 'python' or 'system', posting lists can hold 10M+ document IDs. Block-Max WAND (Weak AND) stores the maximum BM25 score per 128-doc block in skip pointers, allowing the scorer to jump over entire blocks whose upper-bound score cannot beat the current Top-1,000 heap threshold.

FOUNDATION

Block-Max WAND Dynamic Pruning

1.Roaring Bitmaps: Compressed bitsets filter `in_stock=true` or tenant ACLs in microseconds.

2.5-10x Speedup: Block-Max WAND skips hopeless blocks without decompressing docIDs.

Block-Max WAND and Roaring Bitmaps prune millions of postings to emit Top-1,000 candidates fast.

Engineering Decision Framework
Problem
How to implement Multi-Stage Search & Learning-to-Rank (BM25 + LTR) without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
If latency budgets leave no room for synchronous retries, scoring 100M documents with a neural/GBDT model blows past a 100ms latency budget; a funnel architecture (100M -> Top-1000/shard -> Top-200 -> Top-20) achieves both web-scale speed and ML relevance.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

03
intermediate

Coordinator Scatter-Gather & Deduplication (Top-200).

Why this matters: Merge candidate lists from N shards cleanly and guard against tail-latency stragglers.

Think of Coordinator Scatter-Gather & Deduplication (Top-200) as the intuition layer for Multi-Stage Search & Learning-to-Rank (BM25 + LTR): Merge candidate lists from N shards cleanly and guard against tail-latency stragglers.

The Search Coordinator scatters the rewritten query to all index shards in parallel with a strict 25ms deadline. Using hedged requests (firing a backup replica read if a shard hasn't responded in 12ms) and global IDF statistics, it merges shard Top-1,000 lists into a unified Top-200 candidate set.

INTERMEDIATE

Hedged Scatter-Gather Merge

1.Tail Latency: A single slow GC-pausing shard stalls the whole query without hedging.

2.Global IDF: Synchronized corpus IDF keeps BM25 scores comparable across shards.

Hedged scatter-gather keeps shard merge latency bounded even when one replica hits GC.

04
intermediate

Low-Latency Feature Hydration from the Feature Store.

Why this matters: Fetch dynamic document and user features for the Top-200 candidates in a single batch call.

Think of Low-Latency Feature Hydration from the Feature Store as the intuition layer for Multi-Stage Search & Learning-to-Rank (BM25 + LTR): Fetch dynamic document and user features for the Top-200 candidates in a single batch call.

Static inverted indexes shouldn't be re-indexed every time a product's 1-hour CTR or inventory count changes. Instead, the Reranker issues a single MGET batch call to a Redis/RocksDB Feature Store to hydrate 50–200 real-time features (ctr_7d, freshness_hours, user_brand_affinity) for the 200 candidate IDs in <5ms.

INTERMEDIATE

Batch Feature Store Hydration

1.Zero Index Churn: Dynamic CTR and popularity update in Redis without touching Lucene segments.

2.Graceful Default: Missing feature keys fall back to neutral imputed defaults.

Batch `MGET` feature hydration decouples fast-changing behavioral signals from static inverted indexes.

05
intermediate

L1/L2 Learning-to-Rank: Pointwise, Pairwise & Listwise (LambdaMART).

Why this matters: Train GBDT/LambdaMART models directly on NDCG ranking order rather than raw click regression.

Think of L1/L2 Learning-to-Rank: Pointwise, Pairwise & Listwise (LambdaMART) as the intuition layer for Multi-Stage Search & Learning-to-Rank (BM25 + LTR): Train GBDT/LambdaMART models directly on NDCG ranking order rather than raw click regression.

Pointwise models predict click probability independently per document. Pairwise (RankNet) and Listwise (LambdaMART / LambdaRank) models directly optimize ranking metrics like NDCG@10 by weighting gradient updates according to how much swapping two documents changes NDCG.

INTERMEDIATE

Pointwise vs. Pairwise vs. Listwise LTR

1.LambdaMART Standard: GBDTs (LightGBM/XGBoost) score 200 x 100 matrices in ~5-10ms on CPU.

2.Position Bias: Training data must debias higher click rates at position #1 vs #8.

Listwise GBDT models like LambdaMART directly optimize `NDCG@10` on tabular search features.

06
advanced

L2 Neural Cross-Encoder Cascade & Diversity Reranking.

Why this matters: Apply semantic cross-encoders and MMR diversity to the Top-30 without blowing the latency budget.

Think of L2 Neural Cross-Encoder Cascade & Diversity Reranking as the intuition layer for Multi-Stage Search & Learning-to-Rank (BM25 + LTR): Apply semantic cross-encoders and MMR diversity to the Top-30 without blowing the latency budget.

Even a fast GBDT struggles with subtle semantic nuance ('apple watch band' vs 'watch apple keynote'). An L2 cascade passes only the Top-30 candidates from L1 GBDT into a quantized ONNX MiniLM cross-encoder on GPU/AVX-512, followed by Maximal Marginal Relevance (MMR) to prevent 5 near-duplicate results at the top.

ADVANCED

L2 Cross-Encoder + MMR Diversity

1.Cascade Budget: Running neural models on 30 docs instead of 200 keeps latency <20ms.

2.SERP Diversity: MMR ensures varied results rather than 5 clones from one domain.

An L1 GBDT -> L2 Cross-Encoder -> MMR cascade balances semantic precision, diversity, and speed.

07
advanced

Position-Debiased Click Logs & Interleaving Online Tests.

Why this matters: Measure real ranking improvements safely using Team-Draft Interleaving and counterfactual propensity weighting.

Think of Position-Debiased Click Logs & Interleaving Online Tests as the intuition layer for Multi-Stage Search & Learning-to-Rank (BM25 + LTR): Measure real ranking improvements safely using Team-Draft Interleaving and counterfactual propensity weighting.

Users click position #1 far more often than position #5 even when #5 is more relevant (position bias). Logging (query_id, doc_id, position, propensity_weight, click) enables Inverse Propensity Scoring (IPS) offline, while Team-Draft Interleaving blends Model A and Model B results in one SERP to detect wins with 10x less traffic than A/B tests.

ADVANCED

Debiased Telemetry & Interleaving

1.10x Sensitivity: Interleaving pairs A and B on the same query, cutting noise dramatically.

2.Guardrail Metrics: Always monitor zero-result rate and p99 latency alongside CTR.

Position-debiased IPS logs and Team-Draft Interleaving prevent feedback loops in LTR retraining.
