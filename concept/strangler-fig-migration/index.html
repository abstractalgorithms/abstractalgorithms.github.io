Strangler Fig
Migration.

The Strangler Fig pattern incrementally replaces a legacy monolith by intercepting traffic at an edge proxy or gateway, routing specific capabilities to new microservices while keeping existing flows running safely.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Migrate one bounded vertical slice at a time behind a reverse proxy (Envoy/NGINX) with dual-write or Debezium CDC data sync, shadow traffic verification, and instant feature-flag rollback—never a Big Bang cutover.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Big Bang rewrites freeze feature delivery for 12–24 months and routinely fail under parity gaps; Strangler Fig delivers production value in weeks with per-route blast-radius isolation.

  • Every migration follows three phases per slice: Coexist (proxy routes to monolith), Mirror/Verify (shadow traffic + CDC sync), and Cutover/Decommission.
  • An API gateway or L7 proxy (Envoy, NGINX, Kong, AWS ALB) decouples clients from backend topology via path, header, or percentage routing.
  • Data decoupling is the hardest part: avoid shared-database anti-patterns by using Debezium CDC outbox/binlog replication until the new service owns its schema.
  • Shadow (dark-launch) traffic replays live GET/idempotent requests to the new service asynchronously and diffs responses against the monolith before user-facing cutover.
  • Decommissioning the old code path is mandatory; an unretired monolith leaves you maintaining two systems indefinitely.

Good candidates

  • Decomposing a revenue-critical legacy monolith (e.g., Java EE, Rails, or .NET) that cannot afford downtime or a multi-quarter feature freeze.
  • Extracting high-change or high-scale bottlenecks (e.g., checkout, search, or auth) into independent services with separate release cadences.
  • Migrating core data stores (e.g., Oracle to PostgreSQL) incrementally using Change Data Capture (CDC) and shadow reads.

Think twice

  • Small applications (< 50k LOC) where a clean modularization or direct rewrite takes only a few weeks.
  • Tightly coupled batch jobs or shared-memory desktop/embedded systems with no network boundary to intercept.
  • Organizations lacking automated contract tests, observability, or CI/CD to operate distributed services safely.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA retail platform runs catalog, cart, checkout, and invoicing in one Oracle-backed monolith whose 45-minute deploy cycle blocks Black Friday scaling.

The idea

Named after tropical strangler fig vines that grow around a host tree until the host rots away, the Strangler Fig pattern places an interception layer (API gateway or L7 proxy) in front of a legacy system. New features and extracted capabilities are built beside the monolith and gradually take over routes and data ownership until the legacy core can be safely powered down.

Concrete walkthrough

  1. Place the seam: Route all ingress traffic through an L7 gateway (e.g., Envoy) with default fallback to the legacy monolith.
  2. Select a bounded slice: Pick a cohesive domain (e.g., /v1/inventory) with clear inputs/outputs and minimal foreign-key entanglement.
  3. Sync data via CDC: Stream legacy table changes via Debezium (WAL/binlog -> Kafka) into the new service's dedicated database.
  4. Shadow & diff: Enable Envoy traffic mirroring (request_mirror_policies) to send live read requests asynchronously to the new service and compare JSON payloads.
  5. Canary cutover: Shift live traffic 1% -> 10% -> 50% -> 100% while monitoring p99 latency, 5xx rates, and business invariants.
  6. Flip source of truth & prune: Stop CDC into the new DB, reverse-sync if legacy reports still need it temporarily, and delete the legacy route.

An L7 gateway isolates clients from backend topology while Debezium CDC keeps the new service's database warm for shadow verification and weighted cutover.

Breaking the shared database

Splitting compute without splitting data creates a distributed monolith. During migration, establish a single source of truth per table at any moment. Use Change Data Capture (Debezium) or a Transactional Outbox to replicate writes from the current owner to the shadow store. At cutover, drain the replication lag (or pause writes briefly for 1–2 seconds), flip ownership to the new service, and optionally run reverse-CDC if legacy reporting jobs still read the old tables.

Failure modes

The biggest risk during cutover is stale-read race conditions: a user writes to the new service and immediately reads from a legacy endpoint before reverse-sync completes. Solve this by migrating all read and write endpoints of a bounded aggregate together, or by routing read-after-write sessions via a short-lived cookie/header to the new owner.

Parity testing and observability

Attach a consistent X-Correlation-ID at the API gateway so distributed traces (OpenTelemetry) span both the monolith and the new service. In shadow mode, log structural diffs (ignoring non-deterministic fields like timestamps or UUIDs) and require 99.99% semantic parity over at least one full business cycle before shifting write traffic.

Practical checklist

  • Put an L7 proxy/gateway in front of the monolith before extracting any code.
  • Pick a first slice with clear boundaries and low coupling (e.g., read-heavy catalog or notifications).
  • Use CDC or an outbox instead of synchronous app-level dual writes.
  • Run shadow read mirroring with automated response diffing before cutover.
  • Delete the dead legacy endpoints and schema tables as soon as the new slice stabilizes.
03 / Engineering trade-offs

Weighing architectural decisions

Incremental risk reduction vs. interim complexity

Advantage: Each migrated slice ships to production independently with instant DNS/gateway rollback.

Drawback: During transition, teams must maintain routing rules, dual-auth bridges, and CDC pipelines across both systems.

Dual-write from app vs. CDC (Debezium)

Advantage: CDC reads database transaction logs (WAL/binlog) asynchronously with guaranteed ordering and zero app-level 2PC locks.

Drawback: CDC introduces replication lag (typically 50–500 ms), requiring read-your-own-writes routing or sticky cutover windows.

Shared database shortcut vs. isolated schema

Advantage: Pointing the new service at the old DB ships faster on day 1.

Drawback: Creates tight schema coupling and lock contention, preventing independent scaling and trapping you in a distributed monolith.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Dual-write split-brain divergence

Application code writes to both legacy and new databases without distributed transactions; partial failures silently corrupt state.

What helps: Never dual-write directly from app code on critical paths—use single-writer ownership plus transactional outbox or Debezium CDC.

Circular monolith-to-microservice callbacks

The extracted service calls back into the monolith synchronously, creating latency amplification and cascading failure loops.

What helps: Replicate needed read-only reference data into the new service via events/CDC and enforce acyclic dependency rules.

Half-strangled zombie monolith

Teams migrate 60% of endpoints, lose executive sponsorship, and leave both systems running in production for years.

What helps: Tie each slice's Definition of Done to deleting the dead monolith route and archiving its tables.

Non-idempotent shadow traffic mutations

Mirroring POST /payments or POST /orders traffic to the new service triggers duplicate charges or emails.

What helps: Only mirror safe GET/read endpoints, or intercept external side-effect adapters (payment gateways, SMTP) with no-op stubs in shadow mode.

05 / Practical checklist

Avoid these mistakes

  • Starting with the most tangled core domain instead of a low-risk, well-bounded edge capability.
  • Allowing the new microservice to query the monolith's internal tables directly via SQL joins.
  • Skipping automated parity diffing between legacy and new responses before shifting live user traffic.
  • Forgetting session/auth token translation at the edge proxy, forcing users to log in twice.
  • Ignoring latency budgets—adding 3 extra proxy/service hops without tuning connection pooling and timeouts.
