What are Java Virtual Threads.

Why this matters: The mechanism: understand how Java Virtual Threads works from first principles.

Traditional platform threads map 1:1 to OS kernel threads (~1 MB stack each), capping Spring/Tomcat servers at ~200–500 concurrent requests. Java 21+ Virtual Threads (Project Loom) are cheap JVM-managed continuations (~few KB) multiplexed onto a small ForkJoinPool of carrier OS threads.

When a virtual thread hits blocking I/O (Socket, LockSupport), the JVM unmounts its stack chunk onto the heap and frees the carrier OS thread to run another virtual thread—scaling imperative blocking code to 100,000+ concurrent tasks.

Virtual Thread Mount / Unmount & Carrier Pinning State Machine

Replacing synchronized around I/O with ReentrantLock (or upgrading to Java 24+ JEP 491) prevents carrier-thread pinning.

Never Pool Virtual Threads

Virtual threads are cheap, disposable tasks—never wrap them in a fixed Executors.newFixedThreadPool. Use Executors.newVirtualThreadPerTaskExecutor() and bound downstream resources with a Semaphore.

Avoid `ThreadLocal` Bloat

Caching large buffers (e.g., 64 KB SimpleDateFormat or Jackson buffers) in ThreadLocal across 100,000 virtual threads explodes heap! Prefer immutable ScopedValue.

// Safe Java 21+ Virtual Thread fan-out with downstream Semaphore backpressure
private static final Semaphore DB_GATE = new Semaphore(32);
private static final ReentrantLock CACHE_LOCK = new ReentrantLock();

public Profile fetchProfile(String userId) throws Exception {
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        Future<User> user = executor.submit(() -> {
            DB_GATE.acquire();
            try { return queryUser(userId); } finally { DB_GATE.release(); }
        });
        Future<List<Order>> orders = executor.submit(() -> fetchOrdersRpc(userId));
        return new Profile(user.get(), orders.get());
    }
}

Design Trade-Off

Alternatives: Virtual Threads vs. Reactive (WebFlux) vs. Go Goroutines

Before · Unbounded Pool + Nested Locks
  • AB-BA deadlock or OOM heap
  • Blocking I/O starves event loop
  • False sharing thrashes L1 cache
After · Bounded Permits + Lock-Free CAS
  • CallerRuns / shed at capacity
  • Padded cache lines prevent bouncing
  • Structured timeouts release leaks
ChoiceWhat it buysWhat it costs
Java 21+ Virtual ThreadsImperative stack traces, standard `try/catch`, and seamless Spring Boot 3.2+ integration (`spring.threads.virtual.enabled=true`).JDK 21–23 carrier pinning on `synchronized` + I/O (resolved in JDK 24 JEP 491) and `ThreadLocal` memory hazards.
