THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Stop dual-writing to your database and Kafka in application code: tail the committed transaction log (e.g., Debezium + PostgreSQL `pgoutput`) and pair it with the Transactional Outbox pattern for schema-safe, at-least-once event streaming.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Modern architectures constantly need to sync an OLTP database with search indices (Elasticsearch/OpenSearch), caches (Redis), analytics warehouses (Snowflake/BigQuery), and downstream microservices. Application-level dual writes (db.save() followed by kafka.send()) inevitably diverge when a process crashes or times out between the two calls, while SELECT * WHERE updated_at > ? polling misses hard deletes, burdens primary replicas, and adds seconds to minutes of lag. Log-based CDC turns the database's own durability log into an ordered, zero-polling event stream.

  • Log-based CDC (Debezium, Maxwell, Airbyte CDC) reads the append-only WAL/binlog sequentially, adding negligible I/O overhead compared to trigger-based CDC or SELECT polling.
  • CDC guarantees at-least-once delivery and per-key ordering (when partitioned by primary key in Kafka); downstream consumers must still be idempotent using LSN/offset or version checks.
  • Initial snapshots (consistent REPEATABLE READ table reads + seamless switchover to the WAL LSN) allow bootstrapping terabyte-scale tables without taking downtime.
  • Schema evolution is a first-class concern: pairing CDC with a Schema Registry (Avro/Protobuf) prevents an ALTER TABLE ADD COLUMN from silently breaking downstream Flink or ClickHouse sinks.
  • Unbounded replication slots (e.g., an abandoned PostgreSQL logical replication slot) will retain WAL segments indefinitely until the primary database disk fills up and crashes.

Good candidates

  • Synchronizing OLTP state (PostgreSQL, MySQL, Oracle) to read replicas, Elasticsearch, Redis, or data lakes in near real-time (<500 ms lag) without impacting transactional latency.
  • Implementing the Transactional Outbox pattern so domain events are atomically committed in the same ACID transaction as business state.
  • Zero-downtime database migrations (e.g., MySQL 5.7 to Aurora 8.0 or monolith-to-microservice table extraction) via continuous replication and shadow verification.

Think twice

  • When simple batch ETL (hourly or nightly COPY / pg_dump) satisfies analytics SLAs and running Kafka Connect + Debezium adds unjustified operational overhead.
  • When downstream consumers need rich domain context that spans 5 joined tables and isn't materialized in a single row—unless paired with an Outbox table containing the domain payload.
  • On managed databases where transaction log access (wal_level=logical or binlog_format=ROW) is disabled or restricted by vendor tier.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn order service previously wrote to PostgreSQL and published to Kafka in Java code. During network blips, 0.3% of paid orders never reached the fulfillment Kafka topic, causing silent shipping failures.

The idea

Change Data Capture (CDC) converts a database's internal write-ahead log (WAL) or binary log (binlog) into an append-only stream of committed row-level mutations (INSERT, UPDATE, DELETE).

Every ACID database already writes every committed change sequentially to its transaction log for crash recovery and physical replication. Log-based CDC attaches a lightweight reader (such as Debezium via PostgreSQL's pgoutput logical decoding plugin or MySQL's row-based binlog) to that log. Because it only emits changes after COMMIT and reads sequentially in the background, it eliminates dual-write inconsistency without adding locks or polling queries to the hot OLTP path.

Concrete walkthrough

Follow a single order update through a PostgreSQL -> Debezium -> Kafka -> OpenSearch pipeline:

  1. ACID Commit: The Order Service updates orders SET status = 'SHIPPED' WHERE id = 9041 and (optionally) inserts a row into outbox_events within one transaction. PostgreSQL appends the change to pg_wal at LSN 0/1A4F890.
  2. Logical Decoding: PostgreSQL's pgoutput slot decodes the WAL record (including before and after images if REPLICA IDENTITY FULL is set) and streams it over the replication protocol to the Debezium Kafka Connect worker.
  3. Envelope & Schema Serialization: Debezium wraps the mutation in a structured envelope (op: "u", before, after, source.lsn, ts_ms), validates it against Confluent Schema Registry (Avro/Protobuf), and produces it to Kafka topic db.public.orders partitioned by key = 9041.
  4. Offset Commit: Periodically, Kafka Connect commits lsn: 0/1A4F890 to its internal __connect_offsets topic and sends a standby status feedback to PostgreSQL, allowing old WAL segments to be recycled.
  5. Idempotent Sink: The OpenSearch sink reads the event, checks source.lsn (or version), and executes an idempotent _update on document 9041—achieving <300 ms end-to-end search freshness.

Log-based CDC tails committed WAL records through Debezium and Kafka to keep search indices, caches, and warehouses synchronized without dual-write races.

The Transactional Outbox pattern

Exposing raw database tables via CDC couples downstream consumers to your internal schema. The Transactional Outbox pattern solves this cleanly:

  1. Instead of streaming orders and order_items directly, your service inserts a serialized domain event (OrderConfirmedV2) into an outbox table (id, aggregatetype, aggregateid, payload, created_at) inside the exact same ACID transaction as the business update.
  2. Immediately after the insert (or via a background sweep), the row can even be deleted—because PostgreSQL still records the INSERT in the WAL, keeping the live outbox table tiny.
  3. Debezium's EventRouter Single Message Transform (SMT) reads only op = 'c' (create) events from outbox, routes them to outbox.event. keyed by aggregateid, and strips the raw Debezium envelope so consumers receive clean, versioned domain events.

Failure modes

  • Unbounded Replication Slot Bloat: A stopped Debezium connector holds back PostgreSQL's restart_lsn, filling pg_wal until the database crashes with No space left on device.
  • Split-Brain Ordering Across Tables: Partitioning orders and order_items into different Kafka topics means a consumer can receive OrderItemCreated before OrderCreated; use the Outbox pattern to bundle aggregates or buffer out-of-order children.
  • Snapshot Timeout / Lock Contention: Running a legacy blocking snapshot on a busy 2 TB table triggers long-running transaction bloat (xmin horizon pinned, blocking VACUUM). Always use Debezium's incremental snapshot mode.
  • Silent Data Loss on max_slot_wal_keep_size: If you cap WAL retention to protect disk space and the connector falls behind that cap, PostgreSQL invalidates the slot—requiring an automated alert and incremental re-snapshot.

Production operations & schema governance

Operating CDC reliably at scale requires treating the pipeline as Tier-1 infrastructure:

  • Schema Registry Enforcement: Register all Debezium topics in Confluent Schema Registry or Apicurio with BACKWARD compatibility. Never run destructive DROP COLUMN or type-narrowing DDL without a expand-and-contract migration.
  • Heartbeat & LSN Monitoring: Alert on pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn) exceeding 1 GB and enable heartbeat.interval.ms on low-write databases.
  • Dead-Letter Queues (DLQ): Configure errors.tolerance=all and errors.deadletterqueue.topic.name on sink connectors so one malformed UTF-8 string does not halt replication for millions of valid rows.

Practical checklist

  • Enable wal_level = logical (PostgreSQL) or binlog_format = ROW + binlog_row_image = FULL (MySQL) on the source database.
  • Set max_slot_wal_keep_size and alert when replication slot lag exceeds 50% of the cap to prevent primary disk exhaustion.
  • Use the Transactional Outbox pattern for cross-service domain events; reserve raw-table CDC for search, cache, and analytics sinks.
  • Configure heartbeat.interval.ms and Debezium incremental snapshots (signal.data.collection) for zero-downtime backfills.
  • Enforce idempotent upserts keyed by primary key + source.lsn (or ts_ms) on every downstream consumer.
03 / Engineering trade-offs

Weighing architectural decisions

Raw Table CDC vs. Transactional Outbox Pattern

Advantage: Raw table CDC requires zero application code changes and captures every column mutation automatically.

Drawback: Exposes internal database schemas as public contracts—any column rename breaks consumers—whereas the Outbox pattern decouples internal schema from stable versioned domain events.

Log-Based CDC vs. Trigger-Based CDC

Advantage: Log-based CDC reads sequential WAL files asynchronously with ~1–3% CPU overhead and zero impact on write transaction latency.

Drawback: Trigger-based CDC writes shadow tables inside the user transaction (adding 2x write amplification and lock contention), though it works on legacy DBs without WAL access.

Incremental Snapshotting vs. Blocking Initial Snapshot

Advantage: Debezium incremental snapshots (DBLog algorithm) chunk large tables with watermarks, allowing pause/resume and avoiding long-held locks or replication slot bloat.

Drawback: Takes longer to complete the initial backfill than a single parallelized bulk export and requires a primary key on the source table.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

WAL / Binlog Disk Exhaustion

If the Debezium connector crashes or stalls for hours, PostgreSQL retains all unacknowledged WAL segments in `pg_wal` until the primary disk hits 100% and halts all writes.

What helps: Set `max_slot_wal_keep_size` in PostgreSQL 13+, monitor `pg_replication_slots` lag in bytes, and configure PagerDuty alerts at 50% WAL retention threshold.

Schema Change Deserialization Crash

A developer runs `ALTER TABLE` (e.g., changing column type or dropping a non-null field), causing downstream Kafka consumers or BigQuery sinks to fail deserialization and stall the entire partition.

What helps: Enforce Schema Registry `BACKWARD` compatibility, test DDL changes in staging with Debezium running, and prefer additive nullable columns.

Duplicate Events on Connector Rebalance

A Kafka Connect worker restarts before committing the latest LSN offset to `__connect_offsets`, replaying the last 500–5,000 WAL events upon recovery.

What helps: Make all downstream sinks idempotent using `UPSERT` keyed on primary key + source LSN/timestamp (`source.lsn` or `ts_ms`) so older replays never overwrite newer state.

Heartbeat Starvation on Low-Traffic Databases

On a quiet database with active replication slots on a busy shared cluster, Debezium's confirmed LSN never advances because the tracked table has no writes, pinning WAL files from other busy databases.

What helps: Configure `heartbeat.interval.ms=10000` and `heartbeat.action.query` writing to a lightweight heartbeat table so the replication slot LSN advances continuously.

05 / Practical checklist

Avoid these mistakes

  • Exposing raw internal table schemas directly to 10+ downstream microservices, turning every database normalization refactor into a cross-team breaking change.
  • Forgetting to set `REPLICA IDENTITY FULL` in PostgreSQL when downstream consumers need the `before` image of `UPDATE` and `DELETE` rows (default only logs primary keys).
  • Running `SELECT *` initial snapshots on multi-terabyte tables without incremental chunking, exhausting `tempdb`/undo logs or timing out the replication slot.
  • Assuming CDC delivers events exactly once—skipping idempotency checks in consumers and corrupting aggregates during Kafka Connect rebalances.
  • Ignoring TOASTed columns in PostgreSQL (`unchanged-toast-placeholder`), causing `UPDATE` events on unrelated columns to emit placeholder values instead of full text/JSONB blobs.
