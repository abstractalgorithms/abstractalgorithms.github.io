STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Change Data Capture (CDC).

Why this matters: The mechanism: understand how Change Data Capture (CDC) works from first principles.

Change Data Capture (CDC) converts a database's internal Write-Ahead Log (WAL) or binlog into an append-only stream of committed row-level mutations (INSERT, UPDATE, DELETE).

Because every ACID database already writes committed changes sequentially to its transaction log, log-based CDC (Debezium, Maxwell) attaches a lightweight reader (pgoutput logical replication in PostgreSQL) with ~1–3% CPU overhead. Consistent REPEATABLE READ initial snapshots bootstrap terabytes of existing rows and transition seamlessly to the exact WAL LSN.

Log-Based CDC Pipeline

PostgreSQL pg_wal (pgoutput) -> Debezium -> Kafka -> Search / OLAP

1.Zero Dual-Write: Application writes only to Postgres; CDC never sees uncommitted or rolled-back transactions.

2.Per-Key Ordering: Partitioning Kafka by aggregate_id preserves strict mutation order per entity.

3.At-Least-Once + Idempotency: Consumers deduplicate replays using the monotonic WAL LSN or event version.

Tailing the committed WAL guarantees DB and event-bus state never diverge.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need CDC + Outbox (and why dual-writes & naive CDC fail).

Why this matters: The problem: see what breaks without CDC + Outbox under real concurrency or scale.

Writing to PostgreSQL and then calling kafka.send() in app code creates dual-write drift: if the process crashes or Kafka times out after COMMIT, the event is lost forever; if kafka.send() runs before COMMIT and the DB rolls back, downstream sees phantom orders.

Even with CDC, watch three operational traps:

  1. Replication Slot Disk Exhaustion: A stopped Debezium connector holds back PostgreSQL restart_lsn, filling pg_wal until the DB crashes with No space left on device.
  2. Cross-Table Ordering Races: Streaming raw orders and order_items to separate Kafka topics lets consumers see OrderItemCreated before OrderCreated—use the Transactional Outbox pattern!
  3. Polling SELECT Gaps: Query-based polling (WHERE updated_at > ?) misses hard DELETEs and burdens the primary DB.
Transactional Outbox + CDC

Single ACID Commit -> Debezium Outbox Router -> Ordered Domain Event

The Transactional Outbox decouples downstream consumers from internal DB tables while preserving atomic event emission.

Engineering Decision Framework
Problem
How to implement Change Data Capture (CDC) without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
To keep storage layouts predictable as data grows, stop dual-writing to your database and Kafka in application code: tail the committed transaction log (e.g., Debezium + PostgreSQL pgoutput) and pair it with the Transactional Outbox pattern for clean domain events.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Replication Slots, Outbox Cleanup, and Idempotency are managed.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Protect your primary database and downstream sinks:

  1. Cap Slot Retention: Set max_slot_wal_keep_size (PostgreSQL 13+) so a dead CDC connector drops its slot before crashing the primary disk.
  2. Outbox Table Hygiene: Partition outbox by day and DROP old partitions (or delete immediately in CDC if using log-only retention) to avoid vacuum bloat.
  3. Consumer Deduplication: Track source_lsn or event_id in downstream sinks so at-least-once replays are idempotent.
