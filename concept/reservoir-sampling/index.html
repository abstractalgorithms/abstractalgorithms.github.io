Reservoir
Sampling.

Reservoir sampling selects a uniformly random sample of k items from a data stream of unknown or unbounded length n in a single pass using O(k) memory.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Maintain a fixed k-element array and accept the i-th incoming item (i > k) with probability k/i, replacing a random slot—giving every item an exact k/n selection probability without knowing n upfront.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Modern telemetry, log pipelines, and ML feature stores process millions of events per second where storing the full stream in memory—or running a two-pass count-then-sample job—is impossible. Reservoir sampling guarantees an unbiased, representative fixed-size sample in strict O(k) RAM and a single streaming pass.

  • Vitter's Algorithm R initializes the reservoir with the first k items, then for each item i > k generates a random integer j in [1, i]; if j <= k, it overwrites reservoir[j].
  • By induction, after n items have passed, every single item from 1 to n has an exact probability k/n of remaining in the reservoir.
  • Algorithm R runs in O(n) time and O(k) space, calling the random number generator once per incoming element.
  • Vitter's Algorithm L optimizes CPU cost to O(k * (1 + log(n/k))) by sampling geometric skip distances between accepted items instead of rolling RNG on every item.
  • Weighted reservoir sampling (Efraimidis-Spirakis / Algorithm A-Res) assigns each item a key u^(1/w) (where u ~ Uniform(0,1)) and keeps the top k keys in a min-heap.

Good candidates

  • Stream length n is unknown, unbounded, or too large to store in memory (e.g., live Kafka consumers, eBPF packet capture, API gateway logs).
  • You need a guaranteed uniform random sample of exact size k (e.g., 10,000 traces) for debugging, quantile estimation, or evaluation datasets.
  • Memory is tightly bounded (such as embedded agents or sidecar proxies) and must never grow with traffic spikes.

Think twice

  • Total dataset size n is already known and indexed (e.g., a Parquet table or SQL table)—direct index sampling or TABLESAMPLE avoids scanning every row.
  • You need stratified or rare-class coverage (e.g., capturing 100% of HTTP 500 errors); uniform sampling will drown rare anomalies in common 200 OKs.
  • Sliding-window recency is required (e.g., 'sample from the last 5 minutes only')—standard reservoir sampling weights all historical items equally unless adapted with time-decay.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn observability sidecar needs to capture k = 5,000 representative request/response bodies per hour from 180M daily requests without knowing hourly volume ahead of time.

The idea

Reservoir sampling solves a deceptively tricky streaming constraint: how do you pick k items uniformly at random from a sequence of unknown length n in one pass and O(k) memory?

In Vitter's Algorithm R, you fill a k-element array (reservoir[0..k-1]) with the first k items. For every subsequent item at 1-based position i > k, you draw a uniform random integer j in [1, i]. If j <= k, you overwrite reservoir[j - 1] with the new item; otherwise you discard it.

By induction, if every prior item had probability k / (i - 1) of being in the reservoir, the i-th item enters with probability k / i, and each existing item survives with probability (k / (i - 1)) * (1 - 1/i) = k / i. Every item seen so far holds the exact same k / i probability.

Concrete walkthrough

Suppose k = 3 and events A, B, C, D, E arrive one by one:

  1. Fill phase (i = 1, 2, 3): A, B, C fill slots [0, 1, 2]. Reservoir = [A, B, C]. Each has probability 3/3 = 1.0.
  2. Item D arrives (i = 4): Draw j in {1, 2, 3, 4}. Suppose j = 2 (<= 3). Replace slot 1 (B) with D. Reservoir = [A, D, C]. Probability of D entering was 3/4; probability A survived was 1 * (1 - 1/4) = 3/4.
  3. Item E arrives (i = 5): Draw j in {1, 2, 3, 4, 5}. Suppose j = 5 (> 3). Discard E. Reservoir stays [A, D, C].
  4. Optimize with Algorithm L: Instead of rolling j for items 6..1,000,000, Algorithm L samples a geometric jump skip = floor(log(rand()) / log(1 - W)) (updating W *= rand()^(1/k)), jumping directly to the next accepted item and cutting RNG calls from 1,000,000 to ~`21`.

Reservoir sampling dataflow: bounded O(k) memory holds an exact k/n uniform sample regardless of total stream size n.

Weighted and distributed extensions

Real telemetry pipelines rarely run on one core or treat all events equally:

  • Weighted sampling (Efraimidis-Spirakis): For each item with weight w_i > 0, draw u_i ~ Uniform(0, 1) and compute key k_i = u_i^(1 / w_i) (or log(u_i) / w_i to avoid underflow). Keep the k items with the largest keys in a min-heap of size k.
  • Distributed / MapReduce merge: Because priority keys k_i are independent of shard size, each worker maintains a local top-k min-heap and a coordinator simply merges those heaps into a global top-k min-heap—preserving exact global uniformity.

Failure modes and numerical pitfalls

Three subtle bugs commonly break production implementations:

  • Floating-point underflow in u^(1/w): When weights w are tiny (e.g., 0.001), u^(1000) underflows to 0.0. Fix: store log(u) / w instead, since log is strictly monotonic.
  • 64-bit counter overflow or PRNG period: In long-running streams, use uint64 for i and a 64-bit PRNG (PCG64/xoshiro256**)—32-bit rand() cannot sample uniformly once i > 2^31.
  • Windowless stagnation: Always pair reservoirs with tumbling/sliding window resets if the data distribution shifts over time.

Where it appears in production

You will find reservoir sampling embedded inside Apache Spark (takeSample), ClickHouse (quantile / groupSample), OpenTelemetry memory-bounded samplers, and PostgreSQL (ANALYZE statistics collection using Vitter's Algorithm Z/R to sample fixed-size row blocks for query planner histograms).

Practical checklist

  • Pick Algorithm L for n >> k: Save 99%+ of PRNG calls when sampling small k from millions of events.
  • Use log(u) / w for weighted streams: Prevent floating-point underflow and enable effortless distributed heap merging.
  • Use 64-bit PRNGs: Avoid 32-bit rand() modulo bias once stream counts exceed millions.
  • Bound window lifetimes: Reset or decay the reservoir per epoch if recent traffic matters more than last month's.
  • Verify uniformity with tests: Run a chi-squared goodness-of-fit test over 50k synthetic runs to catch off-by-one bugs.
03 / Engineering trade-offs

Weighing architectural decisions

Algorithm R vs. Algorithm L

Advantage: Algorithm R is ~10 lines of trivial code with zero floating-point math.

Drawback: Algorithm R invokes RNG n times; for n = 10^9 and k = 1,000, Algorithm L skips 99.99% of elements and is orders of magnitude faster.

Uniform reservoir vs. Time-decayed / Stratified reservoir

Advantage: Uniform sampling gives an exact unbiased view of the entire stream history.

Drawback: Old items linger in the reservoir during long-running streams, under-representing recent distribution shifts unless periodically reset or exponentially decayed.

Single-node reservoir vs. Distributed mergeable reservoirs

Advantage: Single-node sampling needs no coordination.

Drawback: Merging independent shards of size k naively biases toward lower-traffic shards unless you track shard counts n_m or use priority-key min-heaps.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Biased Distributed Merge

Concatenating or uniformly re-sampling k items from two shards with vastly different traffic (1M vs. 10k events) over-represents the quiet shard by 100x.

What helps: Assign each item a uniform random key `u in (0, 1)` on arrival (or `u^(1/w)` if weighted) and merge shards via a global top-k min-heap.

Stale History Domination

In an infinite daemon, after 10 billion events, new events have only a k / 10^10 chance of entering, freezing the sample.

What helps: Tumble the reservoir per time window (e.g., hourly epochs) or use exponentially weighted keys `u^(1/e^(lambda * t))`.

Off-by-One Indexing Bias

Using 0-based vs. 1-based bounds inconsistently (`rand(0, i)` vs `rand(0, i-1)`) skews selection probabilities for early items.

What helps: Write unit tests over 100k trials verifying chi-squared uniformity across all positions `0..n-1`.

Slow PRNG Bottleneck

Calling a cryptographic RNG (`crypto/rand` or `/dev/urandom`) per event in Algorithm R saturates CPU at high throughput.

What helps: Use a fast thread-local PRNG (xoshiro256** or PCG64) and switch to Algorithm L when `n >> k`.

05 / Practical checklist

Avoid these mistakes

  • Using `hash(id) % M < threshold` when you actually need an exact fixed count k—hash modulo produces variable-size outputs that blow memory budgets during spikes.
  • Forgetting that standard reservoir sampling destroys temporal order; if order matters, store `(arrival_seq, item)` and sort at readout.
  • Merging per-worker reservoirs without weighting by each worker's total seen count `n_worker`.
  • Using `random() % i` in C/Go/Java without care—modulo bias slightly skews large ranges; use unbiased integer range generators.
  • Applying uniform reservoir sampling to anomaly detection where 99.99% of events are normal.
