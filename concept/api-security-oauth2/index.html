THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Use mTLS to prove *who the calling machine is* at the transport layer, and short-lived OAuth2/JWT tokens to prove *what the user or client is authorized to do* at the application layer.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Bearer tokens alone are vulnerable to theft and replay—anyone holding a leaked JWT can call an API until it expires. Combining OAuth 2.0 Authorization Code + PKCE, asymmetric RS256/EdDSA JWTs (5–15 min TTL), and mTLS (RFC 8705 certificate-bound tokens) ensures stolen tokens are useless without the client's private key and eliminates shared static API secrets.

  • OAuth 2.0 is authorization, not authentication: use OpenID Connect (OIDC) id_token for user identity and OAuth2 access_token for API permissions (scope, aud).
  • Always use Authorization Code + PKCE (RFC 7636) for public clients (SPAs, mobile); the Implicit (response_type=token) and Resource Owner Password Credentials flows are deprecated in OAuth 2.1.
  • Stateless JWT validation checks iss, aud, exp, nbf, and the cryptographic signature against the Identity Provider's JWKS endpoint—no DB lookup per request.
  • mTLS (TLS 1.3) requires both server and client to present X.509 certificates during the handshake, authenticating the caller's machine identity before HTTP bytes are parsed.
  • Sender-constrained tokens (RFC 8705 cnf.x5t#S256) embed the SHA-256 thumbprint of the client's mTLS certificate inside the JWT, stopping bearer-token replay dead.

Good candidates

  • Exposing user-facing APIs to SPAs, mobile apps, or third-party integrations requiring fine-grained OAuth2 scopes and consent.
  • Securing B2B financial/healthcare APIs (e.g., Open Banking, FAPI 2.0) where tokens must be cryptographically bound to the caller's X.509 client certificate via mTLS.
  • Authenticating zero-trust microservice-to-microservice calls using workload identities (SPIFFE/SPIRE or Istio mTLS) plus propagated user JWTs.

Think twice

  • Simple internal scripts or single-tenant webhooks where HMAC-SHA256 request signing is simpler than standing up an OAuth2 Authorization Server.
  • Static public read-only APIs (e.g., weather feeds or public docs) where API keys for basic quota tracking suffice.
  • Environments where you need instant, sub-second global session revocation across all services without maintaining a token introspection or revocation cache.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA fintech partner calls POST /transfers using an OAuth2 access token obtained via client_credentials with an mTLS client certificate.

The idea

API security breaks down into two orthogonal questions: Who is the calling software/machine? and What is the user or client allowed to do? Mutual TLS (mTLS) answers the first at the transport layer using X.509 certificates during the TLS 1.3 handshake. OAuth 2.0 and signed JWTs answer the second at the application layer using scoped, short-lived tokens. Binding the two together (RFC 8705) ties an application token to a cryptographic transport identity so neither a stolen token nor an unauthorized host can succeed alone.

Concrete walkthrough

Trace a high-assurance B2B call from Partner Service to POST https://api.bank.io/v1/wires:

  1. Token Acquisition (mTLS + OAuth2): Partner Service opens a TLS 1.3 connection to auth.bank.io/oauth/token presenting its X.509 leaf certificate. Using grant_type=client_credentials, it requests scope=wires:write.
  2. Sender-Constrained Minting: Keycloak/Auth0 verifies the cert against the trusted CA, computes its SHA-256 thumbprint (x5t#S256), embeds it in the JWT cnf claim with a 5-minute exp, and signs it with ES256.
  3. API Call over mTLS: Partner Service dials api.bank.io over mTLS and sends Authorization: Bearer .
  4. Dual-Layer Verification: The API Gateway completes the mTLS handshake, fetches the public key matching the JWT kid from cached JWKS, validates iss, aud, exp, and confirms the live client cert's x5t#S256 matches jwt.cnf.x5t#S256 before forwarding the request over internal mesh mTLS.

Defense-in-depth combines mTLS transport identity with short-lived, certificate-bound OAuth2 JWTs.

OAuth 2.1 flows and token anatomy

A JWT consists of three base64url-encoded parts (header.payload.signature). The header declares alg (prefer EdDSA or ES256 over HS256) and kid for key rotation. The payload carries standard claims: iss (issuer), sub (subject), aud (target API URI), exp (expiration, 5–15 min), scope (space-delimited permissions), and optionally cnf for proof-of-possession.

For user-facing web and mobile apps, Authorization Code + PKCE is mandatory: the client generates a random code_verifier, sends its SHA-256 code_challenge to /authorize, and proves possession of the verifier at /oauth/token. This prevents authorization code interception attacks even without a client secret.

Failure modes

  1. Algorithm Confusion Attack: A library tricked into reading alg: HS256 uses the server's public RSA key as an HMAC secret, allowing anyone to forge valid tokens. Fix: hardcode an allowlist of asymmetric algorithms (["ES256", "RS256"]) in the verifier.
  2. Cross-Service Token Replay (Confused Deputy): Service A accepts a JWT whose aud is service-a, and an attacker replays that same token against Service B if Service B skips aud validation. Fix: enforce strict aud matching per service.
  3. PKI Expiry Cliff: Static 1-year mTLS certificates expire unnoticed on a weekend, dropping 100% of partner traffic. Fix: automate short-lived certs (24h–7d) with SPIRE or cert-manager and alert on cert age.
  4. Clock Skew Rejections: A 90-second NTP drift between the IdP and an API pod causes valid newly issued tokens to fail nbf or iat checks. Fix: allow a bounded 30–60s clock skew tolerance and run chrony.

Architecture patterns for modern teams

For browser SPAs, avoid storing OAuth2 tokens in localStorage where XSS can exfiltrate them; instead use a Backend-for-Frontend (BFF) that holds tokens server-side and issues HttpOnly; Secure; SameSite=Lax session cookies. For east-west microservice traffic, delegate workload mTLS to a service mesh (Istio or Cilium with SPIFFE IDs) so developers never manage PEM files in application containers, while keeping application-level RBAC/ABAC tied to the verified JWT claims.

Practical checklist

  • Enforce OAuth 2.1: use Authorization Code + PKCE for all user flows and client_credentials (with mTLS or private_key_jwt) for M2M.
  • Keep access tokens short-lived: set exp to 5–15 minutes and use rotating, single-use refresh tokens.
  • Validate all 5 JWT invariants: alg allowlist, signature via JWKS kid, iss, aud, and exp/nbf.
  • Bind high-value tokens: enable RFC 8705 cnf.x5t#S256 (mTLS) or DPoP for financial, admin, and PII endpoints.
  • Automate cert rotation: deploy cert-manager or SPIRE with overlapping trust bundles and test rotation in staging monthly.
03 / Engineering trade-offs

Weighing architectural decisions

Stateless JWT vs. Opaque Token + Introspection

Advantage: JWTs validate locally in <100 µs via cached JWKS with zero network hop to the auth server.

Drawback: Revoking a compromised JWT before its `exp` (e.g., 15 min) requires a distributed denylist or short TTLs.

mTLS Client Auth vs. `client_secret`

Advantage: Private keys never traverse the wire, preventing credential stuffing and secret leaks in logs.

Drawback: Requires automated PKI lifecycle management (cert-manager, SPIRE, or ACME) to avoid outages from expired certs.

Coarse Scopes vs. Fine-Grained Claims in JWT

Advantage: Embedding all permissions in the token avoids downstream authorization DB queries.

Drawback: Bloats HTTP `Authorization` headers beyond 4–8 KB, triggering `431 Request Header Fields Too Large`.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Expired mTLS Intermediate or Leaf Certificate

A missed certificate rotation breaks the TLS handshake across all B2B or service-to-service callers simultaneously, causing 100% outage.

What helps: Automate short-lived certs (24h–30d) via SPIRE or cert-manager, support dual-root CA overlap during rotation, and alert at 30% remaining TTL.

Missing `aud` or `alg` Validation in JWT Verifier

Accepting `alg: none`, symmetric HS256 with an RSA public key, or omitting `aud` lets an attacker forge tokens or replay tokens minted for another API.

What helps: Pin allowed asymmetric algorithms (`RS256`, `ES256`, `EdDSA`) explicitly in code and strictly assert `iss` and `aud` on every route.

JWKS Rotation Outage

IdP rotates its signing key (`kid`), but gateways with stale 24-hour JWKS caches reject all newly minted tokens with `401`.

What helps: Trigger an asynchronous, rate-limited JWKS refresh on unknown `kid` cache misses (e.g., max 1 refresh per 10s).

Token Leakage in Logs or URLs

Passing JWTs in query strings (`?access_token=...`) or logging full request headers exposes live credentials in proxy access logs and browser history.

What helps: Accept tokens strictly in `Authorization: Bearer` headers and redact `Authorization` and `Cookie` fields in all structured loggers.

05 / Practical checklist

Avoid these mistakes

  • Using `alg: HS256` with a shared secret across multiple untrusted microservices instead of asymmetric `RS256`/`EdDSA` keys.
  • Setting JWT lifetimes to 24+ hours without refresh token rotation, creating a huge window of exposure if a token is stolen.
  • Storing OAuth2 access tokens in browser `localStorage` instead of using the BFF pattern with `HttpOnly`, `Secure`, `SameSite=Lax` cookies.
  • Terminating mTLS at an edge load balancer and forwarding plain HTTP internally without passing a verified `X-Client-Cert` hash or re-originating mTLS.
  • Putting PII or sensitive roles inside unencrypted JWT payloads (base64url is encoding, not encryption—use JWE if payload confidentiality is needed).
