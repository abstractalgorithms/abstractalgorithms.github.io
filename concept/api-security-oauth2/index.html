OAuth2, JWT & Mutual TLS (mTLS) Security Architecture

Protect API endpoints and microservice communication using asymmetric cryptography, OAuth2 scopes, and mTLS identity.

Orientation & Intuition

API security uses OAuth2 authorization framework with cryptographically signed JSON Web Tokens (JWT) for stateless user verification, and mTLS for mutual identity verification between microservices.

Key takeaway Use mTLS for zero-trust service-to-service communication; use short-lived JWTs with RSA/ECDSA asymmetric signatures for client authorization.

Core Architecture & Trade-offs

Unprotected APIs expose sensitive customer data, permit token forgery, and allow unauthorized service spoofing.

Key Architecture Invariants

  • Asymmetric JWT Signing: Auth server signs JWT with Private Key; gateway verifies via public JWKS endpoint.
  • mTLS (Mutual TLS): Both client and server present X.509 TLS certificates to authenticate TCP connections.
  • Token Revocation: Use short TTLs (15 min) with refresh token rotation to minimize token compromise windows.

When to Use

  • Public mobile/web API authentication.
  • Zero-Trust microservice mesh IPC.
  • Third-party developer app authorization.

When NOT to Use

  • Monolithic single-process local function calls.

Deep Dive & Production Considerations

📖 OAuth2 Authorization Code Flow with PKCE & mTLS Zero-Trust Mesh

Modern distributed security divides identity into two distinct tiers: User-to-Service Authentication (delegated via OAuth 2.0 / OpenID Connect) and Service-to-Service Zero-Trust Communication (enforced via Mutual TLS).

🛡️ Why PKCE Is Required for Public Clients

Public clients (Single-Page Apps and Mobile native apps) cannot securely store a client_secret because decompilers or browser devtools expose plaintext code. Proof Key for Code Exchange (PKCE) prevents authorization code interception attacks:

  1. The client generates a high-entropy cryptographically random code_verifier (43–128 characters).
  2. The client calculates the code_challenge = BASE64URL(SHA256(code_verifier)) and sends it with the initial /authorize request.
  3. The Authorization Server stores the challenge and issues a temporary authorization code.
  4. When exchanging the code at /token, the client transmits the plaintext code_verifier. The server hashes it and verifies it matches the original challenge before issuing access and ID tokens.

🔒 Mutual TLS (mTLS) for East-West Microservice Traffic

Inside the microservice cluster, perimeter network firewalls are insufficient under a Zero-Trust architecture. Mutual TLS (mTLS) establishes bidirectional cryptographic identity:

  • Both the client service and server service present X.509 certificates during the TLS handshake.
  • An identity plane (like SPIFFE/SPIRE or Istio Citadel) issues short-lived certificates (e.g. 1–24 hours) tied to cryptographic workload IDs (spiffe://cluster.local/ns/prod/sa/order-service).
  • Eliminates man-in-the-middle packet sniffing and prevents unauthorized lateral network movement if a single container is compromised.
