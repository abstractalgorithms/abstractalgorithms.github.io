THE BIG IDEA / Key takeaway · CONCEPT GUIDE

A single enterprise-wide canonical data model breaks down across teams; explicit context maps protect each model's integrity with intentional translation boundaries.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

As organizations scale past 3–4 teams, sharing one monolithic Customer or Order schema creates tight coupling: a billing change breaks shipping, and every deployment requires cross-team coordination. Context mapping surfaces both technical dependencies and organizational power dynamics—showing where to build an Anti-Corruption Layer (ACL) to insulate your domain from messy legacy APIs versus where to publish a stable Open Host Service.

  • A Bounded Context is a linguistic and model boundary: Product in Catalog means rich media and SKU attributes, while Product in Warehouse means weight, bin location, and stock count.
  • Context Map relationships come in 9 canonical patterns—including Customer-Supplier, Conformist, Anti-Corruption Layer (ACL), Open Host Service (OHS), Published Language, Shared Kernel, and Separate Ways.
  • An Anti-Corruption Layer translates external schemas (e.g., legacy SOAP/XML or Stripe webhooks) into your domain's own types at the edge so external churn never leaks into core business rules.
  • Open Host Service (OHS) + Published Language (e.g., versioned OpenAPI, Protobuf, or AsyncAPI schemas) lets an upstream team serve many downstream consumers without bespoke per-team endpoints.
  • Shared Kernel (a shared library or database schema) requires synchronized releases between teams and should be restricted to small, stable core primitives.

Good candidates

  • Multiple engineering teams own distinct business capabilities (e.g., Checkout, Fulfillment, Billing) that use the same nouns (Order, Account) with different meanings.
  • Integrating a clean new core domain service with a brittle legacy monolith, ERP (SAP/NetSuite), or third-party payment gateway.
  • Decomposing a modular monolith into microservices where service boundaries and team ownership must align (Conway's Law).

Think twice

  • A small 1–2 team CRUD application where a single shared relational schema and unified domain model are faster to maintain.
  • Purely technical infrastructure splitting (e.g., separating a stateless auth proxy from a static asset CDN) with no competing business semantics.
  • Early-stage prototypes where domain boundaries are still shifting weekly and premature service splits would freeze wrong assumptions.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA retail platform's new dynamic Pricing service must read base costs and tax codes from a 15-year-old ERP that exposes cryptic 4-character status codes (STAT_X9) and mutable XML payloads.

The idea

Domain-Driven Design (DDD) Strategic Design recognizes that large software systems cannot maintain a single, unified object model. A Customer in Sales (lead score, pipeline stage) is fundamentally different from a Customer in Billing (tax ID, credit limit, payment method) or Shipping (delivery instructions, geo-coordinates). Forcing all three into one class creates a bloated, fragile model.

A Bounded Context defines the explicit perimeter within which a specific Ubiquitous Language and domain model apply. Context Mapping documents how multiple Bounded Contexts integrate—both technically (APIs, events, translators) and organizationally (upstream/downstream power).

Concrete walkthrough

Consider an e-commerce platform with three Bounded Contexts: Checkout (Core), Fulfillment (Supporting), and a Legacy ERP (Generic/External):

  1. Checkout -> Fulfillment (Open Host Service + Published Language): When a cart is paid, Checkout emits an OrderConfirmed.v2 Protobuf event to Kafka. Checkout does not know how warehouses pick or pack items; it publishes a stable, documented contract.
  2. Fulfillment consumes OrderConfirmed.v2: Fulfillment's Kafka consumer maps the published event into its own ShipmentRequest aggregate, discarding payment metadata it doesn't need.
  3. Fulfillment -> Legacy ERP (Anti-Corruption Layer): To reserve physical stock in the 20-year-old ERP, Fulfillment calls an internal ACL adapter. The ACL translates ShipmentRequest into the ERP's fixed-width ASCII/SOAP format, handles retry/idempotency, and maps cryptic ERP error codes (ERR-402) back to InsufficientWarehouseStock.

Context map showing Open Host Service / Published Language decoupled from a legacy system via an Anti-Corruption Layer.

Organizational dynamics & Conway's Law

Context mapping is as much about team communication as code. Customer-Supplier works when two teams share a backlog priority—the downstream team can negotiate new fields with the upstream team. Conformist applies when the upstream team (e.g., an external API like Stripe or a central identity provider) will not bend for you, and your domain semantics match theirs closely enough that translation isn't worth the cost.

Separate Ways is an underrated choice: if two contexts share only a minor utility (like PDF invoice rendering), duplicating 100 lines of code is far cheaper than maintaining a cross-team dependency.

Failure modes

The classic failure mode is semantic drift across contexts: Sales changes Account.status = 'ACTIVE' to include trial users, silently causing Billing to invoice free-trial accounts because Billing queried Sales' database directly.

Another failure mode is over-engineering ACLs everywhere: wrapping a clean, internal Customer-Supplier gRPC service in three layers of redundant DTO-to-DTO mappers adds boilerplate without protecting any meaningful invariant. Reserve full ACLs for boundary crossings where the external model is volatile, legacy, or semantically incompatible.

Modular monoliths before microservices

Bounded Contexts do not require separate microservices or network hops on day one. Tools like Spring Modulith (Java) or ArchUnit enforce package-level context boundaries inside a single deployable binary—blocking direct repository imports across contexts while allowing in-process domain events via an outbox. Once a context's scaling profile or team cadence diverges, extracting it to a standalone service is mechanical because the Published Language and ACL boundaries already exist.

Practical checklist

  • Map every cross-team integration explicitly as ACL, OHS/Published Language, Customer-Supplier, Conformist, or Shared Kernel.
  • Prohibit cross-context database joins; each Bounded Context owns its tables and schema migrations.
  • Enforce schema compatibility (BACKWARD / FULL) in a Schema Registry for all Published Language events.
  • Place Anti-Corruption Layers at the infrastructure edge (ports & adapters), never inside core domain entities.
  • Use ArchUnit or module boundaries in a modular monolith before paying the operational tax of distributed microservices.
03 / Engineering trade-offs

Weighing architectural decisions

Anti-Corruption Layer vs. Conformist

Advantage: ACL protects your core domain model from external schema drift and ugly legacy semantics.

Drawback: Adds translation boilerplate, extra mapping tests, and maintenance whenever the upstream contract evolves.

Shared Kernel vs. Separate Ways

Advantage: Shared Kernel avoids duplicating common validation or money/currency logic across two closely aligned teams.

Drawback: Couples CI/CD pipelines—a breaking change in the shared package blocks both teams until coordinated.

Published Language vs. Point-to-Point APIs

Advantage: A documented schema (Protobuf/Avro/JSON Schema) scales cleanly to N consumers with automated compatibility checks.

Drawback: Requires governance (schema registry, deprecation SLAs) to prevent breaking downstream consumers.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Big Ball of Mud Shared Database

Multiple bounded contexts read and write the same database tables directly, bypassing domain invariants and making schema migrations impossible without multi-team freezes.

What helps: Give each bounded context its own schema/database and enforce cross-context communication strictly through OHS APIs or domain events.

Leaky upstream model (unintended Conformist)

A core domain service imports a third-party vendor's DTOs (e.g., Stripe or Salesforce structs) directly into its domain entities, making vendor replacement a full rewrite.

What helps: Wrap third-party SDKs behind an explicit ACL interface that returns domain-native types.

Entity-service microservice explosion

Splitting every noun (`UserService`, `AddressService`, `OrderItemService`) into separate contexts creates distributed joins and chatty RPC chains.

What helps: Draw bounded contexts around cohesive business capabilities and ubiquitous language boundaries, not individual database tables.

Unversioned Published Language

Upstream teams rename fields or change enum semantics in Kafka events without schema registry checks, silently breaking downstream projections.

What helps: Enforce `BACKWARD` or `FULL` compatibility in Confluent Schema Registry / Buf and maintain dual-versioned topics during migrations.

05 / Practical checklist

Avoid these mistakes

  • Attempting to design a single canonical `Customer` object shared across Sales, Support, Shipping, and Billing.
  • Using `Shared Kernel` for fast-moving business entities instead of limiting it to stable primitives like `Money` or `CountryCode`.
  • Building an Anti-Corruption Layer for an upstream service you actually control and could instead collaborate on via Customer-Supplier.
  • Ignoring organizational team topology—drawing context boundaries that cut across a single team or force two competing teams to co-own one codebase.
  • Treating Context Mapping as a one-time architecture diagram rather than updating it when teams reorganize or new integrations land.
