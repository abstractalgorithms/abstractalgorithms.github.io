RBAC Policy
Design.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Model roles around stable job functions—not ad-hoc org charts—enforce deny-by-default evaluation with Separation of Duties (SoD), and shift fine-grained resource-level checks to ABAC/ReBAC before RBAC explodes into thousands of bespoke roles.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Direct user-to-permission ACLs become unmanageable past a few dozen employees: onboarding, role changes, and offboarding turn into error-prone manual diffs that leave orphaned admin rights behind. Clean RBAC turns access reviews and SOC 2 / ISO 27001 audits into deterministic queries.

  • NIST RBAC defines four tiers: Core (User-Role-Permission), Hierarchical (role inheritance), Static SoD (mutually exclusive role assignment), and Dynamic SoD (mutually exclusive active session roles).
  • Deny-by-default evaluation: a request is rejected unless an explicit allow matches (subject_roles, action, resource_scope) and no explicit deny overrides it.
  • Keep roles scoped to tenants/namespaces (e.g., Kubernetes Role + RoleBinding per namespace rather than ClusterRoleBinding) to contain blast radius.
  • Avoid stuffing hundreds of fine-grained permissions into JWTs; tokens hit 4-8 KB HTTP header limits and cannot be revoked immediately on role downgrade.
  • Decouple policy decisions from application code using a Policy Decision Point (PDP) like Open Policy Agent (OPA) or AWS Cedar.

Good candidates

  • Enterprise SaaS, internal platforms, and infrastructure control planes (AWS IAM, Kubernetes RBAC) with clear functional personas like Viewer, Editor, BillingAdmin, and Operator.
  • Regulated environments requiring provable Separation of Duties (SoD)—for example, preventing the same user from both creating and approving a wire transfer.
  • Coarse-to-medium granularity authorization where permissions depend on who the principal is and what action they perform on a resource type.

Think twice

  • Consumer sharing or document collaboration (e.g., Google Drive 'shared with Alice, inherited by folder')—use Relationship-Based Access Control (ReBAC / Zanzibar).
  • Dynamic contextual rules like 'allow access only from corporate VPN between 09:00-17:00 for resources tagged EU-West'—layer ABAC (e.g., OPA/Cedar) alongside RBAC.
  • Micro-permissions tied to individual row IDs across millions of records, which causes catastrophic role explosion if modeled as roles.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA 40-team platform runs shared EKS clusters. Initially, developers were granted cluster-admin to debug pods, leading to accidental cross-team secret reads.

The idea

RBAC introduces an indirection layer—the Role—between Principals (users, service accounts) and Permissions (action + resource_type). Instead of maintaining U×PU \times PU×P direct edges, administrators maintain U→RU → RU→R assignments and R→PR → PR→P definitions, reducing management complexity from O(U⋅P)O(U \cdot P)O(U⋅P) to O(U+P)O(U + P)O(U+P) when roles represent stable organizational functions.

A production RBAC engine enforces three invariants: deny-by-default (no matching allow means reject), explicit deny wins (an explicit deny or Separation-of-Duties rule overrides any allow), and scoped bindings (a role grants power only within a bounded tenant, project, or namespace).

Concrete walkthrough

Consider a multi-tenant CI/CD platform evaluating POST /tenants/acme/pipelines/deploy from user alice:

  1. Authentication (PEP): The API gateway validates Alice's OIDC JWT, extracting sub = user:alice and tenant = acme (no raw permissions are trusted from the client).
  2. Authorization query: The service's Policy Enforcement Point (PEP) sends {subject: "user:alice", action: "pipeline:deploy", resource: {type: "pipeline", tenant: "acme", env: "prod"}} to a co-located OPA sidecar (PDP).
  3. Role resolution: OPA looks up Alice's scoped bindings in acme: [role:deployer, role:viewer].
  4. Constraint & SoD check: OPA verifies role:deployer includes pipeline:deploy, confirms no explicit deny applies, and checks the Dynamic SoD rule (alice is not the pr_author on this commit).
  5. Decision & audit: OPA returns {allow: true, matched_role: "deployer", policy_rev: "v42"} in < 0.5 ms and ships an immutable decision log to SIEM.

Separating the Policy Enforcement Point (PEP) from the Policy Decision Point (PDP) keeps authorization logic consistent, auditable, and fast.

Evolving beyond pure RBAC (ABAC & ReBAC)

Pure RBAC struggles when authorization depends on resource attributes (env == prod, classification == pii) or object-graph relationships (document -> parent_folder -> team).

  • RBAC + ABAC hybrid: Keep 5-10 clean functional roles (Viewer, Operator, Admin), and attach attribute conditions to the binding or policy (e.g., role == Operator && resource.region == user.region). AWS IAM and Cedar excel at this.
  • RBAC + ReBAC: When permissions cascade through hierarchies (orgs, folders, shared links), pair top-level RBAC roles with a Zanzibar-style relationship graph (e.g., SpiceDB / OpenFGA) rather than minting per-folder roles.

Failure modes

  • Role explosion: Encoding tenant IDs, regions, or single-feature toggles as distinct roles creates thousands of roles that nobody understands.
  • Missing tenant-scope binding: Checking hasRole('Admin') globally without binding the role to tenant_id enables trivial cross-tenant privilege escalation.
  • Privilege creep: Users accumulate roles across internal transfers; without automated SCIM deprovisioning, dormant admin rights persist.
  • JWT permission bloat: Packing all permissions into access tokens breaks 8 KB HTTP header limits and delays revocation until token expiry.

Production patterns & governance

  • Policy-as-Code with CI tests: Store role definitions and Rego/Cedar policies in Git; block merges unless negative tests (deny cases, SoD violations, cross-tenant isolation) pass.
  • Break-glass emergency roles: Provision time-bound (e.g., 1-hour TTL) elevated roles that require ticket justification and page security on activation.
  • Shadow policy rollout: Run new policies in audit mode alongside active rules to verify zero unintended DENY spikes on production traffic before flipping to enforce.

Practical checklist

  • Enforce deny-by-default and explicit-deny-overrides-allow across all external and internal endpoints.
  • Bind every role assignment to an explicit scope (tenant_id, namespace, or project_id).
  • Keep JWTs thin (identity + session); resolve fine-grained roles via a local PDP sidecar or short-TTL cache.
  • Encode Static and Dynamic Separation of Duties (SoD) for high-risk actions (deploy, billing, key rotation).
  • Integrate SCIM/IdP lifecycle sync and log every allow/deny decision with policy_version.
03 / Engineering trade-offs

Weighing architectural decisions

Coarse Roles vs. Fine-Grained Roles

Advantage: Coarse roles (4-8 per product) are easy to understand, assign, and audit.

Drawback: Can over-grant privileges when a user only needs one specific action; splitting into micro-roles causes role explosion.

Stateless JWT Claims vs. Stateful PDP Lookup

Advantage: Embedding roles in JWTs avoids a network call on every API request.

Drawback: Role revocations lag until token expiry (often 15-60 min) and large role lists bloat HTTP headers past 8 KB.

Flat Roles vs. Role Hierarchies

Advantage: Hierarchical inheritance (`Admin > Editor > Viewer`) eliminates duplicate permission lists.

Drawback: Deep inheritance chains obscure effective permissions and can accidentally grant sensitive actions (e.g., `billing:delete`) via inheritance.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Role Explosion

Teams create bespoke roles for every edge-case combination (`ProjectA_ReadOnly_NoExport_EU`), ballooning to thousands of un-auditable roles.

What helps: Cap base roles to core job functions and express resource/environment filters via ABAC attributes or scoped bindings.

Privilege Creep & Stale Bindings

Employees transfer teams and accumulate new roles without losing old ones, leaving long-tenured accounts with near-admin access.

What helps: Automate role lifecycle via SCIM/IdP group sync and enforce quarterly access recertification with auto-expiry.

Confused Deputy / Cross-Tenant IDOR

A service checks that `user` has role `Editor`, but forgets to verify that `resource.tenant_id == user.tenant_id`, allowing cross-tenant tampering.

What helps: Require tenant/resource scope as a mandatory parameter in every PDP authorization query (`allow(subject, action, tenant_id, resource)`).

Stale Permission Cache After Revocation

An offboarded or demoted user retains access for hours because role memberships are cached in long-lived JWTs or local memory.

What helps: Keep access token TTLs short (5-15 min), store only `user_id`/`session_id` in JWTs, and push revocation events to PDP caches.

05 / Practical checklist

Avoid these mistakes

  • Mixing authentication (who you are) with authorization (what you can do) by trusting client-supplied role headers.
  • Using `ClusterRole` or wildcard `*:*` permissions in production workloads because scoped rules felt tedious during prototyping.
  • Implementing `allow`-only logic without an explicit `deny` precedence rule for emergency lockouts or SoD constraints.
  • Failing to log both `ALLOW` and `DENY` decisions with `subject`, `role`, `action`, `resource`, and `policy_version` for forensic audits.
  • Checking RBAC only at the API gateway while leaving internal gRPC/GraphQL endpoints unguarded against lateral calls.
