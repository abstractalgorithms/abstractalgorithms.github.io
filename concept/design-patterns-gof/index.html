GoF Design Patterns: Strategy,
Decorator, Factory & Observer.

The Gang of Four (GoF) patterns—especially Strategy, Decorator, Factory, and Observer—provide battle-tested structural templates for swapping algorithms, layering cross-cutting behavior, encapsulating object creation, and decoupling event producers from consumers.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Reach for patterns to isolate a concrete axis of change (varying pricing rules, composable I/O streams, multi-channel alerts), never as preemptive ceremony around static code.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Without these four patterns, teams either copy-paste if/else chains across every billing and routing module or hardcode cross-cutting concerns (retries, metrics, auth) directly into business classes—making every new feature a risky edit to core code.

  • Strategy encapsulates a family of algorithms behind a shared interface so the host context delegates work without branching on type.
  • Decorator wraps an object implementing the same interface (BufferedInputStream(GZIPInputStream(FileInputStream))), enabling O(N) composable wrappers instead of O(2^N) subclasses.
  • Factory Method / Abstract Factory centralizes instantiation logic, hiding concrete classes, validation, and object reuse behind a clean creation boundary.
  • Observer defines a one-to-many publish-subscribe contract inside a process so state changes notify registered listeners without the subject knowing their concrete types.
  • All four patterns favor object composition over deep inheritance hierarchies, keeping classes small and open for extension.

Good candidates

  • Strategy: Multiple interchangeable algorithms exist for one task (e.g., Stripe vs. UPI vs. NetBanking fee calculation, or BM25 vs. vector reranking) selected at runtime.
  • Decorator: You need to dynamically stack orthogonal behaviors (compression, buffering, rate limiting, circuit breaking) around a core interface without subclass explosion.
  • Factory / Observer: Creation involves complex conditional setup or resource pooling (Factory), or one domain event must fan out to independent downstream listeners without coupling (Observer).

Think twice

  • A simple if/else or switch has only 2 stable branches that rarely change—creating 4 interface files adds indirection for zero gain.
  • Modern language features already solve the problem cleanly: Python first-class functions/lambdas or Java Function often replace single-method Strategy classes.
  • Distributed cross-service messaging where reliable delivery, retries, and backpressure are required—use Kafka/SQS rather than an in-process Observer list.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA Java microservice calls external partner APIs and needs configurable timeouts, exponential-backoff retries, Prometheus latency metrics, and bearer-token injection.

The idea

The 1994 Design Patterns (Gang of Four) catalog named recurring object-oriented solutions to change management. Rather than hardcoding how an operation runs, what concrete class is built, or who reacts to state changes, these four core patterns introduce polymorphic seams: Factory isolates creation, Strategy isolates algorithmic variation, Decorator isolates composable cross-cutting layers, and Observer isolates event fan-out. Used together, they keep core domain workflows stable while surrounding requirements evolve.

Concrete walkthrough

Consider an order-notification pipeline in Java:

  1. Factory: NotifierFactory.forChannel(Channel.WHATSAPP) inspects config and returns a WhatsAppNotifier without AlertService importing Twilio/Meta SDKs.
  2. Decorator: The factory wraps the raw sender: new RateLimitedNotifier(new RetryingNotifier(new WhatsAppNotifier(client), 3), bucket). Each layer implements Notifier.send(Message).
  3. Strategy: MessageFormatter is a Strategy (CompactSmsFormatter vs. RichWhatsAppFormatter) injected into the notifier to render payloads per channel.
  4. Observer: When PaymentService marks an invoice PAID, it publishes InvoicePaidEvent to registered EventListener observers (AlertService, AuditLogListener, AnalyticsListener), keeping PaymentService completely unaware of notifications.

Observer decouples the payment trigger, Factory assembles the channel stack, Decorator adds resilience, and Strategy formats the payload.

Modern language idioms vs. classic GoF

Classic GoF was written in 1994 for C++ and Smalltalk, where functions were not first-class values. Today:

  • Strategy: In Python, a dict[str, Callable[[Order], Decimal]] or Protocol replaces 5 boilerplate subclasses. In Java 21, sealed interface + switch pattern matching handles closed algorithm sets concisely, while Function covers single-method strategies.
  • Decorator: Python's @retry(max_attempts=3) syntax is built-in function decoration, whereas Java still uses explicit interface wrappers (FilterInputStream) or Spring AOP.
  • Factory: Static factory methods (List.of(), Duration.ofSeconds()) often replace full AbstractFactory hierarchies unless families of related products must vary together.

Failure modes

  • Infinite Notification Cycles (Observer): Listener A updates Property X, which triggers Listener B, which updates Property Y, which triggers Listener A. Guard with idempotency checks (if (newVal.equals(oldVal)) return;).
  • Opaque Debugging in Deep Decorator Chains: A 7-layer decorator stack produces 40-frame stack traces and hides which layer swallowed an exception. Keep stacks <=3–4 layers and log layer names on failure.
  • Factory Switch-Statement Rot: A central switch (type) factory grows to 300 lines and violates Open/Closed. Use a self-registering map (Map> or Spring List injection).
  • Stateful Strategy Race Conditions: Storing per-request fields on a singleton Strategy bean causes cross-request data corruption under concurrency.

Combining patterns cleanly

Patterns rarely live alone—they compose naturally when each owns one boundary. A Factory is the ideal place to enforce Decorator ordering so callers never accidentally swap retry and circuit-breaker layers. Similarly, Strategy objects should remain stateless so a Factory can safely cache and reuse them as flyweights. When Observer notifications need guaranteed delivery across restarts, replace the in-memory listener list with the Transactional Outbox pattern backed by Kafka or SQS.

Practical checklist

  • Verify at least 2–3 concrete variations exist before introducing a Strategy or Factory.
  • Keep Strategy implementations stateless so they are safe as singletons.
  • Enclose Decorator assembly inside a Builder or Factory to guarantee correct layer ordering.
  • Always provide an unsubscribe() / AutoCloseable handle for every Observer registration.
  • Prefer language-native lambdas/functions over single-method Strategy boilerplate where idiomatic.
03 / Engineering trade-offs

Weighing architectural decisions

Extensibility vs. Indirection & Readability

Advantage: New behaviors (e.g., a new Strategy or Decorator) are added as isolated files with zero risk of breaking existing branches.

Drawback: Jumping through 4 layers of interfaces and wrappers makes stack traces deeper and IDE 'Go to Implementation' harder for newcomers.

In-Process Observer vs. Explicit Orchestration / Message Queue

Advantage: Zero infrastructure overhead and instant decoupling for UI events or local cache invalidation.

Drawback: Execution order is often implicit, slow observers block the publisher thread unless async, and exceptions in one listener can abort others.

Decorator Stack vs. Inheritance Hierarchy

Advantage: Prevents combinatorial class explosion (`EncryptedCompressedBufferedStream`) by composing wrappers at runtime.

Drawback: Wrapper ordering bugs (e.g., compressing *after* encrypting destroys compression ratio) are not caught by the type system.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Lapsed Listener Memory Leak (Observer)

Short-lived UI components or per-request handlers subscribe to a long-lived singleton Subject and never unsubscribe, pinning them in heap until OOM.

What helps: Use explicit `AutoCloseable` subscription tokens, `WeakReference` listener registries, or structured lifecycle hooks that unregister on teardown.

Decorator Ordering Bug

Wrapping `GzipDecorator(EncryptDecorator(stream))` encrypts data first (turning it into high-entropy noise), making Gzip inflate size instead of shrinking it.

What helps: Expose a Builder or Factory that enforces canonical wrapper ordering (`Encrypt -> Compress -> Buffer`) rather than letting callers stack decorators arbitrarily.

Pattern Over-Engineering (Strategy for 1 Implementation)

Teams wrap every helper in `AbstractXFactory` + `XStrategy` + `DefaultXStrategyImpl` 'just in case', tripling file count.

What helps: Follow the Rule of Three: write direct code first, and extract Strategy/Factory only when a second or third genuine variant arrives.

Synchronous Observer Cascade Failure

A slow analytics listener in an in-memory `OrderCreated` Observer loop takes 3 seconds per event, stalling checkout latency.

What helps: Isolate non-critical observers onto bounded async executors with timeouts and exception boundaries, or move them to an outbox/Kafka topic.

05 / Practical checklist

Avoid these mistakes

  • Confusing Decorator (same interface, adds behavior) with Adapter (converts incompatible interface A to B) or Proxy (controls access/lazy-loading).
  • Using heavy Strategy classes in Python or Java 17+ when a `dict[str, Callable]` or `Enum` with a lambda/method is cleaner.
  • Allowing a Factory to return `null` on unknown keys instead of throwing an explicit `IllegalArgumentException` or returning an `Optional`.
  • Mutating shared state inside a singleton Strategy instance, causing race conditions across concurrent requests.
  • Letting Observers mutate the Subject during notification, triggering infinite feedback loops.
