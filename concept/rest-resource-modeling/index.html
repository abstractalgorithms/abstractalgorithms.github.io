REST Resource
Modeling.

REST resource modeling organizes an API around stable, addressable nouns (resources) manipulated through standard HTTP verbs, status codes, and concurrency/idempotency headers rather than RPC-style action verbs.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Model state transitions and workflows as explicit sub-resources (like `/orders/{id}/cancellations`) with `Idempotency-Key` and `ETag` headers so clients get safe retries, caching, and predictable HTTP semantics.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

APIs that tunnel RPC verbs through POST /doAction endpoints lose HTTP's built-in caching, idempotency, partial-failure semantics, and tooling ecosystem. Clean resource modeling makes APIs self-consistent, safely retryable over flaky networks, and resilient to concurrent edits across years of evolution.

  • Identify core nouns as plural collection URIs (/v1/orders, /v1/orders/{orderId}) and avoid verbs in paths (/getOrder, /cancelOrder).
  • Model complex actions or workflows as resources themselves: e.g., POST /v1/orders/{id}/cancellations or POST /v1/exports returning 202 Accepted with a Location to /v1/exports/{jobId}.
  • Honor HTTP method semantics strictly: GET is safe and idempotent; PUT/DELETE are idempotent; POST is non-idempotent unless paired with an Idempotency-Key header.
  • Use ETag + If-Match for optimistic concurrency control, returning 412 Precondition Failed instead of silently overwriting a concurrent update.
  • Standardize error payloads using RFC 9457 (application/problem+json with type, title, status, detail, instance) and cursor pagination (next_cursor) for large collections.

Good candidates

  • Building public, partner, or long-lived internal HTTP APIs where browser/CDN caching, OpenAPI 3.1 tooling, and intuitive URLs matter.
  • Entities have clear lifecycles, relationships, and state transitions that benefit from standard CRUD + sub-resource modeling.
  • Clients operate over unreliable mobile or cross-region networks and need safe retries (Idempotency-Key) and optimistic concurrency (ETag / If-Match).

Think twice

  • Ultra-low-latency internal microservice-to-microservice calls requiring binary framing and bidirectional streaming—prefer gRPC with Protobuf.
  • Client UIs need arbitrary, deeply nested graph queries across dozens of entities in a single round-trip—GraphQL often fits better.
  • Purely event-driven, fire-and-forget ingestion pipelines where message brokers (Kafka/PubSub) outperform synchronous HTTP.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA mobile banking client submits a bank transfer over spotty 4G and times out before receiving the HTTP response.

The idea

REST resource modeling treats an API as a navigable graph of resources (nouns) rather than a catalog of remote procedure calls (verbs). Every entity or workflow gets a canonical URI (/v1/invoices/{invoiceId}), and clients interact with it using HTTP's uniform interface (GET, POST, PUT, PATCH, DELETE).

When an operation feels like an action—such as canceling an order or exporting a report—you reify the action into a noun: POST /v1/orders/{id}/cancellations or POST /v1/exports. That single shift gives the action its own ID, audit trail, status (pending, completed, failed), and polling URI (Location: /v1/exports/{exportId}).

Concrete walkthrough

Consider modeling an asynchronous refund workflow on an e-commerce API:

  1. Client submits request: Sends POST /v1/orders/ord_91f/refunds with Idempotency-Key: 8b2e... and JSON body {"amount_cents": 4500, "reason": "damaged_item"}.
  2. Idempotency & validation: Gateway/handler checks the idempotency store. If 8b2e... was already processed with the same payload hash, it replays the saved response; if the payload differs, it returns 422 Unprocessable Content.
  3. Async acceptance: Because settling with the card network takes 2–5 seconds, the API persists the refund record in status=pending and returns 202 Accepted with Location: /v1/refunds/ref_77a and Retry-After: 2.
  4. Status polling: Client polls GET /v1/refunds/ref_77a and receives 200 OK with ETag: "v2" once status=succeeded.
  5. Safe concurrency: Any later PATCH /v1/refunds/ref_77a (e.g., attaching an internal note) must pass If-Match: "v2".

REST resource lifecycle: edge validation, atomic idempotency/ETag checks, and standardized HTTP status and Location responses.

Nouns, sub-resources, and async operations

Three modeling rules keep large REST APIs clean as they grow from 5 to 200 endpoints:

  • Shallow nesting (max 2 levels): Use /v1/projects/{id}/issues for creation/listing scoped to a project, but expose /v1/issues/{issueId} at top level for direct reads and updates.
  • Reified workflows: Turn multi-step or irreversible actions into sub-resource nouns (/cancellations, /deployments, /verifications) so they can carry timestamps, actor IDs, and failure reasons.
  • Long-running operations: Any mutation exceeding ~1–2 seconds should return 202 Accepted with a Location: /v1/operations/{opId} rather than holding an HTTP connection open until gateway timeout.

Failure modes and API drift

REST APIs degrade in production through three predictable failure modes:

  • Idempotency key mismatch: A client reuses the same Idempotency-Key with a different request body. Always hash the canonical payload and reject mismatches with 422.
  • N+1 chatty endpoints: Over-normalized resources force mobile clients to make 20 sequential GET calls to render one screen. Solve this with selective field expansion (?include=customer) or compound view resources, not by abandoning REST.
  • Silent breaking changes: Changing a field type or making an optional field required without bumping /v2/ or adding a deprecation header (Sunset).

Pagination, rate limiting, and RFC 9457 errors

Standardize cross-cutting envelopes across every endpoint: use keyset/cursor pagination (?limit=50&cursor=eyJpZCI6...) returning {"data": [...], "next_cursor": "..."}, emit 429 Too Many Requests with Retry-After and X-RateLimit-Remaining headers, and return RFC 9457 Problem Details (application/problem+json) with machine-readable type URIs and trace_id extensions so clients can handle errors programmatically.

Practical checklist

  • Audit every URI for verbs: Replace action verbs with plural nouns or reified workflow sub-resources.
  • Enforce Idempotency-Key on POST: Store idempotency records atomically with the domain write (24-hour TTL minimum).
  • Return ETag and honor If-Match: Protect all mutable resources against lost-update race conditions.
  • Default to cursor pagination: Cap limit (e.g., max 200) and never return unbounded arrays.
  • Contract-test with OpenAPI 3.1: Run automated spectral/breaking-change checks in CI on every API PR.
03 / Engineering trade-offs

Weighing architectural decisions

Deeply nested URIs vs. Flat top-level collections

Advantage: Nesting (`/orgs/{id}/projects/{id}/tasks`) clearly expresses ownership and parent scoping.

Drawback: Nesting beyond 2 levels creates brittle, verbose URLs if a child resource is ever accessed or moved independently.

PUT (full replacement) vs. PATCH (partial update)

Advantage: PATCH (JSON Merge Patch RFC 7396) saves bandwidth and avoids requiring clients to echo every read-only or unknown field.

Drawback: PATCH has trickier null-vs-omitted semantics and requires careful validation for required invariants.

Offset pagination vs. Cursor pagination

Advantage: Offset (`?page=3&limit=50`) allows jumping directly to arbitrary page numbers.

Drawback: Offset drifts (duplicates/skips rows) under concurrent inserts and degrades to `O(offset)` scans in SQL; cursor pagination stays `O(1)` via indexed seek.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Lost Update Race Condition

Two clients read a resource, modify different fields, and `PUT`/`PATCH` without `If-Match`, silently overwriting each other's changes.

What helps: Return strong `ETag` headers on `GET` and enforce `If-Match` on all state-mutating `PUT`/`PATCH`/`DELETE` requests.

Duplicate Side Effects on Retry

A client retries a `POST /v1/orders` request after a 504 gateway timeout, creating duplicate orders or charges.

What helps: Require `Idempotency-Key` on non-idempotent `POST` endpoints, storing `(key, request_hash, response)` atomically in the same DB transaction.

Unbounded Collection Responses

`GET /v1/events` returns 500,000 rows in one JSON payload, causing gateway OOMs and 30-second timeouts.

What helps: Enforce server-side default and max `limit` (e.g., default 50, max 200) and return `next_cursor` links.

Leaky 500s and Non-Standard Errors

Returning `200 OK` with `{"error": "..."}` or raw SQL stack traces breaks HTTP client libraries and leaks internals.

What helps: Use exact 4xx/5xx status codes (`400`, `404`, `409`, `422`, `429` with `Retry-After`) and RFC 9457 `application/problem+json` bodies.

05 / Practical checklist

Avoid these mistakes

  • Putting verbs in URLs (`/v1/createUser`, `/v1/orders/123/approve`) instead of nouns (`/v1/users`, `POST /v1/orders/123/approvals`).
  • Using `GET` for state-changing operations (e.g., `/unsubscribe?token=...`), which link-prefetchers and bots trigger accidentally.
  • Returning `200 OK` on synchronous creation instead of `201 Created` with a `Location` header.
  • Exposing sequential auto-incrementing database IDs (`1, 2, 3`) instead of opaque UUIDv7/ULIDs, enabling enumeration attacks.
  • Breaking clients by renaming JSON fields or removing enum values without versioning or additive deprecation windows.
