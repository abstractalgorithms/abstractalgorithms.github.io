Singleflight Request Coalescing:
Eliminating Thundering Herds.

Singleflight maintains an in-flight map of active keys so that concurrent callers for the same key await a single leader execution instead of stampeding the origin.

The idea to keep with you

When nodes partition or reboot past retry windows, by coalescing duplicate in-flight work behind a shared future/channel, Singleflight turns 10,000 concurrent cache misses into 1 origin query—provided you guard against shared-error amplification and context cancellation.

TL;DR30-second simplified summary
▾

A SingleflightGroup coordinates concurrent callers by key. The leader inserts a Call object, runs the origin fetch, removes the key in a finally block, and wakes all followers.

Production implementations bound follower wait times, isolate leader cancellations, and include tenant/auth dimensions in the key.

Distributed & Application Caching
Caching keeps a reusable copy of data so an application can avoid repeating a database query, calculation, or network call. It can make responses faster and reduce database load. The trade-off: the copy may be out of date.
Consistent Hashing & Virtual Nodes
Consistent hashing assigns data keys to servers in a way that limits how many keys move when servers are added or removed. This helps avoid widespread cache misses and sudden load on databases.

STAGE 01 · THE PROBLEMfoundation

Why Hot-Key Expiry Triggers Origin Collapse.

Why this matters: Prevent 2,000+ concurrent cache misses on a hot key from hitting PostgreSQL simultaneously.

Think of Why Hot-Key Expiry Triggers Origin Collapse as the intuition layer for Singleflight Request Coalescing: Eliminating Thundering Herds: Prevent 2,000+ concurrent cache misses on a hot key from hitting PostgreSQL simultaneously.

Suppose a hot key receives 50,000 QPS and takes 40 ms to recompute from PostgreSQL. The moment its Redis TTL expires, ~2,000 concurrent requests miss Redis within that 40 ms window and all 2,000 query PostgreSQL simultaneously, exhausting connection pools and causing cascading timeouts.

STAGE 01 · THE PROBLEM

Why Hot-Key Expiry Triggers Origin Collapse

1.Amplification Math: At 50,000 QPS and a 40 ms DB query, 2,000 requests arrive during the miss window.

2.Leader-Follower Split: Only the first caller executes the origin query; the remaining 1,999 await its shared promise.

3.Zero Extra Latency: Followers receive the exact result as soon as the single leader completes.

Singleflight collapses 2,000 concurrent cache misses into 1 origin query and fans out the result to all waiting callers.

02
STAGE 02 · CORE MECHANISMfoundation

Leader Election & Follower Fan-Out via In-Flight Map.

Why this matters: Coordinate in-flight callers via a mutex-guarded map without holding the lock across slow network I/O.

A SingleflightGroup holds mu (a lightweight mutex) and calls: map[key]*Call. Callers acquire mu only long enough to check/insert into calls (nanoseconds), never across the slow network I/O.

If key exists in calls, the caller increments dups, releases mu, and awaits call.done. Otherwise, it inserts a new Call, releases mu, runs fn(), deletes key from calls under mu, and signals call.done.

STAGE 02 · CORE MECHANISM

Leader Election & Follower Fan-Out via In-Flight Map

1.Never Lock Across I/O: The mutex protects only the in-memory map lookup (~50 ns), never the 40 ms database call.

2.Exception Safety: Wrap leader execution in try/finally so the key is always removed even if fn() panics.

3.Shared Future/Channel: Closing a Go channel or resolving a Future wakes all waiting goroutines/threads at once.

Releasing the map mutex before running fn() lets thousands of keys coalesce concurrently without lock contention.

STAGE 03 · REFERENCE IMPLEMENTATIONintermediate

Implementing Singleflight with Detached Contexts & Error Isolation.

Why this matters: Detach the leader's context from individual caller cancellations so one client abort doesn't fail 500 followers.

Detach the leader's upstream timeout from individual caller cancellations so one impatient client cannot abort 500 waiting followers. Always wrap fn() in try/finally so the in-flight entry is cleaned up even on exception.

import threading
from typing import Any, Callable

class _Call:
    def __init__(self) -> None:
        self.event = threading.Event()
        self.val: Any = None
        self.err: Exception | None = None

class SingleflightGroup:
    def __init__(self) -> None:
        self._mu = threading.Lock()
        self._calls: dict[str, _Call] = {}

def do(self, key: str, fn: Callable[[], Any], wait_timeout: float = 2.0) -> tuple[Any, bool]:
        with self._mu:
            if key in self._calls:
                call = self._calls[key]
                is_follower = True
            else:
                call = _Call()
                self._calls[key] = call
                is_follower = False

if is_follower:
            if not call.event.wait(timeout=wait_timeout):
                raise TimeoutError(f'Singleflight wait timed out for {key}')
            if call.err is not None:
                raise call.err
            return call.val, True

try:
            call.val = fn()
        except Exception as exc:
            call.err = exc
        finally:
            with self._mu:
                if self._calls.get(key) is call:
                    del self._calls[key]
            call.event.set()
STAGE 03 · REFERENCE IMPLEMENTATION

Implementing Singleflight with Detached Contexts & Error Isolation

1.Caller Cancellation Bug: If leader inherits Caller 1's request context, Caller 1 hitting Cancel fails 500 other users.

2.Detached Timeout: Give the leader a bounded backend context timeout independent of any single caller.

3.Try/Finally Cleanup: A leaked entry in calls[key] would wedge every future request for that key until restart.

Detached leader timeouts and try/finally cleanup prevent one client cancellation or panic from wedging followers.

STAGE 04 · BLAST RADIUS CONTROLintermediate

Mitigating Shared-Error Amplification with `Forget(key)`.

Why this matters: Prevent shared-error amplification by calling Forget(key) on transient errors and bypassing negative caching.

If the leader encounters a transient 503 error, all 999 followers receive that same error. Worse, if a stale negative result is cached, traffic fails repeatedly. Using Forget(key) (or only coalescing healthy responses while allowing bounded jittered retry on transient errors) limits blast radius.

Never mutate a returned slice/object in place without cloning, because all followers share the exact same pointer/reference unless copied.

STAGE 04 · BLAST RADIUS CONTROL

Mitigating Shared-Error Amplification with `Forget(key)`

1.Error Amplification: Sharing a transient 503 across 999 followers creates a burst of user-facing errors.

2.Early Forget: Calling Forget(key) when errors occur lets subsequent arrivals elect a fresh leader immediately.

3.Bounded Follower Wait: Give followers a max wait timeout so they can fail fast if the leader hangs.

Calling Forget(key) on transient failures and avoiding negative error caching limits blast radius.

STAGE 05 · CLUSTER-WIDE COALESCINGadvanced

Scaling Singleflight Across 100+ Stateless Nodes.

Why this matters: Eliminate N-pod amplification across 100+ stateless pods using a consistent-hash coalescer ring.

Think of Scaling Singleflight Across 100+ Stateless Nodes as the intuition layer for Singleflight Request Coalescing: Eliminating Thundering Herds: Eliminate N-pod amplification across 100+ stateless pods using a consistent-hash coalescer ring.

In a 100-pod Kubernetes deployment, local-only singleflight still lets 100 pods each send 1 leader request per key. Routing cache-miss traffic through a Consistent-Hash Routing Ring (e.g., Envoy Maglev/RingHash or an internal coalescer tier) funnels all requests for key to the same coalescer pod, reducing 100 origin calls down to 1.

STAGE 05 · CLUSTER-WIDE COALESCING

Scaling Singleflight Across 100+ Stateless Nodes

1.Why Local-Only Fails: Across 200 API pods, 20 expiring keys still emit 20 x 200 = 4,000 DB queries.

2.Consistent-Hash Affinity: Routing key K to dedicated coalescer node P(K) collapses 200 pods down to 1 origin query.

3.L1 + Ring Combo: Keep a 2s L1 process cache on API pods so 100K QPS hot keys don't saturate P(K)'s NIC.

Routing cache misses through a Maglev/Ketama consistent-hash ring collapses cluster-wide misses down to 1 origin query.

STAGE 06 · PROACTIVE DEFENSEadvanced

Pairing Singleflight with Probabilistic Early Refresh (PER) & SWR.

Why this matters: Pair Singleflight with Stale-While-Revalidate and Probabilistic Early Refresh (XFetch) to remove cold-miss waits.

Think of Pairing Singleflight with Probabilistic Early Refresh (PER) & SWR as the intuition layer for Singleflight Request Coalescing: Eliminating Thundering Herds: Pair Singleflight with Stale-While-Revalidate and Probabilistic Early Refresh (XFetch) to remove cold-miss waits.

Singleflight still forces callers to wait for 1 origin round-trip on expiry. Pairing Singleflight with Stale-While-Revalidate (SWR) or Probabilistic Early Refresh (XFetch) lets one background leader refresh the key before TTL=0 while all other callers receive the cached value in < 1 ms.

STAGE 06 · PROACTIVE DEFENSE

Pairing Singleflight with Probabilistic Early Refresh (PER) & SWR

1.Dual-TTL SWR: Callers hitting between soft_ttl and hard_ttl get instant stale responses while 1 leader refreshes asynchronously.

2.XFetch Early Refresh: Hot keys with high QPS probabilistically refresh seconds before soft_ttl expires.

3.Zero Synchronized Spikes: Jittering refresh timing eliminates synchronized expiry waves across keys.

Pairing Singleflight with Stale-While-Revalidate and XFetch refreshes hot keys in the background with zero caller wait.

STAGE 07 · TRADE-OFFS & PITFALLSadvanced

When Singleflight Hurts: Non-Idempotent Writes & Personalized Auth.

Why this matters: Avoid leaking cross-tenant data or coalescing non-idempotent writes by keying strictly on full auth scope.

Think of When Singleflight Hurts: Non-Idempotent Writes & Personalized Auth as the intuition layer for Singleflight Request Coalescing: Eliminating Thundering Herds: Avoid leaking cross-tenant data or coalescing non-idempotent writes by keying strictly on full auth scope.

Never coalesce requests whose key omits tenant ID, auth scope, or user permissions—doing so leaks one user's private payload to 999 followers. Also never coalesce non-idempotent mutations (POST /charge) unless keyed by an explicit client idempotency token.

STAGE 07 · TRADE-OFFS & PITFALLS

When Singleflight Hurts: Non-Idempotent Writes & Personalized Auth

1.Cross-Tenant Leak: If follower B shares key 'dashboard' with leader A without tenant_id, B receives A's private data.

2.Read-Only Rule: Never coalesce state-mutating POST/PATCH requests unless keyed by an explicit Idempotency-Key.

3.Vary Headers: Include locale, currency, and permission tier in the singleflight key.

Including tenant/auth scope in every key and restricting singleflight to idempotent reads prevents data leaks.
