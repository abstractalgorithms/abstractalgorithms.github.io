TCP/IP & Linux
Socket Networking Internals.

TCP/IP is the foundational transport and internetworking stack that turns unreliable, unordered IP packets into a reliable, flow-controlled, congestion-aware byte stream. Understanding its handshakes, windowing, congestion algorithms (CUBIC/BBR), and kernel socket states explains why real networks stall, drop, or exhaust ports.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Most 'mysterious' production latency spikes and connection errors trace directly to TCP fundamentals: 3-way handshake RTTs, Nagle + Delayed ACK stalls, `TIME_WAIT` port exhaustion, or congestion window (`cwnd`) collapses on packet loss.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Every HTTP/1.1, HTTP/2, gRPC, PostgreSQL, and Kafka connection runs over TCP (or learns from its pitfalls in QUIC/HTTP3). Misconfiguring keepalives, TCP_NODELAY, socket backlogs, or MTU sizes quietly degrades p99 latency by 40–200 ms or triggers EADDRNOTAVAIL outages under load.

  • TCP establishes connections with a 3-way handshake (SYN → SYN-ACK → ACK), adding 1 full RTT before the first byte of TLS/HTTP data can even begin (TLS 1.3 adds another 1 RTT).
  • Flow control (rwnd) prevents a fast sender from overflowing the receiver's kernel buffer, while congestion control (cwnd via CUBIC or BBR) prevents overwhelming intermediate network switches.
  • Nagle's algorithm buffers small writes until an ACK arrives; paired with Delayed ACK (40–200 ms on Linux/Windows), it causes artificial 40 ms stalls unless TCP_NODELAY is enabled.
  • Closing a socket leaves the active closer in TIME_WAIT for 2 * MSL (60 seconds on Linux) to drain stray packets—rapid short-lived connections can exhaust the ~28,232 default ephemeral ports.
  • Head-of-line (HoL) blocking occurs because TCP delivers an ordered byte stream: losing 1 packet stalls all subsequent packets in the kernel receive buffer, even across independent HTTP/2 streams.

Good candidates

  • Diagnosing unexplained p99 latency spikes (e.g., 40 ms or 200 ms plateaus), Connection reset by peer, or SYN drops in production microservices.
  • Tuning Linux kernel sysctl parameters, load balancers, and connection pools for high-concurrency proxies, databases, and brokers.
  • Deciding between persistent TCP pools, HTTP/2 multiplexing, or UDP/QUIC for cross-continent or lossy mobile networks.

Think twice

  • Real-time voice/video/gaming streams where waiting for head-of-line packet retransmission creates unacceptable jitter—use RTP/WebRTC/UDP instead.
  • Ultra-low-latency (<10 µs) HFT/HPC fabrics where kernel-bypass RDMA or DPDK replaces the OS TCP/IP stack.
  • Micro-services running behind a service mesh without first checking application-level timeouts and DNS caching.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn internal Java service sends small 200-byte JSON RPC headers followed immediately by a 1 KB body over persistent TCP connections, exhibiting a bizarre bimodal p99 latency at 42 ms.

The idea

IP (Internet Protocol) is a best-effort, connectionless datagram layer: packets can be dropped, duplicated, or reordered at any router. TCP (Transmission Control Protocol) sits on top of IP (Layer 4) to provide applications with an ordered, reliable, full-duplex byte stream identified by a 4-tuple: (src_ip, src_port, dst_ip, dst_port).

To achieve reliability without melting the internet, TCP runs three tightly coupled state machines: (1) Sequence numbers & ACKs for reliability, (2) Sliding receive window (rwnd) so a fast sender never overruns a slow receiver's memory, and (3) Congestion window (cwnd) so senders probe available network bandwidth without overflowing router queues.

Concrete walkthrough

Trace a single HTTPS request from a client in Mumbai to an API in Singapore (RTT = 60 ms):

  1. 3-Way Handshake (1 RTT = 60 ms): Client sends SYN (with initial seq=100, MSS=1460, Window Scale). Server allocates a half-open entry in the SYN queue, replies SYN-ACK (seq=500, ack=101), and client replies ACK (ack=501). The connection moves to ESTABLISHED in the accept queue.
  2. Slow Start & Data Transfer: Server starts with initial congestion window iw=10 segments (~14.6 KB). After TLS 1.3 handshake (1 RTT), the client sends GET /v1/feed. Server writes a 64 KB response: it sends 14.6 KB immediately, waits for ACKs, and exponentially doubles cwnd (10 → 20 → 40 segments) until reaching the Bandwidth-Delay Product (BDP = Bandwidth × RTT).
  3. Packet Loss & Recovery: If 1 segment is dropped in transit, the receiver sends 3 duplicate ACKs (DupACK) for the last contiguous byte. Fast Retransmit resends the missing segment immediately without waiting for the 200 ms+ RTO timer, while CUBIC cuts cwnd by 30%.
  4. Teardown: Client sends FIN, server ACKs and sends its own FIN, and the client enters TIME_WAIT for 2 * MSL (60 s) to absorb any delayed duplicate packets.

Every TCP stream balances sender congestion probing (cwnd) against receiver buffer capacity (rwnd) across an unreliable IP fabric.

Bandwidth-Delay Product (BDP) & window scaling

A TCP sender can have at most min(cwnd, rwnd) unacknowledged bytes in flight. On a high-speed WAN link (e.g., 1 Gbps = 125 MB/s) with a 100 ms RTT, the Bandwidth-Delay Product is 125 MB/s × 0.1 s = 12.5 MB. If the receiver's rwnd were capped at the original 16-bit TCP header limit (64 KB), throughput would stall at 64 KB / 0.1 s = 640 KB/s—using only 0.5% of the link.

RFC 7323 Window Scaling negotiates a bit-shift multiplier (0..14) during the SYN handshake, allowing rwnd up to 1 GB. On Linux, net.ipv4.tcp_rmem and tcp_wmem auto-tune buffers up to 4–16 MB by default, so ensure your proxies and containers do not override them with tiny fixed SO_RCVBUF values.

Failure modes

1. Bufferbloat: Oversized router/switch buffers queue packets for 500–2,000 ms before dropping them. Loss-based CUBIC keeps pumping traffic until the buffer overflows, destroying interactive latency. BBR or AQM (fq_codel) prevents queue buildup.

2. TCP Incast Collapse: In distributed storage/MapReduce, 100 workers reply simultaneously to 1 aggregator over a shallow-buffered ToR switch, overflowing the switch buffer and triggering simultaneous 200 ms RTO timeouts.

3. Silly Window Syndrome & Nagle Interaction: Sending 1-byte writes while the receiver advertises tiny rwnd wastes 40 bytes of IP+TCP header per byte of data; always batch writes at the application layer or use TCP_NODELAY with buffered framing.

Practical Linux tuning & diagnostics

Before changing sysctl defaults, measure with ss -ti (shows live cwnd, rtt, retrans, send_bps, bbr state) and nstat -az Tcp* (tracks TcpExtListenOverflows, TcpRetransSegs).

For high-concurrency edge proxies and API servers on Linux 5.15+, the highest-leverage defaults are: net.core.default_qdisc = fq + net.ipv4.tcp_congestion_control = bbr (for internet-facing egress), net.core.somaxconn = 8192, net.ipv4.tcp_slow_start_after_idle = 0 (prevents cwnd from resetting to 10 segments after brief idle pauses on persistent pools), and net.ipv4.ip_local_port_range = 1024 65535.

Practical checklist

  • Enable TCP_NODELAY on all RPC, database, and HTTP client/server sockets to prevent 40 ms Nagle + Delayed ACK stalls.
  • Use persistent connection pools with max-idle timeouts shorter than upstream NAT/ALB idle timeouts (e.g., 55s vs. 60s AWS ALB).
  • Enable tcp_keepalive (e.g., 60s idle / 10s interval / 3 probes) to detect silently dropped firewall connections.
  • Set tcp_slow_start_after_idle = 0 on persistent backend pools so idle connections don't drop back to slow start.
  • Monitor TcpExtListenDrops and TcpRetransSegs in Prometheus node_exporter to catch SYN/accept queue overflows early.
  • Inspect ss -ti and tcpdump before blaming application code when cross-region p99 latency spikes.
03 / Engineering trade-offs

Weighing architectural decisions

CUBIC vs. BBR Congestion Control

Advantage: BBR models actual bottleneck bandwidth and min-RTT, maintaining high throughput on lossy WAN links where CUBIC collapses `cwnd`.

Drawback: BBRv1 can be overly aggressive against concurrent CUBIC flows on shared shallow-buffered datacenter switches.

TCP Keepalive / Connection Pooling vs. Short-Lived Sockets

Advantage: Pooled connections amortize 1 RTT TCP + 1 RTT TLS handshakes and avoid `TIME_WAIT` port exhaustion.

Drawback: Long-lived connections can pin traffic to old backend pods after a scale-out unless L7 load balancing (HTTP/2, Envoy) or periodic max-connection-age is used.

Standard 1500-Byte MTU vs. Jumbo Frames (9000 Bytes)

Advantage: Jumbo frames cut packet-per-second overhead and CPU interrupts by ~6x for intra-VPC storage/Kafka traffic.

Drawback: If any intermediate router or VPN tunnel drops `DF` (Don't Fragment) packets without ICMP `Fragmentation Needed`, connections silently blackhole.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

SYN Queue / Accept Queue Overflow

During a sudden traffic burst, `net.core.somaxconn` (historically 128, now 4096) or application `listen()` backlog fills up, causing the kernel to silently drop incoming `SYN`s or `ACK`s.

What helps: Increase `net.core.somaxconn` and `net.ipv4.tcp_max_syn_backlog`, enable `tcp_syncookies=1`, and ensure the app accepts connections on a dedicated non-blocking event loop.

PMTUD Blackhole (Path MTU Discovery Failure)

Packets with the `DF` bit set exceed an intermediate VPN/GRE tunnel's 1420-byte MTU, and a misconfigured firewall blocks ICMP Type 3 Code 4 (`Fragmentation Needed`), stalling large payloads after the handshake succeeds.

What helps: Enable MSS clamping on tunnel interfaces (`iptables -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu`) and allow essential ICMP.

Silent Half-Open Connections Behind Firewalls

A NAT gateway or cloud firewall drops idle connection state after 350 seconds without sending `RST`, leaving the app hanging for 15+ minutes until TCP retransmission timeouts (`tcp_retries2`) fire.

What helps: Enable TCP keepalives (`SO_KEEPALIVE` with `tcp_keepalive_time=60`, `intvl=10`, `probes=3`) or application-level HTTP/2 PING frames.

TIME_WAIT Ephemeral Port Exhaustion

Initiating >500 short-lived TCP connections per second to the same `(dst_ip, dst_port)` fills all 28,232 local ports in `TIME_WAIT` for 60 seconds.

What helps: Use persistent HTTP/DB connection pools, expand `net.ipv4.ip_local_port_range = 1024 65535`, and avoid `tcp_tw_recycle` (removed in Linux 4.12 for breaking NAT).

05 / Practical checklist

Avoid these mistakes

  • Assuming `localhost` or LAN TCP latency is free—forgetting that a cold TCP+TLS handshake costs 2 RTTs (~100–300 ms cross-continent).
  • Leaving Nagle's algorithm enabled on RPC/database protocols that perform small sequential writes before reading.
  • Disabling ICMP completely on firewalls, inadvertently breaking Path MTU Discovery and IPv6 Neighbor Discovery.
  • Setting `SO_LINGER` with timeout `0` to bypass `TIME_WAIT`, sending `RST` packets that can corrupt in-flight data on reused 4-tuples.
  • Ignoring TCP Head-of-Line blocking when multiplexing 100 concurrent RPCs over a single HTTP/2 connection on lossy mobile networks.
