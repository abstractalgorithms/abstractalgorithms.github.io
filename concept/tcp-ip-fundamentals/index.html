TCP/IP & Linux Socket Networking Internals

Master reliable byte streams, OS socket buffers, 3-way handshakes, sliding window flow control, and BBR vs CUBIC congestion mechanics under high load.

Orientation & Intuition

TCP delivers an in-order, guaranteed byte stream across unreliable packet-switched IP networks. The Linux kernel manages this via send/receive socket buffers (SO_SNDBUF/SO_RCVBUF), sliding-window flow control to protect receivers from saturation, and congestion algorithms (CUBIC/BBR) to regulate transmission across shared bottlenecks.

Key takeaway Connection setup costs 1.5 RTT (plus 1 RTT for TLS 1.3) and socket teardown leaves ports in TIME_WAIT for 60 seconds; in high-throughput distributed systems, always pool persistent connections, tune Linux socket queues (somaxconn, tcp_max_syn_backlog), and disable Nagle's algorithm (TCP_NODELAY) on latency-sensitive RPC paths.

Core Architecture & Trade-offs

Every microservice RPC, distributed cache lookup, and database replication stream operates over TCP sockets. Un-tuned socket buffers introduce bufferbloat, un-pooled connections exhaust ephemeral ports in TIME_WAIT, and un-tuned accept queues silently drop connection requests during traffic spikes, spiking p99 latencies from 5ms to 1,000ms+.

Key Architecture Invariants

  • Three-Way Handshake (SYN -> SYN-ACK -> ACK): Synchronizes initial sequence numbers (ISN) and negotiates Maximum Segment Size (MSS) and Window Scaling options before application bytes flow.
  • Flow Control via Sliding Window (rwnd): The receiver advertises its available kernel receive buffer space in every ACK header, preventing the sender from overflowing receiver memory.
  • Congestion Control (CUBIC vs BBR): Congestion window (cwnd) bounds unacknowledged in-flight packets. CUBIC cuts window size upon packet loss; Google's BBR models bottleneck bandwidth and round-trip propagation time to prevent router bufferbloat.
  • Nagle's Algorithm vs Delayed ACK: Nagle buffers small outbound packets until an ACK arrives; paired with receiver's 40ms Delayed ACK, this creates pathological 40ms micro-latency spikes unless TCP_NODELAY is enabled.
  • Connection Teardown & TIME_WAIT State: The socket endpoint that initiates active close remains in TIME_WAIT for 2×MSL (typically 60s) to drain duplicate packets; un-pooled client traffic will exhaust the 60,000 ephemeral port range.

When to Use

  • High-throughput APIs and microservice RPCs (gRPC, REST, GraphQL) requiring ordered, lossless byte-stream transport.
  • Database replication streams, transaction write-ahead logs (WAL), and distributed consensus protocols (Raft, Paxos).
  • Persistent stateful connections like WebSockets and server-sent events (SSE) needing continuous bi-directional messaging without packet loss.

When NOT to Use

  • Real-time interactive media (VoIP, video conferencing, multiplayer gaming) where retransmitting lost packets introduces intolerable jitter; use UDP.
  • Multiplexed independent streams over lossy wireless networks suffering from TCP Head-of-Line (HoL) blocking; adopt QUIC (HTTP/3 over UDP).
  • Local inter-process communication on the same Linux host; use Unix Domain Sockets (AF_UNIX) to eliminate IP stack framing and checksum overhead.

Deep Dive & Production Considerations

1. Network Layer Decoupling & Protocol Framing

The TCP/IP stack abstracts unreliable physical networks into guaranteed, ordered byte streams. Understanding where TCP fits in the Linux kernel is essential for troubleshooting throughput and tail latency bottlenecks:

Maximum Transmission Unit (MTU) vs Maximum Segment Size (MSS)

  • MTU (1500 bytes): The largest Ethernet frame payload routers forward without fragmentation.
  • IP Header (20 bytes) + TCP Header (20 bytes): 40 bytes minimum header overhead.
  • MSS (1460 bytes): Maximum raw application payload transmitted in a single TCP segment (MTU - 40).

2. Connection Lifecycle & The 3-Way Handshake

Before a single byte of payload transfers, client and server must agree on starting sequence numbers and options:

code 
Client                                  Server (LISTEN)
  |                                            |
  |-------- 1. SYN (seq=x, MSS=1460) --------->| SYN_RCVD (SYN queue)
  |<------- 2. SYN-ACK (seq=y, ack=x+1) -------|
  |-------- 3. ACK (seq=x+1, ack=y+1) -------->| ESTABLISHED (Accept queue)
  |                                            |
  |==== Application Data (Payload Flow) ======>| app calls accept()
  1. SYN: Client picks a random Initial Sequence Number (ISN=x) and advertises its receive window scale and MSS.
  2. SYN-ACK: Server acknowledges (ack=x+1), transmits its own sequence number (ISN=y), and places socket in the half-open SYN queue.
  3. ACK: Client confirms (ack=y+1). The connection moves to the server's Accept queue (somaxconn). When the server calls accept(), a new connected file descriptor (fd) is returned.

Latency Tax: Connection setup incurs 1.5 RTT before sending application payload, plus 1 RTT for TLS 1.3 handshake. Creating new connections per request imposes devastating latency penalties.

3. Flow Control vs Congestion Control

A common source of confusion in systems engineering is conflating flow control with congestion control:

DimensionFlow ControlCongestion Control
GoalPrevent sender from overwhelming receiver RAMPrevent sender from overwhelming intermediate routers
Governing MetricReceiver Advertised Window (rwnd)Congestion Window (cwnd)
Signaled ByReceiver in TCP header ACK packetsPacket loss (CUBIC) or RTT inflation / delivery rate (BBR)
Effective Sending LimitFlightSize = min(cwnd, rwnd)FlightSize = min(cwnd, rwnd)

Congestion Control Algorithms: CUBIC vs BBR

  • CUBIC (Loss-based): Treats packet drop as the signal of congestion. It increases cwnd aggressively until buffers overflow, causing packet drops, then slashes cwnd by 30%. On high-bandwidth, high-latency links (e.g. transcontinental fibers), CUBIC causes severe bufferbloat.
  • BBR (Bottleneck Bandwidth and RTT): Developed by Google. BBR does not wait for packet loss; it measures actual delivery rates and round-trip propagation times (RTprop) to calculate the link's Bandwidth-Delay Product (BDP = Bandwidth × RTT). BBR paces packets to match network capacity without filling intermediate queue buffers.

4. Connection Teardown & The TIME_WAIT Hazard

Closing a TCP connection requires a 4-way handshake (FIN -> ACK -> FIN -> ACK). The side that initiates active close enters the TIME_WAIT state:

code 
Active Closer                               Passive Closer
  |                                               |
  |----------------- 1. FIN -------------------->| (enters CLOSE_WAIT)
  |<---------------- 2. ACK ---------------------|
  |<---------------- 3. FIN ---------------------|
  |----------------- 4. ACK -------------------->| (CLOSED)
  |                                               |
(enters TIME_WAIT for 2×MSL = 60s)                |

Why TIME_WAIT Exists

  1. Acks the final FIN: If ACK #4 is lost in flight, the passive closer retransmits FIN #3. The active closer must still be alive to resend ACK #4.
  2. Drains Old Duplicate Segments: Prevents delayed packets from an old connection from being accepted by a newly opened connection reusing the same 4-tuple (source IP, source port, dest IP, dest port).

Ephemeral Port Exhaustion: Linux assigns client ports from net.ipv4.ip_local_port_range (typically ~28,232 ports). If an API proxy opens and closes 500 connections/sec to the same upstream IP/port, all ephemeral ports are locked in TIME_WAIT (500/s × 60s = 30,000 sockets), causing EADDRNOTAVAIL crashes!

5. Production Linux Kernel Tuning Checklist (sysctl.conf)

ini 
# Scale accept queue for high-concurrency microservices
net.core.somaxconn = 65535

# Scale SYN queue for traffic bursts and prevent SYN drops
net.ipv4.tcp_max_syn_backlog = 32768

# Enable SYN cookies to survive SYN flood attacks without dropping connections
net.ipv4.tcp_syncookies = 1

# Allow recycling of TIME_WAIT sockets for outgoing connections
net.ipv4.tcp_tw_reuse = 1

# Reduce FIN timeout from 60s to 15s to reclaim dead sockets faster
net.ipv4.tcp_fin_timeout = 15

# Switch default congestion control algorithm to Google BBR
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr

# Disable slow-start restart after idle (prevents connection throughput drop after idle periods)
net.ipv4.tcp_slow_start_after_idle = 0

# Autotune socket memory buffers (min, default, max bytes)
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216
