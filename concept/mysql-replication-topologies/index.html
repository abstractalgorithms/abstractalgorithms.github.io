MySQL Replication
Topologies.

MySQL replication copies binary log (binlog) events from a primary server to one or more replicas to scale reads, isolate analytics, and survive node or availability-zone failures. Choosing between asynchronous, semi-synchronous, and Group Replication (Paxos-based) topologies trades write latency and operational complexity against Recovery Point Objective (RPO).

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Default to GTID-based asynchronous primary-replica with semi-synchronous replication (`rpl_semi_sync_master_wait_for_slave_count=1`) when you need zero data loss on single-node failure without paying full InnoDB Group Replication consensus latency.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

A single MySQL primary hits CPU, IOPS, or connection limits quickly under read-heavy workloads and represents a single point of failure. Replication decouples read scaling and backup execution from the write path while providing warm standbys for sub-minute failover using Orchestrator or ProxySQL.

  • Enable Global Transaction Identifiers (gtid_mode=ON, enforce_gtid_consistency=ON) so replicas track committed transactions by UUID:sequence rather than fragile binlog file/position offsets.
  • Use binlog_format=ROW (binlog_row_image=MINIMAL or FULL) instead of STATEMENT to eliminate non-deterministic replay bugs from UUID(), NOW(), or LIMIT without ORDER BY.
  • Semi-synchronous replication (AFTER_SYNC) guarantees at least one replica has persisted the event to its relay log before the primary commits to InnoDB, preventing phantom reads and lost commits on crash.
  • Parallel replica appliers (replica_parallel_type=LOGICAL_CLOCK, replica_parallel_workers=8–16) apply non-conflicting transactions concurrently using commit-parent timestamps to curb replication lag.
  • InnoDB Group Replication (MySQL 8.0+) uses a Paxos variant (XCom) for certified multi-node consensus, ideal for single-primary HA clusters of 3 or 5 nodes with automatic split-brain protection.

Good candidates

  • Read-to-write ratios exceed 5:1 and SELECT traffic (dashboards, search, reporting) saturates primary buffer pool or CPU.
  • You require zero-downtime schema changes (gh-ost or pt-online-schema-change), logical backups (mysqldump), or physical snapshots without stalling primary transactions.
  • High availability requires automatic promotion of an up-to-date standby within 10–30 seconds across availability zones.

Think twice

  • Write throughput on a single table exceeds what one primary can commit (~15k–30k writes/sec depending on fsync and NVMe IOPS), because replicas must replay every write.
  • Applications require strict linearizable reads immediately after writes without session-stickiness, GTID wait (WAIT_FOR_EXECUTED_GTID_SET), or read-after-write routing.
  • Multi-region active-active writes on the same rows are required without conflict resolution; multi-primary Group Replication suffers certification conflicts and rollback spikes.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA fintech payments service processes 4,000 TPS on MySQL 8.0 across two AWS Availability Zones. Asynchronous replication risked losing up to 500ms of committed ledger entries during an abrupt primary EBS failure.

The idea

MySQL replication is an asynchronous or semi-synchronous state-machine log shipping pipeline. Every data-modifying transaction committed on the primary is recorded in the binary log (binlog) as row-level before/after images (binlog_format=ROW). Replicas connect over TCP port 3306, pull those events via an I/O receiver thread into a local relay log, and apply them via one or more SQL applier threads.

Topologies differ in who can accept writes, how many hops events travel, and when the primary acknowledges a commit to the client. Simple primary-replica topologies optimize for low write latency and read scaling; semi-synchronous topologies close the data-loss window; Group Replication replaces external failover orchestration with Paxos-based distributed consensus.

Concrete walkthrough

Consider an order placement INSERT INTO orders ... on a 3-node semi-synchronous MySQL 8.0 topology (db-primary in AZ-1, db-replica-1 in AZ-2, db-replica-2 in AZ-3) with rpl_semi_sync_source_wait_point=AFTER_SYNC and gtid_mode=ON:

  1. Prepare & Binlog Write: InnoDB prepares the transaction (trx_id=98421), writes undo/redo records, and appends the GTID event (3e11fa47-71ca-11e1-9e33-c80aa9429562:40192) plus WRITE_ROWS event to the primary's binlog, flushing with sync_binlog=1.
  2. Parallel Ship & Wait: The primary's Binlog Dump thread pushes the event to db-replica-1 and db-replica-2. The primary pauses before committing in InnoDB (AFTER_SYNC), holding row locks so no local session can read uncommitted state.
  3. Replica Relay Persist: db-replica-1's I/O thread writes the event to relay-bin.000412, flushes to disk (sync_relay_log=1), and sends an ACK packet back to db-primary.
  4. Primary Commit & Client Return: Upon receiving 1 ACK (rpl_semi_sync_source_wait_for_replica_count=1), db-primary commits the transaction in InnoDB and returns OK to the application (~0.9ms total).
  5. Async Apply: Meanwhile, db-replica-1's LOGICAL_CLOCK worker threads apply the relay log event to its local InnoDB engine and update gtid_executed.

AFTER_SYNC blocks the primary's InnoDB commit until at least one standby flushes the event to its relay log, eliminating phantom reads and lost commits on crash.

GTIDs, parallel appliers, and topology patterns

GTIDs (source_uuid:transaction_id) replace fragile (binlog_file, offset) coordinates. When a replica fails over to a new primary, it executes CHANGE REPLICATION SOURCE TO SOURCE_AUTO_POSITION=1; the new primary inspects the replica's gtid_executed set and streams only missing transactions.

Parallel Replication: Older MySQL versions applied relay logs on a single SQL thread, making a 32-core replica lag behind a 32-core primary. In MySQL 8.0, setting binlog_transaction_dependency_tracking=WRITESET hashes modified primary/unique keys into a dependency window so LOGICAL_CLOCK workers can apply non-overlapping transactions concurrently, often boosting replica apply throughput by 4x–8x.

Common Topologies:

  • Star (1 Primary -> N Replicas): Simplest; supports up to ~20–30 replicas before primary binlog dump network bandwidth saturates.
  • Tree / Cascading (Primary -> Relay -> N Replicas): Offloads binlog dump traffic to an intermediate log_replica_updates=ON relay; adds 1–5ms hop latency.
  • InnoDB Cluster (Group Replication): 3 or 5 nodes using XCom (Paxos) + MySQL Router; automatic quorum failover without external Orchestrator.

Failure modes

1. Semi-Sync Silent Downgrade to Async: If all standbys disconnect or exceed rpl_semi_sync_source_timeout (default 10,000ms), MySQL automatically downgrades to asynchronous replication so writes don't hang forever. Without alerting on Rpl_semi_sync_source_status=OFF, teams mistakenly believe they still have RPO=0.

2. Unbounded DDL & Large Transaction Lag: A single ALTER TABLE or 5-million-row UPDATE writes one massive transaction to the binlog. Because a transaction cannot be applied until fully received and must run on one worker thread, replicas stall for minutes.

3. Group Replication Flow-Control Throttling: If one node in a 3-node InnoDB Cluster falls behind on disk IOPS, group_replication_flow_control_mode=QUOTA throttles writes across the entire cluster to prevent memory exhaustion.

Production operations & read routing

To make replication safe for application code:

  • Read-After-Write Consistency: Route mutations and immediate post-mutation reads (e.g., user profile updates, checkout confirmation) to the primary via ProxySQL query rules, or pass the session's last_gtid and block reads on SELECT WAIT_FOR_EXECUTED_GTID_SET(?, 1).
  • Lag-Aware Pooling: Configure ProxySQL mysql_replication_hostgroups with max_replication_lag=5 so lagging replicas are automatically pulled from the read pool.
  • Online Schema Migrations: Use gh-ost (which tails the binlog and throttles itself based on replica lag) rather than raw ALTER TABLE on tables over 10GB.

Practical checklist

  • Enforce gtid_mode=ON, enforce_gtid_consistency=ON, and binlog_format=ROW across all nodes.
  • Set sync_binlog=1 and innodb_flush_log_at_trx_commit=1 on the primary for crash-safe durability.
  • Enable super_read_only=ON on all replicas to prevent accidental errant writes.
  • Configure replica_parallel_type=LOGICAL_CLOCK, binlog_transaction_dependency_tracking=WRITESET, and replica_preserve_commit_order=ON.
  • Alert on Seconds_Behind_Source > 5, Rpl_semi_sync_source_status == OFF, and Replica_SQL_Running == No.
  • Test automated failover quarterly in staging by killing the primary process (kill -9) and verifying zero split-brain.
03 / Engineering trade-offs

Weighing architectural decisions

Consistency vs. Write Latency

Advantage: Asynchronous replication returns commit success immediately after local binlog/InnoDB flush (~0.3ms), keeping primary p99 latency independent of network RTT.

Drawback: Committed transactions not yet shipped to replicas are permanently lost if the primary storage fails unrecoverably (RPO > 0).

Primary-Replica vs. Group Replication (Single-Primary)

Advantage: Group Replication provides built-in Paxos membership, automatic primary election, and split-brain fencing without external Orchestrator/Zookeeper daemons.

Drawback: Every transaction pays XCom consensus RTT plus certification overhead, and large transactions (> `group_replication_transaction_size_limit`, default 150MB) fail certification.

Circular / Multi-Primary vs. Single-Primary

Advantage: Multi-primary topologies allow local writes in multiple nodes or regions without forwarding every write across a WAN.

Drawback: Auto-increment offsets (`auto_increment_increment`, `auto_increment_offset`) only prevent PK collisions; secondary unique key collisions or concurrent updates cause silent overwrites or certification aborts.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Replication Lag & Stale Read-After-Write

Long-running queries, single-threaded DDL (`ALTER TABLE`), or unindexed batch `DELETE` statements on the primary serialize on replicas, causing `Seconds_Behind_Source` to climb to minutes.

What helps: Enable `LOGICAL_CLOCK` parallel workers, set `binlog_transaction_dependency_tracking=WRITESET`, chunk large deletes to 1,000 rows, and route critical post-write reads to the primary or wait on `WAIT_FOR_EXECUTED_GTID_SET()`.

Split-Brain Dual-Primary Writes

Network partition triggers failover promotion of a replica while the old primary remains reachable by stale application pods, resulting in divergent GTID histories.

What helps: Set `super_read_only=ON` on all replicas by default, fence old primaries via ProxySQL/Orchestrator pre-failover hooks, and revoke VIPs or security-group ingress before unsetting `read_only`.

Errant Transactions on Promoted Replica

An operator runs a local `CREATE USER` or `DELETE` directly on a replica before promotion; its unique GTID breaks subsequent re-attachment of other replicas.

What helps: Enforce `super_read_only=ON` on replicas, restrict `SUPER`/`CONNECTION_ADMIN` privileges, and run `pt-table-checksum` or GTID diff checks before promotion.

Purged Binlogs Before Replica Reconnect

A replica goes offline for maintenance longer than `binlog_expire_logs_seconds` (default 30 days, often tuned down to 24–72h), so the primary purges needed binlogs.

What helps: Size `binlog_expire_logs_seconds` to at least 3x max expected maintenance/outage duration, monitor `Binlog_snapshot_position` vs. replica lag, and keep automated XtraBackup snapshots for fast re-seeding.

05 / Practical checklist

Avoid these mistakes

  • Using `STATEMENT`-based replication with non-deterministic functions or triggers, silently corrupting replica data until checksums catch it months later.
  • Leaving `sync_binlog=0` or `innodb_flush_log_at_trx_commit=2` on the primary, which causes binlog/InnoDB divergence or lost commits on OS crash.
  • Pointing application read pools directly at replicas without a health-aware proxy (ProxySQL or HAProxy) that evicts lagging replicas when `Seconds_Behind_Source > 5s`.
  • Running `STOP REPLICA` and skipping errors with `sql_replica_skip_counter` instead of fixing root-cause drift, compounding silent data inconsistency.
  • Deploying 2-node Group Replication instead of an odd quorum (3 or 5 nodes), which loses quorum whenever either node restarts.
