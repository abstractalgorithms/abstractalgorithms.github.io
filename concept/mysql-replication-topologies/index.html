STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is MySQL Replication.

Why this matters: The mechanism: understand how MySQL Replication works from first principles.

MySQL replication streams committed binary log (binlog) events from a primary server to replica relay logs so replicas can replay mutations for read scaling, backups, and high availability.

Modern production MySQL mandates two baseline settings: gtid_mode=ON (tracking transactions by UUID:sequence rather than brittle binlog file/offset positions) and binlog_format=ROW (eliminating non-deterministic UUID() / NOW() replay bugs).

Semi-Sync AFTER_SYNC

MySQL Primary Binlog -> Replica Relay Log -> InnoDB Commit

1.1. AFTER_SYNC Safety: Primary waits for at least one replica relay-log ACK before committing to InnoDB—preventing phantom reads and lost commits.

2.2. GTID Tracking: Global Transaction IDs allow any replica to re-point to a new primary cleanly without manual log-position math.

3.3. WRITESET Parallelism: LOGICAL_CLOCK + WRITESET lets replicas apply non-conflicting transactions in parallel.

GTIDs + ROW binlogs + WRITESET parallel workers form the foundation of modern MySQL HA.

Why Replication Lag and Dual-Primary Split-Brain happen.

Why this matters: The problem: see what breaks without Why Replication Lag and Dual-Primary Split-Brain happen under real concurrency or scale.

Think of Why Replication Lag and Dual-Primary Split-Brain happen as the intuition layer for MySQL Replication Topologies: The problem: see what breaks without Why Replication Lag and Dual-Primary Split-Brain happen under real concurrency or scale.

Two failure modes plague MySQL clusters:

  • Replication Lag: single-threaded DDL (ALTER TABLE) or unindexed batch DELETEs serialize on replicas, spiking Seconds_Behind_Source to minutes and serving stale read-after-write data.
  • Split-Brain Dual-Primary Writes: after a network partition promotes a replica, stale app pods keep writing to the old primary, diverging GTID histories.
Design Trade-Off

Why Replication Lag and Dual-Primary Split-Brain happen

Before · Seq Scan + Unbounded Bloat
  • Implicit cast breaks B-Tree
  • Deadlock or XID wraparound risk
  • Long tx blocks VACUUM
After · Indexed Plan + Bounded MVCC
  • Index-only scan in <2 ms
  • Deterministic lock ordering
  • Autovacuum keeps bloat flat
Engineering Decision Framework
Problem
How to implement MySQL Replication Topologies without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
If disk I/O or compaction stalls threaten tail latency, enable GTIDs and ROW-based binlogging as your baseline, use semi-synchronous (AFTER_SYNC) or Group Replication to prevent lost commits on failover, and enforce super_read_only=ON on replicas to stop split-brain.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

3-Node Semi-Sync / Group Replication + ProxySQL Fencing.

Why this matters: Production architecture: see how the components compose end to end under real load.

Think of 3-Node Semi-Sync / Group Replication + ProxySQL Fencing as the intuition layer for MySQL Replication Topologies: Production architecture: see how the components compose end to end under real load.

Production MySQL clusters pair ProxySQL (splitting writes to Primary and reads to low-lag Replicas) with Orchestrator or MySQL InnoDB Cluster (Group Replication), automatically fencing unreachable primaries before promoting a replica.

InnoDB Cluster

3-Node MySQL Group Replication (Paxos Single-Primary)

1.1. Automatic Quorum: 3 nodes across 3 AZs tolerate 1 AZ loss without external Zookeeper/Orchestrator.

2.2. Chunked Mutations: Chunk large DELETE/UPDATEs to 1,000 rows and use gh-ost for DDL to keep lag <1s.

3.3. ProxySQL Routing: Shun replicas automatically if Seconds_Behind_Source exceeds threshold.

Group Replication provides built-in consensus fencing, while ProxySQL shields apps from lagged replicas.
