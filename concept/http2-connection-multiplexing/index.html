HTTP/2 Connection
Multiplexing.

HTTP/2 (RFC 9113) multiplexes concurrent binary request/response streams over a single TCP connection using HPACK header compression and flow control, eliminating HTTP/1.1 application-layer head-of-line blocking.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

HTTP/2 removes the 6-connection-per-origin browser limit and HTTP/1.1 pipelining stalls, but all streams still share one TCP congestion window—so packet loss above ~1–2% causes TCP-level head-of-line blocking that only HTTP/3 (QUIC) solves.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Modern web pages and microservice meshes issue 40–150 concurrent requests per origin. HTTP/1.1 forces browsers to open 6 parallel TCP connections (each paying a 1-RTT TCP + 1–2-RTT TLS handshake and cold slow-start) and still stalls behind slow responses. HTTP/2 collapses all traffic onto one warmed TCP+TLS connection, compresses repetitive headers by 75–90% via HPACK, and lets gRPC stream bidirectional RPCs at high throughput.

  • Every HTTP/2 message is split into binary frames (HEADERS, DATA, SETTINGS, WINDOW_UPDATE, RST_STREAM, GOAWAY) tagged with a 31-bit Stream ID (odd = client-initiated, even = server-initiated).
  • Multiplexing allows interleaved frames from dozens of concurrent streams (typically SETTINGS_MAX_CONCURRENT_STREAMS = 100 to 256) on one TCP connection, removing HTTP/1.1 application-layer HoL blocking.
  • HPACK (RFC 7541) compresses headers using a static table (61 common entries), a per-connection dynamic table (default 4,096 bytes), and Huffman encoding—cutting typical header overhead by ~80%.
  • Two-level credit-based flow control (WINDOW_UPDATE per stream and per connection, initial window 65,535 bytes) prevents a single fast sender from flooding a slow receiver's buffers.
  • Because all streams ride one TCP byte stream, a single lost TCP segment blocks delivery of all HTTP/2 streams at the kernel receive buffer until retransmitted (TCP head-of-line blocking).

Good candidates

  • Browser-to-CDN or API-gateway traffic over reliable broadband/fiber where a page loads dozens of concurrent assets or API calls from the same origin.
  • Internal microservice-to-microservice communication (especially gRPC over HTTP/2) where long-lived multiplexed connections eliminate connection-pool churn and TLS handshake overhead.
  • Bandwidth-constrained mobile or API workloads with large, repetitive headers (Authorization JWTs, cookies, trace IDs) that benefit from HPACK stateful compression.

Think twice

  • Lossy cellular or last-mile networks (>2% packet loss) where a single dropped TCP packet stalls all 100 multiplexed HTTP/2 streams simultaneously; prefer HTTP/3 (QUIC).
  • Legacy L4 load balancers without L7 awareness—because HTTP/2 reuses one long-lived TCP connection, L4 round-robin pins all RPCs from a client pod to a single backend pod.
  • Large single-file bulk downloads over high-BDP (bandwidth-delay product) links if the server's HTTP/2 stream flow-control window is undersized (e.g., 64 KB default), throttling throughput below a single HTTP/1.1 socket.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA checkout service makes 12,000 RPS to an inventory service (20 pods) over gRPC/HTTP2. Initially, an AWS NLB (L4) routes connections: each checkout pod opens 1 long-lived HTTP/2 connection, pinning all 1,200 RPS from that pod to 1 lucky inventory pod while others sit idle.

The idea

HTTP/1.1 is a text-based, sequential protocol: on a single TCP socket, Response B cannot start until Response A finishes completely. Even with HTTP pipelining, a slow /api/report response blocks all smaller responses behind it (application-layer head-of-line blocking). Browsers worked around this by opening 6 TCP connections per origin and sharding domains—multiplying TLS handshakes and fighting TCP slow-start.

HTTP/2 (RFC 9113) replaces plain-text messages with a binary framing layer over a single TCP+TLS connection. Every request and response is assigned a unique 31-bit Stream ID and broken into small frames (up to SETTINGS_MAX_FRAME_SIZE, default 16 KB). Frames from dozens of concurrent streams are interleaved on the wire and reassembled at the receiver.

To eliminate per-request overhead, HPACK (RFC 7541) replaces repeated ASCII header strings with integer indices into a static table and a connection-scoped dynamic table. Meanwhile, credit-based flow control (WINDOW_UPDATE frames) ensures a fast stream cannot starve other streams or overflow proxy buffers—without closing the underlying TCP socket.

Concrete walkthrough

Follow a browser loading https://app.example.com that needs /app.js (180 KB) and /api/user (2 KB, slow DB query taking 120 ms) over a single HTTP/2 connection (RTT = 30 ms):

  1. Connection Preface & Settings: After 1-RTT TCP and 1-RTT TLS 1.3 (ALPN h2), client and server exchange SETTINGS frames agreeing on MAX_CONCURRENT_STREAMS = 100, INITIAL_WINDOW_SIZE = 1048576 (1 MB), and HEADER_TABLE_SIZE = 4096.
  2. Concurrent Stream Initiation: At t = 0 ms, the browser opens Stream 1 (HEADERS for /app.js, END_STREAM) and Stream 3 (HEADERS for /api/user, END_STREAM) back-to-back in a single TCP segment. HPACK encodes :method: GET and :scheme: https as 1-byte static-table indices and stores authorization: Bearer ... in the dynamic table.
  3. Interleaved Delivery (No App HoL Blocking): At t = 15 ms, the server immediately begins sending DATA frames for Stream 1 (/app.js) in 16 KB chunks while /api/user is still querying Postgres. By t = 45 ms, /app.js finishes (END_STREAM on Stream 1) even though Stream 3 hasn't sent a single byte yet.
  4. Flow Control & Completion: At t = 135 ms, Postgres returns the user record. The server sends HEADERS (referencing the dynamic table) + DATA (END_STREAM) on Stream 3. If /app.js had been 5 MB, the browser would send WINDOW_UPDATE frames every ~512 KB to replenish the server's send credits.

HTTP/2 binary framing interleaves independent streams (Stream 1 and Stream 3) over one TCP/TLS connection with HPACK compression and per-stream flow control.

HPACK compression and stream lifecycle

Each HTTP/2 stream transitions through a strict state machine (idle -> open -> half-closed (local/remote) -> closed). A client cannot reuse a Stream ID; when Stream IDs approach 2^31 - 1, the connection gracefully shuts down via GOAWAY (carrying the last_stream_id processed so the client knows which in-flight streams are safe to retry on a new connection).

HPACK (RFC 7541) avoids the CRIME/BREACH compression side-channel attacks that broke SPDY's GZIP header compression. Instead of sliding-window DEFLATE, HPACK uses:

  1. Static Table: 61 pre-populated common pairs (e.g., index 2 = :method: GET, index 8 = :status: 200).
  2. Dynamic Table: A FIFO ring buffer (default 4 KB) per connection direction storing custom headers like x-request-id or authorization.
  3. Huffman Coding: Compresses string literals by ~30% when not yet in the dynamic table.

Failure modes

  • TCP head-of-line blocking: On a 3% packet-loss mobile link, TCP stalls the entire HTTP/2 connection waiting for retransmission, making page load slower than HTTP/1.1's 6 independent sockets.
  • L4 load-balancer pinning: Long-lived HTTP/2 connections bypass L4 round-robin, overloading early-started backend pods during autoscaling events.
  • RST_STREAM Rapid Reset floods: Malicious clients open and immediately RST_STREAM thousands of streams per second, exhausting server CPU/memory unless strict reset rate limits are enforced.
  • Dynamic table memory bloat: Proxies accepting large SETTINGS_HEADER_TABLE_SIZE values across hundreds of thousands of idle connections can exhaust RAM.

Operational tuning for Envoy, Nginx, and gRPC

When running HTTP/2 in production:

  • Edge/CDN: Enable HTTP/2 alongside HTTP/3 (Alt-Svc: h3=":443"; ma=86400) so lossy clients upgrade to QUIC automatically.
  • gRPC / Microservices: Always terminate HTTP/2 at an L7 proxy (Envoy/Linkerd/Istio) or use client-side xDS/DNS lookaside load balancing. Set max_connection_age: 300s + max_connection_age_grace: 30s so GOAWAY drains connections cleanly during rolling deploys.
  • Flow Control: Raise initial_stream_window_size from 64 KB to 1–4 MB and initial_connection_window_size to 4–16 MB for high-BDP cross-region links.

Practical checklist

  • Remove legacy HTTP/1.1 domain sharding so browsers coalesce streams onto one HTTP/2 connection.
  • Use L7 load balancing (or MAX_CONNECTION_AGE + GOAWAY) for gRPC/HTTP2 microservice pools.
  • Tune SETTINGS_INITIAL_WINDOW_SIZE (1–4 MB) if serving large payloads over >50 ms RTT links.
  • Cap SETTINGS_MAX_CONCURRENT_STREAMS (e.g., 100–256) and enable RST_STREAM rate limiting against Rapid Reset DoS.
  • Replace deprecated HTTP/2 Server Push with 103 Early Hints for critical CSS/fonts.
  • Pair HTTP/2 with HTTP/3 (QUIC) at the edge to eliminate TCP head-of-line blocking on lossy networks.
03 / Engineering trade-offs

Weighing architectural decisions

Single Connection Efficiency vs. TCP Head-of-Line Blocking

Advantage: Eliminates repeated TCP/TLS handshakes, lets TCP congestion window grow large (cwnd) quickly, and maximizes header compression across streams.

Drawback: At 2–5% packet loss, one dropped packet stalls every concurrent stream on that connection, making HTTP/2 slower than 6 parallel HTTP/1.1 connections in high-loss regimes.

HPACK Stateful Dynamic Table vs. Per-Connection Memory & Ordering

Advantage: Compresses repeated 1 KB+ cookies and JWTs down to 2-byte table indices.

Drawback: Requires strict in-order frame processing per connection and consumes per-connection RAM (4–64 KB) at proxies handling 100k+ concurrent clients.

Long-Lived Connections vs. L4 Load Balancing

Advantage: Avoids ephemeral port exhaustion and connection setup latency.

Drawback: Breaks naive L4 connection-level load balancing; new backend pods receive zero traffic until existing connections cycle via `GOAWAY` or `max_connection_age`.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

TCP Head-of-Line Blocking Under Packet Loss

A single dropped TCP packet on a mobile link causes the OS kernel to hold all subsequent in-flight HTTP/2 frames in the socket buffer until Fast Retransmit / RTO completes, stalling CSS, JS, and API calls together.

What helps: Enable HTTP/3 (QUIC) on edge CDNs so independent streams no longer share a single kernel TCP byte stream, keeping HTTP/2 as fallback.

L4 Load Balancer Hot-Spotting (Connection Pinning)

When gRPC/HTTP2 clients connect through an L4 LB, a single persistent TCP connection carries thousands of multiplexed RPCs to one backend replica, causing CPU saturation while peer replicas sit at 5% CPU.

What helps: Use L7-aware proxies (Envoy, Nginx, ALB) that multiplex/demultiplex streams per request, or configure server-side `MAX_CONNECTION_AGE` (e.g., 5 minutes + jitter) to send `GOAWAY` and force periodic reconnects.

HTTP/2 Rapid Reset DoS (CVE-2023-44487)

An attacker opens thousands of streams with `HEADERS` and immediately cancels them with `RST_STREAM` in the same packet burst, forcing the server to allocate/teardown request contexts while bypassing `MAX_CONCURRENT_STREAMS`.

What helps: Patch HTTP/2 stacks (Envoy, Go `x/net/http2`, Nginx) to rate-limit consecutive `RST_STREAM` frames per connection and terminate abusive connections with `GOAWAY(ENHANCE_YOUR_CALM)`.

Undersized Flow-Control Window Throttling

Keeping the default 65,535-byte stream window on a 100 ms RTT link caps single-stream throughput at `65,535 / 0.1s ≈ 655 KB/s` (~5.2 Mbps) regardless of 1 Gbps link capacity.

What helps: Tune `SETTINGS_INITIAL_WINDOW_SIZE` (e.g., 1–4 MB) and BDP auto-tuning on proxies/gRPC servers for high-bandwidth transfers.

05 / Practical checklist

Avoid these mistakes

  • Keeping HTTP/1.1 domain sharding (`cdn1..cdn4`) after upgrading to HTTP/2, which prevents multiplexing and wastes TLS handshakes.
  • Leaving gRPC clients behind an L4 load balancer without `MAX_CONNECTION_AGE` or client-side round-robin, starving newly scaled pods.
  • Assuming HTTP/2 Server Push is still useful—Chrome and major browsers removed Server Push in 2022; use `103 Early Hints` (`Link: rel=preload`) instead.
  • Setting `SETTINGS_MAX_CONCURRENT_STREAMS` too high (e.g., 10,000) on memory-constrained servers, allowing a single client to exhaust heap.
  • Forgetting to tune HTTP/2 flow-control windows (`initial_stream_window_size`) on high-latency WAN links, capping throughput to a few Mbps.
