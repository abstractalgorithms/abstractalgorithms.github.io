Counting &
Radix Sort.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

When keys are bounded integers, fixed-width strings, or IEEE-754 floats, non-comparative distribution sorting outperforms Quicksort and Timsort by eliminating branch mispredictions and log-factor passes.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Comparison sorts cannot beat Ω(n log n) comparisons in the decision-tree model, and random key comparisons trigger CPU branch mispredictions (~15–20 cycles per miss on modern x86_64 pipelines). In database query engines, columnar analytics (DuckDB, ClickHouse), GPU sorting (CUB/Thrust), and network packet schedulers, sorting millions of 32-bit or 64-bit keys using LSD/MSD Radix Sort cuts CPU cycles by 3x–8x and saturates memory bandwidth instead of stalling on conditional branches.

  • Counting Sort runs in O(n + k) time and O(n + k) auxiliary space by computing a frequency histogram, taking a prefix sum for destination offsets, and scattering elements stably.
  • Radix Sort decomposes a w-bit key into d = ceil(w / r) digits of r bits each (typically r = 8 or r = 11, giving radix b = 256 or 2048) and runs Counting Sort per digit.
  • LSD (Least Significant Digit) Radix Sort processes digits right-to-left and requires each pass to be stable, whereas MSD (Most Significant Digit) recurses left-to-right and enables early termination on distinct prefixes.
  • Choosing radix r = 8 (256 buckets, 1 KB histogram in L1d cache) or r = 11 (2,048 buckets, 8 KB histogram in L1d cache) keeps the entire count array inside the 32–48 KB L1 data cache.
  • IEEE-754 floats and signed two's-complement integers can be radix-sorted without custom comparators using deterministic bit-flipping bijections (flipping the sign bit for signed ints; conditionally flipping all bits if negative for floats).

Good candidates

  • Sorting large arrays (n > 10,000) of fixed-width integers, timestamps, IPv4/IPv6 addresses, or IEEE-754 floats where key bit-width is small (32–128 bits).
  • Building high-throughput database operators (hash-join partitioning, columnar dictionary encoding, LSM-tree SSTable compaction) where branch-free throughput matters.
  • Sorting strings or byte-slices with shared prefixes using MSD Radix Sort (American Flag Sort) combined with insertion sort for small buckets (n <= 16).

Think twice

  • Keys have a huge or unbounded value range k >> n (e.g., 64-bit UUIDs with pure Counting Sort), which blows up histogram memory to O(k).
  • Sorting small arrays (n < 64) where allocation and histogram-clearing overhead exceed O(n log n) comparison costs.
  • Ordering depends on arbitrary runtime comparators (locale-aware collation, multi-column dynamic SQL expressions) that cannot be mapped to lexicographic byte order.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA ClickHouse/DuckDB-style analytics query executes ORDER BY event_ts_ns LIMIT 100000000 on 100 million 8-byte nanosecond timestamps.

The idea

Every comparison-based sorting algorithm—Quicksort, Mergesort, Heapsort, Timsort—models ordering as a binary decision tree. Because n! permutations require at least log2(n!) = Ω(n log n) binary decisions, no comparison sort can break that asymptotic barrier.

Counting Sort and Radix Sort sidestep comparisons entirely by exploiting the internal representation of keys. Counting Sort treats a key in [0, k) as a direct array index, tallying frequencies in a histogram, converting frequencies into starting write offsets via an exclusive prefix sum, and scattering elements into their final positions in O(n + k) time. Radix Sort generalizes this to large w-bit keys by slicing each key into d digits of r bits (base b = 2^r) and executing Counting Sort once per digit, achieving O(d(n + b)) time with zero key-to-key comparisons and zero data-dependent branches.

Concrete walkthrough

Consider sorting 4 unsigned 16-bit integers [0x031A, 0x01FF, 0x0302, 0x0102] using 8-bit LSD Radix Sort (d = 2 passes, b = 256):

  1. Pass 0 (Low byte, shift = 0, mask = 0xFF):

    • Extract low bytes: 0x1A, 0xFF, 0x02, 0x02.
    • Histogram counts: count[0x02] = 2, count[0x1A] = 1, count[0xFF] = 1.
    • Exclusive prefix sum offsets: offset[0x02] = 0, offset[0x1A] = 2, offset[0xFF] = 3.
    • Stable scatter left-to-right into scratch buffer: [0x0302, 0x0102, 0x031A, 0x01FF].

  2. Pass 1 (High byte, shift = 8, mask = 0xFF):

    • Extract high bytes from scratch buffer: 0x03, 0x01, 0x03, 0x01.
    • Histogram counts: count[0x01] = 2, count[0x03] = 2.
    • Exclusive prefix sum offsets: offset[0x01] = 0, offset[0x03] = 2.
    • Stable scatter back to input buffer: [0x0102, 0x01FF, 0x0302, 0x031A].

Notice how stability on Pass 1 preserved the relative order of 0x0102 before 0x01FF (both high byte 0x01) and 0x0302 before 0x031A (both high byte 0x03).

Each LSD Radix Sort pass performs two sequential reads of the input buffer, an L1-resident prefix sum, and one scattered write to the ping-pong buffer.

Hardware & cache mechanics

Modern CPUs spend up to 15–20 cycles recovering from a branch misprediction. In Quicksort, partitioning around a median compares unpredictable keys, causing ~50% branch misprediction rates on random inputs until branchless CMOV optimizations are applied. Radix Sort has zero key-comparison branches.

Its bottleneck shifts entirely to L1d cache capacity and store-buffer/TLB pressure during the scatter phase. With r = 8 bits (256 buckets * 4-byte uint32 counts = 1 KB), the histogram fits comfortably inside a 32 KB or 48 KB L1d cache alongside loop variables. Furthermore, fusing histogram computation for all d passes into a single pre-scan of the input array eliminates half of the read traffic—a standard optimization in Ska Sort and IPS4o-style hybrids.

Failure modes

  1. L1/TLB thrashing from oversized radix: Picking r = 16 (65,536 buckets) creates a 256 KB histogram and scatters across 65,536 distinct streams, overflowing the 64-entry L1 DTLB.
  2. Signed & IEEE-754 ordering bugs: Negative two's-complement integers have MSB = 1, and negative IEEE-754 floats are stored in sign-magnitude order (more negative = larger bit pattern). Failing to apply the order-preserving bijection scrambles negative values.
  3. Degenerate MSD recursion: Deeply shared prefixes in MSD Radix Sort without a small-bucket cutoff (e.g., n <= 16 -> Insertion Sort) waste stack frames and zeroing cycles on 1-element buckets.
  4. Memory bandwidth saturation on small n: For n < 1,000, allocating a scratch buffer and clearing 256-entry histograms costs more than an in-cache Insertion Sort or Quicksort.

Production adoption & hybrids

Production systems rarely use textbook Counting Sort in isolation; they use cache-aware hybrids:

  • Rust radsort / C++ ska_sort: Pre-compute all d histograms in a single pass, skip any digit pass where all keys share the same byte value (histogram[v] == n), and fall back to Insertion Sort on small MSD partitions.
  • GPU Radix Sort (NVIDIA CUB DeviceRadixSort): Uses 4-bit or 8-bit digits with warp-level shared-memory histograms and decoupled look-back prefix sums to sort >10 billion 32-bit keys/sec on H100 GPUs.
  • DuckDB & ClickHouse: Combine 8-bit MSD Radix Sort with normalized binary sort keys (encoding NULL flags, descending order via bitwise NOT, and fixed-prefix string bytes) so multi-column SQL ORDER BY executes as a pure byte-wise radix sort.

Practical checklist

  • Verify keys can be bijected into fixed-width unsigned integers or lexicographic byte strings.
  • Apply sign-bit XOR for signed integers and conditional bit-flip for IEEE-754 floats before pass 0, then invert on completion.
  • Use r = 8 bits (256 buckets) as the default radix to guarantee L1d cache residency.
  • Pre-compute all d pass histograms in one initial scan and skip passes where a single bucket holds all n elements.
  • Fall back to Insertion Sort or Introsort when n < 64 (or when MSD bucket size drops below 16).
  • Benchmark against std::sort / slices.Sort on both uniform random and skewed/pre-sorted distributions.
03 / Engineering trade-offs

Weighing architectural decisions

Radix Bit-Width (r)

Advantage: Larger r (e.g., r = 11 or 16) reduces the number of full-array passes d = ceil(w / r), cutting memory bandwidth traffic.

Drawback: Histogram size grows as 2^r (65,536 entries * 4 bytes = 256 KB for r = 16), spilling out of L1d cache (32–48 KB) into L2/L3 and stalling scatter writes.

LSD vs. MSD Traversal

Advantage: LSD has completely predictable, non-recursive passes with uniform vectorizable loops and guaranteed stability.

Drawback: LSD always inspects every digit of every key even if keys diverge in the top byte, whereas MSD can short-circuit and run in-place.

Auxiliary Memory vs. In-Place

Advantage: Out-of-place ping-pong buffers (2 * n * sizeof(T)) allow sequential reads and clean prefix-sum scatters.

Drawback: Doubles peak RAM footprint compared to in-place American Flag Sort or Introsort, which matters when sorting multi-gigabyte buffers.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Histogram L1 Cache Thrashing

Picking a 16-bit radix (65,536 buckets = 256–512 KB) causes every scatter increment to miss L1d cache and hit L2/L3.

What helps: Cap radix at 8 bits (256 buckets, 1–2 KB) or 11 bits (2,048 buckets, 8–16 KB) so the entire histogram stays resident in L1d.

Signed Integer & Float Sign-Bit Inversion

Treating two's-complement negative integers or negative IEEE-754 floats as unsigned bit patterns places negative numbers after positive numbers (and reverses negative float order).

What helps: XOR the sign bit (key ^ (1 << (w - 1))) for signed integers; for IEEE-754 floats, flip all bits if sign bit is 1, else flip only the sign bit, then invert the transform after sorting.

TLB & Cache-Line Aliasing on Scatter

Writing to 256+ scattered bucket pointers in a single pass can exceed the CPU's L1 TLB entries (typically 64) or cause write-combining buffer thrashing.

What helps: Use small software write-combining buffers (e.g., 8–16 elements per bucket in L1) or keep radix to 8 bits with 4-KB page-aligned ping-pong buffers.

Unbounded Key Range in Pure Counting Sort

Running Counting Sort directly on sparse 32-bit IDs (k = 2^32) allocates 16 GB of zeroed count arrays and triggers OOM.

What helps: Never use single-pass Counting Sort when k > 4 * n; switch to multi-pass Radix Sort with bounded bucket size b = 256.

05 / Practical checklist

Avoid these mistakes

  • Using unstable Counting Sort inside an LSD Radix Sort loop, which destroys the ordering established by lower-significance digits.
  • Forgetting to zero-initialize the histogram array between radix passes, corrupting prefix-sum offsets.
  • Allocating new output arrays inside every recursive call of MSD Radix Sort instead of reusing a single scratch buffer or sorting in-place.
  • Applying LSD Radix Sort to variable-length strings without right-padding shorter strings with a sentinel smaller than any valid character.
  • Benchmarking Radix Sort only on uniformly random integers and missing the fact that pre-sorted or nearly-sorted inputs still pay full d-pass bandwidth.
