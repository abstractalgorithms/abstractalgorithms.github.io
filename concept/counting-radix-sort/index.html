What are Counting Sort & Radix Sort.

Comparison sorts (Quicksort, Mergesort, Timsort) require at least log2(n!) = Ω(n log n) comparisons. Counting Sort sidesteps comparisons by treating each integer key in [0, k) as a direct array index: tallying a frequency histogram, converting frequencies to destination offsets via an exclusive prefix sum, and scattering elements stably in O(n + k) time.

Radix Sort generalizes this to w-bit keys by slicing each key into d = ceil(w / r) digits of r bits (base b = 2^r, typically r = 8 -> 256 buckets) and running Counting Sort once per digit in O(d(n + b)) time with zero data-dependent branches.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Branch-Free Distribution Sorting.

Modern CPUs spend 15–20 cycles recovering from a branch misprediction. On random inputs, Quicksort suffers ~50% branch mispredictions. Eliminating key comparisons saturates memory bandwidth instead of stalling CPU pipelines, yielding 3x–8x speedups in columnar databases (DuckDB, ClickHouse) and GPU sorters.

An 8-pass LSD Radix Sort (8-bit radix, 256-entry L1-resident histogram) sorted 100M nanosecond timestamps in ~420 ms on one core with zero branch mispredictions vs ~2.8s for std::sort (6.6x speedup).

In-Place MSD American Flag Sort for URLs

Sorting 5M URL paths (avg 48 bytes) via MSD Radix Sort partitioned on byte 0 and fell back to Insertion Sort below 16 elements, cutting L3 cache misses by 45%.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Counting & Radix Sort Excel (and Where They Fail).

Distribution sorting shines on large batches of fixed-width keys or prefix-heavy byte slices, and loses to comparison sorts when n is small or comparators are arbitrary.

ChoiceWhat it buysWhat it costs
Use: Large Fixed-Width Keys (n > 10,000)32/64-bit ints, timestamps, IPv4/v6, and IEEE-754 floats sort in O(d * n) with zero branch misses.Out-of-place LSD uses 2x array memory (ping-pong buffer).
Use: Prefix-Heavy Strings (MSD + Insertion Cutoff)Short-circuits as soon as prefixes diverge and can run in-place.Must switch to Insertion Sort when bucket size drops below ~16.
Avoid: Sparse Unbounded Keys in Counting Sort (k >> n)Switching to `std::sort`/Timsort avoids allocating 16 GB histograms for sparse 32/64-bit IDs.Never run single-pass Counting Sort when `k > 4 * n`.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to handle Signed Ints, IEEE-754 Floats & L1d Sizing.

  1. Radix Width (r = 8 or 11): r = 8 (256 buckets * 4B = 1 KB) fits entirely inside a 32–48 KB L1d cache. Picking r = 16 (256 KB) thrash-misses L1d and the 64-entry L1 DTLB.
  2. Signed & Float Bijections: Two's-complement negatives have MSB=1 (key ^ 0x80000000 fixes signed int32). Negative IEEE-754 floats are sign-magnitude reversed (flip all bits if negative, else flip only the sign bit).
  3. Pre-Scan & Skip: Compute all d histograms in one initial pass and skip any byte pass where histogram[v] == n.
# 8-bit LSD Radix Sort for signed 32-bit integers via sign-bit bijection (Python)
def radix_sort_int32(nums: list[int]) -> list[int]:
    if len(nums) < 2:
        return nums
    # Map signed int32 [-2^31, 2^31-1] -> unsigned [0, 2^32-1]
    arr = [(x & 0xFFFFFFFF) ^ 0x80000000 for x in nums]
    out = [0] * len(arr)
    for shift in (0, 8, 16, 24):
        count = [0] * 256
        for v in arr:
            count[(v >> shift) & 0xFF] += 1
        pos = 0
        for b in range(256):
            c = count[b]
            count[b] = pos
            pos += c
        for v in arr:
            b = (v >> shift) & 0xFF
            out[count[b]] = v
            count[b] += 1
        arr, out = out, arr
    return [((x ^ 0x80000000) - (1 << 32) if (x ^ 0x80000000) & 0x80000000 else (x ^ 0x80000000)) for x in arr]

Alternatives: Counting vs. LSD vs. MSD vs. Introsort/Timsort.

Compare sorting algorithms across asymptotic complexity, extra memory, branch behavior, and stability.

Production Architecture: L1d-Resident Histogram & Write-Combining Scatter.

Production hybrids like Rust radsort, C++ ska_sort, DuckDB, and NVIDIA CUB DeviceRadixSort fuse all d histograms into a single read pass and keep the 256-entry count table pinned in L1d cache (1 KB) or GPU shared memory.
