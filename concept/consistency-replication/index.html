Quorum Consistency & Raft Consensus

Guarantee strong consistency across distributed database nodes using Quorum math (R + W > N) and Raft leader election.

Orientation & Intuition

Data replication copies datasets across multiple network nodes to ensure high availability, read scalability, and disaster fault tolerance. Managing replicas forces architects to navigate the fundamental trade-off between strong consistency (immediate linearizability) and high availability during network partitions (CAP and PACELC Theorems).

Key takeaway Select your replication topology deliberately: Single-Leader (Raft/Paxos) guarantees strict serializability at the expense of write downtime during leader failover; Leaderless (Dynamo/Cassandra) maximizes write availability through Quorums (R + W > N) and eventual consistency.

Core Architecture & Trade-offs

Single database instances inevitably experience hardware failures, power outages, and routine maintenance. Without replication, a hardware crash causes permanent data loss and customer downtime. With replication, systems survive node crashes seamlessly.

Key Architecture Invariants

  • Single-Leader Replication: All writes route to a designated leader, which streams change logs to followers. Simple consistency model, but the leader is a write bottleneck and failover introduces downtime.
  • Leaderless Replication: Clients write to and read from multiple replica nodes concurrently. Governed by Quorum arithmetic: $R + W > N$.
  • Synchronous vs Asynchronous Replication: Synchronous replication guarantees zero data loss ($RPO=0$) at the cost of high write latency. Asynchronous replication delivers sub-millisecond writes, but risks data loss during ungraceful leader crashes.
  • Replication Lag Anomalies: Asynchronous follower lag causes read-after-write inconsistencies (users submit a comment, refresh, and do not see their comment).
  • Quorum Tuning: In an $N=3$ cluster, setting $W=2, R=2$ guarantees that the read set and write set overlap by at least one node holding the newest version.

When to Use

  • Building fault-tolerant systems that survive hardware failure without data loss or downtime.
  • Scaling read-heavy applications by distributing read queries across multiple read replicas.
  • Multi-region global deployments providing low-latency reads close to international users.
  • Disaster recovery planning with cross-datacenter asynchronous replication standby pairs.

When NOT to Use

  • Ephemeral scratch caches or temporary worker queues where lost data can simply be recomputed.
  • Single-instance edge devices or embedded IoT microcontrollers with limited storage and network connectivity.

Deep Dive & Production Considerations

📖 Operational Architecture of Distributed Replication

Replication copies data across physically separate nodes to ensure data survives hardware destruction and network outages. The central challenge of distributed replication is coordinating concurrent mutations across unbonded, asynchronous network channels.

⚙️ Quorum Arithmetic in Practice

In leaderless replication (Cassandra, DynamoDB, Amazon S3), consistency is governed by three variables:

  • $N$: The replication factor (number of nodes storing a copy of the key).
  • $W$: The write quorum (number of nodes that must acknowledge a write before success).
  • $R$: The read quorum (number of nodes that must respond to a read before returning).

$$\mathbf{R + W > N} \implies \text{Read and Write Quorum Sets MUST Overlap!}$$

If an $N=3$ cluster is configured with $W=2$ and $R=2$:

  • $R + W = 4 > 3$.
  • At least one node in the read quorum is mathematically guaranteed to be part of the write quorum that accepted the latest mutation.
