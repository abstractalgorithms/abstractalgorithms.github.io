STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is gRPC & How It Maps onto HTTP/2.

Why this matters: The mechanism: understand how gRPC & How It Maps onto HTTP/2 works from first principles.

REST/JSON over HTTP/1.1 burns CPU parsing text keys and stalls behind connection-pool limits. gRPC serializes strongly typed .proto contracts into binary Protocol Buffers (proto3) over persistent HTTP/2 connections.

Each RPC maps to an HTTP/2 stream: initial HEADERS carry :path (/pkg.Svc/Method) and grpc-timeout (500m), DATA frames carry 5-byte length-prefixed Protobuf messages (1B compressed flag + 4B big-endian length + payload), and trailing HEADERS (END_STREAM) deliver grpc-status (0 OK, 4 DEADLINE_EXCEEDED, 14 UNAVAILABLE).

Wire Protocol & Deadlines

HTTP/2 Stream Framing & Cascading grpc-timeout Propagation

gRPC propagates remaining deadline budgets across hops so downstream services abort wasted work immediately.

Engineering Decision Framework
Problem
How to implement gRPC & Streaming RPC over HTTP/2 without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
If latency budgets leave no room for synchronous retries, gRPC cuts serialization and connection overhead for internal microservices and real-time streams, but HTTP/2's single-TCP-connection multiplexing breaks naive L4 load balancing.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

ChoiceWhat it buysWhat it costs

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Streaming Chunks Instead of Giant Payloads & Protobuf Safety.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Think of Streaming Chunks Instead of Giant Payloads & Protobuf Safety as the intuition layer for gRPC & Streaming RPC over HTTP/2: Operational control: configure bounds, failure handling, and safe production defaults.

gRPC enforces a default 4 MB max message size (RESOURCE_EXHAUSTED). Instead of raising it to 100 MB, convert large list responses into server-streaming RPCs emitting 64–256 KiB chunks, and align client keepalive_time_ms (>=60s) with server enforcement to avoid ENHANCE_YOUR_CALM disconnects.

Request & State Flow

Streaming Chunks Instead of Giant Payloads & Protobuf Safety

syntax = "proto3";
package catalog.v1;

service CatalogService {
  // Stream 64-256 KiB chunks instead of hitting 4 MB RESOURCE_EXHAUSTED
  rpc StreamCatalogUpdates(CatalogFilter) returns (stream ProductChunk);
}

message ProductChunk {
  reserved 3;
  reserved "legacy_sku";
  string product_id = 1;
  int64 price_cents = 2;
  int64 updated_unix_ms = 4;
}

Production Topology: L7 Envoy Load Balancing for HTTP/2.

Why this matters: Production architecture: see how the components compose end to end under real load.

Think of Production Topology: L7 Envoy Load Balancing for HTTP/2 as the intuition layer for gRPC & Streaming RPC over HTTP/2: Production architecture: see how the components compose end to end under real load.

Because gRPC multiplexes 100+ concurrent streams over a single persistent TCP connection, a naive L4 load balancer routes all RPCs to the first pod—leaving newly autoscaled pods idle! Production clusters deploy L7 proxies (Envoy/Istio) or client-side round_robin via headless Kubernetes Services.

L7 Load Balancing

Why L4 Pins gRPC — And How L7 Envoy Multiplexes Per-RPC

1.L4 Trap: L4 balances per TCP connection, pinning 100% of traffic to old pods after HPA scale-out.

2.L7 / Headless Fix: Envoy L7 or client-side round_robin over headless DNS spreads individual RPCs evenly.

3.Keepalive Alignment: Match client keepalive >=60s with server limits to prevent GOAWAY ENHANCE_YOUR_CALM.

L7-aware load balancing (or client-side round_robin) is mandatory to scale gRPC horizontally across pods.
