THE BIG IDEA / Key takeaway · CONCEPT GUIDE

gRPC cuts serialization and connection overhead for internal microservices and real-time streams, but HTTP/2's single-TCP-connection multiplexing breaks naive L4 load balancing.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

REST/JSON over HTTP/1.1 wastes CPU parsing text keys and stalls behind head-of-line connection limits when microservices chat thousands of times per second. gRPC uses binary Protocol Buffers (proto3) over HTTP/2, packing dozens of concurrent RPCs and long-lived bidirectional streams onto one TLS connection with built-in deadlines (grpc-timeout), cancellation propagation, and flow control.

  • Every gRPC message is wrapped in a 5-byte Length-Prefixed Message frame inside HTTP/2 DATA frames: 1 byte compression flag + 4-byte big-endian uint32 length + Protobuf bytes.
  • HTTP/2 HEADERS carry :path (/package.Service/Method) and grpc-timeout (e.g., 500m), while a trailing HEADERS frame (END_STREAM) delivers grpc-status (e.g., 0 OK, 4 DEADLINE_EXCEEDED, 14 UNAVAILABLE).
  • HTTP/2 flow control (WINDOW_UPDATE frames, 64 KiB default window) applies backpressure per stream and per connection so a slow consumer cannot OOM a fast producer.
  • Because HTTP/2 pins multiple RPCs to one long-lived TCP connection, L4 TCP load balancers route all traffic to a single pod; you must use L7-aware balancing (Envoy, Linkerd, or client-side xDS).
  • Protobuf wire format tags fields by integer field number (varints, 64-bit, length-delimited) rather than field names—making field renames free while making tag reuse a silent data-corruption bug.

Good candidates

  • Internal service-to-service communication in polyglot stacks (Go, Java, Python, Rust) where strict .proto contracts and 3–10x smaller payloads matter.
  • Real-time streaming pipelines—live telemetry ingestion, LLM token streaming, or financial order-book ticks—using server or bidirectional streaming.
  • Low-latency mobile-to-edge or edge-to-core APIs that benefit from HPACK header compression and deadline propagation across call trees.

Think twice

  • Direct browser-to-backend calls without a proxy; browsers do not expose raw HTTP/2 trailers (grpc-status), requiring gRPC-Web translation via Envoy.
  • Public third-party APIs where human-readable curl debugging, OpenAPI tooling, and HTTP caching semantics matter more than binary efficiency.
  • Simple CRUD services with low QPS (< 100 RPS) where JSON/REST keeps debugging and schema evolution effortless.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA mobile app streams 20 ms Opus audio chunks to an ASR service while receiving partial word hypotheses back before the user finishes speaking.

The idea

gRPC is an RPC framework built directly on top of HTTP/2 and Protocol Buffers. Where HTTP/1.1 opens multiple TCP connections and repeats verbose text headers (Content-Type, Authorization, User-Agent) on every call, gRPC establishes one long-lived TCP/TLS connection and splits it into independent bidirectional HTTP/2 streams.

Each RPC maps to a single HTTP/2 stream ID (odd integers 1, 3, 5... initiated by the client). Request metadata travels in a HEADERS frame compressed with HPACK (reducing repeated headers to 1–2 byte table indices), serialized Protobuf messages travel in 5-byte length-prefixed DATA frames, and the final RPC outcome (grpc-status and grpc-message) is delivered in a trailing HEADERS frame with the END_STREAM flag set.

Concrete walkthrough

Trace a server-streaming RPC rpc WatchMetrics(WatchRequest) returns (stream MetricPoint) between a Go client and a Rust tonic server:

  1. Stream Open (HEADERS): The client allocates Stream 1 and sends :method = POST, :path = /telemetry.v1.Metrics/WatchMetrics, content-type = application/grpc+proto, and grpc-timeout = 30S.
  2. Request Payload (DATA + END_STREAM): The client serializes WatchRequest{host: "prod-db-1"} (11 bytes) with a 5-byte prefix (0x00 0x00 0x00 0x00 0x0B), sends it in a DATA frame with END_STREAM, half-closing its side of Stream 1.
  3. Server Stream Emission: The server reads WatchRequest, subscribes to an internal channel, and sends HEADERS (:status = 200, content-type = application/grpc+proto) followed by a DATA frame every 500 ms for each MetricPoint.
  4. Backpressure (WINDOW_UPDATE): If the client pauses reading for 10 seconds, its local 64 KiB stream receive buffer fills up. The client stops sending HTTP/2 WINDOW_UPDATE frames, forcing the server's tonic sender .send().await to suspend cleanly instead of buffering unbounded RAM.
  5. Graceful Close (Trailers): When the watch finishes (or the client sends RST_STREAM to cancel), the server emits trailing HEADERS with grpc-status: 0 and END_STREAM.

Unlike L4 proxies that pin an entire HTTP/2 connection to one pod, an L7 gRPC-aware proxy distributes individual multiplexed streams across backend pods.

The four RPC streaming patterns

gRPC models all communication using four combinations of unary and streaming endpoints:

  • Unary (Req -> Res): Request-response equivalent to REST, ideal for lookups and mutations under 1 MB with strict deadlines.
  • Server Streaming (Req -> stream Res): One request opens a push feed. Replaces polling and chunked pagination for search results, log tailing, or LLM token generation.
  • Client Streaming (stream Req -> Res): Client uploads an unbounded sequence of chunks (file uploads, IoT sensor batches) and receives a single summary receipt once it half-closes the stream.
  • Bidirectional Streaming (stream Req -> stream Res): Both sides read and write independently on the same HTTP/2 stream. Because HTTP/2 frames are full-duplex, the server can push messages before the client finishes sending, enabling real-time chat, collaborative editing, and audio/video pipelines.

Failure modes

  • Unbounded channel memory in async handlers: If a server spawns a producer task that pushes into an unbounded mpsc queue faster than HTTP/2 WINDOW_UPDATE drains the socket, the server process OOMs. Always use bounded channels (capacity = 32–128) so backpressure propagates from the socket back to the database/Kafka reader.
  • Half-open zombie streams: In NATed mobile networks or idle load balancers (AWS ALB/NLB idle timeout = 60–350 s), silent TCP drops leave streams stuck without FIN. Configure keepalive_time_ms + keepalive_timeout_ms on both client and server.
  • Retry amplification: Enabling automatic gRPC retries for UNAVAILABLE without a retryThrottling token bucket can 3x–5x traffic during a partial outage, turning a brief blip into a sustained collapse.
  • TCP head-of-line blocking: Because all HTTP/2 streams share one TCP connection, 2% packet loss stalls every active RPC on that channel until TCP retransmits.

Deadlines, retries & health checks

Always attach a concrete deadline to every stub call (context.WithTimeout in Go, withDeadlineAfter in Java)—never rely on server-side defaults alone. Propagate incoming deadlines automatically so downstream services abort work the moment the caller's budget expires.

Implement the standard gRPC Health Checking Protocol (grpc.health.v1.Health/Check and Watch) so Kubernetes probes and Envoy outlier detection know when a pod is draining (NOT_SERVING) before closing active streams with GOAWAY. For retries, configure serviceConfig JSON only on idempotent methods (UNAVAILABLE with exponential backoff and maxAttempts: 3) and always enable retryThrottling (maxTokens: 10, tokenRatio: 0.1).

Practical checklist

  • Enforce buf lint and buf breaking in CI and mark all removed Protobuf fields with reserved tag numbers and names.
  • Set explicit per-RPC deadlines (grpc-timeout) on every client call and check ctx.Err() / isCancelled() inside long-running loops.
  • Use L7 load balancing (Envoy, Linkerd, or client-side xDS/round_robin) rather than L4 TCP balancing.
  • Bound internal streaming buffers so HTTP/2 flow control (WINDOW_UPDATE) propagates backpressure to upstream producers.
  • Align keepalive_time_ms and max_connection_age_ms across client, proxy, and server to avoid ENHANCE_YOUR_CALM GOAWAY errors.
  • Implement grpc.health.v1.Health and drain active streams gracefully on SIGTERM before shutting down the listener.
03 / Engineering trade-offs

Weighing architectural decisions

Throughput & payload size

Advantage: Binary Protobuf + HPACK cuts payload size by 40–70% and serialization CPU by 3–5x compared to JSON.

Drawback: Payloads are opaque on the wire; inspecting traffic requires `.proto` descriptors (`grpcurl`, Wireshark Protobuf dissector) instead of plain text logs.

Connection efficiency vs. load balancing

Advantage: One persistent TCP/TLS connection supports `max_concurrent_streams` (typically 100) concurrent RPCs with zero TLS handshake tax per call.

Drawback: New Kubernetes pods receive zero traffic from existing clients unless you deploy an L7 proxy (Envoy), client-side round-robin with DNS/xDS, or `MAX_CONNECTION_AGE` rotation.

Streaming backpressure

Advantage: HTTP/2 `WINDOW_UPDATE` frames pause fast senders automatically when a receiver's buffer fills.

Drawback: A single stalled TCP connection (packet loss) causes TCP head-of-line blocking across all multiplexed streams on that connection.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

L4 load balancer hot-spotting

Clients open persistent HTTP/2 connections through a Kubernetes `ClusterIP` (iptables/IPVS L4). When deployment scales from 2 to 10 pods, existing clients stay pinned to the original 2 pods.

What helps: Use L7 gRPC load balancing (Envoy, Istio, or gRPC client-side `round_robin` via headless DNS) and set `grpc.max_connection_age_ms` (e.g., 300,000 ms) so clients periodically rebalance.

RESOURCE_EXHAUSTED on large messages

A service returns a 6 MB batch response, exceeding gRPC's default 4 MiB `max_receive_message_length` limit and failing with status code 8 (`RESOURCE_EXHAUSTED`).

What helps: Convert large list responses into server-streaming RPCs (emitting 64–256 KiB chunks) rather than raising `max_receive_message_length` indefinitely.

Silent keepalive disconnects (ENHANCE_YOUR_CALM)

Aggressive client `keepalive_time_ms` pings (e.g., every 5 s on idle connections) trigger the server's `GOAWAY` frame with `ENHANCE_YOUR_CALM` (`too_many_pings`).

What helps: Match client `keepalive_time_ms` (>= 60 s) and `keepalive_permit_without_calls` with the server's `http2_min_recv_ping_interval_without_data_ms` policy.

Breaking wire compatibility by reusing Protobuf tags

A developer deletes `string legacy_id = 3;` and later adds `int64 user_id = 3;`, causing old clients to decode ASCII bytes as corrupted integers.

What helps: Always mark deleted tags/names with `reserved 3; reserved "legacy_id";` and gate PRs with `buf breaking --against '.git#branch=main'`.

05 / Practical checklist

Avoid these mistakes

  • Omitting deadlines on client calls—by default gRPC has no timeout, allowing hung streams to leak goroutines/threads indefinitely.
  • Retrying non-idempotent mutations blindly via gRPC service config (`retryPolicy`) without idempotency keys.
  • Sending multi-megabyte blobs inside a single unary message instead of chunking over a client/server stream.
  • Using `required` semantics in `proto3` mentally—every field in `proto3` is optional on the wire and defaults to zero/empty if unset.
  • Assuming `http.Server` / `nginx` defaults work out of the box without enabling HTTP/2 cleartext (`h2c`) or `grpc_pass`.
