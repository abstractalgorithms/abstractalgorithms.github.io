01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Kappa Architecture.

Lambda architecture forces teams to write and reconcile two separate codebases (e.g., Spark SQL for batch + Flink for real-time), guaranteeing semantic drift between yesterday's dashboard and today's. Kappa Architecture (Jay Kreps) deletes the batch layer.

An immutable partitioned log (Kafka with retention.ms=-1 or Tiered Storage to S3/GCS, or Apache Pulsar) is the Single Source of Truth. One stream codebase (Flink / Kafka Streams) handles both live tailing and historical backfills using event-time watermarks.

Single Code Path

Immutable Kafka Log (Live + Tiered S3) -> Flink v1/v2 -> Atomic View Swap

1.Zero Drift: Live metrics and historical backfills execute the exact same Flink/Kafka Streams code.

2.Tiered Storage: Old Kafka segments offload to S3 (~$0.023/GB-mo) instead of expensive broker NVMe.

3.Isolated Replay: job-v2 writes to view_v2 in isolation; serving alias swaps only after catching up to live tail.

Treating the distributed log as SSOT lets you fix bugs via Blue/Green stream replay without maintaining a separate batch engine.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Blue/Green Replay & Determinism Matter.

When a double-counting bug is discovered in a surge-pricing pipeline, engineers deploy surge-v2 with a fresh consumer group starting 14 days back in Kafka Tiered Storage into view_v2, let it catch up to the live tail, and atomically swap the serving alias—zero downtime and zero batch rewrite.

Deterministic Event-Time Only

During replay, never call System.currentTimeMillis() or side-effecting external APIs—use the Kafka record's event timestamp and temporal dimension joins.

Idle Partition Watermarks

One quiet Kafka partition stalls the global event-time watermark; configure WatermarkStrategy.withIdleness(Duration.ofSeconds(30)).

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Kappa Excels (and Where Batch/Lakehouse Wins).

Kappa shines for event-sourced analytics and real-time ML features; petabyte ad-hoc SQL joins still belong in a lakehouse.

ChoiceWhat it buysWhat it costs
Good Candidate: Fraud Features, CDC Views & Real-Time MetricsSingle codebase guarantees training/serving and live/historical parity.Replaying 90 days of high-volume events requires temporary burst Flink TaskManagers.
Avoid: Complex Multi-Table Ad-Hoc Joins & PageRankSpark/Trino over Iceberg Parquet handles petabyte multi-way joins and ML training far more cheaply.Holding massive multi-table join state inside Flink RocksDB explodes checkpoint sizes.
Avoid: Side-Effecting External API CallsKeep email/webhook side effects out of replayable stream jobs or guard with strict idempotency.Replaying from offset 0 would re-send millions of emails or charges.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Bounded RocksDB State TTL & Idempotent Watermark Config.

Prevent unbounded RocksDB state growth by configuring StateTtlConfig on keyed descriptors and enabling incremental RocksDB checkpoints to S3.

// Flink StateTtlConfig + Idleness Watermark preventing RocksDB bloat & watermark stalls
StateTtlConfig ttlConfig = StateTtlConfig
    .newBuilder(Time.days(30))
    .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
    .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired)
    .cleanupInRocksdbCompactFilter(1000)
    .build();

WatermarkStrategy<Event> wm = WatermarkStrategy
    .<Event>forBoundedOutOfOrderness(Duration.ofSeconds(10))
    .withTimestampAssigner((e, ts) -> e.eventTimeMs())
    .withIdleness(Duration.ofSeconds(30));

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Kappa vs. Lambda vs. Unified Lakehouse (Iceberg + Flink).

Compare stream-only Kappa against dual-pipeline Lambda and modern lakehouse streaming.

ChoiceWhat it buysWhat it costs
Kappa (Kafka Tiered Storage + Flink)One codebase, zero batch/stream semantic drift, and fast Blue/Green offset replays.Reading old segments from S3 Tiered Storage adds API/egress cost during huge replays.
Lambda (Spark Batch + Flink Speed)Leverages specialized batch SQL for petabyte historical joins while keeping speed state tiny.Maintaining two codebases causes 10–15% metric drift at batch/speed boundaries.
Flink + Apache Iceberg Unified LakehouseFlink streams into Iceberg; Spark/Trino runs ad-hoc batch SQL on the exact same ACID tables.Requires scheduled Iceberg compaction to avoid small-file proliferation.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Replay: Throttled Staging Backfill Without Prod DB Meltdown.

Replaying 30 days of Kafka events at 500k events/sec will DDoS your serving database if written live. Always write job-v2 to an isolated view_v2 index with sink rate-limiting, then swap the read alias once lag hits zero.

Blue/Green Stream Replay

Zero-Downtime Offset-0 Backfill & Serving Alias Swap

Isolating replays into view_v2 protects live queries and guarantees an atomic cutover.
