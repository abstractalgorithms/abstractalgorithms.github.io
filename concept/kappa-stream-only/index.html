Kappa Stream-Only
Architecture.

Kappa architecture eliminates the separate batch layer of Lambda architecture by treating an append-only distributed log as the single source of truth for both real-time processing and historical replay.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

One code path, one immutable log: when business logic changes, you spin up a second stream job from offset 0, backfill a new serving table, and atomically swap pointers.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Lambda architecture forces teams to write, test, and reconcile two completely different codebases—say, Spark SQL for nightly batch corrections and Apache Flink for real-time metrics—guaranteeing subtle semantic drift between yesterday's dashboard and today's.

  • Immutable log as SSOT: Apache Kafka (log.retention.ms=-1 or Tiered Storage to S3/GCS) stores the canonical, ordered history of events.
  • Single stream codebase: one Flink or Kafka Streams job handles both live tailing and historical reprocessing using event-time watermarks.
  • Blue/Green replay workflow: to fix a bug or change a schema, deploy job-v2 reading from offset 0 into view_v2, let it catch up to the live tail, and atomically swap the serving alias.
  • Stateful stream processing: engines like Flink embed RocksDB for multi-terabyte keyed state with incremental checkpoints to object storage for exactly-once recovery.
  • Compaction for entity state: Kafka log compaction (cleanup.policy=compact) keeps the latest state per key indefinitely without unbounded storage growth.

Good candidates

  • Real-time analytics, fraud scoring, CDC materialized views, and feature stores where maintaining dual batch/stream codebases causes drift.
  • Event-sourced domains where retaining days, months, or infinite history in Kafka Tiered Storage (S3/GCS) or Apache Pulsar is practical.
  • Teams already invested in stateful stream engines (Apache Flink, Kafka Streams) with deterministic event-time processing.

Think twice

  • Complex multi-table ad-hoc joins, global graph algorithms (PageRank), or ML training over petabytes of cold Parquet data better suited to Spark/Snowflake.
  • Workloads where raw events cannot be retained in a log long enough to cover full historical reprocessing windows.
  • Small organizations without operational expertise in RocksDB state backends, Flink checkpointing, or Kafka topic partitioning.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA ride-sharing surge-pricing pipeline discovers a bug in surge-v1 that double-counted cancelled trip events over the past 14 days.

The idea

Proposed by Jay Kreps in 2014 as a reaction to the operational pain of Lambda architecture, Kappa architecture asks a simple question: if a stream processor can already handle real-time data and you can retain the input log long enough to reprocess it, why maintain a second batch engine at all?

In Kappa, an append-only distributed log (Apache Kafka, Redpanda, or Pulsar) is the canonical source of truth. Both real-time serving and historical corrections execute the exact same stream-processing codebase. When you discover a bug or introduce a new metric, you don't write a Spark backfill script—you deploy version 2 of your stream job reading from offset 0 into a parallel output table, wait for it to catch up to the live tail, and atomically switch the application's read pointer.

Concrete walkthrough

Suppose orders-events (24 partitions, Kafka Tiered Storage in S3) feeds revenue-agg-v1 in Apache Flink, writing hourly totals to OpenSearch index revenue_v1 (aliased as revenue_live).

  1. Bug Discovery: A tax-rounding bug is found in v1 affecting the last 30 days.
  2. Parallel Deploy: Engineers deploy revenue-agg-v2 with a fresh consumer group (group-v2) configured with auto.offset.reset=earliest (or a timestamp offset from 30 days ago) and target index revenue_v2.
  3. Catch-Up Replay: Flink scales to 48 TaskManagers, streams 30 days of historical segments from S3 Tiered Storage using event-time watermarks, and builds revenue_v2 in 35 minutes without touching revenue_v1.
  4. Atomic Swap & Decommission: Once group-v2 consumer lag hits ~0 (matching v1 at the live tail), an atomic OpenSearch _aliases swap points revenue_live from revenue_v1 to revenue_v2. revenue-agg-v1 and revenue_v1 are then safely retired.

Kappa replay pattern: a single immutable log feeds both the live v1 pipeline and a parallel v2 historical replay before an atomic serving-view swap.

Event time, watermarks, and deterministic state

For a replay to produce the exact same output as live execution, the stream engine must be strictly deterministic:

  • Event Time over Processing Time: Always window by the timestamp embedded in the event payload (order.created_at), never the wall clock of the Flink TaskManager.
  • Watermarks: A watermark W(t) asserts that no more events with timestamp < t are expected. During a fast replay, event-time windows close deterministically based on the data's own timestamps rather than real-world seconds.
  • Enrichment Joins: Never call a live REST API (GET /users/{id}) inside a map() function during replay—the user's address today may differ from 30 days ago. Instead, ingest a CDC stream (Debezium -> Kafka) and use a Flink Temporal Table Join (FOR SYSTEM_TIME AS OF).

Failure modes

  • Schema evolution breakage: Replaying 6-month-old Avro/Protobuf events crashes v2 if a non-nullable field was added recently without backward-compatible defaults. Enforce BACKWARD or FULL compatibility in Schema Registry.
  • Kafka partition-count rigidity: Changing a topic from 12 to 48 partitions breaks key-based ordering for existing keys unless you migrate to a new topic (orders-v2) during a controlled cutover.
  • Unbounded RocksDB checkpoint bloat: Forgetting StateTtlConfig on session or deduplication state causes checkpoint sizes to grow linearly forever.

Scaling Kappa with Tiered Storage and Iceberg

Pure Kafka broker disks become cost-prohibitive beyond 7–30 days of high-volume events. Modern Kappa deployments solve this with Kafka Tiered Storage (KIP-405 / Confluent / Redpanda), which asynchronously ships closed log segments to S3/GCS while keeping hot tail segments in broker page cache. For teams that also need ad-hoc SQL or ML training, Apache Iceberg (or Paimon/Hudi) acts as a complementary lakehouse sink: Flink reads historical Iceberg snapshots in bounded batch mode and seamlessly switches to the live Kafka stream (Flink Hybrid Source) for zero-duplicate cutover.

Practical checklist

  • Use event-time timestamps and bounded-out-of-orderness watermarks with withIdleness on every stream job.
  • Enforce BACKWARD or FULL schema compatibility in Schema Registry so historical replays never fail deserialization.
  • Enable Kafka Tiered Storage (or compacted topics for entity state) sized to your maximum regulatory/bug-fix replay horizon.
  • Isolate all replays into parallel v2 tables/indices and perform atomic alias/view swaps only after lag reaches zero.
  • Replace synchronous external API calls in stream operators with CDC streams and temporal joins.
03 / Engineering trade-offs

Weighing architectural decisions

Operational Simplicity vs. Compute Cost

Advantage: Eliminates maintaining two separate frameworks (Spark batch + Flink stream) and reconciling their outputs.

Drawback: Replaying 90 days of high-volume events through a stream engine requires temporary autoscaling of Flink TaskManagers and RocksDB IOPS.

Log Retention & Storage

Advantage: Kafka Tiered Storage offloads old segments to S3/GCS at ~$0.023/GB-month instead of expensive NVMe broker disks.

Drawback: Reading historical segments from object storage has higher latency and egress/API costs if replayed frequently.

Event-Time Ordering

Advantage: Watermarks and `AllowedLateness` handle out-of-order mobile events deterministically across both live and replay runs.

Drawback: Side-effecting external API calls inside a stream job are unsafe during replay unless gated by idempotency keys or suppressed.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Replay Thundering Herd on Serving DB

Replaying 30 days of events at 500k events/sec hammers the live PostgreSQL/Redis cluster, starving real-time user queries.

What helps: Write replay output to an isolated staging table/index (`view_v2`), throttle sink writes, or bulk-load SSTables/Iceberg files before swapping.

Non-Deterministic Processing on Replay

Stream code calls `System.currentTimeMillis()`, `UUID.randomUUID()`, or queries a mutable external database during enrichment, producing different results on replay.

What helps: Use event-time timestamps from the Kafka record, deterministic IDs, and temporal joins against CDC-streamed dimension tables.

RocksDB State Explosion

Unbounded key cardinality without state TTL causes Flink RocksDB checkpoints to grow to terabytes and time out.

What helps: Configure `StateTtlConfig` on keyed state descriptors and enable incremental RocksDB checkpoints.

Watermark Stall from Idle Partitions

One quiet Kafka partition receives no events for 10 minutes, freezing the global event-time watermark and stalling all windowed outputs.

What helps: Configure `WatermarkStrategy.withIdleness(Duration.ofSeconds(30))` so active partitions advance the watermark.

05 / Practical checklist

Avoid these mistakes

  • Replaying directly into the live production table (`UPSERT` in place), corrupting active views with mixed v1 and v2 aggregations.
  • Using processing time (`System.currentTimeMillis()`) instead of event time, which collapses 30 days of historical events into a single 10-minute window during replay.
  • Keeping infinite retention on raw Kafka NVMe broker disks instead of enabling Tiered Storage or Iceberg/Parquet archival.
  • Forgetting to handle late-arriving events or tombstones (`null` payloads) in compacted topics.
  • Triggering external webhooks, emails, or payment charges directly inside a replayable stream topology without idempotency guards.
