What is Model Context Protocol (MCP).

Why this matters: The mechanism: understand how Model Context Protocol (MCP) works from first principles.

MCP is an open JSON-RPC 2.0 protocol that decouples AI agent runtimes (clients) from external capabilities (servers).

Every MCP server exposes three standardized primitives:

  • Tools: model-invoked functions with strict JSON Schema inputs (queries or side effects). - Resources: URI-addressed read-only context (repo://README.md, db://schema).

Any MCP-compliant client (IDE, LangGraph worker, CLI) can consume the same tool server without custom glue code.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why N×M custom tool wrappers fail—and common MCP pitfalls.

Why this matters: The problem: see what breaks without Why N×M custom tool wrappers fail—and common MCP pitfalls under real concurrency or scale.

Without MCP, every AI framework re-implements custom N×M wrappers for GitHub, Postgres, Jira, and internal APIs. Standardizing on MCP lets teams build and audit one hardened tool server.

Two production pitfalls remain: unbounded tool output flooding the LLM context window (always paginate/truncate) and missing idempotency keys on mutating tools when agents retry.

Design Trade-Off

Why N×M custom tool wrappers fail—and common MCP pitfalls

Before · Static Batch + Raw Prompt
  • Head-of-line blocking on long prompts
  • O(N^2) KV fragmentation
  • Unfiltered RAG leaks ACLs
After · PagedAttention + Guardrails
  • Zero-waste paged KV blocks
  • Pre-retrieval ACL & RRF rerank
  • Continuous batching boosts tok/s

Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision

Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

from mcp.server.fastmcp import FastMCP
from pydantic import Field

mcp = FastMCP("enterprise-orders")

@mcp.tool()
def search_orders(tenant_id: str, limit: int = Field(default=10, le=25)) -> dict:
    """Search recent orders for a tenant (bounded to max 25 rows)."""
    authorize_tenant_scope(tenant_id)
    rows = db.query_orders(tenant_id=tenant_id, limit=limit)
    return {"orders": rows, "truncated": len(rows) == limit}

Enterprise deployments front MCP servers with an OAuth2-authenticated API gateway, separate read-only Resource endpoints from mutating Tools, and require human-in-the-loop confirmation tokens for destructive actions.

Enterprise MCP Edge

Headless Agents -> OAuth2 MCP Gateway -> Paginated Tool Backends

1.1. Token Passthrough: Validate user/workload JWT scopes at the gateway before invoking any tool.

2.2. Context Budget: Enforce le=25 page limits so tool responses never blow up agent context.

3.3. Audit Trail: Log (caller_id, tool_name, redacted_args, latency) for every JSON-RPC call.

Treating MCP servers as zero-trust microservices prevents prompt-injected agents from escalating privileges.
