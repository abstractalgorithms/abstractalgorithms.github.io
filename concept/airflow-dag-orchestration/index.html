STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Airflow DAG Orchestration.

Why this matters: The mechanism: understand how Airflow DAG Orchestration works from first principles.

Apache Airflow models data pipelines as Directed Acyclic Graphs (DAGs) authored in Python, where nodes are tasks (Operators/Sensors) and edges are execution dependencies. Rather than running scripts blindly on wall-clock cron, Airflow tracks every run against a logical data interval (data_interval_start to data_interval_end) persisted in a central Metadata Database (PostgreSQL).

Airflow strictly separates the control plane (Scheduler + Triggerer + Webserver) from the execution plane (Celery/Kubernetes workers) and the compute plane (Snowflake, BigQuery, Spark, dbt).

Why we need DAG Orchestration (and why naive cron fails).

Why this matters: The problem: see what breaks without DAG Orchestration under real concurrency or scale.

Plain cron jobs have no concept of upstream dependencies, backfills, or partial retries. In Airflow, three classic failure modes still trip teams up: Scheduler Parse Bottlenecks from top-level imports (pandas, torch), Non-Idempotent Appends instead of partition overwrites over {{ ds }}, and Metadata DB Connection Exhaustion without PgBouncer.

Engineering Decision Framework
Problem
How to implement Airflow DAG Orchestration without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
To keep storage layouts predictable as data grows, airflow is a control plane, not a data-processing engine: keep DAG files lightweight, push heavy compute to Spark/dbt/Snowflake, and make every task idempotent over its data_interval_start.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

# Idempotent, deferrable Airflow DAG keyed by logical data interval (Python)
from datetime import datetime, timedelta
from airflow.decorators import dag, task
from airflow.providers.amazon.aws.sensors.s3 import S3KeySensor

@dag(
    dag_id="revenue_mart_daily",
    schedule="@daily",
    start_date=datetime(2026, 1, 1),
    catchup=False,
    max_active_runs=2,
    default_args={"retries": 3, "retry_delay": timedelta(minutes=5)},
)
def revenue_mart():
    wait_raw = S3KeySensor(
        task_id="wait_for_s3",
        bucket_name="raw-events",
        bucket_key="dt={{ ds }}/_SUCCESS",
        deferrable=True,
        timeout=3600,
    )

    @task(pool="warehouse_writes", execution_timeout=timedelta(minutes=30))
    def load_partition(ds=None):
        execute_warehouse_merge(partition_date=ds)

    wait_raw >> load_partition()

revenue_mart()

At scale, Airflow runs behind PgBouncer connected to a managed HA PostgreSQL Metadata DB, while workers act as thin launchers submitting Spark/dbt/Snowflake jobs.

Control vs Compute Plane

Airflow Control Plane -> PgBouncer -> K8s Workers -> Snowflake/S3

1.PgBouncer Pooling: Prevents hundreds of ephemeral Kubernetes pods from exhausting PostgreSQL max_connections.

2.Asset & SLA Alerts: execution_timeout and on_failure_callback route missed SLAs directly to PagerDuty.

3.Thin Launchers: Workers never load multi-GB DataFrames; compute runs in dedicated warehouse/Spark clusters.

Separating control plane (Airflow) from compute plane (Snowflake/Spark) keeps scheduling predictable at thousands of DAGs.
