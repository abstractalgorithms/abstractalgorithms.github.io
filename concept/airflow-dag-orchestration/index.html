Airflow DAG
Orchestration.

Apache Airflow orchestrates batch data workflows as Python-defined Directed Acyclic Graphs (DAGs), decoupling scheduling (data_interval_start) from compute execution across workers (CeleryExecutor or KubernetesExecutor) with built-in retries, backfills, and lineage.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Airflow is a control plane, not a data-processing engine: keep DAG files lightweight, push heavy compute to Spark/dbt/Snowflake, and make every task idempotent over its `data_interval_start`.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Chaining brittle cron jobs breaks down as soon as an upstream S3 drop arrives 2 hours late, a downstream table needs a 90-day backfill, or two teams share dependencies. Airflow's scheduler, metadata database, and data_interval model give data teams deterministic retries, dependency graphs, SLA alerting, and one-command historical backfills.

  • A DAG run represents a logical data interval (data_interval_start to data_interval_end), and the scheduler triggers the run after the interval closes.
  • Idempotency is non-negotiable: tasks must safely re-run on retry or backfill using partition overwrites (INSERT OVERWRITE / MERGE), never blind APPEND.
  • Airflow's Scheduler parses DAG Python files every ~30 seconds (min_file_process_interval), so top-level code must never make DB or HTTP calls.
  • Deferrable operators + the Triggerer process suspend long-running waits (S3KeySensor, SnowflakeOperator) in async asyncio loops instead of holding worker slots.
  • XCom (xcom_push/xcom_pull) stores small metadata (row counts, S3 URIs) in the metadata DB—never pass raw DataFrames or multi-MB payloads through it.

Good candidates

  • Scheduled batch ELT/ETL pipelines (hourly, daily, weekly) coordinating S3/GCS, dbt, Spark, Snowflake, or BigQuery.
  • Complex dependency graphs with branching, sensor/deferrable waits for upstream files, and automated SLA alerts.
  • Historical backfills where each past date partition (ds) must be re-run deterministically.

Think twice

  • Sub-second or continuous event streaming (use Apache Flink, Kafka Streams, or Spark Structured Streaming).
  • High-frequency (<1 minute) micro-jobs—Airflow's scheduler loop and task-startup overhead add seconds of latency per task.
  • Running multi-gigabyte Pandas transformations directly inside Airflow worker memory instead of delegating to external compute.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn e-commerce data team needs orders_daily refreshed by 06:00 UTC using yesterday's Stripe and Postgres CDC drops in S3.

The idea

Apache Airflow treats data pipelines as Directed Acyclic Graphs (DAGs) authored in Python, where nodes are tasks (Operators/Sensors) and edges are execution dependencies. Rather than running scripts blindly on wall-clock cron, Airflow tracks every run against a data interval (data_interval_start to data_interval_end) persisted in a central Metadata Database (PostgreSQL).

Crucially, Airflow separates the control plane (Scheduler + Triggerer + Webserver) from the execution plane (Celery/Kubernetes workers) and the compute plane (Snowflake, BigQuery, Spark, dbt). Airflow orchestrates when and in what order work runs, while external engines do the heavy lifting.

Concrete walkthrough

Trace a daily revenue_mart DAG scheduled at @daily (0 0 * * *) for 2026-11-11:

  1. Interval Close & Scheduling: At 2026-11-12 00:00 UTC, the 2026-11-11 interval closes. The Scheduler reads the DAG's serialized definition from the Metadata DB and creates a DagRun with ds = '2026-11-11'.
  2. Deferrable Wait: Task wait_for_s3 (S3KeySensor(deferrable=True)) checks s3://raw-events/dt=2026-11-11/_SUCCESS. Not found yet—so it defers to the Triggerer, freeing its worker slot.
  3. Trigger & Resume: At 00:14 UTC, the Triggerer detects _SUCCESS, marks the trigger complete, and queues the downstream load_snowflake task.
  4. Idempotent Compute: KubernetesExecutor launches a worker pod that executes MERGE INTO orders_mart USING stage_2026_11_11 ... against Snowflake.
  5. Verification & Lineage: dbt_test validates not_null and unique on order_id. If any test fails, Airflow retries per retries=2, retry_delay=5m and fires an on_failure_callback to PagerDuty/Slack.

Airflow's control plane coordinates state in Postgres while delegating heavy data processing to external compute engines.

Execution model, deferrable operators & XCom limits

Two architectural rules govern healthy Airflow deployments:

  • Never Poll on a Worker Slot: Classic poke-mode sensors hold an entire worker process/pod idle while checking S3 or an API every 60 seconds. Switching to deferrable=True moves the wait into the Triggerer, where a single Python asyncio process can monitor thousands of concurrent waits using minimal RAM.
  • Keep XCom Small: XCom is backed by a BYTEA/JSON column in PostgreSQL. Passing a 10 KB config dict or an S3 URI (s3://bucket/run_123/part.parquet) is ideal; passing a DataFrame triggers serialization bottlenecks and database bloat. Use an Object Storage XCom Backend if larger metadata exchange is unavoidable.

Failure modes

  1. Scheduler Parse Bottlenecks: Heavy imports (pandas, torch) or API calls at the top level of DAG files stall the DagFileProcessor, delaying task scheduling across the entire cluster. Fix: Lazy-import heavy libraries inside @task functions.
  2. Non-Idempotent Retries: Appending rows without partition keys corrupts tables on retry. Fix: Parameterize every write with {{ ds }} and use atomic MERGE or partition overwrite.
  3. Metadata DB Connection Exhaustion: Scaling workers without PgBouncer saturates Postgres max_connections. Fix: Place PgBouncer in front of the Metadata DB and use Airflow Pools for external DBs.
  4. Unbounded Backfills: Triggering a 2-year backfill with max_active_runs=16 hammers downstream warehouses simultaneously. Fix: Set max_active_runs=1 or 2 on heavy DAGs.

DAG parsing hygiene, pools & SLA monitoring

Enforce CI checks on every DAG PR: run pytest to verify DagBag() imports in under 2 seconds with zero import errors, and validate that no top-level code touches network sockets.

Use Airflow Pools (--pool warehouse_writes --slots 8) to protect downstream OLTP/OLAP databases from thundering herds during morning peaks, and configure sla / execution_timeout plus on_failure_callback alerts routed to PagerDuty or Slack.

Practical checklist

  • Use static start_date values and catchup=False unless historical catchup is explicitly desired.
  • Parameterize all reads/writes with data_interval_start / {{ ds }}—never datetime.now().
  • Keep top-level DAG files pure (no DB queries, HTTP calls, or Variable.get() outside tasks).
  • Enable deferrable=True on all Sensors and long-running external job operators.
  • Pass only S3/GCS URIs or small metadata via XCom—never raw datasets.
  • Cap max_active_runs and configure Pools + execution_timeout on every production DAG.
03 / Engineering trade-offs

Weighing architectural decisions

CeleryExecutor vs. KubernetesExecutor

Advantage: `CeleryExecutor` keeps warm worker processes running for low-latency (~1s) task startup on high-frequency DAGs.

Drawback: `KubernetesExecutor` isolates every task in its own pod with custom Docker images/resources, but adds 5–15s pod scheduling overhead.

Standard Sensors (`poke`) vs. Deferrable Operators

Advantage: Deferrable operators free the worker slot completely while waiting in the Triggerer's `asyncio` loop, cutting worker costs dramatically.

Drawback: Requires running the `Triggerer` component and writing/using async-compatible triggers.

Dataset-Driven Scheduling vs. ExternalTaskSensor

Advantage: Airflow Datasets (`outlets=[Dataset('s3://...')]`) decouple producer and consumer DAGs without fragile time-delta matching.

Drawback: Makes end-to-end lineage harder to visualize in a single DAG graph compared to unified task groups.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Non-Idempotent Backfill Duplication

A task uses `INSERT INTO target SELECT ...` without deleting or merging the target `ds` partition; retrying a failed run doubles revenue numbers.

What helps: Delete-and-insert by `ds`, use `MERGE`, or write to an immutable partition path (`s3://bucket/dt={{ ds }}/`) with atomic swap.

Top-Level DAG Parsing Timeouts

A developer puts `requests.get(...)` or `Variable.get(...)` at module import level; the Scheduler runs it every 30s across all DAGs, exhausting DB connections and timing out.

What helps: Move all I/O, SQL queries, and `Variable.get` calls inside task callables or Jinja templates (`{{ var.value.my_key }}`).

XCom Metadata DB Bloat & Worker OOM

Tasks pass 50 MB Pandas DataFrames via XCom, bloating Postgres `xcom` tables and crashing workers on `xcom_pull`.

What helps: Write intermediate datasets to S3/GCS/Snowflake and pass only the URI or table name via XCom.

Zombie Tasks & Connection Pool Exhaustion

Long-running Python tasks get OOM-killed without heartbeating, or 200 parallel tasks overwhelm a 20-connection Postgres warehouse.

What helps: Assign Airflow `Pools` (e.g., `postgres_pool` with 10 slots) to throttle concurrency against shared external databases.

05 / Practical checklist

Avoid these mistakes

  • Using `datetime.now()` inside a task instead of `{{ ds }}` / `data_interval_start`, breaking historical backfills.
  • Setting `start_date=datetime.now()` in a DAG definition, which causes the scheduler's start boundary to shift on every parse.
  • Running heavy Spark/ML/Pandas compute inside the Airflow Scheduler or Worker instead of submitting jobs to EMR, Databricks, or K8s pods.
  • Leaving `catchup=True` unintentionally on a DAG with an old `start_date`, triggering thousands of unwanted historical runs on deploy.
  • Using `depends_on_past=True` without understanding that a single failed day stalls every subsequent day indefinitely.
