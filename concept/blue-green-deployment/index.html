01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Blue-Green Deployment.

Blue-green deployment decouples deployment (provisioning new compute, pulling containers, running additive migrations, verifying health) from release (exposing live user traffic). Two parallel environments—Blue (currently live) and Green (newly provisioned)—sit behind a single L7 routing control plane (AWS ALB target groups, Envoy/Istio VirtualService, or Kubernetes Service selector).

Until Green passes automated smoke and synthetic checks on an isolated test listener, zero external users touch it. Release is an atomic pointer flip (100% Blue -> 100% Green), and rollback flips the pointer back in under 5 seconds.

Cutover & Bake Lifecycle

Blue-Green Provision -> Bake -> Atomic Flip / Rollback State Machine

Keeping Blue warm during the bake window enables sub-5-second rollback via an L7 router swap.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Expand-and-Contract & L7 Swaps (and why DNS/destructive DDL fail).

Blue-green fails catastrophically if you treat the database or DNS naively:

  1. Backward-Incompatible Schema: Dropping a column, renaming a field, or changing a Redis JSON/Kafka Avro format breaks Blue the moment you roll back. Always use Expand-and-Contract (additive nullable column first; drop old column only after bake).
  2. DNS TTL Caching: Route 53 weighted DNS fails for instant swaps because recursive resolvers and JVM networkaddress.cache.ttl ignore low TTLs.
  3. DB Connection Pool Exhaustion: During the 30-minute bake, both Blue and Green hold open pools against PostgreSQL—doubling max_connections demand.
Zero-Downtime Cutover

Expand Migration -> Green Smoke Test -> ALB Target Swap -> Drain

Additive expand migrations let Blue and Green share one database safely across the cutover and rollback window.

Connection Draining

Configure deregistration_delay.timeout_seconds = 30 in AWS ALB or terminationGracePeriodSeconds in K8s so in-flight requests finish cleanly.

Async Consumers & WebSockets

Do not let Blue and Green join the same Kafka consumer group blindly; gate polling with a lease or feature flag.

03
STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Blue-Green fits (and when Canary wins).

Blue-green shines when you want zero version skew (only one version serves production at a time) and instant rollback, provided you can afford 2x compute during cutover.

ChoiceWhat it buysWhat it costs
Stateless APIs & Monoliths Requiring Zero Version SkewNo mixed v1/v2 responses for a single user session; instant <5s rollback.Requires 200% peak compute and 2x DB connection capacity during the bake window.
Immutable AMI / Cluster UpgradesValidates a brand-new OS/K8s node group under synthetic load before flipping traffic.Slow provisioning for huge stateful fleets.
Avoid: High-Risk Changes Without Blast-Radius LimitsUse Canary (1% -> 5% -> 25% -> 100%) when a bug could impact 100% of users on flip.Blue-green's 0% -> 100% flip exposes all users immediately if smoke tests miss a production edge case.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Blue-Green Routing, Draining, and Schemas are managed.

Enforce four operational guardrails:

  1. L7 Selector / Target Group Flip: Switch traffic inside the VPC via Kubernetes Service selectors, Envoy VirtualService, or AWS ALB listener rules.
  2. Expand-and-Contract DDL: Ship additive migrations in PR 1, deploy Green in PR 2, contract old columns only after bake.
  3. PgBouncer / Pool Sizing: Route both colors through PgBouncer so 2x app pools don't exhaust Postgres max_connections.
  4. Pre-Warming Caches: Replay read-only shadow traffic or warm local caches on Green before flipping live traffic.
# Kubernetes Service selector flip for atomic Blue -> Green cutover
apiVersion: v1
kind: Service
metadata:
  name: orders-api
  namespace: prod
spec:
  type: ClusterIP
  selector:
    app: orders-api
    slot: green # atomic flip from 'blue' -> 'green' (rollback flips back to 'blue')
  ports:
    - port: 80
      targetPort: 8080
---
# Pod graceful drain matching ALB deregistration_delay (30s)
spec:
  terminationGracePeriodSeconds: 35
  containers:
    - name: orders-api
      lifecycle:
        preStop:
          exec: { command: ["/bin/sh", "-c", "sleep 5"] } # wait for kube-proxy/endpoints sync

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Blue-Green vs. Rolling Update vs. Canary.

Compare compute overhead, rollback speed, and blast radius across the three standard deployment strategies.

ChoiceWhat it buysWhat it costs
Blue-GreenAtomic 0% -> 100% cutover, <5s rollback, zero v1/v2 skew.200% peak compute during bake; 100% blast radius if smoke tests miss a bug.
Rolling UpdateLow compute overhead (105%–125% maxSurge); built into Kubernetes Deployments.Slow rollback (minutes to re-pull/schedule); mixed v1/v2 pods run concurrently.
Canary Deployment (Argo Rollouts)Limits blast radius (1% -> 5% -> 25% -> 100%) with automated metric rollback.Requires L7 traffic splitting and backward-compatible APIs across v1/v2.
06
STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: ALB / Envoy Blue-Green + PgBouncer + Expand/Contract.

Production blue-green setups place PgBouncer between the Blue/Green fleets and PostgreSQL so doubling application pods never exhausts DB connections, while AWS ALB / Envoy performs the atomic L7 swap with a 30-second connection drain.

Zero-Downtime Topology

L7 ALB Swap -> Blue/Green Fleets -> PgBouncer -> Expand-Only Postgres

1.Pool Multiplexing: PgBouncer absorbs 2x application connection pools without exceeding Postgres max_connections.

2.Synthetic + Shadow Test: Green serves internal smoke tests on a preview header before receiving external traffic.

3.30-Min Bake Window: Blue stays warm for 30 minutes post-cutover so any delayed memory leak rolls back in <5 seconds.

L7 routing, PgBouncer pooling, and expand-and-contract DDL make blue-green swaps safe under heavy production load.
