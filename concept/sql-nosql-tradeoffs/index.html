SQL vs. NoSQL Data
Modeling & Workload Selection.

Choosing NoSQL because 'we might have big data someday' forces engineers to hand-code multi-table joins, foreign-key checks, and two-phase rollbacks in application code—bugs that PostgreSQL solves natively for up to 5,000+ TPS and multi-terabyte datasets. Conversely, forcing 200,000 writes/sec of IoT time-series or shopping-cart key-value lookups into a single B+Tree relational primary hits write-amplification and sharding walls early. Match the storage engine to your exact access patterns, transaction boundaries, and write-to-read ratio.

The idea to keep with you

When selecting a primary datastore, default to relational SQL whenever data has rich multi-entity relationships, ad-hoc queries, or multi-row ACID invariants under ~5,000 write TPS, and adopt specialized NoSQL stores only when partition-key access patterns, extreme write throughput, or horizontal multi-region scale justify giving up relational joins.

TL;DR30-second simplified summary
▾

Modeling relational graphs inside NoSQL forces painful application-side joins and multi-table write duplication. Conversely, LSM-tree NoSQL stores excel when writes arrive at 100K+ TPS along known (partition_key, sort_key) boundaries.

Why Relational Data Inside NoSQL Becomes Application-Code Spaghetti.

Why this matters: Contrast entity-first relational modeling against query-first NoSQL partition modeling.

Suppose you build an enterprise project tracker with Organizations, Users, Projects, Tasks, and Permissions. Users filter tasks by assignee, status, tag, due date, and sprint—and moving a task between sprints updates sprint velocity totals atomically.

If you store this in a Key-Value or Wide-Column NoSQL store, every new filter (WHERE assignee = ? AND status = 'OPEN' ORDER BY due_date) requires building and backfilling a brand-new denormalized table (tasks_by_assignee_and_status) and updating 4 duplicate tables on every task edit. In PostgreSQL, adding a composite index (CREATE INDEX CONCURRENTLY ON tasks(assignee_id, status, due_date)) takes one command with zero application rewrite.

STAGE 02 · REPRESENTATION & ENGINE TAXONOMYcore

Relational SQL vs. Key-Value, Document, Wide-Column & Graph Stores.

Why this matters: Map each database family to its underlying data structure and ideal workload.

'NoSQL' is not one architecture—it spans four distinct storage models:

  1. Relational SQL (PostgreSQL, MySQL): B+Tree pages, strict schemas, multi-row ACID transactions, rich SQL optimizer.
  2. Key-Value (DynamoDB, Redis): Hash/B+Tree lookup by primary key (get(k) / put(k, v)), predictable single-digit millisecond latency at massive scale.
  3. Document (MongoDB, Cosmos DB): Self-contained JSON/BSON aggregates where a parent and its owned child array are read/written together atomically.
  4. Wide-Column (Cassandra, ScyllaDB, Bigtable): LSM-tree partitioned by (partition_key, clustering_key), optimized for ultra-high write throughput and range scans within a partition.

Document Store Sweet Spot vs. Trap: Embedding shipping_addresses or line_items inside an Order document works cleanly because line items belong exclusively to one order (1:few bounded aggregate). Embedding reviews inside a Product document breaks once a popular product hits 50,000 reviews and exceeds the 16 MB BSON document limit.

STAGE 03 · INVARIANT & SAFE IMPLEMENTATIONcore

Partition-Key Design & Bounded Aggregate Validation in Python.

Why this matters: Enforce bounded document/partition growth and validate partition-key cardinality before writes.

Whether using DynamoDB, Cassandra, or MongoDB, the #1 production failure is an unbounded partition or document (e.g., partitioning all events by tenant_id without a time bucket, creating a 50 GB partition for one enterprise customer).

from datetime import datetime, timezone

MAX_EMBEDDED_ITEMS = 200

def build_time_bucketed_partition_key(tenant_id: str, event_ts: datetime) -> str:
    if not tenant_id or not tenant_id.strip():
        raise ValueError("tenant_id must be non-empty")
    utc_dt = event_ts.astimezone(timezone.utc)
    # Time-bucketing by YYYY-MM-DD bounds physical partition size and prevents unbounded growth
    return f"{tenant_id.strip()}:{utc_dt.strftime('%Y-%m-%d')}"

def validate_document_aggregate(items: list[dict]) -> None:
    if len(items) > MAX_EMBEDDED_ITEMS:
        raise ValueError(
            f"Embedded array size {len(items)} exceeds bound {MAX_EMBEDDED_ITEMS}; "
            "promote child items to a separate indexed collection/table"
        )

STAGE 04 · MECHANICS AT SCALEdeepDive

B+Tree vs. LSM Write Physics & Polyglot Operational Costs.

Why this matters: Understand storage-engine trade-offs at scale and avoid unnecessary database sprawl.

SQL databases typically use B+Trees (fast in-place point/range reads, higher random write IOPS when indexes outgrow RAM). High-ingest NoSQL engines (Cassandra, RocksDB, ScyllaDB) use LSM-Trees (append-only MemTable + sequential SSTable flushes, absorbing massive write bursts at the cost of background compaction I/O and Bloom-filter read amplification).

When NOT to Adopt Polyglot NoSQL: Every additional database technology adds dedicated backup pipelines, on-call runbooks, IAM/encryption configs, and cross-store CDC sync bugs. Do not introduce Cassandra or MongoDB just to store a 20 GB JSON config table when PostgreSQL JSONB with a GIN index handles it inside your existing cluster.

Engineering Decision Framework
Problem
How to choose the primary storage engine for a new service without over-engineering or hitting early write/query walls.
Naive Solution
Default to NoSQL for every new microservice under the assumption that relational databases cannot scale.
Why It Fails
Modern PostgreSQL/MySQL handles thousands of TPS and multi-terabyte datasets with full ACID guarantees, while premature NoSQL forces painful application-level joins and data duplication.
Alternatives
Compare Relational SQL (PostgreSQL/MySQL + JSONB), Key-Value/Wide-Column NoSQL (DynamoDB/ScyllaDB), and Distributed SQL (CockroachDB/Spanner).
Engineering Decision
Start with Relational SQL (with JSONB for flexible attributes) as the default for transactional and relational workloads; adopt KV/Wide-Column NoSQL when access patterns are strictly key/range-scoped and require extreme write throughput or multi-region active-active partition scale.
Trade-Offs
Minimizes operational sprawl and preserves ad-hoc query power while reserving NoSQL for workloads where its storage physics genuinely shine.

STAGE 05 · ASSUMPTIONS, LIMITATIONS & GLOSSARYdeepDive

Selection Boundaries & Canonical Database Glossary.

Why this matters: Summarize operational assumptions and canonical SQL/NoSQL data-modeling terms.

Assumptions & Limitations:

  • Single-Node SQL Envelope: Assumes standard NVMe cloud instances sustaining ~3,000-5,000 write TPS and ~2-4 TB storage before read replicas, federation, or sharding are required.
  • Fixed NoSQL Access Patterns: Assumes NoSQL partition and sort keys are designed around known query patterns; frequent ad-hoc analytical queries require a separate OLAP warehouse (ClickHouse/BigQuery/Snowflake).

Canonical Glossary:

  • Normalized Schema (3NF): Relational design storing each fact once and linking entities via primary/foreign keys to eliminate update anomalies.
  • Aggregate-Oriented Modeling: NoSQL approach (Document/KV) grouping data that is read and updated together into a single atomic unit.
  • Polyglot Persistence: Using different storage engines for different bounded contexts based on each workload's dominant access pattern.
