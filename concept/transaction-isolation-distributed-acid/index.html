Distributed ACID Transactions

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

PostgreSQL's REPEATABLE READ is Snapshot Isolation (still vulnerable to Write Skew), not true Serializability; across shards, distributed ACID requires either 2PC + SSI/TrueTime commit-wait or deterministic ordering—and retry loops for 40001 serialization failures.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Default READ COMMITTED isolation lets two concurrent transfers check balance >= $100 simultaneously and both withdraw, leaving a negative balance. Even upgrading to REPEATABLE READ (Snapshot Isolation) in PostgreSQL still allows Write Skew—for example, two on-call doctors both checking that 2 doctors are on shift and both signing off at the same time, leaving 0 on call. In distributed databases (Spanner, CockroachDB, TiDB), preserving ACID across shards adds cross-node clock uncertainty and network round-trips that directly impact p99 tail latency.

  • ANSI SQL-92 defines 4 levels (READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE) around Dirty Reads, Non-Repeatable Reads, and Phantoms, but misses Lost Updates and Write Skew (Berenson et al. 1995).
  • PostgreSQL REPEATABLE READ implements Snapshot Isolation (MVCC): readers never block writers, but two transactions reading the same snapshot and writing to disjoint rows still cause Write Skew.
  • PostgreSQL SERIALIZABLE uses SSI (Serializable Snapshot Isolation) via SIREAD predicate locks—detecting dangerous rw-antidependency cycles without blocking readers, aborting one transaction with SQLSTATE 40001.
  • Distributed ACID combines Two-Phase Commit (2PC) (or Raft-replicated coordinators) with Global Ordering: Spanner uses atomic/GPS clocks (TrueTime commit-wait >= 2ε, ~7 ms), while CockroachDB uses Hybrid Logical Clocks (HLC) + read restarts.
  • In MySQL InnoDB, REPEATABLE READ uses Next-Key Locks (record + gap locks) on locking reads (FOR UPDATE) to prevent phantoms, which can cause unexpected gap-lock deadlocks.

Good candidates

  • Financial ledgers, double-entry accounting, and inventory/seat reservations where lost updates, phantom reads, or write skew violate business invariants.
  • Multi-shard writes in CockroachDB, Google Spanner, or YugabyteDB where cross-partition atomicity and external consistency (linearizability) are required.
  • Read-heavy analytics or billing snapshots (REPEATABLE READ) that need a consistent point-in-time view across multiple tables without blocking concurrent writers.

Think twice

  • High-contention counters (like post view counts or rate-limiters) where SERIALIZABLE triggers 30%+ 40001 aborts—use atomic UPDATE ... SET count = count + 1, Redis INCR, or sharded counters.
  • Multi-service workflows spanning external HTTP APIs (Stripe, Twilio) where holding distributed locks across network calls causes cascading timeouts; use the Saga + Transactional Outbox pattern instead.
  • Append-only telemetry or event logs where READ COMMITTED suffices and zero-coordination throughput is the priority.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA hospital scheduling table requires at least 1 doctor on call. Alice and Bob are both on call. Both open a REPEATABLE READ transaction in PostgreSQL, run SELECT count(*) FROM shifts WHERE on_call = true (both see 2), and Alice updates id = 'alice' while Bob updates id = 'bob' to on_call = false.

The idea

Transaction isolation defines the illusion a database gives each concurrent transaction: at the strongest level (SERIALIZABLE), concurrent transactions produce the exact same final state as if they had executed one-by-one in some serial order.

Weakening isolation boosts concurrency by letting transactions read slightly stale or uncommitted data, but reintroduces anomalies (Lost Updates, Phantoms, Write Skew). Extending ACID across distributed shards adds two hard constraints: atomicity across independent nodes (Two-Phase Commit over Raft) and global timestamp ordering without a single bottleneck clock (TrueTime or Hybrid Logical Clocks).

Concrete walkthrough

Trace a distributed SERIALIZABLE transfer of $500 from Account A (Shard 1) to Account B (Shard 2) in a Spanner/CockroachDB-style engine:

  1. Begin & Timestamp: Coordinator assigns transaction T1 a read/write timestamp ts = HLC.now() (or TT.now().latest) and creates a Raft-replicated PENDING transaction record.
  2. Parallel Write Intents: T1 writes provisional write intents (Account A: -500, Account B: +500) to Shard 1 and Shard 2 via Raft consensus.
  3. 2PC Prepare & Conflict Check: Each shard checks for conflicting READ timestamps > ts or concurrent write intents. If another transaction T2 already read Account A at ts + 1, Shard 1 rejects T1 with 40001.
  4. Commit & Commit-Wait: Once both shards vote PREPARED, the coordinator flips the transaction record to COMMITTED via Raft (and in Spanner, waits out 2ε ~7 ms so now_real > ts).
  5. Async Intent Resolution: T1 returns OK to the client immediately and asynchronously clears the write intent flags on Shards 1 and 2.

Raft-replicated coordinators eliminate single-node 2PC blocking while HLC/TrueTime enforces global serializable order.

Beyond ANSI SQL-92: Lost Updates & Write Skew

ANSI SQL-92's 3 anomalies (Dirty Read, Non-Repeatable Read, Phantom Read) predate MVCC and miss critical concurrency bugs:

  • Lost Update (P4): T1 and T2 both read balance = 100, compute 100 + 20 and 100 + 30, and overwrite each other—leaving 130 instead of 150. Prevented by PostgreSQL REPEATABLE READ (first-committer-wins abort) and FOR UPDATE, but allowed in READ COMMITTED.
  • Write Skew (A5B): T1 and T2 read an overlapping set of rows, check an aggregate invariant (sum >= 0 or count >= 1), and update disjoint rows. Because MVCC Snapshot Isolation only checks write-write conflicts on the same row, both commit. Only SERIALIZABLE (SSI) or explicit SELECT ... FOR UPDATE / materialized lock rows prevent Write Skew.

Failure modes

  1. Convoy Effect on Hot Keys: Under 2PL (SELECT ... FOR UPDATE), 200 concurrent threads updating the same merchant balance form a serial queue; if each takes 15 ms, the 200th waits 3 seconds and triggers client timeouts.
  2. SSI False-Positive Aborts: PostgreSQL's SIREAD locks track page/tuple granularity; heavy concurrent inserts on the same B-tree leaf page can trigger 40001 aborts even between logically disjoint transactions.
  3. Cross-Region RTT Amplification: Synchronous 2PC + Raft across 3 continents adds 80–150 ms per commit, collapsing single-key throughput to ~10 TPS unless batched or localized via geo-partitioning.

Choosing a Distributed ACID Strategy

  • When you need global linearizable reads: Use Google Spanner (TrueTime) or CockroachDB (SERIALIZABLE with geo-partitioned leaseholders) so stale reads never occur after a commit.
  • When you need high write throughput on contended keys: Consider Deterministic Databases (Calvin / Fauna-style) that sequence all transaction inputs via Raft before execution, eliminating 2PC prepare round-trips and aborts—at the cost of requiring all read/write keys to be known upfront.
  • When crossing service boundaries: Never stretch 2PC/XA across independent microservices; keep ACID local to each service's database and bridge services asynchronously with the Transactional Outbox.

Practical checklist

  • Audit every READ COMMITTED read-modify-write path for Lost Updates (FOR UPDATE or atomic UPDATE ... WHERE).
  • Use SERIALIZABLE (or explicit parent-row locking) whenever an invariant spans multiple rows (e.g., quotas, shifts, ledgers).
  • Implement an idempotent retry wrapper for SQLSTATE 40001 / 40P01 with jittered backoff.
  • Keep transactions short: never make external HTTP calls (Stripe, SMTP) inside an open DB transaction.
  • Enforce statement_timeout and idle_in_transaction_session_timeout to protect MVCC vacuuming.
03 / Engineering trade-offs

Weighing architectural decisions

READ COMMITTED vs. SERIALIZABLE (SSI)

Advantage: `READ COMMITTED` avoids `40001` serialization aborts and maximizes throughput for independent single-row updates.

Drawback: Requires manual `SELECT ... FOR UPDATE` or optimistic version columns (`WHERE version = ?`) on every multi-row invariant, or subtle race conditions slip in.

Pessimistic Locking (2PL) vs. Optimistic MVCC / SSI

Advantage: 2PL (`FOR UPDATE` / InnoDB Next-Key Locks) guarantees the lock holder commits without retrying under high contention.

Drawback: Writers block readers/writers, risking lock convoys and deadlocks across shards; SSI never blocks readers but aborts conflicting writers at commit time.

TrueTime Commit-Wait (Spanner) vs. HLC Uncertainty Restarts (CockroachDB)

Advantage: Spanner's `2ε` (~7 ms) commit wait gives strict external consistency—if T1 finishes before T2 starts in real time, T2 is guaranteed to see T1.

Drawback: Adds mandatory ~7–14 ms to every write commit and requires specialized atomic/GPS clocks; HLC runs on commodity NTP VMs at the cost of occasional read restarts.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Missing `40001` Client Retry Loop

Enabling `SERIALIZABLE` on PostgreSQL or CockroachDB without application-level retry logic turns normal optimistic concurrency conflicts into HTTP 500 errors.

What helps: Wrap transactions in an idempotent retry loop (max 3–5 attempts with jittered exponential backoff) specifically catching SQLSTATE `40001` (`serialization_failure`) and `40P01` (`deadlock_detected`).

2PC Coordinator Blocking

In classic un-replicated 2PC, if the coordinator crashes after participants vote `PREPARE`, participants hold locks indefinitely until manual intervention.

What helps: Use Raft/Paxos-replicated transaction coordinators (Spanner, CockroachDB, TiDB) so a new leader immediately resolves `IN_DOUBT` transactions.

Clock Skew Violating External Consistency

In HLC-based distributed DBs, if a node's NTP clock drifts beyond `max_offset` (e.g., 500 ms), the node can serve stale reads or crash itself to protect consistency.

What helps: Run local `chrony` with redundant NTP/PTP sources, monitor `clock_offset` metrics, and configure nodes to self-terminate if skew exceeds `max_offset`.

Long-Running Read Transactions Bloating MVCC & SIREAD Locks

An analytical query left open for 30 minutes under `REPEATABLE READ` or `SERIALIZABLE` prevents PostgreSQL `VACUUM` from reclaiming dead tuples and accumulates megabytes of SIREAD predicate locks.

What helps: Set `statement_timeout` and `idle_in_transaction_session_timeout` (e.g., 30s) on OLTP pools, and route heavy analytics to a read replica.

05 / Practical checklist

Avoid these mistakes

  • Assuming `REPEATABLE READ` in PostgreSQL prevents Write Skew—it only prevents Dirty Reads, Non-Repeatable Reads, Phantoms, and Lost Updates.
  • Catching `40001` serialization errors and retrying *non-idempotent* side effects (like sending an email or charging Stripe) inside the same transaction block.
  • Using `SELECT * FROM accounts FOR UPDATE` in `READ COMMITTED` without realizing PostgreSQL re-evaluates the `WHERE` clause after waiting on a lock, which can still miss newly inserted rows.
  • Running `SERIALIZABLE` across hot single-row counters (like `global_sequence_id`), causing 90% abort storms.
  • Confusing `READ COMMITTED` statement-level snapshots with transaction-level snapshots—two identical `SELECT` queries in the same `READ COMMITTED` transaction can return different rows.
