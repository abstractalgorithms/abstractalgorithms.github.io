Transactional Outbox Pattern

Atomically persist domain changes and outbound events in one database transaction, then relay asynchronously to the message bus.

Orientation & Intuition

The outbox table stores events in the same DB transaction as business rows; a relay process publishes to Kafka/RabbitMQ with at-least-once delivery.

Key takeaway Never “write DB then publish”—dual writes race crashes; outbox makes intent durable before transport.

Core Architecture & Trade-offs

It is the standard fix for “update order row and emit OrderCreated” consistency.

Key Architecture Invariants

  • Same transaction for row + outbox insert
  • Relay polls or tails CDC
  • Consumers must be idempotent

When to Use

  • Microservices emitting integration events
  • Need DB + broker alignment
  • CDC-friendly pipelines

When NOT to Use

  • Fire-and-forget analytics with no consistency requirement

Deep Dive & Production Considerations

Outbox relay

Durably record intent, then async publish.
