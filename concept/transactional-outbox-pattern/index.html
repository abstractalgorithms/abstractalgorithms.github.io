Transactional Outbox
Pattern.

The Transactional Outbox pattern eliminates dual-write split-brain by inserting domain events into an outbox table inside the exact same ACID database transaction as the business state change, then relaying them asynchronously to Kafka/RabbitMQ.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Never publish to Kafka inside a DB transaction—network blips or rollbacks create ghost events or lost events; pair an atomic `outbox` insert with Debezium CDC (or `SKIP LOCKED` polling) and idempotent consumers for guaranteed at-least-once delivery.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

A service that updates PostgreSQL and then calls kafkaProducer.send() suffers from the dual-write problem: if Kafka is unreachable after COMMIT, the database has the order but downstream billing never hears about it; if you publish before COMMIT and the DB transaction rolls back on a constraint error, downstream services process a ghost order that never existed. Distributed 2PC across PostgreSQL and Kafka is unsupported or prohibitively slow. The Transactional Outbox solves this with single-DB ACID atomicity.

  • Both the business entity (orders) and the event row (outbox_events) live in the same database and commit atomically in one BEGIN ... COMMIT transaction.
  • Two relay mechanisms exist: Log-Tailing CDC (Debezium reading PostgreSQL WAL pgoutput with ~10–50 ms latency) and Polling Publisher (SELECT ... FOR UPDATE SKIP LOCKED every 100–500 ms).
  • Because the relay can crash after kafka.send() succeeds but before marking the row sent (or advancing the WAL offset), the outbox guarantees at-least-once delivery—never exact-once without consumer deduplication.
  • Consumers must be idempotent, typically via a processed_events(event_id UUID PRIMARY KEY) table checked inside the consumer's own local DB transaction.
  • Outbox tables grow rapidly under high TPS; without aggressive partitioning (pg_partman daily/weekly drops) or Debezium WAL-only deletion, VACUUM bloat degrades the primary DB.

Good candidates

  • Publishing domain events (OrderCreated, PaymentSettled) to Kafka, RabbitMQ, or SNS/SQS whenever a microservice mutates its own relational or document database.
  • Replacing fragile Two-Phase Commit (XA) across a database and a message broker with reliable at-least-once event delivery.
  • Guaranteeing causal ordering per aggregate (using aggregate_id as the Kafka partition key) without holding database locks during broker I/O.

Think twice

  • Ephemeral, best-effort telemetry (metrics, clickstream logs, cache-warming hints) where losing 0.01% of events on a crash is acceptable and storing outbox rows wastes DB IOPS.
  • Cross-service synchronous validation where the caller needs an immediate reject/accept from another service before committing—use synchronous RPC or a Saga orchestrator.
  • Systems already using pure Event Sourcing where the event log is the primary database.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn e-commerce order-service at 1,500 TPS experienced ~12 missing OrderPaid Kafka events per week during broker leader elections because kafkaTemplate.send() ran after @Transactional committed.

The idea

Updating a database and publishing a message to Kafka are two separate network systems that do not share an atomic commit protocol. Any naive sequential code—whether DB-first or Kafka-first—creates a split-brain window where one succeeds and the other fails.

The Transactional Outbox pattern collapses the dual-write into a single local ACID transaction: your service writes the domain state (orders) and the outgoing event (outbox_events) to the same database. An asynchronous Message Relay (either Debezium CDC tailing the Write-Ahead Log or a SKIP LOCKED poller) reads committed rows and publishes them to the broker with at-least-once guarantees, while consumers deduplicate by event_id to achieve effectively-once processing.

Concrete walkthrough

Trace an OrderService.placeOrder() execution using PostgreSQL + Debezium CDC + Kafka:

  1. Single ACID Commit: BEGIN; INSERT INTO orders (id, total, status) VALUES ('ord_99', 14900, 'CONFIRMED'); INSERT INTO outbox_events (id, aggregate_type, aggregate_id, event_type, payload) VALUES ('0193...', 'Order', 'ord_99', 'OrderConfirmed', '{"total":14900}'); COMMIT;—if either insert fails, both roll back.
  2. WAL Capture: PostgreSQL appends both writes to the WAL. Debezium's pgoutput connector reads the committed WAL entry within ~20 ms (uncommitted/rolled-back transactions are never emitted).
  3. Route & Publish: Debezium's OutboxEventRouter SMT extracts aggregate_id (ord_99) as the Kafka message key (preserving per-order ordering), routes to topic outbox.event.Order, sets id as a Kafka header, and publishes with acks=all + enable.idempotence=true.
  4. Idempotent Consume: inventory-svc reads the message, starts a local DB transaction, runs INSERT INTO processed_events (event_id) VALUES ('0193...') ON CONFLICT DO NOTHING—if rowCount == 1, it reserves stock and commits; if 0, it skips the duplicate safely.

Local ACID commits plus WAL-based CDC eliminate dual-write split-brain while consumer-side deduplication handles retries.

Relay Design: Debezium CDC vs. SKIP LOCKED Polling

Choosing between Log-Tailing CDC and Polling comes down to throughput, latency, and ops footprint:

  • Debezium CDC (pgoutput): Ideal above ~200 events/sec or when < 50 ms relay latency is required. Because Debezium reads the WAL, you can even DELETE the outbox row immediately in a trigger or leave it empty—the WAL still captures the INSERT! However, you must monitor replication slot lag (pg_replication_slots.confirmed_flush_lsn) and set max_slot_wal_keep_size.
  • Polling (FOR UPDATE SKIP LOCKED): Ideal for <200 events/sec or teams without Kafka Connect. Use a partial index CREATE INDEX idx_outbox_pending ON outbox_events (created_at) WHERE published_at IS NULL so polling scans only unpublished rows, and fetch batches of 100–500 rows per cycle.

Failure modes

  1. Replication Slot WAL Bloat: An abandoned staging Debezium connector leaves an inactive replication slot on PostgreSQL, silently retaining 200 GB of WAL until the primary disk hits 100%.
  2. Unbounded processed_events Growth: Consumer deduplication tables grow forever if never pruned; partition processed_events by week and drop partitions older than your Kafka retention window (e.g., 14 days).
  3. Missing Correlation/Trace Headers: Dropping W3C traceparent headers when writing to outbox_events breaks distributed OpenTelemetry traces across async boundaries—store headers JSONB alongside payload.

Canonical Schema & Key Metrics

A production-ready PostgreSQL outbox_events table uses UUIDv7 (time-ordered, B-tree friendly) and explicit routing columns:

  • Columns: id UUID PRIMARY KEY, aggregate_type TEXT NOT NULL, aggregate_id TEXT NOT NULL, event_type TEXT NOT NULL, payload JSONB NOT NULL, headers JSONB, created_at TIMESTAMPTZ NOT NULL DEFAULT now().
  • Key Metrics: Monitor outbox_pending_count (or pg_wal_lsn_diff lag in bytes), outbox_relay_lag_seconds (now() - min(created_at)), and consumer_dedup_skipped_total to verify idempotency is actively catching retries.

Practical checklist

  • Insert into outbox_events inside the exact same ACID transaction as the domain mutation.
  • Set Kafka partition key to aggregate_id so per-entity events stay strictly ordered.
  • Enable acks=all and enable.idempotence=true on the relay's Kafka producer.
  • Enforce consumer idempotency via processed_events(event_id PRIMARY KEY) inside the consumer's DB transaction.
  • Configure max_slot_wal_keep_size (for CDC) and time-based partitioning (pg_partman) for both outbox and processed_events tables.
  • Persist OpenTelemetry traceparent in headers so traces connect across the async hop.
03 / Engineering trade-offs

Weighing architectural decisions

Log-Tailing CDC (Debezium) vs. Polling Publisher (`SKIP LOCKED`)

Advantage: CDC reads the WAL sequentially with near-zero impact on OLTP query plans and ~20–50 ms latency.

Drawback: CDC requires running Kafka Connect, managing PostgreSQL logical replication slots, and handling WAL disk retention if Debezium goes down; polling is pure SQL and trivial to deploy.

Delete-Immediately vs. Mark-`published_at` Retention

Advantage: Deleting (or `DELETE` inside CDC) keeps the active `outbox_events` table tiny (near-zero index size).

Drawback: Loses an easy SQL audit trail for replaying recent events; keeping 7 days in time-partitioned tables allows instant `DROP TABLE` cleanup without `VACUUM` overhead.

Outbox Payload: Thin Event (ID only) vs. Fat Event (Full Snapshot)

Advantage: Fat events (`JSONB` / Protobuf snapshot) eliminate downstream callback queries to the producer service.

Drawback: Increases WAL volume and outbox storage; sensitive PII inside `outbox_events` requires encryption or schema governance.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

PostgreSQL WAL Disk Exhaustion from Stalled Replication Slot

Debezium crashes or loses connectivity to Kafka for 6 hours. PostgreSQL retains all WAL segments for the inactive logical replication slot, filling 100% of `/var/lib/postgresql` disk and halting all writes.

What helps: Set `max_slot_wal_keep_size` (e.g., `20GB`) on PostgreSQL 13+, alert when `pg_wal_lsn_diff` lag exceeds 1 GB, and test slot recreation + snapshot recovery.

Duplicate Event Side Effects on Consumer

Relay publishes `PaymentCaptured` to Kafka, then pod restarts before committing the offset/status; on restart it republishes `PaymentCaptured`, causing the loyalty service to credit points twice.

What helps: Include a deterministic `event_id` (UUIDv7) in every outbox row and enforce `INSERT INTO processed_events(event_id) ON CONFLICT DO NOTHING` inside the consumer's local transaction.

Poison-Pill Serialization Error Blocking the Relay

A single malformed row in `outbox_events` fails Avro/Protobuf schema validation in Kafka Connect, halting the entire partition/slot and delaying millions of valid events behind it.

What helps: Validate event schemas *before* `INSERT` into `outbox_events`, and configure a Dead Letter Queue (DLQ) in the relay after N retries.

Out-of-Order Delivery on Multiple Pollers

Two polling workers grab Event 1 and Event 2 for `order-123` simultaneously via `SKIP LOCKED`; Worker 2 finishes first, delivering `OrderCancelled` before `OrderCreated`.

What helps: Use single-stream CDC (WAL order is strictly serial) or partition polling workers by `hash(aggregate_id) % N` so events for the same aggregate never run concurrently.

05 / Practical checklist

Avoid these mistakes

  • Calling `kafkaProducer.send().get()` *inside* a `@Transactional` DB method—this holds DB connections open during Kafka timeouts and still fails on DB commit/rollback.
  • Polling `outbox_events` with `SELECT * FROM outbox_events WHERE sent = false` across multiple workers without `FOR UPDATE SKIP LOCKED`, causing massive duplicate sends.
  • Using `DELETE FROM outbox_events` at 1,000+ TPS without partitioning or aggressive autovacuum tuning, leading to table bloat and sequential scan slowdowns.
  • Forgetting to set the Kafka message key to `aggregate_id`—events land on random partitions and arrive out of order at consumers.
  • Assuming Debezium guarantees exact-once end-to-end delivery and skipping consumer-side `processed_events` deduplication.
