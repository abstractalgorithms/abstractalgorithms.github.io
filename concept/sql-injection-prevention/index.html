A foundational engineering concept

SQL Injection
Prevention.

SQL injection (CWE-89) happens when untrusted input is concatenated into a SQL string, letting attackers alter query structure; preventing it requires strict code-data separation via parameterized queries (prepared statements), allowlists for dynamic identifiers, and least-privilege database roles.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Never sanitize or regex-escape SQL values—bind every user input through wire-level parameterized queries (`Parse`/`Bind`) and restrict dynamic table/column/sort names to static compile-time allowlists.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

SQL injection remains one of the highest-impact vulnerabilities (OWASP Top 10 A03:2021 / CWE-89) because a single unparameterized WHERE or ORDER BY clause exposes the entire database—allowing full table exfiltration (UNION SELECT), authentication bypass, or OS/file access (xp_cmdshell, COPY TO PROGRAM) in seconds via automated tools like sqlmap.

  • Parameterized queries (JDBC PreparedStatement, psycopg3 %s, Go db.Query($1)) send the SQL template (Parse) and parameter values (Bind) separately at the wire protocol level—data can never become SQL syntax.
  • Parameters only bind literal values (WHERE email = $1), NOT identifiers (table names, column names) or keywords (ASC/DESC); dynamic identifiers require a strict Map/Set allowlist.
  • Always apply least-privilege DB roles: web app users should never connect as superuser, db_owner, or postgres.
  • Stored procedures are NOT automatically safe if they concatenate strings internally (EXEC('SELECT ... ' + @input)); they must use USING or sp_executesql.
  • Defense in depth—PostgreSQL Row-Level Security (RLS), read-only replicas for reporting, and SAST rules (Semgrep/CodeQL)—limits blast radius if a bug slips through.

Good candidates

  • Every database query across web APIs, background workers, GraphQL resolvers, and internal admin tools that touches user or external input.
  • Dynamic search, filter, and sorting endpoints where column names or ASC/DESC directions are chosen by the client (pair prepared statements with strict allowlists).
  • Stored procedures and dynamic SQL inside PostgreSQL/SQL Server using EXECUTE ... USING or sp_executesql.

Think twice

  • Do not rely on regex input blacklists (stripping ', --, or UNION) as a primary defense—encoding tricks and SQL dialect quirks bypass them.
  • Do not rely on Web Application Firewalls (WAFs) alone; WAFs are a defense-in-depth layer, never a substitute for parameterized queries.
  • Do not assume an ORM (Hibernate, SQLAlchemy, Prisma) makes you immune—raw query escape hatches (.raw(), text(), createNativeQuery()) reintroduce SQLi if formatted with strings.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn e-commerce catalog API accepts category, max_price, sort_by, and sort_dir query parameters from users.

The idea

SQL injection happens because a SQL query is a program sent as text to a database parser. When an application builds that string by concatenating untrusted user input ("SELECT * FROM users WHERE email = '" + email + "'"), the database parser cannot tell where the developer's SQL code ends and the user's data begins. An input like ' OR '1'='1 alters the Abstract Syntax Tree (AST) of the query.

Parameterized queries (Prepared Statements) eliminate this class of vulnerability by enforcing structural separation at the wire protocol level (e.g., PostgreSQL's Extended Query Protocol Parse -> Bind -> Execute, or MySQL's COM_STMT_PREPARE / COM_STMT_EXECUTE):

  1. Parse: The client sends the SQL template with placeholders (SELECT id, role FROM users WHERE email = $1) before any user data. The database compiles and locks the AST.
  2. Bind: The client sends the raw user input ("alice@example.com' OR '1'='1") as a typed binary/text parameter.
  3. Execute: The engine compares the literal string against the email column—it is never re-parsed as SQL syntax.

Concrete walkthrough

Trace how a Java Spring / JDBC or Python psycopg3 search endpoint handles a malicious payload q = "widget'; DROP TABLE orders; --" and sort = "price; DROP TABLE orders":

  1. Identifier allowlist check (before SQL): The API looks up sort in an immutable map: ALLOWED_SORTS = {"price": "unit_price", "newest": "created_at"}. Since "price; DROP TABLE orders" is not a key, the API immediately rejects the request with HTTP 400 Bad Request—zero database round-trips.
  2. Wire-protocol Parse (valid sort = "price"): The driver sends SELECT id, name, unit_price FROM products WHERE name ILIKE 1ORDERBYunitpriceDESCLIMIT1 ORDER BY unit_price DESC LIMIT1ORDERBYunitp​riceDESCLIMIT2 to PostgreSQL. The planner compiles the AST once.
  3. Wire-protocol Bind: The driver binds 1="1 = "%widget'; DROP TABLE orders; --%" (with % and _ LIKE wildcards escaped) and 1="2 = 25.
  4. Safe execution: PostgreSQL searches literally for product names containing that exact string, returns 0 rows, and never executes DROP TABLE. Even if EXECUTE were abused, the app_readonly role lacks DROP privileges.

Dynamic identifiers are resolved via static allowlists while all data values travel through separate Parse/Bind wire frames.

Handling tricky SQL constructs safely

Developers often fall back to string concatenation for three specific SQL patterns—each has a clean, safe alternative:

  • Dynamic ORDER BY / Column Names: Parameters cannot bind identifiers. Map user input through a dict/Map ({"date": "created_at", "total": "grand_total"}) and reject unknown keys.
  • Variable-Length IN (...) Lists: In PostgreSQL, bind a single array parameter: WHERE id = ANY($1::bigint[]). In MySQL/SQLite, build the placeholder string dynamically using only "?" tokens (", ".join(["?"] * len(ids))) and pass ids as bound parameters.
  • LIKE Wildcard Escaping: Prepared statements prevent SQLi in LIKE, but an attacker sending %%%% can trigger expensive full-table wildcard scans. Escape \, %, and _ in the application before binding f"%{escaped}%".

Failure modes

  • PgBouncer Transaction Pooling Collisions: Older PgBouncer setups in transaction pooling mode failed when drivers used named server-side prepared statements (PREPARE stmt_1). Ensure PgBouncer >= 1.21 with max_prepared_statements > 0 or use unnamed protocol-level Parse/Bind—never disable parameterization by falling back to unsafe string escaping.
  • Blind / Time-Based Exfiltration: Even when an endpoint returns only 200 OK or 404 with no DB errors, attackers extract data bit-by-bit using pg_sleep(5) or IF(SUBSTR(...), SLEEP(5), 0).
  • Stored Procedure String Concatenation: Wrapping a concatenated query inside CREATE FUNCTION (EXECUTE 'SELECT ... ' || user_input) provides zero protection; use EXECUTE 'SELECT ... WHERE id = $1' USING user_input.
  • Verbose Error Leakage: Returning raw SQL error strings in API responses lets attackers map table and column names in minutes.

Automated verification in CI/CD

Preventing regressions requires automated checks alongside code review:

  1. SAST in Pull Requests: Configure Semgrep or CodeQL rules (java.lang.security.audit.sqli, python.lang.security.audit.formatted-sql-query) to fail builds whenever string formatting touches a DB cursor or ORM raw-query method.
  2. Integration Tests with Injection Payloads: Include test cases passing ' OR '1'='1, "; DROP TABLE users; --, and 1; SELECT pg_sleep(5) into search/sort endpoints to verify they return 0 results or HTTP 400 in < 50ms.
  3. DB Role Audits: Run a periodic CI/migration check asserting that the application DB role has rolsuper = false, rolbypassrls = false, and no CREATE grant on public.

Practical checklist

  • Bind 100% of query values using wire-level parameterized queries (PreparedStatement, %s, $1, @p1)—including inside ORM .raw() calls and stored procedures.
  • Validate all dynamic table names, column names, and ASC/DESC directions against a hardcoded allowlist Map/Set.
  • Use = ANY($1) (Postgres) or generated ?, ?, ? placeholders for variable-length IN clauses.
  • Connect the application with a least-privilege DB role (no superuser, no DDL, no OS command privileges) and enable Row-Level Security for multi-tenant tables.
  • Suppress raw SQL error messages from HTTP responses; log full details internally only.
  • Enforce Semgrep/CodeQL SQLi rules in CI to block accidental string interpolation.
03 / Engineering trade-offs

Weighing architectural decisions

Server-Side Prepared Statements vs. Client-Side Emulation

Advantage: True wire-protocol preparation (`Parse`/`Bind`/`Execute`) enforces strict parser separation and caches query execution plans.

Drawback: In transaction-pooling proxies (PgBouncer in `transaction` mode), named prepared statements can collide across pooled connections unless configured with protocol-level unnamed statements or PgBouncer >= 1.21 prepared statement support.

ORM Query Builders vs. Raw Parameterized SQL

Advantage: ORMs/query builders (Prisma, jOOQ, SQLAlchemy Core) parameterize values by default and catch schema mismatches early.

Drawback: Complex analytical CTEs or window functions often force developers into raw SQL methods where accidental f-strings/concatenation can sneak in.

Static Allowlists vs. Quoted Identifiers

Advantage: Mapping user-facing sort keys (`"created"`) to hardcoded SQL identifiers (`"created_at"`) is 100% immune to injection and hides internal column names.

Drawback: Requires updating the allowlist map whenever a new sortable column is added.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Second-Order SQL Injection

User input (e.g., `admin'--` in a username) is safely stored via a prepared statement, then later concatenated unescaped into a background batch or password-reset SQL string.

What helps: Parameterize every query everywhere—never treat database-loaded strings as trusted SQL syntax.

Unvalidated `ORDER BY` / `IN (...)` Clauses

Developers parameterize `WHERE` values but interpolate `sort_by` directly or build `IN (${ids.join(',')})` strings.

What helps: Use static allowlists for `ORDER BY` / column names, and native array binding (`WHERE id = ANY($1::int[])` in Postgres) or dynamically generated `?,?,?` placeholders for `IN` lists.

ORM Raw-SQL Escape Hatch

Using `User.objects.raw(f"SELECT * FROM users WHERE name = '{name}'")` or `entityManager.createNativeQuery("... " + name)` bypasses ORM parameterization.

What helps: Pass bind parameters as the second argument (`raw(sql, [name])`) and enforce Semgrep/CodeQL SAST rules banning string interpolation inside SQL calls.

Over-Privileged Database Credentials

Application connects as `postgres` or `sa`, turning a read-only injection into `COPY ... TO PROGRAM` remote code execution or `DROP TABLE`.

What helps: Grant only `SELECT, INSERT, UPDATE, DELETE` on specific tables to the app role; revoke `CREATE` on `public` schema and disable `xp_cmdshell`.

05 / Practical checklist

Avoid these mistakes

  • Escaping quotes with `addslashes()` or `.replace("'", "''")` instead of using prepared statements (vulnerable to multibyte encoding and non-quoted numeric contexts).
  • Using `LIKE '%' + ? + '%'` incorrectly by interpolating `?` inside quotes (`LIKE '%?%'`) instead of passing `"%" + term + "%"` as the bound parameter.
  • Assuming `IN (?)` binds an array in MySQL/JDBC—most drivers bind it as a single string unless expanded to `(?, ?, ?)` or using Postgres `= ANY($1)`.
  • Returning raw SQL exception stack traces (`PSQLException: ERROR: syntax error at or near...`) in HTTP 500 responses, handing attackers schema details.
  • Forgetting that stored procedures using string concatenation (`EXEC(@sql)`) are just as vulnerable as application-side concatenation.
