THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Design keys around your exact read access pattern first—composite keys, hash tags, and TTLs replace SQL joins, while hot-key sharding and compaction tuning prevent tail-latency spikes.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Modern high-throughput services—session stores, feature flags, rate limiters, and metadata catalogs—need sub-millisecond reads and predictable horizontal scaling that B-tree RDBMS engines struggle to sustain past 100k+ QPS. Choosing the right key-value engine (in-memory hash vs. disk-backed LSM-tree) and key-modeling pattern determines whether your p99 stays under 2 ms or collapses under hot partitions and write amplification.

  • Access-pattern-driven key naming: encode hierarchy and cardinality in keys (e.g., tenant:{id}:session:{sid}) and use Redis hash tags ({tenant:42}:cart) to co-locate multi-key operations on the same hash slot.
  • Storage engine split: in-memory hash tables (Redis, Memcached) deliver <1 ms p99 at RAM cost, while LSM-trees (RocksDB, Pebble) buffer writes in a MemTable + WAL and flush immutable SSTables for high write throughput on NVMe.
  • Partitioning & consistent hashing: Redis Cluster maps keys to 16,384 hash slots via CRC16(key) mod 16384; DynamoDB hashes the partition key (PK) into storage partitions capped at 1,000 WCU / 3,000 RCU per physical partition.
  • Value serialization & compression: packing small related attributes into a single Hash or Protobuf/MessagePack blob cuts per-key metadata overhead (~64–96 bytes per Redis key) and reduces network round-trips.
  • Read/write amplification defenses: 10-bit/key Bloom filters (~1% false positive rate) skip non-existent SSTable lookups, while leveled compaction bounds space amplification to ~1.1x at the cost of ~10x write amplification.

Good candidates

  • Point lookups and writes indexed by a known primary identifier (userId, sessionId, idempotencyKey) at 10k–1M+ ops/sec.
  • Ephemeral or TTL-bound state such as JWT blocklists, distributed locks (Redlock/etcd leases), and sliding-window rate-limit counters.
  • Write-heavy ingestion (telemetry, time-series buckets, event deduplication) where append-only LSM-trees (RocksDB, DynamoDB) outperform random B-tree page writes.

Think twice

  • Multi-attribute ad-hoc filtering, range aggregations across arbitrary columns, or multi-table joins—use PostgreSQL or ClickHouse instead.
  • Strict multi-entity ACID transactions spanning uncorrelated keys across shards without accepting 2PC latency penalties.
  • Large binary blobs (>1 MB) in memory-first engines like Redis or Memcached, which fragment slab allocators and starve working-set RAM.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn e-commerce checkout service handles 80,000 RPS during a flash sale and must atomically decrement SKU stock while preventing duplicate charges from client retries.

The idea

A key-value store is an associative array scaled across processes and machines: given an opaque key KKK, it locates the owning partition in O(1)O(1)O(1) via consistent hashing or a range/slot map, then resolves K→VK → VK→V locally using either an in-memory hash table (e.g., Redis dict, Memcached slabbed hash) or a disk-backed Log-Structured Merge-tree (e.g., RocksDB, DynamoDB storage nodes). Because the engine refuses to parse or join across arbitrary value fields, it eliminates query-planner overhead, lock-manager contention across tables, and random B-tree page splits—delivering predictable single-digit millisecond latency as data scales from gigabytes to petabytes.

Concrete walkthrough

Consider writing and reading user:84920:prefs in a RocksDB-backed KV node:

  1. Routing: The client hashes user:84920 via MurmurHash3 or CRC16 to select Shard 7 (Raft leader).
  2. Durable Write: The node appends the mutation to an on-disk Write-Ahead Log (WAL) with fdatasync and inserts it into the in-memory MemTable (skip list) in ~80 µs.
  3. Flush: Once the MemTable hits 64 MB, it freezes into an immutable MemTable and flushes sequentially to an L0 SSTable file on NVMe.
  4. Read Path: A Get(user:84920:prefs) checks the active MemTable, immutable MemTables, and then L0→Ln SSTables. Each SSTable's 10-bit/key Bloom filter (~1% false positive rate) immediately skips files that do not contain the key, avoiding unnecessary disk I/O.

Write-optimized LSM-tree path: sequential WAL + MemTable writes paired with Bloom-filtered SSTable reads.

Key Modeling & Partitioning Patterns

Effective KV schemas encode relationships directly into keys:

  • Composite / Hierarchical Keys: :: (e.g., org:42:invoice:2026-11) enables prefix range scans in ordered engines (RocksDB, DynamoDB SK begins_with) without secondary indexes.
  • Hash-Tag Co-location: In Redis Cluster, wrapping the shard root in braces ({org:42}:quota and {org:42}:users) forces CRC16 to hash only org:42, guaranteeing both keys land on the same slot for atomic Lua or MGET.
  • Write-Sharded Counters: For hot keys exceeding 1,000 WCU or single-core limits, split into likes:post99#0 through likes:post99#15 on write and sum 16 keys on read.
  • Inverted Index / Adjacency Lists: Store tag:distributed -> Set[docId] or edge:nodeA -> SortedSet(ts, nodeB) when bounded cardinality (<10k items) replaces an RDBMS join table.

Failure modes

  1. Hot-Key Skew: Consistent hashing balances key count, not traffic volume. A single viral key can saturate one shard's CPU or NIC while 99% of the cluster is idle.
  2. Tombstone Accumulation: Deleting millions of keys in an LSM-tree writes tombstone markers rather than freeing bytes immediately; range scans over deleted prefixes (Seek) degrade to O(T)O(T)O(T) until compaction purges them.
  3. Thundering Herd on Expiration: Synchronized TTLs cause simultaneous cache misses across all application replicas, overwhelming downstream databases.
  4. Split-Brain & Stale Reads: Async replication (e.g., Redis primary→replica) can lose acknowledged writes during a primary crash (WAIT only blocks best-effort unless synchronous quorum like Raft/etcd is used).

Serialization, TTLs & Memory Efficiency

Every standalone key in Redis carries ~64–96 bytes of metadata (redisObject, dictEntry, SDS header). Packing 100 small counters or attributes into a single Hash (with hash-max-listpack-entries 512) or a Zstd-compressed Protobuf blob cuts RAM usage by 4–8x. Always attach randomized TTL jitter (base_ttl + rand(0, 0.15 * base_ttl)) to prevent synchronized expiry waves, and prefer UNLINK over DEL for any value larger than 4 KB so memory reclamation runs on a background thread.

Practical checklist

  • Document every read/write access pattern before choosing a key format or partition key.
  • Verify partition-key cardinality is high enough to distribute peak QPS across all shards (no date-only or status-only PKs).
  • Add ±10–15% jitter to all cache TTLs and use singleflight on cache-miss origin fetches.
  • Cap collection sizes (<10k items) or chunk them into numbered buckets; use UNLINK and SCAN instead of DEL and KEYS.
  • Enable 10-bit/key Bloom filters and monitor L0 file count / compaction pending bytes on LSM-backed stores.
  • Use {hash_tag} in Redis Cluster for any multi-key Lua script or MGET.
03 / Engineering trade-offs

Weighing architectural decisions

In-Memory Hash (Redis) vs. Disk LSM-Tree (RocksDB)

Advantage: Redis serves reads/writes in 0.2–0.8 ms with zero disk seeks and native data structures (Sorted Sets, HyperLogLog).

Drawback: RAM costs ~10–20x more per GB than NVMe SSD, and RDB/AOF fork snapshots can double memory usage during copy-on-write spikes.

Composite Key Packing vs. Normalized Single-Attribute Keys

Advantage: Packing 10 attributes into one Hash or Protobuf value eliminates 9 network hops and saves ~700 bytes of key-header overhead per entity.

Drawback: Updating a single 8-byte field in a serialized blob requires a read-modify-write cycle (or CAS) and rewrites the entire value.

Leveled Compaction vs. Size-Tiered (Universal) Compaction

Advantage: Leveled compaction keeps space amplification near 1.1x and bounds point-read checks to one SSTable per level.

Drawback: Write amplification reaches 10–30x on heavy update workloads, saturating NVMe IOPS and causing compaction stalls.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Hot-Key Partition Saturation

A single celebrity key or global counter hashes to one shard, maxing out its single-threaded CPU (Redis) or 3,000 RCU/1,000 WCU partition ceiling (DynamoDB) while other shards sit idle.

What helps: Apply write sharding by appending a random suffix (counter#0..counter#15) and aggregating on read, or place a 1–5 second L1 in-process cache (Caffeine/Ristretto) in front of hot read keys.

Cache Stampede / Thundering Herd on Expiry

A popular key expires simultaneously across 500 app pods, triggering 500 concurrent origin database queries that exhaust connection pools.

What helps: Add ±15% TTL jitter, use singleflight request coalescing per pod, or serve stale values while refreshing asynchronously in the background (stale-while-revalidate).

Big-Key Blocking & Replication Lag

A single 50 MB Hash or List blocks Redis's single-threaded event loop during DEL, HGETALL, or serialization, spiking p99 latency across all tenants.

What helps: Cap collection sizes (<10,000 elements), shard large lists into time/index buckets, and always use UNLINK (async lazyfree) instead of synchronous DEL.

LSM Compaction Write Stall

Sustained write bursts fill L0 SSTables faster than background compaction threads can merge them into L1, causing RocksDB to throttle or halt client writes.

What helps: Increase max_background_jobs, tune level0_slowdown_writes_trigger (e.g., 20) vs. stop_writes_trigger (36), and rate-limit bulk backfills.

05 / Practical checklist

Avoid these mistakes

  • Running KEYS * or unbounded HGETALL in production Redis instead of cursor-based SCAN/HSCAN, stalling the single-threaded event loop.
  • Using sequential or low-cardinality partition keys (e.g., status='ACTIVE' or today's date) in distributed KV stores, funnelling 100% of traffic onto one node.
  • Omitting TTLs on session, cache, or idempotency keys, causing unbounded memory growth until OOM eviction drops critical keys.
  • Assuming multi-key MGET or Lua scripts work across Redis Cluster nodes without {hash_tag} co-location, triggering CROSSSLOT errors.
  • Storing unindexed JSON strings when only 1–2 fields are queried, forcing full payload deserialization on every read.
