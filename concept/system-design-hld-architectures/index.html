High-Level System Design Architectures: Chat,
Streaming & Distributed Platforms.

High-Level Design (HLD) translates product requirements and scale targets (QPS, p99 latency, durability, RPO/RTO) into a cohesive topology of edge gateways, stateless compute, caches, async queues, and partitioned data stores. Good HLD explicitly isolates failure domains and separates read/write bottlenecks.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Prematurely jumping into database schemas or class diagrams misses the systemic bottlenecks—hot-key thundering herds, cross-region replication lag, and cascading retry storms—that actually cause production outages and 10x cloud bills.

  • Quantify traffic early: compute read/write QPS (peak = 3–5x average), daily storage growth, and network egress before picking databases.
  • Separate stateless compute (horizontally scalable behind L7 load balancers) from stateful tiers (sharded DBs, distributed caches, object stores).
  • Apply CQRS and async decoupling (Kafka/SQS + outbox pattern) when write latency, fan-out, or third-party webhooks would otherwise block user-facing threads.
  • Design for graceful degradation: circuit breakers, adaptive concurrency limits, idempotency keys, and stale-while-revalidate caches prevent partial failures from becoming total outages.
  • Define RPO (acceptable data loss) and RTO (acceptable recovery time) per tier—active-active multi-region is 3x more complex and costly than active-passive.

Good candidates

  • Designing new distributed systems or major platform migrations (>1,000 QPS, multi-region availability, or strict p99 < 100 ms SLOs).
  • Architecture reviews and RFCs where teams must align on component boundaries, data ownership, and failure blast radius before writing code.
  • Principal/Staff system design evaluations requiring end-to-end trade-offs across compute, storage, caching, and async messaging.

Think twice

  • Early-stage MVPs or internal CRUD tools (<50 QPS) where a single modular monolith + managed PostgreSQL handles years of growth.
  • Low-level class/interface design (LLD) inside a single service—HLD stops at service boundaries, APIs, and data-flow contracts.
  • Micro-optimizing CPU cache lines or lock-free data structures before verifying network and storage I/O bottlenecks.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA sneaker drop drives 50,000 concurrent users to GET /product and POST /checkout, risking PostgreSQL connection exhaustion and overselling limited inventory.

The idea

High-Level Design (HLD) is the blueprint of how traffic, state, and failures flow through a distributed system. Rather than prescribing individual classes, HLD defines service boundaries, data ownership, communication patterns (sync vs. async), and scaling axes.

Every scalable HLD rests on three levers: (1) Shedding or caching reads as close to the user as possible (CDN → Edge → Redis → Read Replicas), (2) Absorbing write spikes through durable logs (Kafka/SQS) and partitioned storage (hash/range sharding), and (3) Bounding blast radius via cell-based isolation, timeouts, and backpressure so one degraded dependency cannot take down the entire platform.

Concrete walkthrough

Consider designing a multi-tenant Notification & Webhook Delivery Platform handling 20,000 events/sec:

  1. Edge & Ingestion: Clients call POST /v1/notifications with an Idempotency-Key. Envoy terminates TLS, enforces per-tenant token-bucket rate limits, and routes to stateless ingest-api pods.
  2. Deduplication & Durable Acceptance: ingest-api checks Redis (SETNX idem: EX 86400), validates the payload, writes an ACCEPTED record to a Kafka notifications.inbound topic (partitioned by tenant_id), and returns 202 Accepted in <15 ms.
  3. Routing & Fan-out: Stateless router-workers consume from Kafka, look up tenant preferences (cached in Redis, backed by PostgreSQL), and route to channel-specific topics (email.send, webhook.deliver).
  4. Isolated Delivery & Backpressure: webhook-workers execute outbound HTTP POSTs with strict 3-second timeouts. If a customer's webhook endpoint returns 503, the worker routes the message to tiered retry topics (retry-1m, retry-15m, dlq) without blocking healthy tenants.

Separating fast edge ingestion from bounded-concurrency worker execution keeps p99 API latency flat under downstream spikes.

Capacity estimation & partitioning keys

Before selecting technologies, anchor the design in numbers: QPS (e.g., 100M DAU × 20 actions/day ÷ 86,400 ≈ 23,150 avg QPS, × 3 = ~70,000 peak QPS), Bandwidth (70k × 2 KB = 140 MB/s), and Storage (2B records/day × 500 B = 1 TB/day, 365 TB/year before compression/TTL).

Partitioning keys dictate whether that scale holds. Hash partitioning (hash(user_id) % N) spreads writes evenly across shards but makes range scans (created_at BETWEEN ...) scatter-gather across all nodes. Range or composite keys ((tenant_id, created_at)) support fast time-series queries while risking hot shards for whale tenants—which you mitigate with shard-splitting or salting.

Failure modes

1. Split-Brain Under Network Partition: Two database nodes both believe they are primary after a flaky AZ link, accepting conflicting writes. Always enforce quorum-based fencing (Raft/Paxos) or STONITH/lease-based leader election.

2. Unbounded Queue Lag (Consumer Starvation): A downstream dependency slows down from 10 ms to 2 s, causing Kafka consumer lag to grow to 50M messages. By the time it recovers, messages are hours stale and TTLs expire. Enforce shedding/load-dropping or priority queues (interactive vs. bulk).

3. Cross-Region Failover Thundering Herd: Failing over 100% of traffic to a cold secondary region whose Redis caches are empty sends 100% cache-miss load straight to the secondary DB. Pre-warm caches or keep active-active regional cells sized for 50% headroom.

Resilience, observability & cell-based isolation

At high scale, cell-based architecture (bulkheading) limits the blast radius of bad config pushes or noisy neighbors: partition users into independent cells (each holding 5–10% of traffic with its own compute, Redis, and DB shard) behind a thin L7 routing layer. A poisoned query in Cell 3 cannot impact Cells 1–20.

Every network hop must declare strict timeouts (shorter than caller deadline), circuit breakers (trip at >50% 5xx over 10s), hedged requests (only for idempotent reads at p99), and distributed tracing so bottlenecks are visible in real time.

Practical checklist

  • Document peak read/write QPS, payload size, p99 latency SLO, and RPO/RTO targets before choosing components.
  • Enforce Idempotency-Key headers on all non-idempotent POST/PATCH APIs.
  • Place timeouts, jittered exponential backoff, and retry budgets on every outbound network call.
  • Separate OLTP databases from OLAP analytics via CDC (Debezium → Kafka → ClickHouse/BigQuery).
  • Verify sharding/partition keys against your top 1% 'celebrity' or 'whale' tenants to prevent hot-shard saturation.
  • Test failover and cache-cold recovery in staging via periodic chaos/game-day drills.
03 / Engineering trade-offs

Weighing architectural decisions

Strong Consistency (CP) vs. High Availability (AP)

Advantage: CP stores (Spanner, CockroachDB, single-leader Postgres) prevent double-spending and stale reads on financial ledgers.

Drawback: Cross-AZ/cross-region consensus adds 10–150 ms write latency and halts writes during minority network partitions.

Microservices vs. Modular Monolith

Advantage: Independent deployments, isolated scaling (GPU inference vs. lightweight API), and clear team ownership.

Drawback: Network serialization overhead, distributed transactions (Sagas), and operational complexity of service mesh + observability.

Push (Fan-out on Write) vs. Pull (Fan-out on Read)

Advantage: Fan-out on write pre-computes timelines in Redis, delivering <15 ms feed reads.

Drawback: Celebrity accounts with 10M followers trigger massive write amplification; hybrid push-for-regular / pull-for-celebrities is required.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Retry Storm / Metastable Failure

A transient DB slowdown causes clients and upstream services to retry 3x immediately, tripling load on the struggling DB and locking the system in a permanent brownout even after traffic drops.

What helps: Enforce exponential backoff with full jitter, per-client retry budgets (max 10% retry ratio in Envoy), and circuit breakers.

Hot-Key / Celebrity Partition Skew

Sharding by `tenant_id` or `product_id` sends 40% of total cluster QPS to a single Redis or DynamoDB partition during a viral event, saturating one node while 99 others sit idle.

What helps: Add local in-memory L1 caches (5-second TTL), split hot keys with random suffixes (`key#0..9`), or enable read-replica fan-out.

Dual-Write Inconsistency (DB + Kafka)

A service commits a row to PostgreSQL and then crashes before publishing the `OrderCreated` event to Kafka, leaving downstream search and billing permanently out of sync.

What helps: Use the **Transactional Outbox Pattern**: write the event into an `outbox` table inside the same DB transaction and tail it with Debezium CDC.

Thundering Herd on Cache Expiration

A popular cached key expires simultaneously for 5,000 concurrent requests, slamming the origin database with identical expensive queries.

What helps: Use request coalescing (`singleflight`), probabilistic early expiration, or serve stale cache values while refreshing asynchronously.

05 / Practical checklist

Avoid these mistakes

  • Designing an architecture without first calculating read/write QPS, payload sizes, and 5-year storage capacity.
  • Using a single primary RDBMS for both OLTP transactions and heavy analytical `GROUP BY` reporting queries.
  • Omitting idempotency keys on mutating endpoints (`POST /payments`), causing duplicate charges when mobile clients retry on flaky networks.
  • Assuming synchronous REST/gRPC chains of 6+ services can achieve 99.99% availability (`0.999^6 = 99.4%` composite availability).
  • Drawing an 'API Gateway -> Microservices -> Database' box diagram without specifying partitioning keys, caching eviction, or backpressure.
