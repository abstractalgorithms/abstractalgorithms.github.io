THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Federation decouples schema ownership across teams without forcing clients to stitch APIs, provided you enforce strict subgraph composition checks and batch entity lookups.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

As a monolithic GraphQL server grows past 5–10 teams, schema merge conflicts, shared release trains, and coupled database imports stall delivery. Federation moves schema composition to build/registry time and query execution planning to a high-throughput router (such as Apollo Router in Rust or WunderGraph Cosmo), so the Orders team and Identity team ship independently while mobile clients still fetch user { orders { items { price } } } in one round trip.

  • Subgraphs expose a _service { sdl } field and an _entities(representations: [_Any!]!) entry point so the router can hydrate foreign types by @key.
  • Federation v2 replaces v1's implicit ownership with explicit directives: @shareable for multi-subgraph fields, @external + @requires for computed cross-subgraph fields, and @override(from: "...") for zero-downtime field migrations.
  • The router compiles each incoming query against the composed supergraph SDL into a static QueryPlan (a DAG of Sequence, Parallel, and Flatten fetch steps) before sending a single downstream HTTP request.
  • Entity resolution batches all parent keys at a given depth into one _entities POST per subgraph, preventing per-row N+1 HTTP calls if the subgraph pairs it with DataLoader for its own DB.
  • Schema checks (rover subgraph check) validate composition rules and client traffic impact against persisted operation metrics before a subgraph PR can merge.

Good candidates

  • Multiple autonomous backend teams own distinct domain boundaries (e.g., Identity, Catalog, Checkout) and need independent CI/CD pipelines behind one client-facing API.
  • Mobile or web clients aggregate deeply nested cross-domain data in a single request to avoid client-side waterfall calls over high-latency cellular networks.
  • You are incrementally strangler-figging a legacy REST or monolithic GraphQL service into domain microservices without breaking existing client queries.

Think twice

  • A single team owns the entire backend and database; a modular monolith with one GraphQL server avoids network hops, query-planning overhead, and distributed tracing complexity.
  • Workloads are strictly high-throughput service-to-service RPC or binary streaming where Protobuf over gRPC gives 5–10x lower serialization overhead and strict binary contracts.
  • Subgraphs share the same underlying relational tables with heavy cross-domain joins; federating across them turns SQL joins into chatty network _entities calls.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA Checkout subgraph owns Order { id totalCents buyerId } and needs to display buyer { email } from Identity plus shippingEstimateCents computed from Product.weightGrams owned by Catalog.

The idea

GraphQL Federation separates schema authoring from schema execution. Each backend service (a subgraph) publishes a standard GraphQL schema augmented with federation directives such as @key, @external, and @requires. At build or deploy time, a schema registry composes all subgraph SDLs into a single supergraph SDL—verifying that types align, ownership is unambiguous, and every @key path is reachable.

At runtime, a stateless router (e.g., Apollo Router written in Rust, handling ~10x the RPS per core of a Node.js gateway) receives client queries, parses and validates them against the public API schema, and builds a QueryPlan. Rather than executing resolvers one field at a time, the router batches entity references per depth level and dispatches parallel HTTP/gRPC requests to subgraphs' _entities endpoints, merging the JSON responses back into the exact shape the client requested.

Concrete walkthrough

Consider an e-commerce query fetching a user's recent orders and the current stock count of each ordered SKU:

query UserOrders($id: ID!) {
  user(id: $id) {
    email
    orders(first: 10) {
      id
      items { sku quantity product { title stockCount } }
    }
  }
}
  1. Parse & Plan: The router checks its in-memory QueryPlan cache (keyed by normalized query hash). On a miss, it generates a 3-step Sequence plan:
    • Step 1 (Users Subgraph): Execute query(id: ID!) { user(id:id) { __typename id email } }. The router requests __typename and id even though the client didn't ask for id, because id is the @key needed by Orders.
    • Step 2 (Orders Subgraph): Using the User representation {"__typename": "User", "id": "u_42"}, the router calls POST /graphql on Orders with query(reps: [_Any!]!) { _entities(representations:reps) { ... on User { orders(first: 10) { id items { sku quantity product { __typename sku } } } } } }.
    • Step 3 (Inventory Subgraph): Orders returns 25 line items across 10 orders, deduplicated by the router into 14 unique {__typename: "Product", sku: "..."} keys. The router sends one _entities batch of 14 representations to Inventory to fetch title and stockCount.
  2. Flatten & Merge: The router uses Flatten nodes to splice the 14 Product objects back into their 25 line-item slots in memory and streams the final JSON response to the client.

The router orchestrates `@key` dependencies in sequence while batching all sibling entity keys at each depth into a single `_entities` request per subgraph.

Federation v2 directives & composition rules

Federation v1 relied on implicit extend type ownership, which broke down when two teams legitimately served the same value object (such as Money { amount currency }) or needed to migrate fields without downtime. Federation v2 fixes this with explicit, compiler-checked directives:

  • @key(fields: "id", resolvable: true): Declares an entity's primary key. Setting resolvable: false lets a subgraph reference an entity stub (e.g., User { id }) without implementing __resolveReference.
  • @shareable: Opts a field or object type into multi-subgraph resolution. Both subgraphs must return semantically identical values for the same input; the router picks whichever subgraph is cheapest to reach in the current QueryPlan.
  • @requires(fields: "weightGrams") + @external: Tells the query planner that Checkout cannot compute shippingFee until it receives weightGrams from Catalog, forcing a Sequence edge in the plan.
  • @provides(fields: "name"): Optimization hint declaring that Orders already denormalizes Product.name in its own table, allowing the router to skip calling Inventory when the client only asks for name.
  • @inaccessible: Hides internal join keys or migration fields from the public client API schema while keeping them available to the query planner.

Failure modes

  • Non-nullable error propagation: In GraphQL, an unhandled error in a non-nullable child field (orders: [Order!]!) bubbles up to the nearest nullable ancestor—potentially wiping out the entire user payload when one downstream subgraph blips. Always keep cross-subgraph entity fields nullable.
  • QueryPlan explosion: Unbounded QueryPlan compilation on deeply nested polymorphic fragments (... on TypeA, ... on TypeB) can spike router CPU and memory. Cap query depth, limit fragment/alias counts, and size the router's QueryPlan LRU cache (typically 10k–50k entries).
  • Stale supergraph SDL: If a subgraph deploys a breaking change before the router receives the updated supergraph config, _entities queries fail with 400 Bad Request (Cannot query field X). Always gate subgraph deploys on rover subgraph check and update the supergraph before removing old fields.
  • Header & auth stripping: Forgetting to forward Authorization, x-tenant-id, or traceparent in router headers rules causes subgraphs to reject valid requests or start disconnected trace roots.

Governance, telemetry & production hardening

At scale, the router is your single observability choke point. Configure OpenTelemetry export at the router to emit a root span with graphql.operation.name, query_plan.cost, and child spans per subgraph Fetch node—this immediately isolates whether a 400 ms p99 spike is query planning (< 2 ms in Rust), network transit, or a specific subgraph's _entities resolver.

Pair observability with Persisted Query Lists (PQL) in production: clients ship build-time operation manifests to the registry, and the router rejects arbitrary ad-hoc queries from the public internet. This eliminates runtime query-complexity DoS attacks, shrinks mobile upload payloads to a 64-byte SHA-256 ID, and lets CDNs cache public GET responses at the edge.

Practical checklist

  • Define @key fields using immutable internal IDs (UUIDs/ULIDs), never mutable emails or slugs.
  • Implement a request-scoped DataLoader inside every subgraph's __resolveReference to batch _entities keys into a single DB query.
  • Keep cross-subgraph extension fields nullable so a single subgraph timeout degrades gracefully instead of nulling the root response.
  • Add rover subgraph check (or Cosmo wgc subgraph check) to every subgraph CI pipeline to block composition breaks and field deletions with active client traffic.
  • Enable Automatic Persisted Queries (APQ) or strict Safelisting + max depth (e.g., 8) and timeout budgets (e.g., 1,000 ms per subgraph) at the router.
  • Forward traceparent and verified JWT claims (e.g., x-user-id signed/stripped at the edge) to all subgraphs.
03 / Engineering trade-offs

Weighing architectural decisions

Latency & network hops

Advantage: Clients make 1 external round trip instead of 4–6 sequential REST calls, and independent branches in a query execute in `Parallel` at the router.

Drawback: Deeply nested `@requires` chains create `Sequence` dependencies inside the `QueryPlan`, adding 5–20 ms per hop for router planning, JSON serialization, and internal TLS.

Team autonomy vs. governance

Advantage: Teams deploy subgraphs on independent schedules without coordinating a central GraphQL gateway release.

Drawback: Requires a central schema registry (e.g., Apollo GraphOS or Cosmo Control Plane) and strict linting; an uncoordinated breaking change or `@shareable` conflict can block supergraph composition.

Caching & rate limiting

Advantage: Automatic Persisted Queries (APQ) at the router let clients send a 64-char SHA-256 hash instead of a 10 KB query string, enabling CDN GET caching for public queries.

Drawback: Single-endpoint `POST /graphql` defeats URL-based HTTP caching and WAF rules unless query-depth limits, cost analysis, and per-field `@cacheControl` headers are configured.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Subgraph N+1 database storm

The router batches 50 `User` keys into a single `_entities(representations: [...])` request, but the subgraph's `__resolveReference` handler issues 50 individual `SELECT * FROM users WHERE id = ?` queries.

What helps: Wrap every `__resolveReference` and nested field resolver in a request-scoped DataLoader that batches keys into `WHERE id = ANY($1)`.

Supergraph composition deadlock

Two teams simultaneously add `status: String` to a shared type without `@shareable`, or rename a `@key` field, causing supergraph composition to fail in CI/CD.

What helps: Run `rover subgraph check` in every subgraph's PR pipeline against the latest production supergraph, and use `@override` or additive deprecations (`@deprecated`) for field moves.

Cascading partial failure on non-nullable fields

A non-essential `Reviews` subgraph times out, and because `Product.reviews: [Review!]!` is non-nullable, GraphQL error bubbling nulls out the entire `Product` object.

What helps: Make cross-subgraph extension fields nullable by default, set per-subgraph timeouts (e.g., 800 ms) in the router, and return partial `data` alongside `errors`.

Query complexity & depth DoS

An attacker or buggy client sends a cyclic 15-level query (`user { friends { friends { ... } } }`), triggering exponential `_entities` fan-out across subgraphs.

What helps: Enforce static depth limits (e.g., max depth 8), alias limits, and demand-based cost budgets at the router, or lock production to an allowlist of persisted queries.

05 / Practical checklist

Avoid these mistakes

  • Putting business logic or custom resolvers inside the router instead of keeping the router purely declarative for planning, auth, and telemetry.
  • Splitting a single database across two subgraphs and using `@key` joins over HTTP instead of keeping cohesive tables in one subgraph.
  • Marking every field `@shareable` to silence composition errors, which causes nondeterministic field resolution if two subgraphs return different values.
  • Forgetting to propagate `Authorization` and `traceparent` headers from the router to downstream subgraphs, breaking authz and distributed traces.
  • Allowing unbounded list fields without cursor pagination (`first`/`after`), causing multi-megabyte `_entities` payloads between router and subgraphs.
