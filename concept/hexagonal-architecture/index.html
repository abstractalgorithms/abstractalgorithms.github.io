Hexagonal
Architecture.

Hexagonal Architecture (Ports & Adapters) isolates core domain logic inside an explicit boundary where all external I/O—HTTP, SQL, queues, third-party APIs—plugs in through interfaces owned by the domain.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

By inverting dependencies so adapters depend on domain ports (never the reverse), you can swap databases, frameworks, or message brokers and run full business-logic tests in milliseconds with zero infrastructure.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

In traditional layered architectures (Controller -> Service -> Repository -> DB), business rules inevitably leak framework annotations (@Entity, @Transactional, HTTP status codes) and SQL row shapes. When you need to support a Kafka consumer alongside REST, swap Stripe for Adyen, or migrate from DynamoDB to Postgres, every service method breaks. Hexagonal Architecture places the domain model at the center with zero external imports, forcing all I/O to translate at the edge.

  • Driving (Primary) Ports are interfaces exposed by the application core (e.g., PlaceOrderUseCase), invoked by Driving Adapters (REST controller, gRPC handler, Kafka listener).
  • Driven (Secondary) Ports are interfaces defined by the core for what it needs (e.g., OrderRepository, PaymentGateway), implemented by Driven Adapters (Postgres, Stripe, in-memory fakes).
  • The Dependency Rule is strict and one-way: source-code imports only point inward (adapters -> application -> domain). The domain package has zero imports from Spring, FastAPI, Hibernate, or AWS SDKs.
  • Adapters own their own DTOs and ORM models (OrderEntity, StripeChargeResponse) and map them to/from pure domain entities (Order, Money) at the boundary.
  • Architectural fitness functions (ArchUnit in Java, import-linter in Python, depguard in Go) enforce the boundary automatically in CI so convenience imports don't erode it over time.

Good candidates

  • Core business domains with complex invariants (billing, order state machines, risk scoring, ledger accounting) that outlive web frameworks and databases.
  • Systems with multiple entry points (REST API, gRPC, CLI, Kafka consumer) driving the exact same use cases.
  • Teams that want fast, deterministic unit tests for 90% of business rules without spinning up Docker/Testcontainers on every save.

Think twice

  • Thin CRUD microservices or admin back-offices with almost no domain logic beyond validating JSON and writing rows.
  • Data-intensive ETL or reporting pipelines where SQL window functions and bulk set operations are the business logic; forcing them through domain objects kills performance.
  • Early-stage prototypes or hackathons where speed of iteration matters more than 5-year maintainability.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn e-commerce checkout service accepts synchronous orders via POST /v1/orders and asynchronous subscription renewals from a billing.renewals Kafka topic.

The idea

Proposed by Alistair Cockburn in 2005, Hexagonal Architecture (formally Ports and Adapters) reframes an application from a vertical stack (UI -> Logic -> DB) into an inside/outside symmetry. The inside (the hexagon) contains only pure domain entities, value objects, and application use cases. The outside contains every external actor: web browsers, gRPC callers, cron jobs, relational databases, Redis caches, and third-party webhooks.

Nothing outside touches the inside directly. Instead, the core defines Ports (technology-agnostic interfaces): Driving Ports on the left (what the app offers) and Driven Ports on the right (what the app needs). Adapters live strictly outside the hexagon, translating external protocols (HTTP JSON, SQL rows, Protobuf) into domain calls and back.

Concrete walkthrough

Trace a TransferFunds use case in a banking service:

  1. Driving Adapter (RestTransferController): Receives POST /v1/transfers with { "from": "acc_1", "to": "acc_2", "cents": 5000 }, validates HTTP headers/JWT, maps JSON into a TransferCommand, and calls the driving port TransferFundsPort.execute(cmd).
  2. Application Core (TransferFundsService): Runs inside a UnitOfWork port. It loads Account aggregates via the driven port AccountRepository.findById(...), calls fromAccount.debit(Money.usd(5000)) and toAccount.credit(...) (enforcing overdraft invariants in pure domain code), saves both accounts, and emits FundsTransferredEvent through DomainEventPublisher.
  3. Driven Adapters:
    • PostgresAccountAdapter implements AccountRepository, mapping Account domain objects to accounts_tbl rows via SELECT ... FOR UPDATE.
    • OutboxEventAdapter implements DomainEventPublisher, writing the event to an outbox table in the same SQL transaction.
  4. Unit Test Swap: In TransferFundsTest, PostgresAccountAdapter is replaced with InMemoryAccountRepository. Zero Spring context, zero Docker, and zero network calls—testing overdraft rules and double-entry balance invariants in < 1 ms.

All source-code dependencies point inward toward the hexagon; driven adapters implement interfaces owned by the core via Dependency Inversion.

Driving vs. driven ports and transaction boundaries

A frequent point of confusion is who owns the interface. In Hexagonal Architecture, the core owns both:

  • Driving Ports (e.g., PlaceOrderUseCase) are implemented by the application service and called by controllers or CLI runners.
  • Driven Ports (e.g., OrderRepository) are called by the application service and implemented by infrastructure adapters.

Because the core cannot import @Transactional without violating the dependency rule, model atomicity explicitly using a TransactionPort (or UnitOfWork closure: tx.run(() -> { ... })) implemented by the persistence adapter, or keep @Transactional in a thin application-wiring layer outside the pure domain entities.

Failure modes

  • God-port proliferation: Defining a single DatabasePort with 40 methods forces every test fake to stub 40 methods. Keep driven ports small and cohesive (Interface Segregation Principle, e.g., OrderReader, OrderWriter).
  • Adapter logic creep: Putting discount calculations inside a REST controller or eligibility filters inside a SQL WHERE clause splits business truth across tiers.
  • Fake-vs-Prod divergence: In-memory fakes that don't enforce unique keys, transaction isolation, or pagination sorting create false confidence. Always pair fakes with a shared Repository Contract Test run against real Postgres in CI.
  • Over-mapping simple reads: Running complex read dashboards through aggregate hydration (N entities + mappers) causes severe latency; bypass domain aggregates for read-only CQRS projections.

Enforcing boundaries with fitness functions

Architecture diagrams rot unless automated tests enforce them. Add a build-time dependency check in CI:

  • Java / Kotlin: Use ArchUnit (noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat().resideInAnyPackage("..adapter..", "org.springframework..", "jakarta.persistence..")).
  • Python: Use import-linter contracts (type = forbidden) forbidding domain from importing fastapi, sqlalchemy, or boto3.
  • Go: Place domain in an internal package and enforce import rules with depguard in golangci-lint.

Pair this with a contract test suite: an abstract test class verifying save(), findById(), optimistic locking, and not-found behavior, executed against both InMemoryOrderRepo and TestcontainersPostgresOrderRepo.

Practical checklist

  • Verify domain and application packages have zero imports from web frameworks, ORMs, or cloud SDKs.
  • Name ports after domain capabilities (PaymentGateway, OrderRepository), not vendor implementations (StripeClient, PostgresRepo).
  • Keep ORM entities and JSON DTOs inside adapter packages and map them explicitly at the boundary.
  • Enforce package dependency rules automatically in CI using ArchUnit, import-linter, or depguard.
  • Run a shared contract test suite against both in-memory fakes (fast unit loop) and real Testcontainers adapters (CI).
  • Use thin read-only query projections (CQRS) for complex reporting endpoints instead of forcing them through domain aggregates.
03 / Engineering trade-offs

Weighing architectural decisions

Testability & longevity

Advantage: Domain logic is 100% decoupled from frameworks, enabling sub-second in-memory tests and painless major framework upgrades.

Drawback: Requires extra interfaces, mappers, and package structure—creating boilerplate for simple pass-through operations.

Mapping overhead

Advantage: ORM lazy-loading bugs, JSON serialization quirks, and DB column renames stay trapped inside adapters.

Drawback: Converting `OrderEntity <-> Order <-> OrderResponseDto` adds repetitive mapping code and minor allocation overhead on high-throughput paths.

Transaction boundaries

Advantage: Core use cases stay explicit about consistency boundaries (e.g., via a `UnitOfWork` port).

Drawback: Without care, hiding persistence behind a `Repository` port can accidentally split one logical unit of work into multiple autocommit queries.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Leaky ORM abstractions

Putting `@Entity`, `@Column`, or SQLAlchemy `Base` directly on domain classes so `OrderRepository` returns framework-tracked proxies, causing `LazyInitializationException` in the domain.

What helps: Keep domain models as plain POJOs/dataclasses/structs and map from separate ORM entities inside the persistence adapter.

Anemic pass-through boilerplate

Every single `GET /users/{id}` query is wrapped in a `GetUserPort`, `GetUserUseCase`, `UserReadRepository`, and 4 identical DTOs with zero logic.

What helps: Apply CQRS pragmatically: use full Hexagonal ports for commands/writes with invariants, and allow thin read-only query handlers to project directly from the DB.

Boundary erosion via shared utility imports

A developer imports `org.springframework.http.HttpStatus` or `sqlalchemy.exc.IntegrityError` inside a domain service for convenience.

What helps: Add an automated CI check (ArchUnit / `import-linter` / Go `depguard`) that fails the build if `domain` imports any adapter or framework package.

Mock-heavy tests drifting from real SQL behavior

All tests run against an in-memory `HashMap` fake repository, passing in CI while production fails on a Postgres unique constraint or `NULL` handling.

What helps: Run a shared **contract test suite** against both the in-memory fake (every save) and the real Postgres/Kafka adapter via Testcontainers (in CI).

05 / Practical checklist

Avoid these mistakes

  • Putting business logic inside driving adapters (controllers) or driven adapters (SQL queries / stored procedures) instead of the domain.
  • Naming ports after the technology (`PostgresOrderPort`, `KafkaEventPort`) instead of the domain intent (`OrderRepository`, `OrderEventPublisher`).
  • Returning HTTP status codes or framework exceptions from use cases instead of domain-specific result types or exceptions.
  • Splitting a single transaction across two repository calls without a `UnitOfWork` / transaction boundary port.
  • Enforcing 1-to-1 interface-per-class ceremony everywhere instead of reserving ports for genuine I/O boundaries.
