CSRF Defense
Patterns.

CSRF (Cross-Site Request Forgery) tricks an authenticated user's browser into sending unintended state-changing requests to a target origin that automatically attaches ambient session cookies.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Modern CSRF defense stacks three layers: `SameSite=Lax` (or `Strict`) session cookies, `Sec-Fetch-Site` Fetch Metadata validation, and unpredictable per-session Synchronizer Tokens for legacy or cross-site flows.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Whenever authentication relies on ambient credentials—HTTP cookies, HTTP Basic Auth, or client TLS certificates—any malicious website can submit a hidden

or request that the browser happily signs with the victim's cookies. A single CSRF flaw can trigger unauthorized wire transfers, email/password resets, or OAuth account takeovers. Because browsers now ship SameSite defaults and Sec-Fetch-Site headers, understanding how modern browser defenses interact with legacy endpoints and CORS is critical for zero-gap web security.

  • SameSite=Lax (the modern browser default) withholds cookies on cross-site POST forms and fetch() calls, while still sending them on top-level GET navigations; SameSite=Strict withholds them even on inbound links.
  • Fetch Metadata headers (Sec-Fetch-Site: same-origin | same-site | cross-site | none) are browser-enforced forbidden headers that cannot be spoofed by JavaScript, letting servers reject cross-site state changes in 5 lines of middleware.
  • The Synchronizer Token Pattern embeds a cryptographically random, per-session (or per-request) secret in forms or custom headers (X-CSRF-Token) and compares it using constant-time equality (hmac.Equal / crypto.timingSafeEqual).
  • The Stateless Double-Submit Cookie pattern must bind the token to the user's session using an HMAC (HMAC(secret, sessionId + random)) rather than a raw random cookie; otherwise, an attacker on a compromised subdomain can overwrite the cookie.
  • CORS preflights (OPTIONS) block custom headers and application/json cross-origin fetch() calls, but simple requests (application/x-www-form-urlencoded, multipart/form-data, text/plain) bypass CORS preflight completely.

Good candidates

  • All browser-facing web applications using session cookies (Set-Cookie) for authentication on state-changing (POST, PUT, PATCH, DELETE) endpoints.
  • OAuth 2.0 / OIDC authorization flows, which must bind the authorization callback to the user's session via the state parameter (or PKCE) to prevent login CSRF.
  • Single-Page Applications (SPAs) and APIs that share a parent domain (app.example.com and api.example.com), where SameSite alone does not block sibling-subdomain attacks.

Think twice

  • Pure machine-to-machine or mobile APIs that authenticate strictly via explicit Authorization: Bearer headers read from memory—browsers never auto-attach Authorization headers cross-site.
  • Idempotent, read-only GET/HEAD endpoints (provided they never mutate state—if a GET endpoint mutates state, fix the HTTP verb first).
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn engineering team assumed Access-Control-Allow-Origin: https://app.example.com protected their POST /api/transfer endpoint, which parsed JSON bodies without checking Content-Type.

The idea

Web browsers automatically attach ambient credentials (cookies, HTTP Basic Auth) to every request targeting an origin—regardless of which page initiated the request. If victim is logged into bank.com and visits evil.com, a hidden submitted by evil.com arrives at bank.com with victim's valid session cookie.

CSRF Defense breaks this confused-deputy problem by requiring proof of origin or intent that a cross-site page cannot forge: either telling the browser not to send the cookie cross-site (SameSite), inspecting browser-enforced origin metadata (Sec-Fetch-Site / Origin), or requiring an unpredictable secret (X-CSRF-Token) that evil.com cannot read due to the Same-Origin Policy (SOP).

Concrete walkthrough

Trace how a defense-in-depth POST /api/v1/payout request is evaluated:

  1. Browser Layer (SameSite=Lax + __Host- prefix):
    • Session cookie is set as Set-Cookie: __Host-sid=...; Secure; HttpOnly; Path=/; SameSite=Lax.
    • If evil.com submits a cross-site POST form, the browser strips __Host-sid before the packet leaves the client.
  2. Edge/Middleware Layer (Fetch Metadata):
    • Server inspects Sec-Fetch-Site. If the header is cross-site (and the endpoint is not a public webhook/OAuth callback), the server immediately returns 403 Forbidden.
  3. Application Layer (Synchronizer Token + Content-Type):
    • For same-origin or legacy clients lacking Sec-Fetch-Site, the SPA reads an HMAC-bound token and sends X-CSRF-Token: with Content-Type: application/json.
    • Because X-CSRF-Token and application/json trigger a CORS preflight and evil.com cannot read the token across origins, the server verifies timingSafeEqual(expected, actual) and processes the payout.

Layered CSRF defense: browser cookie scoping, Fetch Metadata origin checks, and cryptographic token verification.

SameSite nuances & subdomain risks

A common misconception is that SameSite=Lax eliminates CSRF completely. Three edge cases remain:

  1. Same-Site != Same-Origin: SameSite uses the registrable domain (eTLD+1). If static.example.com or staging.example.com is compromised, it is considered same-site to app.example.com, so SameSite=Lax and SameSite=Strict cookies are sent.
  2. Lax+POST 2-minute window: Chromium historically allowed cookies on top-level POSTs for 120 seconds after cookie creation if SameSite was omitted (default Lax). Explicitly setting SameSite=Lax removes this grace window.
  3. GET state mutations: SameSite=Lax still sends cookies on top-level GET navigations ( or window.location=...). Any state change on GET remains vulnerable.

Failure modes

  1. CORS misconfiguration with credentials: true: Reflecting arbitrary Origin headers with Access-Control-Allow-Credentials: true lets an attacker read CSRF tokens from GET /csrf-token cross-origin, defeating Synchronizer Tokens.
  2. Unsigned Double-Submit Cookie: Comparing cookie.csrf == header.csrf without HMAC binding allows a sibling-subdomain XSS or MITM on plain HTTP to plant a matching cookie.
  3. CSRF token leaked in GET URLs: Passing ?csrf=... leaks the token in server access logs, Referer headers to third-party images, and browser history.
  4. OAuth Login CSRF: Omitting state on /oauth/callback lets an attacker force a victim's browser to link the attacker's OAuth identity to the victim's session.

Framework & Go/Java implementation notes

  • Go 1.25+ net/http.CrossOriginProtection: Implements Fetch Metadata (Sec-Fetch-Site) + Origin checks in standard library middleware with zero token state.
  • Spring Security (Java): Enables CsrfFilter by default using XorCsrfTokenRequestAttributeHandler (BREACH-mitigated masked Synchronizer Token) and CookieCsrfTokenRepository for SPAs.
  • BREACH mitigation: When embedding a CSRF token inside compressed HTTPS HTML responses, mask the token with a per-response random one-time pad (XOR) so attackers cannot infer the secret via compression-ratio side channels.

Practical checklist

  • Ensure GET and HEAD endpoints are strictly read-only and never mutate state.
  • Set Secure; HttpOnly; SameSite=Lax (and __Host- prefix where possible) on all session cookies.
  • Add Fetch Metadata middleware rejecting Sec-Fetch-Site: cross-site on state-changing routes.
  • Enforce Content-Type: application/json on JSON APIs so simple / text/plain requests fail fast.
  • Use HMAC-bound Synchronizer or Double-Submit tokens verified with constant-time comparison.
  • Validate state and PKCE on all OAuth/OIDC callbacks and protect /login against Login CSRF.
03 / Engineering trade-offs

Weighing architectural decisions

SameSite=Strict vs. SameSite=Lax

Advantage: `SameSite=Strict` blocks all cross-site cookie transmission, including top-level link clicks.

Drawback: Breaks inbound links from emails, Slack, or Google Search—users appear logged out when clicking a link into your app.

Stateful Synchronizer Token vs. Signed Double-Submit

Advantage: Synchronizer tokens require zero extra cookies and are trivial to invalidate on logout.

Drawback: Requires server-side session state (Redis/DB), whereas HMAC-bound double-submit works in stateless JWT-in-cookie architectures.

Fetch Metadata (`Sec-Fetch-Site`) vs. `Origin`/`Referer`

Advantage: `Sec-Fetch-Site` explicitly classifies `same-origin` vs `same-site` vs `cross-site` without brittle URL parsing.

Drawback: Very old browsers or corporate proxies may strip `Sec-Fetch-*` headers, so pair it with `Origin` or a Synchronizer Token fallback.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Simple-Request CORS Bypass

Relying solely on CORS `Access-Control-Allow-Origin` without rejecting `application/x-www-form-urlencoded`, `multipart/form-data`, or `text/plain` lets HTML `<form>` and `fetch()` skip preflight.

What helps: Strictly validate `Content-Type: application/json` on JSON APIs AND enforce `Sec-Fetch-Site` or a CSRF token.

SameSite Sibling-Subdomain Blind Spot

`SameSite=Lax` treats `evil.example.com -> api.example.com` as `same-site` (same registrable eTLD+1), attaching cookies to cross-subdomain attacks.

What helps: Use `__Host-` cookie prefixes (`__Host-session=...; Secure; Path=/; HttpOnly`) and check `Sec-Fetch-Site == 'same-origin'` or `Origin` exact-match.

Login CSRF & OAuth State Omission

Skipping CSRF protection on `POST /login` or omitting `state` in OAuth callbacks lets an attacker log the victim into the attacker's account to harvest subsequent activity.

What helps: Apply CSRF tokens or `Sec-Fetch-Site` to login/logout endpoints and enforce cryptographically bound `state` + PKCE on OAuth.

HTTP Method Override Abuse

Frameworks supporting `_method=DELETE` query parameters or `X-HTTP-Method-Override` let a cross-site `GET` or `POST` form trigger `DELETE` handlers.

What helps: Disable method-override middleware or run CSRF validation before method rewriting.

05 / Practical checklist

Avoid these mistakes

  • Mutating state on `GET` requests (e.g., `GET /logout` or `GET /unsubscribe?confirm=1`), which `SameSite=Lax` explicitly allows cross-site.
  • Setting `Access-Control-Allow-Origin: *` alongside `Access-Control-Allow-Credentials: true` (or blindly echoing the request `Origin` header).
  • Using `==` string comparison instead of constant-time comparison (`timingSafeEqual`) when verifying CSRF tokens.
  • Exposing the CSRF token in URL query parameters, which leaks it via `Referer` headers and browser history.
  • Believing HTTPS/TLS alone prevents CSRF—an attacker's `https://evil.com` page can still submit HTTPS forms to `https://bank.com`.
