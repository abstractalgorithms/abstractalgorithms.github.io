01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is CSRF (Cross-Site Request Forgery).

Web browsers automatically attach ambient credentials (session cookies, HTTP Basic Auth) to every request targeting an origin—regardless of which page initiated it. If a logged-in user visits evil.com, a hidden <form action="https://bank.com/transfer" method="POST"> arrives at bank.com with the victim's valid session cookie.

CSRF Defense breaks this confused-deputy problem by requiring proof of origin or intent that a cross-site page cannot forge: SameSite cookie attributes, browser-enforced Sec-Fetch-Site Fetch Metadata headers, and unpredictable Synchronizer or HMAC-bound Double-Submit tokens.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Naive CORS & Raw Double-Submit Cookies Fail.

Relying solely on CORS Access-Control-Allow-Origin fails because HTML <form> submissions and fetch() with Content-Type: text/plain are simple requests that skip CORS preflight completely. Similarly, SameSite=Lax treats sibling subdomains (blog.example.com -> api.example.com) as same-site (same eTLD+1) and still attaches cookies.

Defense-in-Depth Flow

3-Layer Evaluation of a State-Changing POST /api/v1/payout

Stacking __Host- SameSite=Lax cookies, Sec-Fetch-Site middleware, and Content-Type + HMAC token checks closes simple-request and subdomain bypasses.

Bypassing Naive CORS via text/plain Simple Request

A POST /api/transfer endpoint relied on CORS without checking Content-Type. An attacker sent fetch(..., {credentials:'include', headers:{'Content-Type':'text/plain'}, body:'{...}'}), skipping preflight and executing the transfer.

Subdomain Cookie Overwrite Defeated by HMAC Binding

An XSS on blog.example.com overwrote an unsigned CSRF cookie on .example.com. Binding the token via HMAC(secret, sessionId + random) with __Host- prefix closed the bypass.

03
STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where CSRF Defense Applies (and When Bearer Headers Are Immune).

CSRF applies wherever browsers auto-attach ambient credentials; explicit Authorization: Bearer headers read from memory are never auto-attached cross-site.

ChoiceWhat it buysWhat it costs
Required: Cookie-Authenticated SPAs, SSR Apps & OAuthProtects all `POST`/`PUT`/`PATCH`/`DELETE` routes and binds OAuth `/callback` via `state` + PKCE.Requires middleware on login/logout too (to prevent Login CSRF).
Required: Sibling Subdomains (`app.example.com` / `api.example.com`)`__Host-` cookies + `Sec-Fetch-Site: same-origin` block compromised sibling subdomains.`__Host-` requires `Secure`, `Path=/`, and no `Domain` attribute.
Not Needed: Pure M2M / Mobile `Authorization: Bearer` APIsZero CSRF risk when cookies are never used for auth.Storing JWTs in `localStorage` trades CSRF immunity for XSS theft exposure.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to implement Fetch Metadata & Constant-Time Token Checks.

  1. Keep GET/HEAD Read-Only: Never mutate state on GET (SameSite=Lax sends cookies on top-level GET links).
  2. Enforce Sec-Fetch-Site + Content-Type: application/json: Reject cross-site state changes (except explicit webhooks) and block text/plain / application/x-www-form-urlencoded on JSON APIs.
  3. Constant-Time Verification: Validate Synchronizer or HMAC-bound tokens with hmac.compare_digest / crypto.timingSafeEqual, and mask tokens per-response (BREACH mitigation) when rendered inside compressed HTML.
# Fetch Metadata + Constant-Time HMAC CSRF Guard (Python)
import hmac, hashlib

def verify_csrf_request(headers: dict, session_id: str, secret: bytes) -> bool:
    # 1. Browser-enforced Fetch Metadata (cannot be spoofed by JS)
    fetch_site = headers.get('sec-fetch-site')
    if fetch_site == 'cross-site':
        return False
    # 2. Require explicit JSON Content-Type on API mutations
    if not headers.get('content-type', '').startswith('application/json'):
        return False
    # 3. Verify HMAC-bound X-CSRF-Token in constant time
    provided = headers.get('x-csrf-token', '')
    expected = hmac.new(secret, session_id.encode(), hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, provided)

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: SameSite vs. Fetch Metadata vs. Synchronizer vs. Double-Submit.

Each defense layer has distinct state requirements, subdomain coverage, and legacy browser trade-offs.

ChoiceWhat it buysWhat it costs
`SameSite=Lax` vs. `SameSite=Strict``Lax` preserves inbound links from email/Slack while blocking cross-site `POST` forms.`Strict` breaks inbound links (users appear logged out); neither blocks sibling subdomains (`eTLD+1`).
`Sec-Fetch-Site` (Go 1.25 `CrossOriginProtection`)Zero server state; cleanly distinguishes `same-origin` vs `same-site` vs `cross-site`.Old browsers/proxies may strip `Sec-Fetch-*`—pair with `Origin` or token fallback.
Stateful Synchronizer Token (Spring `XorCsrfToken`)Zero extra cookies; trivially invalidated on logout; BREACH-masked.Requires server-side session storage (Redis/DB).
HMAC-Signed Double-Submit CookieStateless (works with JWT-in-cookie) while preventing subdomain cookie-planting.Must bind token to `HttpOnly` session ID via server HMAC key.
