API Gateway & Layer 7
Protocols: REST, RPC, WebSockets.

An API gateway terminates external Layer 7 traffic (HTTP/1.1, HTTP/2, gRPC, WebSockets) at the edge, centralizing TLS termination, rate limiting, auth verification, and protocol translation before routing to internal services.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Centralize cross-cutting edge concerns in a single L7 proxy, but keep business logic out of it so the gateway never becomes a monolithic bottleneck.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Without an L7 gateway, every microservice re-implements JWT validation, CORS, TLS 1.3 termination, and token-bucket rate limiting—often inconsistently. A dedicated proxy like Envoy or Kong handles 50k+ RPS per node at sub-millisecond p99 overhead while translating external REST/JSON or WebSockets into internal HTTP/2 gRPC streams.

  • Protocol termination and multiplexing: terminate external HTTP/1.1 or HTTP/3 (QUIC) at the edge and reuse long-lived HTTP/2 connections upstream to eliminate TCP/TLS handshake overhead.
  • REST vs. RPC vs. WebSockets: REST maps resources to HTTP verbs with JSON payloads; gRPC uses HTTP/2 binary frames and Protobuf for ~5–10x smaller payloads; WebSockets upgrade an HTTP/1.1 connection via 101 Switching Protocols for full-duplex streaming.
  • gRPC-Web and JSON transcoding: gateways like Envoy transcode external REST/JSON requests into internal gRPC calls using .proto descriptors so browsers can consume gRPC backends without custom clients.
  • Connection statefulness differs sharply: stateless REST requests can be load-balanced per request, whereas WebSockets pin a persistent TCP socket to a specific gateway worker for minutes or hours.
  • Backpressure and timeouts: independent upstream connect timeouts (e.g., 1s), request timeouts (e.g., 15s), and WebSocket idle timeouts prevent slowloris or hung backends from exhausting file descriptors.

Good candidates

  • Exposing dozens of internal gRPC or REST microservices under a unified public domain with consistent auth, rate limiting, and observability.
  • Supporting heterogeneous client protocols—such as browser HTTP/1.1 REST, mobile HTTP/2, and persistent RFC 6455 WebSocket connections—on one ingress tier.
  • Enforcing per-tenant quotas, canary traffic splitting (e.g., 95/5 weighted routing), and circuit breaking before requests hit backend compute.

Think twice

  • Service-to-service east-west communication inside a trusted Kubernetes cluster where a sidecar service mesh (Istio/Cilium) or direct gRPC load balancing is cleaner.
  • Single-service monoliths or early-stage apps where a simple L4/L7 cloud load balancer (AWS ALB/NLB) already covers TLS and health checks.
  • Ultra-low-latency trading or HFT pipelines where an extra L7 proxy hop adds an unacceptable 300–800 µs serialization and buffering penalty.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA web storefront sends POST /v1/orders with a JSON body over HTTP/2, while the internal Order Service only speaks gRPC with Protobuf.

The idea

An API gateway is a reverse proxy operating at OSI Layer 7 (Application Layer). Unlike a Layer 4 load balancer that forwards raw TCP/UDP packets based only on IP and port, an L7 gateway parses HTTP headers, paths, cookies, gRPC metadata, and WebSocket upgrade handshakes. Because it understands the request envelope, it can authenticate JWTs, enforce per-route rate limits, translate REST/JSON to internal gRPC/Protobuf, and route /ws traffic to stateful socket backends—all before a single byte reaches application code.

Concrete walkthrough

Consider a client calling POST https://api.acme.io/v2/payments over HTTP/2 while a second tab opens wss://api.acme.io/ws/ticker.

  1. TLS & L7 Parse: Envoy terminates TLS 1.3 (ALPN h2 for the API call, http/1.1 for the WebSocket upgrade). It normalizes headers and sets X-Request-ID.
  2. Filter Chain: For /v2/payments, Envoy validates the Authorization: Bearer JWT signature locally against a cached JWKS, checks a token-bucket rate limiter (e.g., 500 req/min per sub), and runs grpc_json_transcoder to serialize the JSON body into a Protobuf frame.
  3. Upstream Dispatch: Envoy selects a healthy endpoint from its payments-grpc cluster over a pre-warmed HTTP/2 connection pool and forwards the HEADERS + DATA frames.
  4. WebSocket Upgrade: For /ws/ticker, Envoy sees Connection: Upgrade and Upgrade: websocket, bypasses JSON transcoding, establishes a dedicated bidirectional tunnel to ticker-ws pod :8080, and relays 101 Switching Protocols back to the browser.

One L7 gateway terminates heterogeneous external protocols, applies shared policy filters, and routes to stateless gRPC or stateful WebSocket clusters.

REST, RPC, and WebSockets under the hood

Each Layer 7 protocol optimizes for a different interaction pattern and imposes distinct demands on the gateway:

  • REST (HTTP/1.1 & HTTP/2): Resource-oriented, text-based (JSON), cacheable via ETag/Cache-Control. Easy to inspect and debug, but verbose headers and JSON parsing burn CPU at high RPS.
  • gRPC (HTTP/2 + Protobuf): Contract-first binary RPC supporting unary, server-streaming, client-streaming, and bidirectional streams. Requires HTTP/2 framing (DATA + trailing HEADERS for grpc-status), so L4 proxies cannot load-balance individual RPCs—only L7 gateways can.
  • WebSockets (RFC 6455): Starts as an HTTP/1.1 GET with Upgrade: websocket, then drops HTTP framing entirely in favor of lightweight 2–14 byte binary/text frames over the same TCP socket. Because the connection is stateful, rolling restarts on the gateway require graceful connection draining (GOAWAY or staggered close frames) to avoid thundering-herd reconnects.

Failure modes

  1. gRPC Connection Pinning: Placing a Layer 4 NLB in front of gRPC backends without L7 awareness pins all multiplexed streams from one client onto a single backend pod. Fix: terminate and re-originate HTTP/2 at an L7 gateway (Envoy/Linkerd).
  2. Thundering Herd on WebSocket Deploy: Restarting 20 gateway pods simultaneously drops 500k sockets, causing clients to reconnect at the exact same millisecond and overwhelm TLS handshakes. Fix: drain connections gradually over 5–10 minutes with jittered client backoff.
  3. Buffer Bloat on Large Payloads: Gateways buffering 50 MB file uploads in RAM before forwarding cause tail-latency spikes and OOMKills. Fix: stream bodies directly or route uploads via pre-signed S3/GCS URLs.
  4. Header Spoofing: Trusting client-supplied X-Forwarded-For or X-User-Id lets attackers bypass IP allowlists or impersonate users. Fix: strip internal trust headers at the edge and overwrite them only after verified auth.

Choosing your gateway topology

Small-to-midsize platforms do best with a single managed or ingress-integrated L7 gateway (Kong, Envoy Gateway, or AWS API Gateway) handling TLS, JWT verification, and routing. Once WebSocket or streaming volume exceeds ~50k concurrent connections, split stateful /ws listeners onto a dedicated autoscaling pool so memory-heavy long-lived sockets never compete with latency-sensitive REST/gRPC traffic. Keep business aggregation in a separate BFF service behind the gateway.

Practical checklist

  • Separate timeouts by route: set strict 5–15s request timeouts on REST/gRPC routes and explicit 60s idle + ping/pong timeouts on WebSocket routes.
  • Enforce HTTP/2 upstream pools: configure h2 or h2c between gateway and backends and raise max_concurrent_streams above 100 for high-RPS gRPC.
  • Cap retry budgets: allow automatic retries only on idempotent GET/HEAD requests, bounded to <=20% of active traffic, with per-try timeouts.
  • Sanitize edge headers: strip X-User-* and untrusted X-Forwarded-For hops at the outermost listener before any auth filter runs.
  • Monitor L7 saturation metrics: alert on upstream_rq_pending_overflow, downstream_cx_active vs. ulimit -n, and 502/504 ratios per route.
03 / Engineering trade-offs

Weighing architectural decisions

Unified Gateway vs. Backend-for-Frontend (BFF)

Advantage: One Envoy/Kong fleet keeps TLS, WAF, and rate-limiting policies in a single declarative config.

Drawback: Aggregating 5+ downstream calls inside gateway Lua/Wasm plugins couples teams to the edge tier and slows deployments.

gRPC vs. REST/JSON at the Public Edge

Advantage: HTTP/2 multiplexing and Protobuf schemas give strict contracts, streaming, and lower bandwidth.

Drawback: Browser clients require gRPC-Web proxies, and payloads are opaque in standard curl/browser DevTools.

Centralized Rate Limiting vs. Local Token Buckets

Advantage: Redis-backed global counters enforce exact per-tenant limits across 20+ gateway pods.

Drawback: Every request incurs a 1–2 ms Redis round-trip unless local burst caching or asynchronous sync is used.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

WebSocket File Descriptor Exhaustion

Each concurrent WebSocket holds an open downstream and upstream socket; a surge of 100k reconnects after a deploy hits the OS `nofile` limit or ephemeral port ceiling (65,535).

What helps: Raise `fs.file-max` and `ulimit -n`, bind multiple local IP aliases for upstream NAT ports, and enforce jittered exponential backoff in client reconnect logic.

Cascading Retries (Retry Storm)

Gateway auto-retries on `502`/`504` multiply load 3x–5x against an already degraded upstream service, turning a brief GC pause into a total outage.

What helps: Cap retries to idempotent methods (`GET`/`HEAD`) with a strict retry budget (e.g., max 20% of active requests) and per-try timeouts.

Head-of-Line Blocking on HTTP/1.1 Upstream Pools

Misconfigured HTTP/1.1 upstream pools without pipelining or sufficient max connections stall queued requests behind slow responses.

What helps: Upgrade upstream pools to HTTP/2 multiplexing (`h2c` or TLS) and size `max_connections` and `max_pending_requests` with circuit breakers.

Plugin Memory Leak in Lua/Wasm Filters

Custom body-buffering plugins that read multi-megabyte payloads into memory cause OOMKills across gateway pods under high concurrency.

What helps: Stream request/response bodies without full buffering whenever possible and enforce strict `max_request_bytes` limits (e.g., 4 MB) at the listener.

05 / Practical checklist

Avoid these mistakes

  • Embedding domain orchestration and database lookups directly inside gateway plugins, turning the proxy into a single point of failure.
  • Applying the same 10-second HTTP request timeout to WebSocket or Server-Sent Events (SSE) routes, silently killing live streams.
  • Forgetting to strip or overwrite untrusted `X-Forwarded-For` and `X-Real-IP` headers at the outermost edge, enabling IP-spoofed rate-limit bypasses.
  • Sharing one global connection pool across fast health checks and slow file-upload endpoints, causing thread/connection starvation.
  • Ignoring HTTP/2 `SETTINGS_MAX_CONCURRENT_STREAMS` limits (often defaulting to 100), which bottlenecks high-throughput gRPC over a single upstream TCP connection.
