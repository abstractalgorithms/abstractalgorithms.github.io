STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is a Deadlock (Coffman's Four Conditions).

A deadlock occurs when two or more concurrent executions are permanently blocked waiting for resources held by one another. Coffman's four conditions must all hold simultaneously: (1) Mutual Exclusion, (2) Hold and Wait, (3) No Preemption, and (4) Circular Wait (T1 -> T2 -> T1).

Systems either prevent deadlocks by breaking Circular Wait via canonical lock ordering (min(idA, idB) before max(idA, idB)), or detect & recover by modeling dependencies in a directed Wait-For Graph (WFG) and aborting a victim (SQLSTATE 40P01 in Postgres, Error 1213 in MySQL).

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Deadlocks Freeze Worker Pools & How WFG Breaks Cycles.

In JVM or Go runtimes, mutex deadlocks (synchronized, ReentrantLock, sync.Mutex) are never broken automatically—threads freeze forever until process restart. In databases, undetected lock cycles exhaust HikariCP connection pools and trigger cascading 504 timeouts.

Wait-For Graph Resolution

PostgreSQL AB-BA Row-Lock Deadlock & 40P01 Victim Abort

PostgreSQL defers WFG traversal for deadlock_timeout (1s) so fast lock waits pay zero CPU, then aborts one victim with SQLSTATE 40P01.

Eliminating Bank-Transfer Deadlocks via Canonical Ordering

Sorting account IDs (first, second = sorted([from_id, to_id])) before SELECT ... FOR UPDATE eliminated 400-TPS 40P01 deadlock errors completely at zero runtime cost.

Preventing InnoDB Gap-Lock Deadlocks with READ COMMITTED

Switching a high-concurrency MySQL 8.0 checkout session from REPEATABLE READ (next-key/gap locks) to READ COMMITTED + 3-attempt jittered retry cut Error 1213 failures by 99.8%.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Deadlock Prevention vs. Detection Applies.

Prefer lock-free CAS or optimistic concurrency (WHERE version = ?) on low-contention paths; use canonical ordering whenever locking multiple entities.

ChoiceWhat it buysWhat it costs
Use: Canonical Ordering for Multi-Row / Multi-Mutex LocksEliminates Circular Wait by construction with zero victim rollbacks.Impossible if the second resource ID is only discovered after reading the first.
Use: WFG Detection + Jittered Retry (`40P01` / `1213`)Aborts true cycles deterministically without killing slow-but-healthy batch queries.Immediate un-jittered retries cause livelock; high contention can spike InnoDB WFG CPU.
Avoid: Mixing In-Memory Mutexes with DB Pool AcquisitionKeep `ReentrantLock` / `sync.Mutex` strictly in-memory, never across DB/HTTP I/O.Thread A holding mutex waiting on HikariCP + Thread B holding DB conn waiting on mutex is invisible to Postgres WFG.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to Sort Locks, Bound Timeouts & Retry Victims.

  1. Keep Transactions Short: Do validation, JSON parsing, and external HTTP calls before BEGIN.
  2. Sort Batch IDs: Acquire locks in ascending primary-key order.
  3. Pair lock_timeout + deadlock_timeout: Set lock_timeout = '2s' alongside deadlock_timeout = '1s' to cap tail stalls.
  4. Jittered Victim Retry: Catch 40P01/1213 and sleep 20ms * 2^attempt + uniform(0, 25ms) to avoid synchronized livelock.
# Canonical lock ordering + jittered 40P01 deadlock retry (Python / PostgreSQL)
import random, time

def transfer_ordered(conn, from_id: int, to_id: int, cents: int) -> None:
    first, second = sorted((from_id, to_id))
    for attempt in range(4):
        try:
            with conn.cursor() as cur:
                cur.execute("SET LOCAL lock_timeout = '2s'")
                cur.execute("SELECT id FROM accounts WHERE id IN (%s, %s) ORDER BY id FOR UPDATE", (first, second))
                cur.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s", (cents, from_id))
                cur.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (cents, to_id))
            conn.commit()
            return
        except Exception as err:
            conn.rollback()
            if getattr(err, 'sqlstate', None) != '40P01' or attempt == 3:
                raise
            time.sleep(0.02 * (2 ** attempt) + random.uniform(0, 0.025))

Alternatives: Ordering vs. WFG vs. Timeouts vs. OCC.

Compare concurrency control mechanisms by runtime overhead and failure behavior.

ChoiceWhat it buysWhat it costs
Canonical Lock OrderingZero runtime overhead; zero deadlocks by construction.Requires knowing all lock IDs up front.
Wait-For Graph (WFG) DetectionHandles arbitrary dynamic lock orders cleanly.Under 500+ threads on one hot row, `innodb_deadlock_detect` can burn 100% CPU.
Bounded Lock Timeout (`tryLock` / `lock_timeout`)Minimal CPU overhead; breaks cross-system (Redis + DB) deadlocks.Too-aggressive timeouts (`100ms`) can falsely kill legitimate slow queries.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Architecture: Victim Resolution & Jittered Retry Loop.

In high-throughput MySQL clusters where WFG traversal saturates CPU, teams sometimes set innodb_deadlock_detect = OFF and rely on innodb_lock_wait_timeout = 2s. Across Redis + DB boundaries, always enforce TTLs on distributed locks and bounded timeouts on every blocking call.
