WebSocket Real-Time
Scaling.

WebSockets (RFC 6455) upgrade an HTTP connection into a persistent, full-duplex TCP frame stream; scaling to millions of concurrent connections shifts the bottleneck from request/sec to stateful memory, ephemeral ports, pub/sub fan-out, and reconnect storms.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Terminate TLS and WebSockets on stateless L4-balanced connection gateways backed by a sharded pub/sub bus (Redis/NATS), and enforce jittered backoff + slow-consumer eviction so one dead client never OOMs a node.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Collaborative editors, live trading tickers, multiplayer games, and AI token streaming require sub-50ms bidirectional push without HTTP header overhead. Naive WebSocket architectures collapse at 50k–100k connections due to per-socket memory, single-node state coupling, or thundering-herd reconnects during deploys.

  • Each idle WebSocket consumes ~64–120 KB across kernel TCP buffers (sk_buff) and user-space runtime state; 1M concurrent sockets require ~64–120 GB RAM distributed across 16–32 gateway nodes.
  • A single backend IP:port pair hits the 65,535 ephemeral source-port ceiling when load-testing or proxying from one NAT IP; use multiple local IPs or L4 Direct Server Return (DSR).
  • WebSocket connections are stateful; scaling horizontally requires decoupling Connection Gateways from business services via a distributed pub/sub bus (NATS, Redis Pub/Sub, or Kafka).
  • TCP does not detect half-open dead clients immediately; gateways must send RFC 6455 Ping/Pong frames (opcodes 0x9/0xA) every 20–30s and close unresponsive sockets.
  • Rolling deploys of 100k+ connections trigger a thundering-herd reconnect storm (TLS handshakes + JWT auth) unless clients use randomized jittered exponential backoff.

Good candidates

  • True bidirectional, low-latency (<50ms) client-to-server and server-to-client messaging (chat, collaborative cursors, gaming, live bidding).
  • High-frequency updates (>1 msg/sec) where repeating HTTP/1.1 or HTTP/2 headers wastes bandwidth and battery.
  • Binary frame streaming (audio chunks, telemetry, protobuf deltas) over a single long-lived socket.

Think twice

  • Server-to-client-only streaming like LLM token output or live feeds—Server-Sent Events (SSE) over HTTP/2 works with standard L7 proxies and auto-reconnects natively.
  • Infrequent notifications (a few times per hour)—use Web Push, FCM/APNs, or short polling to avoid holding idle TCP sockets.
  • Request/response CRUD APIs where stateless horizontal scaling, CDN caching, and standard HTTP status codes are simpler.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA brokerage streams L2 order book deltas to 2M mobile/web clients during market open.

The idea

A WebSocket begins as a standard HTTP/1.1 GET request carrying Upgrade: websocket, Connection: Upgrade, and a base64 Sec-WebSocket-Key. When the server replies with 101 Switching Protocols, the underlying TCP/TLS socket switches from HTTP request-response semantics to lightweight RFC 6455 binary/text frames (2–14 bytes of framing overhead per message).

Because the TCP connection stays pinned to a specific server process for minutes or hours, scaling WebSockets requires separating stateful socket termination (Connection Gateways) from stateless business logic via a distributed pub/sub backbone.

Concrete walkthrough

Trace a message flow across a 1M-connection realtime platform:

  1. Handshake: Client connects via wss://rt.example.com/ws?token=... through an L4 Load Balancer to Gateway Pod gw-07.
  2. Auth & Binding: gw-07 validates the short-lived JWT, registers user_42 -> gw-07 in a fast presence store, and subscribes to room:alpha on the NATS/Redis pub/sub bus.
  3. Upstream Publish: Client sends a 120-byte WebSocket frame; gw-07 forwards it via gRPC to the stateless Chat/State Service, which persists the event with monotonic seq_id=8841.
  4. Fan-Out: The service publishes {room: "alpha", seq: 8841, payload} to the pub/sub bus. Only gateways with active room:alpha subscribers (gw-07, gw-12) receive the message and write the framed bytes to their local epoll socket rings.
  5. Heartbeat & Backpressure: Every 25s, gw-07 sends a 0x9 Ping frame; if a client's outbound ring exceeds 512 KB, gw-07 evicts the socket cleanly.

Gateways hold only TCP file descriptors and room subscription maps; all durable state and fan-out live behind the pub/sub bus.

Kernel tuning, memory math, and port limits

Scaling beyond 50,000 connections per Linux host requires tuning both OS limits and memory budgets:

  • Memory Budget: With net.ipv4.tcp_rmem and tcp_wmem tuned down (e.g., 4096 16384 65536), kernel socket structures take ~20–32 KB per idle connection, plus ~30–60 KB in user-space (TLS session state + read/write buffers). That puts 1M connections at ~64–100 GB RAM.
  • File Descriptors: Raise fs.file-max, fs.nr_open, and systemd LimitNOFILE=1048576.
  • Ephemeral Port Exhaustion: An outbound proxy connecting to a single backend (dst_ip, dst_port) is capped at ~28k–64k connections (ip_local_port_range). Bypass this by assigning multiple local source IPs on the proxy or terminating directly on L4-balanced gateway pods.

Failure modes

  • TCP Head-of-Line (HoL) Blocking: Because RFC 6455 runs over a single TCP stream, one lost packet stalls all multiplexed channels on that socket until retransmitted.
  • Unbounded Reconnect Loops: Clients retrying on 1006 Abnormal Closure without exponential backoff + jitter create self-inflicted DDoS outages whenever a regional AZ flaps.
  • Zombie Connections After Network Switch: Mobile devices switching from Wi-Fi to 5G leave dead sockets open on the server until the next Ping timeout (25–50s), requiring seq_id replay on reconnect.

Graceful draining and gapless replay

Zero-downtime deploys on stateful WebSocket fleets rely on rate-limited draining and sequence replay:

  1. Remove the draining gateway pod from the load balancer target group so new handshakes stop.
  2. Drip-close existing sockets at a capped rate (e.g., 1,000 sockets/sec) by sending WebSocket Close frame 1001 Going Away, spreading the reconnect wave across 50 seconds instead of 1 millisecond.
  3. When clients reconnect to a new pod, they pass ?since_seq=8841; the gateway replays missed events from a short-lived Redis Stream / NATS JetStream ring buffer before resuming live pub/sub frames.

Practical checklist

  • Tune LimitNOFILE, somaxconn, and tcp_rmem/tcp_wmem on gateway hosts for 50k–100k sockets/node.
  • Enforce 25s Ping/Pong heartbeats and bounded per-client outbound queues (drop slow consumers cleanly).
  • Implement jittered exponential backoff (min(30s, 1s * 2^n) + rand(0, 2s)) in all client SDKs.
  • Drip-drain pods during rolling deploys (1001 Going Away) and support since_seq replay on reconnect.
  • Monitor active connections, handshake rate/sec, outbound buffer drops, and pub/sub fan-out lag.
03 / Engineering trade-offs

Weighing architectural decisions

L4 Load Balancer (NLB) vs. L7 Proxy (ALB/Envoy)

Advantage: L4 NLB passes raw TCP with minimal memory overhead and supports millions of long-lived connections effortlessly.

Drawback: Cannot inspect HTTP paths/headers for routing or terminate TLS centrally, pushing TLS and auth into the gateway tier.

Redis Pub/Sub vs. Kafka/NATS JetStream

Advantage: Redis Pub/Sub and core NATS deliver sub-millisecond fire-and-forget fan-out with zero disk overhead.

Drawback: Ephemeral delivery means messages sent during a 2-second client disconnect are lost unless paired with a replay log (Redis Streams/JetStream) keyed by sequence ID.

Per-Socket Read/Write Buffers vs. Epoll/Kqueue Event Loop

Advantage: Event-driven async I/O (Netty, uWebSockets, Go netpoll) handles 50k–200k sockets per node without thread-per-connection stack bloat.

Drawback: Requires strict non-blocking handlers and bounded per-client outbound queues to avoid stalling the shared event loop.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Reconnect Thundering Herd

Deploying or restarting a gateway drops 50k connections simultaneously; every client immediately retries TLS + HTTP 101 + DB auth, overwhelming CPUs and auth stores.

What helps: Drain gateways gradually (e.g., 5% of sockets/sec with Close frame 1001) and enforce client-side jittered backoff: min(30s, 1s * 2^attempt) + rand(0, 2s).

Slow-Consumer Memory Exhaustion (OOM)

A mobile client on a stalled 3G link stops ACK-ing TCP packets while subscribed to a high-rate channel; the server's outbound send buffer grows until the gateway OOM-kills all 50k healthy clients.

What helps: Set strict per-connection outbound queue limits (e.g., 256 messages or 512 KB) and immediately close (`1008`/`1011`) or coalesce deltas for slow consumers.

Hot-Room Pub/Sub Fan-Out Saturation

A single celebrity livestream or global broadcast channel sends 1 msg/sec to 500k subscribers across 20 gateways, saturating Redis Pub/Sub single-threaded output buffers.

What helps: Shard hot channels across multiple pub/sub partitions or aggregate updates at the gateway so each gateway subscribes once per room rather than once per user.

Silent Proxy Idle Timeout Drop

Corporate NATs or cloud ALBs silently drop idle TCP flows after 60s without sending a FIN/RST, leaving client and server believing the socket is alive.

What helps: Send application/protocol Ping frames every 25s (well under the 60s NAT/ALB idle timeout) and terminate sockets that miss 2 consecutive Pongs.

05 / Practical checklist

Avoid these mistakes

  • Storing room membership or session state in local gateway RAM, making horizontal scaling and rolling deploys impossible without dropping state.
  • Leaving Linux `ulimit -n` (max open file descriptors) at the default 1024 or 4096, causing `EMFILE` errors under load.
  • Authenticating only at the initial HTTP Upgrade without handling token expiration or revocation on connections that stay open for days.
  • Broadcasting unbatched per-keystroke/per-tick events instead of coalescing frames on a 16–50ms tick interval.
  • Neglecting sequence numbers (`seq_id`) on server-pushed events, forcing clients to refetch full state on every brief network blip.
