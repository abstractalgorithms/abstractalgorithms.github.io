THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Instrument every service boundary with Prometheus/OTel histograms for Latency (p50/p95/p99, splitting 2xx from 5xx), Traffic (RPS), Errors (explicit + policy), and Saturation (the tightest resource bottleneck)—and alert on SLO error-budget burn rates rather than raw CPU spikes.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Dashboards crammed with 80 infrastructure graphs hide the few symptoms users actually feel. The Four Golden Signals (from Google's SRE handbook) give on-call engineers an immediate triage framework: if you can only measure four things on a service, measure these four.

  • Latency: Track request duration using histograms (e.g., http_server_request_duration_seconds) and report p50, p95, and p99—never averages, which mask 10-second tail stalls. Always separate fast-failing 5xx error latency from successful 2xx latency.
  • Traffic: Measure demand in domain-appropriate units—requests per second (RPS) for APIs, messages/sec for Kafka consumers, or active concurrent sessions for WebSockets.
  • Errors: Capture explicit failures (5xx, uncaught exceptions), implicit failures (200 OK with an empty or stale payload), and policy failures (rate-limit 429 or SLA violations > 1,000ms).
  • Saturation: Measure how full your most constrained resource is before it hits 100%—thread pool utilization, DB connection pool wait queue, JVM heap after GC, or CPU CFS throttling.
  • Pair the Golden Signals with USE (Utilization, Saturation, Errors) for hardware/infrastructure and RED (Rate, Errors, Duration) for request-driven microservices.

Good candidates

  • Designing baseline SLIs, SLOs, and executive health dashboards for any HTTP, gRPC, or streaming microservice.
  • Triaging live incidents to isolate whether degradation stems from downstream latency, traffic surges, code errors, or resource exhaustion.
  • Building multi-window, multi-burn-rate SLO alerts that page humans only when user-facing error budgets are genuinely threatened.

Think twice

  • Debugging a single user's failed request or pinpointing which line of code threw an exception—use distributed traces and structured logs for root cause.
  • Monitoring offline batch/ETL jobs where throughput, queue age, and completion freshness matter more than interactive request latency.
  • Replacing business KPIs (checkout conversion, payment authorization rate), which complement technical signals.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA checkout API's blended p99 latency dropped from 240ms to 90ms during an outage, confusing on-call engineers because a broken Redis connection was failing fast in 2ms with 500 errors.

The idea

Coined in Google's Site Reliability Engineering book, the Four Golden Signals define the essential telemetry needed to understand user experience and system headroom: Latency, Traffic, Errors, and Saturation.

Instead of building dashboards around arbitrary internal counters, Golden Signals organize monitoring around external symptoms (Latency, Traffic, Errors) and leading capacity indicators (Saturation). When Latency or Errors degrade, Traffic and Saturation immediately tell you why—whether a sudden 3x traffic spike pushed the database pool to 100% saturation, or a bad deploy introduced 500 errors at flat traffic.

Concrete walkthrough

Here is how a payment API instrumented with OpenTelemetry and Prometheus exposes and correlates all four signals during a flash sale:

  1. Traffic: sum(rate(http_server_request_duration_seconds_count{service="payments"}[1m])) jumps from 1,200 RPS to 4,800 RPS.
  2. Saturation: max(hikaricp_connections_active / hikaricp_connections_max) hits 1.0 (100%), and hikaricp_connections_pending climbs from 0 to 140 queued threads.
  3. Latency: histogram_quantile(0.99, sum by (le) (rate(http_server_request_duration_seconds_bucket{status_class="2xx"}[2m]))) degrades from 45ms to 1,400ms as threads wait for DB connections.
  4. Errors: Requests exceeding the 2,000ms gateway timeout fail with 504; sum(rate(http_server_request_duration_seconds_count{status_class="5xx"}[1m])) / sum(rate(...[1m])) crosses 2.5%, triggering a fast-burn SLO page with a linked Grafana exemplar trace_id pointing straight to hikaricp.acquire.

Golden Signal histograms feed multi-window SLO burn-rate alerts, while trace exemplars bridge aggregate metrics to individual failing requests.

Mapping Golden Signals to RED and USE

Two popular mnemonics operationalize the Four Golden Signals depending on the layer:

  • RED Method (Request-driven services): Rate (Traffic), Errors, Duration (Latency). Ideal for microservices, API gateways, and serverless functions. It omits Saturation because container orchestrators often surface saturation separately.
  • USE Method (Infrastructure resources): Utilization (% busy), Saturation (queue depth/throttling), Errors (hardware/dropped packets). Ideal for CPUs, NVMe disks, network interfaces, Kubernetes nodes, and DB connection pools.

Together, RED + Saturation gives you the complete Four Golden Signals.

Failure modes

1. Low-Traffic Alert Flapping: At 2 AM when traffic drops to 0.5 RPS, two transient network blips yield a 10% error rate for 2 minutes. Without minimum-sample gating or multi-window burn rates (1h + 5m), on-call gets woken up for a non-incident.

2. Healthcheck Pollution: Load balancer /healthz probes (every 2s from 20 nodes) inflate Traffic and artificially lower p99 Latency if not excluded via route!="/healthz".

3. Metric Scrape Gaps: If a service's /metrics endpoint blocks on a slow lock or exceeds Prometheus scrape_timeout (default 10s), all four signals go blank right when the service is most saturated.

From Golden Signals to SLO burn-rate alerting

Raw threshold alerts (p99 > 500ms) cause pager fatigue. Instead, convert Latency and Errors into SLIs (e.g., 99.9% of requests < 300ms and non-5xx over 30 days = 43.2m monthly error budget) and alert using Google SRE's multi-window burn-rate pattern:

  • Page (Urgent): 14.4x burn rate over both 1h AND 5m windows (burns 2% of monthly budget in 1 hour).
  • Page (High): 6x burn rate over both 6h AND 30m windows (burns 5% of monthly budget in 6 hours).
  • Ticket (Low): 1x–3x burn rate over 3d / 6h—investigate during business hours.

Practical checklist

  • Instrument every service with OTel/Prometheus histograms for Latency, splitting 2xx and 5xx.
  • Exclude /healthz and /metrics from Traffic, Latency, and Error SLIs.
  • Bound all metric labels (service, route_template, status_class); ban user_id or raw URLs.
  • Monitor Saturation on the tightest bottleneck (DB pool pending, Kafka lag, CPU throttling) using max().
  • Enable Prometheus exemplars on latency/error histograms to link directly to distributed traces.
  • Replace static threshold pages with multi-window SLO burn-rate alerts.
03 / Engineering trade-offs

Weighing architectural decisions

Native Histograms vs. Fixed Bucket Histograms

Advantage: Fixed Prometheus buckets (`le="0.1", "0.25", "0.5", "1.0"`) are universally supported, while OTel exponential/native histograms preserve accurate p99 across shifting scales without manual bucket tuning.

Drawback: Over-specified fixed buckets (`20+` buckets x high-cardinality labels) multiply time-series cardinality by 20x.

Symptom-Based SLO Alerts vs. Cause-Based Resource Alerts

Advantage: Alerting on Golden Signal SLO burn rate (Latency + Errors) cuts false-positive pages by 70%+ because high CPU without latency/error impact doesn't wake engineers.

Drawback: Rapidly growing saturation (e.g., disk filling at 92%) still needs a proactive warning ticket before it causes an abrupt 100% error cliff.

Client-Side vs. Server-Side Signal Collection

Advantage: Server-side metrics are cheap and always available, while client/synthetic RUM metrics capture DNS, TLS, and CDN latency invisible to origin pods.

Drawback: Client-side telemetry is noisy across user networks and cannot observe internal microservice saturation.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Averaging Latency Hides Tail Outages

Reporting `avg(duration)` shows 45ms even when 2% of requests (all mobile checkouts) time out at 10,000ms.

What helps: Export HDR/Prometheus histograms and compute `histogram_quantile(0.95, ...)` and `0.99` over `rate(...[5m])`.

Silent 200 OK Implicit Errors

A degraded recommendation engine returns `HTTP 200` with an empty JSON array `[]`; `5xx` error rate stays at `0.0%` while conversion plummets.

What helps: Emit explicit domain error/fallback counters (`recommendation_fallback_total{reason="timeout"}`) and include them in the service's Error SLI.

High-Cardinality Label Explosion

Adding `user_id`, `request_id`, or unnormalized URL paths (`/users/12345`) to Golden Signal metrics crashes Prometheus/Mimir.

What helps: Restrict metric labels to bounded dimensions (`service`, `route_template`, `method`, `status_class`); keep `user_id` and `trace_id` in traces/logs or exemplars.

Averaging Across Multi-Pod Saturation

Alerting on cluster-wide average CPU (40%) misses one hot shard or single-threaded Node.js/Python worker pinned at 100% CPU.

What helps: Aggregate saturation using `max()` or `p99()` across pods (`max(container_cpu_cfs_throttled_periods_total)`) rather than cluster `avg()`.

05 / Practical checklist

Avoid these mistakes

  • Computing client-side quantiles (`Summary` metrics) on individual pods and then averaging them across pods in Grafana—quantiles cannot be averaged mathematically.
  • Grouping `4xx` client typos (`404`, `400`) into server error alerts, causing noisy pages whenever a bot scrapes invalid URLs.
  • Using CPU utilization as the sole Saturation metric while ignoring memory pressure, disk IOPS, Kafka consumer lag, and thread/connection pool queues.
  • Setting static thresholds (`latency > 200ms for 1m`) instead of multi-window SLO burn-rate alerts (`14.4x` burn over 5m/1h).
  • Missing Prometheus **exemplars** on latency histograms, forcing engineers to hunt manually for a `trace_id` during a p99 spike.
