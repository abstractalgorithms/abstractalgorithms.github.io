THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Store config declaratively in Git-tracked ConfigMaps, but inject secrets exclusively at runtime via KMS-backed secret managers and short-lived dynamic leases.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Treating database passwords or signing keys like ordinary environment config leads to .env files committed to Git, secrets leaked in CI logs or crash dumps, and 365-day static credentials that are impossible to rotate without coordinated downtime. Separating config from secrets lets teams iterate on timeouts and feature flags via GitOps pull requests while isolating credentials behind IAM, envelope encryption, and audit trails.

  • Classification boundary: Config varies by environment and is safe to log or commit to Git (LOG_LEVEL, DB_HOST, POOL_SIZE); Secrets grant identity, decryption, or billing authority (DB_PASSWORD, JWT_PRIVATE_KEY, STRIPE_SK).
  • Never store plaintext or base64-encoded Kubernetes Secret manifests in Git—base64 is encoding, not encryption; use External Secrets Operator (ESO) or SOPS + KMS/age.
  • Prefer dynamic short-lived credentials (HashiCorp Vault DB secrets engine, AWS IAM Roles for Service Accounts / IRSA, SPIFFE X.509 SVIDs) over static API keys.
  • Mount secrets via memory-backed tmpfs files (/var/run/secrets/...) rather than OS environment variables when possible, preventing leaks via /proc//environ or child-process dumps.
  • Enable etcd encryption at rest with a cloud KMS provider so Kubernetes Secret objects are never written in plaintext to disk snapshots.

Good candidates

  • Any production application running in Kubernetes, ECS, or serverless environments that connects to databases, payment gateways, or third-party APIs.
  • GitOps workflows (ArgoCD, Flux) where manifests are stored in Git repositories accessible to all developers.
  • Multi-tenant or regulated systems (PCI-DSS, SOC 2, HIPAA) requiring cryptographic audit logs and 24-hour credential rotation.

Think twice

  • Ephemeral local unit-test mocks using synthetic throwaway values (test-secret-123) that have zero access to real infrastructure.
  • Publicly distributable client-side bundle identifiers (e.g., public OAuth client_id or Google Analytics measurement ID) that are not actually secret.
  • Over-engineering dynamic Vault leases for truly static public endpoints like PAYMENT_API_BASE_URL or LOG_LEVEL.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA 40-microservice platform shared a single static postgres_prod password across .env files and Kubernetes Secrets, making rotation risky and violating SOC 2.

The idea

The Twelve-Factor App popularized storing configuration in the environment, but modern production security requires splitting that environment into two distinct planes: Configuration (non-sensitive behavior tuning like timeouts, pool sizes, and feature flags) and Secrets (cryptographic material, passwords, and API tokens that grant access or authority). Configuration belongs in version-controlled declarative files for reproducibility and diffability; secrets belong in dedicated KMS-backed vaults with strict IAM scoping, memory-only injection, audit logging, and automated rotation.

Concrete walkthrough

Consider deploying an invoice-worker microservice to Amazon EKS that reads from PostgreSQL and calls Stripe:

  1. Config Plane (Git): configmap.yaml holds DB_HOST=orders-rw.internal, HIKARI_MAX_POOL=12, STRIPE_TIMEOUT_MS=2000, and ENABLE_PDF_V2=true. Any engineer can review and merge changes via GitHub PR.
  2. Identity Plane (Zero Static Keys): Instead of storing AWS access keys, the pod's Kubernetes ServiceAccount uses IRSA (IAM Roles for Service Accounts) to exchange a short-lived OIDC JWT for temporary AWS STS credentials.
  3. Secrets Plane (Runtime Injection): External Secrets Operator (or Secrets Store CSI Driver) authenticates with AWS Secrets Manager / HashiCorp Vault, pulls the Stripe key and requests a dynamic 1-hour Postgres role, and mounts them onto a memory-backed tmpfs volume at /var/run/secrets/app/ (0400 permissions).
  4. Application Read: On startup (and on SIGHUP/file-watch), the app reads /var/run/secrets/app/stripe_key without ever placing the string into os.environ.

Separation of Git-tracked configuration from runtime OIDC-authenticated secret injection using RAM-backed tmpfs mounts.

Static vs. dynamic secrets and workload identity

The gold standard for secrets management is eliminating static long-lived secrets wherever possible:

  • Workload Identity Federation (IRSA, GCP Workload Identity, SPIFFE/SPIRE): Services authenticate to cloud APIs and each other using short-lived cryptographic tokens (OIDC JWTs or X.509 SVIDs rotated every 15–60 minutes) bound to the pod's namespace and service account.
  • Dynamic Database Secrets: Instead of a shared static password, Vault creates a unique database user per pod (CREATE ROLE ... VALID UNTIL ...) and revokes it automatically when the lease expires.
  • Envelope Encryption: When secrets must be stored (e.g., third-party webhook HMAC keys), a Data Encryption Key (DEK) encrypts the secret, and a cloud KMS Key Encryption Key (KEK) wraps the DEK—allowing key rotation and instant revocation via KMS policy.

Failure modes

  • Stale credential after rotation: Applications that read a secret file once at main() startup fail with 401 Unauthorized or 28P01 when a secret rotates in-place. Implement file-watch reload or dual-key grace periods.
  • CI/CD pipeline exfiltration: Printing env in GitHub Actions or passing secrets on CLI flags (curl -H "Authorization: Bearer $TOKEN") exposes credentials in build logs and ps aux output.
  • Over-broad IAM policies: Granting a pod secretsmanager:GetSecretValue on * instead of arn:...:secret:prod/orders/* lets a single compromised dependency read every service's keys.
  • Docker layer caching leaks: Copying .env or passing --build-arg NPM_TOKEN during docker build leaves secrets recoverable via docker history even if deleted in a later RUN step.

Audit, scanning, and drift prevention

Enforcement must be automated across both the build pipeline and runtime:

  • Pre-commit & CI Scanning: Run gitleaks or trufflehog on every PR and push to block high-entropy strings, AWS key prefixes (AKIA...), and private key headers (-----BEGIN ... PRIVATE KEY-----).
  • Admission Control: Use Kyverno or OPA Gatekeeper to reject Kubernetes pods that define literal env[].value matching secret patterns or mount host paths.
  • CloudTrail / Vault Audit Logs: Alert when a secret is accessed by an unexpected IAM role, from outside the production VPC, or when a revoked lease is attempted.

Practical checklist

  • Classify every runtime parameter: move non-sensitive hosts, timeouts, and flags to ConfigMap/Git; move all credentials to a secret manager.
  • Enable etcd envelope encryption at rest with cloud KMS on all Kubernetes clusters.
  • Replace static cloud IAM keys with OIDC Workload Identity (IRSA / GKE WI / SPIFFE).
  • Mount secrets via tmpfs (Secrets Store CSI or Vault Agent) instead of environment variables where supported.
  • Enable gitleaks in pre-commit hooks and CI, plus automated secret-scanning alerts on GitHub/GitLab.
  • Test secret rotation end-to-end in staging with zero pod restarts or dropped connections.
03 / Engineering trade-offs

Weighing architectural decisions

Static Encrypted Git vs. Runtime Secret Manager

Advantage: SOPS-encrypted files in Git keep config and secrets versioned atomically in the same pull request.

Drawback: Runtime stores (Vault, AWS Secrets Manager) support instant revocation, dynamic leases, and access auditing without Git commits.

Env Vars vs. tmpfs File Mounts

Advantage: Environment variables are universally supported by 12-Factor frameworks with zero file-watching code.

Drawback: File mounts on `tmpfs` support hot rotation without pod restarts and cannot be accidentally dumped by debug endpoints printing `os.environ`.

Short-Lived Dynamic Leases

Advantage: 1-hour dynamic DB credentials drastically shrink the blast radius of any credential leak.

Drawback: Applications must handle lease renewal or connection-pool refresh before TTL expiration to avoid sudden auth failures.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Crash-Dump & Debug Env Leakage

Frameworks or error trackers (Sentry, crash reporters, `/actuator/env`) serialize `process.env` or `System.getenv()`, exposing API keys in log aggregators.

What helps: Mount secrets as `tmpfs` files, scrub sensitive keys in logger/APM redaction filters, and disable `/actuator/env` in production.

Rotation Auth Storm

Rotating a shared database password or API key in Secrets Manager without dual-key grace periods immediately breaks all running pods until restarted.

What helps: Use dual-active key rotation (primary + secondary key), dynamic per-pod credentials, or hot-reloadable file watchers.

Secret Store Cold-Start Outage

If Vault or Secrets Manager is unreachable during an autoscaling spike, new pods fail to start because they cannot fetch boot-time credentials.

What helps: Run HA multi-AZ secret stores, use local Vault Agent caching, and decouple non-critical secrets from liveness/startup probes.

Base64 GitOps Illusion

Engineers commit standard Kubernetes `kind: Secret` YAML to Git assuming base64 `data:` fields are safe, permanently exposing credentials in Git history.

What helps: Enforce pre-commit and CI secret scanners (Gitleaks, TruffleHog) and block raw `kind: Secret` manifests in GitOps admission controllers.

05 / Practical checklist

Avoid these mistakes

  • Passing secrets as Docker `ARG` or `ENV` instructions inside a `Dockerfile`, baking credentials permanently into immutable OCI image layers.
  • Putting non-sensitive URLs or feature flags inside Secrets Manager, hitting API rate limits and paying per-secret fees unnecessarily.
  • Leaving Kubernetes `etcd` unencrypted at rest, allowing anyone with snapshot access to read all cluster Secrets in plaintext.
  • Forgetting to purge Git history (`git filter-repo`) and rotate the exposed credential immediately after an accidental commit—deleting the line in a new commit leaves it in history.
  • Using a single wildcard IAM role for all microservices instead of least-privilege per-service secret paths.
