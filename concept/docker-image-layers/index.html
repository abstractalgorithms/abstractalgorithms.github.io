Docker Images
& Layers.

A Docker image is an immutable stack of content-addressable filesystem tarballs (layers) merged at runtime via a copy-on-write union filesystem like OverlayFS.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Order Dockerfile instructions from least-frequently changed to most-frequently changed, combine `RUN` cleanup in the same layer, and use multi-stage builds so build toolchains never ship to production.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Every RUN, COPY, and ADD instruction creates a new read-only layer identified by its SHA-256 diff digest. Poor layer hygiene bloats images from 40 MB to 1.8 GB, busts BuildKit layer caches on every commit, and slows Kubernetes pod cold-starts across nodes.

  • OverlayFS mounts read-only image layers as lowerdir, a container-specific writable layer as upperdir, and presents the unified view at merged.
  • Deleting a file from a lower layer in a subsequent RUN rm instruction only writes a whiteout file (.wh.) in the upper layer—it does not shrink the lower layer's registry size.
  • BuildKit evaluates cache invalidation top-down: once a COPY . . layer changes, every downstream RUN instruction misses cache and re-executes.
  • Multi-stage builds (FROM golang:1.23 AS builder -> FROM gcr.io/distroless/static:nonroot) cut image surface area and CVE count by omitting shells, package managers, and headers.
  • OCI Image Manifests (application/vnd.oci.image.manifest.v1+json) separate compressed layer blobs (diff_ids vs compressed digests) so registries skip transferring layers already cached on the host.

Good candidates

  • Packaging microservices with predictable dependencies so CI/CD builds reuse cached base and dependency layers across commits.
  • Distributing multi-architecture (linux/amd64, linux/arm64) OCI artifacts where registry pulls deduplicate shared base layers by digest.
  • Isolating build-time compilers (GCC, Maven, Node devDependencies) in a builder stage before copying only compiled binaries into a minimal runtime stage.

Think twice

  • Storing mutable application state, database files, or user uploads inside the container writable upperdir instead of external volumes.
  • Baking environment-specific secrets (.env, TLS private keys, AWS credentials) into ENV or COPY layers where docker history and tar extraction expose them permanently.
  • Running monolithic legacy workloads that require full systemd init trees and mutable host kernel modules rather than a single-process container.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA FastAPI service initially used FROM python:3.12 (1.02 GB) with COPY . . before pip install -r requirements.txt, causing 4-minute CI rebuilds on every single-line code edit.

The idea

A Docker (OCI) image is not a monolithic VM disk—it is a JSON manifest pointing to an ordered stack of immutable, gzip/zstd-compressed filesystem tarballs called layers. Each layer captures only the filesystem delta (added, modified, or whiteout-deleted files) introduced by a single RUN, COPY, or ADD instruction.

At container startup, the container runtime (containerd + runc) does not copy those gigabytes of layers. Instead, it instructs the Linux kernel's OverlayFS driver to stack the read-only layers as lowerdir, attach a fresh, empty read-write directory as upperdir, and expose the combined filesystem at merged. Because lower layers are strictly read-only and addressed by their SHA-256 content digest, ten containers on the same host share one physical copy of the OS and runtime layers in page cache.

Concrete walkthrough

Consider building a Go HTTP service with BuildKit (DOCKER_BUILDKIT=1):

  1. FROM golang:1.23-alpine@sha256:... AS builder pulls 3 base layers (~85 MB compressed) once and caches them locally.
  2. WORKDIR /src and COPY go.mod go.sum ./ create tiny metadata/file layers. If go.mod hasn't changed since yesterday, BuildKit hits cache.
  3. RUN --mount=type=cache,target=/go/pkg/mod go mod download populates Go's module cache on a persistent BuildKit cache volume without baking downloaded module tarballs into the image layer.
  4. COPY . . + RUN CGO_ENABLED=0 go build -o /out/server ./cmd/server compiles a static ELF binary.
  5. FROM gcr.io/distroless/static-debian12:nonroot starts stage 2, and COPY --from=builder /out/server /server copies only the 14 MB binary.

When docker push runs, the registry checks each layer's SHA-256 digest via HEAD /v2//blobs/, skips uploading the unchanged distroless base layers, and uploads only the new 14 MB binary layer.

End-to-end lifecycle of OCI image layers from BuildKit compilation and registry digest deduplication to OverlayFS copy-on-write runtime mounting.

BuildKit cache mechanics & multi-stage patterns

Modern Docker builds rely on BuildKit, which builds a directed acyclic graph (DAG) of instructions rather than executing a linear script. Independent stages in a multi-stage Dockerfile execute in parallel, and unused stages are skipped entirely unless targeted.

Two BuildKit mount flags eliminate layer bloat without sacrificing speed:

  • --mount=type=cache,target=/root/.cache/pip keeps package-manager caches across builds on the builder host without writing a single byte into the final image layer.
  • --mount=type=secret,id=github_token exposes credentials at /run/secrets/github_token only during that RUN step, leaving zero trace in docker history or layer tarballs.

Failure modes

  1. Whiteout bloat (rm in a later layer): Running rm -rf /tmp/sdk in a separate RUN creates a .wh.sdk marker in the upper layer while the lower layer still ships the full SDK over the network.
  2. Copy-up stalls: Writing to a 500 MB pre-seeded database file inside lowerdir forces OverlayFS to synchronously copy all 500 MB into upperdir before the first byte mutates.
  3. Context explosion: Omitting .dockerignore causes docker build to tar node_modules or .git on every run, adding 30–60 seconds before instruction 1 even starts.
  4. Layer limit & inode exhaustion: Exceeding ~125 layers degrades OverlayFS lookup latency, while unpacked node_modules trees with 100,000+ tiny files can exhaust host ext4/xfs inodes.

Inspecting and auditing layers

Treat image size and layer contents as CI gate metrics:

  • Run dive locally or in CI (CI=true dive ) to inspect exact wasted bytes, duplicate files across layers, and layer efficiency percentages (aim for >95%).
  • Use docker buildx imagetools inspect to verify multi-arch manifest lists and confirm compressed layer sizes.
  • Scan final runtime images—not builder images—with trivy image --severity HIGH,CRITICAL so CVEs in build-only compilers don't create alert fatigue.

Practical checklist

  • Add a strict .dockerignore excluding .git, .env*, node_modules, target/, __pycache__/, and test fixtures.
  • Pin base images with explicit version tags and SHA-256 digests (@sha256:...).
  • Copy dependency manifests (package-lock.json, go.sum, requirements.txt) before application source code.
  • Use RUN --mount=type=cache for package managers and RUN --mount=type=secret for private registry tokens.
  • Separate compile/build toolchains into an AS builder stage and ship only runtime artifacts into slim or distroless.
  • Run containers as an explicit non-root UID (USER 65532:65532) with COPY --chown.
03 / Engineering trade-offs

Weighing architectural decisions

Base image minimalism (Distroless / Alpine vs Debian Slim)

Advantage: Distroless (`~20 MB`) and Alpine (`~7 MB`) minimize registry transfer time and eliminate shell-based RCE primitives.

Drawback: Alpine's `musl` libc can trigger DNS resolution quirks or wheel compilation failures for Python/C++ binaries, while Distroless lacks `sh`/`curl` for ad-hoc `kubectl exec` debugging (requiring ephemeral debug containers).

Instruction consolidation vs layer granularity

Advantage: Chaining related commands into fewer `RUN` layers reduces overlayfs metadata overhead and ensures temporary files deleted in the same step never persist.

Drawback: Over-consolidating unrelated steps into one giant `RUN` ruins BuildKit cache reuse when only one sub-step changes.

Squashing layers (`--squash` / single-layer tar)

Advantage: Collapses whiteouts and intermediate history into a single compact tarball for distribution.

Drawback: Destroys shared base-layer deduplication across services, forcing nodes to re-download the entire base OS on every minor app release.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Cache busting from early `COPY . .`

Copying the entire repository before installing dependencies invalidates package-manager layers whenever `README.md` or application source files change.

What helps: Copy only lockfiles (`package-lock.json`, `poetry.lock`, `go.sum`) first, install dependencies, and `COPY` application source last; pair with `.dockerignore` excluding `.git`, `node_modules`, and `tests/`.

Phantom size from cross-layer deletion

Downloading a 500 MB SDK tarball in `RUN curl ...` and removing it in a separate `RUN rm` leaves the 500 MB blob permanently inside the image manifest.

What helps: Chain download, extraction, and deletion inside a single `RUN` command (`&& rm -rf ...`) or use BuildKit `RUN --mount=type=bind` / multi-stage `COPY --from`.

OverlayFS copy-up latency on heavy writes

Modifying a large pre-existing file (e.g., an SQLite DB or 200 MB log) in `lowerdir` forces OverlayFS to copy the entire file up to `upperdir` on first write.

What helps: Mount external volumes (`-v` or Kubernetes `emptyDir`/`PVC`) for any directory receiving runtime writes so I/O bypasses OverlayFS copy-up.

Floating `:latest` tag drift

Pinning `FROM node:20` or `:latest` causes builds on Tuesday to pull a different OS/OpenSSL patch layer than builds on Monday, breaking reproducibility.

What helps: Pin base images by immutable SHA-256 digest (`FROM node:20.18.0-slim@sha256:...`) and automate bumps via Renovate or Dependabot.

05 / Practical checklist

Avoid these mistakes

  • Forgetting `.dockerignore`, which sends `.git/` (hundreds of MB) and local `.env` files into the BuildKit build context.
  • Running `apt-get update` in its own `RUN` layer, causing stale package index caches to fail `apt-get install` months later.
  • Assuming `USER nonroot` at the end of a Dockerfile changes ownership of files already `COPY`'d as `root` without `--chown=nonroot:nonroot`.
  • Using `ADD` with remote URLs instead of `curl` + checksum verification, or unintentionally auto-extracting tarballs.
  • Leaving `pip`, `npm`, or `apt` caches inside the final layer instead of mounting `--mount=type=cache` during build.
