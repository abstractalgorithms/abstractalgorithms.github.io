Architecture.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Isolate your core business logic from Spring, SQLAlchemy, or Kafka by defining repository and gateway interfaces inside the domain/application ring and implementing them in the outermost infrastructure ring.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

In traditional N-tier architectures, business services directly import ORM entities and database clients, coupling domain rules to schema quirks and framework lifecycles. When you upgrade Hibernate, swap PostgreSQL for DynamoDB, or test complex pricing rules, you end up booting a 6-second application context or mocking SQL cursors. Onion Architecture inverts those dependencies so pure domain logic compiles and runs in under 15 milliseconds with zero I/O.

  • The Dependency Rule is absolute: source code dependencies may only point inward toward the Domain Model; inner rings never import classes from outer rings.
  • The Domain Model ring holds pure entities, value objects, and domain events with zero framework annotations (no @Entity, @Column, or @Autowired).
  • The Domain Services and Application Services rings orchestrate use cases and define output ports (interfaces like PaymentGateway or OrderRepository).
  • The Infrastructure and UI rings sit on the outside, implementing those ports with concrete adapters (JPA, jOOQ, gRPC, Kafka consumers, FastAPI routers).
  • Boundary enforcement should be automated in CI using tools like ArchUnit (Java) or import-linter (Python) so accidental outer-ring imports fail the build.

Good candidates

  • Core business domains with rich invariants, state machines, or regulatory rules (e.g., billing ledgers, underwriting, order fulfillment) that outlive web frameworks.
  • Long-lived services where swapping persistence engines, message brokers, or external vendor APIs (e.g., Stripe to Adyen) must not require rewriting business logic.
  • Teams that want fast, deterministic unit tests for 80%+ of their codebase without spinning up Docker/Testcontainers for every rule variation.

Think twice

  • Simple CRUD microservices, admin backends, or BFFs where 90% of the code is validating JSON and writing rows to a single table.
  • Short-lived prototypes, hackathons, or early-stage MVPs where mapping between domain objects, DTOs, and ORM models slows down iteration.
  • Read-heavy reporting or analytics pipelines (e.g., dbt, Spark jobs) whose primary job is executing set-based SQL transformations rather than enforcing entity invariants.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA fintech ledger service originally coupled Hibernate @Entity classes directly to settlement rules. Moving to multi-region CockroachDB required changing transaction retry semantics and primary key generation.

The idea

Coined by Jeffrey Palermo in 2008, Onion Architecture solves a recurring rot in layered N-tier systems: the database sits at the bottom of the dependency graph, so every layer above it—business logic, services, and UI—transitively couples to SQL schemas and ORM frameworks.

Onion Architecture flips the graph using the Dependency Inversion Principle (DIP). Instead of the domain depending on a PostgresOrderRepository, the inner rings define an OrderRepository interface (port), and the outer infrastructure ring provides PostgresOrderRepository (adapter). Everything compiles from the outside in, while the core remains pure language primitives and domain types.

Concrete walkthrough

Consider an e-commerce PlaceOrder use case handling inventory reservation and payment capture:

  1. UI / Web Ring (OrderController): Deserializes the HTTP POST /orders payload into a PlaceOrderCommand and invokes PlaceOrderUseCase.execute(cmd).
  2. Application Service Ring (PlaceOrderUseCase): Starts a transaction boundary, loads the Cart via the CartRepository interface, and calls Order.createFrom(cart).
  3. Domain Model Ring (Order, Money): Pure Java/Python objects verify that cart.items() is non-empty, compute totals using Money value objects, and transition status to PENDING_PAYMENT.
  4. Infrastructure Ring (JpaOrderRepository, StripePaymentAdapter): Implements the interfaces defined inside the application/domain rings, translating Order into a orders table row and calling Stripe's /v1/payment_intents API.

Runtime control flows from UI through Application Services to Infrastructure adapters, while compile-time source dependencies point strictly inward toward the Domain Model.

Anatomy of the four rings

Each ring has a strict boundary on what it may import:

  • Domain Model (Center): Entities, Value Objects, Aggregates, and Domain Events. Allowed imports: language standard library only.
  • Domain Services: Stateless business logic spanning multiple aggregates (e.g., currency conversion policies or FX spread calculations).
  • Application Services: Use-case orchestrators (PlaceOrderUseCase), transaction coordination, and output port interfaces (OrderRepository, EventPublisher).
  • Infrastructure & UI (Outer): Web controllers, CLI handlers, JPA/SQLAlchemy repositories, Kafka producers, and DI wiring (Spring @Configuration or FastAPI Depends).

Failure modes

  1. Bypassing Reads Through Heavy Aggregates: Fetching a 12-table aggregate just to render a 3-column summary table kills DB performance. Keep Onion ports for write commands and allow a direct read-only query service for dashboards.
  2. Framework Annotations Creeping Inward: Adding @Transactional, @Validated, or @Entity into the domain package defeats portability and reintroduces 5-second test boots.
  3. Leaky Exceptions: Letting PSQLException or DataIntegrityViolationException bubble uncaught through a repository port forces the Application Service to import database driver packages to handle unique-key conflicts; translate them into domain exceptions like DuplicateOrderException inside the adapter.

Enforcing boundaries with ArchUnit and Python Protocols

Conventions decay unless CI rejects violations. In Java/Kotlin, ArchUnit provides a first-class rule:

Architectures.onionArchitecture()
  .domainModels("com.acme.orders.domain.model..")
  .domainServices("com.acme.orders.domain.service..")
  .applicationServices("com.acme.orders.application..")
  .adapter("persistence", "com.acme.orders.infra.postgres..")
  .adapter("rest", "com.acme.orders.infra.web..");

In Python, define ports as typing.Protocol classes inside domain/ports.py and enforce unidirectional package imports in CI using import-linter (type = layers), ensuring domain never imports sqlalchemy, fastapi, or boto3.

Practical checklist

  • Zero framework imports in domain/: Verify with grep or ArchUnit that no ORM, HTTP, or DI annotations exist inside the domain package.
  • Separate persistence models: Map between Order (domain) and OrderJpaEntity (infrastructure) at the repository boundary.
  • Translate infrastructure errors: Convert SQL unique-constraint or HTTP 429 errors into domain-meaningful exceptions inside adapters.
  • Use CQRS for heavy reads: Let read-only reporting endpoints bypass aggregate hydration via slim query projections.
  • Automate in CI: Fail pull requests automatically on any outward dependency violation.
03 / Engineering trade-offs

Weighing architectural decisions

Boilerplate vs. Decoupling

Advantage: Domain logic stays completely portable and free of ORM lazy-loading surprises or framework magic.

Drawback: Requires explicit mappers between domain aggregates, persistence entities, and API DTOs—adding 15–25% more files per feature.

Test Speed vs. Integration Confidence

Advantage: In-memory fakes implementing repository ports run thousands of business-rule tests in milliseconds.

Drawback: Mocks and fakes can drift from real SQL constraints (unique indexes, lock behavior), so contract tests against real DBs are still mandatory.

Query Optimization

Advantage: Write-side aggregates enforce strict transactional consistency without leaking SQL into domain rules.

Drawback: Complex paginated reads or joins feel awkward through pure repository ports and often need a dedicated CQRS read-model bypass.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Anemic Domain Model

Engineers strip behavior out of domain entities into giant Application Services, leaving entities as dumb getter/setter bags while duplicating validation across use cases.

What helps: Push invariant checks and state transitions (`order.confirm()`, `wallet.debit(amount)`) directly onto domain aggregates and keep Application Services thin.

Leaky ORM Abstractions

Putting `@Entity` or `@JsonProperty` annotations on domain classes or returning Hibernate `PersistentBag` proxies from repositories ties domain behavior to an active DB session.

What helps: Maintain separate persistence models in the infrastructure package and map explicitly at the repository boundary.

Mapping Fatigue & N+1 Regressions

Blindly loading full aggregate graphs through generic `findById()` ports for simple read endpoints causes severe N+1 query storms.

What helps: Use Onion Architecture for command/write paths and allow slim, read-only query projections (CQRS) that map SQL rows straight to response DTOs.

Architectural Drift in Growing Teams

Without automated checks, urgent hotfixes introduce direct imports from `infrastructure` into `domain`, silently collapsing the onion back into a big ball of mud.

What helps: Enforce ring boundaries in CI with ArchUnit (`Architectures.onionArchitecture()`) or Python `import-linter` contracts.

05 / Practical checklist

Avoid these mistakes

  • Confusing runtime call flow with compile-time dependency direction—outer controllers call inner services, but inner services depend only on interfaces.
  • Creating a 1:1 `IRepository` interface for every database table instead of designing ports around aggregate roots.
  • Putting transaction boundaries (`@Transactional`) inside domain entities instead of wrapping use cases in the Application Service or an outer decorator.
  • Over-abstracting standard library utilities (e.g., wrapping `java.time.Clock` is useful for tests, wrapping `StringUtils` is pure noise).
  • Using MapStruct or reflection mappers blindly across boundaries, hiding missing fields until runtime.
