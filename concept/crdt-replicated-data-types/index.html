CRDTs & Conflict-Free
Replicated Data.

CRDTs (Conflict-free Replicated Data Types) are replicated data structures whose concurrent updates commute or form a mathematical join-semilattice, guaranteeing every replica converges to the exact same state without coordination or consensus.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

CRDTs eliminate consensus round-trips for local-first apps and geo-distributed active-active stores by trading coordination latency for metadata overhead (vector clocks, tombstones, or per-element IDs).

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Consensus protocols like Raft and Paxos require a quorum round-trip (50–150 ms across WANs) and stall during network partitions. Real-time collaborative editors (Figma, Notion/Linear-style local-first apps, Yjs, Automerge) and active-active distributed databases (Riak, Redis Enterprise Active-Active, Cassandra counters) need sub-millisecond local writes even offline. CRDTs mathematically guarantee Strong Eventual Consistency (SEC): any two replicas that have received the same set of updates—in any order, with any duplicates—hold identical state.

  • State-based CRDTs (CvRDTs) ship full or delta state (delta-CRDTs) and merge via a join-semilattice operator ⊔ that is associative, commutative, and idempotent (ACID-free convergence).
  • Operation-based CRDTs (CmRDTs) ship small operations, requiring reliable causal broadcast (exactly-once or idempotent causal delivery) and commutative concurrent operations.
  • Core primitives include G-Counter (per-replica monotonic map), PN-Counter (two G-Counters for inc/dec), LWW-Register (timestamp + replicaId tie-breaker), and OR-Set (Observed-Remove Set using unique add-tags).
  • Sequence CRDTs (RGA, YATA/Yjs, Fugue) assign unique fractional/tree-ordered IDs to characters so concurrent insertions at the same cursor never interleave or corrupt text.
  • CRDTs guarantee convergence, not human intention—e.g., LWW-Register silently drops one concurrent write, and concurrent add+remove in an OR-Set resolves to add-wins or remove-wins by design.

Good candidates

  • Local-first collaborative applications (rich-text editors, whiteboards, offline-capable mobile apps) where edits must apply locally at 0 ms and merge cleanly upon reconnection.
  • Multi-region active-active databases tracking distributed counters, feature flags, shopping carts, or user presence sets without cross-region locks.
  • Edge/IoT telemetry aggregation where intermittent nodes push deltas over unreliable networks.

Think twice

  • Strict global invariants such as preventing negative bank balances, enforcing unique usernames, or inventory reservation under scarcity (requires consensus or single-leader serialization).
  • Large binary blobs or relational joins that cannot be decomposed into monotonic state transitions.
  • Memory-constrained systems with high churn of deleted items where tombstone metadata cannot be garbage-collected.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

Scenario50 concurrent editors type, format, and paste offline/online in a shared browser document over WebSockets and WebRTC.

The idea

Traditional replication relies on consensus (Raft/Paxos) to agree on a single global total order of writes. CRDTs invert the problem: instead of agreeing on when operations happened, design the data structure so that order does not matter.

Formally, a state-based CRDT (CvRDT) forms a bounded join-semilattice (S, ⊔). Every local mutation moves the state monotonically upward in the partial order, and merging two replicas computes their least upper bound A ⊔ B. Because ⊔ is associative (A ⊔ B) ⊔ C = A ⊔ (B ⊔ C), commutative A ⊔ B = B ⊔ A, and idempotent A ⊔ A = A, replicas can gossip updates over lossy, out-of-order networks and still converge identically.

Concrete walkthrough

Trace an Observed-Remove Set (OR-Set) with add-wins semantics across two disconnected replicas R1 and R2:

  1. Initial state: Both hold {('milk', tag_1)}. R1 and R2 go offline.
  2. R1 removes 'milk': R1 moves tag_1 into its tombstones set -> visible set is {}.
  3. R2 concurrently removes and re-adds 'milk': R2 tombstones tag_1 and generates a fresh unique tag tag_2 -> visible set is {('milk', tag_2)}.
  4. Merge (R1 ⊔ R2):
    • adds = {('milk', tag_1), ('milk', tag_2)}
    • tombstones = {tag_1}
    • Visible elements = adds \ tombstones = {('milk', tag_2)}.

Unlike a naive set where remove('milk') would wipe out R2's concurrent re-add, tagging each addition with a unique (replicaId, seq) ensures a remove only cancels the specific additions it observed.

Strong Eventual Consistency: concurrent updates travel asynchronously and converge deterministically via the join operator.

State-based vs. operation-based vs. delta

  • CvRDT (State-based): Replicas exchange full states and call merge(). Dead simple transport (works over plain HTTP polling or UDP gossip), but bandwidth is O(state size).
  • CmRDT (Op-based): Replicas broadcast tiny operations (e.g., insert(pos, 'a')). Low bandwidth, but requires reliable causal broadcast (no dropped or out-of-order ops).
  • Delta-state CRDTs (δ-CRDT): The modern sweet spot used in Riak, Yjs, and Automerge. Each mutation produces a small delta δ that is itself a valid CvRDT fragment. Replicas ship deltas and merge them idempotently, combining small payloads with loss-tolerant transport.

Failure modes

  1. Wall-clock drift in LWW: Relying on unsynchronized client clocks lets a skewed device win every conflict forever. Fix: Use Hybrid Logical Clocks (HLC) bounded by server time.
  2. Unbounded tombstone growth: High-churn documents accumulate megabytes of deleted character metadata. Fix: Run causal-barrier compaction when all peers acknowledge a version vector, or use run-length encoding (RLE) of contiguous IDs like Yjs/Automerge.
  3. Interleaving in naive sequence CRDTs: Early sequence CRDTs (Logoot, LSEQ) could interleave two users' concurrently typed words (hweolrldo). Fix: Use modern non-interleaving algorithms like Fugue or YATA.
  4. Broken global invariants: Two replicas concurrently decrementing a PN-Counter from 1 to -1 cannot be prevented locally. Fix: Use Escrow/Bounded-Counter patterns (pre-allocating per-replica quotas) or fall back to consensus for scarce resources.

Compression & production libraries

Production CRDT engines avoid storing a JSON object per character:

  • Yjs: Uses doubly-linked blocks (Item structs) with ID run-length encoding—typing "hello" creates 1 struct of length 5 instead of 5 structs, keeping memory ~1.5x raw text.
  • Automerge 2.0: Stores columnar compressed change logs (inspired by Apache Arrow/Parquet) so a 100,000-edit document loads in ~10 ms and compresses 10x smaller than JSON.
  • Redis Enterprise CRDTs: Implements native G-Counter, PN-Counter, OR-Set, and LWW-Hash inside C modules across active-active clusters.

Practical checklist

  • Verify your domain does not require strict global invariants (e.g., uniqueness, non-negative stock).
  • Assign a unique, persistent replicaId per client instance/tab—never reuse user IDs.
  • Replace raw Date.now() with Hybrid Logical Clocks (HLC) for any LWW conflict resolution.
  • Use delta-CRDTs with run-length-encoded IDs (e.g., Yjs or Automerge) for sequences and large maps.
  • Define a tombstone compaction / snapshot strategy before high-churn workloads hit memory limits.
  • Fuzz-test merge(A, B) for associativity, commutativity, and idempotency under random network reordering.
03 / Engineering trade-offs

Weighing architectural decisions

State-Based (CvRDT) vs. Op-Based (CmRDT)

Advantage: CvRDTs tolerate dropped, duplicated, and reordered messages over plain gossip/HTTP because `merge()` is idempotent and commutative.

Drawback: Shipping full state scales poorly with object size; delta-CRDTs mitigate this by shipping only recent state diffs.

Metadata & Tombstone Growth

Advantage: Keeping tombstones (deleted item IDs) prevents 'zombie resurrection' when stale replicas sync late.

Drawback: Tombstones accumulate indefinitely in high-churn sets/documents unless compacted via causal stability barriers or epoch GC.

Availability vs. Strong Invariants

Advantage: 100% write availability under network partitions (AP in CAP/PACELC) with 0 ms local write latency.

Drawback: Cannot enforce global uniqueness or non-negative bounds (e.g., `stock >= 0`) without adding a coordination layer.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Clock Skew Corrupting LWW-Registers

An LWW-Register using raw wall-clock `Date.now()` allows a replica with a 5-minute fast NTP clock to silently overwrite all newer edits from other nodes.

What helps: Use Hybrid Logical Clocks (HLC) combining physical time with a monotonic logical counter and `replicaId` tie-breaker.

Tombstone Bloat & OOM

A collaborative document or OR-Set with millions of add/delete cycles grows 10x larger than its visible data because deleted elements remain as tombstones.

What helps: Run distributed garbage collection once all known replicas acknowledge a causal version vector, or compact via periodic epoch snapshots.

Zombie Item Resurrection

Pruning tombstones aggressively before an offline mobile client reconnects causes that client's stale state to re-introduce deleted items.

What helps: Never drop tombstones below the minimum causal frontier of active replicas, or force stale offline clients (>30 days) to re-bootstrap from a fresh snapshot.

Replica ID Collisions

Two browser tabs or cloned VMs share the same `replicaId` in a G-Counter or OR-Set, causing updates to overwrite each other and break convergence.

What helps: Generate a cryptographically random 64-bit/128-bit `clientId` per session/instance rather than reusing user IDs or hostnames.

05 / Practical checklist

Avoid these mistakes

  • Using CRDTs to enforce invariants like 'only 1 seat left' or 'account balance cannot go below 0'—CRDTs cannot reject concurrent valid local writes.
  • Implementing a naive G-Counter keyed by `userId` instead of `replicaId`, which breaks when a user opens two tabs.
  • Assuming LWW-Register preserves all data—it explicitly discards losing concurrent writes.
  • Sending full CvRDT states on every keystroke instead of batching delta-CRDTs.
  • Forgetting to persist the local causal clock/vector alongside the CRDT state across restarts.
