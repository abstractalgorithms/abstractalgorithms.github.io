01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are CRDTs (Conflict-Free Replicated Data Types).

Traditional replication relies on consensus (Raft/Paxos) to agree on a global total order of writes. CRDTs invert the problem: instead of agreeing on when operations happened, design the data structure so order does not matter.

A state-based CRDT (CvRDT) forms a bounded join-semilattice (S, ⊔) whose merge operator ⊔ is associative, commutative, and idempotent (A ⊔ A = A). Any two replicas receiving the same updates—in any order, with any duplicates—mathematically converge to Strong Eventual Consistency (SEC).

Leaderless Convergence

Active-Active CRDT Gossip & Semilattice Merge

Every replica accepts local writes at 0 ms and converges deterministically via associative, commutative, idempotent merges.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need CRDTs (and How OR-Sets Prevent Lost Re-Adds).

Consensus protocols require 50–150 ms WAN quorum round-trips and stall during network partitions. Collaborative editors (Yjs, Automerge) and active-active carts need 0 ms local writes—even offline. In an Observed-Remove Set (OR-Set), tagging each addition with a unique (replicaId, seq) ensures a concurrent remove() only tombstones the specific tags it observed, preserving concurrent re-adds.

OR-Set Add-Wins Merge

Concurrent Remove & Re-Add Across Partitioned Replicas

Tagging every add with a unique ID ensures R1's stale remove cannot erase R2's concurrent re-add.

Real-Time Collaborative Rich Text (Yjs / YATA)

50 concurrent editors type offline/online; Yjs encodes insertions with (clientId, clock) and left/right origin pointers, merging 10,000+ out-of-order updates in <5 ms in-browser.

Active-Active Shopping Cart in Redis Enterprise

Using an OR-Set CRDT with vector clocks across Mumbai and Frankfurt, concurrent add(SKU-A) and remove(SKU-B) merge deterministically after link flaps.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to manage Replica IDs, HLCs & Tombstone Compaction.

  1. Unique replicaId: Generate a cryptographically random 64/128-bit clientId per tab/instance—never reuse userId or hostnames.
  2. Hybrid Logical Clocks (HLC): Never use raw Date.now() in LWW-Registers; an NTP-skewed client will silently overwrite all newer edits.
  3. Run-Length Encoding & Causal GC: Production engines like Yjs (Item structs) and Automerge 2.0 (columnar change logs) RLE-compress contiguous character IDs and compact tombstones only below the minimum causal frontier of active replicas.
# Join-semilattice PN-Counter & OR-Set merge primitives (Python)
class PNCounter:
    def __init__(self, replica_id: str):
        self.id = replica_id
        self.p: dict[str, int] = {}
        self.n: dict[str, int] = {}

    def inc(self, delta: int = 1) -> None:
        self.p[self.id] = self.p.get(self.id, 0) + delta

    def dec(self, delta: int = 1) -> None:
        self.n[self.id] = self.n.get(self.id, 0) + delta

    def value(self) -> int:
        return sum(self.p.values()) - sum(self.n.values())

    def merge(self, other: 'PNCounter') -> None:
        for k, v in other.p.items():
            self.p[k] = max(self.p.get(k, 0), v)
        for k, v in other.n.items():
            self.n[k] = max(self.n.get(k, 0), v)

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: CvRDT vs. CmRDT vs. Delta-CRDT vs. Consensus.

Choose between shipping full state, causal operations, or compact deltas depending on network reliability and object size.

ChoiceWhat it buysWhat it costs
CvRDT (State-Based)Tolerates dropped, duplicated, and reordered packets over plain HTTP/gossip.Bandwidth scales as O(full state size) on every sync.
CmRDT (Op-Based)Tiny operation payloads (`insert(pos, 'a')`).Requires reliable causal broadcast—cannot drop or reorder causal dependencies.
Delta-CRDT (δ-CRDT — Yjs / Riak / Automerge)Ships small idempotent state fragments; combines tiny payloads with loss-tolerant gossip.Requires tracking anti-entropy delta intervals per peer.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Architecture: Tombstone Lifecycle & Causal GC.

In production, CRDTs move through active writes, delta replication, and causal-barrier compaction. Never purge tombstones until all active replicas acknowledge the causal version vector—and force stale offline clients (>30 days) to re-bootstrap from a fresh epoch snapshot.

Tombstone Lifecycle

CRDT Element & Causal Compaction State Machine

Tombstones prevent zombie resurrection during late syncs and are safely reclaimed only after crossing the cluster's causal frontier.
