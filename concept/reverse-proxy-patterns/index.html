Reverse Proxy Patterns &
Edge Load Balancing.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Terminate TLS and untrusted client behavior at the proxy boundary so backend services only process normalized, connection-pooled traffic within strict timeout and circuit-breaker budgets.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Exposing application servers directly to the public internet forces every service to handle slowloris attacks, TLS handshakes, certificate rotation, and heterogeneous HTTP/2 or HTTP/3 framing. A reverse proxy (NGINX, Envoy, HAProxy, Cloudflare Pingora) absorbs connection churn, reduces backend CPU spent on cryptography by 30-50%, and enables zero-downtime routing shifts.

  • Connection pooling (keep-alive) between proxy and upstreams eliminates per-request TCP 3-way handshakes and ephemeral port exhaustion.
  • Power of Two Choices (P2C) with least-requests outperforms round-robin when request latencies vary by >5x across endpoints.
  • Consistent hashing (Ketama/Maglev) pins keys like user_id or tenant_id to specific upstream shards, preserving local cache hit rates during deploys.
  • Active health checks plus passive outlier detection (ejecting hosts after 5 consecutive 5xx responses) prevent black-holing traffic to degraded pods.
  • Buffer tuning (proxy_buffering, max_concurrent_streams) isolates fast backends from slow 3G mobile clients draining responses.

Good candidates

  • Terminating TLS 1.3 and HTTP/3 (QUIC) at the edge while speaking plain HTTP/2 or gRPC over mTLS inside a private VPC.
  • Consolidating cross-cutting concerns such as JWT validation, token-bucket rate limiting, and gzip/brotli compression in one control plane.
  • Routing traffic across heterogeneous upstreams using path prefixes, weighted canary splits, or consistent hashing for stateful caches.

Think twice

  • Ultra-low-latency internal RPCs (<100 microseconds) where an extra L7 hop and buffer copy violates the tail-latency budget.
  • Raw non-HTTP binary protocols (e.g., custom UDP game state) unless using an L4 passthrough proxy like IPVS or Envoy TCP proxy.
  • Simple single-binary internal tools behind an existing cloud load balancer where an extra proxy tier adds operational toil without isolation gains.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn e-commerce API running 120 Go microservices behind Envoy saw 42% CPU burned on TLS 1.2/1.3 handshakes and 502 spikes during pod autoscaling.

The idea

A reverse proxy sits in front of one or more origin servers and acts as the single authoritative network boundary for clients. Unlike a forward proxy (which hides clients from the internet), a reverse proxy hides backend topology from clients—terminating TLS 1.3, normalizing malformed HTTP frames, enforcing rate limits, and multiplexing requests over long-lived upstream pools.

By decoupling client-facing connection lifecycles from backend execution lifecycles, a reverse proxy lets backend services run with small, predictable worker pools (e.g., 16-64 threads) even while serving 100,000+ concurrent slow mobile connections.

Concrete walkthrough

  1. Edge TLS & ALPN: A mobile client connects over UDP/443 (HTTP/3 QUIC) or TCP/443 (TLS 1.3). The proxy completes the 1-RTT handshake using session tickets and negotiates h2 via ALPN.
  2. Header Sanitization & Auth: The proxy strips untrusted X-Forwarded-For headers, appends the verified peer IP, validates a JWT signature against a cached JWKS keyset, and checks a local/Redis token bucket.
  3. Route & Upstream Selection: Matching /api/v1/orders/*, the proxy selects a healthy endpoint from its orders cluster using Power of Two Choices (P2C) least-requests.
  4. Pooled Upstream Dispatch: Rather than opening a new TCP socket, the proxy reuses an idle HTTP/2 stream from its mTLS upstream pool, propagating traceparent and setting an x-request-timeout deadline of 800ms.
  5. Response & Outlier Tracking: The backend returns 200 OK in 42ms. If it instead returns 503, passive outlier detection increments the host's consecutive-error counter and ejects it for 30s once it hits 5 errors.

End-to-end L7 reverse proxy flow separating untrusted public TLS termination from pooled, outlier-protected private upstreams.

Connection pooling, buffering, and timeouts

Three knobs determine whether a reverse proxy absorbs spikes or amplifies them:

  • Keep-Alive Skew: Always keep upstream idle timeouts shorter at the proxy (55s) than at the application server (65s) so the proxy closes idle sockets cleanly instead of racing with a server-side FIN.
  • Request/Response Buffering: Buffering full bodies in proxy memory/disk frees backend worker threads immediately when clients are on slow networks, but must be disabled (proxy_buffering off) for SSE, gRPC bi-di streams, and >100 MB downloads.
  • Deadline Propagation: Forward remaining request budget via grpc-timeout or x-envoy-upstream-rq-timeout-ms so backends abort work if the client has already timed out.

Failure modes

  • Retry Amplification: Unbounded retries across multiple proxy tiers turn a 10% slowdown into a 10x traffic spike. Always enforce a global retry budget (<=10% of inflight requests) and never retry non-idempotent POST calls on 504.
  • Head-of-Line Blocking on HTTP/2 Upstreams: Multiplexing 1,000 requests onto a single TCP connection means one lost packet stalls all 1,000 streams. Cap max_concurrent_streams per upstream connection (e.g., 100) and maintain multiple pooled TCP connections per host.
  • DNS Stale Caching: NGINX OSS caches upstream DNS at startup unless configured with resolver and valid=10s inside a variable-based proxy_pass, causing 502s after cloud ALB IP rotations.

Observability and graceful draining

Separate proxy-originated errors from upstream errors in metrics and access logs:

  • Log both upstream_status and status, plus upstream_connect_time, upstream_header_time, and upstream_response_time.
  • During proxy upgrades or scale-in, stop accepting new connections (fail /readyz), send HTTP/2 GOAWAY frames on existing client connections, and wait drain_timeout (e.g., 30s) before closing sockets.

Practical checklist

  • Strip and re-set X-Forwarded-For / Forwarded at the outermost trusted edge proxy.
  • Set proxy upstream idle keep-alive timeout 10s lower than the backend server's timeout.
  • Enable P2C least-requests for variable-latency APIs; reserve consistent hashing for stateful caches.
  • Cap retry budgets at <=10% of active traffic and restrict retries to idempotent methods on connect/503 errors.
  • Configure passive outlier detection (5 consecutive 5xx -> 30s ejection) alongside jittered active health checks.
  • Set explicit connect (2s), header (15s), and total request timeouts, and disable buffering on SSE/streaming routes.
03 / Engineering trade-offs

Weighing architectural decisions

L7 Proxy Buffering vs Streaming

Advantage: Buffering full request/response bodies protects slow backend workers from being tied up by slow mobile clients.

Drawback: Increases proxy RAM usage and breaks Server-Sent Events (SSE), WebSockets, or large file streaming unless explicitly disabled per route.

Centralized Edge Proxy vs Sidecar Mesh

Advantage: A single edge fleet (NGINX/Envoy) is easy to size, monitor, and upgrade without injecting sidecars into every pod.

Drawback: Cannot enforce east-west mTLS or per-service circuit breaking between internal microservices without routing hairpins.

Consistent Hashing vs Least-Connections

Advantage: Consistent hashing maximizes upstream cache locality and minimizes key remapping to ~1/N when a node leaves.

Drawback: Hot keys (celebrity accounts) can overload a single upstream shard regardless of idle capacity on sibling nodes.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Upstream Keep-Alive Race Condition (502 Bad Gateway)

The upstream server closes an idle keep-alive connection at the exact millisecond the proxy writes a new request onto that socket, returning HTTP 502.

What helps: Set the proxy's idle connection timeout strictly lower than the upstream server's keepalive_timeout (e.g., 55s in Envoy vs 65s in Gunicorn/Node) and enable safe idempotent retries on connect/reset.

Proxy Header Spoofing (X-Forwarded-For Injection)

An attacker sends a forged X-Forwarded-For: 127.0.0.1 header, and a misconfigured proxy appends rather than strips untrusted client headers, bypassing IP allowlists.

What helps: Strip or overwrite X-Forwarded-For, X-Real-IP, and Forwarded at the outermost trusted edge proxy, or use PROXY protocol v2 between L4 LB and L7 proxy.

Retry Storm Amplification

When an upstream slows down, aggressive proxy retries (3x per hop across 3 service hops) multiply load by 27x, turning a partial brownout into a total outage.

What helps: Cap retry budgets to <=10% of active requests, retry only idempotent methods on connect-failure or 503, and enforce per-route deadlines via x-envoy-upstream-rq-timeout-ms.

Ephemeral Port Exhaustion

Disabling upstream keep-alive at >20k RPS exhausts the 28k-60k ephemeral TCP ports per proxy IP, leaving sockets stuck in TIME_WAIT.

What helps: Enable HTTP/1.1 keep-alive pools or HTTP/2 multiplexing to upstreams, and bind multiple source IPs or enable tcp_tw_reuse on Linux.

05 / Practical checklist

Avoid these mistakes

  • Leaving proxy_read_timeout at the 60s default while upstream handlers time out at 5s, masking cascading thread exhaustion.
  • Using round-robin for heterogeneous endpoints where 10ms health pings share workers with 2s PDF exports.
  • Forgetting to forward Host and X-Forwarded-Proto headers, causing backends to generate broken http:// redirect URLs.
  • Configuring identical health-check intervals across 50 proxy instances, creating a thundering herd on /healthz.
  • Treating HTTP 499 (client closed connection) as an upstream server error instead of client-side cancellation.
