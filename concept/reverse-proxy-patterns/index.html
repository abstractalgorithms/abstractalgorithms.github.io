Reverse Proxy Patterns & Edge Load Balancing

Terminate TLS, pool upstream TCP sockets, balance traffic across fleets, and enforce rate limits using NGINX, HAProxy, and Envoy.

✓ When to Use

  • ✓Microservice architectures needing unified entrypoints, TLS offloading, and path/header-based routing.
  • ✓Shielding backend servers from slow clients, DDoS surges, and unauthorized direct IP access.
  • ✓Canary deployments, blue-green traffic shifting, and shadow/mirror testing across software versions.

✕ When NOT to Use

  • ✕Simple monolithic applications deployed on single servers where an additional proxy hop adds latency without operational benefit.
  • ✕Ultra-low latency HPC (High Performance Computing) or intra-node MPI workloads where sub-microsecond latency demands direct kernel bypass (e.g. DPDK, RDMA).
  • ✕Direct peer-to-peer (P2P) mesh protocols where intermediaries break end-to-end direct UDP hole-punching.

Context & Constraints — Human Reviewed

Why It Matters

Exposing internal microservices directly to client networks forces every application instance to manage TLS certificates, handle slow client attacks (Slowloris), and execute complex routing. Placing an optimized reverse proxy layer at the edge decouples routing policy from application logic, slashes backend connection overhead by up to 90%, and provides centralized observability.

Core Architecture & Rules

  • →TLS Termination & Offloading: Performs expensive asymmetric cryptography (RSA/ECDSA key exchange) once at the edge, forwarding plain HTTP/1.1 or gRPC over private, encrypted VPC networks.
  • →Connection Multiplexing & Pooling: Converts thousands of slow, erratic client connections into a compact pool of warm, persistent HTTP/2 or TCP upstream connections.
  • →Load Balancing Algorithms: Beyond Round-Robin, production proxies use Weighted Least Connections or Power of Two Choices (P2C) with Peak EWMA to avoid hot-spotting slower backend nodes.
  • →Outlier Detection & Circuit Breaking: Automatically ejects backends returning 5xx spikes or high latency from the routing pool before cascading failures consume downstream services.
  • →Header Manipulation & Security Enforcement: Strips untrusted external headers, injects tracing identifiers (x-request-id), and terminates hop-by-hop HTTP headers.

Failure Modes & Mitigations

  • ⚖Upstream Thundering Herd & Blackholing:When an upstream service restarts, the reverse proxy floods the cold nodes with thousands of simultaneous new connections, instantly crashing them before they can warm caches.

    Mitigation: Configure slow-start warm-up ramps in Envoy/NGINX, enforce concurrency limits, and use health checks to stage node reintroduction.

  • ⚖Buffer Exhaustion & Disk Spooling:Clients uploading large payloads or backends returning large responses exceed proxy RAM buffers (client_body_buffer_size), causing the proxy to write chunks to disk and throttling throughput.

    Mitigation: Stream large payloads directly without buffering, set strict max payload boundaries, and provision proxy nodes with fast NVMe swap or high RAM ceilings.

  • ⚖Misconfigured X-Forwarded-For Trust:Proxy fails to sanitize untrusted client X-Forwarded-For headers, allowing attackers to spoof client IP addresses and bypass IP-based rate limiters and geofences.

    Mitigation: Configure real_ip_recursive or Envoy xff_num_trusted_hops to strip client-supplied headers and only trust the nearest legitimate network hop.

Example Usages

Envoy Upstream Connection Pooling at Scale

Scenario: A backend payments cluster running on 20 nodes was overwhelmed by 40,000 incoming client TLS connections, spending 45% of its CPU on cryptographic handshakes.

Outcome: Deploying Envoy as an edge reverse proxy reduced backend TCP connections from 40,000 to 200 persistent pooled sockets, freeing 40% CPU capacity.

Canary Shifting with Header-Based Routing

Scenario: An engineering team needed to test a new version of their recommendations engine against 5% of production traffic without deploying a separate domain.

Outcome: Configured reverse proxy weighted cluster matching to route 95% to v1 and 5% to v2, shifting to 100% automatically after error budget criteria were met.
