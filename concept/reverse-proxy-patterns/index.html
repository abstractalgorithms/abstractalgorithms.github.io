Reverse Proxy Patterns & Edge Load Balancing

Terminate TLS, pool upstream TCP sockets, balance traffic across fleets, and enforce rate limits using NGINX, HAProxy, and Envoy.

Orientation & Intuition

A reverse proxy acts as an intermediary gateway positioned between external clients and private backend services. It terminates client TLS handshakes, multiplexes requests across persistent upstream connection pools, distributes traffic via balancing algorithms (Round Robin, Least Connections, P2C), and guards internal services against direct internet exposure.

Key takeaway Offload TLS decryption, header sanitation, and connection pooling to the reverse proxy tier (Envoy, NGINX) to prevent backend worker exhaustion; configure health-checked connection pools and active outlier detection to isolate failing upstream instances without cascading outages.

Core Architecture & Trade-offs

Exposing internal microservices directly to client networks forces every application instance to manage TLS certificates, handle slow client attacks (Slowloris), and execute complex routing. Placing an optimized reverse proxy layer at the edge decouples routing policy from application logic, slashes backend connection overhead by up to 90%, and provides centralized observability.

Key Architecture Invariants

  • TLS Termination & Offloading: Performs expensive asymmetric cryptography (RSA/ECDSA key exchange) once at the edge, forwarding plain HTTP/1.1 or gRPC over private, encrypted VPC networks.
  • Connection Multiplexing & Pooling: Converts thousands of slow, erratic client connections into a compact pool of warm, persistent HTTP/2 or TCP upstream connections.
  • Load Balancing Algorithms: Beyond Round-Robin, production proxies use Weighted Least Connections or Power of Two Choices (P2C) with Peak EWMA to avoid hot-spotting slower backend nodes.
  • Outlier Detection & Circuit Breaking: Automatically ejects backends returning 5xx spikes or high latency from the routing pool before cascading failures consume downstream services.
  • Header Manipulation & Security Enforcement: Strips untrusted external headers, injects tracing identifiers (x-request-id), and terminates hop-by-hop HTTP headers.

When to Use

  • Microservice architectures needing unified entrypoints, TLS offloading, and path/header-based routing.
  • Shielding backend servers from slow clients, DDoS surges, and unauthorized direct IP access.
  • Canary deployments, blue-green traffic shifting, and shadow/mirror testing across software versions.

When NOT to Use

  • Simple monolithic applications deployed on single servers where an additional proxy hop adds latency without operational benefit.
  • Ultra-low latency HPC (High Performance Computing) or intra-node MPI workloads where sub-microsecond latency demands direct kernel bypass (e.g. DPDK, RDMA).
  • Direct peer-to-peer (P2P) mesh protocols where intermediaries break end-to-end direct UDP hole-punching.

2. Load Balancing Mechanics: Power of Two Choices (P2C)

Traditional Round-Robin and Random balancing algorithms degrade severely when request execution times vary (e.g. lightweight cache hits mixed with heavy database scans).

Under high load, modern proxies implement Power of Two Random Choices (P2C) with Peak EWMA:

  1. When routing an incoming request, the proxy randomly selects two candidate backend nodes from the upstream pool.
  2. It compares the two candidates using their Exponentially Weighted Moving Average (EWMA) of active requests and connection latency.
  3. It routes the request to whichever node has the lighter current load.

Mathematical Guarantee: P2C achieves an exponential decrease in maximum queue length compared to pure random selection, preventing hotspots with almost zero synchronization overhead between proxy worker threads.

3. Production Configuration Best Practices (Envoy / NGINX)

nginx 
# NGINX Production Reverse Proxy & Upstream Keepalive Pool
upstream backend_cluster {
    server 10.0.1.10:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 backup;

    # Maintain 64 idle keepalive connections per worker
    keepalive 64;
    keepalive_requests 10000;
    keepalive_timeout 60s;
}

server {
    listen 443 ssl http2;
    server_name api.abstractalgorithms.com;

    # TLS termination & session resumption
    ssl_certificate /etc/ssl/certs/api.crt;
    ssl_certificate_key /etc/ssl/private/api.key;
    ssl_session_cache shared:SSL:50m;
    ssl_session_timeout 1d;

    location / {
        proxy_pass http://backend_cluster;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # Timeouts to prevent hanging sockets
        proxy_connect_timeout 2s;
        proxy_read_timeout 10s;
        proxy_send_timeout 10s;
    }
}
