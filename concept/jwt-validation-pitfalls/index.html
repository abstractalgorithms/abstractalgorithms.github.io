THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Never let an untrusted token dictate how it is verified: enforce a strict server-side algorithm allowlist, pin trusted JWKS endpoints, and validate `iss`, `aud`, and `exp` on every request.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

JWTs are self-describing—they carry their own algorithm (alg), key ID (kid), and key URL (jku) inside an unauthenticated Base64URL header. Naive verification libraries that obey those header hints let attackers forge arbitrary admin tokens without knowing any secret.

  • alg: none & Key Confusion (CVE-2015-9235): trusting the token's alg header lets an attacker strip the signature (alg: none) or re-sign a token with HS256 using your public RSA key as the HMAC secret.
  • kid Injection & Path Traversal: interpolating the kid header into a SQL query (SELECT key FROM keys WHERE id = '$kid') or file path (../../dev/null) enables trivial signature bypass.
  • jku / x5u SSRF & Key Spoofing: fetching public keys from a URL embedded in the JWT header lets an attacker host their own JWKS and sign valid-looking tokens.
  • Missing aud (Audience) & iss (Issuer) Checks: a valid JWT issued for billing-api or a third-party tenant can be replayed against admin-api if only the signature and exp are checked.
  • Clock Skew & Revocation Gap: generous exp windows (24h+) or unbounded clock leeway undermine security; keep access tokens short (300–900s) and bound leeway to <= 60s.

Good candidates

  • Stateless service-to-service or API-gateway authentication using short-lived (5–15 min) RS256/ES256 tokens issued by an OIDC provider (Auth0, Okta, Keycloak, Cognito).
  • Cross-domain SSO (OAuth 2.0 / OIDC id_token) where resource servers verify signatures locally via cached JWKS public keys.

Think twice

  • Browser session tokens requiring instant global logout or immediate revocation upon permission downgrade (prefer opaque reference tokens + Redis/DB lookup).
  • Storing large user profiles or sensitive PII inside unencrypted JWS tokens (JWT payloads are Base64URL-encoded, not encrypted—anyone can decode them).

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA Node.js API calls jwt.verify(token, publicKey) without passing { algorithms: ['RS256'] }. An attacker downloads the public .pem from /.well-known/jwks.json.

The idea

A JSON Web Signature (JWS, RFC 7515) consists of three Base64URL-encoded segments: header.payload.signature. The trap is that the header is attacker-controlled input until the signature is verified. Because the header tells a naive parser which algorithm (alg) and which key (kid, jku, x5u) to use, any verifier that blindly follows header instructions hands control of the verification state machine to the caller.

RFC 8725 (JWT Best Current Practices) establishes one golden rule: server policy overrides token headers. The verifier must dictate the allowed algorithms (ES256, RS256, EdDSA), pin the trusted issuer's JWKS URI out-of-band, and enforce semantic claim checks (iss, aud, exp, nbf) before any downstream business logic reads sub or roles.

Concrete walkthrough

Walk through a hardened verification pipeline in an Envoy / API Gateway + Resource Service:

  1. Parse & Reject: Extract the Bearer token. Reject tokens exceeding 8 KB, tokens with != 3 dot-separated parts, or headers containing jku, x5u, or unsupported crit extensions.
  2. Algorithm Allowlist: Read header.alg. If alg is not in the server's pinned list (e.g., ["RS256", "ES256"]), reject immediately with 401 Unauthorized—blocking alg: none and HS256 key confusion.
  3. Pinned JWKS Lookup: Look up header.kid in the in-memory JWKS cache populated solely from the pre-configured https://auth.example.com/.well-known/jwks.json. Also verify the JWK's use: "sig" and alg match.
  4. Cryptographic Verify: Verify the signature over ASCII(header + '.' + payload) using constant-time comparison.
  5. Semantic Claims: Assert iss == "https://auth.example.com/", "api://orders" in aud, now < exp + 30s, and now >= nbf - 30s. Optionally check jti against a Redis revocation set for high-risk actions.

Hardened JWT verification: server-enforced algorithm allowlists and out-of-band JWKS pinning neutralize header-driven attacks.

The key confusion & kid injection mechanics

Why did CVE-2015-9235 affect so many libraries? Because early APIs had a single verify(token, secretOrKey) signature:

  • When alg was RS256, secretOrKey was treated as an RSA public key.
  • When an attacker changed alg to HS256, the exact same function passed the RSA public key string (-----BEGIN PUBLIC KEY-----...) into HMAC_SHA256(key, data).

Since RSA public keys are public (exposed at /.well-known/jwks.json), anyone could compute a valid HMAC tag. Similarly, if kid is used to build a filesystem path (keys/${kid}.pem), setting kid: "../../../dev/null" causes the verifier to read an empty string "" as the HMAC secret, letting the attacker sign tokens with an empty key.

Failure modes

  • Subtle aud array mismatch: RFC 7519 allows aud to be either a JSON string or an array of strings; naive string equality (claims.aud == myService) fails or breaks when an IdP emits an array.
  • Type confusion (typ header): Accepting an OAuth at+jwt access token where an OIDC id_token is expected (or vice versa) can bypass authorization scopes. Enforce explicit typ checks where supported.
  • Revocation blind spot: Relying solely on 24-hour JWTs means an employee whose account is disabled at 09:05 retains API access until 09:05 the next day.

Hybrid stateless + stateful patterns

For high-security systems, combine short-lived JWTs with minimal state:

  1. Short access tokens (exp = 300s) + Refresh Token Rotation: Clients refresh silently; revoking the refresh token in the database caps exposure to 5 minutes.
  2. Phantom Token Pattern (API Gateway): The browser/mobile client holds an opaque reference token; the edge API Gateway exchanges it once (cached in Redis for 30–60s) for an internal signed JWT before forwarding to microservices. Internal services get fast stateless JWTs while external clients never see internal claims or user PII.

Practical checklist

  • Pass an explicit algorithms allowlist (['ES256'] or ['RS256']) to every verify() call—never rely on defaults.
  • Enforce iss, aud, exp, and nbf validation with <= 60s clock skew leeway.
  • Ignore jku, x5u, and jwk embedded headers; load keys strictly from a pinned, rate-limited JWKS cache.
  • Sanitize kid against [a-zA-Z0-9_-]+ before any cache or map lookup.
  • Keep access token exp <= 15 minutes and back critical mutations with a jti revocation check or opaque gateway token.
03 / Engineering trade-offs

Weighing architectural decisions

Stateless Verification vs. Instant Revocation

Advantage: Local signature verification via cached JWKS eliminates a network hop to the IdP on every API call (~0.1 ms CPU vs ~15 ms RPC).

Drawback: Compromised or logged-out JWTs remain valid until `exp` unless you add a stateful `jti` denylist in Redis.

JWKS Caching TTL

Advantage: Caching JWKS for 5–15 minutes prevents IdP rate-limiting and protects against `kid`-miss DoS attacks.

Drawback: Emergency key revocation requires an out-of-band cache invalidation or short TTLs; unknown `kid` lookups must be rate-limited.

Asymmetric (ES256/RS256) vs. Symmetric (HS256)

Advantage: Asymmetric signing ensures resource servers only hold public keys, so a compromised API node cannot mint tokens.

Drawback: RS256/ES256 verification is ~10x slower in CPU cycles than HMAC-SHA256 (though still sub-millisecond).

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

JWKS Cache-Busting DoS

An attacker sends 10,000 requests with random `kid` values; the API gateway synchronously fetches `/.well-known/jwks.json` on every cache miss, taking down the IdP.

What helps: Rate-limit JWKS refreshes (e.g., max once per 60 seconds) and reject unknown `kid`s locally between refreshes.

Critical Header (`crit`) Bypass

A library ignores unknown `crit` extensions per RFC 7515 §4.1.11, bypassing custom policy enforcement expected by the issuer.

What helps: Use RFC 8725-compliant libraries (e.g., `nimbus-jose-jwt`, `jose`, `PyJWT >= 2.8`) that reject unsupported `crit` headers by default.

PII Leakage in Browser Logs & Referer Headers

Developers place JWTs in query strings (`?token=eyJ...`) or store sensitive claims in unencrypted JWS payloads.

What helps: Always transmit JWTs in `Authorization: Bearer` headers, never URLs, and use JWE if payloads contain confidential fields.

Symmetric Secret Brute-Forcing

An HS256 token signed with a weak secret like `supersecret123` is cracked offline in minutes using `hashcat`.

What helps: Prefer ES256/RS256; if HS256 is required, use at least 256 bits of CSPRNG entropy.

05 / Practical checklist

Avoid these mistakes

  • Calling `jwt.decode()` (which only Base64-decodes without verifying the signature) instead of `jwt.verify()`.
  • Omitting the explicit `algorithms` allowlist (`['ES256']` or `['RS256']`), leaving the verifier vulnerable to `alg: none` or HS256 key confusion.
  • Storing JWTs in `localStorage` where any XSS script can exfiltrate them, instead of `HttpOnly; Secure; SameSite=Lax` cookies or BFF patterns.
  • Accepting tokens without checking `iss` (Issuer) and `aud` (Audience), allowing cross-tenant or cross-service token replay.
  • Setting multi-day `exp` lifetimes on access tokens without a `jti` revocation check or refresh-token rotation.
