STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Capacity Planning & Forecasting.

Capacity planning ensures every tier—compute, RAM, storage IOPS, network bandwidth, and third-party quotas—can absorb both organic demand and sudden failover shifts within latency SLOs.

Two quantitative laws anchor the math:

  1. Little's Law (L=λ⋅WL = \lambda \cdot WL=λ⋅W): Average concurrency LLL equals arrival rate λ\lambdaλ (RPS) times response time WWW (sec). If DB lock contention doubles WWW from 50 ms to 100 ms, required threads/pods LLL double immediately at constant RPS!
  2. Universal Scalability Law (USL): C(N)=N1+α(N−1)+βN(N−1)C(N) = \frac{N}{1 + \alpha(N - 1) + \beta N(N - 1)}C(N)=1+α(N−1)+βN(N−1)N​ models both contention (α\alphaα, lock/queue waits) and coherency delay (β\betaβ, cache invalidation), showing where adding nodes actually reduces throughput.
Multi-Tier Bottleneck Model

Demand Forecast -> Little's Law Concurrency -> Tier Saturation Limits

1.Demand Decomposition: Separate organic growth, diurnal seasonality, and scheduled marketing spikes into P95 peak RPS.

2.N-1 Zone Headroom: Size clusters so surviving AZs stay below 70% utilization if 1 of 3 AZs drops completely.

3.Non-CPU Ceilings: Check ephemeral ports (28,232), nf_conntrack_max, and EBS IOPS alongside CPU/RAM.

Capacity planning sizes every bottleneck tier for P95 demand plus N-1 zone failover headroom.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Saturation Curves (and why average CPU lies).

Sizing from 40% average CPU fails during real spikes for three reasons:

  1. Coordinated Omission in Load Tests: Naive load generators pause when the server slows down, hiding the p99 latency cliff until real users hit it.
  2. Cold-Cache Thundering Herd: Pre-scaling stateless pods without warming Redis or CDN sends 100% of peak traffic straight to PostgreSQL.
  3. Ephemeral Port & Conntrack Exhaustion: High-RPS services without HTTP keep-alive exhaust Linux ip_local_port_range or nf_conntrack_max long before CPU hits 50%.
Queuing Knee

System Utilization & Tail-Latency Saturation State Machine

Keep steady-state utilization below the USL knee (~65-70%) so latency shocks don't trigger metastable collapse.

Three-Tier FinOps Commitments

Cover Baseload (P10) with 1-3yr Reserved/Savings Plans (40-60% off), diurnal peaks with On-Demand/HPA, and batch jobs with Spot.

Avoid Cold-Start Trap

Account for container pull + JVM/model warm-up time (2-5m); use scheduled pre-scaling before known flash-sale peaks.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Little's Law & N-1 Failover Budgets are calculated.

Build a repeatable capacity spreadsheet or script that computes required pods, DB connections, and N-1 zone headroom from target RPS and load-tested p95 latency.

# Little's Law + N-1 AZ Failover Capacity Calculator (Python)
import math

def size_service_fleet(
    peak_rps: float,
    target_latency_s: float,
    concurrency_per_pod: int,
    az_count: int = 3,
    max_util: float = 0.70,
) -> dict:
    # Little's Law: L = lambda * W
    required_concurrency = peak_rps * target_latency_s
    active_pods_needed = math.ceil(required_concurrency / (concurrency_per_pod * max_util))
    # N-1 AZ survival: remaining (az_count - 1) zones must carry 100% of active_pods_needed
    pods_per_az = math.ceil(active_pods_needed / (az_count - 1))
    total_pods = pods_per_az * az_count
    return {
        "littles_law_concurrency": round(required_concurrency, 1),
        "min_pods_steady": active_pods_needed,
        "total_pods_n_minus_1": total_pods,
    }
