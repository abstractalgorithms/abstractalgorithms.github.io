RAG Retrieval
Pipelines.

Production RAG retrieval combines semantic chunking, hybrid dense (HNSW) + sparse (BM25/SPLADE) search, Reciprocal Rank Fusion (RRF), metadata pre-filtering, and cross-encoder reranking to deliver high-precision context to LLMs.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Dense vector search alone misses exact SKUs and error codes; hybrid retrieval (BM25 + HNSW) fused via RRF and narrowed by a cross-encoder reranker boosts precision while cutting LLM prompt tokens.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

An LLM can only reason over the context it receives. Naive "embed 500-char chunks + cosine top-5" pipelines fail on exact identifiers, leak cross-tenant data when ACLs are applied too late, and flood the LLM with noisy chunks that trigger hallucinations and high token bills.

  • Hybrid search pairs dense embeddings (e.g., BGE-M3 / text-embedding-3-large) with lexical BM25/SPLADE so neither synonyms nor exact codes are missed.
  • Reciprocal Rank Fusion (RRF: sum(1 / (k + rank)), k=60) merges dense and sparse rankings cleanly without score-normalization tuning.
  • Cross-encoder rerankers (e.g., Cohere Rerank v3, bge-reranker-v2-m3) jointly score query+chunk pairs, pruning top-50 candidates to top-5 high-precision chunks.
  • Metadata pre-filtering (tenant_id, ACLs, date) must execute inside the vector/lexical index—post-filtering can return zero valid results.
  • Parent-child (small-to-big) chunking retrieves crisp 256-token child chunks for matching, then injects their 1,024-token parent section for LLM coherence.

Good candidates

  • Grounding LLM answers in private, rapidly changing enterprise docs, support runbooks, or product catalogs.
  • Queries mixing semantic intent ('how to fix timeout') with exact tokens ('ERR_CONNECTION_RESET', 'SKU-9040').
  • Multi-tenant applications requiring strict document-level RBAC/ACL enforcement before chunks ever reach the LLM.

Think twice

  • Small, static corpora (<50k tokens) that fit cleanly inside a prompt cache with zero retrieval latency or chunking loss.
  • Structured analytical queries ('sum Q3 revenue by region') where Text-to-SQL or APIs beat unstructured chunk retrieval.
  • Real-time streaming telemetry where indexing lag makes vector stores perpetually stale.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA dense-only Qdrant pipeline fails when engineers search for 'AX-9040-V2 firmware rollback', returning generic router docs instead of the exact SKU manual.

The idea

A production RAG pipeline is a multi-stage information retrieval funnel, not a single vector lookup. Dense bi-encoder embeddings excel at semantic similarity ('memory leak' <-> 'OOM killer'), but compress away exact lexical tokens ('CVE-2024-3094', '0x80070005'). Conversely, BM25 excels at exact terms but misses synonyms.

Modern pipelines solve this with two-stage hybrid retrieval: a fast Stage 1 recall layer runs dense HNSW vector search and sparse BM25/SPLADE in parallel (pre-filtered by tenant ACLs), merges them with Reciprocal Rank Fusion (RRF), and passes the top ~50 candidates to a Stage 2 cross-encoder reranker that jointly attends over (query, chunk) pairs to emit the top 5–8 highest-signal chunks.

Concrete walkthrough

Trace a user query "Why did checkout fail with ERR_IDEMPOTENCY_409?":

  1. Query prep & ACLs: Extract tenant_id=acme and role=eng pre-filters; optionally expand abbreviations.
  2. Parallel Stage-1 recall:
    • Dense (HNSW, 1024-dim BGE-M3) returns top-50 semantically related checkout retry docs.
    • Sparse (BM25 / OpenSearch) returns top-50 docs containing the exact token ERR_IDEMPOTENCY_409.
  3. RRF fusion (k=60): Each doc gets score = 1/(60 + rank_dense) + 1/(60 + rank_sparse), promoting docs strong in either or both lists.
  4. Stage-2 cross-encoder rerank: bge-reranker-v2-m3 scores the top-50 fused chunks in ~55 ms, selecting the top-5.
  5. Parent-child expansion: Each matched 256-token child chunk expands to its 1,024-token parent section before entering the LLM prompt.

Separating fast Stage-1 hybrid recall from compute-intensive Stage-2 cross-encoder reranking maximizes Recall@50 and NDCG@5 within a <120 ms retrieval budget.

Chunking & ingestion architecture

Retrieval quality is capped by ingestion quality:

  • Structure-first splitting: Parse PDFs/HTML into Markdown headings, tables, and code blocks first; never split a table or code fence in half.
  • Parent-child (small-to-big): Index 256-token child chunks for crisp vector matching, but store a parent_id pointing to the 1,024-token section so the LLM sees complete context.
  • Contextual headers: Prepend doc_title > section_h2 > updated_at to each chunk before embedding so pronoun-heavy paragraphs ('It must be rotated every 90 days') stay grounded.

Failure modes

RAG pipelines silently degrade in four ways:

  • Post-filtering empty sets: Applying permissions after top-K retrieval starves minority tenants.
  • Stale chunk orphans: Re-ingesting edited docs without deleting prior chunk IDs causes old policies to outrank new ones.
  • Embedding model drift: Mixing query embeddings from model v2 against document embeddings from model v1 silently destroys cosine similarity.
  • Table flattening: Naive PDF text extractors scramble multi-column financial or spec tables into unreadable word soup.

Evaluating retrieval separately from generation

Always decouple retrieval evals from LLM generation evals:

  1. Retrieval metrics: Build a 100–300 query golden set with labeled relevant doc_ids and track Recall@20 (Stage 1) and NDCG@5 / MRR (Stage 2).
  2. Generation metrics: Measure groundedness/faithfulness (does the answer contradict or extrapolate beyond retrieved chunks?) and citation accuracy using frameworks like RAGAS or LLM-as-a-judge.

Practical checklist

  • Enforce tenant_id and ACL predicates as pre-filters inside the vector and lexical indices.
  • Combine dense HNSW + BM25/SPLADE with RRF (k=60) instead of dense-only search.
  • Add a cross-encoder reranker (top-50 -> top-5) to maximize precision and cut LLM input tokens.
  • Use structure-aware chunking with contextual headers (doc_title > section) and atomic delete-by-doc_id upserts.
  • Track Recall@20 and NDCG@5 on a golden query set before changing chunk sizes, embedders, or prompts.
03 / Engineering trade-offs

Weighing architectural decisions

Cross-encoder reranking latency vs. precision

Advantage: Boosts NDCG@5 by ~8-15% and slashes irrelevant context sent to the LLM.

Drawback: Adds ~40-90 ms of GPU inference latency per query on top-50 candidates.

Chunk size (small vs. large)

Advantage: Small chunks (200-300 tokens) yield sharper embedding similarity without topic dilution.

Drawback: Small chunks lose surrounding headers/conditions unless paired with parent-document expansion.

Index complexity (dense-only vs. hybrid)

Advantage: Hybrid dense + BM25 captures both conceptual paraphrases and exact identifiers.

Drawback: Requires maintaining synchronized dense HNSW and inverted lexical indices.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Post-Retrieval ACL Starvation

Filtering permissions after top-K vector search drops authorized results when other tenants dominate the top K.

What helps: Apply tenant_id and group ACL filters as pre-filters inside Qdrant, Milvus, OpenSearch, or pgvector.

Chunk Boundary Context Shredding

Fixed 500-character splits cut tables, code blocks, or 'NOT recommended' caveats away from their subject.

What helps: Use structure-aware Markdown/HTML splitters and parent-child retrieval (match child, return parent).

Stale Index & Orphaned Chunks

Updating a source document appends new chunks without deleting old chunk IDs, causing contradictory answers.

What helps: Key chunks deterministically by (doc_id, chunk_index) and run atomic delete-by-doc_id upserts.

Lost-in-the-Middle Context Overload

Stuffing 20+ unranked chunks into the prompt degrades LLM attention on middle passages and raises hallucination.

What helps: Rerank top-50 down to top-5/8 and place highest-scoring chunks at the start and end of the context window.

05 / Practical checklist

Avoid these mistakes

  • Relying on pure cosine similarity for domains rich in part numbers, error codes, legal citations, or acronyms.
  • Splitting PDFs and Markdown tables mid-row with naive fixed character windows.
  • Applying RBAC/tenant filters in application code after vector search instead of inside the index.
  • Shipping without offline retrieval metrics (Recall@K, MRR, NDCG@10) and only eyeballing 5 sample prompts.
  • Passing top-25 raw chunks directly to the LLM instead of reranking down to top-5.
