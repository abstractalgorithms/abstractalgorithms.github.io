STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is a Production RAG Retrieval Pipeline.

A production RAG pipeline is a multi-stage information retrieval funnel, not a single cosine_similarity lookup. Dense bi-encoder embeddings (BGE-M3, text-embedding-3-large) capture synonyms (memory leak <-> OOM killer), while sparse lexical search (BM25/SPLADE) captures exact tokens (ERR_IDEMPOTENCY_409, SKU-9040).

Reciprocal Rank Fusion (RRF): score(d)=∑1k+ranki(d)\text{score}(d) = \sum \frac{1}{k + \text{rank}_i(d)}score(d)=∑k+ranki​(d)1​ (k=60k=60k=60) merges both rankings without score-normalization tuning, and a cross-encoder reranker narrows top-50 candidates down to the top-5 highest-precision chunks.

Multi-Stage Retrieval Funnel

Pre-Filtered Hybrid Recall -> RRF Fusion -> Cross-Encoder Rerank

Hybrid recall + RRF + cross-encoder reranking boosts NDCG@5 by 8–15% while shrinking prompt token costs.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Naive Vector Top-5 Fails (ACLs, Shredded Tables & Lost-in-the-Middle).

Naive "500-char fixed split + dense top-5" pipelines fail in three predictable ways: (1) Post-retrieval ACL starvation: filtering tenant_id after top-K search returns 0 results if another tenant's docs dominated top-K; (2) Context shredding: fixed character splits sever Markdown tables or NOT recommended caveats from their headers; (3) Lost-in-the-middle: stuffing 25 unranked chunks into the prompt degrades LLM attention.

Parent-Child (Small-to-Big) Chunking

Index crisp 256-token child chunks for sharp embedding similarity, then expand to their 1,024-token parent section for LLM coherence.

Deterministic `(doc_id, chunk_index)` Upserts

Re-ingesting edited documents without deleting prior chunk IDs leaves contradictory policy versions competing in the index.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Hybrid RAG shines (and where Prompt Caching or SQL win).

Use multi-stage RAG for large, mutable enterprise corpora; skip chunking when the entire corpus fits in prompt cache or requires SQL aggregation.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How RRF Fusion & Offline Retrieval Evals are managed.

Always decouple retrieval evals (Recall@20, NDCG@5, MRR on a 100–300 query golden set) from generation evals, enforce tenant_id / ACL filters inside the vector engine (Qdrant, OpenSearch, pgvector), and fuse dense + sparse lists via RRF (k=60).

def reciprocal_rank_fusion(ranked_lists: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    """Merge dense (HNSW) and sparse (BM25) doc_id rankings without score calibration."""
    scores: dict[str, float] = {}
    for ranking in ranked_lists:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Multi-Tenant Hybrid Index with Parent Expansion.

An enterprise support copilot indexes 256-token child chunks in Qdrant (HNSW + sparse BM25 vectors) with tenant_id and acl_groups payload indexes, fuses top-50 candidates with RRF, reranks to top-5 with bge-reranker-v2-m3, and fetches 1,024-token parent blocks from Redis/Postgres.

Small-to-Big Retrieval

Child-Chunk Hybrid Index + Parent-Block Store

1.1. Index-Side ACLs: tenant_id and acl_groups execute inside the HNSW/BM25 filter so unauthorized chunks never enter top-50.

2.2. Sharp Child Match: 256-token child vectors avoid topic dilution while preserving exact error-code BM25 hits.

3.3. Coherent Parent: Top-5 reranked hits expand to full 1,024-token parent sections before LLM synthesis.

Small-to-big indexing + pre-filtered hybrid search solves both precision and context completeness.
