The idea to keep with you

Sliding Window Maximum computes the maximum element in every contiguous subarray of size `k` across a length-`n` sequence in optimal $O(n)$ time and $O(k)$ space. By maintaining a monotonically decreasing double-ended queue (`deque`) of array indices, each element is pushed and popped at most once, beating naive $O(nk)$ scans and $O(n \log k)$ max-heaps.

Trade-Offs & Production: Monotonic deque achieves strict O(n)O(n)O(n) time and bounded O(k)O(k)O(k) memory. 1.

Failure Modes & Application: Store indices—not values—in a monotonically decreasing deque, evicting out-of-window indices from the front and smaller values from the back to hit strict O(n)O(n)O(n) time.

From patterns to decisions.

Real-time stream processors (Apache Flink, Kafka Streams), network anomaly detectors, and financial tick engines continuously compute rolling peak CPU, peak latency, or max bid price over trailing `k`-event or `W`-second windows. At 100,000 events/sec with `k = 10,000`, an $O(n \cdot k)$ rescan executes $10^9$ comparisons per second and collapses, whereas a monotonic deque processes each event in amortized $O(1)$ time with predictable tail latency.

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Sliding Window Maximum.

Pruning dominated candidates with a monotonic deque

When a window slides right by one element nums[i], any older element nums[j] (j < i) inside the window that satisfies nums[j] <= nums[i] is permanently dominated: nums[i] is both larger (or equal) and will expire later than nums[j]. Therefore, nums[j] can never be the maximum of the current window or any future window. By popping all dominated elements from the back of a double-ended queue (deque) before appending i, the deque remains strictly decreasing in value and strictly increasing in index.

Core Pillars:

  • Store indices in the deque rather than raw values so you can check window expiration in O(1)O(1)O(1) via deque[0] <= i - k.
  • Maintain the monotonic decreasing invariant: before pushing index i, pop all back indices j where nums[j] <= nums[i] because j is both smaller and older, so it can never be the max of any future window.
  • Amortized O(1)O(1)O(1) per step: every index enters the back of the deque once and leaves either the front (expired) or back (dominated) at most once, yielding <= 2n deque operations total.
  • The front of the deque (nums[deque[0]]) is always the exact maximum of the current window once i >= k - 1.
  • A two-pass prefix/suffix block-max algorithm also achieves O(n)O(n)O(n) time with O(n)O(n)O(n) space and zero deque pointer chasing, ideal for SIMD/GPU batch arrays.
Monotonic Deque Invariant

Monotonic Decreasing Deque Transitions per Element

Each index enters and leaves the deque at most once, yielding O(N) time and O(k) space.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Sliding Window Maximum (and what fails without it).

Real-time stream processors (Apache Flink, Kafka Streams), network anomaly detectors, and financial tick engines continuously compute rolling peak CPU, peak latency, or max bid price over trailing k-event or W-second windows. At 100,000 events/sec with k = 10,000, an O(n⋅k)O(n \cdot k)O(n⋅k) rescan executes 10910^9109 comparisons per second and collapses, whereas a monotonic deque processes each event in amortized O(1)O(1)O(1) time with predictable tail latency.

Common Pitfalls:

  • Using list.pop(0) in Python instead of collections.deque.popleft(), silently degrading the algorithm from O(n)O(n)O(n) to O(n⋅k)O(n \cdot k)O(n⋅k).
  • Forgetting to check i >= k - 1 before appending nums[deque[0]] to the result array, emitting partial-window maxima for the first k - 1 elements.
  • Evicting from the front after reading the maximum instead of before (or right after pushing i), returning an expired element.

Failure Mode

Mitigation: Always store integer indices (or (timestamp, value) pairs for time-based windows) in the deque.

Failure Mode

Mitigation: For a 0-indexed window [i - k + 1, i], evict while deque[0] <= i - k (equivalently deque[0] < i - k + 1).

Failure Mode

Mitigation: Use a monotonic deque (hard-capped at k elements) instead of a lazy-deletion heap.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Sliding Window Maximum is used (and where to avoid it).

Sliding Window Maximum delivers the highest leverage at well-defined architectural boundaries. Use it for fixed-size (k) or time-bounded rolling max/min queries over streaming or array data where O(n)O(n)O(n) throughput is required.

ChoiceWhat it buysWhat it costs
Production Fit #1Fixed-size (`k`) or time-bounded rolling max/min queries over streaming or array data where $O(n)$ throughput is required.When you need arbitrary order statistics like rolling median, p95, or top-K elements (use two heaps, an order-statistic tree, or DDSketch/t-digest).
Production Fit #2Dynamic programming optimizations (e.g., Jump Game VI / constrained subsequence sum) where `dp[i]` depends on `max(dp[i-k ... i-1])`.Static offline arrays with arbitrary variable-length `[L, R]` range max queries (use a Sparse Table for $O(1)$ query after $O(n \log n)$ build, or a Segment Tree if point updates occur).
Production Fit #3Telemetry and alerting pipelines tracking trailing peak utilization without retaining full sorted window state.Out-of-order event streams with late arrivals where elements cannot be appended monotonically at the window tail (requires a Segment Tree or Windowed Pane aggregation).

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Sliding Window Maximum works under the hood & reference implementation.

Step-by-step trace on nums = [1, 3, -1, -3, 5, 3, 6, 7], k = 3

Maintain dq (indices) and out:

  • i=0 (1): dq=[0(1)]
  • i=1 (3): 3 >= 1 -> pop 0, push 1. dq=[1(3)]
  • i=2 (-1): -1 < 3 -> push 2. dq=[1(3), 2(-1)]. Window [0..2] full -> out=[3]
  • i=3 (-3): -3 < -1 -> push 3. dq=[1(3), 2(-1), 3(-3)]. out=[3, 3]
  • i=4 (5): dq[0]=1 <= 4-3 -> pop front 1. Then 5 pops 3(-3) and 2(-1) from back. dq=[4(5)]. out=[3, 3, 5]
  • i=5 (3): push 5. dq=[4(5), 5(3)]. out=[3, 3, 5, 5]
  • i=6 (6): 6 pops 5(3) and 4(5). dq=[6(6)]. out=[3, 3, 5, 5, 6]
  • i=7 (7): 7 pops 6(6). dq=[7(7)]. out=[3, 3, 5, 5, 6, 7].

Why the nested while loop is still O(n)O(n)O(n)

Although the algorithm places a while loop inside a for loop (while dq and nums[dq[-1]] <= nums[i]: dq.pop()), the total number of pop() operations across the entire run cannot exceed n, because each of the n indices is pushed onto dq exactly once. Combined with at most n popleft() operations, total deque work is bounded by 2n—giving strict O(n)O(n)O(n) worst-case time. Auxiliary space is bounded by O(k)O(k)O(k) because popleft() ensures dq never spans more than k indices.

Reference implementation (Python — Idempotent Bounded Retry with Exponential Backoff)

# Production-safe bounded retry with full jitter (Python)
import random, time
def execute_with_retry(fn, max_attempts: int = 4, base_delay_s: float = 0.05):
    for attempt in range(max_attempts):
        try:
            return fn()
        except TransientError:
            if attempt == max_attempts - 1:
                raise
            cap = base_delay_s * (2 ** attempt)
            time.sleep(random.uniform(0.0, cap))

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives & trade-offs for Sliding Window Maximum.

Evaluating Sliding Window Maximum against alternatives requires balancing latency, operational overhead, failure blast radius, and cost. Monotonic deque achieves strict O(n)O(n)O(n) time and bounded O(k)O(k)O(k) memory.

ChoiceWhat it buysWhat it costs
Monotonic Deque vs Max-Heap (Lazy Deletion)Monotonic deque achieves strict $O(n)$ time and bounded $O(k)$ memory.Max-heap is easier to adapt if arbitrary elements inside the window can be invalidated out of order, at the cost of $O(n \log n)$ worst-case heap growth.
Monotonic Deque vs Two-Pass Block Max (Prefix/Suffix)Monotonic deque works online/streaming in $O(k)$ space without knowing `n` upfront.Block max requires $O(n)$ offline array storage, though it vectorizes cleanly.
Popping `<=` vs `<` at the back of the dequePopping `nums[back] <= nums[i]` keeps the deque minimal and discards older duplicates.If a problem requires counting occurrences of the maximum or tie-breaking by earliest index, you must use strict `<` instead.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production architecture & hardening for Sliding Window Maximum.

Bugs that break correctness or complexity

  1. ArrayDeque / List Front-Pop Penalty: Using ArrayList.remove(0) in Java or list.pop(0) in Python shifts O(k)O(k)O(k) elements on every eviction, turning O(n)O(n)O(n) into O(n⋅k)O(n \cdot k)O(n⋅k).
  2. Time-Based Window Skew: In real-world streaming (e.g., max CPU in the last 60 seconds), the window size is measured in timestamps (ts[i] - ts[dq[0]] >= 60_000) rather than fixed index count k. Confusing count-based and time-based eviction breaks bursty streams.
  3. Integer Overflow in Comparator: In Java/C++, subtracting nums[dq.peekLast()] - nums[i] overflows on Integer.MIN_VALUE; always use direct < / <= comparisons.

Implementation & verification checklist

  • [ ] Store indices (or (ts, val)): Never store raw values alone in the deque.
  • [ ] Evict before or right after window check: Use dq[0] <= i - k for 0-indexed fixed windows of size k.
  • [ ] Use O(1)O(1)O(1) double-ended queue: collections.deque (Python) or ArrayDeque / primitive ring buffer (Java).
  • [ ] Verify <= vs <: Use <= to keep the deque minimal; switch to < only if duplicates/earliest-index ties matter.
  • [ ] Handle boundary inputs: Test n == 0, k == 1, k == n, strictly increasing, strictly decreasing, and all-equal arrays.
  • [ ] Emit only full windows: Append to result only when i >= k - 1.
