A foundational engineering concept

Sliding Window
Maximum Patterns.

Sliding Window Maximum computes the maximum element in every contiguous subarray of size k across a length-n sequence in optimal O(n)O(n)O(n) time and O(k)O(k)O(k) space. By maintaining a monotonically decreasing double-ended queue (deque) of array indices, each element is pushed and popped at most once, beating naive O(nk)O(nk)O(nk) scans and O(nlog⁡k)O(n \log k)O(nlogk) max-heaps.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Store indices—not values—in a monotonically decreasing deque, evicting out-of-window indices from the front and smaller values from the back to hit strict $O(n)$ time.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Real-time stream processors (Apache Flink, Kafka Streams), network anomaly detectors, and financial tick engines continuously compute rolling peak CPU, peak latency, or max bid price over trailing k-event or W-second windows. At 100,000 events/sec with k = 10,000, an O(n⋅k)O(n \cdot k)O(n⋅k) rescan executes 10910^9109 comparisons per second and collapses, whereas a monotonic deque processes each event in amortized O(1)O(1)O(1) time with predictable tail latency.

  • Store indices in the deque rather than raw values so you can check window expiration in O(1)O(1)O(1) via deque[0] <= i - k.
  • Maintain the monotonic decreasing invariant: before pushing index i, pop all back indices j where nums[j] <= nums[i] because j is both smaller and older, so it can never be the max of any future window.
  • Amortized O(1)O(1)O(1) per step: every index enters the back of the deque once and leaves either the front (expired) or back (dominated) at most once, yielding <= 2n deque operations total.
  • The front of the deque (nums[deque[0]]) is always the exact maximum of the current window once i >= k - 1.
  • A two-pass prefix/suffix block-max algorithm also achieves O(n)O(n)O(n) time with O(n)O(n)O(n) space and zero deque pointer chasing, ideal for SIMD/GPU batch arrays.

Good candidates

  • Fixed-size (k) or time-bounded rolling max/min queries over streaming or array data where O(n)O(n)O(n) throughput is required.
  • Dynamic programming optimizations (e.g., Jump Game VI / constrained subsequence sum) where dp[i] depends on max(dp[i-k ... i-1]).
  • Telemetry and alerting pipelines tracking trailing peak utilization without retaining full sorted window state.

Think twice

  • When you need arbitrary order statistics like rolling median, p95, or top-K elements (use two heaps, an order-statistic tree, or DDSketch/t-digest).
  • Static offline arrays with arbitrary variable-length [L, R] range max queries (use a Sparse Table for O(1)O(1)O(1) query after O(nlog⁡n)O(n \log n)O(nlogn) build, or a Segment Tree if point updates occur).
  • Out-of-order event streams with late arrivals where elements cannot be appended monotonically at the window tail (requires a Segment Tree or Windowed Pane aggregation).
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn observability service evaluates max(latency_ms) over a sliding window of the last 5,000 API requests per tenant to trigger circuit-breaker alerts.

Pruning dominated candidates with a monotonic deque

When a window slides right by one element nums[i], any older element nums[j] (j < i) inside the window that satisfies nums[j] <= nums[i] is permanently dominated: nums[i] is both larger (or equal) and will expire later than nums[j]. Therefore, nums[j] can never be the maximum of the current window or any future window. By popping all dominated elements from the back of a double-ended queue (deque) before appending i, the deque remains strictly decreasing in value and strictly increasing in index.

Step-by-step trace on nums = [1, 3, -1, -3, 5, 3, 6, 7], k = 3

Maintain dq (indices) and out:

  • i=0 (1): dq=[0(1)]
  • i=1 (3): 3 >= 1 -> pop 0, push 1. dq=[1(3)]
  • i=2 (-1): -1 < 3 -> push 2. dq=[1(3), 2(-1)]. Window [0..2] full -> out=[3]
  • i=3 (-3): -3 < -1 -> push 3. dq=[1(3), 2(-1), 3(-3)]. out=[3, 3]
  • i=4 (5): dq[0]=1 <= 4-3 -> pop front 1. Then 5 pops 3(-3) and 2(-1) from back. dq=[4(5)]. out=[3, 3, 5]
  • i=5 (3): push 5. dq=[4(5), 5(3)]. out=[3, 3, 5, 5]
  • i=6 (6): 6 pops 5(3) and 4(5). dq=[6(6)]. out=[3, 3, 5, 5, 6]
  • i=7 (7): 7 pops 6(6). dq=[7(7)]. out=[3, 3, 5, 5, 6, 7].

Each index enters the deque once and is removed at most once (either expired at the front or dominated at the back), guaranteeing O(n) total work.

Why the nested while loop is still O(n)O(n)O(n)

Although the algorithm places a while loop inside a for loop (while dq and nums[dq[-1]] <= nums[i]: dq.pop()), the total number of pop() operations across the entire run cannot exceed n, because each of the n indices is pushed onto dq exactly once. Combined with at most n popleft() operations, total deque work is bounded by 2n—giving strict O(n)O(n)O(n) worst-case time. Auxiliary space is bounded by O(k)O(k)O(k) because popleft() ensures dq never spans more than k indices.

Bugs that break correctness or complexity

  1. ArrayDeque / List Front-Pop Penalty: Using ArrayList.remove(0) in Java or list.pop(0) in Python shifts O(k)O(k)O(k) elements on every eviction, turning O(n)O(n)O(n) into O(n⋅k)O(n \cdot k)O(n⋅k).
  2. Time-Based Window Skew: In real-world streaming (e.g., max CPU in the last 60 seconds), the window size is measured in timestamps (ts[i] - ts[dq[0]] >= 60_000) rather than fixed index count k. Confusing count-based and time-based eviction breaks bursty streams.
  3. Integer Overflow in Comparator: In Java/C++, subtracting nums[dq.peekLast()] - nums[i] overflows on Integer.MIN_VALUE; always use direct < / <= comparisons.

Reference Python & Java idioms

In Python, use collections.deque() (doubly-linked block list, O(1)O(1)O(1) at both ends): if dq and dq[0] <= i - k: dq.popleft() followed by while dq and nums[dq[-1]] <= nums[i]: dq.pop(). In Java, use ArrayDeque (cache-friendly circular array, faster than LinkedList and zero per-node GC overhead): peekFirst(), pollFirst(), peekLast(), pollLast(), and offerLast(i). For high-frequency telemetry in Java/Go, replace boxed Integer objects with a primitive int[] ring buffer of capacity k + 1 to achieve zero heap allocations per event.

Implementation & verification checklist

  • Store indices (or (ts, val)): Never store raw values alone in the deque.
  • Evict before or right after window check: Use dq[0] <= i - k for 0-indexed fixed windows of size k.
  • Use O(1)O(1)O(1) double-ended queue: collections.deque (Python) or ArrayDeque / primitive ring buffer (Java).
  • Verify <= vs <: Use <= to keep the deque minimal; switch to < only if duplicates/earliest-index ties matter.
  • Handle boundary inputs: Test n == 0, k == 1, k == n, strictly increasing, strictly decreasing, and all-equal arrays.
  • Emit only full windows: Append to result only when i >= k - 1.
03 / Engineering trade-offs

Weighing architectural decisions

Monotonic Deque vs Max-Heap (Lazy Deletion)

Advantage: Monotonic deque achieves strict $O(n)$ time and bounded $O(k)$ memory.

Drawback: Max-heap is easier to adapt if arbitrary elements inside the window can be invalidated out of order, at the cost of $O(n \log n)$ worst-case heap growth.

Monotonic Deque vs Two-Pass Block Max (Prefix/Suffix)

Advantage: Monotonic deque works online/streaming in $O(k)$ space without knowing `n` upfront.

Drawback: Block max requires $O(n)$ offline array storage, though it vectorizes cleanly.

Popping `<=` vs `<` at the back of the deque

Advantage: Popping `nums[back] <= nums[i]` keeps the deque minimal and discards older duplicates.

Drawback: If a problem requires counting occurrences of the maximum or tie-breaking by earliest index, you must use strict `<` instead.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Storing Values Instead of Indices

Storing raw values in the deque makes it impossible to distinguish whether a duplicate value at `deque[0]` belongs to the expired element `nums[i - k]` or a newer occurrence inside the window.

What helps: Always store integer indices (or `(timestamp, value)` pairs for time-based windows) in the deque.

Off-by-One Window Eviction

Checking `deque[0] < i - k` instead of `<=` retains a `k+1`-element window, returning stale maxima from one step too far back.

What helps: For a 0-indexed window `[i - k + 1, i]`, evict while `deque[0] <= i - k` (equivalently `deque[0] < i - k + 1`).

Unbounded Heap Memory Leak

Using a max-heap with lazy deletion on a monotonically increasing stream (`[1, 2, 3, ...]`) or descending stream (`[n, n-1, ...]`) causes expired elements to stay buried in the heap, growing memory from $O(k)$ to $O(n)$.

What helps: Use a monotonic deque (hard-capped at `k` elements) instead of a lazy-deletion heap.

Edge-Case `k == 0` or `k > n` Panic

Indexing `deque[0]` on empty input (`n == 0`) or `k == 0` throws an index-out-of-bounds error.

What helps: Guard upfront: return `[]` if `n == 0` or `k == 0`, and clamp `k = min(k, n)` if partial windows are desired.

05 / Practical checklist

Avoid these mistakes

  • Using `list.pop(0)` in Python instead of `collections.deque.popleft()`, silently degrading the algorithm from $O(n)$ to $O(n \cdot k)$.
  • Forgetting to check `i >= k - 1` before appending `nums[deque[0]]` to the result array, emitting partial-window maxima for the first `k - 1` elements.
  • Evicting from the front *after* reading the maximum instead of *before* (or right after pushing `i`), returning an expired element.
  • Assuming a monotonic deque can compute the sliding window *sum* or *average* (use a simple running sum for $O(1)$ space instead).
  • Applying the algorithm blindly to out-of-order time-series events without first watermarking/sorting by event timestamp.
