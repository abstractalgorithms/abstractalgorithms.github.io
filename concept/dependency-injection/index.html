Dependency
Injection.

Dependency Injection (DI) flips object creation inside out: instead of a class instantiating its own collaborators with new, an external assembler or IoC container supplies those dependencies through constructors or parameters.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Prefer explicit constructor injection over field/setter injection so required dependencies are immutable, compiler-checked, and trivially mockable in unit tests.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Tightly coupled services that call new PostgresClient() or read global singletons directly cannot be unit-tested without spinning up real databases, and swapping implementations (e.g., Stripe to Adyen, or S3 to MinIO) forces invasive rewrites across business logic.

  • Inversion of Control (IoC) is the broader principle; Dependency Injection is the specific mechanism of passing collaborators in rather than pulling them from globals.
  • Constructor injection guarantees a valid, fully initialized object at creation time and supports final/readonly fields, preventing partial-state bugs.
  • Compile-time DI frameworks (Dagger 2, Micronaut, Google Wire) generate wiring code during compilation, catching missing bindings before deployment and eliminating reflection startup latency.
  • Runtime reflection DI containers (Spring ApplicationContext, Google Guice) offer rich lifecycle hooks (@PostConstruct, AOP proxies) at the cost of slower cold starts and runtime wiring errors.
  • The Composition Root—typically main() or the app bootstrapper—should be the only place that knows about concrete implementations and container configuration.

Good candidates

  • Business services that depend on I/O boundaries—databases, HTTP clients, message brokers, clocks, or feature-flag stores—that must be swapped for fakes in fast unit tests.
  • Multi-module Java (Spring Boot, Micronaut, Dagger 2), Go (Wire), or Python (FastAPI Depends) applications with distinct environment bindings (dev vs. prod).
  • Plugin or multi-tenant architectures where different implementations of an interface are selected at startup or per-request.

Think twice

  • Pure value objects, DTOs, domain entities, or utility functions with zero side effects (e.g., Money, OrderLine, StringUtils).
  • Tiny CLI scripts or Lambda handlers under ~300 lines where a 3-argument main() function wiring dependencies manually is clearer than a reflection-based DI container.
  • Ultra-low-latency hot paths (e.g., HFT matching engines) where runtime reflection proxies or dynamic AOP interceptors add unacceptable allocation or dispatch overhead.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn Indian e-commerce platform migrates UPI/card processing from Razorpay to PayU for 20% of traffic while keeping deterministic unit tests.

The idea

Dependency Injection (DI) separates object graph construction from business behavior. Instead of a component reaching out to construct or look up its own collaborators (new HttpClient(), Config.getInstance()), an external Composition Root instantiates the concrete implementations and passes them in—ideally via constructor parameters typed to interfaces or abstract ports. This simple inversion decouples high-level policy from low-level I/O, makes every dependency explicit in the type signature, and lets tests substitute fast in-memory fakes without bytecode-mocking frameworks.

Concrete walkthrough

Trace an HTTP request in a Spring Boot / Java service using constructor injection:

  1. Startup (Composition Root): Spring scans @Configuration classes and builds a Directed Acyclic Graph (DAG) of beans. It instantiates HikariDataSource -> JdbcOrderRepository(dataSource) -> OrderService(orderRepo, Clock.systemUTC()) -> OrderController(orderService).
  2. Immutability: OrderService stores private final OrderRepository repo; and private final Clock clock;. Neither can ever be null after construction.
  3. Unit Test (No Container): A JUnit 5 test runs var svc = new OrderService(new InMemoryOrderRepo(), Clock.fixed(...)) in <2ms without starting Spring.
  4. Production Swap: Switching from JdbcOrderRepository to DynamoOrderRepository requires changing one @Bean / @Profile binding in the Composition Root—zero lines change in OrderService.

The Composition Root wires concrete adapters into OrderService at startup, while unit tests inject in-memory fakes directly.

Lifecycle scopes and captive dependencies

DI containers manage object lifetimes via scopes:

  • Singleton (1 instance per container): Thread-safe stateless services, HTTP connection pools, ObjectMapper.
  • Request / Scoped (1 instance per HTTP request or gRPC call): Per-request DB transactions, tenant/auth context.
  • Transient / Prototype (new instance per injection): Stateful builders or non-thread-safe buffers.

A captive dependency occurs whenever a longer-lived scope (Singleton) captures a shorter-lived scope (Request) in its constructor. Because the singleton's constructor runs only once at startup, it holds onto the first request's object forever. Always bridge shorter scopes using a Provider / factory or pass request-scoped data as explicit method arguments.

Failure modes

  • Startup Slowdown from Classpath Scanning: Broad @ComponentScan over thousands of classes in Spring Boot can add 3–8 seconds to cold starts (critical in AWS Lambda / Cloud Run). Use explicit @Import configurations or compile-time DI (Micronaut/Dagger).
  • Ambiguous Bean Resolution: Having two implementations of CacheClient (RedisCache, CaffeineCache) without @Primary or @Qualifier crashes startup with NoUniqueBeanDefinitionException.
  • Hidden Circular Graphs: Lazy proxies (@Lazy) mask circular dependencies at startup only to cause stack overflows or subtle initialization-order bugs under load.
  • Async Context Loss: Request-scoped ThreadLocal DI proxies fail when work is offloaded to an ExecutorService or Python asyncio.create_task unless context is explicitly propagated.

Compile-time vs. runtime DI in production

In JVM microservices, Spring Boot (runtime reflection + CGLIB proxies) dominates enterprise backends where rich ecosystem integrations (Spring Security, Actuator, Kafka) outweigh a 2-second startup. For Android apps, serverless functions, or GraalVM native images, Dagger 2 or Micronaut shift dependency resolution to javac annotation processing—eliminating reflection, shrinking memory by 30–50%, and turning missing-bean errors into compiler errors. In Go, Google Wire generates plain InitializeApp() functions at build time, preserving Go's preference for zero runtime magic.

Practical checklist

  • Use constructor injection for 100% of required collaborators; mark fields final/readonly.
  • Keep the Composition Root (main, @Configuration, wire.go) isolated from domain packages.
  • Inject Clock, Random/UUID generators, and Environment wrappers instead of calling static globals.
  • Audit any class with >5 constructor parameters for Single Responsibility violations.
  • Never inject a Request-scoped bean directly into a Singleton without a Provider or method-parameter boundary.
03 / Engineering trade-offs

Weighing architectural decisions

Compile-Time Wiring (Dagger/Wire) vs. Runtime Reflection (Spring/Guice)

Advantage: Compile-time DI fails the build on missing/circular bindings and starts in <50ms with zero reflection overhead.

Drawback: Requires code-generation annotation processors and offers less dynamic runtime rebinding or AOP proxy magic.

Manual Poor-Man's DI vs. IoC Container

Advantage: Zero framework lock-in, explicit stack traces, and crystal-clear object graphs in `main()`.

Drawback: Once an application exceeds ~40–50 wired services, boilerplate factory code and lifecycle management (shutdown hooks, scopes) become tedious.

Constructor Injection vs. Field (`@Autowired`) Injection

Advantage: Constructor injection enforces immutability, makes hidden dependencies obvious (bloated parameter lists signal SRP violations), and works without a container in tests.

Drawback: Slightly more verbose in Java without Lombok `@RequiredArgsConstructor` or Java `record`/primary constructors.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Captive Dependency (Scope Mismatch)

A singleton bean holds a reference to a request-scoped or prototype bean (e.g., an HTTP auth context), freezing stale user state across all future requests.

What helps: Never inject shorter-lived scopes directly into singletons; inject a `Provider<T>` / `ObjectFactory<T>` or pass request context as a method parameter.

Circular Dependency Deadlock

`OrderService` requires `InventoryService` in its constructor while `InventoryService` requires `OrderService`, causing `BeanCurrentlyInCreationException` at startup.

What helps: Extract the shared logic into a third service, introduce an async domain event (`OrderPlacedEvent`), or break the cycle by rethinking module boundaries.

Service Locator Anti-Pattern Disguised as DI

Injecting `ApplicationContext` or a global `Container.get(Foo.class)` into business classes hides true dependencies and breaks static analysis.

What helps: Ban `ApplicationContext` injection outside the Composition Root; inject only the specific interfaces each class actually calls.

Constructor Over-Injection (God Class)

A service accumulates 9–12 constructor parameters because it orchestrates too many unrelated workflows.

What helps: Treat >5 constructor dependencies as a design smell; split the class into focused domain facades or cohesive use-case handlers.

05 / Practical checklist

Avoid these mistakes

  • Using field injection (`@Autowired private Repo repo;`), which prevents `final` fields and forces reflection hacks in unit tests.
  • Injecting `Clock.systemUTC()` implicitly inside methods (`Instant.now()`) instead of injecting `java.time.Clock`, making time-dependent tests flaky.
  • Mocking the DI container itself in unit tests instead of instantiating the class directly with `new MyService(fakeRepo)`.
  • Creating a `FooInterface` for every single class even when only one concrete implementation will ever exist (premature interface proliferation).
  • Leaking container annotations (`@Component`, `@Inject`) into pure domain models that should remain framework-agnostic.
