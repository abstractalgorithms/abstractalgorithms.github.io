Unit Testing
Pyramid.

The testing pyramid structures automated suites with a broad base of fast, isolated unit tests (<10 ms), a smaller middle layer of integration/contract tests, and a thin top layer of end-to-end UI/flow checks.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Push business logic verification down to deterministic in-memory unit tests so CI catches regressions in seconds, reserving Testcontainers and Playwright for wiring, SQL queries, and critical user journeys.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Teams that invert the pyramid into an 'ice-cream cone' (mostly manual QA and Selenium/Playwright E2E tests) suffer 45-minute CI queues, 10%+ flaky-test retry rates, and slow feedback loops that discourage refactoring.

  • Target roughly 70% unit tests (<10 ms each, zero network/disk I/O), 20% integration/contract tests (Testcontainers for Postgres/Redis/Kafka, WireMock/Pact for HTTP contracts), and 10% E2E tests (Playwright/Cypress on core revenue paths).
  • Use fakes (in-memory repositories, sqlite3 :memory: only when SQL dialects match, or FakeClock) over brittle mocks (verify(repo, times(1)).save(...)) that couple tests to implementation details.
  • Google's Test Size taxonomy (Small / Medium / Large) enforces strict resource limits: Small tests cannot touch network, filesystem, or sleep; Medium tests allow localhost Testcontainers.
  • Line coverage (e.g., 85%) measures execution, not assertion quality—mutation testing (PITest for Java, Stryker for JS/TS, mutmut for Python) injects faults (> to >=) to prove tests actually catch bugs.
  • Flaky E2E tests (<99% pass rate) destroy developer trust; quarantine flaky tests automatically and fix root causes (async race conditions, shared DB state, wall-clock time.Now()).

Good candidates

  • Domain logic, pricing/tax calculators, state machines, parsers, and edge-case validation where inputs and outputs are pure or easily faked.
  • CI/CD pipelines targeting <5 minute PR feedback for services with 500+ commits/week.
  • Refactoring legacy modules where fast unit + characterization tests lock down behavior before changing internals.

Think twice

  • Glue code that is 95% SQL queries, Kafka consumer config, or IAM policies; mocking the database driver tests your mock, not your SQL—use Testcontainers integration tests instead.
  • Visual layout, CSS responsiveness, or browser-specific OAuth redirects that only real browser engines (Playwright) can verify.
  • Throwaway prototypes or one-off migration scripts where the cost of maintaining mocks exceeds the risk of manual verification.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA payments service had 320 Selenium E2E tests taking 52 minutes in CI with a 14% flake rate, and only 40 unit tests.

The idea

Automated tests trade fidelity (how closely the test matches production) against speed, determinism, and isolation. The testing pyramid (popularized by Mike Cohn and operationalized at Google as Small/Medium/Large tests) organizes your suite so you get maximum bug detection per second of CI time.

  • Base (Unit / Small, ~70%): Pure in-memory execution (<10 ms/test). Zero network, disk, or Docker. Tests business rules, edge cases, and state transitions.
  • Middle (Integration / Contract, ~20%): Real local dependencies via Testcontainers (Postgres, Redis, Kafka) or schema contracts (Pact, OpenAPI). Verifies SQL, serialization, and HTTP wiring.
  • Apex (E2E, ~10%): Full-stack browser/API journeys (Playwright) verifying that auth, frontend, backend, and database actually talk to each other in a staging environment.

Concrete walkthrough

Design the test suite for an OrderRefundService that calculates prorated refunds, persists a ledger row in PostgreSQL, and publishes an OrderRefunded event to Kafka:

  1. Unit Layer (25 tests, ~40 ms total): Extract RefundCalculator.compute(order, items, now) as a pure function. Test partial item quantities, tax rounding, expired 30-day windows (using an injected Clock), and coupon prorating with zero mocks or DB.
  2. Integration Layer (4 tests, ~6 s total): Spin up postgres:16 and redpanda via Testcontainers (reused across the test class). Verify the INSERT INTO refunds ... ON CONFLICT DO NOTHING idempotency constraint and confirm the serialized Avro/JSON event lands on the Kafka topic.
  3. E2E Layer (1 test, ~15 s): A Playwright test logs into the support portal, clicks "Issue Refund" on a seeded order, and asserts the UI status flips to Refunded.

Fast unit tests catch 70%+ of defects in seconds; heavier Testcontainers and Playwright layers verify wiring and user-visible behavior without stalling PRs.

Test doubles: Fakes vs. Stubs vs. Mocks

Most unit-test fragility comes from confusing test doubles:

  • Fake: A working, lightweight implementation of an interface (e.g., InMemoryOrderRepo backed by a HashMap, or a FakeClock). Fakes preserve real behavioral contracts and survive refactoring.
  • Stub: Returns canned responses (when(fxClient.rate("USD", "INR")).thenReturn(84.0)). Good for isolating external HTTP/gRPC dependencies.
  • Mock: Asserts on how a dependency was called (verify(emailSender, times(1)).send(...)). Use sparingly at true external side-effect boundaries (sending an email, charging a card)—never for internal domain collaborators.

Failure modes

Two anti-patterns ruin test suites in opposite directions:

  • The Ice-Cream Cone: Almost all tests are slow E2E browser scripts. When a rounding bug breaks, it takes 35 minutes to fail, and another 15 minutes to figure out which microservice caused it.
  • The Over-Mocked Unit Suite: 100% coverage achieved by mocking every repository and mapper. All unit tests stay green even when a SQL migration renames a column or a JSON field changes from userId to user_id.

Functional core, imperative shell

The cleanest way to keep the pyramid healthy is the Functional Core, Imperative Shell architecture:

  • Keep I/O (HTTP handlers, DB transactions, Kafka producers) in a thin imperative shell covered by Testcontainers integration tests.
  • Push all conditional branching, state transitions, and calculations into a side-effect-free functional core that takes data in and returns decisions/events out. That core needs zero mocks to unit test exhaustively—including property-based tests (Hypothesis, proptest, fast-check) that throw thousands of randomized inputs at invariants.

Practical checklist

  • Separate fast unit tests from container/E2E tests via tags/markers (@Tag("integration"), pytest -m "not integration") so developers run unit tests locally in <5 seconds.
  • Replace Thread.sleep and time.Now() with injected clocks and polling assertions (Awaitility, Playwright expect(locator).toBeVisible()).
  • Test SQL queries and migrations against the actual database engine in Testcontainers, not an incompatible in-memory substitute.
  • Shuffle test execution order in CI (pytest-randomly) to catch hidden shared state immediately.
  • Track flake rate per test; quarantine and fix any test that fails >1% on unchanged commits.
03 / Engineering trade-offs

Weighing architectural decisions

Mockist (London School) vs. Classicist (Detroit School)

Advantage: Mocking every collaborator isolates a single class so failures pinpoint the exact file.

Drawback: Over-mocking couples tests to private method calls, breaking tests on harmless refactorings while missing integration bugs.

In-Memory Fakes vs. Real Containers (Testcontainers)

Advantage: In-memory fakes run in microseconds with zero Docker daemon overhead.

Drawback: H2/SQLite behave differently from PostgreSQL (`JSONB`, `FOR UPDATE SKIP LOCKED`, locking), giving false confidence.

Code Coverage Gates vs. Mutation Testing

Advantage: Line/branch coverage (JaCoCo, `coverage.py`) runs in seconds on every PR.

Drawback: Coverage can be gamed with assertion-free tests; mutation testing catches weak assertions but is 10–50x slower (best run nightly).

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Tautological Mock Tests

A test stubs `paymentGateway.charge()` to return `Success`, calls the wrapper, and asserts `result == Success`—testing only the mock setup.

What helps: Mock only at true architectural boundaries (external HTTP/clock/randomness) and assert on state changes or side effects rather than internal call counts.

Shared Mutable State & Order-Dependent Tests

Tests share a singleton database or global cache; `test_b` passes only when `test_a` runs first.

What helps: Run test suites in randomized order (`pytest-randomly`, JUnit random order) and isolate each test with transaction rollbacks or unique tenant IDs.

Wall-Clock & Sleep Flakiness

Tests call `time.sleep(0.5)` or `datetime.now()` around midnight/DST boundaries, causing intermittent CI failures under CPU contention.

What helps: Inject a deterministic `Clock` interface (`java.time.Clock.fixed(...)`, `freezegun`) and replace arbitrary sleeps with polling assertions (`Awaitility`, Playwright auto-wait).

Slow CI Causing Batched/Skipped Runs

Integration/E2E bloat pushes PR checks past 25 minutes, prompting developers to merge without waiting or disable checks.

What helps: Split fast Small unit tests (<2 min) as blocking PR gates and run heavy cross-service E2E suites asynchronously or on merge queues.

05 / Practical checklist

Avoid these mistakes

  • Enforcing a blind 100% line coverage target, which forces developers to write noisy tests for getters, constructors, and logging.
  • Using `sqlite:///:memory:` to test PostgreSQL-specific queries (`ON CONFLICT`, array operators, CTEs) instead of a real Postgres container.
  • Writing `verify(mock, times(1))` assertions on internal helper collaborations, making every refactor break dozens of unrelated tests.
  • Putting `Thread.sleep(2000)` in async tests instead of deterministic condition polling or virtual time.
  • Testing private methods directly instead of exercising them through the module's public API.
