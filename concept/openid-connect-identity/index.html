THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Use Authorization Code Flow with PKCE, validate the ID Token's signature via JWKS plus `iss`, `aud`, `exp`, and `nonce`, and never treat an OAuth Access Token as proof of user identity.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

OAuth 2.0 is strictly an authorization protocol—it tells a resource server what a token can access, not who the user is or how they authenticated. Before OpenID Connect (OIDC), every provider (Facebook, GitHub, Google) invented custom /me endpoints and ad-hoc token formats, creating widespread account-takeover bugs. OIDC standardizes authentication with a signed JSON Web Token (id_token), discovery metadata, and uniform claims.

  • OIDC extends OAuth 2.0 by adding the openid scope, which instructs the Authorization Server to return a signed JWT id_token alongside the access_token.
  • Always use the Authorization Code Flow with PKCE (RFC 7636)—even for confidential server-side clients—and never use the deprecated Implicit Flow (response_type=id_token).
  • Clients must validate the id_token signature using the IdP's public keys from jwks_uri (discovered via /.well-known/openid-configuration) and verify iss, aud, exp, and nonce.
  • The sub (subject) claim—combined with iss—is the only immutable unique user identifier; never key user accounts solely on mutable email claims.
  • For SPAs, the Backend-for-Frontend (BFF) pattern keeps refresh tokens and access tokens in HTTP-only, SameSite cookies on the server rather than exposing them in browser localStorage.

Good candidates

  • Implementing Single Sign-On (SSO) across web, mobile, and SaaS apps using Identity Providers (IdPs) like Okta, Auth0, Keycloak, or Microsoft Entra ID.
  • Delegating user authentication, MFA, and passkey/WebAuthn handling to a hardened IdP instead of storing password hashes locally.
  • Federating enterprise B2B logins where each customer tenant brings their own IdP via standard OIDC discovery.

Think twice

  • Machine-to-machine (M2M) microservice authentication with no human user—use OAuth 2.0 client_credentials grant or mTLS instead.
  • Legacy enterprise integrations that strictly mandate XML-based SAML 2.0 assertions without an OIDC broker.
  • High-throughput internal service-to-service authorization where opaque or stateless OAuth access tokens (without ID tokens) are sufficient.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA B2B analytics platform needed to onboard 40+ enterprise customers, each requiring login through their corporate Okta or Entra ID tenant with MFA enforced.

The idea

OpenID Connect (OIDC) 1.0 is an identity layer built directly on top of OAuth 2.0 (RFC 6749). While OAuth 2.0 delegates access to APIs via opaque or JWT access tokens, OIDC standardizes authentication by introducing a third token: the ID Token.

An ID Token is always a signed JSON Web Token (JWT) containing standardized claims about the authentication event itself—who authenticated (sub), which IdP vouched for them (iss), which client app the token was minted for (aud), when it expires (exp), and a replay-protection nonce.

Concrete walkthrough

Walk through a modern Authorization Code Flow with PKCE for a web app using a Backend-for-Frontend (BFF):

  1. Login Initiation: The BFF generates a 256-bit code_verifier, hashes it (S256) into code_challenge, and generates random state and nonce values stored in an HttpOnly session cookie. It redirects (302) the browser to the IdP's authorization_endpoint with scope=openid profile email.
  2. User Authentication: The user completes password + WebAuthn MFA on the IdP's hosted domain.
  3. Authorization Code Callback: The IdP redirects back to /callback?code=abc123&state=.... The BFF verifies state matches the cookie.
  4. Back-Channel Token Exchange: The BFF sends a server-to-server POST /token with code, client_secret, and code_verifier. The IdP returns id_token, access_token, and refresh_token.
  5. Cryptographic Verification: The BFF fetches the IdP's public key matching the JWT kid from jwks_uri, verifies the RS256/ES256 signature, and checks iss, aud, exp (with <=60s clock skew), and nonce.

Authorization Code + PKCE keeps access and refresh tokens off the browser while the BFF cryptographically verifies the ID Token against the IdP's JWKS.

ID Token vs. Access Token

Conflating these two tokens is the #1 OIDC architectural mistake:

  • ID Token: Intended strictly for the client application (Relying Party). Its aud is the client_id. It proves authentication occurred and carries identity claims (sub, auth_time, amr). Never forward it to downstream APIs as a bearer credential.
  • Access Token: Intended for Resource Servers (APIs). Its aud is the API identifier (e.g., https://api.acme.com). It may be an opaque string or a JWT (RFC 9068) carrying scope and permissions.

Failure modes

  1. Cross-Client Token Replay: Accepting an id_token signed by Google without verifying aud == YOUR_CLIENT_ID lets an attacker take a valid token from another app and log into yours.
  2. Clock Skew Rejections: Distributed containers with 10–20 seconds of NTP drift can fail iat or nbf checks. Configure a bounded leeway (30–60 seconds), never unlimited.
  3. Broken Logout (RP-Initiated Logout): Clearing only the local BFF cookie leaves the IdP's SSO session alive, silently logging the user back in on the next click. Redirect to end_session_endpoint with id_token_hint when full sign-out is required.

Handling JWKS key rotation cleanly

IdPs rotate asymmetric signing keys (RS256 or ES256) every 30–90 days. A resilient verifier:

  • Reads the JWT header's kid (Key ID) and looks it up in an in-memory JWKS cache (TTL 1–6 hours).
  • If kid is missing from cache, performs one rate-limited refresh against jwks_uri (with a 30-second cooldown to prevent DoS amplification from forged kid headers).
  • Pins allowed algorithms (["RS256", "ES256"]) explicitly in the verifier config so alg: none or HS256 key-confusion payloads are rejected before signature math runs.

Practical checklist

  • Use Auth Code + PKCE (S256) for every interactive login; disable Implicit and Password (ROPC) grants on the IdP.
  • Verify all 5 core claims: iss (exact match), aud (contains your client_id), exp (> now - 60s), nonce (matches session), and cryptographic signature.
  • Key users on (iss, sub): Never use email as a primary key.
  • Keep tokens server-side: Prefer a BFF with HttpOnly; Secure; SameSite=Lax session cookies for browser apps.
  • Implement kid-miss JWKS refresh with a rate-limit guard so key rotations never cause login outages.
03 / Engineering trade-offs

Weighing architectural decisions

ID Token Claims vs. `/userinfo` Endpoint

Advantage: Embedding `email`, `name`, and `roles` in the `id_token` avoids an extra network round-trip on login.

Drawback: Bloats JWT header/cookie size (risking 4KB/8KB HTTP header limits) and freezes claims until the next login.

Stateless JWT Validation vs. Token Introspection

Advantage: Local JWKS signature verification takes <1ms with zero network calls to the IdP.

Drawback: Cannot immediately revoke a compromised `id_token` or `access_token` before `exp` unless paired with short TTLs (5–15 min) or a revocation list.

SPA Direct PKCE vs. BFF Pattern

Advantage: Direct browser PKCE requires no server-side session store.

Drawback: Exposes tokens to XSS in browser memory/storage; BFF keeps all tokens server-side behind `HttpOnly` cookies.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Missing `aud` or `iss` Validation (Token Confusion)

An application verifies the JWT signature against Google's JWKS but forgets to check `aud == my_client_id`, allowing an attacker to replay an `id_token` issued for a different app.

What helps: Use a battle-tested OIDC library that strictly asserts `iss`, `aud`, `exp`, `alg` (rejecting `alg: none` and `HS256` downgrade), and `nonce`.

Keying Accounts on `email` Instead of `(iss, sub)`

Users who change their corporate email lose access or, worse, an attacker registers a recycled email on a social IdP and hijacks the account.

What helps: Persist `(iss, sub)` as the canonical foreign key and treat `email` as a mutable display attribute (checking `email_verified: true`).

JWKS Cache Miss Storm on Key Rotation

When an IdP rotates its signing key (`kid`), clients with a 24-hour hardcoded JWKS cache reject all logins until the cache expires.

What helps: Cache JWKS for 1–6 hours, and on an unknown `kid`, trigger a rate-limited background refresh (e.g., max 1 fetch per 30s).

CSRF / Login-Mixup Attack

Omitting `state` or `nonce` allows an attacker to trick a victim's browser into binding the attacker's OIDC session to the victim's account.

What helps: Generate a cryptographically random `state` (bound to the user's pre-login cookie) and `nonce` (verified inside the returned `id_token`).

05 / Practical checklist

Avoid these mistakes

  • Sending the `id_token` as an `Authorization: Bearer` header to backend resource APIs instead of using the `access_token`.
  • Accepting `alg: none` or blindly trusting the `alg` header inside an unverified JWT (allowing `RS256` -> `HS256` public-key confusion).
  • Storing refresh tokens in `localStorage` or `sessionStorage`, making them trivial to exfiltrate via any third-party JS XSS.
  • Forgetting to validate `at_hash` when receiving both `id_token` and `access_token` from the authorization endpoint.
  • Hardcoding IdP endpoints instead of resolving them dynamically from `/.well-known/openid-configuration`.
