STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is OpenID Connect (OIDC).

OpenID Connect (OIDC) 1.0 is an identity layer built directly on top of OAuth 2.0. While OAuth 2.0 delegates authorization (what APIs an access_token can call), OIDC standardizes authentication (who the user is) by adding the openid scope and returning a cryptographically signed JWT id_token.

The id_token is intended strictly for the client application (Relying Party) and carries (iss, sub) as the immutable user identity key, alongside aud, exp, nonce, and auth_time.

Auth Code + PKCE Flow

OIDC Authorization Code Flow with PKCE (BFF)

PKCE binds the authorization code to the BFF's secret verifier, and tokens stay server-side behind an HttpOnly cookie.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need OIDC (and why Access Tokens are not Identity).

Using a raw OAuth 2.0 access_token for login creates severe account-takeover vulnerabilities: access tokens may be opaque, lack aud checks for your client, or be replayed from another application. OIDC fixes this with a uniform signed id_token, standard /.well-known/openid-configuration discovery, and nonce/state CSRF bindings.

Key Accounts on `(iss, sub)`, Never `email`

Email addresses change or get recycled; (iss, sub) is the only immutable primary key for federated users.

Always Validate `aud`, `iss`, `alg`, and `nonce`

Verifying only the signature against Google's JWKS allows an attacker to replay an id_token issued for a different app (aud mismatch).

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where OIDC applies (and where OAuth/mTLS fit better).

Use OIDC for human Single Sign-On across web, mobile, and B2B SaaS; use client_credentials or mTLS for machine-to-machine calls.

ChoiceWhat it buysWhat it costs
Good Candidate: Web/Mobile SSO & Enterprise FederationDelegates passwords, MFA, and passkeys to hardened IdPs (Okta, Entra ID, Auth0) via standard discovery.Requires JWKS caching with rate-limited `kid` rotation refresh and strict NTP clock-skew tolerances (<= 60s).
Avoid: Machine-to-Machine (M2M) Microservice AuthUse OAuth 2.0 `client_credentials` or SPIFFE/mTLS when no human user is authenticating.OIDC interactive redirects and `id_token`s do not apply to daemon-to-daemon traffic.
Avoid: Legacy SAML-Only Enterprise MandatesUse an OIDC-to-SAML identity broker (Keycloak/Auth0) if a customer mandates XML SAML 2.0 assertions.Maintaining raw SAML XML parsing inside application services expands XXE/signature-wrapping attack surface.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How ID Tokens and JWKS Key Rotation are verified.

Discover jwks_uri from /.well-known/openid-configuration, cache keys for 1–6 hours, trigger a single rate-limited refresh on an unknown kid, reject alg: none or HS256 downgrade attacks, and verify iss, aud, exp, and nonce.

# OIDC ID Token claim + signature verification pattern (PyJWT + PyJWKClient)
import jwt
from jwt import PyJWKClient

jwks_client = PyJWKClient("https://idp.example.com/.well-known/jwks.json", cache_keys=True, lifespan=3600)

def verify_id_token(id_token: str, expected_client_id: str, expected_nonce: str) -> dict:
    signing_key = jwks_client.get_signing_key_from_jwt(id_token)
    claims = jwt.decode(
        id_token,
        signing_key.key,
        algorithms=["RS256", "ES256"],  # Reject alg=none and HS256
        audience=expected_client_id,
        issuer="https://idp.example.com",
        leeway=30,
    )
    if claims.get("nonce") != expected_nonce:
        raise ValueError("OIDC nonce mismatch")
    return claims

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: BFF Pattern vs. Direct SPA PKCE & JWT vs. Introspection.

Token storage and validation choices trade browser XSS exposure and revocation immediacy against stateless latency.

ChoiceWhat it buysWhat it costs
Backend-for-Frontend (BFF) + `HttpOnly` CookieKeeps `id_token`, `access_token`, and `refresh_token` completely out of browser JS/localStorage.Requires a lightweight server-side session store (Redis) and CSRF protection on cookie endpoints.
Direct Browser SPA PKCERequires zero server-side session state.Any third-party JS XSS can exfiltrate tokens from browser memory or storage.
ID Token Claims vs. `/userinfo` EndpointEmbedding core claims avoids an extra network RTT on login.Bloats JWT size past 4–8 KB header limits and freezes claims until the next login.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Multi-Tenant BFF with JWKS Caching.

An enterprise SaaS BFF caches each tenant IdP's JWKS in memory (L1) and Redis (L2) keyed by (issuer, kid) so key rotations never cause a thundering-herd storm against the IdP, while issuing short-lived HttpOnly; SameSite=Lax session cookies to the browser.

JWKS & Session Topology

L1/L2 JWKS Key Cache + BFF Session Architecture

1.1. Cookie Boundary: Browser holds only an opaque session ID cookie; OAuth tokens stay in Redis.

2.2. JWKS Cache: BFF verifies RS256/ES256 signatures in <1 ms from L1 cache, refreshing once per 30s on unknown kid.

3.3. Immutable Key: User records bind to (iss, sub) rather than mutable email claims.

Zero tokens touch browser storage, and JWKS rotation is absorbed without IdP rate-limit storms.
