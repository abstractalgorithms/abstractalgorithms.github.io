A foundational engineering concept

CAP Theorem
& PACELC.

CAP proves a distributed data store cannot simultaneously guarantee linearizability (C) and 100% availability (A) during a network partition (P); PACELC extends this to normal operation, forcing a choice between latency (L) and consistency (C) even when no partition exists.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Because network partitions are inevitable, the real-world design choice is not 'CP vs AP'—it is whether you pay the cross-region latency tax on every write during healthy operation (PC/EC) or accept stale reads and conflict resolution (PA/EL).

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Treating 'CAP' as a binary label leads engineers to pick eventual consistency when they actually need linearizable uniqueness (like inventory or bank balances), or to deploy synchronous multi-region Raft and wonder why every write takes 85ms. Understanding PACELC and the consistency hierarchy lets you match exact protocol guarantees to each business invariant.

  • CAP's 'C' specifically means Linearizability (every read sees the latest completed write in real-time order), and 'A' means every non-failing node must respond—a strict definition violated if a minority partition refuses writes.
  • PACELC (Daniel Abadi, 2012) captures the missing half: if P (partition), choose A or C; else (E) (normal operation), choose L (latency) or C (consistency).
  • Quorum math (W+R>NW + R > NW+R>N) provides overlap in a 3-node replica set (N=3,W=2,R=2N=3, W=2, R=2N=3,W=2,R=2), but does not automatically guarantee linearizability without read-repair or leader-based ordering (e.g., Raft).
  • Consistency models form a strict spectrum from strongest to weakest: Linearizable -> Sequential -> Causal (preserves happens-before, e.g., comments after posts) -> Read-Your-Writes -> Eventual.
  • Jepsen testing repeatedly proved that misconfigured 'CP' databases (e.g., clock-skew bugs, dirty reads, unpinned leaders) silently lose linearizability under asymmetric partitions.

Good candidates

  • Choose CP / PC-EC (Raft, Paxos, Spanner, etcd, CockroachDB) for distributed locks, leader election, financial ledgers, and unique-constraint enforcement where stale reads or split-brain writes corrupt data.
  • Choose AP / PA-EL (Dynamo-style W=1, R=1, Cassandra with LOCAL_ONE, CRDTs) for shopping carts, user activity feeds, metrics, and edge caches where sub-10ms local writes and partition survival outweigh immediate global consistency.
  • Use tunable per-operation consistency (e.g., Cassandra LOCAL_QUORUM for profile updates vs LOCAL_ONE for view counters) to avoid paying global coordination costs uniformly.

Think twice

  • Avoid strong global consensus (PC/EC across continents) on high-throughput user-facing writes if your p99 latency budget is <30ms—physics sets cross-ocean RTT at ~75–150ms.
  • Avoid AP eventual consistency for strict invariants (account balances, seat reservations, distributed mutexes) where concurrent writes cannot be safely merged post-hoc.
  • Avoid applying CAP to single-node databases or single-AZ synchronous primary-standby setups without understanding that a single-node DB is neither partition-tolerant nor highly available.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA global fintech ledger deploys across US-East, EU-West, and AP-South (~80ms inter-region RTT). CockroachDB uses Raft consensus requiring a majority quorum (2 of 3 regions) per write; DynamoDB Global Tables accepts writes locally in <10ms and replicates asynchronously.

The idea

Eric Brewer's CAP Theorem (formalized by Gilbert & Lynch, 2002) proves that when a network partition (P) splits a distributed store into disconnected groups of nodes, the system must choose between Consistency (linearizability: every read returns the most recent write or an error) and Availability (every non-failing node returns a non-error response, even if stale). Because partitions are unavoidable in real networks, PACELC (Abadi, 2012) completes the picture: during a partition (P), choose A or C; else (E, normal operation), choose between Latency (L) and Consistency (C).

Concrete walkthrough

Consider a 3-node key-value cluster (N1 in US-East, N2 in US-Central, N3 in US-West) holding balance = $100:

  1. Healthy Operation (Else branch of PACELC):
    • PC/EC (e.g., etcd / CockroachDB Raft): N1 (leader) receives SET balance = 80‘,replicatesto‘N2‘(25msRTT),reachesquorum(2/3),andacknowledges.Everysubsequentreadsees‘80, replicates to N2 (25ms RTT), reaches quorum (2/3), and acknowledges. Every subsequent read sees 80‘,replicatesto‘N2‘(25msRTT),reachesquorum(2/3),andacknowledges.Everysubsequentreadsees‘80, paying a +25ms latency cost.
    • PA/EL (e.g., Cassandra LOCAL_ONE): N1 writes locally in 1ms and acknowledges immediately, replicating to N2/N3 asynchronously.
  2. During a Partition (N1 isolated from N2, N3):
    • CP: N1 cannot reach a majority quorum (1 < 2), so it refuses writes (sacrificing A) while N2, N3 elect a new leader and remain consistent.
    • AP: N1 continues accepting SET balance = 60‘while‘N2‘accepts‘SETbalance=60 while N2 accepts SET balance =60‘while‘N2‘accepts‘SETbalance=50, creating divergent state that must be reconciled once the partition heals.

CAP and PACELC in action: healthy operation trades replication RTT for consistency (EC vs EL), while a partition forces minority nodes to either reject writes (CP) or diverge (AP).

The consistency spectrum beyond binary CAP

Real systems rarely sit at only two extremes; they form a hierarchy of guarantees:

  1. Linearizability (Strict/External Consistency): Single-copy illusion ordered by real-time wall clock (etcd, Google Spanner via TrueTime [-7ms, +7ms]).
  2. Sequential Consistency: All nodes see operations in the same total order, though not necessarily matching real-time order across independent clients.
  3. Causal Consistency: Operations that are causally related (A -> B) appear in order everywhere; concurrent unrelated operations may appear in different orders.
  4. Session Guarantees (Read-Your-Writes / Monotonic Reads): A single user always sees their own updates and never moves backward in time.
  5. Eventual Consistency: If writes stop, all replicas eventually converge to the same state.

Failure modes

  1. Clock-Skew Silent Overwrites: Using LWW when NTP drifts by 150ms causes older writes from a fast-clock node to overwrite newer writes from a slow-clock node.
  2. Split-Brain Promotion: Manually promoting an async read replica during a transient network blip while the old primary still accepts writes creates two divergent histories.
  3. Gray Failures / Asymmetric Partitions: Node A cannot reach Node B, but both reach clients; naive health checks pass while quorum heartbeats flap continuously.

Mixing consistency models in one architecture

Production architectures rarely apply one PACELC choice globally. Place identity, billing, inventory reservation, and leader election on a PC/EC store (PostgreSQL/Spanner/etcd) where correctness trumps a 10–50ms write tax. Place shopping carts, session caches, user feeds, and telemetry on PA/EL or causal stores (Redis, DynamoDB, Cassandra) using idempotent updates or CRDTs so local reads and writes stay under 5ms even during cross-AZ or cross-region degradation.

Practical checklist

  • Map every data entity to its required invariant: Linearizable (money/locks), Causal (social/comments), or Eventual (counters/caches).
  • For PC/EC stores, size quorum placement across 3 failure domains (AZs or regions) and measure exact inter-zone RTT.
  • For PA/EL stores, replace raw wall-clock LWW with Hybrid Logical Clocks, CRDTs, or explicit conflict-resolution handlers.
  • Configure fencing tokens (STONITH / Raft term IDs) on primary-standby databases to prevent split-brain on failover.
  • Implement Read-Your-Writes session stickiness or LSN-wait when serving reads from asynchronous replicas.
03 / Engineering trade-offs

Weighing architectural decisions

Linearizability vs. Tail Latency (EC vs. EL)

Advantage: Synchronous quorum replication guarantees every client sees the exact same latest state with zero conflict-resolution code.

Drawback: Write latency is bounded by the slowest node in the quorum (e.g., 75ms+ cross-region), and a partition stalls the minority side.

Availability Under Partitions vs. Anomaly Risk

Advantage: AP/EL systems accept writes on both sides of a split, keeping checkout carts or telemetry ingestion at 99.999% uptime.

Drawback: Divergent writes require deterministic merge logic (CRDTs, vector clocks, or LWW), and LWW silently drops concurrent updates.

Causal Consistency as the Sweet Spot

Advantage: Available under partitions (no global consensus needed) while preventing impossible timelines like seeing a reply before its parent post.

Drawback: Requires tracking causal metadata (Lamport/hybrid logical clocks or session tokens) across every read and write.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Sloppy Quorum + Last-Write-Wins Silent Data Loss

In an AP store using wall-clock timestamps (`LWW`), a node with 200ms NTP clock drift silently overwrites newer writes from other nodes without raising an error.

What helps: Use Hybrid Logical Clocks (HLC), CRDTs (G-Counter, OR-Set), or strict quorum (`W + R > N` with Raft/Paxos) instead of raw wall-clock LWW.

Asymmetric Network Partition Causes Dual Leaders

Node A can reach B, B can reach C, but A cannot reach C. Without strict term/lease fencing, both A and C believe they are the primary and accept conflicting writes.

What helps: Use Raft/Paxos term numbers plus fencing tokens on storage/locks, and validate with Jepsen fault injection.

Stale Reads from Follower Without Read-Index

Serving reads from a Raft follower without checking the leader's `commitIndex` returns stale data even in a CP cluster, breaking linearizability.

What helps: Route linearizable reads through the leader (with `ReadIndex` or leader leases bounded by clock-skew uncertainty).

Read-Your-Writes Violation After Load-Balanced Write

A user updates their profile on primary, then immediately refreshes and hits an async read replica 150ms behind, seeing their old profile and retrying.

What helps: Pin the user's session to primary for 1–2 seconds post-write or pass a causal LSN/timestamp token so replicas wait until caught up.

05 / Practical checklist

Avoid these mistakes

  • Calling a system 'CA'—in any networked distributed system, partitions (P) happen, so 'CA' only describes a single-node database or an impossible ideal.
  • Assuming `W + R > N` in a leaderless Dynamo store guarantees linearizability (concurrent writes without read-repair or consensus can still return stale values).
  • Using `Last-Write-Wins` with unsynchronized NTP clocks (10–100ms drift) for financial or inventory mutations.
  • Enabling multi-region synchronous consensus when only 5% of tables (e.g., billing) need linearizability and 95% (e.g., logs/preferences) can be local.
  • Confusing ACID isolation levels (Serializable) with distributed consistency (Linearizability)—a database can be Serializable on stale snapshots.
