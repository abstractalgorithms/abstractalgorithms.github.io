Model Serving &
GPU Batching.

Group concurrent inference requests into tensor batches on the GPU to shift workloads from memory-bandwidth-bound to compute-bound without blowing tail latency.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Use dynamic batching with a tight queue timeout (2–10 ms) for fixed-shape encoders, and iteration-level continuous batching with PagedAttention for autoregressive LLMs.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Serving models at batch size 1 leaves modern GPUs (like NVIDIA A100/H100) 80–90% idle because loading model weights from HBM into SRAM dominates compute time. Intelligent batching multiplies throughput 5–20x per GPU while keeping p99 latency within strict interactive SLOs.

  • Batching amortizes HBM weight reads across BBB inputs, raising arithmetic intensity (FLOPs/byte) toward the GPU's roofline.
  • Dynamic batching (Triton Inference Server) buffers incoming requests up to max_batch_size or max_queue_delay_microseconds (typically 2,000–10,000 us).
  • Static padding wastes compute on variable-length sequences; bucket by sequence length or use ragged/packed tensors.
  • Autoregressive LLMs fail under request-level batching because short prompts wait behind long generations; continuous (iteration-level) batching (vLLM, TensorRT-LLM) swaps finished sequences out after every decode step.
  • PagedAttention eliminates KV-cache fragmentation by storing attention keys/values in non-contiguous fixed-size blocks (e.g., 16 tokens/block), increasing effective batch size 2–4x.

Good candidates

  • High-concurrency GPU inference (encoders, vision models, embeddings, or LLMs) where single-request execution is HBM memory-bandwidth bound.
  • Traffic arrives asynchronously from many concurrent users (e.g., >20 RPS) so requests naturally overlap within a 2–15 ms window.
  • GPU infrastructure dominates unit economics and maximizing tokens-per-second or inferences-per-dollar is a primary goal.

Think twice

  • Ultra-low-traffic endpoints (<2 RPS) where waiting for a batch window adds pure latency with zero batch formation.
  • Strict single-request hard real-time loops (<5 ms total budget) where any queuing delay is unacceptable.
  • Tiny CPU-bound models (e.g., logistic regression, small GBDTs) where per-sample inference already takes <200 microseconds.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA semantic search service running a 330M-parameter BGE embedding model on an NVIDIA L4 GPU at batch=1 capped out at 140 RPS with 18% GPU utilization.

The idea

GPU inference at batch size 1 is overwhelmingly memory-bandwidth bound: streaming 140 GB of FP16 weights from HBM to compute cores for a single token wastes ~85% of the chip's Tensor Core FLOPs. Model serving batching coalesces concurrent requests into a single matrix-matrix operation (GEMM) so weights are read once from HBM and reused across BBB inputs. For fixed-latency encoders, dynamic batching trades a bounded 2–10 ms queue wait for massive throughput gains; for autoregressive LLMs, continuous batching schedules at the single-token iteration boundary so requests enter and exit without waiting for peers.

Concrete walkthrough

Trace a continuous-batching LLM server (vLLM with PagedAttention) serving Llama-3-8B on an A100-80GB:

  1. Async Tokenization & Ingress: Clients send gRPC/HTTP SSE requests. A Rust/C++ tokenizer pool converts text to token IDs off the GPU thread and pushes them into the scheduler queue.
  2. Iteration-Level Scheduling: At the start of every 25 ms decode step, the scheduler checks free 16-token KV-cache blocks in VRAM. It admits waiting requests (prefill chunks of 512 tokens) alongside active decode sequences up to max_num_batched_tokens=2048.
  3. PagedAttention Forward Pass: A single fused CUDA kernel computes attention across non-contiguous KV-cache blocks for all BBB active sequences simultaneously.
  4. Immediate Ejection & Streaming: Any sequence emitting frees its KV-cache blocks immediately and closes its SSE stream; remaining sequences advance to the next step while a new queued request takes the freed slot.

Continuous batching schedules at every token-generation step rather than per-request, eliminating head-of-line blocking and KV-cache waste.

Latency-throughput physics

Understanding the GPU roofline model explains why batching works and where it stops scaling:

  • Memory-Bound Regime (B<BridgeB < B_{\text{ridge}}B<Bridge​): For FP16 matrix multiplication on an H100 (3.35 TB/s HBM, 989 TFLOPS FP16), the ridge point is ≈295\approx 295≈295 FLOPs/byte. Below batch size ~128–256 for decode, doubling batch size BBB nearly doubles throughput with almost zero increase in step latency.
  • Compute-Bound Regime (B≥BridgeB \ge B_{\text{ridge}}B≥Bridge​): Once arithmetic intensity saturates Tensor Cores, increasing BBB further yields flat throughput while step latency grows linearly with BBB.

Failure modes

Watch for three production failure modes as traffic scales:

  • Queue Buildup Beyond Client Timeout: If arrival rate λ\lambdaλ exceeds service rate μ\muμ for 30 seconds, the batcher processes requests whose clients already timed out at 5 seconds.
  • Dynamic Shape Recompilation: Frameworks like torch.compile or TensorRT without wildcard shape profiles trigger multi-second JIT stalls whenever a new batch size appears.
  • Cross-Request Memory Leaks: Improperly detached tensors or unfreed KV-cache blocks slowly shrink available VRAM until the pod OOMs.

Production hardening

Protect interactive SLOs under bursty load:

  • Admission Control: Reject requests with HTTP 429 (Retry-After) when estimated queue wait exceeds 50% of the TTFT SLO.
  • Warmup Profiles: Pre-compile TensorRT engines or run dummy warmup batches for powers-of-two batch sizes [1, 2, 4, 8, 16, 32, 64] before marking Kubernetes readiness probes healthy.
  • Prefix Caching: Enable automatic radix/prefix KV-cache sharing (e.g., SGLang RadixAttention or vLLM APC) when requests share long system prompts.

Practical checklist

  • Measure baseline batch=1 vs. batch=16 latency and throughput to locate your GPU roofline.
  • Set max_queue_delay_microseconds between 2,000 and 10,000 us for dynamic batching.
  • Use continuous batching + PagedAttention + chunked prefill for all LLM deployments.
  • Pre-warm all batch-size shapes during container startup before readiness passes.
  • Enforce queue-depth admission control (HTTP 429) and track TTFT/ITL p99 separately.
03 / Engineering trade-offs

Weighing architectural decisions

Max Queue Delay vs. Throughput

Advantage: Larger queue windows (e.g., 20 ms) form fuller batches and maximize GPU utilization.

Drawback: Every millisecond in the queue adds directly to p99 latency, especially during off-peak traffic.

Request-Level vs. Continuous (Iteration-Level) Batching

Advantage: Request-level batching is trivial to implement in Triton/TorchServe for fixed-length vision or encoder models.

Drawback: Continuous batching is mandatory for variable-length LLM decoding to avoid head-of-line blocking, at the cost of complex KV-cache block management.

Large Batch Size vs. VRAM Headroom (OOM Risk)

Advantage: Larger batches (64–256) push compute utilization near saturation.

Drawback: Activation memory and KV-cache grow linearly with batch size and sequence length, risking sudden CUDA OOM crashes on long-prompt bursts.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Head-of-Line (HoL) Blocking in Static LLM Batches

One 4,096-token generation stalls 15 already-finished 64-token requests in the same batch, spiking p99 latency 10x.

What helps: Use iteration-level continuous batching (vLLM / TensorRT-LLM) so completed sequences eject immediately after emitting EOS.

Prefill-Decode Interference

A massive 16k-token prompt prefill hogs GPU SMs for 400 ms, causing visible stuttering (ITL > 200 ms) for all streaming decode users.

What helps: Enable chunked prefill (splitting long prefills into 512-token chunks) or disaggregate prefill and decode onto separate GPU pools.

KV-Cache OOM & Preemption Thrash

Too many concurrent requests exhaust GPU VRAM for KV-cache, forcing the scheduler to preempt and recompute sequences repeatedly.

What helps: Cap `max_num_seqs` and `gpu_memory_utilization` (e.g., 0.90), use FP8 KV-cache quantization, and return HTTP 429 when queue depth exceeds SLO.

Low-Traffic Queue Penalty

At 1 AM with 2 RPS, every single request sits idle for the full `max_queue_delay` (e.g., 15 ms) waiting for a second request that never arrives.

What helps: Keep `max_queue_delay_microseconds` tight (2–5 ms) or use adaptive batching that dispatches immediately when concurrency is low.

05 / Practical checklist

Avoid these mistakes

  • Tuning `max_batch_size` without setting a bounded `max_queue_delay_microseconds`, causing unbounded tail latency.
  • Padding every sequence in a batch to `max_seq_len` (e.g., 4,096) instead of padding only to the longest sequence in that batch.
  • Running Python/FastAPI tokenization synchronously on the same event loop as GPU dispatch, starving the batcher.
  • Measuring only average throughput while ignoring Time-To-First-Token (TTFT) and Inter-Token Latency (ITL) p99.
  • Deploying without admission control/backpressure, allowing unbounded queues to trigger client timeouts on already-stale requests.
