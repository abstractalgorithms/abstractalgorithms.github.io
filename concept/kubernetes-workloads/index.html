THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Match the workload controller to statefulness and scheduling needs, and pair readiness probes with PodDisruptionBudgets so zero-downtime rollouts never route traffic to unready or terminating pods.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Running stateless APIs in a StatefulSet wastes operational simplicity, while running Kafka or PostgreSQL in a Deployment risks split-brain storage corruption. Understanding how controllers reconcile Pods and how Services decouple ephemeral Pod IPs via EndpointSlices and kube-proxy is what separates resilient production clusters from cascading rollout outages and 502 storms.

  • Controller specialization: Deployments manage ReplicaSets for interchangeable pods; StatefulSets bind each ordinal (-0, -1) to its own PersistentVolumeClaim and DNS entry ...svc.cluster.local.
  • Service abstraction: Services match Pods via label selectors and maintain EndpointSlice objects (default max 100 endpoints per slice) that kube-proxy (iptables/IPVS) or eBPF (Cilium) programs into kernel packet-forwarding rules.
  • Zero-downtime termination race: kubelet sends SIGTERM to the Pod concurrently with the Endpoints controller removing the Pod IP from EndpointSlices; a preStop sleep (5–10s) prevents in-flight 502s while iptables/eBPF rules propagate.
  • Probe separation: startupProbe protects slow-booting JVMs/ML models, readinessProbe gates Service traffic inclusion, and livenessProbe restarts wedged containers—never point livenessProbe at downstream DB health.
  • Voluntary disruption safety: PodDisruptionBudgets (minAvailable or maxUnavailable) block kubectl drain and cluster autoscaler evictions from taking down quorum or all replicas simultaneously.

Good candidates

  • Deployment: stateless HTTP/gRPC services, workers, and frontends needing rolling updates (maxSurge/maxUnavailable) and instant horizontal scaling.
  • StatefulSet: distributed databases (PostgreSQL, Kafka, etcd, Redis) requiring stable DNS (pod-0.svc), ordered startup/teardown, and persistent per-pod PVCs (volumeClaimTemplates).
  • DaemonSet & Job/CronJob: node-level agents (Fluent Bit, Cilium, Prometheus node-exporter) on every node, or finite batch/scheduled tasks with backoffLimit and ttlSecondsAfterFinished.

Think twice

  • Bare Pods without a controller—if a node dies, a standalone Pod is never rescheduled.
  • StatefulSet for stateless workloads just to get predictable pod names—ordered scaling slows down HPA bursts and complicates node drains.
  • Default ClusterIP Service for gRPC or client-side load-balanced databases—use a Headless Service (clusterIP: None) so clients discover all Pod IPs directly via DNS.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA Go gRPC payment service experiences 0.8% HTTP/2 503 errors during every Deployment rollout because kube-proxy iptables updates lag behind Pod SIGTERM.

The idea

Kubernetes separates what runs (Workload Controllers) from how it is reached (Services). Controllers continuously watch the API server and reconcile desired state (spec.replicas, template, volumeClaimTemplates) against live Pods. Because Pods are mortal and receive new IPs on every reschedule, a Service acts as a stable virtual abstraction: it selects matching Pods by labels, writes their IPs into EndpointSlice objects, and programs kernel forwarding rules (iptables, IPVS, or eBPF) across every node.

Concrete walkthrough

Trace a Deployment rolling update (maxSurge: 1, maxUnavailable: 0) on a 3-replica API behind a ClusterIP Service:

  1. Surge: Updating the container image creates a new ReplicaSet and scales it to 1 Pod (4 total Pods).
  2. Gate: kubelet runs startupProbe and readinessProbe. Until readinessProbe returns 200 OK, the Pod's IP is marked ready: false in the EndpointSlice and receives zero traffic.
  3. Shift: Once ready, kube-proxy adds the new Pod IP to the Service's forwarding rules, and the old ReplicaSet scales down by 1.
  4. Drain: The terminating Pod receives SIGTERM, runs its preStop sleep 10 while EndpointSlice removal propagates across nodes, finishes active HTTP requests within terminationGracePeriodSeconds: 30, and exits cleanly.

Declarative reconciliation loop: controllers manage Pod lifecycle while EndpointSlices and kube-proxy decouple network routing.

Workload Controllers & Service Types

  • Deployment: Stateless pods; supports Recreate or RollingUpdate and instant kubectl rollout undo via revisionHistoryLimit (default 10).
  • StatefulSet: Ordered 0..N-1 identity, stable headless DNS, and sticky PVCs.
  • DaemonSet: Exactly one pod per matching node (taints/tolerations control master/GPU scheduling).
  • Job / CronJob: Finite completion (completions, parallelism, backoffLimit: 6); CronJobs enforce concurrencyPolicy (Allow, Forbid, Replace).
  • Service Types: ClusterIP (internal VIP), Headless (clusterIP: None, raw DNS), NodePort (30000–32767), and LoadBalancer (cloud NLB/ALB).

Failure modes

  1. gRPC Pinning on ClusterIP: HTTP/2 multiplexes all RPCs over one TCP connection; kube-proxy only load-balances at TCP SYN time, pinning 100% of traffic to one Pod until a Headless Service or L7 Envoy mesh is used.
  2. OOMKill Cascade: Missing memory requests == limits (Guaranteed QoS) lets noisy neighbors trigger node eviction.
  3. Ingress / Service Selector Mismatch: A typo in spec.selector leaves EndpointSlices empty (0 endpoints), returning immediate connection refused.
  4. Probe Timeout Thrashing: Under CPU throttling (too-tight resources.limits.cpu), livenessProbe misses its 1s timeout and restarts healthy Pods.

Traffic Shifting & Graceful Shutdown

In production, pair Deployment rollouts with PodDisruptionBudget (maxUnavailable: 1 or 25%) and topologySpreadConstraints (maxSkew: 1 across topology.kubernetes.io/zone) so an entire Availability Zone failure or node drain never drops capacity below quorum. For high-RPS services, remove limits.cpu (or set it generously) while keeping requests.cpu accurate to avoid CFS quota throttling during traffic bursts.

Practical checklist

  • Define startupProbe, readinessProbe, and local-only livenessProbe on every long-running container.
  • Add a preStop sleep (5–10s) and align terminationGracePeriodSeconds (>30s) with app drain time.
  • Attach a PodDisruptionBudget to every multi-replica Deployment and StatefulSet.
  • Set requests for CPU/memory and pin container images by immutable SHA256 digest.
  • Use a Headless Service (clusterIP: None) or L7 proxy for gRPC/HTTP2 workloads to avoid TCP connection pinning.
03 / Engineering trade-offs

Weighing architectural decisions

iptables vs. IPVS vs. eBPF (Cilium) kube-proxy mode

Advantage: IPVS and eBPF use O(1) hash-table lookups, keeping service-routing latency flat even past 10,000 Services.

Drawback: Default `iptables` evaluates rules sequentially in O(N), causing noticeable rule-sync CPU spikes and packet latency above ~5,000 Services.

ClusterIP Load Balancing vs. Headless Service (`clusterIP: None`)

Advantage: ClusterIP gives a single virtual IP (VIP) with transparent L4 round-robin for HTTP/1.1 clients.

Drawback: L4 VIPs pin long-lived HTTP/2 or gRPC TCP connections to one backend Pod; Headless Services expose all Pod IPs in DNS A/AAAA records for client-side L7 balancing.

OrderedReady vs. Parallel PodManagementPolicy (StatefulSet)

Advantage: OrderedReady starts `0 → 1 → 2` sequentially, ensuring primary election or seed discovery completes safely.

Drawback: In a 50-shard cluster, OrderedReady can take 20+ minutes to scale or restart; `Parallel` launches all ordinals simultaneously when the app handles peer discovery.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Liveness Probe Cascading Restart Storm

A `livenessProbe` checks a downstream database; when the DB blips for 10s, Kubernetes kills and restarts all healthy API pods simultaneously, amplifying recovery load.

What helps: Check downstream dependencies only in `readinessProbe` (to shed traffic) and keep `livenessProbe` strictly local (process/event-loop responsiveness).

PDB Deadlock Blocking Node Upgrades

A `PodDisruptionBudget` sets `minAvailable: 100%` or `maxUnavailable: 0`, preventing `kubectl drain` and Managed Node Group upgrades from ever completing.

What helps: Always leave at least 1 disruption budget (e.g., `maxUnavailable: 1` or `minAvailable: 2` on a 3-replica set) and monitor PDB `disruptionsAllowed`.

SIGTERM / EndpointSlice Propagation Race (502s)

A Pod exits immediately on `SIGTERM` in 50 ms, before `kube-proxy` finishes removing its IP from iptables on all worker nodes, causing clients to hit a dead socket.

What helps: Add a `preStop: exec: command: ["/bin/sh", "-c", "sleep 10"]` hook and ensure `terminationGracePeriodSeconds` exceeds `preStop + in-flight drain`.

StatefulSet Stuck Terminating on Lost Node

A worker node crashes hard; Kubernetes refuses to recreate `pod-0` elsewhere because at-most-one semantics forbid two `pod-0` instances sharing one PVC.

What helps: Verify the old node is fenced/dead (e.g., via Cloud Controller Manager) before force-deleting the stuck Pod (`--grace-period=0 --force`).

05 / Practical checklist

Avoid these mistakes

  • Omitting `resources.requests` and `limits`, causing pods to land in `BestEffort` QoS and get OOMKilled first during node memory pressure.
  • Using `latest` image tags without `imagePullPolicy: Always` or immutable SHA digests, leading to version drift across nodes.
  • Setting `readinessProbe` and `livenessProbe` with identical tight timeouts on a slow-starting app without a `startupProbe`, trapping pods in `CrashLoopBackOff`.
  • Assuming deleting a `StatefulSet` deletes its `PersistentVolumeClaims`—PVCs intentionally persist (`persistentVolumeClaimRetentionPolicy`) and must be cleaned up explicitly if ephemeral.
  • Exposing internal microservices with `type: LoadBalancer` instead of `ClusterIP` + an Ingress/Gateway API controller, creating unnecessary public cloud LBs and cost.
