STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are Kubernetes Workload Controllers & Services.

Why this matters: The mechanism: understand how Kubernetes Workload Controllers & Services works from first principles.

Never deploy bare Pods—if a node dies, a standalone Pod is never rescheduled. Kubernetes manages Pod lifecycles through specialized controllers:

  • Deployment: Manages ReplicaSets for stateless, interchangeable Pods with rolling updates (maxSurge/maxUnavailable).
  • StatefulSet: Binds stable ordinals (pod-0, pod-1) to dedicated volumeClaimTemplates PVCs and headless DNS (pod-0.svc.ns.svc.cluster.local) for databases (Postgres, Kafka, etcd).
  • DaemonSet / Job: Runs 1 Pod per node (log/metrics agents) or run-to-completion batch tasks.

Why SIGTERM Races EndpointSlice Removal — And How preStop Fixes 502s

A 10s preStop sleep gives EndpointSlices and kube-proxy time to stop routing new traffic before the app closes its socket.

Three operational traps cause most Kubernetes rollout outages: (1) checking downstream DB health in livenessProbe (if Postgres blips for 10s, kubelet restarts every API pod simultaneously in a cascading storm!), (2) setting a PodDisruptionBudget with minAvailable: 100% (blocking node upgrades forever), and (3) missing preStop sleeps causing 502 Bad Gateway during rolling deploys.

Engineering Decision Framework
Problem
How to implement Kubernetes Workloads & Service Routing without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
When traffic spikes expose hidden coupling, match the workload controller to statefulness and scheduling needs, and pair readiness probes with PodDisruptionBudgets so zero-downtime rollouts never route traffic to unready or terminating pods.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Design Trade-Off

Zero-Downtime Deployment Spec: Probes, preStop & PDB

Before · Unbounded Pods & Abrupt Kill
  • 502s during rolling updates
  • ndots:5 DNS flood or OOMKill
  • Unprotected node drains
After · PDB + Probes + Graceful Drain
  • Zero-drop SIGTERM draining
  • Bounded cgroup & conntrack
  • Canary metrics gate rollout
spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: api
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 10"]  # Wait for EndpointSlice removal
      readinessProbe:
        httpGet: { path: /readyz, port: 8080 }   # Checks DB + warmup
        periodSeconds: 5
      livenessProbe:
        httpGet: { path: /livez, port: 8080 }    # Process-local ONLY (never check DB!)
        periodSeconds: 10

StatefulSet Quorum

3-Pod StatefulSet + Headless DNS + Quorum PDB (minAvailable: 2)

1.Ordinal Identity: pod-0 always reattaches to PVC-0 even if rescheduled onto a new worker node.

2.Safe Drains: PDB minAvailable=2 blocks concurrent node drains that would lose Raft quorum.

3.Lost-Node Fencing: If a node vanishes, verify it is fenced via Cloud Controller Manager before force-deleting.

StatefulSets + Headless Services + Quorum PDBs protect stateful clusters across rolling upgrades and node drains.
