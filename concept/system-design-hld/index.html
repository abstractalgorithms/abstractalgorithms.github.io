System Design
(HLD) Architectures.

High-Level Design (HLD) translates product requirements and scale targets (QPS, p99 latency, durability, RPO/RTO) into a cohesive topology of edge gateways, stateless compute, caches, async queues, and partitioned data stores. Good HLD explicitly isolates failure domains and separates read/write bottlenecks.

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is System Design (HLD) Architectures.

Why this matters: The mechanism: understand how System Design (HLD) Architectures works from first principles.

The idea High-Level Design (HLD) is the blueprint of how traffic, state, and failures flow through a distributed system. Rather than prescribing individual classes, HLD defines service boundaries, data ownership, communication patterns (sync vs. async), and scaling axes. Every scalable HLD rests on three levers: (1) Shedding or caching reads as close to the user as possible (CDN → Edge → Redis → Read Replicas), (2) Absorbing write spikes through durable logs (Kafka/SQS) and partitioned storage (hash/range sharding), and (3) Bounding blast radius via cell-based isolation, timeouts, and backpressure so one degraded dependency cannot take down the entire platform.

Core Pillars:

  • Quantify traffic early: compute read/write QPS (peak = 3–5x average), daily storage growth, and network egress before picking databases.
  • Separate stateless compute (horizontally scalable behind L7 load balancers) from stateful tiers (sharded DBs, distributed caches, object stores).
  • Apply CQRS and async decoupling (Kafka/SQS + outbox pattern) when write latency, fan-out, or third-party webhooks would otherwise block user-facing threads.
  • Design for graceful degradation: circuit breakers, adaptive concurrency limits, idempotency keys, and stale-while-revalidate caches prevent partial failures from becoming total outages.
  • Define RPO (acceptable data loss) and RTO (acceptable recovery time) per tier—active-active multi-region is 3x more complex and costly than active-passive.
Read/Write Scaling Blueprint

Canonical Edge -> Cache -> Async Queue -> Sharded DB Stack

1.Back-of-Envelope: QPS, 3x peak, storage/yr, bandwidth.

2.Failure Isolation: Timeouts, retries+jitter, circuit breakers.

High-level designs scale by caching hot reads, buffering bursty writes through durable queues, and sharding state horizontally.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need System Design (HLD) Architectures (and what fails without it).

Why this matters: The problem: see what breaks without System Design under real concurrency or scale.

Prematurely jumping into database schemas or class diagrams misses the systemic bottlenecks—hot-key thundering herds, cross-region replication lag, and cascading retry storms—that actually cause production outages and 10x cloud bills.

Common Pitfalls:

  • Designing an architecture without first calculating read/write QPS, payload sizes, and 5-year storage capacity.
  • Using a single primary RDBMS for both OLTP transactions and heavy analytical GROUP BY reporting queries.
  • Omitting idempotency keys on mutating endpoints (POST /payments), causing duplicate charges when mobile clients retry on flaky networks.

Problem

Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
To keep the architecture evolvable without sacrificing reliability, start every HLD from back-of-the-envelope QPS, payload size, and consistency bounds, then decouple read-heavy paths with caches/CDNs and bursty writes with durable queues.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How System Design (HLD) Architectures works under the hood & reference implementation.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Concrete walkthrough Consider designing a multi-tenant Notification & Webhook Delivery Platform handling 20,000 events/sec:

  1. Edge & Ingestion: Clients call POST /v1/notifications with an Idempotency-Key. Envoy terminates TLS, enforces per-tenant token-bucket rate limits, and routes to stateless ingest-api pods.
  2. Deduplication & Durable Acceptance: ingest-api checks Redis (SETNX idem:<key> EX 86400), validates the payload, writes an ACCEPTED record to a Kafka notifications.inbound topic (partitioned by tenant_id), and returns 202 Accepted in <15 ms.
  3. Routing & Fan-out: Stateless router-workers consume from Kafka, look up tenant preferences (cached in Redis, backed by PostgreSQL), and route to channel-specific topics (email.send, webhook.deliver).
  4. Isolated Delivery & Backpressure: webhook-workers execute outbound HTTP POSTs with strict 3-second timeouts. If a customer's webhook endpoint returns 503, the worker routes the message to tiered retry topics (retry-1m, retry-15m, dlq) without blocking healthy tenants.

Reference implementation (Python — Idempotent Bounded Retry with Exponential Backoff)

# Production-safe bounded retry with full jitter (Python)
import random, time
def execute_with_retry(fn, max_attempts: int = 4, base_delay_s: float = 0.05):
    for attempt in range(max_attempts):
        try:
            return fn()
        except TransientError:
            if attempt == max_attempts - 1:
                raise
            cap = base_delay_s * (2 ** attempt)
            time.sleep(random.uniform(0.0, cap))

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production architecture & hardening for System Design (HLD) Architectures.

Why this matters: Production architecture: see how the components compose end to end under real load.

Failure modes 1. Split-Brain Under Network Partition: Two database nodes both believe they are primary after a flaky AZ link, accepting conflicting writes. Always enforce quorum-based fencing (Raft/Paxos) or STONITH/lease-based leader election. 2. Unbounded Queue Lag (Consumer Starvation): A downstream dependency slows down from 10 ms to 2 s, causing Kafka consumer lag to grow to 50M messages. By the time it recovers, messages are hours stale and TTLs expire. Enforce shedding/load-dropping or priority queues (interactive vs. bulk). 3. Cross-Region Failover Thundering Herd: Failing over 100% of traffic to a cold secondary region whose Redis caches are empty sends 100% cache-miss load straight to the secondary DB. Pre-warm caches or keep active-active regional cells sized for 50% headroom.

Practical checklist

  • [ ] Document peak read/write QPS, payload size, p99 latency SLO, and RPO/RTO targets before choosing components.
  • [ ] Enforce Idempotency-Key headers on all non-idempotent POST/PATCH APIs.
  • [ ] Place timeouts, jittered exponential backoff, and retry budgets on every outbound network call.
  • [ ] Separate OLTP databases from OLAP analytics via CDC (Debezium → Kafka → ClickHouse/BigQuery).
  • [ ] Verify sharding/partition keys against your top 1% 'celebrity' or 'whale' tenants to prevent hot-shard saturation.
  • [ ] Test failover and cache-cold recovery in staging via periodic chaos/game-day drills.
