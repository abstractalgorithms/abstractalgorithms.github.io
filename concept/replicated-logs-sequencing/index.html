THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Use a consensus-backed replicated log (Raft/Paxos/KRaft) with monotonic term-and-index sequencing whenever multiple nodes must agree on state order despite crashes and network partitions.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

In distributed systems, concurrent client requests arrive at different nodes in different orders due to network jitter, retries, and node failures. Without a globally agreed sequence, replicas diverge into inconsistent states (split-brain). Replicated logs—powering etcd, CockroachDB, Kafka KRaft, and ZooKeeper—turn messy concurrency into deterministic state-machine replication.

  • Every log entry carries a monotonic (term, index) pair: the index orders entries within a log, while the term (epoch) detects stale leaders after network partitions.
  • A leader sequences all incoming writes, appends them to its local Write-Ahead Log (WAL), and replicates them via AppendEntries RPCs to followers.
  • An entry is committed only after a strict majority quorum (e.g., 3 of 5 nodes) persists it to durable storage (fsync), guaranteeing survival across any minority failure.
  • State-machine safety requires that if any node applies log entry at index i, no other node can ever apply a different command at index i.
  • Compaction via periodic snapshots prevents unbounded log growth while allowing slow or newly joined nodes to catch up without replaying terabytes of history.

Good candidates

  • Distributed metadata, locks, leader election, or configuration stores require strong linearizable consistency across node failures.
  • Multiple storage replicas must apply mutations in identical order to guarantee identical B-tree, key-value, or ledger states.
  • Event-driven pipelines need a durable, replayable, strictly ordered commit log per partition (e.g., Kafka, Pulsar).

Think twice

  • Eventual consistency or commutative updates (CRDTs, counters, append-only metrics) suffice and cross-AZ consensus latency (1–5ms RTT) is unacceptable.
  • A single primary database with asynchronous read replicas already meets durability and RPO/RTO requirements.
  • Workload is pure stateless compute or ephemeral caching where losing in-flight state on restart is harmless.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA 5-node etcd cluster stores cluster state, pod scheduling leases, and distributed locks across three availability zones.

The idea

State Machine Replication (SMR) rests on a simple theorem: if two deterministic state machines start in the same initial state and execute the exact same sequence of inputs, they will arrive at the exact same final state.

A replicated log is the mechanism that manufactures that identical sequence across unreliable machines. Instead of replicating complex in-memory structures, a designated leader assigns each command a strictly increasing (term, index) coordinate, appends it to an append-only Write-Ahead Log (WAL), and replicates it to followers. Once a majority quorum (floor(N/2) + 1) persists the entry, it becomes committed and is safely applied to the local state machine.

Concrete walkthrough

Trace a PUT /accounts/42 balance=500 write on a 3-node Raft cluster (N1 Leader, N2 and N3 Followers) in term=7:

  1. Sequence & local append: N1 receives the client request, assigns index=1042, term=7, and writes the entry to its local NVMe WAL (fsync).
  2. Parallel replication: N1 sends AppendEntries(term=7, prevLogIndex=1041, prevLogTerm=7, entries=[1042], leaderCommit=1041) to N2 and N3.
  3. Consistency check & persist: N2 verifies its log has (term=7, index=1041), appends 1042, calls fsync, and replies success=true. (N3 may be temporarily slow or partitioned.)
  4. Quorum commit: N1 now has 2 of 3 confirmations (N1 + N2), forming a majority. N1 advances commitIndex = 1042, applies PUT /accounts/42 to its local KV engine, and returns 200 OK to the client.
  5. Follower apply: On the next heartbeat (within 100ms), N1 advertises leaderCommit=1042; N2 and (once caught up) N3 apply index 1042 to their state machines.

Consensus log replication: every command is ordered by (term, index), persisted by a majority quorum, and applied deterministically.

The invariants that prevent divergence

Correct log sequencing depends on three non-negotiable invariants:

  • Election Restriction: A candidate cannot win an election unless its log is at least as up-to-date (higher last term, or equal term and >= last index) as a majority of nodes. This guarantees the new leader already holds every previously committed entry.
  • Log Matching Property: If two logs contain an entry with the same index and term, they are guaranteed identical for all preceding entries—enforced by checking (prevLogIndex, prevLogTerm) on every AppendEntries.
  • Current-Term Commit Rule: A leader never marks entries from an older term as committed by counting replicas alone; it commits them indirectly by committing a new entry from its current term.

Failure modes and split-brain prevention

The subtlest bugs in replicated logs happen during asymmetric partitions and clock drift:

  • Zombie leader reads: If N1 is partitioned, N2 wins term=8, but N1 doesn't know yet and serves stale reads from memory. Fix: use ReadIndex (leader confirms quorum heartbeat before replying) or bounded hardware-clock leases.
  • Fencing downstream side effects: If a leader writes to external S3/DB storage after losing leadership, pass the Raft term or ZooKeeper zxid as a fencing token so storage rejects stale epochs.
  • Unbounded WAL growth: Without log compaction into snapshots, restart recovery time grows linearly with cluster lifetime.

Throughput and tail-latency tuning

To hit tens of thousands of consensus writes per second without sacrificing safety, production engines use pipelining (sending batch N+1 before N is acked), group commit (coalescing concurrent client writes into one fsync), witness/learner nodes (voting-free replicas for analytics), and Multi-Raft sharding so independent key ranges elect leaders across all nodes.

Practical checklist

  • Deploy odd cluster sizes (3 or 5): Use 3 nodes for single-failure tolerance and 5 nodes if you need maintenance + 1 unexpected failure.
  • Use dedicated NVMe for WAL: Keep log fsync p99 below 2–3 ms by isolating WAL from application/compaction I/O.
  • Enable Pre-Vote: Prevent partitioned nodes from incrementing terms and disrupting healthy leaders upon reconnect.
  • Configure automated snapshots: Compact logs at fixed byte thresholds (e.g., 64–256 MB) to bound recovery time.
  • Monitor leader-change rate: Alert on >1 leader election per hour—frequent elections indicate network drops or disk stalls.
03 / Engineering trade-offs

Weighing architectural decisions

Strong quorum replication vs. Asynchronous replication

Advantage: Quorum replication (`W + R > N`) prevents acknowledged data loss during sudden leader crashes.

Drawback: Every write pays at least one network round-trip to the fastest quorum of followers plus disk `fsync` latency.

Single-leader sequencing vs. Multi-leader / Leaderless

Advantage: Single-leader logs eliminate write-write conflicts and simplify reasoning about exact global order.

Drawback: All writes for a shard/partition bottleneck on one leader node until partitioned across multiple Raft groups (Multi-Raft).

Aggressive fsync batching vs. Per-write fsync

Advantage: Group-committing 50–200 log entries per `fsync` boosts throughput by 10x–30x on NVMe SSDs.

Drawback: Adds 1–5ms of batching delay to individual write latency.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Split-Brain / Stale Leader Writes

A partitioned old leader continues serving reads or accepting writes while the rest of the cluster elects a new leader.

What helps: Require quorum heartbeats (ReadIndex / leader leases) for linearizable reads and pass monotonic fencing tokens (term/epoch) to downstream storage.

Log Divergence on Unclean Failover

Uncommitted entries on an isolated node conflict with the new leader's committed log at the same index.

What helps: Consensus protocols (Raft's Log Matching Property) force followers to truncate conflicting uncommitted suffixes and overwrite them with the leader's log.

Disk I/O Stall Triggering Election Storms

Slow `fsync` or GC pauses prevent the leader from sending heartbeats within `electionTimeout`, causing repeated failovers.

What helps: Isolate WAL on dedicated NVMe drives, tune `heartbeatInterval` (e.g., 100ms) vs. `electionTimeout` (e.g., 1,000ms), and use Pre-Vote to block disruptive elections.

Snapshot / Catch-Up Storm

A restarted node falls far behind, forcing the leader to stream multi-gigabyte snapshots that saturate network bandwidth and starve live replication.

What helps: Rate-limit snapshot transfers, compact logs frequently at bounded sizes (e.g., every 100k entries), and serve snapshots from non-leader learners if supported.

05 / Practical checklist

Avoid these mistakes

  • Deploying an even number of consensus nodes (e.g., 2 or 4), which increases cost without improving fault tolerance (4 nodes still tolerate only 1 failure, same as 3).
  • Serving stale reads directly from a leader or follower without a ReadIndex check or valid lease, breaking linearizability.
  • Running WAL and heavy compaction/application workloads on the same shared disk, causing tail-latency spikes and spurious leader elections.
  • Disabling `fsync` on the consensus log—if a power loss wipes an acknowledged entry on a quorum, committed state is permanently corrupted.
  • Assuming a single Raft group can scale indefinitely instead of sharding into Multi-Raft ranges (as CockroachDB and TiKV do).
