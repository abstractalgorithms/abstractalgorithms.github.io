STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is a Replicated Log.

State Machine Replication (SMR) rests on a simple theorem: if two deterministic state machines start in the same state and execute the exact same sequence of inputs, they produce identical final states. A replicated log (powering etcd, CockroachDB, Kafka KRaft, ZooKeeper) manufactures that global order.

Each entry carries a monotonic (term, index) pair: index orders entries in the log, while term (epoch) detects stale leaders after partitions. An entry commits only after a strict majority quorum (e.g., 2 of 3, or 3 of 5) persists it via fsync.

Raft Log Replication

3-Node Consensus Quorum & `(term, index)` Log Sequencing

1.1. Monotonic (Term, Index): Leader sequences writes, appends to local NVMe WAL, and replicates to followers.

2.2. Election Restriction: A candidate cannot win an election unless its log is at least as up-to-date as a majority.

3.3. Log Matching: Followers truncate conflicting uncommitted suffixes to match the newly elected leader.

Quorum fsync + Election Restriction guarantee that committed entries are never lost across failovers.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Consensus Logs (Split-Brain & Zombie Reads).

Without consensus sequencing, concurrent writes arrive at replicas in different orders and diverge into split-brain. Even with Raft, asymmetric partitions create a classic trap: if Leader N1 is partitioned and N2 wins term=8, N1 may still serve stale zombie reads from memory unless reads go through ReadIndex (quorum heartbeat check) or valid hardware-bounded leader leases.

Deploy Odd Cluster Sizes (3 or 5, Never 4)

A 4-node cluster still requires 3 nodes for a majority quorum, tolerating only 1 failure—identical to 3 nodes at 33% higher cost.

Isolate WAL on Dedicated NVMe + Enable Pre-Vote

Shared disk I/O stalls fsync past electionTimeout, triggering election storms; Pre-Vote blocks partitioned nodes from bumping terms disruptively.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Replicated Logs fit (and where CRDTs/Async Replicas suffice).

Use consensus logs for metadata, locks, and strongly consistent storage; skip quorum fsync RTTs when eventual consistency or commutative updates suffice.

ChoiceWhat it buysWhat it costs
Good Candidate: Metadata, Locks & Linearizable KV (etcd, TiKV, KRaft)Guarantees zero acknowledged data loss and identical replica state machines across minority crashes.Every write pays 1 quorum network RTT + WAL `fsync` latency (2–5 ms on NVMe).
Avoid: Commutative Counters & Ephemeral CachesUse CRDTs or Redis async replicas when 1–5 ms cross-AZ consensus RTT is unacceptable.Consensus serializes all writes for a Raft group through one leader until sharded into Multi-Raft.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How WAL Group Commit, Snapshots & Compaction are managed.

Batch concurrent client writes into a single fsync (group commit, boosting NVMe throughput 10x–30x), compact logs via periodic snapshots so restarted nodes do not replay terabytes, and rate-limit snapshot transfers so catch-up storms do not starve live traffic.

# Raft-style monotonic (term, index) WAL append + fsync group-commit sketch
import os, json

class ConsensusWal:
    def __init__(self, path: str):
        self.fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_APPEND, 0o644)

    def append_batch_and_sync(self, entries: list[tuple[int, int, str]]) -> None:
        """Coalesce (term, index, command) batch into one write + fsync."""
        payload = "".join(
            json.dumps({"term": t, "index": idx, "cmd": cmd}) + "\n"
            for t, idx, cmd in entries
        ).encode("utf-8")
        os.write(self.fd, payload)
        os.fsync(self.fd)  # Mandatory before acknowledging quorum

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Single-Raft vs. Multi-Raft vs. Leaderless Quorum.

Scale consensus throughput by partitioning key ranges across independent Raft groups.

ChoiceWhat it buysWhat it costs
Single Consensus Group (etcd / ZooKeeper)Simple cluster topology for GB-scale metadata, config, and leader election.All writes funnel through one leader node.
Multi-Raft Sharded Ranges (CockroachDB / TiKV)Distributes thousands of 64 MB Raft groups across all cluster nodes for horizontal write scaling.Higher operational complexity and cross-range 2PC/percolator transactions.
Leaderless Quorums (Cassandra / Dynamo)Any node accepts writes even during minority partitions.No global total order; relies on LWW timestamps and anti-entropy.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Linearizable Write + ReadIndex Quorum Check.

A 3-node Raft cluster (N1 Leader in term=7) batches 50 client mutations into one NVMe fsync, pipelines AppendEntries to N2/N3, commits at majority, and serves linearizable reads by confirming leadership via a lightweight ReadIndex heartbeat before reading local state.

Group Commit & ReadIndex

Leader WAL Group Commit + Linearizable ReadIndex Path

1.1. Group Commit: Coalescing concurrent writes into one fsync multiplies throughput 10x-30x.

2.2. ReadIndex: Leader confirms majority heartbeat before serving reads, blocking zombie-leader stale reads.

3.3. Snapshots: Periodic snapshots bound WAL disk growth and speed up lagging follower catch-up.

Dedicated NVMe WALs + ReadIndex + snapshots keep consensus both strictly linearizable and low-latency.
