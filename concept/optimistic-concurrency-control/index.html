THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Use atomic compare-and-swap (`UPDATE ... WHERE id = ? AND version = ?` or HTTP `If-Match`) when conflicts are rare (<5%), and pair retries with exponential backoff and full jitter.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Holding database row locks across network calls or human think-time (like editing a document or checking out a shopping cart) stalls concurrent users and can saturate connection pools in milliseconds. Optimistic Concurrency Control (OCC) eliminates lock waiting on the read path, achieving high throughput with a single round-trip compare-and-swap at write time.

  • Every mutable record carries a monotonically increasing version integer, timestamp, or opaque ETag that changes on every successful write.
  • Reads are completely lock-free; the writer computes the new state in memory and issues a conditional write (WHERE id = 1ANDversion=1 AND version =1ANDversion=2).
  • If 0 rows are affected (SQL) or ConditionalCheckFailedException (DynamoDB) / 412 Precondition Failed (HTTP) is returned, the write is rejected.
  • Safe automatic retries require idempotent, side-effect-free computation and exponential backoff with full jitter to avoid synchronized retry thundering herds.
  • Never use client-supplied wall-clock timestamps (updated_at) for OCC comparisons—clock skew and 1ms collisions silently cause lost updates.

Good candidates

  • Low-to-moderate contention workloads (conflict rate < 5–10%) such as user profile updates, CMS edits, or Kubernetes controller reconciliations.
  • Stateless HTTP/REST APIs where holding a database transaction open while a user edits a form is impossible—use ETag + If-Match headers.
  • Distributed NoSQL stores (DynamoDB, Cosmos DB, Cassandra) where cross-node pessimistic locks are expensive or unavailable.

Think twice

  • High-contention hot keys (e.g., 500 concurrent requests decrementing a single flash-sale SKU or incrementing a global sequence) where >20% conflicts trigger retry storms.
  • Multi-record financial transfers requiring strict isolation across several rows where pessimistic locking or serializable transactions are simpler to reason about.
  • Operations with irreversible external side effects (charging a credit card, sending an email) inside the optimistic retry loop.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioMultiple controllers and kubectl users concurrently patch Deployment objects in the Kubernetes API server backed by etcd.

The idea

Formalized by Kung and Robinson (1981), Optimistic Concurrency Control (OCC) bets that conflicts between concurrent transactions are the exception rather than the rule.

Instead of acquiring locks before reading data, a transaction proceeds in three phases:

  1. Read: Fetch the record and its current version (or ETag) without locking.
  2. Modify: Compute the new state locally in memory.
  3. Validate & Commit: Atomically write the new state only if the stored version still equals the version read in step 1, incrementing it to version + 1 in the same atomic statement.

Concrete walkthrough

Consider two fulfillment workers (Worker A and Worker B) updating an order's shipping address and status simultaneously:

  1. Both workers read order_id = 9001 at version = 42.
  2. Worker A executes UPDATE orders SET status = 'PACKED', version = 43 WHERE id = 9001 AND version = 42. Postgres acquires a brief row-level write lock, sees version = 42, updates the row, and returns rows_affected = 1.
  3. 5ms later, Worker B executes UPDATE orders SET address = 'BLR-2', version = 43 WHERE id = 9001 AND version = 42. Postgres evaluates the WHERE predicate against the newly committed row (version = 43), finds 0 matching rows, and returns rows_affected = 0.
  4. Worker B detects rows_affected == 0, sleeps for a jittered 18ms backoff, re-reads order_id = 9001 at version = 43, applies its address change, and succeeds at version = 44.

Both workers read version 42 without locking; Worker A's atomic compare-and-swap advances the row to 43, forcing Worker B to re-read and retry.

OCC across HTTP, SQL, and NoSQL

The exact same compare-and-swap primitive appears under different names across protocols:

  • HTTP / REST (RFC 9110): Server returns ETag: "v42" on GET. Client sends If-Match: "v42" on PUT/PATCH; server returns 412 Precondition Failed on mismatch.
  • PostgreSQL / MySQL: UPDATE items SET qty = 1,version=version+1WHEREid=1, version = version + 1 WHERE id =1,version=version+1WHEREid=2 AND version = $3. JPA automates this with @Version.
  • DynamoDB: ConditionExpression: "version = :v" returning ConditionalCheckFailedException.
  • Redis: WATCH key -> MULTI -> SET key val -> EXEC (returns nil if key changed between WATCH and EXEC).

Failure modes

  1. Hot-Key Contention Collapse: At 30%+ conflict rates, OCC spends more DB IOPS failing and re-reading than committing. Switch hot keys to pessimistic FOR UPDATE, atomic SQL increments (SET qty = qty - 1 WHERE qty >= 1), or a single-writer queue.
  2. Lost Updates via Nullable Versions: Backfilling a version column with NULL breaks WHERE version = NULL in SQL (NULL = NULL evaluates to UNKNOWN). Always initialize version BIGINT NOT NULL DEFAULT 1.
  3. Retry Loops Without Jitter: Fixed 50ms retries synchronize colliding workers into repeated collisions.

Implementing jittered retries in Java/Python

Wrap only the pure read-compute-CAS block in a bounded retry helper (e.g., 3–5 attempts) using full jitter:

for attempt in range(max_attempts):
    record = repo.get(order_id)
    updated = record.apply_change(cmd)
    if repo.compare_and_swap(updated, expected_version=record.version):
        return updated
    sleep_ms = random.uniform(0, min(cap_ms, base_ms * (2 ** attempt)))
    time.sleep(sleep_ms / 1000.0)
raise ConflictError("Max OCC retries exceeded")

Notice that external calls (HTTP webhooks, emails) must happen after compare_and_swap returns True (or be persisted in an outbox table within the same transaction).

Practical checklist

  • Use monotonic integers (BIGINT NOT NULL DEFAULT 1) or server-generated ETags—never wall-clock timestamps.
  • Assert rows_affected == 1 on every SQL CAS update; treat 0 as a conflict exception.
  • Enforce If-Match on public PUT/PATCH APIs and return 412 Precondition Failed on mismatch.
  • Measure conflict rates: Alert if OCC retry rates exceed 10% on any table so you can switch hot keys to pessimistic or atomic-delta patterns.
  • Keep side effects out of the retry loop to prevent duplicate charges or notifications.
03 / Engineering trade-offs

Weighing architectural decisions

Throughput vs. Retry Overhead

Advantage: Zero lock contention and 1-RTT writes when conflicts are rare.

Drawback: Under heavy contention (>20% conflict rate), wasted work and retries degrade throughput worse than queuing behind a pessimistic lock.

Long-Lived User Sessions

Advantage: Works seamlessly across disconnected HTTP requests using `ETag` and `If-Match`.

Drawback: Users who spend 10 minutes editing a form get a `412 Precondition Failed` and must manually merge or reload.

Implementation Simplicity

Advantage: Avoids deadlocks and lock-wait timeouts completely.

Drawback: Requires explicit retry loops (for automated workers) or conflict-resolution UI (for humans) on every write path.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Retry Storm (Thundering Herd)

100 workers hit a conflict on the same record and immediately retry in a tight `while True` loop, multiplying DB load by 10x.

What helps: Cap retries (e.g., max 3–5 attempts) and apply exponential backoff with full jitter (`sleep(random(0, min(cap, base * 2^attempt)))`).

ABA / Timestamp Collision Problem

Using `updated_at` timestamps instead of an integer `version` lets two writes within the same millisecond or across NTP clock drift pass the condition check.

What helps: Always use a strictly monotonic integer (`version = version + 1`) or storage-assigned revision/ETag.

Side-Effect Duplication on Retry

A worker charges a payment gateway, fails the DB version check, retries the whole function, and charges the customer twice.

What helps: Keep external side effects outside the OCC retry loop (e.g., use the Transactional Outbox pattern) or pass idempotency keys.

Missing `If-Match` Enforcement in APIs

Making `If-Match` optional allows old mobile clients to omit the header and silently overwrite newer server state.

What helps: Return `428 Precondition Required` when `If-Match` is missing on mutable `PUT`/`PATCH` endpoints.

05 / Practical checklist

Avoid these mistakes

  • Incrementing `version` in application memory before checking it, or forgetting to include `AND version = :old_version` in the SQL `WHERE` clause.
  • Checking the affected row count incorrectly—many ORMs silently succeed on `UPDATE` affecting 0 rows unless you explicitly assert `rowsAffected == 1` (e.g., JPA `OptimisticLockingFailureException`).
  • Using OCC on a global counter or flash-sale inventory row where 1,000+ users contend on a single key.
  • Retrying indefinitely without a circuit breaker or max-attempt limit.
  • Returning `500 Internal Server Error` instead of `409 Conflict` or `412 Precondition Failed` when a version mismatch occurs.
