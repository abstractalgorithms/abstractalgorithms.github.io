Control.

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Optimistic Concurrency Control (OCC).

Why this matters: The mechanism: understand how Optimistic Concurrency Control (OCC) works from first principles.

Formalized by Kung and Robinson (1981), Optimistic Concurrency Control (OCC) bets that conflicts are the exception. Instead of acquiring locks before reading, a transaction runs in three phases: Read (fetch record + monotonic version or ETag), Modify (compute new state in memory), and Validate/Write (execute an atomic compare-and-swap such as UPDATE ... SET version = version + 1 WHERE id = $1 AND version = $2).

If 0 rows are affected—or DynamoDB raises ConditionalCheckFailedException or HTTP returns 412 Precondition Failed—the writer aborts and retries or prompts the user.

Compare-And-Swap Race

Two Concurrent Writers Resolved by Monotonic Version

Zero read locks are held; Worker B detects the concurrent write atomically at commit time instead of silently overwriting Worker A.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need OCC (and why wall-clock timestamps fail).

Why this matters: The problem: see what breaks without OCC under real concurrency or scale.

Holding database row locks across network calls or human think-time (like editing a document or checking out a cart) stalls concurrent users and saturates connection pools.

OCC eliminates lock waiting on reads.

Engineering Decision Framework
Problem
How to implement Optimistic Concurrency Control without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
If disk I/O or compaction stalls threaten tail latency, use atomic compare-and-swap (UPDATE ... WHERE id = ? AND version = ? or HTTP If-Match) when conflicts are rare (<5%), and pair retries with exponential backoff and full jitter.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.
Decision Exercise · Make the Call

When Optimistic Concurrency Control experiences a sudden 5x traffic spike alongside a slow downstream dependency, which engineering choice best protects system stability?

Full Jitter Stops Retry Storms

If 100 workers collide on v=42 and retry in a tight loop, DB load multiplies 10x. Cap attempts (3–5) and sleep random(0, min(cap, base * 2^attempt)).

Keep Side Effects Outside the Retry Loop

Never charge a credit card inside an OCC loop; if the DB CAS fails and retries, you double-charge the customer. Use a Transactional Outbox instead.

Component Topology

How OCC Retry Loops and `If-Match` APIs are implemented

import random, time

def update_with_occ(repo, order_id: str, cmd, max_attempts: int = 4, base_ms: int = 20, cap_ms: int = 400):
    for attempt in range(max_attempts):
        record = repo.get(order_id)
        updated = record.apply_change(cmd)
        # Executes: UPDATE orders SET ..., version = version + 1 WHERE id = %s AND version = %s
        if repo.compare_and_swap(updated, expected_version=record.version):
            return updated
        sleep_ms = random.uniform(0, min(cap_ms, base_ms * (2 ** attempt)))
        time.sleep(sleep_ms / 1000.0)
    raise ConflictError("Max OCC retries exceeded")

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: HTTP `ETag` + PostgreSQL MVCC Version Guard.

Why this matters: Production architecture: see how the components compose end to end under real load.

A REST API serves ETag: "42" on GET /orders/9001.

Clients send If-Match: "42" on PATCH.

Storage-Layer CAS

HTTP If-Match -> PostgreSQL MVCC Version Check

1.1. Strict Precondition: Requests omitting If-Match receive 428 Precondition Required so old clients cannot silently clobber state.

2.2. Row-Level CAS: Postgres acquires a brief tuple lock only for the commit instant of the UPDATE statement.

3.3. Deterministic Status: 0 rows affected returns 412 Precondition Failed, never 500 Internal Server Error.

MVCC + versioned WHERE clauses enforce lock-free safety across disconnected HTTP clients.
