Terraform Modules
& State.

Terraform modules package reusable infrastructure patterns behind versioned input/output contracts, while the state file (terraform.tfstate) maps those HCL resource blocks to real cloud IDs. Treating state as a concurrency-locked, blast-radius-scoped database—never a shared monolith—is what keeps Infrastructure as Code safe at scale.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Split state by environment and lifecycle tier, store it in encrypted remote backends with native locking, pin versioned modules, and use `for_each` instead of `count` to avoid accidental resource destruction.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

A single misconfigured terraform apply against a monolithic state file can destroy a production RDS database or lock out an entire engineering org for hours. Clean module boundaries and isolated, locked remote state turn risky manual cloud clicks into repeatable, peer-reviewed changes.

  • State is the source of truth for resource mapping: terraform.tfstate links aws_db_instance.main to arn:aws:rds:... and caches attributes—never commit it to Git because it stores secrets in plaintext.
  • Enforce remote state locking: Use S3 (use_lockfile = true in Terraform 1.10+ or DynamoDB), GCS, or Terraform Cloud so two concurrent apply runs cannot corrupt state.
  • Keep modules shallow and composable: Pass dependencies via explicit inputs/outputs (composition) rather than nesting 5 levels of modules or abusing terraform_remote_state.
  • Prefer for_each over count for lists of resources: removing item [0] with count shifts every subsequent index and destroys/recreates unrelated resources.
  • Use moved and import blocks (Terraform 1.5+) to refactor module names or adopt existing cloud resources cleanly via PRs without terraform state rm/mv CLI surgery.

Good candidates

  • Provisioning repeatable cloud foundations (VPCs, EKS/GKE clusters, IAM roles, RDS instances) across dev, staging, and production.
  • Platform teams exposing 'golden path' self-service modules with baked-in encryption, tagging, and security baselines.
  • Multi-engineer teams requiring atomic state locking, drift detection, and PR-based terraform plan previews.

Think twice

  • Fast-changing application deployments (container image tags, Kubernetes Pods/Deployments)—use Helm, ArgoCD, or Flux instead of Terraform.
  • Putting 500+ unrelated resources (network + DB + 30 microservices) into one giant terraform.tfstate, making every plan take 15 minutes.
  • Ad-hoc one-off data migrations or imperative tasks better handled by scripts or Ansible.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn engineer renames module.postgres to module.orders_db inside a production Terraform root module. A naive terraform plan shows 1 to destroy (aws_db_instance), 1 to add.

The idea

Terraform is declarative: you describe what infrastructure should exist in HCL, and Terraform computes the DAG (Directed Acyclic Graph) to reconcile current reality with your desired config. Modules provide abstraction and reuse—encapsulating a group of resources (e.g., a multi-AZ VPC with flow logs and NAT gateways) behind typed variable inputs and output values.

State (terraform.tfstate) is the bridge between abstract HCL names (module.vpc.aws_subnet.private["us-east-1a"]) and concrete cloud IDs (subnet-0a1b2c3d). Without state, Terraform wouldn't know which cloud resources it owns versus what was created elsewhere, nor could it detect deletions or compute minimal diffs without scanning every API in your AWS/GCP account.

Concrete walkthrough

Consider promoting a v1.3.0 PostgreSQL module change through a layered CI/CD workflow:

  1. Module Authoring: The platform team updates terraform-aws-rds (adding encrypted read-replica support), runs terraform test against an ephemeral sandbox, and tags v1.3.0.
  2. Root Module Update: An app team bumps source = "git::https://.../terraform-aws-rds.git?ref=v1.3.0" in envs/prod/orders-db/main.tf and opens a PR.
  3. Locked Plan in CI: GitHub Actions (with a per-directory concurrency group) acquires the S3/DynamoDB state lock (LockID), downloads terraform.tfstate (serial: 42), refreshes live AWS RDS attributes, and posts the exact diff (~ update in-place, +1 read_replica) on the PR.
  4. Serialized Apply: After peer approval and merge, CI acquires the lock again, verifies the plan matches, creates the replica via AWS APIs, and writes serial: 43 back to the KMS-encrypted S3 bucket before releasing the lock.
  5. Downstream Consumption: The module writes the new read-replica endpoint to AWS SSM Parameter Store (/prod/orders-db/ro_endpoint), which the EKS app layer reads via data "aws_ssm_parameter"—avoiding terraform_remote_state coupling.

Atomic state locking and version-pinned modules prevent concurrent corruption and accidental cross-environment drift.

Module boundaries, for_each & refactoring

Follow flat module composition: keep root modules as thin wiring layers that call 1–2-level-deep child modules (network, eks, rds) rather than deeply nested 'god modules' that hide 80 variables behind one giant abstraction. Every child module should expose narrow, strongly typed variable blocks with validation {} rules and nullable = false where appropriate.

When refactoring HCL names or importing legacy cloud resources, never edit terraform.tfstate by hand. Use declarative moved {} blocks to rename resource/module addresses safely in Git, and import {} blocks (available since Terraform 1.5) to generate HCL and adopt pre-existing cloud resources via standard PR review.

Failure modes

1. Partial Apply Leaving Tainted State: An apply fails halfway through (e.g., IAM role created, RDS times out after 20 min). Terraform still saves the partial state up to the point of failure; re-running apply resumes from the checkpoint, though failed creation resources may be marked tainted for replacement.

2. Circular Dependencies Between Root Modules: Splitting network and security into two states fails if network needs an output from security and vice versa. Always enforce a strict acyclic dependency hierarchy (00-org-iam → 01-network → 02-platform → 03-apps).

3. State File Corruption from -force-unlock: Running terraform force-unlock while a slow CI job is actually still applying causes two writers to race. Always verify in CI logs that the holding process is truly dead before unlocking.

Protecting state secrets & stateful resources

Because terraform.tfstate stores sensitive outputs and resource attributes in plaintext JSON, treat the state bucket like a production database: enable S3/GCS Object Versioning (for instant rollback if state is corrupted), KMS encryption, and strict IAM (developers get read-only or PR-plan access; only the CI OIDC role can write state).

For irreversible resources (RDS instances, KMS keys, S3 data buckets), add lifecycle { prevent_destroy = true } inside the module so any accidental deletion triggers an immediate hard error during plan.

Practical checklist

  • Store all terraform.tfstate files in versioned, KMS-encrypted remote backends with locking enabled (never in Git).
  • Split monolithic states into layered root modules by environment and change frequency (network, platform, apps).
  • Pin module versions (?ref=vX.Y.Z) and commit .terraform.lock.hcl for deterministic provider binaries.
  • Replace count with for_each on any resource list where items can be added or removed in the middle.
  • Use declarative moved and import blocks in PRs instead of manual terraform state mv/rm commands.
  • Add lifecycle { prevent_destroy = true } to stateful databases, KMS keys, and production storage buckets.
03 / Engineering trade-offs

Weighing architectural decisions

Monolithic State vs. Layered Root Modules

Advantage: Monolithic state allows direct HCL references (`aws_vpc.main.id`) across all resources in one `apply`.

Drawback: Slow plans, huge blast radius, and frequent lock contention; layered states require reading outputs via SSM/data sources.

Git-Tag Pinned Modules vs. Local Relative Paths

Advantage: Versioned registry/Git tags (`?ref=v2.4.0`) let dev adopt breaking module changes before prod.

Drawback: Local paths (`../modules/vpc`) force every environment onto the same module code simultaneously, risking prod breakage on refactor.

`terraform_remote_state` vs. Cloud Parameter Store / Data Sources

Advantage: `terraform_remote_state` is built-in and requires zero extra AWS/GCP resources.

Drawback: Grants read access to the entire upstream state JSON (including secrets!) and tightly couples consumer directories to upstream output schemas.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Concurrent Apply Without State Locking

Two engineers or CI jobs run `terraform apply` simultaneously against an unlocked S3 bucket; the second write overwrites the first's newly created resources, orphaning live cloud infrastructure.

What helps: Enable `use_lockfile = true` (S3 native lock in Terraform 1.10+) or DynamoDB lock tables and run all applies strictly from serialized CI pipelines (Atlantis, Spacelift, GitHub Actions concurrency groups).

Index-Shift Destruction from `count`

Removing the first subnet or IAM user from a `list(string)` passed to `count = length(var.users)` shifts indices `1..N` down by one, forcing Terraform to destroy and recreate `N` live resources.

What helps: Always use `for_each = toset(var.users)` or `tomap(...)` so resources are keyed by stable string identifiers instead of integer array positions.

Plaintext Secrets Exposed in `terraform.tfstate`

Marking a variable `sensitive = true` hides it from CLI stdout, but `random_password`, `aws_db_instance.password`, and TLS private keys are still stored in plaintext inside the state JSON.

What helps: Encrypt state buckets with KMS, restrict IAM `s3:GetObject` strictly to CI runners, and prefer ephemeral write-only attributes (`password_wo` in Terraform 1.11+) or Secrets Manager generation.

Manual Console Changes Causing Silent Drift

An engineer emergency-edits a Security Group rule in the AWS Console; the next unrelated `terraform apply` silently reverts the rule back to the old HCL definition.

What helps: Run scheduled daily `terraform plan -detailed-exitcode` drift-detection jobs and enforce read-only console access in production.

05 / Practical checklist

Avoid these mistakes

  • Using `terraform.workspace` (`dev`/`prod`) with shared backend configs when environments have different architectures—prefer separate directories/root modules for prod isolation.
  • Leaving `terraform_remote_state` IAM permissions open to developers, exposing plaintext DB passwords stored in upstream state files.
  • Running `terraform apply -auto-approve` locally from laptops instead of reviewing `plan` output in a pull request.
  • Forgetting `prevent_destroy = true` lifecycle rules on stateful databases, KMS keys, and S3 buckets.
  • Hardcoding provider versions (`~> 5.0` vs unpinned) inconsistently without committing `.terraform.lock.hcl` to Git.
