Supply Chain Security
& SBOMs.

A Software Bill of Materials (SBOM) is a machine-readable inventory (SPDX or CycloneDX) of every direct and transitive package, OS layer, and binary inside a build artifact. Paired with cryptographic attestations (Cosign/Sigstore) and VEX advisories, it lets teams answer 'Are we exposed to CVE-X?' in seconds rather than days.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Generate CycloneDX or SPDX SBOMs inside your CI build, sign them with Sigstore Cosign alongside the container digest, and filter noise with VEX before blocking deploys.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Modern applications pull 80–90% of their code from open-source dependencies, often 5–10 transitive levels deep. When a zero-day like Log4Shell (CVE-2021-44228) or XZ Utils (CVE-2024-3094) drops, teams without an indexed SBOM waste days cloning repos and grepping lockfiles while attackers scan exposed endpoints in minutes.

  • Choose CycloneDX (OWASP, security/VEX-first, lighter JSON) or SPDX (Linux Foundation / ISO 5962, license/compliance-first)—both are supported by Syft, Trivy, and Dependency-Track.
  • Generate SBOMs against the final built artifact (OCI image digest sha256:... or compiled binary), not just package.json or pom.xml, so OS packages and vendored C libraries are captured.
  • Attach and sign SBOMs as OCI referrers using Sigstore Cosign (cosign attach sbom + cosign sign) so consumers can verify the inventory came from your trusted CI runner.
  • Use VEX (Vulnerability Exploitability eXchange) or reachability analysis to suppress false positives where a vulnerable function is never compiled or called.
  • Ingest all release SBOMs into a central graph store (OWASP Dependency-Track, Guac) to enable instant reverse-lookup: package:purl -> affected services.

Good candidates

  • Containerized and cloud-native services shipping to production where fast blast-radius queries across hundreds of microservices are critical.
  • Enterprise B2B software, FedRAMP, or US Executive Order 14028 compliance where customers demand verifiable SPDX/CycloneDX manifests per release.
  • CI/CD pipelines enforcing policy gates (OPA/Kyverno) to block unapproved licenses (AGPL) or critical reachable CVEs before admission.

Think twice

  • Throwaway prototypes, internal hackathons, or ephemeral scripts with no external distribution or production data access.
  • Treating raw SBOM generation as a standalone security control—an SBOM without vulnerability matching (Grype/Trivy) and signature verification is just a static JSON file.
  • Scanning source repos only while ignoring OS base-image packages (glibc, openssl, curl) that enter during docker build.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA critical RCE vulnerability is disclosed in org.apache.commons:commons-text:1.9. The platform team manages 140 Java and Python microservices deployed across 3 EKS clusters.

The idea

A Software Bill of Materials (SBOM) is the software equivalent of a food nutrition label: a standardized, machine-readable graph of every component, version, Package URL (purl), license, and cryptographic hash inside a deliverable. The two dominant formats are SPDX (ISO/IEC 5962, strong on licensing and file-level provenance) and CycloneDX (OWASP, designed for security, services, and VEX).

An SBOM alone only answers what is inside a build. Its operational power comes from pairing it with SLSA provenance (proving how and where it was built), Sigstore Cosign signatures (proving integrity against tampering), and VEX (proving exploitability so teams fix real risks instead of chasing phantom CVEs).

Concrete walkthrough

Here is how a hardened GitHub Actions pipeline produces and enforces an SBOM for a Go/Python microservice:

  1. Build Immutable Artifact: docker buildx build --push produces ghcr.io/acme/billing@sha256:8f91... from pinned lockfiles (poetry.lock / go.sum).
  2. Generate SBOM: syft ghcr.io/acme/billing@sha256:8f91... -o cyclonedx-json=sbom.cdx.json catalogs both OS apk/dpkg layers and language packages with standardized purls.
  3. Attest & Sign (Keyless OIDC): cosign attest --predicate sbom.cdx.json --type cyclonedx ghcr.io/acme/billing@sha256:8f91... mints an ephemeral Fulcio certificate tied to the GitHub OIDC token, logs the signature in Rekor, and pushes the signed attestation as an OCI referrer.
  4. Ingest & Match: CI uploads sbom.cdx.json to OWASP Dependency-Track and runs grype sbom:sbom.cdx.json --vex openvex.json --fail-on critical.
  5. Admission Gate: Before Kubernetes schedules the pod, Kyverno verifies the Cosign attestation signature against the trusted GitHub Actions OIDC issuer and confirms no unwaived CRITICAL KEV vulnerabilities exist.

Binding signed SBOMs to immutable OCI digests ensures runtime admission controllers verify the exact dependency graph.

SPDX, CycloneDX & Package URLs (purls)

Both NTIA-minimum-element formats share the same core goal—identifying supplier, component name, version, unique identifier, dependency relationship, author, and timestamp—but optimize for different workflows. Package URL (purl) acts as the universal primary key across both: pkg:npm/%40babel/core@7.24.0 or pkg:deb/debian/openssl@3.0.11-1~deb12u2?arch=amd64.

Without standardized purls and CPEs, vulnerability databases (OSV, NVD, GitHub Advisory Database) cannot reliably join an SBOM entry to a CVE. Always prefer tools that emit purl + sha256 hashes for every component rather than fuzzy name/version strings.

Failure modes

1. Language-Specific Blind Spots: Running syft on a stripped static C++ binary yields zero package metadata unless debug symbols or build-time Conan/vcpkg manifests are included. For C/C++/Rust, generate the SBOM during the build step (cargo-cyclonedx) and merge it with the container-layer SBOM.

2. NVD CPE Matching False Positives: Naive NVD lookups match cpe:2.3:a:vendor:product:* loosely, flagging irrelevant CVEs. Prefer OSV-backed matchers (Grype, osv-scanner) that match exact purls and commit ranges.

3. Unbounded SBOM Size in Monorepos: A single multi-stage image with leftover build caches can produce a 40 MB JSON SBOM, timing out registry pushes. Use multi-stage builds (FROM scratch or Distroless) so runtime images contain only production artifacts.

Scaling triage with VEX and SLSA provenance

At >50 services, raw SBOM scanning creates unsustainable toil. Combining EPSS (Exploit Prediction Scoring System) with OpenVEX solves this: prioritize patching CVEs with EPSS > 0.1 or listed in CISA KEV, and issue signed VEX statements (status: not_affected, justification: vulnerable_code_not_present) for false positives so they stay suppressed across future scans.

Simultaneously, pair your CycloneDX/SPDX SBOM with SLSA Build Level 2/3 provenance (actions/attest-build-provenance). While the SBOM lists what is in the box, SLSA provenance cryptographically proves which Git commit and which isolated CI runner produced it—preventing a compromised developer laptop from pushing a malicious image with a forged SBOM.

Practical checklist

  • Pin all transitive dependencies with lockfiles (package-lock.json, poetry.lock, go.sum, Cargo.lock) and verify hashes in CI.
  • Generate CycloneDX or SPDX SBOMs against the final built OCI image digest (sha256:...), not just source directories.
  • Strip dev/test dependencies and build-time toolchains via multi-stage Dockerfiles before SBOM generation.
  • Sign and attach SBOMs as in-toto attestations using cosign attest with keyless OIDC.
  • Ingest all release SBOMs into a central store (Dependency-Track) to enable sub-minute zero-day impact queries.
  • Adopt OpenVEX and EPSS/CISA KEV thresholds so CI gates block real exploitable risks without stalling on unreachable CVEs.
03 / Engineering trade-offs

Weighing architectural decisions

Build-Time vs. Post-Build Image Scanning

Advantage: Build-time generators (Maven/Gradle CycloneDX plugins) see exact resolved scopes (`compile` vs. `test`) and avoid false positives on dev dependencies.

Drawback: Post-build image scanners (Syft, Trivy) capture OS packages (`apt`/`apk`) and native binaries that language plugins miss.

Strict CI Blocking vs. Advisory Reporting

Advantage: Failing builds on `CRITICAL` CVEs prevents known-exploitable code from ever reaching registries.

Drawback: Zero-day disclosures with no upstream patch yet can freeze hotfix deploys unless VEX waivers or grace windows exist.

SPDX vs. CycloneDX Format

Advantage: SPDX is an ISO/IEC 5962 standard favored by legal/licensing teams and government procurement.

Drawback: CycloneDX offers native support for VEX, SaaSBOM, and ML-BOMs with simpler schema ergonomics for AppSec tooling.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Stale SBOM Drift After Base Image Rebuild

A team generates an SBOM once from source lockfiles, but later rebuilds the Docker image with `FROM python:3.12-slim` pulling newer vulnerable `libssl` packages, leaving the stored SBOM out of sync.

What helps: Bind SBOM generation to the immutable OCI image digest (`sha256:...`) inside the final release job and reject images without matching digest attestations.

Missing Transitive or Vendored Dependencies

Go binaries compiled with `CGO_ENABLED=1` or Python wheels bundling `.so` C extensions hide native C/C++ libraries from naive lockfile parsers.

What helps: Use ELF/Mach-O/PE binary inspection (Syft/Trivy binary catalogers) and compile Go with `-buildvcs=true` so `debug.BuildInfo` embeds module hashes.

Unsigned SBOMs Vulnerable to Tampering

An attacker who compromises an artifact registry replaces the plain JSON SBOM file to hide a backdoored dependency.

What helps: Sign the SBOM as an in-toto attestation using `cosign attest --predicate sbom.cdx.json --type cyclonedx` and verify signatures in Kubernetes via Kyverno.

Alert Fatigue from Unreachable CVEs

Raw SBOM matching floods Slack/Jira with 500+ CVEs per week, mostly in `test` scopes or uncalled functions, causing engineers to ignore all alerts.

What helps: Exclude `test`/`dev` scopes during SBOM generation, prioritize via EPSS (>0.1) + CISA KEV, and layer OpenVEX/reachability filtering.

05 / Practical checklist

Avoid these mistakes

  • Generating an SBOM from `requirements.txt` without pinned hashes (`pip freeze`) or lockfiles, missing transitive dependency versions.
  • Storing SBOM JSONs as ephemeral CI build logs instead of attaching them to OCI registries or ingesting them into Dependency-Track/Guac.
  • Including `devDependencies` (`jest`, `pytest`, `eslint`) in production SBOMs, inflating CVE counts by 3–5x.
  • Ignoring Package URL (`purl`) standardization (`pkg:pypi/requests@2.32.3`), breaking automated correlation across scanners.
  • Treating SBOM compliance as a one-time PDF export rather than continuous monitoring as new CVEs are published daily.
