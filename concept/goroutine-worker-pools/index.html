01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is a Goroutine Worker Pool.

Goroutines start at just 2 KB of stack, making it tempting to write go process(item) inside a million-item loop. Go's M:N scheduler multiplexes goroutines (G) onto OS threads (M) across P = GOMAXPROCS logical processors using work-stealing and an epoll/kqueue netpoller.

A goroutine worker pool places a fixed ceiling N on active workers pulling from a bounded jobs channel, ensuring downstream databases, APIs, and OS file descriptors (ulimit -n) never collapse under a thundering herd.

Bounded Pipeline

Producer -> Bounded Job Channel -> N Workers -> Shared Transport

1.Backpressure: When the 1,000-slot channel fills, producers block or fail fast with 429/503 instead of OOMing.

2.Netpoller Yield: Network I/O parks G in epoll/kqueue without blocking OS thread M.

3.Container Quota: Use uber-go/automaxprocs in Kubernetes so GOMAXPROCS matches cgroup CPU quota, not host cores.

A bounded channel + fixed N workers decouples spike ingestion from downstream connection limits.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Unbounded Goroutines Cause Port Exhaustion & Leaks.

Spawning 50,000 concurrent goroutines for a webhook burst opens 42,000+ ephemeral TCP sockets—triggering connect: cannot assign requested address and too many open files. Meanwhile, a goroutine blocked on an unbuffered send when the caller already timed out leaks forever in heap.

Always Select on `ctx.Done()`

Wrap every channel send and receive in select { case ch <- val: case <-ctx.Done(): return } so canceled callers never leak workers.

Single-Owner Channel Closing

Only the producer/coordinator closes jobs after all senders finish (defer close(jobs)); closing on the receiver side panics.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Sizing Pools for I/O-Bound vs. CPU-Bound Workloads.

Pool size N depends on whether workers wait on network sockets or saturate CPU cores.

ChoiceWhat it buysWhat it costs
I/O-Bound Fan-Out (Webhooks, S3, RPC)Size `N = 10–200` matched to downstream rate limits and `http.Transport.MaxConnsPerHost`.Without per-job `context.WithTimeout`, one slow tenant causes head-of-line blocking across the shared pool.
CPU-Bound Batch (Hashing, Image Resize)Size `N = runtime.GOMAXPROCS(0)` (with `automaxprocs` in containers) to prevent CFS CPU throttling.Exceeding CPU quota increases context-switch and cache-miss overhead without extra throughput.
Avoid: Strict Per-Key OrderingShard jobs by `hash(key) % N` into `N` dedicated single-worker channels.A single shared worker pool processes keys out of order.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Context-Safe Worker Pool with Bounded Queue & WaitGroup.

Use a bounded jobs channel, sync.WaitGroup for clean drain, and select on ctx.Done() to prevent goroutine leaks during SIGTERM shutdowns.

package pool

import (
	"context"
	"sync"
)

func RunWorkerPool[T any](ctx context.Context, workers int, jobs <-chan T, fn func(context.Context, T) error) {
	var wg sync.WaitGroup
	wg.Add(workers)
	for i := 0; i < workers; i++ {
		go func() {
			defer wg.Done()
			for {
				select {
				case <-ctx.Done():
					return
				case job, ok := <-jobs:
					if !ok {
						return
					}
					_ = fn(ctx, job)
				}
			}
		}()
	}
	wg.Wait()
}

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Fixed Worker Pool vs. errgroup.SetLimit vs. Keyed Shards.

Compare long-lived worker pools against scoped errgroup concurrency limits.

ChoiceWhat it buysWhat it costs
Fixed Worker Pool (`chan` + `WaitGroup`)Reuses long-lived goroutines and per-worker `sync.Pool` buffers; ideal for continuous daemon pipelines.Requires explicit channel-close and drain lifecycle management.
`golang.org/x/sync/errgroup` with `SetLimit(N)`Minimal boilerplate for per-request fan-out/fan-in with automatic first-error context cancellation.Spawns a fresh goroutine per task (2 KB stack each) rather than reusing steady workers.
Key-Sharded Single-Worker ChannelsGuarantees strict per-`tenant_id` or per-`order_id` FIFO ordering while bounding concurrency.Hot keys can saturate one shard while other workers sit idle.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Guards: Race Detector, Backpressure & SIGTERM Drain.

In production Kubernetes pods, pair worker pools with go test -race in CI, automaxprocs for CFS quota alignment, and graceful SIGTERM draining that stops accepting new jobs while letting in-flight workers finish within terminationGracePeriodSeconds.

Graceful Shutdown

SIGTERM Drain Sequence Without Dropping In-Flight Jobs

Closing the jobs channel on SIGTERM lets workers drain buffered tasks cleanly before wg.Wait() exits.
