Artifact Registry
Versioning.

Artifact registry versioning pairs human-readable semantic tags (v1.4.2) with immutable content-addressed digests (sha256:...), ensuring every build, deployment, and rollback runs the exact verified bytes.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Tag for humans, deploy by immutable digest: mutable tags like `:latest` or `:v1` can be overwritten silently, whereas `image@sha256:...` guarantees bit-for-bit reproducibility.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Overwriting a mutable tag like :latest or :prod breaks Kubernetes pod autoscaling—existing pods run old bytes while newly scheduled pods pull different bytes under the same tag. Content-addressed OCI registries (AWS ECR, Google Artifact Registry, Harbor, GHCR) store layers by SHA-256 digest and support tag immutability, SBOM attachment, and Cosign cryptographic signatures.

  • Tag vs. Digest: a tag (v2.3.1) is a mutable pointer; a digest (sha256:9f86...) is the cryptographic hash of the OCI manifest JSON, which in turn hashes every layer.
  • Enable tag immutability at the repository level (IMMUTABLE in AWS ECR / GAR) so no CI job can overwrite a released vX.Y.Z tag.
  • OCI Artifacts beyond containers: Helm charts, Wasm modules, SBOMs (SPDX/CycloneDX), and Cosign .sig attestations all live in the same OCI Distribution Spec registry.
  • Semantic Versioning (SemVer MAJOR.MINOR.PATCH) communicates API compatibility for libraries/Helm charts, while Git SHA + timestamp tags (v1.4.2-g8a3f1c) give exact commit traceability for app images.
  • Lifecycle & retention policies: unreferenced digests and PR-preview tags explode storage bills; automate cleanup rules that keep the last NNN prod tags while purging untagged manifests after 7–14 days.

Good candidates

  • Production container, Helm chart, or library pipelines (Maven, PyPI, npm) where deployments and rollbacks must be 100% deterministic.
  • Regulated software supply chains requiring SLSA provenance, SBOMs, and Cosign signature verification via admission controllers (Kyverno/OPA) before pods start.
  • Multi-architecture builds (linux/amd64 and linux/arm64) unified under a single OCI Image Index (manifest list) digest.

Think twice

  • Local docker compose development loops where fast iteration with a local :dev tag is convenient and never leaves your laptop.
  • Storing multi-gigabyte raw ML training datasets or unstructured blobs—use object storage (S3/GCS) with DVC or LakeFS instead of an OCI registry.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA deployment manifest specifies ghcr.io/acme/api:v1.8.0 without a digest, and a hotfix accidentally re-pushes v1.8.0.

The idea

An artifact registry is a content-addressable storage system. Every container image, Helm chart, or language package you push is decomposed into compressed blobs and a JSON manifest whose SHA-256 hash—the digest—uniquely identifies that exact byte sequence. Tags (v1.4.2, latest) are merely human-friendly aliases pointing to a digest. Reliable delivery pipelines separate human naming (immutable SemVer or commit-SHA tags) from machine execution (pinning @sha256:... digests).

Concrete walkthrough

Follow a single build from commit 8a3f1c to production Kubernetes:

  1. Build & Push Once: CI runs docker buildx build --platform linux/amd64,linux/arm64 and pushes gar.dev/acme/orders:1.4.2-8a3f1c to a staging repository with tag immutability enabled.
  2. Capture Digest & Attest: The registry returns the OCI Image Index digest sha256:7c9e.... CI runs Trivy vulnerability scanning, generates a CycloneDX SBOM, and executes cosign sign to attach the signature and SBOM as OCI referrers to sha256:7c9e....
  3. Promote Without Rebuilding: After integration tests pass, CI runs crane copy (or cosign copy) to promote sha256:7c9e... and its attached signatures to the prod registry—zero rebuilds, zero apt-get drift.
  4. Verify & Run: Argo CD updates the Deployment to prod-gar.dev/acme/orders:1.4.2@sha256:7c9e..., and Kyverno verifies the Cosign signature before the kubelet pulls the layers.

Build once, sign by digest, promote without rebuilding, and verify at Kubernetes admission.

Tagging schemes across ecosystems

Different artifact types call for different versioning contracts:

  • Application Containers: Use - (e.g., 2.1.0-9b4e2a1) or CalVer (2026.11.12-9b4e2a1) paired with @sha256:... in deployment manifests. Never reuse a tag.
  • Shared Libraries (npm, PyPI, Maven): Strictly follow SemVer 2.0 (MAJOR.MINOR.PATCH) because downstream package.json or pom.xml resolvers use range constraints (^1.4.0).
  • Helm Charts (OCI): Store charts in OCI registries (oci://ghcr.io/acme/charts/api:1.4.2) with independent chart version (packaging changes) and appVersion (workload version).

Failure modes

  1. Silent Re-Tagging Corruption: Without registry immutability, two concurrent CI runs on the same branch overwrite each other's tags. Fix: turn on IMMUTABLE tag enforcement in ECR/GAR/Harbor.
  2. Base-Image Supply Chain Drift: Using FROM node:20-alpine pulls different packages on Monday vs. Friday. Fix: pin base images to @sha256:... digests.
  3. Broken Rollbacks After GC: A 30-day retention rule deletes the previous release's image while a canary fails. Fix: exempt v* release tags and any digest currently running in production clusters.
  4. Missing Signatures After Promotion: docker pull + docker push strips OCI referrer signatures and changes manifest digests if re-compressed. Fix: use crane copy or cosign copy to preserve exact manifests and attestations.

Lifecycle and cost governance

Unchecked CI pipelines generate terabytes of ephemeral PR-preview images. Separate registries or tag prefixes into two tiers: ephemeral (pr-*, dev-*, purged after 7–14 days) and release (v*, retained for 180–365 days or protected by an active-cluster-digest check). Combine this with multi-stage Docker builds (distroless or alpine) to shrink per-image layer footprints from ~900 MB to <50 MB.

Practical checklist

  • Enable tag immutability on all staging and production OCI repositories.
  • Deploy by @sha256 digest in Kubernetes/GitOps manifests, keeping the human tag as a prefix (api:v1.4.2@sha256:...).
  • Pin base images in every Dockerfile using @sha256:... and automate updates with Renovate.
  • Build once, promote via crane/cosign copy: never re-run docker build per environment.
  • Automate tiered retention: expire untagged manifests in 7 days and pr-* tags in 14 days while protecting active production digests.
03 / Engineering trade-offs

Weighing architectural decisions

Immutable Tags + Digests vs. Mutable Environment Tags (`:staging`, `:prod`)

Advantage: Immutable tags + digests prevent silent drift, cache poisoning, and broken rollbacks.

Drawback: Requires updating GitOps manifests with new tags/digests on every release instead of re-tagging in place.

Single Registry with Promotion vs. Separate Dev/Prod Registries

Advantage: Separate prod registries isolate blast radius, enforce stricter IAM, and simplify retention rules.

Drawback: Requires cross-registry replication (`crane copy` or ECR replication) to preserve digests.

Aggressive Retention Policies vs. Long-Term Audit Archival

Advantage: Expiring PR/dev images after 14 days cuts registry storage costs by 60–80%.

Drawback: Deleting old prod tags breaks `kubectl rollout undo` or autoscaling if a running pod's digest is purged.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Tag Overwrite / Split-Brain Autoscaling

A CI job overwrites `:prod` with new code; existing pods run old code while HPA-scaled pods pull new code under the same tag.

What helps: Enable repository-level tag immutability and deploy strictly via `@sha256:...` digests.

Purging Active Production Digests

An aggressive cleanup policy (`keep last 10 images`) deletes an older image still referenced by a long-running Kubernetes Deployment, causing `ImagePullBackOff` on node scale-up.

What helps: Protect release tags (`v*`) from auto-expiry, or query active cluster digests before running registry garbage collection.

Floating Base Image Drift

A Dockerfile starts with `FROM python:3.12-slim` without a digest; rebuilding the exact same Git commit a week later pulls a different OS/OpenSSL layer.

What helps: Pin base images by digest (`FROM python:3.12-slim@sha256:...`) and automate bumps via Renovate or Dependabot.

Orphaned Multi-Arch Child Manifests

Garbage collection deletes individual `amd64`/`arm64` child manifests if retention rules only match the parent Image Index tag.

What helps: Use OCI-aware registries (ECR, GAR, Harbor v2.8+) that trace manifest-list references during garbage collection.

05 / Practical checklist

Avoid these mistakes

  • Deploying `:latest` or `:main` to staging/production Kubernetes clusters.
  • Leaving tag mutability enabled on production repositories, allowing accidental `docker push` overwrites.
  • Rebuilding artifacts per environment (dev -> staging -> prod) instead of building once, testing, and promoting the exact same SHA-256 digest.
  • Ignoring `imagePullPolicy: IfNotPresent` hazards with mutable tags—nodes cache stale layers while other nodes pull new ones.
  • Forgetting to include `cosign` signatures and SBOMs when copying/promoting images between registries (use `cosign copy` or `crane`).
