STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are Isolation Levels & MVCC Snapshots.

Isolation (the I in ACID) defines which concurrent transaction side effects are visible. While ANSI SQL-92 defined four levels around Dirty Reads, Non-Repeatable Reads, and Phantoms, modern MVCC engines (PostgreSQL, InnoDB, CockroachDB) also confront Read Skew, Lost Updates, and Write Skew.

Under MVCC, readers read a consistent snapshot (xmin/xmax or HLC timestamp) without blocking writers, and writers don't block readers. However, Snapshot Isolation (REPEATABLE READ in Postgres) still allows Write Skew unless upgraded to Serializable Snapshot Isolation (SSI) or Two-Phase Locking (2PL).

MVCC Snapshot Visibility

How MVCC Separates Concurrent Readers from Uncommitted Writers

MVCC lets readers and writers run concurrently without blocking; SSI adds lightweight SIREAD tracking to catch write-skew cycles.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Default Isolation Permits Write Skew & Lost Updates.

PostgreSQL defaults to READ COMMITTED (which permits lost updates on read-modify-write and read skew across statements), and REPEATABLE READ implements Snapshot Isolation (which still permits Write Skew when two transactions read an overlapping premise and update disjoint rows).

Write Skew vs SSI

Concurrent Room Booking: Snapshot Isolation Double-Books vs. SSI Aborts 40001

Because 501 != 502, Snapshot Isolation sees no write-write conflict and commits both; SSI tracks SIREAD locks and aborts Tx2 with SQLSTATE 40001.

On-Call Doctor Write Skew under Snapshot Isolation

Two doctors both queried COUNT(*) WHERE on_call = true (saw 2) and updated their own disjoint rows to false, leaving 0 doctors on call. Switching to SERIALIZABLE (SSI) aborted the second commit with 40001.

Flash-Sale Lost Update under Read Committed

Two threads read stock = 1 in app memory and both wrote 0. Replacing read-modify-write with UPDATE inventory SET stock = stock - 1 WHERE sku = 'X' AND stock > 0 eliminated the race at READ COMMITTED.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Each Isolation Level Fits.

Match isolation level to the invariant scope—you don't always need global SERIALIZABLE if an atomic SQL expression or UNIQUE / EXCLUDE constraint enforces the rule.

ChoiceWhat it buysWhat it costs
Read Committed (PG Default)Lowest overhead; safe for independent single-row writes and atomic `SET bal = bal - 50 WHERE bal >= 50`.Allows read skew and lost updates on app-level read-modify-write.
Repeatable Read / Snapshot IsolationConsistent multi-table reporting and backups without blocking writers.Allows Write Skew on disjoint rows; long transactions block `VACUUM` / undo purge.
Serializable (PG SSI / CockroachDB / Spanner)Eliminates all anomalies including Write Skew automatically.Requires client-side retry loops for `SQLSTATE 40001` aborts under contention.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to manage Retries, Deadlocks & MVCC Bloat.

  1. Retry 40001 & 40P01: Always wrap REPEATABLE READ/SERIALIZABLE transactions in a bounded, jittered retry loop.
  2. Canonical Lock Ordering: When using SELECT ... FOR UPDATE on multiple rows, sort IDs ascending (ORDER BY id) to prevent AB-BA deadlocks.
  3. Bound Snapshot Lifetime: Set idle_in_transaction_session_timeout = '30s', never hold DB transactions open across HTTP/RPC calls, and route long exports to read replicas.
# Idempotent PostgreSQL SERIALIZABLE retry wrapper for SQLSTATE 40001 / 40P01 (Python)
import time, random

def run_serializable(conn, fn, max_attempts: int = 5):
    for attempt in range(max_attempts):
        try:
            with conn.cursor() as cur:
                cur.execute("BEGIN ISOLATION LEVEL SERIALIZABLE")
                result = fn(cur)
                conn.commit()
                return result
        except Exception as err:
            conn.rollback()
            sqlstate = getattr(err, 'sqlstate', None)
            if sqlstate not in ('40001', '40P01') or attempt == max_attempts - 1:
                raise
            time.sleep(random.uniform(0.01, 0.05 * (2 ** attempt)))

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Engine Behavior & Invariant Enforcement.

Two engines claiming the same ANSI level behave differently under the hood.

ChoiceWhat it buysWhat it costs
PostgreSQL (Pure MVCC + SSI)`REPEATABLE READ` prevents phantoms via Snapshot Isolation; `SERIALIZABLE` uses SSI without blocking readers.False-positive `40001` aborts can occur when `SIREAD` locks coarsen to page level.
MySQL InnoDB (MVCC + Next-Key Locks)Locking reads (`FOR UPDATE`) use record + gap locks to stop phantoms.Gap locks frequently cause `Error 1213` deadlocks on concurrent `INSERT ... ON DUPLICATE KEY UPDATE`.
DB Constraints (`UNIQUE` / `EXCLUDE USING gist`)Enforces non-overlapping bookings or uniqueness at engine level even under `READ COMMITTED`.Limited to constraints expressible on a single table/index.
