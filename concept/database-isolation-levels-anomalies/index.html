Database Isolation Levels
& Transaction Anomalies.

Database isolation levels control what concurrent transaction anomalies—dirty reads, non-repeatable reads, phantom reads, and write skew—are permitted in exchange for lower locking or coordination overhead.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Read Committed does not prevent lost updates or read skew; Snapshot Isolation prevents read anomalies via MVCC but still allows write skew unless you use explicit `SELECT FOR UPDATE` or true Serializable isolation.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Most databases default to Read Committed (PostgreSQL, Oracle) or Repeatable Read (MySQL InnoDB), which silently permit race conditions like double-spending, inventory overselling, and broken invariants under concurrent requests—bugs that pass all single-threaded unit tests.

  • ANSI SQL anomalies: Dirty Reads (reading uncommitted writes), Non-Repeatable Reads (row changes between reads), and Phantom Reads (new rows match a WHERE predicate).
  • Beyond ANSI: Read Skew (seeing half of a transfer), Lost Updates (two concurrent x = x + 1 reads), and Write Skew (two transactions read overlapping data and write disjoint rows, breaking an invariant).
  • MVCC (Multi-Version Concurrency Control): readers read a consistent snapshot (xmin/xmax or HLC timestamp) without blocking writers, and writers don't block readers.
  • Snapshot Isolation vs. Serializable: Snapshot Isolation eliminates read skew and phantoms, but only Serializable (e.g., Postgres SSI or Spanner 2PL+TrueTime) prevents Write Skew.
  • Application retry loops are mandatory: optimistic/SSI engines abort conflicting transactions with SQLSTATE 40001 (serialization_failure), requiring idempotent client retries.

Good candidates

  • Use Read Committed for high-throughput, independent single-row writes and non-critical reads where slight point-in-time skew is acceptable.
  • Use Snapshot Isolation / Repeatable Read for consistent multi-table reporting, backups, and read-only analytics without blocking writers.
  • Use Serializable (SSI or 2PL) or explicit SELECT ... FOR UPDATE when enforcing cross-row invariants (account balances, double-booking prevention, quota limits).

Think twice

  • Blindly setting global SERIALIZABLE on high-contention OLTP workloads without retry logic, which causes high 40001 serialization-failure abort rates.
  • Using READ UNCOMMITTED for any financial, inventory, or user-facing state—dirty reads expose rolled-back data.
  • Relying on Repeatable Read alone (without row locks) for read-modify-write counters, which suffers from lost updates or write skew.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA hospital scheduling app required at least 1 doctor on call per shift. Under PostgreSQL REPEATABLE READ (Snapshot Isolation), Alice and Bob both queried SELECT COUNT(*) WHERE on_call = true (saw 2), and each updated their own row to on_call = false.

The idea

Database isolation (the I in ACID) defines how much concurrency side effects one transaction is allowed to observe from others. The 1992 ANSI SQL standard defined four levels—Read Uncommitted, Read Committed, Repeatable Read, and Serializable—based on three phenomena (Dirty Read, Non-Repeatable Read, Phantom Read).

However, modern MVCC databases (PostgreSQL, MySQL InnoDB, CockroachDB) exposed critical gaps in the ANSI definitions: Snapshot Isolation (SI) prevents all three ANSI anomalies yet still suffers from Write Skew (where two concurrent transactions read an overlapping premise and write to disjoint rows, violating a global invariant). Achieving true Serializability requires either Two-Phase Locking (2PL) or Serializable Snapshot Isolation (SSI).

Concrete walkthrough

Trace Write Skew vs. SSI Detection on a rooms(room_id, slot, booking_id) constraint:

  1. Setup: Room 101 at 10:00 has 0 bookings. Policy: at most 1 booking per (room_id, slot).
  2. Snapshot Taken: Tx1 and Tx2 both start under Snapshot Isolation at T=100.
  3. Concurrent Reads: Tx1 queries SELECT COUNT(*) FROM bookings WHERE room_id=101 AND slot='10:00' (sees 0). Tx2 runs the same query (also sees 0).
  4. Disjoint Writes: Tx1 inserts (id=501, room=101, slot='10:00'). Tx2 inserts (id=502, room=101, slot='10:00'). Because 501 != 502, there is no row-level write-write conflict.
  5. Outcome:
    • Under Snapshot Isolation (REPEATABLE READ in Postgres): Both commit -> double-booked!
    • Under Serializable (SERIALIZABLE SSI): Postgres tracks SIREAD predicate locks on the index range (101, '10:00'), detects the dangerous rw-antidependency cycle (Tx1 reads -> Tx2 writes and Tx2 reads -> Tx1 writes), commits Tx1, and aborts Tx2 with SQLSTATE 40001.

Serializable Snapshot Isolation (SSI) prevents Write Skew: MVCC lets T1 and T2 read without blocking, while SIREAD locks detect the rw-antidependency cycle and abort T2.

How databases implement isolation levels

Two engines claiming the same ANSI level can behave differently:

  • PostgreSQL: Uses pure MVCC. READ COMMITTED takes a fresh snapshot per statement; REPEATABLE READ implements Snapshot Isolation (one snapshot per transaction, prevents phantoms, allows write skew); SERIALIZABLE adds SSI (SIREAD locks).
  • MySQL InnoDB: Uses MVCC for plain SELECTs and Next-Key Locks (record + gap locks) for SELECT ... FOR UPDATE / UPDATE. Plain REPEATABLE READ can still exhibit subtle write skew, whereas SERIALIZABLE converts every plain SELECT into SELECT ... LOCK IN SHARE MODE (2PL).
  • Distributed SQL (CockroachDB, Spanner): CockroachDB defaults directly to SERIALIZABLE using Hybrid Logical Clocks (HLC), write intents, and timestamp-pushing; Spanner uses 2PL + TrueTime atomic clocks for External Consistency.

Failure modes

  • Silent Read Skew in Billing: Generating a multi-table invoice under READ COMMITTED reads orders before a concurrent INSERT commits and order_items after, producing mismatched totals.
  • False-Positive SSI Aborts: Because SIREAD locks operate at page or index-granularity under memory pressure, unrelated transactions on the same index page can trigger unnecessary 40001 aborts.
  • Gap-Lock Deadlocks in MySQL: Concurrent INSERT ... ON DUPLICATE KEY UPDATE under InnoDB REPEATABLE READ acquires overlapping gap locks, causing frequent deadlock rollbacks (Error 1213).
  • Transaction Wraparound / Undo Bloat: Long-running REPEATABLE READ transactions pin old MVCC tuple versions, degrading sequential scan performance.

Choosing the right tool for the invariant

You don't always need global SERIALIZABLE isolation to enforce correctness:

  1. Atomic Single-Statement Updates: UPDATE accounts SET balance = balance - 50 WHERE id = 1 AND balance >= 50 is safe even under READ COMMITTED.
  2. Database Constraints: UNIQUE indexes and PostgreSQL EXCLUDE USING gist (e.g., non-overlapping booking ranges) enforce invariants at the engine level without application retry loops.
  3. Pessimistic Row/Parent Locking: Lock a single parent entity (SELECT * FROM rooms WHERE id = 101 FOR UPDATE) to serialize concurrent child inserts.
  4. SSI (SERIALIZABLE) + Retries: Best for complex multi-table invariants where locks would be too coarse or deadlock-prone.

Practical checklist

  • Never perform SELECT -> compute in app -> UPDATE under READ COMMITTED; use atomic SQL expressions or SELECT ... FOR UPDATE.
  • Verify your specific engine's guarantees (e.g., Postgres REPEATABLE READ = Snapshot Isolation; CockroachDB = SERIALIZABLE by default).
  • Implement an idempotent retry wrapper for SQLSTATE 40001 (serialization failure) and 40P01 (deadlock).
  • Keep transactions short: never hold a DB transaction open across external HTTP/RPC calls.
  • Set idle_in_transaction_session_timeout to protect MVCC garbage collection from abandoned snapshots.
03 / Engineering trade-offs

Weighing architectural decisions

Consistency Guarantees vs. Throughput / Abort Rate

Advantage: Serializable isolation eliminates all concurrency anomalies, letting engineers reason about transactions as if they ran one-by-one.

Drawback: High-contention keys trigger frequent `40001` serialization aborts (under SSI) or lock waits (under 2PL), reducing effective throughput.

Pessimistic Locking (2PL) vs. Optimistic / SSI

Advantage: Pessimistic `SELECT FOR UPDATE` guarantees the winner finishes without wasted work when contention is high (> 10% conflict rate).

Drawback: Pessimistic locks hold resources across network round-trips and risk deadlocks; SSI excels when conflicts are rare.

MVCC Version Retention vs. Garbage Collection

Advantage: Readers never block writers on long-running analytical queries.

Drawback: Long-running `REPEATABLE READ` transactions prevent `VACUUM` / undo-log purge, causing table bloat and OOM.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Missing Retry Handler for SQLSTATE 40001

Enabling `SERIALIZABLE` or `REPEATABLE READ` without exponential-backoff retries surfaces raw `could not serialize access` 500 errors to users.

What helps: Wrap serializable transactions in an idempotent retry loop (3–5 attempts with jittered backoff) at the repository/DAO layer.

Write Skew on Disjoint Rows

Assuming `REPEATABLE READ` (Snapshot Isolation) prevents all race conditions leads to broken cross-row invariants (e.g., double-booking a meeting room).

What helps: Use `SERIALIZABLE` isolation, materialize a parent lock row (`SELECT ... FOR UPDATE` on `rooms`), or use Postgres `EXCLUDE USING gist` constraints.

Long-Lived Snapshot Bloat

An idle-in-transaction `REPEATABLE READ` session stays open for 6 hours, blocking MVCC garbage collection across the entire database.

What helps: Set `idle_in_transaction_session_timeout = '30s'` and route long analytical exports to a read replica.

Deadlock Cascades under 2PL

Transactions acquire row locks in inconsistent order (`A -> B` and `B -> A`), stalling threads until the deadlock detector aborts one.

What helps: Enforce a canonical lock acquisition order (e.g., sort `account_id` ascending before `SELECT FOR UPDATE`).

05 / Practical checklist

Avoid these mistakes

  • Believing PostgreSQL's `REPEATABLE READ` allows phantom reads—in Postgres it implements Snapshot Isolation, which actually prevents phantoms, unlike the ANSI minimum.
  • Confusing MySQL InnoDB's `REPEATABLE READ` (which uses gap locks on `FOR UPDATE` to prevent phantoms, yet still permits write skew on plain `SELECT`s) with `SERIALIZABLE`.
  • Doing `SELECT balance` -> check in Java/Python -> `UPDATE balance` under `READ COMMITTED` instead of atomic SQL updates or `FOR UPDATE`.
  • Holding a database transaction open while making an external HTTP/Stripe API call, exhausting connection pools and holding row locks.
  • Testing concurrency bugs with sequential integration tests instead of parallel stress tests (e.g., Jepsen/Elle or concurrent goroutines).
