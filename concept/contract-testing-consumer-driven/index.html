01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Consumer-Driven Contract Testing (CDCT).

As microservices scale beyond 10–15 services, keeping all versions synchronized in a shared staging environment becomes quadratically expensive and chronically flaky. Consumer-Driven Contract Testing (CDCT) inverts the dependency: each consumer writes fast unit tests against a local mock (Pact Mock Service) that records the exact HTTP or async message fields and status codes it actually uses into a JSON contract.

That contract is published to a central Pact Broker, where the provider downloads it and replays every interaction against its real controller and serializer in complete isolation using Provider States (given(...)).

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need CDCT (Silent Schema Drift & Staging Bottlenecks).

An unannounced field rename (total_cents -> totalAmount) or status-code shift breaks downstream consumers in production, while shared staging E2E suites take 15–60 minutes and flake on unrelated services.

CDCT Workflow

Consumer Pact Publish -> Provider Verification -> can-i-deploy Gate

Consumers and providers never need to run in the same environment at the same time; the Pact Broker matrix gates production deploys in <2 seconds.

Preventing a Silent Checkout Outage

orders-api planned to refactor total_cents to totalAmount assuming only checkout-web used it. Pact provider verification failed in 6 seconds on invoices-worker's contract, catching an undocumented dependency.

Async Kafka Event Contracts

Using Pact V4 Asynchronous Message contracts ({ metadata, contents }), inventory-svc and 4 downstream Kafka consumers verified Avro/JSON serialization in CI without spinning up Kafka or ZooKeeper.

03
STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where CDCT fits (and where Schema-First wins).

CDCT excels for internal microservice boundaries with known consumers, whereas public APIs with thousands of external callers should use OpenAPI/Protobuf schema-first contracts.

ChoiceWhat it buysWhat it costs
Use: Internal Polyglot Microservices & Kafka EventsProves which fields consumers *actually* deserialize, freeing providers to evolve unused fields.Requires maintaining a Pact Broker and Provider State fixtures.
Avoid: Public Third-Party APIsUse OpenAPI 3.1 + `oasdiff` or Protobuf/Buf breaking-change linters instead.External developers cannot publish Pact files to your internal Broker.
Avoid: Deep Business Logic / Infra WiringKeep business permutations in unit tests and IAM/mTLS checks in smoke tests.Writing 40+ Pact interactions per endpoint turns contracts into slow duplicate unit suites.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to manage Matchers, Provider States & Deployment Gates.

  1. Flexible Type/Regex Matchers: Use like(), eachLike(), and iso8601DateTime() instead of hardcoded literal timestamps or UUIDs.
  2. Real Provider States: Execute given(...) hooks against Testcontainers/in-memory repositories rather than stubbing out the JSON serializer.
  3. WIP & Pending Pacts: Enable pendingPacts during rollout so new consumer expectations don't prematurely block provider main.
  4. Matrix Gate: Always run pact-broker can-i-deploy --to-environment prod before rollout and record-deployment immediately after.
// Pact V4 Consumer Test with type matchers (TypeScript / Jest)
await provider
  .given('order ORD-99 is PENDING')
  .uponReceiving('a request to confirm order ORD-99')
  .withRequest({ method: 'POST', path: '/v2/orders/ORD-99/confirm' })
  .willRespondWith({
    status: 200,
    body: { orderId: MatchersV3.string('ORD-99'), status: MatchersV3.equal('CONFIRMED') },
  })
  .executeTest(async (mockServer) => {
    const res = await ordersClient.confirmOrder(mockServer.url, 'ORD-99');
    expect(res.status).toBe('CONFIRMED');
  });

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Pact CDCT vs. Bi-Directional vs. Buf/Protobuf.

Compare contract mechanisms by runtime speed, behavioral coverage, and cross-team coordination overhead.

ChoiceWhat it buysWhat it costs
Pact V4 (Consumer-Driven)5–15s per service; catches status-code, header, and behavioral mismatches.Medium setup overhead (Broker + Provider State hooks).
Bi-Directional (OpenAPI + PactFlow)<5s schema subset check; zero Provider State hooks needed.Validates schema compatibility only, not runtime state transitions.
Protobuf + Buf Breaking<2s linter in PR CI; enforces wire-level backward compatibility.gRPC/Protobuf only; does not catch semantic status/error behavior.
Shared Staging E2EValidates real Kubernetes Ingress, IAM, mTLS, and DB performance.15–60 min runtime; high flakiness and environment contention.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Architecture: Pact Broker Verification Matrix Lifecycle.

Never attempt a big-bang migration across 50 services. Start with the highest-churn consumer-provider pair using pendingPacts, wire can-i-deploy + record-deployment into CD, and expand to async Kafka boundaries.
