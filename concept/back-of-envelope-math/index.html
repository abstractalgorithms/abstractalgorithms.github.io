The idea to keep with you

When sizing a system before choosing components, convert daily active users into peak RPS, daily storage bytes, network egress bandwidth, and Little's Law in-flight concurrency first so every shard, cache, or queue directly addresses a proven physical limit.

TL;DR30-second simplified summary
▾

Back-of-the-envelope estimation prevents both under-provisioning and premature sharding. Little's Law (L = lambda * W) shows how a downstream latency jump multiplies active connections and exhausts pools even at constant RPS, while Pareto working-set math sizes Redis RAM for the 20% hot keys rather than multi-year cold disk.

The 90-Second Estimation Toolkit: Time, Bytes & Latency Tiers.

Why this matters: Master exact mental shortcuts for converting DAU into RPS, storage growth, and hardware latency budgets.

Precision to three decimal places wastes time when traffic spikes 3x on Monday mornings. Round using clean powers of 10:

  • 1 Day = $86,400\text{ s} \approx 10^5\text{ s}$ (so 105 req/day≈1 RPS10^5\text{ req/day} \approx 1\text{ RPS}105 req/day≈1 RPS; 108 req/day≈1,000 RPS10^8\text{ req/day} \approx 1,000\text{ RPS}108 req/day≈1,000 RPS).
  • 1 Month = $2.59 \times 10^6\text{ s} \approx 2.5 \times 10^6\text{ s}$.
  • Peak-to-Average Ratio: Multiply average RPS by 3x for consumer diurnal peaks, or 5x-10x for flash-sale/notification bursts.

Keep hardware latency numbers anchored across six orders of magnitude: L1 Cache (~1 ns), Main RAM (~100 ns), Intra-AZ Redis (~500 us-1 ms), NVMe SSD 4 KB Random Read (~10-50 us), Same-Region Cross-AZ RTT (~1-2 ms), and Cross-Continent RTT (~75-85 ms).

Little's Law (L = lambda * W): Why Slow Downstream Calls Exhaust Pools.

Why this matters: Apply Little's Law to compute exact thread counts, HTTP connection pools, and queue memory footprints.

Little's Law states that for any stable queueing system, the average number of items inside the system (LLL) equals the average arrival rate (λ\lambdaλ) times the average residence time (WWW): L=λWL = \lambda WL=λW.

Worked Trace: An API handling λ=2,000 RPS\lambda = 2,000\text{ RPS}λ=2,000 RPS with a W=25 msW = 25\text{ ms}W=25 ms SQL query needs L=2,000×0.025=50 connectionsL = 2,000 \times 0.025 = 50\text{ connections}L=2,000×0.025=50 connections. If a lock stall pushes query latency to W=400 msW = 400\text{ ms}W=400 ms, the exact same $2,000\text{ RPS}$ now demands L=2,000×0.4=800 concurrent connectionsL = 2,000 \times 0.4 = 800\text{ concurrent connections}L=2,000×0.4=800 concurrent connections—immediately exhausting a 100-connection pool.

STAGE 03 · INVARIANT & IMPLEMENTATIONcore

Automated Capacity & Bottleneck Verifier in Python.

Why this matters: Codify QPS, 5-year storage, NIC bandwidth, and Little's Law concurrency checks in Python.

Turning back-of-the-envelope formulas into a sanity-check helper prevents unit-conversion errors (bits vs. bytes, KiB vs. KB, ms vs. seconds).

from dataclasses import dataclass

@dataclass(frozen=True)
class WorkloadEstimate:
    avg_rps: float
    peak_rps: float
    daily_storage_gb: float
    five_year_storage_tb: float
    peak_egress_mbps: float
    required_concurrency: float

def estimate_system(
    daily_requests: int,
    peak_multiplier: float,
    avg_record_bytes: int,
    write_fraction: float,
    avg_latency_ms: float,
    replication_factor: int = 3,
) -> WorkloadEstimate:
    if daily_requests <= 0 or peak_multiplier < 1.0 or avg_latency_ms <= 0:
        raise ValueError("Inputs must be positive with peak_multiplier >= 1.0")

    avg_rps = daily_requests / 86_400.0
    peak_rps = avg_rps * peak_multiplier
    daily_writes = daily_requests * write_fraction
    daily_storage_gb = (daily_writes * avg_record_bytes * replication_factor) / 1e9
    five_year_storage_tb = (daily_storage_gb * 365.0 * 5.0) / 1e3
    peak_egress_mbps = (peak_rps * avg_record_bytes * 8.0) / 1e6
    required_concurrency = peak_rps * (avg_latency_ms / 1000.0)

    return WorkloadEstimate(
        avg_rps=round(avg_rps, 2),
        peak_rps=round(peak_rps, 2),
        daily_storage_gb=round(daily_storage_gb, 3),
        five_year_storage_tb=round(five_year_storage_tb, 3),
        peak_egress_mbps=round(peak_egress_mbps, 2),
        required_concurrency=round(required_concurrency, 1),
    )

Fan-Out Tail Latency Amplification & Working-Set Cache Sizing.

Why this matters: Calculate how parallel scatter-gather fan-out magnifies p99 tail latency and size Pareto (80/20) caches.

When a request fans out to N=20N = 20N=20 backend shards in parallel and waits for the slowest shard, the probability that all 20 respond within their individual p99 ($0.99$) is $0.99^{20} = 81.8\%$. Thus 18.2% of user requests exceed per-shard p99.

To keep composite p99 under 50 ms across 20 shards, each shard must hit p99.95 latency (via hedged requests or 10 ms shard timeouts). For Cache Sizing (Pareto Principle): 20% of objects typically drive 80% of reads; sizing Redis RAM for the 1-hour hot working set (~7.2 GB for 10K RPS of 1 KB objects) cuts RAM cost by 5x.

Engineering Decision Framework
Problem
How to decide whether a storage workload needs horizontal sharding or fits comfortably on a single replicated primary.
Naive Solution
Immediately shard every database into 32 partitions at day one.
Why It Fails
Sharding breaks cross-partition joins, complicates transactions, and adds operational routing overhead when a single NVMe primary handles 5,000+ write TPS and 4 TB storage effortlessly.
Alternatives
Compare single replicated primary, read-replica scale-out, and hash/range sharding.
Engineering Decision
Keep a single replicated primary when total 5-year storage < 2 TB, peak writes < 3,000 TPS, and working-set indexes fit in RAM; shard only when write IOPS, RAM working set, or storage exceeds single-node hardware ceilings.
Trade-Offs
Preserves full ACID transactions and operational simplicity until physical node limits justify sharding complexity.

STAGE 05 · EDGE CASES, ASSUMPTIONS & GLOSSARYdeepDive

Where Order-of-Magnitude Math Misleads & Canonical Glossary.

Why this matters: Identify non-linear bottlenecks (lock contention, GC pauses, power-law skew) that average-RPS math misses.

Where Back-of-the-Envelope Math Fails:

  • Hot-Key Skew: 5,000 TPS spread across 10M keys is trivial; 5,000 TPS hitting one database row or Redis key saturates a single CPU core or row lock.
  • Small-Packet PPS Limits: 100,000 tiny 64-byte packets/sec uses only 51 Mbps of bandwidth, yet can saturate kernel interrupt/syscall CPU.
  • Write Amplification: LSM-tree compaction and B+Tree page splits amplify 1 KB of logical writes into 5-15 KB of physical NVMe writes.

Assumptions & Glossary:

  • Assumptions: Estimates assume uniform traffic distribution unless a peak-to-average multiplier (3x-10x) is explicitly applied, and include a 3x replication factor for durable storage.
  • Little's Law: L=λWL = \lambda WL=λW, linking concurrency (LLL), throughput (λ\lambdaλ), and residence time (WWW).
  • Tail Amplification: Degradation of end-to-end p99 latency when a request waits on NNN parallel fan-out calls ($1 - p^N$).
