Allocators.

User-space memory allocators like jemalloc, tcmalloc, and mimalloc sit between your application and the OS kernel, carving large mmap/brk regions into thread-local size classes so malloc() and free() complete in ~15–30 ns without global lock contention or virtual memory fragmentation.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Default glibc ptmalloc2 optimizes for general-purpose compatibility, not high-concurrency tail latency; switching to jemalloc or tcmalloc and tuning dirty-page decay routinely cuts RSS by 15–35% and eliminates multi-core lock stalls.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Every malloc, new, Vec::push, or string allocation in C, C++, Rust, Python, or JNI-heavy JVM services hits the user-space allocator before it ever touches the kernel. Under high thread counts or mixed object sizes, a poorly matched allocator causes severe internal/external fragmentation, multi-millisecond mmap/munmap TLB shootdowns, and RSS bloat that triggers Linux OOM-killer even when live heap usage is under 50%.

  • Allocators partition memory into segregated size classes (e.g., 8 B, 16 B, 32 B, ..., up to 32 KB) to bound internal fragmentation under ~12.5% while eliminating free-list search scans.
  • Thread-local caches (tcache in jemalloc/ptmalloc2) and per-CPU caches (using Linux rseq in tcmalloc) serve 95%+ of allocations lock-free in ~10–25 ns.
  • Cross-thread deallocation (Producer Thread A allocates, Consumer Thread B frees) bypasses thread-local fast paths and requires atomic remote-free lists or arena locking.
  • Returning freed pages to the OS via madvise(MADV_DONTNEED) drops physical RSS immediately but forces costly minor page faults on reuse; dirty_decay_ms balances RSS vs CPU.
  • Linux Transparent Huge Pages (2 MB THP) reduce TLB misses for large contiguous arrays, but can amplify small-page allocator fragmentation by 512x if MADV_DONTNEED only punches 4 KB holes.

Good candidates

  • High-concurrency multi-threaded services (C++, Rust, Go cgo, or JVM with RocksDB/Netty off-heap buffers) experiencing futex contention inside ptmalloc2 arenas.
  • Long-running caches and databases (Redis, MySQL, ClickHouse) with mixed allocation sizes (64 B to 1 MB) where external fragmentation steadily inflates RSS over days.
  • Latency-sensitive workloads where 99.9th percentile pauses must stay under 100 microseconds without sudden kernel brk/mmap or Transparent Huge Page (THP) compaction stalls.

Think twice

  • Short-lived CLI tools or batch scripts that exit within seconds, where allocator warm-up and per-CPU cache metadata add unnecessary startup overhead.
  • Strictly bounded, fixed-size real-time embedded systems where dynamic allocation is banned and static slab pools or stack buffers guarantee deterministic O(1) memory.
  • Garbage-collected runtimes using pure managed heaps (pure Go or pure JVM without off-heap JNI) where the runtime's own bump-pointer allocator already bypasses libc malloc.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA 64 GB Redis cluster handling 200k writes/sec with mixed 100 B–16 KB keys saw RSS climb to 61 GB while used_memory stayed at 38 GB (fragmentation ratio 1.60), triggering OOM alerts.

The idea

Calling the OS kernel (brk or mmap) on every allocation is far too slow: a syscall context switch plus page-table setup and zero-fill takes 500–2,000 ns, whereas modern services allocate millions of small objects per second. A user-space memory allocator acts as an amortizing cache over the kernel's virtual memory subsystem.

Instead of asking the kernel for 24 bytes, the allocator requests large aligned chunks (typically 2 MB or 4 MB extents/arenas) via mmap and subdivides them into fixed size classes (e.g., 8, 16, 32, 48, 64, ..., 14 KB). Each thread (in jemalloc/ptmalloc2) or physical CPU core (in tcmalloc) maintains a lock-free local cache of recently freed blocks for each size class. As long as the local cache has a slot, malloc() and free() execute in 10–30 ns with zero syscalls and zero cross-core synchronization.

Concrete walkthrough

Consider a Rust HTTP server running jemalloc on 16 cores handling a 128-byte JSON header allocation followed by a 256 KB response buffer:

  1. Fast-path small allocation (128 B): The worker thread maps 128 B to size class index 8. It pops a pointer directly from its thread-local tcache bin in ~12 ns. No mutexes, no atomics, no syscalls.
  2. Cache miss refill: If the tcache bin for 128 B is empty, jemalloc locks only the specific arena bin (sharded across 16 arenas, so contention is minimal), pulls a batch of 32 blocks (4 KB slab) from the arena's active run, and refills tcache.
  3. Large allocation (256 KB): Objects exceeding tcache_max (default 32 KB) bypass tcache entirely and allocate directly from the arena's extent tree (or mmap if no free 256 KB contiguous run exists), avoiding polluting small-object caches.
  4. Deallocation & Decay: When the 256 KB buffer is freed, jemalloc marks those 64 pages as dirty. Rather than calling madvise(MADV_DONTNEED) immediately, it holds them for dirty_decay_ms (default 10,000 ms). If another 256 KB request arrives within 10 seconds, it reuses the already-faulted physical pages with zero kernel overhead; otherwise, a background/epoch purge returns the physical frames to Linux.

Fast-path allocations stay inside the thread/CPU cache; only bin refills and decayed dirty pages cross into arenas or the OS kernel.

How modern allocators differ

While all modern allocators use size classes and local caching, their concurrency and metadata models diverge sharply:

  • glibc ptmalloc2: Uses a tcache (up to 7 items per bin) backed by up to 8 * cores arenas. Free blocks store intrusive pointers inside freed user memory, which is fast but prone to heap-metadata corruption bugs and severe arena RSS bloat on high-core hosts.
  • jemalloc (Meta / Rust / FreeBSD): Uses out-of-band bitmaps in slab headers, strict dirty_decay_ms / muzzy_decay_ms smoothing, and built-in heap profiling (prof:true, jeprof) that lets engineers capture live allocation flamegraphs in production with <2% overhead.
  • tcmalloc (Google): Replaces per-thread caches with per-CPU caches using Linux rseq (restartable sequences), bounding cache RAM by core count rather than thread count—ideal for servers with 10,000+ threads.
  • mimalloc (Microsoft): Shards free lists per 64 KB page and splits local vs. thread-delayed free lists using lock-free atomic CAS, excelling at asymmetric producer-consumer workloads.

Failure modes

1. Silent OOM from fragmentation, not leaks: An application holds 2 GB of live objects, but a single surviving 64-byte object in each 4 KB page pins 4 GB of dirty pages in RSS. Watch jemalloc's stats.active vs stats.allocated (ratio > 1.25 signals fragmentation).

2. MADV_FREE vs MADV_DONTNEED accounting illusions: MADV_FREE marks pages lazily reclaimable without zeroing RSS immediately, causing Kubernetes cgroup memory.current and top to still count them until kernel memory pressure hits. For strict container limits, prefer MADV_DONTNEED.

3. fork() deadlock: Forking a multi-threaded process while another thread holds an arena mutex deadlocks the child process unless the allocator registers pthread_atfork handlers—always use posix_spawn() or execve() immediately after fork().

Production tuning and observability

You can diagnose allocator health in production without restarting services by inspecting process maps and allocator stats:

  • Check active vs. resident: Compare jemalloc allocated (bytes requested by app), active (bytes in pages containing live data), and resident (physical RSS). A high resident - active gap means dirty_decay_ms is too long; a high active - allocated gap means external fragmentation from mixed lifetimes.
  • Tuned MALLOC_CONF baseline for containers: MALLOC_CONF="background_thread:true,dirty_decay_ms:2000,muzzy_decay_ms:0,narenas:8" offloads page purging to background threads so request threads never stall on madvise.
  • Verify rseq for tcmalloc: Check grep rseq /proc/self/status or kernel version (>= 4.18); without rseq, modern tcmalloc falls back to slower mutex-protected per-thread caches.

Practical checklist

  • Verify whether your runtime uses glibc ptmalloc2 (via ldd ./binary) and benchmark jemalloc or tcmalloc under realistic multi-threaded churn.
  • Set MALLOC_ARENA_MAX=4 if staying on glibc inside memory-constrained containers on high-core hosts.
  • Enable background_thread:true and tune dirty_decay_ms (1000–5000 ms) in jemalloc to bound RSS without causing page-fault CPU spikes.
  • Disable system-wide always Transparent Huge Pages (echo madvise > /sys/kernel/mm/transparent_hugepage/enabled) to prevent 2 MB fragmentation amplification.
  • Alert on (rss_bytes - heap_allocated_bytes) / rss_bytes > 0.30 and capture jeprof / pprof allocation flamegraphs before blaming application code for a leak.
03 / Engineering trade-offs

Weighing architectural decisions

Thread-local cache size vs. Memory footprint

Advantage: Larger `tcache` or per-CPU caches keep more size classes hot in L1/L2, eliminating cross-core synchronization and keeping allocation latency under 20 ns.

Drawback: With 200+ threads, each holding 2–4 MB of cached free blocks, idle thread caches can pin 500 MB–1 GB of unreachable RSS.

Aggressive OS page return (`dirty_decay_ms`) vs. Page fault CPU

Advantage: Short decay windows (0–500 ms) invoke `madvise(MADV_DONTNEED)` quickly, keeping container RSS tightly aligned with live heap so Kubernetes doesn't OOM-kill.

Drawback: Immediately unbacking pages forces the kernel to zero-fill and fault in 4 KB pages on the next allocation burst, burning 5–12% extra system CPU.

Per-CPU caches (`tcmalloc`) vs. Per-thread caches (`jemalloc`)

Advantage: Restartable sequences (`rseq`) bind caches to physical CPU cores rather than OS threads, capping cache overhead even when an app spawns thousands of goroutines or pthreads.

Drawback: Requires Linux kernel >= 4.18 for `rseq` and can suffer cache thrashing if the OS scheduler rapidly migrates a thread across NUMA nodes.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

ptmalloc2 Arena Proliferation

In glibc, threads hitting contention spawn new 64 MB arenas up to `8 * CPU_COUNT`. In containers with 64 host cores but a 4 GB cgroup limit, native virtual and resident memory explodes.

What helps: Set `MALLOC_ARENA_MAX=4` for glibc workloads or switch to `jemalloc` with explicit `narenas` tuned to `2 * cgroup_cpus`.

Producer-Consumer Remote Free Skew

When I/O threads allocate request buffers and worker threads free them, the worker's `tcache` overflows while the I/O thread's cache starves, forcing constant slow-path arena mutex acquisitions.

What helps: Use `mimalloc` (which shards free lists per page with lock-free atomic remote-free lists) or batch-return buffers to an explicit object pool on the allocating thread.

THP Compaction & Page-Zeroing Stalls

Kernel `khugepaged` or synchronous THP allocation attempts to coalesce 512 contiguous 4 KB pages under memory pressure, stalling `malloc()` for 10–150 ms.

What helps: Set `/sys/kernel/mm/transparent_hugepage/enabled` to `madvise` (never `always`) and configure `jemalloc` with `thp:never` or `metadata_thp:auto`.

False Sharing on Adjacent Small Allocations

Two threads allocate separate 16-byte structs that land on the same 64-byte CPU cache line; frequent writes cause MESI cache-line bouncing across cores (~50 ns/write).

What helps: Pad hot per-thread structs to 64 bytes (`alignas(64)`) or use size classes >= 64 bytes for contended atomic counters.

05 / Practical checklist

Avoid these mistakes

  • Assuming `free()` immediately returns RAM to the OS and diagnosing retained RSS in `top` or Prometheus as a memory leak.
  • Running `LD_PRELOAD=libjemalloc.so` on static binaries (like Go or musl-linked Rust) where `libc` malloc symbols are not dynamically resolved.
  • Leaving `MALLOC_ARENA_MAX` unset on high-core Kubernetes nodes running small-memory JVM/Python containers with native C extensions.
  • Benchmarking allocator throughput on a single thread, which completely hides lock contention, false sharing, and cross-thread free-list overhead.
  • Ignoring `mallopt(M_MMAP_THRESHOLD)` or `dirty_decay_ms` when workload patterns shift from steady-state caching to spiky multi-megabyte batch allocations.
