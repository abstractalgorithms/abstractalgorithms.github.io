STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is a User-Space Memory Allocator.

A user-space allocator (ptmalloc2, jemalloc, tcmalloc, mimalloc) batches coarse OS mmap/brk syscalls into segregated size classes (8 B, 16 B, 32 B, ..., 32 KB) to bound internal fragmentation under ~12.5%.

Thread-local caches (tcache) or per-CPU caches (via Linux rseq in tcmalloc) serve 95%+ of allocations lock-free in 10–25 ns without hitting arena mutexes.

Allocator Fast Path

Thread-Local Cache -> Size-Class Arena -> OS Kernel mmap

1.1. Segregated Bins: Fixed size classes eliminate free-list linear scans and bound internal waste.

2.2. Thread-Local Hit: 95%+ of small allocations pop from tcache with zero cross-core synchronization.

3.3. Page Return: Dirty decay timers return freed spans to the OS via madvise(MADV_DONTNEED).

Layered thread caches + segregated arenas keep small allocations fast while returning unused pages to the kernel.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why ptmalloc2 arenas and remote-frees blow up container RSS.

Every malloc, Vec::push, or RocksDB/Netty off-heap buffer hits the allocator. Two production pathologies strike containerized services:

  • ptmalloc2 Arena Proliferation: glibc spawns 64 MB arenas up to 8 * host_CPU_count. A 4 GB cgroup container on a 64-core host can explode virtual/resident memory.
  • Producer-Consumer Remote-Free Skew: I/O threads allocate buffers and worker threads free them, starving the producer's tcache and forcing slow arena locks.

Cap Arenas in Containers

Set MALLOC_ARENA_MAX=4 for glibc or configure jemalloc narenas to 2 * cgroup_cpus.

mimalloc for Cross-Thread Frees

mimalloc shards free lists per page with lock-free atomic remote-free lists, avoiding producer-consumer skew.

04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Tuning jemalloc Dirty Decay & Arenas via MALLOC_CONF.

Balance RSS tightness (dirty_decay_ms) against kernel page-fault CPU (MADV_DONTNEED re-zeroing).

# Production jemalloc tuning for a 4-vCPU container running RocksDB / Rust / C++
export LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2
export MALLOC_CONF="narenas:8,dirty_decay_ms:2000,muzzy_decay_ms:5000,tcache:true,prof:true,prof_prefix:/tmp/jeprof"

# Fallback if staying on glibc ptmalloc2 in high-core Kubernetes hosts:
export MALLOC_ARENA_MAX=4

Alternatives: ptmalloc2 vs. jemalloc vs. tcmalloc vs. mimalloc.

Compare allocators on thread-cache RSS, decay speed, and profiling.

ChoiceWhat it buysWhat it costs
jemallocLow long-running fragmentation, built-in heap profiling (`prof:true`), predictable `dirty_decay_ms`.Slightly larger metadata footprint than ptmalloc2.
tcmalloc (per-CPU rseq)Ultra-low latency with per-CPU caches instead of per-thread caches (saves RAM at 500+ threads).Tighter coupling to modern Linux kernels (`rseq`).
mimallocCompact, fast, and excels at cross-thread producer-consumer deallocation.Less mature built-in production heap-sampling tooling than jemalloc.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Container RSS Guardrails & Heap Profiling.

In Kubernetes, set dirty_decay_ms: 1000–2000 so freed spans return to the kernel before the cgroup OOM killer fires, while avoiding dirty_decay_ms: 0 (which burns 5–12% extra system CPU on 4 KB zero-fill page faults).
