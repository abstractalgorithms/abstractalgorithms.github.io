Distributed Locking &
Redlock Algorithm.

Distributed locking coordinates mutually exclusive access to a shared resource across independent processes that share no memory, using a network-accessible lease store such as Redis, etcd, or ZooKeeper.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

A distributed lock is only a lease—without monotonic fencing tokens verified by the downstream storage engine, GC pauses or network partitions will still cause split-brain corruption.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

In single-node systems, a mutex guarantees mutual exclusion because all threads share one kernel and clock. In distributed systems, processes fail silently, packets delay arbitrarily, and garbage-collection pauses freeze execution for seconds, so naive locks routinely allow two workers to mutate the same account, inventory row, or leader state simultaneously.

  • Every distributed lock must carry a TTL (lease duration) so a crashed holder does not deadlock the cluster indefinitely.
  • Lock acquisition and release must be atomic: use Redis SET key token NX PX 30000 to acquire and a Lua compare-and-delete script to release only if the caller's unique token matches.
  • Redlock attempts fault-tolerant locking across N=5 independent Redis masters by requiring a quorum (N/2 + 1 = 3) within a bounded acquisition window, subtracting elapsed time and clock drift.
  • Consensus-backed stores (etcd via Raft leases, ZooKeeper via ephemeral sequential znodes) provide linearizable monotonic revisions (revision or zxid) that act as true fencing tokens.
  • Mutual exclusion for correctness requires the target resource (database, object store, or API) to validate that incoming writes carry a fencing token >= the highest token seen so far.

Good candidates

  • Preventing duplicate execution of expensive or non-idempotent side effects such as charging a payment gateway or provisioning cloud infrastructure.
  • Coordinating single-leader election for background workers, partition consumers, or cron dispatchers where only one active controller should run.
  • Serializing competing updates to external systems that lack native optimistic concurrency control or compare-and-swap primitives.

Think twice

  • Protecting row-level database updates where optimistic locking (version columns) or ACID transactions with SELECT ... FOR UPDATE already guarantee correctness.
  • High-throughput hot paths (>10,000 ops/sec on the same key) where lock contention serializes traffic and destroys tail latency.
  • Correctness-critical financial ledgers when your lock service cannot issue fencing tokens and your storage layer cannot reject stale tokens.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioTwo checkout workers simultaneously process requests for the last unit of SKU-4829. Worker A acquires a Redis lease (SET lock:sku:4829 uuid-a NX PX 5000), reads stock=1, and decrements to 0.

The idea

A distributed lock grants a single process temporary, exclusive permission to act on a shared resource across an unreliable network. Because processes can crash silently and messages can be delayed indefinitely, a distributed lock cannot be held forever—it must be structured as a time-bounded lease backed by an external coordination service.

At its simplest, a single Redis instance implements a lease with SET resource_id owner_uuid NX PX 30000. However, a single node is a single point of failure, and asynchronous master-replica failover can lose acknowledged locks. To address availability, Redlock deploys N=5N = 5N=5 independent Redis masters with no replication and requires a client to acquire the lock on a strict majority (≥3\ge 3≥3) within a small fraction of the TTL. For strict linearizable safety—especially when combined with fencing tokens—consensus systems like etcd (Raft) or ZooKeeper (Zab) are preferred over wall-clock-dependent leases.

Concrete walkthrough

Consider a billing worker acquiring a Redlock lease across 5 independent Redis masters (R1–R5) with a requested TTL = 10,000 ms:

  1. Timestamp & Token Generation: The worker records its local monotonic start time T1 = 1000 ms and generates a 128-bit random value token = "9f82c1...".
  2. Parallel Quorum Acquisition: The worker sends SET lock:invoice:77 9f82c1... NX PX 10000 to all 5 masters with a tight per-node socket timeout (e.g., 50 ms so a dead node does not stall the loop).
  3. Quorum & Validity Check: R1, R2, R3, and R4 reply OK; R5 times out. The worker completes at T2 = 1045 ms. Elapsed time is 45 ms, plus estimated clock drift 10,000 * 0.01 + 2 = 102 ms. Because 4/5 >= 3 and validity = 10,000 - 45 - 102 = 9,853 ms > 0, the lock is acquired.
  4. Work & Fenced Write: The worker executes the billing step within 9,853 ms. If using etcd instead of Redlock, the worker attaches etcd's monotonic revision to the database UPDATE ... WHERE last_fence < :revision.
  5. Atomic Release: Regardless of whether all 5 nodes succeeded, the worker executes the Lua GET-and-DEL script on all 5 masters so any partial lock is cleaned up immediately.

Without storage-side fencing token validation, a 15 s GC pause turns a valid lease into silent split-brain corruption.

Redlock vs. consensus-based locking

Redlock is designed for efficiency locks—cases where preventing duplicate work saves CPU or API spend, and an occasional race condition is tolerable or caught by downstream idempotency. Martin Kleppmann's well-known critique demonstrated that Redlock relies on a bounded timing model: if a process pauses longer than the TTL, or if system clocks jump, two clients can believe they hold the lock simultaneously, and Redlock provides no monotonic counter to distinguish the newer holder from the older one.

By contrast, etcd and ZooKeeper tie lock ownership to a replicated state machine's log index (revision in etcd, zxid in ZooKeeper). Even if a client pauses, the storage engine can atomically compare incoming_token >= stored_token and reject stale writes. The trade-off is operational complexity and write latency: Raft/Zab require disk-backed consensus across 3 or 5 nodes, whereas Redis operates purely in memory.

Failure modes

  • Zombie Lock Holder (GC / Network Stall): A client passes its local TTL check, pauses for 15 s, and writes stale data. Mitigation: Pass monotonic fencing tokens to storage, or use short leases paired with a watchdog thread that aborts local work if renewal fails.
  • Split-Brain During Redis Async Failover: A lock written to a Redis master is lost when the master crashes before replicating to its standby. Mitigation: Avoid single-master Redis for correctness locks; use Raft-backed etcd or database optimistic locking.
  • Lock Herd Effect: 500 workers watch the same ZooKeeper znode or poll the same Redis key every 10 ms, saturating the coordinator when the lock releases. Mitigation: Use ZooKeeper sequential znodes (each waiter watches only node[i-1]) or randomized exponential backoff with jitter.
  • Clock Drift & NTP Steps: Stepping a server's clock forward by 60 s causes Redlock masters to expire active leases immediately. Mitigation: Configure chrony/ntpd for slewing rather than stepping, and prefer Raft/Zab where safety does not depend on wall-clock synchronization.

Watchdogs, heartbeats, and lease renewal

Choosing a TTL creates a tension: a 2 s TTL recovers quickly from crashes, but risks expiring during normal 3 s work; a 120 s TTL avoids premature expiry, but stalls failover for two minutes after a crash. Production clients (such as Redisson's watchdog or etcd's KeepAlive stream) solve this with lease renewal.

The client acquires a short lease (e.g., 10 s) and spawns a background heartbeat every TTL / 3 (3.3 s) that extends the lease only if the owner token still matches. Crucially, if the heartbeat fails or times out—indicating the worker lost connectivity or paused—the worker must self-fence (cancel its in-flight context or abort the transaction) rather than continuing to mutate shared state.

Practical checklist

  • Verify whether database-native optimistic concurrency (WHERE version = ?) or SELECT ... FOR UPDATE SKIP LOCKED eliminates the need for an external lock service.
  • Generate a cryptographically unique owner_token (UUIDv4) per acquisition attempt and release exclusively via an atomic compare-and-delete script.
  • Set a bounded TTL on every lock and size socket timeouts to < 50 ms per Redlock node so unreachable masters fail fast.
  • For correctness-critical mutations, use etcd/ZooKeeper to obtain a monotonic fencing token and enforce token >= last_seen_token at the target datastore.
  • Implement exponential backoff with full jitter on contended retries and self-fence the worker immediately if a lease-renewal heartbeat fails.
03 / Engineering trade-offs

Weighing architectural decisions

Consensus (etcd / ZooKeeper) vs. In-Memory Leases (Redis / Redlock)

Advantage: Consensus stores guarantee linearizability and emit monotonic fencing tokens across leader failovers without relying on synchronized wall-clock bounds.

Drawback: Consensus writes incur Raft/Zab disk fsync and quorum RTTs (typically 5–20 ms), offering lower raw throughput than single-node Redis (<1 ms).

Short Lease TTL vs. Long Lease TTL

Advantage: A short TTL (e.g., 5–10 s) enables fast failover recovery when a lock holder crashes without graceful release.

Drawback: Short TTLs require reliable background heartbeats (watchdogs) and increase the risk of premature expiration during transient network stalls or GC pauses.

Pessimistic Distributed Lock vs. Optimistic Concurrency Control (OCC)

Advantage: Distributed locks prevent wasted work when contention is high and rollbacks are expensive or impossible (e.g., external HTTP calls).

Drawback: OCC (ETags, version columns) avoids external lock infrastructure and scales horizontally under low contention without lease management.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Lease Expiration During Process Pause (Split-Brain)

A client acquires a 10 s lock, stalls for 15 s due to a JVM stop-the-world GC pause or VM live migration, and resumes writing after another client legitimately acquired the expired lock.

What helps: Attach a monotonic fencing token from etcd/ZooKeeper to every downstream write and enforce `token >= last_seen_token` at the storage layer.

Clock Jump Breaking Redlock Safety

Redlock assumes bounded clock drift (`drift = ttl * 0.01 + 2 ms`). An NTP step forward or hypervisor clock jump on one Redis master expires a lease early, allowing two clients to reach 3/5 quorums.

What helps: Run NTP in slew-only mode (no backward/forward steps), use monotonic clocks (`CLOCK_MONOTONIC`) for TTLs where supported, or use a Raft-based lock service for strict safety.

Non-Atomic Release Deleting Another Client's Lock

Client A issues `GET lock` (sees its own token), stalls briefly while the lock expires and Client B acquires it, then issues `DEL lock`, accidentally deleting Client B's active lock.

What helps: Always release locks using an atomic server-side Lua script (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`).

Async Replication Loss on Redis Failover

In single-master Redis with a replica, Client A acquires a lock on the master, the master crashes before replicating the write, and the promoted replica grants the same lock to Client B.

What helps: Do not rely on single-master Redis + async replica for correctness-critical locks; use Redlock across 5 independent masters or a CP store like etcd.

05 / Practical checklist

Avoid these mistakes

  • Calling `SETNX` followed by `EXPIRE` as two separate commands, leaving an eternal lock if the client crashes between them.
  • Releasing a lock with a plain `DEL key` instead of checking ownership with a unique per-client UUID token.
  • Setting a fixed TTL shorter than the worst-case critical section duration without implementing a lease renewal watchdog.
  • Treating Redlock as a strict correctness guarantee without fencing tokens on the underlying database.
  • Polling a contended lock in a tight loop (`while (!acquire()) {}`) without exponential backoff and jitter, creating a thundering herd.
