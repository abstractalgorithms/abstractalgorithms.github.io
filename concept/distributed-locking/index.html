STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Distributed Locking.

Why this matters: The mechanism: understand how Distributed Locking works from first principles.

On a single machine, a pthread_mutex or Java synchronized block works because all threads share one kernel, one memory space, and one hardware clock. Across multiple servers, there is no shared memory. A distributed lock is a time-bounded lease stored in an external coordination service (such as Redis, etcd, or ZooKeeper) that grants one caller temporary exclusive permission to act on a resource key.

Every safe distributed lock has four fields: a resource key (lock:invoice:77), a globally unique owner token (uuid-a, so only the holder can release it), a TTL / lease duration (PX 30000, so a crashed holder does not deadlock the cluster forever), and—for correctness-critical writes—a monotonic fencing token (revision = 412).

Lease Lifecycle

Distributed Lock State Machine

A lock never stays held forever: either the owner atomically releases it with its UUID, or the TTL expires and a new monotonic token is issued.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Distributed Locking (and why naive locks fail).

Why this matters: The problem: see what breaks without Distributed Locking under real concurrency or scale.

Think of Why we need Distributed Locking (and why naive locks fail) as the intuition layer for Distributed Locking & Redlock Algorithm: The problem: see what breaks without Distributed Locking under real concurrency or scale.

When multiple stateless workers process queues, cron jobs, or checkout requests concurrently, two workers can read the same state (stock = 1 or invoice = UNPAID) and both execute an irreversible side effect—double-charging a credit card or overselling the last item. Even if you add a lock, asynchronous networks and stop-the-world GC pauses break naive mutual exclusion: Worker A can freeze after acquiring a 10 s lock, wake up at 15 s believing it still holds the lock, and overwrite Worker B's work.

Split-Brain Prevention

How GC Pauses Break Leases — And How Fencing Tokens Stop Stale Writes

Mutual exclusion over an unreliable network is only safe when the storage layer rejects writes carrying a fencing token older than the highest token seen.

Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Efficiency Locks vs. Correctness Locks

Use an efficiency lock (like single-node Redis or Redlock) when an occasional duplicate execution only wastes CPU or money. Use a correctness lock with monotonic fencing tokens (etcd/ZooKeeper + storage check) when duplicate writes corrupt financial or inventory state.

The Slow-vs-Dead Ambiguity

A lock service cannot tell whether a silent client crashed or is merely paused in GC. That is why every lock must be a finite lease rather than an indefinite hold.

Distributed locks belong at coarse-grained coordination boundaries, not on every database row. They shine when coordinating external side effects that lack native compare-and-swap primitives, or when electing a single active controller.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Distributed Locks are acquired, renewed, and released.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Safe lock management requires atomic primitives at every step of the lifecycle:

  1. Atomic Acquisition: Never run SETNX followed by EXPIRE—a crash between the two creates an eternal lock. Always use SET lock:sku:4829 <uuid> NX PX 30000.
  2. Watchdog / Lease Renewal: If work can outlive the initial TTL, run a background daemon (e.g., Redisson's watchdog) that extends the TTL at TTL / 3 intervals—and aborts local work if renewal fails.
  3. Atomic Compare-and-Delete Release: Never issue a blind DEL lock:sku:4829. If your lease expired during a pause, DEL will delete another worker's active lock. Execute a server-side Lua script that checks GET == owner_uuid before deleting.
  4. Bounded Retries with Jitter: Contending callers must back off exponentially with full jitter instead of spinning in a tight while (!acquire()) loop.

Alternatives: Redlock vs. Consensus (etcd/ZK) vs. OCC.

Why this matters: The trade-off: compare competing approaches across latency, consistency, and operational cost.

Choosing a locking mechanism means choosing your failure model.

Redlock deploys N=5N = 5N=5 independent Redis masters and requires acquiring ≥3\ge 3≥3 within TTL - elapsed - clock_drift. It tolerates up to 2 node crashes without disk fsync, but relies on bounded wall-clock assumptions and emits no monotonic fencing token.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Fenced etcd Lock + Storage Guard.

Why this matters: Production architecture: see how the components compose end to end under real load.

Think of Production example: Fenced etcd Lock + Storage Guard as the intuition layer for Distributed Locking & Redlock Algorithm: Production architecture: see how the components compose end to end under real load.

In production payment and inventory pipelines, teams pair an etcd Lease (or ZooKeeper ephemeral sequential znode) with storage-enforced fencing. The lock service provides the monotonic revision, and the authoritative database rejects any write whose fence_token <= last_fence_token.

Production Topology

3-Node etcd Raft Lock Cluster + Fenced PostgreSQL Store

1.Step 1 — Lease + Token: Worker acquires an etcd lease; Raft consensus commits and returns monotonic revision 413.

2.Step 2 — Watchdog KeepAlive: Background gRPC stream renews the lease every TTL/3; if renewal drops, the worker aborts its critical section.

3.Step 3 — Storage Fencing: Postgres atomically checks last_fence_token < 413 on UPDATE, neutralizing any zombie worker with token 412.

Consensus issues the monotonic token; the database enforces it.
