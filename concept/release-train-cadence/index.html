01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is a Release Train Cadence.

A release train replaces variable-date, feature-gated releases with a fixed-calendar, scope-variable cadence. Like a commuter train, it departs on a published schedule (e.g., every Tuesday at 14:00 UTC) with whatever commits have already landed and passed CI on main.

Incomplete features merge safely behind feature flags (enable_new_checkout), and each train progresses through branch cut, automated soak testing, progressive canary (1% -> 10% -> 50% -> 100%), and post-release monitoring.

Fixed-Clock Lifecycle

Scheduled Release Train Stages & Cherry-Pick Gate

Holding the branch cut for 'one more PR' turns a predictable release train back into a slipping ad-hoc release.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Release Trains (Bounding Batch Size & Merge Hell).

Ad-hoc feature-driven releases trap organizations in endless stabilization cycles: delaying a release for one unfinished PR piles up unshipped diffs, increases merge conflicts, and balloons blast radius. A fixed train bounds batch size and gives QA, mobile app-review teams, and product launches a reliable clock.

Stop the 'Cherry-Pick Avalanche'

Cherry-picking dozens of late fixes onto a cut branch invalidates soak tests and introduces regressions—limit picks strictly to verified P0/P1 blockers and reset soak timers.

Enforce a 30-Day TTL on Release Flags

Merging behind flags without deleting old flags creates combinatorial config debt—track flag age in CI and block new flags when stale counts exceed threshold.

03
STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Release Trains excel (and where Continuous Deployment wins).

Use release trains when external approval windows or coupled monorepos require coordinated verification; use per-commit CD for decoupled microservices.

ChoiceWhat it buysWhat it costs
Good Candidate: Mobile Apps (iOS/Android) & Coupled MonoreposMatches 24–48h App Store/Play Store review windows and coordinates multi-squad integration testing.Teams missing the cut by an hour wait for the next train unless it is a P0 hotfix.
Avoid: Decoupled Web Microservices with Canary CDIndependent services with contract tests and automated canarying can ship every green commit in minutes.Forcing independent microservices onto a weekly train artificially batches unrelated changes.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Automated Cuts, Merge Queues & Cadence Sizing are managed.

Size train interval to roughly 2x–3x your end-to-end verification and rollout time (e.g., weekly/biweekly for mobile, daily for web). Use GitHub Merge Queue so main is always green at cut time, and automate branch cutting + changelogs in CI.

# Automated scheduled release train branch cut (GitHub Actions)
name: Cut Release Train
on:
  schedule:
    - cron: '0 14 * * 2' # Every Tuesday 14:00 UTC
jobs:
  cut-train:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Create release branch & semantic tag
        run: |
          TRAIN="release/$(date -u +%Y.%m.%d)"
          git checkout -b "$TRAIN" main && git push origin "$TRAIN"

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Continuous Deployment vs. Release Train vs. Feature-Gated Releases.

Compare delivery cadences across batch size, coordination cost, and verification overhead.

ChoiceWhat it buysWhat it costs
Daily / Weekly Release TrainPredictable schedule, bounded batch size, and clean coordination with store reviews or enterprise windows.Slightly higher lead time than per-commit CD.
Continuous Deployment (Per-Commit)1-PR batch size, lowest blast radius, zero release-captain overhead.Impossible for App Store binaries and risky without mature automated canary rollbacks.
Ad-Hoc Feature-Driven ReleasesAllows waiting for a specific marketing feature.Slipping dates, huge risky diffs, and painful merge-day integration.
06
STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Biweekly Web + Mobile Train with Merge Queue.

A 100-engineer org merges PRs to main through a Merge Queue with LaunchDarkly flags. Every other Tuesday at 14:00 UTC, CI cuts release/YYYY.MM.DD, runs a 24-hour soak, shifts canary traffic (1% -> 10% -> 100%), and decouples marketing launches from code shipping via flag activation.

Automated Train Pipeline

Merge Queue -> Scheduled Cut -> Soak -> Flag Activation

Decoupling code shipping from flag activation removes last-minute pressure to hold the train.
