CQRS &
Event Sourcing.

CQRS separates write-side command validation from read-side query projections, while Event Sourcing persists every state transition as an immutable append-only log of domain events rather than overwriting current rows.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Use CQRS without Event Sourcing whenever read and write shapes diverge; adopt Event Sourcing only when an immutable audit log, temporal replay, or multi-projection architecture justifies handling eventual consistency and schema evolution.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Traditional CRUD architectures force a single normalized schema to serve both transactional invariant checks and complex denormalized UI/reporting queries, creating lock contention and N+1 join bottlenecks. Combining CQRS with Event Sourcing—used in financial ledgers (TigerBeetle, Stripe-style double-entry), collaborative editors, and high-throughput order books—gives you append-only write throughput, deterministic state replay for debugging/auditing, and independently scalable read models (PostgreSQL, Elasticsearch, Redis).

  • CQRS (Command Query Responsibility Segregation) and Event Sourcing are orthogonal: you can run CQRS over a plain relational DB, and you can use Event Sourcing with synchronous projections.
  • On the write side, an Aggregate reconstructs its state by replaying its event stream (up to a snapshot), validates the Command's invariants, and appends new Events using optimistic concurrency (expectedVersion).
  • Read models (Projections) asynchronously tail the event store (via EventStoreDB subscriptions, Kafka, or Postgres CDC/Outbox) and update denormalized tables idempotently.
  • Snapshotting every N events (e.g., every 100–500 events) bounds aggregate hydration latency so long-lived streams do not degrade write p99.
  • Because events are immutable facts, schema changes cannot mutate old records; consumers use upcasters (versioned event transformers) or weak-schema deserializers.

Good candidates

  • Financial ledgers, healthcare records, or compliance-heavy domains requiring a cryptographically or structurally immutable audit trail of every state change.
  • Systems with extreme read/write asymmetry (e.g., 100:1 reads to writes) where read queries need specialized denormalized views in Elasticsearch or Redis.
  • Domains needing time-travel queries, retroactive bug-fix replays, or spawning new downstream analytics projections from historical events.

Think twice

  • Standard CRUD domains (user profiles, CMS, simple inventory) where overwriting the current row in PostgreSQL is simpler and faster.
  • Flows requiring immediate strong read-your-own-writes consistency across complex cross-aggregate views without extra client versioning.
  • Small teams lacking operational maturity for idempotent consumers, event schema upcasting, and projection lag monitoring.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA fintech settlement service processes 8,000 transfers/sec while compliance and merchant dashboards query 90-day balance summaries.

The idea

CQRS (Command Query Responsibility Segregation) splits an application's data model into two distinct paths: a Command side that validates business rules and mutates state, and a Query side that reads pre-shaped, denormalized views.

Event Sourcing changes how the Command side persists state. Instead of executing UPDATE accounts SET balance = 150 WHERE id = 42, it appends an immutable domain event (MoneyDeposited{amount: 50}) to an append-only log. Current state is simply the left-fold (reduce) of all events in that stream. When paired together, the write model focuses purely on invariant enforcement and optimistic concurrency, while asynchronous projectors continuously fold the event log into optimized read databases.

Concrete walkthrough

Trace a WithdrawFunds(accountId='acc-9', amount=40) command:

  1. Hydrate: The command handler loads snapshot@v100 (balance=120) plus events v101..v103 (-10, +20, -30), folding them to currentBalance = 100, version = 103.
  2. Validate: Since 100 >= 40, the aggregate emits [FundsWithdrawn{amount: 40, txId: 'tx-77'}]. (No DB mutation happens inside the domain object.)
  3. Atomic Append: The repository appends the event to stream acc-9 with expectedVersion = 103. If another concurrent request already wrote v104, the store rejects with WrongExpectedVersion (HTTP 409).
  4. Project: The AccountSummaryProjector tails the global event log ($all), sees v104, verifies last_checkpoint < global_pos inside a PostgreSQL transaction, executes UPDATE account_views SET balance = balance - 40, last_pos = ..., and commits.

CQRS + Event Sourcing decouples transactional appends from asynchronous, idempotent read-model projections.

Consistency, versioning & snapshots

Event-sourced systems trade immediate global consistency for stream-level linearizability plus eventual read consistency.

  • Write-side concurrency: Optimistic concurrency (expectedVersion) guarantees no two commands overwrite each other on the same aggregate. Cross-aggregate invariants (e.g., transferring funds between two accounts) are coordinated via Sagas/Process Managers rather than distributed 2PC.
  • Read-your-own-writes: Commands return ETag: "v104" or X-Min-Position: 98412. The query API polls or waits briefly for the projection checkpoint >= 98412 before serving the requesting client.
  • Snapshotting: A separate background worker periodically serializes aggregate state at v500, v1000, etc., keeping write-side hydration bounded to O(100) events.

Failure modes

  1. Poison-pill event: A malformed or un-upcasted event crashes the projector in an infinite retry loop, stalling all downstream read updates. Fix: Dead-letter queue (DLQ) per stream or alertable circuit breaker after N retries.
  2. Blue/green projection rebuilds: Rebuilding a 500M-event projection in-place breaks live reads. Fix: Write to a versioned table (orders_v2), catch up to live tail, then atomically swap the DB view/alias.
  3. Eventual consistency surprises: Automated tests or UIs immediately GET after POST and see 404. Fix: Propagate causal position tokens or return the updated state summary in the command response.
  4. Side effects during replay: Sending emails or charging cards inside a projection handler re-executes during a historical rebuild. Fix: Isolate external side effects to a live-only Process Manager that checks isLiveMode or deduplicates via idempotency keys.

Schema evolution & GDPR

Because historical events are immutable facts, you never run UPDATE events SET payload = .... Instead:

  • Additive changes: Add optional fields with defaults.
  • Breaking changes: Introduce OrderPlacedV2 and register an Upcaster (V1 -> V2) in the deserialization pipeline before events reach aggregates or projections.
  • GDPR Erasure: Store PII (name, email, SSN) encrypted with a per-subject AES-256 key (user_key_42) held in a separate mutable key store. Deleting user_key_42 renders all historical PII fields cryptographically unreadable without breaking event-stream hashes or structural replay.

Practical checklist

  • Confirm Event Sourcing is restricted to bounded contexts that require auditability, replay, or temporal queries.
  • Enforce optimistic concurrency (expectedVersion) on every event append.
  • Guarantee atomic write + publish via an Event Store or Transactional Outbox + CDC (never dual-write).
  • Make every projection handler idempotent using (streamId, eventNumber) or global log position checkpoints.
  • Implement crypto-shredding for any PII stored inside immutable event payloads.
  • Test full projection rebuilds from event 0 into a shadow table before going to production.
03 / Engineering trade-offs

Weighing architectural decisions

Read-After-Write Consistency

Advantage: Decoupled async projections let write and read databases scale and fail independently.

Drawback: Introduces replication lag (typically 10–200 ms), meaning a user who submits a command may refresh and see stale data unless the UI tracks a `streamVersion` watermark.

Auditability vs. Query Flexibility

Advantage: Every historical state and the business reason ('why' it changed) is preserved forever for replay and debugging.

Drawback: Ad-hoc queries against raw event streams are painful; every new query shape requires writing and backfilling a dedicated projection.

Schema Evolution Complexity

Advantage: Adding a new read-model column only requires replaying events into a new projection table.

Drawback: Renaming or splitting an existing event type requires maintaining backward-compatible upcasters for the lifetime of the store.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Projection Lag & Stale Read-Your-Writes

A burst of 50,000 events backs up the projection consumer, causing users to see outdated balances or missing orders right after a `200 OK` command.

What helps: Return the committed `streamPosition` in the command response and have read queries wait (briefly) or fall back to reading the aggregate until the projection reaches that checkpoint.

Dual-Write Split-Brain

Writing an event to PostgreSQL and publishing to Kafka in two separate calls fails midway, leaving the read model permanently out of sync.

What helps: Use a dedicated Event Store (EventStoreDB) as the single source of truth, or use the Transactional Outbox pattern with Debezium CDC.

Non-Idempotent Projection Handlers

At-least-once delivery replays an `OrderPaid` event after a worker crash, double-incrementing a merchant's total revenue counter.

What helps: Store the last processed `(streamId, eventNumber)` or `eventId` in the same transaction as the read-model update and skip duplicates.

GDPR / Right-to-Erasure Conflict

PII stored inside immutable events violates legal deletion requests.

What helps: Use **crypto-shredding**: encrypt PII fields with a per-user key stored in a mutable KMS/vault, and delete the key upon erasure request.

05 / Practical checklist

Avoid these mistakes

  • Applying Event Sourcing across an entire monolith instead of isolating it to core subdomains that genuinely need auditability or temporal replay.
  • Designing 'CRUD events' (`UserUpdated`) instead of domain-meaningful events (`SubscriptionUpgraded`, `ShippingAddressCorrected`), losing business intent.
  • Calling external HTTP APIs or generating non-deterministic `time.Now()`/`uuid.New()` inside projection replay handlers.
  • Allowing aggregates to grow unboundedly across millions of events without snapshots or stream archiving (e.g., monthly account closing events).
  • Blocking synchronous HTTP responses while waiting for 5 downstream projections to finish updating.
