CQRS & Event Sourcing

Separate write models from read models and rebuild state from append-only domain events when auditability and scale diverge.

Orientation & Intuition

CQRS splits command (write) and query (read) paths; event sourcing stores state transitions as immutable events that can rebuild projections.

Key takeaway Use CQRS/event sourcing when read and write shapes diverge sharply or you need a verifiable audit log—not as a default microservice layout.

Core Architecture & Trade-offs

It enables independent scaling of reads/writes and time-travel debugging, at the cost of operational complexity.

Key Architecture Invariants

  • Commands enforce invariants on write model
  • Projections are rebuildable
  • Event schema evolution is a first-class problem

When to Use

  • High read/write asymmetry
  • Rich audit requirements
  • Multiple read projections from one write model

When NOT to Use

  • Simple CRUD domains
  • Teams without projection replay tooling

Deep Dive & Production Considerations

Commands vs queries

Optimize each path independently; synchronize via events.
