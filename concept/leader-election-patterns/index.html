THE BIG IDEA · CONCEPT GUIDE

A leader coordinates changes. A majority decides. Fencing protects external state when old leaders wake back up.

Explanation anchor
01

Why choose a leader?

If two nodes both think they are in charge, they can accept conflicting updates. This is called split-brain. Raft coordinates decisions using a majority of voting nodes, called a quorum. Any two majorities overlap, which—together with Raft’s voting and log rules—helps prevent conflicting decisions. Monotonic epoch fencing guarantees linearizable state coordination across distributed clusters.

Good candidates

  • Distributed clusters requiring single-writer coordination (Raft leader, Kafka controller, etcd primary).
  • Active-passive database replication systems requiring automated failover.
  • Distributed job schedulers or partition orchestrators that demand exactly-once task assignment.

Think twice

  • Stateless web tiers where traffic is evenly distributed across interchangeable worker nodes via L4/L7 load balancers.
  • Peer-to-peer gossip topologies where eventual consistency and conflict-free replicated data types (CRDTs) suffice without a single coordinator.

Stored is not committed. Committed is not applied.
A follower’s acknowledgement confirms durable log storage, not execution. Replicas apply entries only after learning they are committed, and always in log order.

Current-term rule: the leader advances commitIndex by counting replicas only for an entry from its current term. Committing that entry also commits earlier entries. In this example, the service waits for local application before returning success.

03

How a leader gets elected.

FollowerListens for heartbeats
→
CandidateRequests votes
→
LeaderWins a majority
  1. Heartbeats stop. A follower waits for its randomized election timeout.
  2. An election starts. It increments its term, votes for itself, and asks peers for votes. Peers vote at most once per term and check that the candidate’s log is sufficiently up to date.
  3. A majority wins. The candidate becomes leader and starts sending heartbeats.
  4. A higher term takes priority. A leader or candidate that discovers a newer term steps down to follower.

Randomized timeouts make simultaneous elections less likely. If votes split, nodes can retry; randomness reduces ties, but does not guarantee an immediate winner.

Engineering trade-offs

Coordination latency vs state consistency

Advantage: Guarantees linearizability and prevents data corruption during network partitions.

Drawback: Requires consensus round-trips (RTT) and heartbeat leases that limit raw write throughput compared to leaderless systems.

Odd vs even voter counts

Advantage: An odd cluster of 3 or 5 nodes achieves optimal failure tolerance per voting participant.

Drawback: An even cluster (4 nodes) requires 3 votes for quorum just like a 5-node cluster, providing zero extra fault tolerance while adding network overhead.

Strict fencing vs lease timeouts

Advantage: Atomic server-enforced fencing tokens protect external storage deterministically regardless of GC pauses or clock drift.

Drawback: Downstream storage systems must support conditional version checks or atomic CAS operations.

04

Keep stale leaders out.

A former leader might pause, lose contact, then resume believing it still has authority. It cannot commit new Raft writes without a majority, but attempts to write to external storage may need extra protection.

Some systems attach an increasing fencing token to each leadership generation. Storage remembers the highest accepted token and rejects older ones.

Current leadertoken 106 ≥ watermark 106✓ Write accepted
Stale leadertoken 105 < watermark 106× Write rejected

The storage must enforce the token. Issuing tokens alone is not enough. Validation and the protected write must be coordinated atomically. Fencing external storage is an additional mechanism, not a stage of Raft replication.

Known failure modes & resilience

Split-brain via asymmetric network partition

An isolated leader continues servicing writes while a new leader is elected in the majority partition.

What helps: Enforce monotonic fencing tokens on all state machine updates and heartbeat leases.

Election storms via synchronized timers

Nodes with identical election timeouts transition to Candidate simultaneously, splitting votes indefinitely.

What helps: Apply randomized election timeouts (e.g., 150ms to 300ms) with jitter so one node consistently times out first.

Stale leader writes to external storage

A paused former leader wakes up and issues writes to external storage assuming it is still the leader.

What helps: Storage engine enforces atomic token validation: reject any write with a token less than the highest accepted generation watermark.

Log divergency after partition heal

Uncommitted entries on an old leader conflict with entries committed by the newly elected leader.

What helps: Raft log matching property: followers overwrite uncommitted conflicting entries with the leader's authoritative log.

05

What matters in production.

  1. Prefer odd-sized voting clusters. Three or five voters usually offer better failure tolerance per node. A cluster of 2F + 1 voters can tolerate F unavailable nodes while retaining a majority.
  2. Tune timeouts to your environment. Allow room for network latency, scheduling delays, and runtime pauses. Heartbeats should be substantially more frequent than election timeouts.
  3. Consider pre-vote. It helps prevent an isolated node from inflating its term and disrupting a healthy cluster when it reconnects.
  4. Compact the log. Snapshots keep storage bounded and help lagging replicas catch up.
  5. Account for coordination costs. More voters can tolerate more failures, but add replication traffic and operational complexity.

Avoid these mistakes

  • ✕Deploying an even number of consensus nodes (e.g., 4 nodes instead of 3 or 5), providing zero additional fault tolerance while increasing quorum requirement.
  • ✕Relying on wall-clock time for leases without monotonic epoch fencing, exposing the cluster to clock drift and GC pause anomalies.
  • ✕Assuming log storage equals execution: replicas apply entries only after learning they are committed.
  • ✕Allowing stale leaders to write to external systems without fencing tokens.
  • ✕Omitting pre-vote phase, allowing isolated lagging nodes with inflated terms to disrupt healthy clusters upon reconnecting.
