Leader Election
Patterns.

Leader election chooses one coordinator to sequence updates across a cluster while a majority confirms them. It helps replicas maintain one consistent history. The trade-off: failover delays writes and external systems need fencing.

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Leader Election.

Why this matters: The mechanism: understand how Leader Election works from first principles.

Leader election coordinates state changes across distributed nodes by appointing a single coordinator to sequence writes. If two nodes both think they are in charge, they accept conflicting updates—a failure called split-brain.

Consensus protocols like Raft prevent conflicting leaders using a majority of voting nodes (quorum): Q≥⌊N/2⌋+1Q \ge \lfloor N / 2 \rfloor + 1Q≥⌊N/2⌋+1. Because any two majorities of N=2F+1N = 2F + 1N=2F+1 nodes overlap by at least one voter, at most one leader can be elected in any given term (epoch).

Raft Node Roles

Leader Election State Machine (Follower / Candidate / Leader)

Randomized election timeouts (150–300 ms) break ties so one candidate wins quorum instead of looping on split votes.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Quorum Election & Monotonic Fencing.

Why this matters: The problem: see what breaks without Quorum Election & Monotonic Fencing under real concurrency or scale.

A cluster cannot tell whether a silent leader crashed or is paused by a stop-the-world GC or asymmetric network partition. Even after a majority partition elects a new leader in Term 106, the isolated old leader (Term 105) may wake up and flush a stale write to external storage.

Monotonic epoch fencing solves this: every newly elected leader mints an incrementing epoch token, and downstream storage rejects any write carrying a token lower than the highest accepted watermark.

Split-Brain Defense

How Monotonic Fencing Stops a Zombie Leader

Quorum prevents two leaders in the same term; storage-side fencing prevents an old-term zombie from corrupting state.

Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision

Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Odd Voter Counts (2F + 1)

A 4-node cluster still needs 3 votes for quorum—tolerating only 1 failure, identical to 3 nodes, while adding replication overhead.

Pre-Vote Phase

Before incrementing its term, a partitioned node checks if a majority would vote for it, preventing isolated nodes from disrupting a healthy leader on reconnect.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

3-Node Consensus Quorum + Fenced Storage.

Why this matters: Production architecture: see how the components compose end to end under real load.

Think of 3-Node Consensus Quorum + Fenced Storage as the intuition layer for Leader Election Patterns: Production architecture: see how the components compose end to end under real load.

In production control planes, an odd-sized Raft quorum (3 or 5 nodes across availability zones) sequences terms and replicates the write-ahead log, while downstream databases enforce the term/revision watermark.

Production Quorum

3-Node Raft Election & Replication Topology

1.1. Quorum (2 of 3): Leader A + Follower B form a majority; Node C can be down or partitioned without stalling writes.

2.2. Pre-Vote Guard: Reconnecting Node C runs Pre-Vote before bumping Term so it cannot depose healthy Leader A.

3.3. Fenced Downstream: All external writes carry Term 106; storage rejects any delayed Term <= 105 request.

Odd-sized quorums (3 or 5) maximize fault tolerance per node while pre-vote and fencing eliminate partition-heal storms.
