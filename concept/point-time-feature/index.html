Point-in-Time ML Feature Store
& ASOF Joins.

A Point-in-Time ML Feature Store eliminates training-serving skew and temporal data leakage by pairing a low-latency online key-value store with an immutable offline time-travel lakehouse queried via ASOF joins.

TL;DR30-second simplified summary
▾

Modern ML platforms separate feature engineering from model serving using a central Feature Registry. Flink computes sliding-window aggregates into Redis (online) and Iceberg (offline).

During training, Spark executes ASOF joins (feature_ts <= event_ts) to reconstruct leak-free historical snapshots, while online inference uses Protobuf key packing and circuit-breaker fallbacks.

Training-Serving Skew & Temporal Leakage.

Why this matters: Diagnose why naive SQL joins corrupt offline training datasets with future information.

Think of Training-Serving Skew & Temporal Leakage as the intuition layer for Point-in-Time ML Feature Store & ASOF Joins: Diagnose why naive SQL joins corrupt offline training datasets with future information.

When data scientists join a label table (e.g., fraud_labels at t=12:00) against a mutable feature table (user_profiles), they read the user's current state rather than the state at t=12:00. This leaks post-event outcomes into training, inflating offline AUC while causing severe online accuracy drops.

Temporal Alignment

Point-in-Time ASOF Join vs Naive Equi-Join

1.Time-Travel Guard: ASOF JOIN strictly enforces feature_ts <= event_ts with a 30-day TTL cutoff.

2.Mutable Table Hazard: Overwriting rows in place destroys historical point-in-time state.

ASOF joins align each training label with the latest feature value recorded before the label event.

Unified Feature Registry & Schema Contracts.

Why this matters: Define declarative feature views once to guarantee identical online and offline semantics.

Think of Unified Feature Registry & Schema Contracts as the intuition layer for Point-in-Time ML Feature Store & ASOF Joins: Define declarative feature views once to guarantee identical online and offline semantics.

A central Feature Registry stores typed entity keys, aggregation windows, null-handling defaults, and serialization schemas (Protobuf/Avro). Both Spark batch backfills and Flink streaming jobs compile from the same transformation definition, preventing subtle SQL-vs-Python drift.

Contract Governance

Declarative Feature Registry Compilation

1.Versioned Views: Immutable v1/v2 feature views allow zero-downtime model rollouts.

2.Fail-Safe Fallback: Clients cache registry metadata locally to survive control-plane blips.

A single declarative registry compiles identical feature logic for both batch and streaming engines.

Alternatives

Dual-Sink Streaming Materialization.

Why this matters: Write real-time Flink aggregations to Redis online and Iceberg offline without divergence.

Think of Dual-Sink Streaming Materialization as the intuition layer for Point-in-Time ML Feature Store & ASOF Joins: Write real-time Flink aggregations to Redis online and Iceberg offline without divergence.

Apache Flink ingests Kafka events, maintains keyed sliding windows in RocksDB state backends, and emits updates to a Dual-Sink Materializer. Online writes use pipelined Redis HSET/MSET with TTLs for sub-5ms lookups, while offline writes buffer into Apache Iceberg Parquet files via two-phase commit.

Dual-Sink Pipeline

Flink Dual-Sink Materialization to Redis & Iceberg

1.Checkpointed 2PC: Flink checkpoints coordinate Kafka offsets with Iceberg snapshot commits.

2.DLQ Protection: Failed Redis writes route to a bounded dead-letter queue after 3 retries.

Flink stateful operators materialize identical aggregates to Redis for low-latency serving and Iceberg for history.

04

Low-Latency Online Feature Serving.

Why this matters: Serve multi-entity feature vectors in under 5ms p99 at 100K+ QPS.

Think of Low-Latency Online Feature Serving as the intuition layer for Point-in-Time ML Feature Store & ASOF Joins: Serve multi-entity feature vectors in under 5ms p99 at 100K+ QPS.

Inference services fetch 50–200 features per request across multiple entities (user, merchant, device). Packing features into compact binary blobs or Redis Hashes per feature-view, batching lookups via MGET/pipeline, and pinning hot keys in local L1 in-memory caches keeps p99 latency under 5ms.

Serving Path

L1 Cache + Pipelined Redis Online Serving

1.Batching & Packing: Packing a feature view into one Protobuf key cuts Redis RTTs by 10x.

2.Graceful Degradation: Circuit breakers return imputed medians if Redis p99 exceeds 4ms.

L1 caching, Protobuf key packing, and strict timeouts protect inference tail latency.

05
intermediate

On-Demand Request-Time Transformations.

Why this matters: Compute context-dependent features at inference time without pre-materialization.

Think of On-Demand Request-Time Transformations as the intuition layer for Point-in-Time ML Feature Store & ASOF Joins: Compute context-dependent features at inference time without pre-materialization.

Features like distance_between(user_gps, merchant_gps) or amount / user_avg_spend_30d depend on live request payloads and cannot be pre-computed. On-Demand Feature Views execute lightweight stateless Python/C++ expressions inside the serving process right after online store hydration.

Request-Time Compute

Hybrid Pre-Computed + On-Demand Feature Hydration

1.Zero-Divisor Guard: Always clamp denominators to epsilon to prevent NaN inference crashes.

2.Shared UDFs: Run the exact same compiled UDF in Spark offline and the serving worker.

On-demand transforms combine stored aggregates with live request parameters at inference time.

Online-Offline Parity & Drift Monitoring.

Why this matters: Detect silent skew between Redis serving vectors and Iceberg historical snapshots.

Think of Online-Offline Parity & Drift Monitoring as the intuition layer for Point-in-Time ML Feature Store & ASOF Joins: Detect silent skew between Redis serving vectors and Iceberg historical snapshots.

Even with shared definitions, late-arriving Kafka events or Redis evictions can cause online-offline drift. A Parity Auditor samples 1% of live inference feature logs, writes them to Iceberg, and runs a daily Wasserstein / PSI distribution diff against batch-recomputed values.

Parity & Drift

1% Inference Logging & PSI Drift Detection

1.Logged Features: Training on logged online features eliminates serving-path discrepancies.

2.PSI Thresholds: PSI > 0.1 signals moderate shift; > 0.2 triggers automated backfill.

Comparing 1% sampled serving logs against offline recomputations catches silent skew early.

Backfilling & Zero-Downtime Schema Evolution.

Why this matters: Hydrate months of historical state for new features without impacting live inference.

Think of Backfilling & Zero-Downtime Schema Evolution as the intuition layer for Point-in-Time ML Feature Store & ASOF Joins: Hydrate months of historical state for new features without impacting live inference.

Launching a new feature requires backfilling 6–12 months of Iceberg history via partitioned Spark jobs and seeding Redis before traffic cutover. Using shadow feature keys and atomic pointer swaps in the Feature Registry ensures live models never read partially backfilled state.

Backfill & Evolution

Partitioned Spark Backfill & Shadow Cutover

1.Idempotent Overwrites: Partition-scoped replaceWhere makes failed backfill retries safe.

2.Namespace Isolation: Shadow keys prevent partial backfills from polluting live v2 traffic.

Partitioned backfills and shadow namespaces enable safe, zero-downtime feature launches.
