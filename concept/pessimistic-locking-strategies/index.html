STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Pessimistic Locking.

Why this matters: The mechanism: understand how Pessimistic Locking works from first principles.

Pessimistic Locking assumes concurrent transactions will collide and prevents lost updates by acquiring a lock before reading or modifying the target record. In SQL (PostgreSQL, MySQL InnoDB), SELECT ... FOR UPDATE places an exclusive (X) row lock until COMMIT or ROLLBACK.

Modern engines also provide FOR NO KEY UPDATE (Postgres: allows concurrent foreign-key FOR KEY SHARE checks), FOR UPDATE NOWAIT (fail immediately with SQLSTATE 55P03), and FOR UPDATE SKIP LOCKED (skip locked rows for multi-worker queues).

Why we need Pessimistic Locking (when OCC collapses).

Why this matters: The problem: see what breaks without Pessimistic Locking under real concurrency or scale.

When hundreds of concurrent buyers target the exact same row—like the last 2 VIP seats on a flight or a hot flash-sale SKU—Optimistic Concurrency Control collapses into a retry storm wasting 80%+ of DB IOPS. Pessimistic locking serializes access at the database lock manager so each writer executes cleanly in turn.

Alternatives

Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Lock Timeouts, Canonical Ordering & `SKIP LOCKED` are managed.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Never leave PostgreSQL's lock_timeout at 0 (infinite) or MySQL's innodb_lock_wait_timeout at 50s.

Set SET LOCAL lock_timeout = '2000ms' inside an explicit `BEGIN ...

-- 1. Deadlock-free multi-row transfer with tight lock_timeout
BEGIN;
SET LOCAL lock_timeout = '2000ms';

SELECT id, balance_cents
FROM ledger_accounts
WHERE id IN (:from_id, :to_id)
ORDER BY id ASC
FOR UPDATE;

-- Perform balance check + debit/credit updates, then COMMIT;
COMMIT;

-- 2. Non-blocking worker queue claim
SELECT id, payload FROM outbox_jobs
WHERE status = 'PENDING'
ORDER BY created_at ASC
LIMIT 10
FOR UPDATE SKIP LOCKED;

Design Trade-Off

Alternatives: `FOR UPDATE` vs. `NOWAIT` vs. Distributed Leases

Before · Seq Scan + Unbounded Bloat
  • Implicit cast breaks B-Tree
  • Deadlock or XID wraparound risk
  • Long tx blocks VACUUM
After · Indexed Plan + Bounded MVCC
  • Index-only scan in <2 ms
  • Deterministic lock ordering
  • Autovacuum keeps bloat flat
ChoiceWhat it buysWhat it costs
`SELECT ... FOR UPDATE` (Blocking)Simple queuing for hot rows when transaction duration is <5 ms.Risk of connection pool exhaustion if a lock holder stalls.
`FOR UPDATE NOWAIT` (Fail-Fast)Protects connection pools by failing immediately (`55P03`) instead of queuing.Pushes retry/backoff responsibility to the caller.
Distributed Leases (etcd / ZooKeeper + Fencing)Coordinates locks across heterogeneous external APIs outside a single SQL DB.Requires TTL leases and monotonic fencing tokens on the storage layer to survive GC pauses.
