01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Pessimistic Locking.

Pessimistic Locking assumes concurrent transactions will collide and prevents lost updates by acquiring a lock before reading or modifying the target record. In SQL (PostgreSQL, MySQL InnoDB), SELECT ... FOR UPDATE places an exclusive (X) row lock until COMMIT or ROLLBACK.

Modern engines also provide FOR NO KEY UPDATE (Postgres: allows concurrent foreign-key FOR KEY SHARE checks), FOR UPDATE NOWAIT (fail immediately with SQLSTATE 55P03), and FOR UPDATE SKIP LOCKED (skip locked rows for multi-worker queues).

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Pessimistic Locking (when OCC collapses).

When hundreds of concurrent buyers target the exact same row—like the last 2 VIP seats on a flight or a hot flash-sale SKU—Optimistic Concurrency Control collapses into a retry storm wasting 80%+ of DB IOPS. Pessimistic locking serializes access at the database lock manager so each writer executes cleanly in turn.

Zero Network I/O Inside Locked Transactions

Holding FOR UPDATE while calling Stripe or Twilio ties up a DB connection for seconds; 50 concurrent buyers exhaust HikariCP in <200 ms.

Canonical Ordering Prevents AB-BA Deadlocks

When transferring between two accounts, always lock in ascending account_id order (min(id) then max(id)).

03
STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Pessimistic Locking fits (and where to avoid it).

Use pessimistic row locks for hot-key serialization, multi-row ledger transfers, and Postgres job queues; avoid holding locks across human think-time or non-indexed scans.

ChoiceWhat it buysWhat it costs
Good Candidate: Flash-Sale Inventory & Ledger TransfersPrevents retry storms at >15–20% conflict rates and protects multi-row atomic invariants.Waiters queue behind the lock holder, increasing p99 latency and connection occupancy.
Good Candidate: Postgres Job Queues (`SKIP LOCKED`)Multiple workers claim distinct pending jobs concurrently with zero lock contention.Does not guarantee strict FIFO ordering under retries.
Avoid: Non-Indexed Columns & Long HTTP Think-TimeUse OCC (`ETag` + `If-Match`) for user-edited forms and ensure `FOR UPDATE` always hits a `UNIQUE` index.`FOR UPDATE` on a non-indexed column or MySQL `REPEATABLE READ` range locks entire gaps/tables.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Lock Timeouts, Canonical Ordering & `SKIP LOCKED` are managed.

Never leave PostgreSQL's lock_timeout at 0 (infinite) or MySQL's innodb_lock_wait_timeout at 50s. Set SET LOCAL lock_timeout = '2000ms' inside an explicit BEGIN ... COMMIT block (autocommit releases FOR UPDATE immediately and protects nothing!), and sort multi-row lock keys.

-- 1. Deadlock-free multi-row transfer with tight lock_timeout
BEGIN;
SET LOCAL lock_timeout = '2000ms';

SELECT id, balance_cents
FROM ledger_accounts
WHERE id IN (:from_id, :to_id)
ORDER BY id ASC
FOR UPDATE;

-- Perform balance check + debit/credit updates, then COMMIT;
COMMIT;

-- 2. Non-blocking worker queue claim
SELECT id, payload FROM outbox_jobs
WHERE status = 'PENDING'
ORDER BY created_at ASC
LIMIT 10
FOR UPDATE SKIP LOCKED;

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: `FOR UPDATE` vs. `NOWAIT` vs. Distributed Leases.

Choose the blocking behavior and lock scope that matches your latency budget and resource topology.

ChoiceWhat it buysWhat it costs
`SELECT ... FOR UPDATE` (Blocking)Simple queuing for hot rows when transaction duration is <5 ms.Risk of connection pool exhaustion if a lock holder stalls.
`FOR UPDATE NOWAIT` (Fail-Fast)Protects connection pools by failing immediately (`55P03`) instead of queuing.Pushes retry/backoff responsibility to the caller.
Distributed Leases (etcd / ZooKeeper + Fencing)Coordinates locks across heterogeneous external APIs outside a single SQL DB.Requires TTL leases and monotonic fencing tokens on the storage layer to survive GC pauses.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Ticketing Seat Hold with `lock_timeout`.

A ticketing checkout service opens a short DB transaction with SET LOCAL lock_timeout = '2000ms', locks the requested seat rows in ascending seat_id order via FOR UPDATE, decrements availability, writes an outbox event, and commits in <4 ms—keeping all payment gateway HTTP calls outside the lock.
