Pessimistic Locking
Strategies.

A concurrency control approach that acquires exclusive or shared locks before reading or modifying data, serializing conflicting writers upfront to prevent lost updates.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Use pessimistic row locks (`SELECT ... FOR UPDATE`) with strict lock timeouts and deterministic lock ordering under high contention, or `SKIP LOCKED` for concurrent job queues.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

When hundreds of concurrent requests target the exact same row—like the last 5 seats on a flight or a hot flash-sale SKU—Optimistic Concurrency Control collapses into a retry storm. Pessimistic locking serializes access at the database or distributed lock manager so each writer executes cleanly in turn without wasting work on aborted retries.

  • In SQL, SELECT ... FOR UPDATE acquires an exclusive row lock (X) until COMMIT or ROLLBACK, blocking other writers and FOR UPDATE readers.
  • FOR UPDATE NOWAIT fails immediately (SQLSTATE 55P03) if locked, while FOR UPDATE SKIP LOCKED skips locked rows—ideal for multi-worker job queues.
  • Always enforce a tight lock_timeout (e.g., 2–5 seconds) rather than relying on MySQL's 50-second innodb_lock_wait_timeout or Postgres's infinite default.
  • To prevent deadlocks when locking multiple rows (e.g., transferring between two accounts), always acquire locks in a canonical order such as ascending account_id.
  • For distributed locks (etcd, ZooKeeper), a TTL lease alone is unsafe against GC pauses; the target storage must validate a monotonically increasing fencing token.

Good candidates

  • High-contention hot keys (conflict rate > 15–20%) such as flash-sale inventory, ticket seat reservations, or account balance transfers.
  • Multi-row atomic invariants (e.g., debiting Account A and crediting Account B) where reading consistent balances before writing is mandatory.
  • Concurrent worker queues backed by PostgreSQL or MySQL using SELECT ... FOR UPDATE SKIP LOCKED to claim jobs without duplicate processing.

Think twice

  • Long-lived user interactions (e.g., holding a row lock while a user fills out a checkout form over HTTP)—locks must never span network think-time.
  • Low-contention CRUD updates where OCC or atomic UPDATE ... SET count = count + 1 avoids lock-acquisition overhead.
  • Cross-service distributed workflows where a single node crash could orphan a lock unless backed by TTL leases and fencing tokens.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

Scenario40 worker pods polling a tasks table used naive SELECT ... LIMIT 10 followed by UPDATE, causing workers to contend on the same rows and waste 60% of CPU on lock waits.

The idea

Pessimistic Locking assumes concurrent transactions will collide and prevents lost updates by acquiring a lock before reading or modifying the target record.

In relational databases (PostgreSQL, MySQL InnoDB), SELECT ... FOR UPDATE places an exclusive (X) lock on the matched row(s) for the duration of the transaction. Any other transaction attempting FOR UPDATE, UPDATE, or DELETE on those rows must either wait until COMMIT/ROLLBACK, fail immediately (NOWAIT), or skip to the next unlocked row (SKIP LOCKED).

Concrete walkthrough

Consider a concert ticketing service reserving the last 2 VIP seats (event_id = 77, available = 2):

  1. Transaction A begins (BEGIN; SET LOCAL lock_timeout = '2000ms';) and runs SELECT available FROM inventory WHERE event_id = 77 FOR UPDATE;.
  2. The database Lock Manager grants an exclusive row lock to Transaction A and returns available = 2.
  3. 2ms later, Transaction B runs the same SELECT ... FOR UPDATE. Instead of reading a stale 2, Transaction B blocks in the Lock Manager's wait queue.
  4. Transaction A verifies 2 >= 2, executes UPDATE inventory SET available = 0 WHERE event_id = 77, and runs COMMIT, releasing the row lock.
  5. Transaction B immediately wakes up, reads the newly committed available = 0, throws SoldOutException, and rolls back cleanly.

SELECT ... FOR UPDATE serializes Transaction B behind Transaction A at the database Lock Manager, ensuring Transaction B only reads post-commit inventory.

SQL locking modifiers and advisory locks

Beyond standard FOR UPDATE, modern Postgres and MySQL provide specialized modifiers:

  • FOR NO KEY UPDATE (Postgres): Acquires a write lock that still allows concurrent FOR KEY SHARE foreign-key checks on child tables.
  • FOR UPDATE NOWAIT: Throws an error immediately if the row is locked, preventing connection-pool queuing during traffic spikes.
  • FOR UPDATE SKIP LOCKED: Returns only unlocked rows—turning a relational table into a reliable concurrent job queue.
  • Advisory Locks (pg_advisory_xact_lock(key)): Lock arbitrary 64-bit integer keys (e.g., hashed tenant IDs) even when no physical row exists yet.

Failure modes

  1. Pool Starvation Under Slow Transactions: If a worker holds FOR UPDATE while calling an external payment API that takes 4 seconds, 50 concurrent buyers saturate the DB connection pool and crash health checks.
  2. Deadlocks Across Unordered Keys: Locking (row 10, row 5) in one request and (row 5, row 10) in another creates an AB-BA cycle.
  3. Unfenced Distributed Locks: Relying on a Redis SET NX PX 10000 lock without a monotonic fencing token allows a GC-paused worker to corrupt data after its lease expires.

Distributed locking and fencing tokens

When locking across multiple services via etcd, ZooKeeper, or Consul, a TTL lease alone cannot guarantee mutual exclusion because client processes can freeze (GC pauses, VM live migration) past the lease expiration.

To make distributed pessimistic locks safe:

  1. The lock service issues a strictly increasing fencing token (e.g., etcd mod_revision = 1042) on every lock acquisition.
  2. Every write sent to the downstream storage server carries that token.
  3. The storage server rejects any write whose token is <= last_seen_token, blocking stale lock holders even after a 30-second pause.

Practical checklist

  • Always set lock_timeout (e.g., SET LOCAL lock_timeout = '2000ms') inside transactions that acquire FOR UPDATE.
  • Zero network I/O inside locked transactions: Complete external API calls before or after the lock window.
  • Sort multi-row lock targets by ascending primary key to eliminate AB-BA deadlocks.
  • Verify index usage with EXPLAIN: Confirm FOR UPDATE hits a primary or unique index so it doesn't lock entire table ranges or gaps.
  • Use SKIP LOCKED for queues and fencing tokens for any cross-service distributed lock.
03 / Engineering trade-offs

Weighing architectural decisions

Contention Predictability vs. Latency

Advantage: Serializes hot-key writes cleanly without wasted retry CPU.

Drawback: Waiters queue behind the lock holder, increasing p99 latency and tying up DB connections.

`FOR UPDATE` vs. `NOWAIT` / `SKIP LOCKED`

Advantage: `NOWAIT` protects connection pools from piling up during spikes; `SKIP LOCKED` maximizes queue throughput.

Drawback: `NOWAIT` pushes retry/fail-fast responsibility to the caller; `SKIP LOCKED` does not guarantee strict FIFO ordering.

Distributed Leases vs. Database Locks

Advantage: Coordinates locks across heterogeneous resources (files, external APIs) outside a single DB.

Drawback: Vulnerable to split-brain or GC pauses unless paired with monotonic fencing tokens on the storage layer.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Connection Pool Exhaustion (Lock Pileup)

A slow transaction holds `FOR UPDATE` on a hot row while 500 incoming requests wait on it, exhausting a 50-connection HikariCP pool in <200ms and taking down unrelated endpoints.

What helps: Keep locked transactions strictly in-DB (zero external HTTP calls), set `lock_timeout = '2s'`, and isolate hot-key pools.

AB-BA Deadlocks

Transaction 1 locks Row A and waits for Row B; Transaction 2 locks Row B and waits for Row A. The DB aborts one after deadlock detection.

What helps: Always acquire multi-row locks in deterministic ascending primary-key order.

InnoDB Gap Lock Contention

Under MySQL's default `REPEATABLE READ`, `SELECT ... FOR UPDATE` on a non-unique or missing index range locks index *gaps*, blocking unrelated `INSERT`s.

What helps: Ensure `FOR UPDATE` queries hit a `UNIQUE` index, or use `READ COMMITTED` where gap locks are disabled for most statements.

Stale Distributed Lock After GC Pause

Process A acquires a Redis/etcd lock with a 10s TTL, pauses for 15s during a stop-the-world GC, wakes up, and overwrites Process B's work after the lock expired.

What helps: Issue a monotonic fencing token from the lock service (e.g., etcd `revision`) and reject writes with older tokens at the storage layer.

05 / Practical checklist

Avoid these mistakes

  • Making external HTTP calls (Stripe, Twilio, microservices) while holding a database `FOR UPDATE` row lock.
  • Leaving PostgreSQL's `lock_timeout` at `0` (infinite wait) or MySQL's `innodb_lock_wait_timeout` at `50s`.
  • Running `SELECT ... FOR UPDATE` on a non-indexed column, escalating row locks into a full table scan lock.
  • Using Redis `SET NX PX` (or Redlock) for correctness-critical mutual exclusion without fencing tokens.
  • Forgetting that `FOR UPDATE` outside an explicit `BEGIN ... COMMIT` transaction (autocommit mode) releases the lock immediately and protects nothing.
