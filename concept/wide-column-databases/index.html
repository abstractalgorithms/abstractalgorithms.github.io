Wide-Column
Databases.

Wide-column databases (Cassandra, ScyllaDB, Bigtable) partition data by a row/partition key and sort rows inside each partition by clustering columns on an LSM-tree storage engine, trading ad-hoc joins for linear horizontal write scale.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Design your table schema around exact read queries using bounded partition keys (<100 MB) and clustering keys—never model wide-column tables like normalized SQL tables.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

When write throughput hits hundreds of thousands of events per second across multiple regions (IoT telemetry, messaging inboxes, time-series logs), single-leader B-tree databases hit lock contention and random disk I/O bottlenecks. Wide-column stores convert writes into sequential appends and scale linearly by adding nodes.

  • The primary key splits into (partition_key, clustering_keys): the partition key hashes (e.g., Murmur3) to a replica set via consistent hashing, while clustering keys sort rows physically on disk within that partition.
  • Writes append sequentially to an on-disk CommitLog (WAL) and an in-memory Memtable, later flushing to immutable SSTables—making writes O(1) without random disk seeks.
  • Reads merge data across the Memtable and multiple SSTables using Bloom filters (typically ~1% false positive rate) and partition indexes, which background compaction periodically merges.
  • Tunable consistency uses R + W > RF (e.g., RF=3 with LOCAL_QUORUM=2 reads and writes) for strong consistency per partition, or LOCAL_ONE for maximum availability.
  • Deletes do not erase data immediately; they write tombstone markers that must be scanned during reads until gc_grace_seconds (default 10 days) and compaction purge them.

Good candidates

  • Write-heavy workloads (100K–1M+ writes/sec) such as time-series telemetry, activity feeds, or immutable event logs.
  • Predictable key-based lookups and range scans (e.g., 'last 50 messages for channel_id X sorted by timestamp DESC').
  • Multi-region active-active availability where tunable consistency (LOCAL_QUORUM) must survive rack or region failures.

Think twice

  • Ad-hoc analytical queries, arbitrary WHERE filters across unindexed columns, or multi-table JOINs.
  • Workloads requiring multi-row ACID transactions with serializable isolation across arbitrary keys.
  • High-churn update/delete-heavy queues where frequent deletes generate millions of tombstones that cripple read latency.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA connected-vehicle platform ingests 500,000 GPS/sensor pings per second and queries the latest 24 hours per vehicle.

The idea

Wide-column databases organize data as a distributed, sorted sparse map: PartitionKey -> ClusteringKey -> ColumnName -> (Value, Timestamp). Consistent hashing (e.g., Murmur3Partitioner) maps the partition key to a token ring owned by RF replicas (typically RF=3), while clustering columns keep all rows of a partition physically sorted on disk.

Under the hood, each node uses an LSM-tree (Log-Structured Merge-tree): writes hit an append-only CommitLog and an in-memory Memtable, flushing sequentially to immutable SSTables. That design eliminates random B-tree page writes and scales write throughput linearly with node count.

Concrete walkthrough

Trace a LOCAL_QUORUM write and read on a 6-node Cassandra/ScyllaDB cluster (RF=3) for PRIMARY KEY ((device_id, day), ts) WITH CLUSTERING ORDER BY (ts DESC):

  1. Token-Aware Routing: The client driver hashes (device_id, day) via Murmur3 and sends the write directly to one of the 3 owning replicas as coordinator.
  2. Local Append & Replication: The coordinator appends the mutation to its CommitLog + Memtable and forwards it in parallel to the other 2 replicas.
  3. Quorum Ack: Once 2 of 3 replicas (floor(3/2) + 1 = 2) acknowledge, the coordinator returns 200 OK to the client in ~1.5–3ms.
  4. Flush & Compaction: When the Memtable fills, it flushes sequentially to an immutable SSTable with a Bloom filter (10 bits/key, ~1% FP) and partition summary.
  5. Range Read: Reading the latest 50 events seeks directly to (device_id, day) in the Memtable + non-eliminated SSTables (via Bloom filters) and streams the top 50 sorted rows without scanning old days.

Sequential CommitLog appends keep writes fast, while compaction and Merkle repairs keep reads bounded and replicas consistent.

Partition sizing and tunable consistency math

Two invariants govern wide-column stability:

  1. Quorum Overlap (R+W>NR + W > NR+W>N): With Replication Factor N=3N = 3N=3 per datacenter, LOCAL_QUORUM sets W=2W = 2W=2 and R=2R = 2R=2 (2+2=4>32 + 2 = 4 > 32+2=4>3). At least one replica in every read quorum holds the latest acknowledged write, guaranteeing last-write-wins (by microsecond client/coordinator timestamp) without cross-region latency.
  2. Partition Ceiling: Keep partitions under 100 MB (ideally 1–10 MB and <100,000 cells). If a device emits 1 KB/sec, a single day is 86,400×1 KB≈86.4 MB86,400 \times 1\text{ KB} \approx 86.4\text{ MB}86,400×1 KB≈86.4 MB—already near the danger zone, so bucket by 4-hour or 1-hour windows instead.

Failure modes

  • Clock Skew Breaking Last-Write-Wins (LWW): Wide-column stores resolve concurrent cell updates using the highest write timestamp; NTP drift between app servers can silently cause older writes to overwrite newer ones.
  • Read Repair & Hinted Handoff Storms: When an overloaded node flaps, coordinators accumulate gigabytes of hints; replaying hints on recovery can push the recovering node back into overload.
  • Tombstone Read Amplification: Scanning a partition with 50,000 tombstones and 10 live rows still reads and discards all 50,000 markers in memory, spiking p99 read latency.

Query-first data modeling

Follow a strict three-step modeling workflow:

  1. List Exact Queries First: Enumerate every SELECT pattern (including sort order and pagination) before defining a single table.
  2. Pick Bounded Partition Keys: Ensure every query specifies the full partition key (=) and optionally a range (>=, <) on clustering columns.
  3. Denormalize Deliberately: If you need to look up users by email and by user_id, maintain two tables (users_by_id, users_by_email) rather than adding a secondary index.

Practical checklist

  • Bound every partition key with a time or shard bucket so max partition size stays <50 MB.
  • Use LOCAL_QUORUM for both reads and writes with RF=3 per datacenter.
  • Select TWCS for TTL-based time-series and LCS for read-heavy mutable datasets.
  • Omit unset columns in INSERT statements instead of binding NULL to avoid tombstone generation.
  • Schedule automated nodetool repair every 3–7 days (strictly < gc_grace_seconds = 10 days) and sync NTP/chrony.
03 / Engineering trade-offs

Weighing architectural decisions

Query-Driven Denormalization vs. Normalization

Advantage: Duplicating data into one table per query pattern guarantees single-partition O(1) + range-scan reads with zero joins.

Drawback: Writes must update multiple tables (logged batches or async CDC), increasing storage footprint and risking partial-update drift if not idempotent.

Size-Tiered (STCS) vs. Leveled (LCS) Compaction

Advantage: STCS minimizes write amplification for write-heavy workloads.

Drawback: STCS requires up to 50% free disk headroom for large merges and suffers higher read amplification than LCS (which needs ~10% headroom but 10–30x higher write I/O).

LOCAL_QUORUM vs. LOCAL_ONE

Advantage: LOCAL_QUORUM (2 of 3 replicas) guarantees linearizable-per-partition reads of the latest acknowledged write within a datacenter.

Drawback: Doubles cross-AZ network traffic and fails writes if 2 of 3 replicas in that rack/AZ set are unreachable.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Unbounded Partition Growth (Hot Partition)

Keying a table by `tenant_id` or `sensor_id` without a time/shard bucket lets a single partition exceed 100 MB–1 GB, skewing disk/CPU onto 3 nodes and triggering OOMs during compaction.

What helps: Add a time or hash bucket to the partition key (`((entity_id, yyyymm), ts)`) to cap every partition under 10–50 MB.

Tombstone Accumulation & Read Failure

Using a wide-column table as a FIFO queue or writing `NULL` values creates millions of tombstones; reads hit `tombstone_failure_threshold` (100,000) and abort.

What helps: Avoid inserting `NULL`s (omit unset columns), use TTLs with TWCS for time-series expiration, and never model mutable job queues in Cassandra.

Skipped Anti-Entropy Repair (Zombie Data)

If a node is down longer than `hinted_handoff_window` (3h) and `nodetool repair` does not run within `gc_grace_seconds` (10 days), tombstones expire and deleted rows resurrect.

What helps: Automate incremental/subrange Merkle-tree repairs on a 3–7 day schedule, well inside `gc_grace_seconds`.

Cross-Partition `IN` / `ALLOW FILTERING` Scans

Issuing `WHERE partition_key IN (...)` with 100 keys or `ALLOW FILTERING` forces a coordinator node to scatter-gather across the entire cluster, spiking p99 latency.

What helps: Ban `ALLOW FILTERING` in production and issue parallel async single-partition queries from a token-aware driver.

05 / Practical checklist

Avoid these mistakes

  • Designing tables around entities first and adding secondary indexes (`CREATE INDEX`) later—global/local secondary indexes in Cassandra scatter-gather across nodes and collapse at scale.
  • Inserting explicit `NULL` values for optional fields in prepared statements, silently generating a tombstone on every write.
  • Using `LOGGED BATCH` across different partition keys for bulk loading, turning a single coordinator into a bottleneck.
  • Running Size-Tiered Compaction (STCS) past 60% disk utilization, leaving insufficient space for the largest SSTable merge.
  • Using `ALL` consistency in production, sacrificing availability whenever a single node restarts.
