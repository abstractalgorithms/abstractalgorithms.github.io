STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Chaos Engineering.

Chaos engineering is empirical verification for distributed systems. Rather than assuming timeouts, retries, circuit breakers, and multi-AZ failovers will work during an outage, you prove they work by injecting controlled turbulence.

Grounded in the scientific method, every experiment follows four steps: (1) define a measurable steady state (e.g., Checkout success >= 99.9%, p99 <= 250 ms), (2) formulate a hypothesis, (3) inject a bounded fault (e.g., 800 ms tc netem delay on 10% of Inventory pods), and (4) verify steady state holds or abort automatically if error budgets burn.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Gray-Failure Injection (and why PodChaos isn't enough).

Most teams start by killing pods (PodChaos), which only tests clean crash-stop behavior where Kubernetes removes the pod IP immediately. Real outages are gray failures: 300–1,000 ms asymmetric packet delay, 5% packet loss, clock skew, or Redis evictions that keep TCP sockets open just long enough to exhaust thread pools.

Watch three chaos anti-patterns:

  1. Unbounded Blast Radius: Targeting an entire namespace instead of a 5% canary or synthetic header slice.
  2. Orphaned Kernel Faults: A crashed chaos agent leaves tc netem or iptables rules active after the experiment.
  3. Telemetry Starvation: Injecting 100% network loss on a node cuts off Prometheus scraping, blinding your abort detector.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Chaos Engineering is applied.

Target the failure modes most likely to cause silent cascading outages: network latency, AZ blackholes, dependency 5xx/timeouts, and cache/DB failovers.

ChoiceWhat it buysWhat it costs
Network Delay & Packet Loss (`tc netem`)Exposes missing timeouts, retry storms, and thread-pool exhaustion from gray failures.Must exclude Prometheus/control-plane ports so telemetry and abort hooks stay reachable.
AZ Blackhole / Failover GameDaysVerifies N-1 zone capacity, DNS/ALB health-check failover, and Kafka/DB leader re-election.Requires sufficient N-1 headroom before running in production.
Avoid: Unattended Production Chaos Without Abort HooksNever inject faults without an automated Prometheus/Datadog stop-button.Turns a resilience test into a self-inflicted customer outage.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Chaos Mesh CRDs, Blast Radius, and Abort Conditions are managed.

Use declarative, time-bounded CRDs (Chaos Mesh, LitmusChaos, or AWS Fault Injection Service) with explicit pod percentage selectors (mode: fixed-percent, value: "10") and automated Prometheus abort alarms.

# Time-bounded Chaos Mesh NetworkChaos injecting 800ms gray latency on 10% of pods
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: inventory-gray-latency
  namespace: prod
spec:
  action: delay
  mode: fixed-percent
  value: "10" # strict blast radius
  selector:
    namespaces: [prod]
    labelSelectors: { app: inventory-service }
  delay:
    latency: "800ms"
    jitter: "100ms"
  duration: "5m" # auto-reverts tc netem rules even if operator pauses

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Chaos Mesh / Litmus vs. Cloud FIS vs. Envoy Fault Injection.

Choose the fault injection layer that matches your blast-radius and realism requirements.

ChoiceWhat it buysWhat it costs
Envoy / Service Mesh L7 Fault InjectionHeader-scoped (x-chaos-test: true) for 0% real-user blast radius in prod; zero kernel tc rules.Tests L7 HTTP/gRPC faults only, not kernel TCP/DNS/disk I/O stalls.
Chaos Mesh / LitmusChaos (Kubernetes CRDs)Rich tc netem, stress-ng, disk I/O, and JVM faults with time-bounded CRDs.Requires privileged DaemonSet; must guard against orphaned netem rules on node crash.
AWS Fault Injection Service (FIS)Tests real cloud control-plane faults (AZ power-off, RDS failover, EBS pause) with IAM/CloudWatch stop alarms.Cloud-provider specific; coarser granularity than L7 header injection.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Continuous Automated GameDay Pipeline.

Mature platforms run header-scoped L7 fault injection continuously in CI/CD and staging, and execute monthly AWS FIS AZ-blackhole GameDays in production wired to CloudWatch/Prometheus stop-alarms that revert faults automatically if checkout error rates rise.

Continuous Verification

Steady-State SLO -> FIS / Chaos Mesh -> Stop-Alarm Guard -> GameDay Score

1.Fail-Safe Stop Button: Stop-alarms run out-of-band from the target namespace so telemetry never goes blind.

2.Header-Scoped Prod: Synthetic canary probes carry x-chaos=true to test prod resilience with zero customer impact.

3.Closed-Loop Remediation: Every uncovered missing timeout or retry storm becomes a tracked engineering fix.

Out-of-band stop alarms and header-scoped prod probes make continuous chaos verification safe.
