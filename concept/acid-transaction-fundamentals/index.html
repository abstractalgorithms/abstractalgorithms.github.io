ACID Transaction
Fundamentals.

ACID guarantees that database transactions execute as all-or-nothing units (Atomicity), preserve schema and domain invariants (Consistency), shield concurrent readers/writers from partial state (Isolation), and survive power loss once acknowledged (Durability) via write-ahead logging (WAL), fsync, and concurrency control (MVCC/2PL).

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

ACID is not a binary switch: durability relies on WAL `fsync` before commit acknowledgment, while isolation is a tunable spectrum from `READ COMMITTED` to `SERIALIZABLE` trading lock/abort overhead for anomaly prevention.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Without ACID guarantees, concurrent requests and sudden process crashes corrupt financial ledgers, oversell finite inventory, and leave foreign-key relationships half-written. Understanding how engines implement ACID via MVCC, undo/redo logs, and lock managers lets you pick the lowest isolation level that still protects your invariants without choking throughput.

  • Atomicity is enforced via Write-Ahead Logging (WAL) in PostgreSQL (pg_wal) or undo/redo logs in MySQL InnoDB: uncommitted changes are rolled back or ignored on crash recovery.
  • Consistency in ACID means the database moves from one valid state to another (enforcing CHECK, UNIQUE, and FOREIGN KEY constraints), though application-level invariants still require proper transaction boundaries.
  • Isolation prevents concurrency anomalies—dirty reads, non-repeatable reads, lost updates, phantom reads, and write skew—using either Two-Phase Locking (2PL) or Multi-Version Concurrency Control (MVCC).
  • Durability requires flushing WAL buffers to non-volatile storage via fsync() (or fdatasync()) before returning COMMIT OK to the client; group commit amortizes this disk I/O across concurrent transactions.
  • Snapshot Isolation (REPEATABLE READ in PostgreSQL) eliminates dirty and non-repeatable reads without read locks, but still permits write skew unless upgraded to SERIALIZABLE (SSI) or explicit SELECT ... FOR UPDATE.

Good candidates

  • Double-entry financial ledgers, wallet transfers, and billing settlements where a debit without its matching credit is catastrophic.
  • Finite inventory, seat booking, and quota enforcement where concurrent requests race to claim the last available unit.
  • Multi-table state transitions (e.g., inserting an orders row, updating inventory, and appending an outbox event) that must succeed or roll back together.

Think twice

  • High-volume clickstream, telemetry, or IoT sensor ingestion where losing or reordering a few milliseconds of unacknowledged events is acceptable for 10x write throughput.
  • Append-only event logs or analytics warehouses (ClickHouse, BigQuery) optimized for columnar batch scans rather than single-row transactional updates.
  • Globally distributed, sub-10ms-latency reads/writes where cross-region consensus (Paxos/Raft) and Two-Phase Commit (2PC) round-trips violate latency SLAs.

The idea

Relational databases sit atop volatile RAM (buffer pools) and block-oriented disks that can fail mid-write while hundreds of clients mutate overlapping rows concurrently. ACID—Atomicity, Consistency, Isolation, Durability—is the contract that lets application engineers reason about multi-step state changes as if each transaction ran alone on an uncrashable machine.

In practice, engines implement ACID with two cooperating subsystems: logging/recovery (Write-Ahead Logging plus fsync for Atomicity and Durability) and concurrency control (2PL or MVCC + SSI for Isolation). Consistency is shared: the engine enforces declarative constraints (UNIQUE, CHECK, FOREIGN KEY), while the developer defines the transaction boundaries that preserve business invariants.

The same happens for acct_202 (balance = 800).
  3. WAL Append: Before any dirty heap page is flushed to disk, PostgreSQL appends redo/undo records (LSN 0/1A4F820 -> 0/1A4F910) to the WAL buffer.
  4. Commit & fsync: On COMMIT, the engine writes a COMMIT 8421 record to pg_wal and issues fsync() (batched via group commit). Only after the NVMe controller acknowledges durability does the server send COMMIT OK to the client and release row locks.
  5. Crash or Rollback: If power fails at step 3, txid = 8421 has no COMMIT WAL record; on restart, its xmin = 8421 tuples are invisible to all future snapshots and cleaned up by VACUUM.

Write-Ahead Logging decouples fast in-memory MVCC page mutations from sequential `fsync()` durability on commit.

Isolation levels & MVCC mechanics

ANSI SQL defines four isolation levels, though real engines implement them differently. Under Two-Phase Locking (2PL), readers acquire shared (S) locks and writers acquire exclusive (X) locks, blocking each other. Under MVCC (PostgreSQL, MySQL InnoDB, Oracle), writers create new row versions instead of overwriting in place, so readers never block writers and writers never block readers.

  • READ COMMITTED (Postgres/Oracle default): Each statement sees a fresh snapshot of committed data as of statement start. Prevents dirty reads, but allows non-repeatable reads and lost updates in read-modify-write patterns.
  • REPEATABLE READ (MySQL InnoDB default; Snapshot Isolation in Postgres): The transaction holds one snapshot for its entire duration. Prevents non-repeatable reads and (in Postgres) phantom reads, but still allows write skew across disjoint rows.
  • SERIALIZABLE: Guarantees an execution equivalent to some serial order. PostgreSQL uses Serializable Snapshot Isolation (SSI), tracking SIREAD predicate locks to abort transactions that form dangerous rw-antidependency cycles, avoiding 2PL's heavy read blocking.

Failure modes

  1. Deadlocks (40P01): Transaction T1 locks acct_101 then requests acct_202; T2 locks acct_202 then requests acct_101. The lock manager's wait-for graph detector kills one victim. Fix: Always lock entities in a canonical sort order (e.g., ascending account_id).
  2. Serialization Failures (40001): Under REPEATABLE READ or SERIALIZABLE, concurrent writers touching the same or conflicting predicate ranges trigger an abort. Fix: Wrap transactional entrypoints in an idempotent retry loop (3–5 attempts with jittered backoff).
  3. Long-Transaction MVCC Bloat: A forgotten BEGIN idle in an interactive session or a 2-hour analytics query pins the global xmin, stalling VACUUM and inflating table sizes 5–10x.
  4. Cross-System Dual-Write Drift: Writing to Postgres and Kafka in the same request without an Outbox table breaks atomicity—if the Kafka publish fails after COMMIT, downstream consumers miss the event.

Tuning WAL, group commit & contention

When transactional throughput hits a wall, profile before relaxing ACID:

  • Batch & Group Commit: Instead of COMMITting every single row insert (10,000 fsyncs/sec), batch 100–1,000 rows per transaction or rely on commit_delay / NVMe storage so one fsync persists dozens of concurrent commits.
  • Keep Transactions Short: Compute hashes, call external APIs, and render payloads before BEGIN or after COMMIT. Never hold row locks across network I/O.
  • Transactional Outbox Pattern: To publish events atomically with DB state changes, insert into an outbox table inside the same local ACID transaction and tail it via Debezium CDC or a polling relay.

Practical checklist

  • Verify fsync = on and full_page_writes = on (or InnoDB innodb_doublewrite = ON) in production configs.
  • Set idle_in_transaction_session_timeout (e.g., 30s) and lock_timeout (e.g., 2s) so stalled callers fail fast instead of piling up locks.
  • Enforce canonical lock ordering whenever a transaction updates multiple rows in the same table.
  • Implement bounded retry logic for SQLSTATE 40001 and 40P01 at the service boundary.
  • Use SERIALIZABLE (or explicit SELECT ... FOR UPDATE / parent-row locking) anywhere invariants span multiple rows.
  • Keep all external HTTP/gRPC calls strictly outside BEGIN ... COMMIT blocks.
03 / Engineering trade-offs

Weighing architectural decisions

Isolation Level (Read Committed vs. Serializable)

Advantage: `SERIALIZABLE` (via SSI in PostgreSQL) eliminates all anomalies including write skew without manual locking.

Drawback: Increases serialization failure (`SQLSTATE 40001`) abort rates under high contention, requiring client-side retry loops.

Synchronous `fsync` vs. Asynchronous Commit

Advantage: Synchronous WAL flush (`synchronous_commit = on`) guarantees zero committed data loss on power failure.

Drawback: Caps single-thread commit rate to disk IOPS/latency unless batched by group commit or NVMe write-back caches with BBU.

Single-Node ACID vs. Distributed Transactions (2PC / Spanner)

Advantage: Single-node transactions execute in microseconds using local memory locks and a single WAL stream.

Drawback: Scaling writes past one primary requires 2PC or Raft/TrueTime coordination, adding network RTTs and coordinator-failure complexity.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Write Skew Under Snapshot Isolation

Two transactions read overlapping rows (e.g., two on-call doctors checking that at least 2 doctors remain on shift) and update disjoint rows (`doctor_1` and `doctor_2`), leaving 0 doctors on call.

What helps: Use `SERIALIZABLE` isolation (SSI detects rw-antidependency cycles) or lock a shared parent row with `SELECT ... FOR UPDATE`.

Lost Update in Read-Modify-Write

Under `READ COMMITTED`, two threads read `balance = 100`, compute `100 + 20` and `100 - 30` in app memory, and both write back, silently overwriting the first update.

What helps: Perform arithmetic in SQL (`SET balance = balance + 20`), use `SELECT ... FOR UPDATE`, or use `REPEATABLE READ` (which aborts the second writer with a serialization error).

Torn Pages on Power Loss

A 16 KB InnoDB page or 8 KB Postgres page is only half-written to disk during a crash, corrupting B-tree pointers.

What helps: Enable `full_page_writes = on` (PostgreSQL) or the InnoDB doublewrite buffer so recovery can reconstruct any partially written page from a clean full-page image.

MVCC Bloat & Transaction ID Wraparound

An idle-in-transaction session holds an old snapshot open for hours, preventing `VACUUM` from reclaiming dead tuples and causing table bloat and latency cliffs.

What helps: Set `idle_in_transaction_session_timeout` (e.g., `30s`), `statement_timeout`, and monitor oldest `xmin` age and `autovacuum` lag.

05 / Practical checklist

Avoid these mistakes

  • Assuming `REPEATABLE READ` in PostgreSQL is free of anomalies—it is Snapshot Isolation, which still allows write skew.
  • Leaving transactions open across external HTTP/gRPC calls, holding row locks and MVCC snapshots for seconds instead of milliseconds.
  • Ignoring `SQLSTATE 40001` (serialization failure) and `40P01` (deadlock detected) instead of implementing bounded exponential-backoff retries.
  • Locking multiple rows in inconsistent orders across code paths, triggering avoidable deadlocks.
  • Disabling `fsync` or `synchronous_commit` in production benchmarks and forgetting to re-enable them before launch.
