ACID Transaction
Fundamentals.

ACID groups four guarantees for a database transaction: Atomicity (all-or-nothing), Consistency (enforced rules stay valid), Isolation (concurrent work does not expose partial state), and Durability (committed changes survive a crash under configured disk-flush settings).

The idea to keep with you

When concurrent writes contend on shared state, ACID is not a single on/off switch: durability depends on WAL flush configuration and storage reliability, while isolation is chosen by the invariant your application must protect—not by habit.

TL;DR30-second simplified summary
▾

Core Mechanics: In plain terms, ACID ensures a group of database operations either finishes completely or leaves no visible trace (Atomicity), keeps enforced schema rules intact (Consistency), shields concurrent readers from partial work (Isolation), and survives process crashes once flushed to non-volatile storage (Durability).

Visual & Structural Flow: Covers the Write-Ahead Log (WAL) + Multi-Version Concurrency Control (MVCC) commit and recovery pipeline (SQL Client -> Buffer Pool + MVCC -> WAL fsync -> CLOG + Heap Pages), the Write Skew sequence under Snapshot Isolation (Tx 1 Dr. Alice & Tx 2 Dr. Bob), and the ACTIVE -> COMMITTED / ABORTED (40001) retry state machine.

Trade-Offs & Production: Choose READ COMMITTED for independent single-row updates, REPEATABLE READ for multi-query snapshot consistency, and SERIALIZABLE (or a shared guard-row lock followed by every writer) when invariants span multiple rows. Local WAL fsync protects against single-node power loss—not disk corruption or site-wide outages.

Failure Modes & Application: On serialization (40001) or deadlock (40P01) errors, roll back explicitly, apply jittered backoff, retry the entire transaction from BEGIN, and keep external HTTP or webhook calls outside the transaction.

STAGE 01 · THE MECHANISML4 · FUNDAMENTALS

What are ACID Transactions.

Why this matters: The mechanism: understand what each ACID letter actually guarantees—and where engine configuration or application logic is required.

In plain terms, a transaction groups one or more database reads and writes into a single logical unit of work. ACID defines four properties that keep data reliable when crashes or concurrent requests happen:

  • Atomicity (All-or-Nothing): Either every change in the transaction takes effect, or none of them become visible. How engines achieve this varies. PostgreSQL uses MVCC (Multi-Version Concurrency Control) tuple headers (xmin and xmax), the CLOG (Commit Log, stored in pg_xact), and the WAL (Write-Ahead Log, stored in pg_wal). Uncommitted row versions are never marked committed in the CLOG, so readers ignore them and background VACUUM reclaims them later. By contrast, undo-based engines like MySQL InnoDB modify pages in place and actively roll back uncommitted changes using undo logs.
  • Consistency (Enforced Rules Stay Valid): A transaction moves the database from one valid state to another—for the constraints the database actually defines and enforces (CHECK, UNIQUE, FOREIGN KEY, NOT NULL). ACID does not automatically enforce every business rule. Rules spanning multiple rows or tables still require explicit transaction boundaries, constraints, locking, or SERIALIZABLE isolation.
  • Isolation (Shielded Concurrency): Concurrent transactions should not expose half-finished updates or corrupt each other's invariants. Engines enforce this using MVCC snapshots, row locks, or dependency tracking.
  • Durability (Crash Survival Under Configured Flush Rules): Once COMMIT succeeds, committed changes survive a process crash or power loss assuming durable settings are enabled (in PostgreSQL, fsync = on, synchronous_commit = on, and full_page_writes = on) on non-volatile storage. Local WAL flushing does not by itself protect against silent disk corruption, asynchronous replica lag, or site-level disasters—those require checksums, synchronous replication, and multi-region backups.
Storage Engine Mechanics

WAL + MVCC Commit & Crash-Recovery Architecture

1.Write-Ahead Rule: WAL records are flushed to disk via fsync before modified heap pages are written or COMMIT returns success.

2.MVCC Visibility: The old row keeps xmax=8421 and the new row gets xmin=8421; readers check CLOG (pg_xact) to see only committed versions.

3.Crash Recovery: On restart, REDO replays WAL records to restore pages, while transactions without a committed CLOG status remain invisible to MVCC readers.

Caption: A commit is acknowledged only after WAL records are flushed to disk; on crash recovery, WAL REDO restores logged changes while CLOG + MVCC ensure only committed transactions are visible.

STAGE 02 · THE PROBLEML4 · FUNDAMENTALS

Why we need ACID (and how Write Skew breaks weak isolation).

Why this matters: The problem: see how crashes and concurrent reads break multi-step invariants, and trace Write Skew step by step.

Without atomicity, a crash between debiting acct_A and crediting acct_B destroys money permanently. Without isolation, two concurrent withdrawals can both read the same balance, pass validation, and overdraw the account.

Even with transactions enabled, isolation-level names can behave differently across databases. For example, PostgreSQL aliases READ UNCOMMITTED to READ COMMITTED (so dirty reads never occur) and implements REPEATABLE READ using Snapshot Isolation (which prevents phantom reads in PostgreSQL, unlike the minimum ANSI SQL standard).

However, Snapshot Isolation still permits Write Skew when an invariant spans multiple rows:

  1. Invariant: At least 1 doctor must remain on call (count(on_call = true) >= 1). Initially, both Dr. Alice and Dr. Bob are on call (count = 2).
  2. Tx 1 Read (Dr. Alice): Reads SELECT count(*) FROM doctors WHERE on_call = true under its snapshot and sees 2.
  3. Tx 2 Read (Dr. Bob): Concurrently reads the same snapshot and also sees 2.
  4. Tx 1 Update: Updates Alice's row (on_call = false) and commits.
  5. Tx 2 Update: Updates Bob's row (on_call = false) and commits.
  6. Violation: Because Tx 1 and Tx 2 modified disjoint rows, Snapshot Isolation detects no write-write conflict. Both commit—leaving 0 doctors on call.
Concurrency Anomaly

Write Skew Sequence Under Snapshot Isolation

Caption: Snapshot Isolation allows disjoint-row updates to commit concurrently; SSI (SERIALIZABLE) or a shared guard-row lock enforced by all writers prevents the invariant violation.

Engine-Specific Isolation Names

Always check your engine's implementation: PostgreSQL REPEATABLE READ uses Snapshot Isolation (no phantoms), whereas MySQL InnoDB REPEATABLE READ uses MVCC reads with next-key gap locks for locking reads.

Shared-Row Lock Protocol

Locking a shared parent row with SELECT ... FOR UPDATE prevents write skew only if every code path mutating that invariant acquires the same lock first.

Where ACID Transactions belong (and where to avoid them).

Why this matters: Scope boundary: match single-database ACID commits to local invariants and keep external network I/O outside transaction locks.

Think of Where ACID Transactions belong (and where to avoid them) as the intuition layer for ACID Transaction Fundamentals: Scope boundary: match single-database ACID commits to local invariants and keep external network I/O outside transaction locks.

ACID transactions excel for single-database financial ledgers, inventory reservations, and multi-table state transitions. By contrast, holding a database transaction open across external HTTP calls or message-broker publishes creates lock queues and exhausts connection pools.

Financial Ledgers & Double-Entry TransfersAtomic debit and credit with SERIALIZABLE or canonical row locking prevents double-spend.Hot accounts serialize writes and require app-level retry loops on 40001/40P01.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How ACID Transactions are tuned, locked, and retried.

Why this matters: Operational control: configure safe durability guardrails, canonical lock ordering, explicit rollbacks, and idempotent retries.

Production tuning pairs durable storage settings with bounded lock waits and safe application retries:

  1. Durability Guardrails: Keep fsync = on, synchronous_commit = on, and full_page_writes = on in PostgreSQL (or innodb_doublewrite = ON in MySQL InnoDB) to prevent torn pages on power loss.
  2. Fail-Fast Timeouts: Set idle_in_transaction_session_timeout = '30s' and lock_timeout = '2s' so stalled clients abort before blocking VACUUM or piling up lock waiters.
  3. Canonical Lock Ordering: Lock multi-row targets in ascending primary-key order (min(fromId, toId), then max(fromId, toId)) so concurrent transfers cannot form AB-BA deadlock cycles (40P01).
  4. Safe Whole-Transaction Retries: In the Java JDBC example below, assume both accounts live in one PostgreSQL database and that no external side effects (emails, webhooks, payment-gateway HTTP calls) run inside the transaction. On serialization failure (40001) or deadlock (40P01), the code explicitly calls conn.rollback(), waits with jittered exponential backoff, and retries the entire transaction from BEGIN on a fresh snapshot.

// Safe double-entry transfer: canonical lock order, explicit rollback, jittered backoff, no external I/O inside TX
public void transferFunds(DataSource ds, long fromId, long toId, long amountCents) throws SQLException {
    long firstLock = Math.min(fromId, toId);
    long secondLock = Math.max(fromId, toId);
    int maxAttempts = 4;

    for (int attempt = 0; attempt < maxAttempts; attempt++) {
        try (Connection conn = ds.getConnection()) {
            conn.setAutoCommit(false);
            conn.setTransactionIsolation(Connection.TRANSACTION_SERIALIZABLE);

            try {
                try (PreparedStatement lockStmt = conn.prepareStatement(
                        "SELECT id, balance_cents FROM accounts WHERE id IN (?, ?) ORDER BY id FOR UPDATE")) {
                    lockStmt.setLong(1, firstLock);
                    lockStmt.setLong(2, secondLock);
                    lockStmt.executeQuery();
                }

                try (PreparedStatement debit = conn.prepareStatement(
                        "UPDATE accounts SET balance_cents = balance_cents - ? WHERE id = ? AND balance_cents >= ?")) {
                    debit.setLong(1, amountCents);
                    debit.setLong(2, fromId);
                    debit.setLong(3, amountCents);
                    if (debit.executeUpdate() != 1) {
                        throw new IllegalStateException("Insufficient funds");
                    }
                }

                try (PreparedStatement credit = conn.prepareStatement(
                        "UPDATE accounts SET balance_cents = balance_cents + ? WHERE id = ?")) {
                    credit.setLong(1, amountCents);
                    credit.setLong(2, toId);
                    credit.executeUpdate();
                }

                conn.commit();
                return;
            } catch (SQLException | RuntimeException ex) {
                try { conn.rollback(); } catch (SQLException suppressed) { ex.addSuppressed(suppressed); }
                throw ex;
            }
        } catch (SQLException ex) {
            String state = ex.getSQLState();
            boolean retryable = "40001".equals(state) || "40P01".equals(state);
            if (retryable && attempt < maxAttempts - 1) {
                long backoffMs = (20L << attempt) + ThreadLocalRandom.current().nextLong(25L);
                try { Thread.sleep(backoffMs); } catch (InterruptedException ie) { Thread.currentThread().interrupt(); throw ex; }
                continue;
            }
            throw ex;
        }
    }
}

Choosing Isolation Levels by Application Invariant.

Why this matters: The production trade-off: select READ COMMITTED, REPEATABLE READ, or SERIALIZABLE based on the invariant you must preserve.

Pick the weakest isolation level that still protects your application's invariant. In PostgreSQL:

  • Choose READ COMMITTED (PostgreSQL default) when statements mutate independent single rows or use atomic UPDATE ... WHERE balance >= amount checks that do not depend on earlier reads in the same transaction.
  • Choose REPEATABLE READ (Snapshot Isolation in PostgreSQL) when a transaction runs multiple SELECT queries—such as financial reports or multi-table exports—that must observe one consistent point-in-time snapshot.
  • Choose SERIALIZABLE (SSI in PostgreSQL) when correctness depends on a multi-row invariant where concurrent transactions read overlapping sets and update disjoint rows (such as on-call scheduling or unique quota budgets), and you cannot route all writers through a shared guard-row lock.
