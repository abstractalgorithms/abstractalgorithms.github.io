STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are Online Schema Migrations.

Online schema migrations decouple schema evolution from table locks and application downtime. Instead of mutating a 200M-row table in place under an ACCESS EXCLUSIVE or metadata lock (MDL), you execute changes as a backward-compatible multi-phase state transition: Expand (add new nullable column/table), Backfill (throttled chunks + dual-write), Switch Reads (v2 pods read new column), and Contract (drop old column after v1 pods drain).

Expand-and-Contract Lifecycle

Four-Phase Zero-Downtime Schema Evolution

Both v1 and v2 application pods remain healthy throughout every phase, preserving instant rollback.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Online Migrations (the Lock-Queue Pileup).

Even a fast ALTER TABLE needing ACCESS EXCLUSIVE waits behind an active 30-second reporting SELECT. Once that ALTER enters the lock queue, every subsequent SELECT, INSERT, and UPDATE queues behind it, exhausting your application's HikariCP/PgBouncer connection pool in seconds and triggering a site-wide outage.

PostgreSQL `lock_timeout` Fail-Fast

Always set SET lock_timeout = '2000ms' before Postgres DDL so a blocked migration aborts cleanly and retries instead of starving live traffic.

Replica-Lag Throttling

Unthrottled backfills or shadow copies saturate replica I/O; cap batches to 1,000–5,000 rows and pause automatically when Seconds_Behind_Source > 100 ms.

03
STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Online Schema Migrations apply (and where instant DDL suffices).

Use multi-phase online migrations on active OLTP tables with millions of rows; skip shadow tables for empty tables or O(1) metadata-only operations.

ChoiceWhat it buysWhat it costs
Good Candidate: Large OLTP Tables (>1M rows / >1k QPS)Prevents metadata lock pileups and allows rolling/blue-green deploys where v1 and v2 pods share one schema.Splits a column rename or type change into 3–4 sequential PRs and requires 2x disk headroom for shadow copies.
Good Candidate: Index Builds & Constraint ValidationPostgres `CREATE INDEX CONCURRENTLY` and `ADD CONSTRAINT ... NOT VALID` + `VALIDATE CONSTRAINT` avoid write locks.Failed `CONCURRENTLY` builds leave `INVALID` indexes that must be dropped and recreated.
Avoid: Empty Tables or Postgres 11+ Constant Defaults`ADD COLUMN ... DEFAULT 0` (non-volatile) in Postgres 11+ is O(1) metadata-only (still wrap with `lock_timeout`).Running `gh-ost` on an empty table adds unnecessary operational ceremony.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Lock-Safe Postgres & MySQL Migrations are executed.

In PostgreSQL, enforce lock_timeout and statement_timeout, build indexes CONCURRENTLY outside transaction blocks, and validate constraints in two steps (NOT VALID -> VALIDATE CONSTRAINT). In MySQL, use gh-ost (binlog-driven shadow table) with replica-lag pause thresholds.

-- PostgreSQL lock-safe constraint & index pattern
SET lock_timeout = '2000ms';
SET statement_timeout = '5000ms';

ALTER TABLE invoices
  ADD CONSTRAINT chk_positive_total CHECK (total_cents >= 0) NOT VALID;

-- Runs with SHARE UPDATE EXCLUSIVE (does not block reads or writes)
ALTER TABLE invoices VALIDATE CONSTRAINT chk_positive_total;

-- Run outside a transaction block:
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_invoices_customer ON invoices (customer_id);

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: gh-ost vs. pt-online-schema-change vs. Native Online DDL.

Choose the migration engine based on your database, replication format, and foreign-key constraints.

ChoiceWhat it buysWhat it costs
gh-ost (MySQL Binlog Shadow Table)Triggerless—streams binlog events asynchronously and dynamically pauses when replica lag spikes.Requires `binlog_format=ROW` and does not natively migrate tables with incoming foreign keys.
pt-online-schema-change (Trigger-Based)Works without row-based binlogs and handles some foreign-key topologies.Adds synchronous `INSERT/UPDATE/DELETE` triggers on the live table, increasing write latency.
PostgreSQL Native (`CONCURRENTLY` / `NOT VALID`)Built-in primitives handle indexes and check constraints without shadow-table 2x disk overhead.Full table rewrites (e.g., `INT` -> `BIGINT` PK) still require Expand-Contract + dual-write or logical replication cutover.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: gh-ost Shadow Table Cutover on 120M Rows.

To widen orders.total_amount from INT to BIGINT at 8,000 QPS, gh-ost creates _orders_gho, copies chunks in throttled 1,000-row batches while tailing the binlog as a fake replica, pauses if replica lag exceeds 100 ms, and executes an atomic RENAME TABLE cutover.

Live traffic never blocks during hours of chunk copying; only the final metadata rename takes milliseconds.
