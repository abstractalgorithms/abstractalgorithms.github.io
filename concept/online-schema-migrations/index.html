THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Never run a blocking `ALTER TABLE` directly on a large table; pair the Expand-and-Contract pattern with online shadow-table tools (`gh-ost`) or Postgres lock-safe primitives (`CREATE INDEX CONCURRENTLY`, `lock_timeout`).

Explanation anchor
01 / The idea

Foundational mechanics & core principles

A naive ALTER TABLE orders ADD COLUMN tax_cents BIGINT NOT NULL or DROP COLUMN can acquire an ACCESS EXCLUSIVE or metadata lock (MDL) that stalls every SELECT, INSERT, and UPDATE behind it. On a 200M-row table, a 20-minute table rewrite exhausts your application's connection pool in seconds and triggers a site-wide outage.

  • Expand-and-Contract separates a breaking change into backward-compatible steps: add new schema, dual-write, backfill, switch reads, then drop old schema.
  • In PostgreSQL, CREATE INDEX CONCURRENTLY avoids blocking writes, while ADD CONSTRAINT ... NOT VALID followed by VALIDATE CONSTRAINT avoids holding ACCESS EXCLUSIVE during full-table scans.
  • Always set SET lock_timeout = '2s' before running Postgres DDL so a blocked migration fails fast instead of queuing behind a long-running analytics query and starving all incoming traffic.
  • In MySQL, tools like gh-ost (triggerless binlog streaming) and pt-online-schema-change (trigger-based) copy rows into a shadow table in throttled chunks and cut over via an atomic RENAME TABLE.
  • Replica lag monitoring is mandatory: online backfills and shadow copies must throttle or pause automatically when replication lag exceeds thresholds (e.g., 50–100ms).

Good candidates

  • Altering tables exceeding a few million rows or several gigabytes in MySQL/InnoDB or PostgreSQL where table rewrites take minutes to hours.
  • Zero-downtime deployments using rolling or blue/green releases where old (v1) and new (v2) application pods run concurrently against the same schema.
  • High-throughput OLTP tables (>1,000 QPS) where even a 5-second metadata lock queue causes cascading API timeouts.

Think twice

  • Brand-new or empty tables with zero production traffic where an instant DDL statement finishes in <10 milliseconds.
  • Offline data warehouses or batch-only staging tables that have scheduled maintenance windows.
  • PostgreSQL 11+ ADD COLUMN ... DEFAULT (non-volatile) without a rewrite—Postgres handles this in O(1) metadata time, though you still need a tight lock_timeout.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA 180M-row users table (95 GB) needed first_name and last_name columns added and backfilled without stalling 12,000 QPS of login and profile traffic.

The idea

Online schema migrations decouple schema evolution from application downtime and table locks. Instead of mutating a live table in place while holding exclusive locks, you treat schema changes as a multi-phase state transition.

Two complementary mechanisms make this work:

  1. Expand-and-Contract (Parallel Change) at the application/schema boundary, ensuring two consecutive app versions (v1 and v2) are simultaneously compatible with the database.
  2. Non-blocking DDL & Shadow Table Copying at the storage engine level (gh-ost, pt-osc, Vitess VReplication, or Postgres CONCURRENTLY / NOT VALID), ensuring writes never stall during multi-hour data copies.

Concrete walkthrough

Suppose we need to change orders.total_amount from INT to BIGINT on a 120M-row MySQL table running 8,000 QPS:

  1. Shadow Table Creation: gh-ost creates _orders_gho with the new BIGINT column and connects as a fake replica to stream the MySQL binary log (ROW format).
  2. Chunked Backfill + Binlog Apply: It copies primary-key ranges of 2,000 rows from orders to _orders_gho while continuously applying live INSERT/UPDATE/DELETE events from the binlog. If replica lag exceeds 50ms, gh-ost throttles automatically.
  3. Atomic Cutover: Once caught up, gh-ost acquires a brief metadata lock and executes RENAME TABLE orders TO _orders_del, _orders_gho TO orders in a few milliseconds.
  4. Verification & Cleanup: After confirming error rates and latency remain flat, _orders_del is dropped.

gh-ost offloads row copying to a shadow table via binlog streaming and throttles on replica lag before performing an atomic RENAME TABLE swap.

The Expand-and-Contract lifecycle

Even when DDL itself is non-blocking, semantic changes (renaming columns, splitting fields, changing enum meanings) require four distinct phases:

  1. Expand: Add the new nullable column or table (first_name, last_name) alongside the old one (full_name).
  2. Dual-Write & Backfill: Deploy v2 code that writes both old and new columns while reading from the old. Run a throttled background job to backfill historical rows.
  3. Switch Reads: Deploy v3 code that reads from the new column (still dual-writing to allow instant rollback).
  4. Contract: Deploy v4 to stop writing the old column, then drop the old column.

Failure modes

  1. Metadata Lock (MDL) Starvation: In both MySQL and Postgres, a DDL waiting on a 30-second reporting query blocks all subsequent short queries behind it. Always set lock_timeout (Postgres) or lock_wait_timeout (MySQL) to 1–3 seconds and retry.
  2. Disk Exhaustion on Shadow Copies: Cloning a 400 GB table on a 500 GB volume triggers an emergency read-only filesystem halt. Verify >= 2.2x table size in free storage before starting.
  3. Broken Rollbacks After Early Contract: Dropping the old column before verifying v3 stability makes rolling back a bad deployment impossible without restoring backups.

PostgreSQL lock-timeout retry loop

Because ACCESS EXCLUSIVE locks only need a few milliseconds for metadata updates—but can wait indefinitely if a long transaction is open—wrap Postgres DDL in a bounded retry loop:

SET lock_timeout = '2000ms';
SET statement_timeout = '5000ms';
ALTER TABLE invoices ADD CONSTRAINT chk_positive_total CHECK (total_cents >= 0) NOT VALID;

If lock_timeout triggers (SQLSTATE 55P03), the migration aborts cleanly without blocking production traffic, sleeps 5 seconds, and retries. Once NOT VALID succeeds, run ALTER TABLE invoices VALIDATE CONSTRAINT chk_positive_total; in a separate transaction—it takes only SHARE UPDATE EXCLUSIVE, allowing concurrent reads and writes.

Practical checklist

  • Set lock_timeout on every migration: Default to 2s in Postgres and 2s lock_wait_timeout in MySQL.
  • Never use CREATE INDEX without CONCURRENTLY in Postgres (and run it outside a transaction block).
  • Throttle backfills: Chunk by primary key (1,000–5,000 rows), sleep between batches, and halt if replica lag > 100ms.
  • Check disk headroom: Confirm free disk exceeds 2x the target table + index size before running gh-ost or pg_repack.
  • Separate schema from code deploys: Keep old and new schemas compatible across at least one full deployment cycle.
03 / Engineering trade-offs

Weighing architectural decisions

Deployment Velocity vs. Safety

Advantage: Zero-downtime rollouts with safe rollback at every phase (v1 and v2 code both work).

Drawback: A single column rename or type change expands from 1 PR into 3–4 sequential PRs across days.

gh-ost (Binlog) vs. pt-online-schema-change (Triggers)

Advantage: `gh-ost` avoids `INSERT/UPDATE/DELETE` trigger overhead on the primary and can dynamically pause on replica lag.

Drawback: `gh-ost` requires row-based replication (`binlog_format=ROW`) and cannot easily migrate tables with foreign keys pointing to them.

Storage & IOPS Headroom

Advantage: Shadow tables keep the live table untouched until the final millisecond swap.

Drawback: Requires at least 2x free disk space for the table being migrated and consumes extra IOPS during chunk copying.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Postgres Lock-Queue Pileup

An `ALTER TABLE` needing `ACCESS EXCLUSIVE` waits behind a slow `SELECT`. Every subsequent `SELECT` or `UPDATE` queues behind the waiting `ALTER`, exhausting connection pools in seconds.

What helps: Enforce `SET lock_timeout = '2000ms'` and `SET statement_timeout = '5000ms'` in migration runners, retrying with backoff if a lock cannot be acquired.

Replication Lag Spike During Backfill

Unthrottled `UPDATE` batches or shadow-table copies saturate replica I/O, causing read replicas to fall seconds or minutes behind and serving stale reads.

What helps: Cap batch sizes (1,000–5,000 rows), sleep 50–200ms between chunks, and monitor `Seconds_Behind_Source` / `pg_stat_replication` to auto-pause.

Incompatible Rolling-Deploy Schema

Dropping or renaming a column in the same deploy as the code change breaks v1 pods still serving in-flight requests during a rolling update.

What helps: Strictly follow Expand -> Backfill -> Switch Reads -> Contract across separate deployments.

Invalid Index Left Behind by Failed CONCURRENTLY

If `CREATE INDEX CONCURRENTLY` fails (e.g., due to a duplicate key in a `UNIQUE` index), Postgres leaves an `INVALID` index that still incurs write overhead without serving queries.

What helps: Query `pg_index WHERE NOT indisvalid`, drop the invalid index with `DROP INDEX CONCURRENTLY`, fix data, and recreate.

05 / Practical checklist

Avoid these mistakes

  • Running `CREATE INDEX` without `CONCURRENTLY` on a live PostgreSQL table, locking out all writes for the entire index build.
  • Adding a `NOT NULL` column with a volatile default (or without `NOT VALID` check constraint on older engines) and triggering a full-table rewrite.
  • Forgetting to dual-write or backfill rows created between the Expand migration and the code rollout.
  • Running `gh-ost` or `pg_repack` when the database volume has less than 50% free disk space.
  • Leaving ORM auto-migrations (`hibernate.hbm2ddl.auto=update`) enabled in production, causing unpredictable DDL locks on app startup.
