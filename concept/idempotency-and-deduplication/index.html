Idempotency &
Message Deduplication.

Idempotency keys and deduplication logs ensure that network retries, at-least-once message deliveries, and double-clicks execute state mutations at most once while returning the original cached outcome.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Because distributed networks only guarantee at-least-once delivery, every mutating API and consumer must pair a client-generated idempotency key with an atomic database/transaction check—not a separate read-then-write.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

In distributed systems, timeouts are ambiguous: when a client or Kafka consumer times out waiting for an ACK, it cannot tell whether the server crashed before processing or after committing. Retrying without idempotency double-charges credit cards, mints duplicate orders, or corrupts inventory balances. Combining client-supplied Idempotency-Key headers (or event IDs) with atomic persistence turns at-least-once transport into effectively-once business effects.

  • Idempotency is an end-to-end property: the client generates a unique key (UUIDv4) before the first attempt and reuses that exact key across all retries of the same logical operation.
  • Always validate a payload hash (e.g., SHA-256 of request body) alongside the key; reusing the same Idempotency-Key with a different amount or target must return 422 Unprocessable Entity / 409 Conflict.
  • Atomic state transitions are mandatory: insert the key (INSERT ... ON CONFLICT DO NOTHING or DynamoDB attribute_not_exists(pk)) inside the same DB transaction as the business write, or use a Redis SET NX EX lock with an explicit IN_PROGRESS state.
  • Concurrent duplicate requests arriving while the first is still IN_PROGRESS should return 409 Conflict (or 425 Too Early with Retry-After) rather than running in parallel or returning an empty response.
  • Kafka's enable.idempotence=true deduplicates broker-level producer retries via (PID, SequenceNumber), and transactional outbox + consumer-side processed_events tables deduplicate application-level side effects.

Good candidates

  • Payment, billing, and ledger APIs (e.g., Stripe-style POST /v1/charges with Idempotency-Key UUIDv4) where duplicate execution causes financial loss.
  • Event-driven consumers reading from at-least-once brokers (Kafka, SQS Standard, SNS, RabbitMQ) that redeliver messages on consumer rebalance or visibility timeout expiry.
  • Mobile or flaky-network clients that automatically retry timed-out POST/PATCH requests.

Think twice

  • Naturally idempotent operations (PUT /users/42 full replacement, DELETE /sessions/9, or SET status = 'PAID') where re-running yields the identical state without side-effect logs.
  • Read-only GET/HEAD endpoints that perform no mutations.
  • High-throughput fire-and-forget telemetry/metrics where storing a deduplication key per event costs more than the 0.01% duplicate rate.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA mobile checkout app sends POST /v1/payments (amount=4999, Idempotency-Key: 9b1deb4d-...). The gateway times out at 3s due to a slow 3DS bank call and retries 2 seconds later while the first request is still running, then retries a third time after it commits.

The idea

In an unreliable network, at-least-once delivery is the practical baseline: HTTP clients retry on 504/timeout, and message brokers (Kafka, SQS) redeliver unacknowledged events after consumer crashes. Without protection, retrying a non-idempotent operation like POST /transfers or decrement_stock executes the side effect multiple times.

Idempotency means applying an operation multiple times produces the same system state and observable result as applying it once. For naturally non-idempotent operations (creating a charge, appending a ledger entry), we achieve this via an idempotency key (client-generated UUIDv4) or message ID paired with an atomic deduplication store.

The core pattern has three phases: (1) Acquire the key atomically (IN_PROGRESS + payload hash), (2) Execute the business mutation and persist the serialized response inside the same ACID boundary (or atomic state machine), and (3) Replay the stored response on any subsequent retry with the same key.

Concrete walkthrough

Trace POST /v1/transfers (amount=25000, to='acct_88', Idempotency-Key: 7c9e6679-7425-40de-944b-e07fc1f90ae7):

  1. Request 1 (Initial): The API computes req_hash = SHA256(canonical_json). Inside a Postgres transaction, it runs INSERT INTO idempotency_keys(key, req_hash, status, locked_until) VALUES (1,1,1,2, 'IN_PROGRESS', now() + interval '30 seconds') ON CONFLICT (key) DO NOTHING. It inserts 1 row and commits the lock.
  2. Request 2 (Concurrent Retry at +1.2s): The mobile client timed out at 1s and retries with the same key. INSERT ... ON CONFLICT DO NOTHING inserts 0 rows. The server selects the existing row, verifies req_hash matches, sees status = 'IN_PROGRESS' with locked_until > now(), and immediately returns 409 Conflict with Retry-After: 2.
  3. Completion of Request 1 (+2.4s): After debiting the sender and crediting acct_88 inside a single DB transaction, the server updates idempotency_keys in that same commit: status = 'COMPLETED', response_code = 201, response_body = '{"transfer_id":"tr_501"}'.
  4. Request 3 (Post-Commit Retry at +3.5s): The client retries once more. The server finds status = 'COMPLETED' and returns the exact cached 201 Created JSON ({"transfer_id":"tr_501"}) in 2 ms without touching the ledger.

Atomic idempotency state machine: IN_PROGRESS lease blocks concurrent retries, while single-transaction commit of business state and cached response guarantees safe replay.

Messaging deduplication: Kafka, SQS, and the Outbox pattern

API idempotency is only half the story; asynchronous pipelines need two additional layers:

  • Producer-to-Broker: Kafka's enable.idempotence=true assigns every producer a ProducerID (PID) and monotonic SequenceNumber per partition, so broker-level retries on network blips are deduplicated before appending to the log. AWS SQS FIFO offers a 5-minute MessageDeduplicationId window.
  • Broker-to-Consumer: Neither Kafka's idempotent producer nor SQS prevents a consumer from processing a message twice after a crash before offset commit/delete. Consumers must maintain a processed_events(event_id PRIMARY KEY, processed_at) table in the same database as their state updates and check/insert it inside the same transaction.
  • Transactional Outbox: When an API must update Postgres and publish a Kafka event, write the event to an outbox table in the same Postgres transaction and let Debezium (CDC) or a poller publish it—giving the event a deterministic event_id for downstream consumers.

Failure modes

  • External side-effect split-brain: Calling a third-party API (e.g., Stripe) inside a Postgres transaction that later rolls back leaves an external charge with no local DB record. Instead, pass the same Idempotency-Key to Stripe, commit a PENDING_EXTERNAL state first, call Stripe outside the DB lock, then finalize.
  • Expired dedup window on DLQ replay: If idempotency_keys is pruned after 24 hours, replaying a 3-day-old dead-letter queue batch re-executes old mutations.
  • Unbounded table growth: Storing full 50 KB response bodies for 10M requests/day adds 500 GB/day; use daily range partitions (DROP TABLE instead of DELETE) and cap cached body sizes.
  • Leased lock starvation: Setting locked_until to 10 minutes on a 2-second endpoint traps clients in 409 loops after a single pod crash.

Key design & retention rules

  1. Scope keys per tenant/user: Key the unique constraint on (tenant_id, idempotency_key) so Tenant A cannot collide with or probe Tenant B's keys.
  2. Keep IN_PROGRESS leases tight: Set locked_until to 2x–3x the endpoint's p99 timeout (e.g., 15–30 seconds).
  3. Partition by time: Use Postgres declarative daily partitions or DynamoDB ttl attributes (24–72 hours for APIs, 7–30 days for async processed_events) to drop expired keys with zero vacuum overhead.

Practical checklist

  • Require client-generated UUIDv4 Idempotency-Key headers on all non-idempotent POST/PATCH endpoints.
  • Scope uniqueness to (tenant_id, key) and verify SHA-256(request_body) matches (422 on mismatch).
  • Acquire IN_PROGRESS atomically (INSERT ... ON CONFLICT or SET NX EX) with a bounded lease timeout.
  • Commit the business mutation and cached response in the same ACID transaction.
  • Propagate the idempotency key to downstream webhooks and payment providers.
  • Pair at-least-once consumers with a processed_events table and time-partitioned TTL cleanup.
03 / Engineering trade-offs

Weighing architectural decisions

Same-DB Transaction vs. Redis Dedup Cache

Advantage: Inserting the dedup key in the same ACID transaction as the business mutation guarantees zero split-brain between state and dedup record.

Drawback: Adds write IOPS and storage growth to the primary OLTP database, requiring TTL partitioning/pruning (e.g., 24h–7d retention).

Strict In-Progress Locking vs. Optimistic Parallelism

Advantage: Returning `409` on concurrent duplicate keys prevents race conditions and duplicate external API calls (e.g., to Stripe/Adyen).

Drawback: If the worker holding `IN_PROGRESS` crashes without a lease timeout, the key stays locked until TTL expiry unless a lease/heartbeat or recovery state machine is implemented.

Dedup Retention Window vs. Storage Cost

Advantage: Longer retention (e.g., 7–30 days) protects against delayed batch retries and dead-letter queue (DLQ) replays.

Drawback: Keeping millions of UUID keys and cached JSON responses bloats indexes unless stored in time-partitioned tables or DynamoDB TTL items.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Check-Then-Act Race Condition

Two identical retries simultaneously execute `SELECT * FROM idempotency WHERE key = ?`, both see `NULL`, and both execute the payment charge before either writes the key.

What helps: Use an atomic `INSERT ... ON CONFLICT DO NOTHING` / `UNIQUE` constraint or Redis `SET key value NX EX 3600`—never a separate `SELECT` followed by `INSERT`.

Dual-Write Split-Brain (Redis + Postgres)

The service writes the business row to Postgres and then crashes before writing the dedup key to Redis (or writes Redis first and Postgres rolls back), causing either a missed dedup or a permanently blocked key.

What helps: Keep the idempotency/processed_events table in the same ACID database as the business mutation, or use the Transactional Outbox pattern.

Orphaned IN_PROGRESS Lock After Worker Crash

A worker sets `status='IN_PROGRESS'` and is OOM-killed mid-request; every subsequent client retry gets `409 Conflict` forever.

What helps: Attach a short lease timestamp (`locked_until = now() + 30s`) to `IN_PROGRESS` records—if expired and no external side effect was started, allow safe takeover or query the downstream provider by the same idempotency key.

Key Reuse with Mutated Payload

A buggy client hardcodes an `Idempotency-Key` across two different orders ($10 then $500) and silently receives the cached $10 response.

What helps: Store `request_hash = SHA256(method + path + canonical_body)` with the key and reject mismatches with `422 Unprocessable Entity`.

05 / Practical checklist

Avoid these mistakes

  • Generating the idempotency key on the server instead of the client—server-generated keys cannot detect client network retries.
  • Implementing deduplication with a non-atomic `GET` followed by `SET` or `SELECT` followed by `INSERT`.
  • Forgetting to pass the idempotency key downstream to external payment gateways or webhooks, causing duplicate external calls on internal retries.
  • Omitting payload-hash verification, allowing accidental key reuse to return a stale response for a different request.
  • Using `SETNX` in Redis without an expiration (`EX`), leaking memory indefinitely until eviction.
