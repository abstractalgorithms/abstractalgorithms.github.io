STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Idempotency & Deduplication.

In distributed systems, timeouts are ambiguous: when a client or Kafka consumer times out waiting for an ACK, it cannot tell whether the server crashed before processing or after committing. Idempotency guarantees that repeating the same logical request yields the exact same side effect as executing it once.

Clients generate a unique Idempotency-Key (UUIDv4) before the first attempt and reuse that exact key on all retries. The server atomically records (key, request_hash, status) and caches the original response.

Atomic Key Lifecycle

Idempotency Key State Machine (With Crash-Safe Lease)

A 30s lease on IN_PROGRESS prevents a crashed worker from leaving an idempotency key wedged forever.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Check-Then-Act & Dual-Writes Break Under Concurrency.

Doing SELECT * FROM idem WHERE key = ? followed by INSERT has a classic check-then-act race: two concurrent double-clicks both see empty, both charge the card, and both insert. Similarly, checking Redis for dedup before committing Postgres creates a split-brain window if the pod crashes between Redis and Postgres.

Payload Hash Validation

Store request_hash = SHA256(method + path + canonical_body). Reusing the same Idempotency-Key with a different amount must return 422 Unprocessable Entity, not silently replay the old charge.

Same-DB Atomic Transaction

For Kafka/SQS consumers, INSERT INTO processed_events(event_id) ON CONFLICT DO NOTHING inside the same ACID transaction as the business update guarantees exactly-once state.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Idempotency Keys Are Mandatory (and Where They're Redundant).

Add explicit idempotency keys to non-idempotent mutations (POST) and at-least-once consumers; skip them on reads and natural full-replacements.

ChoiceWhat it buysWhat it costs
Mandatory: Payment & Ledger `POST` APIsStripe-style `Idempotency-Key` prevents double-charging on mobile network drops and client retries.Requires TTL pruning (7–30 days) on the idempotency table to bound index size.
Mandatory: Kafka / SQS At-Least-Once ConsumersAbsorbs consumer rebalances and SQS visibility-timeout redeliveries cleanly.Adds 1 unique-index insert per consumed message.
Redundant: `GET` / `HEAD` or Full `PUT` Replacement`PUT /users/42` or `DELETE /sessions/9` is already naturally idempotent.Adding idempotency-key storage on reads wastes write IOPS.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Atomic Postgres Idempotency Guard with Payload Hash.

Use INSERT ... ON CONFLICT DO NOTHING RETURNING id inside the ACID transaction (for consumer dedup) or with a short locked_until lease when wrapping external side effects.

-- Atomic consumer deduplication inside the same PostgreSQL transaction
BEGIN;

WITH ins AS (
  INSERT INTO processed_events (event_id, processed_at)
  VALUES (:event_id, NOW())
  ON CONFLICT (event_id) DO NOTHING
  RETURNING event_id
)
UPDATE ledger_accounts
SET balance_cents = balance_cents + :delta_cents
WHERE account_id = :account_id
  AND EXISTS (SELECT 1 FROM ins);

COMMIT;

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Same-DB ACID Table vs. Redis Dedup vs. Conditional Put.

Choose your deduplication store based on whether the business mutation lives in an ACID database.

ChoiceWhat it buysWhat it costs
Same-DB ACID Table (`ON CONFLICT DO NOTHING`)Zero dual-write split-brain; if the business tx rolls back, the dedup key rolls back too.Adds write IOPS to primary OLTP DB; needs daily partition drops for TTL cleanup.
Redis `SET key val NX EX`Sub-millisecond checks and automatic TTL expiration with zero SQL index bloat.Async replication can lose keys on failover, and Redis+DB is a dual-write unless paired carefully.
DynamoDB `attribute_not_exists(pk)`Single-request conditional write with native TTL attribute expiration.Requires `TransactWriteItems` if updating a separate business item atomically.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Payment API: Atomic Lock -> External Call -> Cached Replay.

When an idempotent API must call an external gateway (like Stripe), hold the database transaction open only for the fast IN_PROGRESS insert, execute the external call with the same downstream idempotency key, then commit COMPLETED + cached response.
