The idea to keep with you

To keep the architecture evolvable without sacrificing reliability, Heartbeat Hysteresis & Hybrid Fan-Out, never broadcast every user's presence heartbeat globally—use lazy pull/subscription for presence and switch from write-push to read-pull above ~500 channel members.

TL;DR30-second simplified summary
▾

Broadcasting online/offline status changes for 50M concurrent users to every contact on every flaky mobile reconnect triggers a quadratic fan-out storm (O(N * F) events/sec).

Production presence systems decouple Heartbeat Ingestion (clients ping every 30s, refreshing SETEX presence:user_id 45s in Redis) from Lazy Presence Subscriptions (clients only subscribe to visible friends/active DM headers) and apply Offline Hysteresis (wait 45s+ before flipping offline so brief tunnel drops don't flicker).

Core Intuition & Failure Mode

1.Global Broadcast Trap: Broadcasting every user's online/offline transition to 50M sockets creates O(N^2) storm traffic.

2.45s TTL + Hysteresis: 30s heartbeats into 45s TTL keys tolerate one dropped mobile packet without flapping offline.

3.Hybrid Fan-Out: Push directly to small groups (<=500); let 100K-member channels pull/page from a shared feed.

45s Redis heartbeat TTLs, lazy roster subscriptions, and hybrid push/pull fan-out avoid O(N^2) presence storms.

STAGE 02 · CORE MECHANICS

Architectural Mechanics

1.Snowflake Ordering: Time-ordered Snowflake IDs let multi-device clients sort messages deterministically without client clocks.

2.Batched Presence Lookup: One Redis MGET resolves gateway mappings for hundreds of recipients in a single round-trip.

3.Async Persistence: Write messages durably to Cassandra/ScyllaDB alongside live WebSocket fan-out.

Batched Redis gateway lookups route live WebSocket pushes in <100 ms and fall back to APNs/FCM for offline users.

Engineering Decision Framework
Problem
How to implement Real-Time Presence, Heartbeat Hysteresis & Hybrid Fan-Out without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
To keep the architecture evolvable without sacrificing reliability, heartbeat Hysteresis & Hybrid Fan-Out, never broadcast every user's presence heartbeat globally—use lazy pull/subscription for presence and switch from write-push to read-pull above ~500 channel members.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

def refresh_presence(redis_client, user_id: str, gateway_id: str, ttl_sec: int = 45) -> None:
    if not user_id or not gateway_id:
        raise ValueError('user_id and gateway_id are required')
    redis_client.set(f'presence:{user_id}', gateway_id, ex=ttl_sec)

def get_visible_presence(redis_client, friend_ids: list[str]) -> dict[str, bool]:
    if not friend_ids:
        return {}
    keys = [f'presence:{uid}' for uid in friend_ids[:200]]  # Cap batch size
    vals = redis_client.mget(keys)
    return {uid: (val is not None) for uid, val in zip(friend_ids[:200], vals)}
STAGE 03 · SAFE IMPLEMENTATION

Heartbeat TTL & Presence Batch Reader

1.Non-Empty Guard: Reject missing user_id or gateway_id before touching Redis to prevent orphaned keys.

2.O(1) Refresh: SETEX overwrites both gateway_id and 45s expiry atomically—handling seamless reconnects.

3.Pipeline MGET: Batching recipient lookups avoids N+1 Redis round-trips in group chats.

Atomic SETEX heartbeats and batched MGET lookups cleanly split online WebSocket delivery from offline push queues.

Throughput & Latency Trade-Offs

1.Epoll / Kqueue Edge: Each tuned gateway pod holds ~100K idle TLS WebSockets in ~4-6 GB RAM.

2.Fan-Out Threshold: Switching channels >500 members to pull/cursor-sync caps amplification at 500x.

3.Coalesced Typing: Rate-limit and coalesce typing indicators at the gateway to cut wasted Pub/Sub traffic.

500 gateway pods, user-sharded Redis presence, and a 500-member push cap sustain 50M sockets at <100 ms p99.

STAGE 05 · FAULT ISOLATION

Blast-Radius & Failure Isolation

1.Reconnect Jitter: Without exponential backoff + jitter, a gateway restart triggers 100K simultaneous TLS handshakes.

2.Slow-Consumer Shed: Disconnect WebSockets whose outbound ring buffer fills instead of letting them OOM the gateway.

3.Separate Push Workers: Slow APNs/FCM endpoints never block live WebSocket Pub/Sub threads.

Jittered client reconnects, bounded per-socket send buffers, and isolated push queues contain gateway failures.

STAGE 06 · RECOVERY & CONSISTENCY

Durability, Consistency & Recovery

1.Gap Sync on Reconnect: Clients pass last_seen_seq on WebSocket resume to fetch any missed messages during brief drops.

2.Monotonic Read Cursor: Store max(read_seq) per (user, channel) so an old mobile device never rewinds desktop read state.

3.Client-Generated UUID: Deduplicate retries by client_msg_id so poor cellular connections never double-post.

Per-channel sequence IDs, reconnect gap-sync, and monotonic read cursors keep multi-device chat consistent.
