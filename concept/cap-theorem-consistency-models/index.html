CAP Theorem & PACELC

Understanding the fundamental boundaries of consistency, availability, and partition tolerance.

Orientation & Intuition

The CAP Theorem (Brewer, 2000) proves that a distributed data store can guarantee at most two of three properties simultaneously: Consistency, Availability, and Partition Tolerance. Because physical networks inevitably experience packet drops, cable cuts, and latency spikes, Partition Tolerance (P) is unavoidable. Systems must deliberately choose CP (refusing stale writes/reads during network splits) or AP (serving stale data to keep uptime). PACELC extends this model to normal non-partitioned operation.

Key takeaway Partition Tolerance is not optional in physical networks. In distributed architectures, choose CP when data correctness is critical (banking ledgers, inventory counts), and AP when uptime and latency dominate (social feeds, shopping carts, analytics).

Core Architecture & Trade-offs

Attempting to build a distributed system that guarantees 100% Availability and 100% Strict Consistency across unreliable networks creates distributed deadlocks, split-brain corruption, and catastrophic system failures.

Key Architecture Invariants

  • Consistency (C): Every read receives the most recent write or an explicit error.
  • Availability (A): Every non-failing request receives a non-error response, without guaranteeing it contains the most recent write.
  • Partition Tolerance (P): The system continues operating despite dropped or delayed network messages between nodes.
  • PACELC Extension: If there is a Partition (P), trade off Availability (A) vs Consistency (C); Else (E), trade off Latency (L) vs Consistency (C).

When to Use

  • CP Systems (Zookeeper, MongoDB with majority write, HBase): When stale data violates financial or transactional invariants.
  • AP Systems (Cassandra, DynamoDB, Riak): When five-nines uptime and low write latency are paramount, and business logic supports eventual reconciliation (CRDTs / last-write-wins).

When NOT to Use

  • Single-node monoliths where network partitions cannot occur between compute and storage.

Deep Dive & Production Considerations

📖 Operational Architecture of the CAP Theorem & PACELC

The CAP Theorem, formally proven by Seth Gilbert and Nancy Lynch in 2002, defines the upper bound of reliability in distributed data systems.

Core Definitions

  • Consistency (C): Linearizability. Every read operation receives the most recent write or an error. All nodes see the exact same data at the exact same instant.
  • Availability (A): Every healthy node returns a non-error response for every request, though it cannot guarantee the data is the absolute freshest.
  • Partition Tolerance (P): The system continues to function despite an arbitrary number of messages being dropped or delayed by the network between nodes.

1. Why Partition Tolerance (P) is Unavoidable

In any real-world distributed system, networks will fail:

  • An optical fiber cable will be cut by construction.
  • A top-of-rack switch will suffer power failure.
  • A 10-second JVM Stop-The-World (STW) garbage collection pause mimics a network timeout.

Therefore, Partition Tolerance (P) is not a choice; it is physical reality. When a partition inevitably occurs, you must choose between:

ModelArchitecturePrimary ExamplesBehavior During Network Split
CPStrong ConsistencyZooKeeper, etcd, MongoDB, HBaseIsolated nodes refuse to serve stale reads and return errors, sacrificing Availability to preserve data correctness.
APHigh AvailabilityApache Cassandra, Amazon DynamoDB, CouchDBIsolated nodes continue serving requests with local stale data, sacrificing Consistency to keep the service up.

2. PACELC: The Modern Extension

CAP only describes system behavior during an active network partition. In production, networks are healthy 99.9% of the time. PACELC (Daniel Abadi, 2012) explains the trade-offs during normal operations:

text 
If there is a Partition (P):
    How does the system trade off Availability (A) and Consistency (C)?
Else (E - normal healthy operation):
    How does the system trade off Latency (L) and Consistency (C)?

PACELC System Classification Matrix

  • DynamoDB / Cassandra (PA/EL): If partitioned, choose Availability; Else, replicate asynchronously to minimize Latency over Consistency.
  • MongoDB (PC/EC): If partitioned, choose Consistency; Else, wait for primary acknowledgement to preserve Consistency over Latency.
  • Google Spanner (PC/EC with TrueTime): Uses GPS and atomic clocks to bound uncertainty, delivering linearizability across global data centers with bounded latency.
