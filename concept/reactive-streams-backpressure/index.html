Reactive Streams
Backpressure.

Reactive Streams backpressure is a non-blocking, pull-based flow-control protocol where downstream consumers explicitly signal how many items (request(n)) they can process, preventing fast producers from overwhelming slow consumers.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Never bridge async producers and slow consumers with unbounded queues; use bounded `request(n)` demand signaling (e.g., Project Reactor, RSocket, gRPC HTTP/2 flow control) and define an explicit overflow strategy (`drop`, `latest`, or `error`) at non-backpressured boundaries.

01 / The idea

Foundational mechanics & core principles

In high-throughput async pipelines, a 10x speed mismatch between a network socket (100k msg/s) and a database sink (10k writes/s) silently fills unbounded LinkedBlockingQueues until the JVM hits OutOfMemoryError or GC death spirals. Backpressure turns memory bloat into controlled upstream slowdowns.

  • Reactive Streams standardizes 4 interfaces (Publisher, Subscriber, Subscription, Processor) with dynamic push-pull semantics: Subscription.request(n) pulls demand, Subscriber.onNext(item) pushes data.
  • Demand is cumulative: calling request(10) then request(5) grants 15 total items; the publisher must never emit more than total unfulfilled demand.
  • Dynamic push-pull avoids the RTT penalty of pure 1-by-1 polling: consumers prefetch batches (e.g., Reactor's Queues.SMALL_BUFFER_SIZE = 256) and replenish at 75% consumption.
  • Operators like flatMap and publishOn maintain internal prefetch buffers; misconfiguring concurrency (flatMap(..., maxConcurrency)) can still spike memory.
  • Non-backpressured sources (e.g., Sinks.many(), UDP sockets, UI events) require explicit overflow strategies: BUFFER (bounded), DROP, LATEST, or ERROR.

Good candidates

  • Streaming pipelines connecting fast ingress (Kafka, WebSockets, SSE, HTTP/2) to slower I/O sinks (PostgreSQL, Elasticsearch, ML inference).
  • Non-blocking JVM or actor systems (Project Reactor, Akka/Pekko Streams, RxJava) where threads must never block on queue.put().
  • Cross-service streaming protocols (RSocket REQUEST_N, gRPC HTTP/2 WINDOW_UPDATE) requiring end-to-end flow control.

Think twice

  • Simple request-response CRUD endpoints where single-item HTTP timeouts and connection pool limits already bound concurrency.
  • Live telemetry or mouse-move streams that cannot be slowed down at the source—here you must explicitly drop, sample, or conflate (onBackpressureLatest) rather than propagating demand.
  • Low-volume batch jobs (< 1,000 items) where reactive operator complexity hurts readability without measurable memory or throughput benefit.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA Spring WebFlux + Reactor Kafka consumer reads 50,000 events/sec, but batched PostgreSQL R2DBC inserts top out at 12,000 rows/sec.

The idea

In a naive push pipeline, a fast producer calls onNext(item) as fast as it can generate data. If the consumer is slower, items pile up in an in-memory queue until memory is exhausted or latency degrades to minutes. Conversely, a naive pull pipeline (next() per item) pays a full round-trip latency tax on every single element.

Reactive Streams backpressure (JVM Spec / RSocket / HTTP/2 flow control) solves both problems with dynamic push-pull: the consumer tells the producer how many items it is ready to accept via Subscription.request(n). The producer may push up to nnn items asynchronously, and must pause once unfulfilled demand hits zero until more request(k) arrives.

Concrete walkthrough

Trace a Reactor pipeline reading from a fast Publisher (50k msg/s) and writing to a slower database sink (10k msg/s) with limitRate(64):

  1. Subscription: The sink subscribes; limitRate(64) calls subscription.request(64) upstream (low-tide/high-tide batching).
  2. Push within budget: The producer emits 64 items via onNext(...), decrementing its atomic demand counter from 64 to 0, then pauses without blocking any thread.
  3. Replenish at 75%: Once the sink consumes 48 items (75% of 64), limitRate automatically issues request(48) upstream so the producer can refill the pipeline in parallel with the remaining 16 items.
  4. Sink slowdown: If the DB stalls for 500 ms, the sink stops calling onNext completion; request(48) is never sent, demand stays at 0, and upstream socket reads pause cleanly via Netty autoRead = false.

Cumulative request(n) credits keep the consumer busy without allowing an unbounded backlog to accumulate in memory.

Handling hot sources & overflow strategies

When a source cannot be slowed down (e.g., live sensor telemetry, UI clicks, UDP packets), request(n) cannot stop arrival. You must choose an explicit backpressure overflow strategy at the boundary:

  • BUFFER (bounded): Queue up to NNN items; fail or spill if exceeded.
  • DROP: Discard incoming items when demand is 0 (protects existing work).
  • LATEST (conflation): Keep only the most recent item per key/stream, overwriting stale unconsumed values—ideal for live stock quotes or progress bars.
  • ERROR: Immediately signal onError(MissingBackpressureException) so the caller can fail fast or reconnect.

Failure modes

  • Unbounded buffer OOM: Using onBackpressureBuffer() without a cap silently disables backpressure protection and crashes the JVM under sustained load.
  • Event-loop starvation: Running blocking I/O on a Netty/Reactor event-loop thread halts request(n) processing for hundreds of concurrent streams.
  • Broken demand accounting: Custom operators that miscount Operators.addCap() / produced() either hang at zero demand or violate the spec by over-emitting.
  • TCP head-of-line blocking: Multiplexing multiple reactive streams onto a single TCP socket without stream-level credits allows one stalled stream to block all others.

Production patterns & observability

  • End-to-end credit propagation: Ensure Netty autoRead=false is wired to downstream request(n) so backpressure actually throttles the OS socket rather than just moving buffers around.
  • Monitor queue depth & drop counters: Emit Prometheus gauges for bounded buffer occupancy and counters for dropped_items_total whenever DROP or LATEST triggers.
  • Use Reactor/RxJava TCK: Validate any custom Publisher or Subscriber against the official Reactive Streams Technology Compatibility Kit (TCK) to catch subtle demand-race bugs.

Practical checklist

  • Verify no operator in the pipeline calls request(Long.MAX_VALUE) or uses an unbounded onBackpressureBuffer().
  • Tune limitRate(n) and flatMap(..., maxConcurrency) to match downstream pool sizes and payload memory.
  • Choose an explicit overflow strategy (DROP, LATEST, ERROR, or bounded BUFFER) at every hot/non-backpressured boundary.
  • Keep event-loop threads 100% non-blocking; verify with BlockHound in CI.
  • Instrument buffer fill ratios and dropped-message metrics to detect sustained backpressure before SLAs breach.
03 / Engineering trade-offs

Weighing architectural decisions

Prefetch Batch Size (`request(n)`) vs. Memory & Latency

Advantage: Larger `n` (e.g., 256) amortizes synchronization and network RTTs for high throughput.

Drawback: Larger `n` increases per-stream memory buffers and delays head-of-line cancellation or fairness across multiplexed streams.

Propagate Backpressure vs. Drop/Conflate

Advantage: Propagating demand guarantees zero data loss for durable queues and files.

Drawback: Can stall upstream producers or exhaust client sockets; real-time market tickers prefer `onBackpressureLatest` to stay fresh.

Reactive Pipelines vs. Virtual Threads (Java 21+)

Advantage: Reactive Streams minimize thread count and enforce explicit bounded buffers end-to-end.

Drawback: Steeper debugging stack traces; simple I/O services may get cleaner code with Virtual Threads + bounded `Semaphore`/`BlockingQueue`.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Unbounded `onBackpressureBuffer()` OOM

Inserting an unbounded buffer operator between a fast hot source and a stalled sink absorbs memory until the process crashes with `OutOfMemoryError`.

What helps: Always specify a `maxSize` and `BufferOverflowStrategy` (e.g., `DROP_OLDEST` or `ERROR`), and export buffer fill-level gauges.

Missing Demand Replenishment (Pipeline Stall)

A custom `Subscriber` requests `request(10)` in `onSubscribe` and forgets to call `request(1)` inside `onNext`, hanging the stream permanently after 10 items.

What helps: Use standard base classes (`BaseSubscriber`, `limitRate`) and test custom subscribers with Reactive Streams TCK.

Blocking Call on Event-Loop Thread

Executing a blocking JDBC query or `Thread.sleep()` inside `map()` stalls the shared Netty event-loop thread, halting `request(n)` signals for all other connections.

What helps: Isolate blocking work onto bounded `Schedulers.boundedElastic()` or virtual-thread executors, and enable BlockHound in CI.

Protocol-Boundary Impedance Mismatch

TCP/HTTP backpressure stops at a Kafka topic or Webhook boundary if the producer ignores `REQUEST_N` or `429` signals.

What helps: Enforce explicit bounded queues, circuit breakers, or `onBackpressureDrop` + DLQ at every protocol boundary.

05 / Practical checklist

Avoid these mistakes

  • Calling `request(Long.MAX_VALUE)` in `onSubscribe`, which disables backpressure completely and reverts to unbounded push.
  • Assuming `Flux.create()` automatically applies backpressure without configuring `OverflowStrategy` or registering `onRequest` callbacks.
  • Setting `flatMap` concurrency to default `256` on heavy 10 MB payloads, inadvertently buffering `256 * 10 MB = 2.5 GB` in flight.
  • Swallowing `MissingBackpressureException` instead of tuning prefetch rates or overflow strategies.
  • Confusing TCP flow control (byte-level) with application-level message backpressure when multiple logical streams multiplex over one connection.
