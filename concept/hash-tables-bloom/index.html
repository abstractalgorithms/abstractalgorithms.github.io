Hash Tables &
Bloom Filters.

A Bloom filter is a space-efficient probabilistic data structure used to test set membership. It answers queries with "definitely not in set" (zero false negatives) or "probably in set" (with a tunable false positive rate). By eliminating expensive disk reads and database scans for non-existent keys, Bloom filters protect high-throughput databases like Cassandra, RocksDB, and HBase.

What are Hash Tables & Bloom Filters.

Why this matters: The mechanism: understand how Hash Tables & Bloom Filters works from first principles.

A Hash Table maps keys to values in O(1) average time using a hash function and collision resolution (separate chaining or open addressing). A Bloom Filter trades exact key storage for extreme space efficiency: it uses an m-bit array (all 0s) and k independent hash functions.

On insert, hash the key k times and set those k bit positions to 1. On query, check those k positions: if any bit is 0, the key is 100% definitely not in the set (zero false negatives). If all k bits are 1, the key is probably in the set (tunable false-positive rate p).

In-Memory Guard

Bloom Filter RAM Guard Protecting LSM-Tree SSTable Disk Reads

1.Sizing Rule: 10 bits per key (m/n = 10) with k = 7 hashes yields a ~1% false positive rate.

2.0.1% Precision: 14.4 bits per key with k = 10 hashes drops false positives to 0.1%.

3.No Deletion: Clearing a bit to 0 could break other colliding keys; use Counting or Cuckoo filters for deletes.

Keeping ~10 bits per key in RAM eliminates 99% of wasted disk seeks on non-existent keys.

CDN One-Hit-Wonder Filtering

Akamai and Cloudflare place a Bloom filter in front of SSD caches so 'one-hit wonder' URLs are only written to flash on their second request, doubling SSD lifespan.

Optimal Sizing Formula

Given capacity n and target false-positive rate p: m = -n * ln(p) / (ln(2)^2) bits and k = (m / n) * ln(2) hash functions.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Double-Hashing Bloom Filter Implementation & Saturation Guard.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Think of Double-Hashing Bloom Filter Implementation & Saturation Guard as the intuition layer for Hash Tables & Bloom Filters: Operational control: configure bounds, failure handling, and safe production defaults.

Instead of computing k separate cryptographic hashes, production filters (Kirsch-Mitzenmacher) compute just two 64-bit hashes h1, h2 and derive k positions via (h1 + i * h2) % m.

Request & State Flow

Double-Hashing Bloom Filter Implementation & Saturation Guard

import hashlib, math

class BloomFilter:
    def __init__(self, expected_items: int, fp_rate: float = 0.01):
        self.m = max(8, int(-expected_items * math.log(fp_rate) / (math.log(2) ** 2)))
        self.k = max(1, int((self.m / expected_items) * math.log(2)))
        self.bits = bytearray((self.m + 7) // 8)

    def _hashes(self, key: str):
        d = hashlib.blake2b(key.encode("utf-8"), digest_size=16).digest()
        h1 = int.from_bytes(d[:8], "little")
        h2 = int.from_bytes(d[8:], "little")
        for i in range(self.k):
            yield (h1 + i * h2) % self.m

    def add(self, key: str) -> None:
        for pos in self._hashes(key):
            self.bits[pos >> 3] |= (1 << (pos & 7))

    def might_contain(self, key: str) -> bool:
        return all((self.bits[pos >> 3] >> (pos & 7)) & 1 for pos in self._hashes(key))
