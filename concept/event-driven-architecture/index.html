STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Event-Driven Architecture.

Why this matters: The mechanism: understand how Event-Driven Architecture works from first principles.

In a synchronous microservice chain (Order -> Inventory -> Payment -> Loyalty -> Email), end-to-end availability is the product of every downstream service's uptime, and one slow dependency exhausts caller thread pools. Event-Driven Architecture (EDA) breaks this temporal coupling.

Instead of issuing imperative commands (SendInvoice) to specific receivers, a producer commits its local state change and emits an immutable past-tense event (OrderPlaced) to a durable partitioned log (Kafka, Pulsar, Kinesis). Independent consumer groups subscribe at their own pace without the producer knowing they exist.

Asynchronous Decoupling

Synchronous RPC Chain vs. Durable Event Log Fan-Out

The producer returns immediately after the local DB + Outbox commit; consumers process at independent speeds with isolated failure domains.

Engineering Decision Framework
Problem
How to implement Event-Driven Architecture (EDA) without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
To bound blast radius during partial cluster failures, replacing synchronous RPC chains with durable partitioned logs (Kafka, Pulsar, Kinesis) isolates service failures and enables independent scaling—at the cost of eventual consistency and idempotency engineering.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Partitioned Ordering

Kafka guarantees strict FIFO ordering within a single partition (keyed by order_id or tenant_id), not globally across a topic—preserving per-entity causality while scaling horizontally.

At-Least-Once + Idempotency

Distributed brokers default to at-least-once delivery; consumers must deduplicate by event_id to achieve effectively exactly-once state updates.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Eliminating Dual-Write Split-Brain with Transactional Outbox.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Think of Eliminating Dual-Write Split-Brain with Transactional Outbox as the intuition layer for Event-Driven Architecture (EDA): Operational control: configure bounds, failure handling, and safe production defaults.

Never update PostgreSQL and then call kafkaProducer.send()—a crash or network blip between the two causes dual-write split-brain. Instead, insert the event into an outbox table inside the same ACID transaction and stream it via Debezium CDC or a SKIP LOCKED relay.

Design Trade-Off

Eliminating Dual-Write Split-Brain with Transactional Outbox

Before · Unbounded Coupling
  • No backpressure on spikes
  • Implicit shared state
  • Cascading tail latency
After · Bounded & Observable
  • Explicit capacity budgets
  • Isolated failure domains
  • Predictable p99 latency
# Idempotent Transactional Outbox relay loop (Python)
def publish_pending_outbox_events(db_conn, kafka_producer, batch_size: int = 100) -> int:
    rows = db_conn.execute(
        "SELECT id, aggregate_id, payload FROM outbox WHERE published_at IS NULL "
        "ORDER BY id ASC LIMIT %s FOR UPDATE SKIP LOCKED",
        (batch_size,),
    ).fetchall()
    for event_id, agg_id, payload in rows:
        kafka_producer.send(topic="domain-events", key=str(agg_id), value=payload)
        db_conn.execute("UPDATE outbox SET published_at = NOW() WHERE id = %s", (event_id,))
    db_conn.commit()
    return len(rows)

# Note: Wrap batch in try/except Exception: db_conn.rollback(); raise so failed Kafka sends do not leave partial DB state.

Partitioned Log (Kafka / Pulsar / Kinesis)Retains events for days/months; multiple consumer groups replay independently with per-key ordering.Hot-partition skew and consumer rebalance storms require careful key selection and batch tuning.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production EDA: Outbox + Schema Registry + DLQ Isolation.

Why this matters: Production architecture: see how the components compose end to end under real load.

Think of Production EDA: Outbox + Schema Registry + DLQ Isolation as the intuition layer for Event-Driven Architecture (EDA): Production architecture: see how the components compose end to end under real load.

Resilient production EDA pairs Transactional Outbox + Debezium CDC with Protobuf/Avro Schema Registry (BACKWARD compatibility) and Dead-Letter Queues (DLQs) so a single poison-pill message never blocks an entire Kafka partition.

Production Topology

Transactional Outbox + CDC + Partitioned Consumer + DLQ

1.No Dual-Writes: Outbox row commits atomically with business state; Debezium streams from Postgres WAL.

2.Poison-Pill Safety: Deserialization or permanent errors route to a DLQ after bounded backoff so partitions keep moving.

3.Hot-Key Defense: High-cardinality keys (tenant_id + entity_id) prevent single-partition saturation.

Safe EDA combines atomic outbox publishing, backward-compatible schemas, idempotent consumers, and DLQ isolation.
