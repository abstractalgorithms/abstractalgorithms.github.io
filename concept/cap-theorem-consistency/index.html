CAP Theorem
& PACELC.

CAP proves a distributed data store cannot simultaneously guarantee linearizability (C) and 100% availability (A) during a network partition (P); PACELC extends this to healthy operation, forcing a choice between latency (L) and consistency (C) even when no partition exists.

The idea to keep with you

When durability and read throughput pull in opposite directions, because network partitions are an unavoidable physical reality, you never 'choose CA'—you choose whether the minority side refuses requests (CP) or serves potentially stale data (AP), and whether healthy-path writes wait for replicas (EC) or return immediately (EL).

TL;DR30-second simplified summary
▾

Core Mechanics: Gilbert and Lynch's formalization of CAP proves that when a network partition (P) splits a distributed store into isolated subgraphs, it must choose between Linearizability (C)—every read sees the latest completed write in real-time order—and 100% Availability (A)—every non-failing node returns a non-error response.

Why CA Is Impossible: A single-node database is not distributed, and any multi-node network eventually drops or delays packets. During a split, if node N3 cannot reach N1 after a write, N3 must either reject the read (choosing CP) or return stale data (choosing AP).

PACELC in Healthy Operation: Because partitions are rare, PACELC models the normal Else (E) path: even with zero packet loss, synchronous majority writes (EC) pay cross-node network RTT for linearizability, while local-ack writes (EL) achieve low latency at the cost of replication lag.

Beyond Binary C vs. A: Overlapping quorums (W + R > N) alone do not guarantee linearizability without consensus or read-repair, and Causal Consistency is the strongest consistency model still achievable alongside 100% availability.

STAGE 1 · THE FORMAL PROOFfoundation

What CAP Actually Means: Brewer's Conjecture & Gilbert–Lynch's Proof.

Why this matters: Understand the exact formal definitions of C, A, and P—and why the impossibility proof leaves no loophole for CA.

Eric Brewer proposed the CAP principle in 2000, and Seth Gilbert and Nancy Lynch proved it formally in 2002 under an asynchronous network model. Most confusion around CAP comes from reading C, A, and P loosely instead of using their exact formal meanings:

  • Consistency (C) means Linearizability (Atomic Consistency): Every read must return the value of the most recent completed write (or a concurrent write), establishing a single global real-time order across all nodes. This is not the 'C' in ACID (which means preserving application invariants like balance >= 0).
  • Availability (A) means 100% Non-Failing Node Responsiveness: Every request received by a non-failing node must result in a non-error response—without guaranteeing it contains the most recent write. If a minority node returns 503 Service Unavailable because it lost quorum, the system has sacrificed A.
  • Partition Tolerance (P) means Surviving Arbitrary Message Loss: The network between nodes is allowed to drop or arbitrarily delay messages between subgraphs G1 and G2.
GILBERT & LYNCH 2002 PROOF

Why a Partition Forces CP (Refuse) vs. AP (Stale Read)

Once N1 acknowledges Write(x = 1) during a partition, N2 cannot simultaneously answer Read(x) (A) and return x = 1 (C).

STAGE 2 · WHERE INTUITION BREAKSintermediate

Three Myths That Break Real Distributed Systems.

Why this matters: See why naive quorum rules, heartbeat timeouts, and 'CA' claims fail under real partitions.

Misreading CAP leads engineers into three classic failure modes:

  1. Myth: "W + R > N Guarantees Linearizability." In Dynamo-style leaderless stores (N=3, W=2, R=2), a write can succeed on {N1, N2} while a concurrent write or partial failure leaves N3 stale. If Client 1 reads {N1, N2} (x = 1) and Client 2 immediately reads {N2, N3} before read-repair finishes—or if a failed write only reached N1 without rolling back—Client 2 can observe x = 0 after Client 1 already saw x = 1. Overlapping quorums guarantee at least one node saw the write, not linearizable ordering across readers.
  2. Myth: "A Missed Heartbeat Means the Leader Is Dead." In an asynchronous network, a 5-second stop-the-world GC pause or an asymmetric packet drop looks identical to a crashed process. If N2 promotes itself to leader without revoking N1's lease or requiring a majority quorum (epoch/fencing token), both sides accept writes—producing silent split-brain data divergence.
  3. Myth: "CP Means Low Availability." CAP's A requires 100% of non-failing nodes to respond. In practice, a 5-node Raft cluster (PC/EC) stays available to the majority partition (3 nodes) during a split and only refuses requests on the isolated minority (2 nodes)—often delivering 99.99%+ effective availability.
LINEARIZABILITY COUNTEREXAMPLE

Why W + R > N Without Read-Repair Violates Linearizability

Once any reader observes x = 1, linearizability forbids any later reader from observing x = 0—even if the original write did not reach a full quorum.

PACELC: The Latency vs. Consistency Trade-Off When There Is No Partition.

Why this matters: Understand Daniel Abadi's PACELC extension and why healthy clusters still pay a consistency tax.

CAP only describes what happens during a network partition (P). Yet in production, your network is healthy 99.9%+ of the time. Daniel Abadi introduced PACELC in 2012 to capture the full equation:

> If there is a Partition (P), how does the system trade off Availability (A) and Consistency (C); Else (E)—when the network is healthy—how does it trade off Latency (L) and Consistency (C)?

Implementing CP Majority Quorums vs. AP Local Fallback.

Why this matters: See the exact coordinator branching logic that separates a CP store from an AP store during a partition.

Think of Implementing CP Majority Quorums vs. AP Local Fallback as the intuition layer for CAP Theorem & PACELC: See the exact coordinator branching logic that separates a CP store from an AP store during a partition.

At the coordinator layer, the difference between CP and AP during a network split comes down to whether the node enforces a majority quorum (N // 2 + 1) and monotonic term/epoch before acknowledging a request, plus bounded retry/backoff when transient packet drops occur.

Design Trade-Off

Implementing CP Majority Quorums vs. AP Local Fallback

Before · Unbounded Coupling
  • No backpressure on spikes
  • Implicit shared state
  • Cascading tail latency
After · Bounded & Observable
  • Explicit capacity budgets
  • Isolated failure domains
  • Predictable p99 latency
import time
from dataclasses import dataclass

@dataclass
class VersionedValue:
    value: str
    epoch: int
    seq: int

class PartitionAwareStore:
    def __init__(self, peers: list, mode: str = "CP"):
        self.peers = peers          # includes self
        self.mode = mode            # "CP" or "AP"
        self.quorum = len(peers) // 2 + 1

    def write(self, key: str, val: str, epoch: int, seq: int) -> dict:
        acks = 0
        # Bounded retry with short backoff for transient packet loss
        for attempt in range(2):
            acks = sum(1 for p in self.peers if p.try_replicate(key, val, epoch, seq))
            if acks >= self.quorum:
                return {"status": 200, "acks": acks, "linearizable": True}
            time.sleep(0.02 * (attempt + 1))

        if self.mode == "CP":
            # Sacrifice Availability (A) on minority side to preserve Linearizability (C)
            raise RuntimeError(f"503 Unavailable: quorum not met ({acks}/{self.quorum})")

        # AP mode: accept locally and mark for anti-entropy / conflict resolution later
        self.peers[0].local_put(key, VersionedValue(val, epoch, seq))
        return {"status": 200, "acks": max(acks, 1), "linearizable": False}

STAGE 5 · THE CONSISTENCY SPECTRUMadvanced

Linearizability vs. Causal & Eventual Consistency.

Why this matters: Distinguish CAP's linearizability from weaker models—and learn why Causal Consistency is the strongest model compatible with AP.

CAP often feels overly restrictive until you realize that C in CAP refers specifically to Linearizability—the strongest single-object consistency model. Stepping one rung down the consistency ladder unlocks dramatic availability and latency gains:

  • Linearizability (CAP's C): Global real-time ordering across all clients. Requires coordination across a majority quorum—impossible under a partition if every node must stay available.
  • Sequential Consistency: All nodes see operations in some shared global order that respects each individual client's program order, even if it lags real-time wall clocks. Still impossible alongside 100% availability under partitions.
  • Causal Consistency: Operations that are causally related (e.g., a post and a reply to that post) are seen in the same order by every node, while concurrent unrelated operations may be seen in different orders. Crucially, Causal Consistency is provably achievable with 100% Availability under network partitions (via vector clocks or dependency metadata), making it the strongest practical model for PA/EL systems.
  • Eventual Consistency: If no new updates occur, replicas eventually converge—offering no ordering guarantees in the meantime.

How Three Real Architectures React to the Same Network Partition.

Why this matters: Trace the exact step-by-step behavior of PC/EC, PC/EL, and PA/EL clusters when a region link drops.

Suppose a 3-region cluster (US-East, US-Central, US-West) loses the link isolating US-West (N3) from the other two regions (N1, N2). Each PACELC class handles traffic to N3 differently:

  • PC/EC (3-Node Raft / CockroachDB / Spanner): N1 and N2 retain a 2-of-3 majority quorum and continue serving linearizable writes and reads. N3 loses its leader lease and rejects both writes and linearizable reads (503) until the partition heals.
  • PC/EL (Single-Leader Postgres + Async Replica): Writes routed to N3 fail immediately because N3 is a read-only replica. Reads on N3 may still succeed if configured for local follower reads, returning stale data bounded by async replication lag.
  • PA/EL (3-Node Cassandra CL=ONE / Dynamo-style): Both {N1, N2} and the isolated N3 accept reads and writes independently. When the link heals, hinted handoff, read-repair, and anti-entropy Merkle trees reconcile divergent writes.
