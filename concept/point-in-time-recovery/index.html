A foundational engineering concept

Point-in-Time
Recovery.

Point-in-time recovery (PITR) pairs periodic physical base backups with continuous transaction log archiving (such as PostgreSQL WAL or MySQL binlogs) so you can rewind a database to any exact second, transaction ID, or log sequence number before a destructive event.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Snapshots alone lose everything written since the last backup; PITR bounds data loss to your log-shipping interval by replaying committed changes up to the exact instant before corruption.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Logical and physical snapshots run on coarse schedules—typically every 6 to 24 hours—leaving an unacceptable data-loss window when a bad migration, DELETE without a WHERE clause, or ransomware attack hits production. PITR closes that gap to seconds or minutes by treating the database's append-only transaction log as an immutable replay stream.

  • PITR requires two distinct artifacts: a consistent physical base backup (e.g., pg_basebackup) and an unbroken chain of archived write-ahead log segments (e.g., 16 MB PostgreSQL WAL files) starting from the backup's start LSN.
  • Recovery is non-destructive to history only if you restore into a fresh cluster or standby and advance recovery_target_time, recovery_target_xid, or recovery_target_lsn up to—never past—the bad transaction.
  • High-write workloads generate massive WAL volume (e.g., 14 GB/hour at 4,000 TPS), making parallel WAL fetching (pgBackRest process-max) and archive_timeout tuning critical for both RPO and RTO.
  • PostgreSQL creates a new timeline ID (00000002, 00000003) every time a recovered cluster is promoted, preventing new writes from overwriting the original timeline's archived WAL segments.
  • An untested PITR archive is indistinguishable from a broken one: a single missing or corrupted WAL segment breaks the replay chain at that LSN and halts recovery.

Good candidates

  • Production OLTP databases where losing more than a few minutes of committed transactions violates RPO SLAs.
  • Guarding against logical corruption (accidental DROP TABLE, bad batch updates, application bugs) that replication faithfully copies to standbys.
  • Spinning up isolated forensic clones of production at a historical timestamp to debug billing discrepancies or audit state.

Think twice

  • Ephemeral caches, session stores, or derived search indexes that can be rebuilt from a primary source of truth faster than replaying logs.
  • Single-table or single-row surgical rollbacks when the database is 20 TB and you have logical backups or soft-delete/temporal tables available.
  • Workloads with zero tolerance for RTO delays where pg_basebackup + WAL replay takes hours unless paired with warm standbys or copy-on-write storage snapshots.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAt 14:22:18 UTC, a deployment script runs UPDATE invoices SET status = 'VOID' without a WHERE clause on a 450 GB PostgreSQL 16 cluster. Streaming replicas apply the update within 12 ms, so failing over does not help.

The idea

Every ACID database already writes every state change to an append-only transaction log—Write-Ahead Log (WAL) in PostgreSQL, Redo/Binlog in MySQL—before dirty pages hit data files. Point-in-time recovery exploits that log as an out-of-band time machine.

Instead of relying solely on periodic snapshots, you pair two streams in durable object storage (such as S3 or GCS):

  1. Base backups: A consistent physical copy of the cluster's data directory taken at time T0T_0T0​ (recording a starting Log Sequence Number, e.g. 0/1A000060).
  2. Continuous WAL archive: Every 16 MB WAL segment generated after T0T_0T0​, shipped asynchronously via archive_command (or pg_receivewal) with checksums.

To recover to any target Ttarget>T0T_{target} > T_0Ttarget​>T0​, you restore the base backup onto a clean host, configure restore_command to pull archived WAL segments, and instruct the engine to stop replay at the exact recovery_target_time, recovery_target_lsn, or recovery_target_xid just prior to the fault.

Concrete walkthrough

Suppose a 400 GB PostgreSQL 16 cluster takes a full pgBackRest backup at 02:00 UTC (start LSN 42/80000028) and ships 16 MB WAL segments to s3://db-backups/prod-pg/ with archive_timeout = 300s. At 11:14:07.412 UTC, an operator accidentally runs TRUNCATE TABLE user_sessions;.

  1. Pinpoint the cutoff: Inspect pg_waldump on the latest archived WAL segment or query application audit logs to confirm the TRUNCATE committed at 11:14:07.412 UTC (XID 9841204).
  2. Restore the base backup: On a standby-sized host, run pgbackrest --stanza=prod --delta --type=time --target="2026-11-12 11:14:05+00" --target-action=pause restore.
  3. Replay WAL: PostgreSQL enters recovery mode, fetches segments from 42/80000028 up to 11:14:05 UTC (~9.2 GB of WAL at ~250 MB/s takes ~37 seconds), and pauses before applying XID 9841204.
  4. Verify & promote: Connect read-only, confirm SELECT count(*) FROM user_sessions; returns the expected 18.4M rows, then run SELECT pg_wal_replay_resume(); (or pg_ctl promote), creating Timeline 2 (00000002.history) and switching application DNS/PgBouncer to the recovered primary.

PITR separates immutable history (Timeline 1) from the promoted recovery branch (Timeline 2), allowing safe rollbacks even after logical corruption.

Targeting precision: time, XID, LSN, and restore points

Choosing the right recovery target parameter determines how cleanly you stop before a bad transaction:

  • recovery_target_time: Best when you know the wall-clock timestamp from application logs or APM traces. Vulnerable to clock skew across app servers; always aim 2–5 seconds before the logged error.
  • recovery_target_xid: Stops at an exact PostgreSQL transaction ID found via pg_waldump or log_line_prefix (%x). Combined with recovery_target_inclusive = false, it stops cleanly right before the offending transaction.
  • recovery_target_lsn: Targets a byte offset in the WAL stream (e.g., 42/9A1200F0). Useful when two transactions share the same millisecond.
  • recovery_target_name: Stops at an explicit named marker created beforehand with SELECT pg_create_restore_point('pre_deploy_v42'); right before risky schema migrations.

Failure modes

PITR systems rarely fail loudly during normal operation; they fail silently until an outage forces a restore.

  1. Silent archiver stall: If archive_command returns non-zero (e.g., expired S3 credentials), PostgreSQL retains unarchived WAL files in pg_wal/ until the local disk hits 100% and the database panics.
  2. Split-brain timelines: Promoting a recovered cluster without updating archive_command or isolating the stanza can cause Timeline 2 to overwrite or collide with Timeline 1 metadata.
  3. Unbounded WAL replay time: Heavy UPDATE/VACUUM bursts or CREATE INDEX operations can generate 50+ GB of WAL in an hour; without differential backups, replay becomes the dominant bottleneck in RTO.
  4. Missing recovery_target_action = 'pause': Defaulting to 'promote' immediately opens the cluster to new writes, making it impossible to rewind a few seconds earlier without restarting the entire base restore.

Production tooling and cloud-managed PITR

Self-managed PostgreSQL clusters typically use pgBackRest (C-based, parallel compression, page-level checksums, incremental/differential backups) or WAL-G (Go-based, streaming LZ4/Zstd compression to S3/GCS/Azure Blob). For MySQL 8.0, Percona XtraBackup provides hot physical base backups paired with continuous binary log (binlog) archiving replayed via mysqlbinlog.

Managed services automate the plumbing but still enforce hard limits: AWS RDS / Aurora ships transaction logs to S3 every 5 minutes (capping RPO at ~5 minutes) with a maximum retention of 35 days; Cloud SQL retains transaction logs for 7 days by default; Neon and Aurora separate storage from compute so PITR branches mount copy-on-write pages in seconds without copying terabytes.

Practical checklist

  • Enable wal_level = replica (or logical), archive_mode = on, and archive_timeout = 300 (5 minutes) to bound RPO even during quiet traffic periods.
  • Use pg_create_restore_point('pre_migration') before every destructive DDL or backfill script.
  • Alert when pg_stat_archiver.failed_count > 0 or now() - last_archived_time > interval '10 minutes'.
  • Schedule daily differential backups and weekly full backups so WAL replay never exceeds 24 hours of write volume.
  • Run an automated monthly PITR drill in staging that restores to a random timestamp 48 hours in the past, verifies row counts, and records actual RTO.
03 / Engineering trade-offs

Weighing architectural decisions

RPO vs. storage & network overhead

Advantage: Setting `archive_timeout = 60s` or continuous WAL streaming (`pg_receivewal`) caps data loss to under a minute even on low-traffic databases.

Drawback: Frequent forced WAL switches pad partially filled 16 MB segments, inflating S3/GCS archive storage and object-PUT API costs.

Base backup frequency vs. RTO

Advantage: Daily full or differential base backups keep WAL replay windows short, bounding recovery time to minutes.

Drawback: Frequent physical backups consume disk I/O, network bandwidth, and object storage, especially when `full_page_writes = on` spikes WAL size after checkpoints.

Physical PITR vs. logical snapshots (`pg_dump`)

Advantage: Physical PITR recovers an entire multi-terabyte cluster to a sub-second boundary without table-locking or SQL parsing overhead.

Drawback: You cannot restore a single dropped table directly into the live cluster; you must restore the whole cluster (or tablespace) separately and export the table.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Broken WAL chain (missing segment)

A transient S3 upload error, disk-full event on `pg_wal`, or premature retention cleanup deletes a single 16 MB WAL file between the base backup and the target time.

What helps: Monitor `pg_stat_archiver.failed_count` and alert if `last_archived_time` lags > 5 minutes; use `pgBackRest` or `WAL-G` with checksum verification and retain at least two full base backup cycles.

Overshooting the recovery target

An operator guesses the incident timestamp 10 seconds too late, replays the destructive `DROP TABLE`, and promotes the cluster.

What helps: Always set `recovery_target_action = 'pause'` (not `'promote'`) so you can run read-only `SELECT` checks before issuing `SELECT pg_wal_replay_resume()` or promoting; keep the original timeline's WAL untouched.

Timeline collision after repeated recoveries

Recovering twice from the same base backup without timeline isolation causes tools or operators to mix WAL segments from Timeline 1 and Timeline 2.

What helps: Use timeline-aware archiving tools (`pgBackRest`, `WAL-G`) that store `.history` files and never overwrite existing WAL segments; specify `recovery_target_timeline = 'latest'` intentionally.

RTO blowout from unthrottled WAL accumulation

A bulk backfill generates 800 GB of WAL between weekly base backups; during an outage, single-threaded `restore_command` replays at 60 MB/s and takes nearly 4 hours.

What helps: Schedule daily incremental/differential backups (`pgBackRest --type=incr`), enable parallel WAL prefetch (`archive-get-queue-max`), and run monthly automated restore drills that measure actual RTO.

05 / Practical checklist

Avoid these mistakes

  • Assuming streaming replication or Multi-AZ failover replaces PITR—replicas apply `DROP TABLE` and bad `DELETE`s in milliseconds.
  • Leaving `pg_basebackup` without `-X stream` or verified WAL archiving, producing an inconsistent base backup that refuses to start.
  • Setting `recovery_target_action = 'promote'` on the first restore attempt instead of `'pause'` to inspect the recovered state first.
  • Deleting old base backups aggressively without checking whether any retained WAL segments depend on them.
  • Never running an end-to-end restore test, only discovering years later that IAM permissions or KMS keys block `restore_command` in the recovery environment.
