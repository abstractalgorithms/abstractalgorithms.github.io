The idea to keep with you

Point-in-time recovery (PITR) pairs periodic physical base backups with continuous transaction log archiving (such as PostgreSQL WAL or MySQL binlogs) so you can rewind a database to any exact second, transaction ID, or log sequence number before a destructive event.

01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Point-in-Time Recovery (PITR).

Every ACID database writes state changes to an append-only transaction log (Write-Ahead Log in PostgreSQL, Redo/Binlog in MySQL) before dirty pages hit data files. PITR turns that log into an out-of-band time machine using two artifacts: a consistent physical base backup (pg_basebackup / pgBackRest) and an unbroken chain of archived 16 MB WAL segments starting from the backup's start LSN.

During recovery, you restore the base backup into a fresh cluster and replay WAL up to recovery_target_time, recovery_target_xid, recovery_target_lsn, or a named pg_create_restore_point(...).

Base Backup + WAL Replay

PITR Restoration Architecture (Base Snapshot + WAL Stream)

1.1. Unbroken Chain: Every 16 MB WAL segment between the base backup LSN and target time must exist in object storage.

2.2. Pause & Verify: Set recovery_target_action = 'pause' to run read-only SELECT checks before promoting.

3.3. Timeline Isolation: Promotion increments the timeline ID (00000002) so new writes never overwrite Timeline 1 WAL.

Base backups bound RTO, while continuous WAL archiving bounds RPO to seconds or minutes.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need PITR (and why Replicas do not save you).

Daily pg_dump or storage snapshots leave up to 24 hours of unrecoverable data loss. Worse, streaming replication and Multi-AZ standbys do not protect against human or application errors: an accidental TRUNCATE TABLE, DELETE without WHERE, or ransomware wipe replicates to every standby in milliseconds. Only PITR lets you rewind to the exact transaction before destruction.

An Untested Archive Is a Broken Archive

A single missing 16 MB WAL segment halts replay at that LSN. Monitor pg_stat_archiver.failed_count and run monthly automated restore drills.

Named Restore Points Before Risky DDL

Run SELECT pg_create_restore_point('pre_migration') immediately before backfills or migrations so you have an exact, clock-skew-free stop target.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where PITR is mandatory (and where logical/rebuild suffices).

Use physical PITR on all authoritative OLTP databases; skip it for ephemeral caches or derived search indexes that rebuild faster from primary sources.

ChoiceWhat it buysWhat it costs
Good Candidate: Production OLTP Clusters (RPO < 5 min)Bounds data loss to `archive_timeout` (e.g., 60–300s) and spins up isolated forensic clones at historical timestamps.High-write clusters (4,000 TPS -> ~14 GB/hr WAL) require parallel WAL prefetch and object-storage lifecycle tuning.
Avoid: Ephemeral Redis Caches & Derived Search IndexesRebuild from the primary OLTP database or Kafka log rather than archiving WALs.Archiving volatile cache mutations wastes S3 IOPS and storage.
Avoid: Single-Row Oops on a 20 TB ClusterIf soft-deletes or logical table backups exist, surgical restore avoids replaying terabytes for one row.Physical PITR restores the entire cluster separately before you `pg_dump` the recovered table back.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How PITR Archiving & Safe Target Recovery are configured.

Enable wal_level = replica, archive_mode = on, and archive_timeout = 300s (with pgBackRest or WAL-G for parallel LZ4/Zstd compression and checksums). During recovery, always set recovery_target_action = 'pause' first so you never overshoot and promote past the destructive transaction.

# PostgreSQL postgresql.auto.conf for safe PITR verification
restore_command = 'pgbackrest --stanza=prod-pg archive-get %f "%p"'
recovery_target_time = '2026-11-18 11:14:07.000 UTC'
recovery_target_inclusive = false
recovery_target_action = 'pause'
recovery_target_timeline = 'latest'

-- Verify recovered state while paused, then promote explicitly:
SELECT count(*) FROM users;
SELECT pg_wal_replay_resume(); -- or pg_promote()

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Physical PITR vs. `pg_dump` vs. Copy-on-Write Snapshots.

Balance RPO, RTO on multi-terabyte databases, and operational complexity.

ChoiceWhat it buysWhat it costs
Physical PITR (pgBackRest / WAL-G)Sub-second target precision, seconds-to-minutes RPO, and no table-locking SQL parse overhead.RTO scales with WAL volume since last base backup unless mitigated with daily incremental backups and parallel prefetch.
Logical Backups (`pg_dump`)Allows restoring a single dropped table directly into a live database.24-hour RPO gap and slow single/parallel SQL restore on >500 GB databases.
Cloud CoW Storage Snapshots (RDS/Aurora/ZFS)Near-instantaneous volume restore (low RTO) paired with managed WAL shipping.Cloud vendor lock-in and higher storage snapshot costs on high-churn volumes.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Rewinding Past a 11:14:07 `TRUNCATE`.

A 400 GB Postgres 16 cluster takes a pgBackRest full backup at 02:00 UTC and ships WALs to S3. At 11:14:07.412 UTC an operator runs TRUNCATE TABLE users. Engineers provision an isolated recovery cluster, replay WAL up to 11:14:07.000 UTC with action='pause', verify users rows, promote to Timeline 2, and export the table.
