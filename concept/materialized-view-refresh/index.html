Refresh Strategies.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Choose full concurrent refresh for simple batch dashboards, and incremental or CDC-driven refresh when tables exceed tens of millions of rows or require sub-minute freshness.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Joining 500M-row fact tables with dimension tables on every dashboard load burns CPU, saturates I/O, and blows past 200 ms API budgets. Materialized views (MVs) turn O(N) runtime scans into O(1) or O(K) indexed lookups—provided the refresh strategy does not lock out readers or fall behind write throughput.

  • Full refresh (REFRESH MATERIALIZED VIEW) recomputes the entire query from scratch and acquires an AccessExclusiveLock in PostgreSQL, blocking all SELECTs unless CONCURRENTLY is used.
  • REFRESH MATERIALIZED VIEW CONCURRENTLY in PostgreSQL requires at least one UNIQUE index on the MV and performs a diff-merge, allowing reads during refresh at ~2x–3x slower refresh time.
  • Incremental View Maintenance (IVM) / CDC-based MVs (ClickHouse, Oracle FAST REFRESH, pg_ivm, Flink/Debezium) apply only row deltas (INSERT/UPDATE/DELETE) in O(Δ) time.
  • Non-monotonic operations (DISTINCT, MEDIAN, PERCENTILE_CONT, NOT EXISTS, outer joins) are hard or impossible to maintain incrementally without auxiliary state.
  • Staleness SLAs must be monitored explicitly via last_refreshed_at or TARGET_LAG metrics rather than assuming cron jobs always finish on time.

Good candidates

  • Read-heavy dashboards, leaderboards, and APIs executing repeated multi-table JOIN + GROUP BY aggregations over millions of rows.
  • Systems that can tolerate bounded staleness (e.g., 5 seconds to 1 hour) in exchange for predictable < 20 ms read latency.
  • OLAP/HTAP engines (ClickHouse AggregatingMergeTree, Snowflake Dynamic Tables, Postgres MVs) where pre-aggregation cuts compute cost by 10x–100x.

Think twice

  • Strict read-your-own-writes transactional paths (e.g., checking live bank balance before a transfer).
  • High-cardinality ad-hoc filtering where users slice by arbitrary unindexed columns—querying the MV becomes as slow as the base table.
  • Write-saturated base tables when using non-incremental full refreshes that thrash disk I/O and autovacuum.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA 120M-row usage_events table took 14 seconds per tenant aggregation query, timing out the customer portal.

The idea

A regular SQL view is a saved query macro—every SELECT re-executes the underlying joins and scans. A materialized view (MV) persists the query result physically on disk (and buffer pool/page cache), turning expensive O(N) scans into fast O(log N) or O(1) indexed reads.

The core engineering problem is maintenance: how to keep the materialized copy synchronized with mutating base tables without blocking readers or amplifying write latency beyond budget. Strategies span a spectrum from periodic full recomputation (O(N)), to concurrent diff-swaps, to incremental delta maintenance (O(Δ) via CDC or engine-native triggers).

Concrete walkthrough

Walk through PostgreSQL REFRESH MATERIALIZED VIEW CONCURRENTLY on a 50M-row orders table summarized into daily_revenue_mv (50k rows):

  1. Unique Key Requirement: Create CREATE UNIQUE INDEX idx_rev_pk ON daily_revenue_mv (merchant_id, order_date) so Postgres can uniquely identify rows during diffing.
  2. Snapshot Execution: When REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue_mv runs, Postgres executes the view query against a consistent MVCC snapshot into a temporary internal table.
  3. Full Outer Diff: Postgres performs a full outer join between the old MV and the temp table on (merchant_id, order_date) to find only inserted, updated, or deleted rows (say 1,200 changed rows).
  4. Non-Blocking Apply: Only those 1,200 rows are inserted/updated/deleted in daily_revenue_mv under a RowExclusiveLock, allowing concurrent SELECT queries to read clean snapshots with zero downtime.

Whether using PostgreSQL concurrent diff-refresh or CDC/ClickHouse incremental aggregation, isolating delta computation keeps analytical reads fast and lock-free.

Incremental algebra & algebraic aggregates

Not all SQL expressions can be maintained incrementally in O(Δ) time:

  • Distributive / Algebraic Aggregates (COUNT, SUM, MIN, MAX, AVG): SUM and COUNT are trivially invertible (+x on insert, -x on delete). AVG is maintained by storing (sum, count) and dividing at read time. MIN/MAX handle inserts in O(1) but require a secondary index or heap if the current extremum is deleted.
  • Holistic Aggregates (MEDIAN, PERCENTILE_CONT, COUNT(DISTINCT)): Cannot be updated from a scalar delta alone; engines use sketches like HyperLogLog (uniqHLL12) or t-digest (quantileTDigestState) to stay incremental.

Failure modes

  1. Non-Concurrent Lock Pileup: A 4-minute exclusive refresh blocks all incoming API SELECTs, exhausting the app's connection pool in 5 seconds. Mitigation: Require CONCURRENTLY (with a unique index) or atomic table swaps in CI linting.
  2. Refresh Interval Overrun: Table growth pushes refresh time past the cron period, causing two refreshes to collide and thrash I/O. Mitigation: Guard jobs with advisory locks (pg_try_advisory_lock) and migrate to incremental/partitioned rollups before utilization hits 70%.
  3. Source DELETE/UPDATE Drift in Append-Only MVs: ClickHouse MVs only fire on INSERT; an ALTER TABLE ... DELETE on the source leaves stale totals in the target MV. Mitigation: Use ReplacingMergeTree with versioned upserts or explicit partition-level recomputation.
  4. Autovacuum & Temp-Disk Exhaustion: Frequent CONCURRENTLY refreshes generate dead tuples and large temp sort files. Mitigation: Tune autovacuum_vacuum_scale_factor on the MV and size work_mem / temp storage.

Partitioned & Lambda-hybrid patterns

When a single MV grows too large for full refresh yet needs exact SQL semantics:

  • Time-Partitioned Rollup Tables: Freeze historical partitions (e.g., day < today - 1) as immutable tables and only refresh the hot today + yesterday partitions every 5 minutes.
  • Hot/Cold Union View: Expose a VIEW that UNION ALLs a precomputed historical_mv (up to midnight) with a live indexed query on events WHERE ts >= today, giving zero staleness while scanning < 0.5% of total data.

Practical checklist

  • Define the exact staleness SLA (e.g., < 60 s vs 15 min) and verify readers can tolerate it.
  • Add a UNIQUE index for CONCURRENTLY refreshes plus secondary indexes matching actual WHERE/ORDER BY clauses.
  • Guard scheduled refreshes with an advisory lock to prevent overlapping runs.
  • Store non-additive metrics as (sum, count) or sketch states (HLL, t-digest) for incremental safety.
  • Monitor refresh_duration_seconds, staleness_seconds, and dead-tuple bloat with automated alerts.
03 / Engineering trade-offs

Weighing architectural decisions

Full Refresh vs. Incremental / Delta Refresh

Advantage: Full refresh is trivial to author in SQL and supports arbitrary window functions and `PERCENTILE` logic.

Drawback: Compute cost scales with total table size O(N) on every tick, eventually exceeding the refresh interval.

Concurrent Diff-Refresh vs. Locking Refresh

Advantage: `CONCURRENTLY` keeps `SELECT` queries non-blocking in production.

Drawback: Requires a unique index, uses extra temp/WAL space for the diff, and runs 2x–3x slower than an exclusive swap.

Eager (On-Commit) IVM vs. Scheduled / Lag-Based Refresh

Advantage: On-commit triggers/IVM keep the view strictly fresh with zero staleness.

Drawback: Adds write amplification and lock contention to every OLTP `INSERT`/`UPDATE` transaction.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

AccessExclusiveLock Read Outage

Running `REFRESH MATERIALIZED VIEW` without `CONCURRENTLY` in PostgreSQL blocks all dashboard `SELECT` queries for minutes, piling up API threads.

What helps: Always add a `UNIQUE` index and use `CONCURRENTLY`, or build a new table and atomically `ALTER TABLE ... RENAME`.

Refresh Overlap & Queue Spiral

Data grows so a 5-minute cron refresh takes 7 minutes; overlapping jobs contend on locks and exhaust DB CPU.

What helps: Acquire a non-blocking advisory lock (`pg_try_advisory_lock`) at job start so overlapping runs skip cleanly, and alert when duration > 70% of interval.

MV Log / WAL Bloat

If an incremental refresh consumer stalls, materialized view change logs (`MLOG$_*`) or replication slots grow unboundedly until disk fills.

What helps: Monitor replication lag and log table size; set alert thresholds and fallback to full snapshot re-sync if lag exceeds retention.

Silent Staleness After Failed Job

A refresh fails due to a schema change or timeout, leaving dashboards serving 3-day-old numbers with no user warning.

What helps: Store `refreshed_at` metadata in the view or control table and surface freshness badges + PagerDuty alerts on SLA breach.

05 / Practical checklist

Avoid these mistakes

  • Forgetting to create indexes on the materialized view itself (it starts with zero indexes beyond any required unique index).
  • Using `REFRESH ... CONCURRENTLY` on an empty or newly created MV before an initial non-concurrent populate.
  • Writing `SELECT *` in an MV without explicit column types, causing refreshes to break on upstream `ALTER TABLE`.
  • Expecting ClickHouse `MATERIALIZED VIEW` to retroactively update when `UPDATE`/`DELETE` mutations hit the source table (it only triggers on `INSERT` blocks).
  • Storing non-additive metrics like `AVG()` directly in incremental rollups instead of storing `SUM` + `COUNT` (or `-State` combinators).
