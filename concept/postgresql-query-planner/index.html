STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is the PostgreSQL Query Planner.

SQL is declarative: you specify what rows you want, not how to fetch them. PostgreSQL's Cost-Based Optimizer (CBO) generates equivalent physical plans—varying scan types (Seq Scan, Index Scan, Index Only Scan, Bitmap Index Scan) and join operators (Nested Loop, Hash Join, Merge Join)—and scores them in arbitrary cost units anchored to seq_page_cost = 1.0, random_page_cost = 4.0, and cpu_tuple_cost = 0.01.

Selectivity estimates come from pg_statistic (null_frac, n_distinct, most_common_vals, and equidepth histograms).

Plan Tree & Scan Selection

PostgreSQL Cost-Based Plan & Index Selection

1.1. Statistics: MCVs and histograms in pg_statistic predict row counts at every filter node.

2.2. Scan Choice: Index Scans win at low selectivity; Bitmap Scans batch random heap I/O; Seq Scans win above ~20%.

3.3. Join Strategy: Nested Loop fits tiny outer sets; Hash Join fits unsorted sets within work_mem; Merge Join fits pre-sorted inputs.

Every bad plan starts at the first node where estimated rows diverge sharply from actual rows.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Planner Literacy Matters (1000x Plan Regressions).

A single 100x row-count underestimate in a 4-table join can flip PostgreSQL from a 3 ms Nested Loop with Index Scan to a 45-second Hash Join spilling hundreds of megabytes to temp_files. Worse, wrapping an indexed column in DATE(created_at) or LOWER(email) makes the predicate non-sargable, forcing Sequential Scans even when an index exists.

Correlated Columns Need `CREATE STATISTICS`

Postgres assumes column independence (P(A and B) = P(A) * P(B)). For city = 'Bengaluru' AND state = 'Karnataka', create multivariate stats: CREATE STATISTICS ... (dependencies, mcv).

Calibrate `random_page_cost` for NVMe SSDs

The default random_page_cost = 4.0 assumes spinning HDDs; lowering it to 1.1 on NVMe SSDs stops Postgres from choosing Sequential Scans over Index Scans.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Planner Tuning applies (and where bottlenecks lie elsewhere).

Use EXPLAIN (ANALYZE, BUFFERS) whenever queries regress as tables grow; look elsewhere when the issue is lock waits or table bloat.

ChoiceWhat it buysWhat it costs
Good Candidate: Multi-Table Joins & Skewed Multi-Tenant QueriesFixing stale `ANALYZE` stats, adding multivariate stats, or tuning `plan_cache_mode` eliminates 10x–1000x regressions.Requires inspecting `EXPLAIN (ANALYZE, BUFFERS)` on realistic production parameter values.
Avoid: Blaming the Planner for Lock Contention or BloatCheck `pg_locks` and `pg_stat_user_tables.n_dead_tup` when simple PK lookups stall.Adding redundant indexes slows down writes and `VACUUM` without fixing lock waits.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How `EXPLAIN (ANALYZE, BUFFERS)` and Stats Tuning are managed.

Always run EXPLAIN (ANALYZE, BUFFERS) (wrapped in BEGIN; ... ROLLBACK; for mutations), find the first node where rows= diverges from actual rows= by >10x, rewrite non-sargable predicates into half-open ranges, and run ANALYZE immediately after bulk COPY loads.

-- 1. Inspect actual rows, shared buffer hits/reads, and temp disk spills
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, c.tier
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'PENDING'
  AND o.created_at >= '2026-11-17' AND o.created_at < '2026-11-18'; -- Sargable range

-- 2. Fix correlated column underestimates
CREATE STATISTICS orders_status_region_stats (dependencies, mcv)
ON status, region FROM orders;
ANALYZE orders;

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Fixing Stats & SQL vs. `work_mem` vs. Planner Hints.

Prefer fixing statistics and sargability over brittle query hints or oversized global memory settings.

ChoiceWhat it buysWhat it costs
Multivariate `CREATE STATISTICS` + `default_statistics_target`Gives the CBO accurate row estimates across skewed and correlated columns cleanly.Slightly longer `ANALYZE` runs and larger `pg_statistic` catalog.
Session-Scoped `work_mem` vs. Global `work_mem`Raising `work_mem` for specific reporting queries eliminates `external merge Disk` sorts without risking global OOM.Setting `work_mem = 256MB` globally with 500 connections risks Linux OOM killer termination (allocated per sort/hash node).
Planner Hints (`pg_hint_plan`)Emergency surgical override for an unfixable third-party ORM query.Freezes execution plans even as data grows 10x, creating future regressions.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Fixing an Index-Only Scan & Prepared Plan Trap.

A multi-tenant query degrades after 5 executions because plan_cache_mode = auto switches to a generic plan that hurts a mega-tenant, while Index Only Scan shows high Heap Fetches due to a lagging visibility map. Setting plan_cache_mode = force_custom_plan for the skewed query and tuning autovacuum_vacuum_scale_factor = 0.02 restores 2 ms p99.
