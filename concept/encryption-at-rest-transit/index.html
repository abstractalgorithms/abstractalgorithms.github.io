Encryption at Rest
& in Transit.

Encryption in transit protects data moving across untrusted networks via TLS 1.3/mTLS, while encryption at rest protects persisted disks and backups using AES-256-GCM envelope encryption backed by a KMS.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Terminate TLS 1.3 everywhere (including internal service-to-service mTLS), use envelope encryption (DEK + KMS KEK) for storage, and separate key-management permissions from data-storage permissions.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Unencrypted east-west traffic inside a VPC or Kubernetes cluster lets any compromised pod sniff credentials and PII, while unencrypted snapshots or misconfigured S3 buckets turn a single IAM leak or decommissioned drive into a reportable data breach.

  • Encryption in transit uses TLS 1.3 (RFC 8446) with ephemeral ECDHE key exchange (Perfect Forward Secrecy) and AEAD ciphers (TLS_AES_256_GCM_SHA384 or CHACHA20_POLY1305), ensuring past captures cannot be decrypted even if a server's private key leaks later.
  • mTLS (Mutual TLS) authenticates both client and server via X.509 certificates (e.g., SPIFFE/SPIRE or Istio service mesh), preventing lateral movement inside clusters.
  • Envelope encryption encrypts large payloads locally with a fast symmetric Data Encryption Key (DEK) (AES-256-GCM), then encrypts the DEK with a Key Encryption Key (KEK) held inside a hardware-backed KMS/HSM.
  • Storage-layer encryption (EBS, S3 SSE-KMS) protects against physical disk theft and snapshot leaks, whereas application-layer (field-level) encryption protects sensitive columns (SSN, OAuth tokens) even from DBAs and SELECT * dumps.
  • AEAD ciphers (AES-256-GCM) provide both confidentiality and integrity/authenticity tags—never reuse a 96-bit nonce/IV with the same key, as nonce reuse breaks GCM completely.

Good candidates

  • All public and internal network traffic (HTTPS, gRPC, database connections, Kafka/Redis replication) using TLS 1.3 or mTLS.
  • All persistent storage (EBS/NVMe volumes, RDS, S3/GCS, etcd secrets, backups) using KMS-managed envelope encryption.
  • Multi-tenant SaaS systems requiring cryptographic tenant isolation via per-tenant Customer Managed Keys (CMKs).

Think twice

  • Relying solely on disk-level encryption at rest (e.g., AWS EBS encryption) to protect against SQL injection or compromised application IAM roles—authorized read paths decrypt transparently.
  • Replacing password hashing (Argon2id / bcrypt) with reversible encryption—passwords must be hashed, never encrypted.
  • Skipping TLS on internal VPC traffic under the assumption that 'the private network is safe' (violates Zero Trust and compliance frameworks like PCI-DSS 4.0 / SOC 2).
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA SaaS integration service stored third-party OAuth refresh tokens in Postgres. Even with RDS disk encryption enabled, any DBA or read-replica analytics pipeline could read plaintext tokens.

The idea

Data lives in two vulnerable states: moving across a network (in transit) and sitting on disk, snapshots, or object storage (at rest). Protecting both requires two distinct cryptographic architectures.

In transit, TLS 1.3 (and mTLS for service-to-service traffic) establishes an authenticated, ephemeral session key via ECDHE so passive sniffers and active MitM attackers see only authenticated ciphertext. At rest, envelope encryption pairs fast symmetric AES-256-GCM (via a per-object Data Encryption Key, DEK) with a hardware-backed KMS Key Encryption Key (KEK)—so keys never sit next to the data they protect.

Concrete walkthrough

Consider a client uploading a sensitive tax PDF to a microservice backed by KMS and S3:

  1. In Transit (Edge & Mesh): The browser connects via TLS 1.3 (TLS_AES_256_GCM_SHA384) to the API Gateway. Inside the cluster, the Gateway forwards the payload over mTLS (mutual X.509 certificates issued by Istio/SPIRE) to the Document Service.
  2. DEK Generation: The Document Service calls kms:GenerateDataKey(KeyId=alias/tax-docs, KeySpec=AES_256), receiving a 32-byte plaintext DEK and an encrypted DEK blob.
  3. Local AEAD Encryption: In memory, the service generates a random 96-bit nonce, encrypts the PDF bytes with AES-256-GCM(DEK, nonce, aad=tenantId), and immediately zeros the plaintext DEK after use.
  4. Persistence: It writes { ciphertext, nonce, encryptedDEK, keyVersion } to S3 (which also applies storage-layer SSE-KMS).
  5. Separation of Duties: A backup auditor with s3:GetObject but without kms:Decrypt cannot read the PDF.

Defense-in-depth encryption flow combining TLS 1.3/mTLS in transit with KMS-backed AES-256-GCM envelope encryption at rest.

TLS 1.3 & mTLS internals

TLS 1.3 (RFC 8446) removes legacy, broken primitives (RSA key transport, CBC, SHA-1, RC4) and cuts the handshake to 1-RTT (ClientHello + key_share -> ServerHello + encrypted Certificate/Finished). Every connection uses ephemeral ECDHE, guaranteeing Perfect Forward Secrecy (PFS).

For internal microservices, mTLS requires the client to also present a valid X.509 certificate during the handshake. Service meshes (Istio, Linkerd) automate 24-hour certificate rotation via SPIFFE IDs (spiffe://cluster.local/ns/prod/sa/payments), eliminating static API keys between services.

Failure modes

  1. GCM nonce collision: Reusing a 96-bit nonce with the same DEK leaks the XOR of two plaintexts and allows key-recovery of the GHASH authentication key.
  2. Missing AAD binding: Omitting Associated Authenticated Data (tenantId or recordId) lets an attacker with DB write access copy an encrypted ciphertext blob from Tenant A into Tenant B's row (confused deputy attack).
  3. Unchecked cert verification: Leaving rejectUnauthorized: false or sslmode=require (without verify-full) silently accepts attacker-signed certificates.
  4. KMS outage / throttling: Calling KMS synchronously on every single DB row read without a bounded local DEK cache causes cascading latency spikes.

Key rotation & operational hygiene

  • Enable automatic annual KEK rotation in KMS; KMS retains old key versions transparently for decryption while encrypting all new DEKs under the latest version.
  • For application-layer DEKs, rotate on a schedule or after 2^30 encryptions per key, and use blind indexes (HMAC-SHA256 with a separate key) if you need exact-match lookups on encrypted PII columns like email.
  • Audit every kms:Decrypt call in CloudTrail/SIEM to detect anomalous bulk data exfiltration.

Practical checklist

  • Enforce TLSv1.3 (minimum TLSv1.2) on all public ALBs/CDNs with HSTS enabled.
  • Enable STRICT mTLS across internal service-to-service traffic and sslmode=verify-full on all DB clients.
  • Enable KMS-backed encryption at rest on all volumes, databases, queues, and automated backups.
  • Use AES-256-GCM with fresh random 96-bit nonces and tenant/record AAD for sensitive application fields.
  • Separate storage IAM permissions from kms:Decrypt permissions.
  • Monitor certificate expiration (<14 days) and KMS API throttling alarms.
03 / Engineering trade-offs

Weighing architectural decisions

Storage-layer encryption (SSE-KMS / TDE) vs Application-layer field encryption

Advantage: Storage-layer encryption is transparent to SQL queries, indexes, and ORMs with near-zero developer effort.

Drawback: Application-layer encryption protects against DBA/SQLi exposure, but disables range queries (`>`/`<`), sorting, and substring `LIKE` indexes on encrypted columns.

KMS per-request calls vs local DEK caching

Advantage: Calling KMS for every decrypt enforces real-time key revocation and CloudTrail auditability.

Drawback: Unbounded KMS calls hit API rate limits (e.g., 5,500–30,000 req/s) and add 5–15 ms latency per call; caching DEKs in memory with a short TTL (e.g., 5 minutes) via AWS Encryption SDK solves both.

mTLS everywhere vs edge-only TLS

Advantage: mTLS enforces cryptographic workload identity and prevents packet sniffing inside compromised VPC subnets.

Drawback: Adds automated X.509 certificate rotation complexity (cert-manager/SPIRE) and breaks legacy TCP health checks if misconfigured.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

AES-GCM nonce/IV reuse

Hardcoding a static IV or using a weak counter across restarts with the same AES-256-GCM key allows an attacker to XOR ciphertexts and forge authentication tags.

What helps: Always generate a cryptographically random 96-bit nonce (`os.urandom(12)`) per encryption call, or rotate DEKs well before `2^32` messages.

Expired or unverified TLS certificates (`sslmode=require` trap)

Using `sslmode=require` (instead of `verify-full`) or `InsecureSkipVerify: true` encrypts the wire but skips hostname/CA validation, leaving connections open to MitM.

What helps: Enforce `verify-full` with pinned CA bundles and automate short-lived certificate rotation (e.g., 24-hour SPIFFE certs or Let's Encrypt) with expiry alerts at 14 days.

Co-located key and ciphertext

Storing a hardcoded AES key in `.env` or the same database/S3 bucket as the encrypted backups renders encryption useless on a bucket leak.

What helps: Keep KEKs strictly inside KMS/HSM; grant the backup/storage role `s3:GetObject` without `kms:Decrypt`.

Unencrypted swap, logs, and core dumps

Decrypted PII or DEKs written to stdout logs, APM traces, or unencrypted `/tmp` swap files leak outside the encrypted database.

What helps: Scrub sensitive fields before logging, disable swap on app nodes, and encrypt ephemeral NVMe/root volumes.

05 / Practical checklist

Avoid these mistakes

  • Using `AES-ECB` (which leaks patterns) or unauthenticated `AES-CBC` without HMAC (vulnerable to padding oracle attacks) instead of `AES-256-GCM`.
  • Assuming `HTTPS` at the load balancer means internal traffic to microservices and databases is encrypted.
  • Leaving `TLS 1.0`/`1.1` or weak RSA key-exchange ciphers enabled for 'backward compatibility'.
  • Using `sslmode=require` in PostgreSQL/MySQL drivers and thinking it prevents Man-in-the-Middle attacks (it does not verify the server certificate CN/SAN).
  • Encrypting user passwords instead of hashing them with `Argon2id` + per-user random salt.
