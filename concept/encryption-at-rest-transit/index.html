The idea to keep with you

Encryption in transit protects data moving across untrusted networks via TLS 1.3/mTLS, while encryption at rest protects persisted disks and backups using AES-256-GCM envelope encryption backed by a KMS.

TL;DR30-second simplified summary
▾

Core Mechanics: Data faces two distinct threat surfaces: In Transit: TLS 1.3 (RFC 8446) uses 1-RTT ephemeral ECDHE (Perfect Forward Secrecy) + AEAD ciphers (TLS_AES_256_GCM_SHA384).

Visual & Structural Flow: Depicts TLS 1.3 + mTLS Ingestion & KMS Envelope Encryption with AAD Binding (Browser (TLS 1.3) -> Gateway (mTLS) -> Doc Service -> AWS KMS (KEK) -> S3 (SSE-KMS)); Automated KMS KEK Versioning & SPIFFE mTLS Certificate Rotation (ACTIVE KEK v2 -> RETIRED KEK v1 -> ALERT / REVOKE).

Trade-Offs & Production: Balance real-time revocation against KMS rate limits and operational complexity. Enable automatic annual KEK rotation in KMS (KMS retains old versions transparently for decrypt while encrypting new DEKs under the latest key), rotate short-lived mTLS certs.

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are Encryption in Transit & Envelope Encryption at Rest.

Data faces two distinct threat surfaces:

  • In Transit: TLS 1.3 (RFC 8446) uses 1-RTT ephemeral ECDHE (Perfect Forward Secrecy) + AEAD ciphers (TLS_AES_256_GCM_SHA384). Inside clusters, mTLS authenticates both client and server via short-lived X.509 certificates (Istio/SPIRE).
  • At Rest: Envelope encryption encrypts payloads locally with a fast symmetric Data Encryption Key (DEK) (AES-256-GCM + random 96-bit nonce + AAD), then wraps the DEK with a hardware-backed KMS Key Encryption Key (KEK).
02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Disk-Only Encryption & Plaintext VPCs Still Leak Data.

Unencrypted east-west VPC traffic lets any compromised pod sniff credentials, while disk-only EBS/RDS encryption decrypts transparently for DBAs, BI replicas, and SQL injection—requiring app-layer envelope encryption for high-value secrets like OAuth refresh tokens.

Envelope Encryption Flow

TLS 1.3 + mTLS Ingestion & KMS Envelope Encryption with AAD Binding

Separating s3:GetObject from kms:Decrypt ensures a storage/backup leak cannot decrypt payloads without KMS access.

App-Layer Envelope Encryption for OAuth Tokens

Even with RDS disk encryption, DBAs and BI replicas could read plaintext OAuth refresh tokens. Wrapping per-record AES-256-GCM DEKs with KMS (kms:Decrypt granted only to auth-svc) blocked unauthorized reads.

Enforcing TLS 1.3 + STRICT mTLS (<1.2 ms Overhead)

Enforcing TLSv1.3 on edge ALB, sslmode=verify-full on Postgres, and Istio STRICT mTLS secured east-west traffic with <1.2 ms p99 overhead via TLS session resumption.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Each Encryption Layer Fits (and What It Doesn't Protect).

Never confuse disk encryption with app-layer field encryption—and never encrypt passwords (hash them with Argon2id or bcrypt).

ChoiceWhat it buysWhat it costs
Storage-Layer (EBS / S3 SSE-KMS / RDS TDE)Transparent to SQL queries, indexes, and ORMs; stops physical drive/snapshot leaks.Does NOT stop DBA snooping, BI replica leaks, or SQLi on authorized app roles.
App-Layer Envelope (`AES-256-GCM` + AAD)Protects sensitive PII/tokens even from DBAs and cross-tenant blob swaps (`AAD=tenantId`).Disables SQL range (`>`/`<`) and `LIKE` indexes; exact lookup needs HMAC blind indexes.
Avoid: `sslmode=require` or `InsecureSkipVerify: true`Always use `sslmode=verify-full` with pinned CA bundles.`require` encrypts the wire but skips hostname/CA checks, leaving connections open to MitM.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to Prevent GCM Nonce Reuse, Bind AAD & Cache DEKs.

  1. Never Reuse a 96-Bit GCM Nonce: Reusing (key, nonce) leaks the XOR of plaintexts and compromises GHASH—always generate os.urandom(12) per call and rotate DEKs well before 2^30 messages.
  2. Bind AAD (tenantId:recordId): Stops an attacker with DB write access from copying Tenant A's ciphertext into Tenant B's row.
  3. Cache DEKs Locally (5 min TTL): Avoid hitting KMS 30,000 req/s rate limits and 5–15 ms latency on every row read.
  4. Zero Keys & Scrub Logs: Disable swap, scrub PII from logs/traces, and audit kms:Decrypt in CloudTrail.
# AES-256-GCM authenticated encryption with fresh 96-bit nonce & tenant AAD (Python)
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

def encrypt_field(dek_32b: bytes, plaintext: bytes, tenant_id: str, record_id: str) -> tuple[bytes, bytes]:
    nonce = os.urandom(12)  # Fresh 96-bit CSPRNG nonce per encryption
    aad = f"{tenant_id}:{record_id}".encode("utf-8")
    ciphertext = AESGCM(dek_32b).encrypt(nonce, plaintext, aad)
    return nonce, ciphertext

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Architecture: Automated Key & Certificate Rotation.

Enable automatic annual KEK rotation in KMS (KMS retains old versions transparently for decrypt while encrypting new DEKs under the latest key), rotate short-lived mTLS certs every 24 hours, and alert <14 days before any public TLS cert expiry.
