01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Lambda Architecture.

Some workloads—like ad-tech click attribution (400k clicks/sec)—need both <3s live campaign pacing dashboards and 100% deduplicated, bot-filtered daily financial invoices. Lambda Architecture (Nathan Marz) splits incoming events from Kafka into two parallel paths:

  1. Batch Layer: Appends immutable raw history to an object store (S3/Iceberg) and runs periodic Spark jobs to compute exact historical views.
  2. Speed Layer: Processes only recent hours in Flink/Streaming into Redis/Pinot for sub-second freshness.
  3. Serving Layer: Merges Batch + Speed at query time—or lets Batch atomically overwrite Speed segments.
Dual-Path Pipeline

Immutable Master Log -> Batch Layer (Spark) + Speed Layer (Flink) -> Serving

1.Immutable Master: Raw events land in S3/Iceberg so hourly Spark jobs can recompute exact truth anytime.

2.Bounded Speed State: Speed Layer only retains 24–48h of state via StateTtlConfig, keeping RocksDB small.

3.Segment Overwrite: Pinot/Druid atomically replaces Speed segments with Batch segments at the hourly cutoff.

Lambda pairs a fast streaming tail with a deterministic batch backfill, at the cost of maintaining two processing paths.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Semantic Drift & Boundary Gaps Threaten Lambda.

Lambda's #1 failure mode is semantic logic drift: a developer updates timezone or bot-filtering rules in the Spark batch job but forgets the Flink speed job, causing live metrics to jump 12% every hour when Batch overwrites Speed. Clock skew near the hourly cutoff can also double-count or drop boundary events.

Unified Logic via Shared SQL/UDFs

Share transformation logic via Apache Beam, Spark Structured Streaming, or a shared SQL/UDF library and run automated hourly parity checks.

Deterministic Event-Time Cutoff

Partition by _ingest_cutoff_ts watermarks and use atomic segment replacement in Pinot/Druid instead of complex query-time unions.

04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Deterministic Boundary Cutoff & Serving-Layer Merge.

Always use a deterministic watermark cutoff (_cutoff_ts) so Batch covers event_ts < _cutoff_ts and Speed covers event_ts >= _cutoff_ts—with StateTtlConfig on Speed slightly longer than the maximum Batch recovery SLA (e.g., 24–48h).

-- Serving-layer deterministic union across Batch (exact) and Speed (live tail)
-- Cutoff watermark advances atomically only after hourly Spark + Iceberg commit succeeds
SELECT campaign_id, SUM(clicks) AS total_clicks
FROM (
  SELECT campaign_id, clicks FROM batch_campaign_hourly
  WHERE window_end <= (SELECT last_committed_cutoff_ts FROM pipeline_watermarks)
  UNION ALL
  SELECT campaign_id, clicks FROM speed_campaign_realtime
  WHERE window_end >  (SELECT last_committed_cutoff_ts FROM pipeline_watermarks)
) combined
GROUP BY campaign_id;

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Safeguard: Shared Watermark Table & Automated Parity Audit.

To catch semantic drift before finance or customers notice, production Lambda pipelines run an hourly parity reconciliation job comparing Speed vs. Batch totals for the completed hour and alerting if divergence exceeds 0.5%.
