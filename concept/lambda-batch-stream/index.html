THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Use Lambda when you need sub-second approximate/recent views alongside deterministic, re-computable batch history—or choose Kappa (single stream replay) if your team cannot maintain two codebases.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Real-time analytics platforms (ad-tech billing, fraud dashboards, IoT telemetry) face a classic tension: streaming engines deliver <1s latency but struggle with late-arriving data, schema backfills, and complex global joins, while batch engines (Spark/Iceberg) guarantee exactness over petabytes at the cost of hours of latency. Lambda Architecture bridges both worlds—and understanding its dual-pipeline overhead explains why modern Lakehouse and Kappa designs evolved.

  • Three-layer split: Immutable Master Dataset + Batch Layer (Spark/Iceberg) → Speed Layer (Flink/Kafka) → Serving Layer (ClickHouse/Druid/Cassandra) merging batch + real-time views at query time.
  • Immutability & recomputation: raw events are append-only in object storage (S3/GCS Parquet/Iceberg); any bug in transformation logic is fixed by re-running the Batch Layer over history.
  • Event-time watermarks vs. batch cutoffs: the Speed Layer tracks sliding windows via watermarks (e.g., 5-minute allowed lateness), while the Batch Layer sweeps everything older than T-1 hour.
  • Serving-layer merge: queries union precomputed batch views (ts < cutoff) with speed views (ts >= cutoff), or overwrite speed keys atomically when batch views finish.
  • Kappa alternative: retaining raw events in Kafka (or tiered storage) for 30+ days allows a single Flink job to handle both live traffic and historical replay, eliminating dual-codebase drift.

Good candidates

  • Systems requiring both sub-second operational visibility (Speed Layer) and auditable, bit-exact financial or regulatory reconciliation (Batch Layer).
  • Workloads with frequent late-arriving or out-of-order events (e.g., mobile SDKs offline for 48 hours) where batch reprocessing cleanly corrects prior stream approximations.
  • Legacy organizations that already have mature Spark/Snowflake batch pipelines and need to bolt on real-time Flink/Kafka views without rewriting historical ETL.

Think twice

  • Small or mid-sized teams that cannot afford to write, test, and keep two separate codebases (e.g., Flink Java + Spark SQL) semantically identical—prefer Kappa Architecture instead.
  • Purely real-time operational alerting or stateful workflows where historical 5-year reprocessing is never needed.
  • Low-urgency BI reporting where 15–60 minute micro-batching (Spark Structured Streaming or Iceberg incremental loads) is fast enough.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn ad network processes 400k clicks/sec; advertisers need live campaign pacing dashboards (<3s delay), while finance requires 100% deduplicated daily invoices.

The idea

Proposed by Nathan Marz, Lambda Architecture solves the apparent conflict between low-latency streaming and fault-tolerant historical accuracy by splitting every incoming event into two parallel paths. The Batch Layer persists an immutable, append-only Master Dataset (e.g., S3 + Apache Iceberg) and periodically recomputes exact batch views from scratch or incremental partitions. Simultaneously, the Speed Layer (e.g., Apache Flink) processes only recent events in sub-second time. A Serving Layer (e.g., ClickHouse, Apache Druid, or Pinot) indexes both views so queries see immediate updates that are later replaced by authoritative batch truth.

Concrete walkthrough

Trace an e-commerce order event (order_id: 7741, event_ts: 14:02:10Z, amount: $120) through a Lambda pipeline:

  1. Ingest: The checkout service publishes the event to Kafka topic orders.raw (7-day retention).
  2. Speed Path: Apache Flink consumes orders.raw, updates a 1-hour tumbling revenue counter in RocksDB, and sinks to Redis/Pinot within 400 ms so the live ops dashboard reflects $120 immediately.
  3. Master Dataset: Kafka Connect / Flink sinks raw events into S3 s3://lake/orders_raw/ partitioned by dt=2026-11-12/hr=14.
  4. Batch Path: At 15:10Z, an hourly Spark job runs over hr=14, deduplicates retries, joins currency FX tables, and writes the authoritative view to Druid/ClickHouse, atomically replacing the hr=14 speed-layer segment.

Lambda fan-out: Kafka feeds both an immutable Batch Layer for exactness and a Flink Speed Layer for sub-second freshness.

Lambda vs. Kappa vs. Lakehouse

Modern data engineering has largely converged on two evolutions of Lambda:

  • Kappa Architecture: Drops the Batch Layer entirely. Kafka (with tiered storage to S3) holds long-term history; when logic changes, you spin up a new Flink consumer group at offset 0 and swap the Serving Layer pointer once caught up.
  • Unified Lakehouse Streaming: Engines like Apache Iceberg + Flink/Spark Structured Streaming write directly to one ACID table format, using incremental micro-batches (30–60s) when sub-second latency isn't strictly required.

Failure modes

  1. Dual-Codebase Divergence: Subtle differences in null handling, late-event windows, or floating-point rounding between Flink and Spark cause visible metric jumps at every batch handoff.
  2. Handoff Double-Counting: Overlapping time windows between the Speed Layer and Batch Layer inflate totals unless the Serving Layer uses deterministic partition replacement or idempotent keys.
  3. Checkpoint / Compaction Bottlenecks: Unbounded state in Flink or uncompacted tiny Parquet files in S3 degrade both layers simultaneously.

Boundary Synchronization & Parity Testing

To prevent boundary gaps, partition both layers by event time (event_ts truncated to hour) rather than ingestion time, and have the Serving Layer route queries cleanly via a watermark table (last_verified_batch_hour). Run an automated daily parity diff comparing the Speed Layer's pre-overwrite hour against the Batch Layer's output; alert if divergence exceeds 0.5%.

Practical checklist

  • Confirm you genuinely need <5s latency AND petabyte batch recomputation before choosing Lambda over Kappa or micro-batch.
  • Persist raw events immutably in Parquet/Iceberg with scheduled small-file compaction.
  • Align both Batch and Speed layers on event-time boundaries, not wall-clock processing time.
  • Set Speed Layer state TTLs > 2x your worst-case Batch Layer recovery window.
  • Automate hourly parity checks between Speed and Batch outputs to catch logic drift early.
03 / Engineering trade-offs

Weighing architectural decisions

Lambda (Dual Batch + Speed) vs. Kappa (Stream-Only Replay)

Advantage: Lambda leverages specialized batch engines (Spark/Trino) for massive petabyte joins and deterministic backfills without choking stream state.

Drawback: Maintaining two distinct implementations of business logic (e.g., Flink + Spark) inevitably causes subtle metric drift between live and historical numbers.

Query-Time Merge vs. Batch Overwrite in Serving Layer

Advantage: Query-time union (`WHERE ts < cutoff` from batch + `ts >= cutoff` from speed) keeps batch writes non-blocking.

Drawback: Every dashboard query pays a 2x read fan-out and complex boundary deduplication; atomic segment replacement (Druid/Iceberg) simplifies reads.

Short Speed Retention vs. Long Kafka Replay Retention

Advantage: Keeping only 2–6 hours in the Speed Layer bounds Flink RocksDB state size and memory cost.

Drawback: If the Batch Layer lags or fails for 8 hours, a 6-hour Speed Layer expires data before batch catches up, creating a blind spot.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Semantic Logic Drift Between Batch and Speed

A developer updates timezone handling or bot-filtering rules in the Spark batch job but forgets the Flink speed job, causing live metrics to jump or drop by 12% every hour when batch overwrites speed.

What helps: Share transformation logic via a single SQL/UDF library (e.g., Apache Beam, Spark Structured Streaming unified API, or dbt + Flink SQL) and run automated parity checks.

Batch-Speed Boundary Gap or Double Counting

Clock skew or delayed Kafka-to-S3 compaction causes events near the hourly cutoff to be either missed by both layers or counted twice.

What helps: Use deterministic event-time partition watermarks (`_ingest_cutoff_ts`) and idempotent upsert/segment replacement in the Serving Layer.

Speed Layer Unbounded State Explosion

A Flink `keyBy(userId)` aggregation without state TTL accumulates billions of keys over weeks, exhausting RocksDB disk and checkpointing timeouts.

What helps: Enforce `StateTtlConfig` slightly longer than the maximum batch-recovery SLA (e.g., 24–48h) since older history lives in the Batch Layer.

Small-File Explosion in Master Dataset

Writing raw Kafka micro-batches to S3 every 60 seconds creates millions of 50 KB Parquet files, slowing Spark batch scans by 20x.

What helps: Use Apache Iceberg or Delta Lake with scheduled compaction (`rewrite_data_files`) to merge small files into 128–512 MB blocks.

05 / Practical checklist

Avoid these mistakes

  • Implementing Lambda by default when a 1-minute micro-batch (Spark Structured Streaming) or a single Flink Kappa pipeline would satisfy the SLA.
  • Forgetting to retain raw immutable events in object storage, making it impossible to replay/fix historical bugs.
  • Using processing time (`System.currentTimeMillis()`) instead of event time in the Speed Layer, corrupting hourly boundaries during Kafka consumer lag.
  • Setting Speed Layer retention shorter than the Batch Layer's worst-case failure recovery time.
  • Storing mutable state directly in the Master Dataset instead of appending immutable event records.
