Explanation anchor
01 / The idea

Foundational mechanics & core principles

Replicating data across servers is easy when nothing fails, but real networks drop packets, pause processes via GC, and split into partitions. Without a consensus protocol like Raft or Paxos, two nodes can simultaneously believe they are primary (split-brain), accepting conflicting writes and silently corrupting or losing committed transactions.

  • Majority quorum (floor(N/2) + 1) guarantees any two quorums overlap by at least one node, preserving committed writes across leader elections: 3 nodes tolerate 1 failure, 5 nodes tolerate 2.
  • Raft decomposes consensus into Leader Election (monotonic term + RequestVote), Log Replication (AppendEntries with prevLogIndex/prevLogTerm), and Safety (only nodes with up-to-date logs can win election).
  • A write is only committed once replicated to a majority of nodes; the leader then advances commitIndex and applies it to the state machine.
  • Linearizable reads require either a quorum heartbeat round-trip (ReadIndex) or clock-bounded leader leases—reading blindly from a leader or follower risks stale reads during a partition.
  • Multi-Raft partitions keyspaces into thousands of small 64MB ranges so every node leads some ranges and follows others, scaling write throughput horizontally.

Good candidates

  • Control-plane metadata, distributed locks, and service discovery (etcd in Kubernetes, ZooKeeper, Consul) requiring strict linearizability.
  • Distributed transactional databases (CockroachDB, TiKV, YugabyteDB, Spanner) where Raft/Paxos groups replicate 64MB shards across availability zones.
  • Financial ledgers, inventory reservations, and sequence generators where stale reads or lost committed writes are unacceptable.

Think twice

  • High-throughput caching, session stores, or social feeds where eventual consistency or asynchronous primary-replica replication suffices.
  • Cross-continental active-active writes where 150ms+ WAN round-trips for every synchronous quorum commit violate latency SLAs (unless using CRDTs or local-region homing).
  • Deploying a 2-node cluster expecting high availability—a 2-node quorum requires 2/2 nodes, actually halving availability on single-node failure.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA production Kubernetes cluster spans 3 Availability Zones and must survive both a planned node upgrade and an unexpected AZ failure simultaneously.

The idea

Consensus protocols like Paxos and Raft solve a fundamental distributed systems problem: how can a cluster of unreliable machines agree on an ordered sequence of state transitions—and never lose a committed write—even when nodes crash or the network splits? The core mechanism is combining monotonic term/ballot numbers (fencing out stale leaders) with intersecting majority quorums (floor(N/2) + 1), guaranteeing that any newly elected leader's quorum overlaps with the quorum that committed prior writes.

Concrete walkthrough

Trace a write SET balance = 450 on a 3-node Raft cluster (Node A = Leader, Nodes B & C = Followers, term = 4):

  1. Append locally: Client sends SET balance = 450 to Leader A. A appends (term=4, index=108) to its durable WAL (fsync).
  2. Parallel AppendEntries: Leader A sends AppendEntries(term=4, prevLogIndex=107, prevLogTerm=4, entries=[108]) to B and C in parallel.
  3. Quorum Commit: Node B verifies prevLogIndex=107 matches its log, fsyncs entry 108, and replies success=true. Even if Node C is slow or crashed, A + B form a majority (2 of 3). Leader A advances commitIndex = 108, applies balance = 450 to its state machine, and returns OK to the client.
  4. Crash & Election: Suppose Leader A now crashes permanently. Node B's electionTimeout (e.g., 1,000ms) fires. B increments to term = 5 and sends RequestVote(lastLogIndex=108, lastLogTerm=4) to C. Because B's log is at least as up-to-date as C's, C grants its vote, B becomes Leader for term = 5, and index=108 is guaranteed to survive.

Paxos vs. Raft and linearizable read optimizations

While Single-Decree Paxos agrees on one value via Prepare(n)/Promise and Accept(n, v)/Accepted, real systems run Multi-Paxos (electing a stable leader to skip Phase 1 on steady-state writes). Raft is equivalent in safety and latency (1 RTT per committed write) but enforces contiguous log ordering and stricter election rules (a candidate must hold all committed entries to win, whereas Paxos allows out-of-order log holes that are reconciled later).

For linearizable reads, simply reading from the leader's memory is unsafe if the leader was partitioned and a new leader was elected. Systems solve this in two ways:

  • ReadIndex (etcd / TiKV): The leader records its current commitIndex, sends a lightweight heartbeat round to a majority to confirm it is still leader, waits until appliedIndex >= ReadIndex, and serves the read.
  • Leader Leases (CockroachDB / Spanner): Followers promise not to vote for any other candidate for lease_duration (e.g., 9s) using bounded clock-skew assumptions, allowing the leader to serve linearizable reads locally in 0 RTT.

Failure modes

  • Split-brain via un-fenced stale leader: Serving reads without ReadIndex or valid leases lets an isolated ex-leader return stale balances.
  • Disk I/O starvation: Sharing Raft WAL disks with application logs or container pulls spikes fsync latency past electionTimeout, causing cascading leader elections.
  • Snapshot transfer storms: When a follower falls too far behind and its log is compacted, the leader streams a multi-gigabyte snapshot, saturating NIC bandwidth and triggering heartbeat timeouts.
  • Cross-region WAN latency: Placing a 3-node quorum across US-East, EU-West, and AP-South forces every write to wait on a 150ms+ intercontinental RTT.

Multi-Raft sharding and membership changes

A single Raft group serializes all writes through one leader's log. To scale horizontally, databases like CockroachDB and TiKV split data into 64MB–96MB key-range shards (Multi-Raft), running thousands of independent Raft state machines per node while coalescing heartbeats between node pairs.

When adding or removing nodes, never change cluster membership from 3 to 5 directly in one jump—two disjoint majorities could briefly form. Raft uses Single-Server Membership Changes (adding/removing 1 node at a time) or Joint Consensus (C_old,new) to guarantee majority overlap throughout the transition.

Practical checklist

  • Always size consensus clusters to odd counts (3 for dev/standard HA, 5 for surviving simultaneous maintenance + node failure).
  • Place nodes across 3 distinct failure domains (AZs or racks) within a single low-latency region (<5ms RTT) for OLTP quorums.
  • Isolate Raft WAL storage on dedicated NVMe SSDs and monitor wal_fsync_duration_seconds p99 (<10ms).
  • Enable Pre-Vote and CheckQuorum to prevent partitioned followers from disrupting healthy leaders.
  • Use ReadIndex or clock-bounded leases for any read requiring linearizability; explicitly label follower reads as stale.
  • Perform membership changes one node at a time and test single-node + AZ-loss failover regularly.
03 / Engineering trade-offs

Weighing architectural decisions

3-Node vs. 5-Node Cluster

Advantage: 3 nodes minimize write replication fan-out and hardware cost while tolerating 1 failure.

Drawback: Zero margin during maintenance: if 1 node is down for patching, any second failure halts the entire cluster.

Linearizable Consensus vs. Async Replication

Advantage: Zero data loss (RPO=0) on acknowledged writes and no split-brain divergence.

Drawback: Every write pays at least one network RTT to the closest quorum of followers (1–2ms intra-region, 80ms+ cross-region).

Leader-Based (Raft) vs. Leaderless (Dynamo `R+W>N`)

Advantage: Single leader orders writes cleanly without vector clocks, sibling conflicts, or read-repair complexity.

Drawback: Write throughput for a single Raft group is bounded by one leader's CPU/network until sharded via Multi-Raft.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Stale Leader Read (Split-Brain Illusion)

A partitioned old leader does not yet know a new leader was elected in a higher term and serves stale data to clients hitting it directly.

What helps: Enforce `ReadIndex` (quorum heartbeat check before serving reads) or tightly bounded monotonic clock leases.

Asymmetric Partition Election Storm

A partially isolated follower cannot hear the leader's heartbeats, repeatedly increments its `term`, and disrupts the healthy cluster when packets occasionally leak through.

What helps: Enable Raft `Pre-Vote` extension so a node checks whether a majority would vote for it *before* incrementing its term.

Even-Numbered Quorum Trap

Deploying 2 or 4 nodes: a 2-node cluster has quorum=2 (0 fault tolerance), and a 4-node cluster has quorum=3 (same `f=1` tolerance as 3 nodes, at higher cost).

What helps: Always deploy odd node counts (3, 5, or 7) or add a lightweight non-data witness/arbiter node.

Slow Disk `fsync` Stalling Quorum

Consensus requires durable WAL `fsync` before acknowledging `AppendEntries`. Sharing etcd/Raft disks with noisy I/O neighbors spikes tail `fsync` latency, triggering false leader elections.

What helps: Dedicate local NVMe SSDs for the Raft WAL, monitor `wal_fsync_duration_seconds`, and tune `electionTimeout` (e.g., 10× heartbeat).

05 / Practical checklist

Avoid these mistakes

  • Deploying a 2-node Raft/etcd cluster for HA, which actually lowers availability compared to a single node.
  • Reading from a Raft follower (`stale=true`) for authorization or inventory checks and assuming it is linearizable.
  • Stretching a single 3-node Raft cluster across 3 continents (US, EU, APAC) and wondering why every write takes 150ms+.
  • Setting `electionTimeout` too close to `heartbeatInterval` (e.g., 150ms vs 100ms) across noisy cloud networks, causing constant leadership flaps.
  • Putting large binary blobs (>1MB) into etcd/ZooKeeper, bloating Raft snapshots and stalling follower catch-up.
