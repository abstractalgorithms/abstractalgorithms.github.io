A foundational engineering concept

OAuth2 Authorization
Flows.

OAuth 2.0 delegates scoped API access without sharing user passwords, using distinct grant flows tailored to confidential backends, public SPAs/mobile apps, headless devices, and service-to-service workloads. Modern OAuth 2.1 deprecates the Implicit and Resource Owner Password Credentials (ROPC) flows in favor of Authorization Code + PKCE.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Always use Authorization Code + PKCE (`code_challenge_method=S256`) for any user-facing login and Client Credentials for machine-to-machine calls; never use Implicit or ROPC.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Exposing user passwords to third-party apps or storing long-lived credentials in browser JavaScript creates catastrophic blast radii. OAuth 2.0 separates authentication (often via OpenID Connect) from scoped, revocable, short-lived access tokens so compromised clients cannot take over an entire account.

  • PKCE (RFC 7636) binds the authorization request to the token exchange using a per-session code_verifier and SHA-256 code_challenge, preventing authorization code interception on public and confidential clients alike.
  • Always validate the state parameter (cryptographically random, bound to the user's browser session) on the /callback endpoint to block Cross-Site Request Forgery (CSRF) login attacks.
  • Use short-lived access tokens (5–15 minutes) paired with Refresh Token Rotation (refresh_token invalidated on single use) and reuse detection to limit stolen token windows.
  • For SPAs, the Backend-for-Frontend (BFF) pattern keeps client_secret and refresh tokens in an HttpOnly, SameSite cookie on a confidential server rather than browser localStorage.
  • Confidential server-to-server workloads use grant_type=client_credentials with mTLS or private_key_jwt (RFC 7523) instead of static shared secrets.

Good candidates

  • Granting third-party or first-party web/mobile apps scoped, revocable access to user resources via Authorization Code + PKCE.
  • Authenticating backend microservices or batch jobs to internal APIs via Client Credentials without a human user in the loop.
  • Authorizing input-constrained devices (smart TVs, CLI tools) via the Device Authorization Grant (RFC 8628).

Think twice

  • Using Implicit flow (response_type=token) for SPAs; it leaks access tokens in browser URL fragments, history, and Referer headers.
  • Using Resource Owner Password Credentials (ROPC) to collect raw user passwords in your own login form, bypassing MFA, SSO, and federated IdPs.
  • Treating an opaque OAuth 2.0 access token as user identity proof; use an OpenID Connect (OIDC) id_token or /userinfo endpoint for authentication.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA SaaS dashboard used response_type=token (Implicit flow) and stored 24-hour JWTs in localStorage, exposing tokens to any third-party analytics XSS vulnerability.

The idea

OAuth 2.0 (RFC 6749) is a delegation framework, not an authentication protocol. It defines four roles: the Resource Owner (user), the Client (app requesting access), the Authorization Server (IdP issuing tokens), and the Resource Server (API hosting protected data).

Instead of handing the Client a user's password, the Authorization Server authenticates the user on its own trusted domain, obtains consent for specific scope strings (e.g., orders:read), and issues a short-lived access_token to the Client. The Client presents that token as a Bearer credential (Authorization: Bearer ) to the Resource Server.

Concrete walkthrough

Here is the exact Authorization Code + PKCE flow for a web or mobile client:

  1. Generate PKCE & State: The Client generates a 64-byte random code_verifier, computes code_challenge = BASE64URL(SHA256(code_verifier)), and creates a random state token bound to the user's session.
  2. Authorization Redirect: The Client redirects the user's browser to GET /authorize?response_type=code&client_id=web-app&redirect_uri=https://app.example.com/cb&scope=openid+profile+orders:read&state=xyz&code_challenge=...&code_challenge_method=S256.
  3. User Auth & Consent: The Authorization Server authenticates the user (password + WebAuthn/MFA) and redirects back to redirect_uri?code=auth_9f8a&state=xyz.
  4. State Verification & Token Exchange: The Client verifies state == xyz, then makes a back-channel POST /oauth/token sending grant_type=authorization_code, code=auth_9f8a, redirect_uri, client_id, and the raw code_verifier.
  5. PKCE Validation & Token Issue: The Authorization Server hashes code_verifier, confirms it matches the stored code_challenge, invalidates auth_9f8a (single-use), and returns {access_token (10m), refresh_token (7d), id_token}.

PKCE binds the front-channel redirect to the back-channel token exchange so an intercepted authorization code is useless without the client's code_verifier.

Choosing the right grant type and OIDC layering

OAuth 2.1 consolidates the specification around four surviving patterns:

  • Authorization Code + PKCE: Mandatory for all interactive user flows (confidential web backends, SPAs, native mobile).
  • Client Credentials (grant_type=client_credentials): For service-to-service calls with no user context. Prefer private_key_jwt (signed JWT assertion) or mTLS over static client_secret strings.
  • Device Authorization Grant (RFC 8628): For CLI tools, smart TVs, and IoT devices lacking a browser.
  • Refresh Token Grant: Silent renewal of short-lived access tokens; pair with DPoP (Demonstrating Proof-of-Possession, RFC 9449) when sender-constraining tokens is required.

OpenID Connect (OIDC) sits cleanly on top of OAuth 2.0 by adding the openid scope, returning a signed JWT id_token containing sub, iss, aud, exp, and nonce so the Client knows who logged in.

Failure modes

1. Missing aud Validation in Multi-Tenant APIs: If Service A and Service B share the same IdP, a token minted for aud: service-a with scope: read can be replayed against Service B unless Service B explicitly rejects tokens whose aud claim does not include service-b.

2. Refresh Token Race Conditions: In SPAs making 5 parallel API calls when a 10-minute access token expires, all 5 requests may try to use the same single-use refresh_token. Request #1 succeeds and rotates the token; Requests #2–#5 trigger reuse detection and revoke the user's entire session.

3. alg: none or Key Confusion Attacks: Weak JWT libraries that trust the unverified token header's alg field can be tricked into accepting unsigned tokens or verifying RS256 public keys as HS256 HMAC secrets.

Production hardening & token lifecycle

Hardening an OAuth 2.0 deployment requires defense-in-depth across client and server:

  • Pin Algorithms & Keys: Resource servers should hardcode allowed signing algorithms (e.g., RS256 or ES256), cache IdP JWKS keys with kid lookup, and reject alg=none.
  • Single-Flight Refresh: Wrap client-side token refresh in a mutex/promise queue so concurrent 401 responses share one /oauth/token call.
  • Sender-Constrained Tokens: For high-security financial APIs (FAPI 2.0), bind tokens to the client's TLS certificate (mTLS cnf.x5t#S256) or ephemeral keypair (DPoP) so stolen Bearer tokens cannot be replayed from another host.

Practical checklist

  • Require code_challenge_method=S256 (PKCE) on all Authorization Code grants; disable Implicit and ROPC.
  • Register exact redirect_uri values with no wildcards or open redirects.
  • Generate and verify a cryptographic state parameter (and nonce for OIDC id_token) per login.
  • Keep access token TTLs to 5–15 minutes and enable refresh token rotation with reuse detection.
  • Validate iss, aud, exp, alg, and scope on every Resource Server endpoint.
  • Use a Backend-for-Frontend (BFF) with HttpOnly; Secure; SameSite=Lax cookies for browser SPAs.
03 / Engineering trade-offs

Weighing architectural decisions

SPA Direct PKCE vs. Backend-for-Frontend (BFF)

Advantage: Direct SPA PKCE requires zero session-management backend and works with static CDN hosting.

Drawback: Tokens reside in browser memory or storage (vulnerable to XSS), whereas a BFF keeps tokens server-side behind `HttpOnly` cookies.

JWT Access Tokens vs. Opaque Reference Tokens

Advantage: Self-contained JWTs allow resource servers to verify signatures (`JWKS`) locally in <1ms without calling the authorization server.

Drawback: JWTs cannot be immediately revoked before expiration without maintaining a distributed revocation list or short 5-minute TTLs.

Refresh Token Rotation vs. Static Refresh Tokens

Advantage: Rotating refresh tokens on every `/token` call detects replay if either the legitimate client or an attacker reuses an old token, revoking the entire token family.

Drawback: Concurrent browser tabs racing to refresh the same token can trigger false-positive reuse revocations without a brief 5–10s grace window or single-flight lock.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Authorization Code Interception

On mobile or desktop apps with custom URI schemes (`myapp://callback`), a malicious app registers the same scheme and steals the `code` from the redirect.

What helps: Mandate PKCE (`code_challenge_method=S256`) on the authorization server; the attacker cannot exchange the stolen `code` without the original `code_verifier`.

Open Redirect & Token Leakage

Wildcard `redirect_uri` matching (e.g., `https://app.example.com/*`) lets an attacker redirect the authorization code to an attacker-controlled open redirect path.

What helps: Enforce exact byte-for-byte `redirect_uri` matching in the authorization server configuration; never allow wildcard paths or query-string prefixes.

CSRF on Callback Endpoint

An attacker initiates an OAuth flow with their own account and tricks a victim into visiting the attacker's `/callback?code=...` URL, binding the victim's session to the attacker's account.

What helps: Generate a 128-bit random `state` value stored in an `HttpOnly` cookie before redirecting, and reject any callback where `state` is missing or mismatched.

Confused Deputy / Token Replay Across Audiences

A resource server accepts a valid JWT issued for a different API because it only checks signature and `exp`, ignoring the `aud` (audience) and `scope` claims.

What helps: Validate `iss`, `aud` (must match the exact resource server identifier), `exp`, and required `scope` on every API request.

05 / Practical checklist

Avoid these mistakes

  • Using `client_secret` inside a mobile app or SPA bundle—public clients cannot keep secrets, so any secret shipped in client code is compromised immediately.
  • Confusing OAuth 2.0 (authorization) with OpenID Connect (authentication) and skipping `id_token` `nonce` and `aud` validation.
  • Setting refresh token lifetimes to infinite without idle timeouts or rotation, leaving stolen sessions active for years.
  • Passing `access_token` in URL query parameters (`?access_token=...`), which leaks credentials into proxy logs, browser history, and Referer headers.
  • Skipping `PKCE` on confidential web servers—OAuth 2.1 requires PKCE for all Authorization Code flows to close code-injection vectors.
