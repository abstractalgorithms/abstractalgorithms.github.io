Database Sharding &
Range Partitioning.

Horizontally partitioning a dataset across independent database nodes by a shard key—using either contiguous key ranges or consistent hashing—to scale write throughput and storage beyond a single primary's CPU, IOPS, and memory ceiling.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Range partitioning preserves ordered range scans at the cost of hot-spot risk on monotonic keys; hash partitioning spreads writes evenly at the cost of scatter-gather range queries.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Vertical scaling hits physical and economic walls around 64–128 vCPUs and NVMe IOPS saturation, while single-primary replication only scales reads, not writes. When a PostgreSQL primary crosses ~15,000–25,000 write TPS or its B-tree indexes exceed RAM, vacuum lag, WAL replication delay, and lock contention degrade p99 latency across every tenant. Sharding splits the write path and working set across autonomous primaries so each node holds a bounded slice of data and indexes.

  • Range partitioning (used by CockroachDB, TiKV, and HBase) maps contiguous key intervals like [A–F] or [2026-01–2026-03] to shards, enabling fast ordered scans (WHERE created_at BETWEEN ...) via a metadata routing table.
  • Hash partitioning (used by DynamoDB, Cassandra, and Vitess xxhash) applies a deterministic hash to the shard key and maps to virtual buckets, eliminating monotonic write hotspots at the expense of scatter-gather range queries.
  • Choosing the shard key is practically irreversible without a dual-write backfill; a poor key causes either cross-shard fan-out on every read or severe skew where one shard handles 80% of traffic.
  • Vitess and Citus separate logical shards (keyspace IDs / 1,024–4,096 virtual buckets) from physical database hosts so resharding moves small chunks incrementally rather than rehashing all rows.
  • Cross-shard transactions require two-phase commit (2PC) or asynchronous Sagas with an outbox table, trading single-node sub-millisecond commits for 2–4x network round-trips or eventual consistency.

Good candidates

  • Write throughput or index working-set size exceeds what the largest single-node primary can sustain without p99 latency spikes or vacuum/compaction stalls.
  • Data exhibits a natural isolation boundary—such as tenant_id, account_id, or region—so 95%+ of queries can route to a single shard.
  • Regulatory data residency (e.g., GDPR EU vs. US data) requires physically pinning subsets of rows to geographically separate storage clusters.

Think twice

  • Read traffic is the sole bottleneck and read replicas, connection pooling (PgBouncer), or Redis caching can absorb the load without splitting the write primary.
  • Core business workflows rely heavily on multi-row ACID joins, foreign-key constraints, or global secondary index aggregations across arbitrary entities.
  • Dataset size is under ~2–5 TB and write QPS fits comfortably on a single modern primary, where sharding adds operational complexity without measurable gain.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA B2B billing platform reaches 4 TB in a single MySQL 8.0 primary, with invoices and ledger_entries suffering 400ms p99 write stalls during end-of-month batch runs.

The idea

Database sharding divides a logical table into horizontally disjoint subsets (shards), each hosted on an independent database primary with its own CPU, buffer pool, WAL, and storage volume. Unlike read replicas—which copy 100% of the data and only offload SELECT queries—sharding splits both reads and writes so cluster capacity scales linearly with node count.

Two dominant partitioning functions govern how rows map to shards. Range partitioning divides the keyspace into contiguous, non-overlapping intervals ([0000–3FFF], [4000–7FFF]) tracked in a sorted range map. Hash partitioning applies a uniform hash (such as xxhash64 or Murmur3) to the shard key and maps the digest onto a consistent hash ring or a fixed pool of virtual buckets (e.g., 1,024 vbuckets) assigned to physical primaries.

Concrete walkthrough

Consider an orders service handling 40,000 writes/sec across 16 physical PostgreSQL primaries managed via a routing proxy and an etcd metadata store.

  1. Key selection & colocation: orders, order_items, and payments all carry merchant_id as their shard key so an entire checkout's rows live on the same physical shard and commit in a single local ACID transaction.
  2. Routing lookup: An incoming INSERT INTO orders (merchant_id, order_id, ...) hits the stateless router (vtgate / Citus coordinator). The router computes keyspace_id = xxhash64(merchant_id) and checks its in-memory routing map (cached from etcd with a generation epoch).
  3. Single-shard execution: The router forwards the query over a persistent PgBouncer pool directly to Shard 11's primary. Latency overhead is ~0.8ms.
  4. Online range split: When Shard 11 grows past 500 GB, the control plane splits its keyspace [A000–AFFF] into [A000–A7FF] and [A800–AFFF], streams a consistent snapshot plus WAL/binlog delta to Shard 17, pauses writes on [A800–AFFF] for <500ms, updates the etcd epoch, and resumes traffic on Shard 17.

Request routing through a stateless shard router backed by an epoch-versioned metadata store.

Range vs. Hash vs. Directory partitioning

Range partitioning stores a sorted boundary map (e.g., CockroachDB splits ranges at 64 MB by default), which makes prefix and range scans fast because adjacent keys sit together in the same RocksDB/B-tree SSTables. However, sequential keys write to a single tail range unless prefixed by a tenant or hash bucket.

Hash partitioning sacrifices range locality for uniform write distribution. Consistent hashing or virtual buckets (e.g., 256–4,096 vbuckets) ensures that adding a physical node only moves 1/N of the buckets rather than reshuffling the entire table.

Directory-based (lookup) sharding stores an explicit entity_id -> shard_id table in Redis or a small replicated DB. It handles arbitrary per-tenant placement and easy VIP isolation, but every query pays a lookup hop and the directory itself becomes a critical availability dependency.

Failure modes

The most frequent production outage in sharded clusters is stale routing after a split or failover. If a client caches an old shard map and writes to the demoted primary before its lease expires, split-brain writes occur. Enforcing fencing tokens (epoch numbers checked on every write at the storage node) eliminates this.

Second is cross-shard transaction deadlock and 2PC coordinator failure. If a distributed 2PC coordinator crashes after phase 1 PREPARE, participating shards hold row locks indefinitely until a coordinator recovers or an operator manually resolves prepared transactions. Prefer colocation by shard key or asynchronous Sagas over 2PC on high-throughput OLTP paths.

Operationalizing resharding & global indexes

Live resharding must be zero-downtime: snapshot a consistent LSN/GTID position on the source shard, stream ongoing WAL/binlog changes to the target shard until lag drops under 100ms, briefly fence writes (READ ONLY for <1s), flip the metadata epoch, and drop the migrated keyspace from the source.

For queries that cannot include the shard key (e.g., looking up a user by email when the table is sharded by user_id), maintain an asynchronous global secondary index via Debezium CDC into a separate lookup table sharded by email—accepting ~50–200ms eventual consistency in exchange for single-shard read latency.

Practical checklist

  • Verify >90% of OLTP reads and writes include the chosen shard key so scatter-gather stays rare.
  • Over-provision logical virtual shards (e.g., 256 or 1,024) from day one even on 4 physical hosts.
  • Replace database SERIAL/AUTO_INCREMENT with UUIDv7 or Snowflake IDs to avoid centralized ID bottlenecks.
  • Enforce epoch/fencing-token validation on storage nodes to reject stale-route writes during failovers.
  • Rehearse a live shard split in staging under synthetic write load and measure cutover pause duration.
03 / Engineering trade-offs

Weighing architectural decisions

Partitioning strategy (Range vs. Hash)

Advantage: Range partitioning executes ordered scans (`BETWEEN`, `ORDER BY`, prefix lookups) on 1–2 shards without scatter-gather.

Drawback: Monotonic keys (auto-increment IDs, `now()`) concentrate 100% of inserts onto the tail shard unless prefixed with a high-cardinality tenant or hash byte.

Routing layer (Smart Client vs. Proxy Router)

Advantage: Proxy routers (Vitess `vtgate`, Citus coordinator) centralize topology metadata and shield application code from shard splits.

Drawback: Adds an extra network hop (0.5–2ms) and requires scaling the proxy tier as stateless infrastructure.

Resharding granularity (Fixed Modulo vs. Virtual Shards)

Advantage: Virtual shards / range splits (64 MB chunks in CockroachDB, keyspace intervals in Vitess) move only the affected slice during scale-out.

Drawback: Requires a distributed metadata service (etcd, ZooKeeper, or Raft) to keep routing maps consistent across clients.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Tail-shard write hotspot

Range-partitioned tables keyed by `created_at` or sequential IDs route every new insert to the highest range, saturating one node's CPU and disk while N-1 shards sit idle.

What helps: Prefix the shard key with a high-cardinality attribute (`tenant_id`, `org_id`) or a 2-byte hash prefix, or switch to hash partitioning for write-heavy append logs.

Scatter-gather tail latency amplification

Queries missing the shard key fan out to all 32 or 64 shards; if any single shard experiences a GC pause or compaction spike, overall p99 matches the slowest shard.

What helps: Require the shard key in all OLTP query predicates via linter/ORM guards, and maintain an asynchronous projection (e.g., OpenSearch or a secondary lookup table) for cross-shard search.

Celebrity tenant skew

Even with `hash(tenant_id)`, one enterprise customer generates 35% of total writes, exhausting IOPS on its assigned physical host.

What helps: Use virtual shards so the heavy tenant's keyspace range can be isolated onto dedicated hardware, or sub-shard the hot tenant with a salted key (`tenant_id#0..7`).

Split-brain routing metadata

During a shard split or primary failover, stale routing caches send writes to the old shard owner, causing silent data divergence or failed constraints.

What helps: Use epoch/generation numbers in the routing protocol so the old shard rejects writes with `MOVED` / `RECOVERING` once ownership transfers in etcd or Raft.

05 / Practical checklist

Avoid these mistakes

  • Choosing `hash(user_id)` early when 40% of internal admin and billing queries filter by `merchant_id`, forcing full-cluster scatter-gather on critical paths.
  • Modulo-hashing directly by physical node count (`id % 8`), which forces a massive full-table reshuffle when expanding from 8 to 12 nodes.
  • Assuming global auto-increment sequences will remain cheap; centralized sequence generators become a single point of contention unless replaced with UUIDv7, Snowflake IDs, or per-shard hi/lo ranges.
  • Leaving foreign keys and cross-shard joins in place via application-level N+1 loops instead of colocation (`tenant_id` in every child table) or denormalized read models.
  • Delaying resharding automation until disk hits 90% full, leaving insufficient headroom for double-buffering snapshots during live chunk migration.
