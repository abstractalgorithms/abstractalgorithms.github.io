Saga &
Compensation Patterns.

A Saga coordinates a multi-service business transaction as a sequence of local ACID transactions paired with compensating actions that semantically undo prior steps on failure, avoiding distributed 2-Phase Commit locks at the cost of eventual consistency.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Design every saga step before the pivot transaction to be idempotent and paired with a compensating action, and persist state transitions via a transactional outbox so crashes never leave workflows orphaned.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Microservices with database-per-service cannot span a single ACID transaction across Order, Inventory, and Payment databases. Two-Phase Commit (XA/2PC) holds cross-network locks that stall throughput and block when a coordinator crashes. Sagas keep every local transaction fast and lock-free while guaranteeing either full completion or semantic rollback.

  • Every saga has three transaction classes: Compensable (undoable, e.g., ReserveInventory), Pivot (point of no return, e.g., ChargeCard), and Retriable (guaranteed to succeed, e.g., ConfirmOrder).
  • Orchestration (Temporal, AWS Step Functions) centralizes control flow and debugging, whereas Choreography (Kafka events) decouples services but hides global state.
  • Sagas provide ACD (Atomicity, Consistency, Durability) without Isolation—concurrent sagas can observe intermediate uncommitted states (dirty reads).
  • Countermeasures like Semantic Locks (PENDING_RESERVATION) and Commutative Updates prevent isolation anomalies without distributed locks.
  • The Transactional Outbox pattern (DB write + outbox row in one local ACID tx + Debezium CDC) prevents dual-write split-brain between DB commits and message brokers.

Good candidates

  • Multi-service workflows (e.g., e-commerce checkout, flight+hotel booking, loan origination) spanning independent databases.
  • Long-running business processes (seconds to days) involving external payment gateways or human approvals where DB locks cannot be held.
  • High-throughput systems where 2PC coordinator latency and lock contention would violate p99 SLOs.

Think twice

  • Operations contained within a single database or monolith where a standard local ACID transaction is simpler and strictly isolated.
  • Hard real-time financial ledgers requiring strict serializability (zero dirty-read window) across partitions—use a NewSQL DB (Spanner/CockroachDB) instead.
  • Simple 2-step read-after-write flows where synchronous retry or a single outbox event suffices without compensation logic.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA marketplace checkout spanned Order, Loyalty Points, Warehouse Inventory, and Stripe Payment; network timeouts frequently left loyalty points deducted on failed card charges.

The idea

In a distributed architecture where each service owns its database, a single business operation (like placing an order) cannot rely on a traditional ACID transaction across services. Holding Two-Phase Commit (2PC) locks over WAN/RPC boundaries destroys throughput and halts the system whenever a participant hangs.

A Saga breaks a distributed transaction TTT into a sequence of local ACID transactions T1,T2,…,TnT_1, T_2, \dots, T_nT1​,T2​,…,Tn​. If step TkT_kTk​ fails, the saga executes compensating transactions Ck−1,…,C1C_{k-1}, \dots, C_1Ck−1​,…,C1​ in reverse order to semantically undo the prior effects (e.g., issuing a refund or releasing reserved stock).

Concrete walkthrough

Consider an e-commerce checkout managed by an Orchestrator (e.g., Temporal):

  1. T1 (Compensable) — Create Order: Order Service inserts an order row with status = PENDING and an outbox record in one local PostgreSQL transaction.
  2. T2 (Compensable) — Reserve Stock: Inventory Service decrements available_qty and inserts a semantic lock reservation(order_id, TTL=10m).
  3. T3 (Pivot) — Charge Card: Payment Service calls Stripe with Idempotency-Key: pay_{order_id}. Stripe returns 402 Card Declined.
  4. Pivot Failure -> Compensate: Because T3 failed, the orchestrator reverses direction and invokes C2 (ReleaseStock(order_id)) and C1 (CancelOrder(order_id, reason='PAYMENT_DECLINED')).
  5. Idempotent Convergence: Even if C2 times out once and is retried, the reservations table checks order_id status and applies the release exactly once.

When the T3 payment pivot fails, the orchestrator runs idempotent compensations C2 and C1 in reverse order.

Handling missing isolation (ACD vs ACID)

Because local transactions commit immediately, Sagas lack Isolation. A concurrent request can read uncommitted business state (e.g., an order marked PENDING or stock temporarily deducted). To prevent anomalies without distributed locks:

  • Semantic Lock: Mark records with status = PENDING_RESERVATION so other sagas either block or reject edits until the lock clears.
  • Commutative Updates: Express mutations as deltas (balance += -50) rather than absolute overwrites (balance = 150), so out-of-order compensations still converge.
  • Pessimistic View: Reorder steps so high-risk checks (fraud/credit) run before low-risk reservations, and put customer notifications strictly after the pivot.

Failure modes

  • Stuck Semantic Locks: If an orchestrator or consumer crashes mid-saga without recovery, PENDING reservations can lock inventory indefinitely. Always attach a TTL sweeper or workflow timeout.
  • Out-of-Order Event Delivery: In Choreography sagas over partitioned topics, a CancelOrder event can arrive before CreateOrder if partition keys differ. Partition strictly by saga_id / aggregate_id.
  • Partial Pivot Ambiguity: A timeout on ChargeCard leaves the outcome unknown—never compensate immediately without first querying the payment provider's status endpoint using the Idempotency-Key.

Transactional outbox and idempotency

Reliable sagas depend on at-least-once delivery paired with idempotent receivers:

  • Store an inbox / processed_events(event_id PRIMARY KEY) table in each participant's database and check/insert it inside the same local transaction as the business update.
  • Use Debezium CDC or a transactional outbox table so database commits and event publications are atomic.

Practical checklist

  • Classify every step as Compensable, Pivot, or Retriable; keep non-undoable actions (emails, webhooks) strictly after the Pivot.
  • Persist saga state and outbox events in a single local ACID transaction (no dual writes).
  • Require deterministic idempotency keys (saga_id + step) on all forward and compensating endpoints.
  • Protect in-flight entities with Semantic Locks (PENDING_*) and TTL expiration sweepers.
  • Configure exponential backoff + jitter and a Dead-Letter Queue for compensating transactions.
  • Propagate saga_id and traceparent across all RPCs and broker headers.
03 / Engineering trade-offs

Weighing architectural decisions

Orchestration vs Choreography

Advantage: Orchestration makes state, timeouts, and compensation order explicit in one workflow definition with clear observability.

Drawback: Adds an orchestrator dependency (Temporal/Step Functions) that must be operated and scaled alongside microservices.

Saga vs Two-Phase Commit (2PC)

Advantage: Zero cross-service locks; individual services remain available and fast even if downstream peers are slow.

Drawback: Requires writing custom compensating logic and handling dirty-read isolation anomalies.

Semantic Locks vs Optimistic Retries

Advantage: Semantic locks (PENDING states) prevent conflicting sagas from acting on transient intermediate data.

Drawback: Adds state-machine complexity and requires TTL sweepers to reap abandoned locks.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Dual-Write Split-Brain

A service commits its local DB transaction but crashes before publishing the Kafka/SQS event, stalling the saga indefinitely.

What helps: Use the Transactional Outbox pattern: write the domain change and outbox event in the same local ACID transaction, then tail it via Debezium CDC or a poller.

Non-Idempotent Compensation

A network timeout triggers a retry of RefundPayment or ReleaseStock, crediting the customer twice or inflating inventory count.

What helps: Attach a deterministic idempotency key (saga_id + step_name) to every forward and compensating command, enforced via a UNIQUE constraint.

Failing Compensating Transaction

After ChargeCard fails, the compensating ReleaseStock call also fails due to a DB outage, leaving inventory permanently locked.

What helps: Treat all compensating actions as retriable: retry with exponential backoff + jitter, route poison pills to a DLQ, and alert an operator for manual reconciliation.

Missing Isolation (Lost Update / Dirty Read)

A concurrent saga reads or overwrites a record modified by an in-flight saga that later rolls back, acting on phantom state.

What helps: Apply semantic locks (status flags), commutative updates (delta +/- instead of absolute set), or versioned optimistic concurrency checks.

05 / Practical checklist

Avoid these mistakes

  • Placing a non-compensable side effect (like sending an email or shipping webhook) before the pivot transaction.
  • Assuming compensating transactions never fail and omitting retries or Dead-Letter Queues for rollback paths.
  • Building Choreography sagas across >4 services without a correlation_id, making production failures impossible to trace.
  • Skipping idempotency keys on forward and backward steps, causing duplicate charges or double refunds on at-least-once delivery.
  • Forgetting to set saga step timeouts, allowing stuck workflows to hold semantic inventory locks forever.
