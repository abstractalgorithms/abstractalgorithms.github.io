The idea to keep with you

A Saga coordinates a multi-service business transaction as a sequence of local ACID transactions paired with compensating actions that semantically undo prior steps on failure, avoiding distributed 2-Phase Commit locks at the cost of eventual consistency.

TL;DR30-second simplified summary
▾

Core Mechanics: When each microservice owns its own database, a checkout spanning Order, Inventory, and Payment cannot use a single local ACID transaction—and 2-Phase Commit (2PC) holds cross-network locks that stall throughput.

Visual & Structural Flow: Depicts Orchestrated Checkout Saga: Pivot Failure & Semantic Rollback (Temporal Orch -> Order DB -> Inventory DB -> Payment (Pivot)); Local ACID Commit + Transactional Outbox + Idempotent Inbox (Participant Service -> Domain Table -> Outbox / Inbox Table -> Debezium CDC -> Kafka).

Trade-Offs & Production: Choose the coordination style based on workflow length, service count, and observability needs. A Temporal workflow orchestrates Order (PENDING semantic lock + TTL sweeper), Inventory (commutative delta + inbox dedup), and Payment (Pivot).

Failure Modes & Application: Compare Sagas with 2PC, Transactional Outbox CDC, and idempotent APIs.

01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is a Saga.

When each microservice owns its own database, a checkout spanning Order, Inventory, and Payment cannot use a single local ACID transaction—and 2-Phase Commit (2PC) holds cross-network locks that stall throughput. A Saga splits the workflow into local ACID transactions, classifying steps into: Compensable (ReserveInventory -> undoable via ReleaseInventory), Pivot (ChargeCard -> point of no return), and Retriable (ConfirmOrder, SendEmail -> guaranteed to succeed after Pivot).

Saga Compensation Flow

Orchestrated Checkout Saga: Pivot Failure & Semantic Rollback

No distributed DB locks are held; failed pivot steps trigger idempotent backward compensations.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Sagas Lack Isolation (ACD vs. ACID Countermeasures).

Because each local transaction commits immediately, Sagas provide ACD (Atomicity, Consistency, Durability) without Isolation: concurrent sagas can observe intermediate PENDING states (dirty reads) or cause lost updates. To prevent anomalies without 2PC locks, use Semantic Locks (status = PENDING_RESERVATION with TTL sweepers), Commutative Updates (delta +/- instead of absolute SET), and Transactional Outboxes to eliminate dual-write split-brain.

Compensations Must Also Be Idempotent & Retriable

If ReleaseStock times out and retries, duplicate execution must not inflate stock—attach saga_id + step_name idempotency keys.

Never Put Non-Undoable Side Effects Before Pivot

Sending confirmation emails or shipping webhooks before ChargeCard succeeds forces awkward apology emails on rollback.

03
STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Sagas excel (and where Local ACID or NewSQL wins).

Use Sagas for multi-database or long-running workflows; stay with local ACID or NewSQL when strict serializability is required.

ChoiceWhat it buysWhat it costs
Good Candidate: Multi-Service Checkout, Travel & Loan WorkflowsKeeps local DB transactions fast and lock-free even across external APIs or multi-second workflows.Requires building compensating actions, idempotency keys, and semantic lock sweepers.
Avoid: Single-Database OperationsUse a standard local ACID transaction—zero compensation or outbox overhead.Building a saga inside one database adds needless complexity.
Avoid: Zero-Dirty-Read Financial LedgersUse a NewSQL database (Spanner / CockroachDB) if strict cross-partition serializability is mandatory.Sagas expose intermediate `PENDING` states until completion or compensation.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Transactional Outbox & Idempotent Consumers are implemented.

Write domain mutations and outbox events in the same local ACID transaction (tailed by Debezium CDC or FOR UPDATE SKIP LOCKED relay), and enforce an inbox(event_id PRIMARY KEY) table on every participant.

# Idempotent Transactional Outbox relay loop (Python + Postgres)
def publish_pending_outbox_events(db_conn, kafka_producer, batch_size: int = 100) -> int:
    rows = db_conn.execute(
        "SELECT id, aggregate_id, payload FROM outbox WHERE published_at IS NULL "
        "ORDER BY id ASC LIMIT %s FOR UPDATE SKIP LOCKED",
        (batch_size,),
    ).fetchall()
    for event_id, agg_id, payload in rows:
        kafka_producer.send("saga.events", key=agg_id, value=payload)
        db_conn.execute("UPDATE outbox SET published_at = NOW() WHERE id = %s", (event_id,))
    db_conn.commit()
    return len(rows)

# Note: Wrap batch in try/except Exception: db_conn.rollback(); raise so failed Kafka sends do not leave partial DB state.

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Orchestration vs. Choreography vs. 2-Phase Commit.

Choose the coordination style based on workflow length, service count, and observability needs.

ChoiceWhat it buysWhat it costs
Orchestration (Temporal / AWS Step Functions)Centralizes control flow, timeouts, and compensation order in one debuggable workflow.Adds an orchestrator platform dependency to operate.
Choreography (Kafka Domain Events)Loose service coupling—no central coordinator.Global state is scattered across >4 services and hard to trace without strict `correlation_id`s.
Two-Phase Commit (2PC / XA)Full ACID isolation across participants.Cross-network locks destroy throughput and block if the coordinator crashes mid-commit.
06
STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Temporal Orchestrator + Outbox + Semantic Locks.

A Temporal workflow orchestrates Order (PENDING semantic lock + TTL sweeper), Inventory (commutative delta + inbox dedup), and Payment (Pivot). Every service commits domain state + outbox rows atomically, eliminating dual-write split-brain.

Zero Dual-Write

Local ACID Commit + Transactional Outbox + Idempotent Inbox

1.1. Atomic Outbox: Domain row and outbox event commit together—eliminating crash-induced split-brain.

2.2. Inbox Dedup: INSERT INTO inbox(event_id) ON CONFLICT DO NOTHING makes at-least-once retries safe.

3.3. TTL Sweeper: Stuck PENDING semantic locks expire cleanly if a saga hits workflow timeout.

Outbox + Inbox + Semantic Locks give Sagas reliable execution without distributed 2PC locks.
