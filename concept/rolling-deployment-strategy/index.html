A foundational engineering concept

Rolling Deployment
Strategy.

A rolling deployment incrementally replaces old service instances with new ones in bounded batches (e.g., maxSurge 25%, maxUnavailable 0) gated by readiness probes and connection draining, achieving zero downtime without doubling infrastructure capacity.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Zero-downtime rolling updates require three synchronized invariants: backward-compatible schemas/APIs during the overlap window, accurate readiness probes before shifting traffic, and pre-stop connection draining after SIGTERM.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Deploying a new binary simultaneously across all instances causes immediate downtime, while full blue-green environments double peak compute bills for large clusters. Rolling deployments let teams ship dozens of times per day on existing capacity (10-25% surge) while isolating bad builds before they reach 100% of users.

  • maxSurge controls extra capacity spun up during rollout (e.g., 25%), while maxUnavailable=0 guarantees full serving capacity at every step.
  • Readiness probes (/readyz) gate when a new pod enters the load-balancer EndpointSlice; liveness probes (/livez) only restart wedged processes.
  • Asynchronous EndpointSlice/kube-proxy propagation takes 1-5s; a preStop sleep (5-15s) prevents in-flight 502s after SIGTERM.
  • Because v1 and v2 run concurrently for minutes, every DB migration and internal message schema must follow the expand-and-contract pattern.
  • PodDisruptionBudgets (PDB) protect minimum replica counts when node drains or cluster upgrades overlap with a rolling deploy.

Good candidates

  • Stateless microservices and web APIs running on orchestrators (Kubernetes, AWS ECS, Nomad) where v1 and v2 can coexist safely.
  • Cost-sensitive clusters where maintaining a 100% duplicate idle green fleet is prohibitively expensive.
  • Routine continuous delivery pipelines (10-50 deploys/day) paired with automated readiness gates and metric-based rollbacks.

Think twice

  • Monolithic databases or stateful single-leader systems requiring an exclusive schema lock or incompatible wire-protocol switch.
  • High-risk releases needing instant 100%-to-0% traffic cutover or isolated dark-launch validation (prefer Blue-Green or Canary).
  • Legacy stateful apps that hold unshared in-memory sessions without sticky routing or externalized Redis session stores.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA 40-pod Go payment API saw 150-300 HTTP 502 errors on every deploy because pods exited immediately on SIGTERM while kube-proxy iptables rules still routed traffic for ~3 seconds.

The idea

A rolling deployment updates a fleet of NNN identical instances by replacing a bounded subset at a time—creating a surge of new v2 instances, waiting until they pass readiness checks, draining connections from v1 instances, and terminating v1 only after in-flight requests finish.

Unlike a Blue-Green cutover (which requires 2N2N2N capacity) or a Recreate deploy (which incurs downtime), a rolling update runs on N+maxSurgeN + \text{maxSurge}N+maxSurge capacity—typically 10% to 25% extra headroom—while maintaining 100% serving availability when maxUnavailable: 0.

Concrete walkthrough

Consider a 10-pod Kubernetes Deployment configured with maxSurge: 2, maxUnavailable: 0, minReadySeconds: 15, and terminationGracePeriodSeconds: 45:

  1. Surge v2 Pods: The Deployment controller scales the v2 ReplicaSet to 2 pods (10 v1 + 2 v2 total). v2 pods load config and bind port 8080.
  2. Readiness Gate: kubelet polls GET /readyz every 5s. Once v2 returns 200 OK twice, the EndpointSlice controller adds the v2 pod IPs to the Service.
  3. Wait minReadySeconds: The controller waits 15s to verify v2 does not crash-loop under live traffic before marking those 2 pods available.
  4. Drain v1 Pods: The controller marks 2 v1 pods for termination: EndpointSlice removes their IPs while kubelet runs preStop: ["sh", "-c", "sleep 10"] so kube-proxy/Envoy finishes syncing.
  5. Graceful Shutdown: After 10s, v1 receives SIGTERM, sends HTTP/2 GOAWAY, finishes active requests within 35s, and exits cleanly. The loop repeats in batches of 2 until all 10 pods are v2.

Coordinated surge, readiness gating, and preStop draining ensure zero dropped packets while v1 and v2 coexist.

Managing the v1 + v2 overlap window

During a rolling deploy, v1 and v2 run side by side for 2 to 15 minutes. Any shared state—databases, Redis keys, Kafka topics, or session cookies—must tolerate both versions concurrently:

  • Database Schemas: Use expand-and-contract. Add nullable columns or new tables first, deploy code that dual-writes, backfill historical rows, switch reads to the new column, and drop the old column in a final deploy.
  • Wire & Cache Formats: Never reuse protobuf field numbers or mutate JSON field types in place. Version Redis cache keys (e.g., user:v2:{id}) when payload structure changes.

Failure modes

  • Graceful Shutdown Bypass: Frameworks that do not trap SIGTERM (or apps wrapped in sh -c without exec) ignore the shutdown signal and get SIGKILLed after terminationGracePeriodSeconds, aborting active requests.
  • Silent Crash-Loop Rollout: If minReadySeconds is 0 and the app crashes 10s after passing /readyz (e.g., on first real query), Kubernetes considers the surge pod "available" and proceeds to kill healthy v1 pods.
  • PDB Deadlock: Setting a PodDisruptionBudget with minAvailable: 100% blocks node drains, while maxUnavailable: 0 without maxSurge > 0 freezes the Deployment.

Automated halt and rollback gates

Readiness probes only verify that a pod can accept TCP/HTTP traffic—they do not catch business-logic regressions (e.g., HTTP 500s on /checkout or 3x p99 latency).

  • Pair rolling updates with a controller like Argo Rollouts or Flagger querying Prometheus every 30s for 5xx rate (<0.5%) and p99 latency (<250ms).
  • Configure progressDeadlineSeconds: 600 so stuck rollouts surface immediately in CI/CD rather than hanging silently.

Practical checklist

  • Set maxUnavailable: 0 and maxSurge: 25% (or 1 for small replica sets) to preserve 100% capacity.
  • Use exec in container entrypoints so PID 1 receives SIGTERM directly.
  • Add a preStop sleep (5-15s) and set terminationGracePeriodSeconds > longest request timeout.
  • Separate /readyz (local listener/cache ready) from /livez (deadlock check only).
  • Set minReadySeconds: 15-30 and progressDeadlineSeconds: 600.
  • Enforce expand-and-contract migrations so v1 and v2 never clash on shared DBs or caches.
03 / Engineering trade-offs

Weighing architectural decisions

Batch Size (maxSurge / maxUnavailable)

Advantage: Larger batches (e.g., 50% surge) finish rollouts in 2 steps, shrinking the risky v1+v2 overlap window.

Drawback: Increases transient CPU/RAM cost and widens the blast radius if a bad build passes /readyz.

Rolling vs Blue-Green

Advantage: Rolling updates require only 10-25% headroom instead of 100% duplicate fleet capacity.

Drawback: Rollbacks are slower (must roll forward/reverse batch by batch) and v1/v2 must be mutually compatible.

Strict Readiness Gates vs Fast Startup

Advantage: Checking downstream dependencies or warm caches in /readyz prevents cold-start latency spikes.

Drawback: If /readyz checks external DBs, a brief DB blip can mark all pods unready and cause a full-cluster outage.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

SIGTERM vs Load-Balancer Propagation Race

The orchestrator sends SIGTERM and terminates the process before iptables/IPVS/ALB targets finish removing the pod IP, causing connection resets.

What helps: Fail /readyz immediately on SIGTERM, execute a preStop hook (sleep 10s) to let LB endpoints drain, and only then stop the HTTP listener.

Breaking Schema or Serialization Skew

v2 pods write a new protobuf field or drop a SQL column that still-running v1 pods expect, crashing v1 workers mid-rollout.

What helps: Enforce N-1 backward compatibility in CI (protobuf field deprecation, expand-contract DB migrations) before any rolling deploy.

Readiness Probe Cascading Failure

Putting a hard dependency check (e.g., SELECT 1 on Postgres) inside /readyz causes every pod to drop out of the LB simultaneously during a 2s DB hiccup.

What helps: Keep /readyz focused on local process readiness (listener bound, caches warmed) and handle transient upstream errors with circuit breakers.

Slow Rollout Stalling on Resource Quotas

With maxSurge=25% and tight namespace CPU limits or node capacity, new v2 pods stay Pending forever while v1 pods cannot scale down when maxUnavailable=0.

What helps: Maintain 15-25% cluster headroom for autoscaling/surges, set minReadySeconds appropriately, and configure progressDeadlineSeconds to alert on stalled rollouts.

05 / Practical checklist

Avoid these mistakes

  • Using the same endpoint for livenessProbe and readinessProbe, causing Kubernetes to kill-loop pods that are merely overloaded.
  • Leaving terminationGracePeriodSeconds at 30s for workers that run 90s batch jobs or long-lived WebSockets.
  • Setting maxUnavailable > 0 on small 2-replica services, silently dropping capacity by 50% during peak traffic.
  • Omitting minReadySeconds (default 0), which lets a rollout declare success the instant a pod passes one probe even if it crashes 5s later.
  • Forgetting to configure connection draining on external cloud load balancers (ALB deregistration_delay).
