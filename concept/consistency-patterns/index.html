The idea & core mechanics.

Picture a user updating their shipping address, hitting Refresh, and watching their old address reappear for two seconds. Nothing crashed—the write committed to the SQL primary, while the refresh landed on an asynchronous read replica lagging 400ms behind. Choosing the right consistency pattern lets you avoid paying global Raft/Quorum latency on every read while still protecting user trust via session LSN routing.

ChoiceWhat it buysWhat it costs
Good candidateLinearizability for distributed locks, leader leases, and unique username/inventory claims.
Good candidateRead-Your-Writes & Monotonic Reads for user profiles, comments, and settings.
Good candidateCausal Consistency for threaded discussions and collaborative state.
Think twicePaying cross-region consensus latency for analytics counters or view counts where eventual consistency suffices.

Principle 1

Linearizability provides a single global real-time order: once a write completes, every subsequent read anywhere sees it or a newer value.

Principle 2

Causal Consistency preserves happens-before relationships (e.g., question before answer) without blocking on unrelated concurrent writes.

Principle 3

Read-Your-Writes ensures a user always sees their own recent mutations—achievable via sticky replica routing, session LSN tokens, or reading from primary for N seconds after a write.

Principle 4

Monotonic Reads guarantees time never appears to move backward across consecutive reads (pinning a user to a replica or minimum LSN).

Session-Token Read-Your-Writes Routing.

A user updates their display name (committed at primary WAL LSN = 9042) and immediately reloads /profile, which hits a read replica currently at LSN = 9038.

Lesson: The client sends X-Min-LSN: 9042 in its session cookie; the router either waits briefly for the replica to catch up to 9042 or falls back to the primary, preventing the 'disappearing edit' bug.

Consistency spectrum & real-world mechanisms

Pattern Scope Guarantees Typical Implementation
Linearizable Global (data-centric) Real-time single-copy illusion Raft / Paxos quorum reads (ReadIndex)
Sequential Global Same order for all nodes, not real-time Single-sequencer log
Causal Partial order Preserves cause-before-effect Vector clocks / Hybrid Logical Clocks
Read-Your-Writes Per-client session User always sees own writes Primary-pin window or min_lsn cookie
Monotonic Reads Per-client session Reads never go backward in time Sticky replica or last_seen_lsn
Eventual Global convergence Converges when writes cease Async replication + LWW / CRDT

Reference implementation (Python — Session LSN Read-Your-Writes Router)

# Session-token Read-Your-Writes replica router (Python)
def read_profile(user_id: str, min_lsn: int, primary_db, replica_db):
    if replica_db.current_lsn() >= min_lsn:
        return replica_db.fetch_profile(user_id)
    return primary_db.fetch_profile(user_id)

Failure modes & mitigations.

How Consistency Patterns breaks under concurrency, partial network partitions, or overload—and how production systems recover.

Replication Lag Breaking Read-Your-Writes

Write hits primary, immediate refresh hits lagging replica and returns old state. Mitigation: Route recent writers to primary for a short window or enforce min_lsn on replicas.

Replica Hopping Breaking Monotonic Reads

Request 1 hits Replica A (LSN 100); Request 2 hits lagging Replica B (LSN 92), so data disappears. Mitigation: Pin user session to one replica or pass last_seen_lsn.
