The idea to keep with you

When choosing consistency levels across replicated storage, reserve strict linearizability for uniqueness constraints, leader leases, and financial balances, while using Read-Your-Writes session tokens or causal consistency for user-facing feeds and profiles so reads scale horizontally without stale regressions.

TL;DR30-second simplified summary
▾

Strong consistency is expensive because it forces coordination across replicas on the critical path. Tracking monotonic WAL LSNs per user session offloads >95% of reads to replicas while eliminating stale self-reads, whereas causal consistency prevents out-of-order comment threads across regions without cross-ocean quorum RTT.

The Three Anomalies That Break Asynchronous Read Replicas.

Why this matters: Trace Read-Your-Writes violations, Monotonic Read regressions, and Causal inversions in production.

Suppose Primary DB commits UPDATE users SET bio = 'Staff Eng' at WAL LSN 1042, and Replica A is at LSN 1038 (12 ms behind) while Replica B is at LSN 1042. When the user reloads their profile 5 ms later and hits Replica A, their new bio vanishes.

Three concrete consistency guarantees eliminate these anomalies without global consensus:

  1. Read-Your-Writes (RYW): A user always sees mutations they themselves submitted, even if other users briefly see older data.
  2. Monotonic Reads: Once a user observes state at LSN 1042, subsequent reads for that user never route to a replica behind LSN 1042 (preventing 'time travel' when load balancers bounce requests between Replica B and Replica A).
  3. Causal Consistency: If Event B happens after observing Event A (e.g., Alice posts a bug, Bob replies 'Fixed'), every observer sees A before B, while concurrent unrelated posts can arrive in any order.

From Eventual to Linearizable: Cost vs. Invariant Strength.

Why this matters: Compare latency, availability under partition, and invariant guarantees across the consistency spectrum.

Stronger consistency restricts which replicas can answer a read and how many nodes must acknowledge a write—directly trading tail latency and partition availability for global ordering.

  • Eventual Consistency: Replicas converge once writes stop; reads serve locally in < 1 ms from any node. Great for view counters, recommendations, and DNS.
  • Causal Consistency: Tracks causal dependencies (context_token); commits locally in one datacenter (< 5 ms) and replicates causally across regions without cross-ocean consensus.
  • Sequential Consistency: All nodes observe operations in the same global order, though not necessarily matching wall-clock timestamps.
  • Linearizability (Strong Consistency): Every operation appears to take effect atomically at a single point between its invocation and response. Requires Raft/Paxos quorum writes and leader lease or quorum reads.

STAGE 03 · INVARIANT & SAFE IMPLEMENTATIONcore

LSN-Bounded Replica Router for Read-Your-Writes in Java.

Why this matters: Implement a session-token LSN router that serves from fast read replicas whenever caught up, falling back to primary only when replica lag exceeds the caller's write offset.

Sticky routing to the primary for 5 seconds after every write works for low write rates, but write-heavy users pin all their reads onto the primary. Tracking the exact monotonic WAL LSN (pg_current_wal_lsn()) lets any replica that has replayed >= minRequiredLsn serve the read immediately.

import java.util.List;
import java.util.concurrent.ThreadLocalRandom;

public final class LsnAwareReadRouter {
    public record ReplicaNode(String id, long appliedLsn, boolean healthy) {}

    private final ReplicaNode primary;
    private final List<ReplicaNode> replicas;

    public LsnAwareReadRouter(ReplicaNode primary, List<ReplicaNode> replicas) {
        this.primary = primary;
        this.replicas = List.copyOf(replicas);
    }

    public ReplicaNode selectNodeForRead(long sessionMinLsn) {
        List<ReplicaNode> caughtUp = replicas.stream()
                .filter(r -> r.healthy() && r.appliedLsn() >= sessionMinLsn)
                .toList();

        if (!caughtUp.isEmpty()) {
            int idx = ThreadLocalRandom.current().nextInt(caughtUp.size());
            return caughtUp.get(idx);
        }
        // Fallback to primary only if all replicas lag behind caller's LSN
        return primary;
    }
}

STAGE 04 · MECHANICS AT SCALEdeepDive

Cross-Region Causal Tokens vs. Synchronous Quorum Latency.

Why this matters: Evaluate multi-region consistency trade-offs under speed-of-light RTT constraints.

Across US-East and EU-West (~75 ms RTT), linearizable quorum writes require at least one cross-ocean round trip (~80–120 ms p99). For collaborative comments, social feeds, or shopping carts, paying 100 ms per click hurts conversion.

Causal consistency (used in systems like Meta's TAO / Lamport-clock replication pipelines) attaches a compact causal dependency token to writes. Local datacenters acknowledge writes in < 5 ms, and remote regions buffer out-of-order replicated events until their causal parent LSN arrives.

Engineering Decision Framework
Problem
How to guarantee users immediately see their own profile/settings updates while still offloading 90%+ of reads to asynchronous replicas.
Naive Solution
Route all reads for every user to the primary database, or enable linearizable quorum reads globally.
Why It Fails
Routing all reads to the primary defeats read-replica horizontal scaling and saturates primary CPU/IOPS.
Alternatives
Compare primary-only reads, fixed 5-second sticky-primary cookies, and LSN-tracked replica routing.
Engineering Decision
Propagate the monotonic commit LSN in the user's session token and route reads to any healthy replica whose applied_lsn >= session_min_lsn, falling back to the primary only when all replicas lag behind.
Trade-Offs
Preserves Read-Your-Writes and Monotonic Reads while offloading >95% of reads to replicas within milliseconds of commit.

STAGE 05 · EDGE CASES, ASSUMPTIONS & GLOSSARYdeepDive

Clock Skew Pitfalls, Replica Stall Edge Cases & Glossary.

Why this matters: Highlight subtle failure modes in session-LSN routing and define canonical consistency terms.

Edge Cases & Failure Modes:

  • Replica Lag Spike Fallback Storm: If network congestion causes all replicas to lag 10 seconds behind the primary, LSN-aware routing falls back 100% of active writers onto the primary. Pair fallback with a circuit breaker or bounded wait (e.g., wait up to 15 ms for a replica to catch up before hitting primary).
  • Wall-Clock Timestamp Trap: Never compare updated_at wall-clock timestamps from different app nodes to resolve conflicts (Last-Writer-Wins); NTP clock skew can silently discard newer writes.

Assumptions & Glossary:

  • Assumptions: Assumes single-leader WAL replication exposes a monotonically increasing sequence number (LSN or GTID) per shard.
  • Linearizability: Strongest single-object consistency; every read returns the value of the most recent completed write in real time.
  • Causal Consistency: Operations that are causally related are seen by every node in the same order; concurrent operations may be seen in different orders.
  • Read-Your-Writes: Session guarantee ensuring a client always observes its own prior updates.
