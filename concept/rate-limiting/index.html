Rate Limiting Algorithms & Token Buckets

Protecting APIs from abuse, resource exhaustion, and cascading thundering herds.

Orientation & Intuition

Rate limiting controls the consumption rate of system resources by restricting the number of API calls or operations a client can make within a specified window. Proper rate limiting prevents denial-of-service (DoS) attacks, isolates noisy tenants in multi-tenant architectures, smooths burst traffic, and enforces commercial usage quotas.

Key takeaway Use the Token Bucket algorithm for burst-tolerant API gateways. Execute atomic Redis Lua scripts to prevent distributed race conditions without multi-node locks.

Core Architecture & Trade-offs

Without rate limiting, a single rogue script, buggy mobile app retry loop, or malicious DDoS flood will exhaust database connection pools, spike CPU to 100%, and take down the entire platform for all users.

Key Architecture Invariants

  • Token Bucket: Tokens refill at a constant rate $r$ up to capacity $b$. Requests consume tokens. Handles bursts gracefully.
  • Leaky Bucket: Requests enter a queue processed at a steady rate. Smooths out traffic into a constant egress stream.
  • Fixed Window: Counts requests per fixed minute/hour window. Vulnerable to 2x burst spikes at window boundaries.
  • Sliding Window Log: Tracks exact timestamps in a sorted set (ZSET). Accurate but memory intensive.
  • Atomic Execution: Distributed counters must use Redis Lua scripts or single-threaded atomic operations to prevent concurrency race conditions.

When to Use

  • Public REST/GraphQL API Gateways (Kong, Envoy, AWS API Gateway) to protect backend microservices.
  • Preventing brute-force credential stuffing attacks on authentication endpoints.
  • Enforcing tiered subscription billing and third-party SaaS rate caps.

When NOT to Use

  • Internal, low-latency inter-process communication within a trusted private cluster where backpressure should be managed via reactive streams.

2. Back-of-the-Envelope Capacity Estimation

  • Scale: Assume an API serves 10,000,000 Daily Active Users (DAU).
  • Throughput: Average $\sim 50,000$ QPS; peak $\sim 100,000$ QPS.
  • Memory Footprint:

    $$\text{Per-User Memory} = 2\text{ bytes (token count)} + 8\text{ bytes (last-updated timestamp)} = 10\text{ bytes}$$

    $$\text{Total Memory} = 10\text{ bytes} \times 10,000,000\text{ users} = 100\text{ MB}$$

    $100\text{ MB}$ easily fits in the RAM of a single Redis instance, though sharded across a cluster for high availability.

3. Production Atomic Redis Lua Script

lua 
-- Redis Lua Script for Atomic Token Bucket Rate Limiting
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4] or 1)

local data = redis.call("HMGET", key, "tokens", "last_updated")
local tokens = tonumber(data[1])
local last_updated = tonumber(data[2])

if tokens == null then
    tokens = capacity
    last_updated = now
else
    local elapsed = math.max(0, now - last_updated)
    tokens = math.min(capacity, tokens + elapsed * refill_rate)
    last_updated = now
end

if tokens >= requested then
    tokens = tokens - requested
    redis.call("HMSET", key, "tokens", tokens, "last_updated", last_updated)
    redis.call("EXPIRE", key, math.ceil(capacity / refill_rate) * 2)
    return 1 -- Allowed
else
    redis.call("HMSET", key, "tokens", tokens, "last_updated", last_updated)
    return 0 -- Denied (HTTP 429)
end
