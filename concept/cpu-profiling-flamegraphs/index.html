The idea to keep with you

Sampling CPU profilers capture call stacks at fixed intervals (e.g., 99 Hz) with <1% overhead, and Flame Graphs aggregate those stacks into proportional width rectangles so hot code paths jump out immediately.

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are Sampling Profilers & Flame Graphs.

Instrumenting every function entry/exit distorts timings by 10x–100x (the observer effect) and misses kernel/libc time. Statistical sampling profilers (perf, async-profiler, pprof, py-spy) interrupt each CPU core at a fixed rate (e.g., 99 Hz) via kernel timers or PMUs, record the instruction pointer and call stack with <2% overhead, and resume.

A Flame Graph folds identical call stacks together: the Y-axis is call-stack depth (bottom = root, top = leaf executing on CPU) and the X-axis is sorted alphabetically by frame name—where box width equals the percentage of total samples containing that frame.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Statistical Sampling & Flame Graphs.

Without sampling + visual stack folding, megabytes of raw stack traces hide systemic bottlenecks like repeated regex compilation, JSON deserialization, or JVM GC safepoint tax.

Sampling Pipeline

99 Hz Linux perf Capture -> Stack Collapse -> Flame Graph

Sampling at 99 Hz (instead of 100 Hz) prevents lockstep aliasing with periodic 10 ms application timers.

Eliminating 38% CPU Waste in a Go gRPC Gateway

go tool pprof exposed a 38%-width plateau under regexp.Compile inside per-request routing middleware; hoisting compilation to init() dropped CPU from 85% to 51% and cut p99 latency by 42 ms.

Catching Kernel futex & TLS Overhead on JVM

async-profiler -e cpu (using AsyncGetCallTrace + perf_events to avoid safepoint bias) revealed 44% of samples in libcrypto and sys_futex from unpooled TLS handshakes.

03
STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where On-CPU Profiling Works (and When to Use Off-CPU).

On-CPU sampling only fires when a core is actively executing instructions. If CPU is 10% and p99 latency is 500 ms, threads are sleeping on I/O, DNS, or mutexes.

ChoiceWhat it buysWhat it costs
Use: High CPU Utilization & Regression DiffsCaptures hot loops, serialization, GC mark/sweep, and syscall overhead at <2% prod cost.Normalizes to 100% of captured samples—always check total CPU% first.
Avoid: Blocked I/O, Mutex Waits & Sleep StallsSwitch to eBPF `offcputime` or OpenTelemetry distributed tracing instead.On-CPU samplers are completely blind to threads parked in `epoll_wait` or `futex`.
Avoid: Sub-Microsecond MicrobenchmarksUse hardware PMU counters (`perf stat`) or `JMH` / `criterion`.10 ms sampling period is 1,000,000x coarser than nanosecond functions.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How to Capture Clean Stacks & Read Plateaus.

  1. Preserve Frame Pointers: Compile C/C++/Rust with -fno-omit-frame-pointer so kernel unwinding takes ~100 ns without [unknown] towers.
  2. Generate JIT Maps: Use async-profiler on JVM (no safepoint bias) and --perf-basic-prof on Node.js/V8.
  3. Read Two Shapes: Wide flat plateaus at the top = self-time hotspots (serde_json::from_slice); wide towers with thin spires = high inclusive time from calling tiny helpers in a loop.
# Capture 30s at 99 Hz with frame-pointer unwinding, collapse, and diff against baseline
perf record -F 99 -a -g --call-graph fp -- sleep 30
perf script | stackcollapse-perf.pl > new.folded
flamegraph.pl new.folded > cpu.svg

# Differential Flame Graph (red = CPU regression, blue = speedup)
difffolded.pl baseline.folded new.folded | flamegraph.pl > diff.svg

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Profiler Matrix by Runtime.

Choose the profiler that understands your runtime's stack frames and avoids safepoint bias.

ChoiceWhat it buysWhat it costs
C / C++ / Rust: Linux `perf` (FP vs DWARF)<1% overhead with `-fno-omit-frame-pointer`; includes kernel frames.DWARF unwinding (`--call-graph dwarf`) copies 8 KB stack/sample (5–15% overhead).
JVM: `async-profiler` / JFR1–2% overhead; `AsyncGetCallTrace` + `perf` eliminates safepoint bias.Avoid `jstack`/JVMTI samplers, which blame safepoints instead of tight loops.
Go: `runtime/pprof` (`go tool pprof`)<1% overhead at 100 Hz; built-in HTTP endpoint.Excludes Cgo/kernel frames unless paired with `perf` or eBPF.
Python: `py-spy` / `austin`<1% external `process_vm_readv` sampling without code changes.Pass `--native` to correlate C-extension frames (NumPy, Cython).
