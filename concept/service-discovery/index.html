When routing traffic across dynamic, autoscaling fleets, pair push-based endpoint watch streams with local last-known-good endpoint caching and a panic-mode eviction floor so dead instances drain within seconds while control-plane outages never wipe out healthy routing tables.

Why DNS TTLs & Registry Polling Loops Break Dynamic Fleets.

Why this matters: Diagnose stale DNS caching, connection-pool pinning, and registry CPU storms.

When an autoscaler terminates 20 pods during scale-down or rolling deploy, three discovery failure modes hit naive clients:

  1. Stale DNS Cache: Older JVM runtimes defaulted to caching positive DNS lookups indefinitely (or for 30-60s), routing thousands of requests into dead IPs (ConnectTimeoutException).
  2. HTTP/2 & gRPC Connection Pinning: Even when DNS updates in 1 second, a client holding open a single multiplexed HTTP/2 or gRPC TCP socket keeps sending 100% of RPCs to one existing pod, ignoring newly scaled-out pods.
  3. Polling Thundering Herd: 5,000 pods polling /v1/catalog/service/payments every 2 seconds generates 2,500 full-payload reads/sec against the registry.

Production discovery replaces blind polling with long-lived streaming watches (gRPC xDS ADS or etcd/Consul blocking queries with X-Consul-Index wait-index) and L7 load-aware connection pools that rebalance streams across newly added endpoints.

Client-Side Discovery (xDS) vs. Server-Side Load Balancers.

Why this matters: Compare direct client-side routing against L4/L7 proxy discovery across hop latency and polyglot support.

  • Server-Side Discovery: Clients send requests to a stable VIP/DNS name backed by an ALB, NLB, or Envoy ingress gateway. The load balancer queries the service registry and forwards traffic. Simple for polyglot clients, adds 1 network hop (~0.5-1 ms).
  • Client-Side Discovery: Service instances register in etcd/Consul, and a lightweight SDK or local sidecar (Envoy) subscribes to endpoint updates and routes directly to backend pods with zero extra proxy hop.

Graceful Deregistration Sequence: When Kubernetes terminates a pod, endpoint removal from iptables/xDS happens asynchronously in parallel with SIGTERM. Always configure a preStop: sleep 5 hook and drain in-flight HTTP/gRPC requests before closing the listening socket so zero in-flight requests hit Connection reset by peer.

Lease-Bounded Service Directory With Panic-Mode Threshold in Java.

Why this matters: Implement a thread-safe endpoint resolver with monotonic lease expiry and Envoy-style 50% panic-mode protection.

If a transient switch flap causes 70% of backend instances to miss one heartbeat window, purging all 70% concentrates 100% of cluster traffic onto the surviving 30%—triggering an immediate cascading overload.

import java.time.Instant;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;

public final class ResilientServiceDirectory {
    public record ServiceEndpoint(String instanceId, String host, int port, long leaseExpiresAtMillis, boolean outlierEjected) {}

    private final ConcurrentHashMap<String, ServiceEndpoint> endpoints = new ConcurrentHashMap<>();
    private final double panicThresholdRatio; // e.g. 0.50: if <50% healthy, route to all known endpoints

    public ResilientServiceDirectory(double panicThresholdRatio) {
        if (panicThresholdRatio <= 0.0 || panicThresholdRatio > 1.0) {
            throw new IllegalArgumentException("panicThresholdRatio must be in (0.0, 1.0]");
        }
        this.panicThresholdRatio = panicThresholdRatio;
    }

    public void heartbeat(String instanceId, String host, int port, long ttlMillis) {
        long expiresAt = Instant.now().toEpochMilli() + Math.max(1_000L, ttlMillis);
        endpoints.put(instanceId, new ServiceEndpoint(instanceId, host, port, expiresAt, false));
    }

    public List<ServiceEndpoint> resolveRoutableEndpoints() {
        long now = Instant.now().toEpochMilli();
        List<ServiceEndpoint> all = List.copyOf(endpoints.values());
        if (all.isEmpty()) return List.of();

        List<ServiceEndpoint> healthy = all.stream()
                .filter(ep -> ep.leaseExpiresAtMillis() > now && !ep.outlierEjected())
                .toList();

        double healthyRatio = (double) healthy.size() / all.size();
        if (healthyRatio < panicThresholdRatio) {
            // Panic mode: assume control-plane heartbeat partition and keep routing across all known endpoints
            return all;
        }
        return healthy;
    }
}

Large-Cluster Watch Fan-Out & When Managed LBs Beat Service Meshes.

Why this matters: Prevent O(Pods * Services) watch amplification in huge clusters and avoid unnecessary sidecar complexity.

In a 5,000-node Kubernetes cluster where every pod runs an Envoy sidecar watching all 800 services, a single pod restart triggers $5,000 \times 800$ watch notifications—saturating kube-apiserver and control-plane CPU.

Scope sidecar/SDK watches strictly to declared explicit upstream dependencies (Sidecar egress allowlists) and coalesce rapid endpoint churn into 100-250 ms debounce windows.

When NOT to Build Client-Side xDS Discovery: For teams running < 50 microservices on AWS/GCP or standard Kubernetes, managed ALBs/NLBs or native Kubernetes Service + EndpointSlices with gRPC round-robin load balancing ship with zero control-plane maintenance toil.

Engineering Decision Framework
Problem
How to route internal RPCs across 300 autoscaling microservices with sub-second failover and zero extra proxy hops.
Naive Solution
Use standard OS DNS lookups with a 60-second TTL and single persistent HTTP/2 connections.
Why It Fails
60-second DNS TTLs blackhole traffic into terminated pods, while single HTTP/2 connections pin load onto old pods after scale-out.
Alternatives
Compare standard OS DNS, internal L7 ALB server-side discovery, and gRPC xDS client-side watch discovery.
Engineering Decision
Use internal L7 ALBs for heterogeneous HTTP REST services where +1 ms proxy hop is acceptable, and gRPC xDS watch streams with outlier detection and panic-mode thresholds for ultra-low-latency internal RPC meshes.
Trade-Offs
Eliminates extra proxy hops and stale DNS caches in exchange for control-plane xDS operational management.

STAGE 05 · ASSUMPTIONS, LIMITATIONS & GLOSSARYdeepDive

Registry Assumptions & Canonical Service Discovery Glossary.

Why this matters: Summarize heartbeat jitter assumptions and canonical service discovery terms.

Assumptions & Limitations:

  • Jittered Heartbeat Intervals: Assumes heartbeat timers include +/-20% random jitter so synchronized pod startups do not hammer the registry at identical millisecond ticks.
  • Active Outlier Detection: Assumes callers track transport/5xx errors locally so dead instances are ejected within milliseconds rather than waiting for full lease TTL expiry.

Canonical Glossary:

  • Client-Side Discovery: Pattern where callers query/watch the service registry directly and execute load balancing locally.
  • Server-Side Discovery: Pattern where callers hit a dedicated load balancer or router that resolves backend endpoints.
  • Panic Mode: Load-balancer safety mechanism that routes to all configured endpoints when the healthy fraction falls below a critical threshold (typically 50%).
  • Outlier Detection: Passive data-plane health checking that temporarily ejects endpoints returning consecutive errors or latency spikes.
