STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Mutation Testing.

Why this matters: The mechanism: understand how Mutation Testing works from first principles.

Mutation testing (PITest for Java, Stryker for TS/C#, mutmut for Python) injects single syntactic faults—mutants—such as flipping + to -, > to >=, true to false, or && to || into compiled bytecode or the AST, then runs covering tests.

Outcomes fall into four buckets: Killed (test failed—good!), Survived (tests still passed—assertion gap!), Timed Out (infinite loop—killed), and No Coverage. Mutation Score = Killed / (Total - Equivalent).

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why 95% line coverage gives false confidence.

Why this matters: The problem: see what breaks without Why 95% line coverage gives false confidence under real concurrency or scale.

A test suite can hit 95% line coverage while having weak or tautological assertions—executing a discount calculation without ever asserting the final price.

Two operational traps deter teams: CI Timeout Explosion (running 15,000 mutants across a 100k-line repo without coverage filtering) and Equivalent Mutant Fatigue (burning hours on a mutant that is semantically identical to the original code, like a cache-shortcut check).

Engineering Decision Framework
Problem
How to implement Mutation Testing without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
If latency budgets leave no room for synchronous retries, code coverage measures which lines were executed, not whether assertions actually check correctness; run diff-scoped mutation testing on critical business logic (pricing, auth, state machines) to achieve an 80–90% mutation score.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Diff-Scoped Incremental Mutation Config (Stryker / PITest).

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Think of Diff-Scoped Incremental Mutation Config (Stryker / PITest) as the intuition layer for Mutation Testing: Operational control: configure bounds, failure handling, and safe production defaults.

Scope mutation to changed files (--incremental / --since main) and exclude logging/metrics mutators.

// stryker.config.json: Fast PR-diff incremental mutation on critical domain modules
{
  "mutate": ["src/pricing/**/*.ts", "src/auth/**/*.ts", "!**/*.spec.ts"],
  "incremental": true,
  "coverageAnalysis": "perTest",
  "thresholds": { "high": 85, "low": 75, "break": 70 }
}
