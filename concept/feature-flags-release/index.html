What are Feature Flags.

Why this matters: The mechanism: understand how Feature Flags works from first principles.

In traditional releases, rolling back a buggy feature requires a git revert, CI build, and container redeployment—taking 15–45 minutes while errors spike. Feature flags (LaunchDarkly, Unleash, OpenFeature) separate deployment (pushing binaries to production) from release (exposing behavior to users).

Engineers merge incomplete work behind a flag defaulting to false (dark launch). SDKs stream rule updates via SSE/WebSockets into an in-memory cache and evaluate (flagKey + userId) % 100 locally in <50 µs—never making a per-request network call.

Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Local Deterministic Bucketing & Safe Fallback Defaults.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Think of Local Deterministic Bucketing & Safe Fallback Defaults as the intuition layer for Feature Flags & Progressive Release: Operational control: configure bounds, failure handling, and safe production defaults.

Production flag evaluation must be O(1) in-memory, deterministic across pods, and safe on failure. Never reuse old flag keys (which caused Knight Capital's $440M outage), and always test both true and false branches in CI.

Lifecycle & Failure Recovery

Local Deterministic Bucketing & Safe Fallback Defaults

import hashlib

def evaluate_percentage_flag(flag_key: str, user_id: str, rollout_pct: int, default: bool = False) -> bool:
    if not flag_key or not user_id:
        return default
    if rollout_pct <= 0:
        return False
    if rollout_pct >= 100:
        return True
    # Deterministic sticky bucketing across all stateless pods
    digest = hashlib.sha256(f"{flag_key}:{user_id}".encode("utf-8")).digest()
    bucket = int.from_bytes(digest[:4], "big") % 100
    return bucket < rollout_pct

Control vs. Data Plane

SSE Rule Streaming + Sub-Millisecond In-Memory Evaluation

1.Zero Network Hop: Request threads read the local in-memory ruleset; control-plane outages never block traffic.

2.Immutable Keys: Flag keys are never reused after deletion, preventing Knight Capital-style dead-code reactivation.

3.Dual-Path CI: Integration tests run with both flag=true and flag=false so kill-switch fallbacks stay healthy.

Push flag rules asynchronously to in-memory SDKs so runtime evaluation stays sub-millisecond and resilient to control-plane outages.
