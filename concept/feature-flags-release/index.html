STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are Feature Flags.

In traditional releases, rolling back a buggy feature requires a git revert, CI build, and container redeployment—taking 15–45 minutes while errors spike. Feature flags (LaunchDarkly, Unleash, OpenFeature) separate deployment (pushing binaries to production) from release (exposing behavior to users).

Engineers merge incomplete work behind a flag defaulting to false (dark launch). SDKs stream rule updates via SSE/WebSockets into an in-memory cache and evaluate (flagKey + userId) % 100 locally in <50 µs—never making a per-request network call.

Feature Flag Progressive Rollout & Kill-Switch State Machine

Flags turn rollbacks from 30-minute CI/CD redeploys into sub-second configuration flips.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why Trunk-Based Teams Need Decoupled Releases.

Long-lived feature branches cause painful merge conflicts and big-bang releases. Feature flags let teams merge daily to main while controlling blast radius in production: start with dark-shadow traffic, ramp to 1% internal users, and flip an instant kill switch if p99 latency degrades.

Deterministic Sticky Bucketing

Hashing MurmurHash3(flagKey + ':' + userId) % 100 ensures user u_482 always lands in the same cohort across requests and devices without storing per-user state.

Control-Plane Outage Resilience

Because SDKs cache rulesets locally in memory and supply hardcoded fallback defaults, a LaunchDarkly/Unleash control-plane outage never blocks app startup or request serving.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Feature Flags Belong (and Where They Don't).

Match flag lifespans to their purpose: short-lived release flags (days to weeks) vs. long-lived operational kill switches.

ChoiceWhat it buysWhat it costs
Good Candidate: Infrastructure & Search MigrationsGradually shifts 1% -> 10% -> 100% of queries from Elasticsearch to OpenSearch with instant fallback.Requires maintaining dual read/write compatibility during the migration window.
Good Candidate: Operational Load-Shedding Kill SwitchesDisables non-critical GPU/ML recommendations in <1s during 12x flash-sale traffic surges.Fallback path (e.g., cached trending items) must be tested in CI so it doesn't crash when flipped.
Avoid: Static Environment Config (DB URLs, Ports)Environment variables or Kubernetes ConfigMaps are simpler and audited at deploy time.Wrapping static infra bindings in runtime flags adds unnecessary SDK state and complexity.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Local Deterministic Bucketing & Safe Fallback Defaults.

Production flag evaluation must be O(1) in-memory, deterministic across pods, and safe on failure. Never reuse old flag keys (which caused Knight Capital's $440M outage), and always test both true and false branches in CI.

import hashlib

def evaluate_percentage_flag(flag_key: str, user_id: str, rollout_pct: int, default: bool = False) -> bool:
    if not flag_key or not user_id:
        return default
    if rollout_pct <= 0:
        return False
    if rollout_pct >= 100:
        return True
    # Deterministic sticky bucketing across all stateless pods
    digest = hashlib.sha256(f"{flag_key}:{user_id}".encode("utf-8")).digest()
    bucket = int.from_bytes(digest[:4], "big") % 100
    return bucket < rollout_pct

Alternatives: Server-Side SDKs vs. Edge Workers vs. Traffic Splitting.

Feature flags complement—rather than replace—Kubernetes/ALB canary traffic splitting.

ChoiceWhat it buysWhat it costs
Server-Side In-Memory SDK (OpenFeature / Unleash)<0.1 ms local evaluation; targeting rules and PII never leave your backend.Stale flags accumulate `2^N` code paths unless pruned via automated expiration alerts.
Edge / CDN Evaluation (Cloudflare Workers)Evaluates cohort before hitting origin, enabling full-page CDN cache segmentation.Limited payload size and harder to access deep backend user entitlements.

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Flag Control Plane + Local Streaming SDKs.

A production feature-flag platform separates the Control Plane (audit-logged rule editor + SSE/CDN rule distribution) from Data-Plane Evaluation (in-memory SDKs inside each pod with hardcoded fallback defaults).

Control vs. Data Plane

SSE Rule Streaming + Sub-Millisecond In-Memory Evaluation

1.Zero Network Hop: Request threads read the local in-memory ruleset; control-plane outages never block traffic.

2.Immutable Keys: Flag keys are never reused after deletion, preventing Knight Capital-style dead-code reactivation.

3.Dual-Path CI: Integration tests run with both flag=true and flag=false so kill-switch fallbacks stay healthy.

Push flag rules asynchronously to in-memory SDKs so runtime evaluation stays sub-millisecond and resilient to control-plane outages.
