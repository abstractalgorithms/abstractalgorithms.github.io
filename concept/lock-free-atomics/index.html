What are Lock-Free Atomics.

Why this matters: The mechanism: understand how Lock-Free Atomics works from first principles.

Lock-free atomics coordinate threads using hardware instructions—CMPXCHG on x86-64 or Load-Linked/Store-Conditional (LDXR/STXR) on ARM64—backed by the CPU's MESI/MOESI cache coherence protocol.

Progress guarantees form a strict hierarchy: wait-free (every thread finishes in bounded steps), lock-free (system-wide, at least one thread finishes in finite steps even if others stall), and obstruction-free (progress only in isolation).

Hardware CAS Loop

Compare-And-Swap (CAS) Optimistic Retry State Machine

A CAS failure means another thread just succeeded—guaranteeing system-wide lock-free progress.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why mutexes stall—and the ABA & Use-After-Free traps.

Why this matters: The problem: see what breaks without Why mutexes stall—and the ABA & Use-After-Free traps under real concurrency or scale.

Under heavy multi-core contention, OS mutexes trigger scheduler preemption, priority inversion, and lock convoys. Uncontended CAS takes 5–15 ns with zero kernel syscalls.

However, lock-free pointer structures introduce two subtle hazards:

  • The ABA Problem: Thread 1 reads head = A, pauses; Thread 2 pops A, pops B, and pushes A back. Thread 1's CAS(&head, A, B) succeeds even though B was freed!
  • Use-After-Free: freeing a popped node while a concurrent reader still dereferences its next pointer.
ABA Hazard

How the ABA Problem Corrupts a Naive CAS Stack

Mitigate ABA with versioned/tagged pointers (CMPXCHG16B / AtomicStampedReference) and Hazard Pointers / EBR.

Acquire/Release Memory Ordering & Cache-Line Padding.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Think of Acquire/Release Memory Ordering & Cache-Line Padding as the intuition layer for Lock-Free Atomics: Operational control: configure bounds, failure handling, and safe production defaults.

Use memory_order_acquire / memory_order_release to establish happens-before edges without unnecessary seq_cst fences on ARM64, and pad hot atomics to 64-byte cache lines (alignas(64)) to prevent false sharing.

Request & State Flow

Acquire/Release Memory Ordering & Cache-Line Padding

#include <atomic>
#include <cstddef>

struct alignas(64) PaddedSlot {
    std::atomic<size_t> sequence{0}; // Isolated to its own 64B cache line
};

// Acquire-Release synchronization (cheaper than seq_cst on ARM64)
std::atomic<bool> ready{false};
int payload = 0;

void producer() {
    payload = 42;
    ready.store(true, std::memory_order_release);
}

int consumer() {
    while (!ready.load(std::memory_order_acquire)) {}
    return payload; // Guaranteed to observe 42
}

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Epoch-Based Reclamation & Cache-Line Isolation.

Why this matters: Production architecture: see how the components compose end to end under real load.

Think of Epoch-Based Reclamation & Cache-Line Isolation as the intuition layer for Lock-Free Atomics: Production architecture: see how the components compose end to end under real load.

Production lock-free runtimes (such as Rust crossbeam-epoch or Disruptor) combine 64-byte cache-line padding (eliminating false sharing between producer/consumer cursors) with Epoch-Based Reclamation (EBR) so retired nodes are only freed once every active thread has advanced past the retirement epoch.

Avoid Overusing seq_cst

Use relaxed for standalone counters, acquire/release for producer-consumer handoffs, and reserve seq_cst only when total global ordering across multiple atomics is required.

Tagged Pointers (CMPXCHG16B)

Pack a 64-bit monotonic version counter alongside the 64-bit pointer to defeat ABA in lock-free stacks and freelists.
