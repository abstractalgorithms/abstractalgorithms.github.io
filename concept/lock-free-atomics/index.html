Lock-Free
Atomics.

Lock-free atomics coordinate shared state across threads using hardware compare-and-swap (CAS) primitives and explicit memory orderings so at least one thread always makes progress without OS mutex blocking.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Lock-free atomics eliminate mutex context switches and deadlocks, but high contention still causes CPU cache-line bouncing and subtle ABA/memory-ordering bugs.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

When dozens of cores contend on a single mutex, OS scheduling, priority inversion, and lock convoys cap throughput long before CPU cores are saturated. Hardware atomic instructions (CMPXCHG, LDXR/STXR) and carefully chosen memory barriers let high-throughput queues, ring buffers, and counters scale with bounded tail latency.

  • Lock-free guarantees system-wide progress (some thread finishes in finite steps); wait-free guarantees per-thread progress; obstruction-free only guarantees progress in isolation.
  • Modern CPUs implement atomics via CMPXCHG (x86-64) or Load-Linked/Store-Conditional (LDXR/STXR on ARM64) backed by the MESI/MOESI cache coherence protocol.
  • Memory orderings (relaxed, acquire, release, seq_cst) control compiler and CPU instruction reordering—overusing seq_cst adds unnecessary MFENCE/DMB barriers on ARM/POWER.
  • Lock-free linked structures face the ABA problem (a pointer changes A → B → A between read and CAS) and unsafe memory reclamation while other threads still hold references.
  • False sharing—two unrelated atomics sitting on the same 64-byte L1 cache line—destroys scalability and is fixed with padding (alignas(64) or @Contended).

Good candidates

  • High-frequency counters, metrics, flags, and sequence generators where a single atomic instruction (fetch_add, LongAdder) replaces a mutex.
  • Wait-free/lock-free SPSC or MPMC ring buffers (e.g., LMAX Disruptor, audio/telemetry pipelines) where kernel context switches break microsecond latency budgets.
  • Read-mostly shared metadata swapped atomically via immutable snapshots or RCU (Read-Copy-Update) pointers.

Think twice

  • Multi-object invariants or complex transactional state machines where fine-grained Mutex/RwLock is simpler, easier to prove correct, and fast enough.
  • I/O-bound code paths (database calls, network sockets) where microsecond lock savings are invisible compared to millisecond I/O.
  • Write-heavy shared single variables across 64+ cores without striping or sharding, where cache-line bouncing makes naive CAS slower than a well-partitioned lock.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA 64-core API gateway increments a single global AtomicLong request counter on every packet, causing p99 latency to degrade under cache-line bouncing.

The idea

Lock-free programming replaces mutual exclusion (where one thread sleeps while another holds a lock) with optimistic Read-Modify-Write (RMW) loops backed by CPU hardware:

  • Compare-And-Swap (CAS): Atomically compares a memory word against an expected value and swaps in a new value only if they match, returning whether it succeeded.
  • Progress Guarantees: Wait-free means every thread completes in a bounded number of steps (e.g., fetch_add); Lock-free means at least one thread always makes progress even if others are preempted mid-operation.
  • Coherence & Ordering: Hardware cache coherence (MESI/MOESI) serializes writes to each 64-byte cache line, while memory orderings (relaxed, acquire, release, seq_cst) tell both the compiler and CPU store buffers which reorderings are forbidden.

Concrete walkthrough

Trace a lock-free Treiber stack push(node) and pop() using tagged pointers to prevent ABA:

  1. Prepare: Thread T1 allocates new_node, writes new_node.data = 42, and loads old_head = head.load(acquire) (containing pointer P1 and version tag v=7).
  2. Link Speculatively: T1 sets new_node.next = P1 locally—no other thread can see new_node yet.
  3. Atomic Publish: T1 executes head.compare_exchange_weak(old_head, {new_node, v=8}, release, relaxed).
  4. Contention Handling: If T2 updated head to {P2, v=8} in the meantime, T1's CAS fails, reloads {P2, v=8} into old_head, updates new_node.next = P2, and retries.
  5. Safe Pop: When T2 pops, it reads old_head, enters an epoch/hazard guard so old_head cannot be freed, CAS-swaps head to {old_head.next, v+1}, and retires old_head to the epoch reclaimer.

Lock-free correctness requires pairing tagged CAS and acquire/release fences with safe memory reclamation and cache-line awareness.

Memory orderings & hardware models

Compilers and CPUs aggressively reorder independent loads and stores to hide memory latency (~60–100 ns to DRAM). Memory orderings constrain that reordering:

  • relaxed: Guarantees atomicity and modification order of that single variable only—ideal for telemetry counters.
  • acquire / release: Forms a happens-before edge between a releasing store in Thread A and an acquiring load in Thread B that observes it. On x86-64 (TSO), plain MOV already provides acquire/release; on ARM64, it compiles to LDAR / STLR.
  • seq_cst: Enforces a single total global order across all threads, emitting a heavy MFENCE / LOCK XCHG on x86-64 or DMB ISH on ARM64 for store-load ordering.

Failure modes

  1. Cache-Line Ping-Ponging: 32+ threads performing CAS on one shared head pointer saturate the CPU interconnect with Read-For-Ownership (RFO) traffic, dropping throughput below a mutex. Mitigation: Use bounded backoff, combining funnels, or sharded/SPSC queues.
  2. ARM64 vs. x86-64 Heisenbugs: Missing acquire/release barriers often pass 100% of tests on x86-64 (strong TSO) and corrupt pointers in production on ARM64 Graviton. Mitigation: Test under ThreadSanitizer, Loom (Rust), or GenMC.
  3. ABA Pointer Reuse: Allocators (jemalloc, tcmalloc) aggressively reuse recently freed addresses in thread-local caches, making ABA collisions frequent under load. Mitigation: Pair 128-bit double-width CAS with monotonic version tags or Epoch-Based Reclamation.
  4. Livelock Under compare_exchange_weak: Spurious LL/SC failures on ARM64 or constant peer interference can stall progress if loops lack exponential pause (_mm_pause / yield). Mitigation: Insert CPU_PAUSE hints in retry loops and cap spin counts before backing off.

Production patterns & alternatives

In practice, elite systems avoid general lock-free linked lists in favor of three high-leverage patterns:

  • Single-Producer Single-Consumer (SPSC) Ring Buffers: Require only acquire/release on head and tail indices—no CAS, no ABA, and cache-line-padded indices.
  • Striped / Sharded Counters (LongAdder): Partition updates by thread/core ID into 64-byte padded slots and sum only on read.
  • RCU / Immutable Snapshot Swaps: Writers build a new immutable config/index off-path, swap one atomic pointer with release, and reclaim the old version after a grace period.

Practical checklist

  • Benchmark against a fine-grained mutex or LongAdder first to confirm lock contention is actually the bottleneck.
  • Pad hot atomic fields to 64-byte cache-line boundaries (alignas(64) / @Contended) to prevent false sharing.
  • Specify explicit memory orderings (acquire/release for publication, relaxed for independent counters) and document the happens-before invariant.
  • Solve ABA and safe memory reclamation explicitly (tagged pointers, Hazard Pointers, or EBR) for any dynamic node structure.
  • Verify under ThreadSanitizer / Loom and stress-test on weak-memory-model hardware (ARM64).
03 / Engineering trade-offs

Weighing architectural decisions

Tail Latency vs. Engineering Complexity

Advantage: Eliminates OS scheduler preemption delays, deadlocks, and priority inversion on critical paths.

Drawback: Proving correctness across weak memory models (ARM64) and safe reclamation (EBR/hazard pointers) is orders of magnitude harder than mutexes.

CAS Retry Loops vs. Contended Mutexes

Advantage: Under low-to-moderate contention, uncontended CAS takes 5–15 ns with zero kernel syscalls.

Drawback: Under extreme write contention on one cache line, CAS spin retries burn 100% CPU and starve threads.

Memory Ordering Relaxation vs. Safety

Advantage: `relaxed` and `acquire/release` avoid full store-load fences (`MFENCE`/`DMB ISH`), boosting ARM64 throughput.

Drawback: A single misplaced `relaxed` load can cause data races that only manifest under rare CPU store-buffer reorderings in production.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

The ABA Problem

Thread 1 reads node `A`, gets preempted, Thread 2 pops `A`, pushes `B`, and re-pushes `A` at the same address; Thread 1's CAS succeeds and corrupts the freelist.

What helps: Pack a monotonically increasing version tag with the pointer (128-bit `CMPXCHG16B` / `AtomicStampedReference`) or use Epoch-Based Reclamation.

Use-After-Free During Reclamation

A thread frees a popped node while another concurrent reader is still dereferencing its `next` pointer.

What helps: Defer freeing via Hazard Pointers, Epoch-Based Reclamation (crossbeam-epoch), or garbage-collected runtimes.

False Sharing on 64-Byte Cache Lines

Independent atomic counters for different threads sit in the same 64-byte cache line, forcing constant MESI invalidations across cores.

What helps: Pad hot atomics to cache-line boundaries (`alignas(64)` in C++/Rust, `@Contended` in Java with `-XX:-RestrictContended`).

Weak Memory Model Reordering

Code tested on x86-64 (strong TSO memory model) silently breaks on ARM64 Graviton/Apple Silicon due to relaxed load/store reordering.

What helps: Use explicit `acquire`/`release` pairs for publication, test on ARM64 hardware, and run ThreadSanitizer (TSan) or Loom/CDSChecker.

05 / Practical checklist

Avoid these mistakes

  • Assuming `volatile` in C/C++ provides atomicity or thread synchronization (it only prevents compiler caching for MMIO).
  • Using `compare_exchange_weak` without a retry loop (spurious LL/SC failures on ARM64 will drop updates).
  • Checking two separate atomic variables sequentially and expecting the pair to be mutually consistent.
  • Building a custom lock-free MPMC queue in production instead of using battle-tested libraries (`crossbeam`, `folly::MPMCQueue`, `Disruptor`).
  • Ignoring memory reclamation and leaking nodes or calling `free()` immediately after CAS.
