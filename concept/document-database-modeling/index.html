Document Database
Modeling.

Document database modeling optimizes for read-path locality by co-locating data that is queried together inside self-contained JSON/BSON documents, trading normalized storage for single-round-trip reads.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Model documents around application access patterns rather than abstract entity-relationship tables: embed bounded 1-to-few subdocuments, reference unbounded 1-to-many arrays, and respect document size limits (e.g., MongoDB's 16 MiB BSON cap).

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Treating a document store like MongoDB or DynamoDB as a relational database with $lookup joins everywhere destroys p99 latency and shards poorly. Conversely, blindly embedding unbounded arrays causes 16 MiB document overflows, write amplification, and WiredTiger cache thrashing.

  • Embedding gives single-document atomicity and sequential disk/cache locality, ideal for 1-to-1 and bounded 1-to-few (<100 items) relationships.
  • Referencing stores ObjectId/UUID foreign keys in a separate collection when child counts are unbounded (1-to-millions) or queried independently.
  • The Extended Reference pattern duplicates a small, rarely changing subset of fields (e.g., customerName, customerTier) onto the child document to eliminate cross-collection joins on hot reads.
  • The Bucket Pattern groups time-series or IoT readings into fixed-size documents (e.g., 1 hour or 200 readings per doc) to avoid millions of tiny documents and index bloat.
  • Every index added to a document collection speeds up reads but multiplies write IOPS and RAM footprint; indexes on multikey arrays grow proportionally with array length.

Good candidates

  • Aggregates where parent and child data are read and mutated together in a single atomic transaction (e.g., an Order with its line items and shipping address).
  • Polymorphic catalog or event schemas where different item types (books, laptops, apparel) carry distinct attributes without sparse NULL columns.
  • Read-heavy APIs serving hierarchical JSON payloads directly from a single indexed key lookup without multi-table joins.

Think twice

  • Highly interconnected graph or many-to-many reporting workloads requiring ad-hoc multi-hop joins across arbitrary dimensions.
  • Unbounded time-series or audit-log appends stored as growing arrays inside a single parent document.
  • Strict financial ledgers where multi-entity ACID invariants span dozens of independent aggregates on every write.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA product catalog stored all customer reviews inside an embedded reviews: [] array on the products document. Popular items crossed 15,000 reviews, hitting MongoDB's 16 MiB BSON limit and forcing full-document rewrites on every new review.

The idea

Relational modeling normalizes data to eliminate duplication, assuming joins are cheap and storage is expensive. Document modeling flips that assumption: storage is cheap, network round-trips and distributed joins are expensive, and data that is read together should be stored together.

In engines like MongoDB (WiredTiger) or AWS DynamoDB, a document is a self-contained tree of nested objects and arrays stored contiguously on disk. Designing a document schema starts not from an abstract list of nouns, but from your top 5–10 read and write queries ranked by QPS and latency SLOs.

Concrete walkthrough

Consider an order-management API serving GET /orders/:id at 4,000 QPS:

  1. Identify access patterns: Order detail views always need order status, shipping address, and line items (sku, title, qty, unitPriceAtPurchase). Product catalog descriptions and seller profiles are rarely needed on the order screen.
  2. Choose embedding for 1-to-few: An order has 1–30 line items. Embed items: [...] directly inside the orders document. Because unitPriceAtPurchase is a historical snapshot, it never needs updating if the product's catalog price changes later.
  3. Apply Extended Reference for customer: Embed { customerId, customerName } on the order so the order list page renders without querying customers.
  4. Separate unbounded history: Order audit events or shipment tracking pings go into a separate order_events collection indexed by { orderId: 1, ts: -1 } so the orders document stays small (~2 KB) and cache-friendly.

Decision flow for document modeling: mapping query cardinality to embedding, referencing, extended references, and ESR indexing.

Core design patterns for scale

  • Subset Pattern: When a document contains a large rarely-used array (e.g., 500 historical price changes), keep only the latest 10 in the main document and archive the rest in a *_overflow collection. This keeps the hot working set inside WiredTiger RAM.
  • Computed Pattern: Pre-calculate expensive aggregations (e.g., totalOrders, monthlyRevenue) incrementally via inc‘onwriteratherthanrunning‘inc on write rather than running inc‘onwriteratherthanrunning‘group across millions of documents on every dashboard load.
  • Schema Versioning Pattern: Include schemaVersion: 2 on every document so application readers can lazily upgrade v1 documents in-memory without a blocking migration across 500 million rows.

Failure modes

  1. 16 MiB BSON ceiling crash: Uncapped $push operations silently grow documents until production writes suddenly fail with DocumentTooLarge.
  2. Index memory starvation: Creating 8+ secondary or multikey array indexes causes the index working set to exceed RAM, turning every write into random disk I/O.
  3. Scatter-gather shard queries: Querying a sharded collection without the shard key in the predicate forces mongos to fan out to every shard, tying tail latency to the slowest shard.
  4. Write amplification on document relocation: In storage engines or configurations where document growth forces page splits, frequent array appends fragment disk pages and spike compaction CPU.

Indexing & query plan verification

Every critical query should be verified with .explain("executionStats"):

  • Check that stage is IXSCAN (never COLLSCAN) and totalDocsExamined is close to nReturned (targeting a 1:1 ratio).
  • Follow the ESR rule: place exact-match fields (status: "PAID") first, sort fields (createdAt: -1) second, and range filters (amount: { $gte: 50 }) last.
  • Use partial indexes (partialFilterExpression: { status: "PENDING" }) when 95% of documents are archived/completed, shrinking index size by up to 20x.

Practical checklist

  • Document the top 5 read/write queries and their p99 latency targets before writing any schema.
  • Embed only bounded (<100 items) or immutable snapshot data; reference unbounded children.
  • Enforce $jsonSchema validation and a schemaVersion integer on every production collection.
  • Design compound indexes following Equality -> Sort -> Range (ESR) and verify nReturned / totalDocsExamined >= 0.5 via explain().
  • Add partial or TTL indexes (expireAfterSeconds) for ephemeral sessions, OTPs, and audit logs.
03 / Engineering trade-offs

Weighing architectural decisions

Embedding vs Referencing

Advantage: Embedding delivers single-round-trip reads and single-document ACID atomicity without distributed locks.

Drawback: Updating a duplicated embedded field (e.g., a renamed category) requires fan-out background updates across every referencing document.

Schema flexibility vs runtime validation

Advantage: Zero-downtime rolling deploys can introduce optional fields without `ALTER TABLE` locks.

Drawback: Unvalidated writes accumulate silent type drift (`"42"` string vs `42` int32) that breaks aggregations unless enforced via `$jsonSchema`.

Compound indexes vs multikey array indexes

Advantage: A single ESR-ordered (Equality, Sort, Range) compound index covers complex queries from memory.

Drawback: Indexing large arrays generates one index entry per element, causing rapid index bloat and slower inserts.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Unbounded array growth & 16 MiB overflow

Pushing comments, logs, or followers into an embedded array causes documents to outgrow WiredTiger pages, fragment storage, and eventually throw `BSONObj size exceeds 16777216 bytes`.

What helps: Cap embedded arrays using `$slice` (Outlier/Top-N pattern) or move unbounded children to their own collection with a compound `{ parentId: 1, createdAt: -1 }` index.

Working-set eviction from oversized documents

Fetching a 2 MB document just to read a 200-byte status field pulls the entire 2 MB BSON blob into WiredTiger's RAM cache, evicting hot documents.

What helps: Apply the Subset Pattern: split heavy blobs (descriptions, full histories) into a detail collection and keep hot summary fields in the primary collection.

N+1 `$lookup` join storms

Running `$lookup` across unindexed foreign keys or sharded collections triggers scatter-gather queries across all shards.

What helps: Pre-embed immutable snapshots (e.g., `unitPrice` at order time) or maintain an Extended Reference synced via Change Streams.

Hot shard key contention

Choosing a monotonically increasing shard key like `createdAt` or `ObjectId` routes 100% of writes to a single shard.

What helps: Use a high-cardinality, evenly distributed compound shard key (e.g., `{ tenantId: 1, entityId: 1 }` or hashed key) aligned with primary query predicates.

05 / Practical checklist

Avoid these mistakes

  • Translating a 3NF SQL ERD 1:1 into separate MongoDB collections and stitching them back together with `$lookup`.
  • Indexing fields in the wrong order—violating the **ESR rule** (Equality, Sort, Range)—causing in-memory sorts that hit the 100 MB sort limit.
  • Embedding mutable shared entities (like full `User` profiles) inside millions of `Message` documents without a fan-out update strategy.
  • Omitting `$jsonSchema` collection validators, allowing malformed client payloads to corrupt downstream analytics.
  • Using multi-document ACID transactions as a crutch for every write instead of designing single-document atomic boundaries.
