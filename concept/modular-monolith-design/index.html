THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Enforce module boundaries at compile/test time (ArchUnit, Spring Modulith, import-linter) and isolate database schemas so any module can be extracted into a microservice later in days, not months.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Teams often jump straight from a tangled 'Big Ball of Mud' monolith to microservices, trading code coupling for distributed systems complexity. A modular monolith delivers strict domain isolation, single-transaction ACID guarantees, and sub-microsecond in-process calls while keeping operations down to one CI/CD pipeline.

  • Organize packages by business capability/vertical slice (orders, inventory, billing), never by technical layer (controllers, services, repositories).
  • Expose a narrow public module API (facade + DTOs + domain events) and keep entities, repositories, and helpers package-private/internal.
  • Enforce zero illegal cross-module imports in CI using fitness functions like ArchUnit (Java), Spring Modulith, or import-linter (Python).
  • Give each module its own logical PostgreSQL schema (orders.*, inventory.*) and forbid cross-schema foreign keys or SQL joins.
  • Communicate state changes between modules via an in-process event bus (backed by a transactional outbox if durability/retries are needed).

Good candidates

  • Engineering organizations of 5–60 developers building a rich domain where boundaries are still evolving.
  • Core workflows benefit from single-database ACID transactions and low-latency (<1 ms) cross-module reads without network serialization.
  • You want an evolutionary 'microservices-ready' architecture without paying the Kubernetes, Istio, and distributed debugging tax today.

Think twice

  • Modules require genuinely incompatible runtimes or hardware (e.g., Python/PyTorch GPU inference alongside a Rust high-frequency proxy).
  • Independent scaling or strict compliance isolation (e.g., PCI-DSS cardholder vault) requires physical process and network separation.
  • Teams exceed ~80–100 engineers and hit hard Git merge-queue or single-binary build-time limits even with modular builds.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioShopify's core Rails monolith grew to millions of lines with circular dependencies across billing, shipping, and storefront logic.

The idea

A modular monolith combines the logical decoupling of microservices with the physical simplicity of a single deployable artifact. Every domain capability lives in a self-contained module with an explicit public facade, private internal implementation, and its own logical database schema. Because all modules run in the same process, cross-module calls happen in nanoseconds—yet automated architecture tests enforce strict boundaries so that extracting any module into a standalone microservice later requires swapping an in-process interface for an RPC/event adapter.

Concrete walkthrough

Consider structuring an e-commerce backend using Spring Modulith (Java) or import-linter (Python) over PostgreSQL:

  1. Vertical Package Layout: Top-level packages are com.app.orders, com.app.inventory, and com.app.billing. Inside orders, only OrdersFacade and OrderPlacedEvent are public; OrderEntity and OrderRepository live in orders.internal.
  2. Compile/Test Boundary Gate: An ArchUnit test runs in CI (ApplicationModules.of(App.class).verify()). If billing imports orders.internal.OrderEntity, the build fails immediately.
  3. Logical Schema Isolation: PostgreSQL hosts orders.orders, inventory.stock, and billing.invoices. Foreign keys across schemas are forbidden; billing stores order_id as an opaque UUID.
  4. Post-Commit Async Events: When OrdersFacade.placeOrder() commits, Spring Modulith persists OrderPlacedEvent in orders.event_publication in the same transaction and dispatches it asynchronously to inventory and billing.

Strict package facades, CI fitness functions, and isolated DB schemas keep modules decoupled inside a single deployable binary.

Automated architectural fitness functions

Boundaries without enforcement decay within weeks. Bake three automated checks into every PR:

  • Dependency Acyclicity: import-linter (Python) or ArchUnit (Java) verifies zero cycles between top-level domain modules in <5 seconds.
  • Internal Encapsulation: Only classes/functions in the module root or explicit api/ package may be imported externally; internal/ packages are off-limits.
  • Schema Linting: A migration linter (e.g., Squawk or custom SQL check) rejects REFERENCES foreign keys or JOINs crossing schema namespaces.

Failure modes

Even well-structured modular monoliths can hit operational ceilings:

  • Shared Connection Pool Exhaustion: A slow analytics query in the Reporting module consumes all 50 HikariCP/SQLAlchemy connections, stalling Checkout.
  • Noisy Neighbor CPU/Memory: Unbounded in-memory caching or image processing in one module triggers an OOMKill for the entire binary.
  • Eventual Consistency Without Durability: Using an in-memory-only event bus (like plain EventEmitter) drops events if the pod restarts mid-dispatch.

Production hardening

Make the modular monolith resilient and extraction-ready:

  • Per-Module Bulkheads: Separate thread pools or async worker queues for heavy background modules so interactive HTTP handlers are never starved.
  • Durable Outbox Table: Persist in-process domain events to an event_publication table so failed listeners retry automatically on restart.
  • Extraction Trigger: Extract a module to a microservice only when it hits a concrete scaling, compliance, or team-autonomy wall—not on speculation.

Practical checklist

  • Structure top-level packages by business capability, never by technical layer.
  • Enforce module encapsulation and acyclicity in CI with ArchUnit, Packwerk, or import-linter.
  • Isolate tables into per-module database schemas with zero cross-schema foreign keys.
  • Pass immutable DTOs/events across module facades; never expose ORM entities.
  • Back cross-module async events with a durable transactional outbox table.
03 / Engineering trade-offs

Weighing architectural decisions

In-Process Call Speed vs. Blast-Radius Isolation

Advantage: Cross-module calls execute in ~50 nanoseconds with zero JSON/Protobuf serialization or network failures.

Drawback: An unhandled OOM or infinite loop in one module can crash the entire process and take down all co-located modules.

Single ACID Transaction vs. Future Extraction Friction

Advantage: Modules sharing one database can participate in a single ACID commit when needed.

Drawback: If you rely heavily on cross-module ACID transactions, extracting a module later still requires rewriting them into Sagas.

Unified Deployment vs. Independent Scaling

Advantage: One CI pipeline, one Docker image, and atomic rollbacks eliminate distributed version skew.

Drawback: You cannot scale CPU/memory for one hot module independently without scaling the whole binary.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Boundary Erosion (Accidental Spaghetti)

Under deadline pressure, a developer imports another module's internal ORM entity directly, re-creating a Big Ball of Mud.

What helps: Fail the CI build automatically using ArchUnit (`@ApplicationModuleTest`), Packwerk, or `import-linter` rules.

Database-Level Coupling

Code boundaries look clean, but Module A runs SQL `JOIN`s against Module B's tables, locking both schemas together.

What helps: Separate modules into distinct PostgreSQL schemas with least-privilege DB roles or enforce schema-prefix linting.

Synchronous Event-Bus Cascades

Publishing an in-process event triggers 5 synchronous listeners inside the HTTP request thread, spiking latency and causing deadlocks.

What helps: Run cross-module event listeners asynchronously after transaction commit (`@TransactionalEventListener` + outbox table).

Shared 'Common/Core' Dumping Ground

A `shared-kernel` module accumulates 40% of the domain entities, coupling every module to it.

What helps: Restrict shared code strictly to primitives, clock/ID utilities, and published event contracts; duplicate small DTOs rather than sharing entities.

05 / Practical checklist

Avoid these mistakes

  • Grouping code into `models/`, `services/`, and `controllers/` at the top level instead of domain module folders.
  • Returning JPA/SQLAlchemy ORM entities from a module's public facade instead of immutable DTOs.
  • Allowing circular dependencies (`Orders -> Inventory -> Orders`) instead of breaking cycles with domain events.
  • Relying on developer discipline alone rather than automated CI architecture tests.
  • Using the same database connection pool without per-module query timeouts, letting one bad query starve all modules.
