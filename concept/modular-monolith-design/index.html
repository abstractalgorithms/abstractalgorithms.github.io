Full walkthrough · 7 stages
01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is a Modular Monolith.

A modular monolith packages multiple cohesive vertical business modules (orders, inventory, billing) inside one deployable process—never sliced by technical layer (controllers, services, repositories).

Each module exposes a narrow public API (facade + DTOs + domain events) while keeping its entities, repositories, and database tables strictly private.

Enforced Module Boundary

Public Facade + Async Domain Events Between Vertical Modules

Orders never imports Inventory's internal ORM entities or runs SQL JOINs against inventory tables.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why teams fall into Big Balls of Mud—or premature microservices.

Jumping straight from a tangled monolith to microservices trades code coupling for distributed systems complexity (network latency, Sagas, service mesh).

Yet modular monoliths fail if boundaries are merely cultural: Boundary Erosion (a developer imports another module's internal entity under deadline pressure) and Database-Level Coupling (cross-module SQL JOINs) silently turn the codebase back into a Big Ball of Mud.

Automated CI Fitness Functions

Fail the build automatically on illegal cross-module imports using ArchUnit (Java), Spring Modulith, Packwerk (Ruby), or import-linter (Python).

Separate PostgreSQL Schemas

Give each module its own DB schema (orders.*, billing.*) with least-privilege roles or schema-prefix linting.

03
STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Modular Monoliths excel (and when to extract).

Start with a modular monolith for most products; extract only when hardware, scale, or compliance forces process separation.

ChoiceWhat it buysWhat it costs
Good Candidate: 5–60 Developers & Evolving Domains~50 ns in-process calls, single-DB ACID transactions, and one CI/CD pipeline while boundaries stabilize.Shared runtime blast radius (one OOM kills the process).
Avoid: Incompatible Runtimes or Strict IsolationExtract Python/PyTorch GPU inference, Rust proxies, or PCI-DSS cardholder vaults into separate services.Co-locating incompatible runtimes or compliance scopes in one process creates operational risk.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Enforcing Module Boundaries with ArchUnit / Spring Modulith.

Encode module encapsulation as a unit test in CI so illegal internal imports fail PRs immediately.

// ArchUnit / Spring Modulith CI fitness function
@ArchTest
static final ArchRule modules_must_not_access_internals =
    SlicesRuleDefinition.slices()
        .matching("com.acme.app.(*)..")
        .should().notDependOnEachOther()
        .ignoreDependency(resideInAPackage("..api.."), alwaysTrue());

Alternatives: Layered Monolith vs. Modular Monolith vs. Microservices.

Compare coupling, transaction support, and deployment independence.

06
STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

In-Process Eventual Consistency for Zero-Friction Extraction.

If Module A relies heavily on synchronous cross-module ACID transactions with Module B, extracting Module B later still requires rewriting those writes into Sagas. Using in-process domain events + module-private tables today makes extracting a module into a standalone service take days.

Evolution Path

Modular Monolith -> Async Module Events -> Extracted Service

Decoupling via private schemas and async events inside the monolith is the cheapest path to future microservices.
