Actor Model
Concurrency.

The Actor Model structures concurrent systems as isolated, share-nothing entities (actors) that encapsulate private state and communicate exclusively via asynchronous message passing into per-actor mailboxes (e.g., Erlang/OTP GenServer, Akka/Pekko, Microsoft Orleans).

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Actor Model Concurrency.

Why this matters: The mechanism: understand how Actor Model Concurrency works from first principles.

Proposed by Carl Hewitt in 1973 and battle-tested in Ericsson's AXD301 ATM switches (99.9999999% uptime), the Actor Model treats the actor—not the thread or lock—as the fundamental unit of computation. An actor combines private state, a behavior (message handler), and a mailbox (FIFO queue).

On receiving a message, an actor can do three primitives: send finite messages to known actors, spawn new actors, or designate the behavior for the next message. Because no actor can inspect another actor's memory and each processes one message at a time, torn reads and lock-order deadlocks disappear by construction.

Actor Turn Lifecycle

Single-Threaded Mailbox Turn & Supervision State Machine

An actor executes at most one message turn at a time; failures isolate to the actor and trigger its supervisor's recovery strategy.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Actors (and why shared-memory locks fail at scale).

Why this matters: The problem: see what breaks without Actors under real concurrency or scale.

Shared-memory multithreading forces developers to reason about lock ordering, memory barriers, and cache-line false sharing across every call site.

Actors invert this: state is partitioned by entity, and location transparency (pid ! msg or actorRef.tell(msg)) uses the exact same syntax whether the target actor lives in the same OS process or on another cluster node.

Order-Matching Trace

Asynchronous Tell Flow vs. Synchronous Ask Deadlock

Asynchronous tell with correlation IDs keeps mailboxes non-blocking; synchronous mutual ask deadlocks both actors.

Engineering Decision Framework
Problem
How to implement Actor Model Concurrency without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
To guarantee worst-case bounds under adversarial inputs, by processing one message at a time per actor and forbidding shared mutable memory, you eliminate mutexes and deadlocks—trading synchronous call convenience for mailbox backpressure and supervision trees.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Preemptive vs. Cooperative Scheduling

Erlang BEAM uses reduction-based preemptive scheduling (~4,000 reductions/slice), preventing starvation; JVM/CLR frameworks (Pekko, Orleans) are cooperative, so blocking I/O inside onReceive starves sibling actors.

Supervision Trees

Parents never share memory with children; they observe exit signals and apply One-For-One, All-For-One, or Escalate policies within max_restarts budgets.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Actor Mailboxes, Persistence, and Backpressure are managed.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Operating actors in production requires guarding against unbounded mailboxes, blocking I/O, and split-brain clusters:

  1. Bounded Mailboxes & Backpressure: Configure bounded mailboxes and bridge Kafka/TCP ingress with demand-driven streams (GenStage, Pekko Streams).
  2. Isolated Blocking Dispatchers: Offload synchronous JDBC/HTTP calls onto dedicated I/O thread pools.
  3. Event Sourcing + Snapshots: Persist state transitions to an append-only journal.
  4. Split-Brain Resolver (SBR): Enable a quorum-based SBR before deploying Cluster Sharding.

# Bounded GenServer actor with explicit state & supervision (Elixir / BEAM)
defmodule OrderBookActor do
  use GenServer

  def start_link(symbol), do: GenServer.start_link(__MODULE__, symbol, name: via(symbol))
  def place_order(symbol, order), do: GenServer.cast(via(symbol), {:place, order}) # async tell

  @impl true
  def init(symbol), do: {:ok, %{symbol: symbol, bids: [], asks: [], seq: 0}}

  @impl true
  def handle_cast({:place, order}, state) do
    next_state = match_and_update(state, order)
    {:noreply, %{next_state | seq: state.seq + 1}}
  end
end

Cluster Sharding Topology

3-Node Actor Cluster with Quorum Split-Brain Resolver

1.Consistent Entity Ownership: Shard Coordinator ensures each entityId activates on at most one node at a time.

2.Event-Sourced Recovery: On node loss, surviving nodes rehydrate the actor from its latest snapshot + journal tail.

3.Split-Brain Safety: Quorum SBR downs minority partitions so two nodes never host duplicate actors for the same key.

Cluster sharding + quorum SBR preserves single-writer actor invariants across node failures and partitions.
