THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Helm's value lies in atomic, revision-tracked releases (`--atomic --wait`) and parameterized reuse—treat rendered manifests as immutable build outputs and never mix manual `kubectl edit` into Helm-managed resources.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Deploying a microservice to Kubernetes touches 6–15 YAML objects (Deployment, Service, Ingress, HPA, ServiceAccount, ConfigMap, PodDisruptionBudget). Copy-pasting YAML across dev, staging, and prod drifts immediately. Helm renders Go templates against layered values.yaml overrides, applies them in dependency order, waits for readiness probes, and stores compressed release snapshots (sh.helm.release.v1..v) so a broken deploy can roll back in one command.

  • Chart.yaml separates the chart's own SemVer version (template changes) from appVersion (the container image tag deployed).
  • Values merge left-to-right with increasing precedence: chart values.yaml < parent chart values < -f env.yaml (later files win) < --set / --set-string flags.
  • Helm v3 stores each release revision as a gzipped, base64-encoded JSON blob inside a Kubernetes Secret (sh.helm.release.v1..v) in the release namespace.
  • Lifecycle hooks (pre-install, post-upgrade, pre-rollback) run Kubernetes Jobs or Pods outside normal release ownership unless given helm.sh/hook-delete-policy.
  • Helm v3.8+ supports OCI registries (oci://ghcr.io/org/chart) natively, unifying container image and chart signing/distribution via Cosign and SBOMs.

Good candidates

  • Packaging third-party infrastructure (ingress-nginx, Prometheus, cert-manager, Kafka operators) distributed as OCI or HTTP Helm repositories.
  • Standardizing internal microservice deployments across dozens of teams via a shared library or golden base chart.
  • Needing one-command atomic upgrades (helm upgrade --install --atomic) with pre/post-upgrade hooks (e.g., DB schema migrations) and instant revision rollback.

Think twice

  • Simple, single-team apps with 2–3 static manifests where plain Kustomize overlays avoid Go-template string-escaping headaches.
  • GitOps pipelines where Argo CD or Flux must see every rendered Kubernetes resource in Git before applying—use helm template in CI rather than running helm upgrade imperatively.
  • Managing stateful multi-step day-2 operations (failover, backup/restore, shard rebalancing) better handled by a custom Kubernetes Operator.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA payments API rolls out v2.4.0 requiring an additive PostgreSQL migration before new pods start serving traffic.

The idea

Helm is a package manager and release state machine for Kubernetes. A chart is a directory (or .tgz / OCI artifact) containing Chart.yaml metadata, values.yaml defaults, optional values.schema.json, and Go text/template files under templates/.

When you run helm upgrade --install, Helm does not just pipe YAML to kubectl apply. It merges values, renders templates deterministically, diffs the desired manifests against the previous release revision stored in-cluster, computes a 3-way strategic merge patch, executes ordered lifecycle hooks, waits for workload readiness, and writes a new immutable revision record (v1, v2, v3...).

Concrete walkthrough

Trace helm upgrade --install orders oci://ghcr.io/acme/orders --version 1.8.2 -f prod.yaml --set-string image.tag=a3f9c12 --atomic --wait --timeout 5m:

  1. Pull & Validate: Helm pulls the OCI chart artifact, verifies its values.schema.json against the merged values (values.yaml + prod.yaml + --set-string), and renders templates/*.yaml locally.
  2. Lock Revision (pending-upgrade): Helm reads sh.helm.release.v1.orders.v7 from the target namespace, computes the diff, and writes v8 with status: pending-upgrade.
  3. Pre-Upgrade Hooks: Any resource tagged helm.sh/hook: pre-upgrade (sorted by helm.sh/hook-weight, e.g., -5 before 0) is created and watched until completion.
  4. Apply & Wait: Helm applies updated ConfigMap, Service, and Deployment manifests. With --wait, it polls the Kubernetes API until all new Deployment pods pass readinessProbe.
  5. Commit or Atomic Rollback: If all pods become Ready within 5m, Helm updates v8 to status: deployed and marks v7 as superseded. If a pod CrashLoopBackOffs past 5m, --atomic automatically triggers a rollback to v7 and exits non-zero in CI.

Helm tracks every release revision in-cluster as a compressed Secret, enabling deterministic 3-way diffs and automatic rollback on failed readiness checks.

Values precedence, hooks & checksum annotations

A classic Kubernetes pitfall occurs when you update a ConfigMap, run helm upgrade, and existing pods keep running with stale configuration because the Deployment pod spec didn't change. Helm solves this cleanly via a template checksum annotation:

spec:
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}

Whenever configmap.yaml renders differently, the checksum/config SHA-256 changes, triggering a rolling restart of the Deployment. Similarly, helm.sh/resource-policy: keep protects stateful resources (like PersistentVolumeClaims or Namespaces) from deletion during helm uninstall.

Failure modes

  • 1 MiB Secret overflow: Storing large files or 50+ historical revisions in sh.helm.release.v1.* hits etcd's 1 MiB object limit. Cap --history-max 10 and keep large payloads in object storage.
  • Helm + Argo CD hook impedance mismatch: If you use Argo CD to deploy Helm charts, Argo runs helm template and translates helm.sh/hook into argocd.argoproj.io/hook, but pre-rollback hooks are not executed by Argo CD.
  • Race conditions on CRDs: Helm's crds/ directory installs CRDs once on helm install and never upgrades or deletes them on helm upgrade to avoid wiping custom resources. Manage CRD upgrades in a dedicated chart or pre-sync step.
  • Non-deterministic lookup or randAlphaNum functions: Using randAlphaNum inside a Secret template regenerates a new password on every helm upgrade, breaking running apps. Use lookup to preserve existing values or manage secrets externally.

Chart testing, OCI distribution & security

Treat charts like application code. Run helm lint --strict, helm template piped into kubeconform (verifying against the target Kubernetes API version, e.g., 1.30.0), and helm unittest for template logic before publishing.

Publish charts as OCI artifacts (helm package -> helm push app-1.8.2.tgz oci://ghcr.io/acme/charts), sign them with cosign sign, and pin exact chart versions in production pipelines rather than floating ranges (^1.8.0).

Practical checklist

  • Add values.schema.json to catch missing required keys or wrong types at render time.
  • Always deploy with --atomic --wait --timeout --history-max 10 in imperative CI.
  • Add checksum/config and checksum/secret annotations to pod templates so config edits trigger rolling restarts.
  • Omit replicas from Deployment templates whenever an HorizontalPodAutoscaler is active.
  • Set helm.sh/hook-delete-policy: before-hook-creation,hook-succeeded on all hook Jobs.
  • Validate rendered YAML with helm lint and kubeconform in CI, and use helm diff before production upgrades.
03 / Engineering trade-offs

Weighing architectural decisions

Go templates vs. Kustomize overlays

Advantage: Helm supports loops, conditionals, helper partials (`_helpers.tpl`), and typed schema validation (`values.schema.json`).

Drawback: Whitespace-sensitive YAML inside Go templates (`{{- ... | nindent 8 }}`) is hard to read and debug compared to Kustomize's strategic-merge patches.

Imperative `helm upgrade` vs. GitOps (`helm template`)

Advantage: `helm upgrade --atomic` handles hooks, readiness waits, and automatic rollback directly from CI.

Drawback: CI pipelines need cluster kubeconfig access, and drift from manual `kubectl` edits goes unnoticed unless a GitOps controller reconciles continuously.

Umbrella charts vs. independent releases

Advantage: One command stands up an entire environment with shared global values.

Drawback: Couples failure domains: one broken subchart blocks the whole release and risks hitting Kubernetes' 1 MiB etcd Secret size limit.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Stuck `pending-upgrade` release lock

A CI runner is killed mid-deploy, leaving the latest Secret in `status: pending-upgrade`. Every subsequent `helm upgrade` fails with `another operation (install/upgrade/rollback) is in progress`.

What helps: Run `helm rollback <release> <last-deployed-rev>` (or `helm history` to verify the last `deployed` revision) rather than deleting the Secret manually.

Implicit type coercion with `--set`

Passing `--set image.tag=123456` or `--set app.id=1e5` makes Helm parse the value as a float64 (`1.23456e+05`), breaking container image pulls or pod env vars.

What helps: Always use `--set-string`, quote values in `-f values.yaml`, and enforce types with `values.schema.json`.

Orphaned hook Jobs blocking re-deploys

A `pre-upgrade` Job without `hook-delete-policy: before-hook-creation` already exists on the second upgrade, failing with `jobs.batch "migrate" already exists`.

What helps: Include `"helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded` on all hook resources and give Jobs immutable or revision-suffixed names (`{{ .Release.Revision }}`).

Manual `kubectl edit` drift overwritten silently

An on-call engineer patches `replicas: 10` via `kubectl scale`, and the next `helm upgrade` resets `replicas` back to `3` from `values.yaml`.

What helps: Run `helm diff upgrade` in CI before applying, omit `replicas` from the Deployment template when an HPA manages scaling, and restrict production `kubectl` write RBAC.

05 / Practical checklist

Avoid these mistakes

  • Leaving `--history-max` at `10` or unlimited without checking Secret count, or conversely setting it to `0` (infinite) and bloating etcd.
  • Hardcoding `replicas` inside `Deployment` when a `HorizontalPodAutoscaler` is enabled, causing Helm upgrades to reset autoscaled replica counts.
  • Using `helm upgrade --force` routinely—`--force` deletes and recreates resources (causing downtime on `Service` or `PVC` immutability errors) instead of patching.
  • Modifying `values.yaml` without running `helm lint` and `helm template` in CI, letting broken indentation reach the cluster.
  • Storing plaintext database passwords in `values.yaml` inside Git instead of referencing External Secrets / Sealed Secrets.
