B-Trees vs LSM-Trees
Storage Engines.

B-Trees update fixed-size disk pages (4–16 KiB) in place for fast, predictable point and range reads, whereas LSM-Trees buffer writes sequentially in memory (MemTable + WAL) and merge immutable sorted runs (SSTables) in the background for orders-of-magnitude higher write throughput.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

B-Trees optimize read latency and predictability at the cost of random-write amplification; LSM-Trees optimize sequential write throughput and compression at the cost of background compaction and read/tail-latency variance.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Every transactional database and key-value store sits on either a B-Tree (PostgreSQL, MySQL InnoDB, SQLite) or an LSM-Tree (RocksDB, Cassandra, CockroachDB Pebble, ScyllaDB). Choosing the wrong storage engine under write-heavy ingestion or strict p99 read SLAs causes either IOPS saturation from page splits or CPU/disk stalls from compaction debt.

  • B-Trees (typically B+Trees with 8 KiB pages in PostgreSQL or 16 KiB pages in InnoDB) achieve tree height 3–4 for 1B+ rows, requiring at most 1–2 disk reads when internal nodes are cached in RAM.
  • LSM-Trees append writes to a sequential WAL and an in-memory skiplist (MemTable), flushing immutable SSTables (typically 64 MiB) to disk—turning random writes into sequential I/O.
  • Bloom filters (typically 10 bits/key, ~1% false positive rate) let LSM point reads skip SSTables that do not contain the target key, avoiding O(levels) disk seeks.
  • Leveled compaction (RocksDB default, 10x size ratio per level) minimizes space amplification (~1.1x) at higher write amplification (~10x–15x), while Size-Tiered compaction minimizes write amplification (~4x–6x) at higher space amplification (~2x).
  • Deletes in LSM-Trees write tombstone markers rather than reclaiming space immediately; space and scan speed recover only when compaction merges tombstones down to the bottommost level.

Good candidates

  • Choose a B-Tree when workloads are read-heavy (>70% reads), require tight p99 point-lookup and range-scan latency, and update existing keys frequently in place.
  • Choose an LSM-Tree when workloads are write-heavy (IoT telemetry, time-series, event logs, append-heavy KV) where sequential disk/NVMe writes and high Zstd/LZ4 block compression matter.
  • Choose an LSM-Tree when dataset size exceeds RAM and you want lower space amplification (~1.1x with leveled compaction vs ~1.5x–2x in fragmented B-Trees).

Think twice

  • Avoid B-Trees for high-ingest random-key writes (e.g., UUIDv4 primary keys at 100k+ writes/sec), which cause constant buffer-pool dirty-page evictions and 10x–30x write amplification.
  • Avoid LSM-Trees when strict sub-millisecond p99.9 read latency is required without compaction-throttling or NVMe headroom, as L0->L1 compaction spikes can stall foreground reads.
  • Avoid LSM-Trees with heavy range scans over frequently deleted keys unless tombstones are aggressively compacted or range-delete filters are tuned.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA fintech ledger inserts 25,000 rows/sec into a 2 TB PostgreSQL table indexed by random UUIDv4. InnoDB/PostgreSQL B-Tree leaf pages (8 KiB) constantly split at random offsets, evicting the 64 GB buffer pool and saturating EBS gp3 IOPS.

The idea

Storage engines bridge volatile RAM and persistent block storage (NVMe/SSD/EBS). A B-Tree (B+Tree) organizes data in mutable, fixed-size pages (8–16 KiB) linked in sorted order; every update locates the target leaf page and mutates it in place (logging to a WAL for crash safety). A Log-Structured Merge-Tree (LSM-Tree) never mutates on-disk blocks: it buffers writes in an in-memory sorted structure (MemTable) backed by an append-only WAL, flushes sorted immutable files (SSTables) sequentially, and merges them asynchronously in the background.

Concrete walkthrough

Compare how a 200-byte PUT(user:4812, payload) travels through PostgreSQL (B+Tree) vs. RocksDB (LSM-Tree):

  • B+Tree Path: PostgreSQL appends the change to its WAL, traverses 3–4 internal index pages in the shared buffer pool to find the 8 KiB leaf page containing user:4812, and modifies it in RAM. If the buffer pool is full, a dirty 8 KiB page (plus a full-page image in WAL after a checkpoint) is flushed at a random disk offset—writing ~16 KiB for a 200-byte change.
  • LSM-Tree Path: RocksDB appends 200 bytes to its sequential WAL and inserts the key into the active MemTable (skiplist) in ~2 microseconds. Once the MemTable reaches 64 MiB, it freezes and flushes sequentially to Level 0 (L0) as an immutable SSTable with a 10-bit/key Bloom filter. Background threads later merge overlapping L0 files into non-overlapping sorted runs in L1 (256 MiB), L2 (2.56 GiB), and so on.

Architectural contrast: LSM-Trees decouple foreground writes from background compaction using immutable SSTables, while B+Trees mutate fixed-size pages in place.

The RUM conjecture and amplification math

The RUM Conjecture (Read, Update/Write, Memory/Space) states that optimizing any two overheads worsens the third:

  • Write Amplification (WAWAWA): Physical bytes written to SSD divided by logical bytes written by the app. B-Trees suffer high WAWAWA (10x–30x+) on random small updates because an entire 16 KiB page (plus WAL) is written for 100 bytes. Leveled LSMs have WA≈10–15×WA \approx 10\text{–}15\timesWA≈10–15× across 4–5 levels; Size-Tiered LSMs drop WAWAWA to 4–6×4\text{–}6\times4–6×.
  • Read Amplification (RARARA): Disk pages read per lookup. B-Trees have RA≈1RA \approx 1RA≈1 (only leaf page misses RAM). LSMs have higher worst-case RARARA across L0 + L1..Ln, mitigated by Bloom filters.
  • Space Amplification (SASASA): On-disk size divided by logical dataset size. B-Trees average SA≈1.3–2.0×SA \approx 1.3\text{–}2.0\timesSA≈1.3–2.0× from 50–70% page fill factors; Leveled LSMs achieve SA≈1.1×SA \approx 1.1\timesSA≈1.1×.

Failure modes

  1. L0 Compaction Stall: If L0 exceeds level0_stop_writes_trigger (default 36 in RocksDB), all foreground writes block completely, causing cascading upstream timeouts.
  2. B-Tree Checkpoint I/O Storm: Flushing thousands of dirty buffer-pool pages during a checkpoint saturates NVMe queues and spikes read p99 unless checkpoint_completion_target (e.g., 0.9 in PostgreSQL) paces writes.
  3. Range Scan Tombstone Storms: Point lookups use Bloom filters, but range scans cannot use standard key Bloom filters (unless prefix Bloom filters are configured) and must merge-sort every level plus tombstones.

Hybrid engines and modern NVMe tuning

Modern engines blur the boundary. Bε-Trees (used in TokuDB/PerconaFT) attach small write buffers to internal B-Tree nodes, gaining LSM-like batching with B-Tree range speed. WiscKey / Titan (in TiKV/RocksDB) separates large values (>1 KiB) into an append-only vLog while keeping only small keys and pointers in the LSM-Tree, cutting compaction write amplification by 5x–10x on large-value workloads.

Practical checklist

  • Measure read/write ratio, key distribution (random vs monotonic), and average value size before picking an engine.
  • For B-Trees, use monotonic keys (UUIDv7/ULID) and tune buffer pool size to hold all internal index nodes plus hot leaves.
  • For LSM-Trees, enable 10-bit/key Bloom filters (bloom_locality), O_DIRECT for compaction, and Zstd on bottommost levels.
  • Monitor L0 file count, compaction pending bytes, and tombstone-to-live-key ratios in production.
  • Keep LSM disk utilization below 75% (or <50% for Size-Tiered) to prevent out-of-space compaction deadlocks.
03 / Engineering trade-offs

Weighing architectural decisions

Write Amplification vs. Read Amplification

Advantage: LSM-Trees convert random mutations into sequential flushes, sustaining 5x–10x higher write throughput on SSDs/NVMe.

Drawback: Reads may probe MemTable, L0 overlapping SSTables, and multiple lower levels if Bloom filters miss or range scans span levels.

Space Amplification & Compression

Advantage: Immutable SSTables pack densely with zero internal page fragmentation and compress 2x–4x better than B-Tree pages.

Drawback: Size-tiered compaction requires up to 50% free disk headroom during major merges; B-Trees overwrite in place with bounded disk usage.

Latency Predictability

Advantage: B-Tree read latency is tightly bounded by tree height and buffer-pool hit ratio without background merge storms.

Drawback: LSM-Trees suffer tail-latency jitter when L0 file count hits `level0_stop_writes_trigger` (e.g., 36 files in RocksDB), stalling writers.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

LSM Write Stall from Compaction Debt

Ingestion outpaces background compaction threads, causing L0 SSTables to pile up past `level0_slowdown_writes_trigger` (20) and `stop_writes_trigger` (36), freezing client writes.

What helps: Increase `max_background_jobs`, enable rate-limited compaction I/O, and alert on `rocksdb.num-files-at-level0` before hitting the stop threshold.

B-Tree Page-Split & Fragmentation Bloat

Random inserts and deletes leave B-Tree leaf pages 35%–50% full, doubling memory footprint in the buffer pool and inflating range-scan IOPS.

What helps: Use monotonic keys (ULID/UUIDv7) for append-heavy tables and schedule online `pg_repack` or `OPTIMIZE TABLE` during off-peak windows.

LSM Tombstone Accumulation Degrading Range Scans

A queue or TTL workload deletes millions of sequential keys; range scans (`SELECT ... WHERE k > X LIMIT 100`) must skip millions of tombstones before finding live keys, spiking CPU and latency.

What helps: Partition data by time (drop whole SSTables/partitions), use `DeleteRange` tombstones, or trigger periodic bottommost compaction.

SSD Wear-Out from Unbounded Write Amplification

Updating small 100-byte records in a B-Tree forces 16 KiB page flushes plus doublewrite buffer/WAL writes (~160x–320x logical-to-physical bytes), burning NVMe TBW limits early.

What helps: Batch updates, use an LSM-Tree engine for small-value high-churn KV workloads, or disable redundant OS page-cache double buffering via `O_DIRECT`.

05 / Practical checklist

Avoid these mistakes

  • Assuming B-Trees are always slower at writes—sequential/monotonic inserts into a cached B-Tree can match LSM throughput without compaction overhead.
  • Leaving RocksDB Bloom filters disabled, forcing point lookups to binary-search index blocks across every SSTable level.
  • Using an LSM-Tree as a FIFO job queue where heavy deletes create massive tombstone scan penalties.
  • Filling an LSM-Tree disk past 70%–80% capacity, leaving insufficient headroom for size-tiered or major compaction.
  • Benchmarking only empty or warm-cache databases for 60 seconds, missing B-Tree fragmentation and LSM compaction stalls that appear after hours.
