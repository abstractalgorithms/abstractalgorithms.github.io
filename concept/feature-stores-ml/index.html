ML Feature Stores
(Online & Offline).

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is an ML Feature Store.

Why this matters: The mechanism: understand how an ML Feature Store works from first principles.

Most production ML failures stem not from model architectures, but from training-serving skew (Pandas/SQL in notebooks vs. re-implemented Java/Redis in production) and data leakage. A Feature Store (Feast, Tecton, Hopsworks) centralizes feature definitions in a declarative registry and materializes them into two synchronized planes:

  1. Offline Store (Iceberg, BigQuery, Snowflake): Holds years of append-only feature history for point-in-time (AS-OF) training joins.
  2. Online Store (Redis, DynamoDB, Cassandra): Holds only the latest feature vector per entity key (user_id, card_id) for <10 ms real-time inference.
Dual-Plane Architecture

Unified Feature Registry -> Offline Lakehouse + Online KV Store

1.Single Definition: Batch (Spark/SQL), streaming (Flink), and on-demand transforms share one versioned registry.

2.AS-OF Training Joins: Offline store joins label at ts=T strictly with feature values recorded at or before T.

3.Low-Latency Serving: Online store serves entity vectors in <10 ms without scanning historical Parquet files.

One transformation registry feeds both historical AS-OF training datasets and sub-10ms online inference lookups.

Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision

Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Point-in-Time AS-OF Joins & Online Freshness Guards.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Think of Point-in-Time AS-OF Joins & Online Freshness Guards as the intuition layer for ML Feature Stores (Online & Offline): Operational control: configure bounds, failure handling, and safe production defaults.

Two operational rules keep feature stores healthy: (1) use AS-OF joins with a bounded TTL (ttl=90d) for offline training, and (2) write historical backfills strictly to the Offline Store with timestamp-guarded conditional writes (event_ts > current_ts) on the Online Store so late backfills never overwrite fresher live data.

Request & State Flow

Point-in-Time AS-OF Joins & Online Freshness Guards

-- Point-in-time (AS-OF) join preventing future data leakage in training sets
SELECT
  e.event_id,
  e.user_id,
  e.label_is_fraud,
  f.tx_count_last_5m,
  f.avg_spend_30d
FROM labeled_transactions e
ASOF JOIN user_velocity_features f
  MATCH_CONDITION (e.event_ts >= f.feature_ts)
  ON e.user_id = f.user_id
WHERE f.feature_ts >= DATEADD(day, -30, e.event_ts);
