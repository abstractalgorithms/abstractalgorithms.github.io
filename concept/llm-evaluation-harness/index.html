STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is an LLM Evaluation Harness.

Why this matters: The mechanism: understand how an LLM Evaluation Harness works from first principles.

An LLM evaluation harness is a versioned test runner that executes a prompt, RAG pipeline, or agent against a curated golden dataset (typically 200–500 stratified examples) and computes pass/fail gates across quality, latency, and cost.

Evaluation is organized into three tiers: deterministic code assertions (JSON Schema, regex, SQL execution), reference-based metrics (exact match, F1, semantic similarity), and calibrated LLM-as-a-judge rubrics.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why prompt edits silently break production.

Why this matters: The problem: see what breaks without Why prompt edits silently break production under real concurrency or scale.

LLM outputs are stochastic, and a prompt edit that fixes one edge case routinely breaks three others silently. Without an evaluation harness, teams ship regressions in JSON formatting, hallucinated citations, or latency spikes directly to users—only discovering them via support tickets.

In multi-step agent pipelines, silent 5% per-component regressions compound into broken end-to-end workflows.

Mitigating Judge Position & Verbosity Bias

LLM judges prefer the first option in pairwise A/B comparisons by 5–15% and favor longer answers. Randomize A/B order and score against explicit binary/Likert rubrics.

Preventing Eval Contamination

Maintain a held-out production shadow set refreshed monthly from real logs and never place held-out examples inside few-shot prompts.

Implementing a Position-Debiased Pairwise Eval Runner.

Why this matters: Operational control: configure bounds, failure handling, and safe production defaults.

Think of Implementing a Position-Debiased Pairwise Eval Runner as the intuition layer for LLM Evaluation Harnesses: Operational control: configure bounds, failure handling, and safe production defaults.

Run deterministic schema checks first, then run a pinned judge model with CoT-before-score and swapped A/B ordering to cancel position bias.

from pydantic import BaseModel, ValidationError

def eval_case(pipeline, case: dict, judge_fn) -> dict:
    output = pipeline(case["input"])
    try:
        parsed = case["schema"].model_validate_json(output)
        schema_ok = True
    except ValidationError:
        return {"schema_ok": False, "faithfulness": 0}

    # Debias pairwise/rubric judge by pinning snapshot + requiring reasoning first
    score_ab = judge_fn(case["context"], str(parsed), order="AB")
    score_ba = judge_fn(case["context"], str(parsed), order="BA")
    return {"schema_ok": schema_ok, "faithfulness": (score_ab + score_ba) / 2.0}

Continuous Shadow Eval & Judge Calibration Loop.

Why this matters: Production architecture: see how the components compose end to end under real load.

Think of Continuous Shadow Eval & Judge Calibration Loop as the intuition layer for LLM Evaluation Harnesses: Production architecture: see how the components compose end to end under real load.

Production teams separate a fast PR Gate (200 stratified cases) from a Nightly Shadow Replay (sampled production traffic) and calibrate the pinned LLM judge monthly against 50–100 human-labeled examples (tracking Cohen's kappa).

Eval Feedback Loop

PR Gate -> Nightly Shadow Suite -> Human Calibration Store

1.1. Pin Judge Snapshot: Never point evals at floating 'latest' model aliases that silently shift scoring baselines.

2.2. Stratified Cohorts: Tag cases by difficulty, language, and past incident IDs to prevent aggregate averages from hiding regressions.

3.3. Production Flywheel: Promote user thumbs-down traces into the golden dataset every week.

A calibrated judge + stratified golden dataset turns subjective prompt tuning into measurable engineering.
