01 / The idea

Foundational mechanics & core principles

LLM outputs are non-deterministic, and a prompt tweak that fixes one edge case routinely breaks three others silently. Without an evaluation harness, teams ship regressions in formatting, hallucinated citations, or latency spikes straight to users—only discovering them via support tickets weeks later.

  • Separate evaluation into three tiers: deterministic assertions (JSON schema, regex, SQL execution), reference-based metrics (exact match, F1, semantic similarity), and calibrated LLM-as-a-judge rubrics.
  • A golden dataset of 200–500 stratified examples (covering common paths, adversarial inputs, and past production bugs) gives tight enough confidence intervals to catch 3–5% regressions.
  • LLM judges suffer from position bias (preferring the first option in pairwise comparisons by 5–15%) and verbosity bias; mitigate both by randomizing A/B order and scoring against explicit binary/Likert criteria.
  • Always calibrate an LLM judge against human expert labels using Cohen's kappa (target κ >= 0.80) before trusting it as a CI merge gate.
  • Track quality alongside p95 latency and cost-per-task on every run so a 1% accuracy gain doesn't sneak in a 4x token bill.

Good candidates

  • Before promoting any prompt edit, model upgrade (e.g., GPT-4o to Claude 3.7 Sonnet or a smaller fine-tuned model), or RAG chunking change to production.
  • When building multi-step agent or extraction pipelines where silent 5% per-component regressions compound into broken end-to-end workflows.
  • To quantify cost-vs-quality trade-offs when distilling or routing traffic from frontier models to faster, cheaper open-weights models.

Think twice

  • Early 1-day exploratory prototyping where you are still discovering whether the user problem is even solvable with an LLM.
  • Purely deterministic business logic (regexes, arithmetic, SQL migrations) where standard unit and integration tests give 100% exact verification.
  • Subjective creative brainstorming with no reproducible success criteria or user-facing SLA.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA SaaS team evaluates switching their support bot from gpt-4o to claude-3-5-haiku across 300 real Zendesk tickets with ground-truth citations using Promptfoo and Ragas.

The idea

An LLM evaluation harness is the equivalent of a unit + integration test runner (pytest) combined with a benchmark profiler for probabilistic software. Instead of asserting assert output == "exact string", it executes a versioned Dataset through a Target System (prompt + model + retriever + tools), runs a stack of Graders, and aggregates pass rates, confidence intervals, latency, and token cost into a comparable Run Report.

The core shift is treating prompts, model IDs, and retrieval configs as a single versioned artifact. Whenever any layer changes, the harness answers two questions with numbers rather than intuition:

  1. Did overall task success improve without regressing critical safety or format slices?
  2. Is the improvement statistically significant relative to the cost and p95 latency delta?

Concrete walkthrough

Suppose you operate a legal-contract Q&A pipeline using RAG (text-embedding-3-large + Qdrant + claude-3-5-sonnet). You want to test a new hybrid BM25+vector reranker:

  1. Pull Golden Dataset (v2.4, 300 cases): 180 factual clause lookups, 60 multi-document comparisons, 40 unanswerable questions (must output "Not specified in contract"), and 20 adversarial prompt injections.
  2. Execute Harness (Promptfoo / Braintrust): Runs all 300 queries concurrently (concurrency=16, temperature=0.0) against baseline and candidate pipelines, logging retrieved chunk IDs, raw answers, TTFT, and token spend.
  3. Tier 1 — Deterministic Graders: Validates JSON schema, checks that every cited [Clause X.Y] exists in the retrieved chunks (zero fabricated citations), and verifies abstention regex on the 40 unanswerable cases.
  4. Tier 2 — Calibrated LLM Judge: gpt-4o-2024-08-06 grades faithfulness (1–5) and completeness (1–5) using a binary-decomposed rubric, with A/B order randomized for pairwise tie-breaking.
  5. Statistical Gate: Paired bootstrap resampling (1,000 iterations) confirms completeness rose +4.7% (95% CI: [+2.1%, +7.3%]), abstention_accuracy held at 97.5%, and p95 latency rose only +180 ms—green-lighting the rollout.

Separating deterministic code assertions from calibrated LLM-as-a-judge scoring keeps CI fast, reproducible, and resistant to judge drift.

Calibrating LLM judges and statistical significance

Using an LLM to grade another LLM is only trustworthy when treated as a measurement instrument that must be calibrated:

  • Decompose Rubrics into Binary Questions: Instead of asking "Rate quality 1–10", ask 4 specific Yes/No questions (e.g., "Does the answer invent any metric not in the context?", "Does it include the required JSON keys?"). Binary checks routinely raise human-judge agreement from κ=0.55 to κ>0.82.
  • Mitigate Position & Length Bias: In pairwise A/B grading, run each pair twice (A, B) and (B, A); count a win only if the judge picks the same winner in both orders, otherwise score a tie.
  • Sample Size & Power: With N = 100 binary items at ~85% accuracy, the 95% Wilson confidence interval is roughly ±7%—too wide to detect a 4% improvement. Scaling to N = 400 tightens the interval to ±3.5%, and paired McNemar/bootstrap tests leverage item-level correlation to detect 2–3% shifts reliably.

Failure modes

  1. Goodhart's Law on Proxy Metrics: Optimizing solely for answer_relevancy causes models to write verbose, plausible-sounding fluff that tanks factual precision. Fix: Pair relevancy with strict faithfulness and conciseness constraints.
  2. Hidden Retriever-Generator Coupling: A bad overall score gets blamed on the LLM when the retriever actually returned top_k chunks with 0% recall. Fix: Log context_recall@k independently from generation metrics.
  3. Broken Concurrency & Rate-Limit Retries: Hitting 429s mid-eval records empty strings as 0% accuracy, skewing the run. Fix: Fail the eval run if provider error rate exceeds 1% and distinguish infra errors from model failures.
  4. Eval Set Stagnation: The golden set never updates after launch, missing new product features and shifting user language. Fix: Pipe 10–20 downvoted or flagged production traces into the golden dataset every week.

Online vs. offline evaluation loop

Mature teams run a dual-loop architecture:

  • Offline Gate (Pre-Merge / Pre-Deploy): Runs on PRs (fast 100-case smoke slice, <2 min) and release candidates (full 400-case stratified suite + adversarial red-team). Blocks deployment on any critical slice regression.
  • Online Shadow & Sampling (Production): Evaluates 5–10% of live traffic asynchronously using lightweight judges (e.g., groundedness, PII leak, refusal rate) plus implicit user signals (thumbs down, copy/paste, immediate re-asks). Any trace scoring below threshold is auto-queued for human labeling and promoted into the offline golden dataset.

Practical checklist

  • Curate a versioned golden dataset of 200–500 examples stratified across core intents, edge cases, and abstention/adversarial inputs.
  • Run fast deterministic checks first (JSON Schema, regex, citation existence, SQL dry-run) before invoking paid LLM judges.
  • Calibrate every LLM-as-a-judge rubric against >=50 human-labeled examples until Cohen's κ >= 0.80.
  • Pin temperature=0.0 (and judge model snapshot) and report 95% confidence intervals or paired bootstrap p-values.
  • Track p95 latency and cost-per-run alongside quality scores in every CI report.
  • Establish a weekly pipeline to convert production failures into permanent regression test cases.
03 / Engineering trade-offs

Weighing architectural decisions

Deterministic Assertions vs. LLM-as-a-Judge

Advantage: Code assertions (JSON Schema, AST parse, tool-call match) are instant, free, and 100% reproducible.

Drawback: They cannot evaluate open-ended tone, faithfulness to retrieved context, or nuanced reasoning quality.

Large Eval Suites (2,000+ rows) vs. Fast CI Slices (150–300 rows)

Advantage: Large suites narrow 95% confidence intervals to ±1–2%, detecting subtle regressions on rare cohorts.

Drawback: Running 2,000 multi-turn agent evals per PR takes 20+ minutes and costs tens of dollars; reserve full suites for nightly/release builds.

Pairwise A/B Judging vs. Pointwise Rubric Scoring

Advantage: Pairwise comparison ('Which answer is more accurate?') yields higher inter-annotator agreement on subtle quality differences.

Drawback: Requires O(N) comparisons against a fixed baseline for every new candidate and doesn't produce an absolute trend line over time.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Dataset Contamination / Overfitting to Eval Set

Engineers tune prompts specifically to pass the 100-item test set, achieving 99% locally while failing on unseen production phrasing.

What helps: Maintain a held-out production shadow set refreshed monthly from real user logs and never expose held-out examples in few-shot prompts.

Uncalibrated LLM Judge Drift

The judge model itself is silently updated or biased toward longer, more confident-sounding hallucinations.

What helps: Pin judge model snapshots, require chain-of-thought reasoning before the score, and audit monthly against 50–100 human-labeled examples.

Non-Deterministic Flakiness Masking Real Regressions

Running an eval once at `temperature=0.7` produces ±4% variance between identical runs, causing teams to ignore red CI builds.

What helps: Set `temperature=0.0` (and seed if supported) for evals, run `k=3` trials for stochastic agent paths, and gate on statistical significance (paired bootstrap).

Evaluating Only Happy Paths

Test cases only include clean, well-formed queries, missing prompt injections, empty retrieval results, and malformed user inputs.

What helps: Stratify the golden dataset to include 20–30% adversarial, out-of-domain, and empty-context ('should abstain') test cases.

05 / Practical checklist

Avoid these mistakes

  • Relying on generic academic benchmarks (MMLU, HumanEval) to predict performance on proprietary domain workflows.
  • Using cosine similarity or BLEU/ROUGE to grade semantic correctness of factual Q&A.
  • Storing eval datasets inside mutable spreadsheets without Git/DVC versioning alongside prompt and code commits.
  • Skipping slice-based reporting—an overall 92% average can hide 40% failure on non-English or multi-hop queries.
  • Running LLM-as-a-judge with the exact same model family and prompt phrasing as the generator without checking for self-preference bias.
