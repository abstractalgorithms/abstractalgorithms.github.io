A foundational engineering concept

Multi-Agent
Orchestration.

Multi-agent orchestration coordinates specialized LLM agents—each with scoped prompts, tools, and memory—using explicit control topologies like supervisor graphs, handoff swarms, or DAG pipelines. Rather than stuffing 40 tools and conflicting instructions into one monolithic prompt, orchestration isolates responsibilities, bounds token growth, and enforces deterministic state transitions.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Decompose complex agentic workflows into narrow, stateful specialists connected by typed handoffs, explicit loop budgets, and checkpointed state—never rely on open-ended agent chatter to converge.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

A single LLM prompt degrades sharply once tool definitions exceed ~15–20 schemas or conversation history crosses 30K–50K tokens of mixed planning and raw tool output: tool-selection accuracy drops and latency balloons. Multi-agent orchestration lets an engineer assign a fast, cheap model (e.g., Claude Haiku or GPT-4o-mini) to triage and extraction while reserving reasoning models for synthesis, cutting per-run cost by 40–70% and making failures inspectable at node boundaries.

  • Topology dictates predictability: supervisor-worker graphs (LangGraph) give deterministic routing and bounded cycles, whereas peer-to-peer handoffs (OpenAI Swarm) trade predictability for flexible conversational delegation.
  • Context isolation is the primary performance lever: pass compact structured artifacts (JSON summaries, artifact IDs) between agents rather than forwarding raw 20KB tool payloads.
  • Every cycle needs a hard stop: enforce max_iterations (e.g., 8–12 steps), token budgets, and wall-clock timeouts so two agents cannot argue in a polite verification loop indefinitely.
  • Checkpoint state after every node transition to PostgreSQL or Redis so a transient 429 rate limit or tool crash resumes from step 4 instead of re-running steps 1–3.
  • Standardize tool and agent boundaries using protocols like MCP (Model Context Protocol) for tool discovery and A2A (Agent2Agent) or typed JSON schemas for inter-agent contracts.

Good candidates

  • Workflows span distinct domains or security boundaries where each step needs different tool permissions (e.g., read-only SQL analytics vs. write-scoped Jira/GitHub mutations).
  • Long-running tasks require durable state checkpoints, human-in-the-loop approval gates, or parallel fan-out across independent sub-tasks (such as researching 10 vendors concurrently).
  • A monolithic system prompt has grown past ~3,000 tokens of conditional rules and tool schemas, causing frequent tool-argument hallucinations or instruction-following drift.

Think twice

  • A single model call with 2–5 well-typed tools and structured JSON output solves the task in under 3 seconds—orchestration adds 1.5–4x latency overhead per inter-agent hop.
  • The workflow is strictly deterministic data transformation (ETL, webhook routing, regex/SQL pipelines) where standard DAG engines like Temporal or Airflow are cheaper and 100% predictable.
  • Every sub-agent needs the full raw conversation history anyway, which negates context isolation and multiplies input token billing across every agent turn.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA PagerDuty alert fires for elevated 5xx rates on a checkout service. A Supervisor agent routes to a Metrics Agent (Prometheus/Datadog MCP), a Logs Agent (OpenSearch), and a Deploy Diff Agent (GitHub API) in parallel, then hands their compact JSON findings to a Synthesis Agent to draft a Slack summary and rollback PR.

The idea

Multi-agent orchestration treats an LLM application as a stateful directed graph rather than a single chat completion. Each node is a specialized agent or deterministic function that reads from a typed shared state, performs a bounded unit of work (reasoning, tool execution via MCP, or verification), and emits a structured state patch.

Instead of asking one prompt to plan, query databases, write code, and audit security simultaneously, orchestration separates control flow (who runs next, retry limits, human approval gates) from cognition (what each specialist decides within its narrow context window). Production frameworks like LangGraph, Temporal + AI SDKs, and AutoGen persist this state at every edge transition so workflows survive process restarts and remain auditable.

Concrete walkthrough

Consider an enterprise Vendor Security Review workflow triggered when an engineer requests a new SaaS tool:

  1. Ingest & Checkpoint: The orchestrator creates a ReviewState record in PostgreSQL with trace_id, budget_remaining: 40000 tokens, and step: 0.
  2. Supervisor Routing: A lightweight router (GPT-4o-mini) validates the request and dispatches two read-only specialists in parallel: a Compliance Agent (checks SOC2/ISO docs via RAG) and a Pricing/Contract Agent (extracts renewal and DPA clauses).
  3. Scoped Tool Execution: Each specialist calls only its authorized MCP server. Raw 40-page PDFs stay inside the specialist's ephemeral context; only a validated Pydantic Findings JSON (~600 tokens) is written back to ReviewState.
  4. Policy Gate & Critique: A deterministic Python rule checks for missing SOC2 Type II dates. If missing, it routes back to the Compliance Agent once (retry_count <= 1); otherwise it advances.
  5. Human-in-the-Loop Pause: If the contract includes sub-processor changes, the graph suspends at an interrupt node and posts a Slack approval card, resuming cleanly hours later from the PostgreSQL checkpoint.

Durable checkpoints and typed JSON handoffs isolate specialist context windows while bounding cost and loops.

Routing, state, and handoff contracts

Reliable multi-agent systems separate ephemeral scratchpads from durable shared state. Each agent maintains a local message array for its own multi-step tool loop, which is garbage-collected as soon as the agent returns its structured output. Only the typed result object is merged into the global state.

For routing, prefer deterministic edges first, LLM routing second: if a condition can be expressed in code (e.g., if findings.severity == 'CRITICAL': route('security_escalator')), never spend 600ms and tokens asking an LLM to choose the next node. Reserve semantic routing for genuinely ambiguous user intent or dynamic plan revision.

Failure modes

The most expensive production failures in multi-agent systems are silent semantic drift and runaway loops. Semantic drift happens when Agent A paraphrases a user constraint slightly, Agent B broadens it, and Agent C executes the wrong query—mitigate this by keeping original inputs immutable in state. Runaway loops happen when a critic rejects output for subjective reasons; mitigate with deterministic pass/fail criteria (e.g., unit tests, schema validators) and a strict max_steps circuit breaker.

Transient LLM provider outages (HTTP 429/503) are inevitable during parallel fan-out. Wrap every model node in idempotent retry policies with exponential backoff, jitter, and model fallback (e.g., primary region -> secondary region) backed by persistent checkpoints.

Observability, evals, and cost control

Treat every multi-agent run like a distributed microservice trace. Emit OpenTelemetry spans (GenAI semantic conventions) tagged with trace_id, agent_name, model, input_tokens, output_tokens, tool_latency_ms, and step_index. Track cost per successful task rather than cost per token—a cheaper model that triggers 3 extra critic retries often costs more than a stronger model that succeeds in 1 pass.

Evaluate at two levels: node-level unit evals (given state X, did the SQL Agent emit valid SQL?) and trajectory evals (did the whole graph reach the right outcome in <= N hops without unnecessary tool calls?).

Practical checklist

  • Justify >1 agent: Confirm a single prompt + <=10 tools fails measurably before splitting into multiple agents.
  • Typed state & handoffs: Define Pydantic/JSON Schema contracts for global state and every inter-agent edge.
  • Hard loop & budget caps: Enforce max_steps, max_tokens, and wall-clock timeouts at the orchestrator level.
  • Persistent checkpoints: Store node transitions in PostgreSQL/Redis to enable crash recovery and human-in-the-loop pauses.
  • Context isolation: Pass compact structured summaries between agents; never dump raw 20KB tool logs into shared history.
  • Unified tracing: Propagate a single trace_id across all agents, MCP tool calls, and LLM spans.
03 / Engineering trade-offs

Weighing architectural decisions

Control Topology (Supervisor Graph vs. Decentralized Swarm)

Advantage: Supervisor graphs enforce explicit state machines, audit trails, and predictable cost ceilings.

Drawback: Every new capability requires updating central routing logic, whereas decentralized handoffs adapt organically but are harder to debug.

State Passing (Shared Scratchpad vs. Filtered Handoffs)

Advantage: Filtered JSON handoffs cut token costs by 50–80% and prevent prompt-injection or noisy tool output from poisoning downstream agents.

Drawback: Aggressive summarization can drop subtle edge-case details that a downstream specialist needed.

Execution Mode (Sequential Pipeline vs. Parallel Fan-Out)

Advantage: Parallel fan-out slashes end-to-end wall-clock latency when sub-tasks are independent (e.g., 5 concurrent web/DB lookups in 4s instead of 20s).

Drawback: Concurrent LLM calls spike TPM/RPM quotas, triggering 429 throttling unless gated by a semaphore or token bucket.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Infinite Critique / Ping-Pong Loop

A Writer agent and Reviewer agent disagree on style or a flaky test, bouncing control back and forth until the API bill spikes or the request times out.

What helps: Enforce a hard `max_steps` counter in graph state, hash recent outputs to detect repeated states, and escalate to a human or fallback response on exhaustion.

Telephone-Game Context Loss

Each agent re-summarizes the user's constraints in prose, silently dropping a critical filter (e.g., 'exclude EU accounts' or a specific UUID) by hop 3.

What helps: Keep immutable user constraints and canonical IDs in a typed top-level state object that every agent reads directly rather than relying on conversational summaries.

Tool-Call Amplification Storm

A planner spawns 8 sub-agents, each invoking 5 search calls, hitting OpenAI/Anthropic TPM limits or overwhelming an internal microservice.

What helps: Apply a shared per-trace token and tool-call budget, use exponential backoff with jitter on 429s, and deduplicate identical tool queries via a short-TTL cache.

Cross-Agent Prompt Injection

An extraction agent ingests untrusted web/email text containing adversarial instructions that propagate into a privileged execution agent's context.

What helps: Wrap external data in explicit delimiters, strip instruction-like payloads at boundaries, and enforce deterministic schema validation + human approval before privileged write tools.

05 / Practical checklist

Avoid these mistakes

  • Creating five 'persona' agents ('Senior Architect', 'QA Guru') that all share the same model and tools, adding latency with zero specialization benefit.
  • Forwarding the entire raw `messages[]` array to every sub-agent, causing quadratic token growth across hops.
  • Omitting distributed tracing (OpenTelemetry / LangSmith / Arize Phoenix) with a shared `trace_id`, making it impossible to see which agent hallucinated a parameter.
  • Letting agents invent free-form handoff strings instead of enforcing Pydantic/JSON Schema contracts at every edge.
  • Running uncheckpointed in-memory loops for multi-minute tasks where a single network blip wipes all intermediate work.
