Test Doubles
& Mocks.

Test doubles replace real collaborators with controlled stand-ins (dummies, stubs, spies, mocks, and fakes) so unit and integration suites run in milliseconds without live networks, payment gateways, or flaky third-party sandboxes.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Prefer stateful in-memory fakes and HTTP contract stubs (like WireMock) over over-specified mocks; mocking internal collaborators couples tests to implementation details and breaks refactoring.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Production services depend on PostgreSQL, Kafka, Stripe, and internal gRPC APIs that are slow, rate-limited, or non-deterministic under test. Without disciplined test doubles, a 2,000-test CI suite either takes 45 minutes against shared staging environments or fails randomly on network blips. Conversely, undisciplined mocking creates brittle tests that pass 100% while production crashes on serialization mismatches or SQL dialect bugs.

  • Gerard Meszaros's 5-type taxonomy separates state verification (Dummy, Stub, Fake) from behavior verification (Spy, Mock), each carrying different coupling costs.
  • Fakes implement working, lightweight logic (e.g., an in-memory ConcurrentHashMap repository enforcing unique email constraints), whereas Stubs return canned answers without logic.
  • Mocks pre-program expectations and fail the test if exact method calls, arguments, or invocation counts are not met—making them the highest-coupling double.
  • Classicist (Detroit-school) testing mocks only across architectural boundaries (network, disk, time), while Mockist (London-school) testing mocks every collaborator.
  • Boundary stubs like WireMock or responses must be paired with contract assertions or periodic replay against staging so schema drift does not silently invalidate the suite.

Good candidates

  • Isolating domain logic from non-deterministic boundaries like system clocks (Clock.fixed()), UUID generators, or external payment/SMS webhooks (Stripe /v1/payment_intents, Twilio).
  • Simulating rare infrastructure fault conditions—HTTP 429 rate limits, TLS handshake timeouts, or Kafka broker NotLeaderOrFollower errors—that cannot be reliably triggered against live sandboxes.
  • Replacing slow I/O repositories in fast unit suites (<10 ms per test) using an in-memory Fake that enforces the same uniqueness and state-transition invariants as production.

Think twice

  • Testing SQL queries, ORM mappings, or database migrations—mocking EntityManager or JdbcTemplate hides real PostgreSQL JSONB, index, and constraint bugs that Testcontainers catches.
  • Mocking pure value objects, DTOs, or internal helper classes within the same module, which turns refactoring into a rewrite of verify() assertions.
  • Validating wire-format compatibility with an external API unless the stub's responses are backed by recorded contract tests (e.g., Pact or OpenAPI schema validation).

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn order checkout service calls POST https://api.stripe.com/v1/payment_intents with an Idempotency-Key header and must retry twice on HTTP 503 with exponential backoff, then fail fast on HTTP 402 Card Declined.

The idea

Every automated test sits on a spectrum between isolation (fast, deterministic, pinpoint failure localization) and fidelity (exercising real SQL engines, TCP sockets, and serialization). Test doubles—coined by Gerard Meszaros as the umbrella term for Dummy, Stub, Spy, Mock, and Fake—let you control where a test sits on that spectrum.

Instead of letting a unit test open a TLS socket to Stripe or spin up a 30-second database container, you substitute a collaborator that implements the same port/interface. The critical architectural skill is choosing which kind of double to use and where to draw the boundary: mock or fake only at architectural seams (network, disk, clock, randomness), never between cohesive domain objects.

Concrete walkthrough

Consider a Java RefundService.issueRefund(orderId, amount) method that collaborates with three dependencies: OrderRepository (PostgreSQL), PaymentGateway (Stripe HTTP API), and AuditLogger (Kafka event emitter).

  1. Dummy (CorrelationId or unused Tracer): Passed to satisfy a constructor signature when the test path does not inspect tracing metadata.
  2. Fake (InMemoryOrderRepository): Stores Order records in a HashMap, validates that refundedAmount <= totalAmount, and throws DuplicateRefundException on double-refunds—giving realistic state transitions in <1 ms.
  3. Stub (StubPaymentGateway or WireMock): Configured to return GatewayResult.declined("insufficient_funds") or HTTP 503 so the test deterministically exercises the compensation branch without calling Stripe.
  4. Spy / Mock (AuditLogger): Records emitted AuditEvent objects (Spy) or asserts verify(auditLogger).logRefundAttempt(orderId, DECLINED) (Mock) because the audit log is a fire-and-forget side effect with no return value.

Real domain logic runs untouched while stateful Fakes and HTTP Stubs replace external I/O boundaries.

Detroit vs. London School & Coupling

Two major philosophies govern how aggressively teams use test doubles:

  • Detroit (Classicist) School: Treat a "unit" as a cohesive behavior, not a single class. Use real domain objects together and introduce doubles only at shared mutable boundaries (databases, HTTP clients, system clocks). Tests remain resilient when you extract or inline helper classes.
  • London (Mockist) School: Isolate every class from all collaborators using mocks (@Mock in Mockito, unittest.mock.MagicMock in Python). While this pinpoints which class broke, it creates tight coupling to method signatures and encourages anemic tests that mirror the implementation line-for-line.

In modern microservice architectures, a hybrid boundary-first approach wins: Classicist inside the domain core, WireMock/Testcontainers at network and persistence edges, and strict Mocks/Spies only for fire-and-forget side effects.

Failure modes

  1. Partial Mock Trap (@Spy on SUT): Spying on the class under test to stub one private-adjacent method often bypasses initialization or causes infinite recursion in proxies. Extract the collaborator into its own class instead.
  2. Async & Concurrency Blindness: In-memory fakes rarely reproduce PostgreSQL SERIALIZABLE conflicts, row-level locks, or Kafka consumer rebalancing. Always back critical concurrency paths with a dedicated Testcontainers test.
  3. Unverified Mock Return Defaults: Python's MagicMock silently returns truthy child MagicMock objects for misspelled attributes (e.g., client.asert_called() or resp.status_code), causing tests to pass vacuously. Always pass spec=RealClass or autospec=True.
  4. Over-Mocked Serialization: Mocking the ObjectMapper or HTTP client skips testing Jackson @JsonProperty annotations, date formats, and enum unknown-value handling.

Contract Testing & Anti-Drift Guardrails

To prevent stubs and fakes from lying about production dependencies:

  • Contract Tests for Fakes: Write an abstract OrderRepositoryContractTest suite containing 10–15 behavioral assertions (save, duplicate key, optimistic lock conflict, pagination) and run it against both InMemoryOrderRepository and PostgresOrderRepository (via Testcontainers). Any semantic drift fails immediately.
  • Consumer-Driven Contracts (Pact / OpenAPI): Generate WireMock stubs directly from OpenAPI 3.1 specs or Pact files verified by the provider service in CI.
  • Strict Mock Modes: Use Mockito.strictness(Strictness.STRICT_STUBS) (default in JUnit 5 MockitoExtension) to fail on unused stubs, and create_autospec(Class, spec_set=True) in Python to reject invalid attribute access.

Practical checklist

  • Draw test double boundaries strictly at I/O seams (DB, HTTP, Queue, Clock, RNG)—keep domain objects real.
  • Prefer a reusable Fake over repeating when(...).thenReturn(...) setups across 5+ tests.
  • Run a shared Contract Test against both your in-memory Fake and the real Testcontainers adapter.
  • Enable strict stubbing (MockitoExtension in Java, autospec=True in Python) to catch dead stubs and typos.
  • Use WireMock (or respx/responses) for HTTP clients so serialization, headers, and timeouts are actually exercised.
  • Verify HTTP stubs against OpenAPI/Pact schemas in CI to prevent silent contract drift.
03 / Engineering trade-offs

Weighing architectural decisions

Test Speed vs. Fidelity

Advantage: In-memory fakes and Mockito mocks execute in 1–5 ms per test with zero Docker or network startup overhead.

Drawback: Fakes can drift from production behavior (e.g., missing PostgreSQL `ON CONFLICT` semantics or isolation anomalies) unless verified by a thinner Testcontainers suite.

Behavior Verification (Mocks) vs. State Verification (Fakes/Stubs)

Advantage: Mocks verify exact side effects on fire-and-forget boundaries like audit loggers or metrics emitters (`meterRegistry.counter(...).increment()`).

Drawback: Asserting internal call sequences (`InOrder`) breaks tests whenever implementation internals are optimized or reordered without changing observable outputs.

Hand-Rolled Fakes vs. Mocking Frameworks

Advantage: Hand-rolled fakes require zero reflection/bytecode proxies, run cleanly under GraalVM native tests, and are reused across dozens of test files.

Drawback: Maintaining fakes for complex interfaces with 20+ methods adds boilerplate unless interfaces are kept narrow (Interface Segregation Principle).

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Mock-Induced False Confidence (Tautological Tests)

Tests mock both the input repository and the downstream publisher, asserting only that the mock returned what it was told to return while production fails on a `NullPointerException` in real deserialization.

What helps: Restrict mocks to true external I/O boundaries and run at least one vertical slice integration test per endpoint using real serialization and Testcontainers.

Schema & Contract Drift

An upstream microservice renames `customer_id` to `account_id` in its JSON response, but local WireMock stubs still return `customer_id`, keeping CI green until production throws 500s.

What helps: Validate stub payloads against shared OpenAPI/Protobuf schemas or Pact contracts in CI so breaking provider changes fail the build immediately.

Over-Specified Interaction Coupling

Refactoring a batch lookup from N calls to `getUser(id)` into 1 call to `getUsers(ids)` breaks 80 unit tests that used `verify(client, times(N)).getUser(...)`.

What helps: Assert observable state outcomes and final domain events rather than internal collaborator call counts; reserve `verify()` for strict side-effect boundaries.

Leaky Shared Fake State

A singleton `InMemoryOrderRepository` shared across parallel JUnit 5 or pytest workers retains records from previous tests, causing order-dependent flakiness.

What helps: Instantiate fresh fake instances per test case (`@BeforeEach` / pytest function fixture) and forbid mutable static state in test doubles.

05 / Practical checklist

Avoid these mistakes

  • Mocking types you do not own (like `HttpClient` or `JdbcTemplate` directly) instead of wrapping them in a thin domain adapter interface.
  • Using `any()` matchers everywhere in `verify()`, which allows silently passing `null` or malformed arguments without failing the test.
  • Writing 30 lines of `when(...).thenReturn(...)` setup per test—a clear signal that the class under test has too many responsibilities or needs a Fake.
  • Leaving `verifyNoMoreInteractions()` on mocks, which breaks unrelated tests whenever a new logging or metrics call is added.
  • Replacing SQL/NoSQL integration tests entirely with in-memory fakes, missing query syntax errors, transaction rollbacks, and constraint violations.
