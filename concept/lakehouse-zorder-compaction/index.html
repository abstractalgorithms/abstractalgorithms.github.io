Lakehouse File Compaction, Z-Ordering
& Data Skipping.

Lakehouse engines achieve warehouse-grade scan speeds on S3/GCS by compacting tiny streaming files into 256–512 MB Parquet files and co-locating multi-column query predicates via Z-ordering so min/max stats prune irrelevant files.

The idea to keep with you

When durability and read throughput pull in opposite directions, Z-Ordering & Data Skipping, use bin-pack compaction to fix S3 LIST/GET overhead, and Z-order (or Liquid Clustering) on 2–4 high-cardinality filter columns so min/max manifest bounds skip 95%+ of files.

TL;DR30-second simplified summary
▾

Small-file fragmentation slows lakehouse planning via S3 GET/HEAD storms and prevents min/max data skipping. Bin-pack compaction merges files to 256–512 MB, while Z-order/Hilbert clustering on 2–4 columns tightens manifest bounds under OCC snapshot isolation, followed by manifest rewrites and snapshot expiry.
