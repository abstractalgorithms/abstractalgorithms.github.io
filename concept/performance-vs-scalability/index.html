The idea & core mechanics.

Teams routinely throw hardware or extra stateless replicas at a slow database query—only to watch p99 latency stay flat or worsen because lock contention and N+1 round trips are performance bugs, not capacity limits. Separating Performance from Scalability ensures you profile and fix algorithmic or I/O bottlenecks before sharding or auto-scaling.

ChoiceWhat it buysWhat it costs
Good candidateOptimize performance first when single-request latency is high due to N+1 queries, unindexed scans, or synchronous serialization.
Good candidateScale horizontally (scale out) when single-request latency is fast at low load but saturates CPU, memory, or network I/O at peak QPS.
Good candidateScale vertically (scale up) temporarily for stateful monoliths or single-leader databases before investing in [sharding](/concept/database-sharding).
Think twiceAdding more stateless web servers when the shared primary database connection pool is already saturated.

Principle 1

Performance measures how fast a single request completes under low load; scalability measures how well throughput and latency hold as load and resources increase proportionally.

Principle 2

Vertical scaling (scaling up) adds CPU/RAM/NVMe to one node—zero distributed complexity, but hits hardware ceilings and single-point-of-failure limits.

Principle 3

Horizontal scaling (scaling out) adds commodity nodes behind a load balancer—requires stateless application tiers and partitioned state.

Principle 4

Amdahl's Law caps speedup when a serial bottleneck (like a global lock or single primary DB write) cannot be parallelized: Slatency(s)=1(1−p)+psS_{\text{latency}}(s) = \frac{1}{(1 - p) + \frac{p}{s}}Slatency​(s)=(1−p)+sp​1​.

Reference Implementations (Python & Java)

# Performance fix: eliminate O(N) N+1 DB queries with a single batched lookup
def get_orders_with_users(order_repo, user_repo, order_ids: list[str]) -> list[dict]:
    orders = order_repo.find_by_ids(order_ids)
    user_ids = list({o.user_id for o in orders})
    users_by_id = user_repo.find_map_by_ids(user_ids)  # 1 query instead of N
    return [{"order": o, "user": users_by_id.get(o.user_id)} for o in orders]

// Performance fix: batch user lookup to eliminate N+1 round trips
public List<OrderView> getOrdersWithUsers(List<String> orderIds) {
    List<Order> orders = orderRepo.findByIds(orderIds);
    Set<String> userIds = orders.stream().map(Order::userId).collect(Collectors.toSet());
    Map<String, User> users = userRepo.findMapByIds(userIds);
    return orders.stream().map(o -> new OrderView(o, users.get(o.userId()))).toList();
}
The idea to keep with you

Performance vs. Scalability

If a system is slow for a single user, you have a performance problem; if it is fast for a single user but slows down under heavy load, you have a scalability problem.
