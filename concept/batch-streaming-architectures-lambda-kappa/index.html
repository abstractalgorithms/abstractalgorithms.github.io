STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What are Lambda and Kappa Architectures.

Data platforms must serve both low-latency fresh views (seconds) and 100% accurate historical recomputations (months/years). Two canonical architectures solve this:

  • Lambda Architecture: Splits ingestion into an immutable Batch Layer (Spark/SQL on S3 for exact historical truth), a Speed Layer (Flink/Kafka for real-time deltas), and a Serving Layer that merges both.
  • Kappa Architecture: Eliminates the separate batch codebase—everything is an append-only event stream (Kafka + tiered storage or Lakehouse). Reprocessing historical data simply spins up a new consumer group from offset = 0 (or replays Iceberg/Delta snapshots).
Unified Kappa Flow

Immutable Event Log -> Stream Engine -> Lakehouse Serving Tables

1.Single Codebase: Kappa runs the exact same windowing and watermark logic for live streams and historical replays.

2.Event-Time Watermarks: Handles out-of-order late events using event timestamps rather than wall-clock arrival.

3.ACID Table Snapshots: Iceberg/Delta commits provide time-travel and atomic MERGE for idempotent replays.

Kappa + Lakehouse tables unify real-time freshness and historical replayability without maintaining two codebases.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why we need Stream Replay & Watermarks (and why Lambda drifts).

Maintaining Lambda forces teams to write every business aggregation twice—once in batch SQL/Spark and once in streaming Flink/Java—leading to subtle metric drift between live dashboards and next-day reports.

Moving to Kappa introduces its own engineering challenges: late/out-of-order events (mobile clients offline for hours), schema evolution (Protobuf/Avro compatibility), and state-store OOMs during multi-terabyte replays from offset = 0.

Kappa Reprocessing

Zero-Downtime Logic Upgrade via Parallel Consumer Replay

Kappa upgrades business logic by backfilling a parallel v2 sink until lag hits zero, then atomically swapping serving pointers.

Event-Time Watermarks

Track max_event_time - allowed_lateness so late mobile events update open windows cleanly or route to a late-data side output.

SCD Type 2 Lineage

Track historical dimension changes with effective_from / effective_to columns so replayed streams join against point-in-time attributes.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

How Watermarks, Checkpoints, and Idempotent Sinks are managed.

Production streaming pipelines enforce four invariants:

  1. Event-Time Watermarking: Define explicit withWatermark("event_ts", "10 minutes") so late data doesn't hold state forever.
  2. Checkpointing + Exactly-Once Sinks: Checkpoint RocksDB/state to S3/HDFS and use idempotent MERGE or transactional Kafka-to-Iceberg commits.
  3. Schema Registry Compatibility: Enforce BACKWARD or FULL compatibility on Avro/Protobuf topics so replays can read old records.
  4. Side-Output Dead Letters: Route late/malformed events to a DLQ topic instead of crashing the stream.
# Unified Spark Structured Streaming: event-time watermark + idempotent Iceberg MERGE
from pyspark.sql import functions as F

events = (
    spark.readStream.format("kafka")
    .option("subscribe", "orders.events")
    .load()
    .select(F.from_json(F.col("value").cast("string"), schema).alias("e"))
    .select("e.*")
    .withWatermark("event_ts", "10 minutes") # bound RocksDB state size
)

agg = events.groupBy(F.window("event_ts", "5 minutes"), "merchant_id").agg(F.sum("amount").alias("gmv"))

def upsert_to_gold(batch_df, batch_id):
    batch_df.createOrReplaceTempView("updates")
    batch_df.sparkSession.sql("""
        MERGE INTO gold.merchant_gmv_5m t USING updates s
        ON t.window = s.window AND t.merchant_id = s.merchant_id
        WHEN MATCHED THEN UPDATE SET t.gmv = s.gmv
        WHEN NOT MATCHED THEN INSERT *
    """)

agg.writeStream.foreachBatch(upsert_to_gold).option("checkpointLocation", "s3://ckpt/gmv/").start()

STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production example: Debezium CDC -> Kafka -> Flink/Spark -> Iceberg Medallion.

Modern data platforms pair Debezium CDC (streaming OLTP changes from Postgres WAL) with Kafka and a Bronze -> Silver -> Gold Iceberg Medallion pipeline. Both streaming consumers and ad-hoc Spark backfills read the exact same Iceberg snapshots.

Medallion Lakehouse

OLTP WAL (CDC) -> Kafka -> Iceberg Bronze/Silver/Gold Snapshots

1.Zero Dual-Write: CDC captures committed WAL changes directly without application dual-writes.

2.Time-Travel Replay: Iceberg snapshots allow deterministic historical reprocessing without keeping infinite Kafka brokers.

3.Idempotent Gold MERGE: Keyed MERGE upserts absorb late-arriving CDC events without duplicating rows.

CDC + Kafka + Iceberg Medallion delivers Kappa simplicity with warehouse-grade SQL and time-travel.
