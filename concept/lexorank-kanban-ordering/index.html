The idea to keep with you

If latency budgets leave no room for synchronous retries, by computing the lexicographical midpoint between two adjacent rank strings (e.g., '0|i00007:' and '0|i0000f:' -> '0|i0000b:'), Kanban boards avoid O(N) integer re-indexing while using 3-bucket rotation to bound string length.

TL;DR30-second simplified summary
▾

By combining base-36 midpoint calculation with a UNIQUE (board_id, rank) constraint and jittered CAS retries, Lexorank handles concurrent backlog grooming without range-lock deadlocks. When rank strings grow past 128 characters, a background worker compacts them into the next modulo-3 bucket.

Why Integer Positions Fail at Scale.

Why this matters: Diagnose the O(N) write amplification and row-lock deadlocks caused by sequential integer rank columns.

Think of Why Integer Positions Fail at Scale as the intuition layer for Lexorank & Distributed Kanban Board Ordering: Diagnose the O(N) write amplification and row-lock deadlocks caused by sequential integer rank columns.

In a PostgreSQL-backed Kanban board with 10,000 issues, storing an integer position forces every drag-and-drop reorder from index 9,000 to index 5 to execute UPDATE issues SET position = position + 1 WHERE position BETWEEN 5 AND 8999. Under concurrent backlog grooming, two transactions acquiring row locks in opposite directions immediately trigger deadlocks.

FOUNDATION

O(N) Row-Lock Amplification

1.Write Amplification: 1 UI move = up to N-1 DB row mutations.

2.Deadlock Vector: Opposing range updates collide on B-tree index pages.

Sequential integer positions couple a single UI move to O(N) database row locks.

Floating-Point Midpoints & Precision Collapse.

Why this matters: Understand why IEEE-754 floats initially solve O(1) writes but collapse after ~52 bisections.

Replacing integers with 64-bit floats (pos = (prev + next) / 2.0) reduces reordering to a single-row UPDATE.

However, IEEE-754 double precision only provides 53 bits of significand.

FOUNDATION

IEEE-754 Precision Exhaustion

1.53-Bit Ceiling: IEEE-754 doubles fail after ~52 consecutive insertions in one gap.

2.Silent Tie: Duplicate float keys break deterministic ORDER BY queries.

64-bit floats defer re-indexing but still hit a hard 53-bit precision wall.

Lexorank String Anatomy & Base-36 Encoding.

Why this matters: Construct the <bucket>|<rank>: string format using fixed-width base-36 digits for arbitrary-precision ordering.

Lexorank represents positions as ASCII strings sorted by standard C / POSIX byte collation, e.g., 0|hzzzzz:.

The leading 0| is the active rebalancing bucket (0, 1, or 2), followed by a 6-character base-36 value (0-9, a-z) and a trailing : marker.

INTERMEDIATE

Lexorank String Structure

A 3-part string format (`bucket|base36:`) gives arbitrary precision with native B-tree sorting.

04
intermediate

Arbitrary-Precision Lexicographical Midpoint.

Why this matters: Compute the exact midpoint between two unequal-length base-36 strings in O(L) time.

Think of Arbitrary-Precision Lexicographical Midpoint as the intuition layer for Lexorank & Distributed Kanban Board Ordering: Compute the exact midpoint between two unequal-length base-36 strings in O(L) time.

To insert between prev and next, pad the shorter string on the right with 0 (and treat next as having a trailing virtual character if needed), then compute (val(prev) + val(next)) // 2 in base-36. If prev and next differ by 1 at the last digit (e.g., i00007 and i00008), append midpoint digit i (18 in base-36) to prev, yielding i00007i.

INTERMEDIATE

Base-36 Midpoint Calculation

1.O(1) DB Write: Only the moved issue row is updated in PostgreSQL.

2.Adjacent Extension: Appending 'i' splits a unit gap cleanly without touching neighbors.

Base-36 midpoint arithmetic guarantees a strictly ordered key between any two ranks.

intermediate

Optimistic Locking & Concurrent Rank Collisions.

Why this matters: Prevent duplicate ranks when two users simultaneously drop different cards into the exact same gap.

If Alice and Bob both drag cards between 0|i00007: and 0|i0000f: at the same millisecond, both compute 0|i0000b:.

Without concurrency control, both cards receive identical ranks.

INTERMEDIATE

CAS Retry on Rank Collision

A unique index on `(board_id, rank)` turns silent rank collisions into safe retries.

06
advanced

3-Bucket Rotation & Zero-Downtime Rebalancing.

Why this matters: Prevent unbounded rank string growth using asynchronous 3-bucket rotation (0 -> 1 -> 2 -> 0).

Once any rank string on a board exceeds a length threshold (e.g., 128 characters), a background rebalancer triggers.

Moving from bucket 0 to 1, it walks issues in current ORDER BY rank ASC order and assigns evenly spaced 6-char keys in bucket 1 (1|00000g:, 1|00000w:, ...).

ADVANCED

Asynchronous 3-Bucket Rotation

1.3-Bucket Invariant: Never reuse a bucket until 100% of rows have drained out of it.

2.Zero Lockout: Live drag-and-drop writes keep working during background rebalancing.

Three rotating buckets let a background worker compact rank strings without locking the board.

07
advanced

Sentinel Boundary Rows & Multi-Column Moves.

Why this matters: Handle empty columns, top/bottom insertions, and cross-column status transitions cleanly.

Dropping a card at the top or bottom of a column requires a neighbor rank on both sides.

Storing hidden MIN_RANK (0|000000:) and MAX_RANK (0|zzzzzz:) sentinel markers per board guarantees every insertion has a valid (left, right) pair.

ADVANCED

Atomic Status + Rank Transition

Sentinel bounds and single-row CAS transactions keep cross-column Kanban moves atomic.
