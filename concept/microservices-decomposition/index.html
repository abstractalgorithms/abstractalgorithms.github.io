STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is Microservices Decomposition.

Microservices decomposition partitions a system into independently deployable services aligned to Domain-Driven Design (DDD) bounded contexts (discovered via Event Storming), each owning its own private database schema.

Instead of slicing horizontally (UI, Business, DB) or by CRUD nouns (User, Address), boundaries follow transactional consistency and team ownership.

Strangler Fig Extraction

Incremental Service Extraction via Edge Proxy (Envoy / Kong)

Strangler Fig routes specific paths to the extracted service incrementally without a risky big-bang rewrite.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why premature decomposition creates a Distributed Monolith.

Poorly chosen boundaries turn nanosecond in-memory calls into 2–10 ms network hops, replace ACID transactions with Sagas, and yield composite availability drops (5 synchronous 99.9% services = $0.999^5 \approx 99.5\%$ availability).

Two anti-patterns dominate failed migrations: Distributed Monolith (services share a DB schema or deploy in lockstep) and Chatty RPC Fan-Out (30 sequential N+1 calls per request).

Database-Per-Service Rule

Forbid cross-service SQL joins or shared tables; expose read projections via events or versioned APIs.

Backward-Compatible Schemas

Enforce Protobuf/Avro evolution rules in a Schema Registry so producers and consumers deploy independently.

STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Decoupling Synchronous Writes with Outbox + Retry Budgets.

Replace cross-service synchronous RPC chains with Transactional Outbox events and cap retry budgets at 10% in Envoy to prevent cascading retry storms.

# Envoy Strangler Fig Route + Retry Budget Guardrail
routes:
  - match: { prefix: "/api/v2/invoices" }
    route:
      cluster: billing_service_v2
      timeout: 1.5s
      retry_policy:
        retry_on: "5xx,reset,connect-failure"
        num_retries: 2
        retry_host_predicate:
          - name: envoy.retry_host_predicates.previous_hosts

Alternatives: Modular Monolith vs. Microservices vs. Async Event-Driven.

Balance operational complexity against independent scaling and fault isolation.

ChoiceWhat it buysWhat it costs
Modular MonolithIn-process ACID transactions, zero network latency, single deployment pipeline.Shared runtime blast radius (one OOM kills the process) and coupled scaling.
Microservices (Sync + Async)Fault isolation (Recommendations leak cannot crash Checkout DB) and independent scaling.Distributed tracing, mTLS, eventual consistency, and tail-latency amplification.
06
STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Event-Driven Bounded Contexts + Saga Coordination.

In mature microservice architectures, synchronous RPCs are reserved for read queries or edge aggregation (BFFs), while cross-domain state changes flow through Transactional Outbox -> Kafka and Saga compensations.

Extraction Readiness

Modular Boundary -> Outbox Decoupling -> Independent Service

Always decouple the database schema inside the monolith before extracting the compute process.
