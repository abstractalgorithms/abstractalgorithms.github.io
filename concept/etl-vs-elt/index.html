ETL vs
ELT Pipelines.

ETL transforms raw data on dedicated compute servers before loading it into a target warehouse, whereas ELT loads raw data directly into scalable cloud storage and transforms it in-place using warehouse SQL/compute.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Modern cloud data platforms favor ELT for schema agility and raw-history replayability, reserving pre-load ETL for strict PII redaction, high-frequency stream aggregation, and regulatory compliance.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Choosing between ETL and ELT dictates your data platform's cost structure, schema evolution speed, and compliance posture. Traditional ETL (Informatica, Talend, Spark pre-load jobs) protected expensive, compute-constrained on-premise databases (Oracle, Teradata) by cleaning data before ingestion—but any change in business logic meant re-running upstream pipelines from source systems. Modern cloud warehouses (Snowflake, BigQuery, Databricks) separate storage (~20–20–20–23/TB/month) from elastic compute, making ELT (Fivetran/Airbyte + dbt) the default: land raw JSON/Parquet immediately, then transform with version-controlled SQL.

  • Order of operations: ETL runs Extract -> Transform -> Load (curated schema first); ELT runs Extract -> Load -> Transform (raw schema first, curated models later).
  • Compute engine: ETL relies on external transformation engines (Apache Spark, Flink, Informatica); ELT pushes transformations down into the target MPP engine (Snowflake SQL, BigQuery, Trino).
  • Replayability: ELT preserves raw immutable staging tables (bronze layer), allowing engineers to fix a buggy SQL join and re-materialize silver/gold tables without touching upstream APIs.
  • PII & Governance: ETL can tokenize or drop sensitive columns in flight before persistence; ELT requires column-level masking, tokenization UDFs, or a pre-load redaction proxy.
  • Medallion architecture: Modern lakehouses blend both—lightweight ETL/CDC (Debezium + Kafka) lands clean Avro/Parquet into Bronze, then dbt/Spark ELT builds Silver and Gold.

Good candidates

  • Use ELT when landing data into elastic cloud warehouses or lakehouses (Snowflake, BigQuery, Redshift, Iceberg) where analytical requirements evolve weekly.
  • Use ELT when data scientists and analysts need access to raw, untransformed event payloads to backfill new metrics without re-extracting from OLTP databases.
  • Use ETL when strict regulatory rules (GDPR, HIPAA, PCI-DSS) forbid raw PII, PANs, or unmasked health records from ever touching the destination data lake.

Think twice

  • Avoid pure ELT for raw IoT telemetry emitting 500k+ events/sec of noisy sensor readings where pre-filtering/downsampling (ETL) cuts warehouse ingestion and storage bills by 80%.
  • Avoid heavyweight ETL clusters for simple SaaS-to-warehouse replication (Salesforce, Stripe, HubSpot) where managed ELT connectors + dbt models deploy in hours.
  • Avoid ELT when the target database is a legacy OLTP or constrained on-prem appliance that cannot absorb large MERGE or JOIN workloads without starving transactional queries.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA retail platform ran nightly PySpark ETL jobs on EMR to join PostgreSQL orders with Stripe payouts before loading Redshift. Adding a single attribution column took 4 days of pipeline rewrites and backfills.

The idea

Every analytical pipeline performs three verbs: Extract bytes from operational sources (Postgres, Kafka, SaaS APIs), Transform them (deduplicate, cast types, mask PII, join dimensions), and Load them into an analytical store. The sole architectural distinction between ETL and ELT is where and when Transform runs.

In ETL, transformation happens in flight on a dedicated external cluster (Spark, Informatica, AWS Glue) before the target database ever sees a row. In ELT, raw data is loaded immediately into a cloud warehouse or lakehouse (Snowflake, BigQuery, Databricks), and transformations execute in place via distributed SQL or DataFrame engines (dbt, Spark SQL).

Concrete walkthrough

Trace a 50-million-row daily order stream from PostgreSQL to a BI dashboard under hybrid ELT (Medallion):

  1. Extract & Load (Debezium + Kafka -> Iceberg Bronze): Debezium reads Postgres WAL logical replication slots and emits change events to Kafka. A lightweight sink writes raw Parquet files into an Apache Iceberg bronze.orders_raw table partitioned by _ingested_date with zero business joins.
  2. In-Place Transform 1 (dbt Silver): Every 15 minutes, a dbt incremental model reads new Bronze rows using _ingested_ts > max(target._ingested_ts), deduplicates by (order_id, updated_at DESC), casts currency cents to DECIMAL(12,2), and writes silver.orders_clean.
  3. In-Place Transform 2 (dbt Gold): A downstream dbt model joins silver.orders_clean with silver.customers and silver.fx_rates to materialize gold.daily_revenue_by_region, running not_null and unique schema tests before Looker/Tableau queries it.

Modern ELT with a thin pre-load compliance guard: raw history lands cheaply in Bronze while versioned dbt SQL transforms data into tested Gold marts.

Why cloud economics flipped ETL to ELT

Two hardware shifts made ELT dominant over the last decade:

  1. Decoupled Storage & Compute: In legacy appliances, disk and CPU scaled together—storing 50 TB of raw JSON meant buying expensive database nodes. On S3/GCS + Snowflake/BigQuery, storing 50 TB of compressed Parquet costs ~$1,150/month, while compute spins up only during query execution.
  2. MPP Vectorized Execution: Modern columnar engines execute vectorized SIMD scans over Parquet/micro-partitions at gigabytes per second per node. Pushing JOIN and GROUP BY into the warehouse avoids serializing terabytes out over the network to an external ETL cluster and back.

Failure modes

  • Unbounded Backfill Costs: Re-running a full-refresh dbt DAG over 5 years of unpartitioned event logs can spike monthly warehouse spend by 5x. Always partition by event timestamp and test backfills on a 7-day slice first.
  • GDPR Deletion Gaps: Deleting a user from Postgres does not erase their historical snapshots in Bronze Iceberg/S3 files. Implement periodic Iceberg DELETE + rewrite_data_files compaction or crypto-shredding (per-user KMS keys).
  • Circular Model Dependencies: Without DAG linting, analysts build gold_a -> silver_b -> gold_a cycles or reference Bronze directly from dashboards, bypassing quality checks.

Production patterns: Data contracts and testing

To prevent ELT from turning into an unmaintainable tangle of SQL views, enforce software engineering rigor on transformations:

  • Data Contracts: Validate producer schemas at the Kafka/API boundary using Protobuf or JSON Schema with backward compatibility.
  • Staging -> Intermediate -> Marts: Enforce strict layering via dbt directory rules so BI tools only query gold mart tables.
  • Automated Quality Gates: Run not_null, unique, accepted_values, and freshness SLAs (warn_after: 30m, error_after: 2h) in CI/CD before merging any SQL model change.

Practical checklist

  • Classify data sensitivity first: redact or tokenize regulated PII (SSN, PAN, PHI) before persistence if compliance requires it.
  • Land raw data in an immutable, append-only bronze layer with _ingested_at and _source_system metadata columns.
  • Configure incremental MERGE models with a 2–3 day lookback window to capture late-arriving mobile/webhook events.
  • Partition large tables (>100 GB) by date and cluster by high-cardinality filter keys (tenant_id, user_id).
  • Add automated dbt schema tests (unique, not_null, referential integrity) and freshness monitors on every Gold table.
  • Set hard compute quotas and auto-suspend timers on transformation warehouses to prevent runaway SQL bills.
03 / Engineering trade-offs

Weighing architectural decisions

Time-to-Insight & Schema Agility

Advantage: ELT lands raw data in minutes; analysts write SQL transformations on demand without waiting for data engineering sprints.

Drawback: Raw landing zones can quickly devolve into an undocumented 'data swamp' without strict dbt testing, ownership, and catalog governance.

Compute & Storage Economics

Advantage: ETL drops unused columns and aggregates noisy logs before load, minimizing destination storage and egress.

Drawback: ELT duplicates data across Bronze/Silver/Gold layers and can incur runaway warehouse credit bills if unoptimized `dbt run` models scan full multi-terabyte tables.

Data Privacy & Compliance

Advantage: ETL enforces tokenization, masking, and row filtering in transit before sensitive data is written to analytical storage.

Drawback: ELT stores raw payloads at rest first, expanding the blast radius of a warehouse permission misconfiguration.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Runaway Warehouse Compute in ELT

A `dbt run` schedule executes full-table refreshes every 15 minutes on a 10 TB event table instead of incremental `MERGE` models, burning thousands of dollars in Snowflake/BigQuery slots.

What helps: Use incremental materializations partitioned by `event_date`, enforce cluster keys, and set warehouse resource monitors with hard credit caps.

Upstream Schema Drift Breaking Rigid ETL

An upstream microservice renames or adds a JSON field; a brittle ETL Spark job with a hardcoded Avro/SQL schema fails at 03:00 AM, halting all downstream dashboards.

What helps: In ELT, land semi-structured payloads in `VARIANT`/`JSON` columns, use schema-registry compatibility checks (`BACKWARD`), and alert on unexpected null rates.

PII Leakage into Raw ELT Staging

A developer enables 'sync all columns' on a Fivetran/Debezium connector, inadvertently replicating `password_hash`, `ssn`, or `credit_card_token` into an analyst-accessible raw schema.

What helps: Maintain explicit column allowlists at the ingestion connector and apply automated PII scanners (e.g., BigQuery DLP, Snowflake Horizon) on landing schemas.

Silent Late-Arriving Data Skew

Mobile clients buffer offline events for 48 hours; an incremental ETL/ELT job filtering only `WHERE created_at >= yesterday` permanently misses late events.

What helps: Use a rolling lookback window (e.g., `event_ts >= current_date - 3 days`) keyed on ingestion timestamp (`_loaded_at`) during incremental merges.

05 / Practical checklist

Avoid these mistakes

  • Treating ELT as an excuse to skip data modeling—querying raw JSON blobs directly from BI tools instead of building tested Silver/Gold tables.
  • Running heavy row-by-row Python UDFs inside a SQL warehouse during ELT instead of using native vectorized SQL or external Spark.
  • Failing to deduplicate CDC/webhook retries (`at-least-once` ingestion), which inflates revenue metrics by 2x during upstream hiccups.
  • Putting business logic in both the ingestion ETL script AND downstream dbt SQL, creating two conflicting sources of truth.
  • Ignoring GDPR 'Right to be Forgotten' delete propagation across immutable Bronze Parquet/Iceberg snapshots.
