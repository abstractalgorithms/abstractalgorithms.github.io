ETL vs. ELT
Data Pipelines.

ETL transforms raw data on dedicated compute servers before loading it into a target warehouse, whereas ELT loads raw data directly into scalable cloud storage and transforms it in-place using warehouse SQL/compute.

STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is ETL vs. ELT.

Why this matters: The mechanism: understand how ETL vs. ELT works from first principles.

Every analytical pipeline performs three verbs: Extract bytes from operational sources (Postgres, Kafka, SaaS APIs), Transform them (deduplicate, cast types, mask PII, join dimensions), and Load them into an analytical store. The sole architectural distinction between ETL and ELT is where and when Transform runs.

In ETL (Extract → Transform → Load), transformation happens in flight on a dedicated external cluster (Spark, Flink, Informatica, AWS Glue) before the target database sees a row. In ELT (Extract → Load → Transform), raw JSON/Parquet is loaded immediately into a cloud warehouse or lakehouse (Snowflake, BigQuery, Iceberg), and transformations execute in place via distributed SQL or DataFrame engines (dbt, Spark SQL).

Execution Order

ETL (Transform In-Flight) vs. ELT (Land Raw, Transform In-Place)

ETL cleans data before persistence to protect the target store; ELT persists immutable raw history first so SQL transforms can be replayed anytime.

Why Cloud Economics Flipped ETL to ELT.

Why this matters: The problem: see what breaks without Why Cloud Economics Flipped ETL to ELT under real concurrency or scale.

Think of Why Cloud Economics Flipped ETL to ELT as the intuition layer for ETL vs. ELT Data Pipelines: The problem: see what breaks without Why Cloud Economics Flipped ETL to ELT under real concurrency or scale.

Traditional ETL protected expensive, compute-constrained on-premise appliances (Oracle, Teradata) by cleaning and aggregating data before ingestion—but any change in business logic meant re-running upstream pipelines from source systems. Modern cloud warehouses separate cheap object storage (~$20–$23/TB/month) from elastic compute, making ELT (Airbyte/Debezium + dbt) the default: land raw payloads in minutes and iterate on SQL models without touching upstream APIs.

Problem
How to implement ETL vs. ELT Data Pipelines without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
To keep storage layouts predictable as data grows, modern cloud data platforms favor ELT for schema agility and raw-history replayability, reserving pre-load ETL for strict PII redaction, high-frequency stream aggregation, and regulatory compliance.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

Raw-History Replayability

ELT preserves immutable staging tables (bronze layer). If a SQL join has a timezone bug, engineers fix the dbt model and re-materialize silver/gold tables without re-extracting from OLTP databases.

Compliance & Volume Boundaries

Pure ELT fails when GDPR/HIPAA forbids raw SSNs or PANs from touching the lakehouse, or when 500k+ events/sec of noisy IoT telemetry must be downsampled before warehouse ingestion.

Production pipelines prevent runaway warehouse bills and late-data skew by using rolling lookback windows keyed on _loaded_at in incremental dbt models, paired with explicit column allowlists or deterministic HMAC tokenization in pre-load ETL.

Incremental ELT Merges & Pre-Load PII Redaction

-- models/silver/orders_clean.sql (dbt incremental ELT with 3-day late-data lookback)
{{ config(
    materialized='incremental',
    unique_key='order_id',
    partition_by={'field': 'event_date', 'data_type': 'date'},
    incremental_strategy='merge'
) }}

WITH ranked AS (
  SELECT
    payload:order_id::STRING AS order_id,
    (payload:amount_cents::NUMBER / 100.0)::DECIMAL(12,2) AS amount_usd,
    DATE(payload:created_at::TIMESTAMP_NTZ) AS event_date,
    _ingested_at,
    ROW_NUMBER() OVER (
      PARTITION BY payload:order_id::STRING
      ORDER BY payload:updated_at::TIMESTAMP_NTZ DESC
    ) AS rn
  FROM {{ source('bronze', 'orders_raw') }}
  {% if is_incremental() %}
    WHERE _ingested_at >= DATEADD(day, -3, (SELECT MAX(_ingested_at) FROM {{ this }}))
  {% endif %}
)
SELECT order_id, amount_usd, event_date, _ingested_at
FROM ranked WHERE rn = 1;

High-scale data platforms blend both patterns: a lightweight CDC/ETL proxy strips or tokenizes PII in flight and lands immutable Parquet into Iceberg Bronze, while dbt runs incremental SQL transformations to materialize Silver and Gold tables.

Medallion Architecture

Hybrid CDC Pre-Filter + Iceberg Bronze/Silver/Gold

1.Pre-Load Guard: Debezium/Beam drops password_hash and HMAC-tokenizes SSNs before S3 persistence.

2.Bronze Replay: Raw events stay immutable in Iceberg so buggy Silver/Gold SQL can be backfilled anytime.

3.Cost Control: Partitioned incremental MERGEs with 3-day lookback avoid 10 TB full-table scans.

Use lightweight ETL at the ingestion boundary for PII and noise reduction, and ELT inside the lakehouse for agile business modeling.
