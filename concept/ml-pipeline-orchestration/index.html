STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is ML Pipeline Orchestration.

Why this matters: The mechanism: understand how ML Pipeline Orchestration works from first principles.

ML pipeline orchestration models ingestion, data validation, feature engineering, distributed training, evaluation, and model registration as a Directed Acyclic Graph (DAG) of idempotent tasks keyed by logical execution date (ds) or dataset snapshot.

Crucially, the orchestrator acts strictly as the control plane—passing lightweight immutable object-storage URIs (s3://bucket/run_id/features.parquet) rather than raw DataFrames.

Control vs Data Plane

URI-Based ML Training DAG (CPU Prep -> Gate -> GPU Train)

Decoupling CPU preprocessing from GPU nodes prevents $2–$4/hr GPUs from sitting idle during SQL/Spark joins.

STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why cron scripts, XCom DataFrames, and training-serving skew fail.

Why this matters: The problem: see what breaks without Why cron scripts, XCom DataFrames, and training-serving skew fail under real concurrency or scale.

Ad-hoc bash/cron pipelines fail silently when upstream schemas drift, waste expensive GPU hours waiting on CPU joins, and cannot reproduce a model from 3 months ago.

Two classic failure modes: Orchestrator DB Bloat (serializing DataFrames via Airflow XCom crashes Postgres) and Training-Serving Skew (offline Spark/SQL transforms diverge subtly from online Python/Go inference code).

Engineering Decision Framework
Problem
How to implement ML Pipeline Orchestration without hitting unbounded tail latency, state divergence, or operational fragility.
Naive Solution
Use a single unpartitioned path with unbounded retries and synchronous global coordination.
Why It Fails
Global coordination serializes throughput under load, while unbounded retries amplify transient stalls into full outages.
Alternatives
Compare synchronous strict-consistency paths against bounded asynchronous replication, local caching, or partitioned ownership.
Engineering Decision
If model quality drifts from offline training baselines, separate control-plane orchestration from data-plane compute: pass immutable S3/GCS artifact URIs between tasks, never raw DataFrames, and decouple CPU preprocessing from GPU training.
Trade-Offs
Gains predictable p99 latency and fault isolation in exchange for explicit bounding, observability, and slightly higher implementation complexity.

# Pass immutable S3 URIs (<4 KB metadata), never raw DataFrames
def validate_and_register(features_uri: str, run_id: str) -> str:
    df = load_parquet_sample(features_uri)
    assert df["label"].isna().mean() < 0.01, "Label null spike detected before GPU allocation"
    manifest_uri = f"s3://ml-artifacts/{run_id}/validated_manifest.json"
    write_json(manifest_uri, {"features_uri": features_uri, "rows": len(df)})
    return manifest_uri
