THE BIG IDEA / Key takeaway · CONCEPT GUIDE

DNS is a pull-based, heavily cached control plane—even with a 30 s TTL, stubborn OS, browser, and JVM caches make instant DNS-only failover impossible without Anycast or edge proxies.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

DNS is the first network hop for virtually every user request. Misconfigured TTLs, missing apex records, or naive round-robin DNS can route European users to US-West servers, pin traffic to dead regions for hours after an outage, or overwhelm a backup cluster during failover.

  • Standard DNS runs over UDP port 53 (512-byte classic limit, raised to 1232–4096 bytes via EDNS0) with TCP fallback for large responses/DNSSEC; DoT (port 853) and DoH (port 443) encrypt queries.
  • Anycast BGP announces the same IP prefix from dozens of edge POPs worldwide so BGP routes users to the topologically nearest edge, while GeoDNS/Latency DNS returns different IPs per region.
  • EDNS Client Subnet (ECS, RFC 7871) forwards a truncated client /24 IPv4 or /56 IPv6 prefix from the recursive resolver to the authoritative DNS server so GeoDNS routes to the user's region, not the resolver's.
  • RFC 1034 forbids a CNAME at the zone apex (example.com) alongside SOA/NS records; providers work around this with ALIAS / ANAME / CNAME flattening.
  • Negative caching (NXDOMAIN) is governed by the SOA record's minimum TTL field—a high SOA minimum can prolong an outage long after a deleted record is restored.

Good candidates

  • Steering global users to the closest healthy regional load balancer via latency-based or GeoDNS policies.
  • Performing gradual blue/green traffic shifts or weighted canary rollouts (e.g., 95% v1 / 5% v2) across independent clusters.
  • Implementing multi-cloud or multi-region disaster recovery failover when an entire cloud region goes dark.

Think twice

  • Sub-second per-request load balancing or instant connection draining across backend pods (use L4/L7 proxies like Envoy, HAProxy, or ALB).
  • Fine-grained A/B testing or user-session stickiness (DNS sees the recursive resolver's IP, not individual browser sessions).
  • Enforcing instant emergency cutovers if clients are legacy JVMs or IoT devices that ignore low TTLs.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn application runs active-active in us-east-1 and eu-west-1 behind latency-based DNS (TTL = 60 s) with HTTPS health checks polling /healthz every 30 s.

The idea

DNS traffic routing turns hostname resolution from a static phonebook into a programmable, health-aware steering layer. When a client resolves api.example.com, the query traverses a Stub Resolver (OS/browser) to a Recursive Resolver (ISP, 1.1.1.1, 8.8.8.8), which walks the hierarchy—Root (.) → TLD (.com) → Authoritative Nameserver—and caches the answer for TTL seconds.

Modern authoritative DNS providers (Route 53, Cloudflare, NS1) evaluate routing policies dynamically at query time: Latency/GeoDNS inspects the client's IP (or EDNS Client Subnet /24) to pick the nearest region, Health Checks remove unreachable endpoints, and Weighted Routing distributes percentages across clusters. For sub-second responsiveness without DNS cache lag, global networks pair DNS with Anycast BGP, where dozens of edge POPs announce the exact same IP so internet routers steer packets to the closest POP automatically.

Concrete walkthrough

Trace a user in Bengaluru (103.21.58.44) connecting to api.example.com (TTL = 60 s, Latency-Based + Failover policy across ap-south-1 Mumbai and ap-southeast-1 Singapore):

  1. Cache Check: Chrome checks its local DNS cache and OS stub resolver; on a miss, it sends an A + AAAA query to its recursive resolver (8.8.8.8) over UDP/53 (or DoH/443).
  2. EDNS Client Subnet (ECS): On a recursive cache miss, 8.8.8.8 queries the authoritative nameserver for example.com, attaching ECS = 103.21.58.0/24 (masking the last octet for privacy).
  3. Policy & Health Evaluation: The authoritative server matches 103.21.58.0/24 to ap-south-1 (18 ms RTT vs. 65 ms to Singapore). It verifies that ap-south-1's deep /healthz check (which tests DB connectivity) is HEALTHY.
  4. Response & Caching: The authoritative server returns A 13.234.10.5 with TTL = 60. 8.8.8.8 caches it for 60 s and returns it to Chrome.
  5. Regional Failover: If ap-south-1 fails 3 consecutive 30-second health checks, the authoritative server marks it UNHEALTHY and begins returning Singapore's IP (54.169.22.8). Existing users finish draining over 60–180 s as caches expire.

DNS steers new resolutions via ECS and health checks, while Anycast BGP and edge proxies absorb cache lag for active connections.

Anycast BGP vs. DNS-based steering

Understanding the boundary between Layer-3 Anycast BGP and Layer-7/DNS steering is essential for global architectures:

  • Anycast BGP assigns the exact same IP address (e.g., 1.1.1.1) to servers in 200+ cities. Border Gateway Protocol (BGP) routers on the internet naturally forward packets along the shortest AS-path. If a POP goes offline, BGP withdraws its route announcement within seconds—requiring zero DNS TTL expiration.
  • DNS Steering returns different IP addresses per region. It excels at directing traffic to distinct cloud regions (us-east-1 vs. eu-west-1) without needing your own BGP ASN, and supports fine-grained weighted splits. Most large platforms combine both: DNS points to an Anycast CDN/edge, and the edge routes over private backbones to healthy regional origins.

Failure modes

  • Stale Resolver & Connection Pooling: Even with TTL = 30 s, HTTP/2 and gRPC clients keep existing TCP connections open to the old IP for minutes or hours until a write fails. Mitigation: Pair DNS failover with server-side GOAWAY / connection max-age (300 s) and client-side retry on UNAVAILABLE.
  • Authoritative DNS Provider Outage: If your single DNS provider suffers a control-plane or DDoS outage and your TTLs are 30 s, caches expire rapidly and your entire site becomes unreachable. Mitigation: Use dual-provider authoritative DNS (NS delegation across two vendors) or keep static records at 3600 s+.
  • Split-Horizon DNS Drift: Internal VPCs resolve api.example.com to private IPs (10.x.x.x) while public DNS resolves to public IPs; out-of-sync changes break internal service calls. Mitigation: Manage both public and private hosted zones via unified Infrastructure-as-Code (Terraform/OpenTofu) with automated diff checks.
  • DNSSEC Misconfiguration: Rotating keys without updating the parent zone's DS record causes validating resolvers (8.8.8.8, 1.1.1.1) to return SERVFAIL globally. Mitigation: Use managed automated DNSSEC key rollovers and validate DS chains before cutover.

Pre-migration TTL lowering and health-check design

When migrating an IP or load balancer, lowering the TTL at the moment of cutover does nothing for clients that already cached the old 3600 s record—they will continue hitting the old endpoint for up to an hour. Standard runbooks lower TTLs to 60 s at least 24 hours before the migration, execute the IP swap, verify metrics, and raise the TTL back to 300–3600 s afterward.

Similarly, DNS health checks must be deep enough to catch real failures (e.g., verifying local DB/cache reachability) without being so brittle that a transient downstream hiccup flaps DNS globally. Require 3 consecutive failures at 30 s intervals before flipping a region unhealthy.

Practical checklist

  • Lower record TTLs to 30–60 s at least 24 hours before any planned IP or load-balancer migration.
  • Set the SOA minimum (negative caching) TTL to 60–300 s so accidental NXDOMAIN responses recover quickly.
  • Use ALIAS / ANAME / CNAME flattening at the zone apex (example.com) instead of invalid apex CNAME records.
  • Configure JVM and long-lived HTTP/gRPC clients with explicit DNS cache TTLs (30 s) and connection max-age limits.
  • Test regional failover regularly with chaos drills to verify standby capacity and health-check thresholds.
03 / Engineering trade-offs

Weighing architectural decisions

Low DNS TTL (30–60 s) vs. High DNS TTL (3600–86400 s)

Advantage: Low TTLs allow faster traffic shifts during regional outages or migrations.

Drawback: Low TTLs increase recursive lookup frequency (adding 20–100 ms cold-lookup latency), raise authoritative DNS query bills, and fail open if the authoritative provider suffers an outage.

Anycast BGP Edge vs. GeoDNS / Latency-Based DNS

Advantage: Anycast enables sub-second edge routing and DDoS absorption at a single static IP with zero client-cache staleness.

Drawback: BGP routing changes can theoretically reset long-lived TCP connections mid-flight, and operating global Anycast requires an ASN and multi-POP edge presence (or a CDN).

DNS-Level Weighted Routing vs. L7 Gateway Canary

Advantage: Weighted DNS splits traffic across completely separate cloud providers or regions with zero shared proxy hop.

Drawback: Because corporate NATs and public resolvers cache answers per resolver, a 5% DNS weight can actually send 20% of real user traffic if a large ISP hits the canary record.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Stubborn Client & JVM DNS Pinning

Older or misconfigured JVMs cache DNS forever (`networkaddress.cache.ttl=-1` when SecurityManager is active) or OS/ISP resolvers clamp minimum TTLs to 300 s, sending traffic to a dead IP.

What helps: Explicitly set `-Dsun.net.inetaddr.ttl=30` in JVM services, front origins with Anycast edge proxies, and keep old IPs draining gracefully.

Cascading Failover Overload

Region A fails and DNS shifts 100% of Region A's traffic to Region B, which is only provisioned for 60% headroom, crashing Region B too.

What helps: Pre-provision N+1 failover capacity, apply progressive load shedding at Region B's ingress, or split failover across multiple healthy regions.

Missing EDNS Client Subnet (ECS) Misrouting

A user in Mumbai uses a privacy-focused resolver that strips ECS; the authoritative server sees an out-of-region resolver IP and routes the user to Frankfurt.

What helps: Use Anycast BGP at the edge (which routes by the user's actual IP packet, independent of DNS resolver location) or deploy regional edge POPs.

NXDOMAIN Negative Caching Outage

A Terraform typo briefly deletes `api.example.com` for 20 seconds. Resolvers cache `NXDOMAIN` for the `SOA` minimum TTL (e.g., 3600 s), keeping users down for an hour after the fix.

What helps: Keep the `SOA` minimum/negative-caching TTL low (60–300 s) and protect critical DNS records with change-approval gates.

05 / Practical checklist

Avoid these mistakes

  • Attempting to create a `CNAME` record at the root/apex domain (`example.com`), breaking `MX` and `NS` resolution instead of using `ALIAS`/`ANAME` flattening.
  • Setting a `0 s` or `5 s` DNS TTL expecting instant failover, while ignoring ISP minimum-TTL clamping and browser connection pooling.
  • Pointing a health check at a shallow `/ping` endpoint that returns `200 OK` even when the region's database is down, leaving DNS routing into a broken region.
  • Using DNS round-robin without active health checks, causing 50% of users to hang on TCP timeouts when one server dies.
  • Forgetting to lower TTLs from `3600 s` to `60 s` at least 24 hours *before* a planned IP migration.
