Read Repair
& Anti-Entropy.

Read repair and anti-entropy background repair heal divergent replicas in eventually consistent distributed stores—read repair fixes stale keys on the hot read path, while anti-entropy reconciles entire key ranges offline using Merkle trees.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Use read repair for fast, opportunistic healing of hot keys during `QUORUM` reads, and schedule periodic Merkle-tree anti-entropy repairs (`nodetool repair`) faster than `gc_grace_seconds` (e.g., < 10 days) to prevent deleted tombstones from resurrecting.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

In AP/leaderless databases like Cassandra, ScyllaDB, DynamoDB-style rings, and Riak, network partitions and node restarts inevitably leave replicas out of sync. Without both read repair and anti-entropy, cold data rots silently and expired tombstones can resurrect deleted records ('zombie data').

  • Blocking (synchronous) read repair compares a full data read from 1 replica against cryptographic digests from R-1 replicas; on mismatch, it fetches full values, resolves by timestamp/version vector, and writes the winner back before returning.
  • Asynchronous read repair returns the response immediately after CL=ONE or QUORUM and repairs divergent replicas in the background.
  • Hinted handoff buffers missed writes for a brief outage (typically max_hint_window = 3h), but is a best-effort optimization—not a substitute for anti-entropy.
  • Anti-entropy (e.g., Cassandra nodetool repair) builds Merkle trees over token ranges on each replica, exchanging hashes to pinpoint divergent key buckets in O(log N) network traffic.
  • Tombstone resurrection occurs if a node misses a delete and isn't repaired before gc_grace_seconds (default 10 days / 864,000s) purges the tombstone on peers.

Good candidates

  • Leaderless or multi-master quorum stores (N=3, W=2, R=2) where any replica can accept writes while peers are temporarily unreachable.
  • Read-heavy workloads needing low-overhead healing of active keys via digest comparison on quorum reads.
  • Operational clusters requiring full-dataset convergence across cold keys, dropped hints, and tombstone cleanup.

Think twice

  • Single-leader strongly consistent systems (PostgreSQL synchronous replication, Spanner, Raft/Paxos) where followers apply an ordered WAL/log.
  • Read-repair on CL=ONE reads if strict latency predictability is required and background repair is already frequent—though probabilistic repair is still helpful.
  • Running full-cluster anti-entropy repairs during peak traffic without I/O throttling, which saturates disk compaction and network bandwidth.

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA 12-node Cassandra cluster (RF=3, gc_grace_seconds=864000) had a node down for 4 hours during a DELETE wave, exceeding max_hint_window_in_ms (3h). nodetool repair had been disabled for 3 weeks.

The idea

In leaderless replicated databases (Dynamo-style rings like Cassandra, ScyllaDB, and Riak), there is no single primary log ordering every write. If a replica is temporarily unreachable during a QUORUM write, it misses the mutation. Two complementary mechanisms restore convergence:

  • Read repair (hot path): Opportunistically detects and heals divergent replicas during normal client reads using lightweight digest comparisons.
  • Anti-entropy repair (background): Proactively scans all key ranges—including cold data never touched by reads—using Merkle trees to find and stream missing mutations before tombstones expire.

Concrete walkthrough

Trace a LOCAL_QUORUM (R=2 of RF=3) read on key user:42 where Replica A and B hold v2 (ts=200) and Replica C missed the write and holds v1 (ts=100):

  1. Digest optimization: The coordinator sends a full data read to the fastest replica (Replica A) and a cryptographic digest request to Replica C.
  2. Mismatch detected: Replica A returns {val: v2, ts: 200, digest: 0x9f} while Replica C returns {digest: 0x3a} (0x9f != 0x3a).
  3. Full read & resolution: The coordinator requests the full row from Replica C, compares timestamps (ts=200 > ts=100), and selects v2 as the winner.
  4. Blocking repair write: The coordinator issues a repair write of v2 (ts=200) to Replica C and awaits acknowledgment before returning v2 to the client.
  5. Cold-key safety net: For keys never read, a weekly Merkle-tree anti-entropy job exchanges tree hashes between A, B, and C, streaming only the mismatched token sub-ranges.

Digest reads keep normal-path bandwidth low while blocking read repair ensures stale replicas converge before the client sees the response.

Merkle trees, hints, and tombstone lifecycle

  • Hinted handoff: When Replica C is down for a few minutes, the coordinator stores a local hint (up to max_hint_window = 3h) and replays it once C recovers. If C stays down longer or the coordinator crashes, hints are lost.
  • Merkle tree anti-entropy: Each replica builds a binary hash tree over a token range (e.g., Cassandra uses depth 15 = 32,76832,76832,768 leaf buckets). Nodes compare root hashes; if equal, the range is in sync in O(1)O(1)O(1) network traffic. If unequal, they walk down differing branches and stream only the mismatched leaf ranges.
  • Tombstone safety: Deletes write a tombstone marker retained for gc_grace_seconds (default 10 days). Anti-entropy must complete across all replicas within this window so no node retains pre-delete values after peers purge the tombstone.

Failure modes

  • Zombie data resurrection: Missing an anti-entropy cycle beyond gc_grace_seconds allows stale replicas to re-inject deleted rows via read repair.
  • Clock-skew LWW data loss: Coordinator NTP drift causes older writes to carry higher timestamps, making read repair overwrite newer mutations.
  • Repair I/O starvation: Unthrottled Merkle tree validation scans all SSTables, triggering compaction backlogs and p99 read spikes.
  • Wide-partition Merkle bloat: A single 1 GB partition forces the entire leaf bucket to stream even when only 1 KB differs.

Production patterns & observability

  • Automated sub-range orchestration: Use tools like Cassandra Reaper or ScyllaDB Manager to split repairs into small token segments, pausing automatically when cluster latency or pending compactions spike.
  • Incremental repairs: Enable incremental repair (-inc in modern Cassandra 4.x+) so already-repaired SSTables are skipped on subsequent runs.
  • Alert on repair age: Track time_since_last_repair_seconds per keyspace and page if it exceeds 0.5 * gc_grace_seconds.

Practical checklist

  • Use LOCAL_QUORUM (R + W > RF) with blocking read repair for strong monotonic reads on active keys.
  • Schedule automated sub-range anti-entropy repairs at least every 3-5 days when gc_grace_seconds is 10 days.
  • Never set gc_grace_seconds = 0 on tables with DELETEs or TTL expirations.
  • Throttle repair streaming bandwidth and monitor compaction pending tasks during repair windows.
  • Enforce NTP/chrony sync (< 10 ms drift) across all coordinator and storage nodes if using LWW.
03 / Engineering trade-offs

Weighing architectural decisions

Blocking vs. Asynchronous Read Repair

Advantage: Blocking read repair guarantees monotonic reads—subsequent reads at `QUORUM` see the repaired value immediately.

Drawback: Adds an extra round-trip (fetching full rows + writing repairs) to tail latency whenever a mismatch occurs.

Incremental vs. Full Merkle Repair

Advantage: Incremental repair only hashes newly written SSTables, cutting repair CPU and disk I/O by 80-90%.

Drawback: Requires careful SSTable anti-compaction management and can complicate streaming during node replacements.

Last-Write-Wins (LWW) vs. Version Vectors

Advantage: LWW (Cassandra wall-clock timestamps) resolves conflicts in O(1) without client intervention.

Drawback: NTP clock skew between coordinators can silently discard newer writes; version vectors (Riak) preserve siblings but shift merge logic to clients.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Zombie Data (Tombstone Resurrection)

A replica misses a delete, peers purge the tombstone after `gc_grace_seconds`, and a subsequent read repair treats the stale value as live data.

What helps: Run full or incremental anti-entropy repair strictly within `gc_grace_seconds` (e.g., every 3-5 days for a 10-day grace period).

Merkle Tree Hash-Bucket Amplification

In large partitions/ranges, a fixed-depth Merkle tree (`depth=15`, 32,768 leaves) groups thousands of keys per leaf; a single stale key forces streaming an entire leaf bucket.

What helps: Use sub-range repairs (`-st` / `-et` token ranges via Cassandra Reaper) and keep partition sizes under 100 MB.

Coordinator Clock Skew Overwriting Newer Data

Under LWW conflict resolution, a coordinator whose clock is 2 seconds ahead stamps an older logical write with a higher timestamp, causing read repair to overwrite newer data.

What helps: Enforce strict NTP/chrony sync (`< 10 ms` drift) across all nodes and alert on clock-skew metrics, or use HLC/version vectors.

Repair-Induced Disk & Compaction Storm

Running unthrottled `nodetool repair` across all nodes simultaneously spikes disk reads for Merkle tree generation and floods SSTables.

What helps: Stagger sub-range repairs with an orchestrator (Reaper), throttle `stream_throughput_outbound`, and run during off-peak windows.

05 / Practical checklist

Avoid these mistakes

  • Relying solely on read repair for consistency—cold keys that are rarely read will never heal.
  • Assuming hinted handoff guarantees consistency; hints expire after `max_hint_window` (3 hours default) or drop on node crash.
  • Setting `gc_grace_seconds` to `0` on tables that receive `DELETE`s or TTLs, guaranteeing zombie resurrection on any transient outage.
  • Running `nodetool repair` simultaneously on every node in a ring, causing duplicate work and cluster-wide I/O saturation.
  • Using `CL=ONE` reads with `read_repair` disabled while expecting monotonic read-your-writes consistency.
