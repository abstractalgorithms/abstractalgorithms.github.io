CDN Architecture &
Geo-Distributed Edge Caching.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Edge caching is won or lost in HTTP cache headers and collapse controls: combine `s-maxage`, `stale-while-revalidate`, Origin Shielding, and request coalescing so a single cache miss never becomes a 10,000-RPS origin stampede.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

The speed of light in fiber (~200,000 km/s) imposes a hard ~150 ms round-trip floor between Bengaluru and Virginia. Because a standard TLS 1.2 + TCP handshake takes 3 RTTs before the first byte of HTTP data arrives, serving assets directly from a single origin adds 450+ ms of pure network tax. By terminating TLS 1.3 and HTTP/3 (QUIC) at an edge PoP 10 ms away and absorbing 95%+ of static and semi-dynamic reads, a CDN cuts tail latency by an order of magnitude and reduces origin egress bills by 70–90%.

  • BGP Anycast routes users to the topologically closest healthy edge PoP using a single shared IP; if a PoP fails, BGP withdraws the route and traffic shifts seamlessly within seconds.
  • Separating max-age (browser cache) from s-maxage (CDN shared cache) lets you cache aggressively at the edge (e.g., 24 hours) with instant surrogate-key purging while keeping browser TTLs short (60 seconds).
  • stale-while-revalidate serves slightly expired content immediately (0 ms wait) while asynchronously refreshing from origin in the background, eliminating user-facing cache-miss latency spikes.
  • Origin Shielding (a tiered mid-gress cache layer between 300+ edge PoPs and your origin) collapses 300 regional misses into 1 origin fetch, preventing origin overload during cold starts or global purges.
  • Cache-key hygiene is everything: uncontrolled Vary headers (e.g., Vary: User-Agent) or unstripped marketing query parameters (?utm_source=..., ?fbclid=...) fragment the cache key and tank hit ratios below 20%.

Good candidates

  • Serving static assets (JS/CSS bundles, images, fonts, HLS/DASH video segments) globally with sub-50 ms TTFB.
  • Offloading high-read, low-mutation APIs (product catalogs, public profiles, news feeds, feature flags) using Cache-Control: s-maxage and stale-while-revalidate.
  • Protecting origins against volumetric L3/L4/L7 DDoS attacks and flash-sale traffic spikes via Anycast absorption and edge WAF/rate limiting.

Think twice

  • Strongly consistent, user-mutated endpoints (account balances, shopping cart writes, checkout mutations) where stale reads cause financial or data-integrity bugs.
  • Private, uncacheable 1:1 WebSocket/gRPC streams with bespoke per-user payloads where edge caching adds zero hit ratio (though edge TLS termination and Argo/smart routing can still help).
  • Internal-only microservices communicating inside the same VPC/AZ where 0.5 ms east-west network hops make an external CDN hop counterproductive.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA high-traffic media site publishes breaking news updates every 2 minutes to 40M daily readers. Previously, Cache-Control: max-age=60 caused thousands of simultaneous edge misses every minute across 250 Cloudflare/Fastly PoPs.

The idea

A Content Delivery Network (CDN) is a globally distributed reverse-proxy tier that moves TLS termination, protocol optimization, and content caching to Points of Presence (PoPs) sitting at the network edge—often within 5–20 ms of end users.

Instead of every user traversing 15+ autonomous-system hops across oceans to reach a central origin, BGP Anycast announces the same IP prefix from hundreds of edge locations simultaneously. Routers naturally direct each user's packets to the topologically closest PoP, where HTTP/3 (QUIC) and TLS 1.3 0-RTT complete in minimal round trips. If the requested object is a cache hit, it returns immediately; if it is a miss, tiered Origin Shielding and request coalescing ensure the origin sees only a single consolidated fetch.

Concrete walkthrough

Trace what happens when a user in Bengaluru requests https://shop.example.com/api/v1/catalog/shoes?utm_source=ig:

  1. Anycast & Handshake (0–15 ms): DNS resolves shop.example.com to an Anycast IP. BGP routes the user to the Bengaluru or Chennai PoP. Using QUIC (HTTP/3) + TLS 1.3, connection setup completes in 1 RTT (or 0 RTT on repeat visits).
  2. Edge Normalization & Cache-Key Construction: Edge logic (Cloudflare Worker / Fastly VCL) strips ?utm_source=ig, normalizes Accept-Encoding to br, and computes the canonical cache key GET:shop.example.com:/api/v1/catalog/shoes:br.
  3. Tier-1 Edge Lookup & SWR: Suppose the edge PoP finds the entry expired 12 seconds ago, but the header specifies Cache-Control: public, max-age=30, s-maxage=3600, stale-while-revalidate=300. The PoP immediately returns the stale 200 OK payload to the user in 12 ms while firing an asynchronous background revalidation.
  4. Tier-2 Origin Shield & Collapsed Forwarding: The background revalidation routes to a designated Origin Shield PoP (e.g., Mumbai BOM). If 40 other regional PoPs simultaneously missed the same key, the shield coalesces all 40 misses into one conditional If-None-Match: "v42" request over a warm HTTP/2 connection to the origin.
  5. Conditional Revalidation (304 Not Modified): Origin checks the ETag, returns 304 Not Modified (0-byte body), and the shield/edge refresh the TTL for another 3,600 seconds.

Two-tier Anycast edge caching with Origin Shielding and stale-while-revalidate collapses global traffic spikes into minimal origin fetches.

Cache headers & invalidation mechanics

Mastering HTTP caching requires distinguishing between browser, shared CDN, and revalidation directives:

  • Cache-Control: public, max-age=60, s-maxage=86400: Tells the user's browser to cache for 60 seconds, while the CDN holds the object for 24 hours. This gives you fast global invalidation without trapping stale assets in user browsers.
  • stale-while-revalidate=300 & stale-if-error=3600: The former hides origin latency during routine refreshes; the latter keeps your site online during an origin 502/504 outage by serving cached content for up to an hour.
  • Surrogate-Control vs. Cache-Control: Fastly and Varnish honor Surrogate-Control exclusively at the CDN and strip it before sending to the browser, letting you set completely independent policies.
  • Tag-based purging (Surrogate-Key / Cache-Tag): Tagging every product response with product-123 category-shoes lets your backend invalidate all affected pages in <150 ms via a single API call when inventory or price changes.

Failure modes

  • Query-String Cache Busting: An ad campaign appends unique click IDs (?fbclid=xyz), turning a 99% cache hit rate into 0% and flooding the origin.
  • Cookie Poisoning on Static Routes: An analytics script sets a session cookie on the root domain, and default CDN rules bypass caching whenever a Cookie header is present.
  • Vary-Header Explosion: Returning Vary: * or Vary: User-Agent creates thousands of cache variants per URL, evicting hot objects from PoP RAM.
  • Stale Error Caching: Caching a transient 503 response because the origin omitted Cache-Control: no-store on error handlers.

Security & protocol optimization at the edge

Modern CDNs double as your network perimeter and protocol accelerator:

  • Authenticated Origin Pulls (mTLS): Configure your origin ALB/NGINX to reject all traffic that does not present the CDN's client certificate, closing the classic direct-to-IP DDoS bypass.
  • HTTP/3 (QUIC) + 0-RTT: Eliminates TCP head-of-line blocking on lossy mobile networks (3G/4G), cutting P95 mobile page load times by 15–30%.
  • Brotli (br) Level 11 Pre-Compression: Pre-compress static JS/CSS at build time with Brotli level 11 (15–20% smaller than gzip) and let the edge serve Content-Encoding: br directly.

Practical checklist

  • Separate browser (max-age) and CDN (s-maxage / Surrogate-Control) TTLs, and add stale-while-revalidate + stale-if-error on all cacheable routes.
  • Strip tracking query parameters (utm_*, fbclid, gclid) and unused cookies before cache-key computation.
  • Enable Origin Shielding and request coalescing (collapsed forwarding) to prevent origin stampedes on cold PoPs or purges.
  • Lock down the origin firewall/security group to accept traffic only from CDN IP ranges or mTLS Authenticated Origin Pulls.
  • Verify that authenticated endpoints (/api/me, /checkout) strictly return Cache-Control: private, no-store in automated integration tests.
03 / Engineering trade-offs

Weighing architectural decisions

Long Edge TTL + Active Purge vs. Short TTL

Advantage: Long `s-maxage` (hours/days) with `Surrogate-Key` invalidation maximizes hit ratio (>95%) and shields the origin during traffic surges.

Drawback: Requires reliable purge orchestration in your CMS/backend; a missed purge webhook leaves stale pricing or broken UI live until TTL expiry.

Edge Compute (Workers / Compute@Edge) vs. Origin Rendering

Advantage: Running A/B tests, JWT auth, and HTML fragment stitching at the edge avoids origin round trips and enables personalized responses from cached templates.

Drawback: Edge isolates have tight CPU/memory limits (e.g., 10–50 ms CPU time, 128 MB RAM) and cannot easily maintain persistent TCP connection pools to origin databases.

Multi-CDN Routing vs. Single CDN Vendor

Advantage: Protects against single-vendor global outages (e.g., BGP misconfigurations) and allows regional cost/latency optimization.

Drawback: Doubles operational complexity: VCL/Worker logic must be abstracted, cache-purge APIs diverge, and splitting traffic across two CDNs halves each CDN's cache warmth.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Cache-Key Fragmentation

Including `Cookie`, `Accept-Encoding` variations, `User-Agent`, or tracking parameters (`utm_*`, `gclid`) in the cache key creates millions of duplicate entries for the same object, collapsing hit rate and evicting hot items.

What helps: Normalize `Accept-Encoding` to `br`/`gzip`, strip all non-functional query parameters at the edge, and exclude cookies unless explicitly required for auth.

Thundering Herd / Cache Stampede

When a hot object expires or is purged, hundreds of concurrent requests at the same PoP see a miss and simultaneously hit the origin, causing a CPU/DB meltdown.

What helps: Enable request coalescing (collapsed forwarding) at both edge PoPs and Origin Shield, and serve stale responses via `stale-while-revalidate` and `stale-if-error`.

Private Data Leakage via Shared Cache

Misconfiguring the CDN to ignore `Set-Cookie` or cache responses containing `Authorization` headers without `Cache-Control: private` serves User A's account page to User B.

What helps: Default to `Cache-Control: private, no-store` on all authenticated routes, strip `Set-Cookie` on cacheable responses, and enforce automated CI tests checking response headers.

Origin-to-Edge Connection Exhaustion

Without Origin Shielding or persistent HTTP/2 origin connections, 300+ edge PoPs opening fresh TLS connections to the origin exhaust origin TLS handshakes and file descriptors.

What helps: Enable Origin Shielding, use HTTP/2 or persistent keep-alive pools between shield and origin, and enforce mTLS or authenticated origin pulls (Cloudflare Origin CA) to block bypass traffic.

05 / Practical checklist

Avoid these mistakes

  • Using `Cache-Control: no-cache` thinking it disables caching—it actually allows storing the response while forcing a conditional `If-None-Match` / `ETag` revalidation on every request (`no-store` is what forbids storage).
  • Purging the entire cache (`Purge Everything`) during deploys instead of using content-hashed filenames (`app.8f3a1c.js`) or targeted `Surrogate-Key` tags, triggering an immediate origin stampede.
  • Leaving the origin IP publicly reachable in DNS history or firewall rules, allowing attackers to bypass the CDN WAF and DDoS shield directly.
  • Caching 5xx or 404 error pages with long TTLs during a brief origin blip, prolonging a 5-second outage into a 30-minute user-facing failure.
  • Forgetting to forward `X-Forwarded-For` / `CF-Connecting-IP` or trusting them without validating the CDN's IP ranges, breaking rate limiting and geo-fencing.
