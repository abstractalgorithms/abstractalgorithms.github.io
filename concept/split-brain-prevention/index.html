Split-Brain
Prevention.

Split-brain happens when a network partition splits a distributed cluster into isolated groups that both elect a primary and accept conflicting writes; preventing it requires strict majority quorums (N/2 + 1), time-bounded leases, and monotonic fencing tokens.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Never rely on heartbeats alone to declare a peer dead—pair majority quorum (odd node count >= 3) with monotonic fencing tokens checked by the storage layer so a paused old primary can never corrupt data.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

A single 15-second split-brain event in a primary-replica database or distributed lock service allows two leaders to commit conflicting transactions (e.g., double-spending balances or diverging PostgreSQL LSNs), requiring painful manual data reconciliation or full cluster rebuilds.

  • Majority Quorum (floor(N / 2) + 1) guarantees any two quorums overlap in at least one node—3 nodes tolerate 1 failure, 5 nodes tolerate 2.
  • A 2-node cluster cannot form a safe majority quorum (half of 2 is 1); always deploy 3 nodes or add a lightweight Witness/Arbitrator in a 3rd failure domain.
  • Leases alone are vulnerable to asymmetric clock drift or long JVM/hypervisor pauses (a 20s GC pause outlives a 10s lease, leaving the old leader thinking it still holds the lock).
  • Fencing tokens (monotonically increasing epoch/term numbers issued by the consensus store) must be validated by the storage/target server to reject stale writes.
  • STONITH (Shoot The Other Node In The Head) uses out-of-band power/hypervisor APIs (IPMI, AWS EC2 StopInstances) to guarantee an unreachable node is truly dead before failover.

Good candidates

  • Operating stateful primary-replica databases (PostgreSQL via Patroni, MySQL Group Replication) with automated failover.
  • Building distributed lock managers, leader-elected controllers, or consensus stores (etcd, ZooKeeper, Consul, Raft).
  • Managing shared block/object storage (Ceph, DRBD, Pacemaker) where two writers would corrupt filesystem metadata.

Think twice

  • Stateless, idempotent microservices behind a load balancer where any instance can serve requests independently.
  • AP/eventual-consistency stores (e.g., Cassandra, DynamoDB multi-master with CRDTs or LWW) intentionally designed to accept concurrent writes and merge them later.
  • Single-node deployments where no automated failover exists (manual promotion avoids accidental dual-primary).
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioService Node A acquires a distributed lease (epoch=33) in etcd to write to an object store, then freezes for 25 seconds during a JVM Stop-The-World GC pause. etcd expires the lease at 10s and grants epoch=34 to Node B.

The idea

Split-brain occurs when a network partition divides a cluster into two or more isolated sub-networks and more than one side believes it is the active authority. In a stateful system, two concurrent primaries inevitably generate divergent histories that cannot be merged automatically.

Preventing split-brain rests on three interlocking guarantees:

  1. Mathematical Quorum (floor(N / 2) + 1): Only a partition containing a strict majority of voting nodes may elect a leader or commit writes. By the pigeonhole principle, two majorities always share at least one overlapping node.
  2. Time-Bounded Leases & Demotion: A leader holds a renewable lease (e.g., 10s TTL in etcd/Consul) and must demote itself to read-only the instant renewal fails—before any peer can safely take over.
  3. Storage-Side Fencing: Because process pauses (GC, swap, VM migration) can freeze a leader past its lease expiry, the storage or target system must enforce a monotonic fencing token (or hardware STONITH) so late packets from a zombie leader are rejected.

Concrete walkthrough

Trace a 3-AZ Patroni + etcd PostgreSQL failover combined with storage-level fencing during a partition:

  1. Steady state: Node-A (AZ-1) holds etcd leader lease term=42 (ttl=10s, loop_wait=2s). Node-B (AZ-2) and Node-C (AZ-3) stream WAL replication.
  2. Network partition (t = 0s): AZ-1 is cut off from AZ-2 and AZ-3. Node-A can still talk to a few AZ-1 app pods, so it thinks it is healthy.
  3. Self-demotion (t = 2s–6s): Node-A attempts to renew its term=42 lease in etcd, but cannot reach Node-B or Node-C (1/3 votes < quorum of 2). Before its 10s TTL expires, Patroni on Node-A forcibly demotes local PostgreSQL to read-only.
  4. Quorum election (t = 10s): Node-B and Node-C form a 2/3 majority in etcd, expire term=42, and elect Node-B as primary with term=43.
  5. Zombie protection: Even if Node-A had frozen in a 20-second kernel/GC stall before demoting and later flushed a write tagged epoch=42 to a shared volume or conditional store, the store sees current_epoch=43 > 42 and rejects the write. When AZ-1 heals, Node-A runs pg_rewind to discard any uncommitted local WAL and rejoins as a replica.

Quorum ensures only one leader is elected per term, while storage-side fencing tokens block late writes from paused old leaders.

Quorum math and failure-domain placement

Consensus protocols (Raft, Paxos, ZAB) require Q = floor(N / 2) + 1 votes:

  • N = 3: Quorum = 2, fault tolerance = 1 node. Place 1 node in each of 3 AZs (1 + 1 + 1). Never place 2 + 1 across 2 AZs—if the 2-node AZ goes down, quorum is lost.
  • N = 5: Quorum = 3, fault tolerance = 2 nodes. Ideal for production etcd/ZooKeeper where one node can be down for OS patching while still surviving a sudden crash.
  • Even N (2 or 4): Adds zero fault tolerance over N - 1 (4 nodes still have quorum 3, tolerating only 1 failure) while increasing replication overhead. If you only have 2 database servers, run a tiny quorum witness in a 3rd AZ/region.

Failure modes

  • Silent Stale Reads from Zombie Leader: Even if writes are fenced, an isolated old primary can still serve stale reads to clients unless reads also go through quorum (ReadIndex) or use bounded leader leases with monotonic clocks.
  • Split-Brain in Async Replicas: Promoting an asynchronous PostgreSQL/MySQL replica before draining the old primary loses committed transactions on the old primary that hadn't replicated yet (RPO > 0), causing diverged timelines.
  • Witness Co-Location: Running the 3rd-vote witness on the same physical host or VPC subnet as Node 1 turns a 3-node cluster into a single-point-of-failure 2-node cluster in disguise.
  • Fencing Token Wrap or Non-Persistence: If the storage node resets max_seen_epoch to 0 on reboot, a stale zombie packet can slip through after a restart.

Lightweight fencing with cloud conditional writes

You don't always need a dedicated etcd cluster to get strong fencing. Modern cloud object and NoSQL stores provide atomic compare-and-swap (CAS) primitives:

  • Amazon S3 / GCS: Use If-Match: or If-None-Match: * on lease/manifest objects so only the holder of the latest ETag can commit a checkpoint.
  • DynamoDB: Use ConditionExpression: "epoch = :expected" to increment a monotonic epoch attribute and attach that epoch to every downstream mutation.
  • Kubernetes Leases: coordination.k8s.io/v1 Lease objects use optimistic concurrency (resourceVersion) inside Kubernetes' etcd-backed API server.

Practical checklist

  • Deploy an odd number of consensus/voting nodes (3 or 5) distributed across >= 3 independent failure domains (AZs).
  • Never run a 2-node active-passive cluster with auto-failover without a 3rd-AZ witness.
  • Pair leader leases with monotonic fencing tokens validated by the downstream storage/database.
  • Configure STONITH (IPMI or Cloud Stop-Instance) for shared-disk/block clusters where software fencing isn't possible.
  • Use monotonic clocks (CLOCK_MONOTONIC) for all lease-expiry timers.
  • Chaos-test network partitions (e.g., iptables DROP between AZs) and SIGSTOP pauses on the leader to verify zero dual-primary writes.
03 / Engineering trade-offs

Weighing architectural decisions

Availability vs. Consistency (CP Quorum)

Advantage: Strict majority quorum guarantees zero split-brain writes during any network partition.

Drawback: If >= `ceil(N / 2)` nodes are unreachable (e.g., 2 of 3 nodes down), the entire cluster stops accepting writes until quorum returns.

3-Node vs. 5-Node Consensus Cluster

Advantage: 5 nodes survive 2 simultaneous failures (e.g., 1 planned maintenance + 1 sudden crash) without losing quorum.

Drawback: Increases write commit latency (must replicate to 3 nodes instead of 2) and adds 67% more infrastructure cost.

Fencing Tokens vs. STONITH Hardware Fencing

Advantage: Fencing tokens work purely in software over standard protocols (HTTP `If-Match`, Raft term checks) with zero hardware dependencies.

Drawback: Requires the downstream resource to understand and enforce monotonic tokens; legacy filesystems/SANs often require STONITH power-off instead.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Even-Node Cluster Without Witness

A 2-node active-passive pair splits down the middle; if each side promotes itself on heartbeat loss, both accept writes.

What helps: Always use an odd number of voting members (3 or 5) or place a lightweight quorum witness in a 3rd AZ/region.

Asymmetric Partition / Zombie Leader

Old leader loses contact with peers but stays reachable by clients, continuing to serve stale reads or attempt writes before its lease expires.

What helps: Use ReadIndex / leader leases in Raft for linearizable reads, demote immediately on failed lease renewal, and enforce fencing tokens on all writes.

Hypervisor Pause / Clock Jump

A VM live-migration or NTP step causes a node's wall clock to lag or jump, breaking lease-expiry assumptions.

What helps: Use monotonic clocks (`CLOCK_MONOTONIC`) for lease intervals, keep conservative safety margins, and rely on storage-side fencing tokens rather than timing alone.

Dual-STONITH Shootout

Two partitioned nodes simultaneously send IPMI/cloud-API power-off commands to each other, taking down the entire cluster.

What helps: Gate STONITH behind quorum checks, or configure asymmetric fencing delays (e.g., Node 1 waits 0s, Node 2 waits 5s).

05 / Practical checklist

Avoid these mistakes

  • Deploying a 2-node cluster with automated failover and no 3rd-AZ witness.
  • Using `wall-clock` (`CLOCK_REALTIME`) instead of monotonic clocks (`CLOCK_MONOTONIC`) to measure lease expiration.
  • Assuming a distributed lock (like Redis Redlock without fencing) prevents stale writes after a client process pauses.
  • Placing 2 of 3 consensus nodes in the same availability zone or rack—losing that single AZ loses quorum.
  • Rejoining a fenced old primary without `pg_rewind` or log truncation, causing silent replication corruption.
