SQL Query Tuning: Index Seeks,
Scans, Clustered & Covering Indexes.

SQL query tuning and indexing reduce disk I/O and CPU scans from O(N) full-table reads to O(log N) B+tree lookups and covering index-only scans using execution plans and selectivity statistics.

THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Always measure with EXPLAIN (ANALYZE, BUFFERS) before adding indexes: a single well-ordered composite index (equality columns first, range/sort columns last) routinely cuts p99 latency from seconds to single-digit milliseconds without bloating write amplification.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

At 10M+ rows, a missing or poorly ordered index forces sequential heap scans that saturate NVMe IOPS, evict shared buffers, and stall connection pools under concurrent OLTP load.

  • B+tree composite indexes follow the leftmost-prefix rule: place high-selectivity equality (=) columns first, then range (>, <, BETWEEN) or sort (ORDER BY) columns.
  • Covering indexes (CREATE INDEX ... INCLUDE (col)) enable Index-Only Scans in PostgreSQL when the visibility map confirms all-visible pages, eliminating random heap fetches.
  • Query planners rely on ANALYZE histograms and pg_stats (n_distinct, most_common_vals); stale statistics cause nested-loop vs. hash-join misestimates.
  • Non-sargable predicates like WHERE LOWER(email) = 'a@b.com' or WHERE created_at + INTERVAL '1 day' > NOW() defeat standard B+tree indexes unless backed by an expression index.
  • Unused or duplicate indexes silently degrade INSERT/UPDATE throughput; audit pg_stat_user_indexes (idx_scan = 0) before creating new ones.

Good candidates

  • High-selectivity WHERE predicates (< 5–10% of rows) on large tables in PostgreSQL, MySQL InnoDB, or SQL Server.
  • Hot JOIN keys, ORDER BY / GROUP BY clauses, and pagination queries where avoiding an external disk sort cuts latency by 10x–100x.
  • Read-heavy endpoints that can be satisfied entirely from an index via covering columns (INCLUDE) without touching heap pages.

Think twice

  • Tiny lookup tables (< 1,000 rows or a few 8 KB pages) where a sequential scan is faster than traversing B+tree levels.
  • Low-cardinality boolean or status flags (e.g., is_active = true matching 95% of rows) unless paired with a partial index (WHERE is_active = false).
  • Write-saturated append-only ingestion tables where every extra secondary index adds B+tree page splits, WAL volume, and vacuum overhead.
Deep Dive & Production Considerations
02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioAn e-commerce API runs SELECT id, total_cents, status FROM orders WHERE tenant_id = 42 AND status = 'PAID' ORDER BY created_at DESC LIMIT 50 on an 80M-row table, using only single-column indexes on tenant_id and created_at.

The idea

SQL query tuning aligns physical storage access paths with how the cost-based optimizer (CBO) estimates selectivity, join order, and I/O cost. Instead of scanning millions of 8 KB heap pages sequentially, you shape predicates to be sargable (search-argument-able) and build balanced B+tree, partial, or specialized indexes so the engine touches only the exact leaf pages and heap blocks required.

Concrete walkthrough

  1. Capture slow queries in production via pg_stat_statements sorted by total_exec_time and shared_blks_read.
  2. Run EXPLAIN (ANALYZE, BUFFERS, VERBOSE) on a representative bind parameter to compare actual rows vs. estimated rows.
  3. Spot high-cost nodes: Seq Scan with heavy Rows Removed by Filter, Sort Method: external merge Disk, or Nested Loop multiplying a 100x underestimated row count.
  4. Rewrite non-sargable expressions into range predicates and eliminate OFFSET in favor of keyset cursors.
  5. Create a composite covering index (equality_cols, range_or_sort_col) INCLUDE (select_cols) using CREATE INDEX CONCURRENTLY.
  6. Re-run EXPLAIN (ANALYZE, BUFFERS) and verify Heap Fetches: 0 (after VACUUM) and single-digit shared hit counts.

Covering composite indexes let the optimizer satisfy filtered, sorted queries from cached B+tree leaf pages while the visibility map skips heap I/O.

Composite key ordering and sargability

A B+tree stores keys lexicographically. An index on (a, b, c) supports predicates on (a), (a, b), and (a, b, c), plus ORDER BY b when a is constrained by =. Once a range operator (>, <, BETWEEN, IN with many values) appears on column b, subsequent column c cannot use the tree order for filtering or sorting. Always place equality predicates first, sort/range columns second, and non-filtered projection columns inside INCLUDE so they do not bloat internal branch pages.

Failure modes

The most deceptive production outage is planner cliff flipping: a query runs in 3 ms for months until table growth crosses a cost threshold and PostgreSQL suddenly switches from an Index Scan to a Parallel Seq Scan, saturating disk read bandwidth. Equally dangerous are HOT update breaks—adding an index on a frequently updated column like updated_at prevents Heap-Only Tuple updates, doubling vacuum bloat—and index bloat from heavy churn, which requires periodic REINDEX CONCURRENTLY or pg_repack.

Observability and verification

Track pg_stat_statements weekly for calls * mean_exec_time and shared_blks_read / calls. Verify buffer efficiency (shared hit vs shared read) rather than wall-clock time alone, because warm OS page cache can hide an unindexed scan that will fail under cold-cache load. Pair pg_stat_user_indexes with idx_scan = 0 checks over a full monthly billing cycle before dropping redundant indexes.

Practical checklist

  • Run EXPLAIN (ANALYZE, BUFFERS) against production-scale data before writing migrations.
  • Order composite B+tree columns as (equality_cols, range_or_sort_col) INCLUDE (projection_cols).
  • Replace OFFSET pagination with keyset cursors (WHERE (created_at, id) < (:ts, :id)).
  • Use CREATE INDEX CONCURRENTLY with lock_timeout = '2s' in migrations.
  • Keep pg_stat_statements enabled and prune unused indexes (idx_scan = 0) quarterly.
03 / Engineering trade-offs

Weighing architectural decisions

Read latency vs. write amplification

Advantage: Each targeted B+tree or GIN index turns multi-second table scans into sub-millisecond point or range lookups.

Drawback: Every INSERT, UPDATE on indexed columns, and DELETE must update all affected indexes, generating extra dirty pages, WAL bytes, and HOT-update disqualifications.

Composite covering indexes vs. storage footprint

Advantage: INCLUDE columns satisfy queries with Index-Only Scans, avoiding random 8 KB heap page reads.

Drawback: Wider index tuples reduce B+tree fanout, increase tree depth, and consume more RAM in shared_buffers or InnoDB buffer pool.

Specialized indexes (GIN/BRIN/Hash) vs. generality

Advantage: GIN accelerates JSONB/full-text containment (@>) and BRIN tracks min/max per 128-page range at 1% of B+tree size for time-series data.

Drawback: GIN has expensive pending-list flushes on heavy writes, and BRIN degrades to full scans if physical rows are not correlated with insertion order.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Parameter sniffing / plan instability

A cached generic plan built for a rare tenant_id (10 rows, Nested Loop) is reused for a whale tenant (2M rows), causing CPU spikes and timeouts.

What helps: Use pg_stat_statements to spot high variance, force custom plans when needed (plan_cache_mode = force_custom_plan), or partition skew-heavy tenants.

Stale planner statistics after bulk loads

Loading 5M rows without running ANALYZE leaves pg_class.reltuples outdated, tricking the optimizer into choosing Nested Loop joins over Hash Joins.

What helps: Run ANALYZE immediately after batch ETL/COPY jobs and tune autovacuum_analyze_scale_factor (e.g., 0.02 instead of 0.1) on large tables.

Blocking DDL locks during index creation

Running plain CREATE INDEX acquires a SHARE lock that blocks all concurrent INSERT/UPDATE/DELETE statements for minutes on large tables.

What helps: Always use CREATE INDEX CONCURRENTLY (PostgreSQL) or ALGORITHM=INPLACE, LOCK=NONE (MySQL) with lock_timeout set to 2s.

Deep OFFSET pagination degradation

SELECT ... ORDER BY id LIMIT 20 OFFSET 500000 forces the engine to scan and discard 500,000 index entries on every page turn.

What helps: Switch to keyset (cursor) pagination: WHERE id > :last_seen_id ORDER BY id LIMIT 20 for constant O(log N) latency at any depth.

05 / Practical checklist

Avoid these mistakes

  • Indexing every column individually instead of designing composite indexes matched to actual WHERE + ORDER BY predicates.
  • Putting a range column (created_at > ...) before an equality column (tenant_id = ...) in a composite B+tree index.
  • Using SELECT * on OLTP endpoints, which prevents Index-Only Scans and pulls large TOAST/text columns into memory.
  • Applying functions to indexed columns in WHERE clauses (e.g., DATE(created_at) = '2026-11-12') instead of half-open range bounds (>= '2026-11-12' AND < '2026-11-13').
  • Testing query plans on an empty or 1,000-row staging database where the planner naturally picks Sequential Scans.
