SQL Query Tuning: Index Seeks, Scans, Clustered & Covering Indexes

Eliminate slow table scans and high-cost Key Lookups using B-Tree index seeks, clustered primary keys, and composite covering indexes.

Orientation & Intuition

Relational query execution hinges on whether the optimizer executes an Index Seek (direct O(log N) B-Tree root-to-leaf traversal) or an Index/Table Scan (O(N) sequential page reads). When non-clustered indexes lack requested SELECT columns, the engine must perform a Key/RID Lookup back to clustered index pages for every row, triggering catastrophic random disk I/O.

Key takeaway Eliminate random I/O and table scans by designing clustered indexes on sequential range keys and constructing Covering Indexes (composite keys + INCLUDE columns) that satisfy queries entirely from leaf index pages without touching table data.

Core Architecture & Trade-offs

Unindexed or poorly indexed queries degrade from 2ms to 10,000+ms under concurrent traffic, triggering database connection pool exhaustion and 100% CPU spikes. Analyzing execution plans (EXPLAIN ANALYZE) and replacing expensive Key Lookups with covering B-Tree index seeks is the highest-leverage performance optimization in relational databases.

Key Architecture Invariants

  • Clustered Index: Determines the physical sort order of table rows on disk. Leaf nodes are the actual table data pages (e.g. InnoDB clustered primary key). A table can have only one clustered index.
  • Secondary (Non-Clustered) Index: A separate B-Tree where leaf nodes contain indexed keys plus a row pointer (Clustered Key in MySQL/SQL Server, or physical Tuple ID/RID in PostgreSQL heap tables).
  • Index Seek vs Index Scan: An Index Seek navigates root-to-leaf via binary search to find exact boundaries in O(log N); an Index Scan reads all leaf pages in sequence in O(N).
  • Key / RID Lookup (Bookmark Lookup): Occurs when a secondary index seek matches rows, but the query requests additional columns not present in the index, forcing extra random I/O lookups to the clustered index or heap.
  • Covering Index: Contains all columns needed for a query (in the key or via INCLUDE clause), allowing the database engine to return results entirely from the index tree (Index Only Scan) with zero heap accesses.
  • Leftmost Prefix Rule: Composite indexes (col1, col2, col3) can only be sought if WHERE clauses filter on leading columns in left-to-right order without skipping.

When to Use

  • Tables with >100,000 rows where point lookups or range queries suffer from full table scans (Seq Scan).
  • Queries where execution plans reveal high-cost 'Key Lookup', 'RID Lookup', or 'Bitmap Heap Scan' operations consuming >70% of query time.
  • High-frequency read APIs where queries can be fulfilled completely by index leaf pages (Covering Index).
  • Designing primary keys where range scans or time-series sorting align with the physical clustered index order.

When NOT to Use

  • Small lookup tables (<1,000 rows) where sequential memory page reads are faster than traversing B-Tree branch pages.
  • Write-heavy tables with high ingestion throughput where maintaining multiple secondary indexes creates severe write amplification and page splits.
  • Queries returning >20-25% of table rows, where the optimizer's tipping point mathematically favors sequential scans over random single-page lookups.

Deep Dive & Production Considerations

🔍 Anatomy of SQL Query Execution & B-Tree Navigation

When a database receives a SQL statement, the Query Optimizer evaluates candidate execution plans, calculating cost based on estimated page I/O operations and CPU cycles.

1. B-Tree Root-to-Leaf Seek Mechanics

A B-Tree index maintains a hierarchical tree where non-leaf pages hold pivot keys pointing to child pages, and leaf pages hold ordered key values with pointers to data.

text 
                  +-------------------+
                  | Root Page (Node)  |
                  | Pivot: [100 | 500]| 
                  +---------+---------+
                           / \  
              +-----------+   +-----------+
              | Branch 1  |   | Branch 2  |
              | [10 | 50] |   | [600|800] |
              +-----+-----+   +-----+-----+
                   /  \            /  \   
        +---------+    +---------+   +---------+
        | Leaf P1 |<-->| Leaf P2 |<->| Leaf P3 | (Doubly Linked List)
        | Keys    |    | Keys    |   | Keys    |
        +---------+    +---------+   +---------+
  • Index Seek: Performs a binary search from the root page down to the leaf page in $O(\log N)$. For a table with 100,000,000 rows, a B-Tree depth of 4 requires reading only 4 8KB pages from the buffer cache to locate the starting row.
  • Index Scan: Traverses across the horizontal doubly-linked list of leaf pages, reading all $N$ entries in $O(N)$.
  • Table Scan (Seq Scan): Discards the index entirely and reads every 8KB data page in the heap from disk.

2. Clustered Index vs Secondary Index & The Key Lookup Bottleneck

In relational engines (e.g. MySQL InnoDB, Microsoft SQL Server):

  1. Clustered Index: The table is organized as a B-Tree sorted by the primary key. The leaf pages are the data rows containing all table columns.
  2. Secondary Index: Leaves contain the indexed column values plus the Clustered Key (or heap Row ID / TID in PostgreSQL).
text 
[Query: SELECT order_id, status, total_amount FROM orders WHERE customer_id = 42]

SCENARIO A: Secondary Index on (customer_id) [WITHOUT Covering Columns]
1. Index Seek on idx_customer_id finds 50 matching leaf entries.
2. For EACH of the 50 rows, the engine must perform a KEY LOOKUP:
   Navigate the Clustered Index B-Tree (3-4 page reads each) to fetch 'total_amount'.
   Total Page Reads: 4 (Index Seek) + (50 * 3 Random Lookups) = 154 Page Reads!

SCENARIO B: Covering Composite Index on (customer_id) INCLUDE (status, total_amount)
1. Index Seek on idx_customer_covering finds 50 matching leaf entries.
2. All requested columns (order_id, status, total_amount) exist in the leaf page!
3. Engine returns data directly without touching the clustered index or heap.
   Total Page Reads: 4 Page Reads! (97.4% reduction in I/O)

3. The Composite Index Design Rule: Equality First, Range Second

To maximize index seek selectivity on queries with multiple filters:

  1. Place Equality (=) columns first in the composite index.
  2. Place Range (>, <, BETWEEN, IN) columns last among the seek keys.
  3. Include columns needed for projection in the INCLUDE clause (or at the end of the index) to avoid making the index tree wider.
sql 
-- BAD INDEX: Range column first
CREATE INDEX idx_orders_bad ON orders (created_at, customer_id);
-- Query cannot seek on customer_id because the B-Tree is sorted primarily by created_at!
SELECT * FROM orders WHERE customer_id = 99 AND created_at >= '2026-10-01';

-- GOOD INDEX: Equality first, Range second, Covered columns included
CREATE INDEX idx_orders_good ON orders (customer_id, created_at) INCLUDE (status, total_amount);
-- Engine performs an exact binary seek to customer_id = 99, then a range scan on created_at!
