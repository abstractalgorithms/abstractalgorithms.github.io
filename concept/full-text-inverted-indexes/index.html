THE BIG IDEA / Key takeaway · CONCEPT GUIDE

Inverted indexes turn O(N) document scans into O(k) compressed posting-list intersections using FST dictionaries, delta+bitpacking, and Block-Max WAND pruning.

Explanation anchor
01 / The idea

Foundational mechanics & core principles

Scanning millions of JSON documents or logs with LIKE '%term%' forces O(N) disk and CPU reads. An inverted index—used by Apache Lucene, Elasticsearch, OpenSearch, and PostgreSQL GIN—pre-tokenizes text into normalized terms and stores sorted, compressed lists of matching document IDs, enabling sub-50ms boolean, phrase, and BM25-ranked queries at petabyte scale.

  • Text ingestion runs through an analyzer pipeline (character filters -> tokenizer -> token filters like lowercase/stemming) to emit normalized terms; index and query analyzers must match.
  • A Finite State Transducer (FST) in Lucene maps term prefixes in memory to disk offsets in the term dictionary (.tim/.tip), keeping only ~1–5% of dictionary metadata in RAM.
  • Postings lists store sorted docIDs as delta gaps (d_i - d_{i-1}) packed via Frame-of-Reference (FOR / SIMD-BP128) or Roaring Bitmaps, shrinking 32-bit docIDs to ~2–6 bits each.
  • Phrase queries ("distributed lock") require storing positional offsets inside postings, which typically doubles or triples index disk size.
  • To avoid mutating compressed postings in place, engines write immutable segments (LSM pattern) and merge them asynchronously in the background (TieredMergePolicy), filtering deleted docs via a live-docs bitset.

Good candidates

  • You need fast keyword, phrase, prefix, or BM25 relevance-ranked search across unstructured text fields in millions or billions of documents.
  • Queries combine multiple filter predicates (status:200 AND region:us-east) where intersecting compressed roaring bitmaps or postings lists beats B-tree composite indexes.
  • You can tolerate near-real-time (NRT) visibility delays (typically 1 second in Lucene/Elasticsearch) in exchange for high write throughput via immutable segments.

Think twice

  • Your workload requires strict ACID point-updates on individual fields at high frequency—updating 1 field in an immutable Lucene segment marks the old doc tombstoned and re-indexes the entire document.
  • You primarily run numeric range aggregations or time-series scans (timestamp > T), where columnar engines (ClickHouse, Parquet) or BKD trees outperform inverted postings.
  • Your search requires purely semantic similarity across synonyms with zero lexical overlap—use dense vector HNSW indexes (or combine both in hybrid search).

02 / Concrete walkthrough

Architectural mechanics & implementation

ScenarioA 50-million-SKU catalog handles 15,000 QPS for multi-word queries ("wireless noise cancelling headphones") with brand filters and BM25 relevance ranking (k1=1.2, b=0.75).

The idea

A forward index maps docID -> [terms], which answers "what is in document 42?" in O(1) but forces an O(N) scan to find all documents containing "raft". An inverted index transposes that relationship into term -> sorted [docID_1, docID_2, ...].

Modern engines like Apache Lucene split this into two tiers: an in-memory Finite State Transducer (FST) that maps term prefixes to disk offsets in constant time per character, and on-disk compressed postings lists grouped in 128-doc blocks. Because docIDs are strictly increasing, storing deltas (doc_i - doc_{i-1}) reduces 32-bit integers to tiny values that pack into 2–6 bits per document via SIMD bitpacking.

Concrete walkthrough

Suppose we index three documents for query "raft consensus":

  • Doc 10: "raft leader election"
  • Doc 12: "paxos and raft consensus"
  • Doc 19: "raft consensus protocol"
  1. Tokenize & invert: Term "raft" maps to [10, 12, 19]; "consensus" maps to [12, 19].
  2. Delta encode: "raft" stores [10, +2, +7] (with tf [1, 1, 1] and positions [0], [2], [0]). "consensus" stores [12, +7] (positions [3], [1]).
  3. Query execution: Galloping skip-list intersection aligns "raft" (10 -> 12) with "consensus" (12), finds Doc 12 (pos 2 followed by pos 3 -> phrase match!) and Doc 19 (pos 0 followed by pos 1 -> phrase match!), then scores both using BM25.

Inverted indexes separate an in-memory FST prefix dictionary from immutable, delta-compressed posting segments, using Block-Max WAND to skip low-scoring blocks.

BM25 scoring and Block-Max WAND pruning

Boolean matching alone treats a 10,000-word article mentioning "redis" once the same as a 50-word note repeating it 5 times. BM25 fixes this with diminishing term-frequency saturation (k1 ≈ 1.2), document-length normalization (b ≈ 0.75 against average doc length), and Inverse Document Frequency (IDF) so rare terms dominate.

For top-K queries, Block-Max WAND stores the maximum possible BM25 contribution for every 128-doc block in skip metadata. If the sum of remaining block upper bounds cannot beat the current K-th best score in the priority queue, the engine skips decompressing the entire 128-doc block—cutting CPU work by 5–10x on multi-term OR queries.

Failure modes

  • Sub-second refresh thrashing: Frequent refreshes spawn thousands of tiny unmerged segments, inflating heap FST overhead and exhausting OS file descriptors.
  • Wildcard prefix scans: Leading wildcards (*timeout) bypass the FST prefix structure and enumerate every term in the segment.
  • Analyzer drift: Changing stemming or synonym rules in a search template without reindexing silently drops recall.
  • Deep from pagination: Fetching page 5,000 across 10 shards materializes 500,000 sorted hits in coordinator heap instead of using search_after cursors.

LSM segment lifecycle and deletions

Because postings lists are delta-encoded and bit-packed, deleting or updating a document in place would require rewriting entire megabyte blocks. Instead, Lucene maintains a tiny live-docs bitset (1 bit per doc in the segment). Deleting a document simply flips its bit to 0 in RAM/disk.

Background TieredMergePolicy threads periodically merge multiple small segments into larger ones, physically purging tombstoned documents and reclaiming space. During bulk data loads, setting refresh_interval = -1 and number_of_replicas = 0 temporarily suspends segment creation and replication overhead, boosting indexing throughput by 3–5x.

Practical checklist

  • Match index-time and query-time analyzers explicitly; disable positions (index_options: docs) on fields that never need phrase queries.
  • Keep refresh_interval >= 1s (30s for log pipelines) and never call _refresh on every write.
  • Use keyword / Roaring-bitmap filter contexts (filter clause) instead of must so non-scoring predicates bypass BM25.
  • Replace deep from/size pagination with search_after + Point-in-Time (PIT) tokens.
  • Target 10–50 GB per shard in Elasticsearch/OpenSearch to balance FST heap overhead against parallel query fan-out.
03 / Engineering trade-offs

Weighing architectural decisions

Write Amplification vs. Query Speed

Advantage: Immutable sorted segments compress postings tightly and allow zero-lock OS page-cache reads.

Drawback: Background segment merging consumes significant disk I/O and CPU, and document updates require tombstone + full re-index.

Positional & N-Gram Indexing vs. Disk Footprint

Advantage: Storing positions and edge-ngrams enables exact phrase matching and instant autocomplete.

Drawback: Increases index size by 2x–5x and slows down ingestion throughput.

NRT Refresh Interval vs. Segment Count

Advantage: Short refresh intervals (e.g., 1s) make newly indexed documents searchable almost immediately.

Drawback: Sub-second refreshes create hundreds of tiny segments, exhausting file descriptors and stalling merges.

04 / Failure modes & resilience

Explain where it breaks · Known failure modes

Segment Explosion from Aggressive Refresh

Calling explicit `_refresh` on every write or setting `refresh_interval: 100ms` generates thousands of tiny segments, causing `Too many open files` (`EMFILE`) and merge-throttling stalls.

What helps: Keep `refresh_interval` at `1s` (or `30s` during bulk backfills) and never invoke `_refresh` per request in production write paths.

High-Frequency Term Scanning (Stopword / Skew)

Queries containing ubiquitous terms (`"the"`, `"error"`, `"2026"`) match 80% of documents, forcing full posting-list decompression unless pruned.

What helps: Use Block-Max WAND (enabled by default in Lucene 8+) for top-K BM25 pruning, or index high-frequency boilerplate with `common_terms` / stopword filtering.

Index-Time vs. Query-Time Analyzer Mismatch

Indexing text with a Porter stemmer (`"running" -> "run"`) while querying with a `keyword` or unstemmed analyzer returns zero matches.

What helps: Explicitly bind identical analyzer pipelines for index and search unless intentionally using asymmetric `edge_ngram` (index) + `standard` (search) patterns.

Deep Pagination Heap Exhaustion

Requesting `from=50000, size=20` across 10 shards forces every shard to score and return 50,020 docIDs to the coordinator for an O(N log K) merge sort.

What helps: Use `search_after` with a Point-in-Time (PIT) cursor and tie-breaker `_shard_doc` sort instead of deep `from`/`size` offsets.

05 / Practical checklist

Avoid these mistakes

  • Storing large unsearched JSON blobs inside `_source` or indexing every field with `positions` when only `keyword` exact match is needed.
  • Allowing PostgreSQL GIN `gin_pending_list_limit` (default 4 MB) to bloat or flush synchronously on a random user insert, causing p99 write spikes.
  • Running wildcard queries with a leading `*` (`*error*`), which defeats the FST prefix dictionary and forces a full scan of every term in the index.
  • Leaving shard counts oversized (e.g., 50 shards for 5 GB of data), which multiplies per-query FST/BM25 overhead by 50x.
  • Evaluating BM25 IDF per-shard on small datasets (`dfs_query_then_fetch` disabled), skewing relevance scores when term frequencies vary across shards.
