01
STAGE 01 · WHAT IT ISL4 · FUNDAMENTALS

What is an Inverted Index.

Scanning millions of JSON documents with LIKE '%term%' forces an O(N) full scan. An inverted index (Apache Lucene, Elasticsearch, OpenSearch, PostgreSQL GIN) flips the mapping from doc -> words to term -> sorted list of docIDs (the postings list).

Text enters through an analyzer pipeline (character filters → tokenizer → lowercase/stemming). In Lucene, a Finite State Transducer (FST) in RAM maps term prefixes to disk offsets in the term dictionary (.tim), keeping only ~1–5% of dictionary metadata in memory while postings lists store delta-encoded docID gaps compressed via SIMD-BP128 or Roaring Bitmaps.

Lucene Segment Lookup

FST Term Prefix Trie -> Term Dictionary -> Compressed Postings

1.FST in RAM: Shares common term prefixes/suffixes to locate any term's disk offset in O(term_length).

2.Delta + Bitpacking: Sorted docIDs are stored as gaps (d_i - d_{i-1}) packed to 2–6 bits per docID.

3.Immutable Segments: Updates tombstone the old docID in a live-docs bitset and append a new document.

FSTs pinpoint term offsets without loading all terms into RAM, while compressed postings enable fast intersections.

02
STAGE 02 · WHY WE NEED ITL4 · FUNDAMENTALS

Why B-Trees Fail on Multi-Keyword & Relevance Queries.

B-trees only index exact prefixes from left to right. Searching for 'wireless noise cancelling headphones' across 50M SKUs with brand/price filters requires intersecting multiple term postings lists and scoring TF-IDF / BM25 relevance—which Block-Max WAND prunes in <30 ms by skipping blocks whose maximum possible BM25 score cannot beat the current top-K heap.

Index vs. Query Analyzer Parity

If you stem 'running' -> 'run' at index time, the query analyzer must apply the exact same filter or searches miss.

NRT Segment Refresh Cost

Sub-second _refresh intervals create hundreds of tiny segments, exhausting file descriptors and stalling background merges.

STAGE 03 · WHERE IT IS USEDL5 · APPLIED DESIGN

Where Inverted Indexes Excel (and Where Columnar/BKD Wins).

Use inverted indexes for text and multi-predicate boolean filters; avoid them for high-churn single-field mutations or numeric time-series scans.

ChoiceWhat it buysWhat it costs
Good Candidate: Catalog & Log Full-Text SearchSub-50 ms BM25 relevance, phrase proximity (`.pos`), and Roaring Bitmap filter intersections.Storing positions and edge-ngrams multiplies index disk size by 2x–5x.
Good Candidate: PostgreSQL GIN on JSONB / tsvectorTransactional ACID search inside Postgres with `fastupdate = on` pending-list batching.Pending-list flushes can cause periodic tail-latency spikes unless tuned with `gin_pending_list_limit`.
Avoid: High-Churn Point Updates or Range AnalyticsColumnar stores (ClickHouse) or B-trees handle numeric range aggregations and in-place updates far better.Updating 1 field in an immutable Lucene segment tombstones and re-indexes the entire document.
04
STAGE 04 · HOW IT IS MANAGEDL5 · APPLIED DESIGN

Delta-Encoded Postings & Deep Pagination with search_after.

Never use from + size for deep pagination (e.g., page 500 asks every shard for 10,000 docs, exhausting coordinator heap). Always paginate with search_after + a Point-in-Time (PIT) snapshot and a unique _shard_doc tie-breaker.

// Safe deep pagination with Point-in-Time (PIT) + search_after (Elasticsearch/OpenSearch)
POST /products/_search
{
  "size": 50,
  "query": { "match": { "title": "wireless headphones" } },
  "pit": { "id": "46ToAwMDaWR5BXV1aWQx...", "keep_alive": "2m" },
  "sort": [
    { "_score": "desc" },
    { "_shard_doc": "asc" }
  ],
  "search_after": [12.4821, 90412]
}

STAGE 05 · ALTERNATIVESL6 · SCALE & TRADE-OFFS

Alternatives: Lucene (ES/OpenSearch) vs. Postgres GIN vs. Dense Vectors.

Choose your search engine by corpus size, update transactionality, and whether semantic synonyms are required.

ChoiceWhat it buysWhat it costs
Elasticsearch / OpenSearch (Lucene)Horizontal sharding, Block-Max WAND top-K pruning, and rich BM25 + aggregation DSL.Eventual NRT consistency (~1s refresh) and JVM/merge I/O operations.
PostgreSQL GIN (`tsvector` / `jsonb`)Zero separate search cluster; full ACID consistency with relational joins.Lacks distributed sharding and Block-Max WAND pruning at 100M+ document scale.
Dense Vector HNSW IndexCaptures semantic paraphrases and synonyms without exact keyword overlap.Misses exact SKUs/error codes and requires 4x–10x more RAM than inverted postings.
06
STAGE 06 · PRODUCTION ARCHITECTUREL7 · STAFF / PRINCIPAL

Production Search Lifecycle: Write Buffer -> Segments -> Tiered Merge.

Lucene buffers writes in an in-memory index buffer, flushes immutable segments on refresh_interval (1s normal, 30s during bulk backfills), and runs background tiered merges to keep segment counts bounded and reclaim tombstoned deletes.

LSM-Style Segment Pipeline

Translog WAL -> In-Memory Buffer -> Immutable Segments & Merge

1.OS Page Cache: Segments are mmap'd so Lucene relies on OS page cache rather than JVM heap for postings.

2.Tombstone Bloat: Frequent updates leave deleted docIDs until tiered merging rewrites larger segments.

3.Block-Max WAND: Skips posting blocks whose upper-bound BM25 score cannot enter the top-K heap.

Immutable segments give zero-lock OS page-cache reads while background merging bounds segment count and reclaims deletes.
