Sharding Approaches in SQL and NoSQL: Range, Hash, and Directory-Based Strategies Compared

When One PostgreSQL Instance Is No Longer Enough

💡 Executive Summary

Sharding splits your database across multiple physical nodes so no single machine carries all the data or absorbs all the writes.

🎯 System Scenario & Requirements

System Goal

Sharding splits your database across multiple physical nodes so no single machine carries all the data or absorbs all the writes.

Actors & Components

  • Application Workers
  • Volatile Memory Tier
  • Persistent Disk Tier
  • Worker Process
  • In-Memory Cache
  • Primary Database

Functional Requirements

  • TLDR: Sharding splits your database across multiple physical nodes so no single machine carries all the data or absorbs all the writes.
  • The strategy you choose — range, hash, consistent hashing, or directory — determines whether range queries stay cheap, writes stay balanced, and adding a new node moves 100% or just 1/N of your data.
  • The shard key is the single most consequential architectural decision you will make, and the wrong one is nearly impossible to fix without a full migration.

Constraints & Assumptions

  • Once data lives on multiple shards, operations that used to be simple become multi-step distributed protocols — and some of them are permanently more expensive than their single-node equivalents.
  • A query without a shard key predicate must broadcast to all shards, wait for all responses, and merge the result set at the coordinator.
  • Pick your shard key for read locality, not write convenience.
  • Auto-increment IDs are easy to generate but create a hot-last-shard problem with range sharding and lose ordering with hash sharding.

Stage 2 — The Four Sharding Strategies and What Each One Optimizes

  • Range Sharding: Natural Ordering at the Cost of Write Balance Range sharding assigns contiguous key intervals to each shard.
  • If your shard key is user id and you have four shards, you might configure: - Shard 1 → user id 0 – 999,999 - Shard 2 → user id 1,000,000 – 1,999,999 - Shard 3 → user id 2,000,000 – 2,999,999 - Shard 4 → user id 3,000,0…
  • The router holds a simple lookup table of ranges.
  • Any query with a known user id lands on exactly one shard.

Applies caching to the decision above.

    R -->|user_id 3M and above| S4[Shard 4]

Observable outcome: Any query with a known user id lands on exactly one shard.

Stage 3 — Deep Dive: How SQL and NoSQL Databases Wire Sharding Into Their Engines

  • Internals: Query Routing, Shard Maps, and Database-Specific Partitioning Models SQL databases were designed around the assumption that all data lives in one engine on one server.
  • Sharding is an external capability in most SQL systems, not a native one.
  • PostgreSQL's native PARTITION BY feature creates partitions on the same server — useful for query pruning but not horizontal scaling.
  • True sharding requires the Citus extension (now part of Azure Cosmos DB for PostgreSQL).

Applies consistency-replication to the decision above.
