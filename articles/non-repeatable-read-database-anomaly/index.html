Stage 3 — Deep Dive: How MVCC Snapshot Boundaries Determine Non-Repeatable Read Risk

  • The root cause of non-repeatable reads is not a bug in the database engine — it is a deliberate design decision about when the multi-version snapshot boundary is established and for how long it is held.
  • Understanding this distinction is the key to choosing the right isolation level and knowing exactly what guarantee you are purchasing.
  • The Internals of MVCC Snapshot Mechanics at Read Committed vs.
  • Repeatable Read Multi-Version Concurrency Control (MVCC) is the mechanism that PostgreSQL, MySQL InnoDB, and most modern databases use to serve concurrent readers without blocking them with locks.

Applies consistency-replication to the decision above.

Read Committed (per-statement snapshot):
  T1 SELECT 1 → snapshot at t=0 → sees amount = 1200
  T2 COMMIT   → new committed version arrives at t=1
  T1 SELECT 2 → snapshot at t=1 → sees amount = 950   <- INCONSISTENCY

Repeatable Read (per-transaction snapshot):
  T1 BEGIN    → snapshot established at t=0
  T1 SELECT 1 → snapshot at t=0 → sees amount = 1200
  T2 COMMIT   → new committed version arrives at t=1 (T1 snapshot is frozen)
  T1 SELECT 2 → snapshot at t=0 → sees amount = 1200  <- CONSISTENT

End-to-end outcome

After working through the stages, you should be able to explain:

  • Read Committed does not mean "safe for transactions that read data twice." The name is misleading.
  • Read Committed means each statement reads committed data — not that the same data will be committed to the same value across two statements.
    • A non-repeatable read occurs when a transaction reads the same row twice and receives different committed values — because a concurrent transaction updated and committed that row between the two reads.
    • It is categorically different from a dirty read: only fully committed data is involved.
