Stage 2 — Persistence & Outbox Mechanics

  • When a domain service finishes processing a command, the only way to guarantee exact‑once delivery of the resulting event is to bind the event write to the same transaction that mutates the aggregate.
  • In Java/Spring this typically means persisting a row in an outbox table inside the same @Transactional scope that updates the business tables.
  • The outbox row contains a serialized payload, a target topic, a retry counter, and a deterministic ordering key.
  • Because the row is written atomically with the aggregate, any failure that rolls back the aggregate also rolls back the outbox entry, eliminating the “lost‑event” window that plagues naïve async publishing.

Key learnings

  • Transactional Boundaries Must Be Explicit The outbox pattern hinges on the atomicity of the domain transaction and the outbox write.
  • In practice, developers often forget that the outbox table is part of the same transaction as the business write.
  • The transactional outbox pattern is most effective when it is embedded in a tightly‑coordinated micro‑service stack that separates concerns, guarantees atomicity, and exposes a clear, observable message flow.
  • When a domain service finishes processing a command, the only way to guarantee exact‑once delivery of the resulting event is to bind the event write to the same transaction that mutates the aggregate.
