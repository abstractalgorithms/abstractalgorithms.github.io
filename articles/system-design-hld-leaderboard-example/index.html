Detailed Architectural Analysis

Scenario context

Real-time leaderboards for 10M+ active users require an in-memory ranking engine. Redis Sorted Sets (ZSET) are the industry standard, providing $O(\log N)$ updates and rank lookups via an internal Skip List data structure. Relational databases fail at this scale because calculating rank is an $O(N)$ operation (counting rows with higher scores) that becomes a bottleneck during peak traffic spikes.


This walkthrough focuses on **Deep Dive: Why Redis Sorted Sets Achieve What SQL Cannot**.

Before making a design choice, clarify:

- The performance gulf between Redis ZSET and SQL for leaderboard rank queries is not a matter of hardware speed — it is a fundamental algorithmic difference.
- Understanding the internals of the Redis Skip List reveals why this gap exists and why no amount of database tuning closes it.
- Internals: The Skip List and Hash Map That Power ZREVRANK A Redis Sorted Set is implemented internally as two data structures working in tandem : 1.

## Stage 3 — Basics: How Ranking Differs from Sorting

- At first glance, a leaderboard seems like a simple sorting problem.
- Just sort the table by score and pick the top rows.
- However, at scale, there is a massive difference between sorting and ranking .
- Sorting: Ordering a set of elements.

**Observable outcome:** Sorting: Ordering a set of elements.

## Stage 4 — Mechanics: The Logic of Score Updates

- The core mechanic of a modern leaderboard is the Accumulation and Fan-out of score events.
- - Incremental Updates: Instead of overwriting the score, we often send "score deltas" (e.g., +50 points).
- This allows for easier concurrent updates.
- - Tie-Breaking: To ensure deterministic ranking, we use a composite score.

*Applies **database-indexing** to the decision above.*

## Stage 6 — High-Level Design: The Ranking Pipeline

- The architecture separates the fast-path ranking engine from the durable-path storage.
- The Ranking Pipeline above separates two concerns that must never share a bottleneck: the write path (score ingestion via Kafka → Score Processor → Redis ZSET) and the read path (Leaderboard API → Redis ZREVRANK).
- The Game Server never writes directly to Redis — it goes through the Ingestion Service and Kafka, ensuring durability before the score is considered committed.
- If Redis is unavailable, the API falls back to Postgres for correctness at the cost of higher latency.
