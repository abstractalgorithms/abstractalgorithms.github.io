Functional Requirements

  • TLDR: Real-time application updates can be delivered via WebSockets or Server-Sent Events (SSE).

Constraints & Assumptions

  • Stateful Load Balancing: WebSocket servers are stateful.
  • Once a connection is established, the client remains pinned to that specific server instance.

This walkthrough focuses on The Real-Time Problem: Bypassing HTTP Polling.

Before making a design choice, clarify:

  • Standard HTTP is built on a strict Request-Response lifecycle.
  • The client initiates a TCP connection, sends an HTTP request, the server processes it, returns a response, and the connection is closed (or kept alive for subsequent requests).
  • The server cannot initiate communication or push data to the client without a prior request.

Stage 2 — Server-Sent Events (SSE): Mono-Directional Streaming

  • Server-Sent Events (SSE) is a standard web technology that allows a server to stream text-based data to clients over a persistent HTTP connection.
  • How it works: The Event Stream Unlike WebSockets, SSE does not upgrade the connection to a new protocol.
  • The client opens a request, and the server responds with a specific MIME type: text/event-stream .
  • The server keeps this connection open indefinitely.

Stage 3 — Deep Dive: Connection Management and Heartbeats

  • In a high-scale real-time system, managing connection state is the primary challenge.
  • Because TCP connections can drop silently (e.g., when a mobile device switches towers), both WebSockets and SSE need mechanisms to detect dead connections and free server resources.
  • WebSockets Ping/Pong The WebSocket protocol includes built-in control frames for connection checks: - The server periodically sends a Ping frame.
    • The client must immediately respond with a Pong frame.

Stage 5 — Backpressure and Slow Consumers

  • A server that produces faster than a client consumes will accumulate buffered messages.
  • Set a maximum outbound buffer per connection.
  • For replaceable updates such as cursor positions, coalesce to the newest value.
  • For durable events, disconnect a slow consumer and let it resume from the event log.

End-to-end outcome

After working through the stages, you should be able to explain:

    • A persistent connection is not a durable message guarantee.
    • SSE simplifies one-way delivery and resume; WebSockets enable richer interaction at higher operational cost.
