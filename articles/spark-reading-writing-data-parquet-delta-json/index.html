Constraints & Assumptions

  • At a 60-second batch interval, 500 output partitions, and 10 micro-batches per hour, a single streaming job generates 300,000 small files per hour.
  • Lesson 1: Every JSON query is a full table scan, always.
  • The most common mistake in new Spark pipelines is leaving raw event data in JSON because "it's easier to debug." Easier to debug, yes — but it costs full-table I/O on every query.

This walkthrough focuses on The Team That Turned a 500 GB Daily Scan into an 8 GB Query.

Before making a design choice, clarify:

  • A platform analytics team at a mid-size SaaS company had a daily pipeline that read the previous seven days of raw user-event data from S3 and computed a set of funnel metrics.
  • The data was stored as gzipped JSON — one file per hour per region — totalling approximately 500 GB.
  • The pipeline ran for ninety minutes every morning, used forty executors, and cost the team about $180 per run on their cloud cluster.

Stage 2 — Parquet Internals, the Delta Transaction Log, and How Partition Pruning Works

  • Parquet's Columnar Layout: Row Groups, Column Chunks, and Statistics A Parquet file is divided horizontally into row groups — each row group is a horizontal slice of the data, typically 128 MB.
  • Within a row group, data for each column is stored contiguously as a column chunk .
  • Column chunks are further divided into pages of approximately 1 MB each, which are the unit of compression and encoding.
  • Every column chunk stores column statistics in the Parquet footer: the minimum and maximum values of that column across all rows in the row group.

Applies caching to the decision above.
