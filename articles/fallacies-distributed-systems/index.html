Stage 1 — What Makes a System "Distributed" in the First Place

  • Before the fallacies can bite you, you need to know what kind of system exposes you to them.
  • A distributed system is any application where components run on separate machines and communicate over a network.
  • That sounds obvious — until you realise it covers microservices, mobile apps talking to a backend, two data centre regions sharing a database, and even a monolith that makes third-party API calls.
  • The key insight: a network call is fundamentally different from a function call.
🧠 Applied Concept
Distributed Systems & Storage advanced

Quorum Consistency & Raft Consensus

↗

Distributed databases replicate data across N nodes for fault tolerance. Quorum math (Read Nodes + Write Nodes > Total Nodes) guarantees that any read operation overlaps with at least one node containing the latest write.

Stage 2 — Network Fallacies 1–4: Reliability, Latency, Bandwidth, and Security

  • Fallacy 1: The network is reliable.
  • A single function call that succeeds 99.9% of the time fails once every 1,000 requests, and distributed systems call each other thousands of times per second.
  • Design response: Retry with exponential backoff.
  • Use circuit breakers (Hystrix, Resilience4j).
🧠 Applied Concept
Software Design & Architecture intermediate

Circuit Breakers & Resilience Patterns

↗

Circuit Breakers monitor remote service call failure rates. If downstream failures exceed a threshold (e.g. 50%), the breaker trips to OPEN, instantly returning fallback responses instead of stalling threads.

Stage 3 — Infrastructure Fallacies 5–8: Topology, Administration, Cost, and Compatibility

  • Fallacy 5: Topology doesn't change.
  • Auto-scaling adds and removes instances.
  • Hardcoding IP addresses breaks as soon as a node is replaced.
  • Design response: Use service discovery (Consul, Kubernetes DNS, AWS Cloud Map).

Stage 4 — From False Assumption to Production Outage

  • Every fallacy follows the same lifecycle: the assumption goes unchallenged in local development, test environments mask the problem, and then production traffic amplifies the gap until something fails.
  • The painful part: teams almost always reach R — but only after the outage forces their hand.
  • The goal of knowing these fallacies is to reach R before the first incident, not after.

Distributed Systems & Storage intermediate

In-Memory Caching & Event Loop Architecture

↗

Caching stores high-frequency read data in fast RAM instead of slow disk/network databases. Redis achieves sub-millisecond QPS by operating a single-threaded event loop paired with OS epoll I/O multiplexing, completely eliminating thread locking contention.
